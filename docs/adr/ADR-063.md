### ADR-063: 동기화 실패는 인라인 문단이 아니라 토스트 — 배치 기준과 원인 보존 (구현 완료, 2026-07-30)

**배경**: [[ADR-062]]가 실패 표시의 *껍데기*(공용 `ErrorState`)와 *문구 어미*를 정했다. 남은 질문은 **어디에 띄우는가**다. 실패 문구 전수 조사(2026-07-30)에서 같은 성격의 실패가 자리마다 다른 형태였다 — 스케줄러 3화면은 헤더 아래 인라인 문단, 저장 실패는 토스트, 보스 수익의 파티원 수는 카드 안 인라인 문단인데 그 내용이 예외 메시지 원문이었다.

조사에서 나온 판정 기준은 하나였다.

> **그 문구가 사라진 자리에 남는 것이 있는가.**

남는 게 있으면 실패는 **이벤트**이므로 토스트로 옮긴다. 문구 자체가 그 자리의 **내용**이면(그리드 자리·모달 본문·설정 행의 값) 옮기는 순간 빈 칸이 남으므로 인라인으로 둔다.

**결정**:

1. **스케줄 동기화 전체 실패(`status === 'error'`)를 토스트로 옮긴다.** 스케줄러 3화면의 인라인 문단(`ContentScreen`·`BossScreen`·`BossProfitScreen`)을 걷어낸다.
   - 근거: 새로고침 옆 "n분 전"(`formatSyncedAt`)이 지속 상태를 이미 담당하므로 인라인 문단은 실패 사실만 중복해 말하고 있었다. 게다가 인라인 문단에는 버튼을 붙일 자리가 없어 사용자가 새로고침 아이콘을 스스로 찾아야 했다.
   - 4곳에 하드코딩돼 있던 폴백 문구("오류가 발생했습니다")도 함께 사라진다 — 토스트 호출이 한 곳으로 모이면서 `error === null` 분기 자체가 없어진다.

2. **원인을 버리지 않는다.** 스토어 5곳이 `catch` 에서 잡은 에러를 버리고 `{ kind: 'network' }` 를 하드코딩하고 있었다. `toScheduleSyncError(error)` 를 통과시킨다.
   - 그 전까지 화면 레벨 `error` 는 **항상 network** 였다 — 401/429가 화면에 도달할 경로가 아예 없었다. `character/list` 가 401로 실패해도 "네트워크 오류가 발생했습니다"로 표시돼, 사용자가 통신을 의심하며 새로고침을 반복하게 만들었다.
   - `.catch(() => null)` 로 원인을 통째로 버리던 두 곳(`refresh` 의 부분 동기화 경로)은 `then(onFulfilled, onRejected)` 로 결과와 에러를 함께 들고 오게 바꿨다.

3. **토스트 액션은 원인이 실제로 풀리는 것만 준다**([[ADR-062]] 결정 3과 같은 판단).

   | 원인 | 문구 | 액션 |
   |---|---|---|
   | `invalidApiKey` | API 키가 유효하지 않습니다 | **설정 열기** |
   | `rateLimited` | 잠시 후 다시 시도해주세요 | **없음** (지금 누르면 또 429다) |
   | `network` | 네트워크 오류가 발생했습니다 | 다시 시도 |

   `invalidApiKey` 의 "설정 열기"로 스케줄러 3화면에서도 *설정 진입 유도*가 해결된다([[ADR-062]]가 피커에서 한 것의 연장).

4. **파티원 수 저장 실패(보스 수익 카드 안)를 토스트로 옮긴다.** 앱에서 **유일하게 예외 메시지를 그대로 렌더하던 자리**였다(`BossProfitScreen` 의 `setError(err.message)`). 개발자용 문구(`setPartySize: …`)와 SQLite 네이티브 원문이 사용자에게 새고 있었다.
   - 문구는 보스 관리 화면(`BossManageScreen`)과 같은 "파티원 수를 저장하지 못했습니다" — 같은 동작의 두 경로가 통일된다.
   - 카드 안 인라인 문단이 없어져 행 높이가 튀지도 않는다.

5. **일부 캐릭터만 실패한 경우도 토스트로 옮기되, 이름 대신 인원 수를 싣는다.** `Toast` 본문은 `truncate` 라 이름을 나열하면 잘린다 — "일부 캐릭터를 불러오지 못했습니다 (2명)".
   - 어느 캐릭터인지는 잃는다. 캐릭터 카드 자체에 표식을 붙이는 것이 정답이지만 별도 작업이다(이슈 #78 B).

6. **토스트를 띄우는 위치는 스토어가 아니라 화면(공용 훅)이다.** `features/schedule-sync/use-sync-error-toast.ts` 의 `useScheduleSyncErrorToast`·`useStaleCharactersToast`.
   - 스토어에서 띄우면 실패마다 정확히 한 번이라 중복 걱정이 없지만, `invalidApiKey` 의 액션이 라우터를 필요로 한다. 스토어에서 `window.location` 으로 이동하면 문서 전체가 리로드돼 네이티브 SQLite 커넥션이 stale하게 남는다([[ADR-050]]).
   - 중복 방지: 스토어가 실패마다 **새 객체/새 배열**을 `set` 하므로 그 값 자체를 `useEffect` dep과 ref 가드 키로 쓴다. 같은 종류가 연달아 실패해도 새 객체라 다시 알리고(재시도를 눌렀는데 무반응이면 안 된다), 같은 값으로 재렌더될 때는 띄우지 않는다. ref 가드는 StrictMode의 effect 이중 호출(dev)까지 함께 막는다.

**남는 인라인 실패 문구** — 전부 "그 자리의 내용"이라는 공통점을 갖는다.

| 자리 | 왜 남는가 |
|---|---|
| 캐릭터 관리 피커 (`ErrorState`) | 그리드가 들어갈 자리의 내용. 토스트로 옮기면 모달 본문이 빈 상자가 된다 |
| 온보딩 캐릭터 선택 (`ErrorState`) | 위와 같고, 이 단계를 넘겨야 앱을 쓸 수 있는 차단 상태다 |
| 설정 계정 플로우 (`AccountFlowStatus`) | 상태 머신의 한 상태로 모달 본문 전체를 차지하고, 재시도 버튼이 유일한 진행 수단 |
| 조회 불가 안내 (`UnavailableNotice`) | 실패가 아니라 API 제약 설명. 사라지면 그 기간이 왜 비었는지 알 수 없다 |
| 설정 상태 행의 값 (OTA·캐시 용량) | 행의 "값" 자리. 지금 상태를 계속 보여주는 것이 목적 |
| 보스 수익 기간 백필 실패 | 이번 범위 밖 — 기간 라벨 바로 아래 위치라 맥락과 붙어 있다(추후 재검토) |

**트레이드오프**:

- **토스트는 사라진다.** 화면을 나갔다 오면 실패 사실이 남지 않는다 — 다만 "n분 전" 표기가 남아 마지막 성공 시점은 계속 읽힌다(그것이 이 전환의 전제다).
- **일부 캐릭터 실패에서 이름을 잃는다.** 지금은 선택되지 않은 캐릭터의 실패를 알 방법이 아예 없던 것보다 낫다고 본다.
- **429에 액션이 없어 사용자가 할 수 있는 게 없다.** 문구가 기다리라고 말하는 것으로 충분하다고 봤다(잠금 시각을 추적하는 상태를 새로 만들지 않는다).
- **원인 보존이 표시를 바꾼다.** 전에 "네트워크 오류"로 뭉개졌던 401·429가 이제 제 이름으로 뜬다. 사용자에게는 개선이지만, 그 문구를 기대하던 테스트는 함께 고쳐야 했다.
