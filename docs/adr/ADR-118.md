# ADR-118 — 설정 화면을 본화면 5행 + 하위 페이지 3으로 계층화한다

> 🟢 **ACTIVE — 유효.** 현행 RN 앱에 적용되는 결정이다.

**날짜**: 2026-08-09
**상태**: **구현 완료(2026-08-09, 이슈 #135 · #161) · 실기기 미검증**. 결정 10개가 전부 구현됐고
폐기된 결정은 없다. 설계가 정하지 않아 구현이 정한 것 다섯은 아래 *"구현하며 정정한 것"* 에 적었고

[[ADR-119]](개발 노트 데이터) · 이슈 #135 · #161

## 맥락

`SettingsScreen.tsx:49-79` 는 **카드 하나에 성격이 다른 네 행**을 그룹핑 없이 늘어놓는다.

```
[카드]  계정 변경          →  모달 (계정 재선택 · 예열 · 캐릭터 재선택)
        스케줄 관리 방법    →  모달 (값 선택)          + 현재값 배지
        테마               →  모달 (값 선택)          + 현재값 배지
        연결 해제          →  확인 모달 (파괴적)       위험 색
[섹션]  데이터 관리 / 캐시 데이터 삭제                  위험 색 + 총 용량
[섹션]  앱 업데이트 / 현재 버전 · 상태 · 확인 버튼
[footer] 개인정보 처리방침 링크 · 버전 · 저작권 · 출처 표기 · 비제휴 고지
```

세 가지가 겹쳐 있다.

1. **값을 고르는 행**(스케줄 관리 방법·테마)과 **되돌릴 수 없는 행**(연결 해제)이 **같은 카드 안에서
   구분 없이 인접**한다. 위험 색 하나가 그 구분을 전부 지고 있다.
2. **행의 우측 표기가 규칙 없이 갈린다.** `SettingsRow` 가 `props.rightContent ?? (showChevron && <ChevronRight/>)`
   라 **값이 있으면 chevron 이 사라진다** — 그래서 같은 "탭하면 모달이 열린다"는 세 행 중 `계정 변경`
   에만 화살표가 있고 나머지 둘에는 없다. 화살표의 유무가 **동작이 아니라 값의 유무**를 말하고 있다.
3. **개인정보 처리방침 링크가 정적 고지 문구 사이에 끼어 있다.** 지금은 그 어색함을 색
   (`text-text-muted`)과 밑줄로 달랜다 — 규칙이 아니라 예외로 버티는 자리다.

`docs/features/settings.md` 의 열린 질문 *"설정 화면 섹션 순서/그룹핑(계정/알림/개인정보 등) 미논의"*
가 정확히 이 이슈(#135)이고, 여기에 개발 노트 화면(#161)이 새 행 하나로 들어온다.

### 시안 셋을 견줬다

| | A — 한 카드 5행 | B — 카드 둘 (채택) | C — 카드 둘 + 섹션 제목 |
|---|---|---|---|
| 두 무리의 구분 | 없음 (한 덩어리로 읽힘) | 카드 경계 | 카드 경계 + 제목 |
| 세로 | 가장 짧다 | +8px (카드 간격) | +약 48px (제목 2줄) |
| 읽는 사람이 얻는 것 | — | "여기까지가 값, 여기부터가 화면" | 제목 문구 |

- **A 를 버린 이유**는 이 ADR 이 고치려는 문제가 *"성격이 다른 것들이 한 덩어리로 읽힌다"* 인데
  A 는 행만 늘리고 그 덩어리를 그대로 둔다는 것이다. 짧은 것이 목적이 아니다.
- **C 를 버린 이유**는 제목을 실제로 써 보니 얻는 것이 없어서다. 두 무리를 덮는 제목은
  「동작·표시」/「관리·정보」 정도가 되는데, 이것은 **행 이름(`테마`·`앱 정보`)보다 덜 구체적**이다.
  덜 구체적인 말을 더 구체적인 말 위에 얹으면 읽는 사람은 그 줄을 건너뛴다. 반면 기존의
  「데이터 관리」·「앱 업데이트」 제목은 **그 아래 행이 하나뿐**이라 제목이 사실상 행 이름이었다 —
  그 두 섹션이 하위 페이지로 내려가면서 제목도 함께 사라진다.

## 결정

### 결정 1 — 본화면은 카드 둘 · 5행이다. 섹션 제목은 달지 않는다

```
설정

[카드 1]  스케줄 관리 방법                    자동 ›
          테마                              혼테일 ›
[카드 2]  개발 노트                                ›
          계정 및 데이터                    1.2 MB ›
          앱 정보                            1.0.3 ›

[footer]  v1.0.3
          © 2026 메이플 루틴
          Data based on NEXON Open API
          Maple Routine is not associated with NEXON Korea
```

- **위 카드 = 값을 고르는 행**(모달이 뜨고, 고르면 그 자리에서 끝난다). **아래 카드 = 화면이 넘어가는
  행**(하위 페이지로 이동한다). 두 무리를 가르는 것은 **카드 경계뿐**이다.
- 제목을 달지 않는 이유는 위 표의 C 항목 그대로다 — 두 무리를 덮는 제목이 행 이름보다 덜 구체적이라
  읽는 사람이 얻는 것이 없다.

### 결정 2 — 하위 페이지 셋을 신설한다. 골격은 관리 페이지와 같다

| 경로 | 화면 | 안에 들어가는 것 |
|---|---|---|
| `/settings/release-notes` | 개발 노트 | 버전별 변경 목록([[ADR-119]]) |
| `/settings/account-data` | 계정 및 데이터 | 계정 변경 · 캐시 데이터 삭제 · 연결 해제 |
| `/settings/about` | 앱 정보 | 현재 버전 · 상태 · 업데이트 확인 · 개인정보 처리방침 |

- 골격은 **기존 `/boss/manage`·`/content/manage` 와 같다**([[ADR-035]] 결정 18) — 공용 `PageHeader`
  ([[ADR-094]]) + 좌측 `ArrowLeft`(`aria-label="뒤로"`) + `useScreenNavigate`([[ADR-098]] 결정 1). **새 셸을
  만들지 않는다**: 이미 두 화면이 쓰는 골격이 있고, 그 골격은 `fixed` 헤더·실측 spacer·스크롤 소유
  ([[ADR-085]]·[[ADR-099]]·[[ADR-112]])까지 실기기에서 여러 번 틀린 끝에 얻은 것이라 다시 짤 이유가 없다.
- 라우트는 `App.tsx` 의 `/settings` **형제**로 놓고 `isCompleted` 가드를 똑같이 건다. 중첩 라우트로
  두지 않는 이유는 [[ADR-077]] 이 `/profit/drops` 를 중첩으로 만든 근거 — *"부모가 언마운트되면
  펼침·기간·스크롤을 잃는다"* — 가 여기엔 없기 때문이다. 설정 본화면은 잃을 상태가 없다.
- **푸시·팝 전환과 스와이프 백은 이 ADR 범위 밖이다.** 이슈 #166 이 네 화면(`/boss/manage`·
  `/content/manage` + 여기 셋)에 한꺼번에 입힌다 — 화면마다 다른 전환을 붙이면 그 작업이 통합이
  아니라 정리부터 하게 된다.

### 결정 3 — 파괴적 행은 `/settings/account-data` 안에서 별도 카드로 내린다

```
‹  계정 및 데이터

[카드 1]  계정 변경                              ›
[카드 2]  캐시 데이터 삭제                   1.2 MB      ← 위험 색, chevron 없음
          연결 해제                                     ← 위험 색, chevron 없음
```

- **이슈 #135 가 요구한 분리가 일어나는 자리가 정확히 여기다.** 본화면에서 `연결 해제` 를 없애는
  것만으로는 분리가 아니다 — 옮긴 곳에서 다시 `계정 변경` 과 붙으면 같은 문제가 한 층 아래로
  내려갈 뿐이다.
- **아래 카드에 제목을 달지 않는다.** 「위험한 작업」 같은 제목을 검토했으나, 위험 색 라벨 두 개와
  카드 경계가 이미 그 말을 하고 있어 제목은 같은 사실을 세 번째로 말하는 것이 된다. 결정 1 과 같은
  기준이다.
- 캐시 삭제와 연결 해제가 **지우는 범위가 서로 다르다**는 사실은 그대로다([[ADR-052]]·[[ADR-058]]) —
  같은 카드에 있다고 같은 것이 아니고, 각 확인 모달이 그 범위를 말한다.

### 결정 4 — 행의 우측 표기를 5종으로 고정한다

| 종류 | 왼쪽 | 오른쪽 | 쓰는 곳 |
|---|---|---|---|
| **설정 행** | 라벨 | 현재값 배지 **+** chevron | 스케줄 관리 방법 · 테마 |
| **이동 행** | 라벨 | 대표값(있으면) **+** chevron | 개발 노트 · 계정 및 데이터 · 앱 정보 · 계정 변경 |
| **표시 행** | 라벨 | 값 평문, **탭 불가** | 현재 버전 · 상태 |
| **외부 링크 행** | 라벨 | 외부 링크 아이콘 | 개인정보 처리방침 |
| **실행 행** | **위험 색** 라벨 | 보조 수치, **chevron 없음** | 캐시 데이터 삭제 · 연결 해제 |

핵심은 **`SettingsRow` 의 배타(`rightContent ?? chevron`)를 병기로 바꾸는 것**이다. 지금은 값이 있으면
화살표가 사라져서, 화살표가 *"이 행에 값이 있는가"* 를 말한다 — 사용자가 알고 싶은 것은 그것이 아니다.

> **chevron 이 있으면 누르면 무언가 열린다. 없는 위험 색 행은 누르면 지운다.**

- **`showChevron={false}` 를 남겨 두고 호출부마다 판단하는 안**을 버린 이유: 그것이 지금 상태다.
  판단이 호출부에 흩어져 있으면 새 행이 생길 때마다 다시 틀린다.
- **모든 행에 chevron 을 다는 안**을 버린 이유: 위험 색 행에 화살표가 붙으면 *"다음 화면이 있다"* 로
  읽혀 확인 모달이 나타나는 것이 의외가 된다. 화살표의 유무가 실제로 동작을 가른다.
- 표시 행이 탭 불가인 것은 [[ADR-060]] 계열의 같은 원칙이다 — 아무 일도 일어나지 않는 것을 누를 수
  있게 그리지 않는다.

### 결정 5 — 카테고리 행은 대표값 하나를 미리 보여준다

| 행 | 대표값 | 출처 |
|---|---|---|
| 계정 및 데이터 | 캐시 총 용량 | `getCacheDataSizes()` 두 그룹의 합([[ADR-058]] 결정 8) |
| 앱 정보 | 현재 버전 | 실행 중인 OTA 번들 버전(`currentVersion ?? packageJson.version`) |
| 개발 노트 | **없음 — 비운다** | — |

들어가지 않고도 안을 짐작하게 하는 값이다. 캐시 총 용량은 지금 본화면 캐시 행이 이미 보여주던
값이라 **정보가 줄지 않는다** — 행이 한 층 올라가면서 값도 함께 올라간다.

**개발 노트를 비우는 이유**는 후보가 전부 틀린 말을 하기 때문이다. "최신 버전"은 바로 아래 `앱 정보`
행과 같은 값이라 중복이고, "n개"는 개수가 늘어난다고 사용자에게 의미가 생기지 않으며, "새 소식"류의
정적 문구는 값이 아니라 장식이다. **없는 대표값을 지어내지 않는다.**

### 결정 6 — `계정 변경` 행에는 현재값을 두지 않는다

`accountId` 는 넥슨이 주는 **불투명 문자열**이라 그대로 보여줄 수 없고, 대표 캐릭터 이름은
**파생·변동값**이다(프로브·캐시 상태에 따라 달라지고, 429·조회 불가에서는 아예 없다 —
[[ADR-113]]·[[ADR-116]]). 확실하지 않은 것을 단정해 보여주느니 chevron 만 둔다.

이것은 결정 5 와 모순이 아니라 **같은 기준의 반대편**이다 — 대표값은 "확실히 아는 값이 있으면
보여준다"이지 "칸을 채운다"가 아니다.

### 결정 7 — 개인정보 처리방침 링크가 footer 에서 `/settings/about` 의 행으로 간다

옛 정책(`settings.md` — *"위치는 footer 맨 위 · `text-text-muted` + `underline`"*)을 **폐기한다.**

- 그 정책은 *"정적 고지 문구 사이에 끼면 링크로 안 읽힌다"* 를 색과 밑줄로 달래던 것이다. **독립된
  행이 되면 그 문제 자체가 없어진다** — 달래던 장치(한 단계 밝은 색·밑줄)도 함께 필요 없어진다.
- **스토어 요건은 그대로 충족된다.** Play 사용자 데이터 정책이 요구하는 것은 *"앱 안에 링크"* 이지
  *"첫 화면에 링크"* 가 아니다([../foundation/release.md](../foundation/release.md)). 설정 → 앱 정보는
  두 번의 탭이고, 스토어 등록정보 쪽 URL 은 이 변경과 무관하게 그대로다.
- **아이콘은 chevron 이 아니라 외부 링크 표식이다**(결정 4 의 넷째 종류). 이 행은 앱 안에서 다음
  화면을 여는 것이 아니라 **앱을 떠나 시스템 브라우저로 간다** — chevron 을 쓰면 다른 이동 행과 같은
  약속을 하고는 다른 일을 한다. 여는 방식은 `ApiKeyForm` 의 `openapi.nexon.com` 링크와 같은
  `<a target="_blank" rel="noopener noreferrer">` 이고, 별도 브라우저 플러그인을 들이지 않는다.
- **URL·본문 정책은 불변**이다 — `mapleroutine.store/privacy`, 앱 안에 정책 본문 사본을 두지 않는다
  (법적 문서를 두 벌로 만들지 않는다, [site.md](../features/site.md)).

### 결정 8 — 본화면 footer 는 고지 4줄만 남는다

버전 · 저작권 · `Data based on NEXON Open API` · 비제휴 고지. 결정 7 이 링크를 빼가면서 **전부 읽고
끝나는 정적 문구**가 되어 톤(`text-text-disabled`)이 균일해진다 — 지금 한 줄만 밝은 색인 이유가
"이것만 눌러야 해서"였고, 그 예외가 사라진다.

**그리고 [[ADR-098]] 의 고정 헤더 재판단이 필요 없어진다.** 그 ADR 결정 3 은 설정에 `PageHeader` 를
두지 않으면서 *"행이 늘어 세로가 길어지면 그때 다시 판단할 것"* 이라는 조건을 달아 뒀는데, 이
개편은 **본화면 행을 4 → 5 로 하나 늘리면서 섹션 둘(캐시·앱 업데이트 = 4행 + 제목 2줄 + 버튼 하나)과
footer 한 줄을 내려보낸다.** 순증이 아니라 순감이라 그 조건에 걸리지 않고, 5행 + 4줄이면 스크롤
자체가 생기지 않는다(같은 ADR 이 잰 필요 높이 835pt 기준). **본화면은 계속 고정 헤더 없이 간다.**

하위 페이지 셋은 반대로 `PageHeader` 를 쓴다(결정 2) — 뒤로 가기 버튼이 필요하고, 그 셸은 이미
`fixed` + 실측 spacer 라 [[ADR-098]] 이 막은 결함을 물려받지 않는다.

### 결정 9 — 넣지 않는 것 둘 (사용자 결정 2026-08-09)

**⑴ 개발 노트 안 읽음 표시(뱃지·점)를 두지 않는다.**
구현하려면 *"마지막으로 본 버전"* 을 저장할 Preferences 키가 하나 늘고, 그 키는 [[ADR-052]]
`KEEP_KEYS` 판단([[ADR-058]] 차집합 규칙)에도 걸린다 — 사용자 설정인가 캐시인가를 정해야 한다.
얻는 것은 "새 노트가 있다"는 신호 하나인데, 이 앱은 **업데이트 모달이 이미 그 순간에 무엇이 바뀌는지
말한다**([[ADR-119]] 결정 1). 값에 비해 늘어나는 상태가 크다.

**⑵ `API 키 변경` 행을 부활시키지 않는다.**
[[ADR-115]] 결정 8 이 *"#135 와 함께 본다"* 로 미룬 미정을 여기서 닫는다.

- 무효 키(400 `OPENAPI00005`·401/403)와 429 는 **이미 해결돼 있다** — 닫을 수 없는 안내 모달 → `확인`
  → 키 입력 화면 + 저장된 `apiKey` 삭제, 그리고 뒤 단계는 저장된 값으로 재개([[ADR-115]] 결정 10·4,
  [[ADR-116]] 결정 1). 사용자가 설정을 뒤져 키를 바꿀 필요가 없다.
- 그래서 남는 경우는 **"오류가 아닌데 자발적으로 키를 갈아타는"** 드문 경우뿐이다(다른 넥슨 계정의
  키로 이동, 서비스 단계 키로 승급 — 후자는 429 안내가 이미 사용자를 그리로 보낸다). 그 하나를 위해
  설정 구조를 정리하는 이 phase 에서 행을 하나 더 늘리지 않는다.
- **`useSettingsStore.changeApiKey` 는 지우지 않는다** — 로직·테스트가 살아 있고 **배선만 없는 상태로
  계속 남는다.** 되살릴 때 UI 만 붙이면 되고, 지우면 그 판단을 다시 해야 한다.

### 결정 10 — 업데이트 상태 문구 `최신입니다` → `최신 버전입니다`

`AppUpdateSection` 의 `up-to-date` 문구. `현재 버전` 행 바로 아래 `상태` 행에 놓이는 값이라 주어가
생략되면 *"무엇이 최신인지"* 가 문장 안에 없다 — 한 단어를 더해 그 자리에서 읽히게 한다. 다른 상태
문구(`확인에 실패했습니다`·`이 플랫폼에서는 지원되지 않습니다`)와 같은 하십시오체 어미 규칙
([[ADR-062]])은 그대로다.

## 이유

이 개편이 겨누는 것은 "행이 많다"가 아니라 **"성격이 다른 것이 구분 없이 인접한다"** 이고, 처방은
전부 그 한 문장에서 나온다 — 값 고르기와 화면 이동을 카드로 가르고(결정 1), 되돌릴 수 없는 것을 한
층 아래 별도 카드로 내리고(결정 3), 우측 표기가 **값의 유무가 아니라 동작의 종류**를 말하게 한다
(결정 4). 결정 5·6 은 그 규칙을 값에도 적용한 것이다 — 아는 값은 미리 보여주고, 모르는 값은 칸을
비운다.

## 기각안

- **한 카드 5행(시안 A)** — 행만 늘고 덩어리는 그대로다.
- **섹션 제목 부착(시안 C)** — 제목이 행 이름보다 덜 구체적이다.
- **`연결 해제` 를 본화면에 남기고 캐시 삭제만 내리기** — 본화면에 위험 색 행이 하나라도 남으면
  결정 1 의 "값을 고르는 카드"가 다시 혼종이 된다.
- **하위 페이지를 모달로** — 계정 및 데이터는 안에서 또 모달(계정 선택·캐시 삭제 확인·연결 해제
  확인)을 열어야 해서 모달 위 모달이 된다. 개발 노트는 세로가 길어 모달에 안 들어간다.
- **하위 페이지를 `/settings` 중첩 라우트로** — [[ADR-077]] 이 중첩을 고른 근거(부모 상태 보존)가
  여기엔 없다.
- **모든 행에 chevron** / **`showChevron` 판단을 호출부에 남기기** — 결정 4 참조.
- **개인정보 처리방침을 앱 안 화면으로** — 법적 문서가 두 벌이 된다(불변 정책).
- **개발 노트 대표값에 "최신 버전" 표기** — 바로 아래 `앱 정보` 행과 같은 값이다.

## 트레이드오프

- **캐시 데이터 삭제와 앱 업데이트 확인이 한 탭 멀어진다.** 둘 다 자주 쓰는 기능이 아니고(캐시 삭제는
  파괴적이라 오히려 멀어야 하며, 업데이트는 부팅 체크가 자동으로 돈다 — [[ADR-026]]), 대신 본화면이
  다섯 줄로 줄어 처음 여는 사람이 전체를 한눈에 본다.
- **화면 파일이 3개 늘어난다.** 라우트·가드·테스트가 각각 따라붙는다. 골격을 관리 페이지와 공유해
  새로 만드는 것은 내용뿐이다(결정 2).
- **개인정보 처리방침이 두 탭 안쪽으로 들어간다.** 스토어 요건은 충족하지만(결정 7) 발견성은 낮아진다 —
  법적 고지라기보다 "찾으면 있는 것"에 가까워진다.
- **`SettingsRow` 를 병기로 바꾸면 지금 화살표가 없던 두 행에 화살표가 생긴다**(스케줄 관리 방법·테마).
  행 오른쪽이 그만큼 붐비지만, 그 대가로 화살표가 처음으로 일관된 뜻을 갖는다.
- **본화면 footer 가 균일해지면서 버전 줄이 눈에 덜 띈다.** 같은 값을 `앱 정보` 행 대표값이 한 번 더
  말하므로(결정 5) 잃는 것은 없다.

## 범위 밖

- **푸시·팝 전환과 스와이프 백**(이슈 #166) — 네 화면에 한꺼번에.
- **크래시 리포팅 opt-in·알림 권한 재요청** — `settings.md` 의 후속 task 그대로.
- **개발 노트의 데이터 형식·배포 연동** — [[ADR-119]].
- **`changeApiKey` 배선** — 결정 9.

## 폐기

- [[ADR-104]] 결정 5 의 *"테마 행 오른쪽은 현재 테마 이름 배지 **하나뿐**"* → 배지 **+ chevron** 병기
  (결정 4). **색 표식을 두지 않는다는 그 결정의 본론은 유효하다** — 바뀌는 것은 배지 옆에 화살표가
  붙는다는 것뿐이고, 그것은 테마 행의 규칙이 아니라 모든 행에 걸리는 규칙이다.
- `settings.md` 의 *"개인정보 처리방침 링크는 footer 맨 위 · `text-text-muted` + `underline`"* →
  `/settings/about` 의 행(결정 7).
- `settings.md` 의 *"`SettingsRow` 는 `rightContent` 가 있으면 chevron 을 그리지 않는다"* → 병기(결정 4).
- [[ADR-115]] 결정 8 의 **미정 상태**가 닫힌다 → *"이번에는 부활시키지 않는다"*(결정 9). `changeApiKey`
  를 배선하지 않고 남긴다는 그 결정의 내용 자체는 **그대로 유지**된다.

## 구현하며 정정한 것

**결정 본문은 고치지 않았다.** 아래는 step 1~8 이 구현하며 설계가 정하지 않아 구현이 정한 것들이다.
**설계와 어긋난 결정은 없다** — 열 개가 적힌 대로 구현됐다.

### 1. 결정 4 — 외부 링크 행은 `SettingsRow` 의 변형이 아니라 **별도 컴포넌트**다

결정 4 는 우측 표기 5종을 표로 고정했을 뿐 그것을 **한 컴포넌트로 만드는지**는 말하지 않았다.
구현은 `SettingsLinkRow` 를 따로 두고, 공유 골격만 `row-class.ts` 의 `SETTINGS_ROW_CLASS` 로 뺐다.

- **시맨틱이 다르다** — 외부 링크 행은 `<button>` 이 아니라 `<a target="_blank" rel="noopener noreferrer">`
  여야 한다(결정 7). 한 컴포넌트로 합치면 `onClick` 이 선택 필드가 되어 호출부가 어느 쪽인지 타입으로
  알 수 없다.
- **골격이 컴포넌트 파일이 아니라 별도 파일인 이유는 lint 다** — 컴포넌트 파일이 컴포넌트 아닌 값을
  함께 export 하면 fast refresh 가 깨진다(`react-refresh/only-export-components`).
  `Button/variants.ts` 가 별도 파일인 것과 같은 판단을 그대로 따랐다.

### 2. 결정 2 — 「앱 업데이트」 제목은 **컴포넌트가 껍데기를 벗는 방식**으로 사라졌다

결정 2 는 *"섹션 제목은 화면 제목이 대신한다"* 까지만 적었다. 구현은 `AppUpdateSection` 이 스스로
`<section>` + `<h2>앱 업데이트</h2>` 를 그리던 것을 **떼고 `Card` 만 반환**하게 했다 — 호출부가 제목을
숨기는 프롭을 받는 방식이 아니다(그러면 "제목을 그릴 수도 있다"는 죽은 분기가 남는다).

같은 계열로 **`CacheDataSection.tsx` 는 옮겨진 것이 아니라 삭제됐다.** 그 컴포넌트의 로직(용량 조회·
`isClearing`·`clearCacheDataAndReload`·`reload` 주입)이 `SettingsAccountDataScreen` 안으로 흡수되고
테스트 12케이스는 새 화면 테스트로 이관됐다(커버리지 손실 0). 껍데기만 남을 컴포넌트를 살려 두면
"두 자리 중 어디를 고쳐야 하는가"가 생긴다.

### 3. 결정 3 — 모달 셋은 카드 밖이자 **셸 밖**의 형제다

결정 3 은 카드 배치까지만 정했다. 구현이 정한 것은 `AccountModal`·`CacheClearConfirm`·
`DisconnectConfirm` 이 **`ScreenScroll` 바깥**에 산다는 것이다.

- 카드 **안**에 두면 `divide-y` 가 형제로 잡아 구분선이 하나 더 그려진다.
- `ScreenScroll` **안**에 두면 그 `fixed` 셸이 만든 스태킹 컨텍스트에 갇혀 오버레이가 탭바 아래로
  그려진다([[ADR-099]]).

### 4. 결정 5 — 대표값의 **조회 전 자리**를 `- KB` 로 잡는다

결정 5 는 값의 출처만 정했고 "아직 못 읽었을 때"를 말하지 않았다. 빈 문자열이면 값이 툭 나타나며
행이 밀리므로, [[ADR-061]] 결정 7 대로 값과 같은 폭·타이포의 자리표시를 둔다. 조회 실패도 같은
자리표시로 남는다(`.catch(() => {})` — 설정을 못 여는 실패가 아니다).

### 5. 미검증 3 이 **더 나빠진 방향으로** 확정됐다 — 캐시 용량을 두 번 읽는다

결정 5 는 대표값을 본화면으로 올렸고, 결정 3 의 하위 화면은 **자기 행에도 같은 값을 그린다.** 두
화면이 각각 마운트 시 `loadCacheDataSizes()` 를 부르므로 **설정 → 계정 및 데이터로 들어가면 조회가
2회**다(옛 구조는 `CacheDataSection` 마운트 1회).

- 값을 프롭·스토어로 물려 내리지 않은 이유는 하위 화면이 **직접 진입 가능한 라우트**이기 때문이다 —
  본화면을 거치지 않고 `/settings/account-data` 로 들어오면 물려받을 값이 없다.
- **여전히 미측정이다.** 체감 지연이 확인되면 그때 캐싱 위치를 정한다(이 ADR 은 그것을 정하지 않았다).

## 미검증

구현은 끝났고, 아래는 **눈과 실기기로만 판정되는 것들**이다. 1·2·4 는 설계 때와 같은 이유로 남았고
3 은 위 정정 5 로 조건이 바뀐 채 남았다.

1. **본화면이 정말 스크롤 없이 들어가는가** — 결정 8 의 계산은 [[ADR-098]] 이 잰 835pt 를 기준으로 한
   추정이고, 실제 5행 + 4줄의 높이는 **구현 후에도 재지 않았다**(jsdom 은 레이아웃을 계산하지 않는다).
2. **화살표 병기가 붐비지 않는가** — 배지 + chevron 이 좁은 폭(360px)에서 어떻게 보이는지는 눈으로만
   판정된다.
3. **캐시 총 용량 조회 비용** — 설정을 열 때마다 1회 + 하위 화면 진입 시 다시 1회(정정 5). SQLite +
   Preferences 왕복이고 체감 지연 여부는 미측정.
4. **두 탭 깊이의 개인정보 처리방침이 스토어 심사에서 문제가 되지 않는가** — 정책 문언상 충족하지만
   심사자 판단은 겪어 봐야 안다.

**구현 결과**(step 1~8 누적): 테스트 **2,756개/181파일** 통과(기준선 2,695/177 대비 +61, 새 파일 4) ·
build 성공 · lint **0 errors/17 warnings**(baseline 동일).
