# ADR-125 — 개발 노트 항목이 사용법 안내로 드릴다운한다 (버전 축 · 이미지는 번들)

- 상태: **결정 완료 · 구현 완료(글만) · 스크린샷 대기 · 실기기 미검증** (2026-08-10, 이슈 #198, 마일스톤 v1.0.4). 테스트 2,901개·lint 0 error·프로덕션 빌드 통과. **안내 셋의 이미지가 아직 0장**이고(사용자가 직접 촬영), 화면을 실기기·시뮬레이터에서 눈으로 본 적이 없다
- 관련: [[ADR-119]](릴리스 노트 진실 원천 한 벌 · 항목 단위 표식 · 카테고리 묶음. **이 ADR이 그 위에 얹힌다**) · [[ADR-118]](설정 계층 — 하위 페이지) · [[ADR-120]](스택 스크린 · 2단 스택 선례 · 청크는 탭 단위) · [[ADR-094]](`PageHeader`) · [[ADR-060]](빈 상태 크기) · [[ADR-092]](화면 청크 분할)
- 관련 문서: [features/settings.md](../features/settings.md) · [features/live-update.md](../features/live-update.md)

## 맥락

개발 노트([[ADR-119]])는 **무엇이 바뀌었는지 한 줄로 나열만** 한다.

```
v1.0.3                          2026-08-09
 기능
  · 개발 노트 추가 — 버전별 변경 내역 확인   ← 여기서 끝
```

한 줄은 *"바뀐 것이 있다"* 까지만 말하고, **그것이 화면 어디에 있고 어떻게 쓰는지는 말하지 않는다.**
새 기능일수록 이 간극이 크다 — 버그 수정은 한 줄로 충분하지만, 새로 생긴 화면은 한 줄을 읽어도
어디로 가야 하는지 모른다. 이 앱에는 기능 사용법을 설명하는 자리가 **한 군데도 없다.**

## 결정 1 — 축은 **버전**이다 (기능 카탈로그를 따로 두지 않는다)

두 안을 놓고 사용자가 골랐다.

| 안 | 성질 | 결과 |
|---|---|---|
| 기능별 상시 가이드 | 앱 기능 전체를 나열한 카탈로그 | 기각 |
| **버전별 새 기능 소개** | 릴리스 노트의 버전 축을 승계 | **채택** |

**채택 = 버전 축.** 기능 카탈로그는 릴리스 노트와 **별개의 축을 하나 더** 유지해야 하고, 두 축은
언젠가 반드시 어긋난다 — 기능을 고쳤을 때 노트에는 적고 카탈로그는 잊는 쪽이 정상적인 실패다.
버전 축은 이미 있는 것을 그대로 쓰고, 노트를 쓰는 사람이 **한 곳만** 고치면 된다.

대가는 *"지금 이 앱을 어떻게 쓰나"* 에 답하지 않는다는 것이다 — 오래된 기능은 옛 버전 카드 안에
묻힌다. 그 요구가 실제로 생기면 그때 카탈로그를 얹는다(**지금 짓지 않는다**).

## 결정 2 — 가이드 본문은 `release-notes.ts` **밖**에 산다

**항목에 본문을 직접 붙이려던 것을 뒤집는다**(이슈 #198 최초안 정정, 2026-08-10). 이유는 설계
취향이 아니라 **배포 경로가 깨지기 때문**이다.

`scripts/publish-live-update.mjs:33` 이 `src/data/release-notes.ts` 를 **Node 에서 직접 import**
한다(타입 스트리핑, [[ADR-119]] 결정 1 — 스크립트용 사본을 두지 않으려고 원천을 그대로 읽는다).
가이드 본문에는 이미지가 붙고(결정 4), 이미지는 `import img from '../assets/guide/x.webp'` 로
들어온다. **Node 는 `.webp` import 를 해석하지 못한다** — 넣는 순간 `npm run publish` 가 죽는다.

그래서 참조는 **id 문자열**로 끊는다.

```
src/data/release-notes.ts        items[].guideId?: string   ← 순수 데이터 유지, Node 가 읽는다
src/data/release-note-guides.ts  RELEASE_NOTE_GUIDES        ← 이미지 import + 본문. 앱만 읽는다
```

두 파일이 갈라질 위험은 **테스트가 막는다** — 양방향 참조 무결성(모든 `guideId` 에 가이드가 있고,
모든 가이드가 어느 항목엔가 물려 있다) + id 중복 금지. [[ADR-119]] 가 순서·중복·형식을 데이터
테스트로 강제한 것과 같은 방식이고, 같은 이유다: 런타임에 조용히 통과하는 것을 컴파일이 못 막으면
테스트가 막는다.

### 부수 효과 둘 — 둘 다 이득이다

1. **매니페스트가 안 커진다.** `latest.json` 의 `notes` 는 노트 텍스트만 나가고 가이드는 안 실린다. 업데이트 모달은 번들을 **받기 전** 에 뜨므로 어차피 이미지를 그릴 수 없다.
2. **개발 노트 목록 화면이 이미지 모듈을 안 건드린다.** `›` 를 그릴지는 `guideId` 문자열 유무로 판정되므로, 목록 화면은 가이드 모듈을 import 하지 않는다 — 상세로 들어가야 비로소 이미지가 붙은 모듈이 온다.

## 결정 3 — 진입은 개발 노트 **드릴다운**, 라우트는 그 자식

```
/settings/release-notes             개발 노트
/settings/release-notes/:guideId    기능 안내   ← 자식
```

`/settings/about/privacy` 에 이어 이 앱 **두 번째 2단 스택**이다([[ADR-120]] 결정 11) — 부모 화면의
행에서 열리므로 중첩 라우트이고, 뒤로는 진짜 pop, 스와이프 백이 그대로 산다.

설정 본화면에 `기능 안내` 행을 신설하는 안은 **기각**(사용자 결정) — 같은 내용으로 가는 입구가
둘이 되고, [[ADR-118]] 이 2카드 5행으로 눌러 놓은 설정에 행이 하나 더 는다.

**`:guideId` 는 버전이 아니라 항목 식별자다.** 한 버전에 안내를 가진 항목이 여럿일 수 있고,
딥링크가 가리켜야 하는 것은 "그 버전"이 아니라 "그 기능"이다.

- 없는 `:guideId` 로 들어오면 `/settings/release-notes` 로 `replace` 한다. 옛 딥링크·오타의 착지점이 빈 화면이 되면 안 되고, 그렇다고 히스토리에 남겨 뒤로가기가 다시 그리로 가게 둘 이유도 없다.
- 화면 청크는 `screen-settings` 하나라([[ADR-120]] 결정 14) 상세로 밀어 넣을 때 **JS 추가 읽기가 없다.** 이미지는 별개 에셋이라 그릴 때 온다.

## 결정 4 — 이미지는 **앱 번들**에 넣고, glob 이 아니라 **명시적 import** 로 건다

원격(사이트·GitHub Pages) 로드는 **기각**(사용자 결정) — 번들은 안 늘지만 **오프라인에서 안내가
통째로 빈다.** 개인정보 처리방침을 `iframe` 으로 실으면서 오프라인을 감수한 것([[ADR-120]] 결정 11)과
판단이 갈리는데, 그쪽은 *"어긋난 법적 문서가 안 보이는 것보다 나쁘다"* 가 이유였다. 사용법 안내는
어긋날 위험이 없고 앱과 함께 버전이 고정되는 편이 맞다.

**`import.meta.glob` 을 쓰지 않는다.** `boss-icons`·`item-icons` 는 데이터(보스명·아이템명)가 파일명을
가리키는 수십 장이라 glob 이 옳지만, 여기는 릴리스마다 몇 장이고 가이드가 **자기 이미지를 직접
지목**한다. glob 조회는 파일명이 틀리면 `undefined` 를 돌려주고 화면에 이미지만 빠진 채 통과하지만,
명시적 import 는 **빌드가 실패한다.** [[ADR-119]] 결정 1 이 JSON 대신 `.ts` 를 고른 것과 같은 판단이다.

### 용량은 재고 기록한다

이미지는 `dist/assets/` 에 별개 파일로 나가지만 **OTA 는 dist 전체를 압축해 내려주므로 zip 이 그만큼
커진다** — 지연 로드가 이 비용을 깎아 주지 않는다. 릴리스마다 누적되는 자산이라 **한 장당·누적
상한을 정하고 넘으면 줄인다.** 상한값은 첫 촬영분 실측 후 확정한다(미결 4).

**기준선 실측 (2026-08-10, 이미지 0장, #185 머지 후)** — `npm run build` 후 `dist` 6.9MB /
zip **5.6MB**, `screen-settings` 청크 52.77kB(gzip 16.88kB). 안내 화면과 가이드 데이터가 이 청크
안에 들어갔고 **이미지가 아직 한 장도 없는 상태의 숫자**다. 다음 실측은 스크린샷을 넣은 뒤
같은 방법으로 잰다.

## 결정 5 — **안내가 있는 항목만** 눌린다

전 항목에 안내를 다는 것이 아니다. 버그 수정 한 줄에 붙일 사용법은 없다.

- `guideId` 를 가진 항목만 버튼이 되고 `›` 가 붙는다. 나머지는 **지금과 DOM 이 같다** — 래퍼도 클래스도 만들지 않는다.
- 안내가 없는 것은 결함이 아니라 정상이므로, 비활성 버튼을 두지 않는다(`error-resilience.md` — 액션이 없는 자리에 액션처럼 보이는 것을 두지 않는다).

## 결정 6 — 본문은 **블록 배열**이다 (이미지 ↔ 문단이 번갈아 선다)

```
‹  드롭 아이템 판매가
   [스크린샷]
   드롭한 아이템에 판매가를 매기면 …
   [스크린샷]
   1. 보스 수익 → 가격 에서 …
```

- 블록은 **이미지만 · 문단만 · 둘 다** 를 모두 허용한다. 사용법은 "그림 한 장에 설명 한 줄"로 떨어지지 않는다 — 맥락 문단이 먼저 오거나, 그림 두 장이 잇따르는 것이 자연스러운 경우가 있다.
- 이미지에는 **대체 텍스트를 필수**로 둔다. 안내 화면에서 이미지가 정보를 나르므로 장식이 아니다.
- 제목은 가이드가 자기 것을 갖는다(`PageHeader` 에 선다) — 노트 항목 텍스트(`…를 추가` 같은 완료형 문장)는 그 화면의 제목으로 읽히지 않는다.

## 트레이드오프

- **오래된 기능은 찾기 어렵다.** 버전 축의 대가다(결정 1). 카탈로그가 필요해지면 그때 얹는다.
- **OTA 번들이 릴리스마다 커진다.** 결정 4의 대가이고, 상한으로 관리한다.
- **원천이 두 파일로 갈린다.** 결정 2는 배포가 강제한 것이지 선호가 아니다 — 방어선은 타입이 아니라 참조 무결성 테스트다.
- **안내를 쓰는 비용이 릴리스마다 붙는다.** 스크린샷 촬영이 릴리스 작업에 들어온다. 그래서 **전 항목이 아니라 필요한 항목만** 이다(결정 5).
