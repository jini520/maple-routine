# ADR-007+077 SQLite 커넥션 · 스키마 진화 · 기본키

> 🟢 유효
> 옛 번호: ADR-050 결정 2 · 3 · ADR-176 · ADR-280 결정 5
> 관련 소스: `storage/sqlite/db.ts` · `storage/sqlite/migrations.ts` · `storage/sqlite/boss-tables.ts` · `storage/adapters/rn-sqlite.ts` · `storage/ports.ts` · `storage/sqlite/__tests__/node-sqlite-port.ts`

## 배경

보스 수익 · 드롭 · 가계부 · MVP 등급 같은 기록은 SQLite 파일 하나(`boss_profit`)에 있다. 이 기록은 넥슨 API
로 되살릴 수 없어서, DB 를 못 열거나 스키마 변경이 중간에 끊기면 사용자는 기록이 사라진 것으로 본다.

두 가지 문제를 겪었다.

- **커넥션이 응답 없이 멈췄다.** 앱이 리로드되면 JS 쪽 상태는 처음부터 다시 시작하는데 네이티브 쪽 커넥션은 남아
  있다. 그 상태에서 같은 이름으로 다시 열면 첫 쿼리가 응답 없이 멈춰, 보스 수익이 빈 화면으로 보였다.
- **이미 만들어진 테이블의 제약을 못 바꿨다.** 수입 기록의 `meso_amount` 가 `NOT NULL` 로 만들어져 있었는데,
  메이플 포인트나 캐시로 적는 `기타` 수입은 이 칸이 `NULL` 이라 저장이 통째로 실패했다(이슈 #265).
  `CREATE TABLE IF NOT EXISTS` 는 이미 있는 테이블을 고치지 않고, SQLite 의 `ALTER TABLE` 은 기존 칸의
  제약을 바꾸지 못한다.

## 결정

### 결정 1. 커넥션은 앱 전체에서 하나이고, 실패는 기억하지 않는다

`getBossProfitDb()` 가 여는 Promise 를 모듈 변수에 담아 모든 호출이 같은 커넥션을 쓴다. 같은 이름으로
커넥션을 두 번 열면 네이티브에서 오류가 나기 때문이다.

열기가 실패하면 그 변수를 비운다. 실패한 Promise 를 그대로 두면 앱을 다시 켤 때까지 모든 SQLite 조회가
같은 실패를 돌려받는다.

### 결정 2. 열 때 남아 있는 커넥션이 있으면 닫고 새로 만든다

`openBossProfitDb()` 는 포트의 `isConnection` 으로 같은 이름의 커넥션이 이미 열려 있는지 본다. JS 쪽 변수는
리로드할 때마다 비므로, 열려 있다면 이전 실행이 남긴 커넥션이다. 그대로 쓰면 첫 쿼리가 막히므로 닫고
새로 만든다.

### 결정 3. 열기는 10초, 닫기는 5초 안에 끝낸다

열기가 오류 없이 응답하지 않는 경우가 있다. 그 Promise 가 캐시에 남으면 결정 1 의 복구가 동작하지 않으므로,
10초 타임아웃과 경쟁시켜 응답이 없는 상태를 다시 시도할 수 있는 실패로 바꾼다.

리로드 직전에는 `closeBossProfitDb()` 로 커넥션을 먼저 닫는다. OTA 적용과 캐시 데이터 삭제가 이 순서를
지킨다. 열려 있는 채로 리로드하면 결정 2 의 상황이 생긴다. 닫기는 5초 상한이 있고, 실패해도 던지지 않는다.
이 5초가 OTA 적용에서 사용자가 반응 없는 화면을 보는 최대 시간이라서 열기보다 짧게 잡았다. 닫는 동안에도
캐시 변수를 비우지 않는다. 그 사이에 다른 곳에서 `getBossProfitDb()` 를 부르면 새 커넥션을 열지 않고 닫히는
중인 커넥션을 받는다. 닫기와 새 열기가 겹치면 네이티브에서 같은 이름의 커넥션이 이미 있다는 오류가 나기
때문이다.

### 결정 4. 스키마는 DB 를 열 때 정해진 순서로만 바꾼다

DB 를 열 때마다 아래 순서로 돈다.

1. `TABLE_DEFINITIONS` 의 `CREATE TABLE IF NOT EXISTS` 로 없는 테이블을 만든다.
2. 칸의 제약을 바꿔야 하면 테이블을 다시 쓴다(결정 5).
3. `ensureColumn` 으로 없는 칸을 더한다. SQLite 에는 `ADD COLUMN IF NOT EXISTS` 가 없어서
   `PRAGMA table_info` 로 칸이 있는지 보고, 없을 때만 `ALTER TABLE ... ADD COLUMN` 한다. `ALTER` 를 실행하고
   오류를 무시하는 방식은 다른 원인의 실패까지 숨기므로 쓰지 않는다.
4. 값을 옮겨야 하면 버전 이관을 돌린다(결정 7).

칸을 더할 때는 `CREATE TABLE` 문과 `ensureColumn` 을 둘 다 고친다. `CREATE TABLE` 만 고치면 이미 테이블이
있는 기기에는 칸이 생기지 않는다. `INSERT` 는 모든 칸을 적으므로, 그 기기에서는 저장이 통째로 실패한다.
반대로 `ensureColumn` 만 고치면 새 설치는 문제없이 돌지만, 재작성이 만드는 테이블에 칸이 빠져 그때 실패한다.
`CREATE TABLE` 문이 지금의 스키마 전체여야 한다.

`TABLE_DEFINITIONS` 의 이름 목록(`BOSS_PROFIT_TABLE_NAMES`)은 캐시 데이터 삭제와 용량 계산이 그대로 쓴다
([[ADR-053]]). 테이블을 이 배열 밖에서 만들면 삭제 대상에서 빠진다.

### 결정 5. 칸의 제약을 바꿀 때는 한 트랜잭션 안에서 테이블을 다시 쓴다

`income_records.meso_amount` 의 `NOT NULL` 은 이렇게 뗐다.

```sql
BEGIN
CREATE TABLE income_records_rebuild ( 지금의 스키마 )
INSERT INTO income_records_rebuild (<옮길 칸>) SELECT <옮길 칸> FROM income_records
DROP TABLE income_records
ALTER TABLE income_records_rebuild RENAME TO income_records
COMMIT
```

- **한 트랜잭션이다.** 옛 테이블은 지워졌는데 새 이름은 아직 없는 상태가 파일에 남으면 그 기기의 수입 기록이
  전부 사라진다. 도중에 던지면 `ROLLBACK` 하고 오류를 그대로 올려보낸다.
- **옮길 칸은 옛 테이블이 실제로 가진 칸이다.** `PRAGMA table_info` 로 읽는다. `SELECT *` 를 쓰면
  `ensureColumn` 이 뒤에 붙인 칸 때문에 칸 순서가 지금 DDL 과 달라서, 값이 오류 없이 옆 칸으로 옮겨진다.
  지금 스키마의 칸 목록을 코드에 적어 두면, 그 칸이 아직 없는 옛 기기에서 `SELECT` 가 실패한다.
- **`ensureColumn` 보다 먼저 돈다.** 재작성이 만드는 테이블은 지금 DDL 전체라 칸이 이미 다 있어서, 뒤의
  `ensureColumn` 은 할 일이 없어진다.
- **다시 쓸지는 스키마를 직접 읽어 판단한다.** `meso_amount` 의 `notnull` 이 0 이면 아무 문장도 실행하지 않는다. 값이
  숫자로 올지 글자로 올지 어댑터마다 약속이 없어서 `Number()` 로 바꿔 비교한다. 글자 `'0'` 을 `=== 0` 으로
  비교하면 매번 다시 옮긴다.
- **DDL 본문은 하나만 둔다.** 정상 생성과 재작성이 `INCOME_RECORDS_BODY` 상수 하나를 같이 쓴다. 두 곳에
  따로 두면 언젠가 재작성이 옛 스키마를 다시 만든다.

`meso_amount` 에 `0` 을 넣어 마이그레이션을 피하는 방법은 쓰지 않았다. `0` 이면 메소로 0 을 벌었다는 뜻이
되어, 메소로 번 돈이 아니라는 사실과 구분할 수 없다. 수정 시트는 값이 들어 있는 칸을 보고 어떤 통화로 적었는지 알아낸다.

### 결정 6. 진짜 SQLite 엔진으로 한 번 더 검사한다

목 DB 는 미리 정해 준 동작만 흉내 낸다. `NOT NULL` 제약은 그 목록에 없어서, 이슈 #265 를 목 테스트로는
잡을 수 없었다. 그래서 `node:sqlite`(Node 내장)로 `SqlitePort` 를 구현한 `node-sqlite-port.ts` 를 두고,
`*-real-sqlite.test.ts` 가 그 위에서 `db.ts` 의 실제 코드를 돌린다. 새 의존성은 없다.

목 테스트도 지우지 않는다. 목 테스트는 어떤 문장이 어떤 순서로 나가는지를 보고, 실제 엔진 테스트는 그 문장이
엔진에서 실제로 통하는지를 본다. 둘은 확인하는 대상이 다르다.

### 결정 7. 값을 옮기는 이관은 `PRAGMA user_version` 으로 한 번씩만 돌린다

`migrations.ts` 의 `STEPS` 에 이관이 버전 순서대로 들어 있고, `DB_VERSION`(지금 13)이 마지막 버전이다.
`runVersionedMigrations` 는 `user_version` 보다 큰 버전만 차례로 돌리고, 버전마다 한 트랜잭션 안에서 이관과
`PRAGMA user_version = N` 을 함께 실행한다. 중간에 던지면 그 버전의 변경과 버전 번호가 같이 되돌아가 다음
부팅에 다시 돈다.

부팅마다 도는 `UPDATE` 로 두지 않는 이유는 순서다. 뒤 버전이 앞 버전의 결과를 읽는다. 버전 2 는 버전 1 이
바꾼 이름으로 key 를 찾고, 드롭 기록은 key 를 채운 뒤에야 획득할 수 없는 드롭을 지우는 판정을 돌린다.
판정이 먼저 돌면 아직 key 를 못 찾은 행을 잘못된 기록으로 보고 지울 수 있다. 그리고 key 를 못 찾아 비워 둔
행을 부팅할 때마다 다시 찾지 않는다.

이관은 모든 칸이 생긴 뒤에 돈다. 새 기기는 빈 표를 거쳐 곧바로 마지막 버전이 된다.

### 결정 8. 기본키는 uuid 한 칸이고, 유일해야 하는 조합은 `UNIQUE` 로 건다

기본키는 uuid 한 칸이다. 값의 조합을 기본키로 쓰면 그 안의 값이 바뀔 때 행을 가리킬 방법이 사라진다. 드롭 기록은
기본키에 난이도가 들어 있어서, 처치 난이도가 확정될 때마다 행을 옮겨야 했다([[ADR-018]] 결정 1).

같은 값의 행이 둘 있으면 안 되는 조합에는 `UNIQUE` 를 건다. SQLite 와 Postgres 는 `UNIQUE` 를 인덱스로 만들기
때문에, 조회 속도는 일반 인덱스와 같고 중복 행만 거절한다. 그래서 유일해야 하는 조합을 일반 인덱스로 둘 이유가
없다. 있으면 가져오고 없으면 만드는 쓰기는 `INSERT ... ON CONFLICT` 로 쓴다. 두 쓰기가 겹쳐도 행이 하나만 생긴다.

일반 인덱스는 고치는 동안 값이 잠깐 겹치는 칸에만 쓴다. 드롭 그룹의 `drop_index` 는 저장할 때마다 한 행씩 다시
매겨서 같은 번호가 잠깐 겹친다. 여기에 `UNIQUE` 를 걸면 그 순간 저장이 실패한다.

서버 표도 같은 규칙을 따른다([[ADR-016]] 결정 5). 보스 기록 표는 [[ADR-078]] 이 이 규칙으로 다시 짰다. 앱에는
아직 이 규칙을 따르지 않는 표가 남아 있고, 그 표들과 `시각 + 난수` 꼴 id 는 #670 이 옮긴다. 새로 만드는 표와 기록은
처음부터 이 규칙을 따른다.
