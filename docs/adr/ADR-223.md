# ADR-223: 지출은 계정 단위 사용 내역에서 온다. 일 단위로 받고 어제 이전은 굳힌다

> ⚪ 미구현 · 2026-09-06 · 설계 (응답 실측 완료)

> 사용자 지정(2026-09-06): "/maplestory/v1/history/starforce /maplestory/v1/history/potential
> /maplestory/v1/history/cube 의 결과를 사용 메소로 치환해서 지출로 잡으려고 하는 작업"

**관련**: [[ADR-222]](창 · 층이 데이터를 소유한다) · [[ADR-086]] 결정 4(조회 원장) ·
[[ADR-219]](기록은 추적 목록이 아니라 자기 자신으로 산다) · [[ADR-006]](게임 수치 임의 추정 금지)

## 맥락

가계부의 지출은 지금 **손입력 둘**뿐이다. 큐브·스타포스·잠재 재설정에 쓴 메소가 가장 큰 지출인데
앱이 그것을 모른다.

넥슨이 그 사용 내역을 준다. 그런데 이 셋은 지금까지 앱이 쓰던 API 와 **모양이 다르다.**

| | 지금까지(스케줄러·캐릭터) | 히스토리 셋 |
|---|---|---|
| 단위 | 캐릭터(ocid) | **계정** |
| 조회 | 날짜 하나 | 날짜 하나 + 커서 |
| 한 번에 | 그 캐릭터 전부 | **1000건**. 넘으면 `next_cursor` |
| 과거 | 창 지나면 못 봄 | **영구 확정** |

## 결정

### 결정 0. 응답 모양 (실측 2026-09-06)

```
GET /maplestory/v1/history/{cube|starforce|potential}?count=N&date=YYYY-MM-DD
GET /maplestory/v1/history/{...}?count=N&cursor=…        ← date 없이 이어받는다

{ count, next_cursor, {종류}_history: [ … ] }
```

| 잰 것 | 결과 |
|---|---|
| 정렬 | **최신 → 과거** 내림차순 |
| 커서 방향 | 과거로 이어진다 |
| 커서에 `date` | 필요 없다. 커서가 날짜 맥락을 든다 |
| 쪽 나눔이 빠뜨리나 | 아니다. 두 쪽(17건)이 전체(187건)의 앞부분과 정확히 일치 |
| `count` | **상한**이다. 10 을 달라고 해도 8·9 가 왔다 |
| 결정성 | 같은 요청 두 번에 커서·id 목록·응답 전체가 **같다** |
| 실사용자 하루 | 큐브 187건. `count=1000` 한 번에 다 왔고 커서 없음 |

줄마다 `id` 가 있고 계정 전체에서 유일하다. 비용 계산에 필요한 것이 응답에 다 있다 — 큐브는
`cube_type` + `item_level`, 스타포스는 `before_starforce_count` · `superior_item_flag` ·
`protect_shield` · 이벤트 플래그.

### 결정 1. 원장은 **`(종류, 날짜)`** 하나다

계정 단위라 ocid 축이 없다. 그래서 하루가 **3콜**(스타포스·잠재·큐브)이고 캐릭터 수를 안 곱한다.

[[ADR-086]] 결정 4 의 조회 원장과 같은 모양이고 같은 규칙을 쓴다.

| 원장이 든 것 | 다시 부르나 |
|---|---|
| 없음 | 부른다 |
| 받음(확정) | **안 부른다. 영구** |
| 받음(잠정 = 오늘) | 날이 바뀌면 부른다 |
| `OPENAPI00009`(집계 전) | **안 적는다.** 다음 방문에 다시 온다 |

**어제 이전은 영원히 안 바뀐다.** 9월 5일에 쓴 큐브는 9월 6일부터 확정이다. 그래서 지난 달을
한 번 열면 그 달은 끝이고, 두 번째 방문부터 조회가 0이다.

**확정 시각을 상수로 안 둔다.** 몇 시에 집계가 끝나는지 몰라도 `OPENAPI00009` 가 오면 안 굳히면
된다. 응답이 말하게 한다([[ADR-222]] 결정 3 과 같은 태도).

### 결정 2. 범위는 **화면이 그리는 날짜**다

가계부는 칸 하나가 하루다. **API 단위와 화면 단위가 정확히 같다.** 그래서 달로 끊지 않는다.

```
주간 보기 진입   그 주 7일 + 오늘   21콜 (첫 방문) · 이후 3콜
월간으로 전환    남은 24일          72콜 (첫 방문) · 이후 3콜
지난 달로 이동   그 달 31일         93콜 (첫 방문) · 이후 3콜
```

기본이 주간 보기라 **첫 진입이 21콜**이다. 창 84콜과 겹쳐도 견딜 만하다. 월간은 사용자가 옮길 때
치른다.

**한 달을 통째로 받지 않는 이유**가 이것이다. 월간 보기를 안 여는 사용자가 93콜을 낼 이유가 없다.

### 결정 3. 추적 안 하는 캐릭터의 것도 **담고 보여준다** (사용자 지정)

계정 단위 API 라 추적 목록 밖 캐릭터의 사용 내역도 함께 온다. **거르지 않는다.**

[[ADR-219]] 가 세운 것과 같은 이유다. 추적은 **앞으로 무엇을 받을지**의 축이지 **무엇이 사실인지**의
축이 아니다. 지출은 그보다 더 분명하다. 거를지 말지를 우리가 고를 수 있을 뿐 **돈은 이미 나갔고**,
거르면 합계가 거짓이 된다.

**필터를 두지 않는다.** 숨기면 합계가 거짓이 된다. 추적 캐릭터를 위로 올리거나 표식을 다는 정도로
충분하다.

**초상은 아는 것만 그린다.** 히스토리 응답은 캐릭터 이름을 준다. 초상을 그리려면 ocid 가 필요하고
그것은 캐릭터마다 한 콜이다(계정에 40명이면 40콜). 추적 캐릭터는 `character_profiles` 에 이미
있으니 초상이 붙고, 나머지는 이름만 뜬다. 같은 목록에서 어떤 줄은 초상이 있고 어떤 줄은 없는
모양이 되는데 그것이 정직하다.

### 결정 3.5. 다시 부르는 규칙 (사용자 판단)

**어제 이전은 아예 안 부른다.** 그 날짜의 데이터는 변할 수 없다. 원장의 `settled` 가 1이면
조회 대상에서 빠진다. 그래서 지난 달 두 번째 방문이 **0콜**이다.

**오늘은 매번 1쪽을 받는다.** 저장해 둔 `next_cursor` 와 같으면 새 데이터가 없다는 뜻이라
나머지를 안 부른다. 다르면 **이미 아는 id 를 만날 때까지만** 이어 받는다.

동률 타임스탬프가 실제로 있다(잠재 재설정 3건이 같은 밀리초). 그 순서가 호출 사이에 뒤집히면
id 하나를 만나 멈출 때 나머지를 놓칠 수 있는데, **넥슨이 순서를 보장한다고 본다**(사용자 판단).
이것은 잰 것이 아니라 **가정**이다. 지출이 비는 보고가 오면 여기를 먼저 볼 것.

### 결정 3.7. 장비 레벨 표를 **데이터로 만든다** (사용자 지정)

스타포스 응답에는 `item_level` 이 **없다**(1년치 3,220건 실측). 그런데 비용은 레벨에 크게
좌우된다.

**큐브·잠재 응답이 그 값을 준다.** 그리고 셋 다 `target_item` 을 같은 이름 체계로 준다. 1년치
27,187건에서 **한 이름에 두 레벨이 붙은 적이 없다.**

그래서 표를 코드에 안 넣고 **저장한 것의 투영**으로 만든다.

```
SELECT DISTINCT target_item, item_level FROM enhancement_history WHERE item_level IS NOT NULL
```

별도 표가 없으니 원본과 어긋날 자리도 없다. 실측으로 92종이 서고 스타포스의 **83.7%** 가 덮인다.

**읽을 때 찾는다.** 쓸 때 채우면 그 시점에 표에 없던 장비는 영영 NULL 로 남는다. 레벨은 그
사건의 속성이 아니라 파생값이므로, 표가 자라면 예전에 넣은 행도 함께 값을 얻어야 한다.

**접두사 규칙은 안 넣는다.** `아케인셰이드` 24종이 전부 200 인 것은 맞지만(실측), 그것으로
더 덮이는 것이 1.6%p 뿐이고 그 3종은 큐브를 한 번만 돌리면 저절로 채워진다. 반면 `블랙` 은
계열 안에서 레벨이 갈린다(마법깃펜 100 · 블랙빈 마크 135). 얻는 것에 비해 **틀린 값이 조용히
박힐 자리**가 열린다.

**안 덮이는 14.7%** 는 대개 잠재를 못 붙이는 장비다(블랙·10주년 화이트 계열). 그쪽은 표가
자라도 안 채워지므로 금액 없이 건수만 센다.

### 결정 4. 비용 치환은 **자리만 잡는다** (사용자 지정)

큐브 종류별 가격 · 스타포스 비용 공식 · 잠재 재설정 비용은 [[ADR-006]] 이 금하는 자리다. AI 가
기억으로 쓰면 **틀린 지출이 조용히 쌓인다.**

그래서 이번에는 **받아서 저장하는 데까지**만 한다. 비용 칸은 nullable 로 두고, 표가 들어오는
날 그 칸을 채운다. 화면은 비용을 모르는 줄을 **금액 없이** 센다(`가격 미입력` 과 같은 태도,
[[ADR-124]]).

**그래서 응답 줄을 통째로 남긴다.** 결정 3.5 가 어제 이전을 안 부르기로 했으므로 지금 안 남기면
표가 들어와도 셀 수가 없다. 나중에 `cost_meso` 를 채우는 일이 **조회가 아니라 계산**이어야 한다.

### 결정 5. 수집기는 [[ADR-222]] 의 층이 소유한다

새 소유자를 만들지 않는다. `LedgerDataProvider` 가 창과 히스토리 둘을 든다.

`status` 는 **화면별**이다. 보스 수익에 서 있으면 히스토리가 뒤에서 돌아도 모달이 안 뜬다. 그
화면은 그 데이터를 안 쓴다.

**계획을 먼저 다 세운다**([[ADR-222]] 정정 8). 창이 끝난 뒤 히스토리가 자기 분모를 등록하면 바가
뒤로 간다. 둘 다 콜 없이 원장만 읽어 할 일을 셀 수 있으므로, 계획을 합쳐 분모를 잡은 뒤 실행한다.

진행의 작업 단위는 **`(종류, 날짜)`** 다. 하루가 1000건을 넘으면 커서로 콜이 더 나가는데, 콜을
세면 분모가 도는 중에 늘어난다. 커서는 **작업 안쪽** 일이라 밖에서는 1이다.

## 대가

- **월간 보기 첫 방문이 93콜**이다. 창과 겹치면 더 길다. 모달이 그 시간을 말한다.
- **비용을 모르는 동안 지출이 안 보인다.** 받아 두는 것은 나중에 값을 매길 수 있다는 뜻이지 지금
  화면이 는다는 뜻이 아니다.
- **수익과 지출의 모집단이 다르다.** 수익은 추적 6명, 지출은 계정 전체다. 화면에서 그것을
  **따로 말하지 않는다**(사용자 지정) — 지출은 언제나 계정 전체다.
- **`payload` 를 통째로 남긴다.** 비용을 나중에 셀 수 있게 하는 값이고, 그 대가가 용량이다.

## 열린 질문

- **비용 표.** 큐브 종류별 가격 · 스타포스 비용 공식 · 잠재 재설정 비용. 이것이 오기 전까지
  `cost_meso` 는 NULL 이고 화면은 금액을 안 말한다.

  실측으로 축은 다 확인했다. `cube_type` **16종** · `potential_type` **2종**(잠재능력 재설정 ·
  에디셔널 잠재능력 재설정) · `item_level` 30~250 · `miracle_time_flag` 2값. 스타포스는
  `starforce_event_list` 가 **할인율을 직접 준다**(`cost_discount_rate` · `destroy_decrease_rate` ·
  `recovery_cost_discount_rate`)라 이벤트를 따로 알 필요가 없고, `upgrade_item` 이 빈 문자열이
  아니면 강화권이라 **메소가 안 든다**(1년치 3,220건 중 9건).
- **용량.** 하루 187건 × 3종 × payload 를 통째로 남기면 한 달이 수 MB 다. 캐시 삭제로 비울 수
  있지만 얼마나 커지는지는 실사용에서 재야 안다.
