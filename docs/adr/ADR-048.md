### ADR-048: 고가 드롭 연출 — DropEff 프레임 정렬을 프레임별 origin 테이블로 교체 + ScreenEff 배율 고정(유실된 WZ origin을 템플릿 정합으로 복원) (구현 완료, 2026-07-28)

> 🟢 **ACTIVE — 유효.** 현행 RN 앱에 적용되는 결정이다.

**배경**: [[ADR-038]] 결정 8이 도입한 고가 드롭 전체화면 연출에서 `DropEff`(pre 8 → loop 24 → end 7, 총 39프레임)가 하나의 빛 기둥으로 보이지 않고 재생 내내 좌우로 흔들린다. 원인은 앵커 방식이다 — 프레임 비트맵은 크기가 제각각인데(가로 38~285px, 세로 288~826px) `DropEffectOverlay`가 모든 프레임을 **하단-중앙**(`translate(-50%,-100%)`)으로 붙이고 있었다.

인게임 클라이언트는 WZ 스프라이트마다 `origin` 좌표를 갖고 그 점을 기준으로 렌더링하지만, 이 프로젝트의 에셋은 원본 WZ에서 뜬 PNG 시퀀스를 검은배경 JPEG로 최적화한 것([[ADR-038]] 결정 9)이라 **origin 메타데이터가 유실**됐다. 사이드카 파일도 없다. 즉 정확한 값을 데이터로 받을 수 없어 **이미지 내용에서 복원**해야 한다.

**결정**:
1. **프레임별 origin 테이블 도입**: 신규 `lib/drop-effect-layout.ts`에 39프레임 각각의 origin `[x, y]`(그 프레임 비트맵 자신의 픽셀 좌표계, JPEG 최적화본 기준)를 상수 테이블로 둔다. `DropEffectOverlay`는 하단-중앙 앵커를 버리고 **origin 점이 화면의 고정 앵커에 오도록** 배치한다 — `transformOrigin:'0 0'` + `translate(-x·S, -y·S) scale(S)`. 프레임을 바꿀 때 `src`와 `transform`을 **함께** 갱신한다(별도 헬퍼 `applyDropFrame`).
2. **origin.y = 비트맵 높이(하단 고정)**: 세로는 프레임마다 튜닝하지 않고 전부 비트맵 하단으로 고정한다. 근거 — 전 프레임의 콘텐츠 하단 여백이 3~6px로 일정해(빛 기둥이 지면선에서 잘려 있음) 비트맵 바닥 = 지면이고, 실제로 세로 정합 점수 곡선이 ±12px 구간에서 5% 이내로 평평해 세로 미세조정은 신호가 아니라 노이즈였다.
3. **origin.x는 정합(registration)으로 복원**: 잃어버린 WZ origin을 추정이 아니라 계측으로 되살린다. ① 각 프레임 하단 80행(지면 플레어)의 휘도 가중 중심으로 초기값을 잡고, ② loop 24프레임 평균을 템플릿으로 삼아 matched filter(`Σ template·frame`)로 프레임마다 x를 재정합하고, ③ 템플릿을 다시 만들며 6회 수렴시킨 뒤 포물선 보간으로 서브픽셀 정밀도를 얻는다. pre/end는 기둥 길이가 달라 SSD 대신 matched filter를 써서 겹치는 하단부만으로 정합된다.
4. **테이블-에셋 정합 테스트**: origin 테이블 길이가 `DROP_EFFECT_FRAMES` 각 단계 프레임 수와 일치하는지 단위 테스트로 고정한다. 에셋을 다시 뽑으면 테이블도 같이 갱신해야 하는데, 어긋나면 기둥이 엉뚱한 위치로 튀므로 조용히 깨지지 않게 막는다.
5. **`ScreenEff`는 배율 고정으로 해결(origin 테이블 불필요)**: DropEff 정렬 후에도 몇 프레임이 튄다는 보고를 받아 같이 계측했다. ScreenEff 프레임은 크롭이 **이미 버스트 원점 기준으로 중앙 정렬**돼 있다 — loop 템플릿 정합에서 주 프레임(1~9)의 origin 이 프레임 중심과 0~5px 이내로 일치했고, 꼬리 프레임(8~13)을 감마 부스트해 중심 십자선과 겹쳐 봐도 광선 수렴점이 정확히 중심에 온다. 따라서 **위치는 문제가 아니고 배율이 문제다** — `object-fit:cover` 는 프레임마다 자기 비트맵 크기로 "화면을 덮는 배율"을 따로 계산하므로, 크롭이 큰 프레임과 작은 프레임이 서로 다른 배율로 그려진다. 프레임별 origin 테이블 대신 **기준 프레임(1146x685)이 화면을 덮는 배율 하나를 전 프레임에 동일 적용**한다 — `object-cover`·`h-full w-full` 을 걷어내고 `left-1/2 top-1/2` + `translate(-50%,-50%) scale(S)`, `S = max(vw/1146, vh/685)`. 프레임마다 크기가 다른 이미지를 자연 크기로 그려야 하므로 Tailwind preflight 의 `img{max-width:100%}` 를 `max-w-none` 으로 해제한다.

6. **프레임 픽셀과 좌표를 원자적으로 교체**: 결정 1 이 만든 새 결합 — 프레임마다 좌표가 다르므로 `src` 와 `transform` 이 서로 다른 프레임을 가리키는 순간이 생기면 안 된다. 그런데 `img.src` 교체는 **비동기**다(측정: 39프레임 전부 `src` 대입 직후 `complete === false`). 좌표만 먼저 옮기면 **이전 프레임 픽셀이 새 origin 으로 그려져 딱 한 프레임 옆으로 튄다** — 정렬 전 흔들림과 같은 최대 26px 오차가, 이번엔 산발적으로 나타난다. 두 겹으로 막는다: ① 오버레이 마운트 시 DropEff 39프레임을 `new Image()` + `decode()` 로 **미리 디코드**하고 ref 로 붙잡아 둔다(GC 방지) — 측정상 이후 `src` 교체는 즉시 `complete === true`(로컬 39프레임 34ms). ② 그럼에도 준비가 안 됐으면 `applyDropFrame` 이 **좌표를 그대로 두고 반환**한다. 이 함수는 매 tick 불리므로 준비되는 즉시 픽셀과 좌표가 함께 제자리를 잡는다. 좌표가 아직 없는 프레임이 보이지 않도록 표시(opacity)도 이 함수가 켠다.

7. **계측 도구를 저장소에 남긴다**: 결정 3 의 절차를 `scripts/measure-drop-effect-origins.py` 로 커밋한다. 결정 1·4 가 "에셋을 다시 뽑으면 테이블도 다시 계측하라"를 요구하는데 도구가 없으면 그 지시를 지킬 방법이 없다. 실행하면 붙여 넣을 TS 테이블과 정합 지표를 그대로 출력하며, **현재 커밋된 39개 값을 정확히 재현**한다(그래야 도구가 산출물의 진짜 출처라고 말할 수 있다). 정합 중 y 를 자유도로 여는 것·반복 6회 같은 세부까지 스크립트에 고정해 뒀다 — 바꾸면 결과가 서브픽셀 단위로 달라진다. 개발자 도구라 앱 번들엔 안 들어가고, `numpy`·`pillow` 는 실행할 때만 필요하다(`scripts/execute.py` 선례가 있어 Python 자체는 이질적이지 않다).

**데이터**: 신규 `lib/drop-effect-layout.ts`(39×2 수치). 게임 레퍼런스 수치가 아니라 **커밋된 에셋 비트맵에서 계측한 값**이므로 [[ADR-006]]의 "AI 임의 추정 금지" 대상이 아니다 — 재현 가능한 측정이고, 검증 지표는 아래 참고.

**이유**:
- 하단-중앙 앵커는 "비트맵이 콘텐츠에 딱 맞게 잘려 있고 좌우 대칭"일 때만 맞는데, 실제 크롭은 좌우 여백이 독립적으로 다르다(예 loop/0 좌 48·우 55, loop/5 좌 42·우 34). 그래서 프레임마다 기둥 축이 최대 26px 어긋나 흔들림으로 보였다.
- origin을 눈대중으로 하나씩 맞추면 39개를 사람이 튜닝해야 하고 재현성이 없다. 템플릿 정합은 "모든 프레임이 같은 기둥"이라는 사실 자체를 목적함수로 쓰므로 근거가 명확하고, 에셋을 다시 뽑아도 같은 절차로 재생성할 수 있다.

**검증** — DropEff(loop 전 프레임, 기둥 몸통 축 x). `scripts/measure-drop-effect-origins.py` 가 그대로 재출력한다:
| | 표준편차 | 최대-최소 | 프레임 간 최대 점프 |
|---|---|---|---|
| 하단-중앙(기존) | 6.45px | 26.16px | 14.96px |
| origin 테이블(신규) | 0.37px | 1.31px | 1.18px |

정렬 후 재측정 결과 DropEff 는 지면에서 700px 높이까지 전 구간 축이 300±2px 이고 프레임 간 최대 점프 2.8px, 세로도 플레어 밴드 전용 정합에서 전 프레임이 비트맵 하단 ±2px 이내라 **잔여 흔들림은 DropEff 쪽이 아니었다**. 남은 원인은 ScreenEff 배율이었다(390x844 뷰포트 기준):
| | 배율 범위 | 프레임 간 최대 배율 점프 |
|---|---|---|
| `object-cover`(기존) | 1.232 ~ 2.198 (78% 차) | 42% (프레임 0→1) |
| 고정 배율(신규) | 단일 값 | 0% |

주 프레임(4~7)이 받던 배율이 1.232 로 신규 고정 배율과 같아 **정상 프레임의 크기는 그대로**이고, 튀던 프레임만 제자리를 찾는다.

**트레이드오프**:
- 테이블이 에셋과 **암묵적으로 결합**된다 — 프레임을 다시 export 하면 origin도 다시 계측해야 한다(결정 4의 길이 테스트가 최소 방어선이고, 값 자체의 드리프트는 잡지 못한다). 재계측 도구를 `scripts/measure-drop-effect-origins.py` 로 커밋해 뒀다(결정 7).
- 계측값이라 원본 WZ origin과 정확히 같다는 보장은 없다. 다만 목표는 "인게임 좌표 복원"이 아니라 "한 기둥으로 보이는 것"이므로 정합 지표로 충분하다.
- `end/6`은 전 픽셀이 검정(완전 페이드 아웃)이라 정합할 내용이 없다 — 렌더 결과가 없으므로 origin은 하단-중앙으로 둔다.
- 프레임 프리로드: 오버레이가 뜰 때마다 DropEff 39장을 디코드해 메모리에 붙잡는다(연출이 닫히면 해제). 좌표-픽셀 결합이 없는 ScreenEff 는 프리로드 대상에서 뺐다 — 프레임이 크고(1146x685×16) 동작은 기존과 같아 굳이 메모리를 더 쓸 이유가 없다.
- ScreenEff 고정 배율: 기준보다 작게 크롭된 프레임(예 992x643, 544x384)은 이제 화면을 다 덮지 않고 상하좌우에 여백이 생긴다. 다만 프레임 가장자리는 검정이고 `mix-blend:screen` 에서 검정은 투명이라 어두운 backdrop 위에서는 보이지 않는다. 반대로 프레임 0(544x384, 얇은 사선 섬광)은 예전처럼 화면 가득 확대되지 않고 작게 그려지는데, 이게 원작 상대 크기다.

**TDD**: origin 테이블 길이 = 프레임 수 단언 → `dropFrameTransform`/`screenEffectScale` 순수 함수 → `DropEffectOverlay`가 프레임 전환 시 `src`와 `transform`을 함께 갱신하는지(재생·닫기 전 구간에서 src↔origin 일치) → 픽셀이 준비 안 된 프레임에 좌표를 먼저 옮기지 않는지(jsdom 은 이미지를 로드하지 않아 `complete` 를 스텁으로 양쪽 상황 재현) → ScreenEff 가 `object-cover` 없이 단일 배율 transform 을 쓰는지 → 기존 오버레이 테스트(pointer-events·`data-sheet-keep-open`) 회귀 확인.

**미verify**: 실기기 육안 확인([[ADR-038]]의 미verify 항목과 동일 — 정렬 지표·프레임 몽타주로는 검증했으나 실제 재생은 미확인). → **해소됐다**(2026-08-26, 아래 정정 1).

**정정 1 (2026-08-26, 갤럭시 Z Flip3 릴리스 빌드 + iPhone 17 Pro 시뮬레이터 프레임 계측)**

- **결정 6 은 RN 으로 안 넘어와 있었다.** `new Image()` + `decode()` 프리로드의 짝이 없어, 웹에서 «좌표가 한 프레임 튄다» 였던 것이 RN 에서는 «그 한 장이 통째로 빈다» 로 나타났다(첫 재생 2.1초 동안 빈 프레임 40~49장). 되살린 형태와 계측은 [[ADR-173]] 에 있다. **결정 6 의 취지는 유효하고, 구현만 갈렸다.**
- **결정 5 의 «ScreenEff 크롭은 버스트 원점 기준으로 중앙 정렬» 은 가로만 맞다.** 방사 광선의 수렴점을 focus-of-expansion 으로 재계측하니(합성 시프트로 0.1px 정확도 검증) 원점은 **가로는 비트맵 중심 ±5px**, **세로는 중심보다 ~130px 아래**였다(frame 2~10 에서 117~133px, 안정적). 화면에 얹으면 버스트 중심이 **화면 높이의 69%** 에 서고, 아이템은 66% 에 있다 — 기기 크기와 무관하게 **약 3%(880dp 기준 26dp) 아래**다. 기둥의 지면 앵커(66% + 44dp)보다는 위라 «빔이 닿는 자리» 근처이긴 하다. **지금은 안 건드린다** — 웹에서 눈으로 정해진 값이고, 옮기려면 [[ADR-103]] 이 재생 속도에 대해 그랬듯 사용자 눈으로 확정해야 한다.
- **결정 1~4 의 origin 테이블은 그대로 유효하다.** WebP 재export([[ADR-093]]) 뒤에도 값이 안 흔들렸는지 재계측해 확인했다 — 커밋된 값과 최대 0.8px 차이(표준편차 0.41px). 실기 렌더에서도 loop 322프레임 동안 기둥 축이 **가로 표준편차 0.26pt · 세로 표준편차 0.00pt** 로 붙박이다. 결정 7 의 재계측 스크립트는 `*.jpg` 만 훑고 있어 WebP 전환 이후 **죽어 있었다**(«프레임을 찾을 수 없습니다»). 확장자 둘을 다 받도록 고쳤다.
