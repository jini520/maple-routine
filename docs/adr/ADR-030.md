### ADR-030: 컨텐츠 스케줄러 캐시 — 미접속·월드/계정 공유·API 오염에 대한 다단계 캐싱 전략 (구현 완료)

**배경**: 스케줄러 Open API([[ADR-007]])를 실사용하면서 세 가지 문제가 확인됐다(2026-07-21, 사용자 실측):

1. **미접속 시 데이터 누락**: 캐릭터가 한국시간(KST) 자정 이후 게임에 접속하지 않으면 그 캐릭터를 조회했을 때 `daily_contents`가 비거나 없다. 목요일 리셋(주간) 이후로 접속하지 않았으면 `weekly_contents`까지 함께 비거나 없다 — "마지막 접속일"이 하나 있고, 그게 일간/주간 리셋 경계 중 어느 쪽보다 오래됐는지에 따라 daily만 비거나 daily+weekly가 함께 빈다(주간 경계가 항상 일간 경계와 같거나 그보다 이전이라 자연히 이렇게 된다).
2. **월드/계정 단위 공유 콘텐츠**: 일부 콘텐츠는 완료가 캐릭터 단위가 아니라 월드 전체 또는 계정(현재 앱이 다루는 유일한 `accountId`) 전체에 걸쳐 공유된다(아래 "분류" 참고). 지금까지 `storage/scheduler-cache.ts`는 `schedulerCache:{ocid}` 키 하나에 캐릭터별 스냅샷만 저장해 이 공유를 표현할 방법이 없었다.
3. **"마지막 활성 캐릭터" API 오염**: 월드/계정 단위 콘텐츠에 한해, 실제 게임 클라이언트에 마지막으로 접속했던 캐릭터의 상태가 이후 조회하는 다른 캐릭터의 응답에 새어 들어온다. 확인된 두 사례 — (a) 몬스터파크: A월드 캐릭터에 접속 후 종료하면, 그 뒤 B월드 캐릭터를 조회해도 A월드의 `now_count`가 그대로 나옴. (b) A 캐릭터의 게임 내 스케줄러에 등록 안 된 항목은, 그 항목이 등록된 B 캐릭터를 조회해도 응답에서 통째로 빠질 수 있음. **character 범위 콘텐츠에서는 이 오염이 확인되지 않았다** — character 범위는 정상적으로 독립적이다.

**핵심 통찰**:
- 응답의 `date` 필드는 조회 시각과 무관하게 항상 조회 요청일(기본값 오늘)을 그대로 반환한다(공식 문서·사용자 실측 확인, 2026-07-21) — 즉 타임스탬프 비교로는 stale 여부를 알 수 없다. 대신 **`daily_contents`/`weekly_contents` 배열이 통째로 비어있는지(또는 필드 자체가 없는지) 자체를 신호로 쓴다.** 이게 안전한 이유: [[ADR-007]] 샘플 응답에서 보듯 정상 동기화라면 미등록 항목도 `registration_flag: "false"`로 배열에 포함되므로, 배열이 완전히 비는 건 정상적인 "전부 등록 해제" 상태가 아니라 "이 리셋 주기 이후 이 캐릭터로 접속한 적 없음"으로 해석해도 안전하다.
- 위 오염 현상(3번)은 **world/account 범위 콘텐츠에서만** 확인됐다. 이 두 범위는 애초에 "여러 캐릭터가 하나의 진짜 상태를 공유"하는 개념이라, 개별 캐릭터 응답의 `registration_flag`를 신뢰하는 대신 "이 월드/계정에서 한 번이라도 등록된 적 있는지"를 별도 원장에 누적해두고 그걸 기준으로 삼는 편이 오염에도 안전하고 개념적으로도 더 맞다.

**결정**:

1. **콘텐츠 항목별 정적 분류 테이블 신설** — `src/data/scheduler-content-catalog.json`(신규). 기존 `daily-quest-regions.json` 등(배경/아이콘 매칭 전용)과 목적이 달라 합치지 않고 별도 파일로 둔다. 각 항목은 `{ name, shareScope, maxCountOverride? }` 형태 — `shareScope`는 `"character"`(기본값, 명시 없으면 이걸로 취급) / `"world"` / `"account"` 중 하나, `maxCountOverride`는 API가 알려진 오류를 내는 항목에만 설정(아래 5번). [[ADR-006]]과 동일하게 AI가 임의로 채우지 않고 사용자(도메인 전문가)가 확정한 값만 반영한다.

   **확정된 분류(2026-07-21)**:

   | 항목 | shareScope |
   |---|---|
   | 몬스터파크 (일간) | world |
   | 에픽 던전: 하이마운틴 / 앵글러 컴퍼니 / 악몽선경 | account |
   | 지역 주간 콘텐츠 6종 (소멸의 여로 등) | character |
   | 무릉도장 | character |
   | 길드 지하 수로 / 주간 미션 포인트 / 플래그 레이스 | character |
   | [메이플 유니온] 주간 드래곤 퇴치 | world |
   | 주간 보스 (전체) | character |
   | 월간 보스 (검은 마법사) | character |
   | 그 외 미분류 일간 항목 | character (기본값) |

2. **Stale 감지 (character 범위)**: 캐릭터 동기화 시 `daily_contents`/`weekly_contents`를 독립적으로 판정한다 — 배열이 비어있거나 없으면 그 섹션은 "이 리셋 주기 이후 미접속"으로 간주해, `storage/scheduler-cache`에 남아있는 캐릭터의 마지막 정상 상태에서 이름·`registration_flag`는 유지하되 진행값(now_count→0, quest_state→0, isComplete→false)만 초기화해 표시한다. 배열에 내용이 있으면 응답을 그대로 신뢰하고 캐시를 갱신한다. `boss_contents`는 `cycle: weekly`는 `weekly_contents`와, `cycle: monthly`는 월간 경계(아래 3번)와 동일하게 취급한다.

3. **월간 보스 리셋 경계 확정**: 매월 1일 00:00 KST(사용자 확정, 2026-07-21) — `lib/boss-profit-period.ts`의 기존 "가정" 주석을 확정으로 갱신한다([[ADR-023]] 연계).

4. **world/account 범위 처리**: 개별 캐릭터 응답의 `registration_flag`는 신뢰하지 않는다. 대신 신규 저장 키 `worldSharedProgress:{world}` / `accountSharedProgress:{accountId}`에 항목별로 `{ active: boolean, 진행값, lastUpdatedBucket }`을 누적한다 — 어느 캐릭터든 신선한(섹션이 비지 않은) 응답으로 그 항목을 `registration_flag: true`로 보고하면 `active: true`로 전환되고, 그 뒤로는 이 캐릭터 저 캐릭터 할 것 없이 이 원장 값으로 계속 노출한다(오염된 개별 응답의 `registration_flag`는 완전히 무시). 진행값도 이 원장에서 가져오며, 원장 자체의 stale 여부는 `lastUpdatedBucket`(주간=목요일 기준 주 식별자, 월간=년월)을 `lib/reset-clock`의 리셋 경계와 비교해 판단한다 — 경계를 넘겼는데 그 사이 아무도 갱신 안 했으면 진행값만 리셋(`active`는 유지).
   - **트레이드오프**: 실제로 그 월드/계정의 모든 캐릭터가 게임 내에서 등록을 해제해도 `active`가 계속 `true`로 남아 캐시가 계속 노출될 수 있다 — 오염 현상을 피하기 위해 감수하기로 확정(2026-07-21).

5. **알려진 API 필드 오류 보정**: 길드 주간 미션 포인트는 `max_count`가 게임 규칙상 항상 10인데 API가 가끔 0을 반환한다(사용자 확인, 2026-07-21) — `scheduler-content-catalog.json`의 `maxCountOverride: 10`으로 API 값을 무시하고 고정 표기한다. 다른 항목의 유사 오류는 아직 발견된 게 이것뿐이라(2026-07-21 확인) 발견되는 대로 이 파일에 추가한다.

6. **받아들이는 한계 — 몬스터파크 월드 간 오염**: "A월드 접속 후 B월드 캐릭터 조회 시 A월드 값이 나옴" 현상은 어느 쪽이 진짜 값인지 구분할 신호가 응답에 없어 이번 설계에서 처리하지 않는다(사용자 확정, 2026-07-21). world 범위 원장이 "마지막으로 갱신한 캐릭터"의 값을 그대로 신뢰하는 구조라 이 오염을 그대로 흡수하게 된다는 점을 알려진 한계로 남긴다.

7. **저장소**: SQLite로 전환하지 않고 `@capacitor/preferences` 유지 — 필요한 건 world/character/account 조합의 구조화된 키 조회지 관계형 쿼리(WHERE/JOIN)가 아니라서 [[ADR-003]]의 SQLite 전환 기준(실제 쿼리 필요)에 해당하지 않는다. 기존 `schedulerCache:{ocid}` 하나였던 걸 daily/weekly 각각의 "마지막 신선했던 리셋 버킷" 정보를 포함하도록 확장하고, 신규 키 `worldSharedProgress:{world}`/`accountSharedProgress:{accountId}`를 추가한다.

**미확정**:
- 일간 콘텐츠 전체 목록(몬스터파크 외 다른 항목이 있는지) — 발견되는 대로 `scheduler-content-catalog.json`에 추가.
- `scheduler-content-catalog.json`의 정확한 스키마·타입 정의, `storage/scheduler-cache.ts`의 실제 마이그레이션 방법(기존 캐시 포맷과의 하위 호환)은 구현 단계에서 확정.
