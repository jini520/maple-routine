### ADR-052: 캐시 데이터 삭제 범위 — 사용자 설정 보존, SQLite 테이블 목록 단일 진실 공급원화 (구현 완료, 2026-07-29)

**배경**: "캐시 데이터 삭제"(`storage/cache-data.ts`)는 두 저장소를 서로 다른 방식으로 지운다 — Preferences는 **`KEEP_KEYS`를 제외한 전부**(블랙리스트 없음, 새 키가 자동으로 삭제 대상에 포함)인 반면, SQLite는 **하드코딩된 화이트리스트**(`CLEARED_TABLES`)다. 이 비대칭 때문에 실제 결함이 두 개 났다.

1. **`boss_drop_records`가 삭제 목록에서 빠져 있다.** `storage/sqlite/db.ts`가 만드는 테이블은 4개인데([[ADR-038]]에서 나중에 추가됨) `CLEARED_TABLES`는 3개다. 그래서 (a) 캐시 데이터를 삭제해도 드롭 기록이 남고, (b) 같은 목록을 순회하는 `getCacheDataSize()`가 실제보다 작은 용량을 표시한다. 테이블이 늘 때 `db.ts`와 `cache-data.ts`를 함께 고쳐야 한다는 사실이 **코드 어디에도 표현돼 있지 않아** 사람이 기억해야만 유지되는 구조였다.
2. **확인 모달(`app/settings/CacheClearConfirm.tsx`) 문구가 실제 범위와 어긋난다.** `trackingMode`·`dropEffect`는 `KEEP_KEYS`에 없어 실제로는 삭제되는데 "삭제됨" 안내에 없다.

**결정**:

1. **`trackingMode`·`dropEffect`를 `KEEP_KEYS`에 추가해 캐시 데이터 삭제에도 보존한다.** 둘 다 "재조회로 복구 가능한 캐시"가 아니라 사용자가 명시적으로 고른 취향 설정이고, 같은 성격의 `theme`은 이미 보존 대상인데 이 둘만 지워지는 것은 일관성이 없다. 캐시 삭제는 `apiKey`·`selectedAccountId`를 남기므로 사용자가 온보딩으로 돌아가지도 않는다 — 수동 모드를 쓰던 사용자가 아무 안내 없이 자동 모드로 되돌아가는 것은 "저장 공간 확보"라는 이 기능의 의도를 넘어선 부수효과다. [[ADR-035]] 트레이드오프에서 "캐시 삭제 개편과 함께 정하겠다"며 **보류**했던 결정을 여기서 해소한다.
2. **삭제 대상 SQLite 테이블 목록의 단일 진실 공급원은 `storage/sqlite/db.ts`의 테이블 정의 배열이다.** `db.ts`가 `[{ name, createSql }]` 배열 하나를 갖고 스키마 생성(`openBossProfitDb`)도 그 배열을 순회하며, 이름 배열을 export해 `cache-data.ts`가 import한다. `CLEARED_TABLES` 하드코딩(두 번째 목록)은 없앤다. 새 테이블은 그 배열에만 추가하면 **스키마 생성·캐시 삭제 범위·용량 계산에 자동 반영**되므로, 목록이 코드상 하나뿐이라 구조적으로 drift가 불가능해진다.
   - **검토했으나 기각한 대안**: `sqlite_master` 동적 조회(`SELECT name FROM sqlite_master WHERE type='table'`). 목록을 아예 코드에서 없앨 수 있지만 `sqlite_sequence` 같은 내부 테이블을 걸러야 하고, "이 DB의 모든 테이블 = 캐시 삭제 대상"이 앞으로도 참이라는 보장이 없다(보존해야 할 테이블이 생기면 조용히 지워진다). 배열 하나로도 drift는 이미 막힌다.
3. **확인 모달 문구는 실제 삭제 범위와 동기화한다.** "삭제됨"에 드롭 기록을 추가하고, "유지됨"에 결정 1의 두 항목(트래킹 모드·드롭 연출 설정)까지 적는다.

**이유**:
- 결정 1 없이는 "캐시 삭제"가 사용자 설정 초기화까지 조용히 수행한다. 이 기능의 이름·의도(저장 공간 확보)와 실제 효과가 어긋나 있었고, `theme`만 보존 목록에 있는 것은 설계된 구분이 아니라 그 뒤에 추가된 두 키가 목록에 반영되지 않은 결과다.
- 결정 2 없이 `boss_drop_records`만 목록에 끼워 넣으면 **같은 사고가 다음 테이블에서 반복된다.** 원인은 "한 테이블이 빠졌다"가 아니라 "목록이 두 곳에 있고 그 연결이 코드에 없다"이다.
- **고아 드롭 행 문제**: 수익 기록(`boss_profit_records`)은 지워지고 드롭 기록만 살아남으면 참조 대상 없는 행이 된다. 드롭은 `(ocid, boss, difficulty, period_key, drop_index)`로 저장되므로, 같은 캐릭터가 같은 보스를 같은 기간에 다시 처치하면 **삭제했다고 생각한 예전 드롭이 되살아나 새 수익 기록에 붙는다.** 캐시 삭제 직후 수익이 0이 아닌 이상한 상태로 보이는 경로다.
- 결정 3은 위 둘을 사용자에게 정직하게 알리는 부분이다 — 안내와 실제 동작이 다르면 삭제 결정 자체가 잘못된 정보 위에서 내려진다.

**트레이드오프**:
- 결정 1로 "캐시 데이터 삭제"가 **완전한 초기화는 아니게 된다** — 설정(`theme`·`trackingMode`·`dropEffect`)이 남는다. 완전 초기화를 원하는 사용자에게는 "연결 해제"와 조합해도 설정은 남는 경로가 된다. 다만 이 기능의 이름과 의도가 애초에 "캐시" 삭제이므로, 초기화 수요는 별도 기능(지울 데이터를 고르는 개편, [lifecycle.md](../persistence/lifecycle.md) 참고)에서 다루는 게 맞다.
- 결정 2로 `db.ts`가 스키마 생성뿐 아니라 **삭제 범위까지 책임지게 되어** 저장소 레이어의 결합이 한 줄 늘어난다(`cache-data.ts` → `db.ts`의 테이블 이름 배열 import). 대신 그 결합이 바로 drift를 막는 장치다 — 목록이 갈라질 자리를 없애는 대가로 의존 방향 하나를 고정한다.

**저장소**: 스키마 변경 없음(테이블 정의를 배열로 재구성할 뿐, `CREATE TABLE` 문 자체는 그대로). `KEEP_KEYS` 확대는 Preferences 삭제 범위만 바꾸며 값 형식은 변경 없음.

**구현 완료 (2026-07-29)** — 파일 3개가 바뀌었다.
- `storage/sqlite/db.ts` (결정 2): 흩어져 있던 `CREATE TABLE` 상수 4개를 `TABLE_DEFINITIONS`(`[{ name, createSql }]`) 배열 하나로 합치고 `BOSS_PROFIT_TABLE_NAMES`(`readonly string[]`)를 export한다. `openBossProfitDb()`는 그 배열을 순회해 스키마를 만든다(SQL 본문·실행 순서·메이린 마이그레이션은 그대로).
- `storage/cache-data.ts` (결정 1·2): `KEEP_KEYS`에 `trackingMode`·`dropEffect`를 더해 5개가 됐고(Preferences는 여전히 "이 5개 빼고 전부" 반전 규칙이라 새 키는 자동으로 삭제 대상), `CLEARED_TABLES` 하드코딩을 지우고 `BOSS_PROFIT_TABLE_NAMES` import로 교체했다. `clearCacheData()`의 `DELETE FROM`과 `getCacheDataSize()`의 합산이 같은 배열을 돌아 범위가 구조적으로 일치하며, 빠져 있던 `boss_drop_records`가 이제 실제로 지워지고 용량에도 합산된다. 테이블 이름 문자열은 이 파일에 한 번도 등장하지 않는다.
- `app/settings/CacheClearConfirm.tsx` (결정 3): "삭제됨"에 드롭 기록을, "유지됨"에 트래킹 모드(앱 표기 "스케줄 관리 방법")·드롭 연출을 넣어 실제 범위와 맞췄다 — 유지됨 5항목이 `KEEP_KEYS` 5개와 1:1이다. 레이아웃·색 토큰·버튼은 그대로이고 두 `span`의 텍스트만 바뀌었다.

회귀 가드 테스트 2종을 함께 넣었다. (1) `storage/sqlite/__tests__/db.test.ts` — `db.ts` **소스 텍스트**를 읽어 `CREATE TABLE IF NOT EXISTS (\w+)` 매치 집합과 `BOSS_PROFIT_TABLE_NAMES`를 비교한다. 배열을 우회해 `db.execute`로 직접 만든 테이블까지 잡히므로 "정의는 늘었는데 export가 안 늘었다"가 실패로 드러난다. (2) `storage/__tests__/cache-data.test.ts` — `BOSS_PROFIT_TABLE_NAMES`를 순회하며 `DELETE FROM <name>;`이 전부 호출됐는지 + 호출 횟수가 테이블 개수와 같은지(목록 밖 테이블을 지우지 않는지) 단언하고, `KEEP_KEYS` 5개 보존과 `getCacheDataSize()`가 보존 키를 합산하지 않음을 함께 고정한다.

남은 것 — 확인 모달의 "삭제됨" 줄은 대표 항목만 적은 요약이라 실제로 지워지는 `boss_party_settings`(파티 설정)·`boss_profit_period_checks`(기간 체크)가 문구에 없다. 결정 3이 요구한 두 항목(드롭 기록·보존 설정)은 반영됐고 적힌 항목은 전부 실제 삭제 대상이라 이번 범위에서는 손대지 않았다 — 열거를 어디까지 늘릴지는 문구/UX 판단이라 별도로 정한다.
