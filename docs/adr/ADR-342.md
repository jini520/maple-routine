>
> **결정 1 · 2 · 3 은 구현 완료다**(2026-10-09, `DB_VERSION` 12, PR #630). 드롭 기록의 PK 가

[[ADR-280]](결정 11 - 아이템을 key 로 든다) · [[ADR-227]](`ocid` 는 떼지 않는다)

## 맥락

### 자연키가 설계상 바뀐다

드롭 기록의 지금 PK 는 `(ocid, boss_key, difficulty, period_key, drop_index)` 다. 그 조각 둘이 바뀐다.

**`difficulty` 는 난이도가 확정될 때 바뀐다.** 익스트림으로 적은 드롭이 하드로 확정되면 그 난이도
키로 옮겨진다([[ADR-069]] 결정 4).

**`drop_index` 는 자리 번호다.** `replaceBossDropRecords` 가 그룹을 통째로 지우고 배열 위치로 다시
매긴다.

```ts
await db.run(DELETE_SQL, [ocid, bossKey, difficulty, periodKey])
for (let index = 0; index < drops.length; index++) { … INSERT … }
```

그래서 목록에서 하나를 빼면 뒤가 당겨진다. 이 열쇠로 서버에 가격을 보내면 **가격이 엉뚱한 아이템에
붙는다.**

```
처음         index 0 = A(10억)   index 1 = B(5억)   index 2 = C(3억)
A 를 지우고   index 0 = B        index 1 = C
다시 보내면   서버 (…,0) 이 A 의 10억에서 B 의 5억으로 덮인다
             서버 (…,2) 의 C 는 고아로 남는다
```

### 기기 저장이 서버 왕복에 걸리면 안 된다

서버가 식별자를 만들어 응답으로 주는 모양이면, 응답을 받아야 기기에 저장이 끝난다. 통신이 실패하면
**사용자가 적은 가격이 기기에도 안 남는다.** 서버가 값을 모으는 목적은 시세 추이라 한두 건이 빠지는
것은 문제가 아니지만, 사용자의 기록이 사라지는 것은 다른 등급의 문제다(사용자 지정 2026-10-08).

### 시세 줄과 드롭 기록은 다른 것이다

처음에는 서버 표를 기기 행의 사본으로 두려 했다가 사용자가 거뒀다(2026-10-08). 기기 행은 분배
인원 · 비율 · 수수료 넷까지 들어 **내 몫을 계산하는 재료**이고, 서버가 모으는 것은 시세다. 두 구조를
따로 운영한다.

## 결정

### 결정 1. 드롭 기록의 PK 를 uuid 하나로 바꾼다 (사용자 지정)

`boss_drop_records` 에 `drop_record_id TEXT` 를 더해 PK 로 삼는다. 지금의 다섯 조각은 **평범한 칸으로
남고 그 위에 인덱스**를 건다. 조회하는 코드가 그대로 돌고, 행을 가리키는 값만 안 바뀌는 것으로 갈린다.

**그 다섯에 `UNIQUE` 를 걸지 않는다.** 필요한 것은 유일성이 아니라 조회 속도이고, 유일성을 걸면
결정 2 의 저장 방식에서 깨진다. 한 행씩 고치는 사이에 `drop_index` 가 일시적으로 겹칠 수 있다(A 를
1 로 바꿨는데 B 가 아직 1 이다). SQLite 는 문장마다 제약을 보므로 그 자리에서 실패한다.

uuid 는 **기기가 만든다.** 서버가 만들면 맥락의 둘째 문제가 생긴다.

**만드는 것은 SQLite 다.** 드롭 기록을 어차피 SQLite 에 쓰므로 `INSERT` 안에서 `randomblob()` 으로
만든다. Postgres 의 `gen_random_uuid()` 와 같은 자리다.

```sql
lower(hex(randomblob(4)) || '-' || hex(randomblob(2)) || '-4' || substr(hex(randomblob(2)), 2)
      || '-' || substr('89ab', abs(random()) % 4 + 1, 1) || substr(hex(randomblob(2)), 2)
      || '-' || hex(randomblob(6)))
```

식이 길어 상수 하나로 뽑아 쓰는 자리마다 끼운다. 난수원은 SQLite 의 `sqlite3_randomness()` 이고
unix VFS 가 `/dev/urandom` 에서 씨앗을 받는다(문서에 적힌 동작 · 기기 실측은 착수할 때 한다).

**JS 에서 안 만든다.** `crypto` 가 전역에 없고(확인 2026-10-08) `Math.random` 은 시딩 품질을 모른다.
새 네이티브 모듈을 들이면 스토어 빌드를 기다린다. SQLite 는 이미 번들에 있어 **OTA 로 간다.**

**이 값은 비밀이 아니다.** 남의 것을 맞혀도 그 사람의 인증 없이는 못 쓴다 - 서버가 쓰는 자리에서
소유를 확인한다(결정 7). 암호학적 난수가 아니어도 된다.

### 결정 2. `replaceBossDropRecords` 가 기존 uuid 를 물려준다

지금처럼 그룹을 지우고 다시 넣으면 저장할 때마다 uuid 가 새로 생겨 서버에 같은 기록이 쌓인다.

```
기존 행의 uuid 를 먼저 읽는다
아이템 신분(`item_key` + `box_origin_key` + `slot` + `ring_level`)으로 짝지어 uuid 를 물려준다
새로 생긴 아이템만 새 uuid
목록에서 빠진 아이템은 삭제
```

[[ADR-069]] 결정 4 의 난이도 확정 이관도 같다. 행을 옮기면서 uuid 를 **보존**한다. 거기서 새로 만들면
서버에 행이 하나 더 생긴다. **이 문서의 유일한 함정이 그 두 자리다.**

### 결정 3. 월드를 드롭 기록이 자기 칸으로 든다

`world TEXT` · `world_key TEXT` 를 더한다. `boss_profit_records` 와 `character_profiles` 가 이미 두
칸으로 들고, 집계가 key 로 가른다.

**짝인 수익 행에서 물려받지 않는다.** `defeated_on` 은 그렇게 했지만([[ADR-172]] 결정 6, 근거는 "두
벌로 박으면 갈라질 수 있는 값이 하나 는다") 월드는 다르다. **수익 행이 없는 드롭이 있다**(결정석
가격을 모르는 보스). 그 드롭은 물려받을 짝이 없어 월드를 영원히 모르고, 서버로 보내는 값이라 비면
그 기록을 못 쓴다.

캐시에 월드가 없으면 `NULL` 이다. 0 이나 빈 문자열로 채우면 "모름" 이 값으로 둔갑한다.

### 결정 4. 전송은 가격을 저장·수정하는 그 자리에서 한 건이다

훑어 보내지 않는다. 사용자가 가격을 넣거나 고쳐 저장하는 순간 그 한 건이 나간다. 보낸 것을 적는
원장이 필요 없다 - 보내는 시점이 곧 사용자 동작이다.

`price_state` 가 `'entered'` 인 것만 보낸다. `'excluded'`(기록 안함)와 미입력(`NULL`)은 안 보낸다.

### 결정 5. 기기 저장이 먼저다. 전송 실패가 저장을 막지 않는다 (사용자 지정)

기기에 쓰고 나서 보낸다. 전송이 실패해도 사용자의 기록은 남는다.

### 결정 6. 못 보낸 것은 [[ADR-343]] 의 대기 표가 든다. 드롭 가격이 그 첫 종류다

전송 실패를 드롭 가격만의 장치로 풀지 않는다. [[ADR-299]] 결정 1 이 보스 기록과 가계부까지 범위로
적었으므로 같은 통로를 여러 종류가 쓴다. 공용 장치는 [[ADR-343]] 이 소유한다.

이 문서가 거기에 넣는 것은 종류 하나와 **읽기 함수** 하나다.

```
kind      드롭 가격
읽기      (drop_record_id) => 보낼 값 | null
            원본이 있고 price_state = 'entered'              → 값
            원본이 없거나 price_state 가 'entered' 가 아니다  → null (서버에서 지운다)
```

**기록 표에 전송 상태를 안 둔다.** 처음에는 `boss_drop_records` 에 `price_sent_at` ·
`price_send_attempts` 를 두려 했는데 사용자가 거뒀다(2026-10-08) - 전송 시각과 시도 횟수는 드롭
기록의 값이 아니다. 그리고 칸이 둘 늘면 `RecordedDrop` 을 만드는 다섯 자리가 다 들고 다녀야 한다.

**`'excluded'` 로 바꾼 것과 획득 불가로 지워진 것이 같은 분기를 탄다.** 읽기 함수가 둘 다 `null` 로
답하므로 작업 종류를 적는 칸이 필요 없다.

### 결정 7. 서버 시세 줄은 자기 PK 를 갖고 기기 uuid 는 멱등 열쇠다 (사용자 지정)

기기가 보낸 uuid 를 서버의 PK 로 쓰지 않는다. 서버가 자기 PK 를 따로 만들고, 받은 값은 칸으로
저장해 `UNIQUE` 를 건다.

```sql
id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),   -- 서버가 만든다
user_id           uuid NOT NULL REFERENCES users(id),           -- [[ADR-340]]
drop_record_id  uuid NOT NULL UNIQUE,                         -- 기기가 만든 값. 멱등 열쇠
```

그 `UNIQUE` 가 멱등을 만든다. 응답만 유실돼 기기가 다시 보내도 같은 행을 찾아 고친다. 몇 번
보내도 한 행이다.

**`user_id` 를 그 제약에 엮지 않는다.** uuid 는 혼자서 이미 유일하므로 엮어도 유일성이 안 늘고,
오히려 같은 `drop_record_id` 가 다른 `user_id` 로 올 때 행을 둘 허용한다. 키를 재발급하면 다른
사람으로 보므로(#607) 실제로 일어나는 경우다.

**남의 uuid 를 맞혀 그 행을 덮어쓰는 것은 제약이 아니라 문장이 막는다.**

```sql
INSERT … ON CONFLICT (drop_record_id) DO UPDATE
  SET … WHERE <표>.user_id = EXCLUDED.user_id
```

그 `WHERE` 가 있으면 남의 행에 걸린 충돌은 아무 일도 안 하고 끝난다. 제약으로 풀려 하면 행이 둘
생긴다.

`drop_record_id` 는 `_id` 로 끝나 FK 처럼 읽히지만 **참조할 표가 서버에 없다.** 기기 행의 사본을 서버에
두지 않기로 했으므로(맥락) `REFERENCES` 를 붙이지 않는다.

### 결정 8. 기능이 나간 뒤 시작된 기간만 보낸다 (사용자 지정)

기준은 `period_key` 다. **불변이라** 나중에 흔들리지 않는다(`recorded_at` 은 감사 필드라 그룹을 다시
저장할 때 오늘로 덮인다).

기존 기록은 서버로 안 옮긴다. 기능이 나간 뒤에 **지난 기간**을 채운 기록도 안 보낸다(사용자 지정) -
규칙이 하나이고 칸이 안 는다.

그래서 기존 행의 월드를 채우는 이관이 필요 없다. [[ADR-069]] 결정 3 이 그때 기존 기록을 현재 캐시
월드로 채웠는데 **근거가 "아직 실사용자가 없어" 였고 지금은 사라졌다.** 되풀이하면 리프한 캐릭터의
리프 전 드롭에 리프 후 월드가 박힌다.

## 대가

- **이관이 하나 든다.** `DB_VERSION` 11 → 12 다. `drop_record_id` · `world` · `world_key` 세 칸과
  [[ADR-343]] 의 대기 표, 그리고 PK 재작성이 한 번에 돈다. 기존 행에 `drop_record_id` 를 채워야 한다 -
  안 채우면 `replaceBossDropRecords` 가 그룹을 다시 쓸 때 빈 값과 새 값이 섞인다.
- **칸을 더할 때 두 자리를 함께 고친다.** `boss-tables.ts` 의 `BOSS_DROP_RECORDS_BODY`(새 설치와
  버전 4 재작성이 함께 본다)와 `db.ts` 의 `ensureColumn`(이미 쓰던 기기)이다. 한쪽만 고치면 절반의
  기기에서만 깨진다(`spend_records.form` 이 실제로 그랬다).
- **`RecordedDrop` 을 만드는 자리가 다섯이다.** 변환기 셋(`lib/boss/boss-drops.ts` ·
  `features/boss-profit/rows.ts` · `features/boss-profit/drop-history-store.ts`)과 드롭을 새로 만드는
  둘(`BossDropSheet` 의 `toggleNormal` · `applyBoxResult`)이다. 새 칸을 **필수**로 선언하면 타입
  검사가 다섯을 다 잡는다. 선택으로 두면 빠뜨려도 통과하고 값만 조용히 사라진다([[ADR-124]] 구현
  중 실제로 그랬다).
- **부팅에 작업이 하나 는다.** 지금 `boot.ts` 가 하는 일은 포트 꽂기뿐이다.
- **`randomblob` 의 난수 품질을 기기에서 확인해야 한다.** 문서에 적힌 동작은 `/dev/urandom` 이지만
  재지는 않았다. 착수할 때 `hex(randomblob(16))` 을 두 번 실행해 다른 값이 나오는지, 앱을 완전히 종료한
  뒤 다시 켜도 수열이 안 반복되는지 본다.
- **서버에 유령 행이 드물게 남는다.** `delete` 가 5회 안에 못 나가면 버린다. 획득 불가 항목이었다면
  불가능했던 아이템의 가격이 시세 표본에 남는다.

## 기각

- **서버 표를 기기 행의 사본으로 둔다.** 분배 인원 · 비율 · 수수료 넷은 내 몫을 계산하는 재료이고
  시세와 무관하다. 사용자 지정으로 기각했다(맥락).
- **서버가 식별자를 만들어 응답으로 준다.** 통신 실패가 기기 저장을 막는다(맥락). 응답만 유실되는
  경우에 재전송이 서버에 행을 하나 더 만든다.
- **기기 행에 전송 실패 플래그 한 칸만 둔다.** 삭제를 못 담는다 - 행이 지워지면 플래그를 둘 데가
  없다. 결정 6 의 표가 그 자리까지 덮으므로 플래그는 안 둔다.
- **자연키를 멱등 열쇠로 쓴다.** 맥락이 실측으로 반박한다.
- **기존 기록을 서버로 옮긴다.** 사용자 지정으로 기각했다(결정 8).

## 정정

### 정정 1. 서버 줄은 가격이 바뀔 때마다 쌓인다. 그중 **마지막 한 줄만 유효**하다 (사용자 지정 2026-10-09)

결정 7 은 `UNIQUE (drop_record_id)` 로 한 기록에 한 줄을 강제해 마지막 값만 남겼다. #610 이
"노이즈를 보려면 처음 값과 고친 값 둘 다 의미가 있다" 고 적었고 사용자가 쌓는 쪽을 골랐다.

그 자리에서 사용자가 함정을 짚었다.

> 바뀔 때마다 한 줄을 쌓으면 한 개의 아이템 판매 금액이 여러개 생기는거 아니야?
> 마지막에 기록한 값만 유효하게 만들어?

맞다. 쌓기만 하면 10억으로 적고 3억으로 고친 기록 하나가 시세 분포에 **두 번** 센다. 그래서
유효한 줄을 표가 직접 말한다.

```sql
-- 이 줄을 대신한 줄이 들어온 시각. NULL 이 지금 유효한 한 줄이다.
superseded_at timestamptz

-- 유효한 줄은 기록마다 하나뿐이다. 칸 하나에 거는 유일 인덱스이고 조건이 필터다.
CREATE UNIQUE INDEX drop_prices_current ON drop_prices (drop_record_id)
  WHERE superseded_at IS NULL
```

**집계는 `WHERE superseded_at IS NULL` 하나만 붙이면 된다.** 창 함수로 「기록마다 마지막 줄」을
뽑는 길도 있지만 그 길은 쿼리마다 기억해야 하고, 한 번 빠뜨리면 조용히 두 번 센다. 사용자가
걱정한 바로 그 상태다.

**`drop_record_id` 의 `UNIQUE` 를 걷은 자리를 이 인덱스가 메꾼다.** 엮은 키가 아니다 - 칸은
하나이고 `WHERE` 는 어느 줄에 거는지를 고르는 조건이다(서버의 `notices_pending_schedule` 이 같은
모양을 이미 쓴다).

**멱등은 제약이 아니라 값 비교로 선다.** 받은 가격이 유효한 줄의 가격과 같으면 아무것도 안 한다.
응답만 유실돼 기기가 다시 보내도 줄이 안 늘어난다.

**지우기도 줄을 안 지운다.** 원본이 사라졌거나 `'excluded'` 로 바뀌면([[ADR-343]] 결정 2) 유효한
줄의 `superseded_at` 만 적는다. 유효한 줄이 없는 상태가 「가격을 거뒀다」이고, 거둔 사실 자체가
노이즈 관찰의 재료다.

### 정정 2. 한 건에 실을 칸 (사용자 지정 2026-10-09)

#610 의 "한 건에 실을 것" 이 닫혔다. 핵심 넷에 **월드 key · 반지 레벨 · 슬롯**을 더한다.

| 칸 | 왜 |
|---|---|
| `drop_record_id` | 기기가 만든 값. 같은 기록의 수정을 잇는 열쇠 |
| `user_id` | [[ADR-340]] 의 사람 |
| `item_key` | 분포의 축 |
| `price_meso` | **판매 총액**이다. 내 몫이 아니다([[ADR-124]] 결정 1) |
| `period_key` | 언제 먹었나. 불변이라 추이의 축이 된다 |
| `world_key` | 월드마다 시세가 갈린다. 캐시에 월드가 없으면 `NULL` 이고 그대로 보낸다 |
| `ring_level` | **반지 레벨이 시세를 가른다**(사용자 확인 2026-10-09 · [[ADR-006]] 절차). 없으면 같은 `item_key` 에 레벨이 다른 반지 값이 한 분포에 섞인다 |
| `slot` | 장비 부위. 해당 갈래가 아니면 `NULL` |
| `received_at` | 서버가 받은 시각. 기기 시계를 믿지 않는다 |

**안 싣는 것.** 보스 key · 난이도(사용자 선택에서 빠졌다)와 상자 출처 key. 분배 인원 · 비율 ·
수수료 넷은 애초에 내 몫을 계산하는 재료라 시세와 무관하다(맥락). `quantity` 는 항상 1 이다.

### 정정 3. 노이즈는 관리 화면으로 본다 (사용자 지정 2026-10-09)

psql 쿼리로만 보는 길을 기각했다. 서버에 이미 관리자 페이지 셋이 있어(`admin-page.ts` ·
`admin-list-page.ts` · `admin-manual-page.ts`) 자리와 인증이 그대로 선다.
