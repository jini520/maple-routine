# ADR-099 — 스크롤의 소유자를 문서에서 화면으로 옮긴다

- 상태: **스케줄러 계열 4화면 전환 완료 · 실기기 검증 통과**(프로토타입 1화면 → 확산, 2026-08-06).
  보스 수익은 범위 밖(결정 4)
- 관련: [[ADR-098]](탭 이동 스크롤 클램프 — 이 전환이 그 원인 ①을 없앤다) · [[ADR-085]] 결정 4(이 전환을 "근본이긴 하지만"이라며 미룬 자리) · [[ADR-072]](문서 전체 스크롤 전제 — 이 결정이 뒤집는 것) · [[ADR-073]]·[[ADR-074]](당김 인디케이터 — 유지) · [[ADR-047]](중첩 sticky — 보스 수익, 이번 범위 밖) · [[ADR-077]](히스토리 오버레이는 이미 자기 스크롤을 갖는다)
- 관련 문서: [features/content-scheduler.md](../features/content-scheduler.md) · [foundation/design-system.md](../foundation/design-system.md)

## 왜 다시 꺼내는가

[[ADR-098]]이 원인을 두 층으로 갈랐다.

```
① 스크롤 오프셋이 화면을 넘어 살아남는다(+ 문서 높이가 달라 클램프)  ← SPA: 문서가 하나뿐
② 그 변화가 프레임으로 드러난다                                      ← WKWebView 컴포지터 지연
```

①을 JS로 보정하는 처방은 **보정하는 동작 자체가 ②에 걸려 눈에 보였다.** 실기기 연속 프레임에서
두 얼굴을 다 봤다 — 이동을 한 프레임 미뤘을 때는 *떠나는 화면이 최상단으로 올라간 장*, 같은
태스크로 붙였을 때는 *같은 장이 그대로*(빌드 13). 즉 **문서 스크롤을 쓰는 한 이동 근처에서
오프셋을 만지면 ②가 그것을 그린다.** 리셋을 앞에 두든 뒤에 두든 같다.

남는 길은 오프셋을 안 건드리거나(= 탭을 열면 다른 탭의 위치를 물려받는다), **스크롤의 소유자를
바꾸는 것**뿐이다. 후자가 이 ADR이다.

같은 뿌리에서 증상이 네 번째다([[ADR-080]] 기간 이동 → [[ADR-084]]·[[ADR-085]] 아코디언 접기 →
[[ADR-098]] 탭 이동 → 이동 프레임). "작은 처방으로 충분하다"는 가정이 네 번 빗나갔다.

## 결정 (프로토타입 범위)

**1. 화면이 자기 스크롤 컨테이너를 갖는다 — 단 그 컨테이너는 *뷰포트 크기*다.**

```
<div className="fixed inset-0 overflow-y-auto overscroll-y-none">   ← 스크롤포트 = 뷰포트
  <PageHeader/>        고정 헤더(뷰포트 기준) + 실측 spacer
  <목록>               pb-[calc(4rem+var(--sa-bottom))] 로 탭바 자리
</div>
{모달}                  ← 컨테이너 **바깥**
```

스크롤 상태가 이 DOM 요소에 붙으므로 **화면과 함께 태어나고 함께 죽는다** — 계승할 오프셋이
존재하지 않는다(①이 구조적으로 소멸). 네이티브에서 화면마다 `UIScrollView` 를 갖는 것과 같은
의미론이고, Ionic 이 `ion-content` 로 푸는 방식도 이것이다.

**컨테이너를 뷰포트 크기로 두는 것이 요점**(사용자 요구) — 헤더 아래 박스만 스크롤시키면 스크롤
인디케이터가 그 박스 안에만 그려진다. 스크롤포트가 뷰포트면 인디케이터 범위도, thumb 길이
(`콘텐츠 높이 ÷ 스크롤포트 높이`)도 지금과 같다.

**모달은 컨테이너 바깥에 둔다** — `position: fixed` 는 스태킹 컨텍스트를 만들므로, 안에 두면
모달의 `z-50` 이 그 컨텍스트 안에 갇혀 `z-30` 탭바 **아래**로 그려진다([[ADR-077]] 결정 3이
오버레이를 루트 바깥에 둔 것과 같은 종류의 함정).

**2. 당겨서 새로고침은 스크롤 루트를 프롭으로 받는다 — 판정 기준만 바뀌고 감각은 그대로다.**

`usePullToRefresh({ scrollRoot })` 를 선택 프롭으로 더한다. 주면 최상단 판정이
`scrollRoot.scrollTop <= 0` 이고 조상 사슬 탐색([[ADR-072]] 결정 14, 오버레이 제외)이 그 루트에서
멈춘다(페이지 자신은 배제 대상이 아니다). 안 주면 지금까지의 문서 기준 그대로다 — **전환하지 않은
화면 3개는 코드가 바뀌지 않는다.**

**3. 컨텐츠 스케줄러 한 화면으로 먼저 재고, 통과하면 확산한다.** ① 이동 프레임이 사라지는가
② 모멘텀·러버밴드가 문서 스크롤과 동등한가 ③ 인디케이터가 같은 모습인가 ④ 당김이 살아있는가.

**결과: 네 가지 모두 통과**(실기기, 빌드 14~17). 곁가지로 나온 셋(흰 인디케이터·안전영역 침범·탭바
사이 띠)은 전부 같은 뿌리였다 — **문서 스크롤에만 브라우저가 공짜로 해주던 처리**(인디케이터 색
유추·안전영역 인셋)를 컨테이너에서는 우리가 명시해야 한다는 것(결정 5·6·7).

그래서 **스케줄러 계열 4화면(컨텐츠·보스·컨텐츠 관리·보스 관리)으로 확산**하고, 마크업은 공용 셸
`components/templates/ScreenScroll` 하나가 갖는다 — 네 화면이 같은 상자를 복붙하면 [[ADR-094]]가
`PageHeader` 에서 없앤 취약 구조가 그대로 되살아난다(한 곳을 고쳐도 나머지가 안 고쳐진다).
관리 화면 2개는 제스처가 없어 `ref` 없이 쓴다.

**4. 보스 수익은 이번 범위 밖이다.** ~~(폐기 — [[ADR-100]] 이 같은 날 전환했다)~~ 그 화면은 중첩 sticky([[ADR-047]] 카드 헤더·배지 레일)와
접기 전 사전 스크롤([[ADR-085]] 결정 2)이 문서 스크롤에 얽혀 있어, 옮기는 순간 그 전부가 재검증
대상이 된다. 스케줄러 결과를 보고 별도로 판단한다.

**5. 테마의 라이트/다크를 CSS `color-scheme` 으로도 선언한다.**

프로토타입 첫 실기기 관측에서 **스크롤 인디케이터가 흰색**으로 나왔다(사용자 보고). 원인은 컨테이너
자체가 아니라 **비어 있던 선언**이다 — 우리가 그리지 않는 UI 크롬(스크롤 인디케이터·폼 컨트롤)의
색은 브라우저가 고르는데, 문서 스크롤일 때는 WebKit 이 **페이지 배경색에서 유추**해 우연히 맞았고,
요소 스크롤러에서는 그 유추 경로가 없어 기본값(어두운 표면 가정 → 흰 인디케이터)으로 떨어졌다.

`applyThemeToDocument` 가 이미 계산하는 `isDark` 를 `documentElement.style.colorScheme` 에도 건다 —
네이티브 상태바·내비바에는 같은 값을 이미 넘기고 있었으니 **빠져 있던 세 번째 수신자를 채우는 것**이다.

**그것만으로는 부족했다**(실기기 재확인): 다크 테마는 정상이 됐지만 **라이트 테마에서 인디케이터가
여전히 흰색**이었다. 요소 스크롤러의 인디케이터 색을 WebKit 이 무엇에서 유추하는지에 기대는 대신
표준 프로퍼티로 직접 지정한다 — `documentElement.style.scrollbarColor` 를 모드별 반투명 무채색
(`rgba(0,0,0,.35)` / `rgba(255,255,255,.35)`, 트랙 없음)으로 둔다. `color-scheme` 선언은 그대로
남긴다 — 폼 컨트롤 등 다른 UI 크롬의 근거이고, 애초에 빠져 있던 것이 맞다.

컨테이너에 배경색을 칠하는 안은 쓰지 않는다 — `position: fixed` 라 스태킹 컨텍스트를 만들고, 불투명
배경은 [[ADR-088]] 테마 배경 이미지(`z-index: -1` 백드롭)를 통째로 가린다(그 ADR 이 앱 루트에서
`bg-bg` 를 빼야 했던 것과 같은 이유).

**6. 스크롤포트 상단을 안전영역만큼 인셋한다 — 콘텐츠는 음수 마진으로 되돌린다.**

프로토타입 실기기 관측 두 번째: **스크롤 인디케이터가 상단 안전영역(노치)을 침범**했다. 인디케이터는
페이지 콘텐츠가 아니라 **스크롤포트 위에 겹쳐** 그려지므로(그래서 불투명한 고정 헤더 위에도 그려진다)
상자가 노치까지 닿으면 인디케이터도 거기까지 올라간다. 문서 스크롤일 때는 WKWebView 가 메인
스크롤뷰에 안전영역 인셋을 자동으로 넣어줬다 — 착수 전 "포기 목록"에 적어둔 *"인디케이터 안전영역
인셋 자동 처리"* 가 실제로 나타난 것이라, 우리가 직접 준다.

음수 마진이 요점이다 — 상자만 내리면 콘텐츠 전체가 안전영역만큼 밀려 헤더 아래 간격이 벌어진다.
같은 양을 되돌리면 **최대 스크롤(`콘텐츠 높이 − 뷰포트 높이`)도 인셋 전과 같고**, 잘려나가는 구간은
헤더가 덮는 spacer 안쪽이라 보이지 않는다.

**하단도 탭바 높이만큼 인셋한다** — "탭바가 덮으니 안 보여도 무방하다"고 봤던 첫 판단이 실기기에서
반려됐다(*"스크롤 인디케이터가 하단 네비게이션 뒤로 가려짐"*). 인디케이터는 스크롤포트 끝까지
그려지므로 상자가 화면 바닥까지 닿으면 탭바 뒤로 사라진다. 스크롤포트를
`bottom-[calc(4rem+var(--sa-bottom))]` 로 줄이고, 탭바 자리를 위해 두던 안쪽 `pb` 를 뺀다 —
**최대 스크롤 = 콘텐츠 − 스크롤포트** 라 양쪽에서 같은 값을 빼면 스크롤 범위가 불변이다.

```
스크롤포트: fixed inset-x-0 top-[var(--sa-top)] bottom-[calc(4rem+var(--sa-bottom))]
안쪽 래퍼:  -mt-[var(--sa-top)]   (아래는 pb 제거로 상쇄)
```

정리하면 **스크롤포트를 "실제로 보이는 영역"에 맞추는 것**이 규칙이다. 문서 스크롤일 때 WKWebView 가
메인 스크롤뷰에 해주던 인셋 처리를 컨테이너에서는 우리가 한다.

**7. 탭바 높이는 가정하지 않고 실측한다(`--tab-bar-h`).**

결정 6의 하단 인셋을 `4rem + sa-bottom` 으로 **가정**했더니 실제 탭바 높이(아이콘 20 + 라벨 + `py-2`
+ 보더 ≈ 56px + `sa-bottom`)와 어긋나 **컨테이너와 탭바 사이에 띠가 생겼다**(실기기 관측). `4rem` 은
AppShell 이 흐름 padding 으로 쓰던 값이라 여유가 있어도 무해했지만, 스크롤포트 크기로 쓰면 그 여유가
그대로 빈 자리가 된다.

`BottomTabBar` 가 `useLayoutEffect` + `ResizeObserver` 로 자기 상자를 재 `--tab-bar-h` 에 쓰고,
스크롤 컨테이너는 `bottom-[var(--tab-bar-h)]` 로 그 값을 읽는다([[ADR-085]]·[[ADR-098]] 의 헤더
spacer 실측과 같은 패턴 — 페인트 전에 재야 첫 프레임이 안 튄다). 언마운트(온보딩·키보드로 탭바가
사라질 때)에는 `0px` 로 되돌려 그 상황에서 컨테이너가 화면 바닥까지 쓰게 한다.

## 포기하는 것 (착수 전 합의된 목록)

- **상태바 탭 → 최상단**(iOS 기본): 웹뷰 메인 스크롤뷰에만 붙어 DOM 안쪽 스크롤러는 응답하지 않는다.
  되살리려면 네이티브에서 탭을 잡아 웹으로 넘기는 새 코드가 필요하다.
- **브라우저가 공짜로 해주던 것들**: 뒤로가기 시 스크롤 자동 복원, 인디케이터 안전영역 인셋 자동
  처리, 키보드 등장 시 포커스 입력으로의 자동 보정. 필요해지면 직접 구현 대상이다.
- **스크롤 모델이 둘로 공존한다**(프로토타입 기간): 컨텐츠만 컨테이너, 나머지는 문서 스크롤.
  확산하지 않기로 결론나면 되돌리고, 확산하면 이 항목은 사라진다.

## 실기기 관측 (2026-08-06, 빌드 14·15)

**본안은 통과했다** — 사용자 확인: *"이동 프레임, 스크롤 감각, 당겨서 새로고침은 정상적으로 동작"*.
[[ADR-098]]이 못 지웠던 이동 프레임이 사라졌고, 내부 스크롤러의 모멘텀·러버밴드도 문서 스크롤과
구분되지 않았으며, 판정 기준만 바꾼 당김([[ADR-072]] 재설계)도 그대로 살아 있다.

곁가지로 드러난 것은 전부 **"브라우저가 문서 스크롤에만 공짜로 해주던 것"** 이었다 — 인디케이터 색
(결정 5)과 인셋(결정 6). 착수 전 포기 목록에 "인디케이터 안전영역 인셋 자동 처리"로 적어둔 항목이
실제로 나타난 것이고, 둘 다 컨테이너 쪽에서 명시하면 끝나는 종류였다.

**남은 확인 대상**: 라이트 테마 인디케이터 색(결정 5 후속 처방)과 하단 인셋(결정 6 후속)은 빌드 16
관측 대기. 상태바 탭 → 최상단 상실의 체감 크기도 아직 판단 전이다.
