# ADR-032 스케줄러 응답 병합과 캐시

> 🟢 유효
> 옛 번호: ADR-030 · ADR-034 · ADR-270 · ADR-271 결정 6
> 관련 소스: `lib/scheduler/scheduler-merge.ts` · `lib/scheduler/scheduler-content-scope.ts` · `lib/scheduler/scheduler-activity.ts` · `lib/scheduler/reset-clock.ts` · `features/schedule-sync/schedule-sync.ts` · `storage/scheduler-cache.ts` · `storage/shared-progress-cache.ts`

## 배경

넥슨 스케줄러 API 응답을 그대로 화면에 그리면 세 가지 문제가 생긴다.

1. 캐릭터가 일간 리셋(매일 00:00 KST) 뒤로 게임에 접속하지 않았으면 일간 컨텐츠가 비어서 온다. 주간 리셋(목요일
   00:00 KST) 뒤로 접속하지 않았으면 주간 컨텐츠도 비어서 온다.
2. 몬스터파크나 에픽 던전처럼 월드나 메이플 ID 전체가 진행을 함께 쓰는 컨텐츠가 있다. 캐릭터마다 따로 저장하면
   이 공유를 나타낼 수 없다.
3. 공유 컨텐츠에서는 게임에 마지막으로 접속한 캐릭터의 상태가 다른 캐릭터의 응답에 섞여 나온다. 예를 들어 A 월드
   캐릭터로 놀다 나가면, B 월드 캐릭터를 조회해도 A 월드의 몬스터파크 횟수가 나온다. 반대로 등록한 항목이 응답에서
   통째로 빠지기도 한다. 캐릭터 범위 컨텐츠에서는 이런 일이 확인되지 않았다.

그래서 응답을 받을 때마다 캐릭터 캐시, 월드 원장, 계정 원장 세 가지와 합친 뒤에 화면에 넘긴다.

## 결정

### 결정 1. 미접속인지는 섹션에 캐릭터 범위 항목이 있는지로 판단한다

응답의 `date` 는 조회 시각과 관계없이 항상 요청한 날짜를 돌려준다. 그래서 날짜로는 응답이 낡았는지 알 수 없다.
대신 섹션 내용을 본다. 정상으로 동기화된 캐릭터라면 등록하지 않은 항목도 `registration_flag: "false"` 로 배열에
들어온다. 그러니 배열이 통째로 비어 있으면 그 리셋 뒤로 접속하지 않았다고 봐도 된다.

일간 · 주간은 여기서 한 단계 더 본다. 배열이 비지 않았어도 캐릭터 범위 항목이 하나도 없으면 비어 있는 것으로
본다(`isDailySectionMissing` · `isWeeklySectionMissing`). 실제로 일간 응답에 몬스터파크(월드 공유) 하나만 오고
일일 퀘스트가 전부 빠진 적이 있었다. 이때 배열 길이만 보면 정상으로 판단해서, 캐시가 없는 첫 실행에서는 일일
퀘스트가 화면에서 통째로 사라졌다. 보스는 주간 · 월간 섹션이 비었는지만 본다.

### 결정 2. 캐릭터 범위 항목은 항목 하나씩 합친다

응답이 섹션을 통째로 비우지 않고 항목 몇 개만 빠뜨리는 경우가 있다. 그래서 섹션 단위가 아니라 항목 단위로 합친다.

- 이번 응답에 있는 항목은 그대로 쓴다.
- 이번 응답에는 없고 캐시(쿼리 `schedule(ocid)`)에만 있는 항목은 이름과 등록 여부를 남기고 진행값만 0 으로
  되돌려 다시 넣는다. `nowCount` 는 0, `questState` 는 값이 있을 때만 0 이다.
- 항목은 컨텐츠 key 로 맞춘다. 컨텐츠 표에 없는 항목은 key 가 없으므로 API 이름으로 맞추고, key 가 있는 항목과는
  이름이 같아도 다른 항목으로 본다.
- 보스는 보스 key 와 난이도를 함께 맞춘다. 같은 보스라도 난이도가 다르면 다른 항목이다. 캐시에서 되살린 보스는
  `isComplete` 와 `ownComplete` 를 둘 다 거짓으로 둔다. `ownComplete` 를 남겨 두면 보스 수익이 지난주 처치를 이번
  주 처치로 센다.

캐시에 남은 항목이 게임에서 이미 사라진 컨텐츠라도 계속 되살아날 수 있다. 캐시를 믿는 방식이라 받아들인 한계다.

### 결정 3. 공유 범위는 컨텐츠 표의 `shareScope` 에 적는다

컨텐츠마다 `character` · `world` · `account` 중 하나다. 컨텐츠 표에 없는 컨텐츠는 `character` 로 본다. 이 값은
게임 규칙이라 사용자가 확인한 값만 적는다([[ADR-019]]).

| 컨텐츠 | 공유 범위 |
|---|---|
| 몬스터파크(일간) · 익스트림 몬스터파커 · 메이플 유니온 주간 드래곤 퇴치 | `world` |
| 에픽 던전 네 곳 · 메이플 유니온 PC방 주간 드래곤 퇴치 | `account` |
| 그 밖의 컨텐츠(일일 퀘스트 · 지역 주간 컨텐츠 · 무릉도장 · 길드 셋 등) | `character` |

같은 메이플 유니온이라도 PC방 쪽은 공유 단위가 다르다. 그래서 이름으로 추측하지 않고 줄마다 적는다.

### 결정 4. 공유 항목은 응답의 등록 여부를 믿지 않고 원장에 쌓는다

공유 항목은 섹션이 비지 않은 응답에서만 원장에 쓴다. 원장 한 칸에는 `active` · 진행값 · `lastUpdatedBucket` 이
들어간다.

- `active` 는 한 번 참이 되면 계속 참이다. 어느 캐릭터든 그 항목을 등록했다고 보고하면 참이 되고, 그 뒤로는 모든
  캐릭터가 이 원장 값을 쓴다. 다른 캐릭터의 상태가 섞여 들어온 응답 때문에 항목이 사라지거나 생기는 일을 막기
  위해서다.
- 대신 그 월드나 메이플 ID 의 캐릭터가 모두 등록을 해제해도 항목이 계속 보인다. 이 대가는 알고 받아들였다.
- 진행값은 등록 여부와 관계없이 원장과 병합 결과에 담는다. 몬스터파크는 등록하지 않아도 월드 합계 횟수가 오는데,
  이 값을 버리면 수동 모드에서 실제 횟수 대신 0 이 보인다. 자동 모드는 등록 여부로 걸러서 보여 준다.

원장 키는 `worldSharedProgress:{worldKey}` 와 `accountSharedProgress:{accountId}` 다. 계정은 지금 고른 계정이 아니라
그 캐릭터가 속한 계정이다([[ADR-030]]). 그래야 계정이 다른 캐릭터를 함께 추적해도 에픽 던전 완료가 다른 계정으로
번지지 않는다. 월드 key 를 모르는 응답은 월드 원장을 읽지도 쓰지도 않는다.

몬스터파크의 월드 간 섞임은 어느 쪽 값이 맞는지 응답만으로 가릴 방법이 없어서 막지 않는다. 월드 원장에는 마지막으로
쓴 캐릭터의 값이 그대로 남는다.

### 결정 5. 메이플 유니온 두 항목만 이번 응답의 등록 여부를 그대로 쓴다

`[메이플 유니온] 주간 드래곤 퇴치` 와 `[메이플 유니온] PC방 주간 드래곤 퇴치` 는 `active` 를 이번 응답의 등록
여부로 정하고, 원장에도 그 값을 쓴다. 결정 4 의 방식으로는 아무도 등록하지 않은 PC방 드래곤 퇴치가 원장에
`active: true` 로 남아, today 의 공유 컨텐츠 위젯에 계속 줄이 생겼다([[ADR-058]]).

어느 항목이 해당하는지는 컨텐츠 표의 `trustRegistrationFlag` 에 적고 `trustsRegistrationFlag` 로 읽는다. 위젯이
줄을 그릴지 정하는 `onlyWhenScheduled` 와는 뜻이 달라 칸을 따로 둔다. 하나로 묶으면 한쪽을 바꿀 때 다른 쪽도 함께
바뀐다. 계열 이름이나 `[메이플 유니온]` 접두어로 추측하지도 않는다.

이 두 항목은 다른 캐릭터의 상태가 섞여 들어오는 문제를 막지 못한다. 원장에는 마지막으로 쓴 캐릭터의 값이 남는다.
몬스터파크 · 익스트림 몬스터파커 · 에픽 던전은 결정 4 그대로다.

### 결정 6. 원장에 있는 공유 항목은 결과에 없으면 원장에서 채운다

섹션마다 컨텐츠 표의 공유 항목을 돌면서, 아직 결과에 없는 항목을 원장에서 채운다. 섹션이 비어 온 미접속 캐릭터도,
응답에서 그 항목만 빠진 캐릭터도 같은 방법으로 채워진다.

- `active` 가 거짓인 칸도 채우고, 등록 여부는 원장의 `active` 를 그대로 쓴다(`isRegistered: ledgerEntry.active`).
  거짓인 칸을 건너뛰면 아무도 등록하지 않은 에픽 던전이 오늘 미접속인 캐릭터의 목록에서 빠지고, 에픽 던전 주 3회
  한도([[ADR-033]] 결정 7)가 그 완료를 세지 못한다.
- 원장에 칸이 없으면 채우지 않는다.
- 원장의 `lastUpdatedBucket` 이 지금 리셋 구간과 다르면 진행값만 0 으로 되돌리고 `active` 는 그대로 둔다. 일간은
  KST 날짜, 주간은 목요일에 시작하는 주의 키다.

자동 모드는 등록된 항목만 보여 주므로 `isRegistered: false` 로 채워진 항목은 화면에 나오지 않는다. 수동 모드에서
추적 중인데 게임에 등록하지 않은 공유 항목은 컨텐츠 표 기본값이 아니라 원장 값으로 보인다.

### 결정 7. API 가 틀리게 주는 `max_count` 는 컨텐츠 표 값으로 덮는다

길드 주간 미션 포인트는 게임 규칙상 상한이 항상 10 인데 API 가 가끔 0 을 준다. 컨텐츠 표의 `maxCountOverride` 에
10 이 적혀 있고, 병합할 때 응답 값 대신 이 값을 쓴다. 캐시에서 되살린 항목에도 똑같이 적용한다. 이 칸은 API 오류를
고치는 용도로만 쓰고 게임 규칙을 적지 않는다. 지금 값이 있는 컨텐츠는 이것 하나다.

### 결정 8. 캐시도 없어서 섹션이 비면 지난 날짜를 조회해 채운다

처음 설치했거나 캐시를 지운 상태에서 캐릭터가 아직 접속하지 않았으면, 되살릴 캐시가 없어 화면이 비어 버린다.
그래서 결정 2 의 병합이 끝난 뒤에도 일간 · 주간 · 주간 보스 · 월간 보스 중 하나라도 비어 있으면 지난 날짜를
조회한다(`fillMissingSections`).

- 조회 날짜는 어제부터 13일 동안이다. KST 00:00 ~ 00:10 에는 자정 직후 응답이 불안정하다고 확인돼서 그제부터
  시작한다(`getBackfillDateKeys`).
- 날짜들을 한꺼번에 조회하고, 결과는 최근 날짜부터 차례로 합친다. 각 날짜 응답을 캐시처럼 써서 결정 2 와 같은
  방법으로 항목을 채운다. 한 날짜 응답으로 비어 있던 섹션뿐 아니라 네 섹션의 빠진 항목을 모두 채운다.
- 처음에 비어 있던 섹션이 그 날짜 응답에서 모두 채워져 있으면 거기서 합치기를 멈춘다. 13일을 다 써도 못 채운
  항목은 화면에 나오지 않는다.
- 한 날짜 조회가 실패하면 그 날짜만 건너뛴다. 이 조회가 실패해도 동기화 전체를 실패로 만들지 않는다.
- 조회한 날짜는 조회 원장에 기록해 같은 날짜를 다시 부르지 않는다([[ADR-028]]). 합치기를 일찍 멈춰도 이미 받은
  날짜는 모두 기록한다. 기록하지 않으면 다음 동기화가 같은 13일을 다시 조회한다.

이 조회로는 공유 항목을 채우지 못한다. 공유 항목은 원장에서만 채워지기 때문에(결정 6), 원장도 비어 있는 첫
동기화에서는 몬스터파크나 에픽 던전이 나오지 않는다. 이 경우는 다루지 않기로 했다.

### 결정 9. 원장은 Preferences 에 두고, 병합 결과는 쿼리 캐시가 든다

원장은 키 단위로 읽고 쓰기만 하면 되고 조건 검색이나 조인이 필요 없어서 SQLite 표를 따로 두지 않는다.

- 병합 결과와 받은 시각(`syncedAt`)은 쿼리 `schedule(ocid)` 가 들고, 쿼리 캐시가 SQLite `query_cache` 에 저장한다
  ([[ADR-142]] 결정 1 · 7). 1.0.12 까지는 Preferences `schedulerCache:{ocid}` 에 두었다. 업데이트 뒤 첫 실행이 그 키를
  쿼리 캐시로 옮긴 뒤 지운다(`storage/scheduler-cache.ts` 는 읽기와 지우기만 남았다). 형식 번호(`CACHE_VERSION`)가
  다른 옛 캐시는 옮기지 않는다. 다음 동기화가 다시 받아 오는 값이다.
- 원장은 API 에서 다시 받을 수 없는 값이라 옛 형식을 읽을 때 새 형식으로 옮긴다. 컨텐츠 이름을 키로 쓰던 칸은 컨텐츠 key 로,
  월드 이름을 넣은 원장 키는 월드 key 로 옮긴다. 컨텐츠 표에 없는 이름은 버린다.
- 원장 칸 하나를 쓸 때 표 전체를 읽고 고쳐 다시 쓴다. 추적 캐릭터들은 동시에 동기화되므로, 같은 원장에 쓰기가
  겹치면 먼저 끝난 쓰기가 덮일 수 있다. 메이플 유니온의 `active: false` 쓰기가 덮이면 미접속 캐릭터가 원장의 옛
  `true` 를 읽는다. 이번 응답을 받은 캐릭터의 화면은 응답 값을 바로 쓰므로 영향이 없다.
