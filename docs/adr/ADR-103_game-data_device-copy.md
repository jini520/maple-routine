# ADR-103 게임 데이터와 그림의 기기 사본

> ⚪ 미구현
> 관련 소스: `features/game-data/query.ts` · `storage/query-persister.ts` · `storage/sqlite/db.ts` · `lib/assets/asset-lookup.ts` · `hooks/useReturnToForeground.ts` · 서버 `modules/game-data/` · `modules/admin/` · 이슈 #741

## 배경

지금 앱은 게임 데이터 열네 칸의 사본(`src/data/*.json`)과 그림을 번들에 싣고, 켤 때 서버 값을 받아 그 위에 덮는다
([[ADR-020]] 결정 1 · 3 · 8). 서버에는 그림 파일 이름만 있다. 그래서 서버에서 새 보스나 새 아이템을 더하면 이름과
가격은 바로 나오지만, 그림은 앱 빌드가 나가야 나온다.

이 문서는 번들 사본을 걷고, 게임 데이터와 그림을 모두 서버에서 받아 기기에 저장하는 방법을 정한다. 그림은 관리
화면에서 올린다. 이 결정을 구현하면 [[ADR-020]] 결정 1 · 3 · 5 · 8 을 이 문서에 맞춰 다시 쓴다.

## 결정

### 결정 1. 다 받은 사본이 없으면 화면을 잠그고, 다 받은 뒤에만 앱을 쓴다 (사용자 지정 2026-10-26)

번들에 게임 데이터와 그림을 두지 않는다. 앱은 기기에 다 받은 사본이 있을 때만 화면을 연다. 사본이 없으면 받는 동안
화면을 잠그고 진행을 보여 준다. 받기에 실패하면 다시 시도하는 단추를 둔다.

사본이 없는 때는 셋이다.

- 처음 설치해 켰을 때
- 설정의 캐시 데이터 삭제로 사본을 지웠을 때([[ADR-053]])
- 기기 사본의 계약 판이 지금 앱과 다를 때. 옛 사본을 읽을 수 없으므로 버리고 처음부터 받는다

그래서 처음 켤 때는 서버에 닿아야 앱을 쓸 수 있다. "서버가 꺼져도 앱은 그대로 동작한다"([[ADR-016]] 결정 1)는
사본을 한 번 받은 뒤에만 지켜진다.

### 결정 2. 사본이 있으면 바로 열고, 서버 값이 바뀌면 백그라운드에서 받아 한 번에 바꾼다 (사용자 지정 2026-10-26)

- 받는 때는 앱을 켤 때와 백그라운드에서 돌아올 때(`useReturnToForeground`)다.
- 사본이 있으면 잠그지 않는다. 받는 동안에도 가진 사본으로 화면을 그린다. 보스를 기록하는 도중에 화면이 막히면 안
  되기 때문이다.
- 새 사본의 데이터와 그림을 모두 받은 뒤에 한 번에 바꾼다. 데이터만 새것이고 그림은 옛것인 상태를 화면에 내지 않는다.
- 바뀐 것이 없으면 서버가 304 를 내고 아무것도 받지 않는다(결정 6). 그래서 돌아올 때마다 물어도 비용이 작다.
- 받기에 실패하면 알리지 않고 가진 사본을 그대로 쓴다. 다음에 켜거나 돌아올 때 다시 받는다.

### 결정 3. 게임 데이터는 SQLite 표에 둔다

칸 하나를 한 줄(칸 이름 · `updatedAt` · 칸 JSON)로 둔다. 다 받았다는 표시도 같은 데이터베이스에 두고, 칸과 표시를
트랜잭션 하나로 쓴다.

- Preferences 는 여러 키를 한 번에 쓰지 못한다. 쓰는 도중에 앱이 죽으면 칸은 새것이고 표시는 옛것인 상태가 남는다.
  결정 1 의 잠금은 이 표시를 믿고 풀리므로 반쪽 상태가 남으면 안 된다.
- 지금의 Preferences 는 iOS `UserDefaults.standard` 와 Android SharedPreferences 파일 하나다(`modules/capacitor-storage`).
  UserDefaults 는 켤 때 전체를 메모리에 올리고, SharedPreferences 는 키 하나를 써도 파일 전체를 다시 쓴다. 게임 데이터는
  지금 약 444KB 이고 계속 커진다.
- 표는 `storage/sqlite/db.ts` 의 `TABLE_DEFINITIONS` 에 더한다. 그러면 캐시 삭제의 `general` 그룹과 용량 계산에
  저절로 들어간다([[ADR-053]] 결정 1).
- 지금의 Preferences 키 `queryCache` 는 옮기지 않고 지운다. 결정 1 에 따라 처음부터 다시 받기 때문이다.

### 결정 4. 그림은 문서 디렉터리의 파일로 두고, 이름은 내용 해시다

- `expo-file-system` 의 `Paths.document` 아래에 둔다. `Paths.cache` 는 저장 공간이 모자랄 때 iOS 가 비울 수 있고,
  비워지면 쓰는 도중에 결정 1 의 잠금이 다시 걸린다.
- 파일 이름은 서버 목록의 내용 해시다. 받은 파일의 해시가 목록과 같을 때만 받은 것으로 친다.
- 순서는 그림 파일을 먼저 받고, 그다음 결정 3 의 트랜잭션으로 칸과 다 받음 표시를 쓴다. 중간에 끊기면 표시는 옛
  사본을 가리키므로 화면은 옛 사본 그대로다.
- 새 사본으로 바꾼 뒤 목록에 없는 파일을 지운다.
- 그림 디렉터리는 캐시 삭제의 `general` 그룹이고 용량에도 잡힌다.
- `features/*` 는 `expo-file-system` 을 직접 부르지 않고 `storage/` 어댑터를 거친다.
- `expo-file-system` 은 2026-09-12 부터 스토어 바이너리에 들어 있다. 그래서 새 네이티브 모듈을 더하지 않으면 OTA 로
  낼 수 있다.

### 결정 5. 서버는 그림을 앱 박스 디스크에 두고 nginx 가 바로 낸다

- 서버 컨테이너에 그림 볼륨을 하나 마운트하고, 같은 박스의 nginx 가 `location /assets/` 로 그 디렉터리를 낸다.
- 파일 이름은 내용 해시다. 같은 이름을 덮어쓰지 않으므로 `Cache-Control: public, max-age=31536000, immutable` 을 걸 수
  있고, 올리는 도중의 반쪽 파일을 앱이 받지 않는다.
- 그림 볼륨은 밤에 DB 덤프와 함께 미니 PC 로 받는다. 앱 박스가 회수되면 그림도 함께 사라지기 때문이다.

다른 두 방법은 쓰지 않는다.

| 방법 | 쓰지 않는 이유 |
|---|---|
| OCI Object Storage | 무료 요청이 월 50,000 건이다. 새 설치 한 번에 그림 약 280건이라, 한도에 닿으면 새 사용자가 결정 1 의 잠긴 화면에서 못 나간다 |
| Cloudflare R2 | 장애가 날 곳이 API 서버와 따로 하나 더 생긴다. 결정 1 때문에 그림 서버가 서지 않으면 새 사용자는 앱을 못 쓴다. 처리방침의 위탁 업체도 늘어난다 |

앱 박스는 API 와 같은 곳이라 장애가 날 곳이 늘지 않는다. API 가 서지 않으면 어차피 게임 데이터도 받지 못한다.

### 결정 6. 서버는 그림 목록과 ETag 를 내고, 그림은 관리 화면에서 올린다

- 그림 목록(파일 이름 · 크기 · 내용 해시)은 `GET /v1/game-data` 응답의 칸 하나(`assets`)로 싣는다(사용자 지정 2026-10-26).
  앱은 해시로 바뀐 그림만 받는다. 경로를 따로 두면 두 요청 사이에 관리 화면에서 값이 바뀔 수 있다. 그러면 데이터는 새 그림을
  가리키는데 목록에는 그 그림이 없어서, 결정 2 의 한 번에 바꾸기를 지키려면 이 어긋남을 따로 막아야 한다.
- 게임 데이터 응답에 ETag 를 달고, 같으면 304 를 낸다. 결정 2 에서 돌아올 때마다 묻기 때문이다.
- 그림은 새 관리 화면 하나(`/admin/assets`)에서 올린다(사용자 지정 2026-10-26). 종류별 목록 · 미리보기 · 올리기 ·
  바꾸기를 이 화면에 모은다. 연출 프레임 · MVP 명판처럼 가리키는 표가 없는 그림도 있어서, 표마다 화면에 올리기 칸을
  붙이면 그 그림들을 올릴 곳이 따로 또 필요하다. 서버가 형식 · 크기 상한을 검사한다.
- 보스 · 드롭 아이템 화면 같은 기존 화면의 그림 이름 칸은 지금처럼 글자로 둔다.
- 그림 이름 칸이 실제로 있는 그림을 가리키는지 서버가 쓰기 때 검사한다. 지금은 앱의 `bundled-game-data.spec.ts` 가
  번들을 검사하지만, 번들이 없어지면 검사할 곳이 서버뿐이다.

### 결정 7. 서버로 옮기는 그림과 번들에 남는 그림 (사용자 지정 2026-10-26)

| 서버로 옮긴다 | 번들에 남는다 |
|---|---|
| 보스 초상(`bosses/`) · 아이템(`items/`) · 지도와 지도 아이콘(`maps/`) · 월드 엠블럼(`worlds/`) | 테마 배경(`themes/`)과 테마 색 토큰(`job-themes.json`) |
| MVP 명판(`mvp/`) · 포스(`force/`) · 모르는 캐릭터 자리 그림(`characters/`) | 기능 안내 그림(`guide/`) |
| 고가 드롭 연출 프레임(`drop-effect/`) | 도구 아이콘(`utility/`) · 넥슨 로그인 단추(`nexon/`) |

테마는 색 토큰과 배경이 한 벌이고 앱 코드가 그 값을 쓴다. 그래서 모두 번들에 남긴다. 결정 1 의 잠금 화면도 테마
배경 위에 그릴 수 있다.

기능 안내 그림은 `data/feature-guides/` 의 문구와 짝이라 앱 코드와 함께 바뀐다. 그래서 번들에 남긴다.

### 결정 8. 그림 크롭 좌표 넷도 서버로 옮긴다 (사용자 지정 2026-10-26)

`boss-portrait-crops.json` · `boss-portrait-icon-crops.json` · `boss-portrait-modal-crops.json` · `daily-quest-region-crops.json`
을 서버로 옮긴다. 그림이 서버에서 바뀌는데 크롭이 번들에 남으면 새 그림의 엉뚱한 곳을 자른다. 크롭은 그림과 같은 판으로
받아 결정 2 의 한 번에 바꾸기에 함께 든다. 그래서 그림 목록처럼 `GET /v1/game-data` 응답의 칸으로 받는다.

크롭은 `/admin/assets` 에서 숫자로 고치고, 잘린 모양을 그 자리에서 미리 본다(사용자 지정 2026-10-26). 새 보스를 앱 빌드
없이 더하려면 그 초상의 크롭도 서버에서 맞춰야 하기 때문이다. 크롭이 없는 그림은 지금처럼 기본값(`cover` · 가운데)으로
그린다.

### 결정 9. 잠금 화면은 시안을 먼저 고른다 (사용자 지정 2026-10-26)

결정 1 의 잠금 화면은 테마 여섯 개의 라이트 · 다크 시안을 먼저 만들어 고른 뒤 구현한다.
