### ADR-035: 스케줄러 자동/수동 트래킹 모드 도입 — 앱 자체 체크리스트 지원 (구현 완료)

> 🟡 **PARTIALLY SUPERSEDED — 일부 폐기.** 결정 18 중 보스 관리 진입점 한 줄은 [[ADR-145]] 가 폐기했다.
> **결정 17**(온보딩 기본 선택 제거)은 [[ADR-211]] 이 그 단계째 없앴다.
> 나머지 결정은 유효하다 — 인용 전 본문에서 해당 결정 번호를 확인할 것.

**배경**: [[ADR-007]]은 "게임 클라이언트의 스케줄러 기능에 실제 등록된 항목과 완료 여부만 읽기 전용으로 동기화, 앱 자체의 등록 UI는 두지 않는다"를 확정했다. 이후 실사용 과정에서 `registration_flag` 기반 판정이 실제 게임 상태와 어긋나는 사례가 반복적으로 드러났다([[ADR-031]] 등록/처치 난이도 불일치, [[ADR-033]] bossDaily/bossWeekly 교차 오염 등). 사용자가 게임 내 등록 여부에 전적으로 의존하지 않고 앱에서 직접 추적 항목을 관리할 수 있는 대안 모드 도입을 논의함(2026-07-23).

**검토했으나 기각한 대안**:
- **정적 템플릿으로 자동 모드의 표시 목록 자체를 산출**(모든 가능한 일간/주간 콘텐츠를 미리 나열해두고, 그 템플릿과 API 응답만으로 "이 캐릭터에게 지금 뭐가 뜨는지"까지 알고리즘이 판정): 기각. 일간/주간 퀘스트는 캐릭터의 레벨·직업·스토리 진행에 따라 적용 대상 자체가 달라지는데, 이 적용 가능 여부를 판정하는 정보는 Nexon 서버만 갖고 있다. `src/data/scheduler-content-catalog.json`이 이미 "명시 안 된 항목은 전부 character 범위(기본값)로 취급"이라는 최소 override 전략을 쓰고 있는 것 자체가, 이 프로젝트가 전체 콘텐츠 카탈로그화로 적용 가능 여부까지 판정하려 시도한 적이 없고 필요로 하지도 않았다는 근거다. **혼동 방지**: 이건 "고정 템플릿을 사람이 고르는 픽커로 쓰는 것"(아래 결정 11)까지 기각하는 게 아니다 — 사람이 직접 고르면 적용 가능 여부 판정 자체가 필요 없어져 이 문제가 발생하지 않는다. 보스처럼 캐릭터와 무관하게 닫혀 있는 목록(`weekly-bosses.json`)에 이미 이 템플릿 패턴이 쓰이고 있는 것도 같은 이유다 — "적용 가능 여부를 앱이 판정할 필요가 없는 곳"에서는 템플릿이 항상 잘 맞는다.
- **자동 셋(API 등록 기준)과 수동 셋(사용자 핀)의 합집합을 하나의 목록으로 병합**: 기각. "삭제"가 뭘 의미하는지 모호해진다 — 여전히 인게임에 등록돼 있으면 사용자가 앱에서 지워도 다음 동기화에 자동 셋을 통해 재등장한다.

**결정**:
1. 설정에 전역 토글 `trackingMode: 'auto' | 'manual'`을 추가한다. 컨텐츠 스케줄러·보스 스케줄러 화면 전체에 동일하게 적용하고, 화면별·캐릭터별로 따로 설정하지 않는다.
2. **자동 모드**는 기존 동작([[ADR-007]]~[[ADR-034]])을 그대로 유지한다 — 변경 없음.
3. **수동 모드**는 사용자가 앱 안에서 직접 추적 항목(콘텐츠명, 보스는 +난이도)을 추가·삭제하는 개인 체크리스트다. 최초로 수동 모드에 진입하는 시점에 그때의 인게임 등록 상태로 1회 시드해 콜드스타트 문제를 없앤다.
4. 스케줄러 API 동기화는 **모드와 무관하게 항상 전체 상태**를 가져온다 — 수동 모드가 API 호출 범위나 빈도를 줄이지 않는다.
5. **보스 수익 자동 기록(`boss_profit_records`, [[ADR-014]])은 트래킹 모드와 완전히 독립**이다. 어느 모드든 동기화된 원본 상태(`schedulerCache`)를 기준으로 그대로 자동 기록되며, 트래커 UI에 무엇을 보여주는지는 기록 여부에 영향을 주지 않는다.
6. **저장 구조 — 값의 단일 진실 공급원 유지**: 수동 모드의 추적 목록은 `nowCount`/`questState`/`isComplete`/`isRegistered` 같은 동기화 유래 값 필드를 별도로 들고 있지 않는다. "이 캐릭터가 어떤 콘텐츠명(+난이도)을 추적 중인지"라는 멤버십과, API가 절대 제공하지 않는 `maxCount`(결정 7)만 저장한다. 실제 값은 항상 화면 표시 시점에 기존 `schedulerCache:{ocid}`에서 콘텐츠명(+난이도)으로 조회해서 채운다. 값을 두 곳에 복제하지 않기로 함으로써, 자동/수동 모드를 전환해도 "방금까지 완료로 보이던 게 모드를 바꾸니 미완료로 보이는" 것 같은 동기화 어긋남이 구조적으로 발생할 수 없다 — 두 모드는 같은 순간엔 항상 같은 값을 읽는다.
7. ~~카운트형 콘텐츠(`kind: 'contents'`)의 `maxCount`는 API가 신뢰할 수 있는 값을 항상 주지 않을 수 있어, 수동 모드에서 항목을 추가하는 시점에 사용자가 직접 입력한다.~~ → **정정(같은 세션 내, 2026-07-23)**: 잘못 옮긴 내용이었다 — "수동으로 입력"은 앱 사용자가 UI에서 입력한다는 뜻이 아니라, **개발자(도메인 전문가)가 아래 결정 8의 템플릿 파일에 미리 값을 채워 넣는다**는 뜻이었다. 앱 자체에는 `maxCount`를 앱 사용자가 입력하는 UI가 없다.
8. `schedulerCache`에 한 번도 나타난 적 없는(한 번도 동기화된 적 없는) 수동 추적 항목은 "정보 없음" 상태를 따로 두지 않고, 신규 게임 레퍼런스 데이터 `src/data/scheduler-content-template.json`(컨텐츠 스케줄러 전용, 보스는 `weekly-bosses.json` 재사용 — 결정 11과 동일 파일)에 미리 채워둔 콘텐츠별 default 값을 그대로 쓴다. 이 파일의 각 항목은 Nexon wire 응답(`NexonDailyContentWire`/`NexonWeeklyContentWire`)과 동일한 shape(`content_name`/`type`/`registration_flag`/`now_count`/`max_count`/`quest_state`)을 가지며, 값(특히 콘텐츠마다 다른 `max_count` 실제 상한)은 개발자가 직접 채운다([[ADR-006]] 절차, AI가 임의로 채우지 않음).
9. **저장 위치**: 새 Preferences 키 `manualTrackedContent:{ocid}`(캐릭터별) — `{ contentName, difficulty?, kind, maxCount? }` 배열. 이 데이터의 유일한 writer는 사용자의 추가·삭제 UI 조작뿐이고(동기화는 이 키를 쓰지 않는다) 동시 쓰기 경쟁이 없어, SQLite나 별도 락(`characterBasicCache:index`의 `withIndexLock` 같은) 없이 `trackedCharacters:content`/`:boss`와 동일한 패턴으로 충분하다.
10. 모드 전환은 비파괴적이다 — 전환해도 자동/수동 양쪽 데이터 모두 지우지 않고 그대로 유지한다.
11. **수동 모드 "추가" UI는 고정 템플릿에서 고르는 방식이다.** 자유 텍스트 입력도, 과거 API 응답 이력 기반 자동완성도 아니다 — `weekly-bosses.json`과 동일하게 `src/data/`에 게임 레퍼런스 데이터로 유지되는 고정 콘텐츠명(+보스는 난이도) 목록이며, 사용자(도메인 전문가)가 직접 관리·확장하고 앱 사용자는 이 목록을 고칠 수 없다([[ADR-006]] 절차 그대로 적용). 이 템플릿에 없는 콘텐츠는 애초에 추가 대상이 아니다. 이 방식이면 "한 번도 동기화된 적 없는 콘텐츠라 골라줄 항목이 없는" 문제도 생기지 않는다 — 목록은 동기화 이력이 아니라 템플릿에서 오기 때문이다.
12. **보스 난이도 불일치는 트래커 완료 표시에 한해 콘텐츠명 기준으로 판정한다.** 사용자가 "이지"로 수동 추적 중인데 실제로는 "노멀"을 처치해도, 트래커 UI의 완료 배지는 난이도 무관하게 완료로 표시한다(기존 자동 모드의 `isComplete` 승격과 동일한 방식). 이건 트래커 표시 전용 판정이며, 보스 수익 자동 기록(결정 5)은 이와 무관하게 계속 `ownComplete` 기준을 그대로 쓴다 — 둘이 다른 목적(표시 vs 정산)이라 다른 매칭 기준을 쓰는 게 맞다.
13. **온보딩 순서 재정의**: API 키 입력 → 메이플 ID(계정) 선택 → 전체 캐릭터 예열(기존 [[ADR-016]], 변경 없음) → **자동/수동 선택(신규)** → **컨텐츠 추적 캐릭터 선택(신규, `trackedCharacters:content`에 1개 이상 필수 — 온보딩 완료 조건에 추가됨)** → 완료(컨텐츠 스케줄러로 이동). 자동/수동을 캐릭터 선택보다 먼저 두는 이유: (a) 모드 선택은 특정 캐릭터와 무관한 "이 앱을 어떻게 쓸지"의 전반적 정책 결정이라, 구체적인 대상(캐릭터)을 고르기 전에 정하는 게 일반적인 온보딩 순서(전반 → 구체)와 맞다. (b) 캐릭터 선택 화면 자체의 구성이 모드에 따라 달라질 수 있다(수동이면 그 자리에서 시드된 목록을 보여주고 즉시 편집 가능하게 할 여지가 있음, 자동이면 단순 선택만) — 화면 설계가 모드에 의존하므로 모드가 먼저 정해져 있는 쪽이 자연스럽다. **보스 추적 캐릭터 선택(`trackedCharacters:boss`)은 온보딩에 포함하지 않는다** — 온보딩 완료 후 기본 랜딩 화면이 보스 스케줄러가 아니라 컨텐츠 스케줄러이고(`src/App.tsx`의 라우트 구조), [[ADR-012]]가 이미 컨텐츠/보스를 화면별 독립 추적으로 의도했으므로 온보딩에서 둘을 한꺼번에 강제하지 않는다. 보스는 기존과 동일하게 보스 스케줄러 화면 진입 시 "캐릭터 관리"에서 선택한다.
14. **시드 트리거는 온보딩 전용이 아니라 앱 전체 수명 동안 통하는 두 개의 범용 트리거로 일반화한다**: (a) 이미 추적 중인 캐릭터가 있는 상태에서 `trackingMode`가 `'manual'`로 바뀌는 순간, 그 시점에 추적 중인 캐릭터 전원을 일괄 시드. (b) 이미 `trackingMode`가 `'manual'`인 상태에서 캐릭터가 `trackedCharacters:content`/`:boss`에 새로 추가되는 순간, 그 캐릭터만 개별 시드. 온보딩(결정 13)은 이 중 (a)를 한 번 타는 특수 케이스일 뿐 — 자동/수동을 먼저 고르고(아직 추적 목록이 비어 있어 (a)는 대상 없이 통과) 캐릭터를 그다음 고르면(추적 목록에 추가되는 시점에 이미 모드가 `'manual'`이므로) (b)가 캐릭터별로 실행된다. 이 두 트리거만 있으면 온보딩 순서(모드 먼저 vs 캐릭터 먼저)나 온보딩 이후 시점(설정에서 나중에 모드를 바꾸는 경우, 나중에 새 캐릭터를 추가하는 경우) 어느 조합이든 별도 특수 케이스 없이 동일하게 처리된다.
15. **시드 처리 중에는 로딩 스피너를 보여주고, 템플릿 기본값으로 화면을 먼저 그리지 않는다.** 템플릿 기본값(결정 8)은 대부분 `registration_flag: false`/`now_count: 0` 같은 "미등록·진행 없음" 값이라, 이걸 먼저 그리면 실제 동기화 결과가 아직 안 왔을 뿐인데 "정말 아무것도 등록 안 된 빈 상태"처럼 보여 사용자에게 오해를 준다. 그래서 이 앱의 다른 화면들이 쓰는 캐시 우선 표시(stale-while-revalidate, [[ADR-016]])를 시드 과정에서는 의도적으로 적용하지 않고, 동기화(및 필요 시 [[ADR-034]] 백필)가 끝나 최종 값이 확정될 때까지 로딩 스피너를 유지한 뒤 그 결과를 한 번에 보여준다. 결정 14의 트리거 (a)(온보딩 캐릭터 선택 직후 일괄 시드)와 트리거 (b)(이후 새 캐릭터를 추적 목록에 추가할 때 개별 시드) 둘 다 동일하게 적용한다.
16. **온보딩 화면을 카드/모달 형태에서 페이지 형태로 전환하고, 스텝 인디케이터는 도입하지 않는다 (구현 완료, 2026-07-23).** 기존 `ApiKeyForm.tsx`/`AccountSelectionList.tsx`가 쓰던 `rounded-[14px] bg-surface border border-border p-6` 바깥 카드 박스를 제거하고, 배경 위에 콘텐츠가 바로 놓이는 일반 페이지 레이아웃(`w-full space-y-4`)으로 통일했다 — 카드로 감싸면 모달처럼 보인다는 판단. 내부 요소(입력창·옵션 버튼)의 개별 테두리·배경 스타일은 그대로 유지했고, 바뀐 건 바깥을 감싸던 박스뿐이다. 결정 13의 신규 단계(자동/수동 선택, 컨텐츠 캐릭터 선택)도 처음부터 이 페이지 레이아웃으로 만든다. **스텝 인디케이터(전체 몇 단계 중 몇 번째)는 도입하지 않기로 확정** — 계정 선택 단계가 조건부(메이플 ID 1개면 생략)라 전체 단계 수를 고정할 수 없고, 캐릭터 예열 단계는 이미 자체 진행률 바(`MapleWaveProgress`)가 있어 단계 표시와 의미가 겹치는 문제가 있었다. 기존 온보딩 테스트(`ApiKeyForm.test.tsx`/`AccountSelectionList.test.tsx`/`OnboardingScreen.test.tsx`) 27개는 카드 스타일이 아니라 동작·내용만 검증하고 있어 변경 없이 전부 통과.
17. **정정(2026-07-24) — 모드 선택 화면 카피·기본 선택 개편.** 구현 완료 후 실사용 검토에서 온보딩 `TrackingModeStep`의 표현이 의도와 다르게 나간 부분을 바로잡는다:

18. **정정(2026-07-24, 와이어프레임 리뷰로 확정) — 수동 추적 편집 UI를 스케줄러 화면에서 분리해 전용 관리 페이지로 이동.** 최초 구현(카드 우상단 X 삭제 + 리스트 하단 "+ 항목 추가" + 보스 헤더 "보스 추가")은 보기(진행 확인) 화면에 편집 UI가 상주해 어수선하고, 보스 화면은 수동 모드에서 헤더 텍스트 버튼이 3개(보스 추가·파티 관리·캐릭터 관리)까지 늘어나는 문제가 있었다. 다음으로 재설계한다:
    - **스케줄러 화면은 두 모드 모두 읽기 전용으로 복귀**: 카드 위 X 삭제, "+ 항목 추가", "보스 추가"를 모두 제거하고 `ManualContentPickerModal`/`ManualBossPickerModal`을 폐기한다. 값 조회 원칙(결정 6, 멤버십에 값 복제 없음)은 그대로.

19. **정정(2026-07-24) — 수동 추적 멤버십에 일간/주간 구분 저장 (탭 표시 섞임 버그 수정).** 증상: 수동 모드 컨텐츠 스케줄러의 일간·주간 탭 양쪽에 전체 추적 항목이 모두 표시됐다. 원인: `ManualTrackedItem.kind`가 `'content' | 'boss'`뿐이라 컨텐츠의 일간/주간 구분이 저장되지 않았고, ContentScreen이 같은 목록을 두 탭의 merge에 그대로 넘기며, `mergeManualContentList`는 해당 탭의 동기화 결과·템플릿에 없는 항목도 방어 기본값으로 유지해 모든 항목이 양쪽 탭에 렌더링됐다(보스는 `weekly-bosses.json` cycle 파생 테이블 덕에 무사했다). 수정:
    - `kind`를 `'daily' | 'weekly' | 'boss'`로 세분한다. 시드는 소스 배열(dailyContents/weeklyContents)로, 관리 페이지(결정 18)는 현재 탭으로, **기록 시점에 구분을 확정**한다 — 표시 시점 추론 없음.
    - 레거시 `'content'` 값은 읽기 시점(`getManualTrackedContent`)에 템플릿 조회로 1회 재분류하고, 템플릿에 없으면 목록에서 제외한다. 시드도 템플릿에 있는 컨텐츠만 저장한다 — "템플릿에 없는 콘텐츠는 애초에 추가 대상이 아니다"(결정 11)의 일관 적용이고, 관리 페이지 체크리스트(결정 18)가 템플릿 기반이라 템플릿 밖 항목은 어차피 편집 불가능한 고아가 되기 때문.
    - 함께 발견된 잠재 버그 정정: 시드가 보스를 API 원문명(`boss.name`)으로 저장하는데 `mergeManualBossList`는 `matchBossContent` 정규화 명으로 매칭해, 두 이름이 다른 보스는 시드 직후 매칭에 실패한다(완료 여부가 항상 미완료로 보임). 시드가 `matchedBossName`(매칭 실패 시 원문명)을 저장하도록 정정한다.
20. **정정(2026-07-25) — 수동 모드 스케줄러 표시 순서를 멤버십 삽입 순서에서 관리 페이지 순서로 고정.** 증상(사용자 보고): 수동 모드에서 항목을 추가·삭제할 때마다 목록 순서가 흔들렸다. 원인: `mergeManualContentList`/`mergeManualBossList`가 반환 순서를 `tracked`(멤버십) 배열 순서 그대로 따랐는데(결정 8·12 초기 설계 "사용자가 추가한 순서 유지"), 멤버십은 추가 시 append·삭제 시 filter라 편집할 때마다 순서가 바뀐다. 수정: 표시 순서를 멤버십이 아니라 **각 관리 페이지의 고정 소스 순서**로 바꾼다.
    - **컨텐츠(일간/주간, 결정 8)**: `mergeManualContentList`는 `tracked`가 아니라 넘겨받은 `template` 배열을 순회해 추적 중인 항목만 그 순서대로 낸다(템플릿에 없는 방어적 항목은 뒤에 멤버십 순서로 붙인다). 컨텐츠 관리 페이지(결정 18)와 **완전히 같은 정렬**을 보장하려고, `ContentScreen`이 넘기는 `template`을 raw 배열이 아니라 관리 페이지와 동일한 `categorizeContentEntries(CONTENT_TEMPLATE[tab], 주간이면 WEEKLY_CATEGORY_ORDER)`를 평탄화한 순서로 준다(결정 18 정정의 카테고리 그룹·주간 표시 순서가 그대로 반영됨). 일간·주간 양쪽 적용.
    - **보스(주간/월간, 결정 12)**: `mergeManualBossList`는 매칭·폴백 로직은 그대로 두고, 반환 전에 추적 항목을 **`weekly-bosses.json` 순서**(보스 관리 페이지 `BOSSES_BY_TAB`와 동일: weekly + eventWeekly + monthly)로 정렬한다 — `boss` 이름의 참조 배열 인덱스 기준 안정 정렬이고, 참조에 없는 보스명은 뒤에 멤버십 순서로 둔다. `BossScreen`은 이 결과를 cycle로 필터만 하므로(재정렬 없음) 주간/월간 탭 각각이 관리 페이지와 같은 순서로 나온다.
    - 두 함수 모두 순수 함수 순서 계약 변경이라 회귀 테스트로 고정한다.
21. **정정(2026-07-25) — 보스 수익 페이지 표시 목록도 수동 트래킹 멤버십을 반영 (버그 #33 수정).** 증상(사용자 보고): 수동 선택으로 추가만 하고 인게임 등록/처치가 없는 보스가 보스 수익 페이지 리스트에 나타나지 않았다. 원인: 결정 5는 보스 수익 **자동 기록**(`boss_profit_records`)의 모드 독립성만 정했고, 보스 수익 **표시 목록**이 수동 멤버십을 읽는 브리지는 두지 않았다 — `boss-profit/store.ts`가 `schedulerCache`/`syncSchedules`의 `bossContents`만으로 행을 구성했고, 이 경로의 `selectBossProfitBosses`는 실제 처치(`ownComplete`)했거나 인게임 등록(`isRegistered`)된 보스만 반환하므로 둘 다 없는 순수 수동 보스는 조용히 누락됐다(보스 스케줄러 화면은 결정 12·20의 `mergeManualBossList`로 이미 해결). 수정:
    - **표시 집합 = (실제 처치한 보스 전부, 처치 난이도) ∪ (수동 추적 중이지만 미처치인 보스, 고른 난이도 placeholder).** 자동 모드가 "실제 처치(처치 난이도) + 인게임 등록 placeholder"인 것과 대칭으로, 수동 모드는 placeholder의 출처만 인게임 등록 → 수동 멤버십으로 바꾼다. `boss-profit/store.ts`의 **캐시·라이브 브랜치 양쪽**에서 트래킹 모드가 `'manual'`이면 `getManualTrackedContent(ocid)`를 읽어 이 두 집합을 합친다.
    - **① 실제 처치한 보스는 추적 여부와 무관하게 전부, 처치한 난이도·가격으로 노출한다(사용자 확정 2026-07-25).** 보스 수익 페이지는 정산이 목적이라([[ADR-032]]) 실제로 번 것은 다 보여준다 — 추적 안 한 보스를 처치했어도, 추적한 보스를 고른 난이도와 **다른 난이도로 처치**했어도 항상 처치한 난이도로 표시한다(예: 자쿰 하드 추적 → 카오스 처치 → 카오스로 표시). `selectBossProfitBosses`로 그룹당 실제 처치 난이도를 고르되, 인게임 등록-only(미처치) placeholder는 수동 모드에서 신뢰하지 않으므로 `ownComplete`인 것만 남긴다.
    - **② 수동 추적 중이지만 아직 처치하지 않은 보스**는 사용자가 고른 난이도로 미완료 placeholder(payout 0)로 노출한다(#33의 핵심). `mergeManualBossList`로 보스 관리 페이지와 동일 규약(정규화 명 매칭, cycle 폴백)으로 병합하되, 이미 ①에서 처치 난이도로 나온 보스명은 중복 배제한다. 완료/가격 없는 placeholder는 기존 [[ADR-032]] 처리(`buildBossProfitRow`)와 일관되게 `payoutMeso: 0`/(시세표에 없으면)`priceMeso: null`, `boss_profit_records`에는 기록 안 됨(결정 5 유지 — auto-record는 여전히 `isComplete` 보스만, 모드 독립).
    - **트래커(결정 12)와 다른 점**: 트래커는 체크리스트 표시가 목적이라 표시 난이도를 추적 난이도로 유지하고 완료 배지만 난이도 무관으로 승격한다. 수익 페이지는 정산이 목적이라 표시 난이도 자체를 실제 처치 난이도로 바꾼다 — 결정 5·12의 "표시 vs 정산" 분리 원칙의 연장이다. 자동 모드는 기존 `selectBossProfitBosses` 경로 그대로 — 변경 없음.
    - **범위**: 이번 기간(현재 periodKey) 표시에 한정한다. 과거 기간(백필/`buildRowsFromRecords`)은 변경하지 않는다 — 미처치 수동 보스는 기록이 없고, 실제 처치한 보스는 트래킹과 무관하게 기존 mode-독립 auto-record(결정 5)가 처치 난이도로 이미 기록하므로 과거 기간은 영향 범위 밖이다.
22. **정정(2026-08-03, 이슈 #59, 구현 완료) — 모드 선택 화면 재설계: 카피를 세 필드로 쪼개고 옵션에 아이콘·주의 줄을 준다.** 결정 16의 "기존 선택 카드 클래스를 그대로 재사용한다(신규 스타일 금지)"와 결정 17의 카피가 겹쳐, 이 단계는 온보딩에서 **유일하게 시각 요소가 하나도 없는 화면**이 됐다 — 카드 면적 대부분을 자동 91자·수동 84자의 회색 문단이 차지하고, 두 옵션의 차이는 문단을 다 읽어야 드러났다. 지금 모양은 사고가 아니라 결정의 결과이므로 그 결정을 갱신한다. 카피가 공용(`features/tracking-mode/copy.ts`)이라 **설정 모달(`TrackingModeSelector`)에도 같이 적용**한다.
    - **카피를 세 필드로 쪼갠다** — `title`(한 단어) · `description`(한 문장) · `caution`(신규). 결정 17이 확정한 긴 문장들은 폐기하고 아래로 대체한다(문구는 사용자 확정, 2026-08-03). `title`에서 "· 게임 등록을 그대로 따라가기" 꼬리를 뗀 이유는 새 `description`이 같은 말을 하기 때문이다.

      | | `title` | `description` | `caution` |
      |---|---|---|---|
      | auto | 자동 | 게임 내 스케줄러에 등록한 컨텐츠가 그대로 반영돼요. | API 응답에 따라 컨텐츠가 표시되지 않을 수 있어요. |
      | manual | 수동 | 직접 컨텐츠를 선택하고 관리해요. | 게임 내에 스케줄러를 추가하더라도 앱에는 자동으로 추가되지 않아요. |

      `caution`은 서식이 아니라 **성격의 분리**다 — 각 모드의 "한계"가 전에는 설명 문단 끝에 묻혀 있었고(자동), 수동 쪽은 **아예 어디에도 없었다**(게임에서 추가한 항목이 앱에 자동으로 들어오지 않는다는 사실). 두 한계 모두 사용자가 고칠 수 없는 알려진 제약이라 실패(error)가 아니라 고지다.
    - **설명·주의는 접지 않고 항상 표시한다.** 선택 시에만 펼치는 안을 검토했으나 기각 — 이 화면의 목적은 **고르기 전에 둘을 비교하는 것**이라, 펼침이 비교를 방해한다. 카피가 짧아져 접을 이유도 사라졌다.
    - **옵션마다 아이콘 하나** — 자동 `Gamepad2`, 수동 `ListChecks`. `h-5 w-5 text-primary-ink`, **배지 없이 단독**([design-system](../foundation/design-system.md) "아이콘 컨테이너로 감싸지 않는다" 규칙 준수 — 예외를 늘리지 않는다). `RefreshCw`(동기화)를 검토했으나 기각했다: 이 앱에서 그 아이콘은 **새로고침 버튼의 기능 신호**라 누를 수 없는 자리에 두면 뜻이 흐려진다. `Gamepad2`는 "게임에서 정한 것을 따른다"는 **주어**를 가리켜 수동(= 앱에서 고른다)과 대비가 더 분명하고, 앱 어디에서도 쓰지 않아 의미 충돌이 없다.
    - **주의 줄은 정보 톤 미니 박스** — `mt-2 flex items-start gap-1.5 rounded-[8px] bg-info-tint px-2.5 py-1.5 text-xs text-info-ink` + lucide `Info h-3.5 w-3.5` (`strokeWidth 1.75`), 아이콘+텍스트를 함께 감싸는 고지 박스이므로 위 "아이콘 단독" 규칙과 충돌하지 않는다. `UnavailableNotice`(compact)의 규격을 카드 안 크기로 승계한 것이고, 색이 `error`가 아니라 `info-tint`인 이유도 같다([[ADR-060]] 결정 5 — 고칠 수 없는 제약에 error 색은 과하다). **컴포넌트를 공유하지 않는 이유**: `UnavailableNotice`는 문구를 자기 안에 고정으로 갖는 컴포넌트라 임의 문구를 받지 못한다.
    - **선택 표시는 그대로 테두리+틴트, 체크 마크를 도입하지 않는다** — 보스 관리 화면의 선례(체크 없이 테두리·색으로만)와 톤을 맞춘다.
    - **바깥 카드 클래스는 건드리지 않는다** — `AccountSelectionList`·`ThemeSelector`와 공유하는 `rounded-[10px] border ... px-4 py-3` 는 그대로다. 바뀌는 것은 **카드 안쪽뿐**이라 온보딩 다른 단계와 톤이 갈리지 않고, 이 변경은 #61(API 키 가이드)과 순서를 다투지 않는다.
    - **폐기**: 결정 16의 ~~"신규 스타일 금지"~~ 제약. 결정 16의 나머지(페이지 레이아웃 = 바깥 카드 박스 없음, 스텝 인디케이터 미도입)와 결정 17의 나머지('추천' 배지 없음, 기본 선택 없음, "컨텐츠" 표기 통일)는 **그대로 유효**하다.
23. **정정(2026-08-03, 구현 완료) — 설정 모드 전환에 확인 단계를 넣고, 기다림을 적용 버튼 안으로 옮긴다.** 설정 모달(`TrackingModeModal`)은 **옵션을 탭하는 순간 전역 설정이 저장되고 시드가 시작**됐다(결정 14(a)). 확인도 취소도 없고 이 모달에는 닫기 버튼조차 없어(공용 `Modal`은 오버레이 탭이 유일한 해제 수단인데 적용 중에는 그것마저 막힌다) **되돌릴 자리가 어디에도 없었다**. 로딩 표현도 본문 하단 인라인 `MapleSpinner size=18` + "적용하고 있어요"였는데, 이 크기는 [[ADR-061]]이 정한 두 대역(**버튼 안 16 / 그 밖 24·32**) 어디에도 속하지 않는다. 온보딩 `TrackingModeStep`은 처음부터 선택 → "계속하기" 2단계였으므로, 이 결정으로 두 화면의 **흐름**까지 같아진다(결정 22가 카드 안쪽을 맞춘 데 이어).
    - **탭은 선택일 뿐, 적용은 버튼이 한다.** 모달이 고른 값을 자기 상태로 들고 있다가 "적용"에서 한 번만 `setMode` 를 부른다.
    - **버튼 골격은 설정 안 다른 확정 모달과 같다** — 우측 정렬 `취소`(고스트) + `적용`. `DisconnectConfirm`·`CacheClearConfirm` 과 글자 그대로 같은 구성이고, **다른 것은 색뿐**이다: 모드 전환은 파괴적 동작이 아니라 진행 동작이라 확정 버튼이 `border-error text-error-ink` 가 아니라 `bg-primary text-on-primary` 채움이다([[ADR-062]]의 "재시도는 진행 동작이라 `bg-primary`"와 같은 기준). 취소는 이 모달에 **없던 탈출구를 눈에 보이게** 만든다.
    - **현재 모드와 같으면 적용 버튼을 비활성한다**(사용자 결정) — 바뀐 것이 없으면 누를 것도 없다. ~~같은 모드를 다시 고르면 `setMode` 없이 즉시 닫는다~~ 는 폐기한다(그 동작은 "탭 = 적용"의 부산물이었다). 닫기는 취소·오버레이가 맡는다.
    - **기다림은 적용 버튼 안에 그린다** — `MapleSpinner size={16}` + 라벨 `적용 중`(말줄임표 없는 `~중`, [[ADR-061]] 결정 9), `disabled` + `aria-busy`. 적용 중에는 취소·옵션도 비활성이고 **오버레이 클릭 닫힘 금지는 그대로 유지**한다(저장 도중엔 닫을 수 없다). 하단 인라인 스피너와 "적용하고 있어요"는 폐기 — 그 문구는 그 밖(화면·영역) 자리의 어법이고, 이제 이 대기는 버튼 안에 있다.
    - **진행률(N/M) 모달은 기각.** 시드가 캐릭터별 병렬 실행이라 셀 수는 있지만, **온보딩의 같은 시드는 진행률 없이 스피너만** 쓰기로 결정 15가 이미 정했다 — 같은 작업이 두 자리에서 다른 얼굴이 되고 `setMode` 에 진행 콜백을 뚫어야 한다. 카드 위 덮개(스크림 오버레이)도 기각 — 앱에 없던 패턴을 하나 늘린다.
    - **범위는 이 모달 하나.** [[ADR-061]] S7("모달 차단 작업 보류")이 함께 묶었던 셋 중 **모드 전환만 해소**한다. 캐시 삭제는 이미 같은 골격(취소+확정, 버튼 안 스피너)이고, 계정 검증(`AccountFlowStatus`)은 여전히 자기 얼굴이라 남는다.
    - **알려진 잔여**(이번에 고치지 않음, 현행과 동일): `setMode` 가 실패로 끝나면 `isApplying` 이 풀리지 않아 오버레이도 막힌 채 모달이 갇힌다. 시드 실패 처리 자체가 없는 문제라 이 결정의 범위 밖으로 둔다.

**이유**:
- [[ADR-007]]의 "이중 입력 방지" 취지를 완전히 포기하지 않으면서도, `registration_flag` 신뢰성 문제로 불편을 겪는 사용자에게 탈출구를 준다 — 기본은 자동 모드로 두고, 필요한 사용자만 명시적으로 토글해 전환한다.
- 결정 6(값의 단일 진실 공급원)이 이 설계 전체의 핵심이다 — 두 모드가 값을 각자 들고 있으면 서로 다른 시점에 동기화된 사본을 비교하게 돼, 모드를 오갈 때 사용자에게 "데이터가 사라지거나 되돌아간 것"처럼 보이는 신뢰 문제가 생긴다.
- 멤버십 목록에 값 필드를 두지 않기로 하면서 이 데이터의 writer가 사용자 UI 하나로 좁혀져, SQLite 도입이나 락 없이도 Preferences만으로 안전하다.

**트레이드오프**:
- 콘텐츠명 목록이 고정 템플릿(결정 11)이라, 그 템플릿 자체를 최신 상태로 유지하는 책임은 여전히 사람(도메인 전문가)에게 있다 — 다만 이건 이 프로젝트가 [[ADR-006]]으로 이미 감수하고 있는 일반 정책이라 이 결정만의 새 부담은 아니다.
- `trackingMode` 자체를 저장할 Preferences 키, "캐시 데이터 삭제" 시 보존할지 여부는 **보류**한다 — "캐시 데이터 삭제"가 현재 전부-또는-전무 방식인데, 이걸 사용자가 지울 데이터를 선택할 수 있는 기능으로 개편할 계획이 별도로 있어(`docs/persistence/lifecycle.md` "삭제 범위" 참고), `trackingMode` 보존 여부는 그 개편과 함께 정하는 게 맞다고 판단.

  **정정(2026-07-29) — 보류 해소 ([[ADR-052]])**: ~~"캐시 데이터 삭제" 시 `trackingMode` 보존 여부는 보류~~ → **보존하기로 확정**한다(`dropEffect`도 함께). 지울 데이터를 고르는 개편을 기다리지 않고 지금 정한 이유는, `trackingMode`가 재조회로 복구 가능한 캐시가 아니라 사용자가 명시적으로 고른 취향 설정이고 같은 성격의 `theme`이 이미 보존 대상이기 때문이다 — 수동 모드를 쓰던 사용자가 캐시 삭제 한 번에 아무 안내 없이 자동 모드로 되돌아가는 것은 "저장 공간 확보"라는 그 기능의 의도를 넘어선 부수효과다. 근거·트레이드오프 전문은 [[ADR-052]] 결정 1.
