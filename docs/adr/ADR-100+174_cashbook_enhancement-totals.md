# ADR-100+174 강화 내역을 계산한 합계로 저장하고, 다시 매길 기간은 환경 변수로 건다

> 🟢 유효
> 관련 소스: `features/enhancement-history/spending.ts` · `features/enhancement-history/collect.ts` · `features/enhancement-history/legacy-totals.ts` · `storage/enhancement-totals.ts` · `storage/sqlite/enhancement-tables.ts` · `lib/enhancement/cost.ts` · `features/cashbook/records.ts` · `app/cashbook/CashbookScreen.tsx`

## 배경

가계부는 강화 API(큐브 · 스타포스 · 잠재능력 · 소울 잠재)의 응답 줄을 `enhancement_history.payload` 로 통째로 들고,
읽을 때마다 비용을 계산한다([[ADR-047]] 결정 10). 이것을 계산이 끝난 합계로 저장하게 바꾼다(#614, 사용자 2026-10-06).
합계는 서버로 보내지 않는다([[ADR-099]] 결정 1).

합계를 저장하면 계산 코드나 비용 표를 고쳐도 지난 합계가 저절로 바뀌지 않는다. 그래서 그 기간을 넥슨 API 에서 다시
받아 매기는 요청 장치를 함께 둔다(#615).

## 결정

### 결정 1. 저장 단위는 날짜 · 캐릭터 · 분류 · 장비별 합계이고, 응답 원본은 버린다

가계부의 분류 줄과 장비별 펼침이 그대로 남는다([[ADR-047]] 결정 12). 값을 못 매기는 줄은 지금처럼 버린다. 장비 레벨은
장비 표(서버 게임 데이터의 `equipmentItems` 칸)에서만 찾고, 같은 이름의 큐브 · 잠재 기록에서 레벨을 빌리던 `loadObservedItemLevels` 는 걷는다.
캐릭터 소속을 모르다가 나중에 알게 되는 경우는 예외로 둔다. 없어진 캐릭터가 다시 생기면 새로 만든 캐릭터다(사용자 지정).

### 결정 2. 합계는 MVP 할인 전 비용으로 저장하고, 할인은 화면에 보일 때 앱이 붙인다

MVP 등급 기간을 고쳐도 강화 내역을 다시 받지 않기 위해서다(사용자 지정 2026-10-26). 넥슨 로그인 계정의 강화 내역은 서버
스트림을 거쳐 받으므로, 다시 받으면 서버 부하가 크다.

- 합계 한 줄은 칸 둘로 비용을 든다. `attempt_cost_meso` 는 MVP 할인을 받는 시도 비용이고, `destroy_defence_cost_meso` 는
  할인을 받지 않는 파괴 방지 추가 비용이다([[ADR-050]] 결정 5). 큐브 · 잠재 · 소울은 MVP 와 무관해 시도 비용 칸만 쓴다.
- 이벤트 할인(샤이닝 스타포스 등)은 그 시도에 실제로 붙은 할인이라 시도 비용에 이미 넣는다.
- 화면은 그 날짜 · 그 캐릭터의 MVP 할인을 시도 비용 합계에 한 번 붙이고 내림한 뒤 파괴 방지 비용을 더한다. 등급을 찾는
  규칙은 지금과 같다([[ADR-050]] 결정 2 ~ 4).
- 시도마다 내림하던 것이 합계에 한 번 내림하는 것으로 바뀌어, 시도당 1 메소 이하의 차이가 생긴다. 사용자가 받아들인
  오차다.

### 결정 3. 기존 기기는 부팅 단계가 원본으로 합계를 만들고, 원본 표는 v1.0.14 에서 지운다

SQLite 버전 이관이 아니라 앱이 켜진 뒤 한 번 도는 단계(`ensureEnhancementTotals`)가 옮긴다. 이벤트 월드를 가리는 캐릭터 이름
목록과 메인 넥슨 계정 id 가 Preferences 에 있어, DB 를 여는 자리에서는 읽을 수 없기 때문이다.

- 옛 원본은 메인 계정의 자격으로 받은 것이라 메인 계정 id 로 적는다.
- 수집기와 가계부가 합계를 읽기 전에 이 단계를 기다린다. 다 옮기면 Preferences `enhancementTotalsMoved` 에 적고 다시 돌지 않는다.
- 메인 계정이나 이름 목록이 아직 없으면 옮기지 않고 다음 호출이 다시 본다. 이름 목록 없이 옮기면 판정이 빈 줄이 남는데, 옛
  날짜는 굳어 있어 다시 받지 않으므로 그 지출이 영영 안 보이기 때문이다.
- 옛 `enhancement_history` 는 v1.0.13 에서 이 단계만 읽고 두었다가 v1.0.14 에서 지운다(사용자 선택, #685). [[ADR-078]] 결정 9 와
  같은 이유다.

### 결정 4. 다시 매길 기간은 `EXPO_PUBLIC_*` 환경 변수로 걸고, 끝나면 넥슨 계정마다 완료를 적는다

- 요청은 `EXPO_PUBLIC_ENHANCEMENT_RECOMPUTE` 에 JSON 배열로 담는다. 요청 하나는 `id` · 기간(`from` · `to`) · 종류(`kinds`,
  빼면 넷 다)다. 예: `[{"id":"pulse-2026-09","from":"2026-09-16","to":"2026-10-20","kinds":["cube","starforce"]}]`.
  API 가 아니라 번들에 박히는 환경 변수라 OTA 로 나간다([[ADR-014]] 결정 6).
- 형식이 틀린 요청은 버리고 나머지만 쓴다. 고장 난 요청 하나가 회차를 막으면 안 되기 때문이다. `id` 가 없거나, 날짜가
  `YYYY-MM-DD` 가 아니거나, `from` 이 `to` 보다 뒤거나, 모르는 종류가 있으면 틀린 것이다.
- 기간은 조회 하한(`historyFloorDateKey`)과 오늘 사이로 자른다. 하한 앞은 넥슨이 주지 않고 오늘 뒤는 아직 없다. 남는 날이
  없으면 받지 않고 바로 완료로 적는다.
- 수집기는 끝나지 않은 요청의 날짜를 굳음(`settled`)과 상관없이 다시 받아 합계를 갈아 끼운다(결정 6 과 같은 방법). 그 일도
  계획에 들어 진행 바 분모와 로딩 모달 판정에 들어간다. 다시 매길 때는 지금 비용 표의 값으로 매긴다.
- 진행은 기기 표 `enhancement_recomputes` 에 넥슨 계정 · 요청마다 한 줄로 적는다. 강화 내역이 계정 단위라 계정마다 다시
  받아야 하기 때문이다. 요청의 날짜를 앞에서부터 받고, 한 회차에 받은 날이 모두 성공하면 그 마지막 날을 `done_through_date`
  로 적는다. 다음 회차는 그 뒤부터 잇는다. 하나라도 실패하면 적지 않아 다음 회차가 같은 날부터 다시 받는다. 마지막 날까지
  받으면 `completed_at` 을 적고, 적힌 요청은 다시 돌지 않는다.
- 넥슨 로그인 계정은 한 회차에 7일치만 다시 받는다(사용자 선택 2026-10-26). 그 계정의 강화 내역은 서버 스트림을 거치므로,
  요청을 걸면 모든 로그인 사용자가 그 기간을 한꺼번에 서버로 받게 된다. 나눠 받으면 부하가 여러 날로 흩어진다. API 키
  계정은 앱이 넥슨을 직접 부르므로 나누지 않는다.

### 결정 5. 이벤트 월드인지는 저장할 때 판정해 합계 줄에 적는다

이벤트 월드(스페셜) 캐릭터의 강화는 지출에서 뺀다([[ADR-047]] 결정 11). 원본을 버리면 읽을 때 응답을 다시 볼 수 없어,
받는 회차가 판정해 합계 줄의 `event_world` 칸에 적는다(사용자 선택 2026-10-26).

- 스타포스는 응답의 월드로, 큐브 · 잠재 · 소울은 그 회차에 받은 캐릭터 목록의 이름으로 판정한다. 판정 규칙은 지금과 같다.
- 캐릭터 목록을 못 받은 회차의 큐브 · 잠재 · 소울 줄은 칸을 비운다(모름). 화면은 모름 줄을 지금처럼 지출에서 빼고, 그 날짜는
  굳히지 않아 다음 회차가 다시 받아 칸을 채운다.
- 전용 재화(`펄스 인핸서`) 줄과 값을 못 매기는 줄은 지금처럼 합계에 넣지 않는다.

### 결정 6. 굳지 않은 날은 받을 때마다 그 날을 통째로 다시 받아 합계를 갈아 끼운다

합계에는 응답 줄의 id 가 없어, 같은 줄을 두 번 받았는지 가릴 수 없다(사용자 선택). 그래서 오늘처럼 굳지 않은 날은 그 날의
모든 쪽을 받아 합계를 다시 만들고, 그 계정 · 종류 · 날짜의 합계를 갈아 끼운다. 하루 기록은 보통 한 쪽(1000 줄) 안이라 호출이
늘지 않는다. 결정 4 의 다시 매기기도 같은 방법으로 갈아 끼운다.

- 갈아 끼울 때 같은 열쇠의 줄은 값을 고쳐 적고, 다시 만든 합계에 없는 줄은 지운다.
- 굳은 날은 지금처럼 다시 받지 않는다.

### 결정 7. 표

```
기기 enhancement_totals   id · nexon_account_id · history_date · character_name · enhancement_type · enhancement_category
                          · item_group · item_key · item_name · attempts · attempt_cost_meso · destroy_defence_cost_meso
                          · from_star · to_star · event_world · updated_at
                          UNIQUE(nexon_account_id, history_date, character_name, enhancement_category, item_group)
```

- `enhancement_type` 은 받은 API 종류(큐브 · 스타포스 · 잠재 · 소울)이고 갈아 끼우는 단위다. `enhancement_category` 는 화면의
  분류 다섯(잠재를 본 · 에디셔널로 나눈다)이다.
- `item_group` 은 장비 key, 없으면 NFC 정규화 뒤 공백을 지운 이름이다. 화면이 장비별로 펼치는 열쇠와 같다([[ADR-047]] 결정 12).
- 합계 표는 처음부터 계정 칸을 든다. 옛 원본에서 옮긴 줄도 결정 3 의 단계가 메인 계정 id 를 바로 적어, 빈 글자 표시를 거치지
  않는다.
- `from_star` · `to_star` 는 결정 8 의 스타포스 첫 성과 끝 성이다. 다른 분류의 줄은 `NULL` 이다.

### 결정 8. 스타포스 합계는 그날 첫 성과 끝 성을 들고, 펼친 장비 줄이 `17성 → 21성` 으로 보인다

스타포스 줄을 펼치면 장비마다 횟수와 금액만 있어서, 그 강화로 장비가 몇 성에서 몇 성이 됐는지 알 수 없었다(#876,
사용자 2026-11-05). 응답 줄에는 강화 전 성(`before_starforce_count`)과 강화 후 성(`after_starforce_count`)이 있다. 원본은
저장하지 않으므로(결정 1) 묶을 때 합계 줄에 적는다.

- `from_star` 는 그 합계 줄에 든 시도 중 가장 이른 시도(`date_create`)의 강화 전 성이고, `to_star` 는 가장 늦은 시도의 강화
  후 성이다. 응답은 최신 줄부터 오므로 받은 차례가 아니라 시각으로 고른다.
- 두 끝만 잇는다. 그 사이에 성이 내려가거나 파괴되어도 끝 성은 마지막 시도의 강화 후 성이다. 같은 이름의 장비를 한 날에 둘
  강화하면 둘이 한 줄로 묶여(결정 7 의 `item_group`) 다른 장비의 성끼리 이어질 수 있다. 사용자가 받아들인 모양이다(사용자
  선택 2026-11-05).
- 성은 횟수와 같은 시도에서 잰다. 전용 재화 줄과 값을 못 매긴 줄은 합계에 들지 않으므로(결정 5) 성에도 들지 않는다.
- 펼친 스타포스 장비 줄은 두 줄이다. 첫 줄에 장비 이름(좁은 행 이름 `text-xs font-semibold`)과 금액이 선다. 둘째 줄에
  `17성 → 21성`(`text-11`, `text-muted`)과 `64회`(`text-11`, `text-disabled`)가 8pt 떨어져 선다. 셋을 한 줄에 같은
  크기로 두었더니 이름 · 성 · 횟수가 구분되지 않았다(사용자 2026-11-05, 시안 C). 화살표는 심볼 강화 줄(`세르니움 7 → 10`)과
  같은 `→` 다(사용자 선택). 두 칸 중 하나라도 비면 둘째 줄에 횟수만 선다.
- 다른 분류(큐브 재설정 · 잠재능력 · 에디셔널 잠재능력 · 소울 잠재능력)의 펼친 줄은 이름 · 횟수 · 금액 한 줄 그대로다(사용자
  선택 2026-11-05).
- 칸이 생기기 전에 받은 날은 결정 4 의 다시 매기기 요청으로 채운다. 요청은 스타포스만이고 기간은 조회 하한부터 이 변경을
  배포한 날까지다(사용자 선택 2026-11-05). 하루에 1 콜이고, 넥슨 로그인 계정은 결정 4 대로 한 회차에 7일씩 받는다. 아직
  다시 받지 않은 날은 성 없이 선다.
