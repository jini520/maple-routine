# ADR-277: 공지의 기준은 서버다. 기기에는 마지막 서버 응답의 사본만 둔다

> ⚪ 미구현 · 2026-09-13 · **설계 · 구현 전** · 이슈 #398 · 사용자 결정
>
> **열린 질문 셋이 구현을 막는다.** 분류로 거른 목록과 사본의 관계 · 상세 본문의 사본 · 상세
> 조회의 404. 셋 다 사용자 결정 대기다(문서 끝).

**관련**: [[ADR-228]] 결정 4(공지는 기기에 쌓이고 서버는 보강이다. **이 문서가 뒤집는다**) ·
[[ADR-230]] 결정 4·5(배너에서 닫은 기록과 배너의 두 문. 정정 9 가 이 문서를 따라 고친다) ·
[[ADR-229]] 결정 6(조회 실패를 화면 전체의 실패로 만들지 않는다. 그 성질은 그대로다) ·
[[ADR-247]] 결정 5(목록 응답에는 `blocks` 가 없다)
**문서**: `features/notifications.md` · `features/today.md` · `persistence/preferences.md`
**이슈**: #398

## 맥락

사용자 보고. **서버에서 공지를 지워도 앱에서는 그대로 보인다.** 소식 목록 · 공지 상세 · today
배너 셋 다 남는다.

### 앱: 합치기만 하고 지우는 줄이 없다

`storage/notices.ts` 의 `mergeNotices` 는 기기에 있던 공지와 들어온 공지를 `id` 로 합쳐 발행일순
50건(`KEEP`)으로 자른다. 서버 응답에 없는 `id` 를 빼는 줄이 없다. 서버 목록을 `지금 있는 전부` 가
아니라 `보태 줄 것` 으로 읽는 구조다.

그 한 칸(Preferences 키 `notices`)에 쓰는 길이 넷이다.

| 길 | 자리 |
|---|---|
| 푸시 수신 | `features/notice/receive.ts` 의 `receiveNotice`. 부르는 곳이 셋이다(`use-notice-delivery.ts` 의 앞에서 도착 · 탭, `index.ts` 의 배경 메시지 핸들러) |
| 소식 목록 | `SettingsNoticesScreen` 이 `fetchNotices` 결과를 합친다 |
| 공지 상세 | `SettingsNoticeDetailScreen` 이 `fetchNotice` 결과를 합친다 |
| today 배너 | `banner-store.ts` 의 `refresh()` 가 `fetchNotices` 결과를 합친다 |

**빈 응답은 아무 일도 안 한다.** 목록과 배너는 결과가 0건이면 합치기를 건너뛴다. 그런데 더 앞에서
이미 갈 수 없다. `server/notices.ts` 의 `fetchNotices` 는 **실패해도 `[]` 를 낸다.** 그래서 앱은
`서버에 공지가 없다` 와 `조회가 실패했다` 를 가를 정보를 받지 못한다. `fetchNotice` 도 서버의
404 와 장애를 둘 다 `null` 로 낸다.

### 서버: 삭제 신호가 없다

`maple-routine-server` 의 `notices` 표에는 삭제 칸이 없고 API 에 삭제 경로도 없다. 운영자가 행을
지우면 다음 목록 응답에서 빠질 뿐이다. 없는 id 의 상세는 404 `{ error: 'not_found' }` 를 준다.

### 이슈가 낸 두 안과 사용자 결정

이슈는 (A) 서버가 소프트 삭제하고 지운 id 를 실어 보내는 안과 (B) 응답의 발행일 구간 안에서
서버에 없는 id 를 지우는 안을 냈다. **둘 다 기기에 공지가 쌓인다는 전제 위에 있다.** 푸시로만 쌓인
공지와 20건 밖 공지를 지키려고 삭제 신호나 구간 계산이 필요해진 것이다.

사용자는 그 전제를 걷었다(2026-09-13). 공지는 발행하면 서버에 저장되고 앱은 서버에서 받아 온다.
그러면 기기가 들 것은 쌓아 둔 공지가 아니라 **마지막으로 받은 응답**이고, 응답에 없는 것은
기기에서도 없는 것이 된다. 삭제 신호가 필요 없어진다.

## 결정

### 결정 1. 공지의 기준은 서버다. 푸시 페이로드를 기기에 저장하지 않는다 (사용자 결정)

`receiveNotice` 와 `mergeNotices` 를 없앤다. 푸시가 앱에 닿는 세 길에서 저장이 빠진다.

| 길 | 남는 일 |
|---|---|
| 앞에서 도착(`onMessage`) | 배너 조회(결정 4) |
| 탭(`onNotificationOpenedApp` · `getInitialNotification`) | 상세로 이동. `parseNotice` 로 공지 푸시인지 보고 `id` 를 읽는다 |
| 배경 메시지 핸들러(`index.ts`) | 없다. 등록은 그대로 두고 몸통의 저장만 뺀다. 등록 자리를 지키는 이유는 그 파일의 주석 그대로다 |

**푸시로만 쌓인 공지는 있으면 안 된다.** 그런 공지는 서버가 지워도 기기에서 지울 신호가 끝내
없다. 발행한 공지는 서버에 있으므로 푸시에만 있는 공지를 앱이 들 이유도 없다.

**대가**: 알림을 탭했는데 오프라인이면, 사본에 없는 공지는 상세가 못 연다. 푸시 페이로드의
본문(4KB 로 잘릴 수 있던 것)을 그리던 자리도 함께 사라진다.

### 결정 2. 기기에는 마지막 서버 응답의 사본만 둔다 (사용자 결정)

- **조회가 성공하면 사본을 응답으로 통째로 바꾼다.** 서버에 없는 `id` 는 사본에서 사라진다.
- **조회가 실패하면(오프라인 · 서버 장애) 사본을 그린다.** 목록 · 상세 · today 배너 모두다.
  조회 실패를 화면 전체의 실패로 만들지 않는 [[ADR-229]] 결정 6 의 성질이 여기서도 산다.

그러려면 **성공과 실패를 가를 수 있어야 한다.** `fetchNotices` 는 실패면 `null`, 성공이면 배열을
낸다. 빈 배열도 성공이다.

- **성공은 HTTP 200 이고 본문에 `items` 배열이 있는 응답이다.** 둘 중 하나라도 어기면 실패로 읽어
  사본을 안 건드린다. 계약을 어긴 응답을 성공으로 읽으면 서버 버그 하나가 기기의 공지를 전부
  지운다.
- **`items: []` 는 서버에 공지가 없다는 답이라 사본을 비운다.** 통째로 바꾼다는 결정에서 곧장
  나오는 결과다. 서버의 공지를 전부 지우면 앱에서도 전부 사라진다.

`KEEP = 50` 이 없어진다. 사본의 크기는 응답의 크기다.

사본을 분류별로 나눌지, 상세 본문을 어디에 둘지는 **열린 질문 1·2** 다.

### 결정 3. 목록은 최근 20건이다 (사용자 결정)

`fetchNotices` 의 `limit=20` 을 그대로 쓴다. 서버는 안 바뀐다.

**20건 밖으로 밀린 공지는 사본에서도 빠진다.** 앱은 `서버가 지웠다` 와 `20건 밖이라 이번 응답에
안 왔다` 를 가르지 않는다. 사본이 받은 공지의 보관함이 아니라 마지막 응답이라서 가를 필요가
없다.

**대가**: 오프라인에서는 최근 20건만 열린다. 지금은 기기에 쌓인 50건까지 열렸다.

### 결정 4. 앱이 앞에 있을 때 공지 푸시가 오면 서버를 다시 조회한다 (사용자 결정)

`onMessage` 로 온 푸시를 `parseNotice` 가 공지로 읽으면 today 배너의 `refresh()` 를 부른다.
페이로드는 저장하지 않는다.

이 길은 OS 가 알림을 안 그린다(FCM 이 포그라운드에서 `notification` 을 `onMessage` 로만 넘긴다).
그래서 앱이 아무것도 안 하면 today 를 보던 사용자에게 아무 일도 안 일어난다. 지금은 기기에 쌓고
`load()` 로 다시 골랐는데, 쌓지 않으면 배너가 새 공지를 알 길은 서버뿐이다.

**대가**: 앞에 있을 때 오는 공지 푸시 한 건이 서버 요청 한 건이 된다. [[ADR-230]] 결정 5 가 이
자리를 `load()` 로 둔 이유가 그 비용이었다. 패치 날처럼 여러 건이 같은 분에 오면 그 수만큼 조회가
나간다.

### 결정 5. 배너에서 닫은 기록은 조회가 성공할 때 서버 목록에 없는 id 를 뺀다 (사용자 결정)

`dismissedNotices` 에서 응답에 없는 `id` 를 뺀다. 지워진 공지의 `id` 가 기록에 계속 남지 않는다.

**앱 공지가 든 조회에서만 정리한다.** 게임 공지만 묻는 조회(`kind=game`)의 응답에는 앱 공지 `id` 가
하나도 없다. 그 응답으로 정리하면 닫아 둔 배너 기록이 전부 빠지고, 닫은 공지가 배너에 되살아난다.
정리해도 되는 조회는 분류를 안 거르거나 `app` 을 포함한 조회다.

**20건 밖으로 밀린 앱 공지의 닫은 기록도 빠진다.** 배너 후보는 가장 최근 앱 공지 하나라, 20건 밖의
공지가 다시 후보가 되려면 그보다 새 공지가 서버에서 지워져야 한다. 그때는 배너가 그 공지를 한 번
더 세운다.

`KEEP_KEYS` 에 계속 든다. 닫았다는 사실은 여전히 기기에만 있다.

## 대가

- **오프라인에서 열리는 공지가 줄어든다.** 최근 20건의 사본뿐이고, 사본에 없는 공지(방금 온 알림 ·
  20건 밖)는 상세가 `공지를 찾을 수 없습니다` 를 그린다.
- **알림은 떴는데 목록에 없는 상태가 오프라인 동안 생긴다.** 사본이 그 공지보다 오래됐기 때문이다.
  온라인이 되어 조회가 한 번 성공하면 맞춰진다.
- **앞에 있을 때 오는 공지 푸시가 서버 요청이 된다**(결정 4).
- **서버 응답이 틀리면 앱이 그대로 따른다.** 서버가 잘못된 목록을 200 으로 주면 사본이 그것으로
  바뀐다. 계약을 어긴 모양만 실패로 걸러진다(결정 2).

## 기각

- **(A) 서버 소프트 삭제와 지운 id 신호.** 사본을 통째로 바꾸면 응답에 없는 것이 곧 기기에서도
  없는 것이라 신호가 할 일이 없다. 서버 표와 응답 계약을 바꾸는 비용만 남는다.
- **(B) 응답의 발행일 구간 안에서만 지운다.** 기기에 쌓는 모델을 그대로 두므로 푸시로만 쌓인 공지가
  남는다(결정 1 이 막으려는 것). 구간 밖에서 지운 공지도 계속 남는다.
- **이슈가 (B) 에 걸었던 우려**(`알림으로 받은 공지가 목록에서 조용히 사라진다`)는 이 결정에서
  성립하지 않는다. 발행한 공지는 서버에 있고 최근 20건은 응답에 온다. 사라지는 것은 서버에서 지운
  것과 20건 밖으로 밀린 것뿐이다.

## 열린 질문 (사용자 결정 대기)

### 1. 분류로 거른 목록 다섯 · 배너와 사본의 관계

지금 조회는 여섯 모양이다. 더보기의 소식 행 다섯이 각자 한 분류로 묻고(`kind=app` · `game` ·
`update` · `event` · `cashshop`, 각 20건), 배너의 `refresh()` 는 분류 없이 20건을 묻는다.
사본을 통째로 바꾼다는 결정이 이 여섯과 만나는 방식이 안 정해졌다.

| 안 | 결과 |
|---|---|
| **가. 분류마다 사본 하나.** 조회는 자기 분류의 사본만 바꾼다. 배너는 `kind=app` 으로 물어 앱 공지 사본을 읽는다 | 목록마다 오프라인에서 자기 분류의 마지막 20건이 선다. 배너가 넥슨 공지에 밀리지 않는다([[ADR-230]] 열린 질문 `앱 공지가 저장소에서 밀려날 수 있다` 가 닫힌다). 사본이 최대 100건이다 |
| **나. 사본 하나를 마지막 조회가 통째로 바꾼다.** 결정 2 를 글자 그대로 따른다 | 앱 공지 목록을 연 뒤 오프라인에서 게임 공지 목록을 열면 비어 있다. 배너가 분류 없이 20건을 받으면 넥슨 공지가 몰린 날 앱 공지가 사본에서 빠져 배너가 사라진다 |
| **다. 사본 하나를 늘 분류 없는 20건으로 채우고 화면이 거른다.** 목록도 분류 없이 묻는다 | 사본이 하나로 일관된다. 대신 넥슨 공지가 몰리면 앱 공지 목록이 20건보다 훨씬 적거나 빈다. 분류별 `최근 20건` 이 안 선다 |

### 2. 상세 본문의 사본, 그리고 20건 밖 공지를 알림으로 열었을 때

목록 응답에는 `blocks` 가 없다([[ADR-247]] 결정 5). 지금은 상세 조회 결과를 `mergeNotices` 로 목록
사본에 섞어 본문 블록까지 남긴다. 목록 조회가 사본을 통째로 바꾸면 그 블록이 사라진다.

| 안 | 결과 |
|---|---|
| **가. 상세는 사본을 따로 안 둔다.** 조회 결과는 화면 상태로만 든다. 실패하면 목록 사본의 같은 `id` 를 그린다 | 오프라인 상세에 블록이 없다. 앱 공지는 `body` 로 서고, 넥슨 공지는 `body` 요약만 선다. 이벤트·캐시샵은 `body` 가 비어 `본문을 받지 못했어요` 가 된다. 20건 밖 공지나 방금 온 알림은 `공지를 찾을 수 없습니다` 다 |
| **나. 상세 사본을 `id` 별로 둔다.** 마지막으로 받은 상세 응답을 공지마다 남긴다. 건수 상한이 필요하다 | 한 번 연 공지는 오프라인에서도 본문까지 열린다. 대신 지워진 공지의 상세 사본을 목록 조회로 못 지운다(20건 밖과 삭제를 못 가른다). 상세를 다시 열어 404 를 받을 때만 지워진다(질문 3) |
| **다. 목록 사본의 같은 `id` 에 상세 응답을 덮는다** | 다음 목록 조회가 통째로 바꾸는 순간 블록이 사라진다. 20건 밖 공지는 목록 사본에 자리가 없어 못 남긴다(넣으면 서버 목록에 없는 `id` 가 사본에 생긴다) |

### 3. 상세 조회가 404 를 받았을 때

서버는 없는 `id` 에 404 를 준다. 지금 `server/notices.ts` 는 200 이 아닌 응답을 전부 실패로 접는다.

| 안 | 결과 |
|---|---|
| **가. 404 는 성공한 답(없다)으로 읽는다.** `공지를 찾을 수 없습니다` 를 그리고 사본과 닫은 기록에서 그 `id` 를 뺀다 | 지운 공지를 알림이나 목록에서 열면 다음 목록 조회를 기다리지 않고 바로 사라진다. 대가로 앞단(nginx · 터널)의 설정 사고가 404 를 내면, 사본에 있는 공지도 `찾을 수 없습니다` 가 된다 |
| **나. 404 도 실패로 읽는다(지금 모양)** | 사본에 있으면 그것을 그린다. 지운 공지는 목록 조회가 한 번 성공할 때까지 상세에서 열린다 |
