# ADR-289: 안 보이는 화면의 반복 모션은 멈추고, 배너 줄의 숨은 칸은 스크롤마다 커밋하지 않고, 배너 점은 바탕을 불투명하게 둔다

> 🟢 유효 · 2026-09-17 · **구현 완료**(2026-09-17) · 실기기 검증(안드로이드 · 아이폰) · 사용자 결정(2026-09-17)

**관련**: [[ADR-264]] 결정 2(today 머리에서 얼굴 셋이 도는 드럼) · [[ADR-249]] 결정 3(보스 수익 버튼에서 그림 셋이 도는 드럼) ·
[[ADR-282]] 결정 5(더보기 배너가 넘어가는 모습)
**문서**: `features/today.md` · `features/boss-profit.md`

## 맥락

사용자가 더보기 화면에서 프레임이 떨어지고 기기가 뜨거워진다고 했다(2026-09-17). 실기기 둘에서 쟀다. 안드로이드는 Z Flip3
릴리스 빌드(120Hz)이고, 아이폰은 iPhone 17 개발 서명 빌드다.

1. **더보기에 가만히 있어도 메인 스레드가 쉬지 않는다.** 그려진 프레임이 0장인데 메인 스레드가 코어 하나의 25~29% 를 쓴다(두
   기기 모두). 안드로이드 트레이스를 보면 매 프레임 뷰 셋의 속성을 커밋한다. today 머리의 얼굴 드럼(`CharacterManageButton`)이다.
   탭을 옮겨도 today 화면은 마운트된 채라 `useLoopedValue` 의 `withRepeat` 이 계속 돈다. 안드로이드에서 모션 줄이기로 이 루프만
   끄자 메인 스레드 실행 시간(트레이스의 스케줄 기록)이 25.2% 에서 5.3% 로 떨어졌다. 남은 5% 는 RN 이 프레임마다 거는 기본
   콜백이다.
2. **안드로이드에서 배너를 끄는 동안 터치 이동 하나에 4~10ms 가 걸린다.** 120Hz 의 한 프레임은 8.3ms 다. 스크롤 이벤트마다
   칸 22개의 `useAnimatedStyle` 이 전부 다시 계산되고, 프레임마다 뷰 24~25개가 커밋된다. 값이 실제로 바뀌는 것은 넘어가는 두
   칸과 막 둘, 점 표시 하나로 다섯뿐이다.
3. **아이폰에서는 배너 줄이 화면에 보이기만 해도 합성이 무겁다.** 줄 하나가 보일 때마다 프레임당 오프스크린 패스가 약 100번
   늘고(두 줄 약 220 · 한 줄 약 120 · 없음 18), 합성 13~15ms · GPU 약 12ms 로 스크롤 중 히치가 초당 300~400ms 다. 원인은 점의
   그림자였다(결정 3 을 고친 빌드로 확인). 점 바탕이 반투명(`rgba(255, 255, 255, 0.72)`)이라 RN iOS 가 `shadowPath` 를 못 달고 픽셀 그림자로 그린다.

1 과 2 는 원인이 하나로 모인다. Reanimated 는 새 스타일을 이전 스타일과 **얕게** 비교해 다를 때만 커밋하는데(`shallowEqual`),
워크릿이 `transform: [...]` 를 부를 때마다 새 배열로 만들어 값이 같아도 늘 다르다고 판정한다. 그래서 가만히 서 있는 얼굴도,
숨어 있는 배너 칸도 부를 때마다 커밋된다. 커밋은 ShadowTree 를 거치는 비싼 길이다(`ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS` ·
`IOS_SYNCHRONOUSLY_UPDATE_UI_PROPS` 가 꺼져 있다).

## 결정

### 결정 1. `useLoopedValue` 는 자기 화면이 안 보이면 루프를 멈춘다 (사용자 결정)

화면이 초점을 잃으면 `cancelAnimation` 으로 멈추고, 초점을 되찾으면 `from` 에서 다시 돈다.

- **멈출 때는 값을 그 자리에 둔다.** push 로 화면이 밀려 나가는 동안에도 그림이 보인다. 그때 `from` 으로 되돌리면 나가는
  화면에서 얼굴이 첫 칸으로 튄다.
- **다시 돌 때는 `from` 에서 시작한다.** 초점을 되찾는 것은 화면이 막 보이기 시작할 때라 첫 칸으로 바뀌는 순간이 눈에 안
  걸린다. 멈춘 자리에서 이어 돌리려면 남은 시간을 곡선마다 따로 계산해야 한다.
- **초점은 `hooks/useScreenFocused` 가 낸다.** `BottomBarOverlay` 안에 있던 훅을 꺼내 둘이 같이 쓴다. `useIsFocused` 는
  내비게이터 밖에서 던지는데 이 저장소의 컴포넌트 테스트는 내비게이터 없이 렌더하므로, 컨텍스트가 없으면 보이는 것으로 둔다.
- 모션 줄이기면 지금처럼 `from` 에 머문다.
- 훅 하나를 고치므로 쓰는 곳 넷이 함께 멈춘다. today 드럼(`CharacterManageButton`) · 보스 수익 버튼 드럼(`DropPriceFab`) · 스피너
  둘(`MapleSpinner` · `MapleSweepSpinner`)이다. 보스 수익 버튼은 화면을 떠나면 그림이 걷히지만(`BottomBarOverlay` 가 `null` 을
  낸다) 진행률을 든 `DropPriceFab` 은 마운트된 채라 루프가 돌고 있었다.

### 결정 2. 배너 칸의 스타일은 숨은 칸에 `transform` 을 싣지 않는다 (사용자 결정)

숨은 칸은 `{ opacity: 0, zIndex: 0 }` 만 낸다. 스크롤이 움직여도 같은 값이라 얕은 비교를 통과해 커밋이 나가지 않는다. 보이는
두 칸만 `transform` 을 싣는다. 모양은 `notice-banner-motion` 의 순수 함수(`bannerSlideStyle`)가 낸다.

- 숨기 직전의 `translateX` 가 뷰에 남는다. 불투명도가 0 이고 보이는 칸보다 아래(`zIndex`)라 보이지도 눌리지도 않는다. 다시
  이전 배너나 새 배너가 되면 그 칸의 `translateX` 를 새로 싣는다.
- 막(`veil`)은 이미 숫자 하나라 숨은 칸은 0 으로 같은 값이다. 고칠 것이 없다.
- 넘기는 모습([[ADR-282]] 결정 5)은 그대로다.

### 결정 3. 배너 점은 바탕을 불투명한 흰색으로 두고 점 전체를 옅게 한다. 보이는 모습은 그대로다 (사용자 결정)

맥락 3 의 스크롤 끊김을 없앤다. 점은 지금처럼 흰색 72% 에 옅은 그림자이고, 그리는 방법만 바꾼다.

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 바탕 | `rgba(255, 255, 255, 0.72)` | `#ffffff` |
| 점 전체의 투명도 | 1 | `opacity: 0.72` |
| 그림자 | `shadowOpacity: 0.35` | 그대로 `0.35` |

- **바탕이 불투명해야 RN iOS 가 그림자 모양을 계산한다.** `RCTViewComponentView` 는 바탕의 알파가 1 일 때만 `shadowPath` 를
  둥근 사각형으로 만들고, 아니면 비워 둔다. 비어 있으면 그림자를 픽셀로 떠야 해서 점마다 화면 밖 그리기가 따로 돈다. 배너 줄 둘에
  점이 마흔 개라 배너가 보이는 동안 스크롤 한 프레임의 합성이 8.3ms 를 넘었다.
- **진하기가 같다.** 지금은 그림자가 반투명한 바탕에서 떠져 실제 진하기가 0.35 × 0.72 다. 바꾼 뒤에는 그림자가 계산된 모양으로
  그려지고 점 전체의 `opacity` 가 함께 곱해져 역시 0.35 × 0.72 다. 흰색도 72% 로 같다.
  - 실기기 스크린샷을 픽셀로 견주면 점 가운데가 RGB 로 10 밝고 둘레 그림자가 조금 옅다. 반투명한 점 아래로 비치던 자기
    그림자를 불투명한 바탕이 가려서다. 확대해도 눈으로는 구분이 어렵다.
- 점 뷰에는 자식이 없어 `opacity` 가 겹친 그리기(그룹 불투명도)를 부르지 않는다.
- 안드로이드는 그림자 속성을 안 그리므로 흰색 72% 점 그대로다.
- 이 결정은 처음에 **점 그림자를 그대로 둔다**로 정했다가 같은 날 바꿨다. 그때는 점 모양을 바꾸는 안(테두리 · 반투명 알약 바탕 ·
  그림자 제거)만 물었고, 모양을 지키는 이 방법은 뒤에 나왔다.

## 하지 않은 것

- **today 드럼은 보이는 동안에는 여전히 매 프레임 커밋한다.** 얼굴이 서 있는 구간(한 바퀴의 79%)에도 `transform` 이 새 배열이라
  그렇다. 이번 범위는 안 보일 때다.
- `Skeleton` 의 펄스는 `useLoopedValue` 를 안 쓰고 받아 온 뒤 걷히므로 이번 범위가 아니다.
- Reanimated 정적 플래그(`*_SYNCHRONOUSLY_UPDATE_UI_PROPS`)는 켜지 않는다. 네이티브가 바뀌어 스토어 빌드가 필요하다.

## 검증

안드로이드 Z Flip3 에서 고치기 전 APK 와 고친 APK 를 번갈아 깔아 같은 조건(60Hz · 같은 adb 입력)으로 쟀다(2026-09-17).

| 무엇 | 전 | 후 |
|---|---|---|
| 더보기에 가만히 5초, 메인 스레드 실행 시간 | 25.2% | **5.3%** |
| 세로 스크롤, UI 스레드가 늦어 놓친 프레임 | 11 | **1** |
| 배너를 끌 때 프레임당 커밋되는 뷰 | 24~25 | **4~5** |
| 배너를 끌 때 `onScrollChanged` 중앙값 | 3.53ms | 3.27ms |
| 배너를 끌 때 제 시간을 놓친 프레임 | 14 (3.2%) | 12 (2.8%) |

- 결정 1 은 발열의 원인을 없앴다. 5.3% 는 모션 줄이기로 루프를 끈 대조 실험과 같은 값이다.
- **결정 2 는 커밋 수만 줄이고 끄는 동안의 비용은 거의 그대로다.** 이벤트 하나의 비용이 커밋되는 뷰 수보다 칸 22개의 스타일
  계산과 이벤트마다 한 번 도는 커밋에 있다. 더 줄이려면 넘기는 칸 근처만 애니메이션 스타일을 달거나, 정적 플래그로 커밋을
  건너뛰어야 한다(스토어 빌드). 정하지 않았다.
- **아이폰도 같다.** App Store 앱(OTA 1.0.10, 고치기 전 코드)과 고친 코드의 개발 서명 Release 빌드를 같은 iPhone 17 에서
  USB 로 쟀다. 더보기에 가만히 16초, 메인 스레드가 **24.5% → 1.8%** 다. 배너를 끄는 비용은 아이폰에서 재지 않았다(아이폰의 병목은
  맥락 3 의 합성이라 결정 2 가 닿는 자리가 아니다).
- **결정 3 은 아이폰 스크롤 끊김을 없앴다.** 결정 1 · 2 를 넣은 빌드와 거기에 점만 고친 빌드를 번갈아 깔고, 배너를 건드리지 않고
  더보기를 위아래로 스크롤해 쟀다(`Animation Hitches`). 아래 값은 배너 줄 둘이 보이는 구간이다.

| 무엇 | 전 | 후 |
|---|---|---|
| 프레임당 오프스크린 패스 | 221 | **21** |
| 합성 시간 중앙값 (상위 10%) | 14.0ms (16.4ms) | **6.8ms (8.2ms)** |
| GPU 중앙값 | 12.0ms | **4.4ms** |
| 히치 | 초당 238ms | **초당 2ms** |
