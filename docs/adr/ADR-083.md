### ADR-083: 남아 있던 인라인 실패 문구 3자리를 토스트로 — ADR-063 결정 1의 미완 정리 (구현 완료, 2026-08-02)

> 🟢 **ACTIVE — 유효.** 현행 RN 앱에 적용되는 결정이다.

**배경**: [[ADR-063]]이 "그 문구가 사라진 자리에 남는 것이 있는가"를 배치 기준으로 정하고 스케줄러 3화면의 인라인 문단을 걷어냈다. 2026-08-02 전수 재조사에서 **그 정리가 끝나지 않았다**는 것이 드러났다.

1. 구현 커밋이 실제로 지운 것은 **전역 실패(`status === 'error'`) 문단 하나**였다. 컨텐츠·보스 스케줄러의 **캐릭터별 실패 문단**(`selected.error`)은 그대로 남았고, 이슈 #78 B 수정(`8aad482`)이 조건만 `isStale` → `error != null` 로 고치면서 오히려 "정상 동작하는 인라인 문단"이 됐다.
2. 그 문단이 남은 결과가 결정 1의 목적을 뒤집는다. `syncSchedules` 는 **캐릭터 단위 실패를 예외로 던지지 않고 결과에 실어 반환**하고(`buildFallbackResult`, 401/429는 나머지 캐릭터까지 같은 에러로 채운다), 스토어는 그때 `status: 'loaded'` + 전역 `error: null` 을 쓴다. 즉 **실제 401/429/네트워크 실패의 대부분이 전역 `error` 를 거치지 않는다** — 토스트를 보는 값이 채워지지 않으므로 두 화면에서는 토스트가 아예 뜨지 않고, 액션 없는 빨간 한 줄만 남는다. `invalidApiKey` 에 설정 진입 경로를 준다는 결정 3이 이 두 화면에서 작동하지 않고 있었다.
3. [[ADR-063]]이 "이번 범위 밖 — 추후 재검토"로 유보한 **보스 수익 기간 백필 실패**와, 온보딩 **계정 선택 실패**(인라인)도 같은 기준으로 다시 보면 토스트가 맞다.

디버그 카탈로그(`/debug/inline-errors`, 임시)로 남은 인라인 표시를 한 화면에 모아 확인한 뒤 사용자가 세 자리를 지정했다.

**결정**:

1. **컨텐츠·보스 스케줄러의 캐릭터별 동기화 실패를 토스트로 옮긴다.** 헤더 아래 `<p className="text-sm text-error-ink">` 를 걷어내고 `useScheduleSyncErrorToast(selected?.error ?? null, …)` 를 추가 호출한다.
   - 판정은 결정 1과 동일하다 — 새로고침 옆 "n분 전"(`formatSyncedAt`)과 캐릭터 드롭다운이 그 자리에 남으므로 문단은 실패 사실만 중복해 말한다. 옮기면 그 대가로 **액션이 생긴다**(`invalidApiKey` → 설정 열기).
   - 전역 훅과 **중복되지 않는다**: 전역 `error` 가 채워지는 경로(`syncSchedules` 자체가 throw)에서는 `characters` 가 캐시 뷰로 교체되고 그 뷰의 `error` 는 항상 `null` 이다. 두 훅이 동시에 울릴 조합이 없다.
   - 캐릭터를 바꾸면 새 `error` 객체가 dep에 들어와 다시 뜬다. 의도된 동작이다 — 실패한 캐릭터로 전환한 사용자에게 그 캐릭터가 왜 낡았는지 말해야 한다.

2. **`characterUnavailable` 에는 액션을 주지 않는다**(`useScheduleSyncErrorToast` 확장). 결정 1로 이 종류가 처음 토스트에 도달하는데, 기존 훅은 `invalidApiKey`·`rateLimited` 외 전부에 "다시 시도"를 붙였다. 400 `OPENAPI00003` 은 **영구 실패**라 눌러도 같은 400이다([[ADR-062]] 결정 3·[[ADR-067]] 결정 1).
   - "캐릭터 관리로 보내 추적을 해제시키는" 액션이 진짜 처방이지만 이번 범위에 넣지 않는다 — 해제 경로는 피커 그리드에 이미 있고([[ADR-068]] 결정 4), 액션을 하나 더 만들면 훅이 화면별 핸들러를 셋 받게 된다. 지금은 **잘못된 버튼을 없애는 것**까지만 한다.

3. **보스 수익 기간 로드 실패를 토스트로 옮긴다 — 단, 카드가 있을 때만.** [[ADR-063]]이 유보했던 자리다.
   - **카드가 있으면**(`characterGroups.length > 0`) 기간 라벨·이전/다음 버튼·캐릭터 카드가 전부 남는다 → 토스트. 문구는 카드가 없을 때의 `ErrorState` 제목과 같은 **"이 기간을 불러오지 못했습니다"** 로 통일하고 "— 다시 시도해주세요"는 뗀다(액션 버튼이 그 말을 대신한다). 액션은 **다시 시도**(`retryPeriod`).
   - **카드가 없으면** 문구가 사라진 자리에 빈 칸이 남으므로 `ErrorState` 를 그대로 둔다(변경 없음). 같은 실패의 두 얼굴이지만 기준은 하나로 일관된다.
   - 중복 방지 키는 `periodKey` 이고, **로딩이 시작되면 키를 비운다** — 그러지 않으면 "다시 시도"를 눌러 같은 기간이 또 실패했을 때 아무 반응이 없다.

4. **온보딩 계정 선택 실패를 토스트로 옮긴다.** `AccountSelectionList` 의 `errorMessage` prop과 인라인 `<p>` 를 없앤다.
   - 계정 목록·"계속하기"가 그 자리에 남는다 → 토스트. 네 종류 중 세 종류(`invalidApiKey`·`rateLimited`·`network`)는 **이미 스토어가 토스트를 띄우고 있어** 인라인은 중복이었다([[ADR-065]] 결정 1이 API 키 경로에 넣은 것).
   - 나머지 하나 `storageWriteFailed`(계정 선택 저장 실패)만 토스트가 없어 **인라인을 지우면 무음이 된다** — `selectAccount` 의 `catch` 에 토스트를 추가한다. 액션은 두지 않는다(다시 계정을 누르면 되는 일이라 중복이다, [[ADR-065]] 결정 1의 API 키 단계와 같은 판단).
   - `AccountFlowStatus`(설정 계정 모달)는 이미 `errorMessage={null}` 을 넘기고 있어 표시가 바뀌지 않는다 — prop 시그니처 변경만 따라간다. 모달 본문 전체를 차지하는 `AccountFlowStatus` 자신의 `error` 케이스는 이번 범위 밖이다(그 자리의 내용이라 인라인이 맞다).

**남는 인라인 실패 문구**(이번 결정 반영) — [[ADR-063]]의 표를 갱신한다.

| 자리 | 왜 남는가 |
|---|---|
| 캐릭터 관리 피커 (`ErrorState`) | 그리드가 들어갈 자리의 내용 |
| 온보딩 캐릭터 선택 (`ErrorState`) | 위와 같고, 넘겨야 앱을 쓸 수 있는 차단 상태 |
| 설정 계정 플로우 (`AccountFlowStatus`) | 모달 본문 전체를 차지하고, 재시도 버튼이 유일한 진행 수단 |
| 조회 불가·집계 전 안내 (`UnavailableNotice`) | 실패가 아니라 API 제약 설명 |
| 설정 상태 행의 값 (OTA·캐시 용량) | 행의 "값" 자리 |
| 보스 수익 기간 실패 — **카드가 없을 때만** (`ErrorState`) | 결정 3으로 절반이 토스트가 됐다 |
| 드롭 히스토리 로드 실패 (`ErrorState`) | 목록이 들어갈 자리의 내용 |

**트레이드오프**:

- **캐릭터별 실패가 화면에 상주하지 않는다.** 토스트는 사라지므로, 낡은 캐릭터를 보고 있다는 사실은 "n분 전" 표기로만 남는다. 보스 수익은 카드에 표식이 있지만([[ADR-068]] 결정 3) 스케줄러 두 화면에는 그런 표식이 없다 — 표식을 다는 것이 정답이나 별도 작업이다.
- **캐릭터 전환마다 토스트가 다시 뜬다.** A→B→A 로 오가면 A의 실패를 두 번 알린다(다른 객체라 가드에 걸리지 않는다). 실패한 캐릭터를 보고 있다는 신호가 그것뿐이라 이쪽을 택한다.
- **`characterUnavailable` 토스트에 할 수 있는 일이 없다.** 문구가 "이 캐릭터는 조회할 수 없습니다"라고만 말하고 해제 경로는 사용자가 찾아야 한다. 잘못 작동하는 "다시 시도"보다는 낫다고 본다.

**개발 서버에서 토스트가 2개로 보이는 것은 결함이 아니다**(실측 2026-08-02). `dev` 에서 같은 실패 토스트가 두 번 쌓이는데, `main.tsx` 의 `<StrictMode>` 를 잠시 벗기고 같은 화면을 다시 열면 **1개**로 줄어드는 것을 확인했다. StrictMode dev 이중 마운트가 `loadTrackedOcids` → `refresh` 를 두 번 돌려 **서로 다른 error 객체**를 두 번 만들기 때문이고, 훅의 ref 가드는 "같은 값의 재렌더"를 막는 것이라 이건 통과시키는 게 맞다(같은 종류가 연달아 실패하면 다시 알려야 한다, [[ADR-063]] 결정 6). 프로덕션 빌드에는 이중 호출이 없다. 전역 실패 토스트도 원래 같은 성질이었고 이번 변경이 만든 것이 아니다.
