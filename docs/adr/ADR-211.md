# ADR-211: 온보딩에서 스케줄 관리 방법 단계를 뺀다

> 🟢 유효 · 2026-09-04 · **구현 완료**

**관련**: [[ADR-035]] 결정 17(온보딩 기본 선택 제거. 이 결정이 그 단계째 없앤다) · [[ADR-086]]
결정 1·2(재개 표에서 `trackingMode` 행이 빠진다) · [[ADR-143]] 결정 1(계정 선택 단계를 없앤
같은 판단)

## 맥락

온보딩이 세 단계였다.

```
API 키 → 스케줄 관리 방법 → 캐릭터 선택
```

가운데 단계는 자동·수동 중 하나를 고르게 한다. [[ADR-035]] 결정 17 이 **기본 선택을 없애서**,
사용자가 둘 중 하나를 직접 누르기 전까지 계속하기가 비활성이다.

그 결정의 근거는 「고르지 않은 값을 화면이 선택됨으로 표시하지 않는다」였다. 표시의 정직함
문제였지, **이 질문을 처음 켠 자리에서 해야 하는가**는 묻지 않았다.

물어보면 답이 다르다. 이 선택은 앱을 아직 한 번도 안 써 본 사람에게 **게임의 스케줄러 등록
상태를 따를지, 앱에서 직접 체크할지**를 묻는다. 판단 재료가 전부 앱을 쓴 뒤에 생긴다. 그래서
막는 문장이 하나 서 있다.

> 나중에 설정에서 언제든 바꿀 수 있어요.

나중에 바꿀 수 있는 것을 시작할 때 강제로 고르게 하고 있었다.

## 결정 1. 단계를 없앤다. 온보딩은 두 단계다

```
API 키 → 캐릭터 선택
```

`OnboardingStatus` 에서 `selectingTrackingMode` 가, `OnboardingEvent` 에서
`SELECT_TRACKING_MODE` 가, 스토어에서 `selectTrackingMode` 가 빠진다. `API_KEY_VERIFIED` 는
`selectingContentCharacters` 로 바로 간다.

화면 `app/onboarding/TrackingModeStep.tsx` 와 그 스펙을 지운다. 고르는 자리는
`app/settings/TrackingModeSelector` 하나로 남는다. 두 화면이 카드 안쪽 모양과 공용 카피
(`features/tracking-mode/copy`)를 맞추던 제약도 함께 없어진다.

## 결정 2. 기본은 자동이고, **아무것도 안 쓴다**

온보딩이 `trackingMode` 를 저장하지 않는다. `'auto'` 를 써 넣지도 않는다.

이미 그렇게 되어 있기 때문이다. 값을 읽는 곳이 둘인데 **둘 다 `?? 'auto'` 로 흡수한다**.

| 읽는 곳 | 하는 일 |
| --- | --- |
| `features/tracking-mode/store.ts` | `(await getTrackingMode()) ?? 'auto'` |
| `features/boss-profit/store.ts` | `(await getTrackingMode()) ?? 'auto'` |

`null` 과 `'auto'` 를 구분하던 곳은 **온보딩 게이트 하나뿐**이었다. 그 파일의 주석이 스스로
그렇게 적어 뒀다.

> 미선택(null)이어도 화면 동작은 자동이다. 골랐는가 를 구분해야 하는 곳은 온보딩 게이트뿐이고
> 거기서는 저장 값을 직접 읽는다.

게이트가 없어지면 그 구분에 소비자가 남지 않는다. 그러니 쓰지 않는 편이 정확하다. `'auto'` 를
써 넣으면 **사용자가 고른 값**과 **한 번도 안 고른 값**이 저장소에서 같아지고, 설정 화면이
「자동」을 그리는 근거가 폴백에서 기록으로 바뀐다. 나중에 골랐는가를 다시 묻고 싶어질 때
되돌릴 수 없다.

## 결정 3. 재개 표에서 `trackingMode` 행과 마이그레이션을 뺀다

[[ADR-086]] 결정 1·2 의 표가 이랬다.

| 저장 상태 | 재개 단계 |
| --- | --- |
| `apiKey` 없음 | `awaitingApiKey` |
| ~~`trackingMode` 미선택~~ | ~~`selectingTrackingMode`~~ |
| `trackedCharacters` 비었음 | `selectingContentCharacters` |
| 셋 다 있음 | `completed` |

`deriveResumeTarget` 이 `getTrackingMode` 를 아예 안 읽는다.

**1회성 마이그레이션도 함께 지운다.** 그 분기는 「`trackingMode` 키가 없는데 추적 목록이 있으면
`'auto'` 를 1회 기록하고 `completed`」였고, 존재 이유가 **옛 설치본 사용자가 새로 생긴 단계로
되돌려지는 것을 막는 것**뿐이었다. 단계가 없어지면 막을 것이 없다. 그 분기를 빼도 같은
사용자가 같은 `completed` 에 도달한다(`apiKey` 있음 + 추적 목록 있음). 쓰기가 하나 줄 뿐이다.

## 결정 4. `seedingTracking` 은 **남긴다**

없애고 싶은 유혹이 있다. 온보딩에서 모드를 못 고르니 그 구간의 모드는 항상 자동이고,
`submitContentCharacters` 의 수동 분기는 죽은 코드처럼 보인다.

**아니다.** 도달하는 길이 있다.

```
수동 모드 사용자 → 설정에서 캐시 데이터 삭제(general)
  → trackedCharacters 는 지워지고 trackingMode 는 보존된다(storage/cache-data.ts 의 KEEP_KEYS)
  → 다음 부팅에서 selectingContentCharacters 로 들어온다. 이때 모드는 manual 이다
```

그 자리에서 캐릭터를 고르면 시드가 필요하고, 시드가 끝날 때까지 스피너를 유지해야 한다.
분기를 지우면 수동 사용자의 체크리스트가 빈 채로 완료된다.

## 대가

- **새 사용자는 수동 모드가 있다는 것을 온보딩에서 모른다.** 설정에 들어가야 만난다. 이것을
  메우려고 온보딩에 안내 문구를 새로 넣지는 않는다. 그러면 단계를 뺀 이유(판단 재료가 아직
  없다)를 문구로 되살리는 셈이다.
- **[[ADR-035]] 결정 17 이 무의미해진다.** 그 결정이 다듬은 「기본 선택 없음 + CTA 비활성」은
  설정 모달에는 원래 없던 규칙이라(설정은 항상 현재 모드를 표시한다) 갈 곳이 없다.
- `features/tracking-mode/copy.ts` 의 소비자가 둘에서 하나로 준다. 지우지는 않는다. 설정
  모달이 그대로 쓴다.

## 결과

온보딩 상태가 일곱에서 여섯으로, 이벤트가 아홉에서 여덟로 준다. 화면 파일 하나와 스펙 하나가
없어진다. `deriveResumeTarget` 이 읽는 저장 키가 셋에서 둘로 준다.
