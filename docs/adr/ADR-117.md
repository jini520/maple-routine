## 맥락

### 보고

테스터 보고(2026-08-08, iPhone 16 Pro). 앱 설치 후 실행 → 업데이트 모달에서 `다운로드` →
**`지금 적용 (재시작)`** 을 눌렀더니 **브랜드 주황 스플래시에서 무한 로딩**. 앱이 더 진행되지 않는다.

화면은 "로딩 중"으로 보이지만 실제로는 `#boot-cover` + 네이티브 스플래시가 **걷히지 않은 상태**이고,
iOS `SplashScreen.show()` 가 `parentView.isUserInteractionEnabled = false` 를 걸어두므로 **터치도 죽는다.**

같은 흐름을 iOS 시뮬레이터에서 재현하면 **정상 통과한다**(zip 체크섬·매니페스트·`set()` → 리로드 →
부팅까지 전부). 즉 *"1.0.2 를 받으면 누구나 죽는다"* 가 아니라 **그 순간의 상태·타이밍에 따라 갈리는
실패**다. 이 ADR 이 겨누는 것은 그 실패의 확률이 아니라 **형태**다 — 지금은 실패가 **복구 불가능한
형태로 설계돼 있다.**

### 사슬 — 적용 경로가 되돌아올 수 없는 일방통행이다

`src/features/live-update/store.ts:160-167`:

```ts
async apply() {
  const id = get().downloadedBundleId
  if (id === null) return
  await showSplashScreen().catch(() => {})   // ← 화면을 먼저 덮는다
  await applyDownloadedLiveUpdate(id)        // ← catch 없음, 타임아웃 없음
}
```

호출부는 `onClick={() => void apply()}`(`src/app/UpdatePromptModal.tsx:160`).
**화면을 먼저 가린 뒤에 실패·행(hang) 가능한 작업 둘을 아무 방어 없이 실행한다.** 여기서 무엇이
잘못되든 **커버를 걷는 코드는 존재하지 않는다.**

끊어질 수 있는 고리는 셋이고, **셋 다 증상이 "주황 스플래시 무한"으로 같다.**

| 고리 | 자리 | 무엇이 끊기나 |
|---|---|---|
| **A** | `showSplashScreen()` (`native/splash-screen.ts:22-32`) | iOS `SplashScreen.show()` 는 `UIView.transition` 완료 콜백 안에서만 resolve 한다. 그런데 이 함수는 그 `await` **전에** DOM 커버 div 를 먼저 붙인다(`:27-30`) — 애니메이션 완료가 지연되면 **커버만 남고 다음 줄이 영영 실행되지 않는다.** |
| **B** | `closeBossProfitDb()` (`storage/sqlite/db.ts:193-211`) | `getBossProfitDb` 는 10초 타임아웃(`OPEN_TIMEOUT_MS`)이 있는데 **닫기는 맨몸이다.** 이 저장소는 *"iOS 실기기에서 SQLite 네이티브 호출이 응답 없이 멈춘다"* 를 **두 번** 기록했다([[ADR-008]] 2026-07-17 정정, [[ADR-050]] 결정 2). 온보딩을 끝낸 상태면 `prehydrateTabStores`([[ADR-101]])가 커넥션을 열어둔 채라 이 경로가 열린다. |
| **C** | `CapacitorUpdater.set()` (`native/live-update.ts:154-157`) | reject 할 수 있다. `void apply()` 라 그 reject 는 **아무 데도 도달하지 않는다.** |

고리 B·C 는 어댑터 `applyDownloadedLiveUpdate` 안에서 `close` → `set` 으로 **한 덩어리로 묶여 있어**,
store 가 그 사이에 아무것도 끼울 수 없다.

### 안전망 셋이 전부 꺼져 있다

**① 자동 롤백이 무력화돼 있다.** `src/main.tsx:12` 가 번들의 **첫 문장**으로 `notifyAppReady()` 를
부른다. capgo 의 유일한 안전망은 *"`appReadyTimeout`(**기본 10초** — `capacitor.config.ts` 에 이 값을
설정하지 않았으므로 기본값이 적용된다) 안에 `notifyAppReady` 가 없으면 직전 정상 번들로 되돌린다"* 인데,
**렌더 한 픽셀 전에 "정상"을 선언한다.** 한 번 SUCCESS 로 찍힌 번들은 이후 어떤 실행에서도 롤백되지
않으므로, 메인 청크만 로드되고 그 뒤에 죽는 번들은 **영구히 박힌다.**

`main.tsx:10-11` 의 주석은 이 호출을 **롤백을 피하려고** 앞당긴 근거로 적혀 있다. 롤백은 피해야 할
사고가 아니라 **우리가 유일하게 가진 복구 장치**다 — 의도가 뒤집혀 있다.

**② 커버를 걷는 타이머가 언마운트 때 취소된다.** `src/App.tsx:257-268` 의 스플래시 `useEffect` 는
`setTimeout(() => void hideSplashScreen(), remaining)` 을 걸고 클린업에서 `clearTimeout` 한다.
`hideSplashScreen()` 은 `#boot-cover` 를 지우는 **저장소 전체에서 유일한 코드**다. 첫 1초
(`MIN_SPLASH_MS`) 안에 렌더가 던지면 → ErrorBoundary 가 언마운트 → 클린업이 타이머를 취소 →
**커버는 영원히 남는다.**

**③ ErrorBoundary 폴백이 커버 밑에 그려진다.** 폴백은 `#root` 안이고 `#boot-cover` 는 `index.html:17`
의 `position:fixed; z-index:2147483647`(32비트 정수 최댓값)이다. 게다가 `SplashScreen.show()` 가 건
`isUserInteractionEnabled = false` 는 네이티브 `tearDown()` 에서만 풀린다 — **폴백은 안 보이고
'다시 시작' 버튼은 눌리지도 않는다.**

### 코드를 읽다 발견한 결함 (이슈 본문에 없다)

**`showSplashScreen()` 이 붙이는 `[data-splash-cover]` div 를 걷는 코드가 저장소에 아예 없다.**
`hideSplashScreen()` 은 `#boot-cover` 만 지운다(`splash-screen.ts:14`). `:25-26` 의 주석은 *"문서와 함께
사라지므로 별도 정리가 필요 없다"* 고 적혀 있는데, 그것은 **리로드가 성공한다는 전제**다. 적용이 실패해
문서가 안 죽으면 이 오버레이는 영구히 남는다 — 즉 `apply()` 에 catch 를 달아도 **커버를 걷을 수단이
없다.** 이 phase 는 이것도 함께 고친다(결정 4).

완화가 아니라 절단이다. 각 결정이 위 표·목록의 어느 자리를 자르는지 명시한다.

| 사슬의 자리 | 끊는 결정 |

| 고리 A·B·C — 어느 것이 끊겨도 화면이 안 돌아온다 | **결정 1**(12초 타임아웃 + catch → 커버 걷고 `'apply-error'`) |
| 고리 B — 닫기가 무응답이면 그대로 매달린다 | **결정 5**(닫기 5초 타임아웃) |

## 결정

### 결정 1 — `apply()` 는 되돌아올 수 있어야 한다

순서를 **`closeBossProfitDb()` → 커버 → `set()`** 으로 뒤집는다(지금은 커버가 먼저다). 전체에
**12초 타임아웃 + catch**. 실패하면 **커버를 걷고** `'apply-error'` 로 전환한다.

```
지금:  커버 → [ close → set ]                (실패하면 커버가 남는다)
바꾼 뒤: close → 커버 → set                    (실패하면 커버를 걷고 'apply-error')
        └─ 전체를 12초 타임아웃 + catch 로 감싼다 ─┘
```

- **커버가 올라가 있는 시간을 실제 리로드 구간으로 좁힌다.** 커버의 목적은 [[ADR-027]] 2026-07-17
  추가가 정한 대로 *"리로드 동안 웹뷰 네이티브 배경색이 드러나는 것"* 을 덮는 것이지, 그 앞의 준비
  작업까지 덮는 것이 아니었다. 준비 작업을 커버 앞으로 보내는 것은 그 결정을 어기는 게 아니라 **그
  결정이 말한 구간으로 정확히 되돌리는 것**이다.
- **어떤 고리가 끊겨도 화면이 돌아온다.** 타임아웃은 세 고리 전부를 덮는 하나의 상한이다 — 고리별로
  나누지 않는다(어디서 멈췄는지에 따라 사용자가 볼 화면이 달라질 이유가 없다).
- 12초인 이유: 결정 5 의 닫기 상한 5초 + 커버 + `set()` 이 정상적으로 도는 시간을 넉넉히 덮으면서,
  사용자가 아무 반응 없는 화면 앞에서 견딜 수 있는 상한이다. 성공 경로에서는 이 타임아웃에 **도달할
  수 없다** — `set()` 이 성공하면 그 자리에서 문서가 죽는다.
- **어댑터를 가른다.** `applyDownloadedLiveUpdate` 가 `close` → `set` 을 한 덩어리로 묶고 있어 store 가
  그 사이에 커버를 낄 수 없다. 순서를 뒤집는다는 결정의 기계적 귀결이지 새 결정이 아니다 —
  어댑터에는 `set()` 만 남고 `close` 는 store 가 명시적으로 부른다([[ADR-005]] 어댑터 원칙은 그대로:
  플러그인 호출은 여전히 `native/` 안에 있다).
- `'apply-error'` 는 [[ADR-065]] 결정 2 의 실패 분류표에 한 줄 더해지는 것이다 — **사용자가 시작한
  실패라 모달로 알린다**(`download-error` 와 같은 층).

### 결정 2 — `notifyAppReady()` 를 첫 렌더 커밋 뒤로 옮긴다

`main.tsx` 번들 첫 문장 → **`App` 컴포넌트 마운트 `useEffect`**. "정상"의 정의가 *"메인 청크가
평가됐다"* 에서 **"React 가 마운트에 성공했다"** 로 바뀐다.

- 렌더가 던지면 `useEffect` 가 돌지 않아 **10초 뒤 직전 번들로 자동 롤백된다.** 지금은 같은 상황에서
  번들이 SUCCESS 로 찍혀 영구히 박힌다.
- [[ADR-022]] 결정 6 의 *"번들 실행 직후, 네트워크 요청 이전"* 을 **정정**한다. 그 문장이 지키려던
  것은 "타임아웃 안에 부른다"이지 "가능한 한 빨리 부른다"가 아니었다.

**더 뒤(하이드레이션 완료 뒤)로 옮기지 않는다** — 사용자 결정. `appReadyTimeout` 이 10초인데
`prehydrateTabStores`([[ADR-101]])는 SQLite·저장소 읽기에 의존하고, 이 저장소는 그 호출이 **응답 없이
멈춘 사례를 두 번** 기록했다([[ADR-008]]·[[ADR-050]]). 느린 기기에서 10초를 넘기면 **멀쩡한 번들까지
롤백**돼 업데이트가 영영 안 붙는 역효과가 난다. 첫 렌더 커밋은 네트워크·저장소에 의존하지 않아 그
위험이 없으면서, 가장 흔한 실패인 **부팅 크래시**를 잡는다.

### 결정 3 — `#boot-cover` 에 컴포넌트 밖 실패 안전 타이머를 둔다 (8초)

`index.html` 인라인 스크립트. **`#boot-cover` 가 아직 DOM 에 있을 때만** 동작한다 — 있다는 것은
부팅이 끝나지 않았다는 뜻이다. 이미 걷혔으면(정상 부팅) **아무것도 하지 않는다.**

- **컴포넌트 밖이라는 것이 요점이다.** 안전망 ② 는 커버를 걷는 유일한 코드가 React 트리 안에 있어
  트리가 죽으면 함께 죽는 구조였다. 이 타이머는 그 트리를 모른다.
- 8초인 이유 둘 — 정상 부팅은 `MIN_SPLASH_MS`(1초) + 첫 렌더라 **8배 여유**이고, capgo 롤백
  타임아웃(10초)보다 **짧아** *"커버가 걷힌 화면"* 을 사용자가 롤백보다 먼저 본다.
- 오탐(정상인데 8초를 넘김) 시 노출되는 것은 테마 적용 전 첫 렌더 정도이고([[ADR-027]] 정정이
  `#boot-cover` 를 만든 이유), **그것은 영구 벽돌보다 낫다.**
- **"아직 있을 때만" 가드의 이유**: 이 가드가 없으면 앱이 정상 부팅한 뒤 8초 시점에 사용자가 마침
  `지금 적용` 을 눌러 올라간 **리로드 커버까지 걷어버린다.** 그 구간은 결정 1 의 타임아웃이 맡는다 —
  두 장치의 담당 구간이 겹치지 않게 하는 것이 이 가드다.

### 결정 4 — `hideSplashScreen()` 이 `[data-splash-cover]` 도 걷는다

위 *"코드를 읽다 발견한 결함"*. 커버를 **붙이는** 함수는 있는데 **걷는** 함수가 없었다.
`querySelectorAll` 로 **전부** 지운다(중복 호출로 여러 장 쌓였을 수 있다).

**이 하나가 결정 1 의 "커버를 걷고"를 실현 가능하게 만든다** — 없으면 catch 를 달아도 화면이 돌아오지
않는다. `splash-screen.ts:25-26` 의 *"문서와 함께 사라지므로 별도 정리가 필요 없다"* 는 주석은 리로드
성공을 전제한 것이라 함께 정정된다.

### 결정 5 — `closeBossProfitDb()` 에 타임아웃(5초)을 준다

`getBossProfitDb` 의 `withOpenTimeout`(10초)과 **대칭이되 더 짧다.**

- 여는 것은 파일 생성·마이그레이션을 포함하지만 **닫는 것은 그렇지 않아 정상이면 수 ms** 다.
- 이 값은 **적용 경로에서 사용자가 무반응을 견디는 시간의 상한**이기도 하다(결정 7 의 `'applying'`
  구간이 정확히 이 길이다).
- 실패·타임아웃은 지금처럼 **삼킨다**(best-effort, `db.ts:191-192` 의 기존 주석 그대로) — 곧 리로드될
  것이고 `openBossProfitDb` 의 stale 감지가 최후 폴백으로 남는다. **타임아웃이 바꾸는 것은 "실패로
  끝난다"가 아니라 "끝난다"** 이다.

### 결정 6 — ErrorBoundary 폴백은 마운트 시 `hideSplashScreen()` 을 부른다

커버 제거 + 네이티브 스플래시 해제(**터치 복구**)를 한 번에 얻는다. 안전망 ②·③ 을 동시에 끊는다.

**폴백의 z-index 를 올리지 않는다** — 사용자 결정. 이유 셋:

1. `#boot-cover` 가 이미 `2147483647`(32비트 정수 최댓값)이라 **더 올릴 숫자가 없고** DOM 순서에
   기대야 한다.
2. 같은 매직 넘버가 `index.html` 과 컴포넌트 **두 곳**에 생겨 한쪽만 바뀌면 조용히 깨진다.
3. **z-index 로는 진짜 문제가 안 풀린다** — 폴백을 보이게 만들어도 `isUserInteractionEnabled = false`
   때문에 '다시 시작' 버튼이 **눌리지 않는다.**

커버를 지우면 위에 아무것도 없으므로 z-index 는 올릴 이유 자체가 사라진다. [[ADR-065]] 결정 5 의
*"폴백은 최소로 둔다"* 는 그대로다 — 화면에 보이는 것은 하나도 늘지 않는다.

### 결정 7 — `'applying'` 상태를 추가한다

결정 1 이 순서를 뒤집으면서 **새로 열리는 창**을 막는다.

지금은 커버가 클릭과 같은 틱에 붙어 버튼을 덮으므로 중복 탭이 사실상 불가능한데, 뒤집으면
`closeBossProfitDb()` 가 도는 동안(최대 5초) **모달이 살아 있고 버튼도 눌린다.** 그동안 화면은 여전히
"업데이트 준비 완료"라고 **거짓말을 한다.**

`'applying'` 을 두면 ⑴ 중복 탭이 막히고 ⑵ 그 구간에 정직한 피드백이 생긴다. **후자가 본래 이득이다** —
이 이슈가 지적하는 *"아무 반응 없음"* 의 축소판을 우리가 새로 만들지 않는다.

**단순 재진입 가드(플래그만)는 채택하지 않는다** — 버튼이 살아 있는데 눌러도 무반응이면 같은 문제다.

`'applying'` 과 `'apply-error'` 둘 다 `MODAL_STATUSES` 에 들어간다(전자는 진행 표시, 후자는
[[ADR-065]] 결정 2 골격의 실패 분기).

### 결정 8 — `clearCacheDataAndReload` 도 같은 순서로 고친다

`src/features/settings/cache-data.ts:52-59` 가 **커버 → `closeBossProfitDb()` → `reload()`** 순이라
**동일한 결함**을 갖는다 — 닫기가 매달리면 `reload()` 에 도달하지 못하고 커버만 남는다.
`closeBossProfitDb()` → 커버 → `reload()` 로 뒤집는다. 결정 5 의 타임아웃이 여기에도 함께 적용된다.

**이 경로에는 `'apply-error'` 같은 실패 UX 를 만들지 않는다** — [[ADR-065]] 결정 3 이 이미 *"항상
리로드한다"* 로 확정했고 실패는 `pendingNotice` 플래그로 부팅 후 토스트에 알린다. **그 정책을 바꾸지
않는다** — 여기서 고치는 것은 순서 하나뿐이다.

## 이유

이 이슈의 값은 *"1.0.2 적용이 왜 실패했는가"* 를 밝히는 데 있지 않다. 시뮬레이터에서 같은 흐름이
통과하므로 그 답은 상태·타이밍이고, 그런 실패는 **다시 난다.** 고쳐야 할 것은 **그 실패가 사용자를
가둔다는 사실**이다.

지금 구조는 실패 확률을 낮추는 데 모든 것을 걸고 실패했을 때의 경로를 하나도 두지 않았다 — 화면을
먼저 가리고, 롤백을 스스로 껐고, 커버를 걷는 코드는 죽을 수 있는 트리 안에 하나뿐이며, 마지막
안전망인 폴백은 커버 밑에서 눌리지도 않는다. **네 겹이 전부 같은 방향으로 기울어 있다.**

결정 8개는 확률을 건드리지 않는다. 전부 *"그래서 실패하면 어떻게 되는가"* 에만 답한다.

## 기각안

- **`notifyAppReady` 를 하이드레이션 완료 뒤로**(결정 2) — 10초 안에 못 끝내면 멀쩡한 번들이 롤백된다.
  이 저장소에는 그 호출이 무응답으로 멈춘 전례가 둘 있다([[ADR-008]]·[[ADR-050]]).
- **ErrorBoundary 폴백의 z-index 상향**(결정 6) — 올릴 숫자가 없고, 매직 넘버가 두 곳에 생기며,
  **무엇보다 눌리지 않는 문제가 그대로 남는다.**
- **단순 재진입 가드(플래그만)**(결정 7) — 중복 실행은 막지만 화면은 여전히 거짓말을 하고, 눌러도
  아무 일이 없는 버튼이 남는다.
- **고리별로 타임아웃을 나누기**(결정 1) — 어디서 멈췄는지에 따라 사용자가 볼 화면이 달라질 이유가
  없다. 상한 하나가 세 고리를 전부 덮는다.
- **`apply()` 실패를 토스트로**(결정 1) — 모달이 사라진 자리에 남는 것이 없다([[ADR-063]] 원칙 4,
  [[ADR-065]] 결정 2 가 OTA 다운로드 실패에 내린 것과 같은 판정).
- **캐시 삭제 경로에도 실패 화면 만들기**(결정 8) — [[ADR-065]] 결정 3 이 이미 판정했다.

## 트레이드오프

- **적용을 누르고 최대 5초 동안 커버가 없다.** 결정 1 이 커버를 뒤로 미룬 대가다. 그 구간은 결정 7 의
  `'applying'` 이 채우므로 **빈 화면이 아니라 진행 중인 화면**이 되지만, 지금보다 "즉시 반응"의 체감은
  약해질 수 있다. 실기기에서 확인할 항목이다.
- **결정 3 의 8초 타이머가 걷는 것은 DOM 커버뿐이다.** 네이티브 스플래시 레이어는 결정 1(catch)·결정
  6(폴백 마운트)이 맡는다. 둘 다 실행되지 않는 경로(React 가 **마운트조차 못 하는** 실패)에서는
  네이티브 스플래시가 남고, 그 자리를 메우는 것은 결정 2 가 되살린 **10초 롤백**이다. 이 2초 간극을
  더 좁혀야 한다는 관측이 나오면 그때 인라인 스크립트에서 플러그인을 부르는 안을 검토한다 — 관측 없이
  미리 만들지 않는다.
- **결정 2 로 롤백이 되살아나면, 첫 렌더에서 죽는 번들은 배포자가 "적용이 안 된다"로만 관측한다.**
  롤백은 조용하다. 이것은 의도된 것이다(사용자는 동작하는 앱을 얻는다).
- **결정 5 의 5초는 근거 있는 추정이지 측정값이 아니다.** 닫기가 정상일 때 수 ms 라는 것은 구조에서
  나오지만, 실기기에서 5초를 넘는 정상 케이스가 있는지는 모른다. 넘겨도 잃는 것은 stale 커넥션
  하나이고 그 폴백은 이미 있다.
- **상태가 둘 늘어난다**(`'applying'`·`'apply-error'`). `LiveUpdateStatus` 는 11 → 13 이 된다.
- **커버를 걷는 주체가 넷이 된다** — `hideSplashScreen`(정상 부팅) · 결정 1 의 catch · 결정 3 의
  인라인 타이머 · 결정 6 의 폴백. 셋이 새로 생기지만 **전부 `hideSplashScreen` 또는 그 일부를 부르는
  것**이라 커버 제거 로직 자체는 한 곳에 남는다. `splash.md` 가 이 사실을 기록한다.

## 범위 밖

- **적용이 왜 실패했는지의 규명** — 시뮬레이터에서 재현되지 않는다. 이 phase 는 실패의 **형태**만
  바꾼다.
- **크래시 리포팅 도입**([[ADR-065]] 결정 5 가 미룬 것) — 롤백이 조용하다는 트레이드오프의 정답이지만
  opt-in 토글·전송 항목을 정해야 한다(error-resilience.md 원칙 7).
- **`appReadyTimeout` 값 조정** — 기본 10초를 그대로 쓴다. 결정 2 가 옮기는 것은 호출 시점이지 상한이
  아니다.
- **`showSplashScreen()` 의 고리 A 자체를 없애기**(DOM 커버를 `await` 뒤로 옮기거나 `show()` 를
  기다리지 않기) — 결정 1 의 타임아웃이 그 고리를 덮으므로 지금은 필요 없고, 순서를 바꾸면
  [[ADR-027]] 정정이 규명한 "인셋 띠" 커버 타이밍을 다시 검증해야 한다.

## 미검증

이 phase 가 끝나도 **실기기에서 확인되지 않는 것들**을 미리 적어 둔다.

1. **원래 증상이 사라지는지 모른다.** 시뮬레이터에서 재현되지 않으므로, 고친 뒤에도 "안 났다"가
   "고쳤다"의 증거가 되지 않는다. 이 phase 가 담보하는 것은 **실패했을 때 화면이 돌아온다**는 것이고,
   그것을 실기기에서 보려면 실패를 인위적으로 주입해야 한다.
2. **`'applying'` 구간의 체감**(결정 1·7 의 트레이드오프) — 커버가 5초 늦게 올라오는 것이 어떻게
   보이는지는 눈으로만 판정된다.
3. **결정 3 의 8초 타이머가 실제로 발화하는 것을 본 적이 없다.** 정상 경로에서는 절대 돌지 않는
   코드다 — 자동 테스트가 담보하는 것은 "가드가 맞다"이지 "실기기에서 걷힌다"가 아니다.
4. **결정 2 이후 실제로 롤백이 일어나는지** — 첫 렌더에서 죽는 번들을 일부러 배포해야 확인된다.
5. **결정 5 의 5초가 실기기 정상 케이스를 자르지 않는지.**
