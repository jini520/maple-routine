# ADR-349: 보스 목록과 규칙은 서버가 든다. 앱은 번들 사본으로 켜고 서버가 바뀌면 덮어쓴다

> 🟡 부분 폐기 · 2026-10-15 · 사용자 지정 · **서버 쪽(표 · `GET /v1/bosses` · 관리 화면)과 앱 쪽 구현 완료**(2026-10-15, 배포 완료). **결정 3 의 끝점과 결정 5 의 통로는 [[ADR-350]] 이 `GET /v1/game-data` 하나로 넓혔다**(2026-10-16). 표 셋(결정 1 · 2) · 폼(정정 1) · 직접 완료 참조(결정 6)는 그대로 산다. `GET /v1/bosses` 는 옛 OTA 가 불러 당분간 남는다.

**관련**: [[ADR-006]](게임 데이터는 사용자가 확정한다. 이 결정은 그 데이터가 사는 곳을 옮길 뿐이다) ·
[[ADR-280]] 결정 12(`weekly-bosses.json` 이 보스 key 마스터 표다) · [[ADR-293]](직접 완료가 이 표를 참조한다) ·
[[ADR-054]](두 한도의 뜻) · [[ADR-347]](서버)
**문서**: `foundation/game-data.md` · `features/boss-scheduler.md` · `features/boss-profit.md`

## 맥락

직접 완료([[ADR-293]] 결정 3)는 운영자가 `/admin` 에서 보스를 고르게 하려고 **서버가 보스 key 와 이름 사본을
들어야** 했다. 옛 서버는 그 사본을 코드 안에 26줄로 들고 있었다. 새 보스가 나오면 앱의 JSON 과 서버 코드 두
곳을 고치고, 어긋나도 앱이 모르는 key 를 조용히 무시해 티가 안 났다.

서버를 다시 쓰며([[ADR-347]]) 이 사본을 표로 옮기기로 했고(사용자 지정 2026-10-15), 같은 날 앱도 그 표를
받아 쓰기로 했다. 앱의 `src/data/weekly-bosses.json` 은 보스 26개(주간 24 · 시즌 1 · 월간 1)와 규칙 둘
(선택 한도 12 · 결정석 판매 한도 90)을 든다. 항목은 `key · name · alias · difficulties · requiredLevels ·
portraitSlug` 이고, `difficulties` 와 `requiredLevels` 는 같은 난이도 집합으로 묶인 한 쌍이다.

## 결정

### 결정 1. 표 셋과 ENUM 둘이다. 보스 한 난이도가 줄 하나다 (사용자 지정)

```sql
CREATE TYPE boss_difficulty AS ENUM ('easy', 'normal', 'hard', 'chaos', 'extreme');
CREATE TYPE boss_cycle      AS ENUM ('weekly', 'event_weekly', 'monthly');

bosses
  id             uuid        PK
  key            text        UNIQUE   앱의 boss key. 기기 기록이 이 값을 든다
  name           text        NOT NULL
  alias          text        NOT NULL
  cycle          boss_cycle  NOT NULL JSON 의 묶음 셋. event_weekly 는 12 한도에서 빠진다
  portrait_slug  text        NOT NULL 앱 자산 파일명. 앱에 그 파일이 있어야 그려진다
  sort_order     integer     NOT NULL 배열 순서가 곧 화면 순서라 칸이 있어야 한다
  updated_at     timestamptz NOT NULL

boss_difficulties
  id              uuid            PK
  boss_id         uuid            FK → bosses(id) ON DELETE CASCADE
  difficulty      boss_difficulty NOT NULL
  required_level  integer         NOT NULL
  UNIQUE (boss_id, difficulty)
```

난이도 값과 순서는 앱 `types/scheduler.ts` 의 `BOSS_DIFFICULTIES` 그대로다. 넥슨 API 의 `difficulty` 값이고
그 차례가 정렬 순서다. Postgres ENUM 은 선언 순서로 비교하므로 순위 칸이 따로 없다. 이름은 앱 어휘를 따라
`cycle` 이다(`BossCycle`).

**줄 하나가 보스 한 난이도인 이유.** JSON 의 `difficulties` 와 `requiredLevels` 는 같은 열쇠로 묶인 한 쌍이라
한 줄로 합쳐진다. 난이도마다 값이 다른 메이린(normal 270 · hard 280)도 자연스럽다. 배열 칸으로 두면 두
칸의 열쇠가 어긋나도 DB 가 못 잡는다. 26개 보스에 줄 56개다.

**같은 보스의 다른 난이도는 다른 줄이지만 같은 `boss_id` 다.** 보스 단위의 일(이름 · 주기 · 초상화 · 직접
완료)은 `bosses` 를 보고, 난이도 단위의 일(요구 레벨, 뒤에 결정석 가격과 드롭 표를 옮기면 그 둘)은
`boss_difficulties` 를 본다. 앱은 지금처럼 `(key, difficulty)` 쌍으로 식별한다. 서버 uuid 는 앱에 안 간다.

### 결정 2. 두 한도는 `game_rules` 표다 (사용자 지정)

```sql
game_rules
  id          uuid        PK
  key         text        UNIQUE   weekly_boss_selection_limit · weekly_crystal_sale_limit
  value       integer     NOT NULL
  updated_at  timestamptz NOT NULL
```

보스가 아니라 규칙이라 보스 표에 못 들어간다. [[ADR-054]] 가 둘 다 바뀐 적이 있다고 적어 둬서 앱 상수가
아니라 표다.

### 결정 3. `GET /v1/bosses` 가 보스와 규칙을 한 번에 준다

```
GET /v1/bosses
→ {
    "updatedAt": "2026-10-15T01:00:00.000Z",
    "rules": { "weeklyBossSelectionLimit": 12, "weeklyCrystalSaleLimit": 90 },
    "bosses": [
      { "key": "lotus", "name": "스우", "alias": "스우", "cycle": "weekly", "portraitSlug": "lotus",
        "difficulties": [ { "difficulty": "normal", "requiredLevel": 190 }, … ] },
      …
    ]
  }
```

- 공개 조회다. `bosses` 는 `sort_order` 순, 난이도는 ENUM 순이다.
- `updatedAt` 은 가장 최근에 넣은 시각이다. 앱은 이 값이 사본과 같으면 사본을 그대로 쓴다.
- 아직 한 번도 안 넣었으면 `updatedAt: null` · `rules` 의 값 둘 `null` · `bosses: []` 다.

### 결정 4. 표는 관리 화면에서 JSON 을 붙여 넣어 채운다 (사용자 지정)

`GET /admin/bosses` 가 붙여넣기 칸을 내고 `POST /admin/bosses/import` 가 받는다. JSON 의 모양은 결정 3 의
응답에서 `updatedAt` 을 뺀 것이다. 응답과 같은 모양이라 앱의 번들 파일(결정 5)을 그대로 붙여 넣으면 된다.

- **보스는 key 로 upsert 하고 난이도는 그 보스 안에서 갈아 끼운다.** JSON 에 없는 난이도는 지운다(힐라 하드가
  일간으로 내려간 것처럼 난이도가 빠지는 일이 있다).
- **JSON 에 없는 보스는 지우지 않고 결과에 알린다.** 직접 완료 줄이 그 보스를 참조할 수 있어 지우면 이력이
  깨진다. 지우는 화면은 없다(대가).
- 한 트랜잭션이다. 검사에 걸리면 아무것도 안 바뀐다.
- 인증은 앞단 nginx `auth_basic` 이다([[ADR-347]] 결정 17).

### 결정 5. 앱은 번들 사본으로 켜고, 서버가 바뀌면 덮어쓴다 (사용자 지정)

- 앱은 결정 3 의 응답과 **같은 모양의 JSON** 을 번들에 둔다(`src/data/bosses.json`). 빌드할 때 서버에서 받아
  최신으로 넣는다.
- 켤 때 `GET /v1/bosses` 를 부르고, `updatedAt` 이 사본과 다르면 기기 사본을 덮어쓰고 전역 상태로 든다.
- 못 받으면 사본 그대로다. 첫 실행이 오프라인이어도 번들 사본이 있다.
- 빌드 전에 `node scripts/sync-bosses.mjs`(`scripts/sync-bosses.mjs`)가 `GET /v1/bosses` 를 받아 `src/data/bosses.json` 을
  `updatedAt` 까지 그대로 다시 쓴다. 서버가 비었으면(`updatedAt: null`) 파일을 안 건드리고 멈춘다.

처음에 "기기에 저장하지 않는다" 로 적었다가 사용자가 거뒀다(2026-10-15). 번들에 사본이 있어야 오프라인 첫
실행이 선다.

**앱 쪽 구현(2026-10-15).** 표는 `lib/boss/catalog.ts` 가 든다(`getBossCatalog` · `setBossCatalog` · 구독 ·
계약 검사 `parseBossCatalog`). `lib/boss/bosses.ts` 의 조회 함수와 상수(`BOSS_ENTRIES` · 한도 둘)는 부르는 쪽에서
보기에 그대로이고 안에서 현재 표를 읽는다. `section` 은 `cycle` 에서, `difficulties` 배열과 `requiredLevels`
맵은 난이도 줄에서 만든다. 덮는 흐름은 `features/bosses/store.ts` 의 `hydrateBossCatalog`(번들 → 기기 사본 →
서버) 이고, `boot.ts` 의 `loadBossCatalog` 가 `index.ts` 에서 포트 주입 뒤에 띄운다. 서버 어댑터
`server/bosses.ts`(4초 · 실패와 빈 서버는 `null`) · 기기 사본 `storage/bosses.ts`(Preferences `bossCatalog`,
`KEEP_KEYS` 밖). 보스 관리 화면은 스토어를 구독해 표가 덮이면 목록을 다시 만든다. `status: 'unreleased'` 칸은
서버 모양에 없어 타입과 필터 둘(`BossManageScreen` · `party-appointments/boss-picker`)에서 걷었다. 출시 전
보스는 표에 넣지 않는다.

### 결정 6. 직접 완료는 `bosses` 를 참조하고 열린 줄만 보스당 하나다

[[ADR-293]] 정정 4 가 적는다. `manual_completion_bosses.boss` 가 `boss_id` FK 가 되고, `UNIQUE (boss)` 는
`UNIQUE (boss_id) WHERE closed_at IS NULL` 이 된다. 닫았다 다시 열어도 이력이 남는다.

## 정정

### 정정 1. 표는 관리 화면의 폼으로 채운다. JSON 붙여넣기는 걷었다 (2026-10-15, 사용자 지정)

결정 4 가 JSON 을 붙여 넣어 표를 통째로 넣게 했는데, 첫 배포에 한 번 쓰고 나면 그 모양으로 넣을 일이 없다.
새 보스가 나오면 하나를 더하는 일이지 표를 다시 붙여 넣는 일이 아니다.

- `/admin/bosses` 는 규칙 둘(`PUT /admin/bosses/rules`), 새 보스(`POST /admin/bosses`, 난이도 줄 하나 이상),
  난이도 줄 더하기와 레벨 갈아 끼우기(`PUT /admin/bosses/:key/difficulties/:difficulty`), 난이도 줄 지우기
  (`DELETE …`)를 받는다. `POST /admin/bosses/import` 는 없다.
- **보스는 지우지 않는다.** 직접 완료 줄이 참조한다. **마지막 난이도도 못 지운다.** 난이도 없는 보스가 생기면
  앱의 `parseBossCatalog` 가 표 전체를 거절한다.
- 어느 것을 바꿔도 그 보스의 `updated_at` 이 움직여 응답의 `updatedAt` 이 바뀌고, 앱은 다음에 켤 때 표를
  다시 받는다(결정 5).
- 화면 아래는 `bosses` 와 `boss_difficulties` 를 줄 그대로 보인다. 표가 둘인 것이 보이게.
- `node scripts/sync-bosses.mjs` 는 그대로다. 번들 씨앗은 여전히 서버 응답을 받아 쓴다.

### 정정 2. 보스는 유효 기간을 든다. 시즌 보스는 시즌이 끝나면 안 보인다 (2026-10-16, 사용자 지정)

시즌 보스 메이린은 챌린저스 시즌 4 의 보스라 시즌 5 월드에는 안 나온다. 그런데 시즌 보스를 가리는 판정은
전부 월드 표의 `challengers` 칸 하나였다(보스 관리 화면 · 표시 목록 · 수익 행 · 추적 씨앗 · 백필 기록 · 시즌
배지). 새 챌린저스 월드를 표에 더하는 순간 그 월드 캐릭터에게 메이린이 선다. 수동 모드는 보스 표의
`eventWeekly` 묶음을 그대로 세우고, 자동 모드도 넥슨 API 가 목록에 넣어 주면 선다.

- **`bosses` 에 `from` · `until` 칸을 둔다.** KST 글자 그대로다([[ADR-350]] 결정 9). `YYYY-MM-DD` 또는
  `YYYY-MM-DDTHH:mm`. 없으면 처음부터 · 끝없이다. 응답의 보스 줄에 `from` · `until` 이 는다(`null` 은 없음).
- **판정은 기간으로 한다.** 보스는 **그 기간의 첫날이 `until` 앞이면** 유효하다. 드롭 표 줄과 같은 판정
  (`isEffectiveIn`)이다. 지난 기간은 그대로 선다. 기록이 거기 있어서다. 끝난 뒤의 기간에서는 어느 모드든
  안 선다. 앱의 자리는 `lib/boss/bosses.ts` 의 `isBossActiveIn(key, periodKey, now)` 하나이고, 월드 판정이
  서 있던 여섯 자리가 그것을 함께 본다.
- **관리 화면 보스 목록의 편집기에 기간 둘을 적는 칸이 선다.** `PUT /admin/bosses/:key/period`. 끝은
  시작보다 뒤여야 한다. 기간 경계일 필요는 없다. 시즌이 수요일에 끝나면 그 날을 적고, 그 날을 품은 주는 서고
  다음 주부터 안 선다.
- **값은 사용자가 넣는다.** 메이린의 끝 시각은 [[ADR-006]] 대상이라 이 문서가 정하지 않는다. 관리 화면에서
  적는다.

### 정정 3. 난이도 줄도 유효 기간을 든다. 새로 생긴 난이도는 시작을 든다 (2026-10-16, 사용자 지정)

패치로 한 보스에 난이도가 하나 더 생기는 일이 있다. 그 난이도는 시작 전 기간에 서면 안 된다. 정정 2 의 기간은
보스 단위라 그것을 못 가른다.

- **`boss_difficulties` 에도 `from` · `until` 칸을 둔다.** 모양과 판정은 정정 2 와 같다. **보스의 기간이 먼저 서고
  난이도의 기간이 칸마다 그것을 덮는다**(사용자 지정 2026-10-16). 난이도 줄이 든 칸은 그 값이고 안 든 칸은 보스의
  값이다. 보스가 10-11 ~ 10-23 이고 하드만 10-12 ~ 10-21 이면 하드는 후자, 나머지 난이도는 전자다. 난이도의 끝이
  보스의 끝보다 뒤면 그 난이도만 더 산다. 겹치는 범위가 아니다. 앱의 `isBossActiveIn(key, periodKey, now,
  difficulty)` 가 난이도를 받으면 그렇게 합쳐 본다. 보스가 유효한가는 어느 난이도든 유효한가다.
- **난이도 목록도 기간으로 거른다.** `activeDifficultiesOf(key, periodKey, now)`. 보스 관리 화면 · 파티 인원
  창 · 약속 난이도 고르개는 지금 기간, 직접 완료 시트 · 수익 행의 파티 창은 그 행의 기간이다. 그 행이 든 난이도는
  기간 밖이어도 남긴다. 기록을 고치는 자리라서다.
- **관리 화면 난이도 편집기 줄마다 시작 · 끝 칸이 선다.** `PUT /admin/bosses/:key/difficulties/:difficulty/period`.
  새 난이도를 더할 때도 둘을 받는다.

### 정정 4. 덮는 흐름이 TanStack Query 로 갔다 (2026-10-18)

결정 5 의 통로 중 기기 사본(`storage/bosses`, Preferences `bossCatalog`) · React 에 잇는 스토어(`features/bosses/store`) · 켤 때의
흐름(`features/game-data/hydrate`)을 [[ADR-350]] 정정 7 이 TanStack Query 로 접었다. 표(`lib/boss/catalog`) · 조회(`lib/boss/bosses`) ·
번들 · 폼은 그대로다. 관리 화면은 `useGameTable('bosses')` 로 표를 구독한다. 파티 인원 상한도 이 표에 들었다(난이도 줄의
`maxPartySize` · `rules.defaultMaxPartySize`).

## 대가

- **보스 데이터가 두 벌이다.** 번들 JSON 과 서버 표. 빌드 때 받아 넣는 것이 둘을 맞추는 방법이고, 그 사이의
  차이는 켤 때의 덮어쓰기가 메운다.
- **새 보스의 그림은 여전히 앱 빌드가 필요하다.** `portrait_slug` 는 앱 자산 파일명이라 서버가 새 보스를 넣어도
  그 파일이 번들에 없으면 안 그려진다.
- **보스를 지우는 화면이 없다.** JSON 에서 빠진 보스는 표에 남고 결과 메시지로만 알린다.
- **표가 셋 늘고 ENUM 이 둘 는다.** 값을 더하는 마이그레이션은 [[ADR-347]] 결정 1 의 규칙을 따른다.

## 기각

- **서버가 코드 안에 사본을 든다.** 옛 서버의 모양이다. 새 보스마다 두 곳을 고치고 어긋나도 모른다.
- **난이도와 요구 레벨을 배열 · jsonb 칸으로 둔다.** 두 칸의 열쇠가 어긋나도 DB 가 못 잡는다.
- **두 한도를 앱 상수로 둔다.** 바뀐 적이 있는 값이라 표로 둔다.
- **CLI 로 파일을 읽어 넣는다.** DB 가 앱 박스에서만 닿아 파일을 먼저 옮겨야 한다. 관리 화면이 그 단계를 없앤다.
- **번들에 사본을 안 둔다.** 첫 실행이 오프라인이면 보스 목록이 빈다. 사용자가 거뒀다.
