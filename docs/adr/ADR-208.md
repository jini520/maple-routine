# ADR-208: 캐릭터 관리 컨트롤러를 일 단위 훅 셋으로 가른다

> 🟢 유효 · 2026-09-03 · **구현 완료** · 시뮬레이터 확인

**관련**: [[ADR-144]] 결정 2-1(이 컨트롤러를 화면 둘이 함께 쓰게 된 자리) · [[ADR-205]] 결정 1(같은
「무엇이 무엇을 조합하는가」를 컴포넌트 층에서 물었다) · [[ADR-207]](같은 디렉터리를 정리하다 이
질문이 나왔다)

## 맥락

`use-character-manage.ts` 가 **425줄**이다(코드 313 · 주석 74 · 빈 줄 38). 훅 하나가 `useState` 13개
· `useRef` 2개 · `useEffect` 3개 · `useMemo` 6개 · `useCallback` 9개를 든다.

큰 이유는 길이가 아니라 **한 훅이 일 넷을 하는 것**이다.

| 하는 일 | 줄 | 무엇을 드는가 |
| --- | --- | --- |
| ① 계정 목록 | 56 | `fetchCharacterList` · 대표 레벨 정렬 · 첫 계정 고르기 · `retryAccounts` |
| ② 계정별 후보 + TTL | 72 | `rostersRef` · `commitRosters` · `loadRoster` · `retryRoster` |
| ③ 프로필 캐시 + 조회 불가 | 85 | `neededKey` · 캐시/원장 병렬 읽기 · `knownProfiles` 병합 |
| ④ 선택 편집 | 74 | `editedOcids` · 대표 3상태 · `isDirty` · 추가·빼기·옮기기 |
| 껍데기 | 128 | import 29 · 컨트롤러 인터페이스 33 · 반환 객체 23 · 머리 주석 15 |

**직접 무는 테스트가 하나도 없다.** 화면 테스트 둘(896 + 325줄)을 통해서만 돈다. 그래서 TTL 판정이나
③의 「miss 를 안 적는다」 같은 규칙을 고치려면 화면을 세워야 확인된다. 옆의 `derivations.ts` 는
순수 함수라 자기 spec 304줄을 갖는데, 훅 안에 있는 규칙에는 그 자리가 없다.

## 결정

### 결정 1. 넷 중 셋을 훅으로 뺀다

- `use-known-profiles.ts` (③) — 들어가는 것과 나오는 것이 값 하나씩이라 경계가 가장 깨끗하다
- `use-selection-draft.ts` (④) — 네트워크를 안 본다. 대표 3상태와 `isDirty` 가 여기 산다
- `use-account-rosters.ts` (①+②)

`use-character-manage.ts` 에는 **조립과 파생만** 남는다. 셋을 부르고, `selectedViews` ·
`candidates` · `portraitByAccountId` 처럼 **둘 이상에서 나오는 값**을 만들고, 컨트롤러 모양으로
돌려준다.

### 결정 2. 계정과 로스터는 **붙여 둔다**

①과 ②는 `openAccountRef` 하나를 함께 본다. 계정을 고르는 것이 곧 그 계정의 회차를 여는 일이고,
늦게 온 회차를 버릴 기준도 그 ref 다. 가르면 같은 ref 가 두 파일에 생기고, 그 둘이 어긋나는 순간
직전 계정의 실패가 새 계정 자리에 남는다.

### 결정 3. 뽑은 훅끼리 서로를 모른다. **값으로만 주고받는다**

`useKnownProfiles` 는 로스터를 모른다. 캐시가 모르는 자리를 채울 값을
`CharacterPickerEntry[]` 로 받는다(조립기가 `rosters` 를 펴서 넘긴다). 로스터의 자료구조를 받으면
③이 ②의 타입에 묶여, ②를 고칠 때 ③이 함께 깨진다.

`useSelectionDraft` 는 저장된 목록(`trackedOcids`)만 받는다. 스토어를 직접 부르지 않는 것은 그래야
테스트가 그 자리에 값을 넣어 볼 수 있기 때문이다.

### 결정 4. ~~자리는 **이 디렉터리 그대로**다~~ (정정 1 이 뒤집는다)

`components/organisms/CharacterManage/` 에 나란히 둔다. 「기능별 상태·로직은 `features/`」라는 규칙에
비추면 `features/character-manage/` 가 맞아 보이지만, 지금 `use-character-manage.ts` 가 이미 여기
있고 옮기면 화면 둘의 import 가 함께 움직인다. 이 결정은 **가르는 일 하나만** 한다. 자리를 옮기는
것은 따로 물을 일이다(열린 질문).

## 검증

**425줄 한 파일이 네 파일 565줄이 됐다.** 늘어난 140줄은 훅 셋의 머리 주석과 반환 타입, 그리고
조립기가 새로 지는 일(`needed` · `loadedEntries`)이다.

| 파일 | 줄 |
| --- | --- |
| `use-account-rosters.ts` | 213 |
| `use-character-manage.ts` | 128 |
| `use-selection-draft.ts` | 118 |
| `use-known-profiles.ts` | 106 |

**얻은 것은 테스트다.** 뽑아낸 둘에 직접 무는 스위트가 처음 생겼다.

- `use-selection-draft.spec.tsx` 15개 — 편집 전에는 저장본이 보이는 것 · 한 번 손대면 늦게 온
  저장본이 편집을 안 덮는 것 · 순서만 바꿔도 `isDirty` 인 것과 되돌리면 풀리는 것 · 대표 3상태 ·
  대표를 뺀 캐릭터의 별이 지우는 코드 없이 비는 것 · 저장된 대표를 못 읽어도 화면이 서는 것
- `use-known-profiles.spec.tsx` 12개 — **캐시가 이긴다** · 캐시가 모르면 후보가 채우는 것 ·
  **miss 는 적지 않는다**(늦게 채워진 캐시가 다음 회차에 잡힌다) · 같은 ocid 를 다시 요구해도 다시
  안 읽는 것 · 원장이 던져도 조회 불가로 안 모는 것

이 스물일곱 가지는 **가르기 전에는 화면을 세워야만 물을 수 있었다.**

테스트를 쓰다 규칙 하나를 잘못 알고 있었던 것이 드러났다. 모르는 ocid 는 표에 `null` 로 남는 것이
아니라 **아예 안 들어간다**(`profiles` 에 miss 를 안 적으므로). 그것이 「miss 는 적지 않는다」의
실제 모양이고, 이제 그 문장이 테스트에 적혀 있다.

- `npx tsc --noEmit` 통과 · `npx eslint src` 에러 0
- `npx jest src/components/organisms/CharacterManage src/app/settings src/app/onboarding
  src/__tests__` — 455 통과. 화면 테스트 둘(896 + 325줄)이 **한 줄도 안 바뀌고** 그대로 통과한다.
  실패 하나(`font-scaling-policy` 의 `Segment`)는 이 작업 밖의 것이다
- 시뮬레이터 둘(iPhone 17 Pro/iOS 26.5 · Pixel8_API36)에서 화면이 그대로 뜨고, 안드로이드에서 1번
  행을 3번으로 끌어 `저장` 이 활성이 되는 것까지 확인했다. 네 훅을 지나는 사슬이 다 산다

## 트레이드오프

**파일이 하나에서 넷이 된다.** 전체 흐름을 보려면 조립기를 먼저 읽어야 하고, 「이 값이 어디서
오나」가 한 파일 안에서 안 끝난다.

**조립기가 새 일을 하나 진다.** `neededKey`(선택된 것 + 계정 대표)와 로스터 펴기는 지금 훅 안에서
이웃한 값을 그냥 읽던 것인데, 가르면 **넘겨주려고 만드는 값**이 된다.


## 정정 1 (2026-09-03 · 사용자 지정). **훅 넷을 `src/hooks/` 로 옮긴다**

결정 4 는 자리 옮기기를 「따로 물을 일」로 남겼다. 그 질문의 답이다. 간 곳은 `features/` 가 아니라
**`src/hooks/`** 이고, 그 디렉터리에 이미 훅 셋이 camelCase 파일명으로 살고 있었다
(`useCountUp` · `useLoopedValue` · `useSheetKeyboardTarget`). 넷이 그 규칙에 맞춰 들어간다.

| 옛 이름 | 새 이름 |
| --- | --- |
| `components/organisms/CharacterManage/use-character-manage.ts` | `hooks/useCharacterManage.ts` |
| `components/organisms/CharacterManage/use-account-rosters.ts` | `hooks/useAccountRosters.ts` |
| `components/organisms/CharacterManage/use-selection-draft.ts` | `hooks/useSelectionDraft.ts` |
| `components/organisms/CharacterManage/use-known-profiles.ts` | `hooks/useKnownProfiles.ts` |

스펙 둘도 `hooks/__tests__/` 로 함께 간다(`useCountUp.spec.tsx` 옆이다).

`CharacterManage/` 에는 **그리는 것만** 남는다. `CharacterManageBody` 와 `SelectedCharacterList`.

## 정정 2 (2026-09-03 · 사용자 지정). **`reorder.ts` 를 `useSelectionDraft` 안으로 들인다**

정정 1 이 훅을 옮기면서 `useSelectionDraft` 가 `moveOcid` 를 쓰려고
`components/organisms/CharacterManage/reorder` 를 부르게 됐다. 훅이 컴포넌트 디렉터리를 가리키는
역방향이고, `layer-dependencies.test.ts` 는 `components/` 안만 보므로 잡히지 않는다.

**제품 코드에서 그 파일을 쓰는 곳이 `useSelectionDraft` 하나뿐**이라 파일을 따로 둘 이유가 없다.
`moveOcid` 와 `clampIndex` 가 훅 파일로 들어오고 `reorder.ts` 는 사라진다. `moveOcid` 는 계속
`export` 다. 화면 테스트가 기대값을 손으로 적지 않고 이 함수로 만들기 때문이다.

`reorder.test.ts` 27개는 `hooks/__tests__/useSelectionDraft.spec.tsx` 로 합쳐 42개가 된다. 라이브러리
`reorderInsert` 와 맞대 보는 묶음([[ADR-207]] 결정 3)도 그대로 따라간다.
