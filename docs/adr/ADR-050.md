### ADR-050: iOS 하단 탭 동시 탭 → 문서 전체 리로드 → 보스 수익 데이터 유실 (탭바 클릭 가로채기 + SQLite 커넥션 자가복구) (구현 완료, 2026-07-29)

**배경**: "하단 네비게이션에서 인접한 두 탭을 동시에 누르면 앱 재시작 전까지 보스 수익의 파티원 수·수익 금액이 초기화된 것처럼 보인다"는 사용자 보고. 조사 과정에서 세 개의 가설이 관측과 충돌해 폐기됐고(아래 "폐기된 가설"), 실기기 계측으로 원인이 확정됐다.

**관측 (사용자 보고)**

| 관측 | |
|---|---|
| 트리거 | 하단 탭 **인접 조합만** — 컨텐츠+보스, 보스+수익, 수익+설정 (O) / 컨텐츠+수익, 보스+설정, 컨텐츠+설정 (X) |
| 타이밍 | 시차를 두고 누르면 재현 안 됨 |
| 플랫폼 | **iOS만** — 안드로이드 재현 안 됨 |
| 증상 | 파티원 수·수익 금액이 초기값으로 보임. 에러·로딩 표시 없음 |
| 동반 현상 | **한순간 스플래시/빈 화면이 지나감** |
| 지속 | 탭을 오가도 안 풀리고 **앱 재시작 전까지** 유지 |
| 복구 | 재시작하면 **원래 값이 완전히** 돌아옴 (= 저장 데이터는 무손상) |

**원인 확정 (2026-07-28, iOS 실기기 + Safari 웹 인스펙터 계측)**

`document`에 캡처 단계로 `touchstart`/`touchend`/`click`/`pagehide`를 걸고 인접/비인접 조합을 각각 재현해 비교했다.

```
550017 touchstart /profit touches=2
550017 touchstart /boss   touches=2     ← 두 터치가 같은 ms
550063 touchend   /boss   touches=1
550080 touchend   /profit touches=0
550081 click      /boss                 ← 클릭 하나가 합성됨
       PAGEHIDE                         ← 문서 언로드
```

1. **두 손가락 동시 탭은 대부분 `click`을 아예 만들지 않는다.** 로그의 다른 시도들은 전부 `touchstart`/`touchend`만 찍히고 클릭이 없다 — 그래서 증상이 매번이 아니라 가끔 난다.
2. **드물게 WKWebView가 클릭 하나를 합성하는데, 그 클릭에는 `NavLink`의 `preventDefault()`가 걸리지 않는다.** 그 결과 `<a href="/boss">`의 기본 동작이 실행되고, `PAGEHIDE`가 찍힌다 — **문서 전체가 다시 로드됐다는 뜻**이다(SPA 라우팅이면 절대 찍히지 않는다). 목격된 스플래시가 이것이다(`index.html`의 `#boot-cover` + `App.tsx`의 `MIN_SPLASH_MS`).
   - React Router는 `preventDefault()`를 `shouldProcessLinkClick`이 참일 때만 호출하고, `Link`의 클릭 처리는 React 합성 이벤트 시스템을 탄다. 이 클릭이 그 경로를 타지 않았다는 것이 로그의 결론이다. **정확히 왜 React 이벤트 시스템을 안 타는지는 WebKit 내부라 확정하지 않았다** — 아래 결정 1은 그 이유와 무관하게 성립하는 수정이다.
3. **리로드가 데이터를 죽인다.** 이 리로드는 `closeBossProfitDb()`를 거치지 않는다 — 호출부는 OTA 적용(`native/live-update.ts`)과 캐시 삭제(`app/settings/CacheDataSection.tsx`) 두 곳에 손으로 배선돼 있을 뿐이다. 그 결과 네이티브 SQLite 커넥션이 stale하게 남고, 새 JS 컨텍스트의 첫 쿼리가 응답 없이 멈춘다([persistence/sqlite.md](../persistence/sqlite.md) "커넥션 라이프사이클" — 2026-07-17에 *"앱 업데이트 직후 과거 수익 데이터가 안 불러와지는 증상"*으로 이미 보고된 그 함정과 동일).
4. **`withSqliteFallback`이 그 멈춤을 "기록 없음"으로 위장한다.** 5초 초과를 에러가 아니라 빈 결과로 바꾸므로, 화면은 파티원 1·정가 전액을 그리면서 에러도 로딩도 띄우지 않는다.
5. **재시작 전까지 지속되는 이유**: `getBossProfitDb()`의 자가 복구는 `openBossProfitDb()`가 **reject할 때만** 동작한다. 에러 없이 멈춘 커넥션은 `dbPromise`에 그대로 캐시되어 세션 내내 반환된다.
6. **저장 데이터가 무사한 이유**: 같은 멈춤이 쓰기도 삼켜, 자동 기록 루프의 `party_size = 1` 덮어쓰기가 DB에 도달하지 못했다. **설계가 아니라 운이다** — 커넥션이 죽지 않고 느리기만 했다면 실제로 덮어써졌다.

**왜 인접 조합만·iOS만인가**: 인접 탭은 한 손으로 시차 0에 가깝게 누를 수 있어 WKWebView가 두 터치를 한 제스처로 보는 조건이 만들어진다(비인접은 손을 벌려야 해 자연히 시차가 벌어진다). 안드로이드는 `WebSettings`에서 확대가 꺼져 있어 Chromium이 페이지를 non-scalable로 보고 거리 기반 제스처 판정을 하지 않는 반면, iOS는 뷰포트 meta 기준으로 여전히 scalable이라(Capacitor는 핀치를 `scrollViewWillBeginZooming`에서 사후 취소할 뿐이다) 그 판정이 살아 있다. **이 설명은 정황이며 확정된 것은 아니다** — 확정된 것은 "클릭이 새고 문서가 리로드된다"까지다.

**결정**:

1. **하단 탭바의 클릭을 React 밖의 네이티브 캡처 리스너로 가로채, 어떤 경로로 들어온 클릭이든 문서 네비게이션이 되지 않게 한다.** `BottomTabBar`의 `<nav>`에 `addEventListener('click', handler, true)`로 직접 건다.
   - **React 안에서는 막을 수 없다.** `onClick`으로 `preventDefault()`를 해도 그 핸들러 자체가 안 도는 것이 문제다. 실제 DOM 리스너여야 한다 — 이번 계측의 `document` 캡처 리스너가 문제의 클릭을 잡아냈으므로 이 경로가 동작한다는 것은 확인된 사실이다.
   - **캡처 단계**라 React보다 먼저 돌고, `preventDefault()`가 먼저 걸리므로 React Router의 `Link`는 `if (!event.defaultPrevented)` 가드에 막혀 자기 네비게이션을 건너뛴다 — **이중 이동이 생기지 않는다.**
   - 리스너가 직접 `navigate(href)` 하므로 **탭 이동은 정상 동작한다.** 클릭을 죽이는 게 아니라 SPA 라우팅으로 되돌리는 것이다.
   - `<a href>`를 `<button>`으로 바꾸지 않는다 — 접근성 시맨틱(링크로 읽히는 것)을 유지하면서 같은 보호를 얻을 수 있다.

2. **`openBossProfitDb()`에 타임아웃을 걸어, 멈춘 커넥션에서도 자가 복구가 돌게 한다.** 초과하면 `dbPromise`를 비우고 에러를 전파해 **다음 호출이 처음부터 다시 열게** 한다. 지금은 reject 경로에만 복구가 있어 hang이면 영영 죽은 커넥션을 반환한다.
   - 결정 1이 이 증상의 리로드를 막지만, **우리가 막을 수 없는 리로드 경로가 iOS에 남는다** — `WebViewDelegationHandler.swift`는 WebKit 콘텐츠 프로세스가 죽으면 Capacitor가 **자동으로 `webView.reload()`** 한다. 앱 코드로 개입할 수 없다. 결정 2는 그 경우에 대한 유일한 방어다.

3. **조회가 실패했을 때는 자동 기록으로 기본 파티원 수를 덮어쓰지 않는다.** `getBossProfitRecords` 폴백을 `[]` 대신 `null`로 두어 **"조회 실패"와 "기록 없음"을 구분**하고, 실패면 자동 기록 루프를 건너뛴다.
   - 지금은 조회가 타임아웃되면 모든 행이 `partySize: null`이 되고, 이어지는 자동 기록이 `party_size = 1`·`payout = 정가 전액`으로 **사용자가 저장한 값을 덮어쓴다.** 이번 사고에서 DB가 무사했던 건 커넥션이 완전히 죽어 쓰기까지 막혔기 때문이며, 느리기만 한 커넥션에서는 실제 데이터 손상이 일어난다.

**이유**: 증상의 사슬은 `클릭 누출 → 문서 리로드 → stale 커넥션 → 조회 멈춤 → 폴백이 "없음"으로 위장`이다. 결정 1은 사슬의 시작을 끊고, 결정 2는 우리가 못 막는 리로드에 대비하며, 결정 3은 같은 멈춤이 **읽기 실패에서 그치지 않고 쓰기 손상으로 번지는 것**을 막는다. 세 지점 모두 독립적으로 실패할 수 있어 하나만으로는 부족하다.

**폐기된 가설 (조사 기록)**: 같은 함정을 다시 파지 않도록 남긴다.
- ~~보스+수익만 SQLite를 동시에 요구해 커넥션이 경합한다~~ → 컨텐츠 탭은 SQLite를 아예 안 쓰는데도 재현됨.
- ~~모든 네이티브 호출이 단일 스레드 큐를 공유해 포화된다~~ → 그러면 비인접 조합도 재현돼야 하는데 안 됨. 애초에 안드로이드 전용 논거였고 증상은 iOS 전용.
- ~~두 화면이 동시에 마운트돼 refresh가 이중으로 돈다~~ → 동시 마운트 자체는 테스트로 확인했으나(별도 tick이면 두 화면 모두 `loadTrackedOcids` 실행) 증상과 인과가 없음. 리로드가 실제 고리였다.
- ~~핀치로 확대되는지 확인하면 뷰포트 scalable 여부를 알 수 있다~~ → 판별력 0. Capacitor는 확대를 뷰포트가 아니라 `scrollViewWillBeginZooming`에서 사후 취소하므로 두 경우 모두 "확대 안 됨"으로 관측된다.

**트레이드오프**:
- 탭바 클릭 처리가 `NavLink`의 표준 경로에서 벗어난다. `NavLink`는 활성 스타일(`isActive`)·`aria-current`만 담당하고 **이동은 캡처 리스너가 책임진다** — 두 곳에 나뉘므로 탭바를 고칠 때 이 분담을 알아야 한다.
- 결정 2의 타임아웃 후 재시도는 **네이티브 브릿지 큐 자체가 막힌 경우엔 소용이 없다**(재시도 호출도 같은 큐에 선다). 그 경우 여전히 재시작이 필요하다. 다만 영구 무응답을 재시도 가능한 에러로 바꾸는 것만으로도 회복 가능성이 생긴다.
- 결정 3으로 조회 실패 시 자동 기록이 아예 안 일어난다 — 정상 상황에서 기록됐을 조합이 그 회차엔 안 남는다. 다음 새로고침에서 재시도되므로 유실이 아니라 지연이다.
- 이번 수정은 **하단 탭바에만** 적용한다. 화면 안의 다른 `<Link>`도 원리상 같은 누출이 가능하지만, 두 링크를 동시에 누를 수 있는 구조는 탭바뿐이라 관측된 범위에 맞춘다.

**저장소**: 스키마 변경 없음.
