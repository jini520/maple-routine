# ADR-186. 보스 목록의 순서는 **어디서나 `weekly-bosses.json` 정규 순서**다 — 비교자 하나가 네 자리를 덮는다

> 🟢 **구현 완료 (2026-08-30) · 실기기 미검증.** 사용자 지정: *"모든 장소에서 weekly-bosses.json의
> 순서를 따르도록 수정해."*
>
> 관련: [[ADR-036]](보스 수익의 정규 순서 — 이 결정이 그것을 앱 전체로 넓힌다) ·
> [[ADR-035]] 결정 20(수동 목록의 정규 순서) · [[ADR-164]] 결정 1·2(무리 순서·완료는 자리를 안 바꾼다) ·
> [[ADR-172]] 정정 1(가계부 타일 — **«큰 것부터» 한 줄이 여기서 죽는다**) · [[ADR-181]] 정정 1(today 의 **캐릭터 행** 순서는 그대로) ·
> [[ADR-006]](참조 데이터는 사용자 소유) · [[ADR-008]](매칭 실패는 원문 그대로).

## 배경 — 보스 목록이 서는 자리가 넷인데 기준이 넷이었다

조사(2026-08-30) 결과 같은 보스 무리가 화면마다 다른 차례로 서고 있었다.

| 자리 | 그때까지의 순서 |
|---|---|
| today 「남은 스케줄」 펼침 | 보스 스케줄러와 같음(같은 함수) |
| 보스 스케줄러 | **자동 = Nexon `boss_contents` 응답 순서**(정렬 코드 없음) · 수동 = 정규 순서 |
| 보스 수익 | 정규 순서 → 난이도 → 보스명([[ADR-036]]) |
| 가계부 결정석 타일 | **결정석 금액 내림차순**([[ADR-172]] 정정 1) |

곁들여 **주석 둘이 코드와 어긋나 있었다**. 이 ADR 이 둘 다 고친다.

- `displayed-bosses.ts` 의 `displayedBossSections` 머리 — *"자동 모드가 참조표 순서, 수동 모드가
  추적 순서"*. **정확히 반대**였다(수동만 정렬했다). 이 주석을 근거로 읽으면 다음 세션이
  «자동도 이미 정규 순서다» 라고 판단한다.
- `features/cashbook/records.ts` — 동액 타이브레이크가 *"조회 순서이고, 조회 순서는 [[ADR-036]] 이
  결정적으로 만든다"*. [[ADR-036]] 결정 4 는 **정반대로** «SELECT 에 `ORDER BY` 를 안 넣는다» 이고,
  그 대신 덮기로 한 애플리케이션 정렬(`sortRowsByOcidOrder`)을 **가계부 경로는 지나지 않는다.**

## 결정

1. **보스 목록의 순서는 앱 전체에서 하나다** — `weekly-bosses.json` 정규 순서
   (`REFERENCE_ENTRIES`: weekly → eventWeekly → monthly). 정렬 키도 [[ADR-036]] 결정 3 을 그대로
   쓴다: **참조 인덱스 → 난이도 인덱스(`BOSS_DIFFICULTIES`: 이지<노멀<하드<카오스<익스트림) → 보스명**.
   참조에 없는 보스([[ADR-008]] 매칭 실패 원문명)는 맨 뒤이고 그들끼리는 난이도·이름으로 갈린다.

2. **비교자는 `lib/boss-matching.ts` 의 `compareBossOrder` 하나다.** 정렬 규칙을 `REFERENCE_ENTRIES`
   의 **소유자**에 두고 네 소비자가 그것만 부른다 — [[ADR-036]] 결정 5 가 `manual-boss-merge.ts` 의
   사설 사본을 공용 함수로 흡수한 것과 **같은 태도**다. 지금 정렬 코드가 세 벌(수동 병합 · 보스 수익 ·
   가계부)이고, 자동 모드에 넷째를 새로 쓰면 값 하나를 바꿀 때 네 곳을 고쳐야 한다.

   ```
   lib/boss-matching.ts  compareBossOrder({boss, difficulty}, …)
     ├─ lib/manual-boss-merge.ts      (수동 목록 — 종전의 참조 인덱스 단독 정렬을 대체)
     ├─ features/boss-scheduler/displayed-bosses.ts  (신규 — 자동·수동 둘 다)
     ├─ features/boss-profit/rows.ts  (sortRowsByOcidOrder 의 2차 키 — 인라인이던 것을 대체)
     └─ features/cashbook/records.ts  (결정석 타일 — 금액 내림차순을 대체)
   ```

3. **자동 모드가 API 응답 순서를 버린다.** 정렬 자리는 `displayedBosses` 의 **끝**이고 **모드를 안
   가른다** — 수동 경로는 `mergeManualBossList` 가 이미 같은 순서로 내므로 멱등이고, 대신 이
   모듈의 «어느 순서로 내는가» 계약이 **한 줄**이 된다(모드 분기 안에 넣으면 다시 두 벌이다).

4. **가계부 결정석 타일이 «큰 것부터» 를 버린다** — [[ADR-172]] 정정 1 의 그 한 줄만 폐기다(정정
   1 의 나머지 — 그 자리에서 펼친다 · 읽기 전용 · 마리당 금액 없음 — 은 전부 유효). 정렬에만
   쓰이던 `BossDaySummary.bosses[].payoutMeso` 가 함께 사라진다.

5. **today 는 한 줄도 안 고친다.** 「남은 스케줄」의 보스 칩은 `displayedBosses` 를 그대로 부르므로
   결정 3 이 내려온다([[ADR-147]] 결정 8 이 둔 «같은 함수» 가 여기서 값을 한다). **캐릭터 행**
   순서는 [[ADR-181]] 정정 1 그대로다 — 그것은 보스 순서가 아니다.

6. **[[ADR-164]] 결정 1·2 는 그대로다.** 무리는 여전히 월간 → 주간이고, 완료는 여전히 자리를 안
   바꾼다. 이 결정이 채우는 것은 그 둘이 «전과 같다» 며 비워 둔 **무리 안**뿐이다.

7. **`storage/boss-profit.ts` 의 SELECT 에 `ORDER BY` 를 여전히 안 넣는다**([[ADR-036]] 결정 4 유지).
   결정 1~2 의 애플리케이션 정렬이 가계부 경로까지 덮어 DB 반환 순서가 표시에 무관해졌다 —
   `ORDER BY` 를 더하면 **같은 계약이 두 층에** 생긴다. 틀린 근거를 대던 주석만 사실로 고친다.

## 이유·트레이드오프

- **«같은 것은 같은 차례로 선다» 가 «이 화면에서 제일 큰 것» 보다 비싸다**(사용자 판정). 한
  사용자가 하루에 네 자리에서 같은 보스 무리를 본다 — 차례가 자리마다 다르면 그것이 같은 목록임을
  사람이 알아볼 수 없고, 화면을 옮길 때마다 눈이 목록을 처음부터 다시 읽는다.
- **대가는 가계부다.** «오늘 제일 큰 것이 무엇이었나» 를 타일 판에서 눈으로 못 찾는다([[ADR-172]]
  정정 1 이 «큰 것부터» 를 고른 근거가 그것이었다). 그 질문의 자리는 **보스 수익 탭**으로 남는다 —
  거기는 마리당 금액이 실제로 적혀 있어 눈으로 크기를 잴 수 있고, 타일 판은 애초에 금액을 안 적어
  «큰 것부터» 라는 사실 자체가 화면에 안 보였다(순서만으로 말하고 있었다).
- **자동 모드가 실제로 얼마나 바뀌는지는 모른다.** 참조표는 게임 진행 순서(자쿰 → … → 유피테르)라
  API 응답과 같을 가능성이 크지만, **API 순서를 못 박은 문서도 테스트도 없다**([[ADR-006]] 태도로
  추정하지 않는다). 확실한 것은 이제 **응답 순서가 무엇이든 화면이 안 흔들린다**는 것이다 —
  [[ADR-036]] 이 보스 수익에서 얻은 그 성질을 스케줄러도 갖는다.
- **미지의 보스 타이브레이크가 [[ADR-035]] 결정 20 을 덮는다.** 그 결정은 참조표 밖 보스끼리는
  «tracked 삽입 순서» 로 붙였는데, 공용 비교자는 난이도·이름으로 완전 결정한다. 수동 목록의 항목은
  보스 관리 화면이 참조표에서 고른 것이라 **실제로는 안 생기는 자리**이고(참조표에서 보스가 빠진
  뒤 남은 저장분뿐), 완전 결정성이 «두 벌 금지» 보다 값싸지 않다.
