### ADR-061: 로딩 표현 통일 — 스피너·진행률·문구의 자리별 배정 (구현 완료 2026-07-30 · S7 모달 차단만 보류)

**배경**: 로딩을 표시하는 자리를 전수 조사했다(2026-07-29). **표시하는 자리 20곳, 표시해야 하는데 안 하는 자리 7곳.** [[ADR-060]]이 빈 상태에서 정리한 것과 같은 문제가 로딩에 남아 있다 — 같은 성격의 대기가 자리마다 다른 모양으로 그려지고, 반대로 성격이 다른 대기가 같은 모양을 쓴다.

조사에서 드러난 갈래:

- **스피너가 2종 공존한다** — 공용 `MapleSpinner`(단풍잎 트레일 링) 6곳, 인라인 CSS 링(`border-t-primary animate-spin`) 1곳(`BossProfitScreen.tsx:1193`). 후자는 앱에서 유일한 비-브랜드 스피너다.
- **같은 작업이 3가지 표현을 쓴다** — "캐릭터 정보 예열"은 온보딩에서 `MapleWaveProgress`(단풍잎 물 채우기 + %), 계정 변경에서 얇은 진행률 바, 캐릭터 관리 저장에서 모달 안 얇은 바다. 셋 다 `(완료/전체)` 순차 호출이라는 같은 작업이다.
- **로딩인데 아무 표시도 없다** — 관리 화면 2곳은 로딩 중에 **빈 상태 문구**("캐릭터를 먼저 선택해주세요")를 띄운다. [[ADR-060]]이 금지한 "빈 상태로 위장"이 여기 남아 있었다.
- **문구 톤·말줄임표가 섞였다** — `~중...`(6곳)과 `~하고 있어요`(4곳), `...`(3점)과 `…`(1글자, `AppUpdateSection` 1곳)가 혼재한다.

#### 결정

**1. 스피너는 2종 — 크기로 나눈다.**

| 자리 | 크기 | 스피너 |
|---|---|---|
| 버튼 내부 | 16px | **`MapleSpinner`(트레일 링)** — 외곽선 둘레의 70% 구간이 도는 comet. 기존 컴포넌트 그대로 |
| 영역·화면·모달 | 24 / 32px | **`MapleSweepSpinner`(스윕)** — 흐린 잎 위로 밝은 띠가 **아래에서 위로** 훑고 지나간다 |

스윕은 신규 컴포넌트다. 잎 내부를 `clipPath`로 자르고 세로 그라디언트 띠(`transparent → currentColor → transparent`)를 `translateY`로 통과시킨다. `clipPath`의 직접 자식은 `<path>` 하나여야 한다 — `<g>` 래퍼로 묶으면 Chrome이 조용히 무시해 빈 클립이 된다(`MapleWaveProgress`에서 겪은 트랩).

시안 7종(트레일 링·드로잉·펄스·회전·낙엽·스윕·궤도)을 만들어 `/debug/loading`에서 16/24/32px로 비교한 뒤 위 둘을 골랐다.

**2. 콜드 스타트(S2)와 영역 부분 로딩(S4)은 같은 껍데기 — 셸 승계 카드.**

`components/LoadingState/`(신규). `rounded-[14px] border border-border bg-surface p-6` 안에 **스윕 스피너 + 문구**를 세로 중앙 정렬한다. 로딩이 끝나면 그 자리를 채울 카드와 같은 껍데기라 **결과가 들어와도 배경이 바뀌지 않는다.**

- **`size='page'`(스피너 32px)** — 스케줄러 3화면 콜드 스타트, 컨텐츠·보스 관리 화면 최초 진입
- **`size='inline'`(스피너 24px)** — 보스 수익 과거 기간 백필

**목록·카드가 들어올 자리에만 쓴다.** 모달 안(캐릭터 관리 피커)이나 화면 전체 대기(온보딩 시드)는 이미 자기 껍데기가 있거나 뒤에 카드가 오지 않으므로 카드를 씌우지 않고 **스피너 + 문구만** 둔다(스피너는 스윕으로 통일).

**3. 점선 박스는 로딩에 쓰지 않는다.** 보스 수익 백필의 `border-dashed` 점선 카드를 없앤다. 점선은 [[ADR-060]]이 빈 상태(`EmptyState`)의 어법으로 확정한 것이라, 로딩이 같은 껍데기를 쓰면 "확정된 빈 상태"와 구분되지 않는다([error-resilience.md](../foundation/error-resilience.md) 원칙 2).

**4. 앱에서 유일한 비-브랜드 스피너를 없앤다.** 보스 수익 백필의 인라인 CSS 링(`border-[3px] border-t-primary animate-spin`)을 스윕으로 교체한다. 이로써 앱의 모든 대기 표시가 단풍잎이 된다.

**5. 버튼 내부는 스피너 + 라벨 병기.** 온보딩·설정 구분 없이 모든 제출 버튼이 같은 형태다 — `MapleSpinner size={16}` + 라벨. 라벨을 남기는 이유는 파괴적 동작(캐시 삭제·연결 해제)에서 무엇이 진행 중인지 글자로 확인돼야 하기 때문이고, 그 규칙을 조회성 버튼까지 확대해 형태를 하나로 맞췄다. 접근성 계약(`aria-busy` + `disabled`)은 유지한다.

**6. 결정형 진행률은 전부 얇은 바(`h-1.5`) 하나.** 예열·저장·다운로드가 같은 프리미티브를 쓴다. `MapleWaveProgress`(물결형)와 `h-2` 변형은 **폐기**한다. design-system.md의 "진행률 바 프리미티브 재사용, 새 색·모양 신설 금지"를 그대로 지키는 쪽이다.

**7. 값 하나가 늦게 채워지는 자리는 `- KB` 자리표시.** 캐시 용량(설정 행·삭제 모달 그룹별) 두 곳. 조회 전에도 값과 같은 폭·타이포(`text-sm text-text-muted tabular-nums`)로 자리를 잡아 값이 들어와도 레이아웃이 밀리지 않는다.

**8. SWR 재검증은 현행 유지.** 캐시가 화면에 남아 있으면 스피너로 가리지 않는다([[ADR-016]]). `RefreshCw` 회전 + "조회 중..." 텍스트를 그대로 둔다. 새로고침 아이콘의 회전은 브랜드 장식이 아니라 **기능 신호**(아이콘 모양이 "새로고침"이라는 정보를 담는다)라 커스텀 스피너로 바꾸지 않는다.

**9. 문구 — 말줄임표가 붙는 `~중...`을 없앤다.**

- **말줄임표가 남는 곳은 새로고침 옆 `조회 중...` 한 곳뿐**이다(결정 8이 현행 유지로 확정한 자리).
- **버튼 내부는 말줄임표를 뺀 `~중`** — `확인 중` · `삭제 중` · `해제 중`. 폭이 좁아 `~하고 있어요`가 들어가지 않는다.
- **그 밖은 전부 `~하고 있어요`** — `불러오고 있어요`(콜드 스타트·백필) · `적용하고 있어요`(모드 전환) · `캐릭터 목록을 확인하고 있어요`(계정 검증) · `캐릭터 정보를 준비하고 있어요 (N/M)`(예열).
- 말줄임표는 `...`(마침표 3개)로 통일한다 — `AppUpdateSection`의 `…`(1글자) 1곳을 고친다.

**10. 로딩을 빈 상태로 위장하지 않는다.** 컨텐츠·보스 관리 화면이 로딩 중에 띄우던 빈 상태 문구("캐릭터를 먼저 선택해주세요")를 결정 2의 셸 카드로 바꾼다. 로딩이 끝나고도 캐릭터가 없을 때만 기존 문구를 보여준다.

#### 이유

- **스피너를 크기로 나눈 이유**: 스윕은 채워진 잎 위를 띠가 지나가는 몸짓이라 16px에서는 띠가 잎보다 커져 움직임이 안 읽히고, 바탕 잎(불투명도 0.32)만 남아 비활성처럼 보인다. 반대로 트레일 링은 32px에서 외곽선 한 줄이 도는 것뿐이라 큰 자리를 채우지 못한다. 두 크기 대역의 요구가 반대라 한 시안으로 덮이지 않았다.
- **스윕을 아래→위로 돌린 이유**: 결정 6이 `MapleWaveProgress`(잎 안에 물이 차오르던 결정형 진행률)를 폐기하는데, 차오르는 방향의 스윕이 그 감각을 비결정형 쪽에서 이어받는다. 위→아래는 "훑고 지나간다"에 가깝고 진행감이 없다.
- **셸 승계 카드를 고른 이유**: 스켈레톤을 도입하지 않고도 "자리를 미리 잡는다"는 효용을 얻는다. 로딩 카드와 결과 카드의 껍데기가 같으므로 전환이 배경 변화 없이 내용만 바뀐다.
- **버튼에 라벨을 남긴 이유**: 캐시 삭제는 최대 10초(`CLEAR_TIMEOUT_MS`) 걸리고 되돌릴 수 없다. 스피너만 도는 버튼은 "무엇이" 진행 중인지 말하지 않는다.
- **`~중...`을 없앤 이유**: 같은 대기를 두 어투로 말하고 있었다. 새로고침 옆만 남긴 것은 그 자리가 "마지막 동기화 3분 전"이라는 **시각 표시를 잠시 대체**하는 라벨이라 짧아야 하고, 실제로 폭이 좁기 때문이다.

---

#### 트레이드오프

- **`MapleWaveProgress`가 앱에서 사라진다.** 2026-07-22에 채택한 단풍잎 시안 3종(트레일 링·물결형·펄스형) 중 하나였고, `clipPath` 트랩을 풀어 만든 컴포넌트다. 결정 6으로 배치처를 전부 잃어 컴포넌트·CSS·테스트를 삭제한다. 차오르는 감각은 스윕이 승계하지만 **결정형 진행률에서 브랜드 마크가 없어지는 것**은 실제 손실이다.
- **스피너가 2종이라 "어디에 무엇을" 규칙을 매번 판단해야 한다.** 기준은 크기 하나(16px=트레일 링, 24px 이상=스윕)로 단순하지만, [[ADR-060]]이 빈 상태 마크를 page/inline으로 나눈 것과 같은 종류의 판단 비용이 로딩에도 생긴다.
- **버튼 폭이 상태에 따라 흔들린다.** `확인` → `확인 중`으로 라벨이 바뀌고 스피너가 붙는다. 폭 고정을 위해 최소 너비를 주면 평상시 버튼이 불필요하게 넓어져, 흔들림을 받아들였다.
- **온보딩에서 두 스피너가 연달아 나온다.** API 키 확인 버튼(트레일 링) → 체크리스트 준비 화면(스윕). `/debug/loading`의 "조합" 섹션에서 그 순서를 그대로 재현해 확인했고 어색하지 않다고 판단했지만, 어법이 다른 두 몸짓이 이어지는 것은 사실이다.

---

#### 보류·열린 질문

- **S7 모달 차단 작업은 보류.** 모드 전환(시드)·계정 검증·캐시 삭제 모달이 "진행 중임 표시 · 닫을 수 없음 전달 · 선택 맥락 유지" 세 요구를 어떻게 만족시킬지는 **모달 디자인 자체를 다시 한 뒤** 정한다. 검토했던 3안(상단 띠 + 본문 딤 / 스크림 오버레이 / 상태 줄 승계)은 현재 모달 골격을 전제로 그린 것이라 `/debug/loading`에 참고로만 남긴다. 그때까지 세 모달의 로딩 표현은 현행을 유지하되, 문구만 결정 9를 적용한다.
- **앱 부팅 상태 복원(조사 #23)** — `App.tsx`가 `restoreFromStorage()` 완료 전에 온보딩 API 키 폼을 렌더한다. 로딩 표시를 얹는 것보다 `OnboardingStatus`에 `'restoring'` 초기 상태를 두는 것이 근본 해결이라, 로딩 디자인이 아니라 상태 머신 변경이다. **이 ADR 범위 밖으로 두고 별건으로 뺀다.**
- **스켈레톤은 도입하지 않는다.** 결정 2(셸 승계)와 결정 7(`- KB`)이 "자리를 미리 잡는다"는 스켈레톤의 효용을 프리미티브 신설 없이 달성했다.
