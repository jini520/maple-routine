### ADR-061: 로딩 표현 통일 — 스피너·진행률·문구의 자리별 배정 (설계, 구현 전 — 선택지 제시 단계)

**배경**: 로딩을 표시하는 자리를 전수 조사했다(2026-07-29). **표시하는 자리 20곳, 표시해야 하는데 안 하는 자리 7곳.** [[ADR-060]]이 빈 상태에서 정리한 것과 같은 문제가 로딩에 남아 있다 — 같은 성격의 대기가 자리마다 다른 모양으로 그려지고, 반대로 성격이 다른 대기가 같은 모양을 쓴다.

조사에서 드러난 갈래:

- **스피너가 2종 공존한다** — 공용 `MapleSpinner`(단풍잎 트레일 링) 6곳, 인라인 CSS 링(`border-t-primary animate-spin`) 1곳(`BossProfitScreen.tsx:1193`). 후자는 앱에서 유일한 비-브랜드 스피너다.
- **같은 작업이 3가지 표현을 쓴다** — "캐릭터 정보 예열"은 온보딩에서 `MapleWaveProgress`(단풍잎 물 채우기 + %), 계정 변경에서 얇은 진행률 바, 캐릭터 관리 저장에서 모달 안 얇은 바다. 셋 다 `(완료/전체)` 순차 호출이라는 같은 작업이다.
- **로딩인데 아무 표시도 없다** — 관리 화면 2곳은 로딩 중에 **빈 상태 문구**("캐릭터를 먼저 선택해주세요")를 띄운다. [[ADR-060]]이 금지한 "빈 상태로 위장"이 여기 남아 있었다.
- **문구 톤·말줄임표가 섞였다** — `~중...`(6곳)과 `~하고 있어요`(4곳), `...`(3점)과 `…`(1글자, `AppUpdateSection` 1곳)가 혼재한다.

#### 1차 선택 (2026-07-30, 잠정 — 확정 아님)

사용자가 아래를 골랐다. **최종안이 아니며, 각 항목은 "완료"라고 명시될 때까지 계속 다른 방향을 탐색한다.**

| 상황 | 선택 | 내용 |
|---|---|---|
| S1 버튼 내부 | **B** | 스피너 + 라벨 병기. 온보딩·설정 구분 없이 모든 제출 버튼이 같은 형태 |
| S2 콜드 스타트 | **A** | 스피너 32 + 문구. 스케줄러 3화면·관리 화면 2곳·앱 부팅 복원·온보딩 시드가 공유 |
| S3 SWR 재검증 | **A** | 현행 유지(텍스트 + `RefreshCw` 회전). 스피너를 쓰지 않는 유일한 로딩 자리 |
| S4 영역 부분 로딩 | **새 디자인** | 점선 박스를 버린다 — 점선은 빈 상태(`EmptyState`)의 어법이라 로딩과 겹쳤다 |
| S5 대량 순차 진행률 | **B** | 전부 얇은 바(`h-1.5`). **`MapleWaveProgress`(물결형)가 앱에서 사라진다** |
| S6 다운로드 진행률 | **A** | `h-1.5` 프리미티브로 통일, `h-2` 변형 폐기 |
| S7 모달 차단 | **새 디자인** | 진행 표시·차단 전달·선택 맥락 유지 세 가지를 동시에 만족시킬 것 |
| S8 값 지연 | **`- KB`** | 조회 전에도 같은 폭·타이포로 자리를 잡는다 |
| S9 문구 | — | **제거 대상은 말줄임표가 붙는 `~중...` 형태.** 버튼 내부처럼 좁은 자리는 말줄임표를 뺀 `~중`을 쓸 수 있고, 말줄임표가 살아남는 곳은 새로고침 옆 `조회 중...` 한 곳뿐 |
| S10 스피너 종수 | — | 독립 선택이 아니라 위 자리들에 **무엇을 넣을지**의 문제로 흡수 |

**이 선택이 만든 후속 과제**:

- S5-B로 `MapleWaveProgress`가 배치처를 잃는다. 컴포넌트를 삭제할지, 다른 자리를 찾을지 별도 판단이 필요하다(2026-07-22에 채택한 3종 시안 중 물결형이 여기 있었다).
- S1-B와 S9가 맞물린다 — 버튼에 라벨이 남으므로 어미를 정해야 한다. `확인 중`(말줄임표 없음)과 `확인하고 있어요` 두 안을 비교 중.
- S2-A·S4·S7이 모두 스피너를 쓰므로 **스피너 디자인 자체가 남은 핵심 변수**다(S10이 여기로 흡수된 이유). 16px(버튼)·24px(영역)·32px(화면·모달) 세 크기에서 동시에 성립해야 한다.

#### 스피너 시안 7종

`/debug/loading`에서 하나를 고르면 위 자리들이 전부 그 시안으로 다시 그려진다.

| 시안 | 몸짓 | 성격 |
|---|---|---|
| 트레일 링 | 외곽선 둘레의 70% 구간이 도는 comet | 현행. 16px에서 획이 얇아 약하다 |
| 드로잉 | 외곽선을 그렸다 지운다 | 큰 자리에서 잘 읽히고, 작은 자리에서는 거의 안 보인다 |
| 펄스 | 채워진 잎이 숨쉬고 뒤로 후광이 퍼진다 | 채워진 실루엣이라 작은 크기에서도 존재감이 있다 |
| 회전 | 잎 한 장이 자전한다 | 가장 보편적인 "로딩" 신호. 브랜드 마크가 그대로 읽힌다 |
| 낙엽 | 좌우로 기울며 살짝 흔들린다 | 조용하다. 로딩이 아니라 장식으로 읽힐 위험 |

| 궤도 | 작은 잎 3장이 원을 돌며 시차를 두고 밝아진다 | 점 3개 스피너의 단풍잎판. 작은 크기에서 잎 모양이 뭉갠다 |

#### 선택지 비교용 디버그 화면

**`/debug/loading`** (`src/app/LoadingPreview.tsx`, [[ADR-060]]의 `/debug/empty-states`와 같은 패턴 — 결정이 끝나면 라우트와 파일을 삭제한다). 각 자리를 실제로 놓일 프레임(헤더·목록·모달·설정 행) 안에 렌더하고, 결정형 진행률은 0→100%를 5초 주기로 반복 재생한다.

상단에 **스피너 시안 · 문구안 · 테마** 세 토글이 있고, 고른 조합이 아래 모든 자리에 즉시 적용된다. 1차 선택 이후 이 화면의 역할은 "선택지 나열"이 아니라 **"잠정 결정 위에서 스피너를 갈아끼워 보는 것"** 이다. 테마 전환은 이 화면에서만 적용되고 저장하지 않는다 — 스피너 색이 테마마다 달라지므로 [[ADR-060]]의 레테 대비 문제 같은 함정을 미리 본다.

아직 앱에 없는 후보(드로잉형·펄스형 스피너, 스켈레톤, 인디터미네이트 바)는 `LoadingPreview.tsx` 안에서만 정의한다 — 채택 전에 `index.css`를 오염시키지 않으려는 것이다. 채택 시 keyframe을 `index.css`로 옮기고(Tailwind v4는 `motion-reduce:`가 먹으려면 `@utility` 등록이 필요) 컴포넌트를 `src/components/`로 승격한다.

#### 결정할 것 — 상황별 선택지

로딩 자리를 세 축으로 나눈다: **(a) 진행률을 알 수 있나**(결정형/비결정형) · **(b) 자리 크기**(버튼 / 인라인 한 줄 / 영역 / 화면 / 모달) · **(c) 이미 보여줄 데이터가 있나**(SWR 재검증 / 콜드 스타트). 아래 9개 상황이 이 축의 조합이다.

**S1. 버튼 내부 대기** — 자리 #1·#3(스피너) vs #16·#17·#18(텍스트만)

같은 "제출 버튼을 눌러 기다리는" 자리인데 온보딩은 스피너, 설정은 텍스트다.

- **A. 전부 스피너로 통일** — `MapleSpinner size=18~20`이 라벨을 대체, `aria-busy` + `aria-label`로 상태 전달. 온보딩 2곳 방식을 설정 3곳으로 확대.
- **B. 스피너 + 라벨 병기** — `[⟳ 삭제 중...]`. 파괴적·되돌릴 수 없는 동작(캐시 삭제·연결 해제)은 무엇이 진행 중인지 글자로 남긴다. 버튼 폭이 상태에 따라 흔들린다.
- **C. 성격으로 나눈다** — 되돌릴 수 있는 조회성(API 키 확인·업데이트 확인)은 스피너, **파괴적 동작(캐시 삭제·연결 해제)은 라벨 병기**. A와 B를 자리 성격으로 가른다.
- **D. 현행 유지** — 온보딩=스피너(브랜드 노출 자리), 설정=텍스트(조용한 자리).

**S2. 콜드 스타트 — 보여줄 데이터가 아예 없음** — 자리 #11·#12·#13 (+ 미적용 #21·#22·#23)

- **A. `MapleSpinner size=32 text-primary` + 문구** — 온보딩 시드 화면(#6)과 같은 조합을 3개 스케줄러 화면과 관리 화면 2곳에 확대. 미적용 자리도 이걸로 메운다.
- **B. 스켈레톤(P8 신설)** — 카드 골격을 흐린 펄스로 미리 그린다. 로딩→데이터 전환에서 레이아웃 점프가 없고, 화면마다 골격이 달라 무엇을 기다리는지 전달된다. 화면별 골격 컴포넌트를 새로 만들어야 한다.
- **C. 텍스트만 유지 + 문구 통일** — 최소 변경. "불러오는 중..." 하나로 맞추고 미적용 자리 3곳에도 같은 한 줄을 넣는다.
- **D. A + B 혼합** — 목록형(스케줄러·관리 화면)은 스켈레톤, 단일 결과형(앱 부팅 복원)은 스피너.

**S3. SWR 재검증 — 캐시 데이터가 이미 화면에 있음** — 자리 #14 + #20

[[ADR-016]]은 "캐시가 있으면 재검증 중에도 계속 보여준다 — 스피너로 가리지 않는다"를 이미 확정했다. 남은 질문은 **헤더의 "조회 중..." 텍스트를 유지할지**다.

- **A. 현행 유지** — 텍스트 + `RefreshCw` 회전. 신호가 둘이라 확실하다.
- **B. 텍스트 제거, `RefreshCw` 회전만** — 마지막 동기화 시각("3분 전")이 "조회 중..."으로 바뀌며 헤더 폭이 흔들리는 문제가 사라진다. 회전만으로 충분한지가 쟁점.
- **C. 헤더 하단 인디터미네이트 바** — 페이지 헤더 아래 2px 바가 좌우로 흐른다. 신설 필요, 3화면 헤더가 이미 복잡하다([[ADR-047]]·[[ADR-049]]).

**S4. 영역 부분 로딩** — 자리 #19 (보스 수익 과거 기간 백필)

앱에서 유일한 비-브랜드 스피너다. 기간 화살표를 누를 때마다 반복해 뜨고, 끝나면 캐릭터 카드가 그 자리를 채운다. **1차 선택: 새 디자인** — 점선 박스는 빈 상태(`EmptyState`)의 어법이라 로딩과 겹쳤던 것이 문제였다([[ADR-060]]가 점선 한 줄 박스를 빈 상태로 확정했으므로 로딩이 같은 껍데기를 쓰면 안 된다).

새 디자인 후보(`/debug/loading` S4):

- **A. 셸 승계** — 로딩 후 나타날 캐릭터 카드와 같은 **실선 `bg-surface` 카드**. 카드가 자리를 먼저 잡아 결과가 들어와도 화면이 튀지 않는다.
- **B. 알약** — 스피너와 문구를 한 줄 배지(`rounded-full bg-surface-2`)로 묶어 중앙에. 높이가 낮아 기간을 연달아 넘겨도 화면 요동이 가장 적다.
- **C. 맨몸** — 테두리도 배경도 없이 스피너 + 문구만. 가장 조용하지만 "무엇을 기다리는지"를 문구 혼자 감당한다.

~~A. `MapleSpinner size=24`로 교체 / B. 스켈레톤 카드 / C. 현행 유지~~ (점선 유지를 전제한 1차 선택지 — 폐기)

**S5. 결정형 진행률 — 대량 순차 작업** — 자리 #7·#8·#9

세 자리 모두 `(완료/전체)` 순차 API 호출이라는 같은 작업인데 표현이 셋이다.

- **A. 전부 `MapleWaveProgress`** — 온보딩의 감각을 계정 변경·저장 모달까지 확장. 모달 안에 64px 마크가 들어가 밀도가 올라간다.
- **B. 전부 얇은 바(P3)** — design-system.md의 "진행률 바 프리미티브 재사용, 새 모양 신설 금지"에 가장 충실. 대신 온보딩 예열이 `MapleWaveProgress`를 잃어 브랜드 자리가 하나 줄어든다.
- **C. 자리 기준으로 나눈다** — **화면 전체를 차지하면 `MapleWaveProgress`, 모달·카드 안이면 얇은 바.** 현재 #7(화면)과 #9(모달)는 이미 이 규칙을 만족하고, **#8(계정 변경 예열)만 예외**다 — #8은 모달 안이므로 규칙상 현행 유지가 맞고, 손댈 곳이 없어진다.
- **D. C + 계정 변경을 화면으로 승격** — #8을 모달이 아니라 온보딩과 같은 전체 화면 단계로 바꾸고 `MapleWaveProgress`를 쓴다. 범위가 로딩 디자인을 넘어 계정 변경 플로우 개편이 된다.

**S6. 결정형 진행률 — 다운로드** — 자리 #10 + 미적용 #27

- **A. `h-1.5` 프리미티브로 통일** — P4 변형을 없앤다. 모달에서 바가 얇아진다.
- **B. 현행 `h-2` 유지 + 프리미티브에 크기 변형을 문서화** — "모달 주역이면 `h-2`, 보조면 `h-1.5`"를 design-system.md에 명시.
- **C. `MapleWaveProgress`** — 업데이트 모달은 앱을 대표해 말을 거는 자리라 브랜드 마크가 어울린다. S5-A와 짝을 이룬다.

**S7. 모달 차단 작업(닫을 수 없음)** — 자리 #5(스피너+문구) vs #15(문구만) vs #26(버튼 라벨만)

**1차 선택: 새 디자인.** 공통 요구는 세 가지다 — **진행 중임이 보이고 · 닫을 수 없음이 전달되고 · 무슨 선택을 하던 중이었는지 맥락이 사라지지 않을 것.** 기존 선택지 B(본문 전체 교체)는 세 번째를 잃어서 탈락했다.

새 디자인 후보(`/debug/loading` S7):

- **A. 상단 띠 + 본문 딤** — 카드 최상단에 인디터미네이트 띠, 선택지는 흐려져 맥락만 남는다. 카드 크기가 변하지 않아 모달이 튀지 않고, 스피너를 쓰지 않는다(띠가 모션을 담당).
- **B. 스크림 오버레이** — 카드 위에 반투명 층(`bg-surface/85 backdrop-blur`)을 덮고 그 위에 스피너 + 문구. 선택지가 비쳐 맥락이 남고, 덮개 자체가 "지금은 못 누른다"를 말한다.
- **C. 상태 줄 승계** — 액션 버튼이 있던 자리를 스피너 + 문구 한 줄이 그대로 이어받는다. 누를 것이 사라지는 것으로 차단을 말한다. 액션 버튼이 있는 모달(캐시 삭제)에만 성립하고, 버튼이 없는 모달(모드 전환)에는 적용할 자리가 없다.

**S8. 값 하나가 늦게 채워지는 자리** — 미적용 #24·#25

**1차 선택: `- KB`.** 조회 전에도 값과 같은 폭·타이포(`text-sm text-text-muted tabular-nums`)로 자리를 잡아 값이 들어와도 레이아웃이 밀리지 않는다. 애니메이션이 없어 설정 화면이 조용하고, 단위까지 미리 보여줘 "여기 용량이 들어올 자리"임이 읽힌다. 설정 행과 캐시 삭제 모달의 그룹별 용량 두 곳에 같이 적용한다.

~~A. 스켈레톤 칩 / B. `—` 표시 / C. `MapleSpinner size=14`~~ (1차 선택지 — 폐기, B의 변형으로 수렴)

**S9. 문구 규칙** (모든 자리에 걸리는 축)

현재 9종: "불러오는 중..." · "조회 중..." · "확인 중…" · "삭제 중..." · "해제하는 중..." · "적용하고 있어요" · "캐릭터 목록을 확인하고 있어요..." · "캐릭터 정보를 준비하고 있어요" · "체크리스트를 준비하고 있어요"

말줄임표도 `...`(3점)와 `…`(1글자, `AppUpdateSection` 1곳)로 갈렸다.

**1차 방향(사용자 지침)**: 제거 대상은 **말줄임표가 붙는 `~중...` 형태**다. 버튼 내부처럼 폭이 좁은 자리는 **말줄임표를 뺀 `~중`을 쓸 수 있다.** 말줄임표가 살아남는 곳은 **새로고침 옆 `조회 중...` 한 곳뿐**이다(S3-A로 현행 유지가 확정된 자리).

남은 선택은 버튼 라벨의 어미뿐이다(S1-B가 라벨을 남기기로 했으므로):

- **A. 버튼은 `~중`** (`확인 중` · `삭제 중` · `해제 중`) — 버튼 폭 변화가 적다. 톤이 두 갈래로 남는다.
- **B. 버튼도 `~하고 있어요`** (`확인하고 있어요` · `삭제하고 있어요`) — 톤이 한 갈래로 모이지만 라벨이 길어진다.

버튼 밖의 자리는 어느 안이든 `~하고 있어요`다: `불러오고 있어요`(콜드 스타트) · `적용하고 있어요`(모드 전환) · `캐릭터 목록을 확인하고 있어요`(계정 검증) · `캐릭터 정보를 준비하고 있어요 (N/M)`(예열).

정리 항목(선택지 아님): `AppUpdateSection`의 `…`(1글자) 1곳을 없앤다.

**S10. 스피너 종류를 몇 개 둘 것인가** (S1·S2·S4·S7의 상위 질문)

**1차 판단: 독립 선택이 아니다.** "어디에 어떤 스피너를 쓸지"가 곧 이 질문이므로, S1(버튼 16px)·S2(화면 32px)·S4(영역 24px)·S7(모달 32px)에 무엇을 넣을지가 정해지면 자동으로 답이 나온다. 그래서 위 "스피너 시안 7종"을 만들어 **한 시안을 고르면 네 자리가 모두 그 시안으로 바뀌는** 방식으로 비교한다. 한 시안이 세 크기를 모두 통과하면 1종, 그렇지 않으면 크기·대기 길이로 나누는 안이 다시 살아난다.

~~A. 1종만 유지 / B. 크기로 2종 / C. 대기 길이로 2종~~ (자리별 배정이 정해진 뒤 다시 판단)

**열린 질문**

- **`MapleWaveProgress`(물결형)의 거취** — S5-B·S6-A로 배치처를 전부 잃었다. 컴포넌트·CSS·테스트를 삭제할지, 다른 자리를 찾을지 판단이 필요하다(2026-07-22 채택 3종 시안 중 하나였다).
- **스켈레톤(P8) 도입 여부** — S2-A·S4·S8이 모두 스켈레톤을 쓰지 않는 쪽으로 1차 선택돼, 현재로선 도입 근거가 없다. S4 후보 A(셸 승계)가 채택되면 "카드 셸을 먼저 그린다"는 스켈레톤의 효용 일부를 스켈레톤 없이 얻는다.
- **#23(앱 부팅 복원)** — 로딩 표시를 넣는 것보다 온보딩 상태 머신에 `'restoring'` 상태를 추가하는 편이 근본 해결이다. 이 ADR 범위에 넣을지, 별건으로 뺄지.
- 이 문서는 **선택지 제시 단계**다. 1차 선택은 잠정이며, 각 항목이 "완료"로 확정될 때까지 다른 방향을 계속 탐색한다. 전부 확정되면 결정 본문으로 다시 쓰고 `docs/foundation/design-system.md`에 "로딩 표현" 섹션으로 옮긴다.
