### ADR-061: 로딩 표현 통일 — 스피너·진행률·문구의 자리별 배정 (설계, 구현 전 — 선택지 제시 단계)

**배경**: 로딩을 표시하는 자리를 전수 조사했다(2026-07-29). **표시하는 자리 20곳, 표시해야 하는데 안 하는 자리 7곳.** [[ADR-060]]이 빈 상태에서 정리한 것과 같은 문제가 로딩에 남아 있다 — 같은 성격의 대기가 자리마다 다른 모양으로 그려지고, 반대로 성격이 다른 대기가 같은 모양을 쓴다.

조사에서 드러난 갈래:

- **스피너가 2종 공존한다** — 공용 `MapleSpinner`(단풍잎 트레일 링) 6곳, 인라인 CSS 링(`border-t-primary animate-spin`) 1곳(`BossProfitScreen.tsx:1193`). 후자는 앱에서 유일한 비-브랜드 스피너다.
- **같은 작업이 3가지 표현을 쓴다** — "캐릭터 정보 예열"은 온보딩에서 `MapleWaveProgress`(단풍잎 물 채우기 + %), 계정 변경에서 얇은 진행률 바, 캐릭터 관리 저장에서 모달 안 얇은 바다. 셋 다 `(완료/전체)` 순차 호출이라는 같은 작업이다.
- **로딩인데 아무 표시도 없다** — 관리 화면 2곳은 로딩 중에 **빈 상태 문구**("캐릭터를 먼저 선택해주세요")를 띄운다. [[ADR-060]]이 금지한 "빈 상태로 위장"이 여기 남아 있었다.
- **문구 톤·말줄임표가 섞였다** — `~중...`(6곳)과 `~하고 있어요`(4곳), `...`(3점)과 `…`(1글자, `AppUpdateSection` 1곳)가 혼재한다.

#### 선택지 비교용 디버그 화면

아래 선택지는 **`/debug/loading`** 에서 실제 모션으로 비교한다(`src/app/LoadingPreview.tsx`, [[ADR-060]]의 `/debug/empty-states`와 같은 패턴 — 결정이 끝나면 라우트와 파일을 삭제한다). 각 선택지를 실제로 놓일 자리와 비슷한 프레임(헤더·목록·모달·설정 행) 안에 렌더하고, 결정형 진행률은 0→100%를 5초 주기로 반복 재생한다. 상단에서 4테마를 전환할 수 있다(이 화면에서만 적용되고 저장하지 않는다 — 스피너 색이 테마마다 달라지므로 [[ADR-060]]의 레테 대비 문제 같은 함정을 미리 본다).

아직 앱에 없는 후보(드로잉형·펄스형 스피너, 스켈레톤, 인디터미네이트 바)는 `LoadingPreview.tsx` 안에서만 정의한다 — 채택 전에 `index.css`를 오염시키지 않으려는 것이다. 채택 시 keyframe을 `index.css`로 옮기고(Tailwind v4는 `motion-reduce:`가 먹으려면 `@utility` 등록이 필요) 컴포넌트를 `src/components/`로 승격한다.

#### 결정할 것 — 상황별 선택지

로딩 자리를 세 축으로 나눈다: **(a) 진행률을 알 수 있나**(결정형/비결정형) · **(b) 자리 크기**(버튼 / 인라인 한 줄 / 영역 / 화면 / 모달) · **(c) 이미 보여줄 데이터가 있나**(SWR 재검증 / 콜드 스타트). 아래 9개 상황이 이 축의 조합이다.

---

**S1. 버튼 내부 대기** — 자리 #1·#3(스피너) vs #16·#17·#18(텍스트만)

같은 "제출 버튼을 눌러 기다리는" 자리인데 온보딩은 스피너, 설정은 텍스트다.

- **A. 전부 스피너로 통일** — `MapleSpinner size=18~20`이 라벨을 대체, `aria-busy` + `aria-label`로 상태 전달. 온보딩 2곳 방식을 설정 3곳으로 확대.
- **B. 스피너 + 라벨 병기** — `[⟳ 삭제 중...]`. 파괴적·되돌릴 수 없는 동작(캐시 삭제·연결 해제)은 무엇이 진행 중인지 글자로 남긴다. 버튼 폭이 상태에 따라 흔들린다.
- **C. 성격으로 나눈다** — 되돌릴 수 있는 조회성(API 키 확인·업데이트 확인)은 스피너, **파괴적 동작(캐시 삭제·연결 해제)은 라벨 병기**. A와 B를 자리 성격으로 가른다.
- **D. 현행 유지** — 온보딩=스피너(브랜드 노출 자리), 설정=텍스트(조용한 자리).

**S2. 콜드 스타트 — 보여줄 데이터가 아예 없음** — 자리 #11·#12·#13 (+ 미적용 #21·#22·#23)

- **A. `MapleSpinner size=32 text-primary` + 문구** — 온보딩 시드 화면(#6)과 같은 조합을 3개 스케줄러 화면과 관리 화면 2곳에 확대. 미적용 자리도 이걸로 메운다.
- **B. 스켈레톤(P8 신설)** — 카드 골격을 흐린 펄스로 미리 그린다. 로딩→데이터 전환에서 레이아웃 점프가 없고, 화면마다 골격이 달라 무엇을 기다리는지 전달된다. 화면별 골격 컴포넌트를 새로 만들어야 한다.
- **C. 텍스트만 유지 + 문구 통일** — 최소 변경. "불러오는 중..." 하나로 맞추고 미적용 자리 3곳에도 같은 한 줄을 넣는다.
- **D. A + B 혼합** — 목록형(스케줄러·관리 화면)은 스켈레톤, 단일 결과형(앱 부팅 복원)은 스피너.

**S3. SWR 재검증 — 캐시 데이터가 이미 화면에 있음** — 자리 #14 + #20

[[ADR-016]]은 "캐시가 있으면 재검증 중에도 계속 보여준다 — 스피너로 가리지 않는다"를 이미 확정했다. 남은 질문은 **헤더의 "조회 중..." 텍스트를 유지할지**다.

- **A. 현행 유지** — 텍스트 + `RefreshCw` 회전. 신호가 둘이라 확실하다.
- **B. 텍스트 제거, `RefreshCw` 회전만** — 마지막 동기화 시각("3분 전")이 "조회 중..."으로 바뀌며 헤더 폭이 흔들리는 문제가 사라진다. 회전만으로 충분한지가 쟁점.
- **C. 헤더 하단 인디터미네이트 바** — 페이지 헤더 아래 2px 바가 좌우로 흐른다. 신설 필요, 3화면 헤더가 이미 복잡하다([[ADR-047]]·[[ADR-049]]).

**S4. 영역 부분 로딩** — 자리 #19 (보스 수익 과거 기간 백필)

앱에서 유일한 비-브랜드 스피너다. 기간 이동 때마다 반복해서 보이는 자리라는 점이 판단 근거다.

- **A. `MapleSpinner size=24`로 교체** — 스피너 종류를 1종으로 단일화. 앱 전체에서 "대기 = 단풍잎"이 성립한다.
- **B. 스켈레톤 카드(P8)** — 백필 후 나타날 캐릭터 카드 골격을 미리 그린다. S2-B를 채택하면 같은 프리미티브를 재사용.
- **C. 현행 유지** — 중립 링이 브랜드 마크보다 덜 튄다. 좌우 화살표로 기간을 넘길 때마다 뜨는 자리라 브랜드 마크가 반복되면 피로해진다.

**S5. 결정형 진행률 — 대량 순차 작업** — 자리 #7·#8·#9

세 자리 모두 `(완료/전체)` 순차 API 호출이라는 같은 작업인데 표현이 셋이다.

- **A. 전부 `MapleWaveProgress`** — 온보딩의 감각을 계정 변경·저장 모달까지 확장. 모달 안에 64px 마크가 들어가 밀도가 올라간다.
- **B. 전부 얇은 바(P3)** — design-system.md의 "진행률 바 프리미티브 재사용, 새 모양 신설 금지"에 가장 충실. 대신 온보딩 예열이 `MapleWaveProgress`를 잃어 브랜드 자리가 하나 줄어든다.
- **C. 자리 기준으로 나눈다** — **화면 전체를 차지하면 `MapleWaveProgress`, 모달·카드 안이면 얇은 바.** 현재 #7(화면)과 #9(모달)는 이미 이 규칙을 만족하고, **#8(계정 변경 예열)만 예외**다 — #8은 모달 안이므로 규칙상 현행 유지가 맞고, 손댈 곳이 없어진다.
- **D. C + 계정 변경을 화면으로 승격** — #8을 모달이 아니라 온보딩과 같은 전체 화면 단계로 바꾸고 `MapleWaveProgress`를 쓴다. 범위가 로딩 디자인을 넘어 계정 변경 플로우 개편이 된다.

**S6. 결정형 진행률 — 다운로드** — 자리 #10 + 미적용 #27

- **A. `h-1.5` 프리미티브로 통일** — P4 변형을 없앤다. 모달에서 바가 얇아진다.
- **B. 현행 `h-2` 유지 + 프리미티브에 크기 변형을 문서화** — "모달 주역이면 `h-2`, 보조면 `h-1.5`"를 design-system.md에 명시.
- **C. `MapleWaveProgress`** — 업데이트 모달은 앱을 대표해 말을 거는 자리라 브랜드 마크가 어울린다. S5-A와 짝을 이룬다.

**S7. 모달 차단 작업(닫을 수 없음)** — 자리 #5(스피너+문구) vs #15(문구만) vs #26(버튼 라벨만)

- **A. `MapleSpinner size=18` + 문구로 통일** — `TrackingModeModal`(#5) 방식을 계정 변경 검증·캐시 삭제에 확대.
- **B. 모달 본문 전체를 로딩 상태로 교체** — 진행 중에는 선택지를 감추고 스피너 + 문구만 남긴다. "지금은 못 누른다"가 가장 명확하지만 취소 경로도 함께 사라진다.
- **C. 현행 유지 + 문구만 정리** — 표현은 그대로 두고 S9의 문구 규칙만 적용.

**S8. 값 하나가 늦게 채워지는 자리** — 미적용 #24·#25

- **A. 스켈레톤 칩** — `h-4 w-12 rounded bg-surface-2 animate-pulse`. 자리를 미리 잡아 레이아웃 점프가 없다. P8을 가장 싸게 도입하는 지점.
- **B. 자리만 예약하고 `—` 표시** — 애니메이션 없이 점프만 막는다. 가장 조용하다.
- **C. `MapleSpinner size=14`** — 작은 자리에 브랜드 마크. 설정 화면 행마다 단풍잎이 돌면 과할 수 있다.

**S9. 문구 규칙** (모든 자리에 걸리는 축)

현재 9종: "불러오는 중..." · "조회 중..." · "확인 중…" · "삭제 중..." · "해제하는 중..." · "적용하고 있어요" · "캐릭터 목록을 확인하고 있어요..." · "캐릭터 정보를 준비하고 있어요" · "체크리스트를 준비하고 있어요"

말줄임표도 `...`(3점)와 `…`(1글자, `AppUpdateSection` 1곳)로 갈렸다.

- **A. 전부 "~하고 있어요"체** — 앱 전반의 존댓말 톤([[ADR-060]] 빈 상태 문구·업데이트 모달과 일치). 버튼 안에서는 길다.
- **B. 전부 "~중..."체** — 짧아 좁은 자리에 유리. 온보딩·모달의 따뜻한 톤이 사라진다.
- **C. 자리 기준으로 나눈다** — **버튼·헤더처럼 폭이 좁은 자리는 "~중...", 화면·모달처럼 넓은 자리는 "~하고 있어요".** 현재 분포와 대체로 맞아 변경량이 가장 적다.
- 어느 안이든 **말줄임표는 `...`(3점)로 통일**하고 `AppUpdateSection`의 `…` 1곳을 고친다(이건 선택지가 아니라 정리 항목).

**S10. 스피너 종류를 몇 개 둘 것인가** (S1·S2·S4의 상위 질문)

2026-07-22에 단풍잎 시안 3종(드로잉형·물결형·펄스형)을 채택했지만, 실제로 배치된 건 트레일 링(`MapleSpinner`) + 물결형(`MapleWaveProgress`) 둘뿐이고 드로잉형·펄스형은 배치처가 없다(P9).

- **A. 1종만 유지** — 비결정형은 전부 트레일 링. 드로잉형·펄스형은 폐기. 앱 전체가 한 몸짓으로 대기를 말한다.
- **B. 2종 — 크기로 나눈다** — 작은 자리(버튼·인라인, ≤20px)는 트레일 링, 큰 자리(화면·영역, ≥32px)는 드로잉형. 큰 자리에서 외곽선이 그려지는 동작이 더 읽힌다.
- **C. 2종 — 성격으로 나눈다** — 짧은 대기(1초 내외)는 트레일 링, 긴 대기(수 초~수십 초, 시드·백필·캐시 삭제)는 펄스형. 오래 봐도 덜 피로한 몸짓을 긴 쪽에 둔다.
