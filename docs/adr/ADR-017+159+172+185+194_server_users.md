# ADR-017+159+172+185+194 서버의 사용자와 신원 · 로그아웃과 계정 삭제 · 키 사용자 합치기 · 추천인 코드

> 🟢 유효
> 옛 번호: ADR-299 결정 3 · ADR-340 결정 2 · 3 · 4 · 5 · 7 · 8 · 정정 1 · 2 · 2-1 · 3 · 5 · ADR-347 결정 18
> 관련 소스: `features/auth/server-identity.ts` · `features/auth/store.ts` · `lib/crypto/api-key-hash.ts` · `features/server-sync/forget.ts` · `features/auth/account-deletion.ts` · `server/account-deletion.ts` · `app/settings/SettingsAboutScreen.tsx` · `app/settings/SignOutConfirm.tsx` · `app/settings/DeleteAccountConfirm.tsx` · `app/auth/AccountDeletionPrompt.tsx` · 서버 `modules/users/` · `modules/identity/`

## 배경

서버가 사용자가 보낸 값을 받으려면 누가 보낸 값인지 가려야 한다. 처음 받은 것은 드롭 가격이었고, 1.0.15 부터는 기기 간
동기화로 사용자가 만든 기록 전부를 받는다([[ADR-099]]). 앱 사용자는 두 부류다. 넥슨으로 로그인한 사용자와, 자기 API 키만 넣은
사용자다. 로그인 사용자는 넥슨이 신원을 보증하지만, 키 사용자는 서버가 키를 본 적이 없어 신원을 확인할 방법이 없다. 이 문서는
두 부류를 서버의 표에 어떻게 담고, 요청마다 무엇으로 사람을 찾는지 정한다.
그리고 넥슨 로그인이 들어가면서 스토어가 요구하는 계정 삭제와, 그와 짝을 이루는 로그아웃을 정한다. 키 사용자가 넥슨 로그인으로
바꿀 때 두 사람을 하나로 합치는 일과, 넥슨 로그인 계정마다 추천인 코드를 주는 일도 여기서 정한다.

## 결정

### 결정 1. 사람은 `users` 에 두고, 열쇠는 넥슨 계정 표 `nexon_accounts` 에 둔다

```
users            id · created_at · deletion_requested_at
nexon_accounts   id · user_id · uid_hash(UNIQUE) · referral_code(UNIQUE) · created_at · updated_at   넥슨 ID 하나
maple_ids        id · nexon_account_id · hash(UNIQUE) · created_at                                    메이플 ID 하나
```

`uid_hash` 와 `hash` 에는 원문이 아니라 해시가 들어간다(결정 11). API 키를 담는 표는 두지 않는다. 앱이 키도 키 해시도 보내지
않기 때문이다(결정 4, [[ADR-099]] 결정 62).

한 사람이 넥슨 계정을 여럿 가질 수 있어 열쇠를 사람 표의 칸으로 두지 않고 계정 표의 줄로 둔다([[ADR-101]]).
넥슨 계정 줄은 넥슨 ID 하나에 하나다. 같은 넥슨 ID 의 로그인과 키는 한 줄이다. 같은 넥슨 ID 인지는 메이플 ID 로 가린다([[ADR-101]]
결정 25). 키를 다시 받아도 메이플 ID 는 그대로라 줄이 늘지 않는다.

기록 표에는 열쇠를 담지 않는다. 기록은 캐릭터 줄 · 메이플 ID 줄 · 넥슨 계정 줄을 가리키고([[ADR-099]] 결정 8 · 20 · 48), 드롭
판매가와 사용 로그는 사람(`user_id`)을 가리킨다. 기록 표에 열쇠를 직접 담으면 열쇠가 바뀔 때마다 기록 표를 모두 고쳐야 하고,
하나를 빠뜨리면 그 기능만 조용히 끊긴다.

넥슨 `uid` 는 플랫폼이 달라도 같다(2026-10-12 실측). 넥슨 애플리케이션이 iOS 와 안드로이드로 따로 등록돼
`client_id` 가 다르지만, 같은 넥슨 계정이면 두 플랫폼에서 받은 `uid` 가 같았다. 그래서 안드로이드에서 쓰던 사람이
아이폰에서 로그인하면 같은 `users` 행에 세션이 하나 더 붙는다. 세션은 저마다 자기 플랫폼의 자격 쌍으로 갱신한다.

### 결정 2. 세션은 사람을 가리키는 표이고, 사람이 먼저 생긴다

`nexon_sessions.user_id` 는 `users` 를 가리키고 `NOT NULL` 이다. 로그인 콜백이 `uid` 로 기존 사람을 찾거나 새로
만든 다음에 세션을 만든다. 세션은 갱신 토큰이 만료되거나, 넥슨이 갱신을 거절하거나, 사용자가 로그아웃하면
지워진다. 모두 정상 동작이다. 세션이 지워질 때 사람도 함께 지우면 정상 동작 때문에 데이터를 잃게 된다. 그래서 세션이
지워져도 사람은 남는다.

### 결정 3. 키 사용자의 기록도 받고, 키 사용자의 신원은 확인하지 않는다

넥슨 로그인 사용자와 API 키 사용자 모두의 기록을 받고 돌려준다(사용자 지정 2026-11-10, [[ADR-099]] 결정 1).

키 사용자의 신원은 확인할 수 없다. 확인하려면 서버가 키 원문을 받아 넥슨에 물어봐야 하는데, 그것은 이용자가
키를 남에게 주는 일이라 넥슨 이용약관 제5조 ①·② 에 걸린다. 그래서 키 사용자를 밝히는 메이플 ID 해시(결정 5)는 신원의 증명이
아니라, 같은 넥슨 계정이 보낸 기록을 묶고 계정을 삭제할 때 그 사람의 줄을 찾는 데만 쓴다.

그 해시로 그 넥슨 계정의 기록을 보내고 받는다(사용자 지정 2026-11-10). 서버는 API 키 사용자가 알려 온 메이플 ID 를 넥슨에 확인하지
않으므로([[ADR-101]] 결정 25), 남의 메이플 ID 를 아는 사람은 그 계정인 척 기록을 보내거나 그 계정의 기록을 받을 수 있다. 메이플 ID 는
그 계정의 키나 로그인으로만 얻을 수 있어, 남이 안다면 주인이 넘겼거나 해킹당한 경우이고 우리가 막을 수 없다(사용자 판단 2026-11-10).

로그인으로 보낸 기록인지 키로 보낸 기록인지는 기록 줄에 적지 않는다(사용자 지정 2026-11-18). 기록의 값이 아니라 사람의 값이라
넥슨 계정 줄에 `uid_hash` 가 있는지로 읽는다([[ADR-099]] 결정 8). 틀린 값이 섞이지 않게 막는 일은 신원 확인이 아니라 입력 검사와
집계 때의 이상치 제거가 맡는다. 로그인 사용자도 틀린 값은 보낼 수 있기 때문이다.

### 결정 4. API 키는 원문도 해시도 서버에 보내지 않는다

앱은 API 키를 서버에 보내지 않는다. 원문을 보내면 이용자가 키를 남에게 주는 일이 된다(결정 3). 키의 해시도 보내지 않는다. 키는
다시 받으면 값이 바뀌어 같은 사람을 잇지 못하므로, 키 사용자는 메이플 ID 해시로 밝힌다(결정 5). 서버에는 키를 담는 표가 없다
([[ADR-099]] 결정 62).

앱은 키의 SHA-256 을 기기 안에서만 쓴다. 서버에 등록한 부계정 키를 Preferences `serverAccounts` 에 `로그인 계정 id:키 해시` 로
적어 두고, 같은 키를 다시 등록하지 않는다([[ADR-101]] 결정 14).

- 해시는 소문자 16진 64자다(`apiKeyHashHex`).
- Hermes 에 `crypto` 가 없어서 `@noble/hashes` 의 순수 JS 구현을 쓴다. 네이티브 모듈이었다면 스토어 빌드를 기다려야 했지만, 이
  방법은 OTA 로 나간다.

### 결정 5. 요청은 세션 아니면 메이플 ID 해시 하나로 사람을 밝힌다

| 헤더 | 서버가 사람을 찾는 방법 |
|---|---|
| `Authorization: Bearer <세션>` | 세션 해시로 행을 찾아 수명만 본다. 넥슨은 부르지 않는다. 찾으면 세션을 마지막으로 쓴 시각을 고친다 |
| `x-maple-id-hash: <소문자 16진 64자>` | 메이플 ID 표에서 그 메이플 ID 가 달린 넥슨 계정을 찾고, 없으면 사람 · 계정 줄 · 메이플 ID 줄을 만든다 |

- 로그인 없이 API 키로 쓰는 사람은 메이플 ID 해시로 밝힌다(사용자 지정 2026-11-17). 키가 넥슨 `character/list` 에서
  받은 메이플 ID 가운데 하나의 해시를 보낸다. API 키는 다시 받으면 값이 바뀌지만 메이플 ID 는 바뀌지 않는다. 키 해시로 밝히면 키를
  다시 받을 때마다 서버가 새 사람 · 계정 줄을 만들었다가 메이플 ID 가 겹치는 것을 보고 합쳐야 한다([[ADR-101]] 결정 25).
- 메이플 ID 원문(`account_id`)은 16진 32자다(2026-11-17 실측). 추측할 수 없는 길이라, 해시를 아는 것은 그 계정의 키나 로그인을
  가진 것과 같게 본다(결정 3). 메이플 ID 해시는 다른 사용자에게 가는 응답에 싣지 않는다.
- 키 해시 헤더(`x-api-key-hash`)는 받지 않는다. 그 헤더만 오면 401 이다. 1.0.14 까지의 앱이 보내던 헤더이고, 1.0.15 를 배포하면
  그 앱을 받지 않는다([[ADR-099]] 결정 43 · 64).

- 서버는 세션이 오면 세션만 보고 메이플 ID 해시는 읽지 않는다. 로그인한 사람의 기록이 키 쪽으로 나뉘면 한 사람으로 모은 의미가 없어진다.
- 세션이 죽었으면 메이플 ID 해시로 넘어가지 않고 401 이다. 넘어가면 같은 사람의 기록이 두 열쇠로 갈린다.
- 세션의 사람에게 로그인 계정 줄이 없으면 401 이다. 세션은 로그인 콜백이 로그인 계정 줄을 만든 뒤에만 생겨, 줄이 없으면 그 세션으로
  적을 넥슨 계정이 없다.
- 둘 다 없거나 형식이 틀리면 401 이다. 키 원문을 실어 보내면 길이가 맞지 않아 여기서 걸린다.
- 앱(`serverIdentityHeaders`)도 같은 규칙으로 하나만 싣는다. 세션이 있으면 Bearer 만, 없으면 메인 키의 메이플 ID 해시만 싣는다.
  키 해시는 싣지 않는다. 메인 키는 로그인 없이 쓰는 키다(`mainKeyId`, [[ADR-101]] 결정 5).
  - 메이플 ID 는 메인 키의 넥슨 계정에서 본 것(`character_accounts`) 가운데 정렬해 맨 앞의 것이다. 같은 키로 늘 같은 값을 보내야
    서버가 넥슨 계정 줄을 새로 만들었다가 합치지 않는다([[ADR-101]] 결정 25). 키를 넣으면 그 키의 목록이 그 넥슨 계정 id 로
    `character_accounts` 에 적혀, 넣은 직후부터 밝힐 수 있다.
  - 본 메이플 ID 가 없거나 세션과 메인 키가 모두 없으면 `null` 을 돌려줘 아무것도 보내지 않는다.
- 부계정 키로는 밝히지 않는다. 부계정은 넥슨 로그인 사용자만 등록하므로 그 사용자는 세션으로 밝혀진다. 세션은 그 로그인에
  등록된 부계정의 메이플 ID 에도 쓰고 읽는다([[ADR-101]] 결정 7). 로그인이 만료돼
  부계정 키만 남으면 밝힐 수단이 없어 보내지 않는다. 부계정 키를 메인으로 쓰지 않는 것과 같은 규칙이다.

이 헤더를 받는 경로는 `POST /v1/enhancement-anomalies` · `POST /v1/usage-events` · `DELETE /v1/me` ·
`GET /v1/me/deletion` · `DELETE /v1/me/deletion` · `PUT /v1/me/maple-ids` · `POST /v1/sync/pull` · `POST /v1/sync/push` ·
`POST /v1/sync/clear` 다. 부계정 경로(`/v1/me/sub-accounts`)는 세션으로 온 요청만 받고, 메이플 ID 해시로 오면 403(`login_required`)이다.
부계정은 넥슨 로그인 사용자만 등록하기 때문이다([[ADR-101]] 결정 1). 조회 경로는 공개 정보라 인증 없이 그대로 열려 있다.

### 결정 6. 계정 삭제는 30일 유예 뒤 사람과 열쇠와 동기화한 기록을 지우고, 통계에 쓰는 줄은 사람과의 연결만 끊어 남긴다

`DELETE /v1/me` 는 바로 지우지 않고 삭제를 예약한다. 유예기간은 30일이다(사용자 지정). 실수로 눌렀거나 마음이 바뀐 사람이
되돌릴 수 있게 한다.

```
users   id · created_at · deletion_requested_at   NULL 이 아니면 삭제 예약. 이 시각에서 30일 뒤 지운다
```

| 때 | 서버가 하는 일 |
|---|---|
| 요청(`DELETE /v1/me`) | `deletion_requested_at` 에 지금을 적고 그 사람의 세션을 모두 지운다. 이미 예약돼 있으면 처음 시각을 덮지 않는다 |
| 유예 중 쓰기 요청 | 403(`account_deletion_pending`)으로 거절한다. 지울 사람에게 새 기록이 붙지 않게 한다 |
| 유예 중 확인(`GET /v1/me/deletion`) | 예약 시각과 지울 날을 돌려준다. 예약이 없으면 `null` 이다 |
| 취소(`DELETE /v1/me/deletion`) | `deletion_requested_at` 을 비운다 |
| 30일 뒤 | 매일 04:40(KST)에 도는 일(서버 `AccountDeletionJob`)이 예약한 지 30일이 지난 사람의 `users` 행을 지운다. 그 사람에 딸린 줄은 외래키가 아래 표처럼 정리한다 |

- 세션은 요청 때 바로 지운다. 세션은 기록이 아니라 지금도 쓸 수 있는 자격 증명이라, 남기면 다른 기기의 로그인이 계속 쓰인다.
- 열쇠(`nexon_accounts` · `maple_ids`)는 유예가 끝날 때까지 남긴다. 열쇠가 있어야 같은 넥슨 로그인이나 같은 메이플 ID 로 돌아온
  사람을 찾아 취소를 물을 수 있다. 유예가 끝나 열쇠가 지워지면 그 사람을 다시 찾을 수 없다.

30일 뒤 지울 때 서버의 줄은 표마다 다르게 다룬다.

| 표 | 계정 삭제 때 | 이유 |
|---|---|---|
| 넥슨 계정 · 메이플 ID · 캐릭터 줄과, 그 줄을 주인으로 삼는 동기화 기록 전부([[ADR-099]] 결정 8 의 표) | 함께 지운다. 외래키가 `ON DELETE CASCADE` 다 | 같은 사람의 기기끼리 맞추려고 둔 기록이다([[ADR-099]] 결정 16). 캐릭터와 메이플 ID 를 가리키고 사용자가 친 메모도 들어 있어, 사람과의 연결만 끊어서는 누구의 기록인지 감출 수 없다 |
| `drop_sale_prices` · `usage_events` · `enhancement_anomalies` | 줄은 남기고 사람 칸만 비운다. 드롭 판매가와 사용 로그는 `user_id` 를, 강화 이상 보고는 `nexon_account_id` 를 비운다(`ON DELETE SET NULL`) | 시세 통계와 사용 통계가 사람이 나갈 때마다 흔들리면 안 된다(사용자 지정). 세 표에는 캐릭터와 메이플 ID 를 가리키는 칸이 없다. 판매가 줄에 남는 것은 아이템 · 월드 · 판매가 · 적은 시각이다([[ADR-099]] 결정 26) |

- 부계정 등록 · 추천받은 줄(결정 10) · 시세의 사람별 판정 수(`market_judgements`)도 함께 지워진다.
- 부계정으로 등록한 넥슨 계정은 지우지 않는다. 부계정의 넥슨 계정 줄은 자기 사람 줄을 따로 갖고([[ADR-101]] 결정 7), 메인 계정을
  지우면 등록만 지워진다([[ADR-101]] 결정 6). 그래서 부계정의 메이플 ID · 캐릭터 줄과 그 기록은 서버에 남는다.
- 같은 넥슨 로그인이나 같은 메이플 ID 로 다시 오면 새 사람이 된다. 서버는 지운 사람과 새 사람을 잇지 않는다. 다만 기기에 남은
  드롭을 다시 올리면, 같은 id 의 판매가 줄 가운데 사람 칸이 빈 줄에 새 사람이 채워진다([[ADR-099]] 결정 8). 드롭 id 는 그 기기가
  만든 uuid 라, 같은 id 를 든 요청은 같은 기록이기 때문이다. 계정 삭제는 기기의 기록을 지우지 않는다(결정 7).
- 운영자는 메일로 삭제를 요청받아도 그 사람을 찾을 수 없다. 서버가 가진 것은 되돌릴 수 없는 해시뿐이다. 그래서 삭제는 세션이나
  메이플 ID 해시를 보낼 수 있는 앱 안에서만 한다. 웹의 삭제 안내(`site/support.md`)는 앱에서 지우는 방법을 알려 준다(사용자 지정).

### 결정 7. 로그아웃은 기기의 인증 수단만 지우고, 계정 삭제는 서버에 예약한 뒤 로그아웃한다

로그아웃은 앱 데이터와 서버 데이터를 모두 남기고 로그인만 푼다(사용자 지정). 넥슨 로그인과 메인 키를 모두 뗀다. 넥슨 로그인만
떼는 로그아웃은 따로 두지 않는다(사용자 지정). 이름이 같은 행 둘이 서로 다른 일을 하면 무엇을 눌렀는지 알 수 없다. 넥슨 로그인에
귀속된 부계정 키는 남긴다. 같은 넥슨 ID 로 다시 로그인하면 부계정을 이어 쓰게 하려는 것이다([[ADR-101]] 결정 5).

```
로그아웃 (signOut)
1. 동기화를 한 번 돌려 남은 기록을 올린다. 세션을 거두기 전이어야 그 세션으로 올릴 수 있다
2. 로그인이 있으면 DELETE /v1/auth/nexon/session 으로 서버 세션을 거둔다. 기기에서 지우기 전이어야 세션 값이 있다
3. 사용 로그 표를 비운다. 대기 표는 남긴다
4. 기기에서 세션과 메인 키를 지우고 로그인 화면으로 간다. 넥슨 로그인에 귀속된 부계정 키는 남는다

계정 삭제 (deleteAccount)
1. DELETE /v1/me. 기기에서 키를 지우기 전이어야 서버가 사람을 찾는다
2. 실패하면 멈추고 알린다. 로그아웃하지 않는다
3. 성공하면 `30일 뒤 계정이 삭제돼요` 토스트를 띄우고 로그아웃 1 ~ 4

다시 로그인할 때 (checkAccountDeletion)
1. 로그인이나 키 입력이 끝나면 GET /v1/me/deletion 으로 예약을 묻는다. 앱을 켤 때도 한 번 묻는다
2. 예약이 있으면 `삭제 예정인 계정이에요` 확인 창을 띄운다. 지울 날을 보여 준다
3. `삭제 취소` 를 누르면 DELETE /v1/me/deletion 뒤 그대로 들어간다
4. `로그아웃` 을 누르면 로그아웃 1 ~ 4. 예약은 그대로다
```

- 로그아웃의 1번과 2번은 실패해도 진행한다. 기기에서 지우는 일이 본론이고, 서버 세션은 갱신 토큰 수명이 지나면 정리된다.
- 1번이 올리지 못한 기록은 대기 표에 남는다([[ADR-099]] 결정 14). 같은 사람이 다시 로그인하면 그 신원으로 올라가고, 다른 사람이
  로그인하면 버릴지 묻는다. 계정 삭제를 예약한 사람의 쓰기는 서버가 거절해, 계정 삭제의 1번은 아무것도 올리지 않는다.
- 3번에서 비우는 사용 로그는 못 보낸 것이다(사용자 지정). 사용 로그 표에는 누가 만든 줄인지 적혀 있지 않아, 남기면 다음에 다른 키로
  로그인한 사람의 신원으로 나간다. 기기의 기록 자체는 남는다.
- 계정 삭제는 서버가 예약했다고 답해야 로그아웃한다. 실패한 채로 로그아웃하면 사용자는 지워질 줄 알지만 서버에는 예약이 없다.
- 요청 직후 바로 로그아웃한다(사용자 지정). 유예 중에는 쓰기가 거절되므로, 로그인한 채로 두면 저장할 때마다 서버 전송만
  조용히 실패한다.
- 취소는 다시 로그인했을 때 묻는다(사용자 지정). 묻지 않고 취소하면 사용자가 취소된 줄 모르고, 지운 줄 알던 계정이 그대로 남는다.
- 예약을 묻다가 응답이 없으면 묻지 않고 들어간다. 다음에 앱을 켤 때 다시 묻는다. 서버가 꺼졌다고 앱을 막지 않는다([[ADR-016]] 결정 1).
- 계정 삭제는 기기의 앱 데이터를 지우지 않는다(사용자 지정). 기기 기록은 데이터 삭제([[ADR-053]])가 따로 지운다.

### 결정 8. 계정 묶음은 로그아웃 · 데이터 삭제 · 계정 삭제다

`앱 정보 및 계정` 화면의 `계정` 묶음([[ADR-052]] 결정 7)이다.

| 행 | 확인 창 | 주 버튼 |
|---|---|---|
| 로그아웃 | `로그아웃할까요?` | `로그아웃` |
| 데이터 삭제 | [[ADR-053]] | `취소` |
| 계정 삭제 | `계정을 삭제할까요?` | `취소`, 아래 빨간 `계정 삭제` |
| (다시 로그인했을 때) | `삭제 예정인 계정이에요` | `삭제 취소`, 아래 `로그아웃` |

- 로그아웃은 위험 행과 다른 카드에 둔다. 다시 로그인하면 되돌릴 수 있어서다. 확인은 한 번 받는다. 다시 로그인하려면 넥슨 창을
  거치거나 키를 다시 붙여야 해서, 실수로 눌렀을 때 드는 수고가 작지 않다.
- 계정 삭제는 데이터 삭제와 같은 카드 · 같은 확인 창 형태다. 되돌릴 수 없는 동작의 확인 창 둘이 같은 형태라 하나를 익히면 다른
  하나도 알아본다.
- 계정 삭제 확인 창의 설명은 언제 무엇이 지워지고 무엇이 남는지 말한다(사용자 선택 2026-11-24). 서버에 둔 기록은 계정과 함께
  지워지고, 사용 로그 · 드롭 판매가 · 강화 이상 보고만 사람과의 연결을 끊어 남기 때문이다(결정 6).
  `30일 뒤 서버의 계정과 서버에 둔 기록이 지워져요. 그 전에 다시 로그인하면 취소할 수 있어요. 사용 기록과 드롭 판매가는 익명 기록으로
  남고, 이 기기의 기록은 지워지지 않아요.`
- 로그아웃 확인 창의 설명은 `로그인만 풀려요. 이 기기의 기록과 서버의 기록은 그대로 남아요.` 다. 아이콘은 사람(`CircleUserRoundIcon`) · 주 색이다.
- 계정 삭제 확인 창의 아이콘은 경고(`AlertTriangleIcon`) · 빨간색이다.
- 삭제 예정 확인 창의 설명은 `{지울 날}에 삭제돼요. 계속 쓰려면 삭제를 취소해 주세요.` 다. 지울 날은 `2026년 12월 4일` 처럼 연도까지
  적는다. 30일 뒤가 해를 넘길 수 있다. 아이콘은 달력 시계(`CalendarClockIcon`) · 주 색이다(사용자 선택). 빨간 경고 배지 옆에
  주 버튼 `삭제 취소` 가 서면 그 버튼이 위험한 동작처럼 읽힌다.
- 시안: https://claude.ai/artifact/XgG94NsZYC9ajBpmHWpQhk (테마 여섯 · 화면 다섯, 삭제 예정은 A)
- 세 확인 창 모두 설명을 제목 아래(`description`)에 두지 않고 머리 줄 아래 `card-inset` 칸(`content`)에 둔다(사용자 지정).
  글자는 `text-xs` 흐린 색이다.
- 삭제 예정 확인 창의 주 버튼은 `삭제 취소` 다. 같은 계정으로 다시 로그인한 사람은 대개 계속 쓰려는 사람이다.

### 결정 9. 키 사용자가 넥슨 로그인을 붙이면 서버가 키의 넥슨 계정 줄을 로그인 계정 줄로 합친다

키 사용자가 넥슨으로 로그인하면 서버에는 메이플 ID 해시로 만든 넥슨 계정 줄과 넥슨 `uid` 로 만든 로그인 계정 줄이 따로 있다. 로그인한
기기가 로그인 세션으로 메이플 ID 를 알리면(`PUT /v1/me/maple-ids`) 서버가 같은 메이플 ID 의 줄을 로그인 줄로 합친다([[ADR-101]]
결정 25). 넥슨 계정 줄은 넥슨 ID 하나에 하나다.

- 앱은 로그인 직후 같은 메이플 ID 의 키를 기기에서 지운다([[ADR-025]] 결정 4). 키를 서버에 따로 알리지 않는다. 서버는 키 표를
  두지 않아 키로 줄을 찾지 못하고, 키 사용자는 이미 메이플 ID 해시로 밝혀졌으므로(결정 5) 메이플 ID 만으로 합칠 수 있다.
- 합칠 때 남기는 줄과 옮기는 것, 합치지 않는 경우(두 로그인 줄 · 삭제를 예약한 사람)는 [[ADR-101]] 결정 25 에 있다.

### 결정 10. 넥슨 로그인 계정마다 추천인 코드를 하나 주고, 추천 기록을 담을 표를 둔다

넥슨으로 로그인한 계정마다 다른 사람에게 알려 줄 추천인 코드를 하나 준다(사용자 지정). 이번에는 코드를 만들어 저장하고, 추천
기록을 담을 표를 두는 데까지다. 앱은 아직 코드를 보여 주지 않고, 남의 코드를 넣는 경로도 없다(사용자 지정). 그래서 코드를
돌려주는 API 와 코드를 받는 API 는 없고, `referrals` 표는 비어 있다.

```
nexon_accounts   … · referral_code(UNIQUE)
                 CHECK (uid_hash 가 있는 로그인 줄이면 referral_code 가 있고, 키 줄이면 없다)
referrals        id · referred_nexon_account_id(UNIQUE) · referrer_nexon_account_id · created_at
                 CHECK (referred_nexon_account_id 와 referrer_nexon_account_id 가 다르다)
```

- 코드는 사람(`users`)이 아니라 넥슨 계정(`nexon_accounts`)에 둔다(사용자 지정). 지금은 넥슨 로그인 하나가 사람 하나를 만들어 둘이
  같다. 다른 넥슨 계정으로 로그인하면 `uid` 가 달라 다른 사람이 생긴다. 나중에 한 사람이 넥슨 로그인을 여럿 갖게 되어도([[ADR-101]])
  계정마다 코드가 따로 남는다.
- 키 줄에는 코드를 주지 않는다(사용자 지정). CHECK 가 로그인 줄에는 코드가 꼭 있고 키 줄에는 없게 한다. 키 줄이 로그인 줄에
  합쳐지면 키 줄은 지워지고 로그인 줄의 코드가 남는다(결정 9). 키 줄끼리 합쳐져도 코드는 생기지 않는다.

코드는 아래처럼 만든다.

- `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` 32자 가운데서 8자를 무작위로 뽑는다(사용자 선택). 0 과 O, 1 과 I 는 서로 헷갈려 손으로 옮겨
  적을 때 틀리기 쉬워서 뺐다. 만들 수 있는 코드는 32의 8제곱(약 1조 1천억) 개다.
- 서버가 처음 보는 넥슨 `uid` 로 로그인 계정 줄을 만들 때 함께 만든다(`upsertByNexonUid`). 다른 계정의 코드와 겹치면 다시 뽑는다.
- 운영의 로그인 줄에 이미 있는 코드는 1.0.15 로 옮길 때 넥슨 계정 줄과 함께 그대로 옮긴다(서버 `cli/move-old-db.ts`).
- 코드를 고치는 경로는 두지 않는다.

`referrals` 의 한 줄은 추천 하나다. 추천받은 계정(`referred_nexon_account_id`)과 추천한 계정(`referrer_nexon_account_id`)이 둘 다
`nexon_accounts.id` 를 가리킨다. 칸 이름은 [[ADR-099]] 결정 62 가 정했다.

- 추천받은 계정 칸은 UNIQUE 다. 한 계정은 추천인을 한 번만 넣는다.
- 자기 계정을 추천한 줄은 CHECK 가 거절한다.

계정이 지워질 때(결정 6 의 30일 뒤) 추천 기록은 이렇게 된다.

| 지워지는 계정 | `referrals` 의 줄 | 이유 |
|---|---|---|
| 추천받은 계정 | 함께 지운다(`ON DELETE CASCADE`) | 그 계정이 넣은 기록이라 계정이 없으면 남길 까닭이 없다 |
| 추천한 계정 | 줄은 남기고 `referrer_nexon_account_id` 만 비운다(`ON DELETE SET NULL`) | 추천인을 이미 넣었다는 사실이 남아야 추천받은 계정이 다른 코드를 다시 넣지 못한다(사용자 선택) |

### 결정 11. 서버에는 넥슨 식별자의 원문을 두지 않고 SHA-256 해시만 둔다

대상은 넥슨이 준 식별자 셋이다. 넥슨 로그인의 `uid`, 메이플 ID(`character/list` 의 `account_id`), 캐릭터의 `ocid` 다(사용자 지정
2026-11-10).

- 넥슨 AI 에이전트 가이드에 따르면 64자 ocid 의 뒤 32자는 그 ocid 를 받은 API 키의 뒤 32자와 같다. 서버에 ocid 원문을 쌓으면
  사용자 키의 일부가 함께 쌓인다. 메이플 ID 와 `uid` 도 같은 원칙으로 원문을 두지 않는다.
- 해시는 SHA-256 소문자 16진 64자다. 소금은 섞지 않는다. 같은 ocid 는 어느 기기에서 해시해도 같은 값이어야
  서버가 원문을 몰라도 여러 기기의 기록이 같은 캐릭터를 가리킨다.
- ocid 와 메이플 ID 는 앱이 해시로 바꿔 보낸다(`lib/crypto/nexon-id-hash.ts`). 기기 안에는 원문을 둔다. 서버에서 받은 기록은 넥슨에서
  받은 자기 캐릭터 목록을 해시해 견주고 원문으로 바꿔 넣는다([[ADR-099]] 결정 12).
- 서버는 메이플 ID 와 ocid 칸에 SHA-256 소문자 16진 64자만 받는다. 원문으로 보이는 값은 거절해 원문이 표에 쌓이지 않게 한다.
- 서버는 받은 해시를 한 번 더 해시하지 않고 그대로 둔다(`maple_ids.hash` · `characters.ocid`). 받기 응답에 같은 해시를 돌려줘야
  기기가 자기 캐릭터 목록의 해시와 짝을 맞출 수 있다([[ADR-099]] 결정 12 · 66). 메이플 ID 해시는 키 사용자의 신원이기도 하다(결정 5).
- 넥슨 `uid` 는 로그인 콜백에서 서버가 받자마자 해시로 바꿔 `nexon_accounts.uid_hash` 에 둔다. 서버는 `uid` 로 계정 줄을 찾기만 하고
  넥슨에 `uid` 를 보내는 곳이 없어 원문이 필요 없다.
- 프렌즈 조회(`POST /v1/friends/stream`, [[ADR-016]] 결정 9)는 서버가 사용자 토큰으로 넥슨을 부르는 경로라 ocid 원문을 받는다. 그 값은
  넥슨에 보내는 데만 쓰고 표에도 로그에도 남기지 않는다.
- 운영 DB 에 있던 원문은 서버 이관 `0037_nexon_guide_compliance` 가 해시로 바꿨다. 1.0.15 로 옮길 때는 그 해시를 그대로
  옮긴다(서버 `cli/move-old-db.ts`). 판매가 줄로 옮기는 드롭에는 ocid 칸이 없다([[ADR-099]] 결정 26).

## 번호 기록

- ADR-017 (2026-10-19): 옛 ADR-299 결정 3 · ADR-340 · ADR-347 결정 18 을 합쳐 처음 작성
- ADR-159 (2026-11-04): 연결 해제를 로그아웃으로 바꾸고 넥슨 로그아웃과 합쳤다. 탈퇴 표시를 계정 삭제 예약으로 바꿔, 30일
  유예 뒤 사람과 열쇠를 지우고 보낸 기록은 사람과의 연결을 끊어 남긴다. 유예 중 다시 로그인하면 취소를 묻는다(#848). 결정 1 을 넥슨 계정 표에 맞췄고, ADR-025 결정 10 의 로그아웃 화면을 결정 8 로 옮겼다
- ADR-172 (2026-11-05): 결정 9 를 더했다. 키 사용자가 넥슨 로그인을 붙이면 앱이 키를 지우기 전에 해시를 보내고, 서버가
  키의 사람을 로그인한 사람에 합친다(#607). 결정 4 의 저장 칸 이름을 넥슨 계정 표에 맞췄다
- ADR-185 (2026-11-08): 결정 10 을 더했다. 넥슨 로그인 계정마다 추천인 코드를 주고, 추천 기록을 담을 `referrals` 표를 둔다. 앱은
  아직 코드를 보여 주지 않고 코드를 받는 경로도 없다
- (2026-11-10) [[ADR-101]] 결정 21 · 24 · 25 · 26 을 서버에 구현하며 결정 1 · 5 · 6 · 9 를 고쳤다. 넥슨 계정 줄은 넥슨 ID 하나에
  하나이고, 키 해시와 메이플 ID 를 따로 표로 둔다. 잇기는 사람이 아니라 키의 넥슨 계정 줄을 로그인 계정 줄로 합친다. 기록 표는 메이플
  ID 를 가리켜 계정 삭제 때 메이플 ID 와 함께 지워지거나(드롭은) 그 칸만 빈다
- ADR-194 (2026-11-11): 결정 11 을 더했다. 서버에는 넥슨 식별자(`uid` · 메이플 ID · ocid)의 원문을 두지 않고 SHA-256 해시만 둔다(#956,
  넥슨 AI 에이전트 가이드). 결정 1 · 6 을 그에 맞췄고, 드롭에 남기는 ocid 를 공개 값이라고 한 이유를 걷었다
- (2026-11-17) 결정 3 에 기기 간 동기화가 구현되면 키 해시로도 기록을 받는다는 것과 사용자가 받아들인 위험을 적었다([[ADR-099]] 결정 9).
