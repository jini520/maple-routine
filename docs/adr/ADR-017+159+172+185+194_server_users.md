# ADR-017+159+172+185+194 서버의 사용자와 신원 · 로그아웃과 계정 삭제 · 키 사용자 합치기 · 추천인 코드

> ⚪ 미구현
> 옛 번호: ADR-299 결정 3 · ADR-340 결정 2 · 3 · 4 · 5 · 7 · 8 · 정정 1 · 2 · 2-1 · 3 · 5 · ADR-347 결정 18
> 관련 소스: `features/auth/server-identity.ts` · `features/auth/store.ts` · `lib/crypto/api-key-hash.ts` · `features/server-sync/forget.ts` · `features/auth/account-deletion.ts` · `server/account-deletion.ts` · `app/settings/SettingsAboutScreen.tsx` · `app/settings/SignOutConfirm.tsx` · `app/settings/DeleteAccountConfirm.tsx` · `app/auth/AccountDeletionPrompt.tsx` · 서버 `modules/users/` · `modules/identity/`

## 배경

서버가 드롭 가격을 모으기 시작하면서 누가 보낸 값인지 가려야 했다. 앱 사용자는 두 부류다. 넥슨으로 로그인한
사용자와, 자기 API 키만 넣은 사용자다. 로그인 사용자는 넥슨이 신원을 보증하지만, 키 사용자는 서버가 키를 본
적이 없어 신원을 확인할 방법이 없다. 이 문서는 두 부류를 서버의 표에 어떻게 담고, 요청마다 무엇으로 사람을 찾는지 정한다.
그리고 넥슨 로그인이 들어가면서 스토어가 요구하는 계정 삭제와, 그와 짝을 이루는 로그아웃을 정한다. 키 사용자가 넥슨 로그인으로
바꿀 때 두 사람을 하나로 합치는 일과, 넥슨 로그인 계정마다 추천인 코드를 주는 일도 여기서 정한다.

## 결정

### 결정 1. 사람은 `users` 에 두고, 열쇠는 넥슨 계정 표 `nexon_accounts` 에 둔다

```
users                     id · created_at · deletion_requested_at
nexon_accounts            id · user_id · nexon_uid(UNIQUE) · referral_code                       넥슨 ID 하나
nexon_account_keys        id · nexon_account_id · api_key_hash(UNIQUE)                           API 키 하나
nexon_account_maple_ids   id · nexon_account_id · maple_id(UNIQUE)                               메이플 ID 하나
```

`nexon_uid` 와 `maple_id` 에는 원문이 아니라 해시가 들어간다(결정 11).

한 사람이 넥슨 계정을 여럿 가질 수 있어 열쇠를 사람 표의 칸으로 두지 않고 계정 표의 줄로 둔다([[ADR-101]]).
넥슨 계정 줄은 넥슨 ID 하나에 하나다. 같은 넥슨 ID 의 로그인과 키는 한 줄이고, 키는 키 표에 줄로 단다. 키를 다시 받으면
같은 줄에 키가 하나 더 달린다. 같은 넥슨 ID 인지는 메이플 ID 로 가린다([[ADR-101]] 결정 25).
기능 표(`drop_prices` 등)에는 `user_id` 를 둔다. 기능 표에 열쇠를 직접
담으면 열쇠가 바뀔 때마다 기능 표를 모두 고쳐야 하고, 하나를 빠뜨리면 그 기능만 조용히 끊긴다.

넥슨 `uid` 는 플랫폼이 달라도 같다(2026-10-12 실측). 넥슨 애플리케이션이 iOS 와 안드로이드로 따로 등록돼
`client_id` 가 다르지만, 같은 넥슨 계정이면 두 플랫폼에서 받은 `uid` 가 같았다. 그래서 안드로이드에서 쓰던 사람이
아이폰에서 로그인하면 같은 `users` 행에 세션이 하나 더 붙는다. 세션은 저마다 자기 플랫폼의 자격 쌍으로 갱신한다.

### 결정 2. 세션은 사람을 가리키는 표이고, 사람이 먼저 생긴다

`nexon_sessions.user_id` 는 `users` 를 가리키고 `NOT NULL` 이다. 로그인 콜백이 `uid` 로 기존 사람을 찾거나 새로
만든 다음에 세션을 만든다. 세션은 갱신 토큰이 만료되거나, 넥슨이 갱신을 거절하거나, 사용자가 로그아웃하면
지워진다. 모두 정상 동작이다. 세션이 지워질 때 사람도 함께 지우면 정상 동작 때문에 데이터를 잃게 된다. 그래서 세션이
지워져도 사람은 남는다.

### 결정 3. 키 사용자의 데이터도 모으고, 줄마다 어느 열쇠로 찾았는지 남긴다

드롭 가격은 로그인 여부와 관계없이 모은다. 지금 사용자가 모두 키 사용자라, 키 사용자를 빼면 표본이 없다.

키 사용자의 신원은 확인할 수 없다. 확인하려면 서버가 키 원문을 받아 넥슨에 물어봐야 하는데, 그것은 이용자가
키를 남에게 주는 일이라 넥슨 이용약관 제5조 ①·② 에 걸린다. 그래서 키 해시는 신원의 증명이 아니라, 같은 사람이
다시 보낸 값을 잇고 계정을 삭제할 때 그 사람의 줄을 찾는 데만 쓴다. 해시를 알면 남인 척 값을 보낼 수 있다는 점은
알고 정했다(사용자 지정). 이 경로로 할 수 있는 일은 돌려받는 것 없는 수집뿐이라 피해가 작다.

드롭 가격 줄마다 `identified_by` 칸에 `login` 또는 `key` 를 적는다. 나중에 집계할 때 두 부류의 가중치를 다르게 줄
수 있게 하기 위해서다. 틀린 값이 섞이지 않게 막는 일은 신원 확인이 아니라 입력 검사와 집계 때의 이상치 제거가
맡는다. 로그인 사용자도 틀린 값은 보낼 수 있기 때문이다.

### 결정 4. 앱은 키 원문을 보내지 않고 SHA-256 을 보낸다. 서버는 그것을 한 번 더 해시해 저장한다

앱은 API 키의 SHA-256 을 소문자 16진 64자로 만들어 보낸다(`apiKeyHashHex`). Hermes 에 `crypto` 가 없어서
`@noble/hashes` 의 순수 JS 구현을 쓴다. 네이티브 모듈이었다면 스토어 빌드를 기다려야 했지만, 이 방법은 OTA 로 나간다.
앱과 서버가 같은 알고리즘과 같은 표기를 써야 한다. 표기가 달라도 서버는 거절하지 않고, 매번 새 사람을 만든다.

서버는 받은 값을 그대로 저장하지 않고 SHA-256 을 한 번 더 해서 `nexon_accounts.api_key_hash` 에 넣는다. 받은 값은 서버 기록을
여는 값이기도 해서, 그대로 저장하면 DB 가 샐 때 남의 기록을 열 수 있다. HMAC 은 쓰지 않는다. 넥슨 키는 무작위성이
높아 두 번 해시만으로 DB 유출은 막히고, 비밀 값을 섞어도 신원을 증명할 수 없기는 마찬가지라 얻는 것이 없다.

### 결정 5. 쓰기 요청은 세션 아니면 키 해시 하나로 사람을 밝힌다

| 헤더 | 서버가 사람을 찾는 방법 | `identified_by` |
|---|---|---|
| `Authorization: Bearer <세션>` | 세션 해시로 행을 찾아 수명만 본다. 넥슨은 부르지 않는다 | `login` |
| `x-api-key-hash: <소문자 16진 64자>` | 받은 값을 한 번 더 해시해 키 표에서 그 키가 달린 넥슨 계정을 찾고, 없으면 사람 · 계정 줄 · 키 줄을 만든다 | `key` |

- 서버는 둘 다 오면 세션만 본다. 로그인한 사람의 기록이 키 쪽으로 나뉘면 한 사람으로 모은 의미가 없어진다.
- 세션이 죽었으면 키로 넘어가지 않고 401 이다. 넘어가면 같은 사람의 기록이 두 열쇠로 갈린다.
- 세션의 사람에게 로그인 계정 줄이 없으면 401 이다. 세션은 로그인 콜백이 로그인 계정 줄을 만든 뒤에만 생겨, 줄이 없으면 그 세션으로
  적을 넥슨 계정이 없다.
- 둘 다 없거나 형식이 틀리면 401 이다. 키 원문을 실어 보내면 길이가 맞지 않아 여기서 걸린다.
- 앱(`serverIdentityHeaders`)도 같은 규칙으로 하나만 싣는다. 세션이 있으면 Bearer 만, 없으면 메인 키의 해시만 싣고,
  둘 다 없으면 `null` 을 돌려줘 아무것도 보내지 않는다. 메인 키는 로그인 없이 쓰는 키다(`mainKeyId`, [[ADR-101]] 결정 5).
- 부계정 키로는 밝히지 않는다. 부계정은 넥슨 로그인 사용자만 등록하므로 그 사용자는 세션으로 밝혀진다. 로그인이 만료돼
  부계정 키만 남으면 밝힐 수단이 없어 보내지 않는다. 부계정 키를 메인으로 쓰지 않는 것과 같은 규칙이다.

이 헤더를 받는 경로는 `POST /v1/drop-prices` · `DELETE /v1/drop-prices/:id` · `POST /v1/enhancement-anomalies` ·
`POST /v1/usage-events` · `DELETE /v1/me` · `GET /v1/me/deletion` · `DELETE /v1/me/deletion` · `PUT /v1/me/maple-ids` 다.
부계정 경로(`/v1/me/sub-accounts`)와 `POST /v1/me/api-key-links` 는 세션만 받는다. 조회 경로는
공개 정보라 인증 없이 그대로 열려 있다.

### 결정 6. 계정 삭제는 30일 유예 뒤 사람과 열쇠를 지우고, 보낸 기록은 사람과의 연결을 끊어 남긴다

`DELETE /v1/me` 는 바로 지우지 않고 삭제를 예약한다. 유예기간은 30일이다(사용자 지정). 실수로 눌렀거나 마음이 바뀐 사람이
되돌릴 수 있게 한다.

```
users   id · created_at · deletion_requested_at   NULL 이 아니면 삭제 예약. 이 시각에서 30일 뒤 지운다
```

| 때 | 서버가 하는 일 |
|---|---|
| 요청(`DELETE /v1/me`) | `deletion_requested_at` 에 지금을 적고 그 사람의 세션을 모두 지운다. 이미 예약돼 있으면 처음 시각을 덮지 않는다 |
| 유예 중 쓰기 요청 | 403(`account_deletion_pending`)으로 거절한다. 지울 사람에게 새 기록이 붙지 않게 한다 |
| 유예 중 확인(`GET /v1/me/deletion`) | 예약 시각과 지울 날을 돌려준다. 예약이 없으면 `null` 이다 |
| 취소(`DELETE /v1/me/deletion`) | `deletion_requested_at` 을 비운다 |
| 30일 뒤 | 매일 밤 일이 그 사람의 `users` 행을 지운다. 아래 표처럼 넥슨 계정 줄 · 세션 · 기록이 정리된다. 넥슨 계정 줄과 함께 그 줄의 키 · 메이플 ID 와, 그 줄이 로그인이든 부계정이든 부계정 등록이 지워진다 |

- 세션은 요청 때 바로 지운다. 세션은 기록이 아니라 지금도 쓸 수 있는 자격 증명이라, 남기면 다른 기기의 로그인이 계속 쓰인다.
- 열쇠(`nexon_accounts`)는 유예가 끝날 때까지 남긴다. 열쇠가 있어야 같은 키나 넥슨 계정으로 돌아온 사람을 찾아 취소를 물을 수
  있다. 유예가 끝나 열쇠가 지워지면 같은 키나 넥슨 계정으로 그 사람을 다시 찾을 수 없다.

30일 뒤 지울 때 보낸 기록은 표마다 다르게 다룬다.

| 표 | 계정 삭제 때 | 이유 |
|---|---|---|
| `drop_prices` · `usage_events` · `enhancement_anomalies` | `user_id` 를 비우고 줄은 남긴다. 드롭 가격은 메이플 ID 를, 강화 이상 보고는 넥슨 계정 칸도 비운다. 드롭의 `ocid` 해시는 남긴다 | 시세 통계와 사용 통계가 사람이 나갈 때마다 흔들리면 안 된다(사용자 지정). `ocid` 는 원문이 아니라 해시라 남겨도 키 조각이 남지 않는다(결정 11). 남겨야 지운 뒤 돌아온 사람이 같은 드롭을 다시 보내도 줄이 늘지 않는다([[ADR-101]] 결정 24) |
| `boss_clears` · `cashbook_entries` · `enhancement_totals` | 그 계정의 메이플 ID 줄과 함께 지운다 | 지금 앱이 보내지 않는 표다([[ADR-099]] 결정 1). 캐릭터 식별자(`ocid` · 메이플 ID)가 들어 있어 연결을 끊어도 익명이 아니다 |

- 남기는 표의 `user_id` 는 `NULL` 을 받고 외래키는 `ON DELETE SET NULL` 이다. 같은 사람 안에서만 덮는 규칙([[ADR-018]] 결정 7)은
  사람이 있는 줄에만 걸린다. 연결이 끊긴 줄은 다시 고쳐지지 않는다.
- 같은 키나 같은 넥슨 계정으로 다시 오면 새 사람이 된다. 지운 사람의 기록과 이어지지 않는다. 이어지면 익명이 아니다.
- 옛 탈퇴 표시(`users.deleted_at`)는 삭제 예약 칸(`deletion_requested_at`)으로 바꾼다. 옛 칸에 시각이 있는 사람은 탈퇴만 적혔을
  뿐 삭제를 요청한 사람이 아니므로, 옮기지 않고 비운다.
- 운영자는 메일로 삭제를 요청받아도 그 사람을 찾을 수 없다. 서버가 가진 것은 되돌릴 수 없는 해시뿐이다. 그래서 삭제는 키나
  세션을 들고 있는 앱 안에서만 한다. 웹의 삭제 안내(`site/support.md`)는 앱에서 지우는 방법을 알려 준다(사용자 지정).

### 결정 7. 로그아웃은 기기의 인증 수단만 지우고, 계정 삭제는 서버에 예약한 뒤 로그아웃한다

로그아웃은 앱 데이터와 서버 데이터를 모두 남기고 로그인만 푼다(사용자 지정). 넥슨 로그인과 메인 키를 모두 뗀다. 넥슨 로그인만
떼는 로그아웃은 따로 두지 않는다(사용자 지정). 이름이 같은 행 둘이 서로 다른 일을 하면 무엇을 눌렀는지 알 수 없다. 넥슨 로그인에
귀속된 부계정 키는 남긴다. 같은 넥슨 ID 로 다시 로그인하면 부계정을 이어 쓰게 하려는 것이다([[ADR-101]] 결정 5).

```
로그아웃 (signOut)
1. 로그인이 있으면 DELETE /v1/auth/nexon/session 으로 서버 세션을 거둔다. 기기에서 지우기 전이어야 세션 값이 있다
2. 서버 전송 대기 표와 사용 로그 표를 비운다
3. 기기에서 세션과 메인 키를 지우고 로그인 화면으로 간다. 넥슨 로그인에 귀속된 부계정 키는 남는다

계정 삭제 (deleteAccount)
1. DELETE /v1/me. 기기에서 키를 지우기 전이어야 서버가 사람을 찾는다
2. 실패하면 멈추고 알린다. 로그아웃하지 않는다
3. 성공하면 `30일 뒤 계정이 삭제돼요` 토스트를 띄우고 로그아웃 1 ~ 3

다시 로그인할 때 (checkAccountDeletion)
1. 로그인이나 키 입력이 끝나면 GET /v1/me/deletion 으로 예약을 묻는다. 앱을 켤 때도 한 번 묻는다
2. 예약이 있으면 `삭제 예정인 계정이에요` 확인 창을 띄운다. 지울 날을 보여 준다
3. `삭제 취소` 를 누르면 DELETE /v1/me/deletion 뒤 그대로 들어간다
4. `로그아웃` 을 누르면 로그아웃 1 ~ 3. 예약은 그대로다
```

- 로그아웃의 1번은 실패해도 진행한다. 기기에서 지우는 일이 본론이고, 서버 세션은 갱신 토큰 수명이 지나면 정리된다.
- 2번에서 비우는 것은 못 보낸 것이다(사용자 지정). 대기 표와 사용 로그 표에는 누가 만든 줄인지 적혀 있지 않아, 남기면 다음에
  다른 키로 로그인한 사람의 신원으로 나간다. 기기의 기록 자체는 남는다.
- 계정 삭제는 서버가 예약했다고 답해야 로그아웃한다. 실패한 채로 로그아웃하면 사용자는 지워질 줄 알지만 서버에는 예약이 없다.
- 요청 직후 바로 로그아웃한다(사용자 지정). 유예 중에는 쓰기가 거절되므로, 로그인한 채로 두면 저장할 때마다 서버 전송만
  조용히 실패한다.
- 취소는 다시 로그인했을 때 묻는다(사용자 지정). 묻지 않고 취소하면 사용자가 취소된 줄 모르고, 지운 줄 알던 계정이 그대로 남는다.
- 예약을 묻다가 응답이 없으면 묻지 않고 들어간다. 다음에 앱을 켤 때 다시 묻는다. 서버가 꺼졌다고 앱을 막지 않는다([[ADR-016]] 결정 1).
- 계정 삭제는 기기의 앱 데이터를 지우지 않는다(사용자 지정). 기기 기록은 데이터 삭제([[ADR-053]])가 따로 지운다.

### 결정 8. 계정 묶음은 로그아웃 · 데이터 삭제 · 계정 삭제다

`앱 정보 및 계정` 화면의 `계정` 묶음([[ADR-052]] 결정 7)이다.

| 행 | 확인 창 | 주 버튼 |
|---|---|---|
| 로그아웃 | `로그아웃할까요?` | `로그아웃` |
| 데이터 삭제 | [[ADR-053]] | `취소` |
| 계정 삭제 | `계정을 삭제할까요?` | `취소`, 아래 빨간 `계정 삭제` |
| (다시 로그인했을 때) | `삭제 예정인 계정이에요` | `삭제 취소`, 아래 `로그아웃` |

- 로그아웃은 위험 행과 다른 카드에 둔다. 다시 로그인하면 되돌릴 수 있어서다. 확인은 한 번 받는다. 다시 로그인하려면 넥슨 창을
  거치거나 키를 다시 붙여야 해서, 실수로 눌렀을 때 드는 수고가 작지 않다.
- 계정 삭제는 데이터 삭제와 같은 카드 · 같은 확인 창 형태다. 되돌릴 수 없는 동작의 확인 창 둘이 같은 형태라 하나를 익히면 다른
  하나도 알아본다.
- 계정 삭제 확인 창의 설명은 언제 무엇이 지워지고 무엇이 남는지 말한다(사용자 지정 문구).
  `30일 뒤 서버의 계정이 지워져요. 그 전에 다시 로그인하면 취소할 수 있어요. 삭제 후 사용 기록은 익명 기록으로 변경되고, 이 기기의
  기록은 삭제되지 않고 보관됩니다.`
- 로그아웃 확인 창의 설명은 `로그인만 풀려요. 이 기기의 기록과 서버의 기록은 그대로 남아요.` 다. 아이콘은 사람(`CircleUserRoundIcon`) · 주 색이다.
- 계정 삭제 확인 창의 아이콘은 경고(`AlertTriangleIcon`) · 빨간색이다.
- 삭제 예정 확인 창의 설명은 `{지울 날}에 삭제돼요. 계속 쓰려면 삭제를 취소해 주세요.` 다. 지울 날은 `2026년 12월 4일` 처럼 연도까지
  적는다. 30일 뒤가 해를 넘길 수 있다. 아이콘은 달력 시계(`CalendarClockIcon`) · 주 색이다(사용자 선택). 빨간 경고 배지 옆에
  주 버튼 `삭제 취소` 가 서면 그 버튼이 위험한 동작처럼 읽힌다.
- 시안: https://claude.ai/artifact/XgG94NsZYC9ajBpmHWpQhk (테마 여섯 · 화면 다섯, 삭제 예정은 A)
- 세 확인 창 모두 설명을 제목 아래(`description`)에 두지 않고 머리 줄 아래 `card-inset` 칸(`content`)에 둔다(사용자 지정).
  글자는 `text-xs` 흐린 색이다.
- 삭제 예정 확인 창의 주 버튼은 `삭제 취소` 다. 같은 계정으로 다시 로그인한 사람은 대개 계속 쓰려는 사람이다.

### 결정 9. 키 사용자가 넥슨 로그인을 붙이면 서버가 키의 넥슨 계정 줄을 로그인 계정 줄로 합친다

키 사용자가 넥슨으로 로그인하면 서버에는 키 해시로 만든 사람과 넥슨 `uid` 로 만든 사람이 따로 있다. 앱은 로그인 직후 같은
메이플 ID 의 키를 기기에서 지운다([[ADR-025]] 결정 4). 키를 지우면 해시를 다시 만들 수 없어서, 그 뒤에는 서버가 두 사람이
같은 사람인지 알 방법이 없다. 그래서 앱이 키를 지우기 전에 그 키의 해시를 보내고, 서버가 키의 넥슨 계정 줄을 로그인 계정 줄로
합친다(#607). 앱이 메이플 ID 가 같은 것을 확인한 키라 같은 넥슨 ID 이고, 넥슨 계정 줄은 넥슨 ID 하나에 하나다([[ADR-101]] 결정 25).

```
POST /v1/me/api-key-links
Authorization: Bearer <세션>
{ "apiKeyHash": "<키의 SHA-256, 소문자 16진 64자>" }
→ 204
```

- 세션으로 온 요청만 받는다. 키 해시 헤더로 온 요청은 403(`login_required`)이다. 어느 로그인에 합칠지를 세션이 정하기 때문이다.
- 로그인한 사람이 삭제를 예약했으면 다른 쓰기처럼 403(`account_deletion_pending`)이다(결정 6). 앱은 키를 지우지 않고, 사용자가
  삭제를 취소한 뒤 앱을 켤 때 다시 보낸다.
- 받은 해시는 한 번 더 해시해 키 줄을 찾는다(결정 4).
- 서버는 그 해시가 정말 이 사람의 키인지 확인할 수 없다. 결정 3 과 같은 이유로 받는다. 해시를 만들 수 있는 사람은 키를 가진
  사람뿐이고, 서버는 해시를 한 번 더 해서 저장하므로 DB 가 새어도 이 값은 나오지 않는다. 앱은 메이플 ID 를 맞춰 본 키만 보낸다.

합치는 일은 트랜잭션 하나다. 아래 표에서 L 은 세션의 사람의 로그인 계정 줄, K 는 그 키가 달린 넥슨 계정 줄이다.

| 경우 | 서버가 하는 일 |
|---|---|
| 키가 어디에도 없다 | L 에 키를 단다. 다른 기기가 그 키로 보내도 L 로 모인다 |
| 키가 이미 L 에 있다 | 아무것도 하지 않는다. 앱이 다시 보내도 결과가 같다 |
| K 가 다른 로그인 줄이다 | 옮기지 않는다. 앱이 메이플 ID 를 맞춰 본 키가 다른 넥슨 ID 의 로그인에 달려 있으면 어느 쪽인지 가릴 수 없다 |
| K 의 사람이 삭제를 예약했다 | 옮기지 않는다. K 는 예약대로 30일 뒤 지워진다. 합치면 사용자가 한 삭제 요청이 말없이 사라진다 |
| 그 밖 | K 를 L 로 합친다([[ADR-101]] 결정 25). K 의 사람에게 다른 넥슨 계정 줄이 있으면 사람과 그 줄은 남긴다 |

다섯 경우 모두 204 다. 앱은 204 를 받으면 그 키를 지운다. 옮기지 않은 경우에도 그 키는 로그인과 메이플 ID 가 같아서 기기에 둘
이유가 없다.

합칠 때 옮기는 것은 표마다 다르다.

| 표 | 옮길 때 |
|---|---|
| `nexon_account_keys` · `nexon_account_maple_ids` | K 의 줄을 L 로 옮기고 K 를 지운다. 다른 기기에서 아직 그 키를 쓰면 그 기기가 보내는 값도 L 로 모인다 |
| `sub_accounts` | K 가 든 등록을 L 로 옮긴다. 합친 뒤 L 이 자기 자신을 잇게 되는 등록은 지운다 |
| `enhancement_anomalies` | 넥슨 계정 칸을 L 로 바꾼다. 같은 열쇠가 L 에도 있으면 `updated_at` 이 늦은 줄을 남긴다 |

K 의 사람에게 다른 줄이 없으면 그 사람의 기록을 L 의 사람으로 옮기고 사람을 지운다.

| 표 | 옮길 때 |
|---|---|
| `drop_prices` | `user_id` 를 L 의 사람으로 바꾼다. 같은 기록이 L 의 사람에게도 있어 UNIQUE 가 겹치면 `updated_at` 이 늦은 줄을 남긴다. 같은 사람 안에서는 나중 값이 앞 값을 덮는 규칙([[ADR-018]] 결정 7)과 같다 |
| `enhancement_anomalies` · `usage_events` | `user_id` 를 L 의 사람으로 바꾼다 |
| `boss_clears` · `cashbook_entries` · `enhancement_totals` | 옮기지 않는다. 메이플 ID 를 가리키므로, 메이플 ID 가 L 로 옮겨 가면 함께 이어진다 |

- `identified_by` 는 받을 때의 값(`key`)으로 둔다(사용자 선택). 합치는 일도 해시만 보고 한 것이라, 그 줄을 믿을 수 있는 정도는
  달라지지 않는다. 이 칸은 집계 때 두 부류의 가중치를 나누려고 둔 것이다(결정 3).
- 합친 뒤 같은 키로 오는 요청은 L 로 찾아진다. 키 줄이 L 아래에 있어서다. `identified_by` 는 그 요청도 `key` 다.

### 결정 10. 넥슨 로그인 계정마다 추천인 코드를 하나 주고, 추천 기록을 담을 표를 둔다

넥슨으로 로그인한 계정마다 다른 사람에게 알려 줄 추천인 코드를 하나 준다(사용자 지정). 이번에는 코드를 만들어 저장하고, 추천
기록을 담을 표를 두는 데까지다. 앱은 아직 코드를 보여 주지 않고, 남의 코드를 넣는 경로도 없다(사용자 지정). 그래서 코드를
돌려주는 API 와 코드를 받는 API 는 없고, `referrals` 표는 비어 있다.

```
nexon_accounts   … · referral_code(UNIQUE)
                 CHECK (login 이면 referral_code 가 있고, key 면 없다)
referrals        id · referred_account_id(UNIQUE) · referrer_account_id · created_at
                 CHECK (referred_account_id 와 referrer_account_id 가 다르다)
```

- 코드는 사람(`users`)이 아니라 넥슨 계정(`nexon_accounts`)에 둔다(사용자 지정). 지금은 넥슨 로그인 하나가 사람 하나를 만들어 둘이
  같다. 다른 넥슨 계정으로 로그인하면 `uid` 가 달라 다른 사람이 생긴다. 나중에 한 사람이 넥슨 로그인을 여럿 갖게 되어도([[ADR-101]])
  계정마다 코드가 따로 남는다.
- 키 줄에는 코드를 주지 않는다(사용자 지정). CHECK 가 로그인 줄에는 코드가 꼭 있고 키 줄에는 없게 한다. 키 줄은 로그인한 사람
  아래로 옮겨져도(결정 9) 키 줄이라 코드가 생기지 않는다.

코드는 아래처럼 만든다.

- `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` 32자 가운데서 8자를 무작위로 뽑는다(사용자 선택). 0 과 O, 1 과 I 는 서로 헷갈려 손으로 옮겨
  적을 때 틀리기 쉬워서 뺐다. 만들 수 있는 코드는 32의 8제곱(약 1조 1천억) 개다.
- 서버가 처음 보는 넥슨 `uid` 로 로그인 계정 줄을 만들 때 함께 만든다(`upsertAccount`). 다른 계정의 코드와 겹치면 다시 뽑는다.
- 이미 있는 로그인 줄은 칸을 더하는 마이그레이션이 같은 규칙으로 채운다.
- 코드를 고치는 경로는 두지 않는다.

`referrals` 의 한 줄은 추천 하나다. 추천받은 계정(`referred_account_id`)과 추천한 계정(`referrer_account_id`)이 둘 다
`nexon_accounts.id` 를 가리킨다.

- 추천받은 계정 칸은 UNIQUE 다. 한 계정은 추천인을 한 번만 넣는다.
- 자기 계정을 추천한 줄은 CHECK 가 거절한다.

계정이 지워질 때(결정 6 의 30일 뒤) 추천 기록은 이렇게 된다.

| 지워지는 계정 | `referrals` 의 줄 | 이유 |
|---|---|---|
| 추천받은 계정 | 함께 지운다(`ON DELETE CASCADE`) | 그 계정이 넣은 기록이라 계정이 없으면 남길 까닭이 없다 |
| 추천한 계정 | 줄은 남기고 `referrer_account_id` 만 비운다(`ON DELETE SET NULL`) | 추천인을 이미 넣었다는 사실이 남아야 추천받은 계정이 다른 코드를 다시 넣지 못한다(사용자 선택) |

### 결정 11. 서버에는 넥슨 식별자의 원문을 두지 않고 SHA-256 해시만 둔다

대상은 넥슨이 준 식별자 셋이다. 넥슨 로그인의 `uid`, 메이플 ID(`character/list` 의 `account_id`), 캐릭터의 `ocid` 다(사용자 지정
2026-11-10).

- 넥슨 AI 에이전트 가이드에 따르면 64자 ocid 의 뒤 32자는 그 ocid 를 받은 API 키의 뒤 32자와 같다. 서버에 ocid 원문을 쌓으면
  사용자 키의 일부가 함께 쌓이고, 계정을 지워도 드롭에 남는다. 메이플 ID 와 `uid` 도 같은 원칙으로 원문을 두지 않는다.
- 해시는 결정 4 와 같은 SHA-256 소문자 16진 64자다. 소금은 섞지 않는다. 같은 ocid 는 어느 기기에서 해시해도 같은 값이어야
  서버가 원문을 몰라도 여러 기기의 기록이 같은 캐릭터를 가리킨다.
- ocid 와 메이플 ID 는 앱이 해시로 바꿔 보낸다. 기기 안에는 원문을 둔다. 서버에서 받은 기록은 넥슨에서 받은 자기 캐릭터 목록을
  해시해 견주고 원문으로 바꿔 넣는다.
- 넥슨 `uid` 는 로그인 콜백에서 서버가 받자마자 해시로 바꿔 `nexon_accounts.nexon_uid` 에 둔다. 서버는 `uid` 로 계정 줄을 찾기만 하고
  넥슨에 `uid` 를 보내는 곳이 없어 원문이 필요 없다.
- 키 해시와 달리 서버가 한 번 더 해시하지 않는다. 키 해시는 서버 기록을 여는 값이지만(결정 4), 이 식별자들은 기록을 열지 않는다. 기록은
  세션이나 키 해시로 밝힌 신원이 연다(결정 5).
- 프렌즈 조회(`POST /v1/friends/stream`, [[ADR-016]] 결정 9)는 서버가 사용자 토큰으로 넥슨을 부르는 경로라 ocid 원문을 받는다. 그 값은
  넥슨에 보내는 데만 쓰고 표에도 로그에도 남기지 않는다.
- 운영에 이미 있는 원문(`nexon_uid`, 메이플 ID 표)은 마이그레이션이 해시로 바꾼다. 1.0.13 앱은 ocid 와 메이플 ID 를 저장하라고 서버에
  보내지 않는다(프렌즈 조회만 ocid 를 싣는다). 그래서 드롭 · 처치 · 가계부 · 강화 합계 표에는 ocid 원문이 없고, 옛 앱의 원문과 새 앱의
  해시가 한 칸에 섞이지 않는다. 64자 ocid 와 해시는 길이가 같아 값만 보고는 가를 수 없으므로 이 사실이 중요하다.
