# ADR-115: API 키 무효화(401/403) → 토스트 + 키 입력 화면 자동 이동, 뒤 단계는 저장된 값으로 재개

**날짜**: 2026-08-08
**상태**: **구현 완료 · 실기기 미검증**, 2026-08-08, 이슈 #157
**관련**: [[ADR-008]](401/403 처방 — *"캐시는 유지하되 '설정에서 다시 입력해주세요' 배너"* 가 미구현 보류로 남아 있었고 이 ADR 이 그것을 대체한다) · [[ADR-086]] 결정 1(끝내지 않은 온보딩은 저장된 값에서 재개 지점을 파생한다 — 이 결정의 토대) · [[ADR-062]] 결정 3(원인별 문구·액션 — *"401 은 설정으로 보낸다"* 의 **목적지**를 이 ADR 이 바꾼다) · [[ADR-063]] 결정 3(토스트 액션 표) · [[ADR-050]](문서 리로드가 네이티브 SQLite 커넥션을 stale 하게 만든다 — 이동을 라우터로 하는 이유) · [[ADR-065]] 결정 1(키 입력 폼 자체의 실패는 토스트) · [[ADR-016]](예열 — 재개에서 다시 돌리지 않는 것) · [[ADR-114]] 결정 2(같은 계열의 판단 — 처방이 아닌 액션은 주지 않는다) · 이슈 #157 · #135(설정 구조 개선 — 결정 8 이 미룬 곳)

## 배경

### 두 경우 중 하나만 동작한다 (이슈 #157)

| 경우 | 지금 동작 | |
|---|---|---|
| **A. 키가 저장소에서 사라짐**(앱 데이터 삭제 등) | `restoreFromStorage` 가 `authConfig === null` 이면 조기 반환(`features/onboarding/store.ts:85-88`) → `isCompleted` false → `App.tsx:295` 가드가 `/onboarding` 으로 보냄 | ✅ |
| **B. 키가 무효화됨**(401/403 — 넥슨에서 키 삭제·재발급) | 토스트 `API 키가 유효하지 않습니다` + **설정 열기**(`use-sync-error-toast.ts:49-56`), 피커는 *"설정에서 키를 다시 등록해주세요"*(`schedule-sync/format.ts:60-65`) | ❌ |

**B 는 막다른 길이다 — 설정에 키를 바꿀 자리가 없다.** `ApiKeyModal` 행은 2026-07-25 에 제거됐고
([settings.md](../features/settings.md) 폐기 이력), "계정 변경"은 **저장된 키 그대로** `character/list`
를 다시 부르므로 무효 키로는 같은 401 을 다시 맞는다. 남은 경로는 위험 색으로 칠해진 **연결 해제**
하나뿐이다. 즉 화면이 안내하는 목적지에 실제로는 아무것도 없다.

### 실측 — 재개는 부팅 경로에만 있다

이슈가 **선행 확인 항목**으로 남긴 질문: 저장소에 키만 없고 `selectedAccountId`·`trackingMode`·
`trackedCharacters` 는 남은 상태에서 재개가 어느 단계로 떨어지는가? 실측 결과 **두 구간으로 갈린다.**

| 구간 | 실제 동작 |
|---|---|
| 부팅 시 | `getAuthConfig()` 가 apiKey 없으면 **나머지를 읽지도 않고** `null` 반환(`storage/api-key.ts:6-17`) → `restoreFromStorage` 조기 반환 → `awaitingApiKey` → App 가드가 `/onboarding` 으로 보냄 ✅ |
| **키 재입력 후** | `submitApiKey` → `API_KEY_VERIFIED` → 리듀서가 **무조건** `selectingAccount` 로 가고 `selectedAccountId` 를 `null` 로 리셋(`state.ts:97-106`) → 계정 선택 → 전체 예열([[ADR-016]]) → 모드 → 캐릭터를 **전부 다시 묻는다** ❌ |

이슈가 전제한 *"키 입력만 하고 나머지는 건너뛴다"* 는 **지금 성립하지 않는다.** [[ADR-086]] 결정 1 의
재개 파생이 `restoreFromStorage` 한 곳에만 있고 **키 입력 성공 경로에는 없기** 때문이다. 저장소에
값이 그대로 남아 있는데도 다시 묻는다.

### 부수 발견 — 이동에 라우터가 필요 없다

`App.tsx:295-344` 가드는 이미 `status !== 'completed'` 면 **모든 라우트를 라우터로** `/onboarding` 에
보낸다. 그래서 **온보딩 상태를 뒤집는 것만으로 이동이 일어난다** — 스토어가 라우터를 알 필요가 없고
`window.location` 도 필요 없다([[ADR-050]] 자동 충족). *"훅에서 토스트를 띄우는 이유는 액션이 라우터를
필요로 해서"* 라는 `use-sync-error-toast.ts:15-17` 의 전제도 함께 사라진다.

## 결정

### 결정 1 — 401/403 을 만나면 토스트 한 줄을 띄우고 곧바로 키 입력 화면으로 보낸다

사용자가 액션을 누를 때까지 기다리지 않는다. **토스트에 액션 버튼을 두지 않는다** — 이동이 이미
일어났으므로 누를 것이 없다(`error-resilience.md` 원칙 3 *"원인을 실제로 푸는 행동만 액션으로 준다"*
와 일치). 지금의 `설정 열기` 액션(`use-sync-error-toast.ts:49-56`)은 **제거된다.**

문구는 **`API 키가 더 이상 유효하지 않습니다`** 다. 이슈 초안의 `"키가 더 이상..."` 에 **`API `** 를
붙여 앱 카피 규약에 맞춘다 — 다른 자리가 전부 `API 키` 로 쓴다(`schedule-sync/format.ts:13` ·
`app/settings/error-message.ts:6` · `features/onboarding/format.ts`). 어미는 [[ADR-062]] 결정 5 그대로다.

**대가를 인지하고 고른 것이다**: 작업 중이던 화면을 빼앗는다. 다만 무효 키 상태에서는 어느 화면도
제 기능을 못 하므로 **남겨 둘 화면이 없다.**

### 결정 2 — 이동은 "온보딩 상태를 뒤집는 것"으로 일어난다. 스토어는 라우터를 모른다

`App.tsx:295-344` 의 `isCompleted` 가드가 이미 라우터로 `/onboarding` 에 보낸다(위 "부수 발견").
무효화 진입점은 온보딩 상태를 `awaitingApiKey` 로 만들 뿐이고, 화면 이동은 그 가드가 한다.

- `window.location` 을 쓰면 문서가 리로드돼 네이티브 SQLite 커넥션이 stale 하게 남는다([[ADR-050]]).
  이 결정은 그 함정을 **피하는 것이 아니라 애초에 만나지 않는다.**
- **복귀 화면은 기존 온보딩 완료 규칙 그대로 `/content` 다.** 이탈 라우트를 기억했다 되돌리지
  않는다 — 그 상태를 새로 만들어야 하고 기존 완료 규칙과 충돌한다.

### 결정 3 — 무효 키는 저장소에서 지운다. 단 `apiKey` 키 하나만

`selectedAccountId`·`trackingMode`·`trackedCharacters` 는 **남긴다** — 무효화된 것은 키 하나뿐이므로
나머지를 지울 이유가 없고, 결정 4 의 재개가 그 값들을 쓴다.

- **기존 `clearAuthConfig()` 는 쓰면 안 된다** — 그 함수는 `selectedAccountId` 까지 지우므로
  (`storage/api-key.ts:31-34`) 결정 4 의 재개를 불가능하게 만든다. 그것은 **연결 해제용**이다.
- **지우는 이유**: 안 지우면 앱을 재시작했을 때 무효 키로 다시 `completed` 로 복귀하고, 첫 동기화에서
  또 401 을 맞아 다시 튕긴다. 사용자에게는 *"재시작하면 되는 것처럼 보이다가 안 되는"* 상태가 된다.
- **알려진 열화**: 저장소 삭제 자체가 실패하면(디스크 등) 화면은 키 입력으로 가지만 재시작 시 옛 무효
  키가 되살아난다. 그때는 다시 이 경로를 탈 뿐이라 **막다른 길이 아니므로** 별도 처리를 두지 않는다.

### 결정 4 — 키를 다시 넣으면 뒤 단계는 저장된 값으로 재개한다

계정 선택·트래킹 모드·추적 캐릭터를 **다시 묻지 않는다.**

- 구현은 [[ADR-086]] 결정 1 의 재개 파생표를 **`submitApiKey` 성공 경로에도 적용**하는 것이다.
- **파생 판정은 함수 하나로 두고 부팅(`restoreFromStorage`)과 공유한다** — 두 벌이 되면 재개 규칙의
  진실이 둘이 된다. 그것이 [[ADR-086]] 결정 1 이 진행 상태 전용 키를 거부한 바로 그 이유다.
- **예열([[ADR-016]])을 다시 돌리지 않는다** — 캐시가 이미 따뜻하다([[ADR-086]] 결정 1 과 같은 근거).

### 결정 5 — 재개에는 계정 목록 대조 가드가 붙는다

새로 넣은 키가 **다른 넥슨 계정의 키**일 수 있다. 키 검증 때 이미 받는 `character/list` 응답에 저장된
`selectedAccountId` 가 들어 있는지 확인해, **없으면 재개하지 않고 기존대로 계정 선택부터** 간다.

- 가드가 없으면 남의 계정 키로 이전 계정 ocid 추적 목록을 그대로 쓰게 된다(계정 불일치 상태).
- **추가 호출은 없다** — 이미 손에 있는 응답으로 판정한다.

### 결정 6 — 멱등성은 "`completed` 일 때만 무효화가 성립한다"로 얻는다

여러 화면·여러 캐릭터에서 401 이 동시에 터져도 **토스트 1회 · 이동 1회**다. 첫 호출이 상태를
`awaitingApiKey` 로 뒤집으면 뒤따르는 호출은 가드에 걸려 아무 일도 하지 않는다.

- **키 입력 화면에서 다시 401 이 나는 경우는 이 경로가 아니다** — 그때 상태는 `completed` 가 아니므로
  같은 가드가 막는다. 그 실패는 폼 자체의 에러 처리로 남는다([[ADR-065]] 결정 1 의 토스트).
- **재이동 루프의 경로는 그것 하나가 아니다** — 이 가드만으로는 막지 못하는 두 번째 경로가 구현 중
  재현됐다(아래 "구현하며 정정한 것" 11). 이 결정의 *"구조적으로 불가능"* 은 **키 입력 화면에서 나는
  새 401** 에 대해서만 참이다.

### 결정 7 — 401 감지 지점 전부가 이 진입점 하나를 부른다

| 자리 | 지금 | 바뀌는 것 |
|---|---|---|
| 스케줄러 3화면 동기화 토스트(`use-sync-error-toast`) | 토스트 + `설정 열기` | 진입점 호출, **액션 제거** |
| 캐릭터 피커 로스터 조회(`ErrorState` · 스탈 배너) | *"설정에서 키를 다시 등록해주세요"* + `설정 열기` | 진입점 호출, **액션 제거** |
| 설정 계정 변경 모달(`refreshAccounts`) | 인라인 카드 + `다시 시도` | 진입점 호출 — **저장된 키로 재조회하다 맞는 401 도 키 무효화다** |

그래서 [[ADR-062]] 결정 3 의 *"401 은 설정으로 보낸다"* 는 **폐기**되고 *"401 은 키 입력 화면으로
보낸다(자동)"* 로 대체된다. 목적지가 바뀐 이유는 단순하다 — **설정에는 키를 바꿀 자리가 없다**
(2026-07-25 제거, [settings.md](../features/settings.md) 폐기 이력).

[[ADR-008]] 의 *"401/403 → 설정에서 다시 입력해주세요 배너"*(미구현 보류)도 **배너 없이 자동 이동**
으로 대체된다. **배너를 새로 만들지 않는다.**

### 결정 8 — 설정의 "API 키 변경" 행은 이번에 부활시키지 않는다

무효화가 아닌데 키를 바꾸고 싶은 경우는 이슈 #157 의 미정 3 이고 **#135(설정 구조 개선)와 함께 본다.**

- `useSettingsStore.changeApiKey`(로직·테스트가 살아 있다)는 **배선하지 않고 그대로 둔다** — 그 경로의
  401 은 *"사용자가 방금 나쁜 키를 입력한 것"* 이라 무효화 경로와 **성질이 다르다**(결정 6 의 "키 입력
  화면에서의 401" 과 같은 갈래다).

## 이유

- **결정 1 의 "기다리지 않는다"**: 무효 키 상태에서는 스케줄러·보스·수익 어느 화면도 제 기능을 못 한다.
  액션 버튼을 두고 기다리는 것은 **아무 기능도 없는 화면에 사용자를 붙잡아 두는 것**이다. 액션을 빼는
  근거는 [[ADR-114]] 결정 2 와 같다 — 처방이 그 버튼이 아닌데 버튼을 두면 화면이 두 말을 한다.
- **결정 2 의 "스토어는 라우터를 모른다"**: 이동을 상태 전이의 **결과**로 두면 진입점이 화면 계층에
  묶이지 않는다. 그래서 감지 지점 셋(훅·피커·설정 모달)이 전부 같은 함수 하나를 부를 수 있고, 그것이
  결정 6 의 멱등성이 성립하는 조건이기도 하다(가드가 한 곳에 있다).
- **결정 3 의 "키 하나만"**: 지우는 범위는 *"무엇이 무효가 됐는가"* 로 정한다. 무효가 된 것은 키이고
  계정·모드·추적 목록은 여전히 사실이다. [[ADR-052]] 가 캐시 삭제 범위를 정할 때 쓴 기준과 같은 형태다.
- **결정 4 가 결정 3 과 묶여야 하는 이유**: 키만 지우고 재개를 안 붙이면 사용자는 **키 하나 때문에
  계정 선택·예열·모드·캐릭터를 전부 다시 한다**. 반대로 재개만 붙이고 키를 안 지우면 결정 3 의 "재시작
  하면 되는 것처럼 보이다가 안 되는" 상태가 남는다. 둘은 한 결정의 앞뒤다.
- **결정 5 가 결정 4 의 조건인 이유**: 재개는 *"저장된 값이 여전히 이 키의 것"* 이라는 전제 위에 선다.
  키가 바뀌면 그 전제가 깨질 수 있고, 깨졌는지는 **검증 응답이 이미 말해준다**. 물어볼 수 있는 것을
  가정하지 않는다.

## 기각안

- **전용 키 재입력 라우트(`/api-key` 등)를 새로 판다** — 온보딩 키 입력 단계와 같은 폼·같은 검증·같은
  실패 처리를 두 벌 갖게 된다. 게다가 그 라우트도 결국 "그다음 어디로 갈지"를 재개 규칙에 물어야 해서,
  [[ADR-086]] 결정 1 을 두 번째 호출부로 부르는 것과 다르지 않다.
- **`clearAuthConfig()` 를 그대로 재사용한다** — 한 줄로 끝나 편하지만 `selectedAccountId` 가 함께
  지워져 **결정 4 의 재개가 원리적으로 불가능**해진다(재개가 읽는 값이 그것이다).
- **저장소를 건드리지 않고 화면만 보낸다** — 결정 3 의 "재시작하면 되는 것처럼 보이다가 안 되는" 상태.
- **배너로 알리고 사용자가 누르면 이동한다**([[ADR-008]] 원안) — 배너를 새로 만들어야 하고, 그 배너가
  뜨는 화면들은 어차피 제 기능을 못 한다. 결정 1 의 자동 이동이 같은 목적을 새 UI 없이 이룬다.
- **이탈 라우트를 기억했다 키 재입력 후 되돌린다** — 그 상태를 새로 만들어야 하고 온보딩 완료 후
  `/content` 라는 기존 규칙과 충돌한다(결정 2).
- **설정에 "API 키 변경" 행을 함께 되살린다** — 미정이고 #135 와 함께 보기로 했다(결정 8).

## 트레이드오프

- **작업 중이던 화면을 빼앗는다**(결정 1). 사용자가 보스 목록을 보던 중이었어도 키 입력 화면으로 간다.
  무효 키 상태에서는 그 화면이 어차피 새 데이터를 못 받으므로 **남겨 둘 화면이 없다**는 판단이지만,
  "내가 아무것도 안 했는데 화면이 바뀌었다"는 경험 자체는 비용이다. 토스트 한 줄이 그 이유를 말한다.
- **저장소 삭제가 실패하면 옛 무효 키가 되살아난다**(결정 3). 화면은 키 입력으로 가지만 다음 재시작에
  `completed` 로 복귀하고 첫 동기화에서 다시 이 경로를 탄다. 되돌리는 조치도 재시도도 두지 않는다 —
  **막다른 길이 아니라 같은 길을 한 번 더 도는 것**이라 새 상태를 만들 값이 없다.
- **401 판정이 잘못되면 유효한 키를 지운다.** `NexonAuthError` 는 401/403 에서만 만들어지므로
  (`nexon/http`) 오탐 경로가 좁다고 보고 감수한다. 대가는 사용자가 키를 한 번 다시 붙여넣는 것이고,
  뒤 단계는 결정 4 로 보존되므로 **잃는 것은 키 입력 한 번**이다.
- **여러 화면에서 동시에 401 이 나도 토스트는 1회**(결정 6) — 뒤집으면 **원인이 여럿이어도 하나로만
  보인다**. 지금은 원인이 하나(키)라 문제가 없지만, 401 이 아닌 실패가 같은 진입점을 타게 되면 이
  가드가 그것을 삼킨다. 진입점은 401/403 전용으로 좁게 유지한다.
- **재개 판정 함수가 두 호출부를 갖게 된다**(결정 4) — 부팅과 키 재입력. 공유하지 않으면 진실이 둘이
  되므로 공유가 맞지만, 그만큼 그 함수가 바뀔 때 검사해야 할 경로가 둘이 된다.
- **결정 5 의 가드는 "계정이 겹치면 통과"까지만 본다** — 같은 계정을 포함한 다른 키(권한 범위가 다른
  키 등)는 구분하지 못한다. 그 이상은 응답으로 알 수 없다.

## 범위 밖

맥락으로만 적는다 — **결정이 아니므로 이 phase 에서 구현하지 않는다.**

- **설정의 "API 키 변경" 행 부활** — 결정 8. #135 와 함께.
- **키 입력 화면 자체의 개편** — [[ADR-110]] 이 정한 갈림길 레이아웃 그대로 재사용한다.
- **401 을 애초에 덜 만나게 하는 일**(프리플라이트·동시성 캡) — [[ADR-114]] 가 429 쪽에서 "범위 밖"
  으로 남긴 것과 같은 자리다. 이 ADR 은 401 을 만난 **뒤**만 다룬다.
- **`OPENAPI00003`(조회 불가 ocid) 등 401 이 아닌 영구 실패** — 처방이 다르다(계정 변경). 현행 유지.

## 구현하며 정정한 것

설계에서 벗어난 것이 아니라 **설계가 말하지 않은 자리를 구현이 정한 것**이 대부분이다. 결정 8개는
전부 그대로 구현됐고 폐기된 결정은 없다.

1. **재개 파생은 상태를 바꾸지 않고 "목표"를 반환한다** — 결정 4 는 *"함수 하나를 공유한다"* 까지만
   정했다. 구현은 `deriveResumeTarget(): Promise<ResumeTarget>`(`features/onboarding/resume.ts`)이
   **읽기만 하고 판정 결과를 값으로 돌려주며**, 그 값을 스토어의 지역 함수 `commitResumedStep` 이
   전이로 옮긴다. 그래서 판정이 zustand 밖에서 단위 테스트되고(`resume.test.ts`), 두 호출부는 같은
   판정에 **서로 다른 앞뒤 처리**(부팅은 조기 반환, 재입력은 대조 가드)를 붙일 수 있다.
   - 판정 순서·조건은 `restoreFromStorage` 에 있던 것을 **그대로** 옮겼다([[ADR-086]] 결정 2 의
     `setTrackingMode('auto')` 마이그레이션 1회 쓰기 포함). **기존 온보딩 테스트가 한 건도 수정 없이
     통과**한 것이 순수 이동임의 증거다.
2. **재개 조건에 방어 항 둘이 더 붙었다** — 결정 5 는 계정 대조 가드만 말했으나, 구현은
   `status !== 'awaitingApiKey' && status !== 'selectingAccount' && accounts.some(...)` 다. 앞 둘은
   `setApiKey` 직후라 정상적으로는 올 수 없는 값이고, 왔을 때 throw 하는 대신 **기존 흐름
   (`API_KEY_VERIFIED`)에 떨어뜨린다.**
3. **`invalidateApiKey` 는 새 이벤트를 만들지 않고 `RESET` 을 재사용한다** — 결과가
   `initialOnboardingState` 로 정확히 같아서, 같은 결과의 이벤트를 하나 더 두면 리듀서의 진실이 둘이
   된다. 무효화와 연결 해제의 차이는 **리듀서가 아니라 저장소에서 무엇을 지우는가**에 있다
   (`removeApiKey` vs `clearAuthConfig`). `state.ts` 변경 0줄.
4. **저장소 삭제 실패를 삼킨다** — 결정 3 의 "알려진 열화"를 코드로 옮기면 `try { await removeApiKey() }
   catch {}` 다. rethrow 하면 호출부가 전부 `void` 호출이라 미처리 rejection 이 된다.
5. **감지 지점 셋을 잇는 훅이 하나 생겼다** — `useApiKeyInvalidation(error)`
   (`features/onboarding/use-api-key-invalidation.ts`). 자리가 `features/onboarding/` 인 이유는 이 훅이
   다루는 것이 동기화가 아니라 **온보딩 상태**이기 때문이고(`ScheduleSyncError` 는 `import type` 뿐),
   **자체 중복 가드(ref)를 두지 않는다** — 멱등은 결정 6 의 가드 한 곳이다.
   - 결정 7 표의 "캐릭터 피커 로스터"는 **피커 컴포넌트가 아니라 그것을 띄우는 화면**
     (`ContentScreen`·`BossScreen`)이 `rosterError` 로 부른다. `BossProfitScreen` 은 로스터가 없어
     동기화 경로만 탄다. 온보딩의 `ContentCharacterStep` 은 **일부러 배선하지 않았다**(그 401 은 결정
     6 이 말한 "이 경로가 아닌 401" 이다).
6. **`formatStaleRosterError` 의 시그니처가 줄었다** — 401 의 `설정 열기` 가 사라지자 6종이 피커·온보딩
   두 자리에서 **전부 같아져** `place` 파라미터가 쓰이지 않게 됐다(안 지우면 lint 에러). 이것은 결정 7
   이 예고하지 않은 파생 결과다. `formatRosterError` 는 계속 `place` 를 받는다(온보딩 401 만 재시도를
   유지하므로 — 결정 6).
7. **피커 401 의 인라인 문구를 새로 정했다** — 결정 1 이 정한 것은 **토스트** 문구
   (`API 키가 더 이상 유효하지 않습니다`)뿐이라, `ErrorState` 설명은 구현이 정했다:
   `설정에서 키를 다시 등록해주세요`(거짓이었다 — 설정에 그 자리가 없다) → **`키 입력 화면으로
   이동합니다`**. 이 문구 때문에 어미 단언 정규식에 `합니다` 를 더했다(같은 하십시오체의 다른 활용이라
   [[ADR-062]] 결정 5 를 푸는 것이 아니다).
8. **액션 종류 유니온이 단일 멤버가 됐다** — `RosterErrorCopy.action.kind`·
   `StaleRosterErrorCopy.action.kind` 에서 `'openSettings'` 가 빠져 `'retry'` 하나만 남았다. **`kind`
   필드 자체는 유지한다** — 지우면 호출부 3곳의 분기·`StaleBanner`·`ErrorState` 계약까지 번진다.
   딸려서 `CharacterTrackingPicker` 의 `onOpenSettings` prop 이 사라지고 호출부 2곳이 정리됐다.
9. **설정 401 은 무효화 뒤 `RESET` 까지 한다** — 결정 7 은 *"진입점을 부른다"* 까지만 정했다. 구현이
   `set(RESET)` 을 덧붙인 이유 둘: 화면이 곧 `/onboarding` 으로 가므로 설정 스토어에 `error` 를 남기면
   나중에 설정을 다시 열었을 때 지나간 실패가 되살아나고, `idle` 복귀가 `AccountModal` 의 닫힘 판정이라
   모달이 함께 정리된다.
10. **뒤집힌 옛 테스트는 갱신이 아니라 삭제하고 다시 썼다**(3자리: `settings/store.test.ts` 의
    `refreshAccounts` 401 · `format.test.ts` 의 `place` 파라미터라이즈 · `BossProfitScreen`·
    `BossScreen` 의 옛 `설정 열기` 단언). 계약이 정반대라 같은 이름을 남기면 오독한다. 그래서 step 4
    에서는 테스트 수가 **줄었다**(2,601 → 2,598).
11. **결정 6 의 멱등 가드만으로는 재이동 루프가 막히지 않았다 — 재현하고 고쳤다.** phase 를 마친 뒤
    검토에서 나온 것이고, **실제로 재현된 결함**이다(추론이 아니다).
    - **증상**: 401 → 키 입력 화면 → 키 재입력 성공 → `/content` 복귀 → **곧바로 다시 키 입력 화면**.
      방금 저장한 **유효한 키가 지워진다**. 재입력할 때마다 반복돼 **앱 재시작 전까지 못 들어간다.**
    - **원인 사슬**: 동기화 스토어의 `error` 는 모듈 스코프 zustand 라 화면이 언마운트돼도 살아남는다
      → 재입력으로 `completed` 가 되어 화면이 다시 마운트되면 **이미 처리한 그 401 객체**가 새 effect
      로 들어온다 → 그때 status 는 `completed` 라 결정 6 의 가드를 **통과한다** → 무효화가 다시 돈다.
    - **끊은 고리**: 훅이 *"지속된 값"* 과 *"새 실패"* 를 구분하지 못하는 것(사슬의 셋째 고리).
      `use-api-key-invalidation.ts` 에 모듈 스코프 `WeakSet` 을 두어 **이미 넘긴 error 객체를 기억**한다.
      스토어가 실패마다 새 객체를 set 한다는 이 파일의 기존 전제를 그대로 쓴 것이라, 재입력한 키가
      **또** 무효화되는 경우(새 객체)는 그대로 다시 넘어간다.
    - **훅 인스턴스의 `ref` 로는 안 된다** — 수명이 화면과 같아 재마운트를 넘지 못한다. 그래서 결정 6
      의 *"가드를 두 겹으로 두지 마라"* 와 **모순되지 않는다**: 그 가드는 *동시* 401 을 접는 것이고
      이것은 *지속된* 401 을 거르는 것이라, 막는 대상이 다르다.
    - **기각한 대안**: 무효화 시점에 동기화 스토어 셋의 `error` 를 지우는 것 — 더 근본이지만 온보딩
      스토어가 동기화 스토어 셋을 거꾸로 알아야 해서 의존 방향이 뒤집힌다.
    - 회귀 테스트는 `features/onboarding/__tests__/use-api-key-invalidation.test.tsx` 다(고치기 전에
      먼저 써서 **그 1건만 실패하는 것**을 확인했다).

## 자동 테스트가 담보하지 못하는 것

**전부 실기기·실사용 몫이다.** 아래 넷은 확인된 바 없다.

1. **실제 401 을 받아 본 적이 없다.** 전 경로가 **모킹된** `NexonAuthError` 다 — 넥슨에서 키를 삭제·
   재발급해 진짜 401 이 오는 상황에서 `nexon/http` → `toScheduleSyncError`/`toSettingsError` →
   진입점 사슬이 실제로 이어지는지는 모른다([[ADR-114]] 가 429 에 대해 남긴 것과 같은 종류의 공백).
2. **화면을 빼앗기는 체감**(결정 1 의 트레이드오프). "내가 아무것도 안 했는데 화면이 바뀌었다"가
   실사용에서 어떻게 읽히는지, 토스트 한 줄이 그 이유를 충분히 말하는지는 **눈으로만 판정된다.**
   설계가 대가를 인지하고 고른 것이므로 뒤집을 근거는 실사용 보고뿐이다.
3. **토스트 1회 · 이동 1회가 실기기에서도 그렇게 보이는지**(결정 6). 여러 캐릭터에서 401 이 동시에
   터지는 상황을 실물로 재현한 적이 없다. 테스트는 가드가 있음을 알 뿐 **화면에 토스트가 하나만
   쌓이는 그림**을 보지 못한다.
4. **재입력 후 재개가 실제로 빠른지**(결정 4). 예열을 건너뛴다는 것은 코드로 단언했지만, 캐릭터가 많은
   계정에서 캐시가 정말 따뜻해 **키 입력 직후 `/content` 가 즉시 뜨는지**는 실물 확인이 남았다.
