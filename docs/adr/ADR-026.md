### ADR-026: Live Update 관찰용 UI — 설정 내 "앱 업데이트" 섹션 + 인앱 즉시 적용 (구현 완료)

**배경**: [[ADR-022]]/[[ADR-024]]로 OTA를 도입했지만 체크·적용이 전부 조용히(UI 노출 없이) 이뤄져, 실기기·시뮬레이터에서 "지금 OTA가 실제로 반영되고 있는가"를 눈으로 확인할 방법이 없었다. 베타 채널 검증을 위해 사용자가 업데이트 수신 여부를 관찰할 수 있는 최소 UI를 요청했다(2026-07-15).

**결정**:

1. **설정 화면에 "앱 업데이트" 섹션을 추가한다.** 표시 항목: (a) 현재 실행 중인 번들 버전(`CapacitorUpdater.current().bundle.version` — OTA 적용 후 값이 바뀌므로 반영의 "증거"가 된다), (b) 상태(확인 중 / 최신 / 준비됨 / 오류), (c) 채널(베타/프로덕션, [[ADR-024]] 빌드 시점 분리 값). 기존 버전 푸터(`v{packageJson.version}`)와 별개다 — 푸터는 빌드된 번들 콘텐츠 버전, 섹션은 플러그인이 보고하는 적용 번들 버전이다.

2. **"업데이트 확인" 버튼으로 수동 체크를 제공한다.** 다음 콜드스타트를 기다리지 않고 즉시 `checkForLiveUpdate`를 돌린다. [[ADR-022]] 결정 3의 부팅 시 조용한 백그라운드 체크는 그대로 유지하고, 그 위에 수동 트리거를 더한다.

3. **업데이트가 다운로드되어 준비되면 인앱 "지금 적용(재시작)" 버튼을 노출한다.** 탭하면 `applyLiveUpdate()`(=`CapacitorUpdater.reload()`)로 이미 `next()`로 큐에 든 번들을 즉시 적용한다(기다리지 않고 지금 적용하는 선택지). 실기기·시뮬레이터 검증 결과, [[ADR-022]] 결정 3의 전제였던 "재시작 시 조용한 자동 적용"은 `autoUpdate:'off'`에서는 실제로 일어나지 않는다(아래 결정 7 참고) — 이 버튼(`reload()`) 또는 결정 7의 부팅 자동 적용만이 큐에 든 번들을 실제로 적용한다.

4. **아키텍처**: [[ADR-003]]/[[ADR-005]] 어댑터 원칙에 따라 `native/live-update.ts`가 플러그인 호출을 전담하고, 신규 `features/live-update/store.ts`(zustand)가 상태를 들고, `app/settings`의 섹션 컴포넌트가 표시만 한다. 어댑터 함수: `getCurrentBundleVersion()`(web은 `null` 반환), `checkForLiveUpdate()`(결과 객체 `{ kind }`를 반환하도록 변경 — 기존 `void` 호출부와 호환), `applyLiveUpdate()`(=`reload()`), `applyPendingLiveUpdate()`(결정 7). 부팅 체크(`main.tsx`)를 스토어의 `checkOnBoot`으로 경유시켜, 부팅 중 발견된 업데이트가 섹션에 곧바로 반영되고 수동 버튼과 상태가 한 소스로 일원화된다(같은 번들을 두 번 내려받지 않음).

5. **적용 범위 유지**: 이 UI는 관찰·수동 트리거·적용만 추가한다. OTA 대상 범위([[ADR-022]] 결정 5)·체크섬 검증(결정 4)·롤백(결정 3)은 변경하지 않는다.

6. **실기기 검증에서 드러난 매니페스트 조회 버그 2건을 수정한다**(둘 다 OTA가 실제로 한 번도 돈 적 없어 그동안 가려져 있었음, iOS 시뮬레이터·Android 실기기로 규명):
   - **(a) 매니페스트 캐시**: `latest.json`은 URL이 고정이고 내용만 바뀌어, iOS URLSession·CDN 엣지가 예전 버전을 계속 돌려줬다(한 번 옛 매니페스트를 받은 기기는 새 배포를 영영 못 봄). → `CapacitorHttp.get`에 매 요청 유니크 쿼리 파라미터(`?t=<now>`)와 `Cache-Control: no-cache`를 붙여 모든 캐시 층을 우회한다.
   - **(b) 문자열 응답**: GitHub Releases CDN이 자산을 `application/octet-stream`으로 내려줘 `CapacitorHttp`가 JSON 자동 파싱을 안 하고 `response.data`를 **문자열**로 준다. 기존 `response.data as LiveUpdateManifest`는 런타임에 문자열이라 `manifest.version`이 `undefined` → `isNewerVersion`이 예외 → 항상 실패했다. → `parseLiveUpdateManifest`가 문자열이면 `JSON.parse`, 객체면 그대로 쓰고 형식 검증까지 한다.

7. **다운로드된 업데이트를 "다음 앱 실행 시" 자동 적용한다** — 부팅 시퀀스 맨 앞에서 `applyPendingLiveUpdate()`(=`getNextBundle()`로 대기 번들 확인 → 현재와 다르고 error 상태가 아니면 `reload()`)를 돌린다. 세션 A 부팅에서 조용히 받아 큐에 넣고, 세션 B 부팅에서 자동 적용된다. 롤백된(error) 번들은 건너뛰어 무한 롤백 루프를 막고, `getNextBundle()`이 대기 없을 때 네이티브가 `null`(브릿지 거쳐 JS엔 `undefined`)을 줘도 `== null`로 안전 처리(실기기 규명). **플랫폼 차이(실측)**:
   - **Android**: `autoUpdate:'off'`에서 capgo가 `next()` 큐를 재시작·포그라운드에도 스스로 적용하지 않음(`appMovedToForeground` → "Auto update is disabled", force-stop 후 재실행 시 재다운로드만 반복). 여기서 `applyPendingLiveUpdate()`가 실제로 적용을 수행한다(logcat: `Applying pending bundle before reload: 1.0.1` → `Version successfully loaded: 1.0.1`).
   - **iOS**: capgo가 큐에 든 `next()`를 **콜드 스타트에서 네이티브로 알아서 적용**한다(재시작만으로 1.0.1→1.0.2 자동 반영, `지금 적용` 탭 없이 확인). 이 경우 `applyPendingLiveUpdate()`는 `getNextBundle()`이 이미 소진돼 `null`을 반환하므로 무해한 no-op이다.
   - 결과적으로 **양 플랫폼 모두 다음 실행 시 자동 적용**되며, `applyPendingLiveUpdate()`는 Android에서 load-bearing, iOS에서 안전망 역할을 하는 크로스플랫폼 구현이다. 즉 "iOS=수동/Android=자동"이 아니라 둘 다 자동 적용 + 인앱 즉시 적용(결정 3)을 모두 지원한다.

**트레이드오프**:
- 부팅 체크를 스토어로 경유시키며 `main.tsx`가 `features/live-update` 스토어에 의존하게 됐다. 다만 `notifyLiveUpdateReady()`(네트워크 이전 최우선 호출)는 여전히 스토어와 무관한 bare 호출로 남긴다.
- `reload()`/`set()`은 JS 컨텍스트를 즉시 파괴하므로 "지금 적용" 이후 코드는 실행되지 않는다(플러그인 계약). 이 시점에 저장할 상태가 없어 문제되지 않는다.
- 결정 7의 자동 적용은 세션 B 부팅에서 `reload()`를 부르므로, 그 부팅에 한해 (1.0.0을 잠깐 로드 → 새 번들로 재로드) 스플래시가 한 번 더 도는 짧은 재초기화가 생긴다. 대기 업데이트가 있을 때만 발생하고 네이티브 스플래시가 덮어 흰 화면은 없다.
- 웹/개발 서버에서는 네이티브 플러그인이 없어 섹션이 "이 플랫폼에서는 지원되지 않음"으로 비활성화되고, 현재 버전은 `package.json` 값으로 폴백한다.

**검증(2026-07-15, 실측)**: iOS 시뮬레이터(iPhone 17 Pro)에서 1.0.0 → 업데이트 확인 → 다운로드 → "준비됨(v1.0.1)" → 지금 적용 → **현재 버전 1.0.1·푸터 v1.0.1** 전 과정 스크린샷 확인. Android 실기기(HyperOS)에서 부팅 백그라운드 체크가 `live-update-beta`의 1.0.1을 받아 체크섬 검증(sha256 `4ec8d8ba…`가 GitHub Release의 `1.0.1.zip`·`latest.json`·기기 다운로드본 3자 일치) 후 `next()` 큐잉까지 logcat으로 확인. `x.y.z` 버전 형식([[ADR-024]])·베타 채널·직접 APK 사이드로딩 경로 모두 실동작.
