# ADR-352: 서버 가격 줄이 기록 상태를 든다. 가격 없는 기록도 올리고, 지우기는 기록이 사라진 때만이다

> 🟢 유효 · 2026-10-19 · 사용자 지정 · **구현 완료**(앱 · 서버, 같은 날. 서버 배포 전 · OTA 전 · 실기기 미검증)

**관련**: [[ADR-342]] 정정 1(`deleted_at` 이 가격을 뺀 자리였다. 결정 4 가 지운다) · [[ADR-342]] 정정 4(상태가 없는
드롭은 안 보낸다고 했다. 결정 2 가 보낸다) · [[ADR-342]] 열린 질문(지운 드롭의 서버 줄. 결정 3 이 닫는다) ·
[[ADR-343]] 결정 3(종류마다 함수 둘. `read` 가 `null` 이면 지우기라는 약속은 그대로다)
**문서**: `features/item-drop.md`(기기 쪽 가격 상태 셋) · `README.md` 의 서버 전송 줄

## 맥락

서버 `drop_prices` 는 가격이 있는 기록만 받았다. 기록 안함(`'excluded'`)과 미입력은 둘 다 `DELETE` 로 보내
`deleted_at` 을 채우는 것이 거두는 길이었다([[ADR-342]] 정정 1). 그래서 두 가지가 어긋났다.

- **한 번도 올라간 적 없는 기록에 `DELETE` 가 나간다.** 드롭을 기록하고 바로 기록 안함을 누르면 서버에는
  줄이 없는데 지우기 요청이 간다. 서버는 못 찾고 아무 일도 안 하지만 요청 자체가 이상하다(사용자 지적
  2026-10-19).
- **미입력 기록은 서버가 모른다.** 시트에서 가격 없이 저장한 드롭은 `setBossDrops` 가 건너뛰어 아무것도 안
  보냈다. 그 기록이 나중에 가격을 받으면 그때 처음 올라간다. 서버가 보는 것은 판 것만이고, 먹었는데 안 판
  것이 얼마나 되는지는 안 보인다.
- **기기에서 지운 기록은 서버에 남는다.** 시트에서 아이템을 해제해 저장하면 기기 행은 지워지지만 서버 줄은
  그대로다. 난이도 확정으로 걷힌 드롭도 같다([[ADR-342]] 열린 질문).

`DELETE` 하나가 「가격을 뺐다」와 「기록이 사라졌다」 둘을 말하고 있었고, 「가격이 아직 없다」는 말할 수단이
없었다.

## 결정

### 결정 1. `drop_prices.record_status` 가 기록의 상태를 든다 (사용자 지정)

PG enum `drop_record_status` 넷이다. `NOT NULL` 이고 기본값은 없다.

| 값 | 뜻 | 기기 쪽 |
|---|---|---|
| `pending` | 기록은 있고 가격이 아직 없다 | `price_state` 가 `NULL`(미입력) |
| `completed` | 가격이 있다 | `'entered'` |
| `skipped` | 값을 매기지 않기로 했다 | `'excluded'`(기록 안함) |
| `deleted` | 기기에서 기록이 사라졌다 | 행이 없다 |

`price_meso` 는 `completed` 만 값을 갖는다. 나머지 셋은 `NULL` 이고 `CHECK` 가 그것을 강제한다
(`(record_status = 'completed') = (price_meso IS NOT NULL)`). 0 으로 적지 않는 것은 기기 쪽과 같은 이유다.
0 은 「0메소에 팔았다」라 미입력과 구분이 사라진다.

분포(`summary`)는 `completed` 만 센다. 부분 인덱스도 `WHERE record_status = 'completed'` 다.

### 결정 2. 가격이 없는 기록도 올린다

`dropPricePayloadOf` 가 기기의 가격 상태를 서버 상태로 바꿔 **상태가 무엇이든 값을 만든다.** `null` 을 돌려주는
것은 아이템 key 가 없는 옛 행뿐이다(서버가 그 칸을 분포의 축으로 쓴다).

- 시트 저장(`setBossDrops`)이 **저장된 드롭 전부**를 보낸다. 상태가 없는 드롭을 건너뛰던 줄을 걷는다.
- 난이도 확정 이관(`migrateDropsToConfirmedDifficulty`)도 옮긴 드롭 전부를 보낸다.
- 가격 화면의 `writePrice` 는 전부터 두 상태를 다 보냈고 그대로다.

전송값에 `status` 가 서고 `priceMeso` 가 `null` 일 수 있다. 서버 DTO 는 `status` 가 없으면 `completed` 로 읽는다.
이 칸이 생기기 전 OTA 가 `status` 없이 가격만 보내기 때문이다.

### 결정 3. `DELETE` 는 기기에서 기록이 사라진 때만이다 (사용자 지정)

서버는 그 줄을 `deleted` 로 표시하고 `price_meso` 를 비운다. 줄은 안 지운다([[ADR-340]] 정정 3).

앱이 `DELETE` 를 보내는 자리는 셋이다.

- **시트 저장에서 빠진 드롭.** `setBossDrops` 가 저장 전 `dropsByRowKey` 의 식별자와 저장 뒤 식별자를 비교해
  빠진 것마다 `reportDropRemoved` 를 부른다. 해제하고 같은 세션에 다시 고른 드롭은 `replaceBossDropRecords` 가
  신분으로 식별자를 물려주므로 빠진 것으로 안 센다.
- **획득 불가로 걷힌 드롭.** 확정 난이도에서 못 얻는 드롭은 기기에서 걷히는데(`pruneUnobtainableDrops`), 그
  식별자마다 `reportDropRemoved` 를 부른다. 걷는 자리가 둘이다. 난이도 확정 이관(`migrateDropsToConfirmedDifficulty`,
  같은 타일이 이미 있어 걷힌 것도 포함)과 로드 때의 영구 걷기(`loadDropsByRowKey`)다. [[ADR-342]] 열린 질문이
  이것으로 닫힌다.
- **대기 표의 원본이 사라진 때.** `read` 가 `null` 이면 고리가 `DELETE` 를 보낸다([[ADR-343]] 결정 3). 전부터
  그랬고 이제 그 뜻이 맞는다.

`reportDropRemoved` 는 기록을 다시 읽을 수 없어 기간 키를 인자로 받는다. 기준 기간([[ADR-342]] 결정 8) 앞이면
보내지 않고, 실패하면 대기 표에 적는다. 다음 회차는 원본이 없으므로 그대로 `DELETE` 다.

### 결정 4. `deleted_at` 을 지운다 (사용자 지정)

상태는 `record_status` 하나가 말한다. 두 칸이 같은 사실을 들면 어긋남을 관리해야 한다. 시각은 `updated_at` 으로
본다. 마이그레이션이 `deleted_at` 이 찬 줄을 `deleted` 로, 나머지를 `completed` 로 옮기고 칸을 떨어뜨린다.

### 결정 5. 배포는 서버가 먼저다

새 앱은 `priceMeso: null` 과 `status` 를 보낸다. 옛 서버는 `priceMeso` 가 1 이상이어야 받으므로 pending · skipped
를 400 으로 거절하고, 앱은 5회 뒤 그 건을 버린다([[ADR-343]] 결정 5). 서버를 먼저 올리면 옛 앱의 전송은 그대로
받힌다(`status` 없음 → `completed`, 기록 안함 `DELETE` → `deleted`). 옛 앱의 기록 안함이 `skipped` 가 아니라
`deleted` 로 남는 것은 OTA 가 나갈 때까지의 일이고 받아들인다.

관리 화면 드롭 가격은 상태 칸을 더하고 `completed` 가 아닌 줄을 흐리게 보인다. `deleted` 만 가로줄을 긋는다.

## 대가

- 서버 줄이 는다. 먹은 것 전부가 줄이 되고 판 것은 그 일부다. 분포는 `completed` 만 세므로 수치는 안 움직인다.
- 「처음 뺀 시각」이 사라진다. `deleted_at` 이 들던 값이고 `updated_at` 은 그 뒤 고치면 움직인다.
- `DELETE` 의 뜻이 바뀌어 옛 앱의 기록 안함이 OTA 전까지 `deleted` 로 적힌다(결정 5).

## 기각

- **기록 안함을 `DELETE` 로 그대로 두고 미입력만 `pending` 으로 올린다.** 기록 안함도 사용자의 결정이라 서버가
  알 가치가 있고, 올라간 적 없는 기록에 `DELETE` 가 나가는 어긋남이 그대로 남는다.
- **`price_meso` 를 0 으로 적고 `NOT NULL` 을 지킨다.** 집계가 상태로 걸러야 하고 0 이 「0메소에 팔았다」와
  섞인다. 기기 쪽이 `NULL` 을 고른 이유와 같다.
- **`deleted_at` 을 `record_status` 와 함께 남긴다.** 두 칸이 같은 사실을 말해 어긋나지 않게 관리해야 한다.
  처음 뺀 시각 하나를 위해 그 비용을 지지 않는다.

## 열린 질문

- **옛 앱이 `deleted` 로 적은 기록 안함.** OTA 뒤 그 기록을 다시 열어 기록 안함을 누르면 `skipped` 로 덮인다.
  안 누르면 `deleted` 로 남는다. 되짚어 고칠 길은 두지 않았다.
