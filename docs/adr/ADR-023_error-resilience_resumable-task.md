# ADR-023 이어서 하는 작업과 기록 판 알림

> 🟢 유효
> 옛 번호: ADR-307 · ADR-309
> 관련 소스: `features/resumable-task/` · `app/resumable-task/` · `storage/pending-tasks.ts` · `storage/sqlite/transaction.ts` · `components/organisms/TaskProgressModal` · `components/organisms/TaskResumeModal` · `storage/record-revision-batch.ts`

## 배경

MVP 등급의 수수료 작업 둘([[ADR-050]])은 이미 있는 기록을 다시 쓴다. 처음 구현은 기록마다 따로 `UPDATE` 했고
트랜잭션이 없었다. 그래서 중간에 앱이 닫히면 일부만 바뀐 채 남았고, 기록이 많으면 느렸고, 그동안 화면에는 버튼의
스피너만 돌았다.

기기 DB 의 이관(`storage/sqlite/migrations.ts`)은 스키마 버전에 묶여 DB 를 열 때 돈다. 사용자가 무언가를 골랐을
때 도는 작업은 이관에 넣을 수 없다. 그래서 사용자가 고른 때에 돌고, 앱이 닫혀도 다음에 이어서 끝나는 범용
기능을 따로 만들었다.

같은 시기에, 기록을 여러 건 쓰는 반복에서 쓸 때마다 화면이 다시 그려지는 문제도 드러났다. 수익·지출 탭에 처음
들어간 한 회차에서 보스 기록 쓰기가 60번, 처치 날짜 쓰기가 121번이었다. 저장 계층은 쓰기 한 번마다 판을
올리고 구독자를 부르므로, 판을 구독하는 화면이 그만큼 다시 그려졌다. 아이템 가격 입력 버튼은 포털 안에 있어
다시 그릴 때마다 effect 안에서 갱신을 보낸다. 그래서 개발 빌드에서 `Maximum update depth exceeded` 가 떴다.

## 결정

### 결정 1. 작업은 남은 일을 스스로 세는 단계들로 만든다

작업(`ResumableTask`)은 이름 · 배지 아이콘 · 진행 제목 · 단위 · 단계 목록 · 완료 토스트 문구를 갖는다. 단계는
함수 둘이다.

- `remaining()` 은 남은 일의 수를 센다.
- `runChunk(limit)` 는 남은 일 중 앞의 `limit` 개를 SQLite 트랜잭션 하나로 처리하고, 처리한 수를 돌려준다.
  `limit` 은 200 이다.

처리한 일은 다시 남은 일로 세지 않는다. 그래서 어디서 멈췄는지 따로 적지 않아도 다시 돌리면 남은 것부터 한다.
앱이 조각 도중에 닫히면 그 조각만 되돌아가고 앞의 조각은 남는다. 러너는 처리한 수가 `limit` 보다 적으면 그
단계가 끝난 것으로 본다. 남은 일을 셀 수 없는 작업(한 번 읽고 끝나는 계산)은 이 기능으로 처리할 수 없다.

### 결정 2. 시작하기 전에 끝나지 않은 작업 표시를 적고, 남은 일이 0 이 되면 지운다

표시는 Preferences `pendingTasks` 한 칸이다. 작업마다 `id` 와, 시작할 때 단계마다 남아 있던 수(`totals`)를
적는다. 진행률의 분모가 `totals` 이고 분자는 `totals − remaining()` 이다.

- 표시를 먼저 적고 나서 첫 조각을 돌린다. 반대 순서면 그 사이에 앱이 닫혔을 때 이어서 할 방법이 없다.
- 작업 정의는 등록부(`app/resumable-task/registry.ts`)에서 `id` 로 찾는다. 등록부에 없는 `id` 의 표시는 묻지 않고
  지운다. 앱 버전이 내려가 정의가 없어진 경우다.
- 캐시를 지울 때도 이 표시는 남긴다(`KEEP_KEYS`). 지우면 반쯤 바뀐 기록이 그대로 남는다.
- 표시(Preferences)와 조각(SQLite)은 한 트랜잭션이 아니다. 그래서 남은 일이 0 인데 표시가 남는 경우가 있다.
  다음에 열 때 남은 일을 세어 0 이면 묻지 않고 지운다.

### 결정 3. 진행률 모달은 범용 부품 하나다

`TaskProgressModal` 은 작업이 준 배지 아이콘과 제목을 맨 위에 보인다. 단계가 둘 이상이면 단계 목록을 보인다. 끝난
단계는 체크와 건수, 진행 중인 단계는 스피너와 `N / M건`, 남은 단계는 `대기` 를 보인다. 맨 아래에는 막대 · 건수 · 퍼센트가
있다.

- 닫는 버튼이 없고, 바깥을 눌러도 뒤로가기를 해도 닫히지 않는다. 작업이 끝나면 스스로 닫힌다.
- 0.3초 안에 끝나면 띄우지 않는다. 등급 하나를 고친 뒤 몇 건만 다시 계산할 때 모달이 한 번 번쩍이지 않게 하려는
  것이다.
- 캐릭터 관리 저장도 같은 부품으로 그린다(제목 `캐릭터 정보를 저장하고 있어요`, 단위 `개`, 사람 아이콘). 이
  저장은 네트워크 조회라 남은 일을 셀 수 없어서 표시를 남기지 않고, 이어서 하기 대상도 아니다. 0.3초 규칙도 적용하지 않는다.

### 결정 4. 앱을 다시 열었을 때 끝나지 않은 작업이 있으면 이어서 할지 묻는다

진입 단계가 `ready` 가 되면 `TaskHost` 가 표시를 읽는다. 남은 일이 있으면 `TaskResumeModal` 을 띄운다.

- 제목은 `끝나지 않은 작업이 있어요`, 설명은 `앱이 중간에 닫혀 멈춘 작업이에요. 멈춘 곳부터 이어서 진행해요.` 이고
  모든 작업이 같이 쓴다. 제목에 작업 이름을 넣지 않는 것은 이름마다 조사(이/가)가 달라지기 때문이다.
- 작업마다 이름 · 멈춘 곳까지의 막대 · `N / M건` 을 한 줄에 보인다. 앞 작업 뒤에서 아직 손대지 않은 작업은 `대기`
  로 적는다.
- 버튼은 `이어서 진행하기` 하나다. `나중에` 는 두지 않는다. 미루면 그동안 일부만 바뀐 기록으로 금액을 계산하게
  된다. 바깥을 누르거나 뒤로가기를 해도 닫히지 않는다.
- 누르면 진행률 모달이 0.3초를 기다리지 않고 바로 뜬다. 사용자가 직접 누른 일이라서다. 진행률 모달이 뜰 때까지 확인
  모달은 버튼 스피너로 남아, 두 모달 사이에 뒤 화면이 비치지 않게 한다.
- MVP 등급 모달보다 먼저 뜬다. 확인을 마쳤고(`checked`), 진행 중인 작업도 이어서 하기 확인도 없을 때만 등급 모달이 뜬다.
  등급 모달의 답이 새 작업을 만들어 순서가 꼬이기 때문이다.
- 작업을 겹쳐 부르면 앞 작업이 끝난 뒤에 돈다.

### 결정 5. 끝나면 완료 토스트를 띄우고, 실패하면 알리고 닫는다

끝나면 작업이 준 문구로 완료 토스트를 띄운다. 처리한 수가 0 이면 띄우지 않는다.

작업 도중 저장소 오류가 나면 그 조각만 되돌아가고 표시는 그대로 남는다. `작업을 마치지 못했어요` 토스트를 띄우고
모달을 닫는다. 다음에 앱을 열 때 이어서 하기 확인이 다시 뜬다. 실패한 직후 확인을 곧바로 다시 띄우지 않는
것은 `나중에` 가 없기 때문이다. 같은 실패가 되풀이되면 사용자가 앱을 쓸 수 없게 된다.

### 결정 6. 작업이 바꾼 표는 판을 올린다

`income_records` 에도 판(`getIncomeRecordsRevision`)이 있고, 가계부의 `cashbookDataRevision` 은 이 판을 드롭 · 결정석
판과 함께 더한다. 그래서 수수료 작업이 수입 기록만 바꿔도 가계부가 다음에 화면을 열 때 다시 읽는다.

### 결정 7. 기록을 여러 건 쓰는 반복은 끝날 때 판 알림을 한 번 보낸다

`batchRecordWrites(write)` 안에서 판이 올라도 구독자를 바로 부르지 않고, 가장 바깥 `batchRecordWrites` 가 끝날 때 한
번 부른다(`storage/record-revision-batch.ts`).

- 판 수는 쓸 때마다 바로 오른다. 미루는 것은 알림뿐이다. 그 사이 다른 이유로 다시 그려지는 화면은 새 판을 보고
  다시 읽는다.
- 반복 도중 예외가 나도 알린다. 던지기 전에 쓴 기록이 있을 수 있어서다.
- 반복이 겹치면 마지막 반복이 끝날 때 한 번 알린다. 수익·지출 탭의 한 회차가 오늘 기록과 지난 기간 기록을 나란히
  쓰기 때문이다.

`batchRecordWrites` 로 감싼 곳은 기록을 여러 건 쓰는 반복 네 군데다.

| 반복 | 위치 |
|---|---|
| 자동 기록 | `features/boss-profit/auto-record.ts` 의 `autoRecordRows` |
| 지난 기간 기록 | `features/schedule-window/records.ts` 의 `recordBossProfitFromWindow` |
| 드롭 정리 | `features/boss-profit/drops-loader.ts` 의 `loadDropsByRowKey` 에서 얻을 수 없는 드롭을 지우는 반복 |
| 처치 날짜 | `features/boss-profit/defeat-dates.ts` 의 `runResolveDefeatDates` 에서 날짜를 적는 반복 |

처치 날짜는 쓰는 반복만 감싼다. 앞의 API 조회까지 감싸면 조회가 도는 몇 초 동안 다른 곳의 알림까지 묶이기
때문이다. 한 건만 쓰는 곳(가격 입력 · 직접 완료 · 파티 설정)은 지금처럼 바로 알린다. 판을 올리는 반복을 새로
만들 때는 `batchRecordWrites` 로 감쌀지 그때 정해야 한다. 감싸지 않으면 쓰기마다 알린다.
