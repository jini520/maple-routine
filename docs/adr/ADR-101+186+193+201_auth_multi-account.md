## 배경

넥슨 계정을 여러 개 쓰는 사용자가 모든 계정의 캐릭터를 앱 하나에서 관리하게 한다(사용자 지정 2026-10-26, 다시 정함
2026-11-08 · 11-09). 1.0.14 에 낸다(사용자 지정). 이슈는 하나로 둔다(사용자 지정).

메이플스토리의 계정 단위는 이 순서다.

```
넥슨 계정(넥슨 로그인 또는 API 키 하나) > 메이플 ID > 캐릭터
```

기기 저장소에는 다계정에 필요한 칸이 이미 있다. 인증 수단마다 넥슨 계정 id 가 붙어 있고, `character_accounts` 가 캐릭터를
메이플 ID 와 넥슨 계정으로 잇는다([[ADR-098]] 결정 5 · 6). 계정 공유 컨텐츠의 진행 원장도 메이플 ID 마다 따로 저장한다.

2026-11-08 · 11-09 에 코드를 읽어 보니 아래가 다계정을 막거나, 계정을 바꿔 로그인할 때 문제를 만든다.

- 넥슨을 부를 때 인증 수단을 하나만 고른다(`credentialOf`: 로그인, 없으면 첫 키). 스케줄 회차는 그 수단의 `character/list` 에
  없는 추적 캐릭터를 월드 이전 후보로 넘긴다(`settleStrandedCharacters`). 그래서 다른 넥슨 계정의 캐릭터는 `조회 불가` 가 된다.
- today 공유 컨텐츠 위젯은 추적 캐릭터 전부의 진행을 합친다(`buildSharedContents`). 하나라도 완료면 완료로, 횟수는 최댓값으로
  그린다. 넥슨 계정이 하나여도 메이플 ID 가 둘이면 지금 이미 두 메이플 ID 의 진행이 섞인다.
- 주간 결정석 판매 한도 위젯은 월드로만 묶는다(`summarizeWorldCrystals`). 메이플 ID 가 다른 캐릭터의 판매가 같은 월드에서 더해진다.
- 로그아웃하거나 다른 계정으로 로그인해도 추적 목록을 비우지 않는다. 다른 계정으로 로그인하면 캐릭터 설정 화면이 앞 계정의
  캐릭터가 선택된 채로 시작한다(`useSelectionDraft` 가 저장된 추적 목록에서 시작한다).
- 로그아웃한 뒤 같은 넥슨 ID 로 다시 로그인하면 로그인이 새 계정 id 를 받는다(`setNexonLogin` 의 `randomUuid()`). 키는 메이플 ID 로
  옛 id 를 잇지만(`reusableNexonAccountId`) 로그인은 잇지 않는다. 강화 수집기는 조회 기록과 다시 매기기 진행을 계정 id 로 나눠 두므로,
  새 id 로 지난 날짜를 다시 받아 같은 강화 내역을 한 줄 더 적는다. `enhancement_totals` 의 `UNIQUE` 에 계정 id 가 들어 있어 두 줄이
  막히지 않고, 가계부는 계정을 가리지 않고 읽는다(`loadEnhancementTotals`). 그래서 같은 강화가 가계부에 두 번 잡힌다. 코드로 읽은
  것이고 기기에서 재현하지는 않았다.

## 결정

### 결정 1. 다계정은 넥슨 로그인 사용자만 쓰고, 부계정은 API 키로 등록한다

- 메인 계정은 넥슨 로그인이다. 부계정은 모두 API 키로 등록한다(사용자 지정).
- 넥슨 계정은 로그인을 포함해 최대 5개다(사용자 지정 2026-11-09). 계정이 하나 늘 때마다 그 계정의 `character/list` 와 강화 내역
  수집이 따로 돌아 호출이 늘기 때문에 상한을 둔다. 그래서 상한은 이 기기에 있는 계정으로 센다(사용자 선택 2026-11-12). 늘어나는
  호출은 기기마다 따로이고, 다른 기기에서 등록한 부계정은 이 기기가 부르지 않는다(결정 6).
- 넥슨 로그인을 하지 않은 사용자는 부계정을 등록할 수 없다. 지금처럼 계정 하나만 쓰고, 그 계정이 API 키여도 된다.

### 결정 2. 계정 관리 화면을 설정에 두고, 부계정은 여기서 등록하고 지운다

- 설정에 `계정 관리` 화면을 더한다. 등록한 넥슨 계정 목록, API 키 입력, 메이플 ID 이름 바꾸기(결정 8)가 있다. 화면 구성은 시안에서
  정한다(시안 https://claude.ai/artifact/LoGNQzRyUqjDoMmjsytR4y).
- 목록은 넥슨 계정(넥슨 로그인 하나, API 키마다 하나)마다 묶는다(사용자 지정 2026-11-11). 계정마다 `넥슨 ID 계정 설정` ·
  `API 키 1 계정 설정` 같은 행 하나만 누를 수 있고, 누르면 그 계정의 상세 페이지가 열린다. 그 아래 그 계정의 메이플 ID 이름은 글자로만
  보인다. API 키의 번호는 등록한 차례다.
  - 넥슨 ID 계정은 카드 하나에 따로 두고, API 키 계정들은 한 카드에 이어 둔다. 그 두 카드 사이 오른쪽에 `API 키 추가` 글자 버튼을
    둔다(사용자 지정 2026-11-11).
  - API 키가 하나도 없으면 API 키 카드 자리에 빈 상태 카드(`EmptyState` inline)를 둔다. 제목은 `등록한 API 키가 없어요`, 설명은
    `다른 넥슨 계정의 API 키를 추가하면 그 계정의 캐릭터도 함께 관리할 수 있어요.` 다. 추가는 위의 글자 버튼 하나라 카드 안에 버튼을 두지
    않는다(사용자 선택 2026-11-11). 그래서 키를 넣기 전과 뒤에 추가 버튼의 자리가 같다.
  - 넥슨 계정이 5개(결정 1)여도 `API 키 추가` 를 숨기지 않는다. 누르면 `NoticeModal` 로 알린다(사용자 선택 2026-11-11). 제목은
    `더 추가할 수 없어요`, 안내는 `넥슨 계정은 넥슨 ID 를 포함해 5개까지 등록할 수 있어요.`, 주 버튼은 `확인` 이다. 버튼을 숨기거나
    흐리게 막으면 왜 추가할 수 없는지 보이지 않는다.
  - 키를 추가하면 시트가 닫히고 목록에 그 계정 행이 선다. 다른 화면으로 옮기지 않는다. 그 계정의 캐릭터는 `캐릭터 관리` 에서 고른다.
  - 목록에는 이 기기에 키가 있는 계정만 선다. 부계정은 기기마다 따로 관리하기 때문이다(결정 6). 다른 기기에서 등록한 부계정은 이
    기기에서 그 키를 추가해야 선다.
  - 키 변경 · 키 삭제는 상세 페이지에서 계정 단위로 한다. 키 하나가 넥슨 계정 하나라서다. 키 하나에 메이플 ID 가 둘 이상일 수 있어,
    메이플 ID 단위로 두면 한 메이플 ID 에서 지운 키가 다른 메이플 ID 까지 지운다.
  - 이름 바꾸기는 같은 상세 페이지에서 메이플 ID 마다 한다. 이름은 메이플 ID 마다 붙기 때문이다(결정 8). 페이지 안의 칸에서 고치고,
    입력 카드를 띄우지 않는다(사용자 지정).
  - 상세 페이지는 위에 `메이플 ID 이름` 칸들, 아래에 `API 키` 묶음(`API 키 변경` · `API 키 삭제`)을 둔다(사용자 선택 2026-11-11). 이름
    칸 위에는 대표 캐릭터를 라벨로 적고, 칸 오른쪽에 연필 아이콘을 둔다(사용자 지정). 고친 이름은 이름 칸들을 담은 카드 안 맨 아래의
    `저장` 버튼으로 저장한다(사용자 지정). 아래에 고정하면 바로 끝나는 `API 키 변경` · `API 키 삭제` 와 섞여 무엇을 저장하는지 모호하다.
    `저장` 을 누르지 않고 페이지를 나가면 고친 이름을 버린다(사용자 선택 2026-11-11). 앱의 다른 설정 화면도 나갈 때 묻지 않는다.
    넥슨 ID 계정은 `API 키` 묶음 없이 이름 칸만 둔다.
  - 키는 지금의 키 입력 시트(`ApiKeySheet`, 위에서 내려오는 시트)로 받는다. 제목만 연 곳에 따라 `API 키 추가`(목록) · `API 키 변경`(상세)
    이고, 나머지는 같다(사용자 지정 2026-11-11). 같은 넥슨 계정의 키만 받는다는 안내는 시트에 두지 않고, 다른 계정의
    키를 넣었을 때 결정 3 의 모달로 알린다(사용자 지정).
  - `API 키 삭제` 의 확인 모달은 계정 삭제 확인과 같은 틀이다. 제목 `API 키를 삭제할까요?`, 안내 `이 기기에서 키를 지우고, 이 계정의
    캐릭터를 추적에서 빼요. 보스 수익 · 가계부 기록은 그대로 남아요.`, 주 버튼 `취소`, 그 아래 빨간 글자 버튼 `API 키 삭제` 다.
- 설정의 `캐릭터 · 보스` 묶음에서 `캐릭터 관리` 위에 `계정 관리` 행을 두고, 묶음 이름을 `계정 · 캐릭터 · 보스` 로 바꾼다(사용자 선택
  2026-11-11). 부계정을 등록해야 그 계정의 캐릭터를 고를 수 있어서 두 행을 잇달아 둔다.
- 넥슨 로그인을 하지 않은 사용자도 이 화면에서 메이플 ID 이름을 바꿀 수 있다. 부계정 등록만 막는다. 메이플 ID 이름은 가계부에도
  보이므로(결정 8) 다계정이 아닌 사용자에게도 필요하다.
  - 이 사용자의 목록은 `API 키 계정 설정` 카드 위에 넥슨 로그인 블록을 둔다(사용자 지정 2026-11-11). 로그인 사용자의 `넥슨 ID 계정 설정`
    카드 자리다. 블록 안 맨 위에 `부계정을 추가하려면 넥슨 로그인이 필요해요.` 를 칸 바탕 없이 글자로 두고, 그 아래에 넥슨 로그인 버튼
    (`NexonLoginButton`)을 둔다. 버튼은 좌우를 4px 씩 줄이고 아래를 8px 더 띄운다. 카드 모서리(14)와 버튼 그림의 모서리(6)가 붙으면
    어긋나 보이기 때문이다(사용자 지정).
    `API 키 추가` 는 두지 않는다.
  - 이 버튼은 today 의 `넥슨 ID 연동하기` 와 같은 연동이다. 새 로그인이 아니라 추적 목록을 비우지 않고, 지금 키는 그 로그인의 부계정이
    된다(결정 5 · 14).
  - 이 사용자의 `API 키 계정 설정` 상세에는 `API 키 변경` 만 두고 `API 키 삭제` 는 두지 않는다. 이 키가 유일한 수단이라 지우면 로그아웃과
    같아지고, 키를 떼는 것은 `앱 정보 및 계정` 의 로그아웃이 맡는다. `API 키 변경` 은 [[ADR-024]] 결정 11 의 메인 키 바꾸기와 같다.
- 부계정을 지우면 확인 모달을 띄우고, 그 계정의 추적 캐릭터를 함께 추적에서 뺀다(사용자 지정 2026-11-08). 남겨 두면 부를 수단이
  없는 캐릭터가 `조회 불가` 로 계속 서기 때문이다. 보스 수익 · 가계부 기록은 지우지 않는다.
  - 지우기는 이 기기에서만 한다. 서버의 등록 정보(결정 6)는 지우지 않는다(사용자 선택 2026-11-12). 같은 키를 다른 기기에서 계속 쓰면
    그 기기의 기록이 이 사람에게 이어져야 하기 때문이다. 서버에 묻지 않으므로 서버 때문에 지우기가 실패하는 일은 없다.
- 부계정 키가 429 를 받으면 다시 시도 모달의 `다른 키 입력` 이 그 계정의 상세 페이지를 열고 `API 키 변경` 시트를 바로 띄운다
  ([[ADR-024]] 결정 11). 키를 바꾸는 규칙은 결정 3 에 있다. 이 화면이 생기기 전에는 그 모달에 `다시 시도` 만 두므로, 이 화면을 만들 때 그 버튼을 잇는다(`app/auth/ApiKeyNoticeModal.tsx`
  의 `canEnterOtherKey`).

### 결정 3. 키를 등록하기 전에 셋을 검증하고, 하나라도 걸리면 등록하지 않는다

1. **유효한 키인가.** `character/list` 를 한 번 부른다. 무효 키 판정은 지금처럼 `isInvalidApiKeyError` 하나다([[ADR-024]] 결정 2).
2. **개발 단계 키인가.** `character/list` 를 **20건** 동시에 보내 429 가 하나라도 오면 개발 단계로 본다(사용자 지정 2026-11-08).
   지금은 10건이다. 10건이 같은 1초 안에 다 나가지 못하면 개발 단계 키를 놓치는데, 20건이면 놓칠 여지가 줄어든다. 서비스 단계
   한도(초당 500건 · 하루 2,000만 건)에는 20건이 부담이 되지 않는다. 첫 키 입력도 같은 함수(`probeApiKeyStage`)를 쓰므로 함께
   20건이다([[ADR-024]] 결정 3). 이 판정은 개발 단계를 잡을 뿐, 서비스 단계라고 확인해 주지는 않는다.
3. **이미 등록된 계정인가.** 새 키의 메이플 ID 가 로그인이나 등록된 키의 메이플 ID 와 **하나라도 겹치면** 막는다(사용자 지정
   2026-11-08). 메이플 ID 는 넥슨 계정 하나에만 속해서, 겹치면 같은 계정이다. 집합이 같은지만 보면, 앞서 등록한 뒤 메이플 ID 를
   새로 만든 계정을 다른 계정으로 읽는다. 메이플 ID 가 하나도 없는 키도 막는다. 겹치는지 가를 수 없기 때문이다.

- 무효 키와 개발 단계 키는 `등록할 수 없는 키` 라고 알리고, 키 발급 안내 링크를 함께 준다(사용자 지정 2026-11-08). 걸린 검증은
  모두 같은 모달 틀(`NoticeModal`)로 알린다. 제목은 `등록할 수 없는 키예요`, 주 버튼은 `다시 입력하기` 이고, 안내만 이유마다 다르다
  (시안 2026-11-11).

  | 이유 | 안내 | 링크 |
  |---|---|---|
  | 개발 단계 키 | `넣으신 키 · 개발 단계` 와 `필요한 키 · 서비스 단계` 두 줄. 지금 개발 단계 키 모달과 같다 | `API 키 발급 방법 보기` |
  | 무효 키 | `넥슨 Open API 에서 확인되지 않는 키예요. 키를 다시 확인해 주세요.` | `API 키 발급 방법 보기` |
  | 메이플 ID 가 하나도 없는 키 | `이 API 키에 연결된 메이플 ID 를 찾지 못했어요.` 캐릭터 관리의 빈 목록 안내와 같은 문장이다 | 없음 |
  | 로그인(넥슨 ID 계정)과 같은 계정의 키 | `이미 등록된 넥슨 계정의 키예요. 같은 넥슨 계정은 한 번만 등록할 수 있어요.` | 없음 |
  | 키를 바꿀 때 다른 넥슨 계정의 키 | `이 계정과 넥슨 계정이 일치하지 않는 키예요. 다른 API 키를 넣어 주세요.`(사용자 지정) | 없음 |
- 로그인이 키를 거둘 때의 판정(`apiKeysCoveredByLogin`)은 지금처럼 집합이 같은지 본다. 그쪽은 키를 지우는 일이라, 겹치기만 해도
  지우면 다른 계정의 키를 잃을 수 있다.
- 부계정 키를 같은 넥슨 계정의 새 키로 바꿀 때는 위 3 의 겹침 검사에서 바꾸려는 부계정을 빼고 본다(사용자 선택 2026-11-11). 429
  모달의 `다른 키 입력` 으로 계정 관리 화면(결정 2)에 온 경우다. 바꾸려는 키도 등록된 키라, 빼지 않으면 같은 계정의 새 키는 늘 겹쳐 막힌다.
  - 새 키의 메이플 ID 가 그 부계정의 메이플 ID 와 하나라도 겹쳐야 받는다. 겹치지 않으면 다른 넥슨 계정의 키라 막는다. 다른 계정은 부계정
    등록으로 넣는다.
  - 로그인이나 다른 부계정과 겹치면 지금처럼 막는다. 위 1 · 2 의 검증도 그대로 거친다.
  - 새 키를 저장한 뒤에 옛 키를 지운다([[ADR-024]] 결정 11). 새 키는 옛 키의 넥슨 계정 id 와 귀속(결정 5)을 잇는다. 그래서 그 계정의
    추적 캐릭터와 기록이 그대로 이어진다.
  - 서버에는 새 키로 부계정 등록(결정 6)을 다시 보낸다. 메이플 ID 가 같아 서버가 새 키를 같은 넥슨 계정 줄에 단다(결정 25).
- `API 키 추가` 로 넣은 키가 등록된 부계정과 겹치면 막지 않고, 그 부계정의 키를 새 키로 바꿀지 묻는다(사용자 지정 2026-11-12). 같은
  넥슨 계정의 키를 새로 받은 사용자가 그 계정의 상세 페이지를 찾아가지 않아도 되게 하려는 것이다.
  - 묻는 모달은 `NoticeModal` 이다. 제목은 `이미 등록된 계정의 API 키예요`, 안내는 `API 키 1 계정의 키를 새로 입력한 키로 바꿀까요?`
    (계정 이름은 목록의 이름), 주 버튼은 `바꾸기`, 글자 버튼은 `취소` 다. `취소` 를 누르면 키 입력 시트로 돌아간다.
  - `바꾸기` 를 누르면 위의 키 바꾸기와 같이 저장한다. 위 1 · 2 의 검증은 이미 거쳤으므로 다시 하지 않는다.
  - 무효 표시가 붙은 부계정(결정 15)도 같다. 바꾸면 무효 표시를 걷고, 뺐던 추적 캐릭터를 되돌린다.
  - 로그인과 겹치면 지금처럼 막는다. 넥슨 ID 계정에는 바꿀 키가 없기 때문이다.

### 결정 4. 넥슨은 캐릭터마다 그 캐릭터가 속한 넥슨 계정의 인증 수단으로 부른다

- 캐릭터에서 `character_accounts` 로 메이플 ID 와 넥슨 계정 id 를 찾고, 그 id 의 인증 수단으로 부른다. `scheduler/character-state`
  는 그 계정의 자격으로만 받을 수 있다.
- 로그인 계정은 지금과 같다. 프렌즈 경로는 서버 스트림을 거치고, 나머지는 번들 개발자 키로 부른다([[ADR-025]]).
- 부계정은 그 키로 넥슨을 직접 부른다. 프렌즈 경로가 아닌 `character/basic` 같은 경로도 그 키로 부른다. 번들 개발자 키는 모든
  로그인 사용자가 나눠 쓰는 한도라, 부계정의 호출까지 얹지 않는다.
- `character/list` 와 강화 내역(`history/*`)은 넥슨 계정마다 따로 받는다. 강화 내역은 이미 넥슨 계정 id 로 조회 기록을 나눈다.
- 한 계정의 조회가 실패해도 다른 계정의 캐릭터는 그대로 동기화한다. 한 계정의 실패로 모든 캐릭터가 멈추면 안 된다.
  - 한 계정의 `character/list` 가 실패하면 그 계정의 추적 캐릭터는 그 회차에서 부르지 않고 캐시를 그대로 둔다. 목록에 없다고
    월드 이전 후보나 `조회 불가` 로 넘기지 않는다. 목록을 못 받은 것이지 캐릭터가 사라진 것이 아니기 때문이다.
  - 스케줄 회차는 첫 캐릭터를 먼저 불러 자격 전체가 막혔는지(무효 키 · 429 · 로그인 만료 · 점검) 보는데, 이것을 계정마다 한다.
    한 계정의 키가 막혀도 다른 계정은 그대로 부른다.
- 어느 계정의 캐릭터인지 모르는 캐릭터(`character_accounts` 에 계정 칸이 없는 캐릭터)는 메인 계정의 자격으로 부른다. 계정 칸이
  생기기 전의 기록은 모두 메인 계정의 자격으로 받았기 때문이다([[ADR-098]] 결정 6). 계정은 알지만 그 계정의 자격이 없는 캐릭터는
  부르지 않는다. 다른 계정의 자격으로 부르면 `조회 불가` 가 되기 때문이다.
- 넥슨을 부르는 곳이 모두 이 규칙을 따른다. 스케줄 회차 · 백그라운드 갱신 · 13일 창 · 처치 날짜 · 월드 이전 찾기 · 강화 수집 ·
  MVP 등급 · 가계부의 메이플 ID 이름 · 캐릭터 관리 목록이다.

### 결정 5. 부계정 키는 등록한 넥슨 로그인에 귀속되고, 그 로그인이 살아 있을 때만 부른다

- 키마다 그 키를 부계정으로 등록한 넥슨 로그인의 계정 id(`loginId`)를 적는다(사용자 선택 2026-11-10). 앱은 지금 로그인과 같은 id 가
  적힌 키만 부계정으로 부른다. 다계정은 넥슨 로그인 사용자의 기능이고, 어느 부계정이 이 사용자의 것인지는 로그인이 정하기
  때문이다(결정 6).
- 로그인이 만료되거나, 동의를 철회하거나, 로그아웃해도 부계정 키는 지우지 않고 그 로그인에 귀속된 채 남긴다(사용자 지정 2026-11-08 ·
  11-10). 다시 로그인할 때까지 부계정의 캐릭터를 부르지 않는다.
  - 같은 넥슨 ID 로 다시 로그인하면 결정 16 이 같은 계정 id 를 이어, 그 로그인의 부계정이 그대로 이어진다(사용자 지정 2026-11-10).
  - 다른 넥슨 ID 로 로그인하거나 API 키로 로그인하면 앞 로그인의 부계정 키는 이어지지 않는다(사용자 지정 2026-11-10). 계정 id 가
    달라 보이지 않고 부르지도 않는다. 나중에 today 의 `넥슨 ID 연동하기` 로 그 넥슨 ID 를 붙이면 다시 이어진다.
  - 계정 삭제도 로그아웃과 같이 부계정 키를 남긴다. 계정 삭제는 서버에 예약한 뒤 로그아웃하는 것이고([[ADR-017]] 결정 7), 유예 30일
    안에 같은 넥슨 ID 로 돌아오면 예약을 취소할 수 있기 때문이다.
- 로그인 없이 쓰는 메인 키는 따로 적는다(`mainKeyId`). 메인 계정은 로그인이 있으면 로그인이고, 없으면 이 키다(`credentialOf`).
  부계정 키를 메인 계정으로 쓰지 않는다. 부계정 키만 남으면 부를 수단이 없는 것으로 보고 로그인 화면으로 간다.
  - 귀속과 메인 표시를 따로 두는 이유는, 로그아웃 뒤 로그인 화면에서 앞 로그인의 부계정 키를 넣을 수 있기 때문이다. 그 키는 메인
    키가 되지만 귀속은 그대로라, 나중에 그 넥슨 ID 로 다시 로그인하면 다시 부계정으로 이어진다.
  - 로그아웃하면 메인 키는 지운다. 어느 로그인에도 귀속되지 않아 다시 이을 곳이 없다. 앞 로그인의 부계정 키를 메인으로 쓰고
    있었으면 메인 표시만 지우고 키는 귀속된 채 남긴다.
- 로그인 화면에서 로그인하면(넥슨 로그인 · API 키) 새 로그인이라 앞 메인 수단을 버린다(사용자 지정 2026-11-10). 귀속되지 않은 키는
  지우고, 넥슨 로그인이 남아 있었으면 그 로그인을 뗀다. 온보딩 중에 로그인 화면으로 돌아가 다른 수단으로 다시 들어오는 경우다.
  앞 키를 남기면 그 키가 계속 메인이라, 새 수단의 캐릭터를 앞 키로 불러 `조회 불가` 가 된다.
- today 의 `넥슨 ID 연동하기` 는 새 로그인이 아니다(결정 14). 메인 키는 지우지 않고 그 로그인의 부계정이 된다. 그 키가 앞 로그인의
  부계정 키였어도 지금 쓰는 계정이라 새 로그인으로 귀속을 옮긴다. 옮기지 않으면 지금 쓰던 계정의 캐릭터를 부를 수 없다.
- 두 칸이 생기기 전에 저장된 수단은 이렇게 읽는다. 로그인이 있으면 키는 모두 그 로그인의 부계정이다. 로그인과 함께 남은 키는
  로그인이 거두지 않은 다른 넥슨 계정의 키였기 때문이다. 로그인이 없으면 키는 귀속이 없고 첫 키가 메인 키다. 지금까지 첫 키가
  메인이었다.
- 로그인 만료와 동의 철회는 키 문제(결정 15)가 아니다. 로그인 화면으로 간다.

### 결정 6. 서버는 어느 키가 그 사람의 부계정인지만 적고, 부계정은 기기마다 따로 관리한다

- 부계정을 등록하면 서버가 그 넥슨 로그인에 부계정 등록 정보를 남긴다(사용자 지정 2026-11-08). 서버가 적는 것은 이 키가 이 사람의
  부계정이라는 사실뿐이다(사용자 지정 2026-11-12).
- 앱은 이 기기에 있는 부계정 키를 보여 주고 부른다. 서버의 부계정 목록을 받아 기기끼리 맞추지 않는다(사용자 지정 2026-11-12). 키는
  기기마다 따로 들고 있어서, 목록을 맞추려면 다른 기기에서 지운 키를 이 기기에서도 지우거나 숨겨야 하기 때문이다. 그래서 다른 기기에서
  등록하거나 지운 부계정은 이 기기에 나타나지도 사라지지도 않는다.
- 어느 로그인의 부계정인지는 기기의 키에 적은 귀속(결정 5)이 가른다. 다른 넥슨 ID 로 로그인하면 앞 로그인에 귀속된 키는 보이지 않는다.
- 서버는 부계정의 키 값을 보관하지 않는다(사용자 지정 2026-11-09). 등록 정보는 부계정의 키 해시와 메이플 ID 해시다.
- 등록 정보는 서버 표 `sub_accounts` 가 든다. 줄 하나가 로그인의 넥슨 계정 줄과 부계정의 넥슨 계정 줄을 잇는다. 넥슨 계정 줄은
  넥슨 ID 하나에 한 줄이라(결정 25), 이 표도 넥슨 ID 로 유일하다. 부계정 줄은 `UNIQUE` 라 넥슨 계정 하나는 로그인 하나에만 붙는다.
  결정 5 가 기기에서 키의 귀속을 하나로 두고 연동 때 새 로그인으로 옮기므로, 다른 로그인이 같은 계정을 등록하면 등록을 그 로그인으로
  옮긴다.
- 앱이 부르는 경로는 등록 하나이고, 세션으로만 부른다. 키 사용자에게는 부계정이 없기 때문이다(결정 1).

  | 경로 | 보내는 것 | 하는 일 |
  |---|---|---|
  | `POST /v1/me/sub-accounts` | 키 해시 · 메이플 ID 해시 목록 | 키로 넥슨 계정 줄을 찾거나 만들고(처음 보는 키는 사람도 만든다), 메이플 ID 를 결정 25 대로 적은 뒤 이 로그인에 잇는다 |

- 부계정의 메이플 ID 가 로그인 자신의 메이플 ID 와 겹치면 등록을 거절한다. 같은 넥슨 ID 를 부계정으로 등록하는 것이기 때문이다.
  앱은 결정 3 으로 이미 막지만, 서버도 넥슨 계정 줄이 자기 자신의 부계정이 되지 않게 막는다.
- 메이플 ID 는 원문이 아니라 해시로 보낸다([[ADR-017]] 결정 11).
- 서버는 로그인 하나에 붙는 부계정 수를 세지 않는다(사용자 선택 2026-11-12). 상한은 기기가 센다(결정 1). 부계정을 기기마다 따로 관리해
  서버에는 여러 기기에서 등록한 부계정이 모이고, 기기에서 지운 부계정도 서버에 남기 때문이다(결정 2).
- 메인 계정을 삭제하면 등록 정보만 지운다(사용자 선택 2026-11-10). 부계정 키의 사람과 기록은 남는다. 결정 7 처럼 그 키를 다른 기기에서
  메인으로 쓰고 있을 수 있기 때문이다. 등록 정보는 유예 30일이 지나 로그인 줄이 지워질 때 함께 지워져, 유예 안에 돌아오면 그대로다.

### 결정 7. 서버에서 부계정의 기록은 부계정 행에 붙고, 메인 계정과는 등록 정보로만 이어진다

- 부계정의 기록은 부계정의 넥슨 계정에 붙는다. 메인 계정의 사람에는 부계정 등록 정보만 남아, 둘은 등록 정보를 거쳐
  이어진다(사용자 지정 2026-11-08).
- 그 키로 따로 쓰던 사람이 서버에 있어도 사람을 합치지 않는다. [[ADR-099]] 결정 5 에 있던 합치기(키 사용자를 메인 사람 밑으로
  옮기고 옛 사람 줄을 닫는 것)를 이것으로 바꿨다. 그 키를 다른 기기에서 아직 쓰고 있으면, 합칠 때 그 기기의 기록까지 메인
  사람에게 붙기 때문이다.
- 부계정의 기록은 그 키의 신원(`x-api-key-hash`)으로 보낸다. 기록마다 메이플 ID 를 실어(결정 19), 서버는 그 메이플 ID 가 키의
  넥슨 계정에 있는지 보고 적는다(결정 25). 서버가 키의 줄을 찾는 방법이 지금 키 사용자와 같아서, 서버의 기록 경로를 새로 만들지
  않아도 된다.
- 로그인 방식과 상관없이 모든 계정의 기록을 서버로 보낸다(사용자 지정).
- 앱은 기록마다 그 캐릭터가 속한 넥슨 계정(`character_accounts` 의 넥슨 계정 id)의 신원으로 보낸다. 로그인 계정이면 세션, 키 계정이면
  그 키의 해시다. 계정을 모르는 캐릭터의 기록은 메인 계정의 신원으로 보낸다. 계정 칸이 생기기 전의 기록은 모두 메인 계정의 것이었기
  때문이다(결정 4).
- 지우기는 기기에서 기록이 사라진 뒤에 보내서, 어느 계정의 기록이었는지 모른다. 그래서 지금 쓸 수 있는 신원 모두(로그인과 그 로그인의
  부계정 키, 로그인이 없으면 메인 키)로 보낸다. 서버는 그 신원의 메이플 ID 줄만 지우고, 그런 줄이 없으면 아무 일도 하지 않는다. 신원
  모두가 받아야 보낸 것으로 친다.
- 과거 올리기는 100건 묶음을 신원마다 나눠 보낸다. 지금 쓸 수 없는 계정(다른 로그인의 부계정)의 기록은 대기 표로 보낸다.

### 결정 8. 메이플 ID 마다 이름이 있고, 기본 이름을 사용자가 바꿀 수 있다

- 기본 이름은 `메이플ID-` 뒤에 그 메이플 ID(`character/list` 의 `account_id`) 값의 앞 8자를 붙인 것이다(사용자 지정 2026-11-11).
  `메이플ID-da9b2f21` 처럼 보인다. 사용자가 바꿀 수 있다(사용자 지정 2026-11-09).
- 이름이 붙는 단위가 메이플 ID 라서 메이플 ID 의 값으로 짓는다(사용자 지정). 넥슨 계정의 종류(로그인 · API 키)나 등록한 차례로 번호를
  매기지 않는다. 번호는 메이플 ID 가 늘거나 키를 다시 등록하면 바뀌지만, `account_id` 는 그 메이플 ID 의 값이라 바뀌지 않는다.
- 기본 이름은 그릴 때 만들고, 사용자가 바꾼 이름만 기기에 저장한다. 이름 칸을 비우고 저장하면 저장한 이름을 지워 기본 이름으로
  돌아간다.
- 다른 메이플 ID 와 같은 이름도 저장한다(사용자 선택 2026-11-11).
- 사용자가 짓는 이름은 10자까지다(사용자 지정 2026-11-11). 가장 좁은 폭 320 에서 위젯 드롭다운 버튼(결정 9)에 한글이 11자까지
  들어가서 한 자를 남겼다. 폭 320 에서는 앱이 글자를 0.89배로 줄이므로 그 크기로 잰 값이다. 기본 이름은 14자지만 영문 · 숫자라
  한글 10.7자 폭이어서 버튼에 들어간다.
- 메이플 ID 를 보여 주는 곳은 모두 이 이름을 쓴다. today 위젯 드롭다운 · 캐릭터 관리 드롭다운 · 가계부의 메이플 ID 보기와 하루 목록 ·
  통계 `캐릭터별` 카드 · MVP 등급이다. 지금 이름 `메이플 ID · 대표 캐릭터`([[ADR-161]] 결정 3)를 이것으로 바꾼다(사용자 지정
  2026-11-09). 같은 메이플 ID 가 화면마다 다른 이름이면 같은 ID 로 읽히지 않는다. 가계부 쪽 규칙은 [[ADR-161]] 결정 3 에 있다.
- 계정 관리 화면(결정 2)과 캐릭터 관리 드롭다운(결정 11)의 메이플 ID 줄은 이름 아래에 그 메이플 ID 의 대표 캐릭터를 보조 줄로
  둔다(사용자 선택 2026-11-11). 두 곳은 이름을 바꾸거나 캐릭터를 가져올 메이플 ID 를 고르는 곳이라, 이름만 있으면 어느 메이플 ID
  인지 알 수 없다.
- 통계 `캐릭터별` 카드의 메이플 ID 줄도 이 이름만 쓰고, 캐릭터 줄과 가르는 표시를 따로 붙이지 않는다(사용자 지정 2026-11-09). 지금은
  `메이플 ID ·` 로 시작해서 갈렸다([[ADR-161]] 결정 6).

### 결정 9. today 공유 컨텐츠 위젯은 메이플 ID 마다 따로 보이고, 위젯 드롭다운 버튼으로 고른다

- 메이플 ID 단위로 나눈다(사용자 지정 2026-11-08). 에픽 던전 · 메이플 유니온 같은 계정 공유 컨텐츠의 한도는 메이플 ID 마다 따로라,
  넥슨 계정으로 나누면 한 계정 안의 메이플 ID 들이 여전히 섞인다.
- 고르는 것은 세그먼트가 아니라 위젯용 드롭다운 버튼이다(사용자 지정 2026-11-09). 버튼을 누르면 목록이 뜬다. 세그먼트는 이름이
  길면 위젯 제목과 한 줄에 들어가지 않아, 이름 길이에 여유를 주려고 바꿨다. 이 버튼은 새로 만드는 공용 부품이다.
- 버튼은 위젯 제목 줄 오른쪽에 둔다. `card-inset` 바탕 · 반경 8 의 칸에 고른 메이플 ID 이름(`text-xs font-semibold`)과 ▾ 를
  담는다(사용자 선택 2026-11-11). 누르면 버튼 바로 아래에, 버튼 오른쪽 끝에 맞춰 이름만 있는 목록이 뜬다. 목록의 모양은
  `SelectField` 의 목록과 같고, 폭은 가장 긴 이름에 맞춘다.
- 목록에는 추적 캐릭터가 있는 메이플 ID 만 선다(사용자 지정 2026-11-08). 스케줄러는 캐릭터로만 부를 수 있어서, 추적 캐릭터가
  없는 메이플 ID 는 보여 줄 값이 없다.
- 목록에 설 메이플 ID 가 하나면 버튼을 그리지 않는다. 지금 위젯과 같다.
- 마지막에 고른 메이플 ID 를 기억한다. today 를 열 때마다 처음 것으로 돌아가면 보던 계정을 매번 다시 골라야 한다.
- 고른 메이플 ID 의 추적 캐릭터만 모은다. 월드 공유(`world`) 컨텐츠는 넥슨이 마지막에 접속한 월드의 값을 주므로 월드로 나누지
  않는다. 지금과 같다.
- 넥슨 계정이 하나여도 메이플 ID 가 둘 이상이면 버튼이 선다. 지금 섞이는 것을 함께 고친다.

### 결정 10. 주간 결정석 판매 한도는 메이플 ID 와 월드마다 따로 센다

- 같은 월드라도 메이플 ID 가 다르면 한도를 따로 센다(사용자 확인 2026-11-08). 지금 위젯은 월드로만 묶어서 메이플 ID 가 다른
  캐릭터의 판매를 더한다. 넥슨 계정이 하나여도 메이플 ID 가 둘이면 지금 이미 틀린다.
- 위젯에 설 메이플 ID 가 둘 이상이면 결정석 위젯을 4칸으로 넓혀 메이플 ID 마다 보여 준다(사용자 선택 2026-11-11). 2칸 타일은
  한도 줄 하나만 링으로 그려서, 메이플 ID 가 둘이면 어느 메이플 ID 의 한도인지 보이지 않는다. 넥슨 계정이 하나여도 메이플 ID 가
  둘이면 넓힌다. 메이플 ID 가 하나면 지금처럼 2칸이다.
- 결정석 위젯을 넓히면 같은 줄의 초기화 카운트다운도 4칸으로 넓히고, 결정석 위젯은 그 바로 아래 줄에 둔다(사용자 선택 2026-11-11).
  결정석 위젯만 넓히면 카운트다운이 그 줄에 혼자 남는다. 두 위젯의 순서는 지금과 같다. 넓힌 카운트다운의 내용은 2칸일 때와 같고
  폭만 넓다(사용자 확인 2026-11-11). 그 줄에 다른 위젯이 들어오기 전에는 넓은 폭에 더 넣을 것이 없다.
- 넓힌 위젯은 메이플 ID 마다 `card-inset` 칸 하나를 두고, 칸 맨 위에 메이플 ID 이름을 적는다(사용자 지정 2026-11-11). 칸은 그
  메이플 ID 의 월드 수로 정한다.
  - 월드가 1개면 링 칸이다. 지금 2칸 타일처럼 링 오른쪽에 월드와 `N개 남음` 을 둔다. 위젯 폭의 반이다.
  - 월드가 2개면 막대 칸이다. 월드마다 월드 이름 · `N개 남음` 한 줄과 그 아래 막대를 둔다. 위젯 폭의 반이다.
  - 월드가 3개 이상이면 막대 칸을 위젯 폭 전체로 넓히고, 칸 안의 월드 줄은 두 열로 놓는다. 한 열로 두면 월드 수만큼 위젯이
    높아진다.
- 칸의 기본 차례는 넥슨 계정 차례다. 넥슨 ID 계정(주계정)이 먼저고, API 키 계정(부계정)은 등록한 차례로 뒤에 선다(사용자 지정
  2026-11-11). 월드가 3개 이상인 메이플 ID 가 하나라도 있으면 월드가 많은 차례로 다시 놓고, 월드 수가 같으면 기본 차례를 지킨다.
  넓은 칸이 앞으로 모여서, 넓은 칸 앞뒤로 반 폭 칸이 갈려 혼자 서지 않는다.
- 반 폭 칸은 그 차례대로 둘씩 한 줄에 놓는다. 한 줄의 두 칸은 높이를 맞춘다(사용자 지정). 링 칸이 막대 칸 옆에서 늘어나면 링 줄을
  남는 높이의 세로 가운데에 둔다.
- 짝 없이 남은 반 폭 칸은 반 폭 그대로 두고 오른쪽을 비운다(사용자 지정 2026-11-11). 넓히면 월드 수가 같은 칸의 폭이 자리에 따라
  달라진다.
- 보스 수익 화면 총 수입 카드의 주간 결정석 칸은 이번 주에 판 개수의 합만 적고 분모를 두지 않는다(사용자 선택 2026-11-11). 지금은
  `합 / 90 × 월드 수` 인데, 메이플 ID 마다 나누면 분모가 너무 커지고 어느 줄의 한도도 아니다. 메이플 ID 가 하나인 사용자도 같다.
- 그 칸을 누르면 뜨는 팝오버는 메이플 ID 마다 묶고, 묶음 안에 월드별 줄(주간 `판 수/90` · 월간 개수)을 둔다. 한도는 이 줄마다 본다.
  묶음 위에는 메이플 ID 이름(결정 8)을 적되, 메이플 ID 가 하나면 적지 않는다. 결정 11 의 묶음 라벨과 같은 규칙이다. 팝오버는 한도
  줄이 둘 이상일 때만 열린다.

### 결정 11. 추적 캐릭터는 계정과 상관없이 하나의 목록이고, 캐릭터 관리의 메이플 ID 드롭다운은 넥슨 계정별로 묶는다

- 추적 목록은 지금처럼 하나다. 어느 계정의 캐릭터든 같은 목록에서 순서와 대표를 정한다(사용자 지정).
- 캐릭터 관리의 메이플 ID 드롭다운은 넥슨 계정마다 묶어서 보여 준다(사용자 지정 2026-11-08). 계정마다 `character/list` 를 받는다.
  메이플 ID 에는 결정 8 의 이름을 붙인다.
- 묶음마다 위에 `넥슨 ID 계정` · `API 키 1 계정` 같은 라벨을 두고, 묶음의 차례는 계정 관리 목록과 같다. 라벨은 `SelectField` 의 묶음
  라벨과 같은 모양이다. 넥슨 계정이 하나면 라벨을 두지 않는다(사용자 선택 2026-11-11). 묶음이 하나면 라벨로 가를 것이 없다.
- 행은 대표 캐릭터 얼굴, 메이플 ID 이름(`text-sm font-semibold`), 그 아래 대표 캐릭터 줄(월드 엠블럼 · 월드 · 레벨 · 이름, `text-xs`
  흐린 색)이다(사용자 선택 2026-11-11). 지금 행의 월드별 캐릭터 개수 줄은 뺀다. 닫힌 버튼도 같은 행을 그린다.

### 결정 12. 메이플 ID 단위 기록은 맞는 메이플 ID 에 붙이기만 하고, 계정별 필터는 두지 않는다

- 가계부 기록은 이미 캐릭터나 메이플 ID 하나에만 붙는다([[ADR-161]] 결정 4). 그래서 계정이 늘어도 기록끼리 섞이지 않는다.
  가계부의 메이플 ID 보기에는 부계정의 메이플 ID 도 선다.
- 부계정의 강화 내역은 그 계정 id 로 따로 받아 가계부 합계에 더한다.
- 가계부 · 통계의 계정 필터와 계정별 정보는 나중에 다시 정한다(사용자 지정 2026-11-08). 그래서 다른 넥슨 ID 로 로그인해도 앞 계정의
  기록은 기기에 남아 가계부 · 통계에 함께 잡힌다.

### 결정 13. API 키는 지금처럼 기기 Preferences 에 둔다

키를 SecureStore 로 옮기려면 네이티브 모듈이 들어가 스토어 바이너리가 필요하다. 이번에는 옮기지 않고 따로 정한다(사용자 지정
2026-11-08).

### 결정 14. 로그인할 때마다 추적 목록을 비우고, 앞 목록은 한 번도 그리지 않는다

- 로그인 화면에서 로그인하면(넥슨 로그인 · API 키) 추적 목록을 비운다. 새로 로그인하면 캐릭터를 반드시 새로 고른다(사용자 지정
  2026-11-09). 로그아웃 때가 아니라 로그인 때 비우는 이유는, 로그인 만료(결정 5)는 로그아웃을 거치지 않아서 로그아웃 때만 비우면
  만료 뒤 다른 넥슨 ID 로 들어올 때 앞 목록이 남기 때문이다.
- 로그인 뒤 캐릭터 설정 화면에서 앞 추적 목록이 잠깐이라도 보이면 안 된다(사용자 지정 2026-11-09). 그래서 로그인을 저장하기 전에
  기기 저장소와 쿼리 캐시를 **둘 다** 비우고, 대표 캐릭터 · 마지막에 고른 캐릭터(`lastSelectedCharacter`)도 함께 비운다. 캐릭터 설정
  화면은 쿼리 캐시의 추적 목록에서 시작하므로(`useTrackedOcids`), 저장소만 비우면 앞 목록이 한 번 그려진다.
- 로그인이 실패하면 비우지 않는다.
- 추적 목록이 비면 앱을 쓸 수 없고 캐릭터 설정으로 간다. 추적 캐릭터를 하나 이상 고르게 하는 지금 규칙과 같다(사용자 지정
  2026-11-09).
- 보스 수익 · 가계부 · 드롭 · 강화 기록은 지우지 않는다(결정 12).
- today 머리의 `넥슨 ID 연동하기` 는 비우지 않는다(사용자 지정 2026-11-09). 키로 앱을 쓰던 같은 사람이 로그인을 붙이는 것이라
  새 로그인이 아니다.
  - 그 키가 로그인과 같은 넥슨 계정이면 지금처럼 키를 서버에서 잇고 거두며, 로그인이 키의 계정 id 를 잇는다([[ADR-025]] 결정 4).
  - 그 키가 다른 넥슨 계정이면 그 키를 부계정으로 등록하고(결정 6), 그 계정의 추적 캐릭터를 그대로 둔다(사용자 지정 2026-11-09).
  - 서버 등록이 실패하면 다음에 앱을 켤 때 다시 등록한다. 그 사이에는 기기에 있는 키로 그 계정을 부른다.
  - 등록은 서버 전송 회차가 맡는다. 회차마다 지금 로그인의 부계정 키 가운데 등록한 적이 없는 키를, 그 키의 메이플 ID 해시와 함께
    등록한다(`POST /v1/me/sub-accounts`). 등록한 키는 기기(Preferences)에 키 해시로 적어 다시 보내지 않는다. 그래서 연동 때 등록하지
    못한 키와, 이 기능 전부터 로그인과 함께 남아 있던 키(결정 5)가 다음 회차에 등록된다.
  - 그 키의 메이플 ID 를 아직 모르면 목록을 받을 때까지 미룬다. 서버가 같은 넥슨 ID 라고 거절하면(409 `same_account`) 다시 보내지
    않게 적는다.

### 결정 15. 부계정 키에 문제가 생기면 키에 무효 표시를 붙이고 그 키의 추적 캐릭터를 빼며, 키를 바꾸면 되돌린다

- **키 문제**는 무효 키(401 · 403 · 400 `OPENAPI00005` · `OPENAPI00006`)다. 네트워크 오류 · 점검 · 로그인 만료 · 429 는 키 문제가 아니다.
- 429 는 키를 지우지 않고 다시 시도 모달로 알린다([[ADR-024]] 결정 11, 사용자 지정 2026-11-10). 서비스 단계 키도 같은 키를 여러 기기나 다른
  도구에서 함께 쓰면 잠깐 한도에 닿는다. 한 번의 429 로 멀쩡한 키를 지우면 사용자가 같은 키를 다시 넣어야 한다.
- 닫을 수 없는 모달로 알린다(사용자 지정 2026-11-09). 제목은 지금처럼 `API 키가 더 이상 유효하지 않습니다` 이고, 본문은 `확인` 을 누른
  뒤에 가는 곳을 말한다(사용자 선택 2026-11-12). 확인을 누르면 화면이 바뀌므로 다음에 일어날 일을 먼저 말한다.

  | 문제가 생긴 키 | 그 키의 캐릭터를 뺀 뒤 남은 추적 캐릭터 | 확인을 누르면 | 가는 곳 | 본문 |
  |---|---|---|---|---|
  | 지금 로그인의 부계정 키 | 하나 이상 | 키에 무효 표시를 붙이고 그 키의 추적 캐릭터를 뺀다 | 계정 관리 목록 | `이 키의 캐릭터를 추적에서 빼고 계정 관리로 이동합니다.` |
  | 지금 로그인의 부계정 키 | 없음 | 같다 | 캐릭터 설정 | `이 키의 캐릭터를 추적에서 빼고 캐릭터 설정으로 이동합니다.` |
  | 로그인 없이 쓰는 메인 키 | | 키를 지운다([[ADR-024]] 결정 7) | 로그인 화면 | `키 입력 화면으로 이동합니다.` |

  캐릭터 설정으로 보내는 것은 추적 캐릭터가 없으면 앱을 쓸 수 없기 때문이다. 메인 키는 남는 수단이 없어 로그인 화면으로 간다.
- 부계정 키는 지우지 않는다(사용자 지정 2026-11-12). 부계정은 기기마다 따로 관리해서(결정 6), 키를 지우면 계정 관리 목록에서 그 계정이
  사라진다. 그러면 사용자는 어느 계정의 키가 문제였는지 알 수 없고, 새 키도 `API 키 변경` 이 아니라 `API 키 추가` 로만 넣게 된다.
  - 무효 표시가 붙은 키는 부르지 않고, 서버에 등록하지도 않는다.
  - 계정 관리 목록은 그 계정 행 오른쪽에 빨간 `유효하지 않은 키` 를 둔다(사용자 선택 2026-11-12). 모달 제목과 같은 말이다.
  - 계정 관리로 보낼 때는 목록만 연다(사용자 지정 2026-11-12). 키 입력 시트를 바로 열면 어느 계정의 키를 넣으라는 것인지 알 수 없다.
- 그 키의 넥슨 계정에 속한 추적 캐릭터를 목록에서 빼고, 뺀 캐릭터를 키에 적어 둔다(사용자 지정 2026-11-09 · 11-12). 앱에 `조회 불가`
  캐릭터가 서지 않게 하려는 것이다. 보스 수익 · 가계부 기록은 지우지 않는다.
- 같은 넥슨 계정의 새 키로 바꾸면(결정 3) 무효 표시를 걷고, 뺐던 캐릭터를 추적 목록 끝에 다시 넣는다(사용자 지정 2026-11-12). 이미 추적
  중인 캐릭터는 두 번 넣지 않는다. 새 키는 옛 키의 넥슨 계정 id 를 이어 그 계정의 기록도 이어진다.
- 그 계정을 지우면(결정 2) 뺐던 캐릭터는 되돌리지 않는다.

### 결정 16. 넥슨 로그인도 메이플 ID 로 옛 넥슨 계정 id 를 잇는다

- 로그인이 메이플 ID 가 같은 키를 거두지 않았을 때도, 그 로그인의 메이플 ID 가 속했던 옛 계정 id 가 있으면 잇는다. 키가 이미 하는
  일(`reusableNexonAccountId`)을 로그인에도 쓴다. 이 결정이 배경의 마지막 문제를 고친다. 같은 넥슨 ID 로 다시 로그인하면 같은 계정
  id 라 강화 수집기가 이미 받은 날짜를 다시 받지 않는다.
- 추적 목록을 비우는 것(결정 14)으로는 이 문제가 고쳐지지 않는다. 강화 수집은 추적 목록이 아니라 계정 id 로 돈다.
- 옛 id 는 로그인을 저장하기 **전에**, 그 로그인으로 받은 `character/list` 의 메이플 ID 로 찾는다. 로그인을 저장한 뒤 목록을 적으면
  `character_accounts` 의 계정 칸이 새 id 로 덮여(`recordCharacterAccounts` 의 `ON CONFLICT`) 옛 id 를 찾을 수 없다.
- 로그아웃 뒤 다시 로그인할 때만이 아니라, 로그인 만료나 동의 철회 뒤 다시 로그인할 때도 이 결정이 든다. 만료되면 로그인을 지우면서
  (`clearNexonLogin`) 그 id 도 함께 사라지기 때문이다.
- 이미 두 번 적힌 강화 줄은 결정 18 의 이관이 정리한다.

### 결정 17. API 키로 넥슨을 직접 부를 때는 키마다 초당 요청 수에 상한을 둔다

- 서비스 단계 키가 429 를 받지 않게 하려는 것이다(사용자 지정 2026-11-09). 429 를 받으면 그 조회가 실패하고 다시 시도 모달이
  뜬다([[ADR-024]] 결정 11). 그래서 한꺼번에 보낸 요청이 한도를 넘으면, 멀쩡한 서비스 키를 쓰는 사용자도 모달에 막힌다.
- 지금 요청 간격은 넥슨 로그인의 서버 스트림에만 있다(`BATCH_WINDOW_MS`). API 키 직접 호출은 13일 창(동시 6건)과 강화 내역(동시 3건)에만
  동시 개수 상한이 있고, 스케줄 회차 · 후보 자격 확인 · 후보 프로필 · 처치 날짜 · 시드는 한꺼번에 보낸다. 후보 자격 확인은 캐릭터 수 ×
  최대 13일을 한 번에 보낼 수 있다.
- 상한은 넥슨을 부르는 공통 함수(`nexon/http.ts`)에서 키마다 건다(`nexon/key-rate-limit.ts`). 부르는 곳마다 걸면 새로 생기는
  경로가 빠진다.
- 값은 키마다 초당 50건이다(`KEY_REQUESTS_PER_SECOND`). 서비스 단계 한도(초당 500건)의 10분의 1이라, 같은 키를 기기 여럿에서
  써도 한도에 닿지 않는다. 어느 1초에도 50건을 넘지 않게, 요청이 나갈 시각을 부르는 순간에 정한다. 기다린 뒤에 세면 함께
  기다리던 요청이 한꺼번에 풀려 상한을 넘는다.
- 개발 단계 판정의 20건 동시 호출(결정 3)은 상한에서 뺀다. 한꺼번에 보내야 개발 단계 키가 429 를 낸다.
- 번들 개발자 키는 이 상한의 대상이 아니다. 모든 사용자가 함께 쓰는 키라 기기 하나의 상한으로는 지킬 수 없고, 그 키의 429 는 이미
  사용자 키의 문제로 보지 않는다(`toScheduleSyncError`).

### 결정 18. 강화 줄에 ocid 를 붙여 ocid 로 중복을 판정하고, ocid 를 붙이지 못한 줄은 버린다

- 강화 합계 줄(`enhancement_totals`)에 `ocid` 와 메이플 ID(`account_id`) 칸을 더하고, `UNIQUE` 를 `(ocid, history_date,
  enhancement_category, item_group)` 로 바꾼다(사용자 지정 2026-11-09). 지금 판정에 든 `nexon_account_id` 는 기기가 만든 임의 값이라,
  같은 넥슨 계정이 번호를 새로 받으면 같은 줄이 두 번 들어갔다. ocid 는 넥슨이 주는 값이고 캐릭터 이름을 바꿔도 그대로다.
- 강화 내역 응답에는 ocid 가 없고 그때의 캐릭터 이름만 있다(2026-09-06 실측). 그래서 줄을 쓸 때 그 날짜에 그 이름이었던 캐릭터를
  찾는다(사용자 지정 2026-11-09). 지금 이름으로 맞추면 이름을 바꾸기 전 날짜의 줄이나, 다른 캐릭터가 쓰던 이름의 줄을 잘못 붙이기
  때문이다. 찾는 차례는 아래와 같고, 앞에서 찾으면 뒤로 가지 않는다(사용자 지정 2026-11-09).
  1. **앱이 직접 본 기간**: `character_accounts` 에 그 ocid 를 그 이름으로 본 기록이 있고 줄의 날짜가 처음 본 날 ~ 마지막 본 날 안이면 그 ocid
     를 붙인다. 넥슨을 부르지 않는다. 앱이 그 기간에 확인한 사실이기 때문이다.
  2. **그날 이름**: 그 계정의 `character/list` 에 있는 ocid 로 `character/basic` 을 그 날짜로 불러 그날 이름을 받고, 이름이 같으면 그 ocid 를
     붙인다. 받은 그날 이름은 기기에 적어 같은 ocid · 날짜를 다시 부르지 않는다. 넥슨 로그인 사용자의 이 호출은 모두가 함께 쓰는 번들
     개발자 키로 가서, 부르는 수를 아래 차례로 줄인다(사용자 선택 2026-11-10). 이름은 한때 한 캐릭터만 쓰므로 차례를 바꿔도 붙는
     캐릭터는 같다. 차례 4 만 그날 이름을 직접 받지 못해, 다른 캐릭터가 그날 그 이름이었다가 리프한 캐릭터가 리프 뒤에 그 이름을
     가져간 경우에는 리프한 캐릭터에 붙는다. 한 사람의 캐릭터끼리 이렇게 될 일은 드물다.
     - 그 이름을 쓴 적이 있는 캐릭터를 먼저 묻는다. 이번 회차에 그 이름으로 붙인 캐릭터, 적어 둔 그날 이름에 그 이름이 있는 캐릭터,
       지금 이름이나 앱이 본 이름이 같은 캐릭터다. 이 캐릭터들은 차례 3 · 4 까지 먼저 본다. 리프 전 줄은 지금 이름이 같은 캐릭터에
       차례 4 로 붙는데, 나머지 캐릭터를 다 물은 뒤에야 차례 4 로 가면 리프 전 줄 하루마다 계정의 캐릭터 수만큼 부른다.
     - 나머지 캐릭터 가운데 그 날짜나 그 뒤에 값이 없던 것을 아는 캐릭터는 맨 뒤에 묻는다. 캐릭터 값은 처음 값이 온 날부터 이어져서
       그 앞 날짜에도 값이 없을 것이기 때문이다. 건너뛰지 않고 미루기만 한다. 넥슨 데이터가 중간에 하루 비는 날이 있으면, 건너뛴
       캐릭터의 줄을 버리고 그 날을 굳혀 영영 잃는다.
     - 같은 이름은 날짜마다 차례로 찾는다. 여러 날짜를 한꺼번에 찾으면 앞 날짜에서 찾은 캐릭터를 뒤 날짜가 먼저 묻지 못한다.
  3. **이름을 바꾼 날**: 그날 이름과 다르면 같은 ocid 의 전날 · 다음 날 이름과도 견준다. `date` 의 값이 그날 어느 시각 기준인지 몰라, 바꾼
     날 강화한 줄은 옛 이름으로도 새 이름으로도 올 수 있다.
  4. **리프 전 기간**: 그 ocid 의 그날 값이 `null` 인데 만든 날(`character_date_create`)이 그날보다 앞이면, 그날은 그 캐릭터가 리프하기 전
     기간이다. 그 캐릭터에 처음 값이 온 날의 이름이 줄의 이름과 같으면 그 ocid 를 붙인다. 처음 값이 온 날은 캐릭터마다 한 번 찾아 저장한다.
  5. 넷 다 아니면 그 줄을 버린다(아래).
- `character/basic` 에 `date` 를 넣으면 그날의 이름을 준다(2026-11-09 실측, 사용자 캐릭터 `낟낟`). 이 캐릭터는 2026-01-07 까지 `살름`,
  2026-01-08 부터 `낟낟` 으로 왔다. 그 ocid 에 값이 없는 날은 에러가 아니라 200 에 모든 칸이 `null` 이다. 이 캐릭터는 만든 날
  (`character_date_create`)이 2025-06-19 인데 2025-07-23 까지 `null` 이고, 2025-07-24 에 레벨 277 로 처음 값이 온다.
- 챌린저스 월드에서 일반 월드로 리프하면 ocid 가 바뀌고, 리프 전 날짜는 어느 ocid 로도 이름을 받을 수 없다(2026-11-09 실측, 사용자 캐릭터

  함께 지워, 수집기가 그 날짜를 다시 받아 차례 2 ~ 5 를 거치게 한다(사용자 지정 2026-11-09).
  - 지운 날짜는 다시 받을 날(`enhancement_refetches`)로 적어 뒤에서 받는다(사용자 선택 2026-11-10). 화면이 연 기간만 받으면 열지 않은
    달의 지출이 빠진 채 남기 때문이다. 지난 날 모달은 띄우지 않는다. 다 받기 전까지 그 날의 지출은 가계부에서 잠시 빠진다.
  - 이 받기는 가계부 · 통계 화면의 회차가 끝난 뒤 따로 돌고, 화면은 기다리지 않는다(사용자 선택 2026-11-10). 화면 회차 안에서 돌리자

  날짜를 다시 받지 않게 하고, 이 결정은 다시 받아도 줄이 늘지 않게 한다.
- 1.0.14 스토어 바이너리로 낸다. OTA 로 내면 실패할 때 돌아가는 내장 번들의 옛 코드가 없어진 판정(`ON CONFLICT (nexon_account_id, …)`)
  으로 쓰다 실패한다.

### 결정 19. 앱과 서버의 모든 기록은 계정 · 메이플 ID · 캐릭터 · ocid 식별자를 반드시 채운다

- 강화 내역 넷(큐브 · 스타포스 · 잠재능력 · 소울 잠재능력)은 같은 스키마로 관리한다(사용자 지정 2026-11-09).
- 기록에는 넥슨 계정 · 메이플 ID · 캐릭터 · ocid 가운데 그 기록에 해당하는 식별자를 빠짐없이 채운다(사용자 지정 2026-11-09). 식별자가
  비거나 바뀌는 값(앱 계정 번호 · 캐릭터 이름)만으로 중복을 가리면, 이번처럼 같은 기록이 두 번 들어가거나 누구의 기록인지 모르게 된다.
- 다른 기록과 서버 표도 같은 원칙을 따른다(사용자 지정 2026-11-09). 앱 · 서버 스키마 전수 검사(2026-11-09)로 정한 표마다의 수정은
  결정 20 ~ 28 에 있다.
- 사용자가 만드는 기록의 유일 기준은 넥슨이 준 값과 기록 내용으로만 건다(사용자 지정 2026-11-10). 넥슨이 준 값은 넥슨 ID(로그인의
  `nexon_uid`) · 메이플 ID(`character/list` 의 `account_id`) · 캐릭터(`ocid`)다. 서버에서는 셋 모두 원문이 아니라 해시다([[ADR-017]]
  결정 11). 서버가 만든 줄 id(사람 줄 · 넥슨 계정 줄)와 기기가
  만든 값(앱 계정 번호 · 기록 id · 키 해시)은 기준에 넣지 않는다. 이 값들은 기기를 바꾸거나, 다시 설치하거나, 키를 다시 받으면 바뀌어서
  같은 기록이 한 줄 더 생긴다.
- 기록 id 는 메이플 ID 안에서만 유일하고, 같은 기록을 다시 보냈을 때 그 줄을 찾는 데 쓴다. 내용으로 가릴 수 없는 기록만 기록 id 가
  유일 기준이 된다. 사용자가 직접 적는 가계부 기록이다. 같은 날 같은 물건을 두 번 산 기록은 내용이 같아도 둘 다 맞는 기록이라,
  내용으로 가리면 하나가 사라진다.
- 리프해도 메이플 ID 는 그대로다(사용자 확인 2026-11-10). 리프로 ocid 가 바뀌면 기기는 기록을 새 ocid 로 옮기고(결정 22), 서버는
  같은 메이플 ID · 같은 기록 id 로 다시 온 줄의 ocid 를 고친다. 기록 id 로 줄을 찾지 않으면 옛 ocid 의 줄이 남아 같은 기록이 두 줄이
  된다.
- 사용 로그(`usage_events`)는 사건마다 한 줄인 운영 기록이라 유일 기준을 두지 않는다.

### 결정 22. 리프하면 옛 ocid 의 기록을 새 ocid 로 옮기되, 각 기록은 그때의 월드를 지킨다

- 리프를 이으면 옛 ocid 에 붙은 기록을 새 ocid 로 옮긴다(사용자 지정 2026-11-09). 가계부 기록 · 조각 보관 · 직접 체크 목록 · 마지막 사냥 ·
  기억한 심볼 레벨 · 파티 약속 · 보스 수익 계산기 기록 · 보스 기록이다. 옮기지 않으면 같은 캐릭터의 기록이 두 ocid 로 갈린다.
- 옮기기(`moveWorldLeapRecords`)는 리프 중복 정리([[ADR-040]] 결정 13) 바로 뒤에 연결마다 돈다. 창 동기화와 회차 자동 기록 뒤의 두
  자리다. 리프한 기간의 같은 처치를 먼저 짝지어야 옮긴 옛 기록이 새 기록과 부딪치지 않는다. 잇는 순간 한 번이 아니라 회차마다 도는 것은,
  이 기능 전에 이어 둔 연결의 기록도 옮기고 중간에 실패한 옮기기를 다음 회차가 마저 하기 위해서다. 다 옮긴 연결은 옮길 것이 없어 바로 끝난다.
- 새 ocid 에 같은 자리의 값이 이미 있으면 새 ocid 의 것을 둔다. 리프 뒤에 사용자가 새 캐릭터에 적은 값이기 때문이다. 연결을 처음 쓸 때
  보스 파티 설정을 복사하는 규칙([[ADR-040]] 결정 14)과 같다.

| 기록 | 옮기는 법 |
|---|---|
| 가계부 기록 · 조각 보관 | 기록(`cashbook_entries`)과 헥사 강화가 가져간 보관 조각(`cashbook_entry_fragment_uses`)의 ocid 를 바꾼다. 조각 보관은 이 둘에서 세므로 함께 옮겨진다. 월드 칸은 그대로 둔다 |
| 보스 기록 | 옛 캐릭터의 보스 · 난이도 조합(`boss_parties`)을 새 캐릭터로 옮긴다. 새 캐릭터에 같은 조합이 없으면 조합째 옮기고, 있으면 기간(`boss_party_periods`)만 옮기고 설정은 새 것을 둔다. 새 조합에 같은 기간이 이미 있으면 그 기간은 옮기지 않는다. 기간의 월드 칸은 그대로다 |
| 직접 체크 목록 · 마지막 사냥 | 새 캐릭터에 값이 없을 때만 옮기고, 옛 값은 지운다 |
| 기억한 심볼 레벨 | 대상(심볼 key · 헥사 코어 이름)마다 새 캐릭터에 없는 것만 옮기고, 옛 줄은 지운다 |
| 파티 약속 | 그 캐릭터가 가는 보스 판의 ocid 를 바꾼다. 이 주만 바꾼 회차도 바꾼다. 파티원 칸은 약속에 파티원을 넣는 화면이 없어 늘 비어 있으므로 다루지 않는다 |
| 보스 수익 계산기 기록 | 기록 속 옛 캐릭터를 새 캐릭터로 바꾼다. 새 캐릭터가 챌린저스 월드가 아니면 시즌 보스 줄은 빼고 옮긴다(사용자 지정 2026-11-10). 시즌 보스는 챌린저스 월드 캐릭터만 잡아서, 남기면 일반 월드 캐릭터가 못 잡는 보스가 수입에 든다. 새 캐릭터의 월드를 모르면 보스 선택처럼 시즌 보스를 못 잡는 캐릭터로 보고, 프로필을 못 읽은 회차에는 옮기지 않는다. 그 기록에 새 캐릭터가 이미 있으면 옛 캐릭터 항목을 지운다(사용자 지정 2026-11-10). 기록을 열면 추적 중인 캐릭터만 보이는데 기록 목록의 금액은 기록에 든 캐릭터를 모두 더해, 남겨 두면 두 금액이 갈린다. 기록에서 캐릭터 하나만 지우는 기능은 없다 |

- 옮겨도 기록은 리프 전 월드의 기록으로 남는다(사용자 지정 2026-11-09). 그래서 캐릭터에 붙는 기록은 그때의 월드(`world_key`)를 함께
  적는다. 보스 기간(`boss_party_periods.world_key`)은 이미 그렇게 한다. 가계부 기록과 강화 합계에 이 칸을 더한다. 월드를 캐릭터의 지금
  월드로 읽으면 리프한 캐릭터의 과거가 새 월드로 옮겨 간다.
- 가계부 기록의 월드는 캐릭터 기록을 적을 때 그 ocid 의 프로필 월드(`character_profiles.world_key`)로 채운다. 같은 ocid 의 월드는
  바뀌지 않기 때문이다. 고칠 때는 캐릭터를 바꿨을 때만 다시 채운다. 옮긴 기록을 고칠 때 새 ocid 의 월드로 덮지 않기 위해서다. 메이플
  ID 기록은 월드가 없어 비운다. 주인 모르는 옛 기록을 대표 캐릭터에 붙일 때(결정 28)도 그 캐릭터의 프로필 월드로 채운다.
- 이미 있는 기록의 월드는 1.0.14 이관(DB 버전 19)이 그 기록의 ocid 의 프로필 월드로 채운다. 옮기기 전에 채워야 옛 월드가 남는다. 이관은
  DB 를 열 때 돌고, 옮기기는 그 뒤의 회차에서 돈다.
- 강화 줄의 월드는 스타포스면 응답의 `world_name` 이다. 아니면 결정 18 의 차례 1 ~ 3 으로 ocid 를 붙인 줄은 그 ocid 의 월드다. 같은
  ocid 의 월드는 바뀌지 않기 때문이다(사용자 확인 2026-11-10). 월드를 옮기면 리프처럼 ocid 가 바뀐다. 그래서 차례 1 로 붙인 줄도 그날
  월드를 따로 부르지 않는다.
- 차례 4 로 붙인 리프 전 기간의 줄은 그 ocid 의 월드가 아니다. 리프 전 월드의 줄을 리프 뒤의 ocid 에 붙인 것이기 때문이다. 같은 캐릭터의
  같은 기간 스타포스 줄의 월드를 쓰고, 그것도 없으면 비워 둔다.
- 리프 전 기간의 줄은 이벤트 월드의 줄이 아니다. 스페셜 월드에서 일반 월드로는 리프할 수 없다(사용자 확인 2026-11-10). 그래서 월드를
  비워 둔 리프 전 줄도 지출로 센다. 모름으로 두면 그 날이 굳지 않아 같은 날을 끝없이 다시 받는다.
- 리프를 잇는 자동 판정(`linkWorldLeapsByNameAndJob`)은 이름 · 직업에 만든 날(`character_date_create`)을 더해 본다. 만든 날은 리프
  뒤에도 그대로라(결정 18 의 실측) 이름과 직업이 같은 다른 캐릭터를 가를 수 있다. 만든 날은 `character/basic` 을 받을 때 프로필
  (`character_profiles.created_date`)에 적는다. 두 캐릭터 가운데 하나라도 만든 날을 모르면 이 조건은 건너뛴다. 이 기능 전에 리프한
  캐릭터는 옛 ocid 를 더 부를 수 없어 만든 날을 알 길이 없다. 모름을 다름으로 읽으면 지금 잇는 리프를 못 잇는다.

### 결정 23. 월드 공유 컨텐츠의 진행 원장은 메이플 ID 와 월드마다 따로 둔다

- 월드 공유 컨텐츠는 같은 월드라도 메이플 ID 가 다르면 따로 센다(사용자 확인 2026-11-09). 원장의 열쇠를 `worldSharedProgress:{worldKey}` 에서
  메이플 ID 와 월드를 함께 든 열쇠로 바꾼다. 지금은 같은 월드의 다른 메이플 ID 캐릭터가 원장을 함께 써 진행이 섞인다.
- 이관은 옛 원장을 그 월드에 추적 캐릭터가 있는 메이플 ID 마다 하나씩 베낀다. 원장은 한 번이라도 활성으로 본 적이 있는지를 쌓은 값이라
  넥슨에서 다시 받을 수 없다.

### 결정 24. 서버의 드롭 가격 기록에 ocid 와 메이플 ID 를 싣고, 같은 드롭이 다시 오면 서버에 적지 않는다

- 앱이 드롭 가격을 보낼 때 그 드롭의 `ocid` 와 메이플 ID 를 해시로 싣는다(사용자 지정 2026-11-09 · 11-10, [[ADR-017]] 결정 11). [[ADR-017]]
  결정 6 의 익명 원칙을 이것으로 바꾼다.
- 계정을 삭제하면 메이플 ID 는 비우고 `ocid` 해시는 남긴다(사용자 지정 2026-11-09). 원문이 아니라 해시라 남겨도 키 조각이 남지 않는다.
  남긴 해시가 있어야, 지운 뒤 돌아온 사람이 같은 드롭을 다시 보내도 줄이 늘지 않는다.
- 같은 드롭인지는 `ocid` · 보스 · 기간(`period_key`) · 아이템 · 획득처로 가린다(사용자 지정 2026-11-09 · 11-11). 이것이 `drop_prices` 의
  유일 기준이다(결정 19).
  - 한 캐릭터는 한 기간에 한 보스에게서 같은 아이템을 둘 얻지 못한다(사용자 확인 2026-11-11). 같은 아이템이 두 줄이 되는 것은 보스가
    직접 떨군 연마석과 반지 상자에서 나온 연마석처럼 획득처가 다를 때뿐이다. 그래서 같은 아이템 가운데 몇 번째인지 세지 않고 획득처로 가른다.
  - 획득처는 기기 기록의 상자 칸(`box_origin_key`, [[ADR-044]])이다. 보스가 직접 떨군 드롭은 비어 있고, 상자에서 나온 드롭은 그 상자의
    key 다. 서버는 아이템처럼 상자도 key 로 찾아 적고, 모르는 key 는 받지 않는다.
  - 직접 떨군 드롭은 획득처 칸이 비어 있다. 빈 칸끼리도 같은 획득처로 본다. 그래야 직접 떨군 같은 드롭이 두 번 와도 한 줄이다.
  - 난이도는 넣지 않는다. 한 캐릭터는 한 기간에 한 보스를 한 난이도로만 잡으므로, 난이도를 넣으면 난이도만 고친 같은 드롭이 두 줄이 된다.
    지금 `drop_prices` 에는 보스와 난이도를 묶은 `boss_difficulty_id` 만 있어서 보스 칸을 따로 둔다.
  - 기기에서 지운 줄(`deleted`)은 이 기준에서 뺀다. 지운 줄이 자리를 쥐고 있으면 같은 자리에 다시 적은 드롭을 받지 못한다.
- 같은 드롭이 이미 있으면 누가 보냈든 서버에 적지 않는다. 앱의 기록은 그대로 둔다(사용자 지정 2026-11-09). 앱은 넥슨 로그인이나 API 키로
  들어온 사람만 쓰므로, 보통은 자기 캐릭터가 아닌 ocid 의 드롭을 보낼 수 없다.
- 같은 기록을 다시 보내면(가격 고침 · 과거 올리기 재전송 · 리프 뒤 옮기기) 같은 메이플 ID · 같은 기록 id 의 줄을 고친다(결정 19). 고친
  값이 다른 줄과 같은 드롭이 되면 그 고침도 적지 않는다.
- 적지 않은 건도 서버는 받은 것으로 답한다. 실패로 답하면 앱이 그 건을 대기 표에 넣어 다섯 번 다시 보낸다([[ADR-099]] 결정 3).
  기록의 메이플 ID 가 보낸 계정의 것이 아닐 때만 실패로 답한다(결정 25).
- 이미 올라간 줄에는 ocid · 메이플 ID · 획득처가 없다. 1.0.14 앱이 과거 드롭을 처음부터 다시 올려 셋을 채운다. 옛 줄은 메이플 ID 로 찾을 수 없어
  지금처럼 사람 · 기록 id 로 찾는다. 채우다가 다른 줄과 같은 드롭이 되면 먼저 들어온 줄을 남기고 나중 줄을 지운다.
  - 처음부터 다시 올리려고 과거 올리기의 종류 이름을 `dropPrice` 에서 `dropPriceOwner` 로 바꿨다. 과거 올리기는 옛 종류의 진행을 읽지
    않으므로([[ADR-099]] 결정 1), 1.0.13 에서 다 올린 기기도 처음부터 다시 올린다.
- 1.0.13 앱이 보내는 드롭에는 ocid 와 메이플 ID 가 없다. 1.0.13 을 잠글 때까지는 그 드롭을 지금처럼 사람 · 기록 id 로 받는다.
- 1.0.14 앱은 드롭마다 그 캐릭터의 메이플 ID 해시(`mapleId`) · ocid 해시(`ocid`) · 상자 key(`boxOriginKey`)를 싣는다. 메이플 ID 는
  `character_accounts` 에서 찾는다. 앱이 그 캐릭터를 목록에서 본 적이 없어 메이플 ID 를 못 찾은 드롭은, 메이플 ID 와 ocid 없이 옛 모양으로
  보낸다. 서버는 1.0.13 을 잠글 때까지 그 모양을 받는다.
- 이 앱은 서버의 식별자 해시(0037)와 획득처(0038)를 배포한 뒤에 내야 한다. 그 전 서버는 메이플 ID · ocid 와 함께 몇 번째를 요구해서, 새
  앱의 드롭을 400 으로 거절한다.
- 1.0.13 을 잠근 뒤 ocid 가 없는 줄을 지우고 `ocid` 칸을 `NOT NULL` 로 바꾼다(사용자 선택 2026-11-10). 사람 칸(`user_id`)도 걷는다.
  그 뒤로는 모든 드롭 줄을 넥슨이 준 값으로 가린다.
  - 2026-11-10 운영은 3,949줄이고, 그중 시세에 쓰는 줄(`completed`)이 3,458줄이다. 사람 칸이 빈 줄은 없다. 시세에 쓰는 줄의 사람
    322명은 모두 30일 안에 활동했다.
  - 지워질 줄은 기기에서 지운 줄 75 · 삭제 예약 중인 2명의 6줄 · 1.0.14 로 올리지 않는 사람의 줄이다.
  - 같은 드롭이 사람만 달리 두 줄로 들어간 묶음(아이템 · 기간 · 보스 · 월드 · 가격 · 가격 시각이 같은 줄)은 0건이었다.
- 지금은 `(user_id, drop_record_id)` 로 가려, 사람이 바뀌면 한 줄이 더 생기고 시세 계산에서 두 번 센다.

### 결정 25. 서버의 넥슨 계정 줄은 넥슨 ID 하나에 하나이고, 넥슨 로그인의 uid 와 메이플 ID 로 알아본다

- 서버의 넥슨 계정 줄은 넥슨 ID 하나에 하나다(사용자 지정 2026-11-10). 같은 넥슨 ID 의 넥슨 로그인과 API 키는 한 줄이고, 키를 다시 받아도
  줄이 늘지 않는다. 결정 19 의 유일 기준을 계정에도 건다.
- 표는 셋이다.

  | 표 | 줄 하나 | 유일 기준 |
  |---|---|---|
  | `nexon_accounts` | 넥슨 ID 하나 | `nexon_uid` 해시. 넥슨 로그인으로 확인한 계정만 값이 있다 |
  | `nexon_account_keys` | 그 넥슨 ID 의 API 키 하나 | 키 해시 |
  | `nexon_account_maple_ids` | 그 넥슨 ID 의 메이플 ID 하나 | 메이플 ID 해시. 서버 전체에서 한 줄이다 |

- 넥슨 로그인은 `nexon_uid` 로 알아본다. 기기와 다시 로그인에 상관없이 같은 값이다. API 키는 키 해시로 찾지만, 키 해시는 키를 다시 받으면
  바뀐다. 그래서 같은 넥슨 ID 인지는 메이플 ID 로 가린다. 메이플 ID 는 넥슨 계정 하나에만 속한다(사용자 지정 2026-11-09).
- 지금 `account_record_id` 는 기기가 만든 값이라 기기마다 다르고, 다시 받은 키는 새 사람이 된다(2026-11-09 서버 검사). 이 칸은 걷는다(결정 21).
- 앱은 계정마다 그 계정의 신원으로 메이플 ID 해시 목록을 알린다(`PUT /v1/me/maple-ids`, [[ADR-017]] 결정 11). 로그인은 세션, 키는 그
  키의 해시다. 그 계정의 `character/list` 를 받은 뒤, 서버가 마지막으로 받아 준 목록과 다를 때만 보낸다. 서버가 돌려주는 목록도 해시라,
  앱은 새 목록을 해시해서 견준다. 부계정을 등록할 때는 등록 경로(결정 6)가 함께 받는다.
  - 알리는 때는 서버 전송 회차마다, 기록을 보내기 전이다. 계정의 메이플 ID 는 `character_accounts` 에서 그 넥슨 계정 id 로 모은다. 서버가
    마지막으로 돌려준 목록을 계정마다 기기(Preferences)에 두고, 모은 목록이 그 안에 다 있으면 보내지 않는다. 알리기 전에 보낸 기록은
    서버가 거절하고 대기 표가 다섯 번까지 다시 보내므로, 알리기를 먼저 해야 거절이 생기지 않는다.
- 서버는 받은 메이플 ID 를 보낸 넥슨 계정 줄에 더하기만 하고, 목록에서 빠진 메이플 ID 도 지우지 않는다. 메이플 ID 는 다른 넥슨 ID 로
  옮겨 가지 않아 남겨도 다른 계정과 부딪치지 않는다. 지우면 그 메이플 ID 의 기록이 주인을 잃는다. 메이플 ID 줄은 계정을 삭제할 때만 지운다.
- 받은 메이플 ID 가 이미 다른 넥슨 계정 줄에 있으면 두 줄은 같은 넥슨 ID 다. 키를 다시 받았거나, 같은 넥슨 ID 의 로그인과 키가 따로 들어온
  경우다. 두 줄을 한 줄로 합친다.
  - 남기는 줄은 로그인 줄(`nexon_uid` 가 있는 줄)이다. 둘 다 키 줄이면 먼저 생긴 줄을 남긴다. 키를 다시 받은 계정은 옛 줄로 이어진다(사용자
    선택 2026-11-10).
  - 없앨 줄의 키 · 메이플 ID · 부계정 등록 · 강화 이상 보고를 남기는 줄로 옮기고 없앨 줄을 지운다. 기록은 메이플 ID 를 가리키므로 따로
    옮기지 않는다. 강화 이상 보고가 같은 열쇠로 겹치면 늦게 고친 줄을 남긴다. 합친 뒤 부계정 등록이 자기 자신을 잇게 되면 그 등록을 지운다.
  - 없앨 줄의 사람에게 다른 넥슨 계정 줄이 없으면 그 사람도 지운다(사용자 선택 2026-11-10). 1.0.13 을 잠그기 전에는 사람 칸으로 찾는 옛
    드롭 줄이 있어(결정 24), 그 사람의 드롭 줄은 남기는 줄의 사람으로 옮긴다. 옮기지 않으면 사람을 지울 때 사람 칸이 비어 익명 줄이 된다.
  - 둘 다 로그인 줄이면 합치지 않고 거절한다. `nexon_uid` 가 다르면 다른 넥슨 ID 라 메이플 ID 가 겹칠 수 없고, 앱이 잘못 알린 값이다.
  - 어느 한쪽 사람이 계정 삭제를 예약했으면 합치지 않는다. [[ADR-017]] 결정 9 와 같은 이유로, 합치면 사용자가 한 삭제 요청이 말없이 사라진다.
    겹친 메이플 ID 는 예약한 줄에 남고, 유예가 끝나 그 줄이 지워진 뒤 다시 알리면 보낸 줄에 붙는다.
- `POST /v1/me/api-key-links`([[ADR-017]] 결정 9)도 같은 합치기다. 앱이 메이플 ID 가 같은 것을 확인하고 보낸 키라, 그 키의 넥슨 계정 줄을
  로그인 줄로 합친다. 지금은 키 줄의 사람에게 다른 로그인 줄이 있으면 옮기지 않는다. 넥슨 ID 가 같은 줄은 한 줄이어야 하므로, 그 경우에도
  키의 줄만 합치고 그 사람의 로그인 줄은 그대로 둔다.
- 기록은 그 기록의 메이플 ID 가 보낸 신원의 넥슨 계정 줄에 있을 때만 적는다(사용자 선택 2026-11-10). 없으면 적지 않고 실패로 답해, 앱 대기
  표가 다시 보낸다([[ADR-099]] 결정 3). 메이플 ID 를 알리기 전에 보낸 기록도 이렇게 다음 회차에 들어간다. 남의 메이플 ID 를 아는 사람이
  그 기록을 덮거나 막지 못하게 하려는 것이다.
- 기록 표의 메이플 ID 칸은 이 표의 메이플 ID 를 가리킨다. 계정을 삭제해 메이플 ID 줄이 지워지면 드롭 가격은 그 칸을 비우고, 나머지 기록은
  함께 지워진다(결정 24, [[ADR-017]] 결정 6).
- 메이플 ID 는 앱이 알려 주는 값이라 서버가 넥슨에 확인하지 못한다. 키 해시가 이미 증명이 아닌 꼬리표라([[ADR-017]] 결정 5), 같은 수준의
  믿음으로 받는다.

### 결정 26. 앱이 더 보내지 않는 서버 표는 남기고, 식별자를 고친 뒤 다시 쓴다

- `boss_clears` · `cashbook_entries` · `enhancement_totals` 와 그 경로를 지우지 않는다(사용자 지정 2026-11-09). 중복이 생기지 않게 스키마를
  고친 뒤 다시 보낸다.
- 세 표는 2026-11-10 운영에 줄이 없다. 그래서 옛 줄을 옮길 일 없이, 넥슨이 준 값의 칸을 처음부터 `NOT NULL` 로 다시 만든다.
- 고칠 방향은 결정 18 · 19 · 25 와 같다. 사람 칸(`user_id`)을 걷고 메이플 ID 해시 칸을 둔다. 캐릭터 기록은 `ocid` 해시도 둔다([[ADR-017]]
  결정 11).
- 서버에는 캐릭터 이름을 두지 않는다(사용자 지정 2026-11-10). `enhancement_totals` 의 이름 칸(`character_name`)을 걷는다. 캐릭터는 `ocid`
  해시로 가리키고, 이름은 기기가 자기 캐릭터 목록에서 붙인다.

  | 표 | 유일 기준 | 다시 보낸 기록의 줄을 찾는 기준 |
  |---|---|---|
  | `boss_clears` | `ocid` · 보스 · 기간 | 메이플 ID · 기간 행 id. 리프로 ocid 가 바뀌어도 같은 줄을 찾는다 |
  | `enhancement_totals` | `ocid` · 날짜 · 분류 · 장비 묶음(결정 18) | 왼쪽과 같다. 리프 때 옮기지 않는 기록이다(결정 22) |
  | `cashbook_entries` | 메이플 ID · 기록 id | 왼쪽과 같다. 내용으로 가릴 수 없는 기록이다(결정 19) |

- `boss_clears` 에 난이도를 넣지 않는 이유는 결정 24 와 같다. 보스 칸을 따로 둔다.
- 가계부 기록의 넥슨 계정 칸(`nexon_account_id`)은 걷는다. 캐릭터 없는 기록은 메이플 ID 기록이라(결정 28 · 29) 메이플 ID 칸이 그 자리를 맡는다.
- 지금은 기기 uuid 나 캐릭터 이름으로 가려 기기마다, 이름마다 줄이 갈린다.

### 결정 27. 옛 강화 원본 표는 옛 합계로 바꾼 기기에서만 지운다

`enhancement_history` 는 쓰는 곳이 없고 옛 합계를 만들 때만 읽는다. 1.0.14 이관이 그 기기의 옛 합계 변환이 끝났는지 보고, 끝났으면 지운다
(사용자 선택 2026-11-09). 여러 버전을 건너뛰어 올라온 기기는 변환을 먼저 해야 한다.

### 결정 28. 주인을 모르는 옛 가계부 기록은 대표 캐릭터에게 붙인다

- [[ADR-161]] 결정 5 가 옮기지 못한 옛 기록(`ocid` 와 `account_id` 가 모두 비어 있는 기록)을 그 기기의 지금 대표 캐릭터에게 붙인다(사용자
  지정 2026-11-09). [[ADR-161]] 결정 5 의 "대표 캐릭터의 ID 로 몰아 옮기지 않는다" 를 이것으로 바꾼다.
  - 메이플 ID 도 고를 수 있는 분류의 기록은 대표 캐릭터의 메이플 ID 에 붙인다.
  - 캐릭터만 고르는 분류의 기록은 대표 캐릭터 자체(그 `ocid` 와 메이플 ID)에 붙인다. 이 분류는 캐릭터에만 붙을 수 있기 때문이다.
  - 분류마다 무엇을 고르는지는 결정 29 의 목록을 따른다.
- 지금까지 앱은 넥슨 계정을 하나만 두었다. 그래서 캐릭터나 메이플 ID 를 고르지 않고 적은 기록도 그 넥슨 계정의 것이다. 메이플 ID 가
  여럿이면 어느 ID 에서 쓴 돈인지는 모르지만, 사용자가 직접 적은 기록이라 사용자의 책임으로 보고 대표 캐릭터에게 붙인다(사용자 지정).
- 옮기는 것은 [[ADR-161]] 결정 5 의 부팅 단계에서 한다. 대표 캐릭터가 없거나 그 캐릭터의 메이플 ID 를 아직 모르면 옮기지 않고, 옮길 기록이
  남아 있으면 켤 때마다 다시 본다.

### 결정 29. 지출 컨텐츠도 캐릭터나 메이플 ID 를 고른다

- [[ADR-161]] 결정 1 의 표에서 지출 컨텐츠(`content`)를 "캐릭터만" 에서 "캐릭터나 메이플 ID" 로 바꾼다(사용자 지정 2026-11-09). 나머지
  분류는 그대로다.
- 코드에서는 `ACCOUNT_SPEND_CATEGORY_KEYS` 에 `content` 를 더한다. 시트의 메이플 ID 보기와 옛 기록을 옮기는 부팅 단계가 이 목록 하나를
  본다. 그래서 컨텐츠의 주인 모르는 옛 기록은 결정 28 에 따라 대표 캐릭터의 메이플 ID 로 간다.
- 컨텐츠 시트는 이벤트·BM 과 같은 폼(`CatalogForm`)이라, 메이플 ID 보기를 세우는 칸이 이미 있다.

| 시트 | 메이플 ID 도 고르는 분류 | 캐릭터만 고르는 분류 |
|---|---|---|
| 수입 | 기타 | 사냥 · 사냥 전리품 판매(솔 에르다 조각 포함) · 아이템 판매 |
| 지출 | 컨텐츠 · 이벤트·BM · 기타 | 버프 · 주문서 · 심볼 강화 · 헥사 매트릭스 · 아이템 구매 |
