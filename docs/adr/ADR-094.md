# ADR-094 — 3단계 구조 리팩터링: 아토믹 디자인 + 합성 패턴, **DOM 보존을 안전장치로**

**날짜**: 2026-08-05
**상태**: **구현 완료**(2026-08-05) — 7단계 전부. 착수 후 실측으로 계획을 3번 정정했다(atoms 5→3 · `CharacterAccordion` compound→컨텍스트 · 4단계는 DOM 무변경). **DOM 을 바꾼 단계는 하나도 없다** — 스냅샷 14케이스가 전 구간 무변경
**관련**: [[ADR-092]] [[ADR-093]](1·2단계) · [[ADR-077]] [[ADR-080]] [[ADR-084]] [[ADR-085]](보스 수익 스크롤·sticky 결정 사슬) · [[ADR-047]] [[ADR-049]](sticky 헤더 기하) · [[ADR-064]](on-* 토큰) · [[ADR-060]] [[ADR-061]] [[ADR-062]](빈 상태·로딩·실패 표현)

## 맥락

사용자 방향(2026-08-05): **파일 길이 + 인라인 Tailwind 클래스를 함께 정리**하고, **아토믹 디자인**으로
점차 확장되는 컴포넌트 구조를 지향하며, **compound component**·**render prop** 패턴을 적극 활용해
가독성을 높인다.

착수 전 실측에서 이 방향을 뒷받침하는 사실과, 방식을 제약하는 사실이 함께 나왔다.

**뒷받침 ① — 프리미티브는 이미 문서에 정의돼 있고 코드에만 없다.** `design-system.md` 의
「기본 컴포넌트」절이 카드·버튼·입력 필드를 **클래스 문자열로** 규정하고 있다. 코드는 그 문자열을
637곳에 흩어 반복한다(고유 323개 = 중복 49%). 즉 이 작업은 새 추상을 발명하는 것이 아니라
**이미 있는 규정을 코드로 승격**하는 것이다.

**뒷받침 ② — 프롭 개수가 구조 부재를 가리킨다.**

| 컴포넌트 | 프롭 | 성격 |
|---|---|---|
| `CharacterAccordion` (BossProfitScreen) | **11** | 헤더+본문 구조를 프롭으로 평탄화 |
| `DropIndicator` (BossProfitScreen) | 10 | |
| `AccountFlowStatus` | 10 | |
| `MonthlyAccordionBody` | 8 | |
| `CharacterTrackingPicker` | 8 | |
| `Modal` | 7 | 그중 **4개가 스타일 탈출구**(`card` `maxWidth` `align` `tightBottom`) |

`Modal` 이 특히 명확하다 — `card={false}` 는 "카드 껍데기를 빼 달라"는 뜻이고, 이것은 **프롭이
아니라 구조**로 표현해야 할 것이 flag 로 새어 나온 것이다.

**제약 — 이 저장소의 취약점은 로직이 아니라 DOM·CSS 관계에 있다.**

| 파일 | LOC | ADR 언급 | 테스트 LOC |
|---|---|---|---|
| `BossProfitScreen.tsx` | 1,775 | **117** (15줄당 1회) | 2,770 (1.6x) |

테스트 291케이스로 안전망은 두껍지만 **jsdom 은 레이아웃을 계산하지 않는다** — `getBoundingClientRect`
가 전부 0이고(테스트 코드에도 명시: `BossProfitScreen.test.tsx:1531`) 스태킹 컨텍스트·sticky
흡착·z 순서는 **아무것도 검증되지 않는다.** `BossProfitScreen` 에는 레이아웃 실측 7곳과
`isolate`/`sticky`/`z-*` 참조 65개가 있고, 그 값들은 [[ADR-080]]~[[ADR-085]] 에서 **실기기에서
여러 번 틀린 끝에** 얻은 것이다(그중 [[ADR-084]] 는 폐기까지 갔다).

## 결정 1 — 합성 패턴은 취약 구조를 **한 곳에 가두는 수단**으로 쓴다 (장식이 아니라)

여기서 compound component 와 render prop 을 쓰는 이유가 일반론과 다르다.

`sticky top-0 z-10 …` 클래스가 5곳에, sticky 헤더 + 페이드 조합이 4곳에 복붙돼 있다. **복붙된
취약 구조는 한 곳이 고쳐져도 나머지가 안 고쳐진다** — [[ADR-085]] 가 sticky 를 `position: fixed`
+ spacer 로 바꿨을 때 실제로 겪은 종류의 문제다.

- **Compound component** 는 "이 조각들은 이 DOM 관계를 유지해야 한다"를 타입으로 강제한다.
  `<PageHeader>` 안에 헤더·spacer·페이드가 함께 살고, 호출부는 그 관계를 깰 수 없다.
- **Render prop** 은 부모가 취약한 껍데기(측정·sticky·z 층)를 소유한 채 **내용만** 호출부가
  갈아 끼우게 한다. 껍데기가 복사되지 않으므로 고칠 곳이 하나로 유지된다.

즉 이 두 패턴이 **결정 4의 DOM 보존 규칙을 지키면서도 파일을 줄이는 유일한 방법**이다. 프롭
드릴링을 줄이는 것은 부수 효과다.

**남용 방지** — 사용자 전역 규칙(`~/.claude/CLAUDE.md`)의 "단일 사용 코드에 추상을 만들지 말 것"과
충돌하지 않도록, 패턴 적용은 **둘 중 하나를 만족할 때만** 한다:

1. 실제 호출부가 **2곳 이상**이다, 또는
2. 취약 구조(sticky·측정·스태킹)를 감싸 **복붙을 원천 차단**한다.

둘 다 아니면 패턴을 쓰지 않는다. render prop 은 특히 — 호출부가 하나이고 취약하지도 않으면
그냥 `children` 이 낫다.

## 결정 2 — 아토믹 계층은 **의존 방향 규칙**이고, 디렉터리는 그 표현이다

계층을 이렇게 확정한다. 배치는 기존 인벤토리를 그대로 옮긴 것이라 새로 만드는 것은 atoms 뿐이다.

| 계층 | 정의 | 대상 |
|---|---|---|
| **atoms** | 상태 없음. 토큰과 자기 상자만 안다 | **신설**: `ProgressBar` `Button` `Card` (결정 3 정정 — `Input`·`Badge` 제외) / **기존**: `MapleSpinner` `MapleSweepSpinner` `ProfitIcon` `DifficultyBadge` `AnimatedMeso` |
| **molecules** | atoms 조합. 도메인 모름 | `LoadingState` `EmptyState` `UnavailableNotice` `ErrorState` `BossPortrait` `ValuableDropBadge` `PullToRefreshIndicator` `CharacterSelectDropdown` |
| **organisms** | 상태·포털·컨텍스트를 가짐 | `Modal` `BottomSheet` `ProgressModal` `CharacterTrackingPicker` `ToastStack` `DropEffectOverlay` `ErrorBoundary` |
| **templates** | **취약 구조가 사는 곳** — 화면 셸(fixed 헤더+spacer·스크롤 영역·페이드·PTR) | 신설. [[ADR-085]] [[ADR-047]] [[ADR-049]] 의 기하가 여기로 |
| **pages** | `app/*` 화면. 데이터·스토어 연결 | 현행 유지 |

**규칙: 의존은 아래로만 흐른다.** atom 이 molecule 을 import 하면 계층이 무너진 것이다. 이것이
"점차 확장되는 구조"의 실질 — 새 컴포넌트를 넣을 자리가 계층으로 결정된다.

**디렉터리 물리 이동은 한다 — 다만 마지막에, 단독 커밋으로**(사용자 확정 2026-08-05). 계층이
디렉터리에 드러나야 "새 컴포넌트를 어디 둘지"가 구조로 정해지고, 규칙만 문서에 있으면 시간이
지나며 어긋난다.

순서를 뒤로 미루는 이유는 위험이 아니라 **diff 의 성격** 때문이다 — 경로 변경은 전 파일의
import 를 건드리므로, 내용 변경과 섞이면 그 안에 실수가 숨는다. 마지막에 단독으로 하면
**순수 rename diff** 가 되어 리뷰가 기계적으로 끝난다(작업 순서 7단계).

## 결정 3 — atoms 는 `design-system.md` 가 이미 규정한 것만 만든다

발명하지 않는다. 「기본 컴포넌트」절의 카드·버튼·입력 + 실제 반복이 확인된 배지·프로그레스바까지다.

### 정정(2026-08-05) — 5개 중 **3개만 만든다**

착수해 실측하니 `Input` 과 `Badge` 가 결정 1의 남용 방지선(호출부 2곳 이상)에 걸렸다.

| atom | 실측 | 판정 |
|---|---|---|
| `ProgressBar` | 9곳 · 변형 2종(tone) | **만든다** (구현 완료) |
| `Button` | 16곳 · 변형 3종(primary/text/danger) | **만든다** (구현 완료) |
| `Card` | 21곳 · 코어 4토큰 단일 | **만든다** (구현 완료) |
| `Input` | **실제 입력 필드 1곳** | **만들지 않는다** |
| `Badge` | 15곳에 **고유 변형 12종** | **만들지 않는다** |

- **`Input`** — `rounded-[10px]` 사용처 5곳 중 진짜 입력은 `ApiKeyForm` 하나뿐이고, 나머지 넷은
  안내·경고 박스(`UnavailableNotice` `StaleBanner` 등)라 성격이 다르다. 단일 사용에 추상을
  만드는 것은 사용자 전역 규칙과 결정 1이 함께 금지한다.
- **`Badge`** — 톤(third/primary/secondary/surface-2) × 두께(semibold/medium/bold) × 여백
  (`px-2.5 py-1`/`px-2 py-0.5`/`px-2 py-1`) × 부가(`ml-auto` `tabular-nums` `shrink-0`
  `inline-block`)로 갈려 **15곳에 12종**이다. 사이트당 1.25회꼴이라 묶어도 같은 분산이 프롭으로
  옮겨갈 뿐이고, 프롭 4개짜리 atom 은 결정 1이 경계한 "호출부마다 예외"의 전형이다.

> 배지 톤이 실제로 굳으면(같은 조합이 3곳 이상 반복되면) 그때 만든다. **지금은 근거가 없다.**

#### 재정정(2026-08-05) — `Badge` 는 **만든다** (첫 계산이 틀렸다)

"15곳에 고유 변형 12종"은 `ml-auto` `tabular-nums` `shrink-0` `inline-block` 같은 **레이아웃
유틸까지 조합에 포함**해 센 값이었다. Button·Card 에서는 레이아웃을 atom 이 갖지 않기로 해
놓고, 정작 배지를 셀 때는 그것까지 한 덩어리로 본 것이다.

레이아웃을 걷어내고 **외형만** 세면 조합이 10종으로 줄고, 그중 둘이 **각각 3곳**으로 위 기준을
통과한다 — `bg-primary-tint/text-primary-ink` 와 `bg-third-tint/text-third-ink` 를
`px-2.5 py-1 font-semibold` 로 쓰는 형태다.

**그 둘만 덮는 좁은 atom 을 만든다**(6곳). 두께가 다른 것(`font-bold` 1곳)과 토큰 쌍이 아닌 것
(`bg-surface-2` 위의 `text-text`·`text-text-muted`)은 각각 1~2곳이라 인라인으로 남긴다 — 그것까지
프롭으로 삼키면 결정 1이 경계한 "호출부마다 예외"가 된다.

**변형(variant)은 명시적으로 가른다** — 디자인 원칙 2가 *"컴포넌트 성격별로 라운딩을 다르게 줘
캐주얼함을 표현(전부 rounded-2xl 통일 금지)"* 이라고 못박았다. 카드 14px · 버튼 pill · 인풋 10px 는
**서로 다른 atom** 이지 한 atom 의 옵션이 아니다. 프리미티브가 이 차이를 뭉개면 문서가 금지한
"템플릿 느낌"을 코드가 만든다.

**하지 않는 것** — `text-sm text-text-muted`(22회) `space-y-2`(16회) `flex items-center gap-2`(16회)
같은 **유틸리티 조합**은 감싸지 않는다. 중복 상위는 전부 이런 것들이고, 이걸 컴포넌트로 만들면
중복보다 나쁘다. 인라인 클래스 정리의 목표는 **"모든 className 제거"가 아니라 "디자인 결정이
박힌 문자열의 단일화"** 다.

> 참고 — 점검 때 최대 근거로 들었던 "아이콘 버튼 클래스 26회 중복"은 **[[ADR-092]] 로 이미
> 해소됐다**(그 26회가 전부 삭제된 디버그 화면 안에 있었다, 현재 0회). 남은 최대 중복은
> 카드 셸 8회다.

### 정정(2026-08-05) — `CharacterAccordion` 은 compound 가 아니라 **컨텍스트** 문제였다

착수해 재보니 이 항목도 결정 1의 바에 걸렸고, **진짜 문제는 다른 곳에 있었다.**

- **호출부가 1곳**이다(`characterGroups.map` 안). 헤더/본문으로 가르는 compound 는 결정 1의
  두 조건(2곳 이상 / 취약 구조 복붙 차단)을 **둘 다 만족하지 못한다** — 이 컴포넌트의 취약
  구조(`isolate` · 카드 안 sticky 헤더 · 헤더 실측)는 **이미 한 컴포넌트 안에 갇혀 있어서**,
  쪼갠다고 복붙이 줄지 않는다. `Input`·`Badge` 를 뺀 것과 같은 논리다.
- **프롭 11개의 정체는 "헤더+본문의 평탄화"가 아니라 스레딩이었다.** 8개 프롭(`tab`
  `periodKey` `now` `dropsByRowKey` `setPartySize` `setBossDrops` `isMonthlyBossQueryable`
  `onRetryPeriod`)이 `BossProfitScreen → CharacterAccordion → Weekly/MonthlyAccordionBody →
  BossProfitBossRow` 4단계를 타고 내려가며 **타입 선언 25곳 + JSX 전달 26곳 = 51지점**을 만든다.
  헤더/본문으로 갈라도 본문은 여전히 같은 값들을 받아야 하므로 **하나도 줄지 않는다.**

그래서 compound 대신 **컨텍스트**를 쓴다(합성 패턴의 다른 얼굴이다). 기간·탭·스토어 바인딩을
컨텍스트로 내리면 51지점이 사라지고, 각 컴포넌트의 프롭에는 **자기가 실제로 다루는 것만** 남는다.

> **이 변경이 오히려 가장 안전한 축에 든다** — 컨텍스트는 데이터 흐름만 바꾸고 **DOM 을 전혀
> 건드리지 않는다.** 저장소에서 가장 취약한 파일이지만, 그 취약함은 DOM·CSS 관계에 있고
> 이 변경은 정의상 거기에 닿지 않는다. DOM 스냅샷 6케이스가 그것을 확인한다.

## 결정 4 — **렌더 결과 DOM 은 1:1 로 같아야 한다** (안전장치)

패턴을 얼마나 쓰든, 리팩터링 커밋의 렌더 결과는 **DOM 중첩·클래스·순서가 이전과 동일**해야 한다.
컴포넌트를 쪼개도 최종 트리는 그대로다.

이유는 결정의 맥락에 있다 — 테스트가 못 잡는 유일한 영역이 정확히 그 DOM 관계다. DOM 이 같으면
스태킹 컨텍스트·sticky 흡착·측정값이 바뀔 수 없으므로, **[[ADR-077]]~[[ADR-085]] 를 다시 겪지
않는다.**

이걸 **자동으로 검증한다** — 리팩터링 대상 화면의 렌더 트리 스냅샷을 리팩터링 **전에** 떠서
고정하고, 이후 커밋마다 대조한다. 스냅샷이 바뀌면 그 커밋은 순수 리팩터링이 아니다.

**정밀화(2026-08-05) — "동일"은 클래스 *집합* 기준이다.** 같은 뜻의 클래스가 파일마다 다른
순서로 적혀 있어서(`rounded-[14px] border border-border bg-surface` vs `rounded-[14px] bg-surface
border border-border`), 프리미티브로 묶으면 순서가 하나로 통일된다. 그런데 **class 속성 안의
유틸리티 순서는 CSS 에 아무 영향이 없다** — 적용 여부는 스타일시트 순서가 정한다. 그래서
스냅샷은 클래스 토큰을 정렬해 비교하고, 순서 변화는 무시하되 **추가·삭제는 그대로 잡는다**
(둘 다 의도적 변형으로 확인: `opacity-90` 추가 → 실패, 순서만 뒤바꿈 → 통과).

> 예외를 두는 유일한 경우: 의도적으로 DOM 을 바꾸는 변경. 그런 커밋은 **분리하고, 실기기 확인
> 전까지 머지하지 않는다.**
>
> **정정(2026-08-05)** — 여기 예로 들었던 "sticky 헤더 4곳을 `<PageHeader>` 로 통일하며
> [[ADR-085]] 구조에 맞춤"은 **틀린 전제였다.** [[ADR-085]] 결정 1은 보스 수익 **한 화면만**
> `fixed` 로 바꾸고 *"다른 4개 화면은 공용 sticky 레시피 그대로"* 라고 명시했다 — 그 화면만
> 문서 최상단 첫 요소라 `fixed` 로 바꿔도 보이는 모습이 같았기 때문이다. 즉 나머지 4곳을
> `fixed` 로 통일하는 것은 [[ADR-085]] 를 따르는 것이 아니라 **어기는 것**이다. 그래서 4단계도
> 기존 sticky 마크업을 **그대로** 추출하며, 결국 **DOM 을 바꾸는 단계는 하나도 없다.**

## 결정 5 — `useMemo` 는 넣지 않는다 (측정 근거 없음)

점검이 "3대 화면 모두 `useMemo` 0회"를 지적했지만 성능 문제의 증거가 없다. Lighthouse 실측
TBT **10ms**(임계 200ms), 메인스레드 Script Evaluation 167ms. 증상 없이 넣는 메모이제이션은
의존성 배열이라는 새 버그 표면만 늘린다. 느린 것이 관측되면 그때 넣는다.

## 결정 6 — 레이어 누수 1건을 고친다

`app/settings/CacheDataSection.tsx` 가 `storage/` 함수를 직접 호출한다(`clearCacheData`
`getCacheDataSizes` `setPendingNotice` `closeBossProfitDb`) — CLAUDE.md CRITICAL 규칙과 [[ADR-003]]
위반이다. `features/settings/` 경유로 바꾼다. 나머지 `app/*` → `storage/` import 는 전부
type-only 라 무해하다.

## 결정 7 — 분해의 트리거는 LOC 가 아니라 **관심사 개수**다 (2026-08-05 추가)

앞선 결정들이 "LOC 를 목표로 삼지 않는다"고 정했는데, 실행 중 사용자가 정확히 짚었다 —
**결정 밀도가 높을수록 오히려 나눠서 파일 하나가 이고 있는 무게를 줄여야 한다.** 맞는 말이고,
내가 두 가지를 뭉갠 것이었다:

- **JSX 구조를 재배치**하면 스태킹 컨텍스트·sticky 흡착이 깨질 수 있다 → 이건 실제 위험이다.
- **컴포넌트를 다른 파일로 옮기는 것**은 DOM 을 전혀 바꾸지 않는다 → 위 위험과 **무관**하다.

나는 앞의 위험을 근거로 뒤의 이동까지 막고 있었다. `BossProfitScreen` 은 118개 결정을 이고
있는데, 그건 한 사람이 머리에 담을 수 있는 양이 아니다.

**그렇다고 LOC 를 트리거로 삼는 것도 아니다.** 실측하니 크기와 성격이 따로 논다:

| 파일 | LOC | 판정 |
|---|---|---|
| `lib/boss-profit-period.ts` | 375 | **나누지 않는다** — 함수 20개가 전부 기간 계산 한 가지 |
| `lib/theme-derive.ts` | 484 | **나누지 않는다** — 전부 토큰 파생 한 흐름 |
| `features/schedule-sync/schedule-sync.ts` | 580 | **나눈다** — 로스터 조회 + 동기화 오케스트레이션 |
| `features/boss-profit/store.ts` | 1,316 | **나눈다** — 복원력·행빌드·백필·드롭·기간로드·스토어 |

**규칙**: 파일이 **관심사를 둘 이상** 갖고 있으면 나눈다. 크기는 신호일 뿐 기준이 아니다.
그리고 나눌 때는 **DOM 관계로 묶인 것만 함께 둔다** — `BossProfitScreen` 과
`CharacterAccordion` 은 페이지 헤더 실측값이 카드 내부 sticky 오프셋으로 흘러가므로 함께
남기고, 그것과 무관한 조각은 전부 뺀다.

한 컴포넌트가 통째로 큰 경우(`BossScreen` 613줄에 함수 2개)는 파일 분리가 아니라 JSX
재구조화가 필요하다 — **DOM 이 바뀌므로 별도 판단**으로 미룬다.

## 작업 순서

각 단계는 별도 커밋이고, 앞 단계가 다음 단계의 안전망이 된다.

1. **DOM 스냅샷 고정** — 대상 화면 렌더 트리를 스냅샷 테스트로 박는다. (이후 전부의 안전망)
2. **atoms 신설 + 치환** — `ProgressBar` `Button` `Card` 3종(결정 3 정정 — `Input`·`Badge` 는 근거 미달로 제외). DOM 동일.
3. **compound 전환** — `Modal`(프롭 4개 → 구조, **구현 완료**), ~~`CharacterAccordion`(프롭 11개 → 헤더/본문)~~ → **컨텍스트로 대체**(아래 정정).
4. **templates 추출** — sticky 셸 + 테마 배경 조각 + 하단 페이드를 `<PageHeader>` 로
   (4화면 — 보스 수익은 [[ADR-085]] 의 `fixed` 라 제외, 드랍 히스토리는 오버레이 서브 화면이라
   backdrop·fade 가 없어 제외). 결정 4 정정대로 **DOM 보존**이라 스냅샷이 그대로여야 한다.
5. **순수 함수 분리** — `store.ts`·`BossProfitScreen` 의 순수 헬퍼를 별도 모듈로.
6. **레이어 누수 수정** (결정 6).
7. **디렉터리 물리 이동** — `components/{atoms,molecules,organisms,templates}/`. **단독 커밋**,
   순수 rename + import 경로 변경만. DOM 스냅샷이 그대로여야 한다.
   의존 방향은 `components/__tests__/layer-dependencies.test.ts` 가 강제한다 — 규칙이 문서에만
   있으면 시간이 지나며 어긋나고, 그때는 이미 되돌리기 어렵다.
