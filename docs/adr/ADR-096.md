# ADR-096 — 스케줄러 화면 상태(탭·필터·선택 캐릭터)의 소유 위치

**날짜**: 2026-08-05
**상태**: 설계 · 구현 전
**관련**: [[ADR-035]](수동 편집을 전용 관리 페이지로 분리 — 이 결함이 생긴 지점) · [[ADR-060]](빈 상태 CTA) · [[ADR-023]](보스 수익 주간/월간 탭 — 이미 스토어에 있는 선례) · [[ADR-003]](로컬 저장은 어댑터 경유) · [[ADR-092]](라우트 `lazy` 분할 — 화면 언마운트가 기본 동작인 이유)

## 맥락

컨텐츠·보스 스케줄러의 **탭 선택이 화면 로컬 `useState`** 였고, 스케줄러 화면과 관리 화면이 그 값을 **각자 따로** 들고 있었다. 같은 타입 선언이 네 파일에 두 벌씩 복제돼 있던 것이 그 구조를 그대로 드러낸다.

```
type ContentTab = 'daily' | 'weekly'    ← ContentScreen.tsx · ContentManageScreen.tsx
type BossTab = 'weekly' | 'monthly'     ← BossScreen.tsx · BossManageScreen.tsx
```

여기서 성질 두 개가 나오고, 각각 다른 증상을 만들었다.

**성질 A — 화면 생명주기에 묶인다.** 탭 이동은 라우트 언마운트를 동반하므로([[ADR-092]] 이후 `lazy` 라 더 뚜렷하다) 로컬 state 가 사라진다. 주간을 보다가 다른 탭에 다녀오면 일간으로 돌아왔고, 관리 화면에서 복귀해도(`navigate('/content')` — 아무것도 실어 나르지 않는다) 마찬가지였다.

**성질 B — 두 화면이 서로를 모른다.** 관리 화면이 자기 초기값으로 시작하므로, 주간에서 "컨텐츠 관리"를 눌러도 일간 선택 화면이 열렸다.

성질 B 의 최악 사례가 빈 상태 CTA 다. `contentEmptyProps(tab)` 는 **탭을 인자로 받아** "주간 항목을 골라주세요"라고 안내해 놓고([[ADR-060]]), 정작 이동할 때 그 탭을 버렸다. 사용자는 주간을 고르라는 안내를 받고 일간 목록에 도착한다.

보스 쪽은 양쪽 기본값이 모두 `'weekly'` 라 증상 B 가 월간 탭에서만 드러나 덜 보였을 뿐 구조는 동일하다.

**같은 앱에 이미 반대 사례가 있다.** 보스 수익 화면의 주간/월간 탭은 스토어가 소유하고([[ADR-023]]), 그래서 다른 탭에 다녀와도 유지된다. 두 스케줄러만 로컬에 남아 있었다.

## 결정 1 — 탭·필터는 기능 스토어가 소유한다

`features/content-scheduler/store.ts` 와 `features/boss-scheduler/store.ts` 에 뷰 상태를 둔다.

| 상태 | 스토어 | 기본값 |
|---|---|---|
| `activeTab` | content-scheduler | `'daily'` |
| `activeTab` | boss-scheduler | `'weekly'` |
| `weeklyFilter` / `monthlyFilter` | boss-scheduler | `'all'` / `'all'` |

보스 솔로/파티 필터를 함께 옮기는 이유 — **같은 결함의 다른 인스턴스**다. 탭만 살리면 돌아왔을 때 탭은 유지되는데 필터만 초기화돼 "반쯤 기억하는" 상태가 되고, 그건 전부 초기화되는 것보다 설명하기 어렵다. 두 필터가 탭마다 독립이라는 성질은 그대로 유지한다(기존 정책).

`ContentTab`/`BossTab` 타입도 스토어로 옮겨 **선언을 한 벌로** 만든다. 복제된 선언은 두 화면이 각자 판단해도 되는 것처럼 보이게 하는 원인이었다.

**보스 수익의 `setTab` 과 달리 이 세터들은 동기다.** 그쪽은 탭이 바뀌면 기간을 다시 불러와야 해서 `async` 지만, 스케줄러의 탭은 이미 받아 둔 데이터를 갈라 보여줄 뿐이라 네트워크가 없다. 같은 모양으로 맞추려고 `async` 를 씌우지 않는다.

## 결정 2 — 관리 화면은 **진입 시점에** 스케줄러의 탭을 이어받는다 (한 방향)

일간에서 들어가면 일간 관리, 주간에서 들어가면 주간 관리. 보스도 주간→주간, 월간→월간.

**이어받기는 진입 시점 한 번뿐이고, 관리 화면에서의 탭 전환은 스케줄러로 되돌리지 않는다.**

처음에는 두 화면이 스토어 값을 그대로 공유하게 해 양방향으로 동기화했는데, **그게 과했다**(2026-08-05 사용자 지적). 관리 화면에서 다른 탭을 잠깐 뒤져보기만 해도 돌아갔을 때 스케줄러가 그 탭으로 바뀌어 있었다 — 이 ADR 이 고치려던 문제("보던 자리를 잃는다")를 정확히 반대 방향으로 다시 만든 셈이다.

관리 화면은 스케줄러의 **하위 작업 화면**이다. 들어올 때 맥락(어느 탭에서 왔는지)을 이어받는 것은 그 관계에 맞지만, 거기서 무엇을 뒤져봤는지는 그 화면 안의 일이라 부모 화면을 건드릴 이유가 없다. 두 화면의 탭이 잠시 갈라지는 것은 **이 방향에서는 정상**이다.

구현은 관리 화면의 로컬 `useState` 초기값을 스토어 탭으로 주는 것이다(`useState(schedulerTab)`). 초기값은 첫 렌더에만 읽히므로 "진입 시점"이 정확히 표현되고, 화면을 다시 열면 그때의 스케줄러 탭을 새로 이어받는다.

원래 결함과 구별되는 점 — 그때는 초기값이 **하드코딩**(`'daily'`/`'weekly'`)이라 어디서 왔든 무시했다. 지금은 초기값이 스케줄러의 현재 탭이다.

## 결정 3 — 영속화하지 않는다

앱을 껐다 켜면 기본 탭으로 돌아온다. 저장 매체([[ADR-003]] 어댑터)를 태우지 않는다.

이유는 **요청받은 문제가 "세션 안에서 보던 자리를 잃는 것"** 이기 때문이다. 재시작 후 복원은 다른 요구이고, 보스 수익도 지금 그렇게 하지 않는다. 필요해지면 그때 별도 결정으로 다룬다.

## 결정 4 — 관리 화면의 캐릭터 표시를 드롭다운으로 바꾸고, 선택은 같은 스토어를 쓴다

관리 화면 우상단은 지금까지 **읽기 전용 pill**(월드 엠블럼 + 캐릭터명)이었다. 캐릭터를 바꾸려면 뒤로 나가 스케줄러에서 바꾸고 다시 들어와야 했다 — 관리 화면이야말로 캐릭터를 갈아 가며 쓰는 화면인데도.

그 자리를 기존 `CharacterSelectDropdown` 으로 바꾸고, `onSelect` 는 스케줄러 화면과 **같은 `selectCharacter` 액션**을 호출한다. 그래서 관리 화면에서 바꾼 캐릭터가 돌아갔을 때 스케줄러에도 그대로 반영된다.

**탭과 반대로 이쪽은 양방향이다**(결정 2 참조). 성격이 다르기 때문이다 — 탭은 "무엇을 보고 있는가"라 잠시 갈라져도 되지만, 선택 캐릭터는 **편집 대상**이다. 관리 화면에서 다른 캐릭터의 추적 항목을 고쳐 놓고 돌아왔을 때 스케줄러가 이전 캐릭터를 보여주면, 방금 한 편집이 어디에 적용됐는지 알 수 없다.

## 결정 5 — 드롭다운에 컴팩트 변형을 추가한다

스케줄러의 드롭다운은 제목 아래 **독립된 줄**에 놓이는 주 컨트롤이라 `min-w-[160px] py-3` 다(design-system "스케줄러 캐릭터 드롭다운"). 관리 화면은 제목 줄 우측의 작은 자리이므로 그대로 넣으면 헤더가 두꺼워지고 좁은 화면에서 제목과 폭을 다툰다.

`CharacterSelectDropdown` 에 변형 하나(`size`)를 더해 **기존 pill 과 같은 크기감**(`text-xs`, 낮은 패딩, 작은 엠블럼)으로 그린다. 자리와 무게는 그대로 두고 "누를 수 있다"만 바뀐다.

단일 사용 추상을 만들지 않는다는 전역 규칙과 충돌하지 않는다 — 호출부가 실제로 둘(스케줄러 2개 화면 · 관리 2개 화면)이고, [[ADR-094]] 가 정한 기준("호출부 2곳 이상")을 만족한다.

**화살표는 두 크기 모두 직접 그린다**(`appearance-none` + `ChevronDown`, 2026-08-05 추가).

처음에는 컴팩트의 화살표를 안쪽으로 넣으려고 `padding-right` 를 키웠는데 **틀린 전제였다.** 브라우저에서 재보니 네이티브 `<select>` 의 화살표는 **오른쪽 테두리에 붙어 함께 움직인다** — `pr` 을 12/16/32/64px 로 바꿔도 화살표와 테두리 사이 간격은 그대로고 상자만 넓어진다(글자만 왼쪽으로 밀린다). 위치를 정하려면 UA 화살표를 끄는 수밖에 없다.

끄고 나니 **기본 크기까지 통일할 이유**가 하나 더 드러났다. UA 화살표는 플랫폼마다 모양이 다른데 이 앱은 Android WebView(Chrome)·iOS WKWebView(Safari) 양쪽에서 도는 하이브리드다([[ADR-001]]). 한쪽만 직접 그리면 앱 안에 두 종류의 화살표가 생기고, 남은 쪽은 기기마다 다르게 보인다. 둘 다 그린다.

이 변경은 스케줄러 화면의 DOM 을 바꾸므로 [[ADR-094]] 스냅샷 3건을 함께 갱신했다 — 차이가 `appearance-none` · `px-4`→`pl-4 pr-9` · chevron 추가뿐임을 확인한 뒤 갱신한 것이고, 그 가드가 의도치 않은 변화를 걸러 준다는 전제는 그대로다.

## 검토했으나 기각

- ~~URL 쿼리 파라미터(`/content?tab=weekly`)로 표현~~ → 증상 3건을 똑같이 해결하고 뒤로가기와도 잘 맞지만, **같은 종류의 상태를 앱 안에서 두 방식으로 다루게 된다**(보스 수익은 스토어). 한쪽으로 모으는 편이 낫고, 이미 있는 쪽이 스토어다. 훗날 딥링크가 필요해지면 그때 스토어를 URL 과 동기화하는 문제로 다루면 된다.
- ~~관리 화면 진입 시 `navigate` state 로 탭을 넘기기~~ → 진입 경로가 3곳(헤더 버튼 · 빈 상태 CTA 2종)이라 전부 실어 보내야 하고, 하나만 빠뜨려도 조용히 예전 동작으로 돌아간다. 복귀 경로도 같은 처리가 필요하다. 상태를 공유하면 배선 자체가 사라진다.
- ~~탭을 유지하되 보스 필터는 두기~~ → 결정 1 참조. 반만 기억하는 상태를 만든다.

## 고정 방법

화면 단위 테스트로 **언마운트 후 재마운트에도 살아남는지**를 본다 — 이 결함의 본질이 "화면이 사라질 때 같이 사라지는 것"이라, 한 번 렌더해서 보는 테스트로는 잡히지 않는다. 관리 화면이 스케줄러의 탭으로 초기 렌더되는지, 관리 화면 드롭다운이 `selectCharacter` 를 부르는지도 함께 고정한다.
