# ADR-296: 넥슨 Open ID 로그인을 API 키와 **나란히** 둔다. 토큰은 서버가 든다

> ⚪ 미구현 · 2026-09-19 · 설계 · 이슈 #490 (서버 몫은 maple-routine-server#1)

> 사용자 지정(2026-09-19): api-key 로 호출하는 기능도 모두 남긴다. OAuth 와 access token 으로
> 호출하는 방식을 추가해 two way 로 운영한다. 넥슨 로그인 1개 + API 키 복수 개 방식도 가능하게
> 한다.

**관련**: [[ADR-215]](API 키 화면이 이 앱의 로그인 화면이다. 그 문서가 예고한 자리다) ·
[[ADR-007]](개인 API 키로 직접 호출) · [[ADR-003]](백엔드 없이 기기 저장소) ·
[[ADR-227]](자체 호스팅 서버) · [[ADR-297]](메이플 ID 축)

## 맥락

### 막혀 있던 문이 열렸다

[[ADR-007]] 이 Open ID 를 안 쓰기로 한 근거는 둘이었다. 승인이 필요한 기능인데 신청하지 않은
상태라는 것, 그리고 개인 API 키만으로 필요한 호출이 다 된다는 실측이다. **앞의 것이 2026-09-19
해소됐다**(프렌즈 승인). 뒤의 것은 여전히 사실이라, 이 문서는 **바꾸는 결정이 아니라 더하는
결정**이다.

### Open ID 로 부를 수 있는 것은 넷뿐이다

프렌즈 API 목록(`openapi.nexon.com/ko/friends/maplestory/`, 2026-09-19 확인)이 전부다.

| 묶음 | 엔드포인트 | 스코프 key |
|---|---|---|
| 계정 | `/maplestory/v1/character/list` | `maplestory.characterlist` |
| 계정 | `/maplestory/v1/user/achievement` | `maplestory.achievement` |
| 확률 | `/maplestory/v1/history/cube` · `history/starforce` · `history/potential` · `history/soul-potential` | `maplestory.cube` · `starforce` · `potential` · `soulpotential` |
| 스케줄러 | `/maplestory/v1/scheduler/character-state` | `maplestory.scheduler` |

이 넷은 인증 헤더가 `Authorization: Bearer $AccessToken` 으로 **따로 문서화돼 있다**. 앱이 쓰는
나머지는 그 목록에 없고 공개 레퍼런스에서 `x-nxopen-api-key` 가 `*required` 다. 특히 today 화면이
읽는 `character/basic`, 메소 획득량이 읽는 `character/item-equipment` · `character/symbol-equipment` ·
`user/union-raider`([[ADR-177]])가 거기 있다. **그래서 Open ID 는 API 키를 대체할 수 없다.**

### `client_secret` 을 앱에 둘 수 없다

토큰 교환 `POST https://openid.nexon.com/oauth2/token` 이 `client_secret` 을 필수로 받고, 네이티브
앱용 대안인 PKCE 는 규격에 없다. 넥슨 보안 가이드라인도 액세스 토큰을 서버에서만 관리하라고
적는다. 앱 번들에 넣으면 그대로 뜯긴다.

### 등록 화면은 iOS 와 안드로이드를 받는다

소개 문서는 모바일 앱(Android, iOS)을 지원 예정이라고 적는다. 그런데 애플리케이션 등록 화면에서는
플랫폼으로 iOS 와 안드로이드를 고를 수 있다(2026-09-19 확인). iOS 는 Bundle ID 와 redirect URI 를,
안드로이드는 패키지 이름과 redirect URI 를 받는다. redirect URI 예시가
`com.mycompany.myapp://oauth/callback` 이라 커스텀 스킴을 그대로 등록할 수 있다.

안드로이드 화면은 **서명 해시를 받지 않는다.** 그래서 넥슨은 콜백이 우리가 서명한 앱으로만 가도록
막아 주지 않는다(결정 9).

## 결정

### 결정 1. 두 인증을 나란히 둔다. 어느 쪽도 다른 쪽을 대체하지 않는다 (사용자 지정)

`AuthConfig` 가 지금처럼 키 하나가 아니라 **인증 수단의 목록**을 든다.

```
넥슨 로그인   0개 또는 1개   uid · 서버 세션        프렌즈 API 넷
API 키        0개 이상        x-nxopen-api-key      앱이 쓰는 전부
```

둘 다 없으면 로그인 화면이다. 하나라도 있으면 앱이 선다. **로그인만 있는 사용자와 키만 있는
사용자가 둘 다 정상 상태**이고, 이것이 이 문서의 전제다.

- [[ADR-215]] 는 프렌즈 승급 시 OAuth2 가 API 키 폼을 **대체한다**고 적었다. 그 예측을 여기서
  정정한다. 대체하면 위 표의 오른쪽 열(앱이 쓰는 전부)을 잃는다.

### 결정 2. 넥슨 로그인은 하나, API 키는 여러 개 (사용자 지정)

복수 키의 목적은 **다른 넥슨 계정의 캐릭터까지 보는 것**이다. 키 하나로도 여러 메이플 ID 가
한꺼번에 조회되므로([[ADR-007]] 실측) 같은 계정의 키를 여럿 둘 이유는 없다.

- 로그인이 둘 이상일 이유도 없다. 로그인은 앱 사용자를 식별하는 축이고, 키는 거기 붙는 자원이다.
- 키마다 이름을 붙일 수 있어야 한다. 값이 비슷하게 생겨서 목록에서 구분이 안 된다.

### 결정 3. 인증 수단이 곧 메이플 ID 의 출처다

`character/list` 응답의 `account_list` 가 메이플 ID 목록이고, 그 응답을 준 인증 수단이 그 ID 들의
주인이다. 앱은 **로그인 1개 + 키 N개에서 받은 목록을 합쳐 하나의 메이플 ID 목록**으로 만든다.
그중 하나를 고르는 것이 [[ADR-297]] 이다.

- 같은 메이플 ID 가 로그인과 키 양쪽에서 오면 **로그인을 주인으로 삼는다**. 토큰이 만료돼도 키가
  남아 있으면 그 ID 는 계속 조회된다.
- 어느 메이플 ID 를 어느 수단으로 부를지는 이 표가 정한다. 캐릭터마다 다시 판정하지 않는다.

### 결정 4. 토큰은 서버가 들고 앱은 세션만 받는다

`client_secret` · 액세스 토큰 · 갱신 토큰은 전부 `maple-routine-server` 에 있다. 앱이 받는 것은
서버가 발급한 세션 식별자 하나다.

- 프렌즈 API 넷은 **로그인으로 들어온 메이플 ID 에 한해** 서버를 거친다. 키로 들어온 메이플 ID 는
  지금처럼 앱이 넥슨을 직접 부른다. 한 앱 안에 전송 경로가 둘이다.
- 갈리는 자리는 `nexon/http.ts` 하나다. 호출부는 키 문자열 대신 **자격 객체**를 넘기고, 그 안에서
  `x-nxopen-api-key` 헤더로 직접 나가는 길과 서버로 나가는 길이 갈린다. 각 client 파일
  (`nexon/character` · `nexon/schedule` · `nexon/meso-rate`)은 안 바뀐다.
- 액세스 토큰 30분 · 갱신 토큰 14일이다. 갱신은 서버가 알아서 하고, 갱신 토큰까지 만료되면 앱에
  재로그인이 필요하다고 알린다. **2주 넘게 앱을 안 켠 사용자는 다시 로그인한다.**

### 결정 5. 넥슨은 커스텀 스킴으로 앱에 code 를 주고, 앱이 그 code 를 서버에 넘긴다 (사용자 지정)

넥슨에 등록하는 redirect URI 는 두 플랫폼 모두 `com.mapleroutine.app://oauth/callback` 이다. 등록
화면이 iOS 와 안드로이드를 받기 때문이다(맥락). code 를 토큰으로 바꾸는 일은 여전히 서버가 한다.
교환에 `client_secret` 이 필요하기 때문이다(결정 4).

```
앱      서버에 로그인 시작을 요청한다. 서버가 state 와 검증값을 만들어 짝지어 두고 앱에 준다 (결정 9)
앱      인증 세션으로 openid.nexon.com/oauth2/authorize 를 연다 (state)
넥슨    로그인 · 동의
넥슨    com.mapleroutine.app://oauth/callback?code=&state=   인증 세션이 앱에 돌려준다
앱      state 가 받은 값과 같은지 확인하고 code · state · 검증값을 서버에 넘긴다
서버    검증값이 맞을 때만 code 를 토큰으로 교환해 보관하고, 세션을 응답으로 준다
```

- **정정(2026-09-19)**: 처음에는 서버의 https 주소를 redirect URI 로 등록하고, 서버가
  `com.mapleroutine.app://oauth/done?session=` 으로 앱에 돌려주기로 했다. 등록 화면이 iOS 를 받는
  것을 확인해 바꿨다. 이제 서버에는 넥슨이 부르는 콜백 주소가 없다.
- `state` 는 서버가 요청마다 새로 만들고 한 번 쓴 값은 다시 못 쓰게 한다. 앱은 콜백의 `state` 가
  서버에서 받은 값과 같은지 확인한다. 계정 연동은 넥슨 보안 가이드라인이 `state` 를 필수로 지목한
  작업이다.
- 로그인 창은 `expo-web-browser` 의 `openAuthSessionAsync` 로 연다(사용자 지정). iOS 에서는
  ASWebAuthenticationSession 이라 콜백 URL 이 그 세션에만 돌아온다. Safari 로 열면
  (`Linking.openURL`) 같은 스킴을 등록한 다른 앱이 콜백을 받을 수 있고, 돌아올 때 확인 창도 뜬다.
- 앱 안 웹뷰로 열지 않는다. 사용자가 주소창을 볼 수 없어 자격 증명을 어디에 넣는지 확인할 방법이
  없다.
- iOS 는 `ios/app/Info.plist` 에 `com.mapleroutine.app` 스킴이 이미 있다. **안드로이드에는 없다.**
  `AndroidManifest.xml` 에 `intent-filter` 를 추가해야 한다.

### 결정 6. 키를 쓰던 사용자가 로그인하면, 캐릭터 목록이 같을 때만 키를 지운다 (사용자 지정)

API 키로 쓰던 사용자가 넥슨 로그인을 붙이면 두 목록을 대조한다.

- **같으면** 기기에서 그 키를 지우고 로그인만 쓴다. 같은 계정을 두 수단으로 들고 있을 이유가 없고,
  키는 평문으로 저장돼 있어 지우는 쪽이 안전하다.
- **다르면** 둘 다 남긴다. 다르다는 것은 그 키가 다른 넥슨 계정이라는 뜻이고, 지우면 그 계정의
  캐릭터를 잃는다.
- 대조는 `character/list` 응답의 ocid 집합으로 한다. 추가 호출이 없다.

### 결정 7. 검수 전까지 로그인은 제작자와 테스트 사용자 5명만 된다

애플리케이션은 테스트 단계로 등록되고, 그 단계에서는 등록된 테스트 사용자만 Open ID 로그인이
된다. 모든 사용자에게 열려면 검수를 통과해 프로덕션 단계가 돼야 한다.

- 그래서 **로그인 진입점은 검수 통과 전까지 화면에 세우지 않는다.** 세우면 대부분의 사용자가 누르고
  실패한다.
- 검수는 서비스 이름 · 서비스 URL · 로고 · 로그인 버튼이 사용 가이드대로 쓰인 캡처를 요구한다.
  로그인 버튼 디자인은 `openapi.nexon.com/ko/open-id/design-guide/` 를 따른다.

### 결정 8. 약관 부담은 문서에 적고 수익화 시점에 다시 본다 (사용자 판단)

약관 제6조⑥(영리 목적 제한)은 그대로다. 사용자 판단은 광고는 문제없어 보이고 구독은 제한적일 수
있다는 것이다(2026-09-19). 이 문서는 그 판단을 기록만 하고, #58 을 착수할 때 다시 본다.

- 출처 표기 의무(제6조④)는 설정 화면 하단의 `Data based on NEXON Open API` 가 이미 지킨다.
- API 키 비공유(제5조①)는 여전히 지켜진다. 이 설계는 앱에 공용 키를 내장하지 않고, 서버는 자기
  키로만 부른다. [[ADR-299]] 결정 5 부터는 서버가 그 키로 로그인 사용자의 공개 조회도 대신 부른다.
  키가 서버 밖으로 나가지 않으므로 비공유는 그대로다.

### 결정 9. 서버가 준 검증값이 있어야 code 를 교환한다 (사용자 지정)

안드로이드에서는 다른 앱이 콜백을 가로챌 수 있다. `openAuthSessionAsync` 가 안드로이드에서는 커스텀
탭을 열고, 돌아오는 URL 을 인텐트로 받기 때문이다. 같은 스킴을 선언한 앱이 기기에 있으면 code 와
state 가 그쪽으로 갈 수 있다. 넥슨은 서명 해시를 받지 않아 이것을 막지 않는다(맥락). 그 앱이 code 와
state 를 우리 서버에 넘기면 사용자의 세션을 얻고, 캐릭터 목록 · 확률 기록 · 스케줄러를 읽는다.

그래서 서버는 code 만으로는 교환하지 않는다.

- 로그인 시작 때 서버가 `state` 와 검증값을 만들어 짝지어 두고 앱에 준다. 검증값은 앱과 서버 사이
  https 로만 오가고 콜백 URL 에 실리지 않는다. 가로챈 앱은 code 와 state 만 갖는다.
- code 를 받으면 서버는 `state` 에 짝지은 검증값과 앱이 보낸 값이 같은지 본다. 다르거나 없으면 넥슨에
  교환을 요청하지 않는다.
- 짝은 한 번 쓰면 지운다. 쓰이지 않아도 짧은 시간 뒤 만료된다. 수명은 서버에서 정한다.
- 앱이 아니라 서버가 만드는 이유는 Hermes 에 `crypto` 가 없어서다. 앱이 안전한 난수를 만들려면
  `expo-crypto` 를 더 넣어야 한다. 서버가 만들면 앱에 새 모듈이 들지 않는다. 검증값이 콜백 URL 에
  실리지 않으니 해시로 감출 필요도 없다.
- iOS 도 같은 흐름을 탄다. iOS 는 인증 세션이 이미 가로채기를 막지만, 플랫폼마다 서버 경로를 둘로
  가르면 서버와 앱 모두 분기가 는다.

## 열린 질문

로그인만 한 사용자가 today 의 캐릭터 기본 정보와 메소 획득량을 못 보는 문제는 **[[ADR-299]] 결정 5
가 답했다**(2026-09-19, 사용자 지정). 공개 조회라 서버가 개발자 키로 대신 부른다. 남은 것은 아래다.

- 안드로이드 `intent-filter` 와 `expo-web-browser` 는 둘 다 지문을 바꾼다. 스토어 빌드와 함께
  나가야 한다.
- 서버의 토큰 저장 방식(암호화 여부 · 테이블 모양)은 서버 저장소에서 따로 정한다.
