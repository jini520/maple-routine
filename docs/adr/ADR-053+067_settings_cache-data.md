# ADR-053+067 캐시 데이터 삭제

> 🟢 유효
> 옛 번호: ADR-052 · ADR-058 · ADR-117 결정 8
> 관련 소스: `storage/cache-data.ts` · `storage/sqlite/db.ts` · `storage/pending-notice.ts` · `features/settings/cache-data.ts` · `app/settings/CacheClearConfirm.tsx` · `app/settings/SettingsAccountDataScreen.tsx`

## 배경

`설정 > 계정 및 데이터 > 캐시 데이터 삭제` 는 저장 공간을 비우는 기능이다. 용량 대부분은 다시 받으면 되는 동기화
캐시인데, 처음에는 한 버튼이 모든 것을 지워서 되살릴 수 없는 수익 기록까지 함께 사라졌다. 또 Preferences 는
"남길 키를 빼고 전부" 지우고 SQLite 는 손으로 적은 표 목록만 지워서, 표가 늘었을 때 목록에서 빠지는 사고가 났다.
드롭 기록 표가 목록에 없어 지워지지 않았고 용량에도 잡히지 않았다.

이 문서는 무엇을 지우고 무엇을 남기는지, 그리고 지운 뒤 앱을 어떻게 다시 띄우는지를 정한다.

## 결정

### 결정 1. 지우는 단위는 `일반 데이터` 와 `수익·지출 기록` 두 그룹이다 (사용자 확정)

이 기능에서 부딪히는 요구는 "용량은 비우고 싶지만 되살릴 수 없는 기록은 남기고 싶다" 하나뿐이다. 이 요구를 풀 수 있는
가장 작은 나눔이 두 그룹이다. 더 잘게 나누면 사용자가 매번 판단할 항목만 늘어난다.

| 그룹 | Preferences | SQLite |
|---|---|---|
| `records`(수익·지출 기록) | 없음 | `RECORD_TABLE_NAMES` 에 적은 표, 보스 기록 표 셋의 처치 · 드롭 행 |
| `general`(일반 데이터) | `KEEP_KEYS` 를 뺀 전부 | 전체 표에서 `RECORD_TABLE_NAMES` 와 보스 기록 표 셋을 뺀 나머지(`GENERAL_TABLE_NAMES`), 보스 기록 표 셋의 설정 행 |

- 목록으로 적는 그룹은 `records` 하나뿐이고 `general` 은 나머지로 계산한다. 두 그룹을 모두 목록으로 적으면 어느 그룹에도
  속하지 않는 키나 표가 생겨 영영 지워지지 않는다. 계산으로 두면 새 Preferences 키와 새 표는 저절로 `general` 에 들어가
  계속 지울 수 있다.
- 전체 표 목록은 `storage/sqlite/db.ts` 의 표 정의 배열 하나에서 나온다(`BOSS_PROFIT_TABLE_NAMES`). 스키마를 만들 때도,
  지울 때도, 용량을 셀 때도 같은 배열을 순회한다. 그래서 새 표는 정의 배열에 더하기만 하면 세 곳에 함께 반영된다.
  `sqlite_master` 를 조회하는 방법은 쓰지 않았다. 내부 표를 걸러야 하고, 남겨야 할 표가 생기면 조용히 지워진다.

`records` 에 넣는 표와 그 이유는 이렇다.

| 표 | 이유 |
|---|---|
| 처치(`boss_party_periods` 의 `cleared` 행) · 드롭(`boss_drops`) | 넥슨 API 는 최근 2주치만 준다. 수익만 지우고 드롭이 남으면, 같은 캐릭터가 같은 보스를 같은 기간에 다시 잡을 때 지웠다고 생각한 옛 드롭이 새 기록에 붙는다. 그래서 둘을 나누지 않는다 |
| `enhancement_totals` · `enhancement_history_checks` · 옛 `enhancement_history` | 어제 이전 날짜는 다시 조회하지 않아 지우면 되살릴 수 없다. 원장도 같은 그룹이어야 표식만 남고 합계가 사라지는 일이 없다 |
| `cashbook_entries` · `cashbook_entry_items` · `cashbook_entry_hunt_inputs` · 옛 `income_records` · `spend_records` | 손으로 적은 기록이라 API 로 되살릴 수 없다 |
| `character_profiles` | 이 이름이 없으면 기록을 화면에 그릴 수 없다. 지우면 과거 수익이 화면에서 통째로 사라진다 |
| `character_world_leaps` | 월드 이전 기간의 중복 기록을 지우는 연결이다. 기록만 남으면 두 번 센 채로 남는다 |
| `mvp_grade_history` · `character_accounts` | 사용자가 적은 등급 이력과 옛 이름의 소속이라 다시 받을 수 없다([[ADR-050]]) |

보스 관리의 파티 설정(`boss_parties` 의 분배 칸)과 그 기간만 고친 값(`boss_party_periods` 의 `open` 행 분배 칸)은
`general` 이다. 기록이 아니라 설정이고, 파티 인원은 저장할 때 기록에 복사되므로 설정을 지워도 지난 금액은 바뀌지 않는다.

보스 기록 표 셋(`BOSS_TABLE_NAMES`)은 표를 통째로 지우지 않고 행 단위로 지운다([[ADR-078]] 결정 10). 한 표에 두 그룹의
행이 섞여 있기 때문이다. 조합 행은 처치와 드롭의 부모라, 표를 통째로 지우면 외래키를 따라 `records` 까지 사라진다.

- `general` 만 지우면 조합 행의 분배 칸을 비우고, 드롭이 없는 `open` 기간 행은 지운다. 드롭이 남은 `open` 기간 행은
  분배 칸만 비운다.
- `records` 만 지우면 드롭을 모두 지우고, `cleared` 기간 행과 분배 칸이 빈 기간 행을 지운다.
- 어느 쪽이든 마지막에 분배 칸도 기간 행도 없는 조합 행을 지운다. 남기면 기록을 지웠는데 조합만 남는다.

옛 표 넷은 v1.0.14 까지 DB 에 남아 있어 표 목록에도 남는다. `boss_profit_records` · `boss_drop_records` 는
`RECORD_TABLE_NAMES` 에, 나머지 둘은 `general` 에 든다. 지금 코드는 이 표를 읽거나 쓰지 않는다.

이 나눔에는 대가가 있다. 드롭 기록만 지우거나, 추적 목록은 남기고 캐시만 비우는 일은 할 수 없다. `general` 을 지우면
추적 캐릭터와 수동 선택 항목을 다시 골라야 한다.

### 결정 2. 사용자가 고른 설정과 지우면 안 되는 표시는 어느 그룹을 골라도 남긴다

`KEEP_KEYS` 의 키는 어떤 선택에서도 지우지 않는다. 그래서 이 기능으로 온보딩에 돌아가지 않는다.

| 키 | 남기는 이유 |
|---|---|
| `authMethods` · `apiKey` | 저장된 인증 수단이다. 지우면 다시 띄운 앱이 로그인 화면으로 돌아간다. `apiKey` 는 옛 설치본의 키 칸이다 |
| `theme` · `trackingMode` · `dropEffect` | 사용자가 고른 취향이다. 저장 공간을 비우려다 수동 모드가 자동으로 바뀌는 것은 이 기능의 목적을 벗어난다 |
| `noticeSubscribed` · `noticeSubscriptions` | 지우면 FCM 구독은 남았는데 앱은 꺼진 것으로 알고, 꺼진 스위치로 알림이 온다 |
| `notificationPermissionAsked` | 지우면 iOS 에서 다시 묻는데, 이미 답한 사용자에게는 시스템 팝업이 뜨지 않는다 |
| `partyAlarmEnabled` · `partyAppointments` | 끈 알림이 다시 오거나, 사용자가 적은 스케줄이 사라진다([[ADR-051]]) |
| `notificationLedger` | 지우면 OS 에 남은 예약을 취소할 수 없다([[ADR-056]]) |
| `dismissedNotices` | 닫은 공지가 첫 화면에 다시 나온다 |
| `mvpWeeklyCheckOff` · `mvpBulkApplyAsked` | 끈 주간 확인이 다시 뜨거나, 일괄 적용을 다시 묻는다([[ADR-050]]) |
| `pendingTasks` | 지우면 반쯤 고친 기록이 이어지지 않고 그대로 남는다([[ADR-023]]) |
| `statsCumulativeStart` | 사용자가 고른 날짜라 다시 만들 방법이 없다 |

남길 키를 늘릴 때는 이 목록에 더하고 이유를 한 줄 적는다. 목록에 없는 키는 모두 `general` 을 지울 때 사라진다.

### 결정 3. 확인 창에서 그룹을 골라 지운다 (사용자 확정)

`CacheClearConfirm` 은 `NoticeModal` 형태의 확인 창이다.

- 제목은 `캐시 데이터를 삭제할까요?`, 설명은 `지운 데이터는 되돌릴 수 없습니다. 지울 것을 골라주세요.` 다. 되돌릴 수
  없다는 사실을 각주가 아니라 설명 첫머리에 적는다. 일반 데이터도 수동 선택 항목과 파티 보스 설정은 사용자가 다시 해야
  하므로 그룹을 가리지 않는다.
- 본문은 체크박스 두 줄(`role="checkbox"`, 줄 전체를 누를 수 있다)이다. 줄마다 그룹 이름 · 대표 항목 · 그룹 용량이 있다.

  | 그룹 | 대표 항목 | 경고 |
  |---|---|---|
  | `일반 데이터` | `캐릭터 정보 · 수동 선택 항목 · 파티 보스 설정 등` | 없음 |
  | `수익·지출 기록` | `보스 처치·드롭 · 손으로 적은 수입·지출` | `손으로 적은 수입·지출은 되살릴 방법이 없고, 보스 기록은 NEXON Open API가 최근 2주치만 제공합니다.` |

  대표 항목은 그 그룹이 대략 무엇인지만 알려 준다. 빠짐없이 지워지는지는 결정 1 의 나눔으로 보장한다. 다만 적은 항목은
  모두 실제로 지우는 것이어야 한다. 무엇을 지우는지는 `storage/cache-data.ts` 만 정하고, 화면은 두 불리언만 넘긴다.
- 남는 항목을 나열하는 줄은 두지 않는다. 지우는 데이터는 모두 두 그룹 중 하나에 속하므로 체크를 풀면 그 그룹은 반드시
  남는다. 남는 것을 따로 적으면 무엇을 지울지 고르는 데서 시선을 빼앗는다.
- 처음에는 두 그룹이 모두 선택되어 있다. 열고 바로 지우면 예전의 전체 삭제와 같다. 창을 닫았다 다시 열어도 이 상태로
  돌아간다. 지난번 선택이 남으면 사람마다 다른 범위를 지우게 된다.
- 아무 그룹도 고르지 않으면 삭제 버튼이 꺼진다. 삭제 버튼은 고른 그룹의 용량 합계를 적는다(`삭제 (1.5KB)`).
- 주 버튼은 `취소` 다. 되돌릴 수 없는 동작이라 안전한 쪽을 크게 둔다. 삭제는 그 아래 빨간 글자다.
- 지우는 동안에는 두 버튼과 체크박스가 꺼진다. 삭제 버튼은 라벨을 유지한 채 대기 상태가 된다.

### 결정 4. 용량은 그룹마다 따로 센다

`getCacheDataSizes` 가 그룹별 바이트를 계산한다. 각 값은 그 그룹이 실제로 지우는 것만 더한다. 그래서 사용자는 무엇을 포기하면
얼마가 비는지 보고 고를 수 있다. 남길 키는 어느 그룹에도 더하지 않는다. 설정 화면과 계정 및 데이터 화면에 보이는 총
용량은 두 값의 합이다([[ADR-052]]).

### 결정 5. 지운 뒤에는 선택과 관계없이 늘 앱을 다시 띄운다

어느 그룹을 지워도 화면 스토어가 메모리에 가지고 있는 값이 틀려진다. 다시 띄우지 않으려면 스토어마다 다시 읽는 방법을
따로 만들어야 하고, 그것은 관리해야 할 흐름이 하나 더 생기는 일이다. 아끼는 것은 다시 띄우기 한 번뿐이다.

`features/settings/cache-data.ts` 의 `clearCacheDataAndReload` 가 이 순서로 처리한다.

1. 삭제와 10초 타이머 중 먼저 끝나는 쪽을 기다린다. 삭제가 멈춰도 확인 창이 `삭제 중` 에 갇히지 않게 하려는 것이다.
2. 실패했거나 시간이 지났으면 Preferences 의 `pendingNotice` 에 표시를 남긴다. 다시 띄우면 지금 화면이 사라지므로
   바로 토스트를 띄울 수 없다. 다시 띄운 뒤 `AppShell` 이 `showPendingCacheClearNotice` 로 이 표시를 읽고
   `캐시를 일부만 삭제했습니다` 오류 토스트를 띄운다.
3. SQLite 연결을 닫는다(`closeBossProfitDb`). 연결이 남은 채 다시 띄우면 네이티브에 옛 연결이 남아 과거 기간 조회가 실패한다.
   닫기는 예외를 던지지 않고 5초 안에 끝난다.
4. 스플래시로 덮는다. 다시 띄우는 동안 네이티브 배경색이 깜빡 보이기 때문이다. 덮기에 실패해도 계속한다.
5. 다시 띄운다(`reloadAppAsync`).

덮기는 반드시 닫기 뒤에 한다. 먼저 덮으면 닫기가 늦어지는 동안 사용자가 터치도 되지 않는 스플래시 화면에 갇힌다.
OTA 적용과 같은 순서다.

`pendingNotice` 는 Preferences 에 둔다. React Native 에는 `sessionStorage` 가 없고, 표시를 남긴 직후 앱을 다시 띄우므로
다음 부팅이 바로 읽는다. 읽으면 곧바로 지워서 한 번만 뜬다. 표시는 삭제가 끝난 뒤에 쓰므로 이번 삭제가 지우지 않는다.
