# ADR-015+156 안내 사이트와 홍보 첫 화면

> 🟢 유효
> 옛 번호: ADR-110 · ADR-229
> 관련 소스: `site/` · `site/index.html` · `site/home.css` · `site/home.js` · `site/images/home/` · `site/robots.txt` · `site/sitemap.xml` · `PRIVACY.md` · `scripts/build-site.mjs` · `scripts/deploy-site.sh` · `app/auth/api-key-links.ts`

## 배경

`mapleroutine.store` 는 스토어와 AdMob 이 요구하는 문서를 올려 두는 정적 사이트다. 개인정보 처리방침
(`/privacy`)은 Play 와 App Store 모두에, 지원 URL(`/support`)은 App Store 에 등록되어 있다. `/app-ads.txt`
는 AdMob 이 이 도메인에서 읽어 간다. 이 셋이 열리지 않으면 스토어 등록정보나 광고 승인에 문제가 생긴다.

여기에 스토어가 요구하지 않는 페이지가 하나 더 있다. 넥슨 Open API 키 발급 가이드(`/api-key`)다. 이 앱을
쓰려면 사용자가 넥슨 Open API 사이트에서 키를 직접 받아 와야 하는데, 그 절차가 앱 밖에서 일곱 단계로
진행된다. 앱이 넥슨 사이트 링크만 주고 끝내면 사용자가 첫 화면에서 가장 많이 막힌다.

## 결정

### 결정 1. API 키 발급 가이드는 앱이 아니라 안내 사이트에 둔다

가이드는 `site/api-key.md` 이고 `mapleroutine.store/api-key` 로 열린다. 앱 안에 가이드 화면을 만들지 않은
이유는 셋이다.

- 스크린샷 일곱 장(약 1.2MB)을 앱 번들에 넣으면 모든 사용자가 받게 되는데, 실제로 보는 것은 처음 한 번뿐이다.
- 넥슨이 화면을 바꾸면 가이드도 고쳐야 한다. 사이트는 다시 올리면 바로 바뀌지만, 앱은 OTA 를 한 번 더 내야 한다.
- 사용자는 키를 받는 동안 어차피 브라우저에 있다.

### 결정 2. 앱의 키 입력 화면에는 가이드와 넥슨 사이트 링크를 둘 다 둔다

`API 키 발급 방법 보기` 는 가이드로, 입력 칸에 붙은 링크는 `openapi.nexon.com` 으로 연다. 처음 쓰는 사용자는
가이드를 따라가면 되고, 이미 키가 있는 사용자는 일곱 단계 안내를 거치지 않아도 된다. 개발 단계 키 안내
모달도 가이드를 연다.

두 주소는 `app/auth/api-key-links.ts` 에만 적고 폼과 모달이 함께 쓴다. 따로 적어 두면 사이트를 옮길 때 한쪽만
고쳐지고, 고쳐지지 않은 쪽은 키 때문에 막힌 사용자에게만 보이는 링크라 알아채기 어렵다.

설정 화면에는 가이드 링크를 두지 않는다. 설정에는 API 키를 다시 입력하는 화면이 없어서, 링크만 두면 따라가도
할 수 있는 일이 없다.

### 결정 3. 가이드는 서비스 단계 키를 받도록 안내한다

개발 단계 키는 초당 5건 · 하루 1,000건으로 제한된다. 이 앱은 여러 캐릭터를 한 번에 조회하므로 개발 단계
키로는 중간에 막힌다. 가이드의 단계 선택 항목에서 서비스 단계를 고르라고 적었다.

### 결정 4. 가이드 스크린샷은 저장소에 커밋한다

큰 원본 파일을 저장소에서 빼는 기준([[ADR-044]])은 크기가 아니라 다시 만들 수 있느냐였다. 이 일곱 장은
개인 넥슨 계정으로 들어가야 나오는 화면에 손으로 주석을 얹은 것이라 다시 만들 수 없다. 원본을 잃으면
가이드를 쓸 수 없게 되므로 `site/images/api-key/` 에 커밋한다.

### 결정 5. 사이트의 원본은 이 저장소에 둔다

`site/` 와 루트의 `PRIVACY.md` 가 원본이고, `scripts/build-site.mjs` 가 `dist-site/` 로 빌드한다. 서버 저장소로
옮기지 않는다. 정적 사이트는 서버 코드가 아니라 이 앱이 내놓는 문서이고, 서버는 그것을 내보내기만 한다.

개인정보 처리방침의 원본은 `PRIVACY.md` 하나다. 웹용 사본을 따로 두면 법적 문서가 두 개가 되어 내용이
어긋날 수 있으므로, 빌드할 때 이 파일을 렌더링한다. 페이지 제목과 설명은 프런트매터가 아니라 맨 위 HTML
주석에서 읽는다. `PRIVACY.md` 는 GitHub 에서도 그대로 읽히는 문서라, 렌더링되지 않는 `---` 블록이 맨 위에
보이면 안 되기 때문이다.

빌드 스크립트는 `site/` 에서 `.md` 와 `template.html` 만 빼고 나머지를 재귀로 복사한다. 그래서 `style.css`
· `app-ads.txt` · `images/` 같은 정적 파일은 스크립트를 고치지 않아도 함께 나간다.

### 결정 6. 정적 파일은 Oracle 의 nginx 가 디스크에서 바로 내보낸다

`/privacy` · `/support` · `/app-ads.txt` 는 앱 기능이 아니라 스토어 등록과 광고 승인에 필요한 주소다. 서버
앱이 멈추더라도 이 주소들은 열려야 하므로, 서버 앱을 거치지 않고 nginx 가 `/var/www/mapleroutine/` 의 파일을
바로 내보낸다.

### 결정 7. 배포는 사람이 손으로 한다

`npm run deploy:site`(`scripts/deploy-site.sh`)가 빌드하고, `rsync --delete` 로 Oracle 에 올린 뒤 다섯 경로의
응답 코드를 출력한다. `--delete` 를 쓰므로 지운 페이지가 서버에 남아 계속 열리는 일이 없다.

GitHub Actions 로 자동화하지 않는다. 자동화하려면 GitHub 에 Oracle 접속 키를 맡겨야 하는데, 그 키로는 정적
사이트뿐 아니라 서버 전체에 접속할 수 있다. 이 사이트는 처리방침을 고칠 때 정도만 바뀌어 1년에 몇 번이므로, 그
정도 빈도로는 키를 GitHub 에 계속 맡겨 둘 이유가 없다. 자주 바뀌게 되면 그때 CI 로 옮긴다.

빌드는 `CNAME` 과 `.nojekyll` 을 만들지 않는다. 둘 다 GitHub Pages 를 위한 파일이었고, 남겨 두면
`mapleroutine.store/CNAME` 처럼 아무 의미 없는 파일이 공개된다.

### 결정 8. 첫 화면(`/`)은 앱 홍보 페이지이고, 마크다운이 아니라 HTML 로 쓴다

`/` 는 앱의 기능을 스크린샷과 함께 소개하는 홍보 페이지다. 원본은 `site/index.html` 이고, 이 페이지만 쓰는
스타일과 스크립트는 `site/home.css` · `site/home.js`, 그림은 `site/images/home/` 에 둔다. 다른 페이지는 그대로
`template.html` 과 마크다운으로 만든다.

홍보 페이지는 앱 화면을 엇갈려 겹치거나 가로로 넘기는 배치라 마크다운으로 쓸 수 없다. 문서 페이지의 틀
(`template.html` · `style.css`)에 맞추면 문서 페이지까지 함께 바뀌므로 파일을 나눈다. 빌드 스크립트는 `.md` 와
`template.html` 이 아닌 파일을 그대로 복사하므로(결정 5) `index.html` 도 그대로 나간다. 그래서 `PAGES` 에서
`index.md` 줄을 빼고 `site/index.md` 를 지운다.

그림은 `/images/home/` 아래에 둔다. `/assets/` 는 nginx 가 앱의 게임 데이터 폴더로 넘기는 경로라 이 사이트의
파일이 보이지 않는다. `/images/` 는 nginx 가 7일 캐시를 거는 경로라 그림에 맞다.

스크린샷은 홍보용 데모 데이터(`feat-debug-demo-seed` 브랜치)를 넣은 시뮬레이터에서 찍는다. 데모 데이터가 같은
날짜에는 같은 화면을 내므로 다시 찍을 수 있다.

첫 화면과 자동 기록 쪽 구역(결정석 수입 · 강화 · 파티 스케줄)은 화면 3장에 카드를 띄운 콜라주 그림 한 장으로
보여 준다. 화면만 늘어놓으면 숫자가 작아 무엇을 기록하는 앱인지 안 읽히는데, 카드를 키워 띄우면 이번 주 총 수입이나
강화 비용 같은 핵심 숫자가 첫눈에 읽힌다. 콜라주는 Figma 에서 컴포넌트(`화면` · `띄운 카드`)의 인스턴스로 만들어
같은 스크린샷으로 다시 짤 수 있게 한다. 나머지 구역은 폰 줄을 두고, 화면 모양은 콜라주와 같게 폰 틀 없이 모서리와
그림자만 둔다. 만드는 절차는 `docs/features/site.md` 의 `그림 바꾸기` 에 있다.

### 결정 9. 스토어 배지는 공식 그림을 쓰고, 기기에 맞는 배지 하나만 보여 준다

App Store 와 Google Play 배지는 두 회사가 내놓은 한국어 공식 그림을 그대로 쓴다. 색 · 비율 · 글자를 바꾸면
두 스토어의 배지 정책을 어긴다.

| 파일 | 출처 |
|---|---|
| `app-store-ko-black.svg` · `app-store-ko-white.svg` | Apple 배지 도구 `tools.applemediaservices.com` |
| `google-play-ko.svg` | Google Play Partner Marketing Hub 의 한국어 `Get it on Google Play` 배지 |

Apple 은 흰색 배지를 화면에 배지가 하나뿐일 때만 허용하고, 다른 스토어 배지와 함께 놓을 때는 검정 배지를
App Store 부터 놓으라고 정한다. Google Play 배지는 검정 바탕뿐이다. 둘을 늘 함께 두면 둘 다 검정이 되므로,
`index.html` 머리의 스크립트가 기기를 보고 `<html>` 에 `platform-ios` · `platform-android` · `platform-other`
를 단다.

| 기기 | 보이는 배지 |
|---|---|
| 아이폰 · 아이패드 | 흰색 App Store 배지 하나 |
| 안드로이드 | Google Play 배지 하나 |
| 그 밖(데스크톱 등) | 검정 App Store 배지, 그 오른쪽에 Google Play 배지 |

두 배지는 같은 높이다(데스크톱 56px · 모바일 52px). Apple 은 화면에서 40px 이상, Google 은 App Store
배지보다 작지 않게 정하기 때문이다. 최소보다 크게 두는 이유는 Google 한국어 배지의 한글 획이 배지 높이의 1%
안팎으로 가늘어서다. 48px 에서는 흰 글씨가 회색으로 번져 흐리게 보였다. 배지 둘레에는 배지 높이의 1/4 이상을 비운다. 바닥글에 Apple · Google 의
상표 문구를 둔다.

### 결정 10. 검색엔진이 읽을 정보를 사이트에 둔다

검색과 공유 미리보기에 앱이 바르게 나오도록 아래를 둔다.

| 무엇 | 어디 | 왜 |
|---|---|---|
| 대표 주소(`canonical`) | 모든 페이지 머리 | `/privacy` 와 `/privacy/` 처럼 같은 페이지가 두 주소로 잡히지 않게 한다 |
| 공유 미리보기(Open Graph · 트위터 카드) | 모든 페이지 머리. 그림은 `images/home/og.png`(1200×630) | 카카오톡 · 디스코드 · X 에 링크를 붙였을 때 앱 이름과 그림이 나온다 |
| 구조화 데이터(JSON-LD `MobileApplication` · `WebSite`) | `index.html` | 검색엔진이 이 페이지를 앱 소개로 알아보게 한다 |
| `apple-itunes-app` 메타 | `index.html` | 아이폰 Safari 가 위쪽에 App Store 배너를 띄운다 |
| `robots.txt` | `site/robots.txt` | 사이트맵 위치를 알리고, `/admin` · `/v1` · `/app` · `/ota` 처럼 사람이 읽을 페이지가 아닌 경로를 수집에서 뺀다 |
| `sitemap.xml` | `site/sitemap.xml` | `/` · `/privacy/` · `/support/` · `/api-key/` 를 알린다 |

구조화 데이터의 분류(`UtilitiesApplication`)와 가격(무료)은 App Store 등록 정보에서 확인한 값이다. 평점은 넣지
않는다. 스토어에서 계속 바뀌는 값이라 페이지에 적어 두면 곧 틀린 정보가 된다. 앱 이름은 스토어 이름인 `메이플루틴`
과 페이지에 쓰는 `메이플 루틴` 을 둘 다 적어 어느 쪽으로 검색해도 잡히게 한다.

검색엔진 등록(Google Search Console · 네이버 서치어드바이저 · Bing 웹마스터 도구)은 운영자 계정으로 사람이
한다. 소유 확인에는 HTML 메타 태그를 쓰고, 받은 값은 `index.html` 머리에 넣어 다시 배포한다.

## 테스트

이 결정들을 확인하는 자동 테스트는 없다. 배포 스크립트가 끝에 일곱 경로(`/` · `/privacy` · `/support` ·
`/api-key` · `/app-ads.txt` · `/robots.txt` · `/sitemap.xml`)의 응답 코드를 출력하므로, 배포할 때마다 그 출력을
눈으로 확인한다.
