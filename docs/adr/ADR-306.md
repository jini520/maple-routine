# ADR-306: MVP 등급을 메이플 ID 마다 받아 경매장 수수료와 스타포스 비용에 반영한다

> 🟡 부분 폐기 · 결정 6 의 수동 설명 줄은 [[ADR-310]] 결정 1 이 걷었다 · 2026-09-22 · 구현 완료(브랜치 `feat/mvp-grade`, 실기기 미검증) · 이슈 #514 · 시안 https://claude.ai/artifact/EmnT9Fk5j5nvEa2iooGGik

> 사용자 지정(2026-09-22): MVP 등급마다 인게임 혜택이 있다. 이 앱에서 영향받는 것은 MVP 실버 이상의
> 경매장 수수료 3% 와 등급별 스타포스 할인이다. 최초 사용자는 온보딩에서, 기존 사용자는 업데이트 뒤
> 한 번 등급을 고른다. 등급은 주마다 바뀔 수 있어 주마다 확인하되, 직접 바꾸겠다는 사용자는 묻지 않는다.

## 맥락

앱이 수수료와 스타포스 비용을 셀 때 **MVP 등급을 모른다**. 그래서 두 가지가 틀린다.

- 수수료를 사용자가 자리마다 손으로 고른다. 아이템 판매 폼은 기본이 `없음` 이고, 드롭 판매가 · 조각 정산 ·
  사냥 폼의 조각 판매에는 수수료 칸 자체가 없다.
- **스타포스 지출이 등급 할인만큼 과대계상돼 있다.** 비용 식(`lib/enhancement/cost.ts` 의 `starforceCost`)이 깎는 것은
  응답의 `starforce_event_list` 가 주는 이벤트 할인뿐이다. 그 목록에 MVP 할인은 **안 섞여 온다**(사용자 확인).
  다이아 이상이면 줄마다 약 11% 높게 서 있다.

스타포스 비용은 저장하지 않고 **읽을 때 계산한다**(`features/enhancement-history/spending.ts`).
`enhancement_history.cost_meso` 칸은 스키마에만 있고 아무도 안 쓴다. 그래서 등급을 **지금 값 하나**로만 두면,
등급이 바뀐 날 지난 달의 스타포스 지출이 통째로 움직인다. 기록으로서 거짓이다.

## 결정

### 결정 1. 등급은 메이플 ID 마다 **일곱을 하나씩** 받고, 등급 그대로 저장한다 (사용자 지정)

MVP 는 메이플 ID 의 속성이다. 열쇠는 `character/list` 응답의 `account_id` 이고(`MapleAccount.accountId`),
기록은 캐릭터를 들고 있으므로 캐릭터가 속한 ID 의 등급을 쓴다.

| 등급 | 경매장 수수료 | 스타포스 할인 |
|---|---|---|
| 일반 | 5% | 없음 |
| 브론즈 | 5% | 없음 |
| 실버 | 3% | 3% |
| 골드 | 3% | 5% |
| 다이아 | 3% | 10% |
| 레드 | 3% | 10% |
| 블랙 | 3% | 10% |

값은 전부 사용자 확인(2026-09-22)이고 `src/data/mvp-grades.json` 이 든다([[ADR-006]]).

**혜택이 같은 등급끼리 묶어 넷으로 받는 안을 시안까지 그렸다가 되돌렸다.** 사용자는 자기 등급 이름을 알지
묶음을 모른다. 그리고 실제 등급을 저장해야 넥슨이 레드와 블랙의 혜택을 가르는 날에도 기록이 맞는다.
묶음은 등급에서 언제든 계산할 수 있지만 그 반대는 안 된다.

**고르지 않은 메이플 ID 는 `일반` 으로 계산한다**(사용자 지정). 고르기 화면도 `일반` 이 골라진 채로 선다.

### 결정 2. 등급은 **시작 날짜와 함께** 이력으로 쌓는다. 기록은 그 날짜의 등급으로 센다 (사용자 지정)

이력은 메이플 ID 마다 `(시작 날짜, 등급)` 줄의 목록이다. 스타포스 비용이 읽을 때 계산이라, 이력이 있어야
등급이 바뀌어도 지난 줄이 안 움직인다.

- **기록의 날짜에 맞는 줄은 그 날짜 이하에서 가장 늦은 시작 날짜다.** 다음 등급이 시작되기 전까지 앞 등급이
  이어진다. 매주 안 묻는 사용자(결정 11)는 이력이 드문드문해도 이 규칙이 그대로 맞는다.
- **시작 날짜는 늘 목요일이다**(사용자 지정 2026-09-22). MVP 등급은 매주 목요일에 바뀌어 일 단위로 받을 필요가 없다.
  목요일 리셋 주의 첫날이고 `getCurrentBossProfitPeriod('weekly')` 의 기간 키와 같은 값이다. 기록의 날짜는 그 날이 든 주의
  목요일로 바꿔 등급을 찾는다. 보스 수익이 주를 세는 방식과 같다.
- **시작 날짜는 앱을 쓰기 전 날짜여도 된다.** 그 날짜 이후의 기록은 앱을 쓰기 전 것이라도 그 등급을 받는다.
- **고를 수 있는 가장 이른 주는 가계부가 갈 수 있는 가장 이른 주다**(사용자 지정 2026-09-22). `features/cashbook/range.ts` 의
  `historyFloorDateKey(오늘)` 이고, 18개월 전 달의 1일이 든 리셋 주의 목요일이다(2026-09-22 기준 2025-02-27). 가계부가 그보다 앞을
  안 보여 주어 그 앞에 등급을 적어도 쓸 곳이 없다. 이미 목요일이라 주 고르기의 최솟값으로 그대로 쓴다. 주를 고르는 자리
  셋(고르기 모달의 `적용 시작 주` · 등급 변경 시트 · 기록 추가 시트)이 모두 따른다. 이 값은 달마다 앞으로 움직이고, 그보다 앞선
  이력 줄은 지우지 않고 그대로 둔다.
- **첫 시작 날짜보다 앞선 기록에는 등급을 안 쓴다.** 스타포스는 할인 없이(지금 값) 세고, 수수료 일괄 적용(결정 9)에서 빠진다.
- **등급이 빈 줄도 있다**(`grade` 가 `NULL`). 첫 기록보다 앞선 기간을 끼워 넣으면 그 기간의 끝을 닫는 줄이다(결정 11). 그 줄의
  주부터 다음 줄 전까지는 첫 시작 날짜보다 앞선 기록과 똑같이 등급이 없다.
- **시작 날짜의 기본값은 이번 주 목요일**(오늘이 든 주)이다. 사용자가 바꾼다는 전제라 앱이 추정하지 않는다.
- 같은 주에 다시 고르면 그 줄을 덮는다.
- **달력은 주를 고른다**(사용자 지정 2026-09-22). `DateSelect` 와 `CalendarPopover` 를 쓰되 이 자리에서는 **주 고르기**로 연다.
  - 격자는 **다른 달력과 같이 일요일에서 시작한다**(`일 ~ 토`, 사용자 지정). 그래서 한 주(목~수)가 **두 줄에 걸친다.**
    윗줄 목 · 금 · 토에서 시작한 띠가 아랫줄 일 ~ 수로 이어진다. 윗줄 조각은 목요일 쪽만 둥글고 오른쪽 가장자리로 열리며,
    아랫줄 조각은 왼쪽 가장자리에서 이어받아 수요일 쪽에서 닫힌다. 날짜 범위 고르개가 흔히 쓰는 모양이다.
  - **어느 날을 눌러도 그 날이 든 주(목~수) 전체가 고른 주로 칠해진다.** 목요일 칸은 채운 원이다. 저장되는 값이 그 날이라서다.
  - 달력 아래에 `선택한 주` 와 `목 날짜 ~ 수 날짜` 를 적는다(사용자 지정). 날짜 알약에는 저장값인 목요일이 선다.
  - 이번 주보다 뒤의 주와 가장 이른 주보다 앞의 주는 흐리고 못 고른다.
  - 주를 한 칸씩 넘기는 고르개는 쓰지 않는다. 1년 전까지 가는 데 쉰 번 넘게 눌러야 한다.
  - 선택한 주는 **칠한 띠**(`primary-tint` 바탕)다(사용자 결정). 테두리 띠 안은 반려됐다.
- 표는 SQLite `mvp_grade_history` 다. 이력은 끝없이 자라므로 preferences 의 JSON 한 칸에 두지 않는다
  (`db.ts` 가 조회 원장을 SQLite 에 두는 것과 같은 이유다).
- **캐시 삭제의 `기록` 그룹이다**(`cache-data.ts` 의 `RECORD_TABLE_NAMES`). 사용자가 적은 값이라 지우면 되살릴 길이 없고,
  새 표의 기본값은 `일반` 그룹이라 직접 적어야 한다.

### 결정 3. 캐릭터가 어느 메이플 ID 소속인지 **이름째 기록한다** (사용자 지정)

스타포스 응답은 캐릭터 **이름**만 준다. 캐릭터가 삭제 · 이전되거나 닉네임을 바꾸면 그 줄이 어느 ID 의 것인지
알 길이 없다.

- 표는 SQLite `character_accounts` 이고 한 줄이 `(ocid, 이름, 메이플 ID)` 와 **처음 본 날 · 마지막으로 본 날**이다.
  볼 때마다 줄을 쌓지 않고 두 날짜를 넓힌다. 매일 부르는 목록이라 쌓으면 캐릭터 수 × 날짜로 자란다.
  스타포스 줄은 이름으로, ocid 를 든 기록(수익 · 드롭 · 결정석)은 ocid 로 찾는다. 줄의 날짜 이하에서 가장 늦게 본 기록을
  쓴다. 처음 본 날이 줄의 날짜보다 뒤인 기록은 후보가 아니다(그때는 소속을 몰랐다).
- **캐시 삭제의 `기록` 그룹이다.** 지금 있는 캐릭터는 `character/list` 가 다시 주지만, 옛 이름과 지워진 캐릭터는
  다시 받을 수 없다.
- **옛 이름을 지우지 않는다.** 스타포스 줄에는 그때의 이름이 남아 있다. `character_profiles` 는 캐릭터 하나에
  한 행이고 이름을 덮어써서(`ON CONFLICT(ocid) DO UPDATE SET name`) 이 용도로 못 쓴다.
- **`character/list` 를 받는 모든 자리에서 쓴다.** 지금 다섯 곳이다. 로그인 확인(`features/auth/store`) ·
  강화 기록 수집기(`features/enhancement-history/collect`) · 캐릭터 목록 둘(`features/schedule-sync/character-roster`) ·
  캐릭터 설정의 계정 목록(`hooks/useAccountRosters`). 수집기에서만 쓰면 가계부를 한 번도 안 연 사용자는
  기록이 비어, 아이템 판매를 적을 때 캐릭터의 ID 를 몰라 수수료 기본값을 못 채운다.
  `fetchCharacterBasicCached` 처럼 통과 지점 하나로 모은다.

### 결정 4. 소속을 모르는 스타포스 줄은 **그 날짜의 가장 높은 등급**으로 센다 (사용자 지정)

앱을 쓰기 전의 과거 기록이 여기 든다. 소속 기록으로도 못 찾는 줄(두 번의 수집 사이에 만들고 지운 캐릭터)도 같다.

- 후보는 그 줄을 받아 온 넥슨 계정의 메이플 ID 들이다. 다른 넥슨 계정의 ID 일 수는 없다. 키가 하나인 지금은
  계정의 ID 전부이고, [[ADR-297]] 과 넥슨 로그인 뒤 키가 여럿이 되면 이 한정이 걸린다.
- 그 날짜에 등급을 가진 ID 가 없으면 할인 없음이다(결정 2 의 첫 시작 날짜 규칙).
- **고른 메이플 ID 의 등급으로 세면 안 된다.** 스타포스는 읽을 때 계산이라 고른 ID 를 바꿀 때마다 그 줄의 값이 바뀐다.

### 결정 5. 스타포스 비용은 이벤트 할인과 MVP 할인을 **곱한다** (사용자 확인)

```
rounded   = round100(1000 + L³ × (S+1)^exp / divisor)     지금과 같다
시도 비용 = floor(rounded × (100 − 이벤트) × (100 − MVP) / 10000)
최종      = 시도 비용 + (파괴 방지면 rounded × 200%)
```

- **곱연산이다.** 이벤트가 먼저 깎고 남은 값에서 MVP 할인만큼 더 깎는다. 근거는 사용자가 지정한 인벤 글
  (https://www.inven.co.kr/board/maple/2304/12642)이고, 글이 2018년 것이라 사용자가 결과를 계산기 사이트들과 대조해
  확인했다. 200 레벨 16→17 성 · 샤이닝 30% · 파괴 방지에서 일반 226,798,920 · 실버 225,034,928 · 골드 223,858,934 ·
  다이아 이상 220,918,948 이다.
- **반올림이 할인보다 앞이다.** [[ADR-223]] 의 실측(160 레벨 18 성, 샤이닝 30% → 116,144,140)이 근거다.
  **MVP 할인 뒤에 다시 반올림하지 않는다.** 대조에서 `225,034,928` 처럼 100 으로 안 떨어지는 값이 그대로 맞았다.
- **내림은 끝에서 한 번이다.** 정수 식이라 MVP 가 0 이면 지금 식(`floor(rounded × (100 − 이벤트) / 100)`)과
  한 메소도 안 다르고, 기존 줄이 안 움직인다.
- **파괴 방지 추가분은 어느 할인도 안 받는다.** 지금 코드와 같다. 인벤 글은 추가분을 100% 로 적었지만 오래된 값이고,
  200% 는 [[ADR-223]] 정정 13 의 사용자 제공값이라 그대로 둔다.
- **PC방 할인은 안 센다.** PC방 5% 는 0~17 성 구간에서 MVP 할인에 더해진다(사용자 제공). 앱은 강화한 자리가
  PC방이었는지 알 길이 없다. 그 구간을 PC방에서 강화한 줄은 5% 만큼 높게 서고, 이 한계를 FAQ([[ADR-285]])에 적는다.
  다이아 이상 + PC방은 계산기 사이트마다 1 메소씩 갈리는데(`0.1 + 0.05` 의 부동소수 오차로 보인다) PC방을 안 세는
  이 앱에는 닿지 않는다. 정수 식을 쓴다(사용자 결정).
- 비용을 계산하는 것은 여전히 읽을 때다. 줄마다 그 날짜 · 그 캐릭터의 등급을 결정 2 · 3 · 4 로 찾는다.
  식만 고쳐도 과거 줄까지 한 번에 바로잡힌다.

### 결정 6. 수수료 줄에 **`자동` 체크박스**가 선다. 자동은 등급 기록을 따라 다시 계산되고, 손으로 고른 요율은 고정이다 (사용자 지정)

**새 기록의 기본은 `자동`** 이다.

- **`자동`** 은 그 자리 캐릭터가 속한 메이플 ID 의, 그 기록 날짜의 등급 요율이다. **등급 기록이 바뀌면**(변경 · 추가 · 고치기 · 지우기)
  **자동으로 적힌 기록을 전부 다시 계산한다**(사용자 지정 2026-09-22). 내가 판 기록이 지금 알고 있는 등급을 따라야 하기 때문이다.
- **`없음` · `3%` · `5%`** 는 사용자가 직접 고른 요율이다. **등급이 바뀌어도 그대로다.** 직거래나 등급과 다른 요율로 판 기록이 여기 든다.
- 자동인 기록의 날짜에 등급이 없으면(첫 시작 날짜보다 앞) **`일반` 요율(5%)** 로 센다. 고르지 않은 메이플 ID 를 일반으로 보는 것과 같은 규칙이다.
- 다시 계산하는 방식은 **다시 쓰기**다. 자동 기록도 받는 돈(`meso_amount`)과 뗀 몫을 행에 적고, 등급 기록이 바뀌면 그 ID 의 자동 기록을
  새 요율로 다시 적는다. 집계가 `meso_amount` 한 칸을 더하므로 읽을 때 계산하면 집계 경로가 전부 바뀐다. 드롭도 같은 방식으로
  `dropPayoutMeso` 가 순수 함수로 남는다.
- 행마다 자동인지를 든다. `income_records.sale_fee_auto` · `boss_drop_records.sale_fee_auto` · `split_fee_auto` ·
  `boss_party_settings.split_fee_auto` · `boss_profit_records.split_fee_auto`(`INTEGER`, 1 이 자동). `NULL` 은 이 칸이 생기기 전의 행이고
  수동으로 읽는다.

**수수료 줄은 시안 다 모양이다**(사용자 결정 2026-09-22). 한 줄에 왼쪽부터 `수수료` 라벨 · `자동` 체크박스 · 오른쪽 값이다.

- 체크박스는 `sheet-fields` 의 `CheckBox` 와 그 옆 글자(`text-xs` · `font-semibold` · `text-text-muted`)다. 가계부 사냥 폼의
  `획득 메소 직접 입력` 과 같은 모양이다. 스위치가 아닌 것은 사용자 지정이다.
- **켜면** 값 자리에 **명패와 요율**이 이 순서로 선다(명패 높이 18, 예: `[MVP 다이아 명패] 3%`). 일반은 명패 그림이 없어 `일반` 글자 알약이다.
  명패가 어느 등급의 요율인지 말하므로 **설명 줄을 두지 않는다**(사용자 지정, 시안의 `MVP 다이아 기준 3%예요…` 줄을 뺐다).
- **끄면** 값 자리가 세그먼트 `없음 · 3% · 5%`(모달은 `0% · 3% · 5%`)가 되고, 방금까지 자동이던 요율을 고른 채 선다. 끄는 것만으로는
  금액이 안 움직인다. 줄 아래에 `직접 고른 요율이라 등급이 바뀌어도 그대로예요.` 한 줄이 선다
  (**이 한 줄은 [[ADR-310]] 결정 1 이 걷었다**, 2026-09-23).
- 캐릭터를 고르기 전에는 요율을 찾을 ID 가 없어 값 자리가 빈다. 아이템 판매 폼만 해당한다(결정 10).

| 자리 | 지금 | 바뀌는 것 |
|---|---|---|
| 가계부 아이템 판매 | `없음 / 3% / 5%`, 기본 `없음` | `자동` 이 더해지고 기본이 된다 |
| 가계부 조각 정산 | 수수료 줄 없음 | 줄이 선다(결정 8) |
| 사냥 폼 둘의 조각 판매 | 수수료 없음 | 줄이 선다(결정 8) |
| 드롭 판매가 입력 카드 | 수수료 없음 | 판매 · 분배 두 줄이 선다(결정 7) |
| 파티 모달 송금 수수료 | `0% / 3% / 5%`, 비율로 바꿀 때 3 | `자동` 이 더해지고 기본이 된다(사용자 결정 2026-09-22) |

- **`없음`(모달은 `0%`) 조각은 모든 자리에 남는다.** 직거래를 적는 조각이고, 일괄 적용(결정 9)이 잘못 붙인
  수수료를 사용자가 되돌리는 자리다. 되돌리면 수동이 되어 다시 계산에서 빠진다.
- **송금 · 분배 수수료도 기본값은 내 등급이다**(사용자 결정 2026-09-22). 송금 수수료는 보내는 사람의 등급을 따르므로
  ([[ADR-305]] 결정 5) 내가 받는 쪽이거나 드롭을 파티원이 팔았으면 실제 요율이 다를 수 있다. 고칠 수 있으니 기본값은
  언제나 내 등급으로 채우고, 다르면 사용자가 체크박스를 끄고 고른다.
- **판매 분배금 계산기는 안 건드린다**(사용자 지정). 기록이 아니라 범용 도구라 등급을 자동으로 반영할 필요가 없다.
- 스타포스는 읽을 때 계산해 등급 기록을 저절로 따라가고, 수수료는 자동 기록을 다시 적어 따라간다. 결과는 같다. **등급 기록을
  고치면 자동인 것은 모두 따라온다.**

**파티 모달의 송금 수수료도 자동이다**(사용자 결정 2026-09-22). 고치는 자리 셋([[ADR-305]] 결정 9)이 같은 줄을 쓴다.

- 비율로 바꿀 때의 기본값이 `3` 이 아니라 **`자동`** 이다. [[ADR-305]] 결정 5 의 `NULL 은 3` 을 이것이 바꾼다.
- 설정(`boss_party_settings`)이 자동이면 새 결정석 기록이 **그 기록 날짜의 등급 요율**로 적히고 `split_fee_auto = 1` 을 든다.
  모달은 이번 주의 등급을 보인다. 설정은 앞으로 적힐 기록의 약속이기 때문이다.
- 등급 기록이 바뀌면 자동인 결정석 기록의 `split_fee_percent` 와 `payout_meso` 를 `crystalPayoutMeso` 로 다시 쓴다. 균등 기록은
  차액 송금이 없어 금액이 안 바뀐다.
- 보스 수익 행의 모달은 그 기록 한 건만 고친다([[ADR-305]] 결정 10). 명패와 요율은 **그 기록 날짜의 등급**이고, 체크박스를 끄면
  그 기록만 수동이 된다.
- **옮길 행이 없다.** 비율 기능(PR #515)은 2026-09-22 에 머지됐고 마지막 OTA(1.0.10+3, 09-19)에 안 들었다. 사용자 기기에는
  비율 행이 아직 없다.

**다시 계산했으면 토스트로 알린다**(사용자 결정 2026-09-22). 등급 기록을 저장하거나 지운 뒤, 요율이 달라진 자동 기록이 있으면
`useToastStore` 의 `showSuccess` 로 `자동 수수료 기록 N건을 다시 계산했어요` 를 띄운다.

- N 은 **요율이 바뀐 행**만 센다. 골드에서 다이아로 바꾸면 둘 다 3% 라 수수료 기록은 그대로이고 토스트도 안 뜬다.
  세는 표는 가계부 수입 · 드롭 · 결정석 셋이다.
- 등급 기록을 바꾸는 자리 전부에서 같다. 설정의 세 시트 · 주간 수정 · 새 메이플 ID 흐름이다.
- 일괄 적용(결정 9)은 이 토스트를 안 띄운다. 사용자가 체크박스로 고른 일이라 따로 알릴 것이 없다.

### 결정 7. 드롭 판매가에 **판매 수수료와 분배 수수료**가 붙는다 (사용자 지정, [[ADR-305]] 결정 6 을 뒤집는다)

드롭 아이템을 경매장에 파는 순간 수수료를 문다. 한 명이 팔아 파티원에게 나눠 보내면 그 송금에 한 번 더 문다.
[[ADR-168]] 이 계산기에서 푼 **두 번 떼이는** 상황과 같은 모양이다.

- `boss_drop_records` 에 `sale_fee_percent` 와 `split_fee_percent` 두 칸을 `ensureColumn` 으로 붙인다.
  `NULL` 은 수수료를 안 센 옛 행이고 지금 값 그대로 읽힌다.
- 내 몫은 판매 분배금 계산기와 같은 식이다. 판매 수수료를 뗀 `N` 에서 파티원에게 보낼 금액을
  역산하고(`lib/cashbook/item-split` 의 `transferPerMember`), 내 몫은 `N` 에서 보낸 금액을 뺀 것이다.
  균등이면 보낼 곳이 `인원 − 1` 이고 비율이면 상대 한 쪽이다. 혼자면 분배 수수료가 안 든다.
- 드롭 수익을 읽는 곳이 열두 군데지만 **전부 `dropPayoutMeso` 하나를 거친다.** 식을 그 함수에 넣으면 보스 수익 ·
  today · 가계부가 함께 따라온다. `DropPriceFields` 가 저장 계층과 도메인 양쪽의 구조적 타입이라 칸을 더하면
  둘 다 받는다.

### 결정 8. 조각 정산과 사냥 폼의 조각 판매에 **판매 수수료**가 붙는다 (사용자 지정, [[ADR-283]] 결정 7 의 한 줄을 뒤집는다)

솔 에르다 조각도 경매장에서 판다. 조각 정산 폼(`FragmentSettleForm`)과, 조각 가격을 넣으면 그 자리에서 판 것으로
치는 사냥 폼 둘(`HuntCalculatorForm` · `HuntManualForm`)이 같은 판매를 나눠 든다.

- 저장 칸은 이미 있다. `income_records.sale_fee_percent` · `sale_fee_meso` 를 아이템 판매와 함께 쓴다.
- 정산은 `판 개수 × 개당 가격` 이 판매 대금이고 `netProceedsMeso` 로 뗀 값이 `meso_amount` 다.
- **사냥은 조각 몫에만** 붙는다. 사냥으로 번 메소에는 안 붙는다. `meso_amount = 메소 + (조각 × 가격 − 수수료)` 다.
- **사냥 폼의 수수료 줄은 조각 가격을 안 적어도 늘 선다**(사용자 지정 2026-09-22). 처음에는 가격을 적어야 섰는데, 그러면 사냥 수익에
  수수료 줄이 없는 것처럼 보였다. 가격이 비면 판 것이 없어 떼는 돈이 0 이고, 저장은 수수료 칸을 비우고 자동 여부만 남긴다.
- **정산을 수정으로 열 때 단가를 되짚는 식이 바뀐다.** 지금은 `meso_amount ÷ 판 개수` 라 수수료를 뗀 기록을 열면
  단가가 낮게 선다. `(meso_amount + sale_fee_meso) ÷ 판 개수` 다.

### 결정 9. 기존 사용자의 첫 확인 화면에서 지난 기록에 **수수료를 일괄 적용할지** 묻는다. 적용하면 전부 붙이고 고칠 수 있게 둔다 (사용자 지정)

**따로 모달을 띄우지 않는다.** 앱을 쓰던 사용자가 처음 등급을 고르는 선택 흐름의 **확인 화면에 체크박스 하나**를 더한다
(사용자 지정 2026-09-22). 켠 채 `맞아요` 를 누르면 적용한다. 지난 기록이 없는 사용자(온보딩)에게는 체크박스가 안 선다.
체크박스가 서는 조건은 아래 대상 표 넷 중 하나라도 행이 있는 것이다. 한 번 흐름을 마치면 다시 안 선다.

대상은 **첫 시작 날짜 이후**의 수수료가 빈 행이다(결정 2). 행의 날짜에 맞는 등급의 요율을 쓴다.

- `income_records` 의 아이템 판매 중 `sale_fee_percent IS NULL`
- `income_records` 의 조각 정산 전부(지금은 전부 `NULL`)
- `income_records` 의 사냥 중 조각 가격이 있는 행. 조각 몫에만
- `boss_drop_records` 중 가격을 입력한 행. 판매 · 분배 두 칸

**되짚을 것이 없다.** 네 대상 모두 저장된 금액이 수수료를 안 뗀 값이다(아이템 판매 폼은 `feePercent` 가 `null` 이면
`net === gross` 를 넣는다). 이미 요율이 적힌 행은 사용자가 고른 것이라 수동으로 두고 건드리지 않는다.

**일괄 적용한 행은 `자동` 이 된다.** 그래서 그 뒤 등급 기록을 고치면 함께 다시 계산된다. 체크박스를 끈 채 넘긴 사용자의 빈 행은
수수료 없음(수동)으로 남는다.

**`sale_fee_percent IS NULL` 은 직거래와 안 고름을 함께 뜻한다**(`storage/income.ts` 의 칸 주석). 가릴 단서가 행에
없어서 직거래 행에도 수수료가 붙는다. 이것을 받아들이고, 그런 행은 사용자가 고르개를 `없음` 으로 돌린다.

결정석의 송금 수수료(`boss_party_settings` · `boss_profit_records` 의 `split_fee_percent`)는 대상이 아니다.
`NULL` 인 행은 균등 분배이고, 균등에는 차액 송금이 없어 `crystalPayoutMeso` 가 수수료를 안 본다. 비율 행은 아직 사용자 기기에
없다(결정 6).

스타포스는 일괄 적용이 필요 없다. 읽을 때 계산이라 이력이 들어가면 저절로 따라온다.

**물었다는 표시(`mvpBulkApplyAsked`, 첫 흐름을 마치면 켜진다)는 캐시 삭제에서 보존한다**(`KEEP_KEYS`). 체크박스를 끄고 넘긴 사용자의
빈 행은 수동 없음으로 남는데, 표시가 지워져 다시 물으면 그 행들이 다시 대상이 된다.

### 결정 10. 아이템 판매는 **캐릭터를 골라야** 저장된다 (사용자 지정, [[ADR-173]] 결정 14 의 예외)

요율은 캐릭터가 속한 ID 의 등급에서 온다. 캐릭터를 안 고른 기록(`ocid = null`, 계정 단위)은 요율을 찾을 곳이 없다.

- **아이템 판매 폼만 바꾼다.** 수수료가 붙는 폼 가운데 캐릭터가 선택인 것은 이것 하나다(사냥 둘과 조각 정산은 이미
  필수다, [[ADR-283]] 결정 4). 공용 `CharacterField` 는 안 바꾼다. 수익 기타와 지출 넷은 수수료가 없어 `선택 안함` 을
  그대로 둔다. 아이템 판매 폼은 조각 정산처럼 `ChainSelect` 와 `requiredCharacterOptions` 를 쓴다.
- **이미 캐릭터 없이 적힌 아이템 판매는 대표 캐릭터로 계산한다.** 그 행의 `ocid` 는 안 바꾸고 요율만 대표 캐릭터가
  속한 ID 의 등급에서 가져온다. 대표는 비지 않는다. 저장된 대표가 목록에서 빠지면 표식을 지우고 읽는 쪽이 추적
  목록의 첫 캐릭터를 쓴다(`storage/character-selection.ts`). 그 행을 수정으로 열면 캐릭터 칸이 비어 있어 골라야 저장된다.

### 결정 11. 묻는 자리는 **추적 캐릭터가 속한 ID** 중 등급이 없는 것이다. 주마다 한 번 다시 확인한다 (사용자 지정)

**등급을 묻는 규칙은 하나다.** 추적 캐릭터가 속한 메이플 ID 가운데 이력이 없는 ID 가 있으면, 그 ID 들로
선택 흐름(결정 12)을 띄운다. 이 규칙 하나가 세 경우를 덮는다.

- **온보딩.** 캐릭터 선택이 먼저다. 캐릭터 설정의 `계속하기` 뒤에 선다. ~~진입 단계(`signIn → characterSetup → ready`)는
  늘리지 않는다.~~ → [[ADR-308]] 결정 4: 온보딩 화면 둘이고 진입 단계에 `mvpGrade` 가 더해진다.
- **기존 사용자.** 업데이트 뒤 모든 ID 에 이력이 없으므로 한 번 뜬다.
- **새 메이플 ID.** 나중에 다른 ID 의 캐릭터를 추적하면 그 ID 하나만 담아 뜬다.

계정의 ID 를 전부 묻지 않는다. 추적 안 하는 캐릭터의 스타포스도 지출에 들지만([[ADR-223]]) 그 캐릭터가
등급 없는 ID 에 속하면 할인 없이 선다.

**주간 확인.** 주가 바뀌면(목요일 리셋, `getCurrentBossProfitPeriod('weekly')` 의 기간 키) 모든 추적 ID 의
등급을 확인 화면으로 보인다. 확인 화면의 체크박스를 켠 사용자에게는 안 뜬다. 체크박스는 설정에서 다시 켤 수 있다.

preferences 키는 셋이다. `mvpWeeklyCheckOff`(체크박스, 사용자가 만든 값이라 `KEEP_KEYS`) ·
`mvpLastCheckedWeek`(마지막으로 확인한 주의 기간 키, 지워지면 한 번 더 물을 뿐이라 안 보존) ·
`mvpBulkApplyAsked`(결정 9).

**설정에서 직접 바꾸는 자리는 등급 이력 페이지다**(사용자 지정 2026-09-22). 두 단계다.

- `AppSettingsScreen` 의 `캐릭터 · 테마` 아래에 `MVP 등급` 구역과 행 하나를 두고, 누르면 **목록 페이지**가 선다.
  메이플 ID 마다 카드 하나에 ID 표시 · `변경` · **지금 등급 한 줄**(타임라인 점 · `시작 날짜 부터` · `지금` · 명패) ·
  `이력 N건 보기` 가 있다. 맨 아래가 `매주 등급 확인` 스위치다(`mvpWeeklyCheckOff` 의 반대).
- `이력 N건 보기` 는 **ID 이력 상세 페이지**를 연다. 위 카드가 ID 표시 · `지금 등급`(명패 · 혜택 · 시작 날짜) · `등급 변경`
  이고, 아래 `이력 N건` 이 타임라인 전체다. **해가 바뀌는 자리에 연도 줄**이 서서 길어져도 어디쯤인지 읽힌다.
  이력 줄을 누르면 그 기록을 고친다.
- 목록에 이력을 다 펼치지 않는 것은 이력이 쌓이면 페이지가 끝없이 길어지기 때문이다(사용자 지적).
- **등급 변경과 기록 고치기는 바텀시트다**(사용자 결정 2026-09-22). 이 앱에서 기록을 적고 고치는 화면이 바텀시트이기 때문이다
  (직접 완료 시트 · 가계부 수입 · 지출 시트와 같은 문법). 머리 = 제목 + 주 고르개(주 고르기 달력), 본문 = 7칸 격자 + 혜택 한 줄 +
  고른 주의 뜻 한 줄, 바닥 = `저장`. 고칠 때는 `이 기록 지우기` 가 더 서고 확인 창을 거친다.
  **ID 표시가 없다**(이미 그 ID 의 페이지다). **확인 단계가 없다**(저장하면 뒤의 타임라인이 결과를 보인다).
- **지난 기록을 끼워 넣는 버튼은 따로 있다**(사용자 지정 2026-09-22). `이력 N건` 제목 오른쪽의 `+ 추가` 가 `기록 추가` 시트를 연다.
  `등급 변경` 은 이번 주까지 이어지는 끝이 열린 기간을, `+ 추가` 는 지난주 안에서 끝나는 닫힌 기간을 적는다.
  - `등급 변경` 은 지금 등급을 바꾼다. 지금 기록이 시작된 주부터 이번 주까지 고른다. 같은 주면 그 기록을 바꾼다.
  - `+ 추가` 는 **시작 주와 종료 주**를 고른다(사용자 결정 2026-09-22, 시안 기간 추가-다). 한 번 등급이 달랐던 기간을
    끼워 넣는 자리라 끝이 있어야 한다. 시트 머리의 **기간 알약 하나**가 달력을 열고, 달력 위 **`시작 주 | 종료 주` 탭**이 어느 끝을
    고를지 정한다. 시작 주를 고르면 종료 주 탭으로 넘어간다. 고른 기간은 시작 주 목요일부터 종료 주 수요일까지 줄을 넘어 이어진
    띠로 칠해지고, 달력 아래에 `선택한 기간` 과 그 범위를 적는다.
  - **끝이 닫힌 기간이라 지난주까지만** 고른다. 이번 주가 든 기간은 `등급 변경` 이 바꾼다. 지금 기록 안의 지난 몇 주도 고를 수
    있다(사용자 결정 2026-09-22). 그래서 `등급 변경` 은 끝이 열린 기간, `+ 추가` 는 끝이 닫힌 기간으로 갈린다.
  - 시작 주는 가장 이른 주(결정 2)부터 지난주까지이고, 이미 기록이 있는 주는 흐리고 못 고른다(그 기록은 줄을 눌러 고친다).
    종료 주는 시작 주부터 **그 뒤 첫 기록의 앞 주까지**이고 지난주를 넘지 않는다. 기간이 다른 기록을 넘으면 그 기록을 어떻게
    할지 정할 수 없어서다.
  - 둘 다 고르기 전에는 알약이 `기간 선택` 이고 `저장` 이 꺼진다. 끼워 넣을 자리는 사용자만 알아서 앱이 기본값을 넣지 않는다.
  - **종료 주 다음 주부터는 그 기간을 감싸던 등급이 다시 이어진다.** 저장은 이력 두 줄이다. `(시작 주, 고른 등급)` 과
    `(종료 주 다음 주, 감싸던 등급)`. 이력이 `(시작 날짜, 등급)` 줄의 목록이라(결정 2) 줄을 더하는 것으로 기간이 표현된다.
    종료 주 다음 주가 곧 다음 기록의 주이면 둘째 줄을 안 적는다. 둘째 줄은 타임라인에 보통 기록으로 선다.
  - **첫 기록보다 앞선 기간이면 둘째 줄은 `등급 없음`이다**(사용자 결정 2026-09-22). 감싸던 등급이 없어서다. 고른 기간에만 등급을
    적고 그 기간을 다시 계산하며, 종료 주 뒤부터 첫 기록 전까지는 지금처럼 등급이 없다(스타포스 할인 없음 · 자동 수수료 일반 5%).
    `일반` 으로 채우지 않는 것은 계산은 같아도 사용자가 넣지 않은 기록이 이력에 서기 때문이다. 타임라인에는 명패 자리에 `등급 없음`
    글자 알약이 선다. 누르면 고치기 시트가 열려 등급을 적거나 지울 수 있고, 지우면 앞 기간이 첫 기록까지 이어진다.
  - 기간을 고르면 설명 줄이 **적용 기간과 다시 이어지는 등급**을 말한다. 예: `7월 2일 (목)부터 7월 15일 (수)까지 레드로 계산해요.
    7월 16일부터는 다시 실버예요.` 다음 기록 바로 앞까지면 `…까지 레드로 계산해요. 7월 30일부터는 골드예요.` 다.
  - 끼워 넣으면 그 기간의 **자동** 수수료 기록과 스타포스가 함께 다시 계산된다(결정 6). 손으로 고른 수수료는 그대로다.

### 결정 12. 모달은 **고르기와 확인** 두 화면이다. 주간은 확인이 먼저다 (사용자 지정)

한 모달 안에서 두 화면을 오간다.

- **선택 흐름: 고르기 → 확인.** 고르기의 버튼은 `다음` 이다. 확인은 `맞아요` 와 `수정` 이고, `수정` 은 고른 값을 그대로
  든 채 고르기로 돌아간다.
- **주간 흐름: 확인 → (수정) → 고르기 → 확인.** 확인 화면이 먼저 뜨고, 고르기 화면에서 시작 주 줄은 **등급을 바꾼 ID 에만**
  선다. 바꾸지 않은 ID 는 적용 시작 주가 필요 없다.
- **두 확인 화면에 `앞으로 등급은 직접 바꿀게요` 체크박스**가 선다(atom `CheckBox`). 켜면 주간 확인이 안 뜬다.
- **기존 사용자의 첫 확인 화면에는 체크박스가 하나 더** 선다(결정 9). 지난 기록 일괄 적용이다.

### 결정 13. 모달 모양은 **시안 C**, 확인 카드는 **확인-나**다 (사용자 지정)

- 머리는 `NoticeModal` 과 같다(배지 56 · 제목 · 설명). 폭은 `Modal.Card` 의 기본(`max-w-sm`)이다. `NoticeModal` 의
  `max-w-xs` 에는 등급 일곱과 ID 표시가 함께 안 들어간다.
- 메이플 ID 하나가 테두리 카드 하나다. ID 표시는 캐릭터 설정의 계정 드롭다운(`AccountSelect` 의 `AccountRow`)과 같다.
- **고르기**: 등급 일곱이 7칸 격자다. 칸마다 문양 타일 34 와 등급 이름(10px)이고, 고른 칸은 테마색 테두리 2px 에
  이름이 `primary-ink` 굵게 선다. 그 아래 고른 등급의 혜택 한 줄, 마지막이 `적용 시작 주` 와 `DateSelect`(주 고르기, 결정 2)다.
- **문양 타일은 명패 그림의 왼쪽 정사각을 자른 것**이다. 그림은 `src/assets/mvp/{bronze,silver,gold,diamond,red,black}.webp`
  (높이 50 의 가로 명패, 손실 webp q90)이고 일반은 그림이 없어 `일반` 글자 타일이다. 목록은 `asset-groups.ts` 에
  그룹을 더해 `npm run assets:gen` 으로 만든다([[ADR-129]]).
- **확인 카드**: ID 표시 줄이 폭 전체를 쓰고, 구분선 아래 라벨과 값 세 줄(`등급` = 명패 높이 20 · `혜택` · `적용 시작 주`)이
  선다. 가계부 시트의 `FieldRow` 와 같은 축이다. **명패를 ID 표시 줄 오른쪽에 두는 안은 반려됐다.** 캐릭터 정보가
  잘려 어느 ID 인지 안 읽힌다.

- **묻는 흐름**: 규칙은 `features/mvp-grade/ask.ts` 의 `decideMvpAsk`, 상태는 `flow-store.ts` 의 `useMvpAskStore` 다. 모달은
  `app/mvp-grade/MvpGradeModal.tsx` 이고 `AppShell` 의 `MvpGradeHost` 가 띄운다. 키 안내 모달보다 앞에 놓아 둘이 겹치면 키 안내가 위다.
- **재는 때는 셋이다.** 진입 단계가 `ready` 가 될 때(온보딩의 `계속하기` 뒤 포함), 앱으로 돌아올 때(켜 둔 채 목요일을 넘긴 사용자),
  캐릭터 관리에서 저장한 뒤(새 메이플 ID). 모달이 떠 있으면 다시 안 잰다. 고르던 값이 새 물음으로 덮이기 때문이다.
  겹쳐 불러도 목록은 한 번만 받는다.
- **모달은 바깥 탭 · 뒤로가기로 안 닫힌다.** 답을 받아야 끝나는 흐름이고, 고르지 않은 ID 는 `일반` 으로 이미 서 있다.
- **새 ID 흐름의 `앞으로 등급은 직접 바꿀게요` 는 저장된 값으로 선다.** 꺼진 채로 서면 켜 둔 사용자의 값을 `맞아요` 한 번이 끈다.
- **설정 목록의 ID 는 추적 캐릭터의 ID 가 먼저이고, 이력만 남은 ID 가 뒤다.** 추적에서 빠진 ID 의 이력도 고칠 수 있어야 해서다.
- **기록 고치기의 주는 앞뒤 기록 사이다**(앞 기록 다음 주 ~ 다음 기록 앞 주, 가장 이른 주와 이번 주 안). 기록 추가가 다른 기록을
  넘지 못하는 것(결정 11)과 같은 이유다. `lib/mvp/history.ts` 의 `editWeekBounds` 다.
- 설정 목록을 읽지 못하면 빈 목록이 아니라 실패 화면과 `다시 시도` 가 선다. 시트에서 저장하지 못하면 토스트로 알리고 타임라인은 그대로다.

## 대가

- **직거래로 판 행에 수수료가 붙는다**(결정 9). 가릴 단서가 없어 사용자가 고친다. 고치면 수동이 된다.
- **등급 기록을 고칠 때마다 그 ID 의 자동 기록을 다시 쓴다**(결정 6). 가계부 수입 · 드롭 · 결정석 세 표이고, 기록이 많으면 한 번에
  수백 행을 쓴다.
- **PC방에서 0~17 성을 강화한 줄은 5% 높게 선다**(결정 5). 앱이 알 길이 없다.
- **앱을 쓰기 전 소속을 모르는 줄은 가장 높은 등급으로 선다**(결정 4). 그 줄이 등급 낮은 ID 의 것이었으면 지출이
  그만큼 낮게 선다.
- **추적 안 하는 ID 의 스타포스는 할인 없이 선다**(결정 11).
- 표 둘(`mvp_grade_history` · `character_accounts`)과 칸 일곱이 는다. `boss_drop_records` 넷(요율 둘 · 자동 둘),
  `income_records` · `boss_party_settings` · `boss_profit_records` 에 자동 하나씩이다.
- 스타포스 비용이 줄마다 이력과 소속을 찾는다. 줄 수가 수천이라 표를 한 번 읽어 메모리에서 찾는다.

## 열린 질문

- **구현 때 정한 문구 다섯이 사용자 확인 전이다**(2026-09-22). 결정 14 의 표에 없던 자리다.
  - 기록 추가 시트에서 첫 기록보다 앞선 기간을 고르면: `…까지 레드로 계산해요. 5월 21일부터는 다시 등급이 없어요.`
    (다음 기록 바로 앞이면 `다시` 가 빠진다. 조사는 등급 이름의 받침을 따른다. `블랙으로` · `일반이에요`)
  - 설정 목록의 스위치 설명: `주가 바뀌면 등급이 맞는지 물어요. 끄면 등급은 이 화면에서만 바뀌어요.` (시안의 문구)
  - 지우기 확인 창: 제목 `등급 기록을 지울까요?` · 설명 `9월 17일 (목)부터의 다이아 기록을 지워요. 되돌릴 수 없어요.` ·
    버튼 `그대로 두기` / `기록 지우기`(위험 색)
  - 목록을 읽지 못했을 때: `MVP 등급을 불러오지 못했습니다` · `저장된 기록을 읽지 못했습니다. 다시 시도해주세요.` (드롭 히스토리와 같은 틀)
