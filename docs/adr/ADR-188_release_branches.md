# ADR-188 브랜치 전략과 ADR 번호 받기

> 🟢 유효
> 관련 소스: `scripts/adr-number.mjs` · `scripts/__tests__/adr-number.test.mjs`

## 배경

2026-11-09 까지는 모든 작업 브랜치를 main 에서 따서 main 에 머지했다. 그래서 다음 스토어 버전에만 넣을 네이티브
변경(#907)이 main 에 들어오자 main 이 스토어에 나가 있는 앱과 달라졌다. 그 뒤로 1.0.13 사용자에게 OTA 를 낼 때마다
스토어 바이너리를 빌드한 커밋으로 워크트리를 따로 만들어야 했다. OTA 1.0.13+5 는 `a453777f` 트리에서 발행했다.

ADR 번호도 겹친 적이 있다. 2026-11-04 에 병렬 PR 둘이 같은 번호를 붙였다. 각 브랜치에서는 검사를 통과했지만 머지
뒤 `adr-policy.test.ts` 의 `한 번호는 한 파일에만 있다` 가 깨졌다(#844, #846 에서 고침). 핫픽스를 main 에서 따면
develop 에서 이미 쓴 번호가 그 브랜치에 보이지 않는다. 그래서 같은 일이 더 쉽게 생긴다.

## 결정

### 결정 1. main 은 출시된 것만 담는다

main 에는 `release/x.y.z` 와 `hotfix/<slug>` 만 머지한다. main 에 바로 커밋하지 않고, 작업 브랜치를 main 으로 PR
하지 않는다.

그래야 main 의 끝이 언제나 스토어 바이너리와 그 위에 발행한 OTA 와 같다. 그러면 main 에서 핫픽스를 따기만 해도
그 트리가 OTA 를 발행할 트리가 된다.

### 결정 2. develop 이 다음 스토어 버전을 모은다

GitHub 기본 브랜치는 develop 이다. 지금 develop 에 들어가는 것은 모두 1.0.14 로 나간다. 이슈의 마일스톤도
`v1.0.14` 로 붙인다.

기본 브랜치를 develop 으로 둔 것은 PR 본문의 `Closes #n` 이 기본 브랜치에 머지될 때만 이슈를 닫기 때문이다.
본 체크아웃도 develop 에 둔다. 작업은 `.claude/worktrees/` 의 워크트리에서 한다.

### 결정 3. 작업 브랜치는 develop 에서 따고 develop 으로 PR 한다

브랜치 이름은 `<종류>/<영어 slug>` 다. 종류는 커밋 메시지의 conventional commits 종류와 같은 말을 쓴다.

| 종류 | 쓰는 때 |
|---|---|
| `feat/` | 새 기능 |
| `fix/` | 버그 고침 |
| `chore/` | 빌드 · 설정 · 스크립트 · 버전 올림 |
| `docs/` | 문서만 바꿀 때 |
| `refactor/` | 동작을 바꾸지 않는 코드 정리 |

이슈가 있으면 slug 끝에 이슈 번호를 붙인다(`fix/tracking-mode-unavailable-877`).

### 결정 4. 이슈에 없는 작업은 설계 → 이슈 → 문서 → 테스트 → 구현 순서로 한다

사용자가 시키지 않아도 이 순서를 지킨다.

1. 설계: 무엇을 왜 바꾸는지 정한다. 사용자가 골라야 할 것은 이 단계에서 묻는다.
2. 이슈: 설계를 이슈로 쓰고 마일스톤을 붙인다.
3. 문서: ADR 과 기능 문서를 고친다. 사용자에게 보이고 확인을 받는다.
4. 테스트: 테스트를 먼저 쓴다.
5. 구현: 테스트를 통과시킨다.

문서를 나중에 채우면 문서와 다른 구현이 그대로 머지된다. 이슈가 없으면 그 작업이 어느 버전에 들어갔는지 마일스톤으로
찾을 수 없다.

### 결정 5. 스토어 출시는 `release/x.y.z` 에서 한다

1. 출시를 준비할 때 develop 에서 `release/x.y.z` 를 딴다.
2. 버전 올림 · 스토어 빌드 · 심사 반려 수정은 이 브랜치에서만 한다. 그동안 develop 은 다음 버전의 작업을 계속 받는다.
3. 스토어에 게시되면 이 브랜치를 main 으로 PR 해 merge commit 으로 머지한다.
4. 곧바로 main 을 develop 으로 머지한다(결정 7).
5. `CLAUDE.md` 의 지금 버전과 새 이슈에 붙일 마일스톤을 다음 버전으로 옮긴다.

release 브랜치를 따로 두는 것은 심사를 기다리는 며칠 동안 develop 에 들어온 작업이 같은 바이너리에 섞이지 않게
하려는 것이다. 빌드 절차는 `foundation/release.md` 에 있다.

### 결정 6. 핫픽스는 main 에서 `hotfix/<slug>` 를 딴다

1. main 에서 `hotfix/<slug>` 를 딴다.
2. 결정 4 의 순서대로 이슈 · 문서 · 테스트 · 고침을 한다. ADR 새 번호는 결정 8 로 받는다.
3. OTA 로 낸다면 이 브랜치의 트리에서 발행한다. 버전 올림과 노트 커밋도 이 브랜치에 남긴다
   (`features/live-update.md` 의 `OTA 발행 절차`).
4. main 으로 PR 해 merge commit 으로 머지한다. squash 하면 발행한 트리의 커밋이 main 에서 사라진다.
5. 곧바로 main 을 develop 으로 머지한다(결정 7).

develop 에서 따지 않는 것은 develop 에 아직 출시하지 않은 작업이 있기 때문이다. 거기서 따면 그 작업이 핫픽스와 함께
main 으로 간다. 그 안에 네이티브 변경이 있으면 지문이 달라져 OTA 로도 낼 수 없다.

1.0.14 가 스토어에 게시되기 전까지는 main 에 1.0.13 바이너리에 없는 네이티브 변경(#907)이 들어 있다. 그래서 그동안의
1.0.13 핫픽스는 main 의 끝이 아니라 OTA 1.0.13+5 를 발행한 트리(`a453777f`)에서 딴다. `release/1.0.14` 가 main 에
머지되면 이 단락을 지운다.

### 결정 7. main 에 머지하면 곧바로 main 을 develop 으로 머지한다

release 나 hotfix 를 main 에 머지하면 main 을 head, develop 을 base 로 PR 을 만들어 merge commit 으로 머지한다.
충돌이 나면 develop 에서 `chore/merge-main-<버전>` 을 따서 main 을 머지하고, 충돌을 푼 뒤 develop 으로 PR 한다.

미루면 다음 스토어 바이너리를 develop 에서 빌드할 때 그 고침이 빠진다.

한 기능의 ADR 은 한 파일이고, 결정이 바뀌면 파일 이름에 번호를 덧붙인다. 그래서 hotfix 와 develop 이 같은 ADR 에
서로 다른 번호를 붙였으면 파일 이름이 둘로 갈린다. 이 머지에서 파일을 하나로 합치고 두 번호를 오름차순으로 모두
이어 붙인다(`ADR-011+138+189+190_live-update_protocol.md`). 두 쪽의 결정과 번호 기록 줄도 모두 남긴다.

### 결정 8. ADR 새 번호는 `scripts/adr-number.mjs` 로 받는다

```bash
node scripts/adr-number.mjs
```

스크립트는 `git fetch origin` 을 한 뒤 아래를 모두 본다.

| 보는 곳 | 보는 이유 |
|---|---|
| origin 의 main · develop, main 에 아직 머지되지 않은 `release/*` · `hotfix/*` | 머지됐거나 출시 중인 번호 |
| 열린 PR 의 브랜치(`gh pr list`) | 아직 머지되지 않은 번호 |
| 이 맥에 있는 모든 워크트리의 `docs/adr/` | 다른 세션이 만들고 아직 커밋하거나 푸시하지 않은 번호 |

그중 가장 큰 번호에 1 을 더해 찍는다. 같은 번호를 서로 다른 ADR 파일이 쓰면 충돌로 찍고 종료 코드 1 로 끝난다.
서로 다른 파일이란 파일 이름에서 번호를 뺀 `카테고리_기능` 이 다른 파일이다. 같은 파일의 번호 목록이 브랜치마다
다른 것(`ADR-011` 과 `ADR-011+138`)은 충돌이 아니다. `git fetch` 나 `gh` 가 실패하면 번호를 내지 않고 종료 코드 2
로 끝난다. 일부만 보고 고른 번호는 겹칠 수 있기 때문이다.

로컬 브랜치는 보지 않는다. 진행 중인 작업은 워크트리로 본다. main 에 이미 머지된 `release/*` · `hotfix/*` 도 보지
않는다. 그 번호는 main 이 이미 담고 있다. 게다가 문서 재작성(PR #659) 전에 딴 브랜치는 옛 번호를 써서, 보면 가장
큰 번호가 300 넘게 튄다. 2026-11-09 에 지운 `release/1.0.12` 셋이 그랬다.

쓰는 때는 둘이다.

- 새 번호가 필요하면 스크립트를 돌리고, 받은 번호로 곧바로 파일을 만든다. 파일이 워크트리에 있어야 다른 세션이 돌린
  스크립트가 그 번호를 본다.
- PR 을 머지하기 직전에 다시 돌려 종료 코드 0 을 확인한다. 핫픽스는 main 에 머지하기 전에 반드시 확인한다. main 에
  들어간 뒤에 겹친 것을 알면 이미 출시한 파일의 이름을 바꿔야 한다.

### 결정 9. 서버 저장소도 같은 전략을 쓴다

`maple-routine-server` 도 main 은 운영 박스에 배포된 것만 담고, GitHub 기본 브랜치는 develop 이다. 작업 브랜치와
핫픽스는 결정 3 · 4 · 6 · 7 과 같다.

서버에는 release 브랜치를 두지 않는다. 스토어 심사처럼 기다리는 기간이 없기 때문이다. 배포할 때는 develop 을 head,
main 을 base 로 PR 해 merge commit 으로 머지하고, main 에서 빌드한다.

서버의 결정 문서는 이 저장소 `docs/` 에 있다. 그래서 서버 작업의 ADR 번호도 결정 8 의 스크립트로 받는다.
