# ADR-056+072 알림 예약과 공지 구독

> 🟢 유효
> 옛 번호: ADR-004 · ADR-146 결정 1 · 2 · 5 · 6 · ADR-227 결정 5 · ADR-259 · ADR-278 · ADR-228 결정 2 · 3 · 정정 1 · 2 · ADR-247 결정 2 · 10 · 정정 1
> 관련 소스: `features/local-notifications/` · `features/notice/store.ts` · `features/notice/topics.ts` · `features/notice/permission-gate.ts` · `native/adapters/rn-notifications.ts` · `native/adapters/notification-request.ts` · `native/adapters/rn-push.ts` · `app/settings/SettingsNoticeAlertsScreen.tsx` · `index.ts` · `maple-routine-server` 의 `src/clients/fcm.client.ts`

## 배경

앱이 띄우는 알림은 두 종류다. 하나는 기기가 정한 시각에 스스로 띄우는 로컬 알림이고, 지금은 파티 약속
알림 하나뿐이다. 다른 하나는 서버가 보내는 공지 푸시다. 둘 다 스토어에 낸 바이너리 위에서 돌아야 하는데,
네이티브 코드에 들어간 것은 다음 스토어 심사 전까지 고칠 수 없다. 그래서 바이너리에는 알림을 띄우는 기능만
넣고, 무엇을 언제 띄울지는 모두 JS 에 두었다. JS 는 OTA 로 고칠 수 있기 때문이다.

공지 내용과 화면은 [[ADR-057]] 에 있다. 이 문서는 알림이 기기에 닿기까지의 규칙만 다룬다.

## 결정

### 결정 1. 바이너리에는 알림 기능 둘만 넣고, 정책은 JS 에 둔다

바이너리에 들어간 기능은 로컬 알림(`@notifee/react-native`)과 원격 푸시(`@react-native-firebase/messaging`)
둘이다. 알림 종류 · 문구 · 시각 · 채널 선택 · 구독할 토픽 이름은 모두 JS 에 있다. 네이티브에 적으면 OTA 로
바꿀 수 없기 때문이다.

다만 `index.ts` 최상위에서 등록하는 두 줄은 위치가 정해져 있다. `setBackgroundMessageHandler` 와
`notifee.onBackgroundEvent` 는 모듈 최상위에 있어야 OS 가 꺼진 앱을 깨울 때 이 핸들러를 찾는다. 나중에
OTA 로 등록을 추가하면 OS 가 그 핸들러를 모른다. 그래서 핸들러 몸통이 비어 있어도 등록은 미리 넣어 두었다.

### 결정 2. 로컬 알림은 레지스트리와 원장으로 예약한다

OS 는 예약해 둔 알림 목록을 앱에 주지 않는다. 그래서 앱이 직접 기억한다.

- **레지스트리**(`registry.ts` 의 `NOTIFICATION_KINDS`): 알림 종류 하나가 한 줄이다. 각 종류에는 지금 예약해야 할
  알림 목록을 돌려주는 `plan(now)` 이 있다.
- **원장**(Preferences `notificationLedger`): 지금 예약해 둔 알림의 `{ id, kind, fireAt, title, body }` 목록이다.
- **재조정**(`planReconcile`): 계획과 원장을 비교한다. 원장에만 있으면 취소하고, 계획에만 있으면 예약한다.
  둘 다 있고 시각과 문구가 같으면 아무것도 하지 않는다. 시각이 같아도 문구가 바뀌면 다시 예약한다.

레지스트리에서 빠진 종류가 원장에 남아 있으면 무조건 취소한다. OTA 로 알림 종류를 지웠을 때 그 예약이
OS 에 남아 계속 울리는 것을 막으려고 원장을 둔 것이다.

알림 id 는 `(종류, 범위, 회차)` 를 32비트 FNV-1a 로 해시한 양의 정수다(`notificationId`). 같은 회차는 몇 번을
계획해도 같은 id 가 나오므로, 다시 예약하면 OS 가 덮어쓴다. 그래서 재조정을 몇 번 돌려도 결과가 같다.

원장은 예약과 취소가 끝난 뒤에 쓴다. 중간에 앱이 죽으면 다음 재조정이 같은 id 로 다시 예약하고, 덮어쓰기일
뿐이라 안전하다. 예약에 실패한 것은 원장에 적지 않아 다음에 다시 시도한다. 취소에 실패한 것은 원장에
남겨 다음에 다시 취소한다. 원장을 먼저 쓰면 앱이 죽은 뒤 원장이 예약했다고 기록하고 있어 다시 예약할
기회가 없어진다.

원장은 데이터 삭제 대상이 아니다. 지우면 OS 에 남은 예약을 찾을 방법이 없다.

### 결정 3. 울릴 시각 순으로 앞 64개만 예약하고, 앱을 켤 때마다 다시 채운다

iOS 는 앱 하나당 가장 가까운 64개 예약만 남기고 나머지는 말없이 버린다. 그래서 재조정은 울릴 시각 순으로
앞 64개(`SCHEDULE_SLOTS`)만 예약하고, 범위를 벗어난 원장 항목은 취소한다.

iOS 는 로컬 알림이 울려도 앱을 깨우지 않는다. 그래서 아래 시점마다 남은 알림을 다시 채운다.

| 언제 | 부르는 곳 |
|---|---|
| 앱을 켤 때 | `AppShell` |
| 백그라운드에서 포그라운드로 돌아올 때 | `AppShell` 의 `useReturnToForeground` |
| 파티 약속을 저장하거나 지울 때 | `features/party-appointments/query.ts` 의 `savePartyAppointments` |
| 파티 스케줄 알림 스위치를 바꿀 때 | `features/party-appointments/alarm-settings.ts` |

알림 권한이 없으면 계획을 빈 목록으로 보고, 원장에 있는 예약을 모두 취소한다. 권한이 다시 생기면 다음
재조정이 되살린다.

재조정이 도는 중에 또 요청이 오면 끝난 뒤 한 번 더 돈다(`requestNotificationReconcile`). 둘이 동시에 돌면
서로 원장을 덮어써 예약을 잃는다. 재조정의 실패는 알리지 않는다. 다음 재조정이 같은 계획으로 다시 하기
때문이다.

### 결정 4. 안드로이드 채널은 옛 `default` 와 파티 약속용 `party` 둘이다

안드로이드 채널은 한 번 만들면 앱이 이름과 중요도를 바꿀 수 없다. 그래서 값을 정할 때 신중해야 한다.

| 채널 id | 이름 | 중요도 | 쓰는 곳 |
|---|---|---|---|
| `default` | `Default` | `DEFAULT` | 채널을 고르지 않은 로컬 알림 |
| `party` | `파티 스케줄` | `HIGH` | 파티 약속 알림 |

`default` 는 Capacitor 시절 채널 id 를 그대로 쓴다. 새 id 를 만들면 사용자 알림 설정에 채널이 하나 더 생긴다.
`party` 는 약속 시각이 지나면 쓸모가 없어 화면 위에 뜨는 `HIGH` 로 했다.

두 채널 모두 `sound: 'default'` 를 명시한다. notifee 는 소리를 지정하지 않으면 무음 채널을 만든다.

채널은 예약할 때마다 `createChannel` 로 만든다. 이미 있으면 설정을 바꾸지 않으므로 여러 번 불러도 된다.
채널을 만들었는지 기억하는 상태를 두지 않은 이유는, 그 상태가 실제와 어긋나면 알림이 아무 표시 없이
사라지기 때문이다.

공지 푸시용 채널은 만들지 않았다. 그래서 공지 푸시는 FCM 기본 채널(`fcm_fallback_notification_channel`)로 뜬다.

### 결정 5. 로컬 알림 예약은 잘못된 요청을 네이티브에 넘기기 전에 막는다

`toTriggerNotification` 은 지난 시각이나 `Invalid Date` 를 받으면 예외를 던진다. 지난 시각을 즉시 띄우지 않는
이유는 앱을 켤 때마다 재예약하기 때문이다. 시계가 조금만 어긋나도 재예약 한 번에 알림이 한꺼번에 쏟아진다.

id 는 `String(id)` 로 바꿔 notifee 에 넘긴다. 정수가 아니면 예외를 던진다. `String(NaN)` 은 `'NaN'` 이 되어
다시 숫자로 돌아오지 않고, 그러면 취소할 수 없는 알림이 생긴다. 예약과 취소는 같은 `toNotificationId` 를 쓴다.

취소에는 `cancelNotification` 을 쓴다. 이 함수가 예약 취소와 이미 떠 있는 알림 내리기를 함께 하기 때문이다.

### 결정 6. 로컬 알림을 탭하면 종류에 맞는 화면을 연다

탭을 받는 경우는 셋이다.

| 앱 상태 | 받는 곳 |
|---|---|
| 포그라운드에 있을 때 | `notifee.onForegroundEvent` |
| 백그라운드에 있을 때 | `index.ts` 의 `onBackgroundEvent`. 화면이 리스너를 달기 전에 오면 쌓아 두었다가 리스너를 달 때 넘긴다 |
| 꺼져 있다가 탭으로 열렸을 때 | `getInitialNotification`. 한 번만 답한다 |

`useLocalNotificationPress` 가 셋을 모아 종류를 구분한다. 지금은 종류가 파티 약속 하나뿐이라, 알림을 누르면 그 약속을 연다.
iOS 는 꺼진 앱을 탭으로 열 때 같은 탭을 두 경로로 보내므로, 같은 약속의 같은 회차는 한 번만 연다.

### 결정 7. 공지 알림은 FCM 토픽 푸시이고, 등록 토큰은 앱 밖으로 내보내지 않는다

기기는 토픽을 구독하고 해제하기만 한다(`PushPort` 의 `subscribe` · `unsubscribe`). 등록 토큰을 서버에 보내지
않으므로 서버에 사용자 식별자 저장소가 생기지 않고, 만료 정리나 개인정보 분류도 필요 없다. 무엇을 언제
보낼지는 서버가 정한다.

발송은 자체 호스팅 서버(`maple-routine-server`)가 한다. 서버는 FCM 에 토픽 이름만 넣어 보내고, 넥슨 공지 목록은
서버 자신의 키(`NEXON_KEY`)로 받는다. 사용자의 API 키는 알림 발송에 쓰이지 않는다. 사용자마다 다른 알림(지금은 파티
약속)은 서버가 보내지 않고 기기가 예약한다(결정 2). 서버가 사용자별로 판단해 보내려면 등록 토큰과 개인 기록이 서버에
있어야 하는데, 지금 보내는 공지 알림은 대상을 사용자별로 고를 필요가 없다.

알림 문구는 서버가 만들어 `notification` 페이로드에 싣는다. data 만 보내면 앱이 꺼져 있을 때 iOS 가 배달을
보장하지 않기 때문이다. 서버는 심사 없이 바로 고칠 수 있으므로 문구를 서버에 두어도 된다.

iOS 에서는 토픽을 구독하거나 해제하기 전에 APNs 토큰이 올 때까지 기다린다(`waitForApnsToken`). 구독은 FCM
토큰을 쓰고, FCM 토큰은 APNs 토큰이 있어야 나온다. APNs 등록은 앱이 뜰 때 시작해 비동기로 끝나므로, 그 전에
스위치를 누르면 구독이 실패한다. 250ms 간격으로 5초까지 확인하고, 그래도 없으면 `기기가 알림 서버에 아직
등록되지 않았어요. 잠시 뒤 다시 시도해 주세요` 로 실패한다. 안드로이드는 기다리지 않는다.

### 결정 8. 공지 분류 하나가 스위치 하나이고 토픽 하나다

| 스위치 | 토픽 | 분류 | 권한을 허용하면 |
|---|---|---|---|
| 앱 공지 사항 | `notice` | `app` | 켬 |
| 게임 공지 사항 | `notice-game` | `game` | 켬 |
| 썬데이 메이플 | `notice-event` | `event` | 켬 |
| 게임 업데이트 안내 | `notice-update` | `update` | 꺼둠 |
| 캐시 아이템 업데이트 | `notice-cashshop` | `cashshop` | 꺼둠 |

토픽 이름은 서버(`maple-routine-server` 의 `src/modules/push/push-text.ts` 의 `TOPIC_BY_KIND`)와 같아야 한다.
한쪽만 바꾸면 구독자가 없는 토픽으로 발송되고, 알림이 안 온다는 것 말고는 아무 흔적도 남지 않는다.

`notice` 는 바꿀 수 없다. 스위치가 하나였던 때 스토어에 나간 바이너리가 이 토픽을 구독하고 있어서, 이름을
게임 공지로 돌리면 업데이트하지 않은 기기가 켠 적 없는 알림을 받는다. 같은 이유로 그때 저장한 값
(`noticeSubscribed`)을 앱 공지 스위치가 이어받는다. 새 값(`noticeSubscriptions`)이 없을 때만 옛 값에서 앱 공지를
읽으므로 따로 옮기는 코드가 없다. 앱 공지를 저장할 때는 옛 키에도 함께 적는다. OTA 를 되돌려 옛 코드가 돌아도
같은 값을 읽게 하기 위해서다.

이벤트 토픽으로는 썬데이 메이플만 나간다([[ADR-057]] 결정 11). 그래서 스위치 이름이 `썬데이 메이플` 이다.

권한을 허용해도 다섯을 모두 켜지는 않는다. 업데이트와 캐시샵 공지는 패치 날 한꺼번에 올라오기 때문이다.
8월 20일 8시 14분에 이벤트 5건과 캐시샵 4건이 같은 분에 올라온 적이 있다. 묻지 않고 켜 두면 그날 알림이
여러 번 울리고, 사용자가 알림을 통째로 끌 수 있다. 점검 안내와 썬데이 메이플은 늦게 알면 소용이 없어서 켠다.

구독 값과 권한을 물었는지는 데이터 삭제 대상이 아니다. 구독 값이 지워지면 FCM 쪽 구독은 남아 있는데
앱은 껐다고 알고 있어, 스위치는 꺼져 있는데 알림이 온다.

### 결정 9. 알림 권한은 캐릭터를 고른 직후와 스위치를 켤 때 묻는다

iOS 는 한 번 거부하면 다시 물을 수 없다. 두 번째부터는 시스템 팝업이 뜨지 않아 설정 앱으로 보내는 수밖에
없다. 그래서 언제 묻는지가 중요하다. 앱을 켜자마자 묻지 않는다.

**캐릭터를 고른 직후 한 번 묻는다**(`askNotificationPermissionOnce`). 온보딩의 `completeCharacterSetup` 과 캐릭터
관리의 `saveTrackedOcids` 둘 다 부른다. 이미 물었으면 다시 묻지 않으므로 팝업은 한 번만 뜬다. 캐릭터를 고르는
시점은 사용자가 이 앱을 실제로 쓰기 시작하는 때라, 처음 켰을 때 맥락 없이 묻는 것보다 낫다. 허용하면 결정 8 의
기본 셋까지 켠다. 이 함수는 예외를 던지지 않는다. 캐릭터 저장 흐름 안에서 불리므로, 던지면 캐릭터가 저장되지
않은 것처럼 보인다.

**스위치를 켤 때도 묻는다.** 켜는 경우는 셋으로 나뉜다.

| 상태 | 스위치를 켜면 |
|---|---|
| 권한 있음 | 바로 구독한다 |
| 한 번도 묻지 않음 | 바로 묻고, 허용하면 구독한다 |
| 물었고 거부함 | 구독하지 않고 `기기에서 알림이 꺼져 있어요` 카드를 띄운다 |

가운데 경우가 없으면 이미 캐릭터를 고른 사용자는 팝업을 볼 기회가 없다. 게다가 iOS 는 한 번도 묻지 않은
앱의 알림 항목을 설정 앱에 만들지 않아서, 설정 앱으로 보내도 켤 항목이 없다.

어느 경우든 묻기 전에 물었다고 먼저 적는다(`notificationPermissionAsked`). 팝업은 뜨는 순간 기회가 소모되므로,
뒤에 적으면 그 사이 앱이 죽었을 때 다시 묻게 되고 팝업은 뜨지 않는다. 물었는지를 OS 에 묻지 않고 앱이
기억하는 이유는, 안드로이드의 `denied` 가 거부와 아직 묻지 않음을 구분하지 못하는 경우가 있기 때문이다.

끌 때는 권한을 보지 않는다. 권한이 없다고 끄기를 막으면 사용자가 구독을 해제할 수 없다.

### 결정 10. 구독은 성공한 뒤에만 저장한다

FCM 구독이 실패했는데 켜졌다고 저장하면 스위치는 켜져 있고 알림은 오지 않는다. 화면만 보고는 그 상태를
알아챌 수 없다. 그래서 `subscriptions` 는 구독이나 해제가 성공한 뒤에만 바뀐다. 한 스위치가 실패해도 다른
스위치의 저장 값은 그대로다.

### 결정 11. 스위치 요청은 스토어의 대기열 하나에서 차례로 돌고, 누른 값은 바로 그린다

구독은 FCM 왕복이라 몇 초가 걸릴 수 있다. 그 사이 다른 스위치를 눌러도 반응해야 한다.

- 누르면 그 분류의 `pending` 에 누른 값이 바로 적힌다. 화면은 `{ ...subscriptions, ...pending }` 을 그린다.
- 요청은 `store.ts` 의 대기열(`queue`)에 들어가 한 번에 하나씩 돈다. 다섯 스위치가 같은 저장 값을 고쳐 쓰므로,
  둘이 동시에 돌면 늦게 끝난 쪽이 먼저 끝난 쪽의 결과를 덮는다.
- 요청은 대기열에 들어갈 때가 아니라 차례가 왔을 때 `pending` 을 읽는다. 저장된 값과 같으면 서버에 보내지 않는다. 그래서
  켜기, 끄기, 켜기를 빠르게 누르면 구독은 한 번만 나간다.
- 요청이 끝나면 `pending` 이 그 요청의 값과 같을 때만 지운다. 도는 사이 같은 스위치를 또 눌렀으면 그 값은 남아
  뒤의 요청이 처리한다.
- 실패하면 그 분류의 `pending` 만 지워져 저장된 값으로 돌아간다. 화면은 실패 카드에 마지막 실패 이유를 적는다.
- 전체 스위치는 분류마다 요청 하나를 같은 대기열에 넣는다. 끄면 다섯 모두, 켜면 결정 8 의 기본 셋이다. 저장된 값과
  같은 분류는 보내지 않으므로, 켠 적 없는 토픽을 해제하지 않는다.

대기열이 모듈에 하나라서, 테스트가 끝나지 않은 왕복을 남기면 다음 테스트의 요청이 그 뒤에서 기다린다. 테스트는
연 왕복을 모두 닫아야 한다.

### 결정 12. 앱을 켤 때와 포그라운드로 돌아올 때 켜 둔 토픽을 다시 구독한다

토픽 구독은 FCM 등록 토큰에 묶여 있다. 재설치 · 백업 복원 · 토큰 교체를 겪으면 새 토큰에는 구독이 없는데
저장 값은 켜짐으로 남는다. 앱은 어느 토픽을 구독했는지 FCM 에 물을 수 없으므로(서버 키가 필요하다), 다시
보내는 것 말고는 방법이 없다.

- `AppShell` 이 구독 값을 복원한 뒤 한 번, 그리고 백그라운드에서 `active` 로 돌아올 때마다 `resubscribe` 를 부른다.
  `inactive` 에서 돌아올 때는 부르지 않는다. iOS 에서 알림 센터나 시스템 팝업이 닫힐 때 그렇게 바뀌는데,
  그때는 앱이 백그라운드로 간 적이 없다.
- 저장 값이 켜짐인 토픽에만 `subscribe` 를 보낸다. 꺼짐인 토픽은 해제가 성공한 뒤에만 저장되므로 보낼 것이 없다.
- 알림 권한이 있을 때만 보내고, 권한을 묻지는 않는다. 사용자가 OS 설정에서 권한을 켜고 돌아오면 그때 구독이
  맞춰진다.
- 등록 토큰을 저장하지도 비교하지도 않는다. 대신 부를 때마다 켠 토픽 수만큼 FCM 왕복이 나간다.
- 스위치 요청과 같은 대기열에서 돌고, 저장 값은 차례가 왔을 때 읽는다. 앱을 켠 직후 사용자가 스위치를 끄면
  해제와 재구독이 겹치는데, 대기열에 들어갈 때 읽으면 방금 끈 토픽을 다시 구독한다.
- 대기열에서 기다리는 재구독이 있으면 새 요청은 거기에 합친다. 이미 도는 중이면 뒤에 하나를 더 넣는다. 이미 도는 요청은
  권한을 벌써 읽었을 수 있어서, 그 사이에 켠 권한은 뒤의 요청이 확인한다.
- 실패는 알리지 않는다. 한 분류가 실패해도 다음 분류로 넘어가고, 다음에 부를 때 다시 보낸다.

### 결정 13. 알림 설정 화면은 앱 안의 구독과 기기의 권한을 함께 보여 준다

`더보기 > 설정 > 알림 설정`(`SettingsNoticeAlertsScreen`) 화면이다.

- **전체 스위치**(`알림 받기`)는 저장하지 않고 계산한다. 공지 스위치 하나라도 켜져 있거나 파티 스케줄 알림이
  켜져 있으면 켜짐이다. 따로 저장하면 전체는 켜짐인데 하위는 모두 꺼진 상태가 생겨, 스위치는 켜져 있는데 알림은
  오지 않는다. 전체가 꺼져 있으면 하위 스위치를 그리지 않는다. 전체를 누르면 공지 스위치와 파티 스케줄 알림을
  함께 켜거나 끈다.
- **머리의 `기기 설정` 버튼**은 늘 보인다. 기기 쪽에서 알림이나 채널을 바꾸려는 사용자를 위한 버튼이다.
  안드로이드는 `APP_NOTIFICATION_SETTINGS` 인텐트로 앱의 알림 설정을 바로 연다. `openSettings()` 는 앱 정보
  화면까지만 열어서 한 번 더 눌러야 알림이 나오기 때문이다. iOS 는 앱별 알림 설정을 바로 여는 공개 API 가 없어
  `openSettings()` 로 앱 설정을 연다.
- **`기기에서 알림이 꺼져 있어요` 카드**는 켜려다 권한에 막혔거나, 켜 둔 것이 있는데 기기 권한이 없을 때 뜬다.
  화면에 들어올 때마다 권한을 읽는다(묻지는 않는다). 켜 둔 것이 없으면 띄우지 않는다. 알림을 쓰지 않기로 한
  사용자에게는 잔소리이고, 한 번도 묻지 않은 iOS 앱은 설정 앱에 항목도 없기 때문이다. 권한을 아직 읽지 못했을
  때도 띄우지 않는다. 알림이 켜진 기기를 꺼졌다고 잘못 알리게 된다.
- **`알림을 켜지 못했어요` 카드**는 스위치 요청이 실패한 이유를 그대로 적는다. 알리지 않으면 사용자는 스위치가
  반응하지 않는다고 느낀다.
- **스케줄러 구역**에는 파티 스케줄 알림 스위치가 있고, 그 아래 `미완료 스케줄 알림` · `주간 결산 알림` 은 스위치
  대신 `준비 중` 을 적는다. 켤 수 없는 스위치를 그려 두면 눌러 본 뒤에야 쓸 수 없다는 것을 알게 된다.

### 결정 14. iOS 알림은 로컬 알림과 공지 푸시 모두 소리를 명시한다

iOS 는 알림에 소리가 없으면 무음 알림으로 띄운다. 애플워치는 아이폰 알림을 받아 오지만, 무음 알림은 손목을
울리지 않고 워치 알림 센터에만 쌓인다. 그래서 사용자는 알림이 오지 않았다고 느낀다(2026-10-20 실기기 관측).

- 로컬 알림은 `toTriggerNotification` 이 `ios: { sound: 'default' }` 를 싣는다. notifee 는 iOS 에서 소리를 지정하지
  않으면 무음으로 보낸다. 안드로이드는 결정 4 의 채널이 소리를 정하므로 여기서 따로 싣지 않는다.
- 공지 푸시는 서버의 `FcmClient.send` 가 모든 메시지에 `apns.payload.aps.sound: 'default'` 를 싣는다. FCM 의
  `notification` 페이로드만으로는 APNs 에 소리가 들어가지 않는다. 발송하는 곳이 이 함수 하나라 여기서 붙인다.

소리를 넣으면 아이폰에서도 알림음이 난다. 무음 모드에서는 진동만 난다. 워치 진동만 따로 켜는 방법은 없다.
