# ADR-341: 게임 수치 데이터의 진실은 서버로 옮긴다. 앱은 캐시하고 번들 사본으로 버틴다

> ⚪ 미구현 · 2026-10-08 · 설계 · 사용자 지정

> 사용자 지정(2026-10-08): 앱 내부 `src/data` 의 constant JSON 중 **게임 수치와 목록**을 서버로
> 옮기고 서버의 값이 진실이다. 앱은 이 값을 캐시해 두고 쓴다. `src/data` 의 모든 값을 옮기는 것은
> 아니다.

**관련**: [[ADR-006]](게임 수치는 AI 가 추정하지 않고 사용자 확인을 거친다. 그 절차가 서버로 함께
간다) · [[ADR-227]](서버를 들인 결정) · [[ADR-229]](결정 6 - 서버 조회 실패를 화면의 실패로 안
만든다) · [[ADR-277]](서버가 기준이고 기기는 마지막 응답의 사본을 든다는 선례) · [[ADR-129]](에셋
목록이 생성물이고 번들에 있다. 이 결정이 **넘지 못하는 선**이다) · [[ADR-340]](서버 쪽 사람 표)

## 맥락

### 지금은 게임 패치가 앱 배포를 요구한다

`src/data/*.json` 이 앱 번들에 정적으로 들어간다. 그래서 넥슨이 결정석 가격이나 드롭 테이블을
바꾸면 **값 한 줄을 고치려고 OTA 를 낸다.** 실제로 그래 왔다(이슈 #360 의 09-17 패치 · #615 강화 비용
재계산).

서버가 진실이면 서버 값만 고치면 되고 앱 배포가 없다. **이것이 이 결정의 이득 전부다.**

### 옮기는 것은 16개다

22개 JSON 중 게임 수치와 목록만 간다. 합쳐서 392KB 다.

| 묶음 | 파일 | 간다 |
|---|---|---|
| 게임 수치 · 목록 | `boss-crystal-prices` · `weekly-bosses` · `item-drop-table` · `drop-items` · `equipment-items` · `enhancement-prices` · `symbol-costs` · `hunting-grounds` · `mvp-grades` · `valuable-drops` · `accessory-boxes` · `boss-ring-boxes` · `worlds` · `scheduler-content-catalog` · `scheduler-content-template` · `spend-catalog` | **간다** |
| 번들 그림의 좌표 | `boss-portrait-crops` · `boss-portrait-icon-crops` · `boss-portrait-modal-crops` · `daily-quest-region-crops` | 안 간다 |
| 테마 | `job-themes` | 안 간다 |
| 앱 콘텐츠 | `release-notes.ts` · `feature-guides/` | 안 간다 |

**안 가는 여섯은 번들 파일에 묶여 있다.** 좌표는 번들 그림을 자르는 값이고, 테마는
`src/assets/themes/` 를, 안내는 `src/assets/guide/<안내 id>/` 를 가리킨다. 그림은 번들에 있어
스토어와 OTA 를 타므로, 그것을 가리키는 값만 서버에서 먼저 바뀌면 **없는 그림을 가리키거나 엉뚱한
자리를 자른다.**

### 값이 지금은 모듈 로드 시점에 굳는다

16개를 직접 `import` 하는 모듈이 18곳이고 **거의 전부 `lib/` 에 있다.** 화면과 기능은 JSON 을 직접
안 읽고 그 모듈의 조회 함수를 쓴다. 그 층이 이미 있어서 바꿀 자리가 좁다.

그런데 그 모듈들이 값을 `export const` 로 낸다(다섯 모듈에 10개). `lib/boss/bosses.ts` 가 그렇다.

```ts
export const BOSS_ENTRIES: readonly BossEntry[] = [ … ]   // import 되는 순간 만들어진다
export const WEEKLY_BOSS_CLEAR_LIMIT: number = weeklyBossesData.weeklyBossSelectionLimit
export function findBoss(key: string | null | undefined): BossEntry | null { … }  // 동기
```

`export const` 는 **그 모듈이 처음 import 되는 순간 값이 정해진다.** 서버에서 받아 채우려면 상수가
함수가 되거나, 부팅이 캐시를 채운 뒤에만 이 모듈이 읽히도록 보장해야 한다.

## 결정

### 결정 1. 게임 수치와 목록 16개만 옮긴다. 진실은 서버다 (사용자 지정)

맥락의 표가 범위다. 앱은 서버 값을 캐시해 두고 쓴다. 값이 갈리면 서버가 이긴다([[ADR-277]] 의
선례와 같다).

### 결정 2. 번들 사본은 남고 폴백이 된다

서버가 안 열려도 앱은 서야 한다([[ADR-229]] 결정 6). 게임 데이터는 **없으면 아무 화면도 못 그리는**
값이라 그 원칙이 공지보다 세게 걸린다. 그래서 16개 JSON 은 번들에 그대로 남는다.

즉 실제 모양은 `전부 서버로 옮긴다` 가 아니라 **`서버가 진실이고 번들이 폴백`** 이다. 두 벌이
유지되고, 읽는 순서는 캐시 → 서버 → 번들이다.

**번들 사본은 묶인 시점의 값이다.** 오래된 앱을 켠 기기는 서버에 닿기 전까지 그때의 값으로 그린다.

### 결정 3. 정합성 검사는 서버에도 있어야 한다

지금 `src/data/__tests__` 에 17개 스위트가 있고 `data-consistency.spec.ts` 가 파일 사이를 대조한다.
`weekly-bosses` 의 모든 보스와 난이도가 `boss-crystal-prices` 에 있는지, `item-drop-table` 이
`weekly-bosses` 에 없는 조합을 쓰지 않는지, `priceMeso` 가 `null` 인 항목이 전부
`status: unreleased` 인지를 본다.

**그 검사가 앱에만 남으면 서버에 어긋난 값이 들어가도 아무도 안 잡고, 그 값이 전 사용자에게
나간다.** 앱 쪽 검사는 번들 폴백을 지키므로 남기고, 같은 검사를 서버 입력 경로에도 둔다.

[[ADR-006]] 의 절차도 함께 간다. 값은 AI 가 추정하지 않고 사용자 확인을 거치는데, 그 확인이 이제
서버 입력에서 일어난다.

## 대가

- **그림은 안 따라온다.** [[ADR-129]] 가 에셋 목록을 생성물(`src/assets/generated/*.ts`)로 두고 그
  목록이 번들에 있는 그림이다. 서버가 새 아이템 key 를 보내도 번들에 그림이 없으면 **에러 없이
  폴백만 그린다.** 그래서 새 보스를 서버에서 더하면 이름과 가격은 나오고 **그림은 안 나온다.**
  데이터와 그림의 배포 축이 갈린다.
- **`export const` 를 쓰는 소비자가 바뀐다.** `BOSS_ENTRIES` 2곳 · `WEEKLY_BOSS_CLEAR_LIMIT` 6곳 ·
  `WEEKLY_CRYSTAL_SALE_LIMIT` 4곳이다. 상수를 함수로 바꾸면 그 자리가 전부 호출이 된다.
- **부팅 순서가 새 제약이 된다.** 캐시를 채우기 전에 조회 함수가 불리면 폴백 값이 나간다. 지금은
  그런 순서 문제가 없다.
- **두 벌이 유지된다.** 결정 2 가 번들 사본을 남기므로 값이 두 자리에 있다. 번들 사본을 언제
  갱신하는지가 운영 일이 된다.
- **서버가 전 사용자의 화면을 쥔다.** 잘못된 값 하나가 즉시 전원에게 나간다. 지금은 OTA 를 거쳐
  그만큼 늦게 나가고 되돌릴 수 있다.
- **데이터 안전 신고 범위는 안 바뀐다.** 내려주는 값이고 올리는 값이 아니다.

## 기각

- **`src/data` 전부를 옮긴다.** 번들 그림에 묶인 여섯이 끊긴다. 사용자 지정으로 기각했다(결정 1).
- **번들 사본을 걷고 서버만 본다.** 서버가 안 열리면 앱이 한 화면도 못 그린다. [[ADR-229]] 결정 6 과
  정면으로 어긋난다(결정 2).
- **그림도 서버에서 받는다.** 이 결정의 제약을 없애지만 에셋 파이프라인([[ADR-129]])과 캐시 · 용량 ·
  오프라인이 전부 걸리는 별개의 큰 작업이다. 여기서 안 다룬다.

## 열린 질문

착수 전에 답한다.

- **캐시의 단위.** 16개를 한 덩어리로 받을지 파일마다 받을지. 전부면 392KB 인데 자주 바뀌는 것은
  몇 개뿐이다.
- **무효화를 무엇으로.** 버전 하나로 전체를 가는 길과 파일마다 버전을 두는 길이 있다. 앱이 매번
  전체를 받으면 켤 때마다 392KB 다.
- **언제 받나.** 부팅마다 볼지, 주기로 볼지, 공지처럼 화면이 열릴 때 볼지. 부팅 순서 제약(대가)이
  여기 걸린다.
- **상수를 함수로 바꾸나.** `export const` 10개를 함수로 바꾸는 길과, 부팅이 캐시를 채운 뒤에만
  모듈이 읽히도록 보장하는 길이 있다. 뒤쪽은 보장을 테스트로 지키기 어렵다.
- **값을 누가 넣나.** 운영자 화면 · 시드 스크립트 · 마이그레이션 중 어느 것인가. [[ADR-006]] 의
  사용자 확인이 그 자리에서 일어난다.
- **번들 사본을 언제 갱신하나.** 서버에서 값을 고친 뒤 번들 사본을 그대로 두면 둘이 벌어진다. 스토어
  빌드마다 맞출지, 따로 스크립트로 내릴지.
- **옛 앱이 새 스키마를 만났을 때.** 서버가 칸을 더한 값을 내려주면 옛 앱이 그것을 읽는다. 공지의
  `kind` 가 쓰는 방식(모르는 값은 기본값으로 읽는다)을 여기도 쓸지.
