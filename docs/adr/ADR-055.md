### ADR-055: 수동 선택 가드 — 주간 보스 12개 한도(#62) (구현 완료). 요구 레벨 미달 잠금(#32)은 정정 2로 폐기

> **먼저 읽을 것**: 아래 본문은 **#32(요구 레벨 잠금)와 #62(12개 한도)를 함께 설계했던 원안**이다. #32는 2026-07-29 사용자 결정으로 **폐기**됐고(레벨 미달이어도 자유롭게 선택), 지금 코드에 살아 있는 것은 **#62뿐**이다. 무엇이 남고 무엇이 걷혔는지는 맨 아래 **정정 2**를 볼 것 — 원안을 지우지 않고 남기는 이유는 정정 1(표기 방식)과 [[ADR-057]](길드 잠금)이 이 구조 위에 서 있기 때문이다.

**배경**: 두 이슈는 요구사항 문장이 전혀 달라 보이지만, 코드에서는 같은 질문 하나로 수렴한다 — **"이 항목을 지금 이 캐릭터가 선택할 수 있는가, 없다면 왜인가."**

| 이슈 | 막는 조건 | 데이터 |
|---|---|---|
| #32 | 캐릭터 레벨 < 항목 요구 레벨 | **없음** — 요구 레벨 필드가 어느 참조 파일에도 없다 |
| #62 | 주간 보스 선택 수 ≥ 12 | **있음** — `weeklyBossSelectionLimit: 12` |

둘 다 같은 세 지점을 건드린다: (1) 스토어의 추가 경로(`addManualBoss`/`addManualContent`), (2) 관리 화면 토글의 사전 차단(`handleToggleTracked`/`handleToggle`), (3) 행의 비활성 표현(흐리게 + 사유 표시). 따로 처리하면 먼저 하는 쪽이 "잠김이다/아니다" boolean 구조를 만들고, 나중 쪽이 사유가 둘로 늘면서 그 구조를 갈아엎는다. 같은 자리를 두 번 고치는 대신 처음부터 **사유(reason)를 가진 단일 가드**로 설계한다.

묶는 근거가 하나 더 있다. #62의 12 한도·시즌 보스 제외 규칙은 [[ADR-031]] 결정 1(`countClearedWeeklyBosses`)·[[ADR-054]] 결정 3(`isSeasonBossName`)과 **같은 규칙**인데, 보스 관리 화면의 `BOSSES_BY_TAB`(`BossManageScreen.tsx:25-42`)은 `weekly`와 `eventWeekly`를 합치면서 **출처 구분을 잃는다**. 화면마다 규칙을 다시 해석하는 것을 막는 게 이번 결정의 절반이다.

요구 레벨 수치는 아직 하나도 확정되지 않았다 — 값은 사용자(도메인 전문가)만 채운다([[ADR-006]]). 아래 결정 중 AI가 정한 것은 **구조**뿐이고, 데이터 단위(결정 4)·기존 사용자 처리(결정 10)는 2026-07-29 사용자 확정분이다.

**결정**:

1. **"선택 불가"를 boolean 두 개가 아니라 사유 하나로 모델링한다.**

   ```ts
   type SelectionBlock =
     | { reason: 'levelLocked'; requiredLevel: number }
     | { reason: 'limitReached'; limit: number }
   ```

   한 항목이 두 조건에 동시에 걸릴 수 있으므로 **표시 우선순위를 고정한다: `levelLocked` > `limitReached`.** 레벨 미달은 그 항목의 고유 속성이라 사용자가 이 화면에서 풀 방법이 없고, 한도는 다른 항목을 해제하면 풀리는 상태 의존이다. 풀 수 없는 이유를 먼저 알려야 사용자가 헛수고를 하지 않는다.

2. **가드의 본체는 스토어, UI는 사전 차단이다.** `addManualBoss`/`addManualContent`가 스스로 거부하고 결과를 알린다 — 반환 타입을 `Promise<void>` → `Promise<'added' | 'duplicate' | 'levelLocked' | 'limitReached'>` 로 바꾼다. UI에서만 막으면 다른 호출 경로가 그대로 새어나간다. 실제로 새는 경로가 이미 있다: **`handleSwitchDifficulty`는 remove → add 순서**라 한도에는 안 걸리지만 **잠긴 난이도로 교체**할 수 있다.

3. **12 한도의 카운트 규칙을 `lib/boss-matching` 에 한 번만 정의한다.** `countManualWeeklyBosses(items)` 를 신설한다 — `kind === 'boss'` **그리고** 주기가 주간 **그리고** 시즌 보스가 아닌 항목만 센다. 주기 판정을 위해 `REFERENCE_ENTRIES` 가 이미 갖고 있는 출처 정보를 `getBossCycleByName(bossName)` 으로 export 하고, `isSeasonBossName`([[ADR-054]] 결정 3) 옆에 나란히 둔다. 화면이 `BOSSES_BY_TAB` 으로 잃어버린 구분을 데이터 소스에서 되찾는 것이다.
   - **월간 탭(검은마법사)에는 한도가 없다.** 12는 주간 한도다. 카운터도 차단도 주간 탭에서만 건다. 그런데 월간 보스도 같은 `manualTrackedContent:{ocid}` 배열에 `kind: 'boss'` 로 저장되므로, **`kind` 만으로 세면 검은마법사가 주간 12에 포함돼 버린다** — 주기 판정이 필요한 이유가 이것이다.
   - **시즌 보스(메이린)는 카운트에서 뺀다.** `countClearedWeeklyBosses` 와 같은 규칙이어야 한다. 어긋나면 선택은 `12/12` 인데 처치 카운트는 `11/12` 로 표시되는 모순이 생긴다.

4. **요구 레벨은 (보스, 난이도)별로 보관한다** (사용자 확정 2026-07-29 — 게임의 입장 요구 레벨이 난이도마다 다르다).

   ```jsonc
   // weekly-bosses.json — difficulties 옆에 requiredLevels 맵 추가
   { "boss": "스우", "difficulties": ["노멀", "하드", "익스트림"],
     "requiredLevels": { "노멀": 190, "하드": 190, "익스트림": 275 } }   // 값은 예시(미확정)
   ```

   컨텐츠는 난이도 개념이 없으므로 `scheduler-content-template.json` 엔트리에 **단일 값** `requiredLevel: number` 를 둔다. 조회와 판정은 `lib/required-level.ts` 한 곳에 모은다(`getBossRequiredLevel(boss, difficulty)` · `getContentRequiredLevel(contentName)` · `isLevelLocked(characterLevel, requiredLevel)`). `src/data/__tests__/data-consistency.test.ts` 에 **"`requiredLevels` 의 키는 그 엔트리 `difficulties` 의 부분집합"** 검증을 추가해 오타·난이도 추가 시 조용히 어긋나는 것을 막는다.

5. **레벨을 모르면 잠그지 않는다.** 요구 레벨 데이터가 없는 엔트리이거나 캐릭터 레벨 캐시가 없으면(`getCachedCharacterBasic` 미스) **통과시킨다.** 거짓 잠금이 거짓 허용보다 나쁘기 때문이다 — 잘못 잠그면 사용자가 앱으로 하려던 일이 사라지는데 화면에는 "레벨이 모자란다"는 틀린 이유만 남는다. 반대로 잘못 통과시키면 게임에서 못 잡을 보스가 목록에 남을 뿐이고, 사용자가 직접 해제할 수 있다.

   이 규칙이 **점진 반영을 가능하게 하는 핵심**이다: 요구 레벨은 엔트리 단위로 채워지는 대로 잠금이 켜지고, 코드는 데이터를 기다리지 않고 먼저 나갈 수 있다(#62는 데이터가 이미 있으므로 독립적으로 완결된다).

6. **캐릭터 레벨은 이미 읽고 있는 값을 뷰까지 보존한다.** `sortByCachedLevel`(보스·컨텐츠 스토어 양쪽)이 정렬을 위해 `getCachedCharacterBasic(ocid).profile.level` 을 조회하고 **버린다.** `BossCharacterView`/`ContentCharacterView` 에 `level: number | null` 을 추가해 그 값을 싣기만 하면 된다 — 추가 조회도 추가 API 호출도 0이다([[ADR-054]] 결정 5에서 `world` 를 배관한 것과 같은 수법). 관리 화면에서 별도로 `getCachedCharacterBasic` 을 다시 부르지 않는다(같은 값을 두 경로로 읽으면 갈라진다).

7. **잠금 단위는 난이도 칩이고, 행 잠금은 그 결과다.** (보스, 난이도)별 요구 레벨이므로 같은 보스라도 익스트림만 잠길 수 있다. 따라서 난이도 세그먼트의 잠긴 칩만 `disabled` 로 두고, **모든 난이도가 잠긴 보스만** 행 전체를 잠근다.
   - **`defaultDifficultyFor` 가 잠긴 난이도를 고르지 않게 한다.** 현재는 `등록 난이도 ?? difficulties[0]` 인데, 그대로 두면 행을 탭하는 순간 스토어가 거부해 "눌러도 아무 일이 없는" 행이 된다. 선택 **가능한** 난이도 중에서 고른다.
   - 컨텐츠는 난이도가 없으므로 항목 단위 잠금 하나뿐이다.

8. **UI는 기존 스타일만 조합한다 — 신규 컴포넌트·색 토큰·배지 스타일을 만들지 않는다.**
   - **관리 화면 잠긴 항목**: 행 dim + 사유 칩. 칩은 난이도 세그먼트의 기존 고스트 칩 스타일(`inline-flex h-5 items-center rounded-full border border-border px-2.5 text-[10px] font-bold text-text-disabled`)을 그대로 쓰고 문구만 `Lv.{요구레벨}` — 관리 화면에서는 "왜 안 되는지"보다 **"몇 레벨이면 되는지"**가 실행 가능한 정보다.
   - **한도 카운터**: 보스 관리 헤더 **주간 탭에만** `n/12`. `BossScreen.tsx:449` 의 기존 배지 스타일 재사용([[ADR-054]] 정정 1이 폐기한 것은 *보스 수익 캐릭터 카드*에 한한 재사용이고, 보스 스케줄러 계열 화면에서는 유효하다 — 캐릭터 1명 기준이라 가로 경합이 없다).
   - **표시 화면(`BossScreen`/`ContentScreen`) 잠긴 카드**: 흐리게 + `진행 불가` 칩(이슈 #32 요구사항 문구 그대로).
   - **토스트는 폴백이다.** 사전 차단이 주 경로라 잠긴 버튼은 애초에 클릭 이벤트가 안 난다. 토스트는 결정 2가 막는 우회 경로(난이도 교체 등)에서 스토어가 거부했을 때만 뜬다. 이미 쓰고 있는 `useToastStore` 를 그대로 쓴다.

9. **표시 화면은 표시만 바꾼다 — 잠긴 항목을 자동으로 제거하지 않는다.** 이미 추적 중인 항목이 나중에 잠금 상태가 될 수 있다(요구 레벨 데이터가 새로 채워짐, 다른 캐릭터로 전환). 그때 앱이 조용히 목록에서 지우면 사용자가 손대지 않은 설정이 사라진다. 흐리게 + "진행 불가"로 **보여주기만** 하고 해제는 사용자에게 맡긴다. (자동 모드에서는 게임이 등록한 보스만 오므로 실질적으로 거의 나타나지 않는다.)

10. **기존 초과 선택 마이그레이션은 만들지 않는다.** 앱이 아직 배포 전이라 12개를 넘겨 저장해둔 사용자가 존재하지 않는다(사용자 확인 2026-07-29). 따라서 초과 상태 표시 규칙(`15/12`)도, 진입 시 잘라내기 로직도 두지 않는다 — 카운터는 항상 `n/12`(n ≤ 12)이고 초과는 발생할 수 없는 상태다. 배포 후에 한도를 **바꾸게** 되면 그때 다시 결정한다.

**이유**: 두 이슈의 공통 분모는 "선택 가능 여부"이지 "레벨"이나 "12"가 아니다. 그래서 판정 로직(무엇이 막는가)만 공유하고 표현(어떻게 보이는가)은 화면별로 둔다 — 공용 배지 컴포넌트까지 만들면 관리 화면(`Lv.275`)과 표시 화면(`진행 불가`)의 서로 다른 문구를 억지로 한 컴포넌트에 밀어 넣게 된다. 데이터 쪽도 마찬가지로 **판정 함수만** `lib/required-level.ts` 에 모으고, 값은 기존 참조 파일에 필드로 붙인다(새 JSON 파일을 만들면 보스명·난이도 조인 키가 하나 더 늘어난다).

**트레이드오프**:
- **요구 레벨 데이터 수집이 크리티컬 패스다.** 보스 56쌍(26엔트리 × 난이도) + 컨텐츠 40엔트리를 사용자가 확정해야 #32의 잠금이 실제로 작동한다. 결정 5 덕분에 코드는 먼저 나갈 수 있지만, 그 사이 #32는 사용자 눈에 아무것도 바뀌지 않은 것으로 보인다.
- **캐릭터 레벨은 캐시값이라 실제보다 낮을 수 있다**(레벨업 직후, 동기화 전). 그 경우 실제로는 입장 가능한 보스가 잠긴다 — 캐시가 갱신되면 풀린다. 반대 방향(캐시가 실제보다 높음)은 게임에서 레벨이 내려가지 않으므로 발생하지 않는다.
- **`addManualBoss`/`addManualContent` 반환 타입 변경은 기존 호출부를 전부 건드린다**(관리 화면 토글·난이도 교체·테스트). 스토어를 조용히 두고 UI에서만 막는 쪽이 diff는 작지만, 그러면 결정 2가 지적한 우회 경로가 남는다.
- **12 한도는 (보스, 난이도) 쌍이 아니라 보스 단위로 센다.** 현재 화면이 보스당 난이도 1개만 추적하게 돼 있어 지금은 두 해석의 값이 같다. 다난이도 동시 추적이 생기면 규칙을 다시 정해야 한다(게임 규칙은 난이도 조합 단위이므로 그때는 쌍 단위가 맞다).

**저장소**: 스키마 변경 없음 — `manualTrackedContent:{ocid}` 배열 구조도, SQLite 테이블도 그대로다. 참조 데이터 파일 2개에 필드만 추가한다(`weekly-bosses.json` → `requiredLevels`, `scheduler-content-template.json` → `requiredLevel`). `character-basic-cache` 는 읽기만 하며 `level` 은 이미 저장되는 필드다.

**데이터 반영 메모 (2026-07-29)** — 결정 4의 데이터가 **전량 확정돼 두 파일에 반영됐다**(값은 전부 사용자 제공, AI 추정 0). 구현보다 데이터가 먼저 들어온 순서라, 아직 이 필드를 읽는 코드는 없다(무해한 비활성 데이터).
- **보스 56쌍 전부** (`weekly-bosses.json`, 미출시 벨로나 포함). **메이린을 제외한 모든 보스는 난이도가 달라도 입장 레벨이 같다** — 그럼에도 결정 4의 난이도별 맵 스키마는 유지한다. 메이린(노멀 270 / 하드 280)이 난이도별로 갈리는 실제 사례이므로 단일 값 스키마는 이 데이터를 표현하지 못한다.
- **컨텐츠 40엔트리 중 35개**(`scheduler-content-template.json`). 나머지 5개(메이플 유니온 주간 드래곤 퇴치 2종 · 길드 3종)는 **레벨 제한이 없어 필드를 생략**했다 — 결정 5의 "필드 없음 = 잠금 없음"이 곧 정답인 경우다. 미확정과 제한 없음을 필드 유무로 똑같이 표현하는 셈인데, 둘 다 "잠그지 않는다"로 귀결되므로 구분할 실익이 없다.
- 확정 과정에서 사용자가 판정한 두 건은 [foundation/game-data.md](../foundation/game-data.md) "데이터 확정 현황"에 근거째 기록했다(아케인리버 주간 6종 = 같은 지역 일일퀘 레벨 · "…에 대한 보답" 3종 = 소속 콘텐츠 레벨).

**구현 메모 (2026-07-29)** — 결정을 코드로 옮기며 확정된 세부. 결정 자체는 바뀌지 않았다.
- **행 잠금은 "미선택"일 때만 건다.** 결정 1의 우선순위(levelLocked > limitReached) 위에 조건이 하나 더 붙는다 — **이미 추적 중인 행은 어느 사유로도 잠그지 않는다.** 해제할 수 없으면 한도가 찬 상태에서 목록을 영영 바꿀 수 없고, 결정 9(자동 제거 없음)와도 모순된다.
- **난이도 칩 잠금은 수동 모드 한정.** 자동 모드의 난이도 선택은 멤버십이 아니라 "어느 난이도의 파티 인원을 편집할지"라(화면 전용 상태), 여기를 막으면 미등록·진행 불가 보스의 파티 인원 사전 설정([[ADR-031]] 결정 4)이 막힌다. 이슈 #32의 "자동/표시 뷰는 선택 가능하되 흐리게"와도 일치한다.
- **`handleSwitchDifficulty`는 지우기 전에 레벨을 확인한다.** 이 경로는 `remove` → `add` 순서라, 스토어가 `add`를 거부하면 **항목이 사라진다**. 순서를 뒤집으면(add → remove) 한도 검사에 걸려 12개 상태에서 난이도를 못 바꾼다. 그래서 순서는 그대로 두고 잠금만 선행 확인한다(한도는 같은 보스 1:1 교체라 애초에 걸리지 않는다).
- **컨텐츠 표시 화면은 카드가 아니라 목록 항목을 감싼다.** 카드 컴포넌트가 9종이라 각각에 prop을 뚫는 대신 `renderLevelAware(name, card)` 한 곳에서 dim + 배지를 씌운다. 잠금은 "카드가 무엇을 보여주는가"가 아니라 "이 항목을 진행할 수 있는가"의 문제라 바깥이 맞는 자리다. 보스는 카드가 `BossCard` 하나뿐이라 prop(`isLevelLocked`)으로 받는다.
- **관리 화면의 사유 표기**: 보스 행은 `Lv.{최솟값}`(난이도별 요구 레벨 중 최소 — 그 레벨이면 행이 열린다), 잠긴 난이도 칩은 `{난이도} Lv.{요구레벨}`, 컨텐츠 행은 카운트 태그 자리를 `Lv.{요구레벨}`로 대체한다(진행할 수 없는 항목의 "최대 n회"보다 쓸모 있다).
- 기존 스토어 테스트 5건이 `toEqual`로 뷰 전체를 비교하고 있어 `level` 필드 추가분만큼 갱신했다(동작 변화 아님).

**정정 1 (2026-07-29, 구현 직후 사용자 피드백)** — **잠긴 행의 사유를 오른쪽 뱃지가 아니라 흐린 행 위에 얹는 한 줄로 바꾼다.** 결정 8의 "기존 고스트 칩 재사용"은 스타일을 새로 만들지 않는다는 점에서는 맞았지만, 실제 화면에서 **흐려진 행 + 오른쪽 구석의 `Lv.295`** 조합은 "왜 흐린가"가 읽히지 않았다(사용자 지적). 뱃지는 상태를 이름표로 붙일 뿐이고, 흐림은 그 자체로 이유를 말하지 못한다.

- **문구는 상태가 아니라 다음 행동을 말한다**: `295레벨 달성 시 진행 가능` · `길드 가입 시 진행 가능`([[ADR-057]]) · `주간 12개를 모두 선택했어요`(한도). 앞의 둘은 조건이 갖춰지면 열린다는 뜻이고, 세 번째는 다른 항목을 해제하라는 뜻이라 어미가 다르다.
- **한도로 막힌 행에도 문구를 붙였다.** 원래는 흐림만 있었는데, 레벨 잠금만 이유를 말하고 한도는 말하지 않으면 같은 흐린 행이 두 뜻을 갖게 된다.
- **흐림은 콘텐츠 `opacity` 가 아니라 그 위를 덮는 스크림(scrim)이다** — 정정 1의 1차 구현(콘텐츠 `opacity-30` + 그 위에 문구)이 **읽히지 않았다**(사용자 지적). 원인은 색이 아니라 배경이었다: 문구 뒤에 44px 초상화와 보스명의 형태가 그대로 남아, 글자마다 배경이 달라져 실효 대비가 무너진다. 토큰 대비만 재면 `text-muted`/`surface` 도 테마 4종 모두 6.2~7.3:1로 멀쩡해 보이므로, 색을 바꾸는 것으로는 고쳐지지 않는 문제다.
  - 그래서 흐림과 문구를 **한 레이어로 합친다**: `absolute inset-0` 에 `bg-surface/85`(컨텐츠 관리 화면은 행 자체 배경이 없어 `bg-bg/85`) + `backdrop-blur-[2px]` 를 깔고 그 위에 문구를 올린다. 문구의 배경이 균일한 표면색이 되어 대비가 **13.6~17.8:1**(테마 4종 실측)로 확정되고, 콘텐츠는 15%만 비쳐 "이 행에 무언가 있다"는 것만 남는다.
  - 메커니즘이 둘(콘텐츠 opacity + 문구 오버레이)에서 하나(스크림)로 줄어 `<li>` 안에 흐림 전용 래퍼 `<div>` 도 없어진다.
  - 문구는 `text-sm font-semibold text-text`(흐린 `text-muted` 를 쓸 이유가 사라졌다 — 흐림은 스크림이 담당한다). 레이어는 `pointer-events-none`(토글은 이미 `disabled` 지만 레이어가 히트 영역을 가리지 않게), 모서리는 행과 같은 반경으로 클립.
- **난이도 칩의 `{난이도} Lv.{요구레벨}` 표기는 유지한다.** 그건 오른쪽 구석의 상태 뱃지가 아니라 "이 난이도를 고르려면 얼마가 필요한가"를 칩 자리에서 답하는 것이고, 추적 중인 행(=흐리지 않은 행)에서만 보이므로 이번 지적과 상황이 다르다.

**정정 2 — 요구 레벨 잠금(#32) 폐기 (2026-07-29, 사용자 결정)**: **레벨 미달 항목을 잠그지 않는다. 선택은 자유롭게 둔다.** 이슈 #32의 요구사항 자체를 폐기한 것이므로, 이 ADR에서 `levelLocked` 사유와 그에 딸린 배관·표시를 전부 걷어냈다. 남는 것은 **#62(주간 보스 12개 한도)** 뿐이다.

걷어낸 것:
- `lib/required-level.ts`(+테스트) 삭제. 결정 4·5·7의 판정 로직이 여기 전부 모여 있었으므로 이 파일 하나로 정리된다.
- 두 뷰의 `level` 필드와 `sortByCachedLevel` 의 보존(결정 6) 원복 — 레벨은 다시 **정렬용으로만** 읽고 버린다. 컨텐츠 뷰의 `guildName` 보존([[ADR-057]])은 같은 자리에 남는다.
- 스토어 가드의 `levelLocked` 분기와 반환값(`ManualBossAddResult`·`ManualContentAddResult`), 관리 화면의 난이도 칩 잠금·`defaultDifficultyFor` 의 잠금 회피(결정 7), `handleSwitchDifficulty` 의 레벨 선행 확인.
- 표시 화면의 `진행 불가` 표기(결정 9) — `BossCard.isLevelLocked` prop과 `ContentScreen.renderLevelAware` 둘 다.

남긴 것:
- **요구 레벨 데이터는 `weekly-bosses.json`·`scheduler-content-template.json` 에 그대로 둔다.** 사용자가 확정한 검증된 게임 레퍼런스 데이터라 다시 모으는 비용이 크고, 참조 테이블에 필드가 하나 더 있어도 해가 없다. 정합성 테스트(`data-consistency`)도 유지해 값이 조용히 어긋나는 것은 계속 막는다. **현재 이 필드를 읽는 코드는 없다.**
- 결정 1~3·10의 한도 쪽 구조(사유 모델·스토어 가드 우선·카운트 규칙 단일화)와 정정 1의 표기 방식(흐림 스크림 + 안내 문구)은 그대로 유효하다. [[ADR-057]] 의 길드 잠금이 같은 자리를 쓰고 있어, 사유가 하나로 줄었을 뿐 구조는 살아 있다.
