### ADR-146: **알림 시스템 — 네이티브는 «능력» 만 싣고 알림은 전부 JS 로 온다** (2026-08-17, 사용자 지시)

> ⚪ **NOT IMPLEMENTED — 설계만 있고 코드가 없다.** 설계 완료·구현 전. 착수 전에 이 문서를 다시 읽을 것.

**배경**: [[ADR-004]] 는 *"서버 푸시 없이 로컬 알림만"* 을 정하고 발송 판정을 *"예정 시각에
백그라운드로 API 재확인"* 으로 적었다(2026-07-09 확정). **그 뒤로 한 줄도 구현되지 않았다** — 지금
있는 것은 `NotificationsPort`(권한·예약·취소·개수) 하나와 두 어댑터뿐이고, 그 포트를 부르는
`features/` 코드는 **없다**(`git log -S` 로 확인 — 호출부는 그 어댑터의 자기 테스트뿐이다). 즉 알림은
«설계된 적 있고 만들어진 적 없는» 기능이다.

사용자가 보내고 싶다고 말한 것은 셋이다(2026-08-17).

1. 메이플스토리 **공지사항**
2. 매일 특정 시각, **일간 스케줄 미완료** 알림
3. 매주 특정 시각, **주간 보스 미완료** 알림

그런데 요구의 핵심은 그 목록이 아니라 **시점**이다 — *"네이티브 앱을 스토어에 올리기 전에 설계 및
시스템 구현만 해놓고, 실제 알림은 OTA 로 추가할 수 있게."* RN 전환([[ADR-128]])의 스토어 릴리스가
임박했고 그 릴리스에는 **OTA 안전망이 없다**(`migration/README.md` «되돌릴 수 없는 지점»). 바이너리에
안 들어간 네이티브 능력은 **다음 스토어 심사까지 못 쓴다.**

그래서 이 ADR 이 답하는 질문은 *"어떤 알림을 보낼까"* 가 아니라 ***"무엇이 바이너리에 들어가야 하고
무엇이 나중에 와도 되는가"*** 다.

### 결정 1. 경계는 «알림 종류» 가 아니라 **«네이티브에 적히면 OTA 로 못 고친다»** 다

바이너리에 들어가는 것은 **능력 셋**뿐이고, 그 셋이 여는 문장은 각각 한 줄이다.

| 능력 | 여는 문장 | 없으면 |
|---|---|---|
| 로컬 알림 | *"정한 시각에 알림을 띄운다"* | 예약형 알림 전부 불가 |
| 원격 푸시 | *"서버가 보낸 것을 받는다"* | 공지 알림 불가 |
| 백그라운드 태스크 | *"가끔 우리 JS 를 깨운다"* | 판정이 «앱을 연 시점» 에 굳는다 |

**«무엇을 언제 왜 띄우는가» 는 네이티브에 한 줄도 없다.** 종류 목록·문구·시각·기본 활성값·미완료
판정·중복 억제·설정 화면이 전부 JS 라 OTA 로 온다.

이 경계에는 **위치만 네이티브 요건인 것 셋**이 딸려 온다 — 백그라운드 태스크 핸들러 · 푸시
백그라운드 핸들러 · 알림 이벤트(탭) 핸들러는 **앱 모듈 최상위에 등록돼 있어야** OS 가 죽은 앱을
깨울 수 있다. 그래서 «등록하는 한 줄» 은 바이너리에 박히고 **그 한 줄이 부르는 함수 본문은 JS**다.
등록을 나중에 OTA 로 더할 수는 없다 — 그때는 OS 가 그 앱에 그런 진입점이 있다는 것을 모른다.

### 결정 2. 공지 알림은 **FCM 토픽 푸시**다 — [[ADR-004]] 의 *"서버 푸시 없음"* 을 공지에 한해 뒤집는다

기기 폴링을 **기각한 이유는 iOS 다**. `BGAppRefreshTask` 는 실행 시각을 보장하지 않고, 앱을 자주 안
쓰는 사용자에게는 며칠씩 안 돈다 — 공지 알림은 «늦게 오면 의미가 없는» 종류라 그 실패가 곧 기능
부재다. 게다가 폴링은 **전 사용자가 각자 개인 API 키로 같은 공개 정보를 반복 조회**하는 모양이라,
개발 단계 키 한도(1,000건/일, [nexon-api.md](../foundation/nexon-api.md))를 사용자마다 갉아먹는다.
**모두에게 똑같은 정보를 각자 캐게 하는 것이 틀렸다.**

그래서 이미 있는 `workers/ota-manifest` 옆에 발송 Worker 를 둔다. 지키는 성질 넷:

- **토큰을 서버에 저장하지 않는다 — 토픽으로 보낸다.** 기기는 토픽을 구독할 뿐이고 등록 토큰은 앱
  밖으로 나가지 않는다. 그래서 서버가 드는 상태는 **«마지막으로 발송한 공지 id» 하나**다([[ADR-137]]
  결정 2 의 «무상태 Worker» 를 깨는 최소값 — KV 키 1개). 토큰 DB 를 두는 순간 만료 정리·삭제 요청
  ·개인정보 분류가 전부 따라온다.
- **서버는 자기 키로 넥슨을 부른다.** 사용자 개인 API 키는 여전히 기기 밖으로 나가지 않는다
  ([[ADR-003]] 유지). 이 결정이 [[ADR-003]] 을 건드리지 않는 이유가 그것이다 — 옮겨 가는 것은
  **공개 정보를 긁는 일**이지 사용자 데이터가 아니다.
- **문구는 Worker 가 만들어 `notification` 페이로드로 싣는다.** data-only 로 보내고 앱이 그리게 하면
  «앱이 죽어 있을 때 iOS 가 배달을 보장하지 않는» 자리로 들어간다 — 공지 알림에서 그것은 안 뜨는
  것과 같다. 문구가 서버로 가는 것이 요구를 어기지 않는 이유는 **Worker 는 심사를 안 받아 OTA 보다
  빨리 고쳐지기 때문**이다. `data` 에는 공지 id·링크만 실어 탭 이동과 중복 억제를 JS 가 맡는다.
- **앱은 «구독한다/해제한다» 만 안다.** 토픽 이름·발송 조건·주기는 서버 쪽 값이다.

**대가** — ① 백엔드가 «없다» 에서 «하나 있다」가 된다([[ADR-004]] 이유의 전제였던 문장이 깨진다)
② Firebase 프로젝트·`google-services.json`·APNs 인증 키가 릴리스 준비물에 는다 ③ 등록 토큰은 앱이
서버로 안 보내도 **Firebase 가 갖는 기기 식별자**라, Play 데이터 안전 신고와 `PRIVACY.md` 를
갱신해야 한다([release.md](../foundation/release.md)) ④ 넥슨 공지 API 를 **개발자 키로 서버가 주기
폴링**하는 것이 이용약관상 문제없는지는 **확인되지 않았다**(아래 «열린 질문»).

### 결정 3. 미완료 알림은 **하이브리드**다 — 사전 예약이 도달을 보장하고, 백그라운드가 정확도를 올린다

앱은 **게임 안에서 일어난 완료를 모른다** — Nexon API 로만 안다. 그래서 두 방식 다 반쪽이다.

| 방식 | 얻는 것 | 잃는 것 |
|---|---|---|
| 사전 예약만 | 시각이 정확하고 반드시 뜬다 | 앱을 안 연 사이 다 끝냈어도 뜬다(**오탐**) |
| 백그라운드 재확인만([[ADR-004]] 원안) | 오탐 0 | iOS 에서 태스크가 안 돌면 **아예 안 뜬다**(조용한 실패) |

둘을 겹친다.

1. **앱이 열릴 때·동기화가 끝날 때마다** 마지막으로 아는 상태로 앞으로의 알림을 예약한다.
2. **백그라운드 태스크가 돌면** 같은 재조정을 다시 돌린다 — 그 안에서 동기화가 되면 최신 상태로,
   실패하면 캐시로 판정한다([[ADR-008]] 폴백 그대로).
3. **태스크가 한 번도 안 돌아도 알림은 뜬다.** 이 비대칭이 iOS 대비다 — 백그라운드는 **있으면 좋은
   것**이지 있어야 하는 것이 아니다.

**문구는 마지막으로 아는 상태를 단정하지 않는다.** *"일간 3개 남았어요"* 는 확인 시점의 값이라 발화
시점에 거짓일 수 있고, 이 저장소는 확신 없는 것을 단정하지 않기로 이미 정해 왔다([[ADR-060]]
«확인 못 한 것을 빈 상태로 위장하지 않는다»). 수를 싣는 것은 **발화 직전 재확인이 성공한 경우로
한정**한다.

### 결정 4. **알림은 계정 단위 한 줄로 접는다** — [[ADR-004]] 의 «64개 한도 우선순위 정책» 은 폐기한다

[[ADR-004]] 는 *"캐릭터 수 × (일간 1 + 주간 1)"* 을 예약하려다 iOS 64개 한도에 부딪혔고, 그래서
«임박한 순 → 마지막으로 연 캐릭터 순» 이라는 우선순위 정책과 *"일부 알림이 예약되지 않았습니다"*
안내를 설계했다. **그 문제를 정책으로 푸는 대신 만들지 않는다.**

- 알림은 캐릭터를 말하지 않는다 — *"아직 안 끝낸 것이 있어요"* 한 줄이고, 어느 캐릭터인지는 **앱을
  열면 화면이 이미 말한다**(초상화 레일의 진행 링, [[ADR-142]]).
- 예약은 **앞으로 7일 지평선까지만** 구체 시각으로 잡고, 앱이 열리거나 태스크가 돌 때 다시 채운다.
  OS 반복 알림을 쓰지 않는 이유는 «미완료일 때만» 이라는 조건이 반복 예약에 실리지 않기 때문이다.
- 그래서 동시 예약 수는 **캐릭터 수와 무관하게 10개 안쪽**이고, 64개 한도는 **정책이 아니라 구조로**
  사라진다. 예약 실패 안내도 함께 없어진다(안 일어나는 일을 위한 UI 를 만들지 않는다).

**대가** — 알림만 보고는 어느 캐릭터가 남았는지 모른다. 목적이 «앱을 열게 하는 것» 이라 손해가 작다고
본다.

### 결정 5. **레지스트리 + 원장** — OS 가 든 예약을 이름으로 지울 수 있게 한다

OS 는 예약을 들고 있는데 앱은 **개수만** 조회할 수 있다([lifecycle.md](../persistence/lifecycle.md)).
그래서 OTA 로 알림 종류를 빼면 **그 예약이 유령으로 남는다** — `migration/data.md` 결정 4 가 프레임워크
전환에서 겪은 것과 **같은 사고**이고, 이번엔 OTA 마다 일어날 수 있다.

- **레지스트리**: 알림 종류 하나 = 정의 하나(`kind` · 카테고리 · 기본 활성값 · 기본 시각 · `plan()`).
  `plan()` 은 **순수 함수**다 — `(지금, 지평선, 설정, 스케줄 스냅샷) → 띄울 것들`. 저장소·네이티브를
  모르므로 종류를 더하는 일이 곧 «표에 한 줄 + 순수 함수 하나 + 그 테스트» 가 된다.
- **원장**(`notificationLedger`, Preferences): **우리가 지금 예약해 둔 것** 전부를 `{id, kind, fireAt}`
  로 적는다. OS 를 못 읽으니 우리가 기억한다.
- **재조정은 차집합으로만 움직인다** — 계획에 없는데 원장에 있으면 취소, 있는데 없으면 예약, 둘 다
  있고 `fireAt` 이 같으면 **아무것도 안 한다**. 몇 번을 돌려도 결과가 같다(멱등).
- **원장에 있는데 레지스트리에 없는 `kind` 는 무조건 취소한다.** ← **이 원장이 존재하는 유일한
  이유다.** OTA 가 알림을 지우면 그 예약도 함께 사라진다.
- 순서는 **예약 → 원장 쓰기**, **취소 → 원장 지우기**다. 둘 다 «중간에 죽으면 다음에 한 번 더 한다»
  쪽으로 넘어진다 — 반대로 하면(원장 먼저 쓰기) 크래시 뒤 원장이 «예약돼 있다» 고 말해 **다시 예약할
  기회를 영영 잃는다.**
- ID 는 `(kind, 범위키, 회차키)` 에서 **결정적으로 계산**한다. 같은 알림은 몇 번을 계획해도 같은 id 라
  재예약이 덮어쓰기가 되고, 그것이 위 «한 번 더 해도 안전» 의 근거다.

**권한이 꺼져 있으면 계획은 빈 목록이다** — 예약하지 않고 원장에 있는 것을 전부 취소한다([[ADR-008]]
*"예약 전 권한 재확인"*). 다시 켜면 다음 재조정이 되살린다.

### 결정 6. **Android 채널은 카테고리 단위로 셋**이고, 지금 확정한다

채널은 한 번 만들면 **앱이 이름·중요도를 못 바꾼다**(사용자만 바꾼다). 새로 만드는 것은 OTA 로
되지만 **고치는 것은 안 된다** — 그래서 알림이 하나도 없는 지금 이름을 정한다.

| 채널 | 담는 것 |
|---|---|
| `notice` | 메이플스토리 공지 |
| `schedule` | 일간·주간 미완료 리마인더 |
| `general` | 위 둘에 안 들어가는 것 |

Capacitor 시절 채널 `'default'` 는 기기에 이미 있다 — **그대로 두고 쓰지 않는다**(지울 수 없고,
재사용하면 옛 중요도 설정을 물려받는다).

### 결정 7. 권한은 **알림을 켤 때** 묻고, 이번 릴리스에 설정 화면을 넣지 않는다

iOS 는 한 번 거부하면 **다시 묻지 못한다**(설정 앱으로 보내는 수밖에 없다). 그래서 부팅 때 묻지
않는다 — 사용자가 알림을 켜는 순간이 유일한 요청 시점이다.

그 «켜는 화면» 은 JS 라 OTA 로 온다. **이번 바이너리엔 넣지 않는다** — 켤 알림이 하나도 없는데
설정만 있으면 그 화면이 거짓말을 한다. 설정 > 알림은 **첫 알림과 함께** 온다
([settings.md](../features/settings.md) 의 미착수 항목이 이 결정으로 확정된다).

### 결정 8. **RN 전용**이다 — Capacitor 어댑터는 no-op 으로 남는다

새 네이티브 능력 둘(푸시·백그라운드 태스크)은 `packages/app-rn` 에만 구현한다. 스토어에 나갈
바이너리가 RN 이고 Capacitor 는 패리티 도달 후 퇴역 예정이라([[ADR-128]] 원칙 3), **검증할 수 없는
네이티브 코드를 두 벌 만들지 않는다.**

포트는 core 에 서고 Capacitor 구현은 `isSupported(): false` 다 — [[ADR-140]]·[[ADR-143]]·[[ADR-145]] 가
이미 만든 «RN 전용 결정» 관례를 그대로 따른다. `NotificationsPort`(이미 양쪽 구현이 있다)는 **그대로
둔다** — 지우면 웹뷰 앱의 테스트가 깨지고 얻는 것이 없다.

**여기 빠진 것은 다음 심사까지 못 쓴다.**

- [ ] 알림 표시 런타임 — `@notifee/react-native` (**이미 있다**)
- [ ] 푸시 수신 — Firebase Messaging 계열 의존성 + `google-services.json`(Android) ·
      `GoogleService-Info.plist`(iOS) · APNs 인증 키(.p8) 를 Firebase 콘솔에 업로드
- [ ] 백그라운드 태스크 런타임 — Expo 백그라운드 태스크 계열 의존성
- [ ] iOS `Info.plist` — Background Modes 에 `remote-notification` · `fetch`, Push Notifications capability
- [ ] Android — `POST_NOTIFICATIONS`(notifee core 매니페스트가 병합) · 부팅 후 재예약 경로 확인
- [ ] **모듈 최상위 진입점 셋** — 백그라운드 태스크 핸들러 · 푸시 백그라운드 핸들러 · 알림 이벤트
      핸들러. **등록만 네이티브 요건이고 본문은 core 의 JS 를 부른다**(결정 1)
- [ ] 채널 셋(`notice`·`schedule`·`general`)을 만드는 코드 경로 (결정 6)

**의존성은 «붙는 것을 확인한 뒤» 확정한다** — 이 저장소는 notifee 를 고를 때 `expo prebuild` →
`assembleDebug` 로 오토링킹·dex 진입까지 보고 나서 적었다(`rn-notifications.ts` 머리말). 라이브러리
이름을 문서에 먼저 박고 나중에 안 붙는 것이 확인되면 그 문서가 거짓말이 된다.

공지 필터.

## 기각

- **기기 백그라운드 폴링으로 공지 확인** — iOS 에서 사실상 안 돌고, 전 사용자가 각자 개인 키로 같은
  공개 정보를 캔다(결정 2 «이유»).
- **FCM 토큰 저장 + 개별 발송** — 월드·캐릭터별 타겟팅을 열지만 토큰 DB·만료 정리·개인정보 분류가
  통째로 따라온다. **지금 보내려는 알림 셋 중 타겟팅이 필요한 것이 하나도 없다.**
- **알림 없이 인앱 배지만** — 네이티브 추가 0 이지만 요구를 충족하지 못한다.
- **캐릭터별 알림 + 64개 한도 우선순위 정책**([[ADR-004]]) — 결정 4.
- **이번 릴리스에 설정 > 알림 화면 포함** — 결정 7.
- **`NotificationsPort` 를 새 설계에 맞춰 갈아엎기** — 시그니처는 [[ADR-128]] 원칙 1 이 고정했고,
  이 설계가 필요로 하는 것을 그 넷이 이미 준다. 부족한 것은 포트가 아니라 **그 위층**이었다.

## 열린 질문

- **넥슨 공지 API 를 개발자 키로 서버가 주기 폴링하는 것이 이용약관상 허용되는가.** 공개 정보이고
  개인 데이터가 아니지만 확인된 바 없다. 공지 엔드포인트의 실제 경로·응답 형태도 **아직 실측하지
  않았다** — `scripts/probe-nexon-api.mjs` 로 확인한 뒤 [nexon-api.md](../foundation/nexon-api.md) 에
  적는다.
- **기본 알림 시각** — 일간은 몇 시, 주간 보스는 리셋(KST 목요일 00:00) 몇 시간 전인가. 게임 생활
  패턴에 달린 값이라 **사용자 확인 대상**이다([[ADR-006]] 취지).
- **공지 알림의 범위** — 공지·업데이트·이벤트·캐시샵을 다 보낼 것인가, 점검 공지만 보낼 것인가.
  전부 보내면 알림 피로가 곧 앱 삭제다.
- **재확인이 성공했을 때 수를 싣는가**(결정 3 마지막 줄) — 문구가 두 갈래가 되는 대가와, 그때만
  구체적인 것이 사용자에게 일관되게 읽히는지.
- **기기 재부팅 후 재예약** — Android 는 `BOOT_COMPLETED` 로 되살려야 예약이 산다. notifee 가 어디까지
  해 주는지 실기기 확인 전이다.
