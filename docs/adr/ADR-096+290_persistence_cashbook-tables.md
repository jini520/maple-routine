# ADR-096+290 가계부 기록 테이블 재설계

> 🟢 유효
> 관련 소스: `storage/sqlite/db.ts` · `storage/sqlite/cashbook-tables.ts` · `storage/sqlite/convert-cashbook-tables.ts` · `storage/sqlite/legacy-cashbook-entries.ts` · `storage/sqlite/migrations.ts` · `storage/cashbook-entries.ts` · `storage/cashbook-entry-shape.ts` · `storage/spend.ts` · `storage/income.ts` · `features/cashbook/records.ts` · `lib/cashbook/categories.ts` · `lib/cashbook/entry-ids.ts` · `lib/cashbook/spend-catalog.ts`

## 배경

손으로 적는 가계부 기록은 테이블 둘에 있다. `spend_records`(지출)와 `income_records`(수입)다.

세 가지가 문제다.

- **카드 이름을 기록 칸을 이어 붙여 만든다.** 하루 목록 카드의 이름은 `manualLabelOf` 가 화면을 그릴 때 심볼 · 항목 key ·
  형태 key · 직접 친 글자 · 분류 이름 순서로 찾아 한 줄로 잇는다. 그래서 `지내우시 · 악몽선경 EXP 1단계` 처럼 제목과
  품목이 한 줄에 섞이고, 품목마다 원하는 이름을 따로 정할 수 없다.
- **한 기록에 품목이 여럿이어도 칸 하나에 담는다.** 에픽던전 추가 리워드의 두 형태는 `form_item_keys` 한 칸에 들어간다.
- **id 가 `시각 + 난수` 다**(`newRecordId`). 앱의 기본키는 uuid 한 칸이다([[ADR-077]] 결정 8).

카드는 두 줄로 바꾼다(사용자 지정 2026-10-24).

```
캐릭터이름 · 에픽던전        지내우시 · 심볼강화       지내우시 · 주문서                 지내우시 · 사냥
악몽선경 EXP 1단계, 솔에르다 1단계   세르니움 7 -> 10        매지컬 한손무기 공격력 주문서      8소재
```

이 결정은 #670 과 함께 정했고(2026-10-25), v1.0.13 스토어 바이너리로 낸다. #631 · #507 · #614 는 이 작업에 넣지 않는다(사용자 선택).

DB 버전 15 가 옛 두 표를 기록 표로 옮겼다. 그때 표는 분류 · 품목을 key 글자(`category_key` · `item_key`)로 들고 수입 · 지출을
`entry_type` 칸으로 갈랐다. 1.0.15 기기 변환이 같은 이름의 표를 서버 표와 같은 칸으로 다시 옮긴다([[ADR-286]] 결정 4). 기기와
서버가 기록 줄을 그대로 주고받으려면 두 표의 모양이 같아야 하기 때문이다([[ADR-099]] 결정 19).

## 결정

### 결정 1. 수입과 지출을 테이블 하나로 합치고, 수입과 지출은 분류로 가른다

```
cashbook_entries               id · ocid · account_id · world_id · category_id · date · memo · recorded_at · updated_at
  ├ cashbook_entry_items       id · entry_id · target_type · target_id · item_name · spend_reward_type_id · item_type_id
  │                            · quantity · from_level · to_level · 금액 칸 · inventory_item_id
  ├ cashbook_entry_hunt_inputs id · entry_id · 사냥 계산기 입력
  ├ cashbook_entry_fragment_uses id · entry_id · fragment_source · ocid · fragment_quantity
  ├ cashbook_entry_transfer_inputs id · entry_id · 주간 보스 수입 이전 시트 입력
  └ cashbook_entry_exchange_inputs id · entry_id · 메소마켓 환전 수수료 시트 입력
```

- 수입인지 지출인지는 분류 줄(`category_id`)이 안다. 하루 목록과 기간 합계를 테이블 하나에서 읽으려고 합쳤다(사용자 선택).
  종류 칸을 따로 두면 분류 줄과 같은 사실을 두 번 적는다([[ADR-099]] 결정 45).
- 분류는 수입 · 지출 분류 줄의 id 다. 기타(`etc`)는 수입과 지출 양쪽에 있어 key 로는 가르지 못하지만 분류 줄은 둘이 다르다.
- `date` 는 돈이 오간 날(KST `YYYY-MM-DD`)이고, 시트에서 고르며 고칠 수 있다. 달력 칸 · 하루 목록 · 기간 합계가 이 값으로
  기록을 놓는다. `recorded_at` 은 저장한 시각이라 사용자가 못 고치고, 같은 날 안의 차례를 정한다. 옛 `spent_on` · `earned_on` 을
  옮겼다(사용자 지정).
- 칸 이름은 서버 표와 같다([[ADR-286]] 결정 2). 금액은 `amount_meso` · `amount_maple_point` · `amount_cash` 처럼 `무엇_화폐` 꼴,
  직접 친 품목 이름은 `item_name`, 심볼 레벨은 `from_level` · `to_level` 이다. 서버는 캐릭터와 메이플 ID 를 줄 id 로 가리키고
  기기는 `ocid` 와 `account_id` 로 가리킨다. 기록은 둘 가운데 하나가 반드시 차 있다(CHECK).
- 품목의 대상은 기록의 분류가 정한 표(사냥터 · 아이템 · 지출 항목 · 심볼 · 헥사 코어 · 헥사 스탯)의 줄 id 다. 반지는 레벨
  줄이다. 아이템 종류 · 추가 리워드 종류 · 월드도 게임 데이터의 줄 id 다. 저장 함수가 화면이 드는 key 와 줄 id 를 오간다
  (`storage/cashbook-entries.ts` · `lib/cashbook/entry-ids.ts`). 그래서 화면 코드는 표가 바뀌어도 그대로다.
- 품목은 추가 리워드 종류의 차례로 늘어놓아 차례 칸이 없다([[ADR-099]] 결정 53). 서버처럼 한 기록의 추가 리워드 종류는
  품목 하나다(`UNIQUE`).
- 기록에는 묶음 key 를 두지 않는다(사용자 선택). 품목의 대상이 이미 묶음을 알아서, 두면 같은 값이 두 곳에 생긴다. 한 기록의
  품목은 모두 같은 묶음이다.
- 헥사 기록이 보관에서 가져온 조각은 보관마다 한 줄이라 `cashbook_entry_fragment_uses` 로 뺀다([[ADR-137]] 결정 16).
- 사냥 계산기 입력은 수입 사냥에만 있어서 `cashbook_entry_hunt_inputs` 로 뺀다. 기록 하나에 0개나 1개다. 합친 테이블에 두면
  지출 행마다 빈 칸이 열 개 넘게 붙는다.
- `주간 보스 수입 이전` 과 `메소마켓 환전 수수료` 시트의 입력도 같은 이유로 `cashbook_entry_transfer_inputs` ·
  `cashbook_entry_exchange_inputs` 로 뺀다. 두 시트의 기록은 `기타` 로 저장하므로, 이 줄이 있는지로 어느 시트에서 적었는지
  안다([[ADR-047]] 결정 19 · 20).
- 보스 결정석 · 보스 드롭 판매 · 강화 지출은 원천 테이블(보스 기록 테이블 · `enhancement_totals`)에 그대로 둔다. 카드는
  같은 두 줄 규칙으로 그린다.

### 결정 2. 금액 · 수수료 · 관세는 품목마다 둔다

기록 한 건의 금액은 그 기록에 딸린 품목의 금액을 더한 값이다. 기록 행에는 금액 칸을 두지 않는다. 두 곳에 두면 줄 합계와
기록 금액이 어긋날 수 있기 때문이다. 줄마다 두면 품목별 금액 표시나 품목별 통계를 나중에 더할 수 있다(사용자 선택).

메소 · 포인트 · 포인트 시세 · 캐시 금액과 판매 수수료(`sale_fee_*`) · 구매 관세(`tariff_meso`)가 모두 줄의 칸이다.
수수료와 관세는 품목의 금액에 붙는 값이라, 금액과 같은 줄에 있어야 줄 금액을 그 줄만으로 셀 수 있다(사용자 선택).

### 결정 3. 카드 이름은 서버 참조표에 두고, 기록은 key 와 숫자만 갖는다

- 첫 줄 제목은 묶음의 `card_title` 이다. 묶음이 없는 분류(심볼 강화 · 아이템 구매 · 기타 · 사냥 등)는 분류의 제목을 쓴다.
- 둘째 줄은 줄마다 항목의 `name`(직접 친 품목이면 `item_name`)에 형태 · 단계 · 레벨 · 수량을 이어 적는다.
- 항목의 `name` 은 원본 이름이다. 화면 자리가 좁아 줄여 쓰던 이름은 새 칸 `short_name` 에 따로 두고, 시트 타일처럼 좁은
  곳에서만 쓴다. 비어 있으면 `name` 을 쓴다. 카드 이름 칸을 따로 두지 않는 이유는 원본 이름이 곧 카드 이름이라 칸이
  겹치기 때문이다(사용자 지정 2026-10-25). 예를 들어 `블루베리 농장 입장권` 이 `name`, `블루베리 농장` 이 `short_name` 이다. (1.0.15 에서 바뀐다. 항목의 `short_name` 칸을 없앤다. 타일에는 `spend_tiles.name` 이 선다. [[ADR-099]] 결정 60)
  확률이 하나뿐인 주문서도 확률을 이름에 남긴다(`매지컬 한손무기 공격력 주문서 100%` · `귀 장식 마력 주문서 10%`).
- 에픽던전 리워드 형태도 같은 규칙이다. 원본 이름 `경험치` · `솔 에르다` 를 카드에도 쓴다
  (`악몽선경 경험치 1단계, 솔 에르다 1단계`, 사용자 지정).
- 분류마다 두 줄은 이렇게 선다(카드 이름표, 사용자 확정 2026-10-25). 첫 줄 앞에는 캐릭터 이름과 ` · ` 가 붙는다. 메이플 ID
  기록은 그 자리에 메이플 ID 의 이름이 붙고([[ADR-161]] 결정 3), 캐릭터도 메이플 ID 도 없는 옛 기록은 제목만 선다. 수량은 천 단위 쉼표를 찍고 단위를 붙인다(`1,000포인트`).

  | 기록 | 첫 줄 | 둘째 줄 |
  |---|---|---|
  | 지출 목록(컨텐츠 · 이벤트·BM · 버프 · 주문서) | 묶음 `card_title` | 항목 `name` + 수량 + 항목 `unit`. 항목 이름이 제목과 같으면 수량만(`몬스터 파크` / `7회`) |
  | 에픽던전 추가 리워드 | 묶음 `card_title`(`에픽던전`) | 타일 이름 + 형태마다 `형태 이름 단계`, 쉼표로 잇는다. 0단계 형태는 안 적는다 |
  | 심볼 강화 | 분류 `card_title` | 심볼 이름 `강화 전 → 강화 후` |
  | 아이템 구매 · 판매 | 분류 `card_title` | 직접 친 이름. 소비 · 기타는 수량 + 종류 `unit` 을 붙인다 |
  | 지출 · 수입 기타 | 분류 `card_title` | 직접 친 이름. 수량이 2 이상일 때만 수량 + 단위를 붙인다 |
  | 사냥(계산기) | 분류 `card_title` | 소재 수 + 분류 `unit`. 조각 가격을 적었으면 `, 솔 에르다 조각 n개 판매` 를 잇는다 |
  | 사냥(직접 입력 · 계산 입력이 없던 옛 기록) | 분류 `card_title` | `직접 입력`. 조각 가격을 적었으면 판매를 잇는다 |
  | 솔 에르다 조각 정산 | 분류 `card_title`(`사냥`) | `솔 에르다 조각 n개 판매` |
  | 보스 결정석 · 보스 드롭 판매 · 강화 | 앱 상수 `보스 결정석` · `보스 드롭 판매` · `강화` | `n마리` · `n건` · 강화 분류 이름 + `n회` |

  보스 결정석 · 드롭 판매 · 강화는 손입력 분류가 아니라 원천 표의 줄이라 제목을 앱이 든다.
- 이름을 서버에 두는 이유는 관리 화면에서 고치면 앱 업데이트 없이 바뀌기 때문이다(사용자 선택). 서버 작업을 함께 한다.
- 분류와 에픽던전 리워드 형태도 서버로 옮긴다(사용자 선택). 지금 서버에는 둘 다 enum(`spend_category` 넷 · `spend_form`
  둘)뿐이고 이름은 앱 상수(`SPEND_CATEGORIES` · `INCOME_CATEGORIES` · `SPEND_FORMS`)가 든다. 그래서 묶음이 없는 분류의
  제목과 형태의 카드 이름을 둘 자리가 서버에 없다. 서버에 분류 표(수입 · 지출 분류 열하나)와 형태 표를 만들고, 앱
  상수는 다른 게임 데이터처럼 서버 데이터의 번들 사본이 된다([[ADR-020]]).
- 분류는 `GET /v1/game-data` 의 새 칸 `cashbookCategories` 로 내려준다(사용자 선택). 수입 분류까지 담으므로 지출 목록 칸
  (`spendCatalog`)에 넣지 않는다. 형태는 지출 목록 칸에 남는다.
- 관리 화면에서 분류의 이름 · 카드 제목 · 그림 · 설명 · 차례를 고치고, 새 분류도 더한다(사용자 선택).
- 앱은 분류 key 마다 입력 폼이 코드로 정해져 있다. 그래서 관리 화면에서 새로 더한 분류는 앱에 그 폼이 생길 때까지 분류
  목록에 이름만 서고, 못 고르게 막아 둔다(사용자 지정). 운영자가 앱 작업을 마칠 때까지의 상태다.
- 분류 key 는 서버에서 ENUM 이 아니라 글자다. 관리 화면에서 더하기 때문이다. 구현할 때 [[ADR-020]] 결정 9 의 ENUM 목록에서
  지출 분류 · 형태를 빼고, 이름을 앱 상수에 둔다는 문장도 함께 고친다.
- 심볼 강화의 둘째 줄은 심볼 이름(`symbols.name`)을 그대로 쓰고, 사냥은 수량과 단위만 적는다. 두 표에는 칸을
  더하지 않는다(사용자 선택).
- [[ADR-078]] 결정 6 과 같은 이유로 서버 게임 데이터의 줄은 지우지 않는다. 기록이 줄 id 만 가지므로 줄이 사라지면 그 기록의
  이름을 찾을 수 없다.

### 결정 4. 둘째 줄의 수량에는 단위를 붙이고, 단위는 모두 서버가 든다

`8소재` · `3회` 처럼 수량 뒤에 단위를 붙인다(사용자 지정). 단위는 모두 서버 참조표에 두고 앱에 글자로 두지 않는다(사용자
지정). 지출 목록 항목은 `spend_items.unit`, 묶음이 없는 분류(사냥의 `소재` 등)는 분류 표의 `unit`, 아이템 구매 · 판매는
아이템 종류 표의 `unit` 이다.

### 결정 5. 기록 id 는 uuid 이고, 옛 기록의 id 도 uuid 로 바꾼다

새 기록은 `expo-crypto` 의 `randomUUID()` 로 만든다. 옛 `시각 + 난수` id 는 이관할 때 uuid 로 바꾼다(사용자 선택). 지금
옛 id 를 가리키는 곳은 없다. 이관할 때 서버 동기화 대기 표(`server_sync_queue`)는 드롭 가격만 가리켰다.

### 결정 6. v1.0.13 스토어 바이너리로 내고, 옛 테이블 둘은 DB 버전 23 이 지운다

[[ADR-078]] 결정 9 와 같은 이유다. OTA 가 실패해 옛 코드로 돌아가도 DB 가 열려야 하므로 v1.0.13 에서는 옛 테이블을
지우지 않았다. v1.0.14 의 DB 버전 23 이 옛 보스 표 넷과 함께 지운다.

### 결정 7. 아이템 종류(장비 · 소비 · 기타 · 캐시)도 서버 표가 기준이다

지금은 앱 상수(`ITEM_KINDS`)뿐이다. 나중에 서버가 기록을 보관할 때(#507) 기록의 종류를 알아야 하므로 서버에 표를 두고,
앱은 분류와 같은 응답 칸으로 받아 번들 사본을 든다(사용자 지정). 표는 key · 이름 · 단위 · 구매 관세 여부 · 차례를 갖는다.
소비 · 기타는 월드 간 거래가 안 되어 관세가 없고, 장비는 수량이 없다. 캐시는 수량을 묻고 관세가 붙는다([[ADR-187]] 결정 7).

### 결정 8. 옛 에픽던전 기록은 형태마다 품목 하나로 나눈다

옛 지출 행은 형태 둘을 사도 금액이 하나다. 이관은 형태마다 품목 하나를 만들고, 그 단계 항목의 단가로 금액을 나눈다.
합이 옛 금액과 다르면 차이를 첫 품목에 붙여 기록 합계가 바뀌지 않게 한다(사용자 선택).

### 결정 9. 옮기기 전에 DB 를 파일째 떠 두고, 옮긴 뒤 건수와 합계를 대조한다

손입력은 되살릴 API 가 없어 옮기다 잃으면 끝이다(사용자 지정 2026-10-25, 기존 데이터 백업이 잘 돼야 한다).

- 버전 15 를 돌기 전에 `VACUUM INTO` 로 DB 를 같은 폴더의 `boss_profitSQLite-before-v15.db` 로 떠 둔다. 이미 있으면 덮지
  않는다. 한 번 실패하고 다시 여는 기기에서 사본이 처음 그대로여야 해서다. 다른 이유로 못 뜨면 옮기지 않는다.
- 옮긴 뒤 지출 · 수입 건수와 메소 · 메포 · 캐시 · 관세 · 수수료 · 사냥 조각 합계를 옛 표와 견준다. 하나라도 다르면 던져 버전
  15 를 통째로 되돌린다. 조용히 덜 옮긴 채 버전을 올리는 것보다 DB 를 못 여는 편이 낫다. 옛 표와 사본은 그대로 남는다.
- 사본은 DB 만큼 크다(실기기 45MB). 옛 표를 다 지운 뒤 한 번 사본 파일을 지운다([[ADR-078]] 결정 11). 지우는 일은 DB 가
  버전 23 까지 열린 뒤에만 불리므로, 버전 15 가 실패해 되돌린 기기에서는 사본이 남는다.
