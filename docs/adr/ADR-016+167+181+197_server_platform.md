# ADR-016+167+181+197 서버 구성

> ⚪ 미구현
> 옛 번호: ADR-227 결정 1 · 2 · 3 · ADR-228 결정 6 · ADR-284 결정 1 · 2 · 정정 3 · ADR-293 정정 4 · ADR-347 결정 1 · 3 ~ 17 · 정정 1 · 2 · ADR-348
> 관련 소스: `server/` · `nexon/http.ts` · 서버 저장소 `maple-routine-server` 의 `src/`

## 배경

앱은 처음에 서버 없이 기기 저장소만 썼다. 그런데 운영자가 사용자에게 공지를 보내거나, 넥슨 로그인
토큰을 서버에서만 다뤄야 하거나, 게임 데이터를 앱 배포 없이 고치는 일은 기기만으로는 할 수 없었다. 그래서
서버를 따로 두었다. 이 문서는 서버를 어디에 어떤 구조로 두는지와, 넥슨 로그인 · 프렌즈 조회처럼 서버가
넥슨과 직접 주고받는 일을 어떻게 하는지 정한다. 서버가 누구를 사람으로 보는지는 [[ADR-017]], 앱이 서버로
보내는 값은 [[ADR-018]], 게임 데이터 표는 [[ADR-020]] 에 있다.

## 결정

### 결정 1. 서버가 꺼져도 앱은 그대로 동작한다

사용자가 적은 기록과 넥슨에서 받은 원본은 기기에 남고, 화면도 기기 데이터로 그린다. 서버에 올라가는 것은
그 데이터에서 계산해 낸 값뿐이다. 그래서 서버가 꺼져 있으면 서버에서만 오는 것(공지 새 글 · 결산 안내 · 직접 완료
단추 · 게임 데이터 갱신)만 멈추고, 기록과 조회는 평소처럼 된다.

이를 위해 `features/*` 는 서버를 직접 부르지 않는다. 서버를 부르는 코드는 `server/` 에만 있고, 넥슨 API 를
`nexon/` 에 모아 둔 것과 같은 방식이다. 조회 어댑터는 실패가 어떤 형태든 `null` 하나만 돌려준다. 화면은
`null` 을 받으면 기기에 있는 사본이나 번들 값을 그대로 쓴다.

게임 데이터는 번들에 없고 처음 켤 때 서버에서 받는다([[ADR-020]] 결정 12). 그래서 이 결정은 기기에 사본을 한 번 받은
뒤에만 지켜진다.

### 결정 2. 서버 코드는 별도 저장소에 둔다

이 저장소에는 앱만 있고, 서버는 `maple-routine-server` 저장소에 있다. 서버는 심사 없이 언제든 배포되지만 앱은
스토어 심사와 OTA 를 거친다. 한 저장소에 두면 커밋 하나가 두 배포에 함께 들어가서, 어느 쪽이 이미 나갔는지 헷갈린다.

그 대신 요청과 응답의 형식(계약)이 두 저장소에 따로 적혀 있어서, 한쪽만 바꾸면 타입 검사로 잡을 수 없다.
그래서 앱의 어댑터는 응답을 받을 때마다 형식을 검사하고, 어긋난 값은 버린다. 칸을 더하거나 바꿀 때는
두 저장소를 함께 본다.

### 결정 3. Oracle 무료 인스턴스 두 대에 나눠 둔다

| 인스턴스 | 하는 일 |
|---|---|
| 앱 박스 | nginx 와 서버 애플리케이션. 공개 IP 와 인증서(`mapleroutine.store`)가 여기 있다 |
| DB 박스 | Postgres. 같은 사설망에서만 접속할 수 있다 |

두 대로 나눈 것은 용량보다 격리 때문이다. 인스턴스에 swap 이 없어서 메모리가 넘치면 운영체제가 프로세스
하나를 골라 죽이는데, 한 대에 같이 있으면 서버 애플리케이션의 버그로 Postgres 가 죽을 수 있다. 유료 플랜으로
올리지 않는다(사용자 지정).

집의 미니 PC 는 서버를 돌리지 않고, DB 덤프를 받아 두는 백업용으로만 쓴다. 집 회선은 업로드가 느려서 프렌즈
조회처럼 원본을 그대로 흘려 보내는 일을 감당하지 못한다.

### 결정 4. 서버는 NestJS 로 역할마다 파일을 나눈다

컨트롤러는 HTTP 만, 서비스는 로직만, 리포지토리는 SQL 만, 잡은 주기 작업만 맡는다. 어느 역할이 어느 역할을
부를 수 있는지는 의존성 주입으로 강제한다. 폴더 이름으로만 약속해 두면 다음 작업에서 경로 · 로직 · SQL 이 다시 한 파일에 섞인다.
HTTP 엔진은 Fastify, DB 는 Drizzle, 요청 본문과 환경변수 검사는 zod 다. 기능은 모두 `src/modules/` 아래에
두고, 여러 모듈이 같이 쓰는 설정 · DB · 넥슨 클라이언트만 `src/` 바로 아래에 둔다.

옛 서버 코드는 `legacy/` 폴더에 그대로 옮겨 두었다. 새 코드는 `legacy/` 를 가져다 쓰지 않는다.

### 결정 5. 표의 기본키는 uuid 하나이고, 값이 정해진 칸은 ENUM 이다

모든 표의 기본키는 서버가 만드는 uuid 한 칸이고, 자연키는 `UNIQUE` 로 건다. 값의 조합이 유일해야 할 때도
일반 인덱스가 아니라 `UNIQUE` 로 건다(`drop_prices` 의 `(user_id, drop_record_id)`). 조회 속도는 같고 중복
행만 거절하기 때문이다. 규칙은 앱과 같다([[ADR-077]] 결정 8). 플랫폼(`ios` · `android`), 공지
분류, 보스 난이도처럼 값이 정해진 칸은 `text` 가 아니라 Postgres ENUM 으로 둔다. `text` 로 두면 값이 틀려도
바로 에러가 나지 않는다. 예를 들어 플랫폼이 틀리면 로그인은 되고 14일 뒤 토큰 갱신만 실패한다. 값을
더하는 마이그레이션은 같은 파일 안에서 그 값을 쓰지 않는다. Postgres 가 같은 트랜잭션에서 새 값을 쓰는 것을
거부하기 때문이다.

암호화해 저장하는 값은 `버전 1바이트 · iv · tag · 암호문` 을 한 칸에 이어 붙인다. 첫 바이트로 어느 키로
복호화할지 정하므로(`TOKEN_ENC_KEY_V1`, 다음은 `V2`), 키를 바꿀 때 모든 사용자를 다시 로그인시키지 않아도 된다.

시각은 `timestamptz` 로 저장하고, 관리 화면과 CLI 처럼 사람이 읽는 곳에서는 모두 KST `YYYY-MM-DD HH:mm:ss` 로
보여 준다. 브라우저나 컨테이너의 시간대에 맡기면 화면마다 다른 시간대로 보였다. 앱에 주는 `/v1/*` 응답의 시각은
UTC ISO 문자열 그대로이고, 앱이 받아서 기기 시계 기준으로 보여 준다.

### 결정 6. 넥슨 로그인은 서버가 콜백을 받고, 앱은 키 두 개로 세션을 받는다

넥슨 보안 가이드라인은 액세스 토큰을 서버에서만 관리하고, `state` 를 안전한 곳에 두고 한 번만 쓰라고 한다.
그래서 `redirect_uri` 를 서버 주소(`https://mapleroutine.store/v1/auth/nexon/callback`)로 두고, 토큰 교환도
서버가 한다. 앱은 넥슨 토큰을 받지 않고 서버가 발급한 세션 하나만 가진다.

```
① 앱   POST /v1/auth/nexon/login { platform }         → { authorizeUrl, redeemKey }
② 앱   인증 세션으로 authorizeUrl 을 연다. 사용자가 넥슨에서 로그인하고 동의한다
③ 넥슨 GET /v1/auth/nexon/callback?code&state
       서버가 state 로 짝을 찾아 교환 · userinfo 를 하고 세션을 만든다
       → 302 com.mapleroutine.app://oauth/callback?receipt=…
④ 앱   POST /v1/auth/nexon/session { redeemKey, receipt } → 세션
```

키가 두 개인 이유는 공격 두 가지를 함께 막기 위해서다. `redeemKey` 는 ① 의 https 응답으로만 오므로 로그인을
시작한 앱만 가진다. `receipt` 는 ③ 의 리다이렉트로만 오므로 넥슨에 로그인한 기기만 가진다. 다른 앱이 같은 스킴으로
리다이렉트를 가로채도 `redeemKey` 가 없고, 남에게 로그인 링크를 보내는 공격자는 `redeemKey` 는 있어도 `receipt`
가 피해자 기기로 간다. ④ 가 둘을 다 요구하므로 어느 쪽도 세션을 받지 못한다.

- `state` 는 앱에 주지 않는다. 확인은 ③ 에서 서버가 한다.
- ③ 은 `claimed_at IS NULL` 인 짝만 SQL 한 문장으로 선점해서, 같은 `state` 를 두 번 쓰지 못하게 한다.
- ③ 은 실패해도 늘 302 를 낸다. 에러 화면을 내면 사용자가 브라우저에 갇혀 앱으로 돌아오지 못한다. 교환이나
  userinfo 가 실패하면 짝을 지우고 302 를 낸다.
- 넥슨 동의 화면에서 `취소` 를 누르면 넥슨은 ③ 을 `?error_name=user_cancel_consent` 로 부른다. 표준 OAuth 의
  `error` 가 아니고, `state` 도 `code` 도 없다(2026-11-04 운영 nginx 로그로 확인). 서버는 `receipt` 없이
  돌려보낼 때 넥슨이 보낸 `error_name` 을 그대로 실어 `com.mapleroutine.app://oauth/callback?error_name=…` 로
  302 한다. 앱이 이 값을 보고 실패와 취소를 가르기 때문이다. `state` 가 없어 어느 짝인지, 어느 플랫폼인지
  모르지만, 두 플랫폼이 같은 스킴으로 돌아오므로 돌아갈 주소는 하나다. 짝은 선점되지 않은 채 남았다가 10분 뒤
  1분 잡이 지운다.
- ④ 의 답은 셋이다. 세션이 있으면 `ok`, ③ 이 넥슨과 주고받는 중이면 `pending`(앱이 1초 뒤 다시 묻는다), 짝이 없으면
  404 다. 404 는 만료 · 실패 · 취소 · 이미 받음을 모두 포함하고, 앱은 다시 로그인하라고 안내한다.
- 로그인을 시작해 만든 짝은 10분 동안만 쓸 수 있다. 사용자가 넥슨 화면에서 로그인하는 시간이다.
- 안드로이드도 iOS 와 같은 커스텀 스킴으로 돌아온다. 서명을 확인한 앱만 여는 App Link(`autoVerify`)로는 바꾸지
  않는다. 다른 앱이 스킴을 가로채도 `redeemKey` 가 없어서, 그 한 번의 로그인이 실패할 뿐이다. App Link 가 더 막는
  것은 다른 앱이 직접 로그인을 시작하는 경우다. 이 경우는 iOS 도 막지 못한다. `ASWebAuthenticationSession` 은
  로그인을 시작한 앱에 콜백을 돌려주기 때문이다. 그래서 안드로이드만 바꿔서는 이 위험이 줄지 않는다. 반대로 App Link
  검증에 실패한 기기는 로그인할 때마다 브라우저 페이지를 한 번 더 거쳐야 앱으로 돌아온다.

앱의 넥슨 로그인 입구는 `NEXON_LOGIN_ENABLED` 로 켜고 끈다([[ADR-025]] 결정 9). 로그인 화면과 앱 쪽 흐름은 auth
문서가 다룬다.

### 결정 7. 세션 원본은 봉해서 60초 동안만 꺼낼 수 있게 하고, 1분마다 정리한다

③ 과 ④ 는 서로 다른 요청이라 그 사이에 서버가 세션 값을 보관해야 한다. 세션 표(`nexon_sessions`)에는
해시만 있으므로, 짝 표(`nexon_login_attempts`)에 세션 원본을 암호화해 두고 ④ 가 꺼내 가면서 짝을 지운다.
④ 는 봉한 시각(`sealed_at`)부터 60초 안에만 성공한다. `redeemKey` 와 `receipt` 도 해시로만 저장해서, DB 가 유출돼도
④ 를 다시 해 볼 수 없다.

1분 간격 잡이 한 문장으로 다음을 지운다.

- 선점되지 않고 10분이 지난 짝
- 봉한 뒤 2분이 지난 짝과, 그 짝에 달린 세션(④ 가 오지 않아 아무도 받아 가지 않는 세션이다)
- 선점한 뒤 2분이 지나도 봉하지 못한 짝(③ 이 중간에 죽은 경우)
- 갱신 토큰이 만료된 세션

짝을 먼저 지우면 세션을 가리키던 값이 사라져 남은 세션을 영영 못 찾는다. 그래서 짝과 세션을 한 문장으로
지운다. 그 결과 봉한 원본이 DB 에 남아 있는 시간은 길어야 3분이다.

받아들인 손실이 둘 있다. ④ 의 응답이 중간에 사라지거나, 브라우저가 떠 있는 동안 앱이 꺼지면 그 로그인은
실패하고 사용자가 다시 눌러야 한다. 막으려면 원본을 더 오래 두거나 기기에 평문을 저장해야 해서 그쪽을 고르지 않았다.

### 결정 8. 넥슨 토큰은 세션마다 한 번에 하나만 갱신하고, 거절되면 세션을 지운다

신원 확인과 토큰 발급은 다른 일이다. 신원 확인은 세션 해시로 행을 찾아 수명만 보고 넥슨을 부르지 않는다.
그래서 드롭 가격 쓰기처럼 넥슨 토큰이 필요 없는 경로가 토큰 갱신을 일으키지 않는다.

토큰은 `tokenFor(sessionId)` 한 곳에서만 발급한다. 만료 60초 전이면 갱신하고, 같은 세션의 갱신이 진행 중이면 그
결과를 기다린다. 넥슨의 갱신 토큰은 쓸 때마다 바뀌고 옛것은 바로 무효가 되어서, 같은 토큰으로 갱신을 둘 보내면 하나만
성공한다. 서버 안에서 갱신을 하나로 묶으면 그런 충돌이 생기지 않으므로, 갱신이 거절됐다면 정말로 무효가 된 토큰이다.
그래서 세션 행을 지우고 다시 로그인하라고 답한다.

프렌즈 조회가 넥슨에서 `OPENAPI00012` 를 받아도 세션을 지운다. 사용자가 넥슨 Open API 마이 페이지에서 정보 활용
동의를 철회하면, 넥슨이 1분 안에 그 사용자의 액세스 토큰과 갱신 토큰을 모두 400 `OPENAPI00012` 로 거절한다
(2026-11-04 실측). 저장한 액세스 토큰은 만료 60초 전까지 갱신하지 않으므로, 조회의 거절을 보지 않으면 갱신이
거절될 때까지 최대 30분 동안 조회 실패만 보인다. 세션을 지우는 일은 갱신 거절과 같은 `TokenService` 의 함수
하나가 한다. 앱은 `fail` 줄의 코드를 보고 로그인을 지우지 않는다. 지우는 판단을 서버 한 곳에 두어야 서버에는
세션이 남았는데 앱만 로그인을 지우는 식으로 둘이 갈리지 않는다.

### 결정 9. 프렌즈 조회는 서버가 모아서 NDJSON 스트림으로 보낸다

로그인한 사용자의 프렌즈 경로 여섯(`cube` · `starforce` · `potential` · `soul-potential` · `character-state` ·
`character-list`)은 서버가 사용자 토큰으로 넥슨을 부른다. 앱은 작업 목록 하나를 `POST /v1/friends/stream` 으로
보내고, 서버가 그 작업들을 넥슨에 돌리면서 결과를 줄 단위로 보낸다. 한 건씩 중계하면 사용자 한 명의 조작이 서버
요청 수백 건이 되지만, 이렇게 하면 서버로 가는 요청은 한 건이다.

앱 쪽에서 묶는 것은 `nexon/http.ts` 다. 화면과 회차는 넥슨 조회를 작업 하나씩 부르므로, 세션마다 150ms 동안 들어온
작업을 모아 요청 하나로 보낸다. 같은 작업이 두 번 들어오면 한 번만 싣는다. 한 세션이 동시에 여는 요청은 둘까지이고,
그동안 들어온 작업은 다음 요청에 실린다. 작업마다 자기 `done` · `fail` 줄이 오면 바로 결과를 돌려준다. 그래서 늦게
끝나는 작업이 먼저 끝난 작업을 붙잡지 않는다.

- 전에는 작업 하나가 요청 하나였다. v1.0.13 에서 넥슨 로그인을 열자 캐릭터 설정의 활동 판정(캐릭터 26 × 날짜 7)이
  1초에 요청 180건을 보냈고, nginx 의 속도 제한(IP 당 초당 10건, 순간 20건)에 걸려 436건이 503 으로 돌아왔다
  (2026-11-06). 서버의 동시 회차 상한(결정 10)도 사용자 한 명이 다 차지할 수 있었다.
- 한 세션이 요청을 보내는 간격은 150ms 이상이다. 앞 요청이 끝났어도 앞 요청을 보낸 지 150ms 가 안 됐으면 기다렸다가
  보낸다. 서버 회차는 20~50ms 에 끝나서, 끝나는 대로 다음 요청을 보내면 한 세션이 1초에 20건을 넘긴다. OTA 1.0.13+1 이
  그렇게 돌아 강화 내역 수집 한 번이 1분에 요청 327건을 보냈고 그중 196건이 503 이었다(2026-11-06). 150ms 면 1초에
  7건을 넘지 않는다. 공지 · 결산 · 사용 로그도 nginx 의 같은 구역을 쓰므로 초당 10건보다 여유를 둔다.
- 요청이 503 을 받으면 그 세션은 30초 동안 프렌즈 조회 요청을 보내지 않는다. 그동안 들어온 작업은 요청 없이 바로 못 닿은
  것으로 돌려준다. 503 은 곧바로 돌아오고, 수집기는 실패한 작업을 넘기고 다음 작업으로 간다. 그래서 쉬지 않으면 남은
  작업이 몇 초 만에 전부 503 으로 끝나고, 같은 IP 의 결산 · 공지 · 사용 로그까지 함께 503 을 받는다. 30초는 서버가
  동시 회차 상한(결정 10)의 503 에 싣는 `Retry-After` 값이다. nginx 의 503 에는 `Retry-After` 가 없어 같은 값을 쓴다.
  못 닿은 작업은 원장에 적히지 않아 다음 회차에 다시 온다.
- 로그인 자격이면 창 채우기(`features/schedule-window/window.ts`)와 강화 내역 수집(`features/enhancement-history/collect.ts`)이
  동시 상한 없이 작업을 한꺼번에 넘긴다. 요청 수가 아니라 요청 하나에 실린 작업 수가 처리량을 정하기 때문이다. 수집기가
  작업을 3개씩만 넘기면 요청 간격 150ms 에서 120일이 6초 걸리고, 한꺼번에 넘기면 요청 1건으로 1.1초에 끝난다
  (시뮬레이션, 서버 작업당 30ms). 넥슨을 부르는 속도는 서버가 정한다(결정 10 의 동시 4건 · 초당 900건). 두 수집기의 동시
  상한(`WINDOW_CALL_LIMIT` 6 · `HISTORY_CALL_LIMIT` 3)은 API 키가 넥슨을 직접 부를 때의 한도를 지키는 값이라 API 키에만 건다.
- 한 요청에 싣는 작업은 500개까지다. 서버가 받는 상한은 1,000개다(`MAX_TASKS`).
- 묶인 작업은 결정 10 의 시간 · 바이트 예산을 함께 쓴다. 예산에 걸려 시작하지 못한 작업은 `done` 이 없어 실패로
  돌아가고 다음 회차에 다시 온다.
- 요청이 거절되거나(401 · 503) 끊기면 그 요청에 실린 작업이 모두 같은 실패를 받는다.

```
{"t":"page","kind":"cube","date":"2026-10-01","n":1,"body":<넥슨 응답 원본>}
{"t":"done","kind":"cube","date":"2026-10-01","pages":1}
{"t":"fail","kind":"cube","date":"2026-10-02","status":400,"code":"OPENAPI00009"}
{"t":"end","reason":"done" | "deadline" | "budget" | "relogin"}
```

- 넥슨 응답은 가공하지 않고 그대로 싣는다. 가공하려면 `src/data` 의 게임 수치가 서버로 넘어가야 하는데, 그 값은
  사용자 확인을 거쳐야 하는 데이터라 이 작업에 넣지 않았다.
- 한 줄은 넥슨 응답 한 쪽이다. 작업 하나가 수십 쪽이 될 수 있어서, 작업 단위로 묶으면 기기가 큰 줄을 통째로 메모리에 올려야 한다.
- `fail` 은 넥슨 본문의 `error.name` 을 `code` 로 함께 싣는다. 앱이 400 을 날짜 문제 · 결산 중 · 영구 불가로 나눠서
  처리하기 때문이다.
- 넥슨이 토큰을 거절하면(`OPENAPI00012`) 그 작업은 `fail` 을 싣지 않고, 세션을 지운 뒤 회차를 `relogin` 으로 끝낸다.
  남은 작업도 시작하지 않는다. `fail` 을 실으면 앱이 그 작업을 조회 실패로 읽어 로그인 만료 창을 띄우지 않는다.
- 앱은 `done` 을 받은 작업만 기기 원장에 적는다. 그래서 회차가 중간에 끊겨도, 적히지 않은 작업은 다음 회차에 다시 온다.
  `end` 없이 끊겨도 같다.
- 응답은 gzip 으로 줄마다 내보내고, 15초마다 빈 줄을 하트비트로 보낸다. nginx 는 이 경로만 버퍼링을 끄고
  읽기 타임아웃을 60초로 둔다. 서버도 `X-Accel-Buffering: no` 를 함께 보내서, 한쪽 설정이 바뀌어도 버퍼링으로
  돌아가지 않게 한다.
- 앱이 연결을 끊으면 서버도 진행 중인 넥슨 요청과 대기 중인 요청을 취소한다.
- 개발자 키로 부르는 비프렌즈 경로는 서버를 거치지 않고 앱이 계속 직접 부른다.

앱에서 받는 쪽은 `server/friends-stream.ts` 다. RN 의 기본 `fetch` 는 응답 본문을 스트림으로 주지 않아서
`expo/fetch` 로 받고, 줄바꿈에서 잘라 읽는다.

### 결정 10. 프렌즈 조회의 메모리와 넥슨 호출 수에 상한을 둔다

회차 하나가 받는 바이트 수는 사용자의 활동량에 달려 있어 상한이 정해져 있지 않다. 그래서 상한을 넷 둔다. 값은 모두
환경변수이고 아래는 시작값이다.

| 상한 | 값 | 이유 |
|---|---|---|
| 회차 하나의 동시 넥슨 요청(`FRIENDS_FANOUT`) | 4 | 앱의 다운로드 속도가 병목이라 더 열어도 빨라지지 않고 메모리만 늘어난다 |
| 동시 회차(`FRIENDS_MAX_RUNS`) | 40 | 넘으면 기다리게 하지 않고 바로 503 과 `Retry-After: 30` 을 낸다. 기다리게 하면 그 연결도 메모리를 차지한다 |
| 새 작업을 시작하는 시간 · 바이트(`FRIENDS_RUN_DEADLINE_MS` · `FRIENDS_RUN_BYTES`) | 120초 · 16MB | 진행 중인 작업은 끝까지 보낸다. 중간에 자르면 그 작업이 매번 같은 곳에서 잘려 영영 적히지 않는다 |
| 플랫폼마다 넥슨 초당 호출(`FRIENDS_NEXON_RPS`) | 900 | 프렌즈 API 의 상한이 애플리케이션마다 초당 1,000 이다. 그 가까이까지 쓰고(사용자 지정 2026-11-11), 넥슨과 서버의 1초 경계가 어긋나는 몫으로 10% 를 남긴다. 작은 회차는 빨리 끝나서 동시 회차 상한만으로는 이 한도를 지킬 수 없다 |

- 넥슨의 호출 한도는 둘이고 서로 다르다(사용자 확인 2026-11-11). 섞어 적지 않는다.
  - **API 키 한도**: 키 하나의 한도다. 서비스 단계가 초당 500건 · 하루 2,000만 건, 개발 단계가 초당 5건 · 하루 1,000건이다. 서버의 공지 ·
    결산 확인과 앱의 사용자 키 · 번들 개발자 키 호출이 이 한도를 받는다.
  - **프렌즈 API 한도**: 넥슨 로그인 토큰으로 부르는 프렌즈 경로의 한도다. 애플리케이션마다 초당 1,000건이다. 애플리케이션은 iOS 와
    안드로이드가 따로 등록되어 있어([[ADR-017]] 결정 1) 플랫폼마다 따로 센다.
- 서버의 프렌즈 호출은 플랫폼마다 초당 1,000건을 넘지 않게 하되, 그 가까이까지 쓴다(사용자 지정 2026-11-10 · 11-11). 그래서 상한을
  400건에서 900건으로 올린다.
- 상한까지 쓰려면 요청을 1초 안에 고르게 내보내야 한다. 지금 버킷(`nexon-bucket.ts`)은 1초마다 토큰을 한꺼번에 채운다. 그러면 한 초의
  끝과 다음 초의 처음에 요청이 몰려, 1초를 어디서 잘라 보느냐에 따라 상한의 두 배까지 나갈 수 있다. 400건일 때는 두 배여도 800건이라
  1,000건 안이었지만, 900건이면 1,800건이 된다. 그래서 요청 사이에 `1초 ÷ 상한` 의 간격(900건이면 약 1.1ms)을 둔다(Bottleneck 의
  `minTime`).
- 운영 박스의 환경변수에 `FRIENDS_NEXON_RPS` 가 적혀 있으면 그 값도 함께 바꾼다. 코드의 기본값만 바꾸면 운영은 옛 값으로 돈다.

- 서버는 넥슨 응답 한 쪽을 받으면 바로 내보내고, 소켓 쓰기가 밀리면 비워질 때까지 기다린 뒤 다음 쪽을 요청한다.
  모아 두거나 미리 요청하면 그만큼 메모리에 쌓인다.
- 작업 하나는 50쪽까지만 따라간다. 커서가 끝나지 않는 경우를 막는 상한이다.
- 넥슨 요청마다 10초 타임아웃을 건다. 응답 없이 멈춘 요청 하나가 회차 슬롯을 계속 차지하지 않게 하기 위해서다.
- 넥슨이 429 를 주면 그 플랫폼의 버킷을 1초 비우고 그 쪽만 한 번 다시 시도한다. 또 429 면 `fail` 이다.

### 결정 11. 넥슨 결산 중인지는 서버가 밤마다 확인해 보관한다

결산의 시작과 끝은 날마다 달라서 앱이 시각만으로 판단할 수 없다. 그래서 서버가 환경변수 `SETTLEMENT_OCID` 의 캐릭터 하나로
넥슨에 어제 날짜의 `character-state` 를 물어 판정하고, 앱은 `GET /v1/settlement` 로 그 결과만 받는다.

- KST 00:00:01 부터 06:00:01 까지 10분마다(`00:00:01 · 00:10:01 · … · 06:00:01`) 확인한다(사용자 지정 2026-11-10). 자정에서
  1초 띄운 것은 넥슨과 서버의 시계 차이 때문이다. 앱이 0시 ~ 2시 회차를 시작할 때 이 값을 먼저 읽고 결산 중이면 어제 날짜를 묻지
  않으므로([[ADR-021]] 결정 14), 결산이 시작되자마자 판정이 서야 한다. 서버가 그 시간에 다시 켜지면 바로 한 번 확인해서, 다음
  확인까지 결산 아님으로 답하지 않는다.
- 400 `OPENAPI00009` 면 결산 중이다. 200 이 오면 결산 중을 본 뒤라면 끝난 것이고, 아직 못 봤다면 시작 전이다.
- 6시가 지나면 결산 아님이다. 06:00:01 확인에서도 `OPENAPI00009` 가 오면 그대로 결산 아님으로 둔다(사용자 선택 2026-11-11). 그
  확인이 그날 마지막이라, 결산 중으로 두면 다음 날 0시까지 그 판정을 풀 확인이 없고 앱은 하루 종일 어제 날짜를 묻지 않는다.
- 그 밖의 실패(네트워크 · 키 · `OPENAPI00003`)는 모름이고 판정을 바꾸지 않는다. 실패를 결산 중으로 읽으면 넥슨이 멀쩡한
  날에도 안내가 뜨고, 결산 아님으로 읽으면 결산 중에 넥슨이 잠깐 죽을 때 안내가 사라졌다가 다시 뜬다.
- `startedAt` 은 관측 시각이 아니라 그 밤의 날짜 00:00 KST 다. 서버가 다시 켜져도 같은 값이 나가서, 앱에서 사용자가 닫은
  안내가 다시 뜨지 않는다.
- 판정은 서버 프로세스 메모리에 둔다. 인스턴스가 하나라 그것으로 충분하다.

### 결정 12. 직접 완료를 여는 보스는 보스 표를 가리키고, 닫은 줄은 지우지 않는다

운영자가 관리 화면에서 직접 완료를 여는 보스는 `manual_completion_bosses` 표에 둔다. 보스는 `boss_id` 로 `bosses` 표를
가리키므로 관리 화면의 보스 목록도 그 표에서 나온다. 앱이 받는 형식(`{ boss, from }`)은 그대로이고, 서버가 보스 key 로
바꿔 준다.

```
manual_completion_bosses
  id         uuid  PK
  boss_id    uuid  FK → bosses(id)
  from_date  text  여는 날 KST YYYY-MM-DD
  opened_at  timestamptz
  closed_at  timestamptz   NULL 이면 열려 있다
  UNIQUE (boss_id) WHERE closed_at IS NULL
```

열린 줄만 보스마다 하나다. 닫았다가 다시 열면 닫은 줄은 남고 새 줄이 생겨서, 언제 열고 닫았는지 이력이 남는다. 닫기는
보스 key 가 아니라 줄 id 로 한다(`DELETE /admin/manual-completion/:id`). 이력이 여럿인 표에서 어느 줄인지 분명하게 하기
위해서다.

### 결정 13. 관리 화면은 테두리와 구분선 없이 바탕색 · 간격 · 그림자로 면을 가른다

관리 화면의 모양은 서버 `modules/admin/views/layout.ts` 하나가 정한다. 차가운 회색 바탕 · 코발트 강조 · 왼쪽 메뉴다(2026-10-15
시안 B). 여기에 앱과 같은 원칙을 건다. 테두리와 구분선을 쓰지 않고, 면은 바탕색 차이 · 간격 · 그림자로 가른다(사용자 지정
2026-11-06). 앱과 관리 화면이 면을 짓는 법이 다르면 한쪽 부품을 다른 쪽에 옮길 때마다 다시 그려야 한다.

| 부품 | 지금 | 바꾼 뒤 |
|---|---|---|
| 카드 · 지표 칸(`card` · `stat`) | 1px 테두리와 옅은 그림자 | 흰 면과 그림자. 페이지 바탕(`--bg`)과의 차이로 갈린다 |
| 왼쪽 메뉴(`nav` · `group`) | 오른쪽 선 · 묶음 왼쪽 선 | 흰 면. 묶음 안은 들여쓰기로만 가른다 |
| 표(`th` · `td` · `mini`) | 머리 줄 아래 선 · 줄마다 아래 선 | 머리 줄은 바탕색으로, 줄 사이는 선 없이 올리면 바탕색이 바뀐다 |
| 고른 줄(`tr.open`) | 왼쪽 코발트 막대 | 코발트 옅은 바탕(`--accent-tint`)만 |
| 입력 칸(`input` · `select` · `textarea`) | 1px 테두리 | 옅은 회색으로 채운 면 |
| 보조 단추(`btn.ghost`) · 꼬리표(`tag`) | 테두리 | 옅은 회색으로 채운 면 |
| 안내(`msg`) · 코드(`code`) · 묶음 칸(`sub`) | 테두리 | 바탕색만 |
| 묶음 제목(`section`) · 목록(`card > .list`) | 위 선 · 줄 사이 1px 선 | 간격 |
| 그림 화면(`assets.ts`) | 줄과 칸을 가르는 선 넷 | 간격과 바탕색 |

- 차트의 눈금선과 기준선은 남긴다. 면을 가르는 선이 아니라 값을 읽는 눈금이다. 앱의 통계 차트도 눈금선을 그린다.
- 키보드 초점 표시(`:focus-visible` 의 outline)는 남긴다. 지금 어디에 있는지 보여 주는 표시라 면을 가르는 선이 아니다.
