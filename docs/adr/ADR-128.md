# ADR-128 — React Native 로 옮긴다: 뷰만 다시 쓰고, 로직과 데이터는 있던 자리에 둔다

**날짜**: 2026-08-11
**상태**: 결정 · **단계 0~4 구현 완료**(2026-08-13) · **결정 7(OTA)은 [[ADR-137]] 이 닫았다**(2026-08-14) ·
5단계 남음 — 실기기 검증·롤아웃.
화면은 다 옮겨졌다(자리표시자 라우트 0 · `@keyframes` 화면 몫 0). **결정 7 의 OTA 프로토콜은
그대로 남아 있고**(모달·섹션은 다 그렸으나 배선 없음), 못 옮긴 것 **셋**이 남는다 —
[[ADR-065]] 결정 3 캐시 삭제 실패 토스트 하나만 남았다(`migration/README.md` «4단계 결과» ⓐ).
[[ADR-047]] 중첩 sticky 는 **안 만들기로 판정났고**([[ADR-131]]), [[ADR-088]] 테마 배경은 구현됐다.

**드롭 연출은 그 목록에서 빠졌다**(2026-08-13) — 재생 엔진을 되살렸고 [[ADR-103]] 의 1.5배가
RN 에서도 맞는다는 것을 사용자가 눈으로 확인했다.
**첫 육안 확인을 했다**(2026-08-13, iOS 시뮬레이터). 그 한 번이 자동 검사 1,398개가 전부 초록인
채로 숨어 있던 **결함 아홉**을 드러냈다 — 설정 탭이 통째로 자리표시자, 하단바 아이콘 부재, 시트가

공통점이 있다: **전부 «값은 맞는데 어디에 걸었나» 이거나 «넘겼지만 그려지지 않는다»** 라, 프롭을
검사하는 테스트로는 원리적으로 못 잡는다.

*"예전과 같아 보이는가"* 는 여전히 5단계 몫이다 — 육안 대조 67항목이 그 목록이고, 위 아홉은

## 맥락

[[ADR-001]] 이 Capacitor를 고른 이유는 *"웹 기술로 앱을 내고, 스토어를 거치지 않고 고친다"* 였다.
그 판단은 지금도 유효하다 — OTA는 3년간 이 저장소의 가장 큰 자산이었다.

문제는 **웹뷰가 하나의 거대한 네이티브 뷰**라는 데서 오는 한계가 제품 방향과 충돌하기 시작했다는 것이다.

### 광고 인벤토리가 구조적으로 막혀 있다

```
[ Activity ]
  ├─ WebView          ← 보스 카드 리스트 전체가 이 안의 DOM
  └─ AdMob BannerView ← 형제 네이티브 뷰. 위/아래 겹치는 것만 가능
```

DOM 카드 3번과 4번 **사이**에 네이티브 뷰를 넣을 자리가 없다. 스크롤 동기화도 불가능하다(웹뷰 내부
스크롤을 네이티브가 모른다). 그래서 지금 쓸 수 있는 형태는 전면광고([[ADR-090]])와 상/하단 고정
배너뿐이고, **네이티브 광고(Native Advanced)는 플러그인이 지원조차 하지 않는다.**

이것이 단순한 수익 최적화 문제가 아닌 이유는, **전면광고를 걷어내고 인라인으로 가는 선택지 자체가
없기** 때문이다. 전면광고는 탭 전환마다 흐름을 끊고, 그래서 [[ADR-090]] 이 30분 게이트를 두고 있다.
거슬리지 않으면서 노출을 늘리는 경로가 웹뷰에는 존재하지 않는다.

### 화면 전환을 손으로 만들고 있다

[[ADR-120]] 이 남긴 것은 iOS 스타일 push 스택의 **자체 구현**이다.

| 파일 | 줄 |
|---|---|
| `lib/stack-transition.ts` · `features/screen-stack/store.ts` · `lib/preloaded-screen.tsx` · `lib/use-stack-location.ts` 외 | ~955 |
| `BackGesturePlugin.java` · `SystemBarsPlugin.java` | 328 |

그 과정의 흉터가 주석에 남아 있다 — `transform` 이 걸리면 `fixed` 후손의 containing block이 뷰포트가
아니게 되는 CSS 사양 문제, `React.lazy` 의 300ms fallback 스로틀(콜드 305ms 계측), `startTransition`
이 안 먹히는 이유(`BrowserRouter` 가 외부 스토어 구독). **웹뷰에서 네이티브를 흉내 내느라 생긴
비용이고, 앞으로도 그 영역을 건드릴 때마다 같은 종류로 계속 나온다.**

### 그런데 OTA를 잃는다고 오해하고 있었다

전환을 망설이게 한 것은 *"RN으로 가면 OTA를 잃는다"* 였는데, **사실이 아니다.**

RN 번들은 Hermes에서 도는 인터프리터 코드이고, Apple 개발자 프로그램 라이선스 계약 §3.3(b)의
*"Interpreted code may be downloaded to an Application…"* 과 Google Play Device and Network Abuse
정책의 *"…code that runs in a virtual machine or an interpreter"* 예외에 **똑같이** 들어간다. 예외의
조건은 **런타임 종류가 아니라 인터프리터 여부**다. 웹뷰는 그 예외를 쓰는 한 가지 방법일 뿐이었다.

### 그리고 이식 비용이 생각보다 낮다

[[ADR-003]]·[[ADR-005]] 가 강제해 온 어댑터 경계 덕분이다. DOM 의존을 레이어별로 실측한 결과:

| 레이어 | 무수정 이식 가능 (DOM·Capacitor 둘 다 미참조) |
|---|---|
| `data/` `types/` `nexon/` | **30 / 30 (100%)** |
| `features/` | **39 / 41 (95%)** |
| `lib/` | **41 / 49 (84%)** |
| `storage/` | **7 / 21 (33%)** — 나머지 14는 플러그인을 **직접** import 한다 |
| **합계** | **117 / 141 (83%)** |

나머지 24개의 처리는 셋으로 갈린다 — **포트 역전 후 이식 15**(`storage/` 14 · `lib/use-system-back`),
**DOM 의존 수정 후 이식 2**(`features/theme/store` · `features/onboarding/store`), **삭제 7**(`lib/` 의
전환 machinery).

`storage/` 가 [[ADR-003]]·[[ADR-005]] 의 어댑터 레이어이면서도 플러그인을 직접 import 하는 것은 모순이
아니다 — 그 규칙이 금지한 것은 **`features/*` 가 직접 접근하는 것**이고, 실제로 `features/` 의 Capacitor
직접 import 는 **0개**다. 어댑터가 어댑티를 아는 것은 정상이고, 다만 그 방향을 뒤집어야 core 로 갈 수 있다.

`lib/` 에서 걸린 7개 중 6개는 **포팅 대상이 아니라 삭제 대상**이다(`stack-transition` ·
`use-swipe-back` · `use-pull-to-refresh` 등 — react-navigation이 대체한다). **DOM 의존이 정확히
"RN이 없애주는 코드"에만 몰려 있다.**

## 결정

### 결정 1 — Capacitor에서 React Native로 전환한다

[[ADR-001]] 을 대체한다. 동인은 **광고 인벤토리**이고, 화면 전환 machinery 소멸(~1,283줄)과 브리지
성능(JSON 직렬화 → JSI)은 부수 이득이다.

전환하지 않을 근거였던 OTA는 **성립하지 않는다**(맥락 참고). `expo-updates` 로 동등하게 유지한다.

### 결정 2 — Flutter는 기각한다

같은 문제를 푸는 다른 후보였으나 **이 프로젝트의 우선순위 두 가지 모두에서 가장 약하다.**

| | Capacitor | RN | Flutter |
|---|---|---|---|
| OTA | 자유 | 자유 | **Shorebird 단독 · 유료 · 포크된 엔진 · iOS 인터프리터 강제로 패치 코드가 느려짐** |
| 인라인 광고 | 불가 | 네이티브 뷰 그대로 | **PlatformView 경유 — Android 9↓ 성능 저하, iOS 48~55fps 보고, 화면 진입 전 임프레션 집계로 AdMob 밴 위험** |
| 기존 자산 재사용 | — | **83% 무수정 + 12% 포트 역전 후 이식** | **0% (Dart 전면 재작성)** |
| 재작성 규모 | — | 12.3k줄 + 테스트 78 | **27.6k줄 + 테스트 198** |

특히 **임프레션 조기 집계**는 그냥 넘길 문제가 아니다. `native/ads.ts` 가 개발 빌드에 테스트 ID를
강제하는 이유가 *"무효 트래픽으로 AdMob 계정이 정지될 수 있고, 그건 되돌리기가 매우 어렵다"* 인데,
**프레임워크가 알아서 가짜 임프레션을 만드는** 구조는 그 원칙과 정면으로 어긋난다.

Flutter가 이기는 영역(커스텀 전환 애니메이션의 자유도, `drift`)은 있으나 **동인이 아니다.**

### 결정 3 — `packages/core` 를 공유해 병렬로 운영한다

```
packages/
  core/            141 파일. DOM도 Capacitor도 모른다(포트 역전 후)
  app-capacitor/   현재 앱. 패리티까지 계속 OTA로 배포한다
  app-rn/          새 앱
```

**"다 갈아엎고 몇 달 뒤 기도하며 배포"를 하지 않는다.** 현재 앱은 한 순간도 멈추지 않고, `core` 가
단일 원본이라 로직 수정이 양쪽에 동시 반영된다. 패리티 도달 시 스토어 릴리스 한 번으로 스위치한다.

**언제든 중단해도 손해는 `app-rn` 작업분뿐이다.** `core` 분리는 RN을 안 가더라도 남는 이득이라
(경계 강제·테스트 속도) 이 단계는 전환 결정과 독립적으로 정당하다.

### 결정 4 — 어댑터 인터페이스는 한 글자도 바꾸지 않는다

`storage/*` · `native/*` 의 **함수 시그니처를 고정**하고 구현만 교체한다. 이것이 117개 파일이 무수정으로
사는 유일한 조건이고, 포트 역전으로 손대는 15개도 **밖으로 나가는 시그니처는 그대로** 두어야 하는 이유다.

*"이왕 하는 김에"* 시그니처를 손대는 순간 **이식이 재작성이 된다.** 개선하고 싶은 것이 있으면 전환이
끝난 뒤 별개 작업으로 한다.

### 결정 5 — 데이터는 마이그레이션하지 않는다. 같은 저장소를 계속 쓴다

기존 데이터는 "Capacitor 안"이 아니라 **OS가 앱마다 주는 표준 저장소**에 있다.

| | 저장 위치 | 확인 |
|---|---|---|
| Preferences (Android) | `getSharedPreferences("CapacitorStorage")` | 네이티브 소스 확인 |
| Preferences (iOS) | `UserDefaults.standard`, 키 = `"CapacitorStorage." + key` | 네이티브 소스 확인 |
| SQLite | `boss_profitSQLite.db`, **`'no-encryption'`** | `db.ts:143` |

**앱 번들 ID에 귀속되므로** 같은 `com.mapleroutine.app` 으로 빌드한 RN 앱이 그냥 읽는다. 복사도 변환도
하지 않는다.

이것이 이 전환에서 가장 중요한 안전 장치다. 상세는 `migration/data.md`.

### 결정 6 — 이식 단위는 파일이 아니라 **ADR 계약**이다

소스에 박힌 ADR 참조를 전수 추출한 결과 **113개 ADR이 203개 파일**에 걸려 있다. 그중 상당수는 화면에
드러나지 않는 엣지 케이스 처리다 — 기기 시계를 되돌린 사용자([[ADR-090]]), 월드를 옮긴
캐릭터([[ADR-069]]), 롤백된 번들([[ADR-126]]), 가격 미입력과 0원의 구분([[ADR-124]]).

**"새 화면이 잘 도는 것처럼 보이는 것"과 그 판단들을 보존하는 것은 다른 일이다.** 그래서 파일별 ADR
목록을 체크리스트로 만들고(`migration/parity-inventory.md`), 한 파일을 끝냈다는 것을 *"그 파일의 ADR을
전부 다시 읽고 해당 동작이 새 코드에 있음을 확인했다"* 로 정의한다.

가장 무거운 파일은 `app/boss-profit/BossProfitScreen.tsx` — **ADR 32개**. 다른 화면과 같은 취급을
하지 않고 단독으로 계획한다.

### 결정 7 — OTA 프로토콜 재설계는 별도 ADR로 미룬다 → **[[ADR-137]] 이 닫았다**(2026-08-14)

`native/live-update.ts` 만 성격이 다르다. 다른 어댑터는 같은 일을 하는 다른 SDK로 바꾸는 것이지만
이쪽은 **프로토콜 자체가 바뀐다**(@capgo 자체 호스팅 매니페스트 → expo-updates).

[[ADR-022]](자체 호스팅) · [[ADR-026]](체크 시점) · [[ADR-119]](노트 한 벌) · [[ADR-126]](`highlights` ·
`minNativeVersion` · 완료 안내)가 정한 것들을 새 프로토콜에 어떻게 싣는지는 **이 ADR의 범위 밖**이다.
1단계 착수 전에 별도 ADR을 쓴다.

> **[[ADR-137]] 로 닫혔다**(2026-08-14 · 구현 완료, 실기기 미검증). 위 넷은 전부 새 프로토콜로
> 옮겨졌다 — `minNativeVersion` → `runtimeVersion`(fingerprint) · `highlights` 외 셋 → 매니페스트
> `extra` · 체크 시점·노트 한 벌은 무변경. **채널만 폐기**됐고([[ADR-024]]) 그 부수 효과로 core 의
> `import.meta.env` 벽이 사라져, 이 ADR 이 «못 옮긴 것» 으로 남겨 둔 «스토어를 값으로 import 하면
> 죽는다» 도 함께 끝났다. `LiveUpdatePort` 는 결정 4(*"시그니처를 개선하며 옮기지 않는다"*)의 유일한
> 예외가 됐다 — 그 포트만은 **@capgo 의 모양 자체**라 갈아끼울 수 없었다.

## 이유

전부 **"웹뷰가 하나의 네이티브 뷰라는 사실"** 에서 나온다. 그것이 광고를 콘텐츠 사이에 넣지 못하게
막고(결정 1의 동인), 화면 전환을 손으로 만들게 했다([[ADR-120]]). 반대로 그 웹뷰를 걷어내도 잃을 줄
알았던 OTA는 애초에 웹뷰에 딸린 것이 아니었다(맥락).

비용이 감당 가능한 것은 [[ADR-003]]·[[ADR-005]] 가 3년간 강제해 온 경계 덕분이다 — 그 경계가 로직
83%를 손도 안 대고 옮길 수 있게 지켜 뒀고(맥락), 저장 어댑터를 인터페이스 뒤에 가둬 데이터를 그 자리에 둔 채
구현만 갈아끼울 수 있게 했다(결정 5). **이 전환은 그 경계를 다시 긋는 작업이 아니라 쓰는 작업이다**(결정 4).

## 기각안

- **Capacitor에 남고 광고만 확장** — 보상형·앱오픈을 붙이면 eCPM 상위 포맷을 오늘 얻는다(실제로 그것부터
  하는 것이 맞다). 그러나 **인라인/네이티브 광고는 영원히 불가능하고**, 전면광고를 걷어내는 방향으로는
  갈 수 없다. 전환의 동인은 수익 최적화가 아니라 **제품 방향의 선택지 확보**다.
- **Flutter** — 결정 2.
- **네이티브 2벌(Kotlin + Swift)** — OTA가 원천 봉쇄되고 재작성 규모가 두 배다. 검토 가치 없음.
- **RN에 `react-native-webview` 로 기존 앱을 감싸기** — Capacitor보다 나쁘다(런타임 두 벌).
- **브라운필드 점진 전환**(같은 Activity에 웹뷰와 RN 뷰 공존) — 바이너리가 커지고 상태 저장소가 둘이
  되며 두 세계를 잇는 브리지를 따로 만들어야 한다. **결정 3의 `core` 공유가 같은 목적(중단 가능성)을
  훨씬 싸게 달성한다.**
- **데이터를 MMKV로 1회 복사** — 단발 실행 코드가 늘고, 하필 **OTA로 못 고치는 릴리스**에서 실패하면
  복구가 불가능하다. 결정 5가 그 코드를 아예 없앤다.
- **`storage`/`native` 시그니처를 개선하며 옮기기** — 결정 4.

## 트레이드오프

- **전환 릴리스에는 OTA 안전망이 없다.** 프레임워크 교체는 정의상 스토어 릴리스이고, 새 빌드에
  `@capgo` 가 없어 되돌릴 수도 없다. 이 저장소에서 **처음으로 "고칠 수 없는 릴리스"** 가 생긴다.
  단계적 롤아웃과 결정 5(원본 보존)로만 관리된다.
- **DOM 스냅샷 3종을 잃는다.** `BossProfitScreen`·`BossScreen`·`ContentScreen` — 하필 가장 복잡한
  셋이고, *"예전과 같은가"* 에 기계적으로 답하던 **유일한 장치**다. 대체 장치를 3단계 전에 정해야 한다.
- **순수 웹 라이브러리를 OTA로 넣던 자유를 잃는다.** RN 생태계는 쓸 만한 것 대부분이 네이티브 모듈이라,
  새 역량을 붙일 때 스토어를 더 자주 탄다. 기존 기능 수정은 그대로 OTA다.
- **CSS `@keyframes` 7종을 Reanimated로 재구현해야 한다.** 선언형 → 명령형이라 1:1 변환이 아니고,
  *"같아 보이는가"* 를 눈으로 판정해야 한다. 단풍잎 스피너([[ADR-061]])와 드랍 연출([[ADR-048]]·[[ADR-103]]).
  (작성 시 «8종»으로 어림잡았으나 실제로는 일곱이다 — 3단계 step 7 이 `index.css` 를 세어 확정했고,
  이제 `keyframes-parity.test.ts` 가 원본을 읽어 목록을 고정한다. 그중 넷은 컴포넌트 계층이라 3단계에서
  옮겼고, `valuable-drop-*` 셋은 붙는 자리가 화면이라 4단계 몫이다.)
- **브라우저 개발 루프를 잃는다.** devtools, `npm run dev` 즉시 반영, 웹 폴백(`jeep-sqlite`·`sql.js`)이
  전부 사라진다. 폴백 소멸은 이득이기도 하다(의존성 2개 감소).
- **기간이 길다.** 풀타임 2.5~4개월, 사이드 프로젝트면 7~11개월. 그동안 `core` 를 통해 양쪽을 유지해야
  하므로 **일시적으로 관리 비용이 늘어난다**(결정 3의 대가).
- **`data/` 는 [[ADR-006]] 대상이다.** 전환 중에도 AI가 게임 수치를 임의로 바꾸지 않는다 — 옮기기만 한다.

## 범위 밖

- **OTA 프로토콜 재설계** — 결정 7. 별도 ADR.
- **광고 포맷 확장 전략**(보상형·앱오픈·인라인을 어디에 어떤 빈도로) — 전환은 *가능하게* 만들 뿐이고,
  무엇을 할지는 `features/ads.md` 와 별도 결정이다. **보상형·앱오픈은 Capacitor에서도 오늘 가능하므로
  전환을 기다릴 이유가 없다.**
- **`apiKey` 를 Keychain/Keystore로 올리기** — 현재 평문 Preferences이고 전환 후에도 그대로다(회귀 아님).
  저장 레이어를 손대는 김에 검토할 만하나 별개 결정이다.
- **MMKV 도입** — 결정 5의 "나중에". RN 안정화 후.
- **디자인 변경** — 전환은 **같게 만드는 작업**이다. 개선하고 싶은 것은 전환 후로 미룬다.
- **Flutter 재검토** — 결정 2로 닫는다.

## 폐기

- **[[ADR-001]] Capacitor 기반 하이브리드 앱 채택** → **React Native**(결정 1). 그 ADR이 웹 기술과 OTA를
  근거로 삼은 부분은 **폐기가 아니다** — RN도 같은 조건을 만족한다(맥락). 폐기되는 것은 **웹뷰라는 구현
  선택**이고, 그것이 광고 인벤토리와 화면 전환에서 치르는 비용이 이득을 넘어섰다는 판정이다.
- **[[ADR-120]] 의 구현**(자체 화면 스택 machinery ~1,283줄) → react-navigation 네이티브 스택.
  **그 ADR이 정한 동작은 폐기가 아니다** — 스택 깊이에 따른 탭바 동반 이동, 제스처 진행률에 따른 아래
  화면 시차, 3버튼과 제스처가 같은 결과로 수렴하는 것은 새 구현에서도 성립해야 한다. react-navigation
  기본값이 그와 다르면 **기본값이 아니라 [[ADR-120]] 을 따른다.**
