# ADR-059+136+224+346+348 화면 스택과 하단바

> 🟢 유효
> 옛 번호: ADR-077 · ADR-098 · ADR-120 결정 1 · 4 · 9 · 18 · ADR-132 결정 1 · 2 · 3 · 7 · 11 · ADR-167 · ADR-209 · ADR-210 · ADR-234
> 관련 소스: `navigation/` · `components/organisms/BottomBar/` · `patches/expo-glass-effect+*.patch` · `lib/bottom-bar-metrics.ts` · `hooks/useButtonNavigation.ts` · `modules/app-system-bars/` · `hooks/useOpenTab.ts` · `hooks/useScreenNavigation.ts` · `hooks/useScrollToTop.ts` · `hooks/useRootBackToBackground.ts` · `native/haptics.ts`

## 배경

앱의 탭 화면은 열 개다. 이것을 하단바 한 줄에 모두 놓으면 칸이 좁아져 라벨부터 깨진다. 그래서 하단바에는
그룹 다섯 개만 두고, 하위 화면이 있는 그룹을 누르면 바가 그 그룹의 하위 행으로 바뀌게 했다.

탭 화면 위에서 여는 하위 페이지(보스 관리, 드롭 히스토리, 설정의 하위 화면 등)는 스물두 개다. 이 페이지들과
하단바의 하위 행이 같은 방식으로 열려야 한다. 같은 방식이란 오른쪽에서 밀려 들어오고, iOS 에서 화면 왼쪽 끝을
밀면 돌아가는 것이다. 이 문서는 그 구조를 react-navigation 스택으로 어떻게 짰는지를 정한다.

## 결정

### 결정 1. 하위 페이지는 루트 스택에 push 하고, 아래 화면은 그대로 둔다

하위 페이지는 `RootNavigator` 의 루트 스택에 쌓는다. 전환 애니메이션과 iOS 가장자리 스와이프는
`@react-navigation/native-stack` 에 들어 있어서 앱이 따로 만들지 않는다.

push 로 열면 아래 화면이 언마운트되지 않는다. 그래서 하위 페이지에서 돌아와도 펼쳐 둔 아코디언, 보던 기간,
스크롤 위치가 그대로 남는다. 뒤로 가기는 `goBack()` 한 번이다. 딥링크를 두지 않아서 스택은 앱이 push 한 만큼만
깊고, 하위 페이지가 떠 있으면 그것을 연 화면이 반드시 아래에 있다. 그래서 화면마다 부모 경로를 갖고 있을
필요가 없다. 딥링크 설정(`linking`)을 넣으면 없던 진입 경로가 생기므로 두지 않는다.

하위 페이지에는 하단바가 없다. 바는 `LayerStack` 안에 있고(결정 2), 하위 페이지는 `LayerStack` 전체를 옆으로
밀어내므로 바도 아래 화면과 함께 밀려 나간다. 바를 앱 맨 위로 올리면 하위 페이지 위에서 언제 숨길지를 따로
판정해야 하고, 밀려 나가는 대신 사라지게 된다.

하위 페이지 목록은 `routes.ts` 의 `ROUTE_TABLE` 에서 뽑는다. `RootNavigator` 의 `STACK_SCREENS` 는
`Record<StackRouteName, …>` 이어서, 표에 행을 더하고 화면을 빠뜨리면 컴파일이 안 된다.

### 결정 2. 하단바의 그룹 행과 하위 행은 스택 한 단씩이다

```
RootStack
├─ Main (LayerStack)
│   ├─ Groups        Today · Utility · Settings
│   ├─ ScheduleSubs  Appointments · Content · Boss
│   ├─ LedgerSubs    Profit · Cashbook · Stats · Inventory
│   └─ BottomBar     layout 이 그린다
└─ 하위 페이지 스물둘
```

하위가 있는 그룹을 누르면 `LayerStack` 에 그 그룹의 레이어 화면(`ScheduleSubs` · `LedgerSubs`)이 push 된다.
하위 행으로 내려가는 것도 진짜 push 라서, 하위 페이지와 같은 전환과 가장자리 스와이프가 생긴다. 두 스택은
`PUSH_SCREEN_OPTIONS` 상수 하나를 함께 쓴다. 각자 값을 적어 두면 한쪽만 고쳤을 때 열리는 방식이 조용히 달라진다.

각 레이어 화면 안은 탭 내비게이터다. 그래서 같은 그룹 안에서 하위끼리 옮겨 갈 때(컨텐츠에서 보스로)는 스택이
늘어나지 않고 전환도 없다. 이때 ← 를 누르면 그 그룹에 들어오기 전 화면으로 나간다. 탭 내비게이터는
`backBehavior="none"` 이다. `"history"` 로 두면 모든 탭 전환이 쌓여 유틸리티에서 설정으로 옮긴 것까지 뒤로 가기로
되돌아온다. 하위끼리 옮겨도 탭이라 서로 언마운트하지 않으므로 스크롤 위치도 남는다.

바는 `LayerStack` 의 `layout` 이 레이어 화면들 뒤에 형제로 그린다. 레이어가 밀려도 바는 움직이지 않는다.
라우트 이름 `Main` 은 화면들이 `navigate('Main', …)` 으로 쓰고 있어서 컴포넌트 이름이 `LayerStack` 으로 바뀐
뒤에도 그대로 둔다.

### 결정 3. 그룹은 다섯이고, 어느 행을 보여 줄지는 지금 페이지로 정한다

| 그룹 | 라벨 | 하위 |
|---|---|---|
| `today` | today | 없음 |
| `schedule` | 스케줄러 | 파티 스케줄 · 컨텐츠 · 보스 |
| `ledger` | 수입·지출 | 보스 수입 · 가계부 · 통계 · 인벤토리 |
| `utility` | 유틸리티 | 없음 |
| `settings` | 더보기 | 없음 |

표는 `bar-groups.ts` 의 `BAR_GROUPS` 하나다. 표의 순서는 기본 순서이고, 바는 사용자가 정한 순서(`BarState` 의
`order`)로 그린다([[ADR-152]] 결정 3). 그룹은 하위가 있으면 레이어 화면(`layer`)을, 없으면 자기
페이지(`page`)를 가진다. 둘 중 하나만 가져야 하고, 둘 다 가지거나 둘 다 없으면 어느 행을 그릴지 정할 수 없다.

지금 페이지의 그룹이 하위를 가지면 하위 행을, 아니면 그룹 행을 그린다(`barLayer`). 그룹 행을 보여 주라는 상태를
따로 두지 않는다. 따로 두면 가계부에 있는데 그룹 행이 떠 있는 상태가 생기고, 그 상태에서 뒤로 가기가 어디로
가야 하는지 답할 수 없다.

← 는 하위 행에만 나온다. 그룹 행에서는 다섯 그룹이 이미 다 보여서 나갈 버튼이 필요 없다. 하위 행에 있으면
스택이 반드시 두 단 이상이므로 ← 를 눌렀을 때 돌아갈 곳이 없는 경우는 없다.

### 결정 4. 레이어 상태는 react-navigation 이 관리하고, 바는 마지막 하위 하나만 기억한다

지금 페이지는 react-navigation 상태에서 읽는다(`pageFromLayerState`). 바가 사본을 따로 가지면 탭은 가계부인데 바는
스케줄러를 그리는 프레임이 생긴다. 중첩 내비게이터는 첫 프레임에 아직 상태가 없어서, 그때는 이동할 때 넘긴
`params.screen` 을 읽고, 그것도 없으면 그 레이어의 첫 화면으로 정한다. 모르는 이름이 오면 첫 화면으로 떨어진다.
바가 예외를 던지면 앱 전체가 멈추기 때문이다.

바가 직접 갖는 값은 `lastSub` 하나다(`bar-store.ts`). 그룹을 나가면 그 레이어 화면이 언마운트되므로, 다시
들어갈 때 어느 하위를 열지는 앱이 기억해야 한다. 하위를 가진 그룹을 다시 누르면 마지막으로 보던 하위가 열린다.
기억이 없으면 사용자가 정한 순서의 맨 왼쪽 하위가 열린다([[ADR-152]] 결정 3).

`bar-groups.ts` 의 함수들은 새 상태가 아니라 해야 할 이동(`BarIntent`)을 돌려준다. 상태가 react-navigation
쪽에 있어서 새 상태를 돌려줄 수 없기 때문이다. 이동은 `openSubs` · `switchSub` · `switchGroupPage` · `back` ·
`none` 다섯 가지이고, 실제로 이동시키는 일은 `BottomBar` 가 `BarNavigation`(`openLayer` · `goBack`)으로 한다.
판정이 순수 함수라 렌더 없이 테스트할 수 있다.

### 결정 5. 같은 레이어 화면은 스택에 두 번 쌓지 않는다

이미 아래 단에 있는 레이어로 가면 새로 쌓지 않고 그 단까지 되돌아간다. react-navigation 7 의 `navigate` 는
되돌아가지 않고 한 단 더 쌓기 때문에, 바는 `StackActions.popTo` 를 먼저 보낸 뒤 안쪽 탭을 정한다. 이렇게 하지
않으면 하위 행에서 그룹 페이지로 갈 때 바닥에 있는 `Groups` 가 한 번 더 쌓인다. 그러면 바에는 ← 가 없는데
가장자리 스와이프로는 뒤로 갈 수 있는 상태가 된다.

화면에서 탭을 여는 `useOpenTab` 도 같은 규칙을 따른다. 그룹 페이지(Today · Utility · Settings)로 갈 때는 먼저
`popToTop` 으로 `Groups` 까지 되돌아간다. 다만 `LayerStack` 이 한 단뿐이면 보내지 않는다. 뺄 단이 없을 때
`POP_TO_TOP` 을 보내면 처리하는 내비게이터가 없어 개발 모드 경고가 뜬다. 단 수는 `getParent(LAYER_STACK_ID)` 로
`LayerStack` 을 직접 찾아서 센다. `canGoBack()` 은 탭 내비게이터의 뒤로 가기까지 세어서 바닥에서도 참이 될 수
있다.

`useOpenTab` 은 `navigate('Main', …, { pop: true })` 로 보낸다. 하위 페이지(거래 내역 · 컨텐츠 관리 · 보스 관리)에서
부르면 맨 위가 `Main` 이 아니라서, `pop` 없이는 `Main` 이 통째로 하나 더 쌓인다. 그러면 아래에 남은 하위 페이지와 앱 전체가
계속 그려지고 부를수록 느려진다(2026-11-15 아이폰 계측). `pop` 이면 아래의 `Main` 까지 되돌아가며 그 위의 하위 페이지가 빠진다.

그래서 스케줄러, 가계부, 스케줄러 순으로 옮긴 뒤 ← 를 누르면 가계부가 아니라 스케줄러에 들어오기 전 화면으로
나간다. 스택 깊이가 끝없이 늘어나지 않게 하려고 이렇게 정했다.

### 결정 6. 화면은 페이지 이름만 알고, 레이어 구조로 바꾸는 일은 `navigation/` 이 한다

탭으로 가려면 `navigate('Main', { screen: 레이어, params: { screen: 페이지 } })` 처럼 두 단을 적어야 한다.
이것을 화면마다 적으면 어느 페이지가 어느 레이어에 있는지가 화면 수만큼 복사된다. 그래서 이 변환은
`tab-navigate.ts` 의 `tabNavigateArgs` 하나에서만 하고, 화면은 `useOpenTab()` 에 페이지 이름만 넘긴다. 파라미터는
가장 안쪽 화면에 붙인다. 한 단 위에 붙이면 레이어 화면이 받고 목적지 화면은 못 받는다.

하위 페이지를 열 때는 `useScreenNavigation()` 을 쓴다. `useSettingsNavigation` 은 같은 훅의 별칭이다.

`navigation/` 에는 내비게이터와 페이지 표만 둔다. 하단바를 그리는 코드는 `components/organisms/BottomBar/` 에,
훅은 `hooks/` 에 둔다. `bar-groups.ts` 는 바만 쓰는 것이 아니라 `tab-navigate.ts` 와 `page-from-layer-state.ts` 도
읽는 페이지 표라서 `navigation/` 에 남긴다.

### 결정 7. 앱은 today 에서 시작하고, `ROUTE_TABLE` 의 `/` 행은 컨텐츠를 그대로 가리킨다

`INITIAL_TAB_ROUTE` 는 `Today` 다. 타입이 `keyof GroupLayerParamList` 여서 하위 페이지를 첫 화면으로 적을 수
없다. 적을 수 있으면 앱을 켜자마자 스택이 두 단인 상태가 생긴다.

`ROUTE_TABLE` 의 `/` 행은 옛 웹 앱이 `/` 에서 무엇을 보여 줬는지 적어 둔 기록이라 `Content` 그대로 둔다. 첫
화면과 이 행이 다른 것은 의도한 것이다. 둘이 어긋나 보인다고 `/` 를 `Today` 로 고치지 않도록 테스트가 두 값을
한 번에 확인한다.

### 결정 8. 안드로이드에서 더 뺄 화면이 없으면 뒤로 가기는 앱을 백그라운드로 보낸다

하위 페이지나 하위 행이 떠 있으면 react-navigation 이 뒤로 가기를 받아 한 단 뺀다. 레이어도 진짜 스택이라
`canGoBack()` 하나로 판정할 수 있다. 더 뺄 것이 없을 때의 기본 동작은 액티비티 종료인데, 그러면 다음 실행이 콜드
스타트가 되어 스플래시부터 다시 본다. 그래서 `useRootBackToBackground` 가 그때만 뒤로 가기를 받아
`moveAppToBackground()` 를 부른다. 다시 열면 보던 화면 그대로다. 종료할지 묻는 창은 띄우지 않는다. 홈 버튼과 같은
동작이라 잃는 것이 없다.

`BackHandler` 리스너는 나중에 등록된 것부터 불린다. 이 훅은 pop 할 것이 있으면 `false` 를 돌려주고 react-navigation
에 넘기므로, 어느 쪽이 먼저 불려도 결과가 같다. 컨테이너가 아직 준비되지 않았으면 판정하지 않는다.

### 결정 9. 활성 탭을 두 번 누르면 그 화면이 맨 위로 스크롤된다

300ms 안에 같은 항목을 두 번 누르면 더블탭으로 본다(`double-tap.ts` 의 `isSecondTap`). 두 플랫폼의 시스템 더블탭
간격과 같은 값이다. 더 늘리면 한참 떨어진 두 번의 누름이 더블탭으로 잡혀, 탭을 확인하려고 두 번 누른 사용자가 맨 위로
튕긴다. 더블탭으로 잡히면 기록을 지워서 세 번째 누름은 다시 첫 누름이 된다. 다른 탭에서 옮겨 온 직후의 누름도
더블탭의 첫 누름으로 세지 않는다.

바는 화면 밖에 있어서 화면의 `ScrollView` 를 직접 잡을 수 없다. 그래서 `scroll-to-top.ts` 에 라우트 이름별로
맨 위로 올리는 함수를 등록해 두고, 바는 지금 페이지 이름으로 그 함수를 부른다. 함수 하나만 등록하는 방식은 안
된다. 같은 레이어의 탭 화면들은 서로 언마운트하지 않아서 마지막에 등록한 화면만 남기 때문이다. 등록은
`ScreenScroll` 이 `useScrollToTopTarget` 으로 하고, 화면 안에 버튼을 달 때는 `useScrollToTop()` 을 쓴다. 두 훅은
`useRoute()` 대신 `NavigationRouteContext` 를 읽는다. 컴포넌트 테스트가 내비게이터 없이 렌더하는데 `useRoute()`
는 그때 예외를 던진다. 해제할 때는 이름이 아니라 등록한 함수가 같은지를 보고 지운다. 이펙트가 다시 돌면
새 등록이 옛 해제보다 먼저 일어나서, 이름만 보면 방금 등록한 함수가 지워진다.

### 결정 10. 누른 결과로 무언가 바뀌면 햅틱을 낸다

햅틱은 두 종류다.

| 함수 | 뜻 | iOS | 안드로이드 |
|---|---|---|---|
| `tapFeedback()` | 눌러서 어딘가로 갔다 | `impactAsync(Light)` | `performAndroidHapticsAsync(Virtual_Key)` |
| `selectionFeedback()` | 고른 값이 바뀌었다 | `selectionAsync()` | `performAndroidHapticsAsync(Clock_Tick)` |

하단바의 탭 이동과 ← 는 `tapFeedback()` 을 낸다. 활성 탭을 다시 누를 때와 맨 위로 스크롤할 때는 내지 않는다.
화면은 그대로인데 손끝에 무언가 바뀌었다고 알리면 거짓 신호가 되기 때문이다. ← 도 화면이 바뀌는 이동이라 탭
이동과 같은 햅틱을 낸다. 같은 바 안에서 누름마다 촉감이 다르면 헷갈린다.

같은 기준을 앱 전체에 쓴다. 페이지 뒤로(`BackButton`), 기간 이동 화살표, 떠 있는 버튼(`SpeedDial` ·
`DropPriceFab`)은 `tapFeedback()` 을, `Segment` · 난이도 고르개(`DifficultyExpander`)와 `Switch` ·
`CalendarGrid` · `CharacterRail` · 캐릭터 카드 순서 바꾸기와 `Stepper` 의 `−` · `+` 는 `selectionFeedback()` 을 낸다.
이미 고른 값을 다시 누르면 내지 않는다. `Stepper` 가 최솟값 · 최댓값에 닿으면 그쪽 버튼이 막혀 누름이 없으므로
햅틱도 없다. 값이 바뀌지 않았는데 울리면 거짓 신호가 된다. 가능하면 부품 안에서 부른다. 호출하는 화면마다 적어 두면 새 화면에서 빠뜨리기 쉽다.

안드로이드에서 `impactAsync` · `selectionAsync` 를 쓰지 않는다. 그쪽 구현은 진동 모터를 직접 돌려서, 사용자가
시스템 설정에서 촉각 피드백을 꺼도 울린다. `Segment_Tick` 대신 `Clock_Tick` 을 쓰는 것은 `Segment_Tick` 이
API 34 이상에만 있기 때문이다. 기기에 진동 장치가 없거나 촉각 피드백이 꺼져 있어 거절되면 그 오류는 무시한다.
햅틱 때문에 이동이 막히면 안 된다. 포트가 주입되지 않은 것은 배선 실수라서 그대로 예외를 던진다.

### 결정 11. 바는 화면 위에 떠 있고, 높이는 62 로 고정한다

바는 `position: absolute` 로 띄운다. 콘텐츠는 바 아래로 지나가고, 끝에 남길 여백은 `ScreenScroll` 이 바 높이로
계산한다([[ADR-063]]).

| 값 | 계산 |
|---|---|
| 폭 | `min(창 폭 − 21 × 2, 420)`. 상한에 걸리면 남는 폭을 좌우로 나눠 가운데에 둔다 |
| 높이 | 62 |
| 아래 위치 | 하단 안전영역 바로 위. 안드로이드는 안전영역 최소 34. 아래에 3버튼 내비게이션 바가 있으면 21 더 띄운다 |
| 안쪽 여백 · 알약 | 여백 4. 알약 높이 54, 알약 폭은 그룹 행의 칸 폭 + 9 |
| 칸 폭 | `(폭 − 4 × 2 − 9) ÷ 5` |
| 하위 행 | 바 왼쪽에 ← 원(지름 54)이 바와 간격 8 을 두고 따로 선다. 바는 남은 폭을 채우고 늘 네 칸으로 나눈다 |
| 아이콘 · 라벨 | 아이콘 칸 높이 25, 아이콘과 라벨 사이 3, 라벨 10pt · 600. 라벨은 시스템 글자 크기를 따르지 않는다 |

높이를 62 로 고정한 것은 iOS 시스템 탭 바가 기기 폭과 관계없이 62 이기 때문이다. 바의 모양과 움직임을 시스템 탭 바에
맞췄으므로 높이도 같이 둔다. 전에는 높이를 폭에 비례시켰다. 알약이 칸보다 23 넓어서 칸 폭이 바뀌면 알약의 가로세로 비가
크게 달라졌기 때문이다. 지금 알약은 칸보다 9 만 넓어서 높이를 고정해도 비가 거의 같다. 좌우 여백 21 과 알약의 덧폭 9 도
시스템 탭 바에서 잰 값이다.

하위 행이 언제나 네 칸인 것은 하위 수가 다른 두 그룹(스케줄러 셋 · 수입·지출 넷)을 오갈 때 알약 폭이 바뀌지 않게 하려는
것이다. 셋인 행은 넷째 칸을 비운다. 알약 폭은 하위 행에서도 그룹 행과 같은 값을 쓴다. 칸이 넓어진 하위 행에서 알약까지
넓어지면 행이 바뀔 때 알약 크기가 튄다.

치수를 측정하지 않고 계산하는 이유는 측정값이 첫 프레임에 0 이어서 알약이 한 프레임 접혀 보이기 때문이다.
같은 함수(`resolveBottomBarMetrics`)를 바와 `ScreenScroll` 이 함께 써서 두 값이 어긋나지 않는다.

3버튼 내비게이션 바 위에서만 21 을 더 띄우는 것은 그 바가 버튼 줄 전체를 인셋으로 주기 때문이다. 인셋 바로
위에 서면 하단바의 아래 끝이 버튼 줄의 위 끝에 붙는다(#984). 아이폰 홈 인디케이터와 안드로이드 제스처 핸들은
인셋 안에 가는 막대만 있어서, 같은 계산으로도 바가 떠 보인다. 그래서 그 기기들은 더 띄우지 않는다. 21 은
바가 좌우 가장자리에서 남기는 최소 여백(`BAR_SIDE_MARGIN`)과 같은 값이다. 바가 좌우와 아래 세 방향에서 같은
간격으로 뜬다(사용자 지정).

3버튼인지는 인셋 크기로 어림잡지 않고 안드로이드에 묻는다. 탭할 수 있는 시스템 바의 인셋
(`WindowInsetsCompat.Type.tappableElement()`)은 제스처 내비게이션에서 0 이고, 3버튼에서는 버튼 줄 높이다.
RN 과 `react-native-safe-area-context` 는 이 값을 주지 않는다. 그래서 로컬 모듈 `app-system-bars` 가 이 값을 읽고,
바뀌면 이벤트로 알린다. 사용자가 내비게이션 방식을 바꾸거나 갤럭시의 버튼 숨기기로 버튼 줄을 내리면 바가 그
자리에서 따라 움직인다. iOS 에는 이 바가 없어 언제나 띄우지 않는다.

띄운 높이는 콘텐츠가 바 아래에 남기는 몫(`spacePx`)에 들어간다. 그래서 콘텐츠 끝 여백, 안전영역 페이드, 팝오버와
FAB 의 위치가 함께 올라간다. 한 곳만 올리면 콘텐츠가 바 뒤로 들어간다. 토스트(`ToastStack`)도 같은 `spacePx` 위에
12 를 띄워 선다. 바 높이를 상수로 따로 적어 두면 바를 고칠 때 토스트만 옛 자리에 남는다.

키보드가 떠 있으면 바를 그리지 않는다(`useKeyboardShown`). 키보드 높이가 0 인 show 이벤트는 뜬 것으로 보지 않는다. 화면을 돌리거나
접고 펼 때 iOS 가 높이 0 인 키보드의 show 를 보내고 hide 는 보내지 않아서, 키보드가 없는데도 바가 숨은 채 남았다(#945).

오른쪽 안전영역에 레일이 있는 화면은 바를 세로 막대로 바꿔 그 자리에 세운다. 치수와 위치는 [[ADR-191]] 결정 4 가 정한다.

### 결정 12. iOS 26 이상은 유리 바, 그 밖은 불투명 바이고, 알약은 어디서나 테마 색 판이다

iOS 26 이상에서는 바를 `expo-glass-effect` 의 `GlassView`(`regular`, 색 `glassTint`)로, ← 원을 `clear`(색
`pillOnGlass`) 유리로 그린다. 둘은 `GlassContainer`(간격 16) 안에 둔다. `colorScheme` 은 OS 설정이 아니라 앱 테마의
`mode` 를 따른다. 기본값 `auto` 로 두면 라이트 OS 에서 다크 테마를 켰을 때 어두운 페이지 위에 밝은 유리판이 뜬다.

`expo-glass-effect` 는 색과 명암을 바꿀 때 애니메이션을 건다. 그래서 테마를 바꾸면 바가 잠깐 옛 테마 색으로 보였다
바뀐다. patch-package 로 이 애니메이션을 끈다(`patches/expo-glass-effect+*.patch`). 테마를 고르는 순간 바가 함께
바뀌어야 하기 때문이다(사용자 지정 2026-11-28). 네이티브 변경이라 스토어 바이너리로만 낼 수 있다.

쉬고 있는 알약은 유리가 아니라 테마 색 판이다. iOS 26 이상은 다크에서 흰색 14%, 라이트에서 검정 6% 판이다. 시스템
탭 바의 알약도 유리가 아니라 옅은 판이다. 유리 알약을 바 유리 위에 겹치면 테마를 바꿀 때 알약만 늦게 바뀌었다.

iOS 26 미만과 안드로이드는 유리가 없어서 바와 ← 원이 테마 `bar` 색의 불투명 판에 그림자다. 쉬고 있는 알약은 테마
`pill` 색 판에 판 그림자다(사용자 지정 2026-11-28). 이 바탕에서 옅은 판을 쓰면 라이트 테마에서 알약이 거의 안 보인다.
블러로 유리를 흉내 내지 않는다.

← 원은 `Pressable` 밖에 둔다. 안에 두면 iOS 가 그 `GlassView` 를 그리지 않는다. 원은 `opacity: 0` 으로
마운트하지 않고 ← 가 필요할 때만 마운트한다. 투명한 상태로 마운트하면 iOS 가 유리 효과를 꺼 버리고 다시 켜지 않는다.

색은 `bar-colors.ts` 의 `resolveBarColors` 가 테마에서 계산한다.

- 바와 활성 알약 둘레에 선(헤어라인)을 긋지 않는다(사용자 지정 2026-10-30, [[ADR-060]] 결정 19). 유리 재질 위에서도 같다.
  불투명 바는 페이지와 색이 아니라 그림자로 구분한다. 바를 어둡게 해서 구분하면 그 위의 글자가 안 읽힌다.
- 활성 아이콘과 라벨은 같은 색이고, 그 테마의 메인 컬러(`primaryInk`)다. 다크에서는 메인 컬러가 비활성보다
  어두워질 수 있어서 명도만 올린다. `text` 쪽으로 섞으면 채도까지 빠져 주황이 갈색이 된다.
- 비활성 아이콘과 라벨은 `textMuted` 에서 채도를 뺀 색이다. 바 안에서 색을 가진 것은 활성 항목 하나뿐이어야
  한다. 이 처리는 바 안에서만 하고, 테마 토큰은 그대로 둔다.
- 아래의 SF Symbols 와 안드로이드 대체 아이콘은 활성일 때 색만 바꾼다. 채우면 안쪽 선이 사라진다.
- 앱의 아이콘(`BarGlyph`)을 쓰는 자리 중 today · 유틸리티 · 보스 · 보스 수입(대시보드 · 렌치 · 검 · 수익)은 활성일 때 면을
  채운다. 안쪽에 의미 있는 선이 없어 채워도 모양이 남기 때문이다. 인벤토리 배낭은 늘 채운 그림이다. 선 굵기는 1.5 그대로
  둔다. 안쪽에 선이 많은 그림(달력 · 목록 · 장부)은 모두 SF Symbols 자리라 색만 바꾼다.

아이콘은 플랫폼마다 다르다. iOS 는 일곱 자리에 SF Symbols 를 쓴다(스케줄러 `calendar` · 수입·지출 `wonsign.circle` ·
더보기 `ellipsis.circle` · 파티 스케줄 `person.3` · 컨텐츠 `checklist` · 가계부 `book.closed` · 통계 `chart.bar`). 그림은
@3x PNG 로 넣고 색을 입힌다. 안드로이드는 같은 일곱 자리에 lucide(ISC 라이선스)의 `calendar-days` · `circle-ellipsis` ·
`book` · `list-checks` 와 직접 그린 원 안 ₩ · 세 사람 · 막대 셋을 쓴다. SF Symbols 는 라이선스가 Apple 플랫폼 밖에서
쓰는 것을 막아서, SF 그림은 iOS 전용 파일(`*.ios.tsx`)에만 두고 안드로이드 번들에 넣지 않는다. 나머지 자리(today ·
유틸리티 · 보스 · 보스 수입 · 인벤토리 · ←)는 두 플랫폼 모두 앱의 아이콘(`BarGlyph`)을 쓴다.

설정의 `하단 탭 순서` 미리보기(`BarPreview`)도 같은 치수 · 아이콘 · 색으로 그린다. 미리보기만 옛 모양이면 사용자가
바꾼 순서가 실제 바에서 어떻게 보일지 알 수 없다.

그림자는 `boxShadowOf` 로 `boxShadow` 에 적는다. `shadowOpacity` 같은 iOS 전용 속성은 안드로이드에 전달되지 않는다.
라벨에는 `includeFontPadding: false` 를 준다. 안드로이드는 글자 상자에 여백을 더해서 아이콘이 3px 위로 밀린다.

### 결정 13. 같은 행 안에서는 알약이 스프링으로 미끄러지고, 행이 바뀌면 두 행이 겹쳐 바뀐다

움직임은 모두 Reanimated 스프링이다(mass 1). 값은 시스템 탭 바를 녹화해 맞췄다.

| 움직임 | stiffness · damping |
|---|---|
| 알약 이동 | 410 · 36 |
| 누를 때 바 부풀기 · ← 누름 | 470 · 28 |
| 알약 들림 | 900 · 50 |
| 떼고 돌아오기 | 520 · 30 |
| 칸 수가 바뀔 때 바 폭과 자리 | 362 · 38 |

같은 행 안에서 탭을 옮기면 알약이 이동 스프링으로 미끄러진다. iOS 는 이동하는 동안 시스템 탭 바처럼 알약이 가로로
늘었다가 돌아온다. 하위가 없는 그룹과 하위 행 안의 탭이 이 경우다.

하위가 있는 그룹(스케줄러 · 수입·지출)을 누르면 그룹 행의 알약은 움직이지 않는다. 손을 떼면 옛 행(항목과 알약)이
100ms 에 빠지고 새 행(항목과 새 선택 칸의 알약)이 120ms 에 나타나며, 두 페이드는 겹친다. 같은 순간 바 폭이 칸 수 스프링으로
줄고 ← 원이 바 쪽 26 안쪽에서 300ms 동안 나온다. ← 로 돌아갈 때도 같은 움직임을 거꾸로 한다. 알약을 행의 일부로 다루는
것은 두 행의 칸이 달라 알약이 이어 갈 자리가 없기 때문이다(사용자 확인 2026-11-28). 화면 이동은 행이 바뀐 다음 프레임에 보낸다. 같은 프레임에
보내면 새 화면을 그리느라 행 전환의 첫 프레임이 밀린다. 화면 전환은 그대로 push 슬라이드다(결정 1 · 2).

알약과 항목은 `transform`(이동 · 크기)과 `opacity`, iOS 렌즈의 셰이더 값으로만 움직인다. 폭이나 위치 같은 배치 값을
애니메이션하면 프레임마다 메인 스레드에서 배치를 다시 계산한다. 배치 값으로 움직이는 것은 칸 수가 바뀔 때의 바 폭과 자리
하나다. 행이 바뀔 때 한 번(약 330ms) 움직이고 누르거나 끄는 동안에는 움직이지 않는다. 갤럭시에서 이것을 `transform` 으로 바꾸자 끌기 중 16.6ms 를 넘는 프레임이 17 개에서
2 개로 줄었다(2026-11-28 계측).

안드로이드는 알약 이동 스프링과 행 전환 페이드만 쓴다. 부풀기 · 들림 · 이동 중 모양 변화는 없다. 알약은 세 겹(자리 ·
`transform` 만 받는 층 · 색 판)으로 그려서 움직이는 층이 배치에 닿지 않게 한다. 갤럭시에서 눈에 띄는 끊김 없이 바의
역할을 하는 것이 움직임보다 먼저이기 때문이다(사용자 지정 2026-11-28).

### 결정 14. 누르는 칸으로 알약이 바로 가고, 누른 채 끌면 따라온다

두 플랫폼이 같다.

- 누르는 순간 알약이 누른 칸으로 출발한다. 손을 뗄 때까지 기다리지 않는다.
- 처음 누른 자리에서 3 넘게 움직이면 끌기다. 알약은 손가락이 움직인 만큼 처음 자리에서 상대로 움직인다. 누른 칸
  가운데로 알약이 먼저 튀지 않게 하려는 것이다.
- 놓으면 가장 가까운 칸으로 이동 스프링을 타고, 그 칸으로 이동한다. 하위가 있는 그룹을 누른 채 끌어도 끌기로 넘어가고,
  놓은 칸이 그 그룹일 때만 행이 바뀐다.
- ← 원은 누르면 1.14 배로 커지고 누름 바탕(다크 흰색 13% · 라이트 검정 7%)이 깔린다.

iOS 는 누르는 동안 바가 1.035 배로 부풀고 알약이 가로 1.26 · 세로 1.34 배로 들린다. 쉬는 알약의 판과 선택 색은 누르는
순간 빠져 알약이 투명한 렌즈가 된다(결정 15). 떼고 알약이 앉으면 판은 170ms(이동했으면 최대 300ms 기다린 뒤 380ms)에,
선택 색은 판과 같은 시간에 돌아온다.

결정 9 의 더블탭과 결정 10 의 햅틱은 그대로다. 끌어서 놓은 칸이 다른 탭이면 누름과 같은 이동이므로 `tapFeedback()` 을 낸다.

### 결정 15. iOS 는 누르고 끄는 동안 알약을 Skia 렌즈로 그린다

iOS 26 이상의 시스템 탭 바는 누르는 동안 알약이 볼록 렌즈가 되어 아래 아이콘과 바 판을 휘어 보인다. 이 렌즈는 비공개
뷰(`_UILiquidLensView`)라 앱이 쓸 수 없다. 그래서 `@shopify/react-native-skia` 의 셰이더(`RuntimeEffect`)로 같은 모양을
그린다(`BarLens.tsx`). 쉬는 동안의 바는 앱 뷰 그대로이고, 렌즈 캔버스는 누르고 끄는 동안만 그 위에 올린다. 쉬는 동안까지
캔버스로 그리면 테마를 바꿀 때 옛 그림이 남는다.

렌즈는 그림 세 장을 휜다.

- 바의 항목 줄 두 장(비활성 · 선택). 화면 밖에 그린 줄을 `makeImageFromView` 로 뜬다.
- 렌즈 뒤 그림. 화면을 뜨지 않고, 바 뒤에 빈 화면이 있었다 치고 테마마다 같은 그림을 쓴다(사용자 지정 2026-11-28).
  페이지 바탕색이고, 배경 그림이 있는 테마는 `ThemeBackdrop` 과 같은 배치 · 크기로 깐 배경 그림에 덮는 색까지 얹은
  것이다. 그 가운데 렌즈 캔버스가 지나는 바 자리 띠만 Skia 로 그린다. 약 10 흐린 사본 위에 테마 바 색 60% 를 얹어
  렌즈 안의 바 판으로 쓴다.

화면을 뜨지 않는 것은 뜬 그림이 금방 낡기 때문이다. 페이지가 바뀔 때만 떴더니 스크롤한 뒤 누르면 스크롤 전 화면이
렌즈에 비쳤다(#1290). 누를 때마다 뜨면 그 프레임이 100ms 가까이 멈춘다(아이폰 17, 화면 뜨기 평균 78ms · 최대 107ms).
렌즈 안의 그림은 휘고 흐려서 바 위 콘텐츠가 비치지 않아도 렌즈로 읽힌다.

| 값 | 내용 |
|---|---|
| 캔버스 | 바 양 끝 밖 40, 위아래 12 넓힌다. 렌즈가 바 밖으로 부푸는 몫이다 |
| 확대 | 1 + 0.12 × 휨 세기. 안쪽은 휘지 않는다 |
| 테 띠 | 반지름 비 0.82 밖을 늘인다. 0.82 에서 부드럽게 시작한다(`over² ÷ (over + 0.06)`, 세기 0.55) |
| 뒤 바 판 | 렌즈 가운데에서 위아래를 3.5 줄여 판이 얇게 보인다. 바 둥근 끝 구역에서는 줄인 띠가 둥근 끝을 감싸 돈다 |
| 흰빛 | 다크만 흰색 17%, 바 판 자리에만. 라이트는 0 이다 |
| 테 반사광 | 가장자리 3.5, 위쪽을 조금 밝게, 세기 0.18 × (0.35 ~ 1). 무지개 테두리는 없다 |

휨 세기와 판 효과는 누르는 순간 전부 걸리고 뗄 때까지 그대로다. 제자리에서 누를 때 · 끌 때 · 끌다 멈췄을 때 모양이 같다.
움직임 속도로 세기를 정하면 멈추는 순간 번짐이 가라앉아 렌즈가 출렁여 보였다(사용자 지정 2026-11-28).

그림은 미리 만들어 두고 누를 때 쓴다. 항목 줄을 누르는 순간 뜨면 그 프레임이 멈춘다(아이폰 17, 275ms). 그래서 언제
다시 만들지를 정해 둔다.

- 항목 줄은 테마가 바뀔 때, 위 화면에서 돌아올 때, 백그라운드에서 돌아올 때 다시 뜬다.
- 렌즈 뒤 그림은 테마 · 창 크기 · 바 자리(가로 바와 세로 막대)가 바뀔 때만 다시 그린다. 페이지가 바뀌거나 스크롤해도
  그대로다.
- 그림마다 만든 순간의 테마를 적어 두고, 지금 테마와 다르면 쓰지 않는다. 옛 테마 색이 렌즈에 비치기 때문이다.
- 항목 줄 그림은 첫 칸 가운데 픽셀로 비었는지 본다. 비었으면 0.5초 뒤 다시 뜨고 다섯 번까지 한다. 쓸 그림이 없으면
  렌즈를 띄우지 않고 앱 뷰를 그대로 둔다. 빈 그림을 쓰면 누르는 동안 아이콘과 라벨이 통째로 사라진다(2026-11-28 실기기).

iOS 26 미만도 렌즈와 누르기 · 끌기는 26 이상과 같다(사용자 지정 2026-11-28). 렌즈는 Skia 로 그려서 유리가 없어도 돈다.

안드로이드에는 렌즈가 없다. 그림을 뜨는 비용이 iOS 보다 크고, 갤럭시는 끊김 없이 바 역할을 하는 것을 먼저 하기로
했다(결정 13).
