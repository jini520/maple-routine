### ADR-234: **하단바가 손끝에 답한다.** 활성 탭 더블 터치는 최상단으로, 탭 이동은 햅틱으로 (2026-09-08, 사용자 지시)

> 🟢 **구현 완료 · 실기기 미검증** (2026-09-08). 최상단 이동은 테스트가 잡지만 **두드림은 실기기에서만**
> 확인된다. 햅틱은 네이티브 모듈이라 **OTA 로 못 나간다**. 다음 스토어 빌드에서만 나간다.

**배경**: 사용자 지시.

> `하단바에 기능을 추가하려고해.`
> `1. 하단바의 현재 활성화된 탭을 더블 터치하면 scroll to top 기능 추가.`
> `2. 비활성화 된 탭을 터치하여 페이지를 이동할 때 햅틱 추가.`

지금까지 **활성 탭을 누르면 아무 일도 안 났다**. `pressGroup`·`pressSub` 가 그 경우에 `none`
지시를 돌려주기 때문이다(`navigation/bar-groups.ts`). 그 빈 자리에 최상단 이동을 얹는다.

### 결정 1. 활성 탭을 두 번 두드리면 그 화면의 스크롤이 맨 위로 간다

판정은 **같은 항목인가 · 간격이 300ms 이내인가** 둘뿐이고, 순수 함수 하나
(`components/organisms/BottomBar/double-tap.ts` 의 `isSecondTap`)가 갖는다. 시간을 재는 코드를
컴포넌트 안에 두면 그것을 물으려면 렌더와 가짜 타이머가 필요해진다.

300ms 는 두 플랫폼의 시스템 더블탭 창과 같은 값이다. 늘리면 한참 뒤의 별개 누름 둘이 하나로
묶여, 탭을 확인하려 두 번 누른 사용자가 영문 모르고 맨 위로 튕긴다.

**세 번째 누름은 다시 첫 누름이다.** 짝을 이룬 뒤 기록을 지운다. 안 지우면 빠르게 세 번
두드릴 때 2·3 번째가 또 한 쌍이 되어 이미 맨 위인 화면에서 최상단 이동이 두 번 돈다.

### 결정 2. 최상단 이동의 과녁은 라우트 이름으로 찾는다

바는 화면 밖에 산다. `LayerStack` 의 `layout` 이 그리므로 화면의 `ScrollView` 를 직접 잡을
길이 없다. 그래서 **라우트 이름 → 최상단 이동 함수** 표를 하나 둔다
(`navigation/scroll-to-top.ts`).

**슬롯 하나짜리 레지스트리는 안 된다.** 층 안의 화면은 탭이고 형제가 서로 언마운트하지 않아,
셋이 한 슬롯에 등록하면 마지막 등록자가 이긴다. `ScreenScroll` 이 당겨서 새로고침을 화면
프롭으로 받은 것과 같은 이유이고(그 머리말이 이 방식을 이미 한 번 거부했다), 그때와 다른 것은
**여기서는 부르는 쪽이 목적지 이름을 안다**는 점이다. 이름을 키로 두면 형제가 함께 살아 있어도
섞이지 않는다.

등록하는 자리는 `ScreenScroll` 하나다. 탭 화면 여덟이 전부 이 셸을 쓰므로 화면마다 배선하면
같은 다섯 줄이 여덟 벌이 되고, 그중 하나가 빠져도 그 탭에서만 조용히 안 먹는다.

### 결정 3. 부르는 길은 훅 둘이다. 화면 안의 버튼도 같은 길로 간다

최상단 이동은 하단바 전용이 아니다. 페이지가 자기 헤더나 목록 끝에 **버튼으로도 붙일 수 있어야**
하므로(사용자 지시), 표를 직접 만지는 코드가 호출부마다 생기지 않게 훅으로 가른다.

| 훅 | 누가 쓰나 | 하는 일 |
|---|---|---|
| `useScrollToTopTarget(ref)` | `ScreenScroll` | 이 화면의 스크롤 컨테이너를 과녁으로 등록 |
| `useScrollToTop()` | 화면 안의 버튼 | 이 화면을 맨 위로 되돌리는 함수를 낸다 |

둘 다 자기가 선 화면을 **`NavigationRouteContext` 로** 안다. `useRoute()` 를 안 쓰는 것은 그
훅이 내비게이터 밖에서 던지기 때문이다. 이 저장소의 컴포넌트 테스트는 내비게이터 없이
렌더한다(`BottomBarOverlay` 의 `useScreenFocused` 가 같은 이유로 컨텍스트를 직접 읽는다).

**바만 표를 직접 부른다**(`scrollPageToTop(page)`). 바는 화면 밖이라 라우트 컨텍스트가 없고,
대신 어느 페이지가 활성인지를 이미 프롭으로 받는다.

### 결정 4. 햅틱은 실제로 이동이 일어날 때만 낸다

비활성 탭 누름은 이동이고, 활성 탭 누름은 이동이 아니다. 후자에 햅틱을 주면 손끝이 **바뀌었다**
고 말하는데 화면은 그대로라 신호가 거짓이 된다.

**최상단 이동에는 안 낸다**(사용자 지정). iOS 의 같은 동작도 침묵한다.

~~`←`(뒤로)는 이번 범위 밖이다.~~ → **`←` 도 낸다**(아래 정정 1).

### 결정 5. 햅틱은 포트를 지나고, 두 플랫폼이 서로 다른 API 를 쓴다

`HapticsPort.tap()` 하나다. 부르는 쪽이 아는 것은 **가벼운 두드림 한 번**이고 그 아래가 갈린다.

| | 부르는 것 | 왜 |
|---|---|---|
| iOS | `impactAsync(ImpactFeedbackStyle.Light)` | `UIImpactFeedbackGenerator` 직결 |
| Android | `performAndroidHapticsAsync(AndroidHaptics.Virtual_Key)` | `View.performHapticFeedback` 직결 |

안드로이드에서 `impactAsync` 를 쓰지 않는다. 그쪽 구현이 `Vibrator` 로 **흉내 낸 것**이라
`VIBRATE` 권한을 먹고 진동 모터를 그냥 돌리며, 사용자가 시스템 설정에서 촉각 피드백을 꺼도
울린다(expo-haptics 자신의 문서가 이 자리에 `performAndroidHapticsAsync` 를 권한다).
`Virtual_Key` 는 안드로이드가 **화면 위의 키를 눌렀다**에 쓰는 상수이고 API 5 부터 있다.

**실패는 삼킨다.** 진동 장치가 없거나 시스템 촉각 피드백이 꺼져 있으면 플러그인이 거절하는데,
그것 때문에 화면 이동이 막히면 안 된다. 포트가 주입되지 않은 것은 여전히 던진다. 그것은
배선 사고이지 이 기기에 그 기능이 없다가 아니다.

### 대가

**OTA 로 못 나간다.** `expo-haptics` 는 네이티브 모듈이라 지문(`runtimeVersion`)이 바뀐다.
최상단 이동은 JS 뿐이라 라이브 업데이트로 나갈 수 있지만, 둘을 갈라 내보내면 같은 커밋의 절반만
기기에 있는 상태가 생긴다. 함께 다음 스토어 빌드로 나간다.

### 정정 1. `←` 도 두드림을 낸다 (2026-09-08, 사용자 지시)

같은 날 실기기에서 확인하고 정했다. 가르는 기준이 **탭인가**가 아니라 **화면이 바뀌는가**라면
`←` 는 처음부터 이쪽이었다. 한 단 올라가는 것도 화면이 바뀌는 이동이고, 손끝이 탭 이동에만
답하면 같은 바 안에서 어떤 누름은 응답하고 어떤 누름은 안 하는 것이 된다.

세기는 탭 이동과 **같은 값**이다(`tapFeedback()` 하나). 뒤로 가기라고 다른 촉감을 주면 바 안에서
두 가지 언어가 생긴다.

**남는 비대칭 하나**. 가장자리 스와이프로 돌아갈 때는 두드림이 없다. 그쪽은 시스템 제스처라
우리 코드가 완료 시점을 받지 않고, `BackGesturePort` 의 `onInvoked` 는 안드로이드 시스템
뒤로가기 자리다. 같은 결과에 도달하는 길 둘의 촉감이 갈리는 것을 알고 남긴다.

### 열린 질문

- 최상단 이동 버튼을 실제로 붙일 화면. 훅은 섰고 부르는 자리는 아직 없다.
- 가장자리 스와이프에도 두드림을 맞출 것인가(정정 1 의 비대칭).
