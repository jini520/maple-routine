### ADR-036: 보스 수익 페이지 — 캐릭터 내부 보스 표시 순서 결정성 확보(weekly-bosses.json 정규 순서) (구현 완료)

> 🟢 **ACTIVE — 유효.** 현행 RN 앱에 적용되는 결정이다.

**배경**(이슈 #28): 보스 수익 페이지에서 **한 캐릭터 안의 보스 표시 순서가 로드/렌더마다 달라진다**는 버그가 실사용에서 보고됐다. 캐릭터 순서 자체는 [[ADR-017]](레벨 내림차순 → 이름순)으로 결정적이지만, **캐릭터 내부 보스 순서는 [[ADR-017]] 결정 2가 "이번 결정 범위에 포함하지 않는다 … 필요하면 별도로 확인 후 진행"으로 명시적으로 보류**했던 부분이다 — #28이 바로 그 후속이다.

**원인 분석**:
- `features/boss-profit/store.ts`의 `sortRowsByOcidOrder`는 `ocid` 순위로만 정렬하고 stable sort에 의존해, 같은 캐릭터 안의 보스 행은 **데이터 소스가 만든 순서를 그대로 물려받는다**(주석에도 명시됨).
- **확정적 비결정성**은 과거 기간/레코드 병합 경로의 소스인 `storage/boss-profit.ts`의 `getBossProfitRecords` SELECT에 `ORDER BY`가 없다는 점 — SQLite가 미지정(구현 의존) 순서로 반환하고, 이 순서는 upsert·DB 재오픈 등으로 로드마다 바뀔 수 있다.
- **부차 요인**(현재 기간 경로): `selectBossProfitBosses` → `groupByApiName`의 Map 삽입 순서에 의존하므로, 캐시 우선 렌더와 라이브 렌더가 `bossContents`를 다른 순서로 공급하면 한 페이지 로드 안에서도 순서가 시각적으로 바뀔 수 있다(이 경로는 소스별로는 결정적).

**결정**:
1. **캐릭터 내부 보스 순서를 `weekly-bosses.json` 정규 순서(`REFERENCE_ENTRIES`: weekly → eventWeekly → monthly)로 고정**한다. 이는 [[ADR-035]] 결정 20이 스케줄러 화면(수동 모드 `mergeManualBossList`)에 이미 확립한 것과 **동일한 원칙·동일한 순서**를 보스 수익 페이지로 확장하는 것이라, 두 화면의 보스 순서가 자연히 일치한다("각 캐릭터의 `bossRows`를 참조 인덱스로 정렬"이 #28이 권장한 방향과도 동일).
2. **적용 지점은 `sortRowsByOcidOrder` 단일 choke point 하나**다. 모든 행 생성 경로 — 캐시 병합(`cachedMergedRows`), 라이브(`sortedRows`), 과거 기록(`buildRowsFromRecords`) — 가 반드시 이 함수를 거치므로, 여기에 2차 정렬 키를 더하면 소스/DB 반복 순서 의존이 세 경로에서 한꺼번에 사라진다. `filterRowsForTab`(필터라 순서 보존)·`BossProfitScreen.tsx`의 `buildCharacterGroups`(행 배열 순서를 그대로 그룹화)는 이 순서를 그대로 물려받으므로 **손대지 않는다**.
3. **정렬 키(캐릭터 순위 뒤에 이어붙이는 2차 키)**: `보스 참조 인덱스 → 난이도 인덱스(BOSS_DIFFICULTIES: 이지<노멀<하드<카오스<익스트림) → 보스명`. 참조 인덱스는 `lib/boss-matching.ts`가 이미 보유한 `REFERENCE_ENTRIES`에서 파생한 **신규 export `getBossReferenceOrder(bossName)`** 로 조회한다(새 게임 데이터 테이블을 만드는 게 아니라 기존 배열에 대한 인덱스를 노출할 뿐이라 [[ADR-006]] 대상 아님). 참조에 없는 보스(매칭 실패 원문명, [[ADR-008]])는 `Number.MAX_SAFE_INTEGER`로 맨 뒤로 보내고, 그들끼리는 난이도·이름으로 최종 결정한다(완전 결정성). 난이도 tiebreak은 같은 캐릭터가 같은 보스를 여러 난이도로 추적한 수동 placeholder 등 드문 동률에 대비한 것.
4. **`storage/boss-profit.ts` SELECT에 `ORDER BY`는 추가하지 않는다.** 결정 2의 애플리케이션 레이어 정렬이 레코드·캐시·라이브 세 경로를 모두 같은 순서로 덮으므로 DB 반환 순서 자체가 표시에 무관해진다. `ORDER BY`만 추가하면 **레코드 경로만** 고쳐지고 현재 기간(캐시/라이브)의 Map 삽입 순서 의존은 그대로 남아 두 경로가 여전히 어긋날 수 있어, 근본 해결이 아니라 부분 해결이 된다.
5. **[[ADR-035]] 결정 20의 사본을 공용 함수로 흡수한다.** `manual-boss-merge.ts`의 사설 `BOSS_ORDER_INDEX`/`orderIndexOf`(같은 `weekly-bosses.json` 정규 순서 인덱스)를 결정 3의 `getBossReferenceOrder`로 대체해 중복을 제거한다 — 정렬 순서 계약은 동일하고, 스케줄러 화면의 기존 순서는 ADR-035 결정 20 회귀 테스트가 그대로 지켜준다. `manual-boss-merge.ts`의 cycle 조회 테이블(`BOSS_CYCLE_BY_NAME`/`lookupCycle`)은 정렬과 별개 관심사라 그대로 둔다.

**이유·트레이드오프**:
- 단일 choke point 수정이 세 경로를 한 번에 덮어, 표현 계층(`buildCharacterGroups`)·DB 계층(`ORDER BY`)에 각각 손대는 방식보다 회귀 위험이 작다.
- `getBossReferenceOrder`를 `boss-matching.ts`(= `REFERENCE_ENTRIES`의 소유자)에 두고, [[ADR-035]] 결정 20에서 `manual-boss-merge.ts`가 만든 사설 사본 `BOSS_ORDER_INDEX`/`orderIndexOf`도 **이번에 이 공용 함수로 흡수해 중복을 제거한다**(결정 5). 두 사본은 같은 `weekly-bosses.json` 순서를 각자 인덱싱하던 것이라, 하나로 합쳐도 스케줄러 화면의 기존 순서 계약(ADR-035 결정 20 회귀 테스트로 고정됨)은 그대로 유지된다.
