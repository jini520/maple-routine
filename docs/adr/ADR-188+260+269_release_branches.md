# ADR-188+260+269 브랜치 전략과 ADR 번호 받기, 사용자에게 묻기 전에 확인할 것, 버전의 역할과 릴리즈 대기 단계, 찾은 잘못을 그 자리에서 고치기

> 🟢 유효
> 관련 소스: `scripts/adr-number.mjs` · `scripts/__tests__/adr-number.test.mjs`

## 배경

2026-11-09 까지는 모든 작업 브랜치를 main 에서 따서 main 에 머지했다. 그래서 다음 스토어 버전에만 넣을 네이티브
변경(#907)이 main 에 들어오자 main 이 스토어에 나가 있는 앱과 달라졌다. 그 뒤로 1.0.13 사용자에게 OTA 를 낼 때마다
스토어 바이너리를 빌드한 커밋으로 워크트리를 따로 만들어야 했다. OTA 1.0.13+5 는 `a453777f` 트리에서 발행했다.

ADR 번호도 겹친 적이 있다. 2026-11-04 에 병렬 PR 둘이 같은 번호를 붙였다. 각 브랜치에서는 검사를 통과했지만 머지
뒤 `adr-policy.test.ts` 의 `한 번호는 한 파일에만 있다` 가 깨졌다(#844, #846 에서 고침). 핫픽스를 main 에서 따면
develop 에서 이미 쓴 번호가 그 브랜치에 보이지 않는다. 그래서 같은 일이 더 쉽게 생긴다.

## 결정

### 결정 1. main 은 출시된 것만 담는다

main 에는 `release/x.y.z` 와 `hotfix/<slug>` 만 머지한다. main 에 바로 커밋하지 않고, 작업 브랜치를 main 으로 PR
하지 않는다.

그래야 main 의 끝이 언제나 스토어 바이너리와 그 위에 발행한 OTA 와 같다. 그러면 main 에서 핫픽스를 따기만 해도
그 트리가 OTA 를 발행할 트리가 된다.

### 결정 2. develop 이 다음 스토어 버전을 모은다

GitHub 기본 브랜치는 develop 이다. develop 은 새 버전, 곧 다음 스토어 버전을 모은다. 그 버전의 `release/x.y.z` 를 딴
뒤에 develop 에 들어가는 것은 그다음 버전으로 나간다(결정 5). 지금 몇 버전인지는 문서에 적지 않고 작업 전에 확인한다(결정 11).

기본 브랜치를 develop 으로 둔 것은 PR 본문의 `Closes #n` 이 기본 브랜치에 머지될 때만 이슈를 닫기 때문이다.
본 체크아웃도 develop 에 둔다. 작업은 `.claude/worktrees/` 의 워크트리에서 한다.

### 결정 3. 작업 브랜치는 develop 에서 따고 develop 으로 PR 한다

브랜치 이름은 `<종류>/<영어 slug>` 다. 종류는 커밋 메시지의 conventional commits 종류와 같은 말을 쓴다.

| 종류 | 쓰는 때 |
|---|---|
| `feat/` | 새 기능 |
| `fix/` | 버그 고침 |
| `chore/` | 빌드 · 설정 · 스크립트 · 버전 올림 |
| `docs/` | 문서만 바꿀 때 |
| `refactor/` | 동작을 바꾸지 않는 코드 정리 |

이슈가 있으면 slug 끝에 이슈 번호를 붙인다(`fix/tracking-mode-unavailable-877`).

### 결정 4. 이슈에 없는 작업은 설계 → 이슈 → 문서 → 테스트 → 구현 순서로 한다

사용자가 시키지 않아도 이 순서를 지킨다.

1. 설계: 무엇을 왜 바꾸는지 정한다. 사용자가 골라야 할 것은 이 단계에서 묻는다.
2. 이슈: 설계를 이슈로 쓰고 마일스톤을 붙인다.
3. 문서: ADR 과 기능 문서를 고친다. 사용자에게 보이고 확인을 받는다.
4. 테스트: 테스트를 먼저 쓴다.
5. 구현: 테스트를 통과시킨다.

문서를 나중에 채우면 문서와 다른 구현이 그대로 머지된다. 이슈가 없으면 그 작업이 어느 버전에 들어갔는지 마일스톤으로
찾을 수 없다.

### 결정 5. 스토어 출시는 `release/x.y.z` 에서 한다

1. 출시를 준비할 때 develop 에서 `release/x.y.z` 를 딴다. 여기서 릴리즈 대기 단계가 시작된다(결정 12). 그 자리에서
   새 버전의 마일스톤을 만든다. 그 뒤 develop 에 들어가는 것은 다음 버전으로 나가기 때문이다.
2. 버전 올림 · 스토어 빌드 · 심사 반려 수정은 이 브랜치에서만 한다. 그동안 develop 은 다음 버전의 작업을 계속 받는다.
   바이너리를 올린 뒤에는 심사 반려 수정만 넣는다. 이 브랜치가 그 바이너리의 트리로 남아야 그 위에 OTA 를 낼 수 있다.
3. 바이너리를 올리면 이 브랜치의 끝에서 `patch/x.y.z` 를 딴다(결정 12).
4. 스토어에 게시되면 이 브랜치를 main 으로 PR 해 merge commit 으로 머지한다.
5. 곧바로 main 을 develop 과 `patch/x.y.z` 로 머지한다(결정 7). 이어서 `patch/x.y.z` 를 main 으로 낸다(결정 12).

release 브랜치를 따로 두는 것은 심사를 기다리는 며칠 동안 develop 에 들어온 작업이 같은 바이너리에 섞이지 않게
하려는 것이다. 빌드 절차는 `foundation/release.md` 에 있다.

### 결정 6. 핫픽스는 main 에서 `hotfix/<slug>` 를 딴다

1. main 에서 `hotfix/<slug>` 를 딴다.
2. 결정 4 의 순서대로 이슈 · 문서 · 테스트 · 고침을 한다. ADR 새 번호는 결정 8 로 받는다.
3. OTA 로 낸다면 이 브랜치의 트리에서 발행한다. 버전 올림과 노트 커밋도 이 브랜치에 남긴다
   (`features/live-update.md` 의 `OTA 발행 절차`).
4. main 으로 PR 해 merge commit 으로 머지한다. squash 하면 발행한 트리의 커밋이 main 에서 사라진다.
5. 곧바로 main 을 develop 으로 머지한다(결정 7).

develop 에서 따지 않는 것은 develop 에 아직 출시하지 않은 작업이 있기 때문이다. 거기서 따면 그 작업이 핫픽스와 함께
main 으로 간다. 그 안에 네이티브 변경이 있으면 지문이 달라져 OTA 로도 낼 수 없다.

1.0.14 가 스토어에 게시되기 전까지는 main 에 1.0.13 바이너리에 없는 네이티브 변경(#907)이 들어 있다. 그래서 그동안의
1.0.13 핫픽스는 main 의 끝이 아니라 마지막으로 발행한 1.0.13 OTA 트리(지금은 1.0.13+8 의 `ccd57f54` 에 1.0.14 의 심사 중 지문만 더한 `a9121c44`)에서 딴다.
그보다 옛 트리에서 따면 뒤에 발행한 OTA 의 고침이 빠진다. 그래서 1.0.13 핫픽스를 발행하면 이 커밋을 그 핫픽스 브랜치의
끝으로 고친다. `release/1.0.14` 가 main 에 머지되면 이 단락을 지운다.

### 결정 7. main 에 머지하면 곧바로 main 을 develop 으로 머지한다

release 나 hotfix 를 main 에 머지하면 main 을 head, develop 을 base 로 PR 을 만들어 merge commit 으로 머지한다.
충돌이 나면 develop 에서 `chore/merge-main-<버전>` 을 따서 main 을 머지하고, 충돌을 푼 뒤 develop 으로 PR 한다.
릴리즈 대기 단계에는 `patch/x.y.z` 에도 같은 방법으로 main 을 머지한다(결정 12).

미루면 다음 스토어 바이너리를 develop 에서 빌드할 때 그 고침이 빠진다.

그 뒤 열려 있는 작업 브랜치는 다음 커밋 전에 develop 을 머지하고, 그 위에서 작업을 이어 간다(사용자 지정 2026-11-10).
핫픽스가 같은 파일을 건드렸는지 가리지 않고 모든 작업 브랜치가 받는다. 겹치는지 따지다 놓치는 일이 없고, 작업 브랜치의
테스트도 핫픽스가 든 코드에서 돌기 때문이다. 충돌은 작업 브랜치에서 푼다.

한 기능의 ADR 은 한 파일이고, 결정이 바뀌면 파일 이름에 번호를 덧붙인다. 그래서 hotfix 와 develop 이 같은 ADR 에
서로 다른 번호를 붙였으면 파일 이름이 둘로 갈린다. 이 머지에서 파일을 하나로 합치고 두 번호를 오름차순으로 모두
이어 붙인다(`ADR-011+138+189+190_live-update_protocol.md`). 두 쪽의 결정과 번호 기록 줄도 모두 남긴다.

### 결정 8. ADR 새 번호는 `scripts/adr-number.mjs` 로 받는다

```bash
node scripts/adr-number.mjs
```

스크립트는 `git fetch origin` 을 한 뒤 아래를 모두 본다.

| 보는 곳 | 보는 이유 |
|---|---|
| origin 의 main · develop, main 에 아직 머지되지 않은 `release/*` · `hotfix/*` | 머지됐거나 출시 중인 번호 |
| 열린 PR 의 브랜치(`gh pr list`) | 아직 머지되지 않은 번호 |
| 이 맥에 있는 모든 워크트리의 `docs/adr/` | 다른 세션이 만들고 아직 커밋하거나 푸시하지 않은 번호 |

그중 가장 큰 번호에 1 을 더해 찍는다. 같은 번호를 서로 다른 ADR 파일이 쓰면 충돌로 찍고 종료 코드 1 로 끝난다.
서로 다른 파일이란 파일 이름에서 번호를 뺀 `카테고리_기능` 이 다른 파일이다. 같은 파일의 번호 목록이 브랜치마다
다른 것(`ADR-011` 과 `ADR-011+138`)은 충돌이 아니다. `git fetch` 나 `gh` 가 실패하면 번호를 내지 않고 종료 코드 2
로 끝난다. 일부만 보고 고른 번호는 겹칠 수 있기 때문이다.

로컬 브랜치는 보지 않는다. 진행 중인 작업은 워크트리로 본다. main 에 이미 머지된 `release/*` · `hotfix/*` 도 보지
않는다. 그 번호는 main 이 이미 담고 있다. 게다가 문서 재작성(PR #659) 전에 딴 브랜치는 옛 번호를 써서, 보면 가장
큰 번호가 300 넘게 튄다. 2026-11-09 에 지운 `release/1.0.12` 셋이 그랬다.

쓰는 때는 둘이다.

- 새 번호가 필요하면 스크립트를 돌리고, 받은 번호로 곧바로 파일을 만든다. 파일이 워크트리에 있어야 다른 세션이 돌린
  스크립트가 그 번호를 본다.
- PR 을 머지하기 직전에 다시 돌려 종료 코드 0 을 확인한다. 핫픽스는 main 에 머지하기 전에 반드시 확인한다. main 에
  들어간 뒤에 겹친 것을 알면 이미 출시한 파일의 이름을 바꿔야 한다.

### 결정 9. 서버 저장소도 앱과 같은 모양을 쓴다 (사용자 선택 2026-11-20)

`maple-routine-server` 도 main 은 운영 박스에 배포된 것만 담고, GitHub 기본 브랜치는 develop 이다. develop 은 새 버전의 앱이 쓸
서버를 모은다. 작업 브랜치와 핫픽스는 결정 3 · 4 · 6 · 7 과 같다.

- develop 에 지금 앱과 호환되지 않는 변경이 없으면, develop 을 head · main 을 base 로 PR 해 merge commit 으로 머지하고 main 에서
  배포한다. 서버에는 스토어 심사처럼 기다리는 기간이 없어서다.
- develop 에 호환되지 않는 변경이 들어 있는 동안에는 develop 을 운영에 배포하지 않는다. 운영 서버의 고침과 기능은 모두 main 에서
  `hotfix/<slug>` 를 따서 main 에 머지하고 main 에서 배포한다. 곧바로 main 을 develop 으로 머지한다(결정 7). 2026-11-20 부터
  #947 의 새 표가 그런 변경이다.
- 그동안 운영 서버에 관한 문서의 고침도 hotfix 로 낸다(사용자 선택 2026-11-20). 서버 `README.md` 의 배포 · 운영 절차와 서버
  `CLAUDE.md` 의 규칙이다. hotfix 작업과 배포는 main 의 문서를 읽는데, develop 에만 넣으면 새 버전을 게시할 때까지 main 에 가지
  못한다. 새 표에만 해당하는 문서는 develop 에 둔다.
  - 호환되지 않는 변경을 처음 넣기 전에 develop 을 main 에 머지한다. 2026-11-20 에는 서버 develop 에만 브랜치 규칙과 배포 끝에
    Docker 데몬을 다시 켜는 단계가 있어서, #947 의 첫 표 묶음(서버 #126)을 넣기 전에 develop 을 main 에 머지했다. 코드 차이가
    없어 배포하지 않았다.
- 그 새 버전의 앱이 `release/x.y.z` 를 딸 때 서버도 develop 에서 `release/x.y.z` 를 딴다. 심사용 서버([[ADR-099]] 결정 43)는
  이 브랜치에서 띄우고, 심사 중의 서버 고침도 이 브랜치에 넣는다. 앱이 게시되면 이 브랜치를 main 에 머지해 운영에 배포하고 main 을
  develop 으로 머지한다.
- 서버에는 `patch/x.y.z` 가 없다. 게시 전이든 뒤든 운영 서버의 고침은 hotfix 다.
- 호환되지 않는 서버 작업만 모으는 브랜치를 따로 두지 않고 앱과 같은 모양으로 둔 것은, 앱에서 쓰는 역할(운영 · 릴리즈 대기 ·
  새 버전)을 서버에서도 그대로 쓰려는 것이다(사용자 지정).

서버의 결정 문서는 이 저장소 `docs/` 에 있다. 그래서 서버 작업의 ADR 번호도 결정 8 의 스크립트로 받는다.

### 결정 10. 사용자에게 묻기 전에 관련된 것을 모두 확인하고, 다듬은 질문을 한 번에 낸다 (사용자 지정 2026-11-19)

> 사용자 지정(2026-11-19): 자꾸 두 번씩 일 시키지 말고 나한테 질문할 때에는 문서와 현재 코드, 로직 등 관련 된거 다 확인하고
> 최적화 해서 나한테 질문해.

덜 확인한 질문은 사용자가 되묻게 만든다. 답을 받은 뒤에 다시 조사해 고치게 되고, 사용자는 같은 것을 두 번 판단한다.
2026-11-19 에 서버 표를 검토하면서(#947) 하루에 다섯 번 그랬다.

- 서버에 줄을 지우는 경로가 없는 표를 두고 줄을 찾지 못하면 어떻게 할지 물었다.
- 관리 화면에 고치는 경로가 있다는 것만 보고 다시 물었다. 관리 화면은 사용자 혼자 쓰고, 그 표는 한 번도 고친 적이 없었다.
- 서버 코드에 없는 경우를 보기의 근거로 들었다.
- 앞에서 설명했고 사용자가 받아들인 이름 기준과 어긋나는 보기를 권했다.
- 기기 표의 칸 이름을 서버 표와 다르게 두는 것을 묻지 않고 정했다. 그 칸이 서버 표의 어느 칸에 대응하는지 따져 보지 않았다.

결정 4 의 설계 단계뿐 아니라 사용자에게 내는 모든 질문에 적용한다. 묻기 전에 아래를 모두 한다.

1. 문서를 읽는다. 그 주제를 다루는 ADR 의 결정을 뒤 결정까지 모두 읽고, `docs/features/*` 와 `docs/persistence/*` 의 해당 문서를
   읽는다. 이미 정한 결정과 거기서 따라 나오는 것은 묻지 않는다.
2. 지금 코드를 읽는다. 그 값을 쓰는 곳과 읽는 곳을 모두 찾는다. 저장소를 다루면 기기 표(`src/storage/sqlite/*`)와 서버
   표(서버 저장소 `src/database/schema.ts`)를 함께 보고, 기기 표의 칸이 서버 표의 어느 칸에 대응하는지 적는다. 화면에 보이는
   것을 말하려면 그 화면의 코드를 읽는다.
3. 실제 값을 본다. 운영 DB 는 읽기 전용으로 조회하고, 기기의 값은 기기 백업에서 본다.
4. 질문 · 보기 · 근거에 든 경우가 실제로 생기는지 확인한다. 그 일을 일으키는 경로가 코드에 있는지, 그 경로가 실제로 쓰인 적이
   있는지, 사용자만 쓰는 경로면 사용자가 그 일을 하는지를 본다. 생기지 않는 경우는 쓰지 않는다.
5. 사용자가 정한 기준, Claude 가 설명했고 사용자가 받아들인 기준과 어긋나는 보기를 내지 않는다.
6. 한 주제에서 물을 것은 모아서 한 번에 묻는다. 답 하나로 끝나도록 그 답에 딸린 것(이름 · 기기 표 · 유일 기준 · 옮기는 방법)을
   같은 질문에 담는다.
7. 확인한 결과를 질문에 숫자와 파일 이름으로 적는다.

스스로 확인할 수 있는 것은 묻지 않는다. 확인해도 정할 수 없는 것만 묻는다. 묻지 않고 Claude 가 정한 것이 있으면 정했다는
것과 이유를 알린다.

### 결정 11. 버전은 역할로 부르고, 작업 전에 어느 버전의 일인지 정한다 (사용자 지정 2026-11-20)

규칙에 버전 숫자를 적으면 단계가 바뀔 때마다 낡는다. 2026-11-20 에는 `release/1.0.14` 를 딴 뒤에도 결정 2 에 `develop 에
들어가는 것은 모두 1.0.14 로 나간다` 가 남아 있었다. 그래서 규칙은 역할로만 쓰고, 숫자는 작업할 때 확인한다(사용자 선택).

| 역할 | 브랜치 | 숫자를 얻는 곳 | 마일스톤 |
|---|---|---|---|
| 운영 버전 | main | main 의 `app.json` `expo.version` | 그 위의 OTA 는 `v<운영>+N` |
| 릴리즈 대기 버전 | `release/x.y.z` · `patch/x.y.z` | main 에 머지되지 않은 `release/x.y.z`. `git branch -r --no-merged origin/main --list 'origin/release/*'` | 바이너리에 든 것은 `v<대기>`, 게시 직후 OTA 는 `v<대기>+1` |
| 새 버전 | develop | 가장 큰 `vx.y.z` 마일스톤 | `v<새>` |

- develop 의 `app.json` 은 release 를 딸 때까지 버전을 올리지 않는다. 그래서 새 버전의 숫자는 마일스톤으로 안다. release 를
  딸 때 다음 마일스톤을 만드는 것(결정 5)이 이 확인을 지킨다.
- 작업을 시작할 때 이슈 마일스톤으로 어느 버전의 일인지 정한다. 마일스톤이 없거나 두 버전에 걸치면 사용자에게 묻는다.
- 운영 버전의 고침은 hotfix(결정 6), 릴리즈 대기 버전의 고침은 `patch/x.y.z`(결정 12), 새 버전의 작업은 develop(결정 3)
  이다. 고침은 이슈 · 문서 · 테스트 · 코드를 모두 그 브랜치에 둔다. 문서만 develop 으로 PR 하면 그 문서는 새 버전에만
  들어가고 고침과 문서가 갈린다.
- 서버만 고치는 일(앱 코드는 그대로이고 서버만 바뀌는 일)의 앱 저장소 문서는 앱 develop 으로 PR 한다(사용자 선택 2026-11-20).
  서버는 앱 버전과 상관없이 배포되고, 다음 작업은 develop 에 있는 본 체크아웃에서 문서를 읽기 때문이다. 앱의 hotfix 나
  patch 에 넣으면 그 문서는 다음 출시 때까지 develop 에 없다.
- 새 버전이 앱과 서버를 새 표로 통째로 바꾸는 동안(#947, [[ADR-099]] 결정 43 · 65)은 더 조심한다.
  - 운영 · 릴리즈 대기 버전의 고침에 새 표 · 새 칸 이름 · 새 버전의 기능을 넣지 않는다. 새 버전의 작업에 옛 표와 옛 앱의
    호환을 넣지 않는다. 섞이면 옛 표로 도는 운영이 깨지거나 새 코드에 옛 호환이 남는다.
  - 서버도 같은 모양이다(결정 9). 운영 서버를 쓰는 앱의 고침은 서버 main 에서 딴 hotfix 로 지금 표와 모듈을 고친다. 새 버전의
    작업은 서버 develop 에서 새 표로 한다.
  - 로직을 고친 운영 · 릴리즈 대기 버전의 고침은 새 표 위의 코드에도 필요한지 확인하고, 필요하면 #947 에 옮길 일로 적는다.
    이 항목은 Claude 가 더했다.
  - 이 묶음은 새 버전을 게시하고 옛 앱을 막으면([[ADR-099]] 결정 43) 지운다.

### 결정 12. 릴리즈 대기 단계에는 심사 중인 버전의 고침을 `patch/x.y.z` 에 모은다 (사용자 선택 2026-11-20)

`release/x.y.z` 를 따고 게시되기 전까지는 버전이 셋이다. 운영 버전(main), 릴리즈 대기 버전(release), 새 버전(develop)이다.
이 단계를 처음 둔 2026-11-20 에는 운영 1.0.13 · 대기 1.0.14 · 새 버전 1.0.15 였다.

이 단계에는 심사 중인 버전이 게시되자마자 OTA 로 낼 고침이 갈 곳이 없었다. release 는 심사에 올린 바이너리의 트리로 남아야
그 위에 OTA 를 낼 수 있고, main 에는 그 버전이 아직 없다. #1093 은 release 의 끝에서 hotfix 를 따고 게시될 때까지 PR 을
미뤘다. 그러면 PR 이 열린 채 쌓이고, 운영 버전의 고침과 심사 반려 수정을 브랜치마다 따로 받아야 한다.

1. 바이너리를 올리면 `release/x.y.z` 의 끝에서 `patch/x.y.z` 를 딴다. 그 자리에서 main 을 머지한다. release 를 딴 뒤에 낸
   운영 버전의 고침이 main 에 있을 수 있다.
2. 심사 중인 버전에 게시 직후 낼 고침은 `fix/<slug>` 같은 작업 브랜치를 `patch/x.y.z` 에서 따서 `patch/x.y.z` 로 PR 한다.
   이슈 마일스톤은 `v<대기>+1` 이다.
3. `patch/x.y.z` 에 머지하면 곧바로 `patch/x.y.z` 를 develop 으로 머지한다. 미루면 새 버전에 그 고침이 빠진다.
4. 운영 버전의 hotfix 를 main 에 머지하면 main 을 develop 과 `patch/x.y.z` 로 머지한다(결정 7). release 에 심사 반려
   수정이 들어가면 release 를 `patch/x.y.z` 로 머지한다.
5. 게시되면 release 를 main 에 머지하고, main 을 develop 과 `patch/x.y.z` 로 머지한다(결정 5). 이어서 `patch/x.y.z` 를 main
   으로 PR 하고, 그 트리에서 첫 OTA(`<대기>+1`)를 낸 뒤 merge commit 으로 머지한다. 곧바로 main 을 develop 으로 머지하고
   `patch/x.y.z` 를 지운다. 여기서 이 단계가 끝난다.

- `patch/x.y.z` 로 가는 PR 의 `Closes #n` 은 이슈를 닫지 않는다. 기본 브랜치가 아니기 때문이다. 머지하면 이슈를 손으로 닫는다.
- 게시 뒤 옛 바이너리를 잠그는 발행(`features/live-update.md`)도 운영 버전의 hotfix 다. 4 와 같이 main 을 `patch/x.y.z` 로
  머지한다.
- 서버 저장소에는 `patch/x.y.z` 가 없다. 서버의 고침은 게시 전이든 뒤든 운영 서버의 hotfix 이고, 새 버전의 앱이 호환되지
  않는 서버를 쓸 때만 서버에도 release 를 둔다(결정 9).

### 결정 13. 작업 중에 찾은 잘못 · 경고 · 실패는 그 자리에서 고친다 (사용자 지정 2026-11-20)

> 사용자 지정(2026-11-20): 잘못된 부분을 찾으면 같이 수정해 당연한거 아니야?
>
> 1. 동작과 관계없는 문서, 주석 등이 잘못된 것을 발견했을 때 즉시 수정한다.
> 2. 린트, 프리티어 등이 경고나 에러가 발생했을 때 즉시 수정한다.
> 3. 테스트 코드가 실패하는 것이 발생하면 원인을 찾고 즉시 수정한다.

#1116 에서 Claude 는 잘못된 것을 찾고도 고치지 않고 보고만 했다. 점검 배너의 자리를 `화면 맨 위` 라고 적은 주석을 `동작과
관계없다` 며 남겼고, `npx oxlint src` 의 경고 19건을 `이번 작업과 상관없다` 며 남겼다. `npm run lint` 는 돌리지도 않았다. 본
체크아웃에서 돌리면 오류가 3,440건이었다. ESLint 가 `.claude/worktrees` 의 사본까지 훑었기 때문이다(#1122).

남겨 둔 잘못은 사용자가 다시 시켜야 고쳐진다. 그사이 다음 작업은 잘못된 문서와 주석을 읽고 그대로 따른다. 경고가 쌓여 있으면
새로 생긴 경고가 그 사이에 묻힌다.

작업 중에 아래를 찾으면 지금 작업과 관계가 없어도 같은 작업에서 고친다. 보고만 하고 넘어가지 않는다.

1. 문서 · 주석 · 테스트 이름이 지금 코드와 다르다. 동작과 관계가 없어도 고친다.
2. 린트 · 포매터 · 타입 검사가 경고나 오류를 낸다. 오류만이 아니라 경고도 고친다.
3. 테스트가 실패한다. 바꾼 것 때문이 아니어도 원인을 찾아 고친다.

어떻게 고칠지가 사용자가 정할 일이면(게임 레퍼런스 수치 · 앱 문구 등) 남겨 두지 않고 그 자리에서 묻는다. 고친 것은 보고에
적는다. 전역 `CLAUDE.md` 의 `Surgical Changes`(주변 주석을 고치지 말고 알리기만 하라)보다 이 결정이 먼저다.
