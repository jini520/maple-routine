## 증상 (이슈 #168, 사용자 보고 1건)

보스 수익에서 **기록이 없는 과거 기간으로 이동**하면 `지난 주 기록을 불러오고 있어요` 카드가
**한 프레임 아래쪽(약 90px)에 그려졌다가 제자리로 올라온다.** 같은 카드가 자리를 옮기는 것이지
내용이 바뀌는 것이 아니다.

**이 ADR 시점의 근거는 이슈 보고 1건과 코드 읽기뿐이다.** 브라우저 프레임 계측도, 실기기 관측도
아직 없다. 이 프로젝트는 브라우저에서 멀쩡하던 것이 실기기에서 깨진 이력이 반복됐으므로
([[ADR-079]]·[[ADR-085]]·[[ADR-098]]) 확인하지 않은 것을 확인한 것처럼 적지 않는다.

## 원인 사슬

1. 기간을 이동하면 스토어가 `isPeriodLoading: true` 로 바꾼다(`features/boss-profit/store.ts`).
2. 헤더 안의 총 수익 헤드라인 블록이 `!isPeriodLoading` 게이트에 걸려 사라진다
   (`BossProfitScreen.tsx:744`) → **헤더 DOM 이 약 91px 짧아진다.**
3. 그런데 spacer 높이(`stickyHeaderHeight`)는 아직 옛 값이다 — 측정 `useLayoutEffect` 의 deps 가
   `[isEmpty]` 하나뿐이라 이 전환에서 재실행되지 않는다(`BossProfitScreen.tsx:512~526`).
4. **이 상태로 한 프레임이 그려진다** ← 헤더는 이미 짧은데 spacer 는 아직 길어서, 카드가 약 90px
   아래에 있다.
5. `ResizeObserver` 가 발화해 `setState` → 다음 렌더에 spacer 가 줄고 카드가 제자리로 튀어 오른다.

### 이동량 ~91px 내역

헤드라인 블록이 사라지면서 함께 빠지는 것들이다.

| 요소 | px |
|---|---|
| 라벨행 `h-6` | 24 |
| 금액행 `mt-1.5` | 6 |
| 금액행 `h-8` | 32 |
| 헤어라인 `mt-3` | 12 |
| 헤어라인 `h-px` | 1 |
| 부모 `space-y-4`(사라진 형제만큼 빠지는 간격) | 16 |
| **합계** | **91** |

### 핵심 — 갱신 경로가 `ResizeObserver` 하나뿐이다

`ResizeObserver` 콜백 자체는 스펙상 페인트 **전**에 배달된다. 문제는 그 안의 `setState` 다 —
React 이벤트 밖이라 React 가 Scheduler(MessageChannel) 태스크로 넘겨 **다음 프레임**에 렌더한다.
[[ADR-102]] 가 아코디언 접기에서 관측한 그 성질이 그대로다(그쪽은 `rAF` 콜백 안의 `setState`
였고, 여기는 RO 콜백 안의 `setState` 다 — 둘 다 "이벤트 밖"이라는 점이 같다).

반면 `useLayoutEffect` 안의 `setState` 는 **같은 커밋에서 페인트 전에 동기 반영된다.** 그래서
헤더 높이를 바꾸는 상태 전환에 대해서는 RO 가 원리적으로 한 프레임 늦고, layout effect 는 안 늦는다.

**[[ADR-085]] 트레이드오프의 세 번째 항목이 이미 이 자리를 가리키고 있었다** — *"헤더 높이가
바뀌면(탭·경고·동기화 영역) `ResizeObserver` 가 따라가고, 첫 프레임은 `useLayoutEffect` 실측이
막는다."* 그 문장은 **마운트 첫 프레임**만 layout effect 가 맡는다고 읽히고, 실제 구현도 그랬다
(deps `[isEmpty]` / `[]`). 마운트 이후에 헤더 높이를 바꾸는 상태 전환은 RO 에게만 맡겨져 있었다.

## '미확인' 2건 — 코드 확인 결과

이슈에 '미확인'으로 적힌 두 가지는 **코드 확인으로 답이 나왔다.**

**1. 기록이 있는 기간에서도 같은 프레임이 나는가 → 난다.**
헤드라인 게이트는 `!isPeriodLoading && characterGroups.length > 0` 이고, 기간 이동 중에는
`isPeriodLoading` 이 참이라 **기록 유무와 무관하게** 헤더가 짧아진다. 다만 기록이 있으면 곧이어
캐릭터 카드가 들어차 튐이 콘텐츠 변화에 섞여 **눈에 덜 띌 뿐**이다. 기록이 없는 기간에서 보고가
올라온 것은 그 자리에 셸 승계 로딩 카드([[ADR-061]] 결정 2) 하나만 있어 이동이 그대로 읽히기 때문이다.

**2. 공용 `PageHeader` 도 같은 문제인가 → 구조적으로 같다. 다만 관측은 없다.**
`PageHeader.tsx:48~62` 의 deps 가 `[]` 라 마운트 1회 외엔 갱신 경로가 RO 하나뿐인데, 이 셸을 쓰는
네 화면 전부 헤더 `children` 안에 조건부 블록이 있다:

| 화면 | 헤더 안의 조건부 블록 |
|---|---|
| `ContentScreen` | 셸 승계 로딩 카드(`characters.length === 0`), 일간/주간 탭 줄 |
| `BossScreen` | 로딩 카드, 탭 줄, 주간 클리어 카운트, 시즌 보스 줄 |
| `BossManageScreen` · `ContentManageScreen` | `selected !== null` 게이트 블록 |

즉 같은 사슬이 성립할 조건이 갖춰져 있다. **사용자 보고는 아직 없고 브라우저·실기기 관측도 없다** —
"구조가 같으므로 함께 고친다"이지 "관측됐다"가 아니다([[ADR-098]] 결정 4가 관리 화면 2개를 함께
고친 것과 같은 종류의 판단).

## 결정

### 결정 1 — 측정 전용 layout effect 를 deps 없이 따로 둔다. `ResizeObserver` 는 남긴다

두 effect 가 서로 다른 것을 맡는다.

```
측정 effect : deps 없음 → 매 커밋, 페인트 전에 getBoundingClientRect().height
관찰 effect : ResizeObserver → 렌더 밖 변화(폰트 로드·기기 회전 등) 담당
```

끊는 고리는 3이다 — **헤더 DOM 을 바꾼 그 커밋에서 spacer 도 함께 갱신되므로** 4의 어긋난 프레임이
그려질 자리가 없어진다. RO 를 지우지 않는 이유는 그것이 끊는 고리가 따로 있기 때문이다: 렌더 없이
높이가 바뀌는 경우(웹폰트 로드, 기기 회전, 안전영역 변화)는 커밋이 아예 없어 측정 effect 가 안 돈다.
둘은 대체 관계가 아니라 담당이 다르다.

### 결정 2 — 공용 훅 `src/lib/use-measured-height.ts` 로 추출한다

호출부는 두 곳이다 — `components/templates/PageHeader/PageHeader.tsx`, `app/boss-profit/BossProfitScreen.tsx`.

[[ADR-094]] 가 정한 두 조건을 다 충족한다: **호출부 2곳 이상**이고, **취약 구조**다(실측 + spacer 는
[[ADR-085]]·[[ADR-098]] 이 실기기에서 여러 번 틀린 끝에 얻은 형태이고, 그 값을 [[ADR-047]] 중첩
sticky 가 자기 `top` 오프셋으로 다시 쓴다). 복붙된 채로는 한 곳을 고쳐도 나머지가 안 고쳐진다 —
[[ADR-098]] 결정 2가 `PageHeader` 를 만들며 이미 겪은 종류의 문제다.

### 결정 3 — 훅의 API 는 `RefObject` 가 아니라 **콜백 ref** 다

```ts
export function useMeasuredHeight<T extends HTMLElement>(): {
  ref: (node: T | null) => void
  height: number
}
```

**콜백 ref 인 것이 설계의 핵심이다.** 요소를 state 로 잡아야 관찰 effect 가 요소의 등장·소멸을 따라
재부착된다. `RefObject` 는 `.current` 가 바뀌어도 리렌더를 일으키지 않아, 요소가 조건부로 마운트되는
화면에서는 "언제 다시 observe 할 것인가"를 호출부가 deps 로 알려줘야 한다 — 그것이 지금
`BossProfitScreen` 의 `[isEmpty]` 다(빈 상태에서 헤더가 통째로 언마운트되는 경로).

콜백 ref 로 바꾸면 그 **`[isEmpty]` deps 가 사라진다.** 훅이 요소의 등장·소멸을 구조적으로 처리하므로
호출부가 자기 상태를 훅에 알려줄 이유가 없어진다.

## 기각한 대안

**1. deps 목록을 명시한다**(`isPeriodLoading` · `characterGroups.length > 0` · `periodState` ·
`canRefreshPeriod`) → 헤더에 조건부 블록이 추가될 때마다 deps 를 같이 고쳐야 하고, 빠뜨리면 같은
버그가 **조용히** 되살아난다(에러가 아니라 한 프레임 어긋남이라 테스트로도 잘 안 잡힌다). 무엇보다
**공용 `PageHeader` 는 `children` 이 임의라 이 방식이 원리적으로 불가능하다** — 셸은 자기 안에 무엇이
들어오는지 모른다.

**2. 헤더 높이를 상태와 무관하게 고정한다**(로딩 중에도 헤드라인 자리를 예약) → 튐이 원천적으로
없어지지만 **로딩 중 약 90px 빈 블록이 남는 디자인 변경**이고, 결정할 사람이 다르다. 게다가
`PageHeader` 의 탭 줄·필터·로딩 카드에는 적용할 수 없어 **화면 전용 처방**이 된다(공용 셸 쪽 결함이
그대로 남는다).

**3. `ResizeObserver` 콜백의 `setState` 를 `flushSync` 로 감싼다** → 같은 프레임에 반영되긴 하나 RO
broadcast 루프 안에서 렌더 + 레이아웃을 다시 돌려 `ResizeObserver loop completed with undelivered
notifications` 계열의 위험을 새로 들인다. 측정 effect 쪽이 **같은 효과를 더 단순하게** 낸다.

**4. spacer 를 없애고 헤더를 흐름 안으로 되돌린다** → **기각이 아니라 금지에 가깝다.** [[ADR-085]]
결정 1이 `fixed` 로 옮긴 것은 iOS 실기기에서 `sticky` 헤더가 화면 밖(`-1065px`)으로 날아가는 문제를
풀기 위해서였다(실기기 프레임 계측). 되돌리면 훨씬 큰 문제가 살아난다. spacer 는 그 결정의 짝이지
군더더기가 아니다.

## 트레이드오프

- **커밋마다 `getBoundingClientRect()` 1회 = 강제 리플로우 1회.** 이것이 이 결정의 유일한 실비다.
  지금은 안전하다 — 당겨서 새로고침 드래그는 목록에 `transform` 만 걸어 레이아웃을 더럽히지 않으므로
  ([[ADR-073]] 결정 1·2) 캐시된 레이아웃 값이 그대로 돌아오고, [[ADR-072]] 결정 4·[[ADR-073]] 이 지킨
  **"터치 프레임마다 리플로우 없음"**은 유지된다. **다만 인디케이터나 목록 이동을 흐름·크기를 바꾸는
  방식**(흐름 자식 배너, 마진·높이 애니메이션)**으로 되돌리면 이 대가가 실제 비용이 된다** — 당기는
  동안 매 프레임 리플로우가 돈다. 그쪽을 바꿀 일이 생기면 이 항목을 먼저 읽을 것.
- **RO 와 측정 effect 가 같은 값을 두 번 쓸 수 있다.** 같은 높이면 `setState` 가 리렌더를 만들지
  않으므로(React 의 bailout) 비용은 함수 호출 한 번이다.
- **관측 없이 `PageHeader` 를 함께 고친다.** 구조가 같다는 코드 근거만으로 넷을 바꾸는 것이라,
  스케줄러 4화면에서 실제로 증상이 있었는지는 이 결정으로는 끝내 알 수 없다.

## 구현하며 정정한 것

**1. 훅은 요소가 사라져도 마지막 실측값을 남긴다.** 설계에 없던 사항인데 두 호출부의 기존 동작이
그렇다(`BossProfitScreen` 은 빈 상태에서 헤더를 통째로 언마운트한다). 이 훅이 정하는 것은 **측정
시점**이지 값의 수명이 아니라고 못박고 테스트로 고정했다.

**2. 측정 effect 의 `setState` 한 줄에서만 `react-hooks/set-state-in-effect` 를 끈다.** 레이아웃
실측은 외부 시스템(DOM) 읽기라 렌더 중에 할 수 없고, 페인트 전에 state 로 들어가야 spacer 가 헤더와
같은 프레임에 맞는다 — 그 "동기 반영"이 이 훅의 존재 이유라 규칙이 겨누는 연쇄 렌더와는 다르다(같은
높이면 React 가 bailout 한다). 사유를 주석에 남기고 그 한 줄에서만 껐다. lint 결과는 baseline 과 같다.

**3. 훅 호출부는 설계대로 둘이고, `BossProfitScreen.tsx` 안에는 `new ResizeObserver` 가 한 건 남는다.**
남은 것은 같은 파일 `CharacterAccordion` 의 **카드 헤더** 실측이다([[ADR-047]] 후속 — 접힘 66px /
펼침 64px, `useEffect` deps `[isExpanded]`). 페이지 헤더 spacer 와 **다른 요소·다른 관심사**라 이번
범위 밖으로 두었다: 결정 2가 호출부를 둘로 못박았고(훅 doc 도 "`fixed` 페이지 헤더 spacer 전용"),
옮기면 `useEffect` → `useLayoutEffect` 로 카드 하단 페이드 위치의 갱신 타이밍이 바뀌는데 그것을
다루는 결정이 아직 없다. **바꿀 이유가 생기면 별도 결정이 필요하다.**

| RO 경로가 죽지 않았다 | 훅 테스트 `ResizeObserver 콜백이 오면 갱신한다` · `언마운트하면 관찰을 끊는다` |
| 콜백 ref 가 렌더마다 새 함수가 되지 않는다 | 훅 테스트 `요소가 그대로면 관찰을 다시 붙이지 않는다` — ref identity 와 `observe` 호출 횟수를 **둘 다** 단언한다(후자만으로는 못 잡는다: React 가 커밋 중 `setElement(null)`→`setElement(node)` 를 한 배치로 합쳐 state 가 제자리로 돌아오면 bailout 한다) |
| 첫 커밋 실측이 `useLayoutEffect` 다 | 훅 테스트 `첫 커밋에 실측 높이를 낸다` |
| [[ADR-085]]·[[ADR-098]]·[[ADR-100]] 계약 유지 | 기존 `fixed` 회귀 가드와 DOM 스냅샷이 그대로 통과 — 제품 코드 변경은 두 파일의 실측 블록뿐이고 DOM 은 안 바뀌었다(스냅샷 diff 0) |

**세 회귀 가드의 판별력은 `vitest.setup.ts` 의 `ResizeObserver` 스텁이 콜백을 절대 부르지 않는다는
데서 나온다** — RO 경로가 죽은 상태이므로 통과한다는 것은 측정 layout effect 가 같은 커밋에 실제로
쟀다는 뜻이다. 구현 중 코드 변이로 각 케이스의 판별력을 확인했다: 측정 effect 에 `[element, measure]`
deps 를 달면(= 기각안 1) 그 세 케이스만 실패하고 나머지는 전부 통과하며, 관찰 effect 를 지우면 RO
3케이스가 실패한다.

### 자동 테스트가 못 닿는 자리

**jsdom 은 레이아웃을 계산하지 않는다** — `getBoundingClientRect()` 가 늘 0이라 위 케이스들은 전부
높이를 스텁 값으로 흉내 낸다. 그래서 테스트가 담보하는 것은 **측정 시점**(헤더를 바꾼 그 커밋에
spacer 가 따라오는가)이지 **픽셀이 아니다.** "실제로 한 프레임 어긋나 보이는가"는 브라우저·실기기의
몫이다([[ADR-094]] 가 DOM 스냅샷을 안전장치로 삼으며 적어 둔 것과 같은 한계다).

## 남은 확인 — 실기기 미검증

이 세션은 실기기에 접근하지 않았고 브라우저 프레임 계측도 하지 않았다. **이 프로젝트는 브라우저에서
멀쩡하던 것이 실기기에서 깨진 이력이 반복됐으므로**([[ADR-079]]·[[ADR-085]]·[[ADR-098]]) 아래는
전부 열려 있다.

1. 보스 수익에서 **기록 없는 과거 기간**으로 이동할 때 `지난 주 기록을 불러오고 있어요` 카드가
   **한 번에 제자리에** 그려지는가(이슈 #168 의 원 증상 — 약 90px 튐이 사라졌는가).
2. 기록이 **있는** 기간 이동에서도 어긋난 프레임이 없는가(코드상 같은 사슬이지만 캐릭터 카드가
   들어차며 콘텐츠 변화에 섞여 덜 띄던 자리다).
3. 컨텐츠·보스 스케줄러에서 **로딩 카드 → 탭 줄 전환**(콜드 스타트)에 목록이 튀지 않는가.
   `PageHeader` 쪽은 애초에 사용자 관측이 없던 자리라, 여기서 무언가 보인다면 그것이 첫 관측이다.
4. 펼친 캐릭터 카드의 **중첩 sticky 헤더가 stuck 위치를 유지하는가**([[ADR-047]] — 이 실측값을 자기
   `top` 오프셋으로 쓴다). 측정이 매 커밋 돌게 되었으므로 값이 흔들린다면 여기서 먼저 보인다.
