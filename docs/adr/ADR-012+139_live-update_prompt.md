# ADR-012+139 업데이트 동의 모달과 적용

> 🟢 유효
> 옛 번호: ADR-026 · ADR-027 결정 1 · 4 · 6 · 7 · ADR-065 결정 2 · ADR-117 결정 1 · 5 · 7 · ADR-268 결정 1 · 5
> 관련 소스: `features/live-update/store.ts` · `app/UpdatePromptModal.tsx` · `app/settings/AppUpdateSection.tsx` · `native/live-update.ts` · `storage/sqlite/db.ts`

## 배경

OTA 번들을 받아 적용하면 앱이 다시 시작된다. 사용자가 무언가를 입력하는 도중에 앱이 저절로 재시작되면
안 되므로, 적용은 사용자에게 묻는다. 받는 것은 크기가 작으면 묻지 않는다(결정 2). 그리고 적용은 JS 를 통째로 갈아 끼우는
일이라, 중간에 실패하면 사용자가 스플래시 화면에 갇힐 수 있다. 실제로 테스터가 `지금 적용 (재시작)` 을
누른 뒤 앱이 스플래시 화면에서 넘어가지 않았다(이슈 #175). 이 문서는 무엇을 언제 묻는지, 그리고 적용이
실패해도 화면이 돌아오게 하는 방법을 정한다.

프로토콜과 발행은 [[ADR-011]] 에 있다.

## 결정

### 결정 1. 부팅 때 확인하고, 작은 업데이트는 그 자리에서 받는다

`AppShell` 이 마운트되면 `checkOnBoot()` 를 `await` 없이 부른다. 확인은 부가 작업이라 실패해도 앱은
떠야 하고, 부팅이 네트워크 응답을 기다려서도 안 되기 때문이다. `checkOnBoot` 는 지금 버전을 읽고
매니페스트를 확인한다. 새 번들이 있을 때 무엇을 하는지는 결정 2 가 정한다. 적용은 부팅 때 하지 않는다.

부팅 확인과 설정 화면의 `업데이트 확인` 버튼은 같은 스토어(`useLiveUpdateStore`)를 쓴다. 그래서 부팅
때 찾은 업데이트가 설정 화면에도 바로 보이고, 같은 번들을 두 번 받지 않는다.

### 결정 2. 5MB 이하는 묻지 않고 받고, 적용만 묻는다 (사용자 지정 2026-10-30)

새 번들의 `extra.sizeBytes`([[ADR-011]] 결정 8)가 5MB(5,000,000 바이트) 이하면 모달 없이 바로 받는다.
받는 동안에는 모달을 띄우지 않고, 설정 화면 카드의 상태 줄에만 받는 중이라고 보인다. 다 받으면
`업데이트 준비 완료` 모달이 `지금 적용 (재시작)` · `나중에` 를 묻는다. 지금의 OTA 는 몇 MB 라서, 매번
`다운로드` 를 누르게 하는 것은 확인이 아니라 번거로운 절차일 뿐이다(사용자 지적). 번들은 gzip 으로
압축해 보내서 이 기준 아래로 맞춘다([[ADR-011]] 결정 13).

5MB 를 넘으면 지금처럼 모달이 버전과 다운로드 크기를 보여 주고 `다운로드` · `나중에` 를 묻는다. 기준을
넘는 것은 번들이 실수로 크게 불어났을 때 같은 드문 경우다. 셀룰러인지는 알 수 없어서(결정 5) 크기만으로
판정한다.

받은 뒤에도 자동으로 적용하지 않는다. 사용자가 무언가를 입력하는 도중에 앱이 재시작되면 안 되기
때문이다. 처음 실행만은 예외로 묻지 않고 적용한다(결정 12). `나중에` 를 누르면 지금 버전을 그대로 쓴다. 받아 둔 번들은 `expo-updates` 에 남아 있어서
다음에 앱을 새로 켤 때 그 번들로 시작한다. 거절했다는 기록은 남기지 않는다.

### 결정 3. 사용자가 시작한 실패만 모달로 알린다

| 실패 | 언제 | 알리는 방법 |
|---|---|---|
| `check-error` | 매니페스트 조회 실패. 부팅 때 자동으로 확인한 경우도 포함 | 모달 없음. 설정 화면 상태 줄에만 `확인에 실패했습니다` |
| `background-download-error` | 5MB 이하 번들을 받다가 실패 | 모달 없음. 설정 화면 상태 줄에만 남고, 다음에 앱을 켤 때 다시 받는다 |
| `download-error` | `다운로드` 를 누른 뒤 실패 | 모달. `다시 시도` 는 다시 받는다 |
| `apply-error` | `지금 적용` 을 누른 뒤 실패하거나 시간이 넘음 | 모달. `다시 시도` 는 다시 받지 않고 적용만 다시 한다 |

사용자가 시작하지 않은 확인 때문에 모달을 띄우면, 앱을 켤 때마다 네트워크 상태에 따라 오류 창이 뜨게
된다. 실패 분류의 공통 원칙은 [[ADR-022]] 에 있다.

두 실패 모달은 다른 모달과 같은 구성(아이콘 배지, 제목, 설명, 버튼 둘)이고 배지 색만 `error` 다. 예전에는
다운로드가 실패하면 모달이 아무 말 없이 닫혔다. 실패 상태가 모달 대상 목록에 없었기 때문이다.

`나중에` 같은 보조 버튼은 주 버튼보다 작은 글자 버튼이다. 주 버튼과 같은 크기였을 때는 보조 버튼이 너무
눈에 띄었다(사용자 지적). 버튼과 패널의 생김새는 [[ADR-062]] 결정 8 을 따른다.

모달이 뜨는 상태는 `update-available` · `confirm-cellular` · `downloading` · `ready-to-apply` ·
`store-required` · `download-error` · `applying` · `apply-error` 여덟 가지다(`MODAL_STATUSES`). 완료 안내는 상태가
아니라 `justUpdated` 값으로 띄운다(결정 10). 이 중 `downloading` 과 `applying` 은 버튼이 없어서 `UpdatePromptModal` 이
머리 줄과 진행 표시를 직접 놓고, 나머지와 완료 안내는 `NoticeModal` 로 그린다. 이 두 진행 상태에서는 배경을 눌러도 모달이
닫히지 않는다. 묻지 않고 받는 `background-downloading` 과 그 실패 `background-download-error` 는 모달이 없다.

### 결정 4. 스토어 업데이트가 필요하면 닫을 수 없는 모달을 띄운다

`store-required` 모달에는 `스토어로 이동` 버튼 하나만 있다. `onClose` 를 빈 함수로 넘겨서 배경을 눌러도,
안드로이드 뒤로가기를 눌러도 닫히지 않는다. 네이티브가 오래돼 새 번들을 받을 수 없는 기기라서, 모달을
닫아 봐야 옛 번들에 머물 뿐이다. 그런 기기의 사용자는 새 기능을 받지 못하면서도 문의는 똑같이 했다.

앱 종료 버튼도 없다. iOS 에서는 앱이 스스로 종료할 수 없다(`BackHandler.exitApp` 의 iOS 구현이 빈
함수다). 한쪽 플랫폼만 종료 버튼을 두면 같은 화면이 플랫폼마다 다르게 동작한다.

버전 배지도 그리지 않는다. 잠금을 켜는 시점의 번들은 스토어 바이너리와 같은 버전일 수 있어서, 배지를
그리면 이미 쓰고 있는 버전으로 업데이트하라는 말이 된다.

이 모달은 부팅할 때만 판정한다. 그래서 앱을 계속 켜 두면 다음 콜드 스타트까지는 잠기지 않는다.
오프라인이면 `/latest` 조회가 실패해 잠기지 않는다([[ADR-011]] 결정 5).

모달에는 `최소 앱 버전` 줄을 그리는 코드가 있지만 지금은 나오지 않는다. 어댑터가 `minNativeVersion` 을
채우지 않기 때문이다. `runtimeVersion` 은 지문 해시라 사용자에게 보여 줄 값이 아니다.

### 결정 5. 셀룰러 경고는 코드에 있지만 도달하지 않는다

`startDownload` 는 네트워크가 `cellular` 면 `confirm-cellular` 로 멈추고 데이터 요금 경고를 띄운다.
그런데 RN 어댑터의 `getNetworkType` 은 항상 `unknown` 을 돌려준다. RN 에는 네트워크 종류를 묻는 내장
API 가 없고, `@react-native-community/netinfo` 를 추가하면 네이티브 의존성이 늘어 스토어 바이너리를 다시
빌드해야 한다. 그래서 지금은 경고 없이 바로 받는다. 경고를 다시 살리려면 그 패키지를 먼저 넣어야 한다.

### 결정 6. 적용은 DB 닫기, 커버, 재시작 순서로 하고, 실패하면 12초 안에 화면을 되돌린다

`native/live-update.ts` 의 `applyLiveUpdate` 한 함수가 이 순서를 지킨다.

```
closeBossProfitDb() → showSplashScreen() → Updates.reloadAsync()
```

- SQLite 커넥션을 먼저 닫는다. 닫지 않고 재시작하면 네이티브 커넥션이 남아 재시작 뒤 첫 쿼리가 응답
  없이 멈춘다.
- 스플래시 커버는 닫기 뒤에 올린다. 커버를 먼저 올리면 닫기가 멈췄을 때 사용자가 스플래시에 갇힌다.
  커버는 재시작하는 순간을 가리려는 것이지, 그 앞의 준비 작업까지 가리려는 것이 아니다. 커버를 올리지
  못해도 적용은 계속한다.
- 세 단계를 한 함수에 둔다. 순서가 두 파일에 나뉘어 있으면 다음 사람이 한쪽만 고치게 된다.

스토어의 `apply()` 는 이 함수를 12초(`APPLY_TIMEOUT_MS`) 타임아웃으로 감싼다. 어느 단계에서 실패하거나
멈춰도 `hideSplashScreen()` 으로 커버를 걷고 `apply-error` 로 바뀐다. 타임아웃은 단계별로 나누지 않았다.
어디서 멈췄든 사용자가 볼 화면은 같아야 하기 때문이다.

적용이 성공하면 `reloadAsync()` 가 곧바로 JS 를 새로 시작하므로 상태를 바꾸는 코드가 실행되지
않는다. 그래서 성공한 뒤의 상태 변경 코드를 두지 않았다. 두면 실행되지 않는 거짓 정보가 된다.

`apply-error` 에서는 `hasDownloadedBundle` 을 그대로 둔다. 받아 둔 번들이 남아 있으므로 `다시 시도` 는
다시 받지 않고 `apply()` 만 다시 부른다. 이 점이 `download-error` 와 다르다.

### 결정 7. 적용 중에는 `applying` 상태로 바꿔 버튼을 모두 없앤다

커버는 DB 를 닫은 뒤에 올리므로, 닫는 동안(최대 5초) 모달이 화면에 남는다. 그동안 `업데이트 준비 완료` 와
버튼을 그대로 두면 화면이 사실과 다르고, 같은 버튼을 두 번 누를 수도 있다. 그래서 `apply()` 는 어떤
`await` 보다 먼저 상태를 `applying` 으로 바꾸고, 이미 `applying` 이면 아무것도 하지 않는다. 바꾸기 전에
`await` 가 있으면 그 사이에 두 번째 탭이 들어올 수 있다.

`applying` 모달에는 `적용하고 있어요` 와 스피너만 있고 버튼이 하나도 없다. 적용은 진행률을 알 수
없어서 진행 막대 대신 스피너를 쓴다([[ADR-062]] 결정 8). `나중에` 도 두지 않았다. 그 버튼을 누르면 받아 둔 번들
표시가 지워져 다시 시도할 수 없다.

### 결정 8. SQLite 닫기는 5초 안에 끝낸다

`closeBossProfitDb` 는 커넥션을 기다리는 시간과 닫는 시간을 합쳐 5초(`CLOSE_TIMEOUT_MS`) 타임아웃으로
감싼다. 여는 쪽 타임아웃(10초)보다 짧은 것은, 닫기는 파일 생성이나 마이그레이션이 없어 정상이면 몇
ms 안에 끝나기 때문이다. 이 값이 `applying` 화면이 떠 있는 최대 시간이기도 하다.

실패나 타임아웃은 지금처럼 삼킨다. 곧 재시작할 것이고, 재시작 뒤 `openBossProfitDb` 가 남은 커넥션을
감지해 다시 연다. 타임아웃은 닫기를 성공시키려고 둔 것이 아니라, 닫기가 반드시 끝나게 하려고 둔 것이다.
데이터 삭제도 같은 함수를 쓰므로 이 타임아웃이 똑같이 적용된다.

### 결정 9. 앱 정보 화면에 업데이트 상태 카드를 둔다

설정의 `앱 정보` 화면(`SettingsAboutScreen`)에 `AppUpdateSection` 카드가 있다. `현재 버전` 줄과 `상태`
줄, `업데이트 확인` 버튼이 있다. OTA 가 실제로 적용됐는지 눈으로 확인하려고 만든 카드다. 적용하면
`현재 버전` 이 바뀐다.

- 상태 열다섯 가지에 각각 문구가 하나씩 있다. 상태를 하나 더하면 문구도 함께 더해야 타입 검사를
  통과한다.
- 확인, 다운로드, 적용 중에는 버튼이 대기 상태가 되고 눌리지 않는다.
- 라이브 업데이트 런타임이 없으면(개발 서버) `이 플랫폼에서는 지원되지 않습니다` 를 보이고 버튼을
  숨긴다.
- 카드는 섹션 제목을 따로 그리지 않는다. 화면 제목이 이미 `앱 정보` 다.

받기와 적용 버튼은 카드에 없고 모달에만 있다. 카드에서 `업데이트 확인` 을 눌러 새 번들이 있으면 같은
스토어 상태를 보고 모달이 뜬다.

### 결정 10. 완료 안내는 업데이트 확인을 기다리지 않는다 (사용자 지정 2026-10-30)

예전 `checkOnBoot()` 는 방금 업데이트했는지 먼저 판정해 두고도, 매니페스트 확인(`/manifest`)과 스토어 업데이트
판정(`/latest`)이 차례로 끝난 뒤에야 완료 안내를 띄웠다. 2026-10-30 맥 와이파이에서 두 요청이 각각 0.7 ~ 0.9초였고,
기기를 막 켰을 때나 셀룰러에서는 더 걸린다. 그래서 완료 모달이 몇 초 늦게 떴다(이슈 #803).

업데이트를 마쳤다는 것은 네트워크와 상관없는 사실이므로, 판정이 참이면 확인을 기다리지 않고 `justUpdated` 를 켠다.
완료 안내를 상태(`status`)가 아닌 따로 둔 값으로 둔 것은, 그 뒤에서 확인이 돌며 상태를 바꾸기 때문이다. 새 번들이 또
있으면 결정 2 대로 받고, `업데이트 준비 완료` 는 완료 모달을 닫은 뒤(`dismissUpdated`)에 뜬다. `dismiss` 는 받아 둔
번들 표시까지 비우므로 완료 안내의 `확인` · 배경 탭 · `자세히 보기` 는 `dismissUpdated` 만 부른다. 스토어 업데이트가
필요하면(`store-required`) 닫을 수 없는 모달이 완료 모달을 대신한다.

### 결정 11. 업데이트 모달은 스플래시가 걷힌 뒤에만 뜬다 (사용자 지정 2026-10-30)

확인이 빨리 끝나면 업데이트 모달이 주황 스플래시 위에 떴다(이슈 #803). `BootSplash` 는 트리 안의 `View` 이고 모달은 따로 창을
띄우는 RN `Modal` 이기 때문이다. 이 조건은 업데이트 모달만이 아니라 모든 가운데 모달에 걸리므로 `Modal` 한 곳에 둔다
([[ADR-062]] 결정 16). 결정 10 으로 완료 모달이 앞당겨지면 이 겹침이 더 잦아지므로 두 결정을 함께 구현한다.

### 결정 12. 잠근 채 켜지면 OTA 가 게임 데이터보다 먼저고, 처음 실행에는 묻지 않고 적용한다 (사용자 지정 2026-10-30)

게임 데이터가 잠긴 채 켜지는 때(처음 실행 · 계약 판이 바뀜, [[ADR-020]] 결정 12)에는 게임 데이터 받기를 OTA 확인이 끝난 뒤에
시작한다. 이유는 둘이다.

- 새 번들이 게임 데이터 계약 판을 바꾸면, 게임 데이터를 먼저 받았을 때 재시작 뒤 또 받는다.
- 잠금이 풀리지 않는 결함이 나가도 OTA 로 고칠 수 있어야 한다. 지금은 업데이트 모달이 잠금이 풀린 뒤에만 마운트되는
  `ReadyShell` 안에 있어서, 잠금 화면에서 받기에 실패한 사용자는 OTA 를 받을 길이 없다.

그래서 `UpdatePromptModal` 을 `ReadyShell` 밖(`AppShell`)으로 옮겨 잠금 화면 위에도 뜨게 한다. 처음 실행인지에 따라 순서가 갈린다.

**처음 실행(기기에 게임 데이터 사본이 없음)에는 묻지 않고 받아 바로 적용한다.** 묻는 이유(입력하는 도중에 재시작되면 안 된다)가
처음 실행에는 없다. 아직 아무것도 입력하지 않았기 때문이다. 앱이 두 번 켜지는 것처럼 보여도 괜찮다(사용자 지정).

1. `BootSplash` 를 걷지 않고 OTA 확인을 기다린다. 확인이 5초 안에 끝나지 않으면 기다리지 않는다.
2. 새 번들이 있으면 크기와 상관없이 모달 없이 받고, 다 받으면 바로 `applyLiveUpdate()` 로 재시작한다. 재시작 뒤 앱은 새 번들로
   다시 처음 실행 흐름을 탄다. 스플래시가 계속 덮고 있으므로 사용자에게는 스플래시가 조금 길게 보인다.
3. 재시작 뒤에는 `업데이트를 마쳤어요` 를 띄우지 않는다. 방금 설치한 사용자에게 업데이트했다는 사실은 의미가 없다.
4. 최신이거나, 확인 · 받기 · 적용 중 어디서든 실패하면 모달 없이 스플래시를 걷고 게임 데이터 받기를 시작한다.
   적용 실패도 `apply-error` 모달을 띄우지 않는다.
5. 스플래시를 붙들어 두는 시간은 처음 켠 때부터 20초가 상한이다. 받기가 그 안에 끝나지 않으면 스플래시를 걷고 게임 데이터 받기를
   시작한다. 받기는 뒤에서 계속 돌고, 다 받으면 계약 판이 바뀐 잠금과 같이 `업데이트 준비 완료` 모달로 묻는다. 이미 게임 데이터를
   받는 중일 수 있어서 그 자리에서 재시작하지 않는다. `boot-splash.ts` 의 8초 실패 안전 타이머는 1겹 스플래시만 내리고
   `BootSplash` 는 내리지 않으므로, 이 상한은 `BootSplash` 가 직접 갖는다.

**계약 판이 바뀌어 잠긴 때에는 적용을 묻는다.** 사용자가 쓰던 앱이므로 결정 2 의 규칙을 따른다.

1. 게임 데이터 받기를 멈춰 두고 OTA 확인을 기다린다. 그동안 잠금 화면은 패널 없이 테마 바탕만 보인다(`checking` 단계).
2. 새 번들이 있으면 결정 2 대로 먼저 받는다. 다 받으면 `업데이트 준비 완료` 모달이 잠금 화면 위에 뜬다. 5MB 를 넘으면
   `다운로드` 모달이, 스토어 업데이트가 필요하면 닫을 수 없는 모달이 잠금 화면 위에 뜬다.
3. 최신이거나, 확인에 실패했거나, 사용자가 `나중에` 를 누르면 그때 게임 데이터 받기를 시작한다. 묻지 않고 받다가 실패해도
   게임 데이터 받기를 시작한다.
4. OTA 확인이 5초 안에 끝나지 않으면 기다리지 않고 게임 데이터 받기를 시작한다. 확인은 그 뒤에서 그대로 돌고, 새 번들이
   있으면 결정 2 대로 받는다. 확인이 멈추면 사용자가 잠금 화면에 갇히기 때문이다.

사본이 있어 잠그지 않고 여는 때에는 이 순서가 없다. 앱이 바로 열리고, 게임 데이터의 조용한 받기([[ADR-020]] 결정 13)와
OTA 확인이 따로 돈다.
