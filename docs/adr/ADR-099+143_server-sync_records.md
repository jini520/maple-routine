# ADR-099+143 서버로 보내는 기록은 드롭 가격 하나이고, 과거 드롭도 묶음으로 올린다

> 🟢 유효
> 관련 소스: `features/server-sync/*` · `storage/server-sync-sources.ts` · `storage/server-backfill.ts` · `server/write.ts` · 서버 `modules/users` · `modules/identity`

## 배경

> 사용자 지정(2026-09-19): 원본 데이터는 사용자 기기에 저장하지만, 변경되지 않는 총액과 2차 생산 목록 등은 서버에서
> 관리한다. 사용자 기기의 데이터를 완전히 옮기려는 게 아니다. 화면을 그리는 데이터는 남겨 둔다.

서버로 올리는 이유는 여러 사용자의 기록으로 통계를 내기 위해서다. 드롭 가격의 전송 규칙은 [[ADR-018]] 에 있고, 이 문서는
어떤 기록을 보내는지와 업데이트 전에 쌓인 기록을 올리는 방법을 다룬다.

보스 처치 · 가계부 기록 · 강화 합계도 한때 서버로 보냈으나 걷었다(#800). 같은 일이 기기 수만큼 서버에 쌓였기 때문이다(결정 1).

## 결정

### 결정 1. 서버로 보내는 기록은 드롭 가격 하나다. 보스 처치 · 가계부 기록 · 강화 합계는 보내지 않는다 (사용자 지정 2026-10-30)

서버는 API 키의 해시로 사람을 정한다. 그래서 같은 키를 넣은 기기는 모두 같은 `user_id` 다. 그런데 기록 id 는 기기마다
따로 만든다. 같은 보스 처치를 두 기기가 각자 동기화하면 id 가 다른 줄 둘이 되고, 서버의 처치 · 지출 통계가 기기 수만큼
부푼다.

- 드롭 가격은 계속 보낸다(사용자 지정).
- 강화 합계에서 빠진 줄의 상황 알림([[ADR-102]])은 계속 보낸다. 기록이 아니라 운영자가 예상하지 못한 상황을 보는 값이다.
- 서버의 `boss_clears` · `cashbook_entries` · `enhancement_totals` 표와 경로, 이미 올라간 줄은 그대로 둔다. 앱만 보내기를 멈춘다.
- 기기의 대기 표(`server_sync_queue`)에 이미 들어 있던 세 종류의 줄(`boss-clear` · `cashbook-entry` · `enhancement-total`)은
  레지스트리(`registry.ts`)에 없는 종류라, 전송이 원본을 읽지도 서버에 보내지도 않고 그 줄을 지운다. 남겨 두면 줄이 영원히 쌓인다.
- Preferences `serverBackfill` 에 남은 세 종류의 진행 값은 읽지 않는다. 다음에 진행을 적을 때 드롭 값만 남는다.

### 결정 2. 드롭의 기준일을 걷고 과거 드롭도 올린다

처음에는 2026-10-15 이후 기간의 드롭만 보냈다(`SERVER_PRICE_FROM`). 이 기준을 걷고, 과거 드롭도 결정 3 의 묶음으로
올린다(사용자 선택). 드롭 시세 통계에 과거 판매가가 들어간다. 드롭 줄에는 어느 처치 기간의 드롭인지 기기 기간 행 id
(`periodRecordId`)를 싣는다. 서버 `drop_prices.period_record_id` 에는 외래키가 없어, 처치 기간을 서버로 보내지 않아도 받는다.

### 결정 3. 과거 드롭은 묶음 경로로 100 건씩 나눠 보낸다

업데이트 직후 사용자마다 천여 건이 한 건씩 나가면 서버 요청이 몰린다(사용자 선택 2026-10-26). 그래서 앱을 켤 때 보내지
않은 드롭을 `POST /v1/drop-prices/batch` 로 100 건씩 보낸다.

- 어디까지 보냈는지는 마지막으로 보낸 기록 id 를 Preferences `serverBackfill` 에 적는다. 앱이 중간에 꺼져도 다음 회차가 그
  뒤부터 잇는다. 100 건보다 적게 읽히면 끝으로 적고 다시 훑지 않는다.
- 한 묶음이 실패하면(응답 없음 · 거절) 그 회차를 멈추고 다음에 앱을 켤 때 같은 자리부터 다시 보낸다. 서버는 기록 id 로
  덮으므로 두 번 받아도 줄이 늘지 않는다.
- 서버는 건마다 결과를 돌려주고 받을 수 있는 건은 받는다. 통째로 거절하면 앱이 같은 묶음을 계속 다시 보내 그 사용자의 과거
  올리기가 멈추기 때문이다. 받지 못한 건만 평소 대기 표에 넣어 한 건씩 다섯 번 다시 보낸다(사용자 선택).
- 평소 저장은 지금처럼 한 건씩 보낸다([[ADR-018]] 결정 4). 과거를 보내는 동안 고친 드롭은 한 건 전송이 따로 덮는다.

### 결정 4. 대기 표 전송은 한 번에 한 회차만 돈다

전송을 깨우는 `kick.ts` 는 도는 중에 다시 깨우면 끝난 뒤 한 번 더 돈다. 두 회차가 겹치면 같은 줄을 두 번 보낸다.

### 결정 5. 서버는 사람과 넥슨 계정을 나눈다

다계정([[ADR-101]])을 위해 나눴다(사용자 선택 2026-10-26). 옛 `users` 는 한 줄에 `nexon_uid` 나 `api_key_hash` 하나를 둬서,
한 사람이 넥슨 계정을 여럿 가질 수 없었다.

- `users` 는 사람이다. `nexon_accounts` 가 자격을 든다. 한 줄이 넥슨 계정 하나이고, 칸은 `user_id` · 종류(로그인 · 키) ·
  `nexon_uid` 또는 `api_key_hash` · 기기가 만든 계정 id 다.
- 기기가 만든 계정 id([[ADR-098]] 결정 5)는 사람 안에서만 유일하다. 드롭 기록 id 와 같은 이유다([[ADR-018]] 결정 7).
- 로그인 방식과 상관없이 모든 계정의 기록을 보낸다(사용자 지정). 부계정의 기록도 메인 계정의 신원으로 보낸다.
- API 키로만 쓰던 사람이 나중에 그 키를 부계정으로 등록하면, 그 키의 계정과 기록을 메인 사람 밑으로 옮기고 옛 사람 줄은
  닫는다(사용자 선택). 통계에서 한 사람이 둘로 세이지 않게 하려는 것이다.
  이 합치기는 부계정을 등록하는 경로가 생기는 다계정 작업([[ADR-101]])에서 만든다. 지금은 부계정을 등록할 길이 없다.

```
users             id · deleted_at · created_at
nexon_accounts    id · user_id · identity_source(login · key) · nexon_uid UNIQUE · api_key_hash UNIQUE
                  · account_record_id · created_at · updated_at        UNIQUE(user_id, account_record_id)
```

### 결정 6. 기기의 넥슨 계정 id 는 쓰기 요청마다 신원 헤더 옆에 싣는다

`x-nexon-account-id` 헤더에 메인 계정의 id([[ADR-098]] 결정 5)를 싣는다(사용자 선택 2026-10-26). 서버는 그 신원의
`nexon_accounts` 줄에 이 id 를 적는다. 따로 등록하는 호출이 없어 앱이 등록했는지를 기억할 필요가 없다. 헤더가 없는
옛 OTA 의 요청도 받는다. 그때는 계정 id 를 안 적을 뿐이다.

### 결정 7. 가계부 메모 칸을 없앤다

기기의 `cashbook_entries.memo` 칸과 기록 타입의 `memo` 를 지운다(사용자 지정). 입력 시트 아홉이 모두 이 칸을 `null` 로
적고 화면에 입력하는 곳이 없다. 실기기에도 메모가 든 기록이 없었다(옛 표 둘 포함 0 건).

  나누기 · 계정 id 헤더 · 과거 기록 묶음 · 드롭 기준일 걷기 · 메모 칸 없애기를 함께 정했다
- ADR-143 (2026-10-30): 보스 처치 · 가계부 기록 · 강화 합계의 전송을 걷고 드롭 가격만 남겼다(결정 1, #800). 세 종류에만 걸리던
  결정을 지우고 남은 결정을 다시 번호 매겼다
