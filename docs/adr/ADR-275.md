# ADR-275: 대표 표식은 스토어 하나가 든다. 대표를 바꾸는 자리가 그 스토어를 고친다

> 🟢 유효 · 2026-09-13 · **설계 · 구현 전** · 이슈 #395 · 사용자 결정 (C)
>
> 스토어의 파일 자리, 부팅 복원 자리, 쓰기 순서는 **아직 안 정했다**(아래 열린 질문). 이 저장소의
> 관례가 둘로 갈려 사용자에게 물었다.

**관련**: [[ADR-218]] 결정 3(새로고침 끝에서 표식을 다시 읽던 자리. 그 절반을 이 ADR 이 걷는다) ·
[[ADR-143]] 결정 4(대표 표식) · [[ADR-264]] 결정 2(머리 버튼의 첫 칸이 대표) · [[ADR-159]](고른
캐릭터를 스토어 하나가 든다. 같은 모양의 앞선 결정) · 이슈 #395
**문서**: `features/today.md` · `features/settings.md` · `features/app-entry.md` ·
`features/content-scheduler.md` · `persistence/preferences.md`

## 맥락

캐릭터 관리에서 대표를 옮기고 `저장` 을 누른 뒤 today 로 돌아오면 대표 캐릭터 카드가 옛 캐릭터를
그린다. 머리의 캐릭터 관리 버튼이 돌리는 얼굴도 옛 순서다. 화면을 당겨야 바뀐다.

저장은 맞게 됐다. 기기의 `representativeCharacter` 는 새 값이고, 앱을 다시 켜면 맞게 선다. 낡은 것은
`TodayScreen` 이 `useState` 로 든 사본 하나다.

그 사본을 채우는 자리가 둘뿐이다.

| 자리 | 언제 도나 | 대표만 바꿨을 때 |
|---|---|---|
| 프로필 이펙트(`readCharacterProfiles`) | 추적 목록(`orderedOcidsKey`)이 바뀔 때 | 안 돈다. 대표 저장은 목록을 안 건드린다 |
| `refreshAll` 끝(`readRepresentativeProfile`) | 당김 · 헤더 버튼 | 사용자가 당길 때까지 안 돈다 |

다른 계기도 없다. today 는 탭이라 `SettingsCharacters` 를 push 했다 돌아와도 다시 마운트되지 않는다.
이 화면의 `useFocusEffect` 둘은 드롭 기록과 공지 배너만 본다. 캐릭터 관리 저장이 끝에 부르는
`reloadTabStores(['boss', 'profit'])` 는 스토어의 추적 목록을 다시 읽히는 함수다. 화면 상태인 표식에는
닿지 않는다.

이슈가 낸 갈래는 셋이었다. (A) today 가 포커스마다 표식을 다시 읽는다. (B) 캐릭터 관리가 today 에
알린다. (C) 표식을 스토어로 올린다. 이슈는 (A) 를 권했고 **사용자는 (C) 를 골랐다**.

두 갈래의 차이는 사본이 남는가다. (A) 는 사본을 두고 채우는 계기를 하나 더 붙인다. 그 모양은
[[ADR-159]] 가 고른 캐릭터에서 기각한 갈래(화면 진입마다 저장소를 다시 읽기)와 같다. 값은 맞지만
두 벌이 남고, 계기를 빠뜨린 자리에서 같은 결함이 다시 난다. (C) 는 사본을 없앤다.

## 결정

### 결정 1. 대표 표식은 스토어가 든다. today 는 그 값을 구독한다

`TodayScreen` 의 `representativeOcid` `useState` 를 없앤다. 뷰모델에 넘기는 `representativeOcid` 는
스토어 값이다. `buildTodayViewModel` 의 입력 모양은 안 바뀐다.

today 에서 이 값을 읽는 자리는 둘이다. 대표 캐릭터 카드(위젯 1)와 머리 버튼의 얼굴 순서
(`headerPortraits`)다. 둘 다 뷰모델 안에서 `resolveDisplayRepresentative` 를 지나므로 스토어 값 하나가
바뀌면 함께 바뀐다.

**스토어가 드는 것은 저장된 표식이다.** `getRepresentativeCharacter` 가 돌려주는 값이고, 미지정이면
`null` 이다. 목록의 첫 번째(임시 대표)는 담지 않는다. 담으면 순서를 바꿀 때마다 사용자가 고른 대표와
앱이 적어 둔 대표가 갈린다. `resolveDisplayRepresentative` 가 저장하지 않는 파생값인 이유와 같다.

### 결정 2. 대표를 바꾸는 자리는 스토어를 거친다

지금 main 에서 대표 표식을 바꾸는 자리는 셋이다.

| 자리 | 지금 부르는 것 | 바뀐 뒤 |
|---|---|---|
| `SettingsCharactersScreen` 의 `handleSave` | `setRepresentativeCharacter` · `clearRepresentativeCharacter` | 스토어 액션 하나. 저장소와 메모리를 함께 고친다 |
| `CharacterSetupScreen` 의 `handleSubmit` | 같다 | 같다 |
| `world-leap-store` 의 `confirm` | `replaceTrackedCharacter` · `removeTrackedCharacter` | 그대로 부르고, 끝나면 스토어가 표식을 저장소에서 다시 읽는다 |

**화면 둘은 저장소 함수를 직접 부르지 않는다.** 직접 부르면 저장은 되고 today 는 옛 값을 그린다. 이
결함이 그렇게 났다.

**대표는 여전히 목록 저장 뒤에 쓴다.** `setTrackedCharacterOcids` 안의 `pruneDanglingRepresentative`
가 새 목록에 없는 대표를 지운다. 순서가 뒤집히면 방금 쓴 대표가 지워진다. 두 화면의 머리말이 이미
지키는 순서다.

**월드 이전만 다시 읽는 것은 판정이 저장소 안에 있어서다.** 옛 ocid 가 대표였으면
`replaceTrackedCharacter` 가 표식을 새 ocid 로 옮긴다. `removeTrackedCharacter` 에서는 목록 저장이
표식을 지운다. 스토어가 그 판정을 한 번 더 쓰면 규칙이 두 벌이 된다. 다시 읽지 않으면 대표였던
캐릭터가 월드를 옮긴 뒤 today 의 대표 자리가 목록의 첫 번째로 떨어진다. 스토어가 든 옛 ocid 가
목록에 없어서다.

**온보딩도 거친다.** `completeCharacterSetup` 은 목록을 저장하고 `stage` 를 `ready` 로 바꾼 뒤
돌아오고, 대표는 그 다음에 쓴다. today 는 `ready` 에서 마운트되므로 today 의 첫 읽기와 대표 쓰기의
순서를 코드가 보장하지 않는다. 스토어를 거치면 순서와 무관하게 쓰는 순간 today 가 다시 그린다.

`storage/character-selection` 의 `setCharacterSelection` 도 표식을 쓰지만 제품 코드에서 안 불린다
(테스트만 부른다). 이 결정의 대상이 아니다.

### 결정 3. 새로고침 끝과 마운트는 표식을 다시 읽지 않는다

[[ADR-218]] 결정 3 의 절반을 고친다. `refreshAll` 이 `allSettled` 뒤에 읽는 것은 **대표 하나의
프로필**뿐이다. 누구의 프로필인지는 스토어 값으로 `resolveDisplayRepresentative` 가 정한다. 마운트의
프로필 이펙트(`readCharacterProfiles`)도 프로필 맵만 읽는다.

표식을 함께 읽던 이유는 대표를 바꾸는 캐릭터 관리가 추적 목록을 안 건드려서였다. 결정 2 가 그
이유를 없앤다. 남겨 두면 저장소 읽기가 스토어를 덮는 자리가 된다. 늦게 도착한 읽기가 방금 바꾼
대표를 되돌릴 수 있다. [[ADR-159]] 결정 2 가 같은 모양을 적어 뒀다.

EXP·레벨을 새로고침 끝에 다시 읽는 것([[ADR-218]] 결정 3 의 나머지)은 그대로다.

## 바꾸지 않는 것

- **`useSelectionDraft`** 는 저장된 대표(`storedRepresentative`)를 마운트에서 저장소로 읽는다. 캐릭터
  관리는 열 때마다 새로 push 되는 화면이라 그 사이에 값이 낡을 틈이 없다.
- **`schedule-sync` 의 `runSyncRound`** 는 회차마다 저장소에서 표식을 읽어 5분 가드를 건너뛸 캐릭터를
  고른다([[ADR-218]] 결정 1). 네트워크 회차라 스토어를 볼 이유가 없다.
- **뷰모델**(`app/today/view-model.ts`)은 안 고친다. 입력 이름과 모양이 그대로다.

## 열린 질문

사용자 답을 기다린다(2026-09-13). 답이 오면 결정으로 올린다.

1. **스토어의 파일 자리와 부팅 복원.** 이 저장소의 관례가 둘이다.
   - (가) `features/character-selection/store.ts` 에 표식을 더한다. 같은 저장 모듈
     (`storage/character-selection`)을 읽는 스토어다. 복원은 그 스토어의 `hydrate()` 를 스케줄러
     스토어의 `loadTrackedOcids()` 가 부르는 길([[ADR-159]] 결정 2)을 탄다. `AppShell` 은 안 바뀐다.
     미지정(`null`)이 유효한 값이라 `이미 값이 있으면 안 읽는다` 조건을 그대로 못 쓰고, 읽었는지를
     따로 든다. 그 스토어 머리말의 `이 스토어가 갖는 것은 무엇을 골랐나 하나뿐` 문장을 고친다.
   - (나) 새 스토어 파일을 두고 `AppShell` 의 `restoreFromStorage` 이펙트로 부팅 때 읽는다(인증 ·
     테마 · 트래킹 모드 · 드롭 연출의 관례). 로그인 전에도 한 번 읽는다(값이 없으면 `null`). 파일
     자리는 대표 판정(`derivations.ts`)과 `world-leap-store.ts` 가 있는 `features/character-manage/`
     가 후보다.
2. **쓰기 순서.** 저장이 실패했을 때만 갈린다.
   - 저장소 먼저(테마 · 트래킹 모드 · 드롭 연출의 관례). 실패하면 today 도 옛 대표를 그린다. 기기
     값과 화면이 늘 같다.
   - 메모리 먼저(선택 스토어 `select` 의 관례). 실패해도 today 는 새 대표를 그리고, 앱을 다시 켜면
     옛 대표로 돌아간다.

## 대가

- 대표를 쓰는 자리가 새로 생기면 스토어를 거쳐야 한다. 저장소 함수를 바로 부르면 이 결함이 다시
  난다. 그것을 기계로 막는 장치는 이 결정에 없다.
- `world-leap-store` 가 대표 스토어를 부른다. 방향이 한쪽(월드 이전에서 대표로)이고 대표 스토어는
  저장소만 가져오므로 import 고리가 안 생긴다.
