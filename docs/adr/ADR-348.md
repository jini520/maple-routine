# ADR-348: 서버를 NestJS MVC 로 세우고 옛 코드는 `legacy/` 에 모아 둔다

> 🟢 유효 · 2026-10-14 · 구현 완료(같은 날) · 사용자 지정

> 구현하면서 결정 3 을 셋 고쳤다. `nestjs-zod` 를 뺐고(Nest 12 를 안 받는다), TypeScript 6 과 ESM 전용
> Nest 12 에 맞춘 설정 둘을 결정 6 으로 적었다.

**관련**: [[ADR-347]](서버를 처음부터 다시 쓴다. 이 문서는 그 결정들이 들어갈 **집의 모양**이다)

## 맥락

`maple-routine-server` 는 `src/` 바로 아래에 파일 30개, 8,500여 줄이 평평하게 놓여 있다. 경로 · 로직 ·
SQL · 배경 고리가 한 파일에 섞여 있고 기능을 찾아가는 길이 파일 이름뿐이다. [[ADR-347]] 이 서버를
처음부터 다시 쓰기로 했는데, 구조 없이 다시 쓰면 같은 모양으로 돌아온다.

**앱이 운영 중이라 옛 코드는 새 코드가 설 때까지 돌아야 한다**(사용자 지정). 그래서 옛 코드를 지우지
않고 옆에 모아 둔다.

**이번 회차는 구조만 잡는다**(사용자 지정). 배포 · 경로 전환 · 인스턴스 교체는 없다. 그것들은
[[ADR-347]] 결정 15 와 함께 뒤에 따로 한다.

## 결정

### 결정 1. MVC 를 NestJS 로 강제한다 (사용자 지정)

컨트롤러 · 서비스 · 리포지토리 · 모듈이 프레임워크 개념이고, 어느 층이 어느 층을 부를 수 있는지를
의존성 주입이 정한다. 폴더 약속으로만 지키면 다음 세션이 평평한 파일로 되돌린다. HTTP 엔진은
Fastify 어댑터다.

- `*.controller.ts` 는 HTTP 만. 요청을 받아 서비스를 부르고 응답을 낸다.
- `*.service.ts` 는 로직만. Fastify 와 Nest 의 HTTP 객체를 모른다.
- `*.repository.ts` 는 SQL 만. Drizzle 쿼리가 여기만 있다.
- `*.job.ts` 는 배경 고리만. `@Interval` · `@Cron` 이 붙는 자리다.

**대가.** 데코레이터 메타데이터 때문에 `--experimental-strip-types` 로는 못 돌고 tsc 빌드를 탄다.
모듈 체계는 CommonJS 다. 메모리가 Fastify 단독보다 50MB 안팎 더 든다. 952MB 박스에서 들어간다.

### 결정 2. 가로 부품은 `src/` 바로 아래, 기능은 전부 `src/modules/` 아래 (사용자 지정)

```
src/
  main.ts                 부트스트랩. NestFactory + FastifyAdapter
  app.module.ts           루트 모듈
  config/                 env.schema.ts(zod) · config.module.ts   [[ADR-347]] 결정 17 의 환경 표가 곧 타입
  common/                 zod-validation.pipe.ts · logger.module.ts
  database/               database.module.ts · schema.ts(표 6 · enum 2 = Model) · migrations/
  clients/                nexon-open-api.client.ts · nexon-open-id.client.ts · nexon-bucket.ts · fcm.client.ts
  modules/
    auth/                 auth.module · auth.controller · auth.service · token.service
                          attempts.repository · sessions.repository · cleanup.job · dto/
    friends/              friends.module · friends.controller · run.service · budget.ts · ndjson.ts · dto/
    notices/              notices.module · controller · service · repository · poll.job
    push/                 push.module · push.service · scheduled.job
    settlement/           settlement.module · controller · watch.job
    manual-completion/    module · controller · service · repository
    drop-prices/          module · controller · service · repository · dto/
    users/                module · service · repository
    admin/                module · controller · views/
```

- `config` · `common` · `database` · `clients` 는 모든 모듈이 쓰는 가로 부품이라 위에 둔다. 기능은
  하나도 그 높이에 두지 않는다.
- **Model 은 `database/schema.ts`** 다. Drizzle 이 표 정의를 TS 코드로 받고 거기서 타입과
  마이그레이션을 뽑는다. [[ADR-347]] 결정 1 의 표 여섯과 ENUM 둘이 여기 선다.
- **View 는 `modules/admin/views`** 뿐이다. 나머지는 JSON 과 NDJSON 이라 뷰가 없다.
- 테스트는 Nest 관례대로 같은 폴더에 `*.spec.ts` 다.

### 결정 3. 라이브러리는 이 목록이고 더하지 않는다

| 자리 | 패키지 | 하는 일 |
|---|---|---|
| 프레임워크 | `@nestjs/core` · `@nestjs/common` · `@nestjs/platform-fastify` · `reflect-metadata` · `rxjs` | 컨트롤러 · 서비스 · 모듈 · DI. 뒤 둘은 Nest 의 동반 패키지 |
| 설정 | `@nestjs/config` | env 를 읽어 주입. 시작할 때 zod 로 검사해 빠진 값이 있으면 안 뜬다 |
| 배경 고리 | `@nestjs/schedule` | `@Interval` · `@Cron`. [[ADR-347]] 결정 5 의 1분 청소 · 공지 폴링 · 결산 감시 |
| DB | `drizzle-orm` · `pg` · `drizzle-kit`(dev) | 스키마 선언이 곧 타입, 쿼리는 SQL 모양 그대로. `drizzle-kit` 이 선언에서 마이그레이션을 뽑는다 |
| 검증 | `zod` | 요청 본문과 env 의 모양을 한 번 적어 검증과 타입을 같이 얻는다. Nest 파이프는 `common/zod-validation.pipe.ts` 열 줄이다 |
| 넥슨 상한 | `bottleneck` | 자격 쌍마다 초당 400 토큰 버킷. 429 면 비운다([[ADR-347]] 결정 16) |
| 로그 | `nestjs-pino` · `pino-http` · `pino` | 요청마다 JSON 한 줄. 회차 로그도 여기 |
| 푸시 | `firebase-admin` | FCM 공식 SDK |
| 개발 | `@nestjs/cli` · `@nestjs/schematics` · `typescript` | `nest start --watch` · `nest g` · tsc 빌드 |
| 테스트 | `jest` · `ts-jest` · `@types/jest` · `@nestjs/testing` | 앱 저장소와 같은 Jest. 라우트는 Fastify 의 `app.inject()` |
| 서식 · 린트 | `prettier` · `eslint` · `typescript-eslint` · `eslint-config-prettier` | |
| 타입 | `@types/node` · `@types/pg` | |

**내장으로 끝내는 것 셋.** `node:crypto` 로 AES-256-GCM 봉인, `node:zlib` 로 gzip 스트림, 전역 `fetch`
로 넥슨 호출과 `AbortSignal.timeout`.

**쓰지 않는 것.** Express · Fastify 단독 · Kysely · Prisma · TypeORM · class-validator · BullMQ ·
p-throttle · axios · got · winston · Vitest. 옛 서버의 `node-pg-migrate` 와 `node:test` 도 각각
drizzle-kit 과 Jest 로 바뀐다.

**`nestjs-zod` 를 안 쓴다.** 최신 5.5.0 의 peer 가 `@nestjs/common` 10 · 11 까지라 Nest 12 와 안 맞는다. 하는 일이 zod 스키마를 Nest 파이프와 DTO 로 잇는 것뿐이라 파이프 하나를 직접 둔다.

**Prettier 를 쓴다.** 앱 저장소는 Prettier 설정이 없어 한 번 돌리면 82개 파일이 뒤집히는 사고가 있었다.
서버는 새 저장소라 그 사정이 없고, 처음부터 서식을 고정해 두면 그 사고가 안 생긴다.

**Drizzle 인 이유.** 선언 → 타입 → 마이그레이션이 한 줄로 이어져 Model 층이 실제로 생긴다. Kysely 는
타입만 얹고 마이그레이션은 손으로 쓴다. Prisma 는 자기 DSL 과 쿼리 엔진이 따로 있어 [[ADR-347]] 의
CTE · `RETURNING` 이 raw 로 빠진다. TypeORM 은 타입이 느슨하다.

### 결정 4. 옛 코드는 `legacy/` 로 옮기고 손대지 않는다 (사용자 지정)

`src` · `bin` · `migrations` · `Dockerfile` · `compose.yml` · `package.json` · `package-lock.json` ·
`tsconfig.json` · `.env.example` · `README.md` 를 통째로 `legacy/` 에 넣는다. 안의 import 가 전부
상대 경로라 폴더째 옮기면 그대로 돈다. `bin/notice.ts` 의 `../src/` 도 `legacy/bin` 에서 같은 상대
경로다.

- **미니 PC 의 컨테이너는 다시 빌드하지 않는다.** 지금 돌고 있는 이미지가 그대로 돈다. 저장소의
  파일 위치가 바뀌어도 실행 중인 컨테이너는 모른다.
- **핫픽스가 필요하면 `legacy/` 안에서 빌드한다.** `legacy/Dockerfile` 과 `legacy/compose.yml` 이
  그 자리에 그대로 있다. `legacy/README.md` 첫 줄이 이것을 말한다.
- 새 코드는 `legacy/` 를 import 하지 않는다. 참고도 하지 않는다([[ADR-347]] 사용자 지정).

### 결정 5. 이번 회차는 구조만이고, 서는 기준은 셋이다

배포 · nginx 경로 전환 · 인스턴스 교체는 이 문서 밖이다. 경로 전환은 Oracle nginx 의 `location`
단위로 하나씩 옮기고 되돌리기가 한 줄인 모양이 되는데, 순서는 그때 정한다(사용자 판단으로 지금은
중요하지 않다).

골격이 섰다고 말할 수 있는 기준.

1. `nest build` 가 통과한다.
2. `GET /healthz` 가 `{ ok: true }` 를 내는 스펙이 통과한다. 모듈 아홉은 빈 모듈로 등록돼 있다.
3. `database/schema.ts` 에 [[ADR-347]] 결정 1 의 표 여섯과 ENUM 둘이 있고, `drizzle-kit generate` 가
   뽑은 초기 마이그레이션이 그 결정의 SQL 과 같다. PK 는 uuid 한 칸, `platform` · `notice_kind` 는
   ENUM, 부분 인덱스 둘이 있다.

### 결정 6. Nest 12 와 TypeScript 6 에 맞춘 설정 둘

설치 시점(2026-10-14)의 최신이 `@nestjs/core` 12.1.3 과 `typescript` 6.0.3 이었고, 둘이 각각 하나씩 요구했다.

- **Nest 12 는 ESM 전용이다**(`@nestjs/common` 의 `package.json` 이 `"type": "module"`). 우리 빌드는
  CommonJS 이고 Node 22.12 이상이 CJS 에서 ESM 을 `require` 할 수 있어 실행은 그대로 된다. 그러나 **Jest 의
  샌드박스는 `--experimental-vm-modules` 가 있어야 그 길을 탄다.** 그래서 `npm test` 가
  `NODE_OPTIONS=--experimental-vm-modules jest` 다. Nest 12 의 자체 템플릿도 ts-jest 와 Jest 30 이다.
- **TypeScript 6 은 `moduleResolution: node` 를 거부하고 `@types/*` 를 자동으로 안 올린다.** 빌드는
  `module: node20` 에 `types: ["node"]`, `rootDir: ./src` 를 명시한다. ts-jest 는 아직 `node20` 을 CJS 로
  안 내므로 `tsconfig.spec.json` 이 `module: commonjs` · `moduleResolution: node10` ·
  `ignoreDeprecations: "6.0"` 으로 따로 선다.

## 대가

- 옛 코드와 새 코드가 한 저장소에 둘 다 있는 기간이 생긴다. `legacy/` 라는 이름이 경계다.
- NestJS 의 개념(모듈 · 프로바이더 · 데코레이터)을 모르는 사람은 처음에 읽는 비용이 있다.

## 열린 질문

- NestJS 의 응답 스트리밍에서 Fastify 의 `reply.raw` 를 그대로 쓸 때 Nest 의 인터셉터와 필터가
  어디까지 걸리는지. [[ADR-347]] 결정 7 의 NDJSON 이 이 자리다.
