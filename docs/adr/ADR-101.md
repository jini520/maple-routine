## 맥락

실기기 관측(2026-08-06): **앱을 껐다 켠 뒤** 보스 스케줄러·보스 수익 탭에 처음 들어가면, 목록이 나오기 전에 화면 두 장이 각각 한 프레임씩 스쳐 지나간다.

| # | 스쳐 지나가는 화면 | 문구 |
|---|---|---|
| 1 | 보스 스케줄러 빈 상태 | "표시할 캐릭터가 없습니다" |
| 2 | 보스 스케줄러 로딩 | "불러오고 있어요" |
| 3 | 보스 수익 빈 상태 | "추적 중인 캐릭터가 없습니다" |
| 4 | 보스 수익 로딩 | "불러오고 있어요" |

사용자 지적: 캐시도 있고 컨텐츠 스케줄러가 이미 같은 API 를 받아놨는데 이 화면들이 낄 이유가 없다.

### 실측 — 프레임 시퀀스는 `empty → loading → list` 다

추측을 쌓지 않고 재현 테스트로 계측했다(`BossScreen.cold-start.test.tsx`). 저장소 모킹을 **매크로태스크 경계를 넘는 비동기**로 두어(네이티브 브리지가 실제로 그렇다) 매 커밋의 화면을 기록했다:

```
frame sequence: empty → loading → list
```

**네트워크는 한 번도 나가지 않는다.** [[ADR-097]] TTL 게이트가 걸린 조건(`hasSyncAttemptedThisRun() === true` + 신선)에서 재현되므로, 이 프레임들은 API 지연이 아니라 **로컬 저장소 읽기 지연** 위에 그려진 것이다.

### 원인 1 — `null`(아직 안 읽음)을 `0명`으로 읽는다

세 화면이 모두 같은 한 줄을 갖고 있다.

```ts
const isEmpty = trackedOcids === null || trackedOcids.length === 0
```

`trackedOcids: string[] | null` 에서 `null` 은 **"저장소를 아직 안 읽었다"** 는 뜻이다(`initialState`). 그걸 `length === 0`("추적 중인 캐릭터가 0명")과 `||` 로 묶는 순간, 마운트 첫 페인트가 **아직 모르는 사실을 단정한다.** 프레임 1·3 이 그것이다.

이건 새 원칙이 필요한 문제가 아니다. [[ADR-060]]·[[ADR-061]] 이 이미 같은 것을 금지했다 — "로딩을 빈 상태로 위장하지 않는다", "세 상태(조회 중 / 확정된 빈 상태 / 확인 불가)는 항상 서로 구분 가능해야 한다". [[ADR-061]] 조사가 잡아낸 것은 관리 화면 2곳이었고, **세 메인 화면의 같은 위반은 그때 발견되지 않았다.**

### 원인 2 — 추적 목록과 캐릭터 뷰가 두 커밋에 나뉜다

```ts
async loadTrackedOcids() {
  const [ocids, selectedOcid] = await Promise.all([...])
  set({ trackedOcids: ocids, selectedOcid })   // ← 커밋 A
  if (ocids !== null) await get().refresh(ocids, undefined, { auto: true })  // ← 커밋 B 는 한참 뒤
}
```

커밋 A 와 B 사이에 `refresh` 가 **브리지 왕복을 여러 번** 한다 — 수동 모드 멤버십 읽기 N회, `getCachedSchedulerState` N회(Preferences), `loadPartySizes` 1회(**SQLite 커넥션 오픈 포함**), `sortByCachedLevel` 의 `getCachedCharacterBasic` N회. 그동안 화면이 보는 상태는 **"추적 중인데 캐릭터 0명"** 이라 로딩 카드가 뜬다. 프레임 2·4 다.

원인 2 는 화면 안에서는 못 없앤다. 캐시를 읽는 데 드는 왕복은 실재하고, 그 시간에 화면은 무언가를 그려야 한다. **없앨 수 있는 것은 "그 시간에 사람이 보고 있다"는 조건 쪽이다.**

## 결정

### 결정 1 — `trackedOcids === null` 은 빈 상태가 아니다

세 화면의 판정을 바꾼다.

```ts
// 미로드(null)는 "0명"이 아니다 — 아직 모르는 사실을 단정하지 않는다.
const isEmpty = trackedOcids !== null && trackedOcids.length === 0
```

`null` 은 이제 빈 상태 분기로 빠지지 않고 본 화면 경로로 흘러, 이미 있는 콜드 스타트 로딩([[ADR-061]] C-11·12·13)이 그 자리를 받는다. **거짓을 말하는 프레임이 구조적으로 사라진다** — 빈 상태는 저장소를 읽고 0명임을 확인한 뒤에만 그려진다.

적용 지점: `ContentScreen.tsx` · `BossScreen.tsx` · `BossProfitScreen.tsx`.

### 결정 2 — 부팅 때 세 스토어를 순차로 선하이드레이션한다

결정 1 이후 남는 것은 정직한 로딩 한 프레임이다. 그마저 사용자가 볼 이유가 없다 — **탭을 누르기 전에 이미 끝나 있게 하면 된다.**

앱 셸이 마운트되면(온보딩 완료 상태에서만) 세 스토어의 `loadTrackedOcids()` 를 백그라운드로 돌린다. 스플래시 최소 표시 시간이 1초([[ADR-092]] 시대의 `MIN_SPLASH_MS`)이므로, 사용자가 보스 탭을 누를 수 있게 될 무렵엔 세 스토어가 이미 메모리에 있다. 화면은 하이드레이션된 스토어 위에 마운트되어 **첫 페인트가 곧 목록**이다.

### 결정 3 — 순차다. 병렬이 아니다

[[ADR-097]] 의 게이트는 두 조건이다: `hasSyncAttemptedThisRun()` **그리고** 캐시가 신선할 것. `markSyncAttemptedThisRun()` 은 `syncSchedules` 진입 즉시 찍히지만 **신선도는 그 회차가 캐시를 다 쓴 뒤에야** 참이 된다. 세 스토어를 동시에 띄우면 셋 다 옛 `syncedAt` 을 보고 게이트를 통과해 **같은 응답을 3번 받는다** — [[ADR-097]] 이 없애려던 바로 그 낭비다.

그래서 `await` 로 줄을 세운다: 컨텐츠 → 보스 → 보스 수익. 첫 회차가 캐시를 쓰고 나서야 다음이 게이트를 본다.

### 결정 4 — `loadTrackedOcids()` 는 동시 호출을 한 회차로 합친다 (single-flight)

선하이드레이션이 도는 동안 화면도 마운트되어 같은 `loadTrackedOcids()` 를 부른다(첫 탭인 컨텐츠는 반드시 겹친다). 두 회차가 각각 `refresh` → `syncSchedules` 로 이어지면 결정 3 이 막으려던 중복이 **한 스토어 안에서** 되살아난다.

각 스토어에 모듈 수준 in-flight 핸들을 둬, 진행 중인 회차가 있으면 그 `Promise` 를 그대로 돌려준다. 끝나면 잊는다 — **"평생 한 번"이 아니라 "동시에 하나만"** 이다(진입 재조회는 10분 TTL 로 계속 살아 있어야 하므로, 영구 메모로 만들면 [[ADR-097]] 이 죽는다).

`storage/character-selection.ts` 의 `migrationLock` 과 같은 모양·같은 이유다.

### 결정 5 — 선하이드레이션은 동적 `import` 로 스토어를 가져온다

[[ADR-092]] 가 라우트를 `lazy` 로 쪼갠 이유는 8개 화면·모든 store·`src/data/*.json` 이 첫 페인트에 함께 평가되던 것이었다. 앱 셸이 세 스토어를 **정적 import** 하면 그 청크들이 메인 청크로 되돌아와 [[ADR-092]] 가 통째로 무효가 된다.

동적 `import()` 를 첫 페인트 **이후**의 이펙트에서 부르므로 청크는 그대로 갈라져 있다. 덤으로 이 청크들이 미리 받아져 탭 전환의 `RouteFallback`("불러오는 중") 도 대개 사라진다.

**산출물로 확인했다**([[ADR-093]] 이후의 규칙 — 자산·번들 판정은 추론이 아니라 `npm run build` 실측 + `dist/assets/*.js` grep). HEAD 를 별도 워크트리에서 빌드해 대조했다:

| | 메인 청크 | 메인 청크(gzip) | 전체 JS |
|---|---|---|---|
| HEAD | 340.55 kB | 107.6 kB | 1,298.4 kB |
| 이 변경 | 345.29 kB | 109.8 kB | 1,300.2 kB |

**스토어 코드는 양쪽 모두 자기 청크에 그대로 있다** — 스토어에만 있는 문자열(`파티원 수를 저장했어요`·`이하의 정수여야 합니다`)이 두 빌드 다 `store-*.js` 에서만 잡히고 `index-*.js` 에는 없다. 즉 결정 5 가 막으려던 "스토어가 메인 청크로 돌아오는 것"은 일어나지 않았다.

메인 청크 +2.2 kB(gzip, +2%)는 스토어 유입이 아니라 **청크 경계 재분할**이다 — 스토어 모듈의 importer 가 둘(화면 청크 + 예열 청크)이 되면서 Rollup 이 공용 청크를 다시 갈랐고(`valuable-drops` 245.6 → 197.3 kB + 새 `boss-drops` 48.3 kB), 전체 JS 증가는 1.8 kB 로 사실상 없다. `prehydrate` 는 1.23 kB 짜리 자기 청크이고 그 안에서 세 스토어를 동적으로 부른다.

### 결정 6 — 온보딩 미완료면 돌리지 않는다

`syncSchedules` 는 API 키·계정이 없으면 던진다(`resolveRegisteredCharacters`). 온보딩 중에 선하이드레이션을 돌리면 스토어가 `status: 'error'` 로 시작하고 토스트까지 울린다. 셸의 `status === 'completed'` 게이트를 그대로 쓴다.
