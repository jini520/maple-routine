# ADR-216: 스플래시는 두 겹이다. 1겹을 내리는 신호는 시계가 아니라 **2겹이 그려졌다는 사실**이다

> 🟢 유효 · 2026-09-04 · **구현 완료 · 에뮬레이터 확인 · 실기기 미검증**

> **확인**(에뮬레이터 Pixel 8 API 36 · release · `pm clear` 후). 빈 구간 0 프레임이고 두 층이
> 직행한다. **1겹이 시스템 테마를 따라간다.**
>
> | 모드 | 1겹 | 2겹 | 다음 |
> |---|---|---|---|
> | 라이트 | 흰 빈 화면 `rgb(252,255,252)` | 주황+로고 | 앱 콘텐츠 `rgb(234,235,218)` |
> | 다크 | 검정 빈 화면 `rgb(14,18,19)` | 주황+로고 | 앱 콘텐츠 `rgb(25,24,23)` |

> 사용자 지정(2026-09-04): "애니메이션 스플래시는 완전히 다시 만들거야." · "요즘 앱들의 스플래시
> 화면들을 보면 애니메이션도 들어가고 훨씬 다채로운 스플래시 화면이 나오잖아? 그렇게 하려면 js로
> 띄우는게 맞지 않아?"

**관련**: [[ADR-138]](아이콘·스플래시 자산 파이프라인) · [[ADR-136]](앱 루트 바탕색) ·
⛔ [[ADR-025]] 🔗(첫 렌더 전 깜빡임을 스플래시로 덮는다) · ⛔ [[ADR-117]] 🔗 결정 3·4(실패 안전
타이머, 내리는 코드 한 곳). **문서**: `features/splash.md`

## 맥락

### 요구는 애니메이션인데 구조가 정지 화면 한 장이다

지금 스플래시는 OS 가 그리는 화면 하나이고 앱이 하는 일은 언제 내리는가 하나뿐이다
(`features/splash.md`). 애니메이션이 들어갈 자리가 구조에 없다.

### 그 화면은 애니메이션을 못 받는다

- 안드로이드 12+ 의 `windowSplashScreenAnimatedIcon` 은 AnimatedVectorDrawable 을 받지만 상한이
  1000ms 다. 그리고 `expo-splash-screen` 의 config plugin 이 그 자리를 `@drawable/splashscreen_logo`
  PNG 로 **하드코딩**한다(`plugin/build/withAndroidSplashStyles.js` 의 `addSplashScreenStyle`).
  AVD 를 넣으려면 커스텀 플러그인을 써야 하고, 안 그러면 `expo prebuild` 가 매번 덮는다.
- iOS 의 LaunchScreen storyboard 는 정지 이미지 외에 아무것도 못 한다.

그래서 애니메이션은 앱이 그리는 층으로 간다. 그것이 실제 앱들이 하는 것이기도 하다.

### 계측: 두 층 사이에 검정이 있다

1겹을 흰색 단색으로, 2겹을 노란색으로 갈라 놓고 콜드스타트를 녹화해 프레임을 훑었다
(에뮬레이터 Pixel 8 API 36 · **debug 빌드** · 2026-09-04).

| 구간 | 길이 | 정체 |
|---|---|---|
| 1.60 ~ 6.40s | 4.80s | 흰색. 1겹 |
| 6.55 ~ 10.30s | **3.75s** | **검정. 어느 층도 아니다** |
| 10.65 ~ 12.40s | 1.75s | 노랑. 2겹 |
| 12.40s ~ | | 앱 콘텐츠 |

logcat 이 두 경계에 정확히 맞는다. `transferring splash screen timeout` 이 흰색이 끝나는 지점이고
`Displayed +8s882ms` 가 검정이 끝나는 지점이다.

**이 숫자들은 못 쓴다.** debug 라 Metro 에서 번들을 받고, 그래서 OS 의 전달 제한 시간(약 5초)에
걸렸다. release 는 번들이 내장이라 걸릴 이유가 없다. 그래도 사슬 하나는 읽힌다. **OS 가 1겹을 앱에
넘기는 데 제한 시간이 있고, 못 받으면 시스템이 걷는다. 그 아래에 칠해진 것이 없어 검정이 드러난다.**

그리고 이 실험이 잰 것은 **아무도 안 쓰는 설계**였다. 두 층 사이에 계약이 없어 1겹은 시계를 보고
내려갔고 2겹은 그것과 무관하게 그려졌다.

### 진짜 원인은 타이머다

```ts
// src/app/AppShell.tsx:128
const remaining = MIN_SPLASH_MS - (Date.now() - APP_START_MS)
setTimeout(() => { void hideSplashScreen() }, Math.max(0, remaining))
```

이 타이머는 **화면에 무엇이 그려졌는지 모른다.** 게다가 `APP_START_MS = Date.now()` 가 같은 파일
모듈 최상위라 기준점이 앱 실행이 아니라 **번들 평가 시점**이다. 실제 공식은
`번들 평가까지 걸린 시간 + 1초` 다.

`expo-splash-screen` 문서도 `hide()` 에 같은 경고를 단다. 앱이 보여줄 콘텐츠가 준비됐는지 확인하고
내려라, 아니면 빈 화면을 잠깐 본다.

지금 빈 화면이 안 보이는 것은 설계가 맞아서가 아니라 **부팅이 그 1초보다 빨랐던 것뿐**이다.

### 실제 앱들이 지키는 것 셋

`react-native-bootsplash` 의 `useHideAnimation` 이 이 셋을 그대로 API 로 굳혀 놓았다.

| | 실제 앱 | 이 저장소 |
|---|---|---|
| 2겹이 1겹과 **같은 그림**으로 시작 | `manifest` 가 로고 크기·위치를 JS 에 넘긴다 | 2겹이 없다 |
| 1겹을 내리는 시점이 **2겹이 그려진 뒤** | animate 콜백 뒤에 `hide()` | 고정 타이머 |
| 1겹이 걷혀도 그 아래가 **브랜드색** | `windowBackground` | 지정이 없다 |

## 결정

### 결정 1. 스플래시는 두 겹이고, 그 사실이 코드에 이름으로 있다

1겹은 OS 시작 창이다. 실행 15ms 만에 뜨고 앱은 그 자리에 못 온다. `app.json` 의
`expo-splash-screen` 블록이 정하는 그림과 색이 전부다.

2겹은 앱이 그리는 브랜드 화면이다. `src/app/BootSplash.tsx`. **애니메이션은 전부 여기 있다.**

두 겹인 것은 선택이 아니다. 1겹은 프로세스가 뜨기 전에 그려져 없앨 수 없고, 2겹은 애니메이션을
받을 수 있는 유일한 자리다.

### 결정 2. 1겹을 내리는 신호는 **2겹이 그려졌다는 사실**이다

`MIN_SPLASH_MS` 타이머를 지운다. 대신 `BootSplash` 의 `onLayout` 이 `hideSplashScreen()` 을 부른다.

```
2겹 마운트 → onLayout 발화 → hideSplashScreen() → 2겹 애니메이션 → 언마운트
```

이 순서면 **틈이 생길 수가 없다.** 1겹이 걷히는 순간 그 아래는 이미 칠해져 있다. 시계로는 그것을
보장할 방법이 없다.

### 결정 3. 최소 표시 시간은 2겹이 갖고, **1겹이 사라진 뒤부터** 센다

> **정정 3**(2026-09-04). 안드로이드의 퇴장 페이드(기본 400ms)를 `boot-splash.ts` 에서 끈다.
> `hideAsync()` 는 요청이 접수되면 끝나는데 1겹은 그 페이드만큼 더 남아 있어, 그동안 2겹이
> 그려진 채로 가려진다. 끄면 1겹 노출과 2겹의 낭비되는 앞부분이 **함께** 줄어든다
> (계측: 1겹 0.91s → 0.35s, 2겹 0.16s → 0.57s).

`MIN_SPLASH_MS` 의 원래 의도는 스플래시가 충분히 보이게 하는 것이었다. 그 의도를 2겹이 더 정확히
이룬다. **1겹은 OS 가 언제 걷을지 모르지만**(전달 제한 시간) **2겹은 우리가 통제한다.**

즉 지금 1겹에 걸려 있던 보장이 2겹으로 옮겨간다. 1겹은 자기가 뜰 수 있는 만큼만 뜨면 된다.

**세기 시작하는 시점은 계측이 정정했다.** 처음에는 `onLayout` 에서 바로 셌는데, 그렇게 하면 그
시간의 일부를 1겹에 가려진 채로 보낸다. 색을 갈라 찍어 보니 600ms 중 **보인 것이 280ms** 였다.
`hideSplashScreen()` 이 끝난 뒤부터 센다. 애니메이션이 붙으면 이 차이가 그대로 안 보이는 앞부분이
된다.

기다림에는 상한을 둔다(`BOOT_SPLASH_HANDOFF_CAP_MS`, 2초). 없으면 그 함수가 끝내 안 끝날 때 이
층이 영영 안 걷혀 앱이 브랜드색에 갇힌다. **트리 밖 실패 안전 타이머가 대신 받아 주지 못한다.**
그쪽도 같은 함수를 기다린다.

### 결정 4. 2겹의 첫 프레임은 1겹과 **같은 그림**이다

같은 배경색 `#F58B0F`, 같은 로크업(`assets/splash-icon.png`), 같은 폭 200, 화면 중앙.

전환이 안 보여야 사용자에게 **한 장으로 읽힌다.** 애니메이션은 그 프레임에서 출발한다. 이것이
안 맞으면 두 층이 갈리는 순간이 깜빡임으로 드러나 검정 대신 다른 결함이 된다.

> **정정 1**(2026-09-04, 사용자 지정 "나는 1겹에 컨텐츠를 넣지 않을거야"). 1겹은 **로고 없는
> 빈 화면**으로 내린다. `app.json` 의 `image` 를 완전 투명 PNG `assets/splash-icon-none.png` 로
> 준다. 플러그인이 `windowSplashScreenAnimatedIcon` 을 `@drawable/splashscreen_logo` 로
> 하드코딩해 **항목 자체는 못 지우고** 투명으로 비우는 것이 유일한 길이다.
>
> **로고가 나타나는 순간이 곧 애니메이션의 시작점**이 된다.
>
> **정정 2**(2026-09-04, 사용자 지정 "시스템 테마에 따라 흰색과 검정색"). 배경색도 안 맞춘다.
> **1겹은 시스템 테마를 따라간다** - 라이트 `#FFFFFF`, 다크 `#000000`. `app.json` 의
> `dark.backgroundColor` 를 주면 플러그인이 `values-night/colors.xml` 과 iOS colorset 의 다크
> 변형에 내린다(`withAndroidColorsNight`).
>
> 그래서 결정 4 에서 살아남는 것은 **"1겹과 2겹 사이에 빈 구간이 없다"** 뿐이고, 두 층이 같은
> 그림이라는 부분은 폐기된다. 전환은 이제 보인다. **빈 화면에서 브랜드 화면으로 넘어가는 것이
> 의도다.**
>
> **덤으로 MIUI force-dark 문제가 구조에서 사라진다.** 다크에서 1겹이 검정이라 **깎을 밝은 색이
> 없고**, 브랜드 주황은 전부 RN 뷰인 2겹으로 옮겨갔다. ⛔ [[ADR-025]] 의 색 split 이 풀려던 문제고
> [[ADR-138]] 결정 4 가 대가로 받아들였던 것이다. **다만 MIUI 실기기 미검증이다.**
>
> **대가**: 1겹이 뜨는 0.28초 동안 브랜드가 없다. 캐패시터 시절 🗑 ADR-028 이 이 모양으로 두 번
> 실패했는데 그때는 그 시간이 **1.8초**였다. 0.28초라 산수가 다르다.

### 결정 5. 1겹이 걷힌 자리 **아래**를 1겹과 같은 색으로 칠한다

`AppTheme` 의 `android:windowBackground` 를 `@color/splashscreen_background` 로 준다. 1겹이 쓰는
바로 그 색이라 테마 split 도 따라간다(라이트 흰색·다크 검정).

결정 2 가 정상 경로를 막고, 이것은 **OS 가 먼저 걷어갈 때의 안전망**이다. 느린 기기·진짜 콜드
스타트에서 전달 제한 시간에 걸리면 결정 2 의 신호가 도착하기 전에 1겹이 사라지는데, 그때 드러나는
것이 검정 고정이 아니라 **1겹과 이어지는 색**이어야 한다.

**config plugin 으로 넣는다.** 손으로 `values/styles.xml` 을 고치면 다음 `expo prebuild` 가 지운다
(그 파일은 prebuild 산출물이다). 자리는 `app.config.js` 이고 `withAndroidStyles` 를 쓴다.

### 결정 6. 실패 안전 타이머가 2겹에도 상한을 건다

지금 `boot-splash.ts` 의 8초 타이머는 1겹만 내린다. 결정 2 뒤에는 **2겹이 안 걷히는 경우**가
새로 생긴다. 애니메이션이 끝내 안 끝나면 브랜드색 화면에 갇힌다.

2겹 자신이 상한을 갖는다. 그 상한이 지나면 애니메이션과 무관하게 언마운트한다.

## 기각한 것

**A. `react-native-bootsplash` 로 교체.** 위 셋을 통째로 준다(`useHideAnimation` · `manifest` ·
Expo config plugin). 두 가지로 기각한다. **이 저장소가 이미 한 번 탈락시킨 라이브러리**이고
(SDK 와 독립적으로 버전이 움직여 광고 SDK 와 Kotlin 메타데이터가 충돌했다. `rn-splash-screen.ts`),
애니메이션을 새로 만들면 그 라이브러리가 주는 값의 대부분인 **정합 도우미의 값이 준다**. 맞춰야
하는 것은 첫 프레임 하나이고 그 뒤는 어차피 자유다. 이 앱은 광고 SDK 때문에 네이티브 의존성 하나
늘리는 비용이 다른 앱보다 비싸다.

**B. 1겹을 애니메이션으로.** 안드로이드만 가능하고 상한 1000ms 이며 config plugin 이 그 자리를
안 내준다. iOS 는 아예 불가. 두 플랫폼이 갈리면 그것만으로 유지 비용이 배가 된다.

**C. 1겹을 무채색으로 낮추고 브랜드를 2겹에만 두기.** 캐패시터 시절 두 번 시도해 두 번 실패한
그림이다(🗑 ADR-028). RN 은 숫자가 다르지만 **2겹이 늦으면 브랜드가 아예 안 보이는** 실패 방식은
그대로 남는다. 결정 4 가 반대로 간다. 두 겹이 같은 그림이면 어느 쪽이 이겨도 브랜드가 보인다.

> **정정 1 이 이 기각을 절반 뒤집는다.** 1겹에서 **로고**는 뺀다. 다만 **색은 안 뺀다** - 무채색이
> 아니라 브랜드 주황 그대로다. C 가 실패한 핵심은 색까지 버려서 브랜드가 아예 안 보인 것이었고,
> 그 부분은 그대로 기각으로 남는다.

## 대가

- **`MIN_SPLASH_MS` 가 보장하던 것이 옮겨간다.** 1겹이 얼마나 보이는지는 이제 아무도 보장하지
  않는다. 빠른 기기에서는 1겹이 거의 안 보이고 곧바로 2겹이 될 수 있다. 결정 4 때문에 그것이
  눈에는 같은 화면이라 문제가 아니지만, **1겹의 노출 시간을 재는 기존 감각은 못 쓴다.**
- **네이티브 변경이라 OTA 지문이 바뀐다.** 결정 5 의 config plugin 이 `app.config.js` 의 해석된
  설정을 바꾼다(그 파일 상단 경고). 스토어 바이너리가 받던 OTA 가 끊기므로 재배포가 뒤따라야 한다.
- **부팅 경로에 렌더 한 겹이 는다.** 2겹은 `AppShell` 이 처음 렌더될 때 함께 그려져야 하므로
  가장 가벼워야 한다. 여기에 무거운 것을 얹으면 그것이 곧 1겹의 노출 시간이 된다.

## 곁가지로 드러난 것 둘

이 조사에서 나왔고 이 ADR 의 결정에는 안 들어가지만 기록해 둔다.

- **`expo prebuild` 는 `android/` 를 통째로 지우고 다시 만든다.** 커밋 안 된 것 셋이 함께
  사라진다. 릴리스 서명 블록([[ADR-091]]) · `android/keystore.properties` · 직전 빌드 APK.
  이번 작업에서 두 번 다 밟았고, 두 번째는 산출물이 `app-release-unsigned.apk` 로 나와서야
  알았다. `features/splash.md` 에 표로 적었다.
- **`values-night/colors.xml` 이 비어 있는 이유는 `app.json` 에 `dark` 블록이 없어서다.**
  `expo-splash-screen` 은 `dark.backgroundColor` 를 받아 `withAndroidColorsNight` 로 그 파일에
  쓴다. MIUI force-dark 대응(⛔ [[ADR-025]] 의 색 split)을 되살리려면 네이티브를 손댈 필요가 없고
  `app.json` 몇 줄이면 된다. **이 ADR 은 그 문제를 안 다룬다.** 색과 층은 별개다.

## 검증

에뮬레이터 Pixel 8 API 36 · release · `pm clear` 후 · 프레임 스캔(60fps) + logcat.

| | 기준선(시계로 내림) | 이 ADR 적용 후 |
|---|---|---|
| 스플래시 총 길이 | 1.80s | 2.43s |
| **검정** | **0** | **0** |
| `transferring splash screen timeout` | 없음 | 없음 |
| `Displayed` | +1s621ms | +2s088ms |

**검정 구간은 debug 산출물이었다.** Metro 가 12초에서 14초를 쓰는 바람에 OS 제한 시간에 걸린
것이고, 번들이 내장인 release 는 그 근처에도 안 간다. **debug 로는 이 확인 자체가 불가능하다.**
그쪽은 매번 걸린다(세 번 시도해 세 번 다).

2겹만 노란색으로 갈라 찍은 판이 넘겨받는 순간을 잡았다. `주황 1.65s → 노랑 0.28s → 앱 콘텐츠`.
그 0.28s 가 결정 3 의 정정을 낳았다.

정정을 적용하고 다시 찍은 판(`Displayed +441ms`).

| 시각 | 일 |
|---|---|
| 2.13s | 1겹 뜸 |
| 2.55s | RN 첫 프레임. 여기서 `onLayout` 이 `hideSplashScreen()` 을 부른다 |
| 3.04s | **1겹이 실제로 사라짐**(`remove starting view`) |
| 3.20s | 2겹 걷힘 |

스플래시 총 길이가 **1.80s 에서 1.07s 로 줄었다.** 고정 1초 타이머가 사라지고 콘텐츠 준비 시점을
따라가게 된 결과다.

**그리고 남은 것 하나가 보였다.** `hideAsync()` 는 요청이 접수되면 끝나고, 1겹은 그 뒤로 400ms 를
더 걸려 사라진다. 그래서 600ms 중 이 층이 혼자 보인 것이 160ms 였다.

**원인을 찾아 껐다**(결정 3 의 정정 3). 안드로이드는 퇴장에 alpha 페이드를 **항상** 건다
(`SplashScreenManager.kt` 의 `setOnExitAnimationListener`, 기본 400ms). 그 400ms 는 2겹이 이미
그려진 채로 가려져 있는 시간이라 통째로 낭비다. `boot-splash.ts` 에서
`setOptions({ duration: 0, fade: false })` 로 끈다. iOS 는 `fade` 가 기본 꺼짐이라 원래 없다.

그건 스플래시가 아니라 시작 성능 과제이고, 308ms 중 몇 ms 인지부터 재야 한다.
