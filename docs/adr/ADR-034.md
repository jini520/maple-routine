### ADR-034: 스케줄러 최초 동기화·캐시 유실 대비 — 어제(또는 그제) 응답으로 빈 섹션 선채움 (구현 완료, world/account 공유 콘텐츠 선채움은 범위 밖)

> 🟢 **ACTIVE — 유효.** 현행 RN 앱에 적용되는 결정이다.

**배경**: [[ADR-030]]의 stale 폴백(로컬 캐시로 복원)은 "로컬 캐시가 있을 때"만 동작한다. 앱을 처음 설치했거나(캐시 자체가 없음), 실기기 재설치·"캐시 데이터 삭제" 등으로 로컬 캐시가 유실된 상태에서, 마침 그 캐릭터가 이번 리셋 주기 이후 게임에 아직 접속하지 않아 Nexon 응답이 stale(섹션이 비어 옴, [[ADR-030]])이면 — 폴백할 로컬 데이터 자체가 없어 컨텐츠 스케줄러·보스 스케줄러 화면이 완전히 빈 채로 보인다(실측 확인, 2026-07-23, 지내우시 캐릭터). 이 캐릭터가 게임 내에서 스스로 정보를 갱신하기 전까지는 새로고침을 아무리 눌러도 계속 빈 상태가 유지된다.

**결정**:

1. **당일 응답에서 여전히 빈 섹션만 골라 어제(또는 그제) 응답으로 선채움**: [[ADR-030]] 로컬 캐시 병합(1단계) 이후에도 `daily`/`weekly`(컨텐츠)/`weeklyBoss`/`monthlyBoss` 중 "그 섹션이 stale인데(당일 응답에 아예 없음) 병합 후에도 여전히 비어있는" 섹션이 있으면(로컬 캐시조차 없었다는 뜻), `fetchSchedulerCharacterState(apiKey, ocid, date)`를 그 섹션들에 필요한 과거 날짜로 한 번 더 호출해(2단계) 그 응답을 "previous"로 삼아 [[ADR-030]]과 완전히 동일한 병합 로직(진행값 0/미완료로 리셋 등)을 그대로 재사용해 채운다. 이미 채워진 섹션(당일 fresh든 로컬 캐시든)은 건드리지 않는다 — "정보가 있으면 그대로 사용".
2. **조회 날짜 계산 — `lib/reset-clock.ts`에 `getBackfillDateKey(now)` 신설**: 평소엔 KST 기준 어제 날짜, 단 **KST 00:00~00:10 사이**(자정 직후 API 응답이 불안정하다는 사용자 확인, 2026-07-23)에는 그제 날짜를 반환한다. 기존 `getCurrentKstDateKey`/`getMostRecentWeeklyResetKst`와 동일하게 기기 로컬 타임존 getter를 쓰지 않고 `+9시간` 후 UTC getter로 읽는 방식을 그대로 따른다.
3. **적용 범위 — `schedule-sync.ts`의 `syncOneCharacter`에 구현해 3개 화면에 공통 적용**: 컨텐츠 스케줄러·보스 스케줄러·보스 수익(실시간 화면) 스토어가 전부 `syncSchedules`→`syncOneCharacter`를 그대로 재사용하는 구조([[ADR-030]] 확인)라, 이 함수 하나에 넣으면 세 화면 모두 자동으로 적용된다. **보스 수익의 과거 기간 백필(`backfillTarget`, [[ADR-032]] 결정 3)과는 별개의 메커니즘**이다 — 그쪽은 이미 끝난 기간의 완료 기록을 소급 조회하는 것이고, 이건 "오늘" 화면의 빈 섹션을 최근 실측 데이터로 근사 채움하는 것이다. 이름 혼동을 피하기 위해 함수명은 `backfill`이 아니라 `fillMissingSections`류로 짓는다.
4. **실패 시 best-effort**: 이 추가 API 호출이 실패(네트워크·레이트리밋 등)해도 동기화 전체를 실패시키지 않는다 — 1단계 결과(여전히 빈 섹션 포함)를 그대로 쓴다.

**알려진 한계 — world/account 공유 콘텐츠(몬스터파크 등)는 이 메커니즘으로 채워지지 않을 수 있음**: [[ADR-030]]의 stale 폴백은 world/account 범위 항목을 로컬 캐시(`previous`)가 아니라 별도 원장(`worldSharedProgress`/`accountSharedProgress`)에서만 복원한다(`mergeSection`의 stale 분기가 world/account 항목을 `previous`에서부터 명시적으로 건너뜀). 이 원장도 함께 비어있는 극단적 케이스(그 월드/계정으로 이 캐릭터가 사실상 최초 동기화)에서는, 이번 결정으로 어제자 응답을 가져와도 몬스터파크·에픽 던전 같은 항목은 채워지지 않고 character 범위 항목(일일 퀘스트, 주간 보스 등)만 채워진다 — 원장까지 선채움하려면 `mergeSection`의 stale 분기 자체를 확장해야 하는데, 이번 결정 범위 밖으로 둔다.

**확정(2026-07-23)**: 위 world/account 원장 선채움은 이번 범위에서 제외한다 — character 범위(일일 퀘스트·주간 콘텐츠·주간/월간 보스) 선채움만 구현한다.

**정정(2026-07-23) — 섹션 단위 판정을 항목 단위로, 조회 범위를 -13일로 확장**: 실측 재현 결과(지내우시 캐릭터) 결정 1의 "섹션이 완전히 비었는지"(`length === 0`) 판정만으로는 부족하다는 게 확인됐다 — Nexon 응답은 섹션을 통째로 비우는 대신 **개별 항목만 누락**시키는 경우가 있다(예: 오늘 daily_contents가 완전히 빈 배열이 아니라 `[몬스터파크]` 1개뿐이고, 원래 있어야 할 나머지 17개 일일 퀘스트 항목이 빠짐 — 반면 어제자 응답엔 18개가 전부 있었음). 이 경우 `isDailyStale`이 `false`가 되어 결정 1의 트리거에 안 걸리고, 기존 [[ADR-030]] 병합(`mergeSection`/`mergeBossCycle`)도 "stale이 아니면 fresh 항목만 사용"이라 로컬 캐시에 있던 나머지 항목이 그대로 버려진다 — 이 구조적 빈틈은 백필 이전부터 있던 문제로, 로컬 캐시 폴백 경로에도 동일하게 존재한다.

**결정(개정)**:
1. `mergeSection`/`mergeBossCycle`의 character 범위 항목 처리를 "섹션 단위 boolean"에서 **항목(콘텐츠는 이름, 보스는 이름+난이도) 단위**로 바꾼다 — fresh에 있으면 그대로 쓰고, fresh에 없는데 previous(로컬 캐시)에 있으면 진행값을 리셋해 복원한다. 이 병합은 `isXStale` 값과 무관하게 항상 수행한다(world/account 범위는 기존 로직 그대로 유지, 범위 밖).
2. 위 병합 후에도, **당일 원본 응답(`fresh`) 기준으로 daily/weekly/weeklyBoss/monthlyBoss 중 하나라도 `isXStale: true`**(그 섹션이 당일 응답에서 완전히 비어 옴)이면, 과거 조회를 시작한다 — 결정 1(어제/그제 1회)을 대체해 **오늘 기준 -1일(00:00~00:10 KST엔 -2일부터)부터 -13일까지 하루씩** 순차 조회한다. 매 조회마다 그 날짜 응답으로 아직 못 채운 항목(모든 섹션 공통)을 채우고, **그 날짜 자체의 `isXStale` 플래그가 원래 stale이던 섹션들 기준으로 전부 `false`**(그 날은 정상 응답)이면 그 시점에서 조회를 멈춘다. 하루 조회 실패(네트워크 등)는 그 날짜만 건너뛰고 다음 날짜로 계속 진행한다(best-effort). 13일을 다 써도 못 채운 항목은 포기하고 화면에 표시하지 않는다(현재와 동일).
3. 한 번의 과거 조회(하루치 응답)로 stale이던 섹션뿐 아니라 **4개 섹션 전부**의 항목 gap을 동시에 채운다 — 예: 주간 보스가 stale이라 조회가 트리거돼도, 그 조회 응답에 있는 daily/weekly 콘텐츠 항목도 함께 병합에 쓴다(API 호출을 아끼기 위함).

**트레이드오프(추가)**:
- 캐릭터가 여러 날 미접속이었으면 API 호출이 최대 13회까지 늘어날 수 있다(레이트리밋 위험 증가) — 다만 "그 날짜 자체가 정상"이면 즉시 멈추므로, 실제로는 캐릭터가 마지막으로 활동한 날을 찾는 순간 멈춘다.
- 항목 단위 병합으로 인해, previous(로컬 캐시)에 남아있던 항목이 실제로는 게임에서 이미 삭제/변경된 콘텐츠라도 계속 복원될 수 있다 — 기존 [[ADR-030]]도 동일한 전제(previous를 신뢰)를 이미 갖고 있어 새로운 리스크는 아니다.

**추가 정정(2026-07-25) — 백필 트리거를 "섹션 완전 비었는지(isXStale)"에서 "character 범위 항목이 있는지"로 확장**: 실측 재현(ocid `4c9b04…`, 콜드 스타트) 결과, 정정(2026-07-23)의 항목 단위 병합만으로도 여전히 빠지는 사각지대가 확인됐다 — 당일 daily 응답이 완전히 비지 않고 **월드공유 항목 `몬스터파크` 1개만 남아**(length 1) `isDailyStale`이 `false`가 되는 상황에서, 로컬 캐시까지 없으면(콜드 스타트) ① 항목 단위 병합은 복원할 `previous`가 없고 ② 결정 2의 백필 트리거(`isXStale: true`)에도 안 걸려, 등록된 일일 퀘스트가 통째로 화면에서 사라진다. weekly/boss는 당일 응답이 온전하면 영향 없고, **웜 캐시면 항목 단위 병합이 캐시에서 복원해 가려진다** — 즉 "콜드 스타트 + 섹션 부분 누락"에서만 재현된다.
- **결정**: `schedule-sync.ts`의 백필 트리거 판정을 raw `isXStale`(=`length === 0`)이 아니라 **"그 섹션에 character 범위 항목이 하나라도 있는가"**로 바꾼다. daily/weekly는 캐릭터가 동기화되면 항상 자기 범위 항목(일일/주간 퀘스트 등)이 들어오므로, 월드/계정 공유 항목(`몬스터파크` 등)만 남았으면 "이 캐릭터의 그 섹션은 아직 stale"로 본다. 판정 대상은 1단계 병합 결과(`stage1.characterState`)라, 웜 캐시가 이미 채운 경우엔 트리거되지 않아 불필요한 과거 조회를 피한다. 과거 조회 중단(`resolved`) 판정도 같은 기준(그 날짜 응답에 character 범위 항목이 있는가)으로 확장한다. `normalize.ts`의 `isDailyStale`/`mergeSection`의 world/account 분기는 건드리지 않는다 — `isDailyStale`을 character 기준으로 재정의하면 콜드 스타트에서 `몬스터파크` 자체가 stage1의 world 분기를 못 타 되려 사라지기 때문(범위 밖 유지).
- **여전히 범위 밖**: world/account 공유 항목(`몬스터파크`·`에픽 던전` 등) 자체의 콜드 스타트 선채움은 위 "알려진 한계" 그대로 미구현이다. 이번 변경은 그 옆에 딸려 사라지던 **character 범위 항목**만 되살린다.
