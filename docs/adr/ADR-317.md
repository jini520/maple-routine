# ADR-317: 로그인 만료는 키 무효화와 다른 실패다. 확인은 남은 수단을 세고 나서 이동한다

> 🟢 유효 · 구현 완료 2026-09-26 · 실기기 미검증 · 사용자 지정 · 이슈 #542

**관련**: [[ADR-296]] 결정 4(갱신 토큰까지 만료되면 앱에 재로그인을 알린다) · [[ADR-115]] 결정 9·10(무효 키 판정 · 안내 모달의 확인) · [[ADR-116]] 결정 1(429 가 같은 사슬을 탄다) · [[ADR-215]] 결정 2(키 입력 화면이 곧 로그인 화면)

## 맥락

넥슨 로그인의 갱신 토큰은 14일이다. 그 뒤로 서버가 세션 행을 지우고 앱에 401 을 준다
([[ADR-296]] 결정 4). 2주 넘게 앱을 안 켠 사용자가 여기 걸린다.

그 401 이 지금은 **키가 죽은 것과 똑같이 읽힌다.** `nexon/http.ts` 가 전송 경로를 안 보고 401·403 을
전부 `NexonAuthError` 로 던지기 때문이다. 사슬을 끝까지 따라가면 이렇게 된다.

```
서버 401        →  NexonAuthError        어느 전송이든 401 은 같게 읽는다
                →  isInvalidApiKeyError  참
                →  'invalidApiKey'
                →  모달 「API 키가 더 이상 유효하지 않습니다」
                →  확인
                →  notice.apiKey 가 null   로그인으로 부르다 실패해 실을 키가 없었다
                →  removeAllApiKeys()      ← 여기
```

**로그인 하나가 만료되면 사용자의 API 키가 전부 지워진다.** 그 키들은 멀쩡하고, 여럿이면 다른 넥슨
계정의 키까지 함께 사라진다. 그리고 모달은 키를 다시 넣으라고 말한다. 실제 처방은 다시 로그인하는
것이다.

같은 뿌리에서 두 번째 결함이 나온다. `confirmApiKeyNotice` 는 **무조건** `SIGNED_OUT` 을 낸다. 키가
여럿인 사용자의 키 하나가 죽어도, 로그인이 살아 있는 사용자의 키 하나가 죽어도 앱 전체가 로그인
화면으로 내려간다. 남은 수단으로 조회되던 메이플 ID 까지 같이 잃는다. [[ADR-296]] 결정 1(키와
로그인이 나란히 선다)이 확인 버튼 한 곳에서 무너져 있었다.

## 결정

### 결정 1. 로그인 전송의 401 은 따로 던진다 (사용자 지정)

`nexon/http.ts` 가 **자격의 종류를 보고** 갈라 던진다.

- `credential.kind === 'login'` 이고 401·403 이면 `NexonSignInRequiredError`
- 그 밖의 401·403 은 지금처럼 `NexonAuthError`

`NexonSignInRequiredError` 는 `NexonApiError` 를 직접 상속한다. `NexonAuthError` 밑에 두면
`isInvalidApiKeyError` 가 참을 돌려줘 지금 결함으로 그대로 되돌아간다.

전송 경로가 갈리는 자리가 이미 이 파일 하나라(`routeOf`), 자격의 종류를 아는 곳도 여기뿐이다.

로그인 전송에서 403 도 같이 묶는 것은 **처방이 같기 때문이다.** 그 경로에는 탓할 키가 없어
`다시 로그인` 말고 사용자가 할 수 있는 것이 없다.

### 결정 2. 어휘에 `signInRequired` 를 더한다

`ScheduleSyncError` 에 종류를 하나 더한다. `format.ts` 의 전수 검사 셋이 문구를 쓰도록 강제한다.

- 토스트: `로그인이 만료됐습니다`
- 로스터 `ErrorState`: `로그인이 만료됐습니다` / `다시 로그인해주세요`
- 스탈 배너: `로그인이 만료되어 목록을 갱신하지 못했습니다`

재시도 액션은 안 준다. 눌러도 같은 401 이다([[ADR-114]] 결정 2 와 같은 근거).

`WithApiKey` 를 함께 붙이지만 **이 종류는 값을 안 싣는다.** 로그인으로 부르다 난 실패라 실을 키가
없다. 교차 타입을 유지하는 것은 소비자가 `error.apiKey` 를 종류마다 갈라 읽지 않게 하기 위해서다.

### 결정 3. 알림 종류도 갈린다. 지우는 것은 로그인 하나다

`ApiKeyNoticeKind` 에 `signInRequired` 를 더한다. 모달 문구는 `넥슨 로그인이 만료됐습니다` /
`다시 로그인해주세요.` 이고 아이콘은 `CircleUserRound` 다. 키 계열(`KeyRound`)·한도 계열(`Gauge`)과
한눈에 갈려야 한다.

확인을 누르면 `clearNexonLogin()` 만 부른다. **API 키는 안 건드린다.**

본문이 다음에 일어날 일을 말하지 않는 것은 그것이 **사용자마다 다르기 때문이다**(결정 4). 대신
처방을 말한다. 두 갈래에서 모두 참인 문장이다.

### 결정 4. 확인은 남은 수단을 세고 나서 이동한다 (사용자 지정)

`confirmApiKeyNotice` 의 차례를 뒤집는다. **죽은 수단을 먼저 지우고**, `getAuthConfig()` 로 남은 것을
센 다음 이동을 정한다.

- 남은 수단이 **없으면** `SIGNED_OUT` 이다. 이 앱은 수단 없이 할 수 있는 것이 거의 없어 반드시
  로그인 화면에 세운다(사용자 지정).
- **있으면** 알림만 닫는다. 앱은 그 수단으로 계속 선다.

지우기가 실패하면 세지 않고 `SIGNED_OUT` 으로 보낸다. 무엇이 남았는지 모르는 채로 앱을 세우면
같은 실패를 무한히 다시 만난다.

알림만 닫는 자리를 위해 `NOTICE_ACKNOWLEDGED` 이벤트를 더한다.
`DEVELOPMENT_STAGE_KEY_ACKNOWLEDGED` 와 같은 모양이다.

이 결정은 **로그인 만료만 고치는 것이 아니다.** 키 무효화도 같은 길을 탄다. 로그인을 쓰는 사용자의
키 하나가 죽어도 앱은 계속 선다.

## 대가

- **모달을 확인한 뒤 앱이 그대로 서 있는 갈래가 생긴다.** 사용자는 로그인이 만료됐다는 것을 읽고
  확인을 눌렀는데 화면이 그대로다. 재로그인은 설정에서 손으로 해야 한다. 모달이 재로그인을 바로
  띄우는 길은 안 골랐다 - `signInWithNexon()` 이 브라우저 세션을 여는 일이라 확인 버튼 하나가
  담기에는 크다. **실사용에서 이것이 유도로 충분한지는 미확인이다.**
- **확인이 저장소 쓰기를 기다린 뒤에 화면을 바꾼다.** 종전에는 상태를 먼저 뒤집었다. 남은 수단은
  지운 뒤에야 셀 수 있어 차례를 바꿀 수 없다. 쓰기는 로컬 환경설정 한 번이라 체감은 없을 것으로
  보지만 **실기기에서 안 쟀다.**
- **로그인 전송의 401 을 서버와 넥슨이 갈라 주지 않는다.** 우리 서버가 세션을 모를 때도, 서버가 든
  토큰이 넥슨에서 거절당할 때도 401 이다. 처방이 같아 접었지만, 서버 쪽 장애로 401 이 나면 사용자는
  자기 로그인이 만료된 줄 안다.
