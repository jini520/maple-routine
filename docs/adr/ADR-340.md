# ADR-340: 서버가 드는 사람은 `users` 한 표이고 열쇠 둘을 칸으로 든다. 새 기능은 로그인에만 열린다

> 🟢 유효 · 2026-10-08 · 사용자 지정
>
> **결정 2 · 4 · 5 · 6 은 구현 완료다**(2026-10-08 배포, 서버 PR #13). `users` 표가 서고
> `nexon_sessions.user_id` 가 그것을 참조하며(`ON DELETE CASCADE`), `sealApiKeyHash` 가 받은
> 해시를 한 번 더 해시하고, `uid` 없는 로그인은 사람으로 승격되지 않는다. **결정 1 · 3 · 7 · 8 은
> 아직 코드가 없다** - 묶을 새 기능도, 쓰기 경로도 없다.

> 사용자 지정(2026-10-08): API 키를 사용해서 앱을 이용하는 사람들에게 이용에 제한을 두고 싶진
> 않으나, 새로 추가될 크레딧 · 드롭스 · 상점 · 데이터 내보내기 · 불러오기 같은 기능은 사용할 수

## 맥락

### 같은 날 쓴 결정 셋이 서로 다른 무게를 적었다

2026-09-19 에 세 문장이 함께 나왔다.

| 출처 | 적힌 것 | 함의 |
|---|---|---|
| [[ADR-296]] 결정 1 | 어느 쪽도 다른 쪽을 대체하지 않는다. 로그인만 있는 사용자와 키만 있는 사용자가 둘 다 정상 상태다 | 두 수단의 무게가 같다 |
| [[ADR-296]] 결정 2 | 로그인은 앱 사용자를 식별하는 축이고, 키는 거기 붙는 자원이다 | 무게가 다르다. 사람은 로그인뿐이다 |
| [[ADR-299]] 결정 3 | uid 가 없으면 API 키의 해시로 가른다 | 키를 사람으로 승격시킨다. 결정 2 를 깬다 |

**셋은 서버가 아무것도 저장하지 않는 동안만 공존한다.** 서버가 사람 단위로 데이터를 들기 시작하는
순간 결정 2 와 결정 3 이 같은 질문에 다르게 답한다. 이 문서는 그 경계를 긋는다.

### 무게를 축마다 재면 두 군데서 뒤집힌다

| 축 | 넥슨 로그인 | API 키 |
|---|---|---|
| 신원을 누가 보증하나 | 넥슨. 서버가 `client_secret` 으로 교환해 받은 uid | 아무도. 서버는 키를 본 적이 없다 |
| 한 사람에 몇 개 | 1개 | N개 ([[ADR-296]] 결정 2) |
| 수명 | 갱신 14일. 끊겨도 다시 로그인하면 같은 uid | 재발급하면 영구히 다른 사람. 넥슨에서 지우면 `400 OPENAPI00005` 로 죽는다(실측 2026-08-08, `foundation/nexon-api.md`) |
| 사용자가 치르는 값 | 버튼 한 번 | 개발자 포털 가입 + 서비스 단계 키 신청. 개발 단계 키는 429 로 쫓겨난다([[ADR-116]] 결정 1 · [[ADR-214]]) |
| 개발자가 치르는 값 | 비프렌즈 12경로가 번들에 심은 개발자 키를 탄다. 약관 제6조⑥ 부담도 개발자 쪽([[ADR-320]] 결정 4) | 0. 사용자 자기 키 · 자기 한도 |
| 지금 열려 있나 | 아니다. `NEXON_LOGIN_ENABLED = false`([[ADR-334]]), 테스트 사용자 5명 | 열려 있다. 현 사용자 100% |

**신원이 약한 쪽이 더 깊이 들어온 사용자다.** 지금 키 사용자는 서비스 단계 키 신청까지 통과한
사람이다. 제품에 가장 많이 투자한 사용자가 서버 입장에서는 신원이 가장 희박하다.

**로그인 사용자가 늘수록 개발자 비용이 는다.** [[ADR-320]] 결정 4 가 비프렌즈 12경로를 번들
개발자 키로 돌렸다. 키 사용자는 자기 한도를 쓰는데, 로그인으로 넘어온 사용자는 개발자 키 한도와
약관 부담을 개발자에게 넘긴다. 이 문서의 유도가 성공할수록 그 비용이 는다.

### 세션은 임시 티켓이다

서버는 이미 요청의 주인을 가릴 수 있다. 앱이 `x-nexon-session` 헤더를 싣고
`resolveSession()` 이 해시로 `nexon_sessions` 행을 찾아 `nexonUid` 까지 들고 돌아온다. 토큰 갱신도
그 안에서 한다.

**그런데 그 행은 지워진다.** 셋 다 정상 동작이다.

| 언제 | 자리 |
|---|---|
| 갱신 토큰 14일이 지나면 | `resolveSession` 이 `sessionExpired` 를 보고 `deleteNexonSession` |
| 넥슨이 갱신을 거절하면 | 같은 함수의 `catch` |
| 사용자가 연결을 해제하면 | `DELETE /v1/auth/nexon/session` |

재로그인하면 새 `session_hash` 로 새 행이 생긴다. 지금 `nexon_uid` 는 그 **세션 행의 칸**이라,
세션이 죽으면 서버가 그 사람을 알아보는 유일한 자리가 함께 사라진다. 크레딧 잔액을 세션에 매달면
2주 안 켠 사용자의 크레딧이 없어진다.

### 앱에는 해시 수단이 없다

`expo-crypto` 가 `package.json` 에 없고, `src/` 안에 해시를 쓰는 자리가 한 곳도 없다(확인
2026-10-08). `crypto` 가 전역에 없는 것도 확인했다 - `react-native` 0.86.2 의 `Libraries/Core` 가
심지 않고, `expo` 의 winter 런타임이 심는 것은 `AbortSignal` · `DOMException` · `FormData` ·
`TextDecoder` · `URL` · `fetch` 여서 `crypto.randomUUID()` 도 못 부른다. 전이 의존으로 들어온
패키지도 없다. 키 해시를 앱이 만들려면 수단을 먼저 들여야 한다.

**난수는 이 질문에 안 든다.** uuid 는 SQLite 가 만든다([[ADR-342]] 결정 1). 여기 필요한 것은
SHA-256 구현 하나이고 결정론적 함수라 순수 JS 로 충분하다.

## 결정

### 결정 1. 기존 기능은 수단으로 안 가른다. 새 기능만 로그인에 묶는다 (사용자 지정)

| | API 키 사용자 | 로그인 사용자 |
|---|---|---|
| 지금 있는 기능 전부 | 그대로 | 그대로 |
| 크레딧(#609) · 드롭스(#620) · 상점 · 내보내기와 불러오기(#612) | 못 쓴다. 로그인으로 유도한다 | 쓴다 |

[[ADR-296]] 결정 1(두 수단이 둘 다 정상 상태)은 **지금 있는 기능에만** 적용된다. 서버가 드는
사람의 정의는 결정 2 가 소유한다. 그것이 두 문서의 경계다.

**가르는 기준은 서버가 데이터를 돌려주는지다.** 재화와 백업은 서버가 그 사람에게 되돌려 주는
것이라, 신원이 틀리면 남의 것을 가져간다. 조회는 되돌려 줄 것이 없어 그 위험이 없다.

### 결정 2. 사람은 `users` 한 표이고 열쇠 둘을 칸으로 든다 (사용자 지정)

```sql
CREATE TABLE users (
  id            uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  nexon_uid     text        UNIQUE,   -- 로그인 사용자의 열쇠
  api_key_hash  bytea       UNIQUE,   -- 키만 쓰는 사용자의 열쇠
  created_at    timestamptz NOT NULL DEFAULT now(),
  last_seen_at  timestamptz NOT NULL DEFAULT now(),
  CHECK (nexon_uid IS NOT NULL OR api_key_hash IS NOT NULL)
);
```

**열쇠가 칸으로 들어가는 것은 사람 하나에 열쇠가 각 종류 하나씩이기 때문이다**(결정 8). 수단을 행으로
가른 별도 표(`user_identities`)를 두면 1:N 을 표현할 수 있지만, 지금 1:N 이 될 수 있는 것은 키뿐이고
결정 8 이 그 자리를 닫는다.

기능 표는 `user_id` 를 직접 든다. 그래서 크레딧을 읽을 때도 드롭 가격을 적을 때도 `users` 를 join
하지 않는다. **얇게 두는 것이 join 을 안 만드는 선택이다.** `users` 에 칸이 늘면 그 칸을 읽으려고
join 이 생긴다.

사람을 거치지 않고 수단을 기능 표의 열쇠로 쓰면, 수단이 바뀔 때마다 기능 표 전부를 UPDATE 해야
한다. 표가 늘수록 그 목록이 늘고 하나를 빠뜨리면 그 기능만 조용히 끊긴다.

**둘 다 비울 수 없다.** 열쇠가 없는 사람은 다시 찾을 수 없어 행이 쓰레기가 된다. `CHECK` 가 그것을
막는다.

### 결정 3. 키 사용자의 데이터도 모은다 (사용자 지정)

#610 드롭 가격 · #611 수익 백분위 · #507 불변 과거값은 **수단을 안 가리고** 모은다. 표본이 지금
100% 에서 나오고, [[ADR-299]] 결정 4(전송은 무조건)가 그대로 선다.

**사칭이 가능한 것을 알고 고른 것이다**(사용자 지정 2026-10-08). 해시를 아는 사람이 그 사람으로
읽힌다. 이 길로 할 수 있는 일이 쓰기와 돌려받기 없는 수집뿐이라 피해가 재화 · 백업보다 작다는
판단이다. 재화와 백업은 결정 1 이 로그인으로 막는다.

### 결정 4. 세션은 사람을 가리키는 티켓이다. `nexon_sessions` 가 `users` 를 참조한다

`nexon_sessions.nexon_uid` 를 `users` 로 올린다. 로그인할 때 uid 로 기존 사람을 찾고 없으면
만든다. 세션 행은 지금처럼 지워지고, 사람은 남는다.

맥락이 적은 대로 세션은 세 경우에 지워지는데 그것이 전부 정상 동작이다. 사람을 세션에 매달면
**정상 동작이 데이터 소실이 된다.**

### 결정 5. 서버는 받은 해시를 다시 해시해 저장한다

앱이 보낸 해시를 칸에 그대로 넣지 않는다. 서버가 한 번 더 해시한 값을 저장하고, 조회할 때 들어온
값을 같은 방법으로 해시해 맞춘다.

[[ADR-299]] 열린 질문이 지목한 자리다. 앱이 보낸 해시는 서버 기록을 여는 값이기도 해서, 받은
그대로 저장하면 DB 가 새어 나갈 때 남의 기록을 열 수 있다.

**이 앱에 이미 있는 방식이다.** `nexon_sessions` 가 세션 원본이 아니라 `hashSession()` 의 결과를
열쇠로 쓰고, 그 마이그레이션이 이유를 적어 뒀다. 같은 문제에 같은 모양을 쓴다.

### 결정 6. `uid` 를 못 받은 로그인은 사람으로 승격하지 않는다

`nexon_sessions.nexon_uid` 는 비어 있을 수 있다. userinfo 가 실패해도 로그인을 진행하기 때문이고
(그 마이그레이션 주석에 적혀 있다), 그 선택 자체는 그대로 둔다. 조회는 되게 하는 쪽이 맞다.

uid 가 없으면 `users` 행을 만들지 않는다. 그 세션으로 조회는 되고 새 기능만 안 열린다. 결정 1 이
그은 선과 같은 모양이라 사용자가 보는 규칙이 하나다.

**로그인 자체를 실패시키지 않는 이유**는 그러면 userinfo 한 번의 실패가 조회 전부를 막기 때문이다.
결정 1 이 기존 기능을 안 가르기로 했으므로 그 방향으로 깨지게 둘 수 없다.

### 결정 7. `/v1` 의 쓰기 경로는 세션을 사람으로 바꾸는 한 겹을 공유한다

`resolveSession` 위에 사람까지 찾아 주는 한 겹을 올리고, 크레딧 · 상점 · 백업 경로가 그것을 함께
쓴다. 경로마다 베끼면 한 곳만 고쳐지는 날이 온다.

지금 `/v1` 조회는 전부 인증이 없고(공개 정보라서) 세션을 읽는 곳은 `auth-routes.ts` 셋뿐이다.
인증을 든 경로가 처음 생기는 자리다.

### 결정 8. 키를 더하는 기능은 로그인 사용자에게만 연다 (사용자 지정)

API 키가 여러 개 들어와도 사람은 하나다. 추가 키를 새 사람으로 안 잡는다. 그 방법으로 **키를
더하는 자리 자체를 로그인 뒤로** 둔다.

**그래서 서버가 보는 열쇠는 늘 하나다.** 키만 쓰는 사용자는 키가 하나뿐이라 그 해시가 곧 열쇠다.
키가 여럿인 사용자는 로그인 사용자이고 `nexon_uid` 로 식별된다. 키는 [[ADR-296]] 결정 2 가 적은
대로 조회 자원으로만 남는다.

**지금 동작을 바꾸지 않는다.** `setApiKey` 가 배열에 더하도록 쓰여 있지만 쓰는 자리는
`features/auth/current-credential.ts` 와 `saved-key.ts` 의 `apiKeys[0]` 하나이고, 키를 더하는 화면이
없다. 이 결정은 그 자리를 로그인 뒤로 못박는 것이다.

**순서가 하나 걸린다.** 키 사용자가 로그인할 때 [[ADR-296]] 결정 6 이 기기에서 키를 지운다. 그
행에 `nexon_uid` 를 적는 일이 **키를 지우는 일보다 먼저** 와야 한다. 뒤집히면 서버가 그 사람을 다시
못 찾는다.

**백분위가 닿을 수 없는 값이 되는 문제는 이 결정으로 안 풀린다**(사용자 지적 2026-10-08). 계정 여럿을
가진 사람의 합계는 한 계정으로는 못 닿는 값이다. 그것은 식별의 축이 아니라 집계 단위의 축이라
수집 표에 무엇을 적는지가 정한다(열린 질문).

## 대가

- **승인 전까지 새 기능이 아무에게도 안 열리고, 유도할 자리도 없다.** [[ADR-334]] 결정 2 가 로그인이
  꺼진 동안 넥슨 블록과 더보기 버튼을 안 세운다. 크레딧 화면에서 로그인을 권해도 누를 버튼이 없다.
  서버와 앱을 지어 두고 승인을 기다리는 모양이 된다.
- **유도가 성공할수록 개발자 키 한도와 약관 부담이 는다.** [[ADR-296]] 결정 6 이 캐릭터 목록이 같으면
  기기에서 키를 지우므로, 넘어온 사용자의 비프렌즈 조회가 번들 개발자 키로 간다([[ADR-320]] 결정 4).
- **해시가 사실상 비밀번호다.** 결정 3 이 쓰기에 한정해 받아들였다. 결정 5 가 DB 유출 쪽만 막는다.
- **키를 재발급하면 그 사람의 수집 기록이 끊긴다.** 다른 사람으로 본다(#607, 사용자 2026-10-06).
- **개인정보 의무가 지금 전원에게 걸린다.** 계정 삭제 경로 · 처리방침 개정 · Play 데이터 안전 ·
  App Store 개인정보 라벨이다([[ADR-299]] 대가 · `foundation/release.md`). 키 사용자도 사람 단위로
  모이므로 승인을 기다릴 수 없다.
- **앱에 SHA-256 구현을 들여야 한다.** 순수 JS 면 번들에 실려 OTA 로 가고 네이티브 모듈이면 스토어
  빌드를 기다린다. 키 해시 경로는 이 선택 뒤에 선다.
- **키를 더하는 자리가 로그인 뒤로 묶인다.** 결정 8 이 그 기능을 넥슨 승인 뒤로 보낸다. 다른 넥슨
  계정의 캐릭터를 보려는 사용자는 그때까지 기다린다. [[ADR-296]] 결정 2 가 복수 키의 목적으로 적은
  것이 그것이다.
- **로그인과 키 지우기의 순서가 깨지면 사람을 잃는다.** 결정 8 이 적은 순서다. 테스트가 그 순서를
  지켜야 하고, 순서를 코드 두 곳이 나눠 들면 어긋난다.

## 기각

- **새 기능을 키 사용자에게도 연다.** 재화와 백업을 재발급 가능하고 사칭 가능한 열쇠에 매단다.
  사용자 지정으로 기각했다(결정 1).
- **기존 기능도 로그인으로 모은다.** 지금 사용자 100% 가 못 쓰게 된다. 사용자 지정으로 기각했다.
- **키 사용자의 데이터를 안 모은다.** 표본이 로그인 사용자로 줄고, 승인 전에는 0 이다. 사용자
  지정으로 기각했다(결정 3).
- **수단을 행으로 가른 별도 표(`user_identities`)를 둔다.** 한 사람에 수단 여럿을 매달 수 있지만, 결정 8 이 키를 더하는 자리를 로그인 뒤로 두어 1:N 이 생기지 않는다. 표를 하나 더 두면 사람을 찾는 조회가 한 번 늘고, 수단 둘이 각자 다른 사람에 붙었을 때 사람을 합치는 일이 생긴다.
- **사람을 앱이 만든 익명 식별자로 둔다.** 사칭을 막고 지금 100% 를 덮지만, 기기를 바꾸면 사람이
  바뀌어 기기 이관이 로그인 사용자 한정이 된다. 결정 1 이 이관을 이미 로그인 한정으로 정해 이 안의
  이점이 사라졌다.

## 정정

- **[[ADR-296]] 결정 8 의 근거 한 줄이 사실이 아니다.** 약관 제5조①(키 비공유) 준수 근거로 `이
  설계는 앱에 공용 키를 내장하지 않고` 를 적었는데, [[ADR-320]] 결정 4 가 개발자 키 둘을 번들에
  심었다. 그 결정이 대가를 적어 두고 사용자가 알고 고른 것이라 결론은 유지되지만, 근거 문장은
  낡았다.
- **[[ADR-299]] 결정 5 는 [[ADR-320]] 이 대체했다.** `서버가 개발자 키로 대신 부른다` 였던 것이
  `앱이 번들 키로 직접 부른다` 가 됐다([[ADR-320]] 결정 1 · 4). [[ADR-320]] 의 관련 목록에
  [[ADR-299]] 가 없어 이 교체가 기록되지 않은 채였다.

## 열린 질문

착수 전에 답한다.

- **집계 단위를 무엇으로 두나.** 사용자가 지적한 자리다(2026-10-08). 사람 단위로 합산하면 계정
  여럿을 가진 사람의 값이 **한 계정으로는 닿을 수 없는 값**이 되어 상위를 독식하고, 나머지 사용자의
  순위가 거짓으로 낮아진다. 그리고 **앱 화면이 보여주는 합계의 단위와 서버 분포의 단위가 같아야
  한다** - 지금 `features/stats/aggregate.ts` 는 추적 목록 전체를 더하고 메이플 ID 를 가로지른다
  ([[ADR-297]] 미구현). 후보 셋 중 선 채로 틀리지 않는 것은 캐릭터(`ocid`) 단위뿐이다. 메이플 ID
  단위는 서버가 `ocid` → 메이플 ID 매핑을 모르고(기기 `character_accounts` 에만 있다) [[ADR-297]] 이
  먼저 서야 한다. **수집 표에 무엇을 적는지가 이 답에 걸리므로 그 표를 만들기 전에 답해야 한다.**
  결정은 #611 이 소유한다.
- **키 사용자가 로그인하면 해시 쪽 기록을 uid 로 잇는 조건.** #607 이 요구사항으로 적었다.
  [[ADR-296]] 결정 6 은 캐릭터 목록(ocid 집합)이 같을 때만 키를 지운다. 같은 기준을 쓸지, 다를 때는
  어떻게 할지. 결정 6 이 키를 지우므로 잇는 일이 먼저다.
- **uid 를 뒤늦게 채우는 길.** 결정 6 이 uid 없는 로그인을 사람으로 안 만든다. 그 사용자가 다음에
  앱을 켤 때 userinfo 를 다시 불러 승격시킬지.
- **[[ADR-296]] 결정 6(키 삭제)을 유지하는가.** 근거는 키가 평문으로 저장돼 있어 지우는 쪽이
  안전하다였다. 이 문서의 유도가 성공할수록 개발자 키 비용이 늘어, 안전과 비용의 교환을 다시 볼
  자리가 된다.
- **계정 삭제에서 해시 쪽 기록을 어떻게 지우나.** 로그인 사용자는 uid 로 지운다. 키 사용자는 삭제를
  요청할 화면도, 자기 해시를 증명할 방법도 없다.
- **SHA-256 구현을 무엇으로 들이나.** 순수 JS 라이브러리면 OTA 로 가고 네이티브면 스토어 빌드를
  기다린다. 후보와 OTA 영향(`npm install` 이 다른 패키지를 범위 최신으로 올려 지문을 바꾼 적이 있다)을
  함께 재야 한다. **uuid 는 이 질문에 안 든다** - SQLite 가 만든다([[ADR-342]] 결정 1).
- **`ApiKeyForm` 안내 문구.** [[ADR-299]] 에서 넘어온 질문이다. `입력한 키는 이 기기에만 저장되고
  넥슨 외 어디로도 전송되지 않아요` 가 적혀 있는데, 키 원문은 여전히 안 나가도 키에서 만든 값이
  나간다.
- **처리방침 개정과 스토어 신고의 시점.** 결정 3 이 수집을 전원으로 넓혀 승인을 기다릴 수 없다.
  스토어 빌드가 나가기 전에 끝나야 하는 일이라 일정이 묶인다.
