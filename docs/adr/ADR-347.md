## 맥락

### 이어 가지 않는다

운영 DB 의 행을 직접 셌다(2026-10-14).

| 표 | 행 | |
|---|---|---|
| `notices` | **151** | 유일하게 옮길 것. 176 kB |
| `nexon_login_attempts` | 18 | 만료된 테스트 흔적(09-25 ~ 09-30) |
| `nexon_sessions` | 2 | 테스트 로그인 |
| `manual_completion_bosses` | 2 | 둘 다 `closed_at` 이 찍혀 닫혀 있다 |
| `users` | 1 | 테스트 계정 |
| `drop_prices` | 0 | |

**실제 사용자 데이터가 없다.** 넥슨 로그인이 앱에서 꺼져 있고 드롭 가격 수집도 안 켜졌다. 그래서
스키마를 **마이그레이션이 아니라 초기 스키마로** 세울 수 있다.

### 넥슨 가이드라인이 로그인 모양을 정한다

개발 가이드(`openapi.nexon.com/ko/open-id/development-guide`)의 두 탭에 셋이 적혀 있다.

- **안전한 토큰 관리**: `유저의 인가 코드를 사용해 발급 받은 Access Token은 반드시 서버에서만
  관리하고 사용합니다.`
- **State 파라미터 사용**: `State 파라미터는 … 이후 Redirect URI에서 올바른 요청인지 확인하는
  데에 사용됩니다.` · `State 값은 제3자가 접근할 수 없는 안전한 곳에 보관해야 합니다.` ·
  `한번 인증에 사용된 State 값은 재사용 불가능하도록 구성합니다.`
- **인가 코드 발급 요청**: `redirect_uri` 예시가 `http://test.io/login` 이고 응답 예시가
  `302 Found Location: http://test.io/login?code=…&state=…` 다. **이 문서는 서버가 리다이렉트를
  받는 것을 전제로 쓰여 있고** 커스텀 스킴은 나오지 않는다.

**셋이 같은 한 점을 가리킨다.** 토큰을 서버만 쓰려면 교환을 서버가 해야 하고, state 를 Redirect
URI 에서 확인해야 하므로 그 주소가 서버여야 한다. `redirect_uri` 를 서버의 https 주소로 두는 것은
예외적 선택이 아니라 **스펙의 기본형**이다.

### 넥슨 스펙에서 읽은 것

| | |
|---|---|
| `authorize` 파라미터 | `response_type` · `client_id` · `redirect_uri` · `scope`(필수) · `state`(옵션·권장). **PKCE 가 없다** |
| 교환 파라미터 | `grant_type` · `client_id` · `client_secret` · `code` **넷. `redirect_uri` 가 표에 없다** |
| 토큰 수명 | access **30분** · refresh **14일**. 갱신 토큰이 만료되면 인가 코드 재발급 |
| 갱신 | `client_secret` 을 요구한다 |
| 식별자 | `GET /oauth2/userinfo` 가 `{ result: { uid, scope } }` |

### 실측

| 잰 것 | 결과 |
|---|---|
| 넥슨이 기밀 클라이언트만 받나 | **그렇다**(10-12). 비밀을 빼면 `OPENAPI00004` |
| 넥슨이 `code_verifier` 를 검사하나 | **아니다**(10-14). `code_challenge = S256(A)` 를 실어 로그인하고 교환에 `B` 를 보냈는데 `200` 에 토큰이 왔다 |
| https redirect URI 를 등록받나 | **받는다**(10-14). redirect URI 칸이 **5개**라 검수 중인 값을 안 건드리고 새 애플리케이션에 등록해 쟀다 |
| 넥슨이 그 주소로 리다이렉트하나 | **한다**(10-14). `GET /v1/auth/nexon/callback?code=…&state=…` 가 nginx 에 닿았다(Referer `openid.nexon.com`) |
| 갱신 토큰이 회전하나 | **회전하고 옛것이 즉시 죽는다**(10-12). 같은 토큰으로 동시에 둘 보내면 **하나만 이긴다**(A 400 / B 200) |
| `uid` 가 플랫폼을 가로질러 같나 | **같다**(10-12). pairwise 가 아니라 계정 자기 식별자다 |

**PKCE 는 두 갈래가 다 막혔다.** 비밀을 대신하지도 못하고 `code` 의 자물쇠도 못 된다. 그래서
`code` 를 authorize 요청에 묶는 길은 **서버가 콜백을 직접 받는 것** 하나뿐이고, 그 사실이 로그인
설계를 정했다.

**인가 코드가 nginx `access.log` 에 두 줄 남는다**(실측). 기본 `combined` 형식이 `$request` 를
쿼리까지 찍고, 브라우저가 이어 요청하는 `/favicon.ico` 의 `Referer` 에 한 번 더 들어간다.

### 커스텀 스킴 콜백이 안드로이드에서 막히지 않았다

redirect URI 가 커스텀 스킴이고 넥슨이 안드로이드 등록에서 서명 해시를 안 받아, 같은 스킴을 선언한
다른 앱이 콜백의 `code` 와 `state` 를 받을 수 있었다. 앱과 서버만 아는 값을 하나 더 두는 것으로
막으려 했지만 **그 자리가 비어 있었다** - 로그인 시작 경로에 인증이 없어 악성 앱이 **자기 짝을
새로 만들어** 가로챈 `code` 를 내면 통과한다. `code` 와 `state` 를 묶는 끈이 아무 데도 없기
때문이다(넥슨 교환 요청에 `state` 가 없다).

**iOS 는 해당하지 않았다.** 앱이 `openAuthSessionAsync` 로 열고 iOS 에서는 그것이
`ASWebAuthenticationSession` 이라 콜백이 그 세션에만 돌아온다 - 스킴 등록표를 안 거친다.
안드로이드는 Custom Tabs 뒤 딥링크가 보통의 인텐트 해석을 탄다.

이 문서의 로그인 설계는 **그 구멍이 생길 수 없는 모양**이다.

### 전제로만 두는 것

`PK 는 항상 uuid 한 칸이고 자연키는 단일 UNIQUE` 는 이 저장소의 규칙이다. 이 문서의 결정이 아니라
지켜야 하는 것이고, DB 를 처음부터 세우므로 **이관 없이 그냥 그 모양으로 만든다.**

## 결정 — 저장

### 결정 1. 표를 처음부터 이 모양으로 세운다

이어 갈 데이터가 없으므로 마이그레이션이 아니라 초기 스키마다.

```
users
  id              uuid        PK   서버가 만든다
  nexon_uid       text        UNIQUE  넥슨 uid. 플랫폼을 가로질러 같다
  api_key_hash    bytea       UNIQUE  앱이 보낸 해시를 서버가 한 번 더 해시
  created_at      timestamptz NOT NULL
  deleted_at      timestamptz          탈퇴. 사용자 요청으로 줄을 지우지 않는다
  CHECK (nexon_uid IS NOT NULL OR api_key_hash IS NOT NULL)

nexon_sessions
  id                 uuid        PK
  session_hash       bytea       UNIQUE  앱이 든 값의 sha256. 원본은 저장하지 않는다
  user_id            uuid        FK → users(id) ON DELETE CASCADE   NULL 허용
  platform           platform    NOT NULL  갱신도 같은 자격 쌍으로 해야 넥슨이 받는다
  access_sealed      bytea       NOT NULL  iv‖tag‖cipher
  access_expires_at  timestamptz NOT NULL  30분
  refresh_sealed     bytea       NOT NULL  iv‖tag‖cipher
  refresh_expires_at timestamptz NOT NULL  14일
  created_at         timestamptz NOT NULL
  last_used_at       timestamptz NOT NULL
  INDEX (user_id) · INDEX (refresh_expires_at)

nexon_login_attempts
  id              uuid        PK
  state           text        UNIQUE  넥슨에 넘기고 콜백으로 돌아오는 값
  redeem_hash     bytea       UNIQUE  sha256(redeem_key). 원본은 앱만 든다
  platform        platform    NOT NULL
  created_at      timestamptz NOT NULL
  expires_at      timestamptz NOT NULL  시작부터 10분

  id            uuid        PK

  push_body     text

  price_meso      bigint      NOT NULL  판매 총액. 내 몫이 아니다
  period_key      text        NOT NULL  주간 YYYY-MM-DD · 월간 YYYY-MM

  ring_level      integer               반지 레벨이 시세를 가른다
```

**`platform` 과 `notices.kind` 를 ENUM 타입으로 둔다.**

```sql
CREATE TYPE platform    AS ENUM ('ios', 'android');
CREATE TYPE notice_kind AS ENUM ('app', 'game', 'event', 'update', 'cashshop');
```

`text` 로 두면 틀려도 **에러가 아니라 나중에 조용히 실패한다** - `platform` 이 틀리면 로그인은 되고
**14일 뒤 갱신만** 실패하고, `kind` 가 틀리면 앱이 그 분류를 안 가져가 **공지가 조용히 안 보인다.**

`CHECK` 가 아니라 ENUM 인 근거(PG 16 실측 2026-10-12): 값을 더하는 것이 `ALTER TYPE … ADD VALUE`
**한 문장**이고 표를 안 훑는다. `RENAME VALUE` 가 **저장된 행도 따라온다.** 표 둘이 `platform` 을
공유하므로 타입 하나가 진실인 쪽이 실익이 있다. `DROP VALUE` 가 없는 것이 대가지만 이 두 칸은
값이 빠진 적이 없다.

**운영 규칙 하나.** 값을 더하는 마이그레이션은 **그 값으로 쓰지 않는다.** PG 16 은 같은 트랜잭션에서
더한 값을 쓰면 `unsafe use of new value` 로 거부하고 마이그레이션 도구가 트랜잭션으로 감싼다.
백필이 필요하면 파일을 둘로 가른다.

**봉한 값은 한 칸이다.** `iv`(12바이트) · `tag`(16바이트) · 암호문을 **한 덩이로 이어 붙인다.**
둘 다 길이가 고정이라 읽을 때 자르면 되고, 셋은 늘 함께 쓰이고 함께 읽히며 **따로 조회하거나
인덱스를 걸 일이 없다.** 칸을 가르는 것은 의식이다.

### 결정 2. `notices` 151줄만 옮긴다

나머지 다섯 표는 버린다. 옮길 때 지킬 것 둘.

- **`blocks` 가 있는 5줄을 잃으면 안 된다.** 넥슨이 지난 글 상세를 400 으로 거절해 **우리 DB 가
  유일한 사본**이다. `event` 분류의 썬데이 메이플 글들이다.
- **`sent_at` 이 찍힌 54줄을 함께 옮긴다.** 안 옮기면 이미 보낸 공지가 **다시 알림으로 나간다.**

## 결정 — 로그인

### 결정 3. 콜백을 서버가 받는다. 커스텀 스킴에 값을 안 싣는다 (사용자 지정)

`redirect_uri` 는 `https://mapleroutine.store/v1/auth/nexon/callback` 다.

```
① 앱 ──► POST /v1/auth/nexon/login { platform }
         state · redeem_key 를 만들어 짝에 둔다 (expires_at = +10분)
    ◄──  authorizeUrl · redeem_key          state 를 앱에 주지 않는다

② 앱 ──► 인증 세션으로 authorizeUrl 을 연다
   사용자  넥슨에서 로그인 · 동의

③ 넥슨 ──► GET /v1/auth/nexon/callback?code=&state=
         state 로 짝을 집는다 · 교환 · userinfo · users · nexon_sessions
         세션 원본을 짝에 봉한다 (결정 4)
    ◄──  302 com.mapleroutine.app://oauth/callback      값을 안 싣는다

④ 앱 ──► POST /v1/auth/nexon/session { redeem_key }
    ◄──  session
```

**앱이 내는 값이 바뀌는 것이 구멍을 닫는다.** `code` 는 넥슨이 발급해 우리가 짝을 못 박는 값이고,
`redeem_key` 는 **우리가 ① 에서 발급해 그 짝에 적어 둔** 값이다. 콜백을 가로챈 앱이 ① 로 자기 짝을
새로 만들어도 거기엔 봉한 세션이 안 달려 있다.

**커스텀 스킴에 실리는 값이 없다.** 302 는 돌아오라는 신호일 뿐이라 가로채도 얻을 것이 없다.
④ 의 열쇠인 `redeem_key` 는 ① 의 응답으로 **https 로만** 왔다. 그래서 신호를 놓쳐도 된다 - 앱은
그 값을 들고 있으니 ④ 를 그냥 부를 수 있고, 안드로이드에서 다른 앱이 신호를 먹어도 지연조차 아니다.

**`state` 를 앱에 주지 않는다.** 앱이 확인할 일이 없고(③ 에서 서버가 한다) 가이드라인의
`제3자가 접근할 수 없는 안전한 곳에 보관` 도 그래야 맞다.

**`claimed_at` 이 state 재사용을 막는다.** ③ 이 한 문장으로 집는다.

```sql
UPDATE nexon_login_attempts SET claimed_at = now()
 WHERE state = $1 AND claimed_at IS NULL AND expires_at > now()
RETURNING id, platform
```

0줄이면 거절한다. 한 문장이라 경합이 없고 넥슨 왕복 동안 트랜잭션을 붙들지 않는다. **없으면
state 를 아는 쪽이 자기 `code` 로 짝을 덮어쓸 수 있다** - state 는 리다이렉트 URL 에 실려
브라우저와 `access.log` 를 지나므로 **비밀이 아니고**, 그러면 우리 앱이 남의 계정으로 로그인된다.
가이드라인의 `한번 인증에 사용된 State 값은 재사용 불가능하도록 구성합니다` 가 이 칸이다.

**③ 은 무슨 일이 있어도 302 만 낸다**(사용자 지정). 교환 실패 · DB 실패 · 예외를 전부 감싼다.
안 그러면 사용자가 브라우저의 에러 화면에 갇히고 앱으로 안 돌아온다. **서버 가용성이 로그인 화면에
직결되는 것**이 이 설계에서 가장 큰 대가다.

**④ 의 답이 취소·실패·만료를 가른다.** 짝의 상태가 그대로 말한다 - `claimed_at` 이 없으면 사용자가
창을 닫은 것, 있는데 봉한 세션이 없으면 교환이 실패한 것, 짝 자체가 없으면 만료다.

**콜백 하나를 두 플랫폼이 공유한다.** 어느 자격 쌍으로 교환할지는 짝의 `platform` 이 말한다. 넥슨
애플리케이션이 둘이어도 돌아올 주소는 하나다.

**콜백 경로에 App Links·Universal Links 를 걸지 않는다.** 걸면 앱이 설치된 기기에서는 OS 가 그
주소를 앱으로 보내고 안 설치된 기기에서는 브라우저가 서버로 보내 **같은 주소가 두 가지로
동작한다.** 서버가 늘 콜백을 받는 것이 짝을 못박는 전제라 이 경로는 브라우저로 두고 결정적으로
만든다.

**그 경로의 로그 형식을 따로 둔다.** 기본 `combined` 가 인가 코드를 두 줄에 남긴다.

**경로 이름은 명사로 둔다.**

```
POST   /v1/auth/nexon/login      ①  로그인을 시작한다
GET    /v1/auth/nexon/callback   ③  넥슨이 부른다
POST   /v1/auth/nexon/session    ④  redeem_key 로 세션을 받는다
DELETE /v1/auth/nexon/session        로그아웃
```

`login` 인 것은 앱의 저장 형식이 `{ login, apiKeys }` 라 **그 말이 곧 넥슨 OAuth** 이기 때문이다.
**수단은 경로의 둘째 칸에서 가른다** - 지금 API 키 로그인에는 엔드포인트가 없지만, `/v1/auth/login`
처럼 수단을 안 적으면 나중에 키 쪽이 들어올 자리가 없어 `?method=` 같은 것이 붙는다.

### 결정 4. 세션 원본을 짝에 봉해 두고 60초 안에 꺼내 간다 (사용자 지정)

③ 과 ④ 가 **서로 다른 요청**이라 그 사이에 서버가 세션을 들고 있어야 한다. `nexon_sessions` 는
해시만 두므로 꺼내 줄 수 없다.

```
③  세션 값 S 를 뽑는다 → nexon_sessions 행 (session_hash = sha256(S))
                       → 짝에 봉한 S · session_id

④  DELETE FROM nexon_login_attempts
     WHERE redeem_hash = sha256($1) AND session_sealed IS NOT NULL
       AND claimed_at > now() - interval '60 seconds'
    RETURNING session_sealed
    → 풀어서 S 를 앱에 준다
```

**`redeem_key` 를 해시로 둔다.** 평문으로 두면 **DB 유출만으로 ④ 를 재생할 수 있다** - 키가 없어도
된다. `session_hash` 를 해시로 둔 이유가 그대로 여기 걸린다. 해시로 두면 DB 유출만으로는 아무것도
못 한다 - 해시는 제시할 수 없고 봉한 세션은 못 푼다.

**봉하는 이유.** 평문으로 두면 DB 유출만으로 그 세션을 읽는다. 봉하면 키가 함께 새야 하고, 키가
샜다면 이미 `nexon_sessions` 전체의 14일 갱신 토큰이 털린 상황이라 추가 손해가 없다.

**봉할 때 용도를 AAD 로 묶는다.** `access` · `refresh` · `session` 셋이 서로의 칸으로 옮겨 심어지지
않게 한다. 셋은 수명과 권한이 다르다.

**되묻는 창을 짝의 10분과 따로 60초로 둔다.** ① 의 10분은 사용자가 넥슨 화면에서 쓰는 시간이고
④ 는 리다이렉트를 받아 되묻는 시간이라 초 단위다. **이 설계의 유일한 대가가 봉한 원본이 DB 에 있는
창이므로, 짧게 두는 것이 그 대가를 갚는 수단이다.**

**기각 - 세션을 아직 만들지 않고 넥슨 토큰만 짝에 둔다.** 토큰 칸이 `nexon_sessions` 와 겹쳐 같은
모양이 두 자리에 생긴다. 가이드라인이 토큰 보관 자리를 늘리지 말라는 방향이기도 하다.

**기각 - 세션 행만 만들고 ④ 에서 값을 새로 뽑아 해시를 갈아 끼운다.** 원본이 아무 데도 저장되지
않아 **엄격히 더 안전하다.** 그러나 이기는 칸이 `DB 와 키가 함께 샌다` 하나뿐이고, 그 공격은 이미
`nexon_sessions` 전체의 14일 갱신 토큰을 내준다 - 추가로 내주는 것이 **진행 중인 세션 하나 ·
최대 60초**라 비교가 안 된다. `DB 만 샌다` 칸에서는 둘이 동등하다. 대가로 `session_hash` 가
변하는 칸이 되고 ④ 가 두 표를 건드려 상태 조합이 는다. **안전 차이가 측정 가능한 수준이 아니라
실수할 자리가 적은 쪽을 골랐다.**

**기각 - 커스텀 스킴에 1회용 인수증을 싣는다.** `redeem_key` 가 이미 그 열쇠라 인수증이 없어도
된다. 빼면 커스텀 스킴에 실리는 값이 0 이 되고 가로채기를 막는 논증 자체가 필요 없어진다.

**기각 - `state` 를 ④ 의 열쇠로 겸용해 값을 하나로 줄인다.** 이 설계에서는 `state` 가 앱을 안
지나므로 **기술적으로는 되고 칸도 줄지만**, `state` 는 **설계상 `access.log` 에 적히는 값**이다.
합치면 **로그 한 줄이 세션 발급 자격**이 되고, 나중에 로그를 어디로든 보내는 순간 그 자격이 함께
간다. 지금은 겹이 둘이고 합치면 `claimed_at` 의 1회용이 유일한 방어가 된다.

**받아들이는 손실 둘**(사용자 지정).

- **④ 의 응답이 유실되면 재로그인한다.** 서버는 세션을 발급하고 짝을 지웠는데 앱이 못 받은
  경우다. 그 세션은 아무도 안 드는 고아가 되고 결정 5 의 만료 청소가 14일 뒤 걷는다. 멱등하게
  만들려면 원본을 바로 비우지 않아야 하는데 그러면 노출 창이 한 시간대로 늘어 전제가 무너진다.
- **브라우저가 떠 있는 동안 앱이 죽으면 로그인이 유실된다.** `redeem_key` 를 앱이 메모리에만
  들어서다. ③ 은 서버에서 독립적으로 돌았으므로 세션이 이미 섰고, 그 고아는 결정 5 가 즉시
  치운다. 기기에 적어 막을 수 있지만 평문 저장이 하나 늘어 그쪽을 안 고른다.

### 결정 5. 1시간 간격 고리가 짝과 고아 세션을 치운다 (사용자 지정)

짝은 **10분** 보관하고 치우는 일은 **1시간 간격 고리**가 한다.

```sql
WITH dead AS (
  DELETE FROM nexon_login_attempts
   WHERE (claimed_at IS NULL     AND expires_at <= now())
      OR (claimed_at IS NOT NULL AND claimed_at <= now() - interval '10 minutes')
  RETURNING session_id
)
DELETE FROM nexon_sessions
 WHERE id IN (SELECT session_id FROM dead WHERE session_id IS NOT NULL);

DELETE FROM nexon_sessions WHERE refresh_expires_at <= now();
```

**한 문장으로 묶는 것이 요점이다.** 짝을 먼저 지우면 `session_id` 포인터가 사라져 고아 세션을
영구히 못 찾는다.

**살아남은 짝에 `session_id` 가 있으면 그것이 곧 고아다.** ④ 가 오면 짝이 지워지므로, ③ 까지
갔는데 남아 있는 짝은 ④ 가 안 온 것뿐이다. **추론이 아니라 기록이다.** 그 세션 행에는 유효한 넥슨
토큰(access 30분 · refresh 14일)이 들어 있어 빨리 없애야 한다.

**조건을 `created_at` 이 아니라 `claimed_at` 으로 쓴다.** `created_at < now() - 10분` 으로 쓰면
사용자가 넥슨 화면에서 늦게 동의한 짝을 **④ 를 기다리는 중에** 지울 수 있다 - `claimed_at` 이
`created_at + 10분` 까지 올 수 있다.

**만료 세션 청소를 함께 돌린다.** 갱신 토큰이 죽은 세션은 누구에게도 쓸모가 없으니 추론이 아니고,
결정 4 가 받아들인 유실 고아도 여기서 걷힌다.

**성공·실패를 적는 칸을 두지 않는다.** 보관이 10분이면 그 기록을 읽을 창이 없어 **안 읽는 값을
적는 일**이 된다. 실패율을 보려면 보관을 늘리고 그 칸을 함께 더해야 한다.

**벽시계가 아니라 간격인 이유.** 벽시계 새벽을 맞추려면 `오늘 이미 돌았나` 상태와 KST 변환이
필요한데(DB 는 UTC) 표가 작아서 그 복잡도를 살 이유가 없다. **인스턴스가 여럿일 때 한쪽에서만
돌아야 한다.**

**로그인 시작 경로가 인증 없이 열려 있어 이 결정이 필요하다.** `{ platform }` 만 보내면 누구나
짝을 만든다. nginx 의 `10r/s` 를 꽉 채우면 하루 86만 줄이다.

### 결정 6. 신원 확인과 토큰 갱신을 한 자리에 묶지 않는다

세션으로 사람을 가리는 일과 쓸 수 있는 액세스 토큰을 내는 일은 **다른 일이다.** 한 함수가 둘을
하면 넥슨 토큰을 안 쓰는 경로(드롭 가격 쓰기 등)가 **신원 확인만 하려는데 넥슨 갱신을 일으킨다.**

갱신 토큰은 회전하고 겹치면 하나만 이긴다(맥락의 실측). 그래서 불필요한 갱신은 **다른 갱신을
죽이는** 경합을 만들고, 진 쪽이 세션을 지우면 **멀쩡한 토큰을 방금 받았는데 사용자가 재로그인을
본다.**

- 신원 확인은 `session_hash` 로 행을 찾아 수명만 본다. **넥슨을 부르지 않는다.**
- 토큰을 내는 자리는 하나로 모으고, 그 안에서만 갱신한다.
- 갱신이 거절됐을 때 **세션 행을 지우는 판단을 자동으로 하지 않는다.** 겹친 갱신의 진 쪽이
  `OPENAPI00012` 를 받는 것과, 갱신 토큰이 정말 죽은 것을 구분해야 한다.

## 결정 — 프렌즈 조회

### 결정 7. 프렌즈 조회를 서버가 모아 SSE 로 흘린다 (사용자 지정)

앱이 **작업 목록 하나**를 보내고 서버가 그 작업들을 넥슨에 돌면서 결과를 이벤트로 흘린다.

```
앱 → 서버 SSE 1건  →  서버 → 넥슨 × 124  →  이벤트 124개
```

**앱은 넥슨 토큰을 아예 받지 않는다.** 가이드라인의 `서버에서만 관리하고 사용` 에서 **관리**는
결정 3·4 가 받고 **사용**을 이 결정이 받는다.

**1:1 중계가 아니라 모아 흘리는 것이 요점이다.** 한 건씩 중계하면 사용자 한 명의 조작이 우리
서버에 수백~수천 요청이 되지만, 모아 흘리면 **우리 서버로 가는 요청이 1건**이다. 그래서 nginx 의
`rate=10r/s burst=20` 에 안 닿는다 - 이 설계가 그 한도를 **지켜 주는** 쪽이다.

**범위는 프렌즈 6경로다.** 비프렌즈 12경로는 Open ID 가 안 열어 서버가 대신 부를 것이 없고,
개발자 API 키를 쓰므로 가이드라인 문장의 대상도 아니다. 앱이 계속 직접 부른다.

**앱이 끊으면 서버도 멈춘다.** 안 두면 사용자가 화면을 떠난 뒤에도 넥슨 호출 124건이 계속 나가고
그 비용은 보이지 않는다.

### 결정 8. 원본 줄을 그대로 내린다 (사용자 지정)

서버는 넥슨 응답의 줄을 **가공하지 않고** 흘린다. 장비 신분 매핑 · 비용 계산 · 특수 캐릭터 가리기는
앱에 남는다.

가공하면 응답이 훨씬 작아지지만 **게임 레퍼런스 수치(`src/data/`)가 서버로 넘어간다.** 그
데이터는 도메인 전문가 확인을 거쳐야 하는 축이라 이 변경에 끼우지 않는다.

**대가**: 응답 바이트가 넥슨 원본과 같다. 본문이 서버를 **두 번** 지난다(넥슨에서 들어와 앱으로
나간다). 가공이 없어 CPU 는 여유가 있고 파싱이 필요한 것은 **커서를 꺼내 다음 쪽을 부르는 것**
하나다.

### 결정 9. 작업 하나가 이벤트 하나다

이벤트 하나에 `(종류, 날짜)` 와 그 결과를 싣고 **성공·실패를 이벤트가 든다.**

앱이 **받은 작업만 기기 원장에 적으면** 실패한 날짜가 다음 회차에 자동으로 다시 온다. 응답 하나로
묶으면 날짜 하나의 실패가 전체를 실패시키거나 조용히 사라진다.

**기획은 앱에 남는다.** 기기 원장을 읽어 안 받아진 작업을 세는 일을 서버가 하게 하면 원장을 서버로
옮겨야 하고, **두 번째 방문이 0건이라 요청 자체가 안 나가는** 성질도 잃는다.

### 결정 10. 메모리를 동시 수에 묶는다. 모아 두지 않고, 앞질러 당기지 않는다

**모아 두지 않는다.** 한 사용자의 124페이지를 버퍼에 쌓아 끝에 보내면 동시 회차 수의 배수가 같은
시각에 힙에 있다. 받은 쪽에서 바로 이벤트로 내보내면 **동시에 연 소켓 수만큼만** 든다.

**앞질러 당기지 않는다.** 소켓 쓰기가 `false` 를 돌려주면 **그 바이트는 보내진 것이 아니라 쓰기
큐에 쌓인 것**이다. 넥슨은 쪽 하나(870KB)를 200ms 에 주고(≈4 MB/s) 앱은 0.3~2 MB/s 로 받으므로,
무시하고 계속 당기면 **차이가 전부 힙에 남는다.** 회차 총 바이트에 상한이 없으니 그 힙도 상한이
없다. 그래서 **배수가 빠질 때까지 기다린 뒤 다음 쪽을 당긴다.**

**둘 중 하나만 있으면 메모리가 안 묶인다.** 그래서 한 결정으로 둔다.

### 결정 11. 동시 회차에 전역 상한을 두고 넘으면 미룬다고 알린다

상한이 **둘**이다. 사용자당 팬아웃(동시에 여는 넥슨 소켓 수)과 **전역 동시 회차 수**다. 앞엣것만
두면 메모리가 사용자 수에 선형으로 자란다.

전역 상한을 넘은 요청은 **기다리게 두지 않고 미룬다고 알린다.** 기다리게 하면 그 연결도 메모리를
들고 서 있어 상한을 둔 이유가 없어진다. 앱은 그 이벤트를 받으면 이번 회차를 접고, 원장이 그대로
남아 다음에 다시 온다(결정 9 가 그 성질을 이미 든다).

**상한값을 표본이 아니라 예산에서 푼다.** 메모리가 `전역 동시 회차 × 사용자당 팬아웃 × 870KB` 다.
앱 박스 여유 ~640MB 중 **200MB** 를 이 버퍼에 주면 `동시 × 팬아웃 ≈ 235` 다.

| 사용자당 팬아웃 | 전역 동시 회차 |
|---|---|
| 5 | 47 |
| 10 | 23 |

**팬아웃을 키워도 소용이 없다.** 역압(결정 10)이 걸리면 넥슨에서 당기는 속도가 앱이 받아 가는
속도에 묶인다. 앱이 1 MB/s 로 받는데 소켓을 열 개 열어도 아홉 개는 멈춰 서 있다. 그래서 팬아웃은
작게 두고 전역 동시 수를 크게 두는 쪽이 **같은 메모리로 더 많은 사람을 받는다.**

**완화책이 우리 손에 있다.** 버스트가 푸시에서 오므로 예약 발송으로 흩뿌리면 피크가 낮아진다.

### 결정 12. 회차를 시간이나 바이트로 끊는다

유지 시간이 `총 바이트 ÷ 앱 다운링크`이고 둘 다 우리가 못 정한다. 50MB 를 받는 사용자가
300 KB/s 면 **3분**을 붙들고, 측정된 300초 창의 동시 수가 84명이다.

**끊어도 잃는 것이 없다.** 결정 9 가 작업 하나를 이벤트 하나로 두고 앱이 받은 것만 원장에 적으므로,
못 보낸 작업은 **적히지 않아 다음 회차에 다시 온다.** 재개 장치를 따로 만들 필요가 없다.

**커서에 안전핀을 둔다.** 무한 루프를 막는 상한이지 용량 예산이 아니다.

## 결정 — 전송과 배치

### 결정 13. 전송은 `react-native-sse` 로 하고 재연결을 끈다

RN 에 `EventSource` 가 없고 `fetch` 가 `whatwg-fetch` 폴리필이라 `response.body` 가 없다(확인
2026-10-12, `node_modules` 를 직접 열었다). 그래서 **XHR 의 증분 응답을 읽는 장치**가 유일한
길이다. `react-native-sse` 1.2.1 이 그것을 **순수 JS** 로 하고 헤더와 POST 본문을 받는다.

**재연결을 끈다.** 기본값이 5초 재연결인데 이 요청은 **한 번만 돌아야 하는 비싼 팬아웃**이다.
끊길 때마다 124건이 조용히 다시 도는 것은 사용자가 볼 수 없는 낭비다.

**기각 - 직접 구현한다.** 증분 응답을 자르고 이벤트를 모으는 코드는 40~50줄이라 못 할 일은 아니다.
다만 라이브러리를 선호하는 저장소 방침이고 줄 끝 처리와 종료 구분 같은 밟을 자리가 정리돼 있다.

**⚠️ 의존을 더하면 지문이 바뀔 수 있다.** 바뀌면 이 변경은 OTA 로 못 가고 **스토어 발행을 탄다.**

### 결정 14. nginx 에 그 경로의 자리를 따로 만든다

```nginx
proxy_buffering off;        # 기본값 on 이라 손대지 않으면 스트림이 안 흐른다
proxy_read_timeout <길게>;  # 지금 10s 라 10초에 잘린다
```

서버가 `X-Accel-Buffering: no` 를 함께 보낸다. **둘 중 하나만 두면 설정이 갈릴 때 조용히 버퍼링으로
돌아간다.** 같은 박스에 있어도 nginx 가 앞에 서는 한 기본값 `on` 이 먼저 막는다.

**속도 제한은 그대로 둔다.** 한 회차가 요청 1건이라 안 닿는다(결정 7).

### 결정 15. Always Free 인스턴스 둘에 나눈다. 유료 플랜으로 올리지 않는다 (사용자 지정)

```
앱 박스   nginx + 애플리케이션     공개 IP · 인증서가 여기 있다
DB 박스   Postgres                 사설망만
```

**가르는 이유가 용량보다 격리다.** `swap` 이 0 이라(실측) 메모리가 넘치는 순간 OOM-killer 가
피해자를 고르고, Postgres 가 애플리케이션보다 RSS 가 크면 **앱 버그가 DB 를 죽인다.** 가르면 그
경로가 없어진다.

| | 한 박스 | 가른 뒤 (앱 박스) |
|---|---|---|
| 기저 | ~438MB | ~308MB |
| 요청에 쓸 수 있는 것 | ~500MB | **~640MB** |

| 동시 회차 | 평균 쪽 25.6KB | 큰 쪽만 287KB | 꽉 찬 쪽 870KB |
|---|---|---|---|
| 4 | 1MB | 11MB | 35MB |
| **40** | **10MB** | **115MB** | **348MB** |

**가장 흔한 값이 10MB 이고 가능한 최악이 348MB 다.** 가른 뒤 여유 ~640MB 에서는 최악도 들어가고
한 박스였다면 아슬아슬했다. 그래서 가름이 격리뿐 아니라 **용량에서도 값을 한다.** 상한은 그래도
필요하지만(결정 11) **전형을 맞추기 위한 것이 아니라 꼬리를 막기 위한 것**이라 넉넉히 둘 수 있다.

**DB 박스는 과잉이다.** 기본 설정이 15GB 박스용이라 작게 내린다 - `shared_buffers` 128MB → 32MB ·
`effective_cache_size` 4GB → 256MB · `max_connections` 100 → 20.

**사설망으로 잇는다.** 같은 VCN 에 두면 DB 트래픽이 인터넷을 안 타고 요금도 안 붙는다. 5432 는
**Oracle 보안 목록과 ufw 양쪽**에 `10.0.0.0/24` 로 한정해 열어야 하고, 한쪽만 열면 조용히 막힌다.

**양쪽에 swapfile 1~2GB 를 둔다.** 둘 다 `swap` 이 0 이고 디스크가 38GB 여유다. 느려지지만 kill 은
안 당한다. Postgres 는 VACUUM 때 특히 그렇다.

**힙 상한을 건다.** 터져도 DB 를 안 죽이지만, 상한이 있으면 **OOM 이 아니라 힙 에러**라서 그 요청만
죽고 로그에 원인이 남는다.

**DB 가 네트워크 건너로 가므로 연결 실패가 새 고장 모양이다.** 연결 타임아웃을 두고, DB 박스가
재시작하는 동안 요청이 매달리지 않고 깨끗히 실패하게 한다.

**미니 PC 는 백업 받는 자리로 쓴다.** WireGuard 통로가 이미 서 있어 덤프를 집으로 당기면 오프사이트
백업이 된다.

## 대가

- **서버 가용성이 로그인 화면에 직결된다**(결정 3). 콜백이 302 를 못 내면 사용자가 브라우저에
  갇힌다.
- **브라우저에서 기다리는 시간이 생긴다.** 콜백이 넥슨 왕복 둘(교환 · `userinfo`)과 DB 쓰기를 하고
  나서야 302 를 낸다. **이 시간을 안 쟀다**(사용자 판단으로 무시하기로 했다).
- **베어러 값을 저장하는 자리가 최대 60초 생긴다**(결정 4).
- **콜백이 `users` 행을 앱이 확인하기 전에 만든다.** ④ 가 안 와도 그 행은 남는다. 동의가 끝난
  시점이라 **그 사람은 가입자이고 행은 맞다** - `nexon_uid` 가 `UNIQUE` 라 다시 로그인하면 같은
  행을 받는다.
- **긴 요청이 생긴다**(결정 7). nginx · 애플리케이션 · 앱 세 층의 타임아웃을 함께 봐야 하고, 한
  층만 짧으면 그 층에서 잘린다.
- **원본 본문이 서버를 지나 나간다**(결정 8). 집 업링크(2.17 MB/s)에서는 이것이 벽이고
  Oracle(60 MB/s)에서는 아니다. 그래서 **옮기는 것을 전제로 한다.**
- **앱이 쓰는 라이브러리가 하나 는다**(결정 13). 순수 JS 이지만 지문 확인이 필요하다.

## 이 문서 밖에 남는 것

[[ADR-345]] 에 있던 **기기 SQLite 쪽 소견**은 서버와 무관해 여기로 안 가져온다. 집이 필요하다.

- 기기 표 일곱의 복합 PK(`boss_profit_records` · `boss_party_settings` ·
  `boss_party_period_overrides` · `boss_profit_period_checks` · `character_accounts` ·
  `enhancement_history_checks` · `mvp_grade_history`). 옮기면 조회가 전체 스캔이 되므로 인덱스를
  함께 세워야 한다.
- 가계부 두 표의 대리키가 `시각(36진) + Math.random()` 인 것. 근거였던 `Hermes 에
  crypto.randomUUID 가 없다` 는 전제가 사라졌다.
- 자연키 한 칸으로 선 표 셋(`character_profiles` · `character_world_leaps` ·
  `enhancement_history`). 규칙의 예외로 둘지가 결정이다.
- 기기 DB 에 인덱스가 하나뿐인 것. 복합 PK 가 곧 인덱스였기 때문이다.

## 열린 질문

- **교환에 `redirect_uri` 를 보내나.** 스펙의 파라미터 표에 **그 칸이 없다**(넷뿐). https 로
  옮기면 값을 보낼지 뺄지 정해야 한다. 넥슨이 안 보는 것이 사실이면 커스텀 스킴으로 시작한
  로그인의 `code` 를 https 짝으로 교환할 수 있다 - 결정 3 의 `state` 확인이 막지만 보내는 쪽은
  맞춰 두는 것이 맞다.
- **콜백의 왕복이 얼마인가.** `oauth2/token` 과 `userinfo` 를 안 쟀다. 길면 `userinfo` 를 ④ 로
  미룰 수 있지만 그러면 `users` 행을 ④ 에서 만들어 두 자리의 일이 섞인다.
- **되묻는 창 60초가 맞나.** 리다이렉트를 받아 되묻는 데 실제로 얼마가 걸리는지 실기기에서 재야
  한다.
- **두 상한의 값**(결정 11). 동시에 열린 앱 중 몇이 조회를 시작하는지를 몰라 어느 조합을 고를지
  못 정했다. **같은 로그로는 못 잰다** - 지금 조회가 우리 서버를 안 거치기 때문이고, 넣은 뒤에
  보인다.
- **회차를 무엇으로 끊나**(결정 12 의 기준과 값). 시간이면 유지 시간이 고르고 바이트면 메모리가
  고르다. 작으면 무거운 사용자가 여러 회차에 걸쳐 받고 그 사이 원장이 부분만 차 있다.
- **무거운 계정의 실제 분포.** 남의 계정은 재 볼 수 없다. 서버가 회차당 바이트를 기록해 보는 것이
  유일한 길이고 결정 11·12 의 값이 그 분포에 걸린다.
- **기기 메모리.** RN 의 XHR 이 증분 응답을 문자열에 **누적**한다. 앱이 스트림 전체를 JS 문자열로
  들게 되므로 결정 12 의 바이트 상한이 서버뿐 아니라 **기기에서도 하중을 받는다.**
- **창 채우기도 같은 통로로 가나.** 프렌즈 6경로에 들어 있고 첫 진입 84건이 같은 성질의
  팬아웃이다. 쪽 크기를 재려다 400 을 받았고 **에러 본문을 안 찍어** 원인을 못 봤다.
- **지문이 바뀌나**(결정 13). 바뀌면 스토어 발행을 탄다.
- **같은 플랫폼의 두 기기에서 로그인하면 먼저 기기가 죽나.** 저장된 갱신 토큰이 **저장된 만료보다
  먼저 죽어 있었다**(2026-10-12). 같은 `client_id` 로 그날 새 로그인을 한 번 돌린 것이 유일한
  설명인데 직접 재지는 않았다.
- **갱신이 갱신 토큰의 수명을 늘리나.** 넥슨은 갱신마다 14일을 돌려준다. 실제로 늘어나는지는 안
  쟀고, 안 늘어나면 서버가 죽은 토큰을 최대 14일 살아 있다고 믿어 결정 5 의 만료 청소도 그만큼
  늦게 걷는다.
- **앱 무결성 증명을 요구하나.** 로그인 시작 경로가 인증 없이 열려 있는 것은 그대로다. ④ 에
  Play Integrity · App Attest 증명을 요구하면 악성 앱은 우리 패키지 서명으로 증명을 못 만든다.
  넥슨에 의존하지 않는 대신 양 플랫폼의 증명 검증을 서버에 들여야 한다. **지금 단계에서 꺼낼
  카드는 아니다.**

## 순서 제약

**기존 넥슨 애플리케이션 둘이 검수 중이라 수정할 수 없다**(사용자 확인 2026-10-14). https URI 를
그 둘에 등록하는 것이 결정 3 의 선행 조건이다. 시험은 새로 만든 애플리케이션의 자격으로 하고,
서버에 넣을 때 기존 자격을 덮지 않는 별도 이름으로 둔다.

**앱에서 넥슨 로그인을 켜기 전에 이 문서가 전부 들어가야 한다.** 지금 실제 위반은 0 이다 - 로그인이
꺼져 있어 이 경로를 타는 사용자가 없다.
