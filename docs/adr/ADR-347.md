### 넥슨 가이드라인이 로그인 모양을 정한다

개발 가이드(`openapi.nexon.com/ko/open-id/development-guide`)의 두 탭에 셋이 적혀 있다.

- **안전한 토큰 관리**: `유저의 인가 코드를 사용해 발급 받은 Access Token은 반드시 서버에서만
  관리하고 사용합니다.`
- **State 파라미터 사용**: `State 파라미터는 … 이후 Redirect URI에서 올바른 요청인지 확인하는
  데에 사용됩니다.` · `State 값은 제3자가 접근할 수 없는 안전한 곳에 보관해야 합니다.` ·
  `한번 인증에 사용된 State 값은 재사용 불가능하도록 구성합니다.`
- **인가 코드 발급 요청**: `redirect_uri` 예시가 `http://test.io/login` 이고 응답 예시가
  `302 Found Location: http://test.io/login?code=…&state=…` 다. **이 문서는 서버가 리다이렉트를
  받는 것을 전제로 쓰여 있고** 커스텀 스킴은 나오지 않는다.

**셋이 같은 한 점을 가리킨다.** 토큰을 서버만 쓰려면 교환을 서버가 해야 하고, state 를 Redirect
URI 에서 확인해야 하므로 그 주소가 서버여야 한다. `redirect_uri` 를 서버의 https 주소로 두는 것은
예외적 선택이 아니라 **스펙의 기본형**이다.

### 넥슨 스펙에서 읽은 것

| | |
|---|---|
| `authorize` 파라미터 | `response_type` · `client_id` · `redirect_uri` · `scope`(필수) · `state`(옵션·권장). **PKCE 가 없다** |
| 교환 파라미터 | `grant_type` · `client_id` · `client_secret` · `code` **넷. `redirect_uri` 가 표에 없다** |
| 토큰 수명 | access **30분** · refresh **14일**. 갱신 토큰이 만료되면 인가 코드 재발급 |
| 갱신 | `client_secret` 을 요구한다 |
| 식별자 | `GET /oauth2/userinfo` 가 `{ result: { uid, scope } }` |

### 실측

| 잰 것 | 결과 |
|---|---|
| 넥슨이 기밀 클라이언트만 받나 | **그렇다**(10-12). 비밀을 빼면 `OPENAPI00004` |
| 넥슨이 `code_verifier` 를 검사하나 | **아니다**(10-14). `code_challenge = S256(A)` 를 실어 로그인하고 교환에 `B` 를 보냈는데 `200` 에 토큰이 왔다 |
| https redirect URI 를 등록받나 | **받는다**(10-14). redirect URI 칸이 **5개**라 검수 중인 값을 안 건드리고 새 애플리케이션에 등록해 쟀다 |
| 넥슨이 그 주소로 리다이렉트하나 | **한다**(10-14). `GET /v1/auth/nexon/callback?code=…&state=…` 가 nginx 에 닿았다(Referer `openid.nexon.com`) |
| 갱신 토큰이 회전하나 | **회전하고 옛것이 즉시 죽는다**(10-12). 같은 토큰으로 동시에 둘 보내면 **하나만 이긴다**(A 400 / B 200) |
| `uid` 가 플랫폼을 가로질러 같나 | **같다**(10-12). pairwise 가 아니라 계정 자기 식별자다 |
| 서버의 302 가 인증 세션을 거쳐 앱으로 돌아오나 | **돌아온다**(10-14 · 아이폰 실기기 · Pixel8 에뮬레이터). nginx `return 302` 셋으로 넥슨 화면의 단추 클릭부터 콜백까지 사슬을 흉내 냈다. iOS 커스텀 스킴은 단추 클릭 2.5초 · 클릭 없이 1.2초, Android 는 커스텀 스킴 0.5초 · **검증된 App Link** 6.2초 · `intent://` 폴백 6.2초(둘 다 단추 클릭 포함)에 `receipt` 가 그대로 실려 돌아왔다. Android 는 `assetlinks.json` 을 올린 뒤 `pm verify-app-links` 로 `verified` 를 확인하고 쟀다 |
| `expo/fetch` 가 gzip 응답을 증분으로 주나 | **준다**(10-14 · 두 플랫폼). 서버가 0.5초마다 `Z_SYNC_FLUSH` 한 50KB 줄 열 개가 같은 간격으로 reader 에 닿았다. iOS 는 `content-encoding: gzip` 헤더를 보이면서 풀어서 주고, Android(OkHttp) 는 헤더를 지우고 풀어서 준다. Oracle nginx 와 WireGuard 를 거쳐도 0.4초 간격이 그대로다 |

**PKCE 는 두 갈래가 다 막혔다.** 비밀을 대신하지도 못하고 `code` 의 자물쇠도 못 된다. 그래서
`code` 를 authorize 요청에 묶는 길은 **서버가 콜백을 직접 받는 것** 하나뿐이고, 그 사실이 로그인
설계를 정했다.

**인가 코드가 nginx `access.log` 에 두 줄 남는다**(실측). 기본 `combined` 형식이 `$request` 를
쿼리까지 찍고, 브라우저가 이어 요청하는 `/favicon.ico` 의 `Referer` 에 한 번 더 들어간다.

### 커스텀 스킴 콜백이 안드로이드에서 막히지 않았다

redirect URI 가 커스텀 스킴이고 넥슨이 안드로이드 등록에서 서명 해시를 안 받아, 같은 스킴을 선언한
다른 앱이 콜백의 `code` 와 `state` 를 받을 수 있었다. 앱과 서버만 아는 값을 하나 더 두는 것으로
막으려 했지만 **그 자리가 비어 있었다** - 로그인 시작 경로에 인증이 없어 악성 앱이 **자기 짝을
새로 만들어** 가로챈 `code` 를 내면 통과한다. `code` 와 `state` 를 묶는 끈이 아무 데도 없기
때문이다(넥슨 교환 요청에 `state` 가 없다).

**iOS 는 해당하지 않았다.** 앱이 `openAuthSessionAsync` 로 열고 iOS 에서는 그것이
`ASWebAuthenticationSession` 이라 콜백이 그 세션에만 돌아온다 - 스킴 등록표를 안 거친다.
안드로이드는 Custom Tabs 뒤 딥링크가 보통의 인텐트 해석을 탄다.

콜백을 서버가 받으면 이 구멍은 닫힌다. 그런데 같은 날 검토가 그 자리에서 **다른 구멍**을 찾았다.
다음 절이다.

### 콜백을 서버로 옮기면 로그인 CSRF 가 열린다

로그인 시작 경로 ① 은 인증이 없고, ④ 의 열쇠인 `redeem_key` 는 ① 을 부른 쪽이 든다. 그러면
① 을 부른 사람과 넥슨에 로그인한 사람이 같다는 보장이 어디에도 없다.

```
공격자 앱 ──► ① login                       짝 A · redeem_key R 을 받는다
공격자    ──► 피해자에게 authorizeUrl 을 보낸다  state 는 짝 A 의 것
피해자    ──► 진짜 넥슨 화면에서 로그인 · 동의    동의 대상도 메이플 루틴이라 의심할 자리가 없다
넥슨      ──► ③ /callback?code&state          서버가 짝 A 를 집고 피해자의 토큰을 교환한다
서버          피해자 세션을 짝 A 에 봉한다
공격자 앱 ──► ④ { R } 를 1초마다               피해자의 세션을 받는다
```

**커스텀 스킴 시절에는 안 됐던 공격이다.** 그때는 `code` 가 넥슨에서 **피해자 기기**로 돌아와
공격자 손에 닿지 않았다. 콜백을 서버로 옮기면서 `code` 가 짝으로 가게 됐고, 짝은 공격자가 만든
것이다. 처음 설계가 "그 구멍이 생길 수 없는 모양" 이라고 적은 것은 가로채기에만 참이었다.

**두 구멍은 각각 열쇠 하나씩만 가질 수 있는 공격자다.** 가로채기 공격자는 돌아오는 길을 먹지만
① 의 열쇠는 자기 짝의 것뿐이고, CSRF 공격자는 ① 의 열쇠를 들지만 돌아오는 길은 피해자
기기로 간다. 결정 3 이 ④ 에 둘 다를 요구한다.

6초지만, 총 바이트에 상한이 없으므로 **유지 시간에도 상한이 없다.**

**작은 쪽에는 역압이 안 걸린다.** 쪽 중앙값이 0.1KB 다. 그런 쪽은 소켓이 차지 않아 왕복 30ms 로

### 전제로만 두는 것

`PK 는 항상 uuid 한 칸이고 자연키는 단일 UNIQUE` 는 이 저장소의 규칙이다. 이 문서의 결정이 아니라
지켜야 하는 것이고, DB 를 처음부터 세우므로 **이관 없이 그냥 그 모양으로 만든다.**

### 결정 1. 표를 처음부터 이 모양으로 세운다

이어 갈 데이터가 없으므로 마이그레이션이 아니라 초기 스키마다.

```
users
  id              uuid        PK   서버가 만든다
```

```sql

```

`text` 로 두면 틀려도 **에러가 아니라 나중에 조용히 실패한다** - `platform` 이 틀리면 로그인은 되고
**14일 뒤 갱신만** 실패하고, `kind` 가 틀리면 앱이 그 분류를 안 가져가 **공지가 조용히 안 보인다.**

`CHECK` 가 아니라 ENUM 인 근거(PG 16 실측 2026-10-12): 값을 더하는 것이 `ALTER TYPE … ADD VALUE`
**한 문장**이고 표를 안 훑는다. `RENAME VALUE` 가 **저장된 행도 따라온다.** 표 둘이 `platform` 을
공유하므로 타입 하나가 진실인 쪽이 실익이 있다. `DROP VALUE` 가 없는 것이 대가지만 이 두 칸은
값이 빠진 적이 없다.

**운영 규칙 하나.** 값을 더하는 마이그레이션은 **그 값으로 쓰지 않는다.** PG 16 은 같은 트랜잭션에서
더한 값을 쓰면 `unsafe use of new value` 로 거부하고 마이그레이션 도구가 트랜잭션으로 감싼다.
백필이 필요하면 파일을 둘로 가른다.

**봉한 값은 한 칸이다.** `version`(1바이트) · `iv`(12바이트) · `tag`(16바이트) · 암호문을 **한
덩이로 이어 붙인다.** 앞 셋은 길이가 고정이라 읽을 때 자르면 되고, 넷은 늘 함께 쓰이고 함께 읽히며
**따로 조회하거나 인덱스를 걸 일이 없다.** 칸을 가르는 것은 의식이다.

**version 이 키를 고른다.** 환경변수는 `TOKEN_ENC_KEY_V1` 이고 키를 바꿀 때 `TOKEN_ENC_KEY_V2`
를 더한다. 새 봉인은 가장 높은 버전으로 하고 읽기는 첫 바이트가 말하는 키로 한다. 이 바이트가
없으면 키를 바꾸는 유일한 길이 전원 재로그인이다. 초기 스키마라 지금 넣는 것이 공짜다.

**`nexon_sessions.user_id` 는 NOT NULL 이다.** ③ 이 `users` 행을 만들고 나서 세션을 만든다.
사용자 없는 세션을 만드는 경로가 없는데 NULL 을 허용하면 그런 경로가 있는 것처럼 읽힌다.

## 결정 — 로그인

### 결정 3. 콜백을 서버가 받고, 돌아오는 길에 1회용 인수증을 싣는다 (사용자 지정)

`redirect_uri` 는 `https://mapleroutine.store/v1/auth/nexon/callback` 다.

```
① 앱 ──► POST /v1/auth/nexon/login { platform }
         state · redeem_key 를 만들어 짝에 둔다 (expires_at = +10분)
    ◄──  authorizeUrl · redeem_key          state 를 앱에 주지 않는다

② 앱 ──► 인증 세션으로 authorizeUrl 을 연다
   사용자  넥슨에서 로그인 · 동의

③ 넥슨 ──► GET /v1/auth/nexon/callback?code=&state=
         state 로 짝을 집는다 · 교환 · userinfo · users · nexon_sessions
         receipt 를 새로 뽑아 sha256 을 짝에 적는다 · 세션 원본을 봉한다 · sealed_at (결정 4)
    ◄──  iOS      302 com.mapleroutine.app://oauth/callback?receipt=…
         Android  302 https://mapleroutine.store/app/oauth/return?receipt=…   검증된 App Link

④ 앱 ──► POST /v1/auth/nexon/session { redeem_key, receipt }
    ◄──  session
```

**열쇠가 둘이다.** `redeem_key` 는 이 짝을 내가 시작했다는 증명이고 ① 의 응답으로 **https 로만**
왔다. `receipt` 는 넥슨에 로그인한 그 기기가 나라는 증명이고 ③ 이 만들어 **돌아오는 길로만**
보낸다. 맥락의 두 구멍은 각각 한쪽 열쇠만 가질 수 있는 공격자다. 안드로이드 가로채기는 돌아오는
길을 먹어도 ① 을 자기가 다시 부르면 `redeem_key` 가 다른 짝의 것이고, 로그인 CSRF 는 ① 의
열쇠를 들고 있어도 `receipt` 가 피해자 기기로 갔다. ④ 가 둘 다 요구하면 둘 다 막힌다.

**처음 설계는 커스텀 스킴에 값을 안 실었다.** 안드로이드에서 다른 앱이 신호를 먹어도 얻을 것이
없게 하려는 것이었고, 그 성질은 CSRF 앞에서 값을 치르지 못했다. 신호를 놓쳐도 된다는 편의도
잃는다. 돌아오는 길을 놓치면 `receipt` 가 없어 로그인이 유실되고 사용자가 다시 누른다. 결정 4 가
받아들인 손실과 같은 종류다.

**iOS 는 커스텀 스킴에 실어도 안전하다.** `openAuthSessionAsync` 가 iOS 에서
`ASWebAuthenticationSession` 이라 콜백이 그 세션을 연 앱에만 돌아온다. 스킴 등록표를 안 거친다.

**Android 는 `/app/oauth/return` 을 `autoVerify` App Link 로 건다.**
`https://mapleroutine.store/.well-known/assetlinks.json` 에 릴리스·디버그 서명 해시 둘을 적고,
OS 가 서명을 확인한 앱만 그 주소를 연다. 커스텀 스킴은 서명을 안 보지만 App Link 는 본다. 맥락의
가로채기가 안드로이드에서만 있었던 이유를 그대로 닫는다.

**검증이 안 된 기기의 폴백.** App Link 검증은 기기마다 실패할 수 있다. 그러면 브라우저가 그
주소를 서버에 요청한다. 서버는 `receipt` 를 화면에 적지 않고
`intent://oauth/callback#Intent;scheme=com.mapleroutine.app;package=com.mapleroutine.app;end`
단추 하나를 낸다. 패키지 이름을 명시한 인텐트는 그 이름의 앱 하나에만 가고, 한 기기에 같은 이름의
앱은 둘일 수 없다. 이 폴백에 닿은 횟수를 로그로 센다. 자주 닿으면 `assetlinks.json` 이 틀린 것이다.

**세 길 다 실기기에서 돌아왔다**(맥락의 실측 표). 돌아오는 길 자체는 더 잴 것이 없고, 남은 것은 넥슨 화면을
끼운 전체 사슬이다.

**`state` 를 앱에 주지 않는다.** 앱이 확인할 일이 없고(③ 에서 서버가 한다) 가이드라인의
`제3자가 접근할 수 없는 안전한 곳에 보관` 도 그래야 맞다.

**`claimed_at` 이 state 재사용을 막는다.** ③ 이 한 문장으로 집는다.

```sql
UPDATE nexon_login_attempts SET claimed_at = now()
 WHERE state = $1 AND claimed_at IS NULL AND expires_at > now()
RETURNING id, platform
```

0줄이면 거절한다. 한 문장이라 경합이 없고 넥슨 왕복 동안 트랜잭션을 붙들지 않는다. **없으면
state 를 아는 쪽이 자기 `code` 로 짝을 덮어쓸 수 있다** - state 는 리다이렉트 URL 에 실려
브라우저와 `access.log` 를 지나므로 **비밀이 아니고**, 그러면 우리 앱이 남의 계정으로 로그인된다.
가이드라인의 `한번 인증에 사용된 State 값은 재사용 불가능하도록 구성합니다` 가 이 칸이다.

**③ 은 무슨 일이 있어도 302 만 낸다**(사용자 지정). 교환 실패 · DB 실패 · 예외를 전부 감싼다.
안 그러면 사용자가 브라우저의 에러 화면에 갇히고 앱으로 안 돌아온다. **서버 가용성이 로그인 화면에
직결되는 것**이 이 설계에서 가장 큰 대가다. 교환이나 `userinfo` 가 실패하면 **짝 행을 지우고** 302
를 낸다. 실패를 적는 칸이 없고, 실패한 짝에 봉한 것이 남을 일도 없다.

**④ 의 답이 셋이다.** 행이 있고 `claimed_at` 이 없으면 사용자가 창을 닫은 것이다. `claimed_at` 은
있고 `sealed_at` 이 없으면 ③ 이 넥슨 왕복 중이라 앱이 1초 뒤 다시 묻는다. 행이 없으면
만료·실패·이미 받음이라 다시 로그인이고 사용자 문구는 하나다. 처음 설계는 `claimed_at` 과
`session_sealed` 둘로 취소·실패·만료를 갈랐는데 ③ 진행 중이 실패로 읽혔다.

**교환에 `redirect_uri` 를 보낸다.** 스펙의 파라미터 표에는 없지만 RFC 6749 4.1.3 절이 authorize
에 넣었으면 교환에도 필수라 한다. 넥슨이 안 보면 해가 없고 보면 필요하다.

**콜백 하나를 두 플랫폼이 공유한다.** 어느 자격 쌍으로 교환할지는 짝의 `platform` 이 말한다. 넥슨
애플리케이션이 둘이어도 돌아올 주소는 하나다.

**콜백 경로에는 App Link 를 걸지 않는다.** 걸면 앱이 설치된 기기에서는 OS 가 그 주소를 앱으로
보내고 안 설치된 기기에서는 브라우저가 서버로 보내 **같은 주소가 두 가지로 동작한다.** 서버가 늘
콜백을 받는 것이 짝을 못박는 전제라 이 경로는 브라우저로 두고 결정적으로 만든다. 콜백은 늘
서버가 받고, 돌아오는 길은 늘 앱이 받는다. 두 가지로 동작하는 일은 돌아오는 길에서만 일어나고
거기서는 그것이 의도다.

**그 경로의 로그 형식을 따로 둔다.** 기본 `combined` 가 인가 코드를 두 줄에 남긴다.
`/app/oauth/return` 도 같은 형식이다. `receipt` 가 쿼리에 실린다.

**경로 이름은 명사로 둔다.**

```
POST   /v1/auth/nexon/login      ①  로그인을 시작한다
GET    /v1/auth/nexon/callback   ③  넥슨이 부른다
GET    /app/oauth/return         ③  안드로이드가 돌아오는 길. 앱이 집고, 못 집으면 폴백 페이지
POST   /v1/auth/nexon/session    ④  redeem_key · receipt 로 세션을 받는다
DELETE /v1/auth/nexon/session        로그아웃
```

`login` 인 것은 앱의 저장 형식이 `{ login, apiKeys }` 라 **그 말이 곧 넥슨 OAuth** 이기 때문이다.
**수단은 경로의 둘째 칸에서 가른다** - 지금 API 키 로그인에는 엔드포인트가 없지만, `/v1/auth/login`
처럼 수단을 안 적으면 나중에 키 쪽이 들어올 자리가 없어 `?method=` 같은 것이 붙는다.

### 결정 4. 세션 원본을 짝에 봉해 두고 봉한 시각부터 60초 안에 꺼내 간다 (사용자 지정)

③ 과 ④ 가 **서로 다른 요청**이라 그 사이에 서버가 세션을 들고 있어야 한다. `nexon_sessions` 는
해시만 두므로 꺼내 줄 수 없다.

```
③  세션 값 S 를 뽑는다 → nexon_sessions 행 (session_hash = sha256(S))
                       → 짝에 봉한 S · session_id · receipt_hash · sealed_at = now()

④  DELETE FROM nexon_login_attempts
     WHERE redeem_hash = sha256($1) AND receipt_hash = sha256($2)
       AND session_sealed IS NOT NULL
       AND sealed_at > now() - interval '60 seconds'
    RETURNING session_sealed
    → 풀어서 S 를 앱에 준다
```

**창의 기준이 `claimed_at` 이 아니라 `sealed_at` 이다.** `claimed_at` 은 ③ 의 머리에서 찍히고
봉하는 것은 넥슨 왕복 둘과 DB 쓰기 뒤다. 그 왕복을 안 쟀으니(열린 질문) `claimed_at` 기준이면
창이 얼마나 줄어드는지 모른다.

**`redeem_key` 와 `receipt` 를 해시로 둔다.** 평문으로 두면 **DB 유출만으로 ④ 를 재생할 수 있다**
- 키가 없어도 된다. `session_hash` 를 해시로 둔 이유가 그대로 여기 걸린다. 해시로 두면 DB
유출만으로는 아무것도 못 한다 - 해시는 제시할 수 없고 봉한 세션은 못 푼다.

**봉하는 이유.** 평문으로 두면 DB 유출만으로 그 세션을 읽는다. 봉하면 키가 함께 새야 하고, 키가
샜다면 이미 `nexon_sessions` 전체의 14일 갱신 토큰이 털린 상황이라 추가 손해가 없다.

**봉할 때 용도를 AAD 로 묶는다.** `access` · `refresh` · `session` 셋이 서로의 칸으로 옮겨 심어지지
않게 한다. 셋은 수명과 권한이 다르다.

**되묻는 창을 짝의 10분과 따로 60초로 둔다.** ① 의 10분은 사용자가 넥슨 화면에서 쓰는 시간이고
④ 는 리다이렉트를 받아 되묻는 시간이라 초 단위다. 다만 **봉한 원본이 DB 에 있는 시간은 60초가
아니다.** 창이 닫혀도 행은 결정 5 의 고리가 걷을 때까지 남는다. 처음 설계는 고리가 1시간이라 그
시간이 최악 70분이었고 대가 절에 60초라고 적어 틀렸다. 지금은 고리가 1분이고 봉한 짝 보관이
2분이라 **최악 3분**이다.

**기각 - 세션을 아직 만들지 않고 넥슨 토큰만 짝에 둔다.** 토큰 칸이 `nexon_sessions` 와 겹쳐 같은
모양이 두 자리에 생긴다. 가이드라인이 토큰 보관 자리를 늘리지 말라는 방향이기도 하다.

**기각 - 세션 행만 만들고 ④ 에서 값을 새로 뽑아 해시를 갈아 끼운다.** 원본이 아무 데도 저장되지
않아 **엄격히 더 안전하다.** 그러나 이기는 칸이 `DB 와 키가 함께 샌다` 하나뿐이고, 그 공격은 이미
`nexon_sessions` 전체의 14일 갱신 토큰을 내준다 - 추가로 내주는 것이 **진행 중인 세션 하나 ·
최대 3분**이라 비교가 안 된다. `DB 만 샌다` 칸에서는 둘이 동등하다. 대가로 `session_hash` 가
변하는 칸이 되고 ④ 가 두 표를 건드려 상태 조합이 는다. **안전 차이가 측정 가능한 수준이 아니라
실수할 자리가 적은 쪽을 골랐다.**

**기각을 거둔다 - 돌아오는 길에 1회용 인수증을 싣는다.** 처음 설계는 `redeem_key` 가 이미 열쇠라
인수증이 없어도 된다며 기각했다. 로그인 CSRF 가 그 전제를 깼다. `redeem_key` 는 ① 을 부른 쪽의
것이지 로그인한 사람의 것이 아니다. 그래서 결정 3 이 인수증을 다시 싣는다. 다만 안드로이드는
커스텀 스킴이 아니라 App Link 로 싣는다.

**기각 - `state` 를 ④ 의 열쇠로 겸용해 값을 하나로 줄인다.** 이 설계에서는 `state` 가 앱을 안
지나므로 **기술적으로는 되고 칸도 줄지만**, `state` 는 **설계상 `access.log` 에 적히는 값**이다.
합치면 **로그 한 줄이 세션 발급 자격**이 되고, 나중에 로그를 어디로든 보내는 순간 그 자격이 함께
간다. 지금은 겹이 둘이고 합치면 `claimed_at` 의 1회용이 유일한 방어가 된다.

**받아들이는 손실 둘**(사용자 지정).

- **④ 의 응답이 유실되면 재로그인한다.** 서버는 세션을 발급하고 짝을 지웠는데 앱이 못 받은
  경우다. 그 세션은 아무도 안 드는 고아가 되고 결정 5 의 만료 청소가 14일 뒤 걷는다. 멱등하게
  만들려면 원본을 바로 비우지 않아야 하는데 그러면 노출 창이 한 시간대로 늘어 전제가 무너진다.
- **브라우저가 떠 있는 동안 앱이 죽으면 로그인이 유실된다.** `redeem_key` 를 앱이 메모리에만
  들어서다. ③ 은 서버에서 독립적으로 돌았으므로 세션이 이미 섰고, 그 고아는 결정 5 가 2분 뒤
  치운다. 기기에 적어 막을 수 있지만 평문 저장이 하나 늘어 그쪽을 안 고른다.

### 결정 5. 1분 간격 고리가 짝과 고아 세션을 치운다 (사용자 지정)

안 집힌 짝은 **10분**, 봉한 짝은 **2분** 보관하고 치우는 일은 **1분 간격 고리**가 한다.

```sql
WITH dead AS (
  DELETE FROM nexon_login_attempts
   WHERE (claimed_at IS NULL AND expires_at <= now())
      OR (sealed_at IS NOT NULL AND sealed_at <= now() - interval '2 minutes')
      OR (claimed_at IS NOT NULL AND sealed_at IS NULL
          AND claimed_at <= now() - interval '2 minutes')
  RETURNING session_id
)
DELETE FROM nexon_sessions
 WHERE id IN (SELECT session_id FROM dead WHERE session_id IS NOT NULL);

DELETE FROM nexon_sessions WHERE refresh_expires_at <= now();
```

**한 문장으로 묶는 것이 요점이다.** 짝을 먼저 지우면 `session_id` 포인터가 사라져 고아 세션을
영구히 못 찾는다.

**살아남은 짝에 `session_id` 가 있으면 그것이 곧 고아다.** ④ 가 오면 짝이 지워지므로, ③ 까지
갔는데 남아 있는 짝은 ④ 가 안 온 것뿐이다. **추론이 아니라 기록이다.** 그 세션 행에는 유효한 넥슨
토큰(access 30분 · refresh 14일)이 들어 있어 빨리 없애야 한다.

**셋째 조건이 ③ 이 도중에 죽은 짝을 걷는다.** ③ 이 `claimed_at` 을 찍고 넥슨 왕복 중에 프로세스가
죽으면 `sealed_at` 없는 짝이 남는다. 처음 설계에는 이 행을 치우는 문장이 없었다. 세션이 안 달려
있어 고아는 아니지만 `state` 가 영원히 집힌 채 남는다.

**간격이 1분인 이유.** 봉한 원본이 DB 에 있는 시간은 되묻는 창이 아니라 **고리가 올 때까지**다.
1시간이면 최악 70분이고 1분이면 최악 3분이다. 표가 작아 1분마다 도는 비용이 없다.

**조건을 `created_at` 으로 쓰지 않는다.** `created_at < now() - 10분` 으로 쓰면 사용자가 넥슨
화면에서 늦게 동의한 짝을 **④ 를 기다리는 중에** 지울 수 있다 - `sealed_at` 이 `created_at + 10분`
뒤에 올 수 있다.

**만료 세션 청소를 함께 돌린다.** 갱신 토큰이 죽은 세션은 누구에게도 쓸모가 없으니 추론이 아니고,
결정 4 가 받아들인 유실 고아도 여기서 걷힌다.

**성공·실패를 적는 칸을 두지 않는다.** 보관이 2분이면 그 기록을 읽을 창이 없어 **안 읽는 값을
적는 일**이 된다. 실패율을 보려면 보관을 늘리고 그 칸을 함께 더해야 한다.

**벽시계가 아니라 간격인 이유.** 벽시계 새벽을 맞추려면 `오늘 이미 돌았나` 상태와 KST 변환이
필요한데(DB 는 UTC) 표가 작아서 그 복잡도를 살 이유가 없다. 앱 박스가 하나(결정 15)이고, 이
문장들은 겹쳐 돌아도 무해하다.

**로그인 시작 경로가 인증 없이 열려 있어 이 결정이 필요하다.** `{ platform }` 만 보내면 누구나
짝을 만든다. nginx 의 `10r/s` 를 꽉 채우면 하루 86만 줄이다.

### 결정 6. 토큰을 내는 자리는 세션별 single-flight 이고, 거절되면 세션을 지운다

세션으로 사람을 가리는 일과 쓸 수 있는 액세스 토큰을 내는 일은 **다른 일이다.** 한 함수가 둘을
하면 넥슨 토큰을 안 쓰는 경로(드롭 가격 쓰기 등)가 **신원 확인만 하려는데 넥슨 갱신을 일으킨다.**

- 신원 확인은 `session_hash` 로 행을 찾아 수명만 본다. **넥슨을 부르지 않는다.**
- 토큰을 내는 자리는 `tokenFor(sessionId)` 하나다. 만료 60초 전이면 갱신하고, 같은 세션의 갱신이
  진행 중이면 그 프라미스를 기다린다. 프로세스 안 `Map<sessionId, Promise>` 하나면 되고,
  인스턴스가 하나(결정 15)라 그것으로 끝이다.
- 갱신이 거절되면 **세션 행을 지우고** 재로그인을 돌려준다.

**경합을 우리 안에서 없애면 거절은 죽은 토큰뿐이다.** 갱신 토큰은 회전하고 겹치면 하나만
이긴다(맥락의 실측). 처음 설계는 그 경합을 전제로 "거절돼도 세션 삭제를 자동으로 하지 않는다"
고 했는데, 그 경합은 한 회차의 팬아웃 소켓들이 같은 토큰으로 동시에 갱신을 보낼 때 **우리 코드가
만드는 것**이다. single-flight 가 그것을 없애면 `OPENAPI00012` 는 진 쪽이 아니라 죽은 토큰이고,
지우는 것이 맞다. 미루면 죽은 세션이 14일을 산다.

**회차는 시작에 한 번 토큰을 집는다.** 액세스 토큰이 30분이고 회차는 결정 12 가 120초에서
끊으므로 도중에 만료될 일이 거의 없다. 넥슨이 401 을 주면 `tokenFor` 를 한 번 더 부르고 그 쪽만
재시도한다.

**같은 플랫폼의 두 기기도 이 길로 풀린다.** 넥슨이 새 로그인에서 옛 갱신 토큰을 죽이면(열린 질문)
옛 기기의 갱신이 거절되고 그 기기가 재로그인을 본다. 그것이 맞는 동작이다.

## 결정 — 프렌즈 조회

### 결정 7. 프렌즈 조회를 서버가 모아 NDJSON 스트림으로 흘린다. 앱은 토큰을 안 든다 (사용자 지정)

앱이 **작업 목록 하나**를 보내고 서버가 그 작업들을 넥슨에 돌면서 결과를 줄로 흘린다.

```
POST /v1/friends/stream
Authorization: Bearer <세션>
{ "tasks": [{ "kind": "cube", "date": "2026-10-01" }, …] }

200  Content-Type: application/x-ndjson · Content-Encoding: gzip · X-Accel-Buffering: no
401  세션이 없거나 갱신이 거절됐다 (결정 6)
503  Retry-After: 30   전역 상한을 넘었다 (결정 11). 몸체 없이 바로 끊는다

앱 → 서버 1건  →  서버 → 넥슨 × 124  →  줄 124개 이상
```

**작업의 모양.** `kind` 는 넥슨 경로의 마지막 마디 그대로이고 여섯이다. `date` 는 내역 넷과
`character-state` 가 들고, `character-state` 는 `ocid` 도 들고 `date` 는 없어도 된다(없으면 오늘. 자정 전 결산 중에도 200 을 주는 조회를 앱이 그대로 쓴다). `character-list` 는 둘 다 없다(한 쪽으로
끝난다). 서버는 줄마다 `kind` · `date` · `ocid` 를 받은 그대로 돌려주고 앱은 그것으로 원장의 칸을 찾는다.
작업 수는 한 요청에 1,000 까지다. 창 채우기가 캐릭터 수 × 날짜라 가장 많다.

```
kind              넥슨 경로                                   date  ocid
cube              /maplestory/v1/history/cube                  ○
starforce         /maplestory/v1/history/starforce             ○
potential         /maplestory/v1/history/potential             ○
soul-potential    /maplestory/v1/history/soul-potential        ○
character-state   /maplestory/v1/scheduler/character-state     △     ○   date 가 없으면 오늘
character-list    /maplestory/v1/character/list
```

내역 넷의 첫 쪽은 `count=1000&date=` 이고 다음 쪽은 `count=1000&cursor=` 만이다. 커서가 날짜 맥락을
든다(앱 실측 2026-09-06). 나머지 둘은 커서가 없어 한 쪽이다.

**앱은 넥슨 토큰을 아예 받지 않는다.** 가이드라인의 `서버에서만 관리하고 사용` 에서 **관리**는
결정 3·4 가 받고 **사용**을 이 결정이 받는다.

**1:1 중계가 아니라 모아 흘리는 것이 요점이다.** 한 건씩 중계하면 사용자 한 명의 조작이 우리
서버에 수백~수천 요청이 되지만, 모아 흘리면 **우리 서버로 가는 요청이 1건**이다. 그래서 nginx 의
`rate=10r/s burst=20` 에 안 닿는다 - 이 설계가 그 한도를 **지켜 주는** 쪽이다.

**범위는 프렌즈 6경로다.** 비프렌즈 12경로는 Open ID 가 안 열어 서버가 대신 부를 것이 없고,
개발자 API 키를 쓰므로 가이드라인 문장의 대상도 아니다. 앱이 계속 직접 부른다. 창 채우기도
`kind` 만 다른 작업이라 같은 통로다.

**앱이 끊으면 서버도 멈춘다.** 안 두면 사용자가 화면을 떠난 뒤에도 넥슨 호출 124건이 계속 나가고
그 비용은 보이지 않는다. 응답(`reply.raw`)의 `close` 가 `AbortController` 를 당겨(요청 쪽 `close` 는 Node 16 부터 본문을 다 읽은 뒤에도 나서 끊김의 신호가 아니다) 진행 중인 넥슨 fetch 와
결정 16 의 버킷 예약을 거둔다.

**SSE 가 아니라 NDJSON 인 이유.** 처음 설계는 SSE 였다. 받는 쪽이 `react-native-sse` 가 아니라
`expo/fetch` 의 스트림(결정 13)이 되면서 `event:` · `data:` 틀과 주석 하트비트가 할 일이 없어졌다.
줄 하나가 이벤트 하나면 서버는 `JSON.stringify` 뒤에 개행 하나, 앱은 개행에서 자르는 것뿐이다.

### 결정 8. 원본 줄을 그대로 내린다 (사용자 지정)

서버는 넥슨 응답의 줄을 **가공하지 않고** 흘린다. 장비 신분 매핑 · 비용 계산 · 특수 캐릭터 가리기는
앱에 남는다.

가공하면 응답이 훨씬 작아지지만 **게임 레퍼런스 수치(`src/data/`)가 서버로 넘어간다.** 그
데이터는 도메인 전문가 확인을 거쳐야 하는 축이라 이 변경에 끼우지 않는다.

**대가**: 응답 바이트가 넥슨 원본과 같다. 본문이 서버를 **두 번** 지난다(넥슨에서 들어와 앱으로
나간다). 가공이 없어 CPU 는 여유가 있고 파싱이 필요한 것은 **커서를 꺼내 다음 쪽을 부르는 것**
하나다.

### 결정 9. 쪽 하나가 줄 하나다. 작업의 끝을 알리는 줄이 따로 있다

```
{"t":"page","kind":"cube","date":"2026-10-01","n":1,"body":<넥슨 원본 그대로>}
{"t":"done","kind":"cube","date":"2026-10-01","pages":1}
{"t":"fail","kind":"cube","date":"2026-10-02","status":429}
                                              빈 줄 = 하트비트 (결정 14)
{"t":"end","reason":"done" | "deadline" | "budget" | "relogin"}
```

**작업이 아니라 쪽이 단위인 이유.** 처음 설계는 작업 하나가 이벤트 하나였다. 작업 하나가 50쪽
43MB 까지 가므로 그러면 기기가 그 줄을 통째로 들어야 한다. 쪽 단위면 한 줄이 최대 870KB 다.

**`body` 는 파싱 없이 싣는다.** 결정 8 그대로다. 서버가 본문에 하는 일은 둘뿐이다. 바이트의 개행을
공백으로 바꾸는 것(JSON 문자열 안에 날개행은 올 수 없어 모든 개행이 공백이다)과
`"next_cursor":"…"` 를 정규식으로 꺼내는 것. 넥슨이 200 이 아니거나 JSON 이 아니면 `body` 를
안 싣고 `fail` 이다. 넥슨에 닿지 못했거나 10초를 넘겼거나 쪽이 안전핀 50 을 넘으면 `status` 가 0 이다.

**앱이 `done` 을 받은 작업만 원장에 적는다.** 그러면 실패한 날짜가 다음 회차에 자동으로 다시 온다.
응답 하나로 묶으면 날짜 하나의 실패가 전체를 실패시키거나 조용히 사라진다. 앱은 작업의 첫 쪽을
받기 전에 그 `(종류, 날짜)` 칸의 행을 지우고, 쪽마다 넣고, `done` 에 칸을 굳힌다. 잘리면 안 굳은
칸이 다음 회차에 다시 와서 그때 지워진다. 트랜잭션이 네트워크를 가로지르지 않고 깃발 칸도 없다.
안 굳은 칸의 행이 반쪽일 수 있는데 오늘 칸이 이미 그 성질이다
(`features/enhancement-history/collect.ts` 의 "오늘은 굳을 수 없어 언제나 든다").

**`end` 없이 끊기면 앱은 `end` 와 똑같이 처리한다.** 적힌 작업은 적혔고 나머지는 다음 회차다.

**기획은 앱에 남는다.** 기기 원장을 읽어 안 받아진 작업을 세는 일을 서버가 하게 하면 원장을 서버로
옮겨야 하고, **두 번째 방문이 0건이라 요청 자체가 안 나가는** 성질도 잃는다.

**`fail` 줄은 `code` 도 든다**(2026-10-15 추가). 넥슨 본문의 `error.name` 이다. 앱이 400 을 날짜 문제
(`OPENAPI00004`) · 결산 중(`OPENAPI00009`) · 영구 불가(`OPENAPI00003`)로 갈라 쓰는데, status 만 있으면
그 셋이 하나가 된다. 본문이 JSON 이 아니면 `code` 가 없다.

### 결정 10. 메모리를 동시 수에 묶는다. 팬아웃 4, 쪽은 통째로, drain 을 기다린다

**모아 두지 않는다.** 한 사용자의 124페이지를 버퍼에 쌓아 끝에 보내면 동시 회차 수의 배수가 같은
시각에 힙에 있다. 받은 쪽에서 바로 줄로 내보내면 **동시에 연 소켓 수만큼만** 든다.

**앞질러 당기지 않는다.** 소켓 쓰기가 `false` 를 돌려주면 **그 바이트는 보내진 것이 아니라 쓰기
큐에 쌓인 것**이다. 넥슨은 쪽 하나(870KB)를 200ms 에 주고(≈4 MB/s) 앱은 0.3~2 MB/s 로 받으므로,
무시하고 계속 당기면 **차이가 전부 힙에 남는다.** 회차 총 바이트에 상한이 없으니 그 힙도 상한이
없다. 그래서 **배수가 빠질 때까지 기다린 뒤 다음 쪽을 당긴다.**

**둘 중 하나만 있으면 메모리가 안 묶인다.** 그래서 한 결정으로 둔다.

**팬아웃은 4 다**(사용자 지정 2026-10-14). 회차 하나가 동시에 여는 넥슨 요청 수다. 1 이면 쪽
중앙값 0.1KB 인 작업 124개가 왕복 30ms 씩 직렬로 4초 가까이 걸리고, 10 이면 회차당 메모리가
8.7MB 로 늘면서 속도는 안 는다(큰 쪽은 앱 다운링크가 병목이라 소켓을 더 열어도 멈춰 서 있다).
4 면 124개가 약 1초이고 회차당 최악 3.5MB 다. 앱이 지금 기기에서 직접 돌리는 값이 강화 내역 3 ·
창 채우기 6 이다.

**쪽은 통째로 `Buffer` 에 받는다.** 넥슨 본문을 소켓으로 파이프하면 회차당 메모리가 64KB 까지
줄지만, 팬아웃 4 의 3.5MB 가 이미 예산 안이라 실수할 자리가 적은 쪽을 둔다. 메모리가 실측 병목이
되면 그때 당길 레버다.

### 결정 11. 동시 회차 상한 40, 넘으면 503 으로 미룬다 (사용자 지정)

상한이 **둘**이다. 사용자당 팬아웃(결정 10)과 **전역 동시 회차 수**다. 앞엣것만 두면 메모리가
사용자 수에 선형으로 자란다.

```
FRIENDS_MAX_RUNS   40    동시 회차. 넘으면 503
FRIENDS_FANOUT     4     결정 10
```

**넘은 요청은 기다리게 두지 않고 503 과 `Retry-After` 로 바로 끊는다**(사용자 지정 2026-10-14).
기다리게 하면 그 연결도 메모리를 들고 서 있어 상한을 둔 이유가 없어진다. 스트림을 열어 이벤트로
알리는 것도 같은 이유로 안 한다. nginx 의 속도 제한도 503 이라 앱의 처리가 하나다. 앱은 이번
회차를 접고, 원장이 그대로 남아 다음에 다시 온다(결정 9).

**시작값은 40 이다**(사용자 지정 2026-10-14). 메모리가 `MAX_RUNS × FANOUT × 870KB` 라
`40 × 4 × 870KB ≈ 139MB` 이고 앱 박스 여유 ~640MB 중 200MB 예산 안이다. 실측 동시 접속이 30초 창
45명 · 300초 창 84명이고 그중 조회를 시작하는 쪽은 일부다. 870KB 는 이론 최대이고 실측 최대 쪽은
287KB 라 현실 최악은 46MB 다.

**사용자가 늘면 곱을 지키며 옮긴다.** 하루 활성 3,000 을 가정하면 도착 초당 15명 · 보통 회차
0.5초 · 무거운 꼬리 2% × 60초로 전형 25 안팎이다. 그때는 `80 × 2` 가 같은 139MB 로 두 배를 받는다.
`80 × 4` 는 278MB 로 예산을 넘는다. 넘쳤을 때의 대가가 503 한 번이라 MAX_RUNS 는 전형에 맞추고,
메모리가 넘치면 프로세스가 죽으니 올릴 때는 FANOUT 을 내린다.

**팬아웃을 키워도 소용이 없다.** 역압(결정 10)이 걸리면 넥슨에서 당기는 속도가 앱이 받아 가는
속도에 묶인다. 앱이 1 MB/s 로 받는데 소켓을 열 개 열어도 아홉 개는 멈춰 서 있다. 그래서 팬아웃은
작게 두고 전역 동시 수를 크게 두는 쪽이 **같은 메모리로 더 많은 사람을 받는다.**

**완화책이 우리 손에 있다.** 버스트가 푸시에서 오므로 예약 발송으로 흩뿌리면 피크가 낮아진다.

### 결정 12. 회차는 새 작업을 시작할 때만 시간과 바이트를 본다

유지 시간이 `총 바이트 ÷ 앱 다운링크`이고 둘 다 우리가 못 정한다. 50MB 를 받는 사용자가
300 KB/s 면 **3분**을 붙들고, 측정된 300초 창의 동시 수가 84명이다.

```
FRIENDS_RUN_DEADLINE  120s   지나면 새 작업을 안 시작한다
FRIENDS_RUN_BYTES     16MB   원본 기준. 지나면 새 작업을 안 시작한다
```

**진행 중 작업은 끝까지 보낸다.** 결정 9 의 원장이 작업 단위라 쪽 단위 재개가 없다. 작업 하나가
43MB 까지 가는데 예산이 진행 중 작업을 자르면 그 작업은 매 회차 같은 자리에서 잘려 영원히 안
적힌다. 그래서 둘 다 새 작업을 시작할지만 정한다. 실제 상한은 예산 더하기 작업 하나이고, 유지
시간은 "상한 없음" 에서 "120초 더하기 작업 하나" 가 된다.

**둘이 따로 있는 이유.** DEADLINE 은 느린 회선에서 시간을 묶고 BYTES 는 빠른 회선에서 양을
묶는다. 빠른 회선은 120초에 200MB 를 당길 수 있고 그러면 기기가 한 회차에 그만큼을 SQLite 에
쓴다.

**값의 근거.** 실측 3MB 회차가 500KB/s 에서 6초라 보통은 한 회차에 끝나고, 50MB 를 300KB/s 로
받는 최악도 두 회차 안에 끝난다. 16MB 는 실측 한 달 네 종류 합 3MB 의 다섯 배다. 둘 다
시작값이다(사용자 지정 2026-10-14). 서버가 회차마다 바이트 · 작업 수 · 시간 · 끝난 이유를 한
줄로 남기고, 그 분포를 보고 고친다.

**끊어도 잃는 것이 없다.** 결정 9 가 작업 하나를 `done` 까지로 두고 앱이 굳힌 것만 원장에
적으므로, 못 보낸 작업은 **적히지 않아 다음 회차에 다시 온다.** 재개 장치를 따로 만들 필요가 없다.

**커서에 안전핀을 둔다.** 무한 루프를 막는 상한이지 용량 예산이 아니다.

## 결정 — 전송과 배치

### 결정 13. 전송은 `expo/fetch` 로 받고 gzip 으로 흘린다. 의존을 더하지 않는다

RN 의 전역 `fetch` 는 `whatwg-fetch` 폴리필이라 `response.body` 가 없다(확인 2026-10-12). 처음
설계는 그래서 XHR 의 증분 응답을 읽는 `react-native-sse` 를 골랐다. 그런데 Expo 57 의 **`expo/fetch`
가 `body` 를 `ReadableStream` 으로 준다**(맥락). 앱은 reader 에서 청크를 받아 개행에서 자르고
줄마다 파싱해 쓰고 버린다. 기기 힙에는 한 줄만 있다.

**`react-native-sse` 를 걷는 이유 둘.** 의존을 더하면 지문이 바뀔 수 있어 OTA 로 못 가는 위험이
있었는데 `expo/fetch` 는 이미 번들에 있다. 그리고 그 라이브러리는 XHR 의 `responseText` 를 읽어
**응답 전체를 문자열로 누적**하므로 결정 12 의 바이트 상한이 기기 메모리까지 묶고 있었다. 스트림은
읽은 청크를 버린다.

**직접 구현이 느는 것은 개행에서 자르는 15줄이다.** 라이브러리를 선호하는 저장소 방침이지만, 그
15줄을 의존으로 바꾸면 지문 확인이 돌아온다.

**응답을 gzip 으로 흘린다.** `zlib.createGzip({ flush: Z_SYNC_FLUSH })` 가 줄마다 내보낸다.
하트비트 빈 줄도 10바이트로 나간다. 줄 JSON 은 보통 5~10배 줄어 유지 시간 표(맥락)는 압축 뒤
바이트로 다시 잰다. 기기는 `Accept-Encoding` 을 직접 적지 않는다. OkHttp 는 자기가 붙인 헤더일
때만 투명하게 푼다.

**재연결은 없다.** 한 번만 돌아야 하는 비싼 팬아웃이라 끊기면 끝이고(결정 9 의 `end` 없는 종료)
다음 회차가 이어 받는다.

**실측했다**(2026-10-14 · 맥락의 실측 표). 두 플랫폼 다 gzip 을 투명하게 풀어 줄 단위로 증분 전달한다.
`react-native-sse` 로 돌아갈 이유가 없다.

### 결정 14. nginx 에 그 경로의 자리를 따로 만든다

```nginx
location = /v1/friends/stream {
  proxy_buffering off;        # 기본값 on 이라 손대지 않으면 스트림이 안 흐른다
  proxy_http_version 1.1;
  gzip off;                   # 서버가 이미 gzip 으로 보낸다
  proxy_read_timeout 60s;     # 하트비트 15초의 네 배. 지금 10s 라 10초에 잘린다
  proxy_pass …;
}
```

서버가 `X-Accel-Buffering: no` 를 함께 보낸다. **둘 중 하나만 두면 설정이 갈릴 때 조용히 버퍼링으로
돌아간다.** 같은 박스에 있어도 nginx 가 앞에 서는 한 기본값 `on` 이 먼저 막는다.

**서버가 15초마다 빈 줄을 흘린다.** 역압 대기와 넥슨 대기 중 연결이 유휴가 되는데 이동통신 NAT 와
`proxy_read_timeout` 이 그것을 끊는다. `proxy_read_timeout` 은 바이트마다 리셋되니 하트비트가
있으면 "길게" 가 아니라 60초면 된다. 처음 설계에는 하트비트가 없어 타임아웃을 길게 두는 것이
유일한 길이었다.

**속도 제한은 그대로 둔다.** 한 회차가 요청 1건이라 안 닿는다(결정 7).

### 결정 15. Always Free 인스턴스 둘에 나눈다. 유료 플랜으로 올리지 않는다 (사용자 지정)

```
앱 박스   nginx + 애플리케이션     공개 IP · 인증서가 여기 있다
DB 박스   Postgres                 사설망만
```

**가르는 이유가 용량보다 격리다.** `swap` 이 0 이라(실측) 메모리가 넘치는 순간 OOM-killer 가
피해자를 고르고, Postgres 가 애플리케이션보다 RSS 가 크면 **앱 버그가 DB 를 죽인다.** 가르면 그
경로가 없어진다.

| | 한 박스 | 가른 뒤 (앱 박스) |
|---|---|---|
| 기저 | ~438MB | ~308MB |
| 요청에 쓸 수 있는 것 | ~500MB | **~640MB** |

| 동시 회차 | 평균 쪽 25.6KB | 큰 쪽만 287KB | 꽉 찬 쪽 870KB |
|---|---|---|---|
| 4 | 1MB | 11MB | 35MB |
| **40** | **10MB** | **115MB** | **348MB** |

**가장 흔한 값이 10MB 이고 가능한 최악이 348MB 다.** 가른 뒤 여유 ~640MB 에서는 최악도 들어가고
한 박스였다면 아슬아슬했다. 그래서 가름이 격리뿐 아니라 **용량에서도 값을 한다.** 상한은 그래도
필요하지만(결정 11) **전형을 맞추기 위한 것이 아니라 꼬리를 막기 위한 것**이라 넉넉히 둘 수 있다.

**DB 박스는 과잉이다.** 기본 설정이 15GB 박스용이라 작게 내린다 - `shared_buffers` 128MB → 32MB ·
`effective_cache_size` 4GB → 256MB · `max_connections` 100 → 20.

**사설망으로 잇는다.** 같은 VCN 에 두면 DB 트래픽이 인터넷을 안 타고 요금도 안 붙는다. 5432 는
**Oracle 보안 목록과 ufw 양쪽**에 `10.0.0.0/24` 로 한정해 열어야 하고, 한쪽만 열면 조용히 막힌다.

**양쪽에 swapfile 1~2GB 를 둔다.** 둘 다 `swap` 이 0 이고 디스크가 38GB 여유다. 느려지지만 kill 은
안 당한다. Postgres 는 VACUUM 때 특히 그렇다.

**힙 상한을 건다.** 터져도 DB 를 안 죽이지만, 상한이 있으면 **OOM 이 아니라 힙 에러**라서 그 요청만
죽고 로그에 원인이 남는다.

**DB 가 네트워크 건너로 가므로 연결 실패가 새 고장 모양이다.** 연결 타임아웃을 두고, DB 박스가
재시작하는 동안 요청이 매달리지 않고 깨끗히 실패하게 한다.

**미니 PC 는 백업 받는 자리로 쓴다.** WireGuard 통로가 이미 서 있어 덤프를 집으로 당기면 오프사이트
백업이 된다.

### 결정 16. 넥슨 호출 수를 자격 쌍마다 전역으로 묶는다

```
FRIENDS_NEXON_RPS   400   자격 쌍마다. iOS 버킷 하나 · Android 버킷 하나
```

**동시 회차 상한으로는 넥슨 초당 상한이 안 지켜진다.** 결정 10 의 역압은 큰 쪽에만 걸린다. 쪽
중앙값이 0.1KB 라 작은 쪽은 왕복 30ms 로 돌고, 소켓 160개(40 × 4)가 그 속도로 돌면 초당 5,000건이
넘는다(맥락의 용량 실측). 넥슨은 애플리케이션당 1,000/s 다.

**토큰 버킷을 자격 쌍마다 둔다.** 넥슨 fetch 는 버킷의 토큰을 집어야 나간다. 400 은 1,000 의 절반
아래라 넥슨 쪽 집계 오차와 재시도 몰림이 겹쳐도 안 닿는다. 작으면 피크에 회차가 느려질 뿐 에러는
없고, 크면 429 가 나고 실패한 작업이 다음 회차에 다시 몰린다. `bottleneck` 같은 라이브러리로 두고
직접 짜지 않는다. 공지 폴러는 개발자 API 키라 할당량이 다르고 이 버킷을 안 거친다.

**429 가 오면 그 버킷을 1초 비우고 그 쪽만 한 번 재시도한다.** 다시 429 면 `fail` 이다.

**넥슨 fetch 마다 `AbortSignal.timeout(10_000)` 을 건다.** 결정 11 의 상한이 있으니 매달린 쪽 하나가
회차 슬롯을 영구 점유한다.

**앱이 끊으면 예약도 거둔다.** 결정 7 의 `AbortController` 가 버킷에 줄 선 요청도 취소한다.

### 결정 17. 새 서버의 책임 표

"기존 서버 코드를 참고하지 않는다" 와 "결정은 로그인 · 조회 · 저장 · 배치만" 을 합치면 빠지는
것이 조용히 빠진다. 출처는 앱의 호출부(`src/server/*` 와 `features/*` 가 부르는 `/v1/*`)와
`docs/features/*` 다.

**`/v1/auth/nexon/token` 은 없다.** 앱이 토큰을 안 든다(결정 7).

**`/v1/notices` 의 `nextCursor` 는 늘 `null` 이다.** 앱이 커서를 보낸 적이 없고 목록은 최근 20건이
규칙이라([[ADR-277]]) 커서 넘기기를 만들지 않는다. 계약의 모양은 지킨다.

**썬데이 기록은 Notice 에 `startsAt` · `endsAt` 을 더한 모양이다.** `body` 는 빈 문자열이고 `blocks` 를
싣는다([[ADR-247]] 결정 11). 판정은 조회 때 제목으로 한다. 썬데이 본문의 HTML 은 `cheerio` 로 블록을
만든다(사용자 지정 2026-10-14).

**CLI 는 `src/cli/notice.ts` 다.** `npm run notice -- send | list | push` 의 모양은 옛 README 그대로이고
예약은 없다. `--dry` 는 저장하지 않고 FCM 검증만 한다.

**`/v1/auth/nexon/start` 는 `/v1/auth/nexon/login` 이다.** 결정 3 의 이름이다.

**결산 감시는 창 안 10분 간격이고 부팅 때도 한 번 본다.** 판정은 프로세스 메모리이고 `startedAt` 은 그 밤의
날짜 00:00 KST 다. 모름은 판정을 안 바꾼다([[ADR-284]] 정정 3, 사용자 지정 2026-10-15).

**보스 목록과 규칙은 `bosses` · `boss_difficulties` · `game_rules` 가 들고 관리 화면이 채운다**([[ADR-349]],
사용자 지정 2026-10-15). `manual-completion` 은 그 표를 참조한다([[ADR-293]] 정정 4). 관리 화면은 JSON 끝점을
부르는 작은 HTML 이다. 폼 본문 파서를 안 들이려고 `fetch` 로 JSON 을 보낸다.

**운영자 공지의 관리 화면은 옛 README 의 규칙 그대로다.** `GET /admin/notices` 화면 하나에 쓰는 폼과 쓴 목록이
있고, 끝점은 `POST /admin/notices` · `PATCH /admin/notices/:id` · `DELETE /admin/notices/:id` ·
`DELETE /admin/notices/:id/schedule` 넷이다. 저장이 발송보다 먼저다. 알림은 기본 꺼짐이고 켜면 지금 보내거나
시각을 예약하며, 예약은 `scheduled_at` 과 `push_title` · `push_body` 에 적어 1분 고리가 보낸다. 지난 시각은
400 이다. 수정에는 예약이 없고, 알림을 켜면 지금 다시 보내며 보낸 문구를 덮고, 안 켜면 예약 문구는 그대로다.
`published_at` 은 안 건드린다. 예약은 취소만 있고 공지는 남는다. 넥슨 공지는 수정 · 삭제 · 목록에서 빠진다.
되돌릴 수 없어서다. 열쇠 함수는 `notice-key.ts` 하나이고 CLI 와 화면이 함께 쓴다.

**드롭 가격 보기는 읽기만 한다**([[ADR-342]] 정정 3 의 "노이즈는 관리 화면으로 본다"). `GET /admin/drop-prices` 가
아이템 key · 기간 key 필터로 아이템 × 기간의 분포(개수 · 최소 · 중앙값 · 최대)와 최근 줄을 보여 준다. 분포는
뺀 가격을 빼고 세고, 줄 목록은 뺀 가격도 흐리게 보인다. 이름은 앱의 `drop-items.json` 에만 있어 key 로 본다.

### 결정 18. 쓰기 경로의 신원은 세션 아니면 키 해시다. 해시는 증명이 없다 (사용자 지정)

[[ADR-340]] 결정 7 의 "세션을 사람으로 바꾸는 한 겹" 이다. `POST /v1/drop-prices` · `DELETE /v1/drop-prices/:id` ·
`DELETE /v1/me` 셋이 함께 쓴다. 조회 경로는 그대로 공개다.

| 헤더 | 사람을 찾는 길 | `identified_by` |
|---|---|---|
| `Authorization: Bearer <세션>` | `session_hash` 로 행을 찾는다. 넥슨을 안 부른다(결정 6) | `login` |
| `x-api-key-hash: <소문자 16진 64자>` | 받은 값을 한 번 더 sha256 해 `users.api_key_hash` 를 찾거나 만든다 | `key` |

- **둘이 다 오면 세션이 이기고 키는 안 읽는다.** 로그인한 사람의 기록이 키 쪽으로 갈라지면 한 표로 모은 것이
  다시 쪼개진다.
- **세션이 죽었으면 키로 안 넘어간다. 401 이다.** 앱도 같은 선을 보여 한쪽만 싣는다(`features/auth/server-identity.ts`).
- **둘 다 없거나 모양이 틀리면 401 이다.** 키 원문이 실려 오면 길이가 안 맞아 여기서 걸린다.

**로그인 사용자의 신원은 넥슨이 보증하고 서버 세션이 증명한다.** 넥슨 보안 가이드라인이 액세스 토큰을 서버에서만
관리하라고 적어 앱은 토큰을 못 든다. 대신 서버가 `client_secret` 으로 교환하고 userinfo 로 uid 를 받은 뒤 발급한
세션이 그 사람의 증거다. 가이드라인 넷(HTTPS · `client_secret` 비공개 · `state` 고유 난수와 1회 사용 ·
토큰 서버 보관)은 결정 3~6 이 다 지킨다.

**키 사용자의 신원은 확인할 길이 없다.** 확인하려면 키 원문을 받아야 하는데 이용약관 제5조 ①·② 가 막는다.
사용자가 [[ADR-340]] 결정 3 을 그대로 두기로 했다(2026-10-15). 해시는 자격이 아니라 **표본을 묶는 꼬리표**다.
같은 사람의 재전송을 잇고 탈퇴 삭제를 찾는 데만 쓰고, 줄마다 `identified_by` 를 남겨 뒤에 가중을 가른다.
오염은 신원이 아니라 입력 검증과 집계 때의 이상치 제거가 막는다. 로그인 사용자도 틀린 값은 보낼 수 있다.

**멱등은 사람 안에서다.** `UNIQUE (user_id, drop_record_id)` 이고 `POST` 는 그 쌍으로 upsert 한다. 같은 본문이
다시 와도 줄이 안 늘고 200 `{ ok: true }` 다. 남의 기록 id 로 보내면 내 줄이 하나 생길 뿐 남의 줄은 안 건드린다.
갱신은 값 · `updated_at` · `deleted_at = NULL` 이다. 뺐던 가격을 다시 적으면 되살아난다.

**4xx 는 본문이 틀릴 때만이다.** 앱이 응답이 온 시도를 5회 세어 그 건을 버린다(`server/drop-price.ts`). 배포
중 5xx 도 세므로 서버는 멀쩡한 본문을 거절하지 않는다. 검증은 이것뿐이다.

```
dropRecordId  uuid
itemKey       1~200자
priceMeso     1 이상의 정수, Number.MAX_SAFE_INTEGER 이하  앱이 0 이하는 안 보낸다(drop-price-sync.ts)
periodKey     YYYY-MM-DD 또는 YYYY-MM
worldKey      1~100자 또는 null
ringLevel     정수 또는 null
slot          1~100자 또는 null
boss          1~100자 또는 없음   보스 key. 서버가 difficulty 와 함께 boss_difficulties 줄을 찾는다. 못 찾으면 NULL([[ADR-342]] 정정 5)
difficulty    1~50자 또는 없음
```

**`DELETE /v1/drop-prices/:dropRecordId` 는 내 줄의 `deleted_at` 만 채운다.** 없어도 204 다.

**`DELETE /v1/me` 는 `users.deleted_at` 을 적고 그 사람의 세션을 전부 지운다.** 이미 적힌 시각은 안 덮는다.
표본은 그대로다([[ADR-340]] 정정 3). 204 다.

**가드는 `modules/identity` 가 들고 `DELETE /v1/me` 도 거기 있다.** `auth` 가 `users` 를 가져오고 가드는 둘을
다 쓰므로, `users` 안에 두면 두 모듈이 서로를 가져온다.

## 정정

### 정정 1. 안드로이드 복귀는 다음 스토어 빌드까지 스킴이다 (2026-10-15, 사용자 지정)

결정 3 은 안드로이드를 `autoVerify` App Link(`/app/oauth/return`)로 돌려보낸다. 그 인텐트 필터는 네이티브
매니페스트 변경이라 스토어 빌드를 타는데, 사용자가 다음 버전을 스토어 빌드로 내고 싶지 않다고 했다.

**지금은 안드로이드도 iOS 와 같이 `com.mapleroutine.app://oauth/callback?receipt=` 로 302 한다.** 서버
`auth.service.ts` 의 `ANDROID_USES_APP_LINK` 가 `false` 다. `/app/oauth/return` 경로와 폴백 페이지는 그대로
둔다.

**잃는 것은 가로채인 그 한 번의 로그인이 실패하는 것뿐이다.** 결정 3 이 ④ 에 `redeem_key` 와 `receipt` 둘을
요구해서 `receipt` 만으로는 세션을 못 받는다. 같은 스킴을 선언한 앱이 신호를 먹으면 진짜 앱이 `receipt` 를
못 받아 그 로그인이 안 되고, 그뿐이다. 악성 앱이 자기 웹뷰로 동의 화면을 여는 공격은 App Link 로도 못
막고 열린 질문(앱 무결성 증명)에 그대로 있다.

**다음 스토어 빌드에서 App Link 로 바꾼다.** 앱에 인텐트 필터(`feat-debug-oauth-probe` 에서 쟀던 것)를
넣고 서버 상수를 `true` 로 돌린다. 앱 저장소 이슈가 그 일을 든다.

## 대가

- **서버 가용성이 로그인 화면에 직결된다**(결정 3). 콜백이 302 를 못 내면 사용자가 브라우저에
  갇힌다.
- **브라우저에서 기다리는 시간이 생긴다.** 콜백이 넥슨 왕복 둘(교환 · `userinfo`)과 DB 쓰기를 하고
  나서야 302 를 낸다. **이 시간을 안 쟀다**(사용자 판단으로 무시하기로 했다).
- **봉한 원본이 DB 에 있는 자리가 최악 3분 생긴다**(결정 4 · 5). 되묻는 창 60초 · 봉한 짝 보관
  2분 · 고리 1분.
- **콜백이 `users` 행을 앱이 확인하기 전에 만든다.** ④ 가 안 와도 그 행은 남는다. 동의가 끝난
  시점이라 **그 사람은 가입자이고 행은 맞다** - `nexon_uid` 가 `UNIQUE` 라 다시 로그인하면 같은
  행을 받는다.
- **앱 쪽 일이 는다**(결정 3). `assetlinks.json` 을 `mapleroutine.store/.well-known/` 에 두고, Expo
  `android.intentFilters` 에 `autoVerify` 로 `/app/oauth/return` 을 적고, 검증이 안 된 기기의 폴백
  페이지를 서버가 든다. 디버그 서명도 적어야 개발 빌드가 돌아온다.
- **긴 요청이 생긴다**(결정 7). nginx · 애플리케이션 · 앱 세 층의 타임아웃을 함께 봐야 하고, 한
  층만 짧으면 그 층에서 잘린다.
- **원본 본문이 서버를 지나 나간다**(결정 8). 집 업링크(2.17 MB/s)에서는 이것이 벽이고
  Oracle(60 MB/s)에서는 아니다. 그래서 **옮기는 것을 전제로 한다.**

## 이 문서 밖에 남는 것

[[ADR-345]] 에 있던 **기기 SQLite 쪽 소견**은 서버와 무관해 여기로 안 가져온다. 집이 필요하다.

- 기기 표 일곱의 복합 PK(`boss_profit_records` · `boss_party_settings` ·
  `boss_party_period_overrides` · `boss_profit_period_checks` · `character_accounts` ·
  `enhancement_history_checks` · `mvp_grade_history`). 옮기면 조회가 전체 스캔이 되므로 인덱스를
  함께 세워야 한다.
- 가계부 두 표의 대리키가 `시각(36진) + Math.random()` 인 것. 근거였던 `Hermes 에
  crypto.randomUUID 가 없다` 는 전제가 사라졌다.
- 자연키 한 칸으로 선 표 셋(`character_profiles` · `character_world_leaps` ·
  `enhancement_history`). 규칙의 예외로 둘지가 결정이다.
- 기기 DB 에 인덱스가 하나뿐인 것. 복합 PK 가 곧 인덱스였기 때문이다.

## 열린 질문

- **콜백의 왕복이 얼마인가.** `oauth2/token` 과 `userinfo` 를 안 쟀다. 길면 `userinfo` 를 ④ 로
  미룰 수 있지만 그러면 `users` 행을 ④ 에서 만들어 두 자리의 일이 섞인다.
- **되묻는 창 60초가 맞나.** 리다이렉트를 받아 되묻는 데 실제로 얼마가 걸리는지 실기기에서 재야
  한다.
- **다섯 값의 실제 분포.** 결정 10 · 11 · 12 · 16 의 시작값은 가정 둘 위에 있다. 앱을 연 사람이
  전부 조회를 시작한다는 것과 무거운 회차가 2% 라는 것. 앞엣것은 비관적이고 뒤엣것은 모른다.
  **같은 로그로는 못 잰다** - 지금 조회가 우리 서버를 안 거치기 때문이고, 회차 로그가 쌓이면
  곱을 다시 맞춘다.
- **무거운 계정의 실제 분포.** 남의 계정은 재 볼 수 없다. 서버가 회차당 바이트를 기록해 보는 것이
  유일한 길이다.
- **창 채우기의 쪽 크기.** 프렌즈 6경로에 들어 있고 첫 진입 84건이 같은 성질의 팬아웃인데, 쪽
  크기를 재려다 400 을 받았고 **에러 본문을 안 찍어** 원인을 못 봤다.
- **같은 플랫폼의 두 기기에서 로그인하면 먼저 기기가 죽나.** 저장된 갱신 토큰이 **저장된 만료보다
  먼저 죽어 있었다**(2026-10-12). 같은 `client_id` 로 그날 새 로그인을 한 번 돌린 것이 유일한
  설명인데 직접 재지는 않았다. 결정 6 은 그렇다고 보고 옛 기기에 재로그인을 돌려준다.
- **갱신이 갱신 토큰의 수명을 늘리나.** 넥슨은 갱신마다 14일을 돌려준다. 실제로 늘어나는지는 안
  쟀고, 안 늘어나면 서버가 죽은 토큰을 최대 14일 살아 있다고 믿어 결정 5 의 만료 청소도 그만큼
  늦게 걷는다.
- **앱 무결성 증명을 요구하나.** 로그인 시작 경로가 인증 없이 열려 있는 것은 그대로다. ④ 에
  Play Integrity · App Attest 증명을 요구하면 악성 앱은 우리 패키지 서명으로 증명을 못 만든다.
  넥슨에 의존하지 않는 대신 양 플랫폼의 증명 검증을 서버에 들여야 한다. 결정 3 의 `receipt` 가
  CSRF 를 닫아 급하지 않다. **지금 단계에서 꺼낼 카드는 아니다.**

## 순서 제약

**기존 넥슨 애플리케이션 둘이 검수 중이라 수정할 수 없다**(사용자 확인 2026-10-14). https URI 를
그 둘에 등록하는 것이 결정 3 의 선행 조건이다. 시험은 새로 만든 애플리케이션의 자격으로 하고,
서버에 넣을 때 기존 자격을 덮지 않는 별도 이름으로 둔다.

**`assetlinks.json` 이 App Link 검증의 선행 조건이다.** 릴리스 · 디버그 서명 해시 둘을
`https://mapleroutine.store/.well-known/assetlinks.json` 에 올려야 안드로이드가 `/app/oauth/return`
을 앱에 준다. 올리기 전에는 모든 기기가 폴백을 탄다.

**앱에서 넥슨 로그인을 켜기 전에 이 문서가 전부 들어가야 한다.** 지금 실제 위반은 0 이다 - 로그인이
꺼져 있어 이 경로를 타는 사용자가 없다.
