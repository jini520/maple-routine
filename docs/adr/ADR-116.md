# ADR-116: 개발 단계 키의 429 — 막힌 자리마다 "서비스 단계 키로 다시 입력" 경로를 연다

**날짜**: 2026-08-08
**상태**: **(구현 완료 · 실기기 미검증, 2026-08-08, 이슈 #176 · #177 · #178)** — 결정 5개 전부 구현,
폐기된 결정 없음. **실제 429 응답을 받아 본 적은 한 번도 없다**(아래 "자동 테스트가 담보하지 못하는 것").
**관련**: [[ADR-115]] 결정 10(닫을 수 없는 안내 모달 → 확인 → 키 입력 화면 — 이 ADR 이 **그 구조를 429 로 확장한다**)·결정 6(멱등 가드 — **두 번째 정정**)·결정 9(무효 키는 400 `OPENAPI00005`) · [[ADR-114]] 결정 1(429 문구는 키 단계를 판정하지 않는다 — 그대로 선다)·결정 2(429 에 액션을 주지 않는다 — **`ErrorState` 자리에서만 정정**)·결정 3(스탈 배너 — **건드리지 않는다**) · [[ADR-113]] 결정 3(프로브가 settle 할 때까지 목록을 그리지 않는다)·결정 4(`isSettled` 는 성공이 아니라 settle — **바꾸지 않는다**)·결정 7(실패한 프로브는 후보 자격을 유지한다 — **정정**) · [[ADR-062]] 결정 3(원인별 문구·액션)·결정 5(어미 `~습니다`) · [[ADR-067]] 결정 1(400 본문 에러 코드로 실패 종류를 가른다) · [[ADR-086]] 결정 8(조회 불가 계정 선택 차단) · [[ADR-065]] 결정 1(키 입력 폼 자체의 실패는 토스트) · 이슈 #176 · #177 · #178

## 맥락

### 세 이슈가 한 원인이다

테스터 보고 3건(2026-08-08)은 전부 **개발 단계 API 키의 호출 한도 초과(429)** 에서 나왔다. 고쳐야 할
자리가 다를 뿐이다.

| 이슈 | 자리 | 무엇이 깨졌나 |
|---|---|---|
| #177 | 계정 선택 | 429 가 `allUnavailable` 판정을 **삼켜** 못 쓰는 계정이 정상으로 보이고 선택된다 |
| #176 | 온보딩 캐릭터 선택 | 앞·뒤·재시작 전부 막힌 **하드 잠금** |
| #178 | 캐릭터 피커 3자리 | `ErrorState` 의 429 에 출구가 없어 **자리가 회복되지 않는다** |

**#177 → #176 은 인과다.** 429 로 정상처럼 보인 계정을 고르면 그대로 그 잠금에 도착한다.

### #177 — 프로브가 429 를 조용히 버린다

`src/features/onboarding/use-account-probes.ts:121-125` 의 `catch` 는 `characterUnavailable`(400
`OPENAPI00003`)만 다루고 나머지를 버린다. 그래서 429 로 **아무것도 못 본** 캐릭터가 전부 "조회 가능"
으로 분류되고, `allUnavailable`(`:145`)은 **항상 false** 가 된다 — 위양성이 아니라 **위음성**이다.
전원이 003 인 계정도 429 만 나면 멀쩡해 보이고, `pickRepresentativeCharacter(queryable)`(`:136`)가
조회 불가 캐릭터를 대표로 세울 수 있다([[ADR-068]] 결정 4 가 전수 프로브로 없앴다고 적은 문제가 429
경로로 되살아난 것이다).

**화면은 429 를 안다는 사실 자체가 없다** — `AccountProbe`(`:8-20`)에 판정 실패를 담을 필드가 없다.
사용자가 보는 것은 순식간에 100% 로 차는 진행률 바와, 모든 초상화가 `?` 인 **정상적인 목록**이다.

### #176 — 온보딩 캐릭터 선택의 하드 잠금

출구 다섯 방향이 전부 막힌다(이슈 #176 의 표).

| 출구 | 왜 막히나 |
|---|---|
| `계속하기` | 로스터가 비어 고를 캐릭터가 없다 → `disabled` 영구(`ContentCharacterStep.tsx:187`) |
| `다시 시도` | 같은 요청을 그대로 다시 쏜다 → 또 429 |
| `계정 다시 선택` | **실패 가지에 렌더되지 않는다** — `emptyAction` 은 *확정된 빈 상태* 가지에만 붙는다 |
| 뒤로 가기 | 온보딩 단계는 라우트가 아니라 `status` switch 라 되돌릴 UI 가 없다 |
| 앱 재시작 | `deriveResumeTarget()` 이 **같은 단계로 되돌린다**(`resume.ts`) |

남은 것은 설정의 **연결 해제**뿐인데 온보딩 중에는 설정 화면 자체가 없다.

### #178 — `ErrorState` 의 429 는 자리를 회복시키지 못한다

[[ADR-114]] 결정 2 가 `rateLimited` 의 액션을 없앴다(`format.ts` — `action` 없음). 그 결정의 근거는

> 배너는 목록이 남아 있어 액션이 없어도 막다른 길이 아니다.

인데, **`ErrorState` 는 정의상 목록이 없는 자리**라 그 근거가 뒤집힌다. 실제로 같은 ADR 이 401 에
대해서는 정확히 그렇게 판단해 놓고(`ContentCharacterStep.tsx:36-39` 주석 — *"액션을 빼면 화면에 아무
길도 남지 않으므로 재시도를 유지한다"*) 429 에는 반대로 적용했다. 컨텐츠/보스 탭에서는 이것이 루프가
된다 — `isEmpty` 면 화면 전체가 `EmptyState` 하나이고 그 유일한 액션이 피커 열기인데, 피커가 429 면
본문에 버튼이 0개라 닫으면 같은 `EmptyState` 로 되돌아온다.

`ErrorState.tsx:10` 의 컴포넌트 계약(`ErrorState … 액션 항상`)도 구현(`action?`)과 어긋나 있다.

### 429 를 실제로 줄이는 일은 이번에 하지 않는다

429 의 상류는 로스터·예열·프로브의 **fan-out 동시성 캡 부재**다([[ADR-113]] "미해결로 남기는 사실"
첫 항목 · [[ADR-114]] "범위 밖"). **사용자가 이번 범위에서 명시적으로 기각했다**(2026-08-08). 결정 5
에 그 한계를 그대로 적는다.

## 결정

### 결정 1 — 429 는 [[ADR-115]] 결정 10 의 알림 구조를 그대로 탄다

**새 메커니즘을 만들지 않는다.** 무효 키가 이미 쓰고 있는 사슬 — 감지 → `notice` → 닫을 수 없는 모달
→ `confirm` → 키 입력 화면 + 저장된 `apiKey` 삭제 — 을 429 가 그대로 탄다. 갈리는 것은 **문구뿐**이다.

상태를 원인별로 넓힌다:

```
apiKeyInvalidNotice: boolean   →   apiKeyNotice: 'invalid' | 'rateLimited' | null
```

| 원인 | 제목 | 본문 |
|---|---|---|
| `invalid` | `API 키가 더 이상 유효하지 않습니다` | `키 입력 화면으로 이동합니다.` |
| `rateLimited` | `호출 한도를 초과했습니다` | `서비스 단계 키로 다시 입력해주세요.` |

- 429 본문은 [[ADR-114]] 결정 1 의 처방(*"입력하신 API 키가 서비스 단계 키인지 확인해주세요"*)과
  **같은 말**이다 — 키의 단계를 판정하지 않고 안내만 한다. 그 결정은 그대로 선다.
- **모달은 토스트와 달리 줄바꿈이 되므로 처방을 본문에 그대로 담는다** — [[ADR-114]] 결정 4 의
  *"자리마다 담을 수 있는 만큼"* 기준이 여기서는 처방을 담는 쪽으로 나온다(토스트는 `truncate` 라
  원인만 말했다).
- **닫을 수 없다** — 오버레이 탭도 취소도 없고 `확인` 하나뿐이다. 무효 키와 완전히 같다.
- **확인하면 저장된 `apiKey` 를 지운다**(사용자 결정 2026-08-08) — 이것도 무효 키와 같다.
  `clearAuthConfig()` 는 쓰지 않는다([[ADR-115]] 결정 3 — `selectedAccountId` 까지 지우면 재개가
  불가능해진다).
- 어미는 [[ADR-062]] 결정 5 그대로다.

**이 결정 하나가 세 이슈의 출구를 동시에 만든다** — #176 의 잠긴 화면 위에도, #178 의 세 자리 위에도
같은 모달이 뜬다. #177 은 이 모달을 **띄울 수 있게 되는 것**이 결정 3 의 값이다.

### 결정 2 — 알림 가드를 "키 입력 화면에 있지 않을 때"로 바꾼다 ([[ADR-115]] 결정 6 정정)

지금 가드는 `status !== 'completed'` 면 no-op 이다(`store.ts:251`). 그런데 **#176 의 잠금은 온보딩
안에서 일어난다** — 그 가드로는 잠긴 사용자를 구할 수 없다.

새 조건: **`status` 가 `awaitingApiKey`·`verifyingApiKey` 면 알리지 않는다.**

- 그 두 상태가 곧 *"이미 키 입력 화면"* 이라 보낼 곳이 없다. 폼에서 다시 나는 실패는 폼 자체의
  토스트가 맡는다([[ADR-065]] 결정 1).
- **재이동 루프는 여전히 불가능하다** — 근거만 *"completed 일 때만"* 에서 *"키 입력 화면에서는 안
  알린다"* 로 바뀐다. 막는 대상은 같다.
- 이미 알림이 떠 있으면(`apiKeyNotice !== null`) 다시 알리지 않는다 — 여러 화면·여러 캐릭터에서
  동시에 실패해도 **모달 하나**로 접힌다([[ADR-115]] 결정 6 의 성질 유지).
- **원인이 겹칠 때는 먼저 뜬 것을 유지한다**(덮어쓰지 않는다). 두 원인 모두 처방이 *"키를 다시
  입력한다"* 로 같아 갈아끼울 실익이 없고, 문구가 눈앞에서 바뀌면 사용자가 읽던 것이 사라진다.
- **가드를 여는 것과 무엇이 진입점을 타는지는 다른 층이다.** 가드는 *"알려도 되는 상태인가"* 만
  정하고, 어느 실패가 진입점에 도달하는지는 **감지 지점의 배선**이 정한다. 온보딩 캐릭터 선택
  (`ContentCharacterStep`)에 새로 배선되는 것은 **429 뿐**이고, 그 자리의 **401 은 계속 폼 자체의
  실패로 남긴다**([[ADR-115]] "구현하며 정정한 것" 5 의 의도적 미배선 유지 · [[ADR-062]] 결정 3 의
  온보딩 401 = 재시도). **다만 그렇게 두는 근거는 바뀐다** — 전에는 *"가드가 어차피 막는다"* 였고
  이제는 *"그 자리를 배선하지 않는다"* 다. 근거가 구조에서 배선으로 내려왔으므로 [onboarding.md]
  (../features/onboarding.md) 의 서술도 함께 고친다.

**[[ADR-115]] 결정 6 의 *"구조적으로 불가능"* 이 정정되는 것은 이번이 두 번째다.** 첫 번째는 그 ADR
자신의 "구현하며 정정한 것" 11 — 동기화 스토어의 `error` 가 화면보다 오래 살아 재마운트 때 **이미
처리한 401 객체**가 가드를 통과했고, 모듈 스코프 `WeakSet` 으로 끊었다. 두 정정의 성격이 다르다:
그것은 **가드가 못 막던 경로**를 더 막은 것이고, 이번은 **가드가 과하게 막던 자리**를 연 것이다.
`WeakSet` 은 그대로 유지된다(막는 대상이 다르다).

### 결정 3 — #177: 003 이 아닌 프로브 실패는 "판정 불가"이고, 판정 불가면 목록을 그리지 않는다

**429 만이 아니라 003 이 아닌 모든 실패를 하나로 묶는다**(사용자 결정 2026-08-08). 규칙이 하나로
단순해지고, 오프라인에서도 같은 화면이 뜨는 것은 **옳다** — 어느 쪽이든 우리가 그 계정에 대해 알아낸
것이 없다는 사실은 같다.

- `AccountProbe` 에 **판정 실패를 담을 자리**를 만든다. 지금은 담을 필드가 없어 화면이 429 를 안다는
  사실 자체가 없다. 003 은 지금처럼 **영구 판정**이고, 그 외 실패는 **"확인하지 못함"** 이다.
- **판정하지 못한 계정이 있으면 목록을 그리지 않는다** — [[ADR-113]] 결정 3(*"모르는 동안은 보여주지도
  않는다"*)을 429 에도 적용한다. 그 자리에서 사용자가 볼 것은 결정 1 의 모달이다.
- 지금은 같은 ADR 의 **결정 3 과 결정 7 이 서로 반대 방향으로** 적용돼 있다 — 결정 3 은 모르는 동안
  목록을 미뤘는데, 프로브가 통째로 429 로 끝나면 **모르는 채로 확신에 찬 목록**을 그린다.
- 이것은 [[ADR-113]] 결정 7(*"실패한 프로브는 후보 자격을 유지한다"*)의 **정정**이다. **원칙은 그대로
  다** — *"모르는 실패를 영구로 단정하지 않는다"* 는 여전히 참이고, 003 만 영구인 것도 그대로다.
  바뀌는 것은 *"모른다"* 와 *"괜찮다"* 를 **같은 화면으로 그리지 않는다**는 것뿐이다.
- **`isSettled` 의 의미는 바꾸지 않는다**([[ADR-113]] 결정 4). 성공이 아니라 settle 기준인 것은 무한
  스피너를 막으려고 옳게 고른 것이고, 바뀌어야 하는 것은 settle **이후의 표시**다.
- 대표 캐릭터 오염도 같은 처방으로 사라진다 — 판정 못 한 계정은 목록에 서지 않으므로 그 계정의
  대표를 고를 일이 없다.

### 결정 4 — #178: `ErrorState` 가 그려지는 자리는 원인과 무관하게 진행 경로를 하나 이상 갖는다

[[ADR-114]] 결정 2(*"429 에는 액션을 주지 않는다"*)를 **`ErrorState` 자리에서만 정정**한다.

- **스탈 배너는 그대로다** — 배너는 아래에 목록이 남아 막다른 길이 아니다. 그 ADR 이 든 근거가
  배너에서는 여전히 참이므로 배너의 429·401 에 액션을 되살리지 않는다.
- `ErrorState` 는 **정의상 목록이 없는 자리**라 그 근거가 뒤집힌다. 액션을 빼면 화면에 아무 길도 없다.
- **다만 그 "진행 경로"가 반드시 `ErrorState` 안의 버튼일 필요는 없다.** 이 phase 에서 429 의 경로는
  **모달**이 제공한다(결정 1) — `ErrorState` 는 그 모달에 덮인다. 규칙은 *"자리마다 버튼을 달아라"* 가
  아니라 **"그 자리에서 사용자가 앞으로 갈 수 있어야 한다"** 이다.
- 그래서 **"429 에 재시도를 되살린다"가 아니다** — [[ADR-114]] 결정 2 의 판단(눌러도 또 429 인 버튼은
  "고칠 수 있다"는 잘못된 신호다)은 유효하다. 더하는 것은 **재시도가 아닌 다른 출구**다.
- `ErrorState.tsx:10` 의 컴포넌트 계약(`ErrorState … 액션 항상`)을 구현(`action?`)에 맞춘다 —
  **액션 없이 쓸 수 있는 조건**(그 자리의 진행 경로를 다른 것이 제공할 때)을 계약에 명시한다.

### 결정 5 — 429 를 실제로 줄이는 일은 이 ADR 이 하지 않는다

프로브·로스터·예열의 **fan-out 동시성 캡 부재**가 429 의 상류인데(중첩 `Promise.all`, 저장소 전체에
동시성 제한 유틸이 없다 — [[ADR-113]] 미해결), **사용자가 이번 범위에서 명시적으로 기각했다.**

> **429 발생 건수는 한 건도 줄지 않는다.** 이 ADR 이 바꾸는 것은 *막혔을 때 빠져나갈 길*뿐이다.

[[ADR-114]] 가 *"429 자체는 한 건도 줄지 않았다 — 바뀐 것은 화면이 하는 말뿐"* 이라고 적은 것과
**같은 한계가 그대로 남는다.** 그때는 화면이 사실대로 말하게 했고, 이번은 그 화면에서 나갈 수 있게
한다. 둘 다 429 를 만난 **뒤**를 다룬다.

- single-flight 부재도 그대로다(TTL 은 이미 끝난 요청만 접는다 — [[ADR-113]]).
- 자격 스윕이 429 를 삼켜 캐릭터가 조용히 사라지는 문제(`character-eligibility.ts` — 429 는
  `continue`)도 그대로다([[ADR-114]] "미해결로 남기는 사실" 첫 항목). **목록이 비는 실제 원인은
  여전히 이쪽이다.**

## 이유

- **결정 1 이 새 UI 를 만들지 않는 이유**: 무효 키와 429 는 원인이 다르지만 **처방이 같다** — 저장된
  키로는 앞으로 갈 수 없고, 사용자가 새 키를 넣어야 한다. 처방이 같으면 화면도 같아야 한다. 종류마다
  다른 알림을 만들면 문구·액션 표가 두 벌이 되고, 그것이 [[ADR-115]] 결정 9 가 새 `kind` 를 거부한
  이유이기도 하다.
- **결정 2 가 결정 1 의 조건인 이유**: 429 가 가장 많이 나는 자리가 온보딩(예열 직후 로스터 조회)인데
  가드가 `completed` 만 허용하면 **정작 잠긴 사람에게 모달이 안 뜬다.** 결정 1 만 하고 결정 2 를
  안 하면 #176 은 그대로 남는다.
- **결정 3 이 결정 1 과 묶여야 하는 이유**: 계정 선택에서 429 를 판정하기 시작하면 그 자리에 "볼 것이
  없는 화면"이 생긴다 — 목록도 없고 액션도 없다. 그 자리를 채우는 것이 결정 1 의 모달이다. 반대로
  결정 3 없이 결정 1 만 하면, 계정 선택은 429 를 **감지조차 못 하므로** 모달이 뜰 계기가 없다.
- **결정 4 가 규칙인 이유**: 지금까지 액션은 **원인별로** 정해졌고(401 은 이것, 429 는 저것), **자리
  단위로 잠기는지는 아무도 보지 않았다.** #176·#178 이 정확히 그 사각지대에서 나왔다. 규칙을 자리
  기준으로 세우면 다음에 원인이 하나 늘어도 같은 사고가 나지 않는다.

## 기각안

- **429 에 "다시 시도"를 되살린다** — 눌러도 또 429 다([[ADR-114]] 결정 2 의 판단은 유효하다).
  이 ADR 이 더하는 것은 재시도가 아닌 **다른 출구**다.
- **스탈 배너의 429·401 액션을 함께 되살린다** — 배너는 목록이 남아 막다른 길이 아니다. 정정 범위는
  `ErrorState` 뿐이다.
- **온보딩 실패 가지에 `계정 다시 선택` 만 넘긴다**(#176 의 "가장 작은 수정") — 계정을 바꿔도 **같은
  키라 429 는 그대로**다. 진짜 출구가 아니다.
- **온보딩 전체에 뒤로 가기를 넣는다**(#176 결정 필요 3) — 단계가 라우트가 아니라 `status` switch 라
  구조 변경이 크고, 되돌아가도 429 는 그대로다. 별건으로 남긴다.
- **fan-out 동시성 캡을 이 ADR 의 결정으로 삼는다** — 사용자가 이번 범위에서 명시적으로 기각했다
  (결정 5). 근본이지만 별건이다.
- **429 전용 알림 UI 를 새로 만든다** — 처방이 무효 키와 같아 화면이 같아야 한다(위 "이유").
- **`isSettled` 를 "성공 기준"으로 바꿔 판정 실패를 대기로 흡수한다** — [[ADR-113]] 결정 4 가 막은
  무한 스피너가 그대로 되살아난다. 바꿔야 하는 것은 settle **이후의 표시**다(결정 3).
- **판정 불가 계정을 "확인하지 못함" 중립 톤으로 표시하고 선택은 허용한다**(#177 결정 필요 1 의 ②) —
  고르면 그 다음이 #176 의 잠금이다. **들어갈 수 없는 문은 잠근다**([[ADR-086]] 결정 8 과 같은 판단).

## 대가/트레이드오프

- **일시적인 초당 한도에서도 사용자를 온보딩으로 내보낸다.** 모달에 닫기가 없으므로 429 가 몇 초 뒤
  풀리는 종류였어도 사용자는 키 입력 화면으로 간다. 429 응답(`OPENAPI00007`)에는 일 한도와 초당 한도의
  구분이 없어([[ADR-114]]) **구분할 수 없는 것을 구분해 다룰 수 없다.** 뒤 단계는 [[ADR-115]] 결정 4 의
  재개로 보존되므로 **잃는 것은 키를 한 번 다시 붙여넣는 것**이다.
- **429 로 키를 지우는데, 그 키가 다음 날이면 다시 쓸 수 있는 키일 수 있다.** 일 한도를 소진한
  개발 단계 키는 무효가 아니라 **오늘 소진된 것**이다. 그래도 지우는 이유는 [[ADR-115]] 결정 3 과
  같다 — 안 지우면 재시작 때 같은 키로 `completed` 에 복귀해 또 429 를 맞고, 사용자에게는
  *"재시작하면 되는 것처럼 보이다가 안 되는"* 상태가 된다. 같은 키를 다시 붙여넣는 것은 막지 않는다.
- **판정 불가 시 목록을 안 그리므로 429 가 잦은 계정은 계정 선택 자체가 막힌다**(결정 3). 그 자리의
  출구는 결정 1 의 모달이고, 그 외에는 없다. 이것은 **후퇴가 아니라 사실을 드러내는 것**이다 — 지금은
  고를 수 있어 보이지만 고르면 #176 의 잠금이다.
- **오프라인에서도 계정 선택에 429 와 같은 화면이 뜬다**(결정 3 이 003 아닌 실패를 하나로 묶은 대가).
  규칙이 하나여서 얻는 단순함과 맞바꾼 것이고, 어느 쪽이든 그 계정에 대해 알아낸 것이 없다는 사실은
  같다. 다만 **문구는 429 를 말하므로** 오프라인 사용자에게는 어긋난 안내가 갈 수 있다.
- **모달이 뜨는 자리가 늘어난다.** [[ADR-115]] 는 `completed` 한 구간에서만 떴는데 이제 온보딩 중에도
  뜬다. 결정 2 의 가드가 좁아진 만큼 **오탐의 대가도 커진다** — 429 판정이 틀리면 온보딩 중인 사용자의
  키까지 지운다.
- **429 자체는 한 건도 줄지 않는다**(결정 5). 사용자는 새 키를 넣기 전까지 같은 자리에 다시 도달할 수
  있고, 서비스 단계 키를 받는 것은 앱 밖의 일이다([[ADR-110]] 가이드 페이지가 그 자리다).

## 범위 밖

맥락으로만 적는다 — **결정이 아니므로 이 phase 에서 구현하지 않는다.**

- **fan-out 동시성 캡·프리플라이트·single-flight** — 결정 5. 429 를 실제로 줄이는 쪽.
- **자격 스윕이 429 를 삼켜 캐릭터가 조용히 사라지는 문제** — [[ADR-114]] 가 남긴 그대로.
  **목록이 비는 실제 원인은 여전히 이쪽이다.**
- **온보딩 전체의 뒤로 가기**(#176 결정 필요 3) — 단계 구조 변경이라 별건.
- **설정의 "API 키 변경" 행 부활** — [[ADR-115]] 결정 8, #135 와 함께.

## 폐기

- [[ADR-113]] 결정 7 의 **"실패한 프로브는 후보 자격을 유지한다"** 중 *"그래서 그 계정을 정상 목록에
  함께 그린다"* 부분 — 결정 3 으로 정정. **003 만 영구로 다룬다는 규칙과 "모르는 실패를 영구로
  단정하지 않는다"는 원칙은 그대로 선다**(폐기가 아니라 표시 방식이 갈린 것이다).
- [[ADR-114]] 결정 2 의 **"429 에는 액션을 주지 않는다"** 중 **`ErrorState` 자리** — 결정 4 로 정정.
  **스탈 배너·토스트에서는 그대로 유효하다**(배너는 목록이 남아 막다른 길이 아니다).
- [[ADR-115]] 결정 6 의 가드 조건 **"`completed` 일 때만 무효화가 성립한다"** — 결정 2 로
  **"키 입력 화면(`awaitingApiKey`·`verifyingApiKey`)에서는 알리지 않는다"** 로 대체. 멱등성(동시
  실패 → 모달 하나)과 재이동 루프 불가는 그대로 유지된다.

## 구현하며 정정한 것

설계(결정 1~5)에서 벗어난 곳은 없다. 아래는 **설계가 정하지 않은 자리를 구현이 정한 것**과, 구현
중에 드러나 되돌린 것이다.

1. **모달의 켜짐 판정을 `=== null` 이 아니라 falsy 로** (step 1) — `apiKeyNotice === null` 이면 스토어를
   **부분 모킹**한 테스트에서 `undefined` 가 와 **모든 라우트 위에 닫을 수 없는 모달이 떴다**
   (`route-splitting` 5건이 실제로 그렇게 깨졌다). 차단 UI 는 *"켜라고 명시했을 때만"* 켜지는 쪽이
   안전하다. 근거를 코드 주석에 남겼다.
2. **"먼저 뜬 원인을 유지한다"가 두 겹으로 구현됐다** (step 1) — 리듀서가 `apiKeyNotice !== null` 이면
   **같은 state 객체를 그대로 반환**하고(불필요한 렌더도 안 만든다), 스토어 가드가 그 앞에서 한 번 더
   막는다. 결정 2 는 규칙만 정했고 어느 층인지는 정하지 않았다.
3. **아이콘이 원인을 가리키고 톤은 갈리지 않는다** (step 2) — 결정 1 의 표는 문구만 정했다. 무효 키는
   `KeyRound`, 429 는 계기판(`Gauge`)이고 톤은 둘 다 `error` 다(429 도 어미 규칙상 실패이고
   error-resilience.md 실패 표에 함께 선다). `TimerOff` 계열은 *"시간이 지나면 풀린다"* 가 읽혀
   처방(키 단계 확인)과 어긋나 배제했다.
4. **이름이 원인 하나에 묶여 있던 것을 전부 풀었다** (step 2·3) — `ApiKeyInvalidModal` →
   `ApiKeyNoticeModal`, `use-api-key-invalidation` → `use-api-key-notice`,
   `api-key-invalid-overlay` → `api-key-notice-overlay`(전부 `git mv` 로 이력 보존).
5. **429 의 토스트를 뗐다** (step 3) — 결정 1 은 모달을 정했을 뿐 옛 토스트를 어떻게 할지 말하지
   않았다. `use-sync-error-toast` 에서 429 를 401 과 같이 조기 반환시켰다 — 모달이 원인과 처방을 함께
   말하므로 **같은 사실을 두 번 말하지 않는다**. `format.ts` 의 `rateLimited` case 는 `assertNever`
   소진 가드라 그대로 둔다.
6. **`changeApiKey` 는 계속 미배선이다** (step 3) — [[ADR-115]] 결정 8 그대로. 그 경로의 실패는
   *"방금 나쁜 키를 입력한 것"* 이라 성질이 다르다. 429 도 진입점을 부르지 않는다는 단언을 새로 넣었다.
7. **프로브 재시도(`retry`)를 훅이 새로 갖는다** (step 4) — 결정 3 은 *"목록을 그리지 않는다"* 까지만
   정했고 그 자리의 비-429 원인에는 재시도가 실제 처방이라 수단이 필요했다. `attempt` 카운터를 effect
   deps 에 넣고 `ProbeRun` 이 `source`+`attempt` 로 세대를 가른다(계정 참조가 바뀔 때와 같은 방식).
8. **대표 후보를 "확인된 캐릭터"로 좁혔다 — 결정 3 이 말한 것보다 한 겹 더** (step 4). 결정 3 본문은
   대표 오염이 *"판정 못 한 계정은 목록에 서지 않으므로"* 저절로 사라진다고 적었는데, 구현은 후보
   집합 자체를 `!unavailableOcids.has(ocid)` → `confirmedOcids.has(ocid)` 로 바꿔 **회귀 가드**를
   하나 더 뒀다([[ADR-068]] 결정 4 가 없앤 문제의 429 판이 다른 경로로 되살아나지 않게).
9. **`undeterminedProbeErrors()` 헬퍼를 만들었다가 인라인으로 되돌렸다** (step 4) — 범위 밖 테스트
   2파일(`OnboardingScreen`·`AccountFlowStatus`)이 그 모듈을 통째로 목으로 덮고 있어 깨졌다. 호출부가
   1곳뿐이라 화면 안 한 줄로 인라인해 해소했다(단일 사용 추상 금지 규칙과도 맞다).
10. **결정 4 는 코드를 거의 안 바꿨다** (step 5) — src 변경이 `ErrorState.tsx` 의 주석·JSDoc 한 파일
    뿐이고 **새 UI 는 0개**다. 세 자리의 출구는 결정 1 의 모달과 껍데기(`닫기`·`취소`)가 이미 주고
    있어, 이 step 이 한 일은 **규칙을 세우고 세 자리가 그것을 지키는지 테스트로 고정한 것**이다.
    #178 이 지적한 `EmptyState` ↔ 피커 루프도 step 1~3 으로 **이미 끊겨 있었다**(피커를 여는 순간
    로스터 429 가 진입점을 불러 모달이 덮는다) — 코드를 더 고치지 않고 확인 테스트만 넣었다.
11. **step 1 은 실행 중 status 갱신에 실패해 `error` 로 남았고 남은 뒷정리를 사람이 마쳤다** — 테스트
    3파일의 스탈 mock 이름 교체와 `route-splitting` mock 보강. 그 실패가 정정 1 의 결함을 드러냈다.

**자동 테스트가 담보하지 못하는 것**

1. **실제 429 를 한 번도 받아 본 적이 없다.** 전 경로가 **주입된 `rateLimited`** 다 — `nexon/http`
   (429 → `NexonRateLimitError`) → `toScheduleSyncError` → 진입점 → 모달까지가 **실제 429 응답에서**
   이어지는지는 모른다. 개발 단계 키로 실기기 재현을 하지 않았다. [[ADR-114]] 가 같은 항목을
   미확인으로 남겼고 **여전히 미확인이다.**
2. **429 는 한 건도 줄지 않았다**(결정 5). fan-out 동시성 캡이 범위 밖이라 **상류는 그대로**다 —
   프로브는 전 계정 × 전 캐릭터를 한 번에 부르고, 자격 스윕이 429 를 삼켜 캐릭터가 조용히 사라지는
   문제([[ADR-114]] "범위 밖")도 그대로다. **목록이 비는 실제 원인은 여전히 그쪽이다.** 이 phase 가
   바꾼 것은 *막혔을 때 빠져나갈 길*뿐이다.
3. **일시적인 초당 한도에서도 사용자를 온보딩으로 내보내는 것이 실사용에서 옳은지** — 모달에 닫기가
   없고 429 응답에 일/초당 구분이 없어 **구분할 수 없는 것을 구분해 다룰 수 없다.** 몇 초 뒤 풀렸을
   실패에도 키 입력 화면으로 간다(잃는 것은 [[ADR-115]] 결정 4 의 재개 덕에 키를 한 번 다시 붙여넣는
   것). 눈으로만 판정된다.
4. **429 로 지운 키가 다음 날이면 다시 쓸 수 있는 키일 수 있다** — 일 한도를 소진한 개발 단계 키는
   무효가 아니라 **오늘 소진된 것**이다. 그래도 지우는 근거는 [[ADR-115]] 결정 3 과 같지만
   (안 지우면 *"재시작하면 되는 것처럼 보이다가 안 되는"* 상태), 같은 키를 다시 붙여넣게 되는 사용자가
   그것을 납득하는지는 확인되지 않았다.
5. **모달이 온보딩 중에 뜨는 체감** — 키를 넣고 계정을 고르고 예열까지 통과한 사용자에게 "처음부터
   다시"처럼 읽히는지.
6. **새 키를 받으러 실제로 나가는지** — 서비스 단계 신청은 앱 밖의 일이라([[ADR-110]] 가이드) 문구가
   거기까지 데려가는지는 사람에게 물어야 안다([[ADR-114]] 가 남긴 같은 질문).
7. **`App.test.tsx` 의 탭 이동 스크롤 3건이 전체 스위트 8회 중 1회 실패한 관측**(step 5) — 이 phase 가
   건드리지 않은 파일이고 `React.lazy` 청크 해석 타이밍에 의존하는 동기 단언이라 **기존 flaky** 로
   판단했다(재현 7회·격리 3회·기준선 3회 전부 통과). 관측된 사실이라 남긴다.
