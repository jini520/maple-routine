# ADR-345: 스키마 검토에서 나온 것을 한 묶음으로 고친다

> ⚪ 미구현 · 2026-10-12 · 설계 · 사용자 지정

> 사용자 지정(2026-10-12): 검토하면서 나온 것은 **설계만 해 두고 한꺼번에** 고친다. 그래서 이
> 문서는 결정을 쌓는 자리이고, 검토가 끝나면 한 묶음으로 착수한다.

**관련**: [[ADR-340]](서버 쪽 사람 표) · [[ADR-342]](드롭 기록이 uuid 로 자기를 가리킨다. 식별자
규칙을 처음 적용한 자리) · [[ADR-343]](대기 표) · [[ADR-038]](기기 보스 표의 복합 PK 가 여기서 왔다) ·
[[ADR-320]](토큰 보관. 결정 2 가 그 문서의 결정 6 을 정정한다)

## 맥락

### 검토 대상과 원천

서버 Postgres 7개 표와 기기 SQLite 14개 표를 식별자 규칙으로 훑었다. 숫자는 손으로 옮겨 적지
않았다 - 서버는 운영 DB 의 `pg_dump -s`, 기기는 `node:sqlite` 로 `storage/sqlite/db.ts` 를 실제로
열어 받은 `PRAGMA table_info` 다.

검토 노트: https://claude.ai/artifact/CCKYroX7fBS2eGFamK2E9d

### 규칙은 이미 있고 적용이 덜 됐다

**PK 는 항상 uuid 한 칸이고 자연키는 단일 `UNIQUE`** 가 이 저장소의 규칙이다. 지난 세션에 규칙을
안 지키는 곳도 따르게 하기로 했는데, 실제로 옮긴 것은 서버 표 셋과 기기 표 하나다. 기기에 복합 PK
일곱이 남아 있고 그중 `boss_profit_records` 는 **PK 에 `difficulty` 가 들어 있어** 난이도가 확정될
때 행을 옮겨야 한다 - 그것이 `boss_drop_records` 를 uuid 로 옮긴 바로 그 이유였다.

## 결정

### 결정 1. `platform` 과 `notices.kind` 를 ENUM 타입으로 든다 (사용자 지정)

지금 셋 다 `text NOT NULL` 이고 값 집합은 앱 코드의 `isPlatform` · `isNoticeKind` 에만 있다.

```sql
CREATE TYPE platform    AS ENUM ('ios', 'android');
CREATE TYPE notice_kind AS ENUM ('app', 'game', 'event', 'update', 'cash');
```

| 칸 | 지금 | 틀렸을 때 나는 증상 |
|---|---|---|
| `nexon_sessions.platform` | `text` | 로그인은 되고 **14일 뒤 갱신만** 조용히 실패한다. 세션을 만든 쌍과 다른 쌍으로 갱신을 부르면 넥슨이 거절하기 때문이다 |
| `nexon_login_attempts.platform` | `text` | 교환이 다른 쌍으로 나가 실패한다 |
| `notices.kind` | `text` | 앱이 그 분류를 안 가져가서 **공지가 조용히 안 보인다** |

셋 다 **에러가 아니라 나중에 조용히 실패하는** 모양이라 DB 가 그 자리에서 막는 쪽이 낫다. 같은
이유로 `api_key_hash` 에 모양 검사를 뒀다([[ADR-340]] 결정 5).

**`CHECK` 가 아니라 ENUM 인 근거.** PG 16 에서 재 봤다(2026-10-12).

| | ENUM | `CHECK` |
|---|---|---|
| 값을 더할 때 | `ALTER TYPE … ADD VALUE` **한 문장**. 표를 안 훑는다 | 제약을 내리고 다시 거는 두 문장. `ADD` 가 표 전체를 검증한다 |
| 이름을 바꿀 때 | `RENAME VALUE` 하나. **저장된 행도 따라온다** | 제약을 바꾸고 행을 `UPDATE` 로 따로 고친다 |
| 값을 뺄 때 | **`DROP VALUE` 가 없다.** 타입을 다시 만들고 의존 칸을 재작성한다 | 두 문장 |
| 여러 표가 공유할 때 | 타입 하나가 진실 | 칸마다 다시 적어 갈릴 수 있다 |

빼는 것이 어렵지만 **이 두 칸은 빠진 적이 없다** - `notices.kind` 는 `app` 하나에서 넷이 늘었고
줄어든 적은 없다. `platform` 은 표 둘이 공유하므로 타입 하나로 두는 실익이 실제로 있다.

**운영 규칙 하나.** 값을 더하는 마이그레이션은 **그 값으로 쓰지 않는다.** PG 16 은 같은 트랜잭션에서
더한 값을 쓰면 `unsafe use of new value` 로 거부하고, `node-pg-migrate` 9 가 마이그레이션을
트랜잭션으로 감싼다. 백필이 필요하면 파일을 둘로 가른다. 조용히 실패하는 것이 아니라 에러라 밟아도
그 자리에서 보인다.

**대가**: 값을 더한 마이그레이션의 `down` 이 no-op 이다. 되돌릴 수단이 없어 안 쓰이는 값 하나가
남는다. 해로운 상태는 아니고, `users.last_seen_at` 을 걷을 때 받아들인 「값은 못 돌아온다」와 같은
등급이다.

### 결정 2. 액세스 토큰의 만료는 서버만 안다. 앱은 부르기 직전에 묻는다 (사용자 지정)

앱이 `accessExpiresAt` 을 저장해 **기기 시계로** 판정하는 것을 걷는다. 앱이 드는 것은 세션
하나이고, 넥슨을 부르기 직전에 `/v1/auth/nexon/token` 을 불러 쓸 수 있는 토큰을 받는다.

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 만료 시각을 드는 곳 | 앱(`login.accessExpiresAt`)과 서버 둘 | 서버만 |
| 판정하는 시계 | 앱은 기기 시계 · 서버는 서버 시계 | 서버 시계 하나 |
| 앱이 아는 것 | 세션 · 토큰 · 만료 | 세션 · 토큰 |

**기기 시계로 남이 적은 값을 보는 것이 어긋나는 자리다.** 기기 시계가 앞서 있으면 멀쩡한 토큰을
버리고 받으러 가고, 뒤처져 있으면 죽은 토큰으로 부른다. 서버는 자기 시계로 자기가 적은 값을 보므로
그 어긋남이 없다.

**서버는 이미 이렇게 돌고 있다**(`auth-routes.ts` 의 `resolveSession`). 바뀌는 것은 앱 쪽뿐이다 -
`current-credential.ts` 의 `needsToken` 과 `RENEW_MARGIN_MS` 를 걷고, 저장 형식에서
`accessExpiresAt` 을 뺀다.

**[[ADR-320]] 결정 6 을 정정한다**(기기에서 만료를 판정하는 부분). 그 결정의 나머지는 그대로
살아 있다 - 부르기 **직전에** 챙기는 것은 유지되고, 그때 묻는 상대가 저장된 만료 시각에서 서버로
바뀐다. **결정 1 은 안 건드린다** - 앱이 넥슨을 직접 부르고 `client_secret` 과 갱신 토큰이 서버에
남는 모양이 그대로다.

**회차마다 한 번 묻는다.** 호출마다 묻는 모양이면 강화 내역 한 회차에 `/token` 이 124번 나가고,
동시 3이라 갱신이 겹칠 수 있다(결정 4).

**기각 - 앱이 혼자 교환·갱신한다.** 넥슨이 기밀 클라이언트만 받아 못 한다(실측 2026-10-12).
`code_challenge` 를 실은 authorize 는 통과하지만, 교환에서 `client_secret` 을 빼면 `verifier` 가
있든 없든 `OPENAPI00004 Required request parameter 'client_secret' … is not present` 다. 비밀을 앱
번들에 넣으면 누구나 우리 `client_id` 행세로 동의 화면을 띄워 사용자 토큰을 받는다.

**기각 - `/token` 이 올 때마다 무조건 갱신한다.** 만료 판정과 액세스 토큰 보관을 서버에서 걷을 수
있어 더 단순해 보이지만, 넥슨이 갱신 토큰을 **회전**시키므로 겹친 두 요청이 서로를 죽인다. 막으려면
**기다리는** 자물쇠가 필요하고(지금 `single-runner.ts` 의 것은 못 잡으면 건너뛰는 모양이라 요청
경로에 못 쓴다), 그 자물쇠의 자연스러운 최적화가 「앞 사람이 방금 받았으면 그걸 쓴다」인데 그것이 곧
걷으려던 **만료 판정과 토큰 보관**이다. 걷으려던 둘이 그대로 돌아온다.

### 결정 3. 갱신 여유를 5분으로 둔다 (사용자 지정)

```
REFRESH_MARGIN_MS = 5 * 60 * 1000   // 유효 수명 25분
```

**여유는 앞당기는 시간이 아니라 앱에 보장하는 최소 잔여 시간이다.** `needsRefresh` 가
`잔여 ≤ 여유` 에서 갱신하므로, 앱이 `/token` 에서 나올 때 토큰은 늘 여유보다 많이 남아 있다 - 안
걸렸으면 여유 초과가 남아서, 걸렸으면 30분이 새로 차서.

**전형적인 회차를 덮는 값이다.** 넥슨 확률 기록 경로의 왕복을 쟀다(2026-10-12, `count=1000` 한 쪽
전체). **90~140ms**. 강화 내역 124작업을 동시 3으로 돌리면 42회차라 **4초**이고, 창 채우기 84작업이
같은 회차에 겹쳐도 비슷한 자리다. LTE 로 5배를 쳐도 20초다.

**모든 회차를 덮지는 못한다.** 날짜마다 커서를 최대 50쪽 따라가므로(`MAX_PAGES`) 최악은
124 × 50 = 6,200콜이고 측정값으로도 3.5분이다. 어떤 여유로도 30분을 넘는 회차는 못 덮는다. 그
꼬리는 [[ADR-320]] 결정 5 의 401 재시도가 받는다 - 여유는 재시도가 **드물게** 일어나게 하는 값이고
보장이 아니다.

**키워도 비용이 안 든다.** 40분을 연속으로 쓰는 사람의 갱신 횟수가 여유 1분이면 2회, 5분이면 2회,
10분이어도 2회다(`⌈40/25⌉ = 2`). 15분을 넘겨야 3회가 된다.

**그래서 상한의 근거는 호출 수가 아니라 갱신 토큰 회전 횟수다.** 회전마다 쓰기가 한 번이고 그
쓰기가 실패하면 사슬이 끊긴다. 10분을 넘길 이유가 없다.

**0 일 수 없는 이유.** 서버는 `accessExpiresAt = 응답받은 시각 + 1800` 으로 적는데 넥슨이 발급한
시각은 그보다 왕복 하나만큼 이르다. 서버의 추정이 늘 실제보다 늦어서, 0 이면 넥슨이 먼저 죽는다.

### 결정 4. 겹치는 갱신은 앱이 막는다. 서버에 자물쇠를 안 붙인다

`renewNexonAccessToken` 이 **같은 요청을 하나로 묶게** 한다. 이미 나간 호출이 있으면 그 약속을
돌려주고, 새로 안 띄운다.

**세션 하나는 기기 하나의 것이다.** 로그인 교환마다 `nexon_sessions` 행이 하나 생기고 앱은 그중
하나를 든다. 그래서 같은 세션의 갱신이 겹치는 일은 **한 앱 프로세스 안에서만** 생기고, 앱에서
묶으면 서버에 자물쇠가 필요 없다. 붙였을 때 따라오는 것 다섯을 전부 안 진다 - 요청이 줄 서서
직렬화되는 것, HTTP 요청이 매달리는 것, `pg.Pool` 에서 잡은 연결과 푸는 연결이 달라 안 풀리는 것,
대기 상한을 따로 설계하는 것, 사람 id 를 64비트 자물쇠 번호로 접을 때의 충돌.

**지금 묶여 있지 않다.** `renewNexonAccessToken` 에 그 장치가 없어, 동시에 부르면 각자 `/token` 을
때린다. 강화 내역이 동시 3으로 도는 중 셋이 함께 401 을 받으면 갱신이 셋 나간다.

**안 쟀다** - 넥슨이 **옛 갱신 토큰을 즉시 무효화하는지**. 회전해서 새 값을 주는 것은 실측이지만,
옛 값으로 한 번 더 되는지는 안 봤다. 즉시 무효화하지 않으면 이 경합의 피해가 없다. 재는 데
로그인 한 번과 갱신 두 번이 든다.

## 아직 결정 전

검토가 이어지는 동안 아래가 결정으로 올라온다. 지금은 **소견**이다.

- **기기 표 일곱의 복합 PK.** `boss_profit_records` · `boss_party_settings` ·
  `boss_party_period_overrides` · `boss_profit_period_checks` · `character_accounts` ·
  `enhancement_history_checks` · `mvp_grade_history`. 옮기면 그 표의 조회가 전체 스캔이 되므로
  **인덱스를 함께 세워야 한다**(`boss_drop_records` 가 그렇게 했다).
- **가계부 두 표의 대리키.** `income_records.id` · `spend_records.id` 가
  `시각(36진) + Math.random()` 이다. 코드에 적힌 근거는 「Hermes 에 `crypto.randomUUID` 가 없다」인데
  그 전제가 사라졌다 - `storage/sqlite/uuid.ts` 의 `NEW_UUID_SQL` 이 SQLite 에서 v4 uuid 를 만든다.
- **서버 `nexon_login_attempts.state` 가 PK 다.** 어제 uuid 로 옮긴 표 셋에서 이것만 빠졌다. 1회용
  행이고 `state` 가 곧 조회 열쇠라 실무상 문제는 없다.
- **자연키 한 칸으로 선 표 셋.** `character_profiles(ocid)` · `character_world_leaps(from_ocid)` ·
  `enhancement_history(id)`. 복합키는 아니고 넥슨이 발급한 값이 곧 PK 다. 대리키를 더해 얻는 것이
  없는 자리라 **규칙의 예외로 둘지**가 결정이다.
- **기기 DB 에 인덱스가 하나뿐이다**(`boss_drop_records_group`). 복합 PK 가 곧 인덱스였기 때문이다.
- **[[ADR-320]] 결정 5 의 전제가 측정으로 약해졌다.** 그 문서는 「강화 내역 수백 건이 30분을 넘길
  수 있다」고 적었는데, 전형적인 회차는 4초이고 커서가 최대로 도는 최악이 3.5분이다(결정 3 의
  측정). 401 재시도 자체는 그대로 필요하다 - 토큰이 없는 경우와 30분을 넘는 회차가 남는다.

## 열린 질문

- 한 묶음을 **한 마이그레이션**으로 두나, 표마다 가르나. 기기 쪽은 `DB_VERSION` 하나가 여러 표를
  다시 쓰는 모양이 되고, 그 이관은 사용자 기기마다 따로 돌아 결과를 확인할 길이 없다.
- 기기 복합 PK 를 옮길 때 **옛 PK 조각으로 서버에 보낸 것이 있나**. 없으면 소급 영향이 없다.
- **회차 중간에 받은 새 토큰을 그 회차가 집어 쓰나.** `collect.ts` 가 자격을 회차 시작에 한 번
  잡아 124 작업에 돌려쓴다. 중간에 만료되면 `nexon/http.ts` 가 그 호출을 갱신해 재시도하지만 잡아
  둔 값은 그대로라, **남은 작업이 각자 401 을 한 번씩 더 받는다**. 측정값으로 작업당 0.1초,
  최악 12초다. 회차마다 한 번 묻는 모양(결정 2)을 깨지 않고 고치려면 `requestJson` 이 자격을
  값이 아니라 **읽는 함수**로 받아야 한다.
- **옛 갱신 토큰이 즉시 죽나**(결정 4 의 안 잰 것). 안 죽으면 겹친 갱신의 피해가 없어 앱의 단일
  비행이 최적화로 내려간다.
