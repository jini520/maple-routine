## 맥락

### 검토 대상과 원천

서버 Postgres 6개 표와 기기 SQLite 14개 표를 훑었다. 숫자는 손으로 옮겨 적지 않았다 - 서버는
운영 DB 의 `pg_dump -s`, 기기는 `node:sqlite` 로 `storage/sqlite/db.ts` 를 실제로 열어 받은
`PRAGMA table_info` 다. 그 뒤 로그인 경로를 넥슨 개발 가이드와 맞춰 보면서 설계가 바뀌었다.

### 넥슨 가이드라인이 로그인 모양을 정한다

개발 가이드의 두 탭에 셋이 적혀 있다.

- **안전한 토큰 관리**: `유저의 인가 코드를 사용해 발급 받은 Access Token은 반드시 서버에서만
  관리하고 사용합니다.`
- **State 파라미터 사용**: `State 파라미터는 … 이후 Redirect URI에서 올바른 요청인지 확인하는
  데에 사용됩니다.` · `State 값은 제3자가 접근할 수 없는 안전한 곳에 보관해야 합니다.` ·
  `한번 인증에 사용된 State 값은 재사용 불가능하도록 구성합니다.`
- **인가 코드 발급 요청**: `redirect_uri` 파라미터 예시가 `http://test.io/login` 이고 응답 예시가
  `302 Found Location: http://test.io/login?code=…&state=…` 다. **이 문서는 서버가 리다이렉트를
  받는 것을 전제로 쓰여 있고** 커스텀 스킴은 나오지 않는다.

**셋이 같은 한 점을 가리킨다.** 토큰을 서버만 쓰려면 교환을 서버가 해야 하고, state 를 Redirect
URI 에서 확인해야 하므로 그 Redirect URI 가 서버여야 한다. `redirect_uri` 를 서버의 https 주소로
두는 것은 예외적 선택이 아니라 **스펙의 기본형으로 돌아가는 것**이다.

`nexon-oauth.ts` 가 적은 `등록 화면이 iOS 와 안드로이드를 받아서 https 콜백이 필요 없다` 는
**안 필요하다는 관찰이었고 안 받는다는 뜻이 아니었다.**

### 지금 코드가 어기는 것

| 가이드라인 | 지금 |
|---|---|
| 토큰을 서버에서만 **관리** | `/session`·`/token` 이 앱에 넘기고 앱이 Preferences **평문**에 적는다 |
| 토큰을 서버에서만 **사용** | 앱이 프렌즈 API 를 직접 부른다 |
| state 를 Redirect URI 에서 확인 | 앱이 받아 앱이 확인한다 |
| state 를 제3자가 못 보는 곳에 | 커스텀 스킴 콜백으로 노출된다 |
| HTTPS · `client_secret` 서버 보관 | 지킨다 |
| state 재사용 불가 | `DELETE … RETURNING` 으로 지킨다 |

**실제 위반은 0 이다.** 앱에서 넥슨 로그인이 꺼져 있어 이 경로를 타는 사용자가 없다. 다만
**로그인을 켜기 전에 이 설계가 먼저 들어가야 한다.**

### 콜백 가로채기가 안드로이드에서 막히지 않는다

redirect URI 가 커스텀 스킴(`com.mapleroutine.app://oauth/callback`)이고 넥슨이 안드로이드
등록에서 서명 해시를 안 받아, 같은 스킴을 선언한 다른 앱이 콜백의 `code` 와 `state` 를 받을 수
있다. `verifier` 가 그것을 거르려고 둔 칸인데 **그 자리가 비어 있다.**

```
1. 악성 앱이 콜백을 가로챈다        code_진짜 · state_진짜
2. 악성 앱이 /start 를 직접 부른다   state_악성 · verifier_악성   (인증이 없다)
3. { code: code_진짜, state: state_악성, verifier: verifier_악성 } 으로 /session
```

서버는 `state_악성` 으로 줄을 찾고 `verifier_악성` 이 맞아 통과시킨 뒤 `code_진짜` 를 교환한다.
**`code` 와 `state` 를 묶는 끈이 아무 데도 없다** - 넥슨은 교환 요청에서 `state` 를 안 받고
(파라미터 표가 `grant_type` · `client_id` · `client_secret` · `code` 넷이다) 서버도 그 `code` 가
어느 짝에서 나왔는지 모른다. 서버가 확인하는 것은 **이 호출자가 우리와 로그인을 시작한 적이
있다** 까지이고 **이 `code` 를 만든 그 로그인을 시작했다** 는 확인이 안 된다.

**iOS 는 해당하지 않는다.** 앱이 `openAuthSessionAsync` 로 열고(`features/auth/nexon-login.ts`)
iOS 에서는 그것이 `ASWebAuthenticationSession` 이라 콜백 URL 이 그 세션에만 돌아온다 - 스킴
등록표를 안 거치므로 다른 앱이 끼어들 자리가 없다. 안드로이드는 Custom Tabs 뒤 딥링크가 보통의
인텐트 해석을 타서 노출된다.

### 버린 길 - PKCE

**비밀을 대신하지 못한다**(실측 2026-10-12). `code_challenge` 를 실은 authorize 는 통과하지만
교환에서 `client_secret` 을 빼면 `verifier` 가 있든 없든
`OPENAPI00004 Required request parameter 'client_secret' … is not present` 다.

**`code` 의 자물쇠도 못 된다**(실측 2026-10-14). `code_challenge = S256(A)` 를 실어 로그인하고
교환에 `code_verifier = B`(길이가 같은 다른 난수)를 비밀과 함께 보냈더니 **`200` 에 토큰이 왔다.**
넥슨은 challenge 를 받아 두고 검사하지 않는다. `authorize` 파라미터 표에도 PKCE 가 없다.

**둘은 다른 질문이고 둘 다 아니다.** 그래서 `code` 를 authorize 요청에 묶는 길은 **서버가 콜백을
직접 받는 것** 하나뿐이고, 그 사실이 이 문서의 설계를 정했다.

### https 콜백이 동작한다 (실측 2026-10-14)

redirect URI 칸이 **5개**라 검수 중인 기존 값을 건드리지 않고 새 애플리케이션에
`https://mapleroutine.store/v1/auth/nexon/callback` 을 등록해 쟀다.

```
"GET /v1/auth/nexon/callback?code=<가림>&state=probe-https-1014 HTTP/2.0" 404
  Referer: https://openid.nexon.com/
```

404 는 라우트가 아직 없어서다. **`code` 와 `state` 가 한 요청에 실려 우리 서버에 닿았다** 는 것이
요점이다.

**인가 코드가 nginx `access.log` 에 두 줄 남는다.** 기본 `combined` 형식이 `$request` 를 쿼리까지
찍고, 브라우저가 이어 요청하는 `/favicon.ico` 의 `Referer` 에 한 번 더 들어간다.

**검수 중인 애플리케이션 둘은 수정할 수 없다**(사용자 확인). https URI 를 그 둘에 등록하는 것이
선행 조건이라 이 문서의 로그인 결정은 검수가 끝난 뒤에 착수한다.

### 갱신 토큰은 회전하고 겹치면 하나만 이긴다 (실측 2026-10-12)

```
① code 교환        200   R1
② R1 로 갱신       200   R2        회전한다
③ R1 재사용        400   OPENAPI00012 Invalid Token
④ 같은 토큰 동시 둘  A 400 OPENAPI00012  /  B 200
```

`resolveSession` 은 갱신이 거절되면 `deleteNexonSession` 을 부르므로 **진 쪽이 세션 행을 지운다.**
멀쩡한 토큰을 방금 받았는데 세션이 사라지고 사용자는 재로그인을 본다. 이것이 결정 2 의 근거다.

### 규칙은 이미 있고 적용이 덜 됐다

**PK 는 항상 uuid 한 칸이고 자연키는 단일 `UNIQUE`** 가 이 저장소의 규칙이다. 서버 표 다섯은
옮겼고 기기에 복합 PK 일곱이 남아 있다. 그중 `boss_profit_records` 는 **PK 에 `difficulty` 가
들어 있어** 난이도가 확정될 때 행을 옮겨야 한다 - 그것이 `boss_drop_records` 를 uuid 로 옮긴 바로
그 이유였다([[ADR-342]]).

### 이 설계로 불필요해진 것

옛 본문의 결정 셋이 **설계가 바뀌어 할 말이 없어졌다.** 되살리지 않기 위해 적어 둔다.

- **앱이 만료를 모르게 한다 · 갱신 여유를 5분으로.** 토큰이 기기에 아예 없으면 만료를 숨길 대상이
  없다. 앱에서 `accessExpiresAt` · `RENEW_MARGIN_MS` · `needsToken()` 이 통째로 사라진다.
- **겹치는 갱신을 앱이 단일 비행으로 막는다.** 앱이 갱신을 부르는 자리가 없어진다. 갱신은
  [[ADR-346]] 의 팬아웃 안에서 서버가 하고, 요청 하나에 `resolveSession` 이 한 번이라 세션에
  동시성이 안 생긴다.

## 결정

### 결정 1. `platform` 과 `notices.kind` 를 ENUM 타입으로 든다 (사용자 지정)

지금 셋 다 `text NOT NULL` 이고 값 집합은 앱 코드의 `isPlatform` · `isNoticeKind` 에만 있다.

```sql
CREATE TYPE platform    AS ENUM ('ios', 'android');
CREATE TYPE notice_kind AS ENUM ('app', 'game', 'event', 'update', 'cash');
```

| 칸 | 지금 | 틀렸을 때 나는 증상 |
|---|---|---|
| `nexon_sessions.platform` | `text` | 로그인은 되고 **14일 뒤 갱신만** 조용히 실패한다. 세션을 만든 쌍과 다른 쌍으로 갱신을 부르면 넥슨이 거절하기 때문이다 |
| `nexon_login_attempts.platform` | `text` | 교환이 다른 쌍으로 나가 실패한다 |
| `notices.kind` | `text` | 앱이 그 분류를 안 가져가서 **공지가 조용히 안 보인다** |

셋 다 **에러가 아니라 나중에 조용히 실패하는** 모양이라 DB 가 그 자리에서 막는 쪽이 낫다. 같은
이유로 `api_key_hash` 에 모양 검사를 뒀다([[ADR-340]] 결정 5).

**`CHECK` 가 아니라 ENUM 인 근거.** PG 16 에서 재 봤다(2026-10-12).

| | ENUM | `CHECK` |
|---|---|---|
| 값을 더할 때 | `ALTER TYPE … ADD VALUE` **한 문장**. 표를 안 훑는다 | 제약을 내리고 다시 거는 두 문장. `ADD` 가 표 전체를 검증한다 |
| 이름을 바꿀 때 | `RENAME VALUE` 하나. **저장된 행도 따라온다** | 제약을 바꾸고 행을 `UPDATE` 로 따로 고친다 |
| 값을 뺄 때 | **`DROP VALUE` 가 없다.** 타입을 다시 만들고 의존 칸을 재작성한다 | 두 문장 |
| 여러 표가 공유할 때 | 타입 하나가 진실 | 칸마다 다시 적어 갈릴 수 있다 |

빼는 것이 어렵지만 **이 두 칸은 빠진 적이 없다** - `notices.kind` 는 `app` 하나에서 넷이 늘었고
줄어든 적은 없다. `platform` 은 표 둘이 공유하므로 타입 하나로 두는 실익이 실제로 있다.

**운영 규칙 하나.** 값을 더하는 마이그레이션은 **그 값으로 쓰지 않는다.** PG 16 은 같은
트랜잭션에서 더한 값을 쓰면 `unsafe use of new value` 로 거부하고, `node-pg-migrate` 9 가
마이그레이션을 트랜잭션으로 감싼다. 백필이 필요하면 파일을 둘로 가른다.

**대가**: 값을 더한 마이그레이션의 `down` 이 no-op 이다. 되돌릴 수단이 없어 안 쓰이는 값 하나가
남는다. 해로운 상태는 아니고 `users.last_seen_at` 을 걷을 때 받아들인 **값은 못 돌아온다** 와 같은
등급이다.

### 결정 2. 사람을 가리는 일에 넥슨을 부르지 않는다

`main.ts` 가 쓰기 경로의 신원 확인을 `resolveSession` 으로 한다.

```ts
userIdForSession: async (value) => (await resolveSession(authDeps, value))?.userId ?? null,
```

**그 함수가 하는 일이 둘인데 여기 필요한 것은 하나다.** 이 사람이 누구냐는 행 조회로 끝나고,
쓸 수 있는 액세스 토큰을 내라만 갱신을 요구한다. 드롭 가격 POST 는 `user_id` 만 쓰고 넥슨 토큰을
안 쓰는데도 **갱신을 일으킨다.**

그 갱신은 다른 갱신과 겹칠 수 있고, 겹치면 맥락의 실측대로 **진 쪽이 세션을 지운다.** 쓰기 경로와
조회 경로는 서로 다른 코드 경로라 앱에서 묶을 공통 자리가 없다.

가르면 **갱신하는 경로가 줄고** 쓰기 한 번에 끼어 있던 넥슨 왕복도 사라진다. 신원 확인은 행을
찾아 `sessionExpired` 만 보면 되고 넥슨을 안 부른다. 갱신 토큰 회전 횟수가 주는 것도 곁따라 온다.

### 결정 3. 콜백을 서버가 받는다. 커스텀 스킴에 값을 안 싣는다 (사용자 지정)

`redirect_uri` 를 `https://mapleroutine.store/v1/auth/nexon/callback` 로 옮긴다.

```
① 앱 ──► POST /v1/auth/nexon/start { platform }
         서버가 state · verifier 를 만들어 짝에 둔다 (expires_at = +10분)
    ◄──  authorizeUrl 만                      state 를 앱에 주지 않는다

② 앱 ──► openAuthSessionAsync(authorizeUrl)
   사용자  넥슨에서 로그인 · 동의

③ 넥슨 ──► GET /v1/auth/nexon/callback?code=&state=
         state 로 짝을 집는다 · 교환 · userinfo · users · nexon_sessions
         세션 원본을 짝에 봉한다 (결정 4)
    ◄──  302 com.mapleroutine.app://oauth/callback      값을 안 싣는다

④ 앱 ──► POST /v1/auth/nexon/session { verifier }
    ◄──  session
```

**앱이 교환하는 대상이 바뀌는 것이 구멍을 닫는다.** `code` 는 넥슨이 발급해 우리가 짝을 못 박는
값이고, ④ 가 내는 `verifier` 는 **우리가 ① 에서 발급해 그 짝에 적어 둔** 값이다. 콜백을 가로챈
앱이 `/start` 로 자기 짝을 새로 만들어도 거기엔 봉한 세션이 안 달려 있다.

**커스텀 스킴에 실리는 값이 없다.** 302 는 돌아오라는 신호일 뿐이라 가로채도 얻을 것이 없다.
④ 의 열쇠인 `verifier` 는 ① 의 응답으로 **https 로만** 왔다. 그래서 신호를 놓쳐도 된다 - 앱은
`verifier` 를 들고 있으니 ④ 를 그냥 부를 수 있고, 안드로이드에서 다른 앱이 신호를 먹어도 지연조차
아니다.

**`state` 를 앱에 주지 않는다.** 앱이 확인할 일이 없어졌고(③ 에서 서버가 한다) 가이드라인의
`제3자가 접근할 수 없는 안전한 곳에 보관` 도 그래야 맞다.

**`claimed_at` 이 state 재사용을 막는다.** ③ 이 한 문장으로 집는다.

```sql
UPDATE nexon_login_attempts SET claimed_at = now()
 WHERE state = $1 AND claimed_at IS NULL AND expires_at > now()
RETURNING platform
```

0줄이면 거절한다. 한 문장이라 경합이 없고 넥슨 왕복 동안 트랜잭션을 붙들지 않는다. **없으면
state 를 아는 쪽이 자기 `code` 로 짝을 덮어쓸 수 있다** - state 는 리다이렉트 URL 에 실려
브라우저와 `access.log` 를 지나므로 비밀이 아니고, 그러면 우리 앱이 남의 계정으로 로그인된다.
가이드라인의 `한번 인증에 사용된 State 값은 재사용 불가능하도록 구성합니다` 가 이 칸이다.

**③ 은 무슨 일이 있어도 302 만 낸다.** 교환 실패 · DB 실패 · 예외를 전부 감싼다. 안 그러면
사용자가 브라우저의 에러 화면에 갇히고 앱으로 안 돌아온다. 지금은 콜백이 앱으로 바로 가서 서버가
죽어 있어도 앱이 안내를 띄울 수 있는데, 이 설계는 **서버 가용성이 로그인 화면에 직결된다.**

**④ 의 답이 취소·실패·만료를 가른다.** 짝의 상태가 그대로 말한다 - `claimed_at` 이 없으면
사용자가 창을 닫은 것, 있는데 봉한 세션이 없으면 교환이 실패한 것, 짝 자체가 없으면 만료다.
`nexon-login.ts` 가 신경 쓰는 **취소가 실패와 갈린다** 를 서버가 공짜로 준다.

**콜백 하나를 두 플랫폼이 공유한다.** 어느 자격 쌍으로 교환할지는 짝의 `platform` 이 말한다.
넥슨 애플리케이션이 둘이어도 돌아올 주소는 하나다.

**콜백 경로에 App Links·Universal Links 를 걸지 않는다.** 걸면 앱이 설치된 기기에서는 OS 가 그
주소를 앱으로 보내고 안 설치된 기기에서는 브라우저가 서버로 보내 **같은 주소가 두 가지로
동작한다.** 서버가 늘 콜백을 받는 것이 짝을 못박는 전제라 이 경로는 브라우저로 두고 결정적으로
만든다.

**그 경로의 로그 형식을 따로 둔다.** 기본 `combined` 가 인가 코드를 두 줄에 남긴다(맥락의 실측).

### 결정 4. 세션 원본을 짝에 봉해 두고 60초 안에 꺼내 간다 (사용자 지정)

③ 과 ④ 가 **서로 다른 요청**이라 그 사이에 서버가 세션을 들고 있어야 한다. `nexon_sessions` 는
해시만 두므로(`서버는 세션 원본을 저장하지 않는다` 가 그 표의 전제다) 꺼내 줄 수 없다. 그래서
짝에 봉해 둔다.

```
③  세션 값 S 생성 → nexon_sessions 행 (session_hash = sha256(S))
                  → 짝에 AES-256-GCM(S) · session_id

④  DELETE FROM nexon_login_attempts
     WHERE verifier = $1 AND session_cipher IS NOT NULL
       AND claimed_at > now() - interval '60 seconds'
    RETURNING session_cipher, session_iv, session_tag
    → 풀어서 S 를 앱에 준다
```

`nexon_login_attempts` 에 칸 다섯이 붙고 `verifier` 가 `UNIQUE` 로 오른다. **`nexon_sessions` 는
한 칸도 안 바뀐다.**

```
claimed_at       timestamptz   ③ 이 집은 시각. state 재사용을 막는다 (결정 3)
session_cipher   bytea         ③ 이 봉한 세션 원본
session_iv       bytea
session_tag      bytea
session_id       uuid  FK → nexon_sessions(id) ON DELETE SET NULL
```

**되묻는 창을 짝의 10분과 따로 둔다.** ① 의 10분은 사용자가 넥슨 화면에서 쓰는 시간이고 ④ 는
리다이렉트를 받아 되묻는 시간이라 초 단위다. **이 설계의 유일한 대가가 봉한 원본이 DB 에 있는
창이므로, 짧게 두는 것이 그 대가를 갚는 수단이다.** 60초면 칸을 더 안 늘린다.

**기각 - 세션을 아직 만들지 않고 넥슨 토큰만 짝에 둔다.** 토큰 칸 여섯이 `nexon_sessions` 와
겹쳐 같은 모양이 두 자리에 생긴다. 가이드라인이 토큰 보관 자리를 늘리지 말라는 방향이기도 하다.

**기각 - 세션 행만 만들고 ④ 에서 값을 새로 뽑아 해시를 갈아 끼운다.** 원본이 아무 데도 저장되지
않아 **엄격히 더 안전하다.** 그러나 이기는 칸이 `DB 와 키가 함께 샌다` 하나뿐이고, 그 공격은 이미
`nexon_sessions` 전체의 14일짜리 갱신 토큰을 내준다 - 추가로 내주는 것이 **진행 중인 세션 하나 ·
최대 60초** 라 비교가 안 된다. `DB 만 샌다` 칸에서는 둘이 동등하다(암호문을 못 푼다). 대가로
`session_hash` 가 변하는 칸이 되고 ④ 가 두 표를 건드려 상태 조합이 는다. **안전 차이가 측정
가능한 수준이 아니라 실수할 자리가 적은 쪽을 골랐다.**

**기각 - 커스텀 스킴에 1회용 인수증을 싣는다.** `verifier` 가 이미 그 열쇠라 인수증이 없어도
된다. 빼면 커스텀 스킴에 실리는 값이 0 이 되고 가로채기를 막는 논증 자체가 필요 없어진다.

**받아들이는 손실 둘.**

- **④ 의 응답이 유실되면 사용자가 재로그인한다**(사용자 지정). 서버는 세션을 발급하고 짝을
  지웠는데 앱이 못 받은 경우다. 앱은 실패로 보고 처음부터 다시 로그인하고, 그 세션은 아무도 안
  드는 고아가 된다. 결정 5 의 만료 청소가 14일 뒤 걷는다. 멱등하게 만들려면 원본을 바로 비우지
  않고 ①이 나중에 비워야 하는데, 그러면 노출 창이 60초에서 한 시간대로 늘어 이 결정의 전제가
  무너진다.
- **브라우저가 떠 있는 동안 앱이 죽으면 로그인이 유실된다**(사용자 지정). `verifier` 를 앱이
  메모리에만 들어서다. ③ 은 서버에서 독립적으로 돌았으므로 세션이 이미 섰고, 그 고아는 결정 5 가
  즉시 치운다. Preferences 에 적어 막을 수 있지만 평문 저장이 하나 늘어 그쪽을 안 고른다.

### 결정 5. 1시간 고리가 짝과 고아 세션을 치운다 (사용자 지정)

짝은 **10분** 보관하고, 치우는 일은 **1시간 간격 고리**가 한다.

```sql
WITH dead AS (
  DELETE FROM nexon_login_attempts
   WHERE (claimed_at IS NULL     AND expires_at <= now())
      OR (claimed_at IS NOT NULL AND claimed_at <= now() - interval '10 minutes')
  RETURNING session_id
)
DELETE FROM nexon_sessions
 WHERE id IN (SELECT session_id FROM dead WHERE session_id IS NOT NULL);

DELETE FROM nexon_sessions WHERE refresh_expires_at <= now();
```

**한 문장으로 묶는 것이 요점이다.** 짝을 먼저 지우면 `session_id` 포인터가 사라져 고아 세션을
영구히 못 찾는다. CTE 로 묶으면 순서를 틀릴 자리가 없다.

**살아남은 짝에 `session_id` 가 있으면 그것이 곧 고아다.** ④ 가 오면 짝이 지워지므로, ③ 까지
갔는데 남아 있는 짝은 ④ 가 안 온 것뿐이다. 추론이 아니라 기록이다. 그 세션 행에는 **유효한 넥슨
토큰**(access 30분 · refresh 14일)이 들어 있어 빨리 없애야 한다.

**조건을 `claimed_at` 으로 쓰는 이유.** `created_at < now() - 10분` 으로 쓰면 사용자가 넥슨 화면에서
늦게 동의한 짝을 **④ 를 기다리는 중에** 지울 수 있다(`claimed_at` 이 `created_at + 10분` 까지 올 수
있다). 위 조건은 집히지 않은 짝은 만료로, 집힌 짝은 집힌 뒤 10분으로 끊어 그 겹침이 없다.

**세션 만료 청소가 지금 없던 구멍을 메꾼다.** `nexon_sessions_refresh_expires_at` 인덱스가 정확히
이것을 위해 있는데 **훑는 코드가 아예 없었다.** 갱신 토큰이 죽은 세션은 누구에게도 쓸모가 없으니
추론이 아니고, 결정 4 가 받아들인 유실 고아도 여기서 걷힌다.

**`outcome` 칸을 두지 않는다.** 보관이 10분이면 성공·실패 기록을 읽을 창이 없어, 안 읽는 값을
적는 일이 된다. 실패율을 보려면 보관을 늘리고 그 칸을 함께 더해야 한다.

**벽시계가 아니라 간격인 이유.** 서버에 이미 도는 주기 작업 둘(`poll` · `schedule`)이 간격 고리
+ advisory lock(`LOCK_IDS`) 이고, 끝난 뒤 다음을 잡는다. 벽시계 새벽을 맞추려면 오늘 이미 돌았나
상태와 KST 변환이 새로 필요한데(DB 는 UTC) 표가 작아서 그 복잡도를 살 이유가 없다. `LOCK_IDS` 에
번호 하나를 더한다.

**`/start` 가 인증 없이 열려 있어 이 결정이 필요하다.** `{ platform }` 만 보내면 누구나 짝을
만든다. nginx 의 `10r/s` 를 꽉 채우면 하루 86만 줄이고, 집히지 않은 짝을 만료 즉시 지우지 않으면
DB 전체가 8.3MB 인 박스에 수백 MB 가 쌓인다.

**`purgeExpiredLoginAttempts` 를 이 고리가 쓴다.** 지금 `db.ts` 에 정의만 있고 호출부가 테스트에도
없다 - 운영 DB 에 만료된 짝 18줄이 2026-09-25 ~ 09-30 테스트 흔적으로 남아 있다.

## 이 설계로 앱에서 사라지는 것

| 사라지는 것 | 이유 |
|---|---|
| `accessToken` (디스크·메모리) | 서버만 든다 |
| `accessExpiresAt` | 저장도 비교도 안 한다 |
| `RENEW_MARGIN_MS` | 같은 60초 상수가 두 저장소에 있었다 |
| `needsToken()` | 판정할 값이 없다 |
| `renewNexonAccessToken()` | 갱신을 부를 일이 없다 |
| `retryWith` 의 401 갱신 | 프렌즈 경로가 앱을 안 지난다([[ADR-346]]) |
| `started.state` 비교 | 콜백을 안 받는다 |
| `POST /v1/auth/nexon/token` | 경로 자체를 지운다. 가이드라인 위반의 본체다 |
| `/session` 응답의 토큰 둘 | 앱의 계산을 먹이려고만 있던 칸 |

```
Preferences 의 authMethods 키 하나

지금      { login: { kind, session, accessToken, accessExpiresAt }, apiKeys: [...] }
바꾼 뒤   { login: { kind, session }, apiKeys: [...] }
```

**상수가 둘로 갈린다.** 지금 `REDIRECT_URI` 하나가 두 일을 한다. 바꾼 뒤에는 넥슨에 등록한
주소(② 의 `authorize` 에 싣는 값)와 서버가 앱으로 돌려보내는 주소(③ 의 302 대상)가 다른 값이고,
`openAuthSessionAsync` 에 주는 것은 뒤엣것이다.

**비프렌즈 12경로는 그대로 앱이 부른다.** 가이드라인의 문장은 `유저의 인가 코드를 사용해 발급
받은 Access Token` 에 대한 것이고 그 12경로는 Open ID 가 안 열어 **개발자 API 키**를 쓴다
([[ADR-320]] 결정 4 유지).

## 대가

- **서버 가용성이 로그인 화면에 직결된다.** ③ 이 302 를 못 내면 사용자가 브라우저에 갇힌다.
  그래서 결정 3 이 `무슨 일이 있어도 302` 를 못박는다.
- **브라우저에서 기다리는 시간이 생긴다.** ③ 이 넥슨 왕복 둘(교환 · `userinfo`)과 DB 쓰기를 하고
  나서야 302 를 낸다. 지금은 콜백이 즉시 앱으로 가고 교환이 앱 뒤에서 돈다. **이 시간을 안
  쟀다**(사용자 판단으로 무시하기로 했다. 프렌즈 API 왕복 19~39ms 는 쟀지만 `oauth2/token` 과
  `userinfo` 는 안 쟀다).
- **베어러 값을 저장하는 자리가 최대 60초 생긴다**(결정 4).
- **③ 이 `users` 행을 앱이 확인하기 전에 만든다.** ④ 가 안 와도 그 행은 남는다. 동의가 끝난
  시점이라 **그 사람은 가입자이고 행은 맞다** - `nexon_uid` 가 `UNIQUE` 라 다시 로그인하면 같은
  행을 받는다. 고장도 집계 오류도 아니다.

## 아직 결정 전

검토가 이어지는 동안 아래가 결정으로 올라온다. 지금은 **소견**이다.

- **기기 표 일곱의 복합 PK.** `boss_profit_records` · `boss_party_settings` ·
  `boss_party_period_overrides` · `boss_profit_period_checks` · `character_accounts` ·
  `enhancement_history_checks` · `mvp_grade_history`. 옮기면 그 표의 조회가 전체 스캔이 되므로
  **인덱스를 함께 세워야 한다**(`boss_drop_records` 가 그렇게 했다).
- **가계부 두 표의 대리키.** `income_records.id` · `spend_records.id` 가
  `시각(36진) + Math.random()` 이다. 코드에 적힌 근거는 Hermes 에 `crypto.randomUUID` 가 없다는
  것인데 그 전제가 사라졌다 - `storage/sqlite/uuid.ts` 의 `NEW_UUID_SQL` 이 SQLite 에서 v4 uuid 를
  만든다.
- **`nexon_login_attempts.state` 가 PK 다.** uuid 로 옮긴 표 다섯에서 이것만 빠졌다. 넥슨이
  돌려주는 값이라 **바꿀 수도 없다.**
- **자연키 한 칸으로 선 표 셋.** `character_profiles(ocid)` · `character_world_leaps(from_ocid)` ·
  `enhancement_history(id)`. 복합키는 아니고 넥슨이 발급한 값이 곧 PK 다. 대리키를 더해 얻는 것이
  없는 자리라 **규칙의 예외로 둘지**가 결정이다.
- **기기 DB 에 인덱스가 하나뿐이다**(`boss_drop_records_group`). 복합 PK 가 곧 인덱스였기 때문이다.
- **[[ADR-320]] 결정 5 의 전제가 측정으로 약해졌다.** 그 문서는 강화 내역 수백 건이 30분을 넘길
  수 있다고 적었는데, 실제 계정으로 31일을 받아 보니 150여 호출에 커서가 한 번도 안 떴다
  ([[ADR-346]] 의 크기 실측). 401 재시도 자체는 그대로 필요하다 - 토큰이 없는 경우가 남는다.

## 열린 질문

- **교환에 `redirect_uri` 를 보내나.** 스펙의 파라미터 표에 **그 칸이 없다**(넷뿐). 우리는 다섯
  번째로 보내고 통과한다. https 로 옮기면 값을 바꿔 보낼지 아예 뺄지 정해야 한다. 넥슨이 안 보는
  것이 사실이면 커스텀 스킴으로 시작한 로그인의 `code` 를 https 짝으로 교환할 수 있다 - 결정 3 의
  `state` 확인이 그걸 막지만 보내는 쪽은 맞춰 두는 것이 맞다.
- **③ 의 왕복이 얼마인가.** `oauth2/token` 과 `userinfo` 를 안 쟀다. 길면 `userinfo` 를 ④ 로
  미룰 수 있지만 그러면 `users` 행을 ④ 에서 만들어 ③ 과 ④ 의 일이 섞인다.
- **한 묶음을 한 마이그레이션으로 두나, 표마다 가르나.** 기기 쪽은 `DB_VERSION` 하나가 여러 표를
  다시 쓰는 모양이 되고, 그 이관은 사용자 기기마다 따로 돌아 결과를 확인할 길이 없다.
- **기기 복합 PK 를 옮길 때 옛 PK 조각으로 서버에 보낸 것이 있나.** 없으면 소급 영향이 없다.
- **같은 플랫폼의 두 기기에서 로그인하면 먼저 기기가 죽나.** 저장된 안드로이드 세션의 갱신
  토큰이 **저장된 만료보다 먼저 죽어 있었다**(2026-10-12. DB 는 10-22 까지라 적었는데 넥슨은
  `OPENAPI00012`). 같은 `client_id` 로 그날 새 로그인을 한 번 돌린 것이 유일한 설명인데 **직접
  재지는 않았다.** 사실이면 기기를 바꿔 로그인할 때 먼저 기기의 세션이 조용히 죽는다.
