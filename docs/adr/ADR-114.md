# ADR-114 — 429 는 키의 단계를 판정하지 않고 문구로만 안내한다 + 스탈 배너가 원인별로 갈린다

**날짜**: 2026-08-08
**상태**: **구현 완료 · 실기기 미검증**, 2026-08-08, 이슈 #158
**관련**: [[ADR-062]] 결정 3(원인별 문구·액션 표 — "429의 재시도 버튼은 비활성화하지 않는다"를 이 ADR 이 폐기한다)·결정 4(스탈 배너를 만든 결정 — 문구가 하나로 고정된 자리)·결정 5(어미 `~습니다`) · [[ADR-063]](자리 판정 기준 "그 문구가 사라진 자리에 남는 것이 있는가" · 결정 3 의 토스트 액션 표) · [[ADR-008]]("병렬 호출이 한도와 충돌하지 않는다"가 이 ADR 이 정정하는 전제 위에 서 있다) · [[ADR-067]] 결정 1(400 본문 에러 코드를 살려 실패 종류를 갈랐다 — 배너가 읽을 `ScheduleSyncError` 의 출처) · [[ADR-083]] 결정 2(영구 실패에는 액션을 주지 않는다는 같은 계열의 판단) · 이슈 #158

## 맥락

### 증상 (이슈 #158)

테스터 일부에게 **캐릭터 관리 피커에 캐릭터가 거의 뜨지 않는다.** 추적 중인 대표 캐릭터 1명만
남고 그 위에 **"목록이 최신이 아닙니다"** 배너가 뜬다. 원인은 **개발 단계 API 키의 호출 한도
초과(429)** 로 확인됐다(2026-08-07).

### 전제가 틀렸다

`docs/foundation/nexon-api.md:10` 은 이렇게 적혀 있다:

> 개발 단계 초당 5건/일 1,000건, 서비스 단계 초당 500건/일 2,000만 건. **이 앱은 사용자가 이미
> 승인받은 서비스 단계 키를 쓰므로** 개발 단계 상한 검증은 불필요.

이 문장은 **개발자 본인 키에만** 맞다. 테스터·사용자는 각자 `openapi.nexon.com` 에서 발급받은
**개발 단계 키**(초당 5건 / 일 1,000건)를 넣는다. 같은 전제가 [[ADR-008]] "호출량 한도" 항목과
2026-07-17 정정에도 그대로 적혀 있고, **"프리플라이트 1건 뒤 나머지를 `Promise.allSettled` 로
병렬"** 이라는 현재 동기화 구조가 바로 그 위에 서 있다.

### 이 이슈가 고치는 것은 "문구"다

429 가 세 자리에서 서로 다르게 뭉개진다.

**(a) 스탈 배너가 원인을 무시한다.** `StaleBanner.tsx:12-15` 의 props 는 `message: string` 과
`onRetry: () => void` 둘뿐이라 `loadError.kind` 를 볼 수 없다. 호출부 2곳
(`CharacterTrackingPicker.tsx:59` · `ContentCharacterStep.tsx:46`)이 `"목록이 최신이 아닙니다"` 를
하드코딩한다. **401·429·`characterUnavailable`·네트워크가 전부 같은 한 줄로 보이고**, 배너는
무조건 "다시 시도" 버튼을 붙인다(`StaleBanner.tsx:26-32` — 액션이 옵셔널이 아니다). 같은 화면의
`ErrorState` 경로는 이미 `formatRosterError` 로 원인별 문구·액션을 그리는데
(`CharacterTrackingPicker.tsx:88-106` · `ContentCharacterStep.tsx:69-79`), **항목이 남아 있는
쪽만 [[ADR-062]] 결정 3 이전 상태로 남아 있었다.** 그런데 캐시 stub 이 네트워크보다 먼저
방출되므로([[ADR-017]] 결정 6) 예열이 끝난 정상 경로에서는 **배너 쪽이 기본 분기**다 — 실패의
대다수가 원인을 잃는 자리가 정확히 여기다.

**(b) 429 문구가 잘못된 처방을 준다.** 현재 4곳이 전부 "잠시 후 다시 시도해주세요" 계열이다.

| 자리 | 파일 | 현재 문구 |
|---|---|---|
| 토스트(스케줄러 3화면·온보딩) | `features/schedule-sync/format.ts:14` | 잠시 후 다시 시도해주세요 |
| `ErrorState`(피커·온보딩) | `features/schedule-sync/format.ts:70-77` | 요청이 너무 많습니다 / 잠시 후 다시 시도해주세요 + **다시 시도** |
| 온보딩 토스트 | `features/onboarding/format.ts:9-10` | 잠시 후 다시 시도해주세요 |
| 설정 계정 카드(인라인) | `app/settings/error-message.ts:7-8` | 잠시 후 다시 시도해주세요 |

개발 단계 키에는 **틀린 안내**다. 일 1,000건을 넘긴 것이면 다음 날까지 안 풀리고, 초당 5건이면
앱이 버스트를 쏘는 한 재시도해도 또 429다. 실제 해결책은 **넥슨 개발자 센터에서 서비스 단계
신청**인데 아무도 그 말을 하지 않는다.

### 열린 결정은 이미 닫혔다 — A안(판정하지 않는다)

넥슨 API 는 키의 단계를 알려주지 않는다. 429(`OPENAPI00007`)는 두 단계 모두에서 같은 코드로
오고 응답 본문에도 구분이 없어, **429 만으로 개발/서비스 단계를 구분할 수 없다.** 세 안 중
**A(판정하지 않는다)** 를 사용자가 채택했다(2026-08-08).

## 결정

### 결정 1 — 429 는 키의 단계를 판정하지 않고 문구로만 안내한다 (A안)

**감지 자체가 목적이 아니라 사용자가 다음 행동을 아는 것이 목적**이므로, 단계를 알아내는 장치를
만들지 않고 **단계 무관하게 쓸 수 있는 문구 한 벌**로 끝낸다. 추가 호출 0회 · 새 상태 0개 ·
오탐 없음.

문구는 확정값이다(사용자 확정 2026-08-08).

| 자리 | 429 문구 | 액션 |
|---|---|---|
| `ErrorState`(피커·온보딩, 목록이 아예 없을 때) | 제목 **호출 한도를 초과했습니다** / 설명 **입력하신 API 키가 서비스 단계 키인지 확인해주세요** | 없음 |
| `StaleBanner`(목록이 있을 때) | **호출 한도를 초과했습니다 — 서비스 단계 키인지 확인해주세요** | 없음 |
| 설정 계정 카드(인라인) | **호출 한도를 초과했습니다. 입력하신 API 키가 서비스 단계 키인지 확인해주세요** | 없음 |
| 토스트(스케줄러 3화면·온보딩) | **호출 한도를 초과했습니다** | 없음(현행) |

**수치(초당 5건·일 1,000건)는 넣지 않는다** — 서비스 단계 키 사용자가 봐도 어색하지 않아야 하고,
배너 한 줄처럼 좁은 자리에도 같은 문구가 들어가야 한다. 어미는 [[ADR-062]] 결정 5 그대로
`~습니다`/`~주세요` 다.

### 결정 2 — 429 에는 액션을 주지 않는다 ([[ADR-062]] 결정 3 일부 폐기)

[[ADR-062]] 결정 3 의 **"429의 재시도 버튼은 비활성화하지 않는다(사용자 결정 2026-07-30)"** 를
폐기한다. 그 결정은 *"즉시 누르면 또 429지만, 잠글 시각을 추적하는 상태를 새로 만들 만큼의 이익이
없다"* 였다 — 즉 **"초당 한도라면 잠시 뒤 재시도가 통한다"** 를 전제하고 잠금 여부만 따졌다.
전제가 둘 다 흔들린다: 일 1,000건 소진이면 **다음 날까지 안 풀리고**, 새 문구의 처방은 재시도가
아니라 **키 단계 확인**이다. 처방이 "키를 확인하라"인데 버튼이 "다시 시도"면 화면이 두 말을 한다.

이로써 이 앱의 429 처리가 한 방향으로 모인다 — 토스트는 [[ADR-063]] 결정 3 부터 이미 액션이
없었고(`use-sync-error-toast.ts:59-66`), `error-resilience.md` 원칙 3 의 *"429에는 액션을 주지
않는다"* 도 원래 그렇게 적혀 있었다. **`formatRosterError` 의 `ErrorState` 경로와 스탈 배너
두 자리만 규칙 밖에 있었다.**

### 결정 3 — 스탈 배너가 원인별로 갈린다

`StaleBanner` 는 계층(molecule)을 지키기 위해 **`ScheduleSyncError` 를 받지 않는다.** 대신
호출부가 `features/schedule-sync/format.ts` 의 새 함수 **`formatStaleRosterError(error, place)`**
로 문구·액션을 뽑아 넘긴다(같은 파일의 `formatRosterError(error, place)` 와 같은 어법 · 같은
`RosterErrorPlace` 를 쓴다). 배너의 액션은 옵셔널이 된다.

| 원인 | 배너 문구 | 피커 | 온보딩 |
|---|---|---|---|
| `invalidApiKey` | API 키가 유효하지 않아 목록을 갱신하지 못했습니다 | 설정 열기 | 없음 |
| `rateLimited` | 호출 한도를 초과했습니다 — 서비스 단계 키인지 확인해주세요 | 없음 | 없음 |
| `characterUnavailable` | 이 계정의 캐릭터를 조회할 수 없습니다 | 없음 | 없음 |
| `network`·`periodOutOfRange`·`notCollected` | 목록이 최신이 아닙니다 *(현행 유지)* | 다시 시도 | 다시 시도 |

배너는 **재시도가 실제로 통하는 실패에만** 액션을 준다. 온보딩에서 401 이 액션 없음인 것은
그 화면에 설정이 없기 때문이고([[ADR-062]] 결정 3 과 같은 이유), 배너에서는 그것이 문제가
안 된다 —

> **배너는 목록이 남아 있어 액션이 없어도 막다른 길이 아니다.**

이것이 `ErrorState` 와 갈리는 유일한 근거이고, **같은 401 이 온보딩 `ErrorState` 에서는 재시도를
유지하는 이유도 같은 근거의 뒷면**이다. 그쪽은 목록이 없어 액션을 빼면 화면에 아무 길도 남지
않는다. 자리가 문구와 액션을 정한다는 [[ADR-063]] 의 기준을 액션 쪽으로 한 번 더 적용한 것이라
예외가 아니다.

### 결정 4 — 토스트는 원인만, 인라인은 처방까지

`Toast.tsx:88` 의 본문은 `min-w-0 flex-1 truncate` 라 **한 줄이 상한**이다. 429 문구에 처방을
넣으면 그 자리에서 잘린다. `truncate` 를 풀어 전 토스트의 레이아웃 규칙을 바꾸는 대신,
**자리마다 담을 수 있는 만큼** 담는다 — 토스트는 원인만(`호출 한도를 초과했습니다`), 처방은
목록 자리(배너·`ErrorState`)와 설정 계정 카드가 준다. [[ADR-063]] 의 *"자리가 문구를 정한다"* 와
같은 계열이고, 같은 이유로 이미 [[ADR-063]] 결정 5 가 토스트에서 캐릭터 이름을 인원 수로
줄인 선례가 있다.

### 결정 5 — `nexon-api.md` 의 "서비스 단계 키 전제"를 정정한다

사용자는 각자 발급받은 **개발 단계** 키(초당 5건 / 일 1,000건)를 쓰고, 앱은 그 한도를 실제로
넘긴다(이슈 #158). [[ADR-008]] 의 *"병렬 호출 자체가 한도와 충돌하지 않는다"* 도 이 전제 위에
서 있었다는 것을 문서에 함께 남긴다.

**다만 프리플라이트·동시성 캡 도입은 이 ADR 의 범위가 아니다.** 이 결정이 고치는 것은 **전제가
적힌 문장**이고, 그 전제 위에 세워진 **호출 구조를 다시 짜는 것은 별건**이다(아래 "범위 밖").

## 기각안

- **B. 온보딩 키 검증 때 단계를 프로브한다** — 짧은 간격으로 연속 호출해 429 가 나는지로 추정.
  판정은 확실해지지만 온보딩에 호출·시간이 붙고, 무엇보다 **일부러 429 를 내는 설계**다. 지금
  줄이려는 것이 429 인데 그것을 생산한다.
- **C. 429 발생 횟수·간격을 누적해 "개발 단계로 보인다" 플래그를 세운다** — 추가 호출은 없으나
  **상태와 판정 규칙이 새로 생기고**(저장 위치·리셋 시점·임계값), 판정이 서기 전 **첫 429 에는
  여전히 틀린 문구**가 나간다. 사용자가 처음 부딪히는 그 한 번이 이 이슈의 증상이다.
- **`Toast` 본문의 `truncate` 를 `line-clamp-2` 로 바꿔 전 자리에 같은 문구를 쓰기** — 429 하나
  때문에 **모든 토스트의 레이아웃 규칙**이 바뀐다. 높이가 가변이 되면 여러 개가 쌓일 때의 스택
  높이·스와이프 제스처 영역까지 함께 검토해야 한다.
- **문구에 수치(초당 5건·일 1,000건)를 넣기** — 서비스 단계 키 사용자에게는 관계없는 숫자이고
  (A안은 그 사용자도 같은 문구를 본다는 전제 위에 선다), 배너 한 줄에 들어가지 않는다.
- **`StaleBanner` 가 `ScheduleSyncError` 를 직접 받기** — molecule 이 feature 어휘를 알게 된다.
  포맷은 호출부가 하고 배너는 문구·액션만 받는다([[ADR-094]] 결정 2 — 아토믹 계층은 **의존 방향
  규칙**이고, molecule 이 feature 를 참조하는 것이 정확히 그 방향을 거스른다).

## 대가/트레이드오프

- **서비스 단계 키 사용자도 "서비스 단계 키인지 확인해주세요"를 본다.** A안을 고른 값이 정확히
  이것이다 — 오탐(판정을 세웠다가 틀리는 것) 대신 **무해한 잉여 안내**를 택했다. 그 사용자에게
  이 문구는 "확인해 보니 맞더라"로 끝난다.
- **429 에서 사용자가 앱 안에서 할 수 있는 일이 없어진다**(버튼이 사라진다). 후퇴가 아니라,
  실제로 할 수 있는 일이 없었던 것을 화면이 인정하는 것이다 — 눌러도 또 429 인 버튼은
  "고칠 수 있다"는 잘못된 신호였다.
- **토스트와 인라인의 429 문구가 다르다.** 같은 원인에 두 문구가 생기는 것은 유지 비용이지만
  (한쪽만 고치면 어긋난다), 잘린 문구보다는 낫다. 두 문구가 같은 파일 안에서 갈리도록 두어
  한눈에 보이게 한다.
- **일 한도 소진과 초당 한도를 구분하지 않는다.** 429 응답(`OPENAPI00007`)에 그 구분이 없다 —
  "다음 날까지 안 풀림"과 "몇 초 뒤 풀림"이 사용자에게 같은 문구로 간다. 구분할 수 없는 것을
  구분해 말하지 않는다.
- **문구를 바꿔도 429 자체는 줄지 않는다.** 이 ADR 은 **화면이 사실대로 말하게** 할 뿐이고,
  호출을 덜 내보내는 일은 별건이다(아래).

## 범위 밖 (이슈 #158 이 명시적으로 분리한 것)

맥락으로만 적는다 — **결정이 아니므로 이 phase 에서 구현하지 않는다.**

- **자격 스윕이 429 를 삼켜 캐릭터가 조용히 사라지는 문제**(`character-eligibility.ts:90-102` —
  `characterUnavailable`·`periodOutOfRange` 만 원장에 기록하고 429 는 `continue` 로 흘린다).
  문구가 아니라 **목록이 비는 원인**이라 별도 버그다.
- **로스터·예열 경로의 프리플라이트·동시성 캡 부재** — 429 를 애초에 덜 나게 하는 쪽.
  [[ADR-008]] 전제 재검토([[ADR-113]] "미해결로 남긴 사실"의 fan-out 폭과 같은 자리)와 함께
  별도로 다룬다.
- `character/basic` 3라운드 중복 제거는 **이미 끝났다**([[ADR-113]] 결정 1, 이슈 #163).

## 구현하며 정정한 것

설계에서 명시하지 않았거나, 코드로 옮기며 형태가 정해진 것들이다.

1. **`StaleBanner` 의 라벨도 호출부가 넘긴다** — 설계는 "액션이 옵셔널이 된다"까지만 적었으나,
   피커의 401 이 **"설정 열기"** 라 라벨이 하드코딩 `다시 시도` 로 남으면 결정 3 의 표가 절반만
   구현된다. `onRetry: () => void` → `action?: { label, onClick }` 으로 바꿔 라벨·핸들러를 함께
   받는다(`StaleBanner.tsx:27-31`). 마크업·클래스·`data-testid`·`role="alert"` 는 한 글자도
   안 바꿨다.
2. **`StaleRosterErrorCopy.action` 은 콜백이 아니라 `kind` 판별자를 싣는다**(`format.ts:120-124`
   — `{ kind: 'retry' | 'openSettings'; label: string }`). `features/` 포맷터가 컴포넌트 핸들러를
   알 수는 없으므로, 포맷터는 "어느 종류의 액션인가"만 말하고 호출부가 `onRetry`/`onOpenSettings`
   로 매핑한다. `formatRosterError` 의 기존 `RosterErrorCopy` 와 같은 어법이라 두 함수의 호출부
   코드가 같은 모양이 된다(`CharacterTrackingPicker.tsx:64-79` 가 같은 파일 `:88-106` 과 같은 꼴).
3. **온보딩은 `kind === 'retry'` 를 확인하고 매핑한다**(`ContentCharacterStep.tsx:56-58`).
   `place='onboarding'` 은 `openSettings` 를 반환하지 않으므로 무조건 `onRetry` 로 이어도 지금은
   같지만, 포맷터가 바뀌어 `openSettings` 가 오면 **갈 곳 없는 버튼을 그리는 대신 버튼이 사라져**
   드러난다.
4. **설정 카드의 가드는 `props.error?.kind !== 'rateLimited'` 다**(`AccountFlowStatus.tsx:112`).
   `error === null` 폴백("오류가 발생했습니다")에서는 `undefined !== 'rateLimited'` 가 참이라
   버튼이 **자연히 남는다** — 원인을 모르는 실패는 재시도 가능이 폴백 원칙이고, 429 하나만
   빼려는 결정 2 의 범위와도 맞는다.
5. **어미 규칙 단언은 `/(습니다|아닙니다|주세요)$/` 다.** [[ADR-062]] 결정 5 를 그대로 `습니다`
   로만 재면 `network` 문구 `목록이 최신이 아닙니다` 가 걸린다 — 같은 하십시오체 활용이라 규칙
   위반이 아니므로 정규식 쪽을 넓혔다.
6. **뒤집힌 옛 기대값은 갱신이 아니라 삭제했다.** `ErrorState.test.tsx` 의 옛 `StaleBanner`
   3케이스(`onRetry` 를 필수로 전제)를 5케이스로 다시 썼고, `format.test.ts` 에서는
   `rateLimited → retry` 를 단언하던 두 자리(`나머지 원인은 액션이 있다` 의 루프 원소 ·
   `rateLimited·network 는 재시도를 준다`)에서 그 기대를 **빼냈다**. 계약이 정반대인데 같은
   이름을 남기면 다음에 읽는 사람이 오독한다.
7. **`nexon/http.ts:44` 는 바꾸지 않았다** — `NexonRateLimitError` 의 생성자 메시지
   (`'Nexon API 호출 한도를 초과했습니다 (OPENAPI00007)'`)는 사용자 문구가 아니라 내부 진단
   문자열이다. 결정 1 의 표가 세는 "자리 4곳"에 들어가지 않는다.

### 자동 테스트가 담보하는 것

- `formatStaleRosterError(error, place)` 의 **6종 × 2자리 전수** — 문구가 있고 어미 규칙을
  따르는 것, 그리고 429·401(온보딩)·`characterUnavailable` 이 **`action === undefined`** 인 것.
  `assertNever` 가 종류 추가 시 컴파일을 깨므로 표가 조용히 비지 않는다.
- `formatRosterError` 의 `rateLimited` 가 새 제목·설명(`호출 한도를 초과했습니다` /
  `입력하신 API 키가 서비스 단계 키인지 확인해주세요`)이고 **액션이 없다**는 것 — [[ADR-062]]
  결정 3 폐기의 회귀 가드.
- `formatScheduleSyncError`·`formatOnboardingError`·`formatSettingsError` 의 `rateLimited`
  문구가 **자리마다 갈린 채로** 고정된 것(토스트 둘은 `호출 한도를 초과했습니다`, 설정 인라인은
  처방까지).
- `StaleBanner` 가 액션 없이도 렌더되고 그때 **버튼이 DOM 에 없다**는 것. 판별력 확인: 조건부
  렌더를 지워 항상 버튼이 나오게 하자 그 1건만 실패했다.
- 피커·온보딩이 원인별 배너 문구를 **실제로 넘기는지** — 제품 코드에서 호출부 하드코딩
  `"목록이 최신이 아닙니다"` 는 **0건**이고(남은 것은 `format.ts:153` 포맷터 본문 하나),
  `"잠시 후 다시 시도"` 도 `src/` 전체에 **0건**이다.
- `network` 계열이 **현행 문구·액션 그대로**인 것(결정 3 은 폐기가 아니라 좁혀진 것) — 온보딩
  회귀 케이스는 버튼을 눌러 `getCharacterPickerRoster` 가 2회 불리는 것까지 본다.
- 설정 계정 카드의 `error` 케이스가 **`rateLimited` 일 때만** 버튼을 빼는 것(짝이 되는
  `network` 케이스가 버튼이 남는 것을 지킨다).

### 실기기·실사용으로만 확인되는 것

1. **개발 단계 키로 실제 429 를 재현해 배너를 확인하는 것** — 이슈 #158 "검증" 절의 첫
   항목이고 **미확인**이다. 자동 테스트는 `loadError={{ kind: 'rateLimited' }}` 를 주입해 화면을
   검사할 뿐, `nexon/http`(429 → `NexonRateLimitError`) → `toScheduleSyncError` → 로스터 실패 →
   배너까지의 사슬이 **실제 429 응답에서** 그대로 이어지는지는 알지 못한다. 재현 조건은 이슈의
   증상이 나온 테스터 환경(개발 단계 키 + 캐릭터 다수)이다.
2. **새 문구를 본 사용자가 실제로 서비스 단계 신청에 도달하는지** — A안이 판정(감지) 대신
   안내를 택한 값이 **여기서만** 확인된다. "입력하신 API 키가 서비스 단계 키인지 확인해주세요"
   를 보고 넥슨 개발자 센터까지 가는지는 사람에게 물어야 안다. 도달하지 않는다면 다음 후보는
   문구가 아니라 **경로**다(앱 안에서 발급 가이드로 보내는 것 — [[ADR-110]] 이 만든 자리).
3. **429 자체가 줄었는지 — 이 phase 는 429 를 줄이지 않는다.** 호출은 한 건도 덜 나가지 않았고
   바뀐 것은 **화면이 하는 말**뿐이다. 429 를 실제로 덜 나게 하는 일은 아래 "미해결로 남기는
   사실"의 둘째 항목(프리플라이트·동시성 캡)이고, 이 ADR 은 그 작업을 하지 않았다.
4. **배너 한 줄에 새 문구가 잘리지 않는지** — 좁은 폭(360px)에서 `text-xs` 한 줄 + 액션 없는
   레이아웃이 어떻게 접히는지는 눈으로 본다. 새 배너 문구는 32자로 옛 문구(11자)의 3배다.

## 미해결로 남기는 사실

이 phase 가 **손대지 않은 것**을 명시한다. 다음 작업이 잘못된 전제 위에 서지 않도록.

- **(c) 자격 스윕이 429 를 삼켜 캐릭터가 조용히 사라진다** — `character-eligibility.ts:90-102`
  는 `characterUnavailable` 과 `periodOutOfRange` 만 원장에 기록하고 **429·네트워크는 `continue`
  로 흘린다**(주석대로 "나중에 다시 시도한다"는 의도된 설계, [[ADR-086]] 결정 4). 13일을 다 돌면
  `ineligible` 이 되고 `shouldShowEntry` 가 목록에서 뺀다. **이슈 #158 스크린샷에서 "추적 중
  1명만 남은" 원인은 문구가 아니라 이쪽이다** — 그 1명은 추적 중이라 자격 판정을 우회했다.
  즉 **문구를 고쳐도 목록은 여전히 빈다.** 이 ADR 이 한 것은 그 빈 목록 위의 배너가 사실대로
  말하게 한 것뿐이다.
- **로스터·예열 경로의 프리플라이트·동시성 캡 부재** — `character-roster.ts` 의
  `Promise.all(characters.map(...))` 은 동시성 캡이 없고(40캐릭터면 40갈래 동시 발사),
  `prefetch.ts` 도 같다. 동기화 경로에만 있는 프리플라이트([[ADR-008]])가 여기엔 없다.
  [[ADR-113]] 이 "미해결로 남긴 사실"에 적은 **fan-out 폭**과 같은 자리이고, [[ADR-008]] 전제
  재검토와 함께 별건이다. 결정 5 는 **전제가 적힌 문장**을 고쳤을 뿐 그 위에 세워진 호출 구조는
  그대로다.
- **일 한도 소진과 초당 한도를 구분하지 않는다** — 429 응답(`OPENAPI00007`)에 그 구분이 없다.
  "다음 날까지 안 풀림"과 "몇 초 뒤 풀림"이 사용자에게 같은 문구로 간다. 구분할 수 없는 것을
  구분해 말하지 않는 것이지, 구분이 무의미해서가 아니다.
- **서비스 단계 키 사용자도 "서비스 단계 키인지 확인해주세요"를 본다** — A안의 대가다.
  오탐(판정을 세웠다가 틀리는 것) 대신 **무해한 잉여 안내**를 택했고, 그 사용자에게 이 문구는
  "확인해 보니 맞더라"로 끝난다.
- **토스트와 인라인의 429 문구가 갈린 채로 유지된다**(결정 4) — 한쪽만 고치면 어긋나므로 두
  파일(`features/onboarding/format.ts:9-13` · `app/settings/error-message.ts:7-11`)에 서로를
  가리키는 주석을 남겼다. 테스트가 아니라 **주석**이 담보하는 유일한 항목이다.

## 폐기

- [[ADR-062]] 결정 3 의 **"429의 재시도 버튼은 비활성화하지 않는다(사용자 결정 2026-07-30)"** —
  결정 2 로 폐기. 비활성화가 아니라 **액션 자체를 주지 않는다**. 같은 결정 3 의 나머지(원인별
  문구·자리별 액션 분기, 401 의 "설정 열기")는 그대로 선다.
- [[ADR-062]] 결정 4 의 스탈 배너 문구 **"목록이 최신이 아닙니다" + 다시 시도 고정** — 결정 3 으로
  원인별 분기. `network` 계열에서는 그 문구·액션이 그대로 남으므로 **폐기가 아니라 좁혀진 것**이다.
- `nexon-api.md` 의 **"이 앱은 사용자가 이미 승인받은 서비스 단계 키를 쓰므로 개발 단계 상한
  검증은 불필요"** — 결정 5 로 폐기(그 문서 history 절로 이동). [[ADR-008]] 의 병렬 호출 결정
  자체는 폐기하지 않는다 — **근거가 약해졌다는 사실만 기록**하고 재검토는 별건이다.
