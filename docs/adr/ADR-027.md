### ADR-027: Live Update 사용자 동의형 업데이트 UX + 스토어 업데이트 구분 (구현 완료)

**배경**: [[ADR-026]]의 UI는 관찰용이고 부팅 시 조용히 다운로드+자동 적용([[ADR-026]] 결정 7)이라, 사용자가 "지금 업데이트가 일어난다"는 사실을 인지하거나 통제할 수 없었다. 사용자가 (1) 새 업데이트 인앱 알림 + 파일 용량, (2) 셀룰러 데이터 경고, (3) 다운로드 진행률(0~100%), (4) 거절 시 기존 버전 유지, (5) 라이브로 못 받는 "스토어 전용 업데이트" 구분 + 스토어 이동을 요청했다(2026-07-15).

**결정**:

1. **부팅은 "체크만" 한다(자동 다운로드·자동 적용 제거).** `checkForLiveUpdate`는 매니페스트만 조회하고 버전/네이티브 요구사항만 비교한다 — 다운로드하지 않는다. [[ADR-026]] 결정 7의 `applyPendingLiveUpdate`(부팅 자동 적용)와 부팅 시 백그라운드 다운로드를 **제거**한다.

2. **새 버전이 있으면 앱 실행 시 모달로 알린다** — "새 업데이트 vX.Y.Z / 크기 nMB / [다운로드] [나중에]". 거절("나중에")하면 다운로드·적용 없이 **기존 버전을 계속 사용**한다. 재로지 정책은 "매번 물음"(거절해도 다음 실행 때 다시 표시, 버전 건너뛰기 없음). 설정의 "앱 업데이트" 섹션([[ADR-026]])에서도 언제든 수동 확인 가능.

3. **파일 용량 표기**: 매니페스트에 `size`(zip 바이트) 필드 추가. `publish-live-update.mjs`가 `statSync`로 기록하고, 모달이 MB로 환산해 보여준다.

4. **적용은 사용자 동의로만 — `next()` 대신 `download`+`set()`.** 다운로드는 큐잉(`next()`)하지 않고 번들만 받아둔다. 사용자가 "지금 재시작"을 누르면 `CapacitorUpdater.set({ id })`로 즉시 적용·재로드한다. `next()`를 안 쓰므로 iOS의 네이티브 콜드스타트 자동 적용([[ADR-026]] 결정 7 참고)까지 발생하지 않아 **양 플랫폼 모두 완전히 사용자 제어**가 된다.

5. **진행률 0~100%**: `CapacitorUpdater.addListener('download', ({ percent }) => …)`로 진행률을 받아 모달에 프로그레스 바로 표시한다.

6. **셀룰러 데이터 경고**: `@capacitor/network`(신규 네이티브 플러그인)로 `connectionType`을 읽어, 다운로드 직전 `cellular`면 "모바일 데이터로 nMB를 받습니다. 계속?" 확인을 띄운다. **네이티브 플러그인 추가라 이 부분은 OTA로 못 나가고 다음 네이티브 빌드부터 적용된다**(그 전에 설치된 구버전 셸에선 셀룰러 경고만 빠짐 — 나머지 UX는 OTA로 반영).

7. **스토어 전용 업데이트 구분 + 이동**: 매니페스트에 선택 필드 `minNativeVersion` 추가. 앱이 설치된 네이티브 버전(`CapacitorUpdater.current().native`)과 비교한다.
   - 설치 네이티브 ≥ `minNativeVersion`(또는 필드 없음) → 라이브 업데이트 경로(모달 다운로드).
   - 설치 네이티브 < `minNativeVersion` → **스토어 업데이트 필요**(라이브 번들이 요구하는 네이티브 기능이 설치본에 없음) → "스토어에서 업데이트하세요 [스토어로 이동]". 이동은 `Capacitor.getPlatform()` 분기(Android `market://details?id=com.mapleroutine.app`, iOS `itms-apps://…/id<APP_STORE_ID>`) + `window.open(url, '_system')`(플러그인 불필요).
   - **caveat**: 앱이 아직 스토어 미출시([[ADR-024]] 사이드로딩)라 실제 스토어 URL/ID는 placeholder다. 사이드로딩 상태에선 "스토어 이동" 대신 "새 APK를 받아 설치하세요" 안내가 맞다(코드는 표준 스토어 URL 패턴으로 준비, 출시 시 상수만 기입).

8. **아키텍처**([[ADR-003]]/[[ADR-005]]): `native/live-update.ts` 어댑터가 check/download(progress)/apply(`set`)/`getNetworkType`/`openStoreForUpdate`를 담당하고, `features/live-update` 스토어가 상태·플로우를 들고, `app/`의 **`UpdatePromptModal`**(AppShell에 마운트, 실행 시 알림)과 설정의 **`AppUpdateSection`**([[ADR-026]])이 표시한다.

9. **모달 디자인**(사용자 요청, 2026-07-15): 상태별 아이콘 배지(원형 틴트 — 다운로드=primary/CloudDownload, 준비완료=secondary/CheckCircle2, 스토어=third/Store), pill 배지(**`beta`는 한글 "베타"가 아니라 영문**, 버전 `v1.0.4`), 부가 정보는 본문 문장과 분리해 `info-tint` 콜아웃(Info 아이콘 + "다운로드 크기", "최소 앱 버전 2.0.0 이상 필요")으로 표시한다. "(최소 앱 버전 …)" 같은 괄호 인라인 표기는 쓰지 않는다. 라운딩·배지 스케일은 [[UI_GUIDE]] 규칙(카드 14px·배지 pill·인풋 10px)을 따른다.

**트레이드오프**:
- 셀룰러 경고만 네이티브 의존이라 기능이 두 층으로 갈린다(OTA 가능 부분 vs 네이티브 빌드 필요 부분). 구버전 셸에서도 나머지 UX는 정상 동작하고 셀룰러 경고만 생략된다.
- `next()`를 버리고 `set()`으로 즉시 적용하므로, "다운로드는 했지만 아직 적용 안 함" 번들은 다음 실행에서 스스로 적용되지 않는다(사용자가 다시 확인/적용해야 함) — 이게 "완전 사용자 제어"의 의도된 결과다.
- "매번 물음"이라 업데이트를 계속 미루는 사용자는 실행마다 모달을 본다(건너뛰기 미채택). 강제성은 낮지만 인지 확실.
- 스토어 미출시라 스토어 이동은 지금은 placeholder — 실제 검증은 출시 후.

**검증(2026-07-15, iOS 시뮬레이터 실측)**: 클린 설치(builtin 1.0.0) 부팅 → 모달 "새 업데이트 [베타] v1.0.3 · 6.5MB [다운로드][나중에]"(용량 표기) → 다운로드 "다운로드 중 0%" 프로그레스 바 → "업데이트 준비 완료 v1.0.3 [지금 적용][나중에]" → 지금 적용 시 `set()`으로 1.0.3 적용(콘솔 `Version successfully loaded: 1.0.3`, checksum 일치, notifyAppReady 호출·롤백 없음) 전 과정 스크린샷 확인. 이어 `--min-native 2.0.0`으로 배포한 1.0.4에 대해 부팅 시 "스토어 업데이트가 필요해요(최소 앱 버전 2.0.0) [스토어로 이동]" 모달 확인(minNativeVersion 게이트 동작). **미검증**: (1) 셀룰러 경고 — 시뮬레이터에서 셀룰러 강제가 어려워 유닛 테스트로만 검증. (2) Android 실기기 시각 검증 — MIUI가 uninstall·`pm clear`를 모두 차단(SecurityException)해 이미 적용된 이전 OTA 번들을 builtin(신규 코드)으로 리셋할 수 없었다. OTA 메커니즘 자체는 [[ADR-026]]에서 실기기로 검증됐고 동의 UX 코드는 iOS와 동일하다(플랫폼 무관 JS). 다음 네이티브 빌드 배포 시 자연 전환됨.

**추가(2026-07-17) — 적용(재시작) 시 스플래시로 리로드 구간 커버**: `set()` 적용은 웹뷰를 리로드하는데, 새 문서가 첫 페인트를 하기 전까지 웹뷰의 네이티브 배경색(`capacitor.config` `backgroundColor` `#FB8101`)이 그대로 드러나 주황 화면이 깜빡인다 — 디버그 데이터 초기화의 `window.location.reload()`에서 같은 증상을 발견해 원인을 규명했다(2026-07-17). 앱 실행 때 이 구간을 네이티브 스플래시가 덮는 것([[ADR-025]])과 동일하게, 적용 직전 `showSplashScreen()`(`native/splash-screen.ts`, `autoHide:false`)을 띄우고 리로드된 앱의 부팅 흐름(App.tsx → `hideSplashScreen`, 최소 표시 시간 보장)이 내리게 한다. 스플래시 표시가 실패해도 적용은 계속 진행한다(깜빡임은 미관 문제일 뿐 업데이트 적용을 막을 이유가 아님).

**정정(2026-07-17) — 리로드 커버 스플래시가 Android에서 가로로 눌리고 시스템 바를 못 덮는 문제**: 위 "추가"의 `showSplashScreen()`이 Android에서 그리는 스플래시(`@capacitor/splash-screen` `show()` — WindowManager에 ImageView를 직접 얹는 방식)에 결함 2가지가 실기기(갤럭시 Z 플립3, Android 15)에서 화면 녹화로 재현됐다(사용자 리포트, 2026-07-17). (1) **가로 눌림**: `androidScaleType` 미지정 시 플러그인 기본값이 `FIT_XY`(비율 무시 늘리기)라 정사각(2732×2732) `@drawable/splash`가 세로로 긴 화면에 맞춰 늘어나 로고가 가로로 눌려 보인다 — [[ADR-029]]에서 `windowBackground`(`Gravity.FILL`)로 겪은 것과 같은 증상의 플러그인판. (2) **시스템 바 미커버**: 플러그인이 스플래시 뷰에 `fitsSystemWindows`를 하드코딩해 이미지가 상태바·제스처 바 영역을 덮지 못하고, 그 자리에 직전 화면 색(설정 화면 베이지·탭바 흰색)이 위아래 띠로 남아 스플래시 주황과 안 맞는다. 해결은 두 겹이다. **(1) 플러그인 설정**(`capacitor.config.ts`): `androidScaleType: 'CENTER_CROP'`([[ADR-029]] `activity_splash.xml`의 `centerCrop`과 동일 원리로 비율 유지) + `backgroundColor: '#FB8101'`(뷰가 인셋 패딩으로 못 덮는 영역을 이미지 가장자리와 같은 브랜드 주황으로 채움) — 이걸로 눌림과 상단 상태바는 해결되지만, 실기기 재검증 결과 **하단 내비게이션 바 인셋만큼은 플러그인 창 자체가 잘려** 제스처 띠가 여전히 남았다. `splashImmersive`(바 숨김)도 검토했으나 플러그인이 hide 시 액티비티에 `setDecorFitsSystemWindows(true)`를 걸어 앱의 edge-to-edge([[ADR 시스템 바]] `SystemBarsPlugin`)를 되돌리는 부작용이 있어 기각. **(2) 스플래시 창이 못 덮는 띠의 "뒤"를 주황으로**: 리로드 타임라인 3구간 중 가운데(웹뷰 네이티브 배경)는 이미 `#FB8101`이므로, 양끝만 채운다 — 리로드 직전 구 문서 위에 전체 화면 브랜드색 오버레이를 깐다(`showSplashScreen()`이 native `show()` 전에 DOM에 삽입, 문서 파괴와 함께 사라지므로 정리 불요). 리로드 직후 신 문서는 `index.html`의 정적 `#boot-cover`(전체 화면 고정 div, 인라인 스타일 브랜드색 — 파싱 첫 시점부터 존재)가 앱 준비 시점(`hideSplashScreen()`이 제거)까지 캔버스와 첫 렌더를 통째로 덮는다. 처음엔 `<html>` 인라인 배경으로 캔버스만 칠했으나, **다크 테마(레테)에서 흰 띠가 여전히 남는다는 사용자 스크린샷으로 재발견**(2026-07-17): 테마는 `restoreFromStorage`(비동기 Preferences)가 useEffect에서 적용하므로 **첫 렌더는 항상 라이트 기본값**이고, 탭바가 라이트 색으로 먼저 그려지면 캔버스 배경이 아니라 "렌더된 콘텐츠"가 띠에 노출된다 — 라이트 테마에선 최종 UI와 같은 색이라 안 보였을 뿐. `#boot-cover`는 렌더된 콘텐츠까지 덮으므로 테마 적용 전 라이트 플래시 자체가 사용자에게 보이지 않는다(제거 시점의 스플래시 최소 표시 1초가 테마 복원(~수십 ms)보다 훨씬 길어 실질 보장). 콜드 스타트 스플래시([[ADR-025]]/[[ADR-029]] — Android 12+ 테마·`SplashActivity` 경로)는 이 플러그인 설정을 안 타므로 영향 없고(신 문서 인라인 배경은 콜드 스타트의 스플래시→앱 전환 캔버스색을 베이지에서 브랜드 주황으로 바꿔 오히려 연속성이 좋아짐), iOS는 런치 스토리보드가 원래 `scaleAspectFill`이라 눌림이 없었다(`backgroundColor`는 스토리보드 이미지 뒤 배경이라 무해).
