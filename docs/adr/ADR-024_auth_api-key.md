# ADR-024 API 키 로그인과 키 재입력

> 🟢 유효
> 옛 번호: ADR-065 결정 1 · ADR-115 · ADR-116 결정 1 · 2 · ADR-214 · ADR-215 결정 1 · 2 · ADR-317
> 관련 소스: `app/auth/` · `features/auth/` · `nexon/key-stage.ts` · `nexon/errors.ts` · `storage/api-key.ts`

## 배경

이 앱은 넥슨 Open API 를 사용자의 API 키로 부른다. 그래서 키를 입력하는 화면이 곧 로그인 화면이다.
키에는 두 가지 문제가 생길 수 있다. 하나는 처음부터 쓸 수 없는 키를 넣는 경우다. 넥슨에서 키를 만들 때
단계를 `개발 단계` 로 고르면 호출 한도가 초당 5건뿐이라, 이 앱이 한 번에 보내는 요청을 감당하지 못한다.
다른 하나는 잘 쓰던 키를 나중에 못 쓰게 되는 경우다. 사용자가 넥슨에서 키를 지웠거나, 호출 한도를 넘었거나,
넥슨 로그인이 만료된 경우다.

이 문서는 키를 받아 저장하기까지, 그리고 저장된 수단으로 더 이상 조회할 수 없을 때 사용자에게 알리고
다시 로그인하게 하기까지를 다룬다. 넥슨 로그인 자체는 [[ADR-025]] 에 있다.

## 결정

### 결정 1. 로그인 상태는 셋이고, 실패는 상태로 두지 않는다

`AuthStatus` 는 `signedOut` · `verifying` · `signedIn` 셋이다. 검증에 실패해도 화면에는 같은 로그인 폼이
그대로 있으므로, 실패를 상태로 따로 두면 같은 사실을 두 값이 말하게 된다. 그래서 실패 원인은 `error`
필드에만 담는다.

이 상태에는 캐릭터와 관련된 값이 없다. 로그인 방식이 바뀌어도 캐릭터 설정이 영향을 받지 않게 하려는
것이다. 로그인은 `features/auth/` 에, 앱을 켰을 때 어느 화면을 보여 줄지는 `features/app-entry/` 에 둔다.
호출은 한 방향으로만 한다. 로그인이 성공하거나 로그아웃하면 `features/auth` 가 `useAppEntryStore` 를
부르고, 반대 방향의 호출은 없다.

### 결정 2. 키는 `character/list` 한 번으로 검증하고, 무효 키 판정은 한 함수가 한다

키를 제출하면 `character/list` 를 한 번 불러 검증한다. 이 시점에는 ocid 가 없어서 키만으로 부를 수 있는
엔드포인트가 이것 하나뿐이다.

넥슨은 무효한 키에 401 이 아니라 400 `OPENAPI00005` 를 준다. 처음부터 없던 키도, 쓰다가 넥슨에서 지운
키도 같다. 이 코드를 알 수 없는 400 으로 처리하면 사용자는 키를 못 쓰게 됐는데도 `네트워크 오류가 발생했습니다`
만 보게 된다. 그래서 401 · 403 · 400 `OPENAPI00005` 를 모두 무효 키로 보고, 그 판정은
`nexon/errors.ts` 의 `isInvalidApiKeyError` 한 곳에서만 한다. 무엇이 무효 키인지는 넥슨이 정하는 사실이라,
여러 곳에 조건을 복사해 두면 서로 어긋날 수 있기 때문이다.

### 결정 3. 개발 단계 키는 저장하기 전에 막는다

검증이 성공하면 `character/list` 를 10건 동시에 보낸다(`nexon/key-stage.ts` 의 `probeApiKeyStage`).
개발 단계 한도가 초당 5건이므로, 10건 가운데 하나라도 429 가 오면 개발 단계 키로 판정한다.

- 검증 1건을 먼저 보내고, 성공했을 때만 10건을 보낸다. 키 오타처럼 흔한 실패 때문에 10건을 낭비하지
  않으려는 것이다.
- 판정 결과는 `'developmentStage' | 'undetermined'` 둘뿐이고 `service` 는 없다. 429 를 보면 개발 단계가
  확실하지만, 429 를 보지 못했다고 서비스 단계라고 할 수는 없다. 429 가 아닌 실패는 모두
  `undetermined` 로 두고, 이때는 막지 않는다. 막으려면 429 라는 확실한 근거가 있어야 한다. 그래야
  네트워크가 끊긴 상황에서 멀쩡한 키를 거부하지 않는다.
- 판정은 `setApiKey` 보다 먼저 한다. 저장한 뒤에 지우는 순서라면, 그 사이에 앱이 꺼졌을 때 개발 단계
  키가 남고 다음 부팅이 그 키로 앱을 연다.
- 막히면 `developmentStageBlocked` 를 켜고 `status` 를 `signedOut` 으로 되돌린다. `verifying` 에 그대로
  두면 모달을 닫은 뒤에도 제출 버튼이 스피너인 채로 남아 다시 입력할 수 없다. 이 실패는 `error` 에 넣지
  않는다. `error` 는 그대로 토스트 문구가 되므로, 넣으면 모달과 토스트가 같은 말을 두 번 한다.

검증 1건은 통과했는데 10건이 같은 1초 안에 나가지 못하는 경우처럼, 판정을 못 하고 통과하는 개발 단계
키가 있을 수 있다. 그런 키는 쓰다가 429 를 만나 결정 6 의 알림을 받는다.

### 결정 4. 개발 단계 키 모달은 제목에 `개발 단계` 라는 말을 쓰지 않는다

`DevelopmentStageKeyModal` 의 문구는 다음과 같다.

| 위치 | 문구 |
|---|---|
| 제목 | `이 키로는 연결할 수 없습니다` |
| 표 윗줄 | `넣으신 키` · `개발 단계` |
| 표 아랫줄 (`primary-tint` 바탕) | `필요한 키` · `서비스 단계` |
| 본문 | `넥슨 오픈 API에서 단계를 ‘서비스 단계’로 골라 키를 새로 발급받은 뒤 입력해주세요.` |
| 주 버튼 | `다시 입력하기`. 모달만 닫는다 |
| 아래 링크 | `발급 방법 자세히 보기`. 안내 사이트를 인앱 브라우저로 연다([[ADR-025]] 결정 8) |

이 사용자는 `개발 단계` 가 무슨 뜻인지 모르고 그것을 골랐다. 제목에서 그 말을 다시 들려줘도 무엇이
잘못됐는지 알 수 없다. 그래서 제목은 쓸 수 없다는 사실만 말하고, 두 단계는 아래 표에서 위아래로 나란히
보여 준다. 두 줄을 붙여 두면 다른 값을 골랐어야 했다는 것이 한눈에 보인다. 왜 쓸 수 없는지와 한도가
몇 건인지는 적지 않는다. 그걸 알아도 사용자가 할 일은 새 키를 받는 것 하나로 같기 때문이다.

- 주 버튼은 폼으로 돌아가게 한다. 사용자가 바로 할 일이 폼으로 돌아가는 것이어서, 가장 큰 버튼이 앱 밖으로
  내보내면 안 된다. 발급 안내는 그 아래 링크로 두고, 주소는 폼과 같은 `app/auth/api-key-links.ts` 의
  `GUIDE_URL` 을 쓴다. 주소를 두 곳에 적어 두면 사이트를 옮길 때 한쪽만 바뀐다.
- 모달은 닫을 수 있다. 뒤에 키 입력 폼이 그대로 있어서, 닫으면 곧바로 다시 입력할 수 있다. 받지 않은
  키라서 확인을 눌러도 저장소는 건드리지 않는다.
- 배지는 `primary-tint` 바탕에 `primary-ink` 열쇠이고, 붉은 원이 아니다. 무언가 실패한 것이 아니라
  다른 종류의 키를 넣은 것이고, 앱에서 빨강은 이미 조회 실패와 삭제에 쓰고 있다. 원이 아니라 네모로 한
  것은 아래 표와 모서리를 맞추기 위해서다.
- 골격은 `ApiKeyNoticeModal` 과 같은 `organisms/NoticeModal` 을 쓴다. 두 모달이 같은 앱의 것으로 보이게
  하려는 것이다.

### 결정 5. 저장된 수단으로 조회할 수 없으면 닫을 수 없는 모달로 알린다

원인은 셋이고(`ApiKeyNoticeKind`), 셋 다 저장된 수단으로는 더 조회할 수 없다는 점이 같다. 그래서 알리는
방법도 하나로 두고 아이콘과 문구만 바꾼다.

| 원인 | 신호 | 아이콘 | 제목 | 본문 |
|---|---|---|---|---|
| `invalid` | 401 · 403 · 400 `OPENAPI00005` | `KeyRound` | `API 키가 더 이상 유효하지 않습니다` | `키 입력 화면으로 이동합니다.` |
| `rateLimited` | 429 | `Gauge` | `호출 한도를 초과했습니다` | `서비스 단계 키로 다시 입력해주세요.` |
| `signInRequired` | 로그인 자격의 401 · 403 (결정 8) | `CircleUserRound` | `넥슨 로그인이 만료됐습니다` | `다시 로그인해주세요.` |

- 실패를 알게 되면 `noticeApiKeyIssue` 가 `apiKeyNotice` 만 채운다. `status` 는 바꾸지 않아서 뒤에 원래
  화면이 그대로 남는다. 화면을 먼저 바꾸면 사용자는 이미 바뀐 화면에서 이유를 읽게 된다. 토스트도 띄우지
  않는다. 스스로 사라지는 토스트로는 반드시 확인해야 하는 실패를 놓칠 수 있고, 같은 말을 두 번 하게 된다.
- 모달은 닫을 수 없다. 오버레이를 누르거나 안드로이드 뒤로가기를 눌러도 닫히지 않고, `확인` 하나만 있다.
  이 상태에서는 어느 화면도 제대로 동작하지 않으므로 닫아 봐야 돌아갈 화면이 없다.
- 알림이 이미 떠 있으면 새로 알리지 않는다. 여러 화면이나 캐릭터에서 동시에 실패해도 모달은 하나이고,
  원인이 겹치면 먼저 뜬 것을 유지한다. 읽던 문구가 눈앞에서 바뀌면 안 되기 때문이다.
- `status` 가 `signedOut` 이나 `verifying` 이면 알리지 않는다. 이미 로그인 화면이라 보낼 곳이 없고, 폼에서
  난 실패는 폼의 토스트가 알린다. 캐릭터 설정 화면은 `signedIn` 이라 알림을 받는다. 429 로 캐릭터 목록이
  비는 일이 그 화면에서 일어나므로, 거기서 막으면 그 사용자는 빠져나갈 수 없다.
- 429 문구에는 해야 할 일까지 넣는다. 같은 실패의 토스트(`호출 한도를 초과했습니다`)는 한 줄을 넘으면 잘리지만,
  모달은 줄을 바꿀 수 있다. 로그인 만료 본문은 다음에 무슨 일이 일어나는지를 말하지 않는다. API 키가
  남아 있는 사용자는 확인을 눌러도 화면이 그대로여서, 사용자마다 결과가 다르기 때문이다.

### 결정 6. 실패를 알리는 곳은 `useApiKeyNotice` 를 거친다

스케줄 동기화(`useScheduleSyncErrorToast`)와 캐릭터 관리 화면(`SettingsCharactersScreen`)은 조회 오류를
`useApiKeyNotice` 에 넘긴다. 이 훅은 `ScheduleSyncError` 의 `invalidApiKey` · `rateLimited` ·
`signInRequired` 만 알림으로 넘기고 나머지는 무시한다. 스케줄 동기화 토스트는 이 셋에 토스트를 띄우지
않는다.

- 캐릭터 설정 화면(`CharacterSetupScreen`)은 429 만 넘긴다. 이 화면의 무효 키 오류는 알림으로 넘기지 않고,
  오류 화면에 `API 키를 다시 확인해주세요` 와 `다시 시도` 버튼을 보여 준다(`formatRosterError` 의
  `characterSetup` 문구).
- 캐릭터 관리 본문(`CharacterManageBody`)은 조회되는 메이플 ID 가 하나도 없을 때 `API 키 다시 입력` 버튼을
  보여 주고, 누르면 `invalid` 로 알린다.
- 훅은 이미 넘긴 오류 객체를 모듈 범위의 `WeakSet` 에 기억해 두고 다시 넘기지 않는다. 동기화 스토어의
  `error` 는 화면이 사라져도 남아 있다. 그래서 키를 다시 넣어 화면이 다시 마운트되면 처리했던 오류가
  다시 들어오고, 그때는 알림이 꺼져 있어 방금 저장한 키가 지워진다. 화면마다 따로 기억하면 화면이
  다시 마운트될 때 지워지므로 모듈 범위에 둔다. 새로 생긴 실패는 새 객체라 다시 넘긴다.

### 결정 7. 확인을 누르면 못 쓰게 된 수단만 지우고, 남은 수단을 센 뒤에 이동한다

`confirmApiKeyNotice` 가 삭제와 이동을 이 순서로 한다.

1. 못 쓰게 된 수단을 지운다. 로그인 만료면 `clearNexonLogin()` 으로 넥슨 로그인만 지운다. 무효 키와 429 는
   실패와 함께 넘어온 키(`ApiKeyNotice.apiKey`)가 있으면 `removeApiKey` 로 그 키 하나만 지운다. 넘어오지
   않았으면 어느 키인지 알 수 없어 `removeAllApiKeys` 로 API 키를 모두 지운다.
2. `getAuthConfig()` 로 남은 수단을 센다. 남아 있으면 알림만 닫고(`NOTICE_ACKNOWLEDGED`) 앱은 그 수단으로
   계속 쓴다. 없으면 `SIGNED_OUT` 으로 로그인 화면에 보내고 진입 단계도 되돌린다.
3. 지우다 실패했으면 세지 않고 로그인 화면으로 보낸다. 무엇이 남았는지 모르는 채로 앱을 열어 두면 같은
   실패를 끝없이 다시 만난다.

연결 해제용 `clearAuthConfig` 는 여기서 쓰지 않는다. 그 함수는 인증 수단을 통째로 지워서 다른 넥슨
계정의 키까지 사라진다. 추적 캐릭터 같은 다른 저장값도 지우지 않는다. 못 쓰게 된 것은 키 하나뿐이고,
결정 9 의 재개가 그 값들을 쓴다.

429 에도 키를 지운다. 지우지 않으면 앱을 다시 켤 때 같은 키로 열려 또 막히고, 사용자는 다시 켜면 될 것
같은데 안 되는 상태에 빠진다. 같은 키를 다시 붙여 넣는 것은 막지 않는다. 삭제가 실패해도 다음에 같은
알림을 다시 받을 뿐이라 더 진행할 수 없는 상태가 되지는 않는다.

### 결정 8. 로그인 자격의 401 은 키 무효화와 따로 던진다

넥슨 로그인으로 부른 요청이 401 · 403 으로 실패하면 `nexon/http.ts` 가 `NexonSignInRequiredError` 를
던진다. 서버의 프렌즈 스트림이 401 로 거절하거나, 스트림의 `end` 줄이 `relogin` 이거나, `fail` 줄의
status 가 401 · 403 일 때다. 그 밖의 401 · 403 은 `NexonAuthError` 다.

`NexonSignInRequiredError` 는 `NexonAuthError` 를 상속하지 않는다. 상속하면 `isInvalidApiKeyError` 가
참이 되어 무효 키로 처리되고, 확인을 누르는 순간 멀쩡한 API 키가 모두 지워진다. 로그인으로 부르다
실패한 것이라 함께 넘길 키가 없기 때문이다.

이 오류는 `ScheduleSyncError` 의 `signInRequired` 가 되고, 재시도 버튼은 주지 않는다. 다시 눌러도 같은
401 이 나기 때문이다. 토스트 · 목록 오류 · 갱신 실패 배너 문구는 `features/schedule-sync/format.ts` 에 있다.

### 결정 9. 키를 다시 넣으면 앞서 고른 것을 다시 묻지 않는다

키가 무효화되어 로그인 화면으로 왔더라도 못 쓰게 된 것은 키 하나라, 추적 캐릭터 같은 나머지 저장값은 그대로
맞다. 그래서 키를 다시 넣으면 `signIn` 이 검증 응답을 `useAppEntryStore.resolveAfterSignIn` 에 넘기고,
부팅 때와 같은 함수(`deriveEntryStage`)로 다음 단계를 정한다. 판정을 한 함수로 두는 것은 부팅과 키
재입력의 규칙이 어긋나지 않게 하려는 것이다.

새로 넣은 키가 다른 넥슨 계정의 것일 수도 있다. 그래서 검증 응답에 저장된 추적 ocid 가 하나도 없으면
캐릭터 설정부터 다시 하게 한다. 이미 받은 응답으로 판정하므로 호출이 늘지 않는다. 저장된 추적 목록이
비어 있으면 비교하지 않는다. 처음 키를 넣는 사용자는 지킬 목록이 없기 때문이다. 저장값으로 다음 단계를
정하는 표는 [[ADR-026]] 에 있다.

### 결정 10. 키 입력이 실패하면 원인에 맞는 문구를 토스트로 알린다

`signIn` 이 실패하면 `formatAuthError` 가 원인(`AuthError`)마다 다른 문구를 만들어 토스트로 띄운다. 무효 키 ·
429 · 네트워크 오류 · 저장 실패가 각각 다른 문구다. 원인과 관계없이 한 문구만 띄우면 사용자는 키가 틀렸는지
네트워크가 끊겼는지 알 수 없다.

- 키 저장(`setApiKey`)도 `try` 안에서 한다. 밖에 두면 저장이 실패해도 아무 일도 일어나지 않은 것처럼 보인다.
  실패하면 `storageWriteFailed` 로 알린다.
- 폼 아래에 문구를 따로 두지 않는다. 토스트가 사라진 뒤에도 폼은 그대로 있어서 다시 입력하면 된다.
- 토스트에 버튼은 두지 않는다. 로그인 화면에서는 갈 수 있는 설정 화면이 없고, 다시 시도는 폼에서 한다.
- `formatAuthError` 는 `features/auth/format.ts` 에 둔다. 이 함수를 쓰는 것이 스토어(`features/`)라서,
  `app/` 에 두면 `features/` 가 `app/` 을 가져다 쓰게 된다.
