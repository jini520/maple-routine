### ADR-033: 보스 수익 — 등록 난이도 ≠ 실제 처치 난이도 오류 수정 (ownComplete 도입), bossDaily/bossWeekly 교차 오염 수정 (구현 완료)

**배경**: [[ADR-032]] 작업 중 사용자가 지적한 문제(2026-07-22) — 보스 스케줄러에 특정 난이도로 등록해두고 실제로는 다른 난이도를 처치하면 보스 수익 페이지가 어떻게 동작하는지 조사 요청. 확인 결과 두 가지 버그를 재현으로 확인했다:

1. **이번 주(실시간) 화면**: [[ADR-031]] 결정 2가 도입한 "등록된 항목은 다른 난이도가 완료면 자기도 완료로 승격" 로직(`normalize.ts`)이, 등록 난이도의 `difficulty` 필드는 그대로 둔 채 `isComplete`만 승격시킨다. 보스 수익 화면은 이 `difficulty`를 그대로 가격 조회에 써서, 루시드를 이지로 등록하고 실제로 노멀을 처치해도 **이지 가격(29,800,000)으로 잘못 계산**되어 표시·자동 기록됐다(재현 확인).
2. **과거 기간 백필**: `backfillTarget`은 그룹 dedup 없이 `isComplete`만 보고 완료 보스를 골라, 승격된 등록 항목(이지)과 실제로 완료된 미등록 항목(노멀)이 **둘 다** 통과해 `upsertBossProfitRecord`가 2번 호출됨 — 보스 하나를 한 번 잡았는데 **이중 기록**돼 그 주 합계가 부풀려졌다(재현 확인, 호출 2회).
3. 사용자가 추가로 확인해준 게임 규칙: **같은 content_name + 같은 cycle(bossWeekly/bossMonthly)에서는 한 캐릭터가 여러 난이도를 동시에 완료하는 게 불가능**하다. 단, 같은 content_name이 bossDaily·bossWeekly에 함께 오는 보스(힐라 하드·핑크빈 카오스 등, [[ADR-007]])가 있어, 이 경우까지 고려해야 한다.
4. 위 3번을 실제로 테스트해보니 새로운 교차 오염 버그가 하나 더 발견됐다: `normalize.ts`의 완료 승격 판정(`completedBossNames`)이 cycle을 구분하지 않고 전체 `boss_contents`에서 만들어져, 무관한 bossDaily 완료가 등록된 bossWeekly 항목을 잘못 완료로 승격시켰다(재현 확인 — 힐라 노멀을 bossWeekly로 등록만 하고 안 잡았는데, 힐라 하드가 bossDaily로 완료됐다는 이유만으로 `isComplete: true`가 됨).

**결정**:

1. **`ownComplete` 필드 도입**: `BossContent`/`MatchedBoss`에 `ownComplete`(이 난이도 자신의 원본 완료 여부, 승격 없음)를 추가한다. 기존 `isComplete`(카드 뱃지 표시용, 승격됨)는 보스 스케줄러가 그대로 쓰고, 보스 수익 계산기는 `ownComplete`만 사용한다 — 승격된 `isComplete`만으로는 "등록 난이도가 진짜 완료된 건지, 다른 난이도 완료로 승격된 것뿐인지" 원리적으로 구분할 수 없어서, 정규화 단계(`normalize.ts`)에서 원본 정보를 별도로 보존해야 한다.
2. **`selectBossProfitBosses`(신규, `lib/boss-matching.ts`) 도입**: 보스 수익 전용 선택 로직. `content_name` 그룹별로 `ownComplete: true`인 항목이 있으면 그것(들)을 실제 처치 난이도로 선택하고, 없으면 등록된 항목을 미완료 placeholder로 선택한다. 위 3번 게임 규칙 덕분에 weekly/monthly에서는 `ownComplete: true` 항목이 그룹당 최대 1개임이 보장되지만, 혹시 여러 개가 나오더라도(예: 서로 다른 cycle이 우연히 같은 content_name을 쓰는 극단적 경우) 데이터를 숨기지 않고 전부 보여준다([[ADR-031]]과 동일한 철학). 보스 스케줄러 전용 `selectDisplayBosses`(등록 여부 우선, 카드 중복 방지용)는 그대로 유지 — 두 화면의 우선순위가 다르기 때문에 함수를 분리했다(수익 계산은 "실제로 얼마에 팔렸는가"가 최우선, 카드 표시는 "등록된 항목을 우선 보여주는 것"이 최우선).
3. **`refresh()`/`backfillTarget` 교체**: 보스 수익 스토어의 캐시 우선 표시·실시간 동기화·과거 기간 백필 세 경로 전부 `selectBossProfitBosses`를 쓰도록 교체했다(기존엔 `refresh()`만 `selectDisplayBosses`를 썼고 `backfillTarget`은 아예 그룹 dedup이 없었다). `BossProfitRow.isComplete`/`payoutMeso` 계산도 `isComplete` 대신 `ownComplete`를 기준으로 삼는다.
4. **bossDaily 교차 오염 수정**: `normalize.ts`의 `completedBossNames` Set을 만들 때 `bossDaily` cycle 항목을 제외한다 — 이 앱은 애초에 bossDaily를 처리하지 않으므로([[ADR-007]]), 완료 승격 판정에도 반영되면 안 된다.
5. **`mergeSchedulerState`의 stale 리셋 로직도 함께 수정**: `ownComplete` 필드를 새로 추가하면서 발견한 부수 문제 — 주간/월간 보스가 stale(미접속)이라 이전 캐시로 폴백할 때, 기존 코드는 `isComplete`만 `false`로 리셋하고 `ownComplete`는 그대로 뒀다. 이러면 지난주 완료 여부가 이번 주에도 `ownComplete: true`로 남아, 보스 수익 계산기가 아직 처치하지 않은 보스를 완료로 오판할 뻔했다 — `ownComplete`도 함께 `false`로 리셋하도록 고쳤다.

**이유**:
- `ownComplete`를 정규화 단계에서 보존하는 이유: 컨슈머(보스 수익) 쪽 로직만으로는 이미 뭉개진 `isComplete` 값에서 "승격됐는지 원본인지"를 되돌릴 수 없다 — 정보 손실은 손실이 일어난 지점(정규화)에서 막아야 한다.
- `selectDisplayBosses`를 고치지 않고 별도 함수로 분리한 이유: 두 화면의 "무엇을 우선할지"가 근본적으로 다르다(카드 표시는 등록 여부, 수익 계산은 실제 처치 여부) — 하나의 함수에 두 우선순위를 조건부로 넣으면 어느 화면이 어떤 경로를 타는지 추적하기 어려워진다.
- 3번 게임 규칙(같은 content_name·같은 cycle 동시 다난이도 완료 불가) 덕분에 `selectBossProfitBosses`가 "여러 개 진짜 완료" 경우를 방어적으로 처리할 필요가 사실상 없어져 로직이 단순해졌고, [[ADR-031]]이 우려했던 "카드 두 장" 현상도 이 재검토로 재해석됐다(위 참고).

**트레이드오프**:
- 이미 (이 수정 이전에) 잘못된 난이도로 저장된 `boss_profit_records`/`boss_party_settings` 과거 데이터는 소급 수정하지 않는다 — 이 프로젝트는 과거 기록을 임의로 되돌리지 않는다는 원칙([[ADR-008]] 참조 무결성)을 따른다.
- `ownComplete`가 그룹당 최대 1개라는 보장은 같은 content_name이 서로 다른 cycle에 걸쳐 나타나지 않는다는 전제에 의존한다 — `groupByApiName`이 cycle을 구분하지 않고 묶기 때문에, 만약 이 전제가 깨지는 보스가 발견되면 재검토가 필요하다.

**추후 확장 시 설계 원칙 (아직 코드 변경 없음, 논의만)**:
- **드랍 아이템 확장([[ADR-032]] 결정 4)과의 관계**: 미완료 placeholder(등록 난이도로 표시 중)에 드랍 아이템을 미리 추가했는데 나중에 실제 처치 난이도가 다르게 확정되는 경우, 아이템 기록이 고아가 되지 않으려면 드랍 아이템 테이블의 키를 `(ocid, boss, difficulty, period_key)`가 아니라 **난이도를 뺀 `(ocid, boss, period_key)`**로 설계해야 한다 — "이번 주 이 보스를 처치했다"는 사실과 "어느 난이도였는가"는 서로 다른 차원이고, 후자는 나중에 정정 가능한 부가 속성으로 다뤄야 마이그레이션 로직 없이 자연스럽게 해결된다. `boss_profit_records`(가격 계산용)는 난이도별 결정석 가격이 다르므로 지금처럼 난이도를 키에 유지하는 게 맞다 — 이 원칙은 드랍 아이템 테이블에만 적용한다.
- **인게임 `registration_flag`와 무관한 앱 자체 등록/난이도 수정 계획과의 관계**: "미완료일 때 어떤 난이도를 보여줄지"(현재 Nexon의 `registration_flag`+`difficulty`를 직접 읽음)를 작은 조회 함수 하나로 감싸두면, 나중에 이 조회를 앱 자체 설정(사용자가 인게임 등록과 무관하게 앱 안에서 직접 설정)으로 대체할 때 `selectBossProfitBosses`의 선택 로직은 그대로 두고 그 함수 내부만 교체하면 된다.
