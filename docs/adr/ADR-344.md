# ADR-344: 넥슨 공지는 새 글을 가릴 만큼만 저장한다. 상세는 썬데이 메이플만 받는다

> ⚪ 미구현 · 2026-10-08 · 설계 · 사용자 지정

**관련**: [[ADR-228]](공지 계약과 푸시 `data` 를 정한 문서. 그 결정 1 의 계약은 안 바뀐다) ·
[[ADR-277]](공지의 기준은 서버이고 기기는 사본을 든다) · [[ADR-227]](서버를 들인 결정) ·
이슈 #370(썬데이 배너. 이 결정이 남기는 것의 유일한 소비자)

## 맥락

### 넥슨 공지의 상세를 앱이 안 읽는다

앱은 **우리 서버에서 `app` 분류만** 가져간다(`features/notice/notice-feed.ts` 의 `receive`).

```ts
if (kind === 'app') return fetchNotices(20, ['app'])        // 우리 서버
const credential = await savedCredential()
return fetchNexonNoticeList(credential, kind).catch(() => null)   // 넥슨 직접
```

상세도 같다. `fetchNoticeDetail` 이 id 모양을 보고 갈라서 `game-150276` 꼴은 넥슨으로 간다. 그래서
서버가 든 넥슨 공지의 본문은 **앱에서 열 수 있는 길이 없다.**

앱은 같은 HTML 을 자기 파서(`nexon/notice/contents.ts`)로 다시 파싱해 화면을 그린다. 서버 파서
(`html.ts`)와 블록 타입 5종 · `MAX_BLOCKS = 2000` 까지 같은 모양이다.

### 파싱 결과가 둘인데 하나만 쓰인다

`poll.ts` 가 공지마다 상세를 받아 파싱하고 둘을 만든다.

| 만드는 것 | 실제 소비자 |
|---|---|
| `blocks` | **`/v1/sunday-maple` 뿐.** `SundayRecord.blocks` |
| `body` 미리보기 | **없다.** 넥슨 공지의 푸시는 제목만 쓴다 |

푸시 문구를 만드는 `pushTextFor` 가 `notice.body` 를 **`app` 분기에서만** 읽는다. 넥슨 공지는
`PUSH_TITLE[kind]` 와 `notice.title` 로 만든다. 그래서 미리보기를 뽑으려고 423KB HTML 을 파싱하는데
그 값이 아무 데도 안 간다.

### 크기가 치우쳐 있다 (운영 DB 실측 2026-10-08)

| `kind` | 행 | `blocks` 합 | 평균 |
|---|---|---|---|
| `update` | 23 | **1,036 kB** | **45 kB** |
| `game` | 50 | 78 kB | 1.6 kB |
| `event` | 36 | 9.5 kB | 265 B |
| `cashshop` | 33 | 7.2 kB | 217 B |
| `app` | 7 | 없음 | |

`update` 하나가 전체의 90% 다. `html.ts` 주석의 실측과 맞는다 - 업데이트 한 건이 423KB · 문단
1,200개다.

### 썬데이 판정은 제목만 본다

`isSundayMaple(title)` 이 공백을 지운 제목에 `썬데이` 가 담겼는지 본다. 제목은 **목록 응답**
(`NexonListItem`)에 있다. 그래서 상세를 받기 전에 가릴 수 있다.

알림 판정도 같은 함수를 쓴다(`shouldNotify`: `event` 면 썬데이만, 나머지 분류는 전부). 판정이 한
자리에 모여 있다.

## 결정

### 결정 1. 상세는 썬데이 메이플만 받는다 (사용자 지정)

```
새 id 마다  isSundayMaple(목록의 제목)
              참   → 상세 조회 → 파싱 → blocks · starts_at · ends_at 저장
              거짓 → 상세를 안 받고 목록 값만 저장
```

목록 값은 `id` · `kind` · `title` · `published_at` · `link` 다. 그것으로 `knownIds` 와 `hasAny` 가
새 글을 가리고, `pushTextFor` 가 알림 문구를 만든다. 더 필요한 것이 없다.

**회차마다 최대 스물이던 상세 조회가 0~1번이 된다.** 썬데이는 주 1~2회다.

### 결정 2. 서버 파서는 남는다

썬데이의 `blocks` 를 만드는 유일한 수단이다. `/v1/sunday-maple` 이 그것을 응답에 싣고 #370 이 그
소비자를 세운다.

**다만 두 파서가 같은 결과를 내야 할 이유는 사라진다.** 서버 파서는 썬데이 한 종류만 다루고 화면을
그리지 않는다. 화면용 블록의 주인은 앱 파서 하나다.

### 결정 3. `notices.body` 를 nullable 로 바꾼다 (사용자 지정)

운영자 공지 말고는 넣을 내용이 없다. 넥슨 공지는 `NULL` 이다.

**계약은 안 바뀐다.** [[ADR-228]] 결정 1 의 `Notice.body` 는 그대로 `string` 이고, 응답을 만드는
자리가 `NULL` 을 빈 문자열로 바꾼다. 앱은 `app` 분류만 가져가므로 그 값은 늘 차 있다.

### 결정 4. `notices.ongoing` 칸을 걷는다 (사용자 지정)

캐시샵 상시 판매 여부인데 **읽는 `SELECT` 가 0건**이다. `poll.ts` 가 넣고 `db.ts` 가 쓰기만 한다.
안 쓸 값이다.

`starts_at` · `ends_at` 은 **남긴다.** 썬데이 응답이 쓰고, 정렬이 `startsAt ?? publishedAt` 이다.
그 둘은 상세에만 있어서(`NexonDetail`) 결정 1 이 썬데이에만 상세를 받는 것과 맞는다.

### 결정 5. 기존 행의 `blocks` 를 비운다 (사용자 지정)

운영자 공지와 썬데이 메이플만 남기고 `NULL` 로 만든다.

```sql
UPDATE notices SET blocks = NULL
 WHERE kind <> 'app'
   AND NOT (kind = 'event' AND regexp_replace(title, '\s+', '', 'g') LIKE '%썬데이%');
```

판정을 SQL 로 옮겨 적는 것이 `isSundayMaple` 과 갈릴 자리다. 두 벌이 되지만 이 문장은 **한 번만
돈다** - 마이그레이션이고, 그 뒤로는 결정 1 이 애초에 안 만든다.

## 대가

- **되돌릴 수 없다.** 넥슨이 지난 글 상세를 400 으로 거절해 우리 DB 가 유일한 사본이었다. 비우면
  영구히 사라진다. 쓰는 곳이 없는 것을 확인하고 고른 것이다(사용자 지정 2026-10-08).
- **썬데이 판정이 바뀌면 그 전에 지나간 썬데이를 못 살린다.** `isSundayMaple` 주석이 **아직 실물
  제목을 못 봤다**고 적어 뒀다. 판정이 좁아서 놓친 썬데이는 상세를 안 받았으므로 `blocks` 가 없고,
  나중에 함수를 고쳐도 그 글은 비어 있다. 종전에는 전부 저장해 뒀으니 고치면 함께 바로잡혔다.
- **`ongoing` 을 다시 쓰려면 칸을 되살려야 한다.** 캐시샵 상시 판매 여부를 화면에 쓰기로 하는 날
  마이그레이션이 하나 더 든다.
- **SQL 에 썬데이 판정이 한 벌 더 생긴다.** 결정 5 의 한 번만 도는 문장이다.

## 기각

- **서버 파서를 걷는다.** 썬데이의 `blocks` 를 만들 수단이 없어진다. 사용자 지적으로 기각했다
  (결정 2).
- **`blocks` 를 전부 남긴다.** 1MB 중 쓰이는 것이 9.5kB 미만이고, 앱이 같은 HTML 을 자기 파서로
  다시 파싱한다.
- **푸시에서 `body` 를 뺀다.** [[ADR-228]] 결정 1 의 계약을 바꾸게 되고 옛 앱이 그 칸을 기대한다.
  결정 3 이 칸만 nullable 로 바꿔 계약을 지킨다.

## 열린 질문

- **`/v1/sunday-maple` 이 `blocks` 를 계속 실을지.** 지금 앱에 소비자가 없다(`src/` 에 `sunday` 가
  0건). #370 이 배너를 세울 때 그림을 서버 블록에서 받을지 넥슨에서 직접 받을지 정한다. 넥슨에서
  받기로 하면 결정 2 의 근거가 사라지고 서버 파서를 걷을 수 있다.
- **놓친 썬데이를 되받을 길.** 대가 둘째 항목이다. 넥슨이 지난 글을 400 으로 거절하므로 지금은 길이
  없다.
