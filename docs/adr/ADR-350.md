# ADR-350: 게임 데이터는 서버가 든다. 앱은 `GET /v1/game-data` 하나로 받는다

> 🟢 유효 · 2026-10-16 · 사용자 지정 · **토대 구현 · 배포 완료**(2026-10-16. 서버 `GET /v1/game-data` · 씨앗 CLI · 앱의 받는 통로, 보스 표를 그 안으로 접었다) · **2단계 드롭 묶음 · 3단계 월드 · 4단계 지출 · 심볼 · 5단계 컨텐츠 · 6단계 장비 · 강화 · MVP 의 서버 쪽 구현 완료**(정정 1 ~ 5, 2026-10-16 ~ 17. 표 스물하나 · 씨앗 열하나 · 관리 화면 열하나. 정정 1 ~ 4 는 배포 완료. 앱 쪽은 한 번에 바꾼다). 실기기 미검증.

## 맥락

`src/data/*.json` 21개 중 14개가 게임 수치다. 결정석 가격 · 드롭 표 · 드롭 아이템 · 상자 둘 · 고가 목록 ·
장비 · 사냥터 · 심볼 비용 · 강화 비용 · MVP 등급 · 컨텐츠 표 · 공유 카탈로그 · 지출 카탈로그 · 월드다. 게임
패치마다 값이 바뀌는데 지금은 값 하나를 고쳐도 OTA 를 발행해야 앱이 안다. 지출 카탈로그의 메포샵 묶음을
열고 닫는 것도 OTA 다.

[[ADR-349]] 가 보스 표 하나를 서버로 옮기고 통로를 세웠다. 번들 사본으로 켜고, 켤 때 서버 응답의 `updatedAt`
이 다르면 덮고, 빌드 전 스크립트가 사본을 다시 쓴다. 그 문서가 결정석 가격과 드롭 표를 열린 질문으로 남겼다.

2026-10-16 에 파일 전부를 검토했다(사용자 요청). 파일마다 규모 · git 변경 횟수 · 소비 코드를 열어 **읽지 않는

번들에 남는 것은 일곱이다. `bosses.json` 은 이미 서버 사본이고, `job-themes.json` 과 크롭 파일 넷은 게임
수치가 아니라 화면 설정이며 그림과 짝이다. `release-notes.ts` 와 `feature-guides/` 는 앱 문구다.

## 결정

### 결정 1. 끝점 하나 `GET /v1/game-data` 가 표 전부를 한 번에 준다. 표마다 `updatedAt` 이다 (사용자 지정)

```
GET /v1/game-data
→ {
    "bosses": { "updatedAt": "…", "rules": { … }, "bosses": [ … ] },
    "dropItems": { "updatedAt": "…", "items": [ … ] },
    …
  }
```

- 공개 조회다. 칸 하나가 표 하나이고, 칸의 몸체는 그 표의 응답이다. `bosses` 칸은 [[ADR-349]] 결정 3 의 몸체
  그대로다.
- 표마다 `updatedAt` 을 든다. 앱이 칸마다 사본과 비교해 **바뀐 표만** 덮기 위해서다. 응답 전체의 시각은 없다.
  하나로 접으면 표 하나가 바뀌어도 전부를 다시 쓰게 된다.
- 아직 한 번도 안 넣은 표는 그 칸의 `updatedAt` 이 `null` 이고 목록이 빈다. 앱은 그 칸을 버린다.
- 이름에 game-data 를 쓴 것은 사용자 지정이다. 무엇을 받는 끝점인지 경로만 보고 알게 한다.
- **`GET /v1/bosses` 는 남긴다.** 스토어 1.0.12 의 OTA 가 이 끝점을 부른다. 앱이 `game-data` 를 부르는 OTA 가
  나간 뒤에 걷는다(열린 질문).

### 결정 2. 옮기는 표와 차례 (사용자 지정)

PR 하나가 묶음 하나다. 묶음마다 서버 표 · 씨앗 · 앱 번들 파일 · 앱 조회 모듈을 함께 바꾼다.

| 차례 | 묶음 | 서버 표 |
|---|---|---|
| 1 | 토대. 끝점 · 씨앗 CLI · 앱의 받는 통로. 보스 표를 여기로 접는다 | 새 표 없음 |
| 2 | 드롭 아이템과 고가 칸 → 드롭 표 · 상자 둘 → 결정석 가격 | `drop_items` · `boss_drop_rewards` · `drop_boxes` · `drop_box_contents` · `boss_crystal_prices`. `maxPartySize` 는 `boss_difficulties` 칸, 기본값 6 은 `game_rules` |
| 3 | 월드 | `worlds` |
| 4 | 지출 카탈로그와 심볼 비용 | `spend_groups` · `spend_tiles` · `spend_items` · `spend_item_options` · `spend_item_forms` · `symbol_groups` · `symbols` · `symbol_level_costs`. 관세율 · 주화 판매가 · 심볼 시작일은 `game_rules` |
| 5 | 컨텐츠 표에 공유 카탈로그를 접기 | `contents` · `content_categories` |
| 6 | 장비 · 강화 비용 · MVP 등급 | `equipment_items` · `potential_reset_costs` · `soul_potential_reset_costs` · `starforce_steps` · `mvp_grades`. 상수 셋은 `game_rules` |
| 7 | 사냥터 | `hunting_regions` · `hunting_grounds` |

드롭 묶음이 먼저인 이유는 서버의 `drop_prices.item_key` 와 `world_key` 가 지금 참조할 표가 없어서다. 표가
서면 FK 를 건다. 표 이름과 칸은 그 PR 의 ADR 정정이 못박는다. 이 표는 차례와 범위만 정한다.

### 결정 3. 첫 채움은 씨앗이다. 관리 화면 폼은 자주 바뀌는 표부터 (사용자 지정)

- `node dist/cli/seed-game-data.js` 가 `src/database/seed/<표>.json` 을 읽어 **비어 있는 표만** 채운다.
  줄이 하나라도 있는 표는 건드리지 않는다. 운영자가 폼으로 고친 값을 씨앗이 덮지 않기 위해서다.
- 씨앗 파일은 앱 번들 JSON 에서 결정 7 로 걷은 칸을 뺀 것이다. 마이그레이션 SQL 처럼 실행 이미지에 그대로
  싣는다.
- 폼은 결정석 가격 · 드롭 표 · 지출 묶음과 항목 · 장비 넷부터 세운다. 변경 횟수가 많은 넷이다. 나머지 표는
  씨앗으로 서고 폼은 뒤에 붙인다.
- [[ADR-349]] 정정 1 이 JSON 붙여넣기 화면을 걷은 것과 어긋나지 않는다. 씨앗은 화면이 아니라 배포 때 한 번
  도는 CLI 이고, 표가 열셋이라 한 번은 통째로 넣을 길이 있어야 한다.

### 결정 4. 앱은 번들 사본으로 켜고, 한 번 받아 바뀐 표만 덮는다

[[ADR-349]] 결정 5 의 통로를 표 여럿으로 넓힌다.

- **번들.** 표마다 `src/data/<표>.json` 이고 모양은 응답의 그 칸과 같다. 지금 파일이 든 설명 글(`source` ·
  `note` · 각종 `…Note`)은 파일에서 빠지고 이 문서와 `foundation/game-data.md` 로 간다.
- **기기 사본.** 표마다 Preferences 키 하나다(`bossCatalog` 선례). 표 하나가 깨져도 다른 표가 선다.
- **켤 때.** `features/game-data/hydrate` 가 기기 사본을 전부 세운 뒤 `server/game-data` 로 **한 번** 받는다.
  칸마다 `updatedAt` 이 지금 표와 다르면 그 표만 덮고 사본을 바꾼다. 칸 하나의 모양이 계약을 어기면 그 칸만
  버리고 나머지는 쓴다. 못 받으면 들고 있던 표 그대로다.
- **빌드 전.** `node scripts/sync-game-data.mjs` 가 응답을 받아 번들 파일 전부를 다시 쓴다. `updatedAt` 이
  `null` 인 칸은 그 파일을 안 건드린다. `package.json` 의 `scripts` 에는 넣지 않는다. 그 칸이 OTA 지문 재료라
  (`foundation/release.md`) 스크립트 한 줄에 두 플랫폼 지문이 바뀐다.
- 표의 현재 값을 드는 자리는 표마다 하나다(`lib/boss/catalog` 선례). 조회 함수는 그 값을 읽고, 부르는 쪽은
  표가 서버에서 왔는지 모른다.

### 결정 5. 그림은 번들에 두고 서버는 파일명만 든다 (사용자 지정)

`portraitSlug` 선례 그대로다. 드롭 아이템 `iconFile` · 지출 타일 그림 · 심볼 그림 · 월드 엠블럼 · 컨텐츠
배경이 전부 앱 자산 파일명이고 서버는 그 글자만 든다. 새 항목의 그림은 여전히 앱 빌드가 필요하다. 그림을
서버로 옮기는 것은 뒤의 일이다(열린 질문).

### 결정 6. 세트는 걷고 고가는 `drop_items.valuable` 한 칸이다 (사용자 지정)

세트 넷이 정의돼 있고 드롭 표 줄 20개가 세트를 가리키는데, 코드가 세트를 쓰는 자리는 고가 판정
(`lib/drop/valuable-drops.ts`) 하나다. 세트 이름을 보이는 화면은 없다. 고가 세트는 칠흑과 광휘 둘이고 나머지
둘은 메모다.

- `drop_items` 에 `valuable` 칸을 두고 명시 13개와 두 세트 구성원 16개, 합쳐 29개를 참으로 넣는다.
- 드롭 표 줄의 `set` 칸과 `drop-items.json` 의 `sets` 를 걷는다. `valuable-drops.json` 은 없어진다.
- 새 아이템이 고가면 관리 화면에서 그 칸을 켠다. 세트 소속으로 자동 판정하는 길은 안 둔다.

### 결정 7. 걷는 칸은 PR 마다 사용자가 정한다 (사용자 지정)

맥락의 표가 후보다. 묶음 PR 을 열기 전에 그 묶음의 후보를 보이고, 걷을지 칸으로 살릴지를 사용자가 정한다.
코드가 안 읽어도 사용자가 준 자료이고 뜻이 있는 값이 있어서다. 드롭 표의 교환 가능 · 불가, 상자 확률, 장비
`group`, 사냥터 추천 레벨이 그렇다. 정한 결과는 그 PR 의 정정으로 이 문서에 적는다.

### 결정 8. 가변 축은 줄 표다. jsonb 와 배열 칸을 안 둔다

지출 항목 일곱이 `options` 를 든다. 주문서 타일 둘에서 고르는 축이 둘이라 단계 하나로 못 펴는 칸이고, 축
이름이 타일마다 다르다(무기 × 능력치 · 능력치 × 스탯). `spend_item_options` 표에 항목 · 축 · 값으로 줄을
세운다. `forms` 도 `spend_item_forms` 로 같다. 심볼 비용 배열은 `symbol_level_costs` 에 레벨마다 줄이다.
[[ADR-349]] 결정 1 이 배열 칸을 기각한 이유 그대로다. 두 칸의 열쇠가 어긋나도 DB 가 못 잡는다.

### 결정 9. 기간 칸은 KST 글자 그대로 text 다

결정석 가격 · 드롭 표 · 지출 항목 · 컨텐츠 줄이 `from` · `until` 을 든다. 값은 `YYYY-MM-DD` 또는
`YYYY-MM-DDTHH:mm` 이고 앱의 판정(`lib/boss/boss-profit-period` 의 `isEffectiveIn`)이 문자열 비교다.
서버도 text 로 들고 같은 글자를 내린다. timestamptz 로 바꾸면 경계 판정이 두 벌이 된다.

### 결정 10. 공유 카탈로그는 컨텐츠 표의 칸으로 접는다 (사용자 지정)

`scheduler-content-catalog.json` 의 공유 줄 여덟은 컨텐츠 key 로 템플릿 줄을 가리키는 덧칸이다. `contents`
표에 공유 범위 · 위젯 이름 · `onlyWhenScheduled` · `trustRegistrationFlag` · 누적 점수 · 최대 횟수 덮기를
칸으로 둔다. 갈래 단위 둘(`groupWeeklyLimits` · `sharedGroupOrder`)은 `content_categories` 표가 든다. 갈래
key 집합은 코드가 분기에 쓰므로 ENUM 이고, 표는 이름 · 태그 · 한도 · 차례만 든다. 파일은 없어진다.

### 결정 11. 정합성 검사는 서버 제약과 관리 화면의 쓰기 검사로 간다

`src/data/__tests__/data-consistency.spec.ts` 23건과 파일별 스펙이 지키던 규칙은 셋으로 나뉜다.

- 참조 무결성(가리키는 key 가 표에 있다)은 FK 와 UNIQUE 다.
- 줄 규칙(한 조합의 가격 줄이 겹침 없이 잇는다 · 경계가 그 보스의 기간 경계에 선다 · 기간 칸의 글자 모양)은
  관리 화면의 쓰기 끝점이 검사한다. 걸리면 400 이고 아무것도 안 바뀐다.
- 앱은 모양만 본다(`parseBossCatalog` 선례). 값의 규칙은 서버가 지킨 것을 믿는다.

표가 옮겨 갈 때 그 표의 스펙은 서버 리포지토리 스펙으로 옮기고 앱 쪽은 번들 사본의 모양 검사만 남긴다.

## 대가

- **서버 표가 스무 개쯤 는다.** 지금 아홉이다. 관리 화면 폼은 넷만 먼저 세우고 나머지는 씨앗으로 선다.
- **데이터가 두 벌이다.** 번들과 서버. 빌드 전 스크립트와 켤 때의 덮어쓰기가 둘을 맞춘다.
- **새 항목의 그림은 여전히 앱 빌드다**(결정 5).
- **`GET /v1/bosses` 와 `game-data` 의 `bosses` 칸이 한동안 둘이다.** 같은 리포지토리 함수를 부르므로 값은
  하나다.
- **설명 글이 파일을 떠난다.** 값의 출처와 경위를 알려면 이 문서와 `foundation/game-data.md` 를 열어야 한다.

## 기각

- **표마다 끝점을 둔다.** [[ADR-349]] 의 모양을 열셋으로 늘리면 켤 때 요청이 열셋이고 동기화 스크립트도 열셋이다.
- **응답 하나에 시각 하나.** 표 하나가 바뀌어도 전부를 다시 쓴다.
- **jsonb · 배열 칸.** 결정 8.
- **세트 표를 둔다.** 소비처가 고가 판정 하나라 칸 하나로 접힌다(결정 6).
- **서버가 그림을 호스팅한다.** 범위가 커서 뒤로 미룬다(결정 5).
- **관리 화면에 JSON 붙여넣기.** [[ADR-349]] 정정 1 이 걷었다. 첫 채움은 씨앗 CLI 다(결정 3).
- **씨앗이 있는 표를 덮어쓴다.** 폼으로 고친 값이 배포 때 되돌아간다.

## 열린 질문

- **`GET /v1/bosses` 를 걷는 시점.** 앱이 `game-data` 를 부르는 OTA 가 나가고 옛 OTA 를 쓰는 기기가 없어진
  뒤다.
- **그림의 서버 이전.** 사용자가 뒤에 할 계획이라 했다. 그때 결정 5 를 뒤집는다.
- **묶음마다 걷는 칸.** 결정 7 대로 PR 때 정한다.
- **관리 화면 폼을 넷 뒤에 어디까지 세울지.**

### 정정 3. 지출 카탈로그와 심볼 비용의 서버 표 여덟과 관리 화면 둘 (2026-10-17, 사용자 지정)

결정 2 의 4단계다. 설계는 사용자가 페이지로 보고 넷을 정했다. ① **심볼 비용은 결정석 가격처럼 기간 줄이다.** 강화
비용도 주기적으로 바뀐다. 표가 선 날 2026-09-17 은 첫 줄들의 `from` 이 되고 묶음에는 날짜 칸이 없다. ② **갈래
(`category`)는 묶음 칸이다.** 70개 항목 전부 묶음마다 갈래가 하나였다. ③ **형태(`forms`)는 ENUM 이다.** 이름
(경험치 · 솔 에르다)은 앱 `lib/cashbook/categories.ts` 에 남는다. ④ **단위(`unit`)는 글자다.** 관리 화면이 넷(회 ·
개 · 포인트 · 시간)을 고르개로 낸다.

```sql

CREATE TYPE spend_currency AS ENUM ('point', 'meso');
CREATE TYPE spend_form     AS ENUM ('exp', 'sol_erda');

spend_groups           지출 목록의 제목 한 줄. 12줄. 닫힌 것은 메이플 포인트 샵 하나

  active      boolean         NOT NULL DEFAULT true. 닫힌 묶음은 흐리게 서고 못 고른다. 날짜로 판정하지 않는다
  sort_order  integer         NOT NULL

spend_tiles            목록의 한 칸. 54줄. 같은 타일의 항목이 한 칸으로 접힌다
  id · key UNIQUE · name
  icon_file   text                     아이템 그림 파일명. 47개
  icon_map    text                     지역 아이콘 slug. 에픽던전 넷. 없는 셋은 둘 다 NULL
  CHECK (icon_file IS NULL OR icon_map IS NULL)

spend_items            기록이 가리키는 항목 한 줄. 70줄
  id            uuid            PK
  key           text            UNIQUE   기록의 item_key. 이름이 바뀌어도 그대로
  group_id      uuid            FK → spend_groups(id)
  tile_id       uuid            FK → spend_tiles(id)
  name          text            NOT NULL
  tier          text                     타일 안의 단계(1단계 · 공격력). 20개. 축 값을 든 항목은 NULL
  currency      spend_currency  NOT NULL
  unit_price    bigint                   NULL 은 경매장 값이라 적을 때 친다. 23개, 전부 메소
  unit          text            NOT NULL 회 · 개 · 포인트 · 시간. 수량 칸의 라벨
  max_quantity  integer                  기록 한 건의 수량 상한. 14개
  reward_coins  integer                  한 형태에서 받는 세라자르 주화 개수. 형태를 든 8개만
  from · until  text                     KST 글자(결정 9). 판정은 적는 날짜가 든 주간 기간의 첫날
  sort_order    integer         NOT NULL 묶음 안의 차례. 타일 차례는 첫 항목의 차례
  CHECK (unit_price IS NULL OR unit_price >= 0)

spend_item_options     축이 둘인 주문서 타일 둘의 항목 7개. 13줄
  id · item_id FK CASCADE · axis text(무기 · 능력치 · 스탯) · value text
  UNIQUE (item_id, axis)

spend_item_forms       에픽던전 추가 리워드 8개가 값을 받는 형태. 16줄
  id · item_id FK CASCADE · form spend_form
  UNIQUE (item_id, form)

symbol_groups          아케인 · 어센틱 · 그랜드 어센틱. 3줄

symbols                14줄

symbol_level_costs     비용 배열을 레벨마다 한 줄로 편다. 한 조합(심볼 · 레벨)에 기간 줄이 여럿. 첫 줄 194
  id · symbol_id FK CASCADE

game_rules         + spend_tariff_percent 10 · reward_coin_price_meso 40000000
```

- **응답.** 칸 둘이 는다. `spendCatalog { updatedAt, rules { tariffPercent, rewardCoinPriceMeso }, groups[{ key, name,
  category, active }], tiles[{ key, name, iconFile, iconMap }], items[{ key, group, tile, name, tier, currency, unitPrice,
  unit, maxQuantity, rewardCoins, from, until }], itemOptions[{ item, axis, value }], itemForms[{ item, form }] }` ·
  `symbolCosts { updatedAt, groups[{ key, name, maxLevel, defaultFrom, defaultTo }], symbols[{ key, group, name,
  requiredLevel, iconFile }], levelCosts[{ symbol, level, costMeso, from, until }] }`. 2단계처럼 줄 표 그대로 납작하다.
  배열은 `sort_order` 차례이고 응답에 `sort_order` 는 없다. 세라자르 주화의 이름 · 그림, 형태 · 갈래의 이름은 앱
  상수로 남는다. 규칙 둘은 보스 표의 규칙과 같은 `game_rules` 에 들지만 `bosses.updatedAt` 을 안 움직인다.
- **씨앗.** `spend-catalog.json` · `symbol-costs.json`. 모양은 응답의 그 칸이다. 지출은 표 셋(묶음 · 타일 · 항목)이 다
  비어 있을 때만 채우고 규칙 둘은 없을 때만 넣는다. 심볼은 묶음 표가 비어 있을 때만 채운다.
- **관리 화면 둘.** `/admin/spend-catalog`(맨 위 규칙 둘. 묶음 표와 열기 · 닫기 스위치. 묶음을 펴면 항목 줄과 새 항목
  폼이 서고 항목 편집기에 축 값과 형태가 있다. 타일 표. 지우기는 없다. 항목은 `until` 로 닫는다) ·
  `/admin/symbol-costs`(묶음마다 표 하나. 가로가 레벨, 세로가 심볼, 칸이 지금 비용. 심볼 줄을 펴면 레벨마다 새 비용
  칸과 시작일이 서고, 바뀐 칸만 새 줄로 열린다. 지금 줄은 닫힌다. 지난 줄은 못 거둔다. 새 심볼 · 새 묶음).
- **쓰기 검사(결정 11).** 묶음 · 타일 · 항목 · 심볼의 key 는 못 바꾼다. 항목은 `tier` 와 축 값 중 하나만 들고, 같은
  타일의 항목은 한 묶음에 들며 전부 `tier` 를 들거나 전부 축 값을 든다(축 이름이 같고 값 조합이 겹치지 않는다. 앱의
  `optionItemOf` 가 꼭 맞는 하나를 찾아야 해서다). 주화는 형태를 든 항목만 든다. 심볼의 비용은 넣고 나서 지금 서는
  줄이 1 부터 `max_level−1` 까지 빠짐없이 있어야 하고(새 심볼은 한 번에 넣는다), 새 시작은 지금 줄의 시작보다 뒤다.
  그 레벨의 유일한 줄은 못 거둔다. 묶음의 `max_level` 은 그 위에 비용 줄이 있으면 못 내린다. 올리면 빈 레벨이
  생기고 화면이 그것을 보인다. 나머지는 FK · UNIQUE · CHECK 다.
- **걷은 칸(결정 7).** 사용자가 후보 전부를 걷었다. `currencies` · `categories` · 항목의 `category`(묶음이 든다) ·
  `limit` 6줄(화면이 안 쓰고 `maxQuantity` 숫자의 출처였다) · `note` 2줄 · `seasonal` 5줄(코드가 안 읽는다) ·
  `marketRateUnit`(읽는 곳이 없다) · `rewardCoin.name` · `icon`(앱 상수) · 파일의 `updatedAt` · `source` · `note` ·
  `tariffNote` · `marketRateNote`.
- 맥락 표의 심볼 비용 180 은 센 값이 틀렸다. 6 × 19 + 8 × 10 = 194 다. 표를 같은 날 고쳤다.

앱 쪽은 한 번에 바꾼다(사용자 지정). `spend-catalog.json` · `symbol-costs.json` 을 응답 모양으로, `lib/cashbook/spend-catalog`
· `symbol-costs` 가 현재 표를 읽게, `features/game-data/hydrate` 에 칸 둘을 더한다. 심볼 비용은 기록 날짜로 기간 줄을
고른다. 날짜 고르개의 바닥은 비용 줄 중 가장 이른 `from` 이다.

### 정정 4. 컨텐츠 표 둘에 공유 카탈로그를 접는다 (2026-10-17, 사용자 지정)

결정 2 의 5단계이고 결정 10 의 구현이다. 설계는 사용자가 페이지로 보고 둘을 정했다(권장안 그대로). ① **갈래의 이름 ·
태그 · 관리 화면 주간 목록 차례를 표로 옮긴다.** 앱 상수 `CONTENT_CATEGORIES` 의 글자와 `WEEKLY_CATEGORY_ORDER` 가
`content_categories` 의 칸이 된다. 코드에는 key 집합만 ENUM 으로 남는다. 카드 모양 · 길드 판정 · 계열 한도가 key 로
갈리기 때문이다. ② **수동 모드 기본값 넷 중 `now_count` · `quest_state` 를 걷는다.** 41줄 전부 `now_count` 가 0 이고
`quest_state` 는 `type` 이 정한다(quest 는 `'0'`, contents 는 `null`). 표는 `type` · `max_count` 만 들고 앱 조회 모듈이
둘을 만들어 낸다.

```sql
CREATE TYPE content_category AS ENUM ('monster_park', 'daily_quest', 'epic_dungeon', 'maple_union',
                                      'arcane_river_quest', 'weekly_quest', 'mu_lung_dojo', 'guild');
CREATE TYPE content_section  AS ENUM ('daily', 'weekly');
CREATE TYPE content_type     AS ENUM ('contents', 'quest');
CREATE TYPE share_scope      AS ENUM ('character', 'world', 'account');

content_categories     갈래. 8줄. ENUM 과 일대일이라 더하기 · 지우기는 마이그레이션이다
  id              uuid              PK
  key             content_category  UNIQUE
  name            text              NOT NULL 카드 라벨 · today 공유 위젯 머리글
  count_tag       text                       갈래의 참고 태그. 에픽 던전 'ID당 1회'
  hide_count_tag  boolean           NOT NULL DEFAULT false. 아케인리버 지역 퀘스트만 true
  weekly_limit    integer                    갈래의 주간 진행 한도. 에픽 던전 3
  shared_order    integer                    today 공유 위젯의 계열 차례. 몬스터파크 0 · 메이플 유니온 1 · 에픽 던전 2. NULL 은 뒤에
  sort_order      integer           NOT NULL 관리 화면 주간 목록의 갈래 차례
  CHECK (count_tag IS NULL OR NOT hide_count_tag) · CHECK (weekly_limit IS NULL OR weekly_limit >= 1)

contents               컨텐츠 한 줄. 41줄. 캐시 · 추적 목록 · 공유 원장이 key 를 든다. 지우지 않고 until 로 닫는다
  id                        uuid             PK
  key                       text             UNIQUE   앱의 컨텐츠 key
  section                   content_section  NOT NULL 일간 18 · 주간 23
  api_name                  text             UNIQUE   넥슨 응답의 content_name
  category_id               uuid             FK → content_categories(id)
  display_name · short_name text             NOT NULL 카드 · 관리 화면 이름, 좁은 자리 이름
  background_map · background_portrait text  지도 slug 32 · 보스 초상 slug 4. 길드 셋 · 유니온 둘은 둘 다 NULL
  count_tag                 text                      컨텐츠가 참고 태그를 덮는 글자. 둘
  type                      content_type     NOT NULL
  max_count                 integer          NOT NULL 수동 모드 기본 상한. 14 · 100 · 5 · 1 · 10 · 0
  required_level            integer                   표시용. 36줄
  from · until              text                      KST 글자(결정 9). 아우룸 레기스만 from 2026-09-17
  share_scope               share_scope      NOT NULL DEFAULT 'character'. 캐릭터 33 · 월드 3 · 계정 5
  shared_short_name         text                      today 공유 위젯의 글자('일간' · '앵글러컴퍼니'). 공유 줄 8개만
  only_when_scheduled       boolean          NOT NULL DEFAULT false. 메이플 유니온 둘만 true
  trust_registration_flag   boolean          NOT NULL DEFAULT false. 메이플 유니온 둘만 true
  cumulative_score          boolean          NOT NULL DEFAULT false. 길드 지하 수로
  max_count_override        integer                   API 오류 덮기. 길드 주간 미션 포인트 10
  sort_order                integer          NOT NULL 섹션 안의 차례
  CHECK (background_map IS NULL OR background_portrait IS NULL)
  CHECK ((share_scope = 'character') = (shared_short_name IS NULL))
  CHECK (share_scope <> 'character' OR (NOT only_when_scheduled AND NOT trust_registration_flag))
  CHECK (max_count >= 0) · CHECK (required_level >= 1) · CHECK (max_count_override >= 1)
```

- **응답.** 칸 하나가 는다. `contents { updatedAt, categories[{ key, name, countTag, hideCountTag, weeklyLimit,
  sharedOrder }], contents[{ key, section, apiName, category, displayName, shortName, backgroundMap, backgroundPortrait,
  countTag, type, maxCount, requiredLevel, from, until, shareScope, sharedShortName, onlyWhenScheduled,
  trustRegistrationFlag, cumulativeScore, maxCountOverride }] }`. 배열은 `sort_order` 차례이고(컨텐츠는 일간 뒤 주간)
  응답에 `sort_order` 는 없다.
- **씨앗.** `contents.json` 하나. 모양은 응답의 그 칸이다. 갈래 표가 비어 있을 때만 둘을 함께 채운다. 씨앗의 갈래 줄은
  ENUM 여덟을 빠짐없이 들어야 한다.
- **관리 화면 하나.** `/admin/contents`. 맨 위에 갈래 표 8줄(이름 · 태그 · 숨김 · 주간 한도 · 공유 차례 · ↑↓. 새 갈래는
  없다). 그 아래 일간 · 주간 표 둘. 줄의 수정을 누르면 그 아래로 편집기가 펼쳐지고, 새 컨텐츠는 같은 편집기가 표 맨
  아래에 열려 섹션 맨 끝에 선다. 지우기는 없다. `until` 로 닫는다.
- **쓰기 검사(결정 11).** 컨텐츠 key · 섹션 · 갈래 key 는 못 바꾼다. API 이름은 NFC 로 맞추고 공백을 지운 뒤에도
  유일해야 한다. 앱이 그 모양으로 key 를 얻어서다. UNIQUE 는 원문에 걸고 정규화 유일성은 쓰기 끝점이 본다. 공유 줄은
  위젯 글자를 들고, 캐릭터 줄은 위젯 글자 · `only_when_scheduled` · `trust_registration_flag` 를 못 든다. 그림은 지도와
  초상 중 하나이고 갈래 태그는 글자와 숨김 중 하나다. 기간은 `from` 이 앞이다. 나머지는 FK · UNIQUE · CHECK 다.
- **걷은 칸(결정 7).** 사용자가 후보 전부를 걷었다. `registration_flag` 41줄(전부 `'false'`) · `now_count` 41줄(전부 0) ·
  `quest_state` 41줄(`type` 이 정한다) · 카탈로그 공유 줄의 `section` 8(컨텐츠의 section 과 전부 같다) · 설명 칸 9개
  (`note` · `matchingNote` · `cumulativeScoresNote` · `groupNote` · `maxCountOverrideNote` · `groupWeeklyLimitsNote` ·
  `fromNote` · `trustRegistrationFlagNote` · `onlyWhenScheduledNote`. 사고의 경위와 근거는 그 글이 인용하는 [[ADR-030]] ·
  [[ADR-086]] · [[ADR-147]] · [[ADR-261]] · [[ADR-270]] · [[ADR-271]] · [[ADR-280]] 과 `foundation/game-data.md` 에
  이미 있다) · 파일의 `updatedAt` · `source` · `note`.
- 설계 때 확인한 사실 셋. 공유 줄의 `section` 은 템플릿과 전부 같다. API 이름은 정규화 뒤에도 41개가 유일하다. 그림이
  없는 다섯 줄과 요구 레벨이 없는 다섯 줄이 같다(길드 셋 · 메이플 유니온 둘).

앱 쪽은 한 번에 바꾼다(사용자 지정). 파일 둘(`scheduler-content-template.json` · `scheduler-content-catalog.json`)이
응답 모양의 `contents.json` 하나가 되고, `lib/scheduler/contents` · `scheduler-content-scope` · `content-categories` 가
현재 표를 읽는다. `CONTENT_CATEGORIES` 는 key 집합만 남는다. 조회 모듈이 줄에서 `content_name` · `registration_flag:
'false'` · `now_count: 0` · `quest_state` 를 만들어 `ContentEntry` 를 낸다. `features/game-data/hydrate` 에 칸 하나를
더한다.

### 정정 5. 장비 · 강화 비용 · MVP 등급의 서버 표 다섯과 규칙 셋, 관리 화면 셋 (2026-10-17, 사용자 지정)

결정 2 의 6단계다. 설계는 사용자가 페이지로 보고 셋을 정했다. ① **MVP 등급 key 는 ENUM 이고 줄은 일곱과 일대일이다.**
앱이 `normal` 로 분기하고 `MvpGradeKey` 가 코드의 합집합이라 갈래(정정 4 ①)와 같은 자리다. 새 등급은 마이그레이션이다.
② **잠재 종류 · 등급은 영문 ENUM 이고 API 의 한글 글자('잠재능력 재설정' · '레어')는 앱 상수가 맞춘다.** 정정 3 ③ 의 형태와
같은 규칙이다. 넥슨이 표기를 바꿔도 표는 그대로다. ③ **비용 표 셋은 기간 줄 없이 지금 값 하나다.** 강화 기록은 서버에
두지 않고 앱이 날짜 · 캐릭터 · 갈래 · 장비별 합계로 저장하므로(이슈 #614, 착수 전) 서버 표에 지난 값이 설 자리가 없다.
고친 값은 앱이 다음에 수집하는 기록부터 쓰고 이미 저장한 합계는 안 바뀐다. 지난 기간을 다시 매기는 일은 #615 의 재계산
요청이고 그때도 지금 값으로 매긴다. 결정석 가격 · 심볼 비용이 기간 줄인 것은 앱이 그 값을 저장하지 않고 날짜로 찾기
때문이다. 강화 비용은 #614 뒤에 그 자리가 아니다.

```sql
CREATE TYPE potential_reset_type AS ENUM ('potential', 'additional');
CREATE TYPE potential_grade      AS ENUM ('rare', 'epic', 'unique', 'legendary');
CREATE TYPE mvp_grade            AS ENUM ('normal', 'bronze', 'silver', 'gold', 'diamond', 'red', 'black');

equipment_items        강화 비용을 매길 장비. 467줄. 기록(enhancement_history.item_key)이 key 를 들어 지우지 않는다
  id     uuid    PK
  key    text    UNIQUE   드롭 아이템 표와 같은 장비 17개는 key 가 같다
  name   text    UNIQUE   붙여 쓴 이름. 앱이 API target_item 을 NFC · 공백 제거 뒤 완전 일치로 key 를 얻는다
  level  integer          착용 레벨. NULL 은 모른다는 뜻이고 0 이 아니다. 그 장비의 스타포스는 안 매기고 건수만 센다
  CHECK (level IS NULL OR level >= 1)

potential_reset_costs  잠재 재설정 1회 비용. 종류 2 × 레벨 구간 4 × 등급 4 = 32줄. 비용은 누르기 전 등급으로 매긴다(ADR-300)
  id · type potential_reset_type · min_level integer(구간의 시작. 1 · 160 · 200 · 250. 장비 레벨 이하인 줄 중 가장 큰 것)
  grade potential_grade(노멀은 재설정할 수 없어 없다) · cost_meso bigint
  UNIQUE (type, min_level, grade) · CHECK (min_level >= 1) · CHECK (cost_meso >= 0)

soul_potential_reset_costs  소울 잠재 재설정 1회 비용. 등급 하나로 정해지고 장비 레벨을 안 본다. 4줄
  id · grade potential_grade UNIQUE · cost_meso bigint · CHECK (cost_meso >= 0)

starforce_steps        스타포스 한 단계의 식 재료. 30줄. 식 자체(1000 + L³ · (S+1)^e / d, 십의 자리 반올림)는 코드가 든다
  id · from_star integer UNIQUE(시도 전 성수 0~29) · exponent double precision(1 · 2.7) · divisor integer(36~571)
  CHECK (from_star >= 0) · CHECK (divisor >= 1)

mvp_grades             7줄. 차례가 높낮이다. 소속을 모르는 스타포스 줄이 그 날 가장 높은 등급을 찾을 때 쓴다
  id · key mvp_grade UNIQUE · name text · auction_fee_percent integer · starforce_discount_percent integer · sort_order integer
  CHECK (auction_fee_percent BETWEEN 0 AND 100) · CHECK (starforce_discount_percent BETWEEN 0 AND 100)

game_rules         + cube_appraisal_free_max_level 120 · cube_appraisal_coefficient 20 · starforce_destroy_defence_surcharge_percent 200
```

- **응답.** 칸 셋이 늘어 열둘이다. `equipmentItems { updatedAt, items[{ key, name, level }] }` · `enhancementCosts { updatedAt,
  rules { cubeAppraisalFreeMaxLevel, cubeAppraisalCoefficient, starforceDestroyDefenceSurchargePercent }, potentialResetCosts[{ type,
  minLevel, grade, costMeso }], soulPotentialResetCosts[{ grade, costMeso }], starforceSteps[{ fromStar, exponent, divisor }] }` ·
  `mvpGrades { updatedAt, grades[{ key, name, auctionFeePercent, starforceDiscountPercent }] }`. 장비는 key 차례, 등급은
  `sort_order` 차례이고 응답에 `sort_order` 는 없다. 규칙 셋은 `game_rules` 에 들지만 `bosses` · `spendCatalog` 의 `updatedAt`
  을 안 움직인다. 장비 467줄이 응답을 30KB 남짓 늘린다.
- **씨앗.** `equipment-items.json` · `enhancement-costs.json` · `mvp-grades.json`. 모양은 응답의 그 칸이다. 장비와 등급은 표가
  비어 있을 때만, 강화 비용은 표 셋이 다 비어 있을 때만 채우고 규칙 셋은 없을 때만 넣는다.
- **관리 화면 셋.** `/admin/equipment-items`(거르기 칸 · 새 장비 폼 · 표 467줄. 줄의 수정을 누르면 이름 · 레벨이 입력으로
  바뀐다. 지우기는 없다) · `/admin/enhancement-costs`(맨 위 규칙 셋. 잠재 재설정 표 둘은 종류마다 가로가 등급 넷, 세로가
  레벨 구간이고 칸을 제자리에서 고친다. 새 구간은 등급 넷을 한 번에 더하고 구간째 지운다. 소울 표 한 줄. 스타포스 단계
  표는 성수마다 지수 · 제수를 고치고 끝 성수만 더하고 지운다) · `/admin/mvp-grades`(7줄의 이름 · 퍼센트 둘 수정과 ↑↓. 새
  등급은 없다).
- **쓰기 검사(결정 11).** 장비 key 는 못 바꾸고 장비는 지우지 않는다. 이름은 NFC 로 맞추고 공백을 지운 뒤에도 유일해야
  한다. 드롭 아이템 표에 같은 이름이 있으면 key 가 같아야 한다. 앱 `equipment-items.spec.ts` 가 지키던 규칙이 서버로 온다.
  장비 레벨은 비우거나 1 이상이다. 잠재 재설정은 종류마다 `min_level 1` 구간이 있어야 어느 레벨이든 한 줄에 걸리므로 그
  구간은 못 지운다. 스타포스 단계는 0 부터 빠짐없이 있어야 하므로 끝 성수만 더하고 지운다. 퍼센트 둘은 0~100 이다. 나머지는
  UNIQUE · CHECK 다.
- **걷은 칸(결정 7).** 사용자가 후보 전부를 걷었다. 장비의 `group` 467줄(값 셋. 읽는 코드가 없다) · `cubeAppraisal.formula` ·
  `starforce.formula` · `rounding`(식과 반올림은 `lib/enhancement/cost.ts` 가 든다. 계수 20 만 규칙이다) · `discount.order` ·
  `discount.field` · `destroyDefence.field`(적용 순서와 응답 칸 이름이라 코드다) · `soulPotentialReset.from`(소울 잠재가 생긴
  패치 날짜 2026-09-17. 바뀌지 않는 사실이고 그 전 날짜의 소울 내역을 안 부르는 것은 앱의 일이라 앱 상수 `SOUL_POTENTIAL_FROM`
  으로 남는다) · 설명 칸(`note` 6 · `updatedAt` · `source`. 누르기 전 등급 · 강화권 무료 · 복구비용 안 셈 · 세트를 key 접두사로
  판정하지 말 것 같은 규칙은 [[ADR-223]] · [[ADR-280]] 결정 14 · [[ADR-300]] · [[ADR-306]] 결정 1 과 `foundation/game-data.md` 에
  이미 있다).
- 맥락 표의 "표 셋 42줄" 은 잠재 재설정을 넓은 줄 8 로 센 것이다. 등급을 줄로 펴면 32 라 비용 줄 합은 66 이다.
- 설계 때 확인한 사실. 장비 467줄은 key · 이름이 전부 유일하고 이름에 공백이 없으며 레벨이 전부 있다(10~250). 드롭
  아이템 표와 같은 이름 17개는 key 가 전부 같다. 강화 지출은 지금 읽을 때 매기지만(`features/enhancement-history/spending.ts`)
  #614 가 수집할 때 매겨 합계로 저장하게 바꾼다.

앱 쪽은 한 번에 바꾼다(사용자 지정). 파일 셋이 응답 모양의 `equipment-items.json` · `enhancement-costs.json` · `mvp-grades.json`
이 되고, `lib/enhancement/cost.ts` 는 식을 두고 재료만 현재 표에서 읽는다. API 글자 → key 표(`잠재능력 재설정` → `potential` ·
`에디셔널 잠재능력 재설정` → `additional` · `레어` → `rare` …)와 `SOUL_POTENTIAL_FROM` 은 앱 상수다. `lib/mvp/grades.ts` ·
`lib/equipment/equipment-items.ts` 가 현재 표를 읽고 `features/game-data/hydrate` 에 칸 셋을 더한다.
