### ADR-028: Android 네이티브 스플래시 최소화 — 무채색 즉시 해제 + JS(HTML) 풀 브랜드 스플래시로 대체 (설계 후 폐기, 구현 없음)

**배경**: [[ADR-025]]가 MIUI/HyperOS의 다크모드 force-dark 대응으로 `values-night` 색 split(`#D06100`)을 도입했지만, 실기기 hue 스윕 검증([[project_miui_forcedark_splash]] 메모리, 2026-07-16) 결과 **이 색이 이미 도달 가능한 최댓값**임이 확인됐다 — hue를 어느 방향으로 돌려도 더 밝은 안전값은 나오지 않는다. 그런데도 `MIN_SPLASH_MS=1000`(`App.tsx`) 때문에 이 색이 다크모드에서 **최소 1초간 그대로 보여**, 사용자가 "칙칙하고 너무 어둡다"고 느끼는 근본 원인이 됐다. force-dark는 **네이티브 테마 색에만 걸리고 WebView가 그리는 내용은 건드리지 않는다**(같은 메모리에서 확인 — `capacitor.config`의 WebView 배경 `#FB8101`은 다크모드에서도 그대로 렌더링됨)는 점에 착안해, Android에 한해 색 문제 자체를 우회하는 구조를 검토한다.

**결정** (Android만 해당, iOS는 [[ADR-025]] 그대로 유지 — iOS 런치 스토리보드는 force-dark 문제가 없음):

1. **네이티브 스플래시(Android 12+ SplashScreen API)에서 브랜드 아이덴티티를 뺀다.** `windowSplashScreenBackground`를 커스텀 브랜드 색(`@color/splash_background`) 대신 **테마 기본 배경색**(예: 시스템 `?attr/colorBackground` 또는 라이트/다크 각각의 무채색 안전값)으로 되돌리고, `windowSplashScreenAnimatedIcon`(아이콘+워드마크 락업)도 제거한다. force-dark가 다크모드에서 이 배경을 건드리더라도, 애초에 "브랜드 색"이 아니므로 깎여도 이상해 보이지 않는다(무채색 → 좀 더 어두운 무채색).

2. **네이티브 스플래시 유지 시간을 JS 타이머(`MIN_SPLASH_MS`)로 강제로 붙잡지 않는다.** 현재 `MainActivity.onCreate`의 `setKeepOnScreenCondition`이 `App.tsx`의 `hideSplashScreen()` 호출(1초 후)까지 붙잡아두는 구조를 Android에서만 제거하고, OS 기본 동작(Activity 첫 프레임이 그려지면 자동 해제)에 맡긴다. 즉 Android 네이티브 스플래시는 "무채색 + 아이콘 없음 + 최대한 짧게"로 축소.

3. **브랜드 룩(로고+워드마크+주황 배경)은 `index.html`에 정적으로 박아넣는 HTML/CSS 레이어가 담당한다.** React 번들 로드·파싱을 기다리지 않고 그려지도록 인라인 CSS(외부 리소스 fetch 없이)로 구성하고, 앱 콘텐츠가 준비되면(`App.tsx`의 기존 "콘텐츠 준비" 시점) JS가 이 레이어를 제거(또는 fade-out)한다. `MIN_SPLASH_MS`로 보장하던 "최소 노출 시간"은 이 HTML 레이어 쪽으로 옮겨온다(네이티브가 아니라 이 레이어가 최소 시간을 보장).

**이유 / [[ADR-025]] 결정 2에서 폐기했던 대안과 다른 점**:
- [[ADR-025]]는 네이티브 스플래시 위에 HTML 부트 스플래시를 **얹어 유지**하려다 "네이티브 로고와 HTML 로고가 동시에 보이는 이중 스플래시" 문제로 폐기했다. 이번 안은 **네이티브 쪽에 애초에 로고를 두지 않으므로** 겹칠 대상이 없어 그 결함이 구조적으로 사라진다.
- 색을 더 안전하게 튀닝하는 시도(hue 스윕)는 이미 실기기로 막다른 길임을 확인했으므로([[project_miui_forcedark_splash]]), "색 자체를 안 쓴다"가 유일하게 남은 근본 해결 방향이라고 판단했다.

**트레이드오프 / 리스크**:
- **백지 화면 리스크**: 네이티브 스플래시를 OS 기본 타이밍(첫 프레임에 자동 해제)에 맡기면, WebView 초기화가 느린 저사양 기기에서 "네이티브 해제 → HTML 스플래시 첫 페인트" 사이에 짧은 백지(흰 화면) 프레임이 생길 가능성이 있다. HTML 스플래시를 완전히 인라인·동기적으로 구성해 최소화할 계획이나, **실기기 검증 전까지는 가설**이다.
- Android와 iOS의 스플래시 구현 방식이 더 벌어진다(Android: 무채색 네이티브+HTML 브랜드 / iOS: 브랜드 네이티브 그대로) — 이미 [[ADR-025]]에서도 플랫폼별 유지 방식이 갈려 있었으므로 관리 부담이 크게 늘지는 않으나, 두 플랫폼의 "스플래시가 뭘 보여주는가"에 대한 개념 모델이 달라진다.
- `MIN_SPLASH_MS`의 의미가 Android에서는 "네이티브 유지 시간"에서 "HTML 레이어 유지 시간"으로 바뀐다 — 코드 위치·타이밍 로직 변경이 필요하다.

**검증 계획**: 실기기(Xiaomi HyperOS)에서 (a) 다크모드 무채색 네이티브 배경이 실제로 어색하지 않게 보이는지, (b) 네이티브 해제~HTML 첫 페인트 사이 백지 프레임이 실제로 발생하는지(콜드스타트 다회 반복), (c) 기존 라이트모드·iOS 경험이 그대로 유지되는지를 스크린샷/화면 녹화로 확인한다.

**검증 결과 (2026-07-16, 실기기 화면 녹화 — 결정 2 실패, 재설계 필요)**: `adb shell screenrecord`로 콜드스타트를 녹화해 112프레임(전체 구간)을 픽셀 단위로 스캔한 결과, **주황 브랜드 색이 단 한 프레임도 나타나지 않았다.** 실제로 관찰된 것:
- 0~3.2초: 무채색 회색(`(28,27,32)`, 결정 1의 테마 기본 배경)이 그대로 유지됨 — 네이티브 스플래시가 즉시 해제되지 않는다.
- 3.2~3.5초: 그 회색이 앱의 라이트 테마 배경(`(242,239,226)`)으로 직접 크로스페이드.
- 그 사이 어디에도 `#boot-splash`(HTML, 주황)가 노출되지 않는다 — WebView/React 마운트가 여전히 네이티브 스플래시 뒤에 완전히 가려진 채 끝난다.

**원인**: 결정 2("OS 기본 동작에 맡긴다")의 전제가 틀렸다. AndroidX core-splashscreen의 기본 `keepOnScreenCondition`은 "첫 프레임이 빨리 그려지면 바로 해제"가 아니라, 이 앱의 콜드스타트 전체(브릿지 초기화 + 8개 Capacitor 플러그인 등록 + WebView 부착)가 끝날 때까지(실측 ~3초, `ActivityTaskManager: Displayed +3s1ms`) 계속 유지한다. 그동안 HTML 레이어는 그 뒤에서 이미 마운트→`hideBootSplash()`까지 끝나버려, 사용자에게 노출될 기회 자체가 없다. 결과적으로 **이전(고정 1초, 브랜드 색 노출)보다 더 나쁜 회귀** — 노출 시간은 3배 이상 늘고 브랜드 노출은 0이 됐다.

**다음 단계(미구현)**: 결정 2를 다시 커스텀 `setKeepOnScreenCondition`으로 되돌리되, 고정 타이머가 아니라 **JS→네이티브 신호**(예: WebView가 `#boot-splash`를 페인트한 시점에 작은 브릿지 호출로 네이티브의 플래그를 켬)로 유지 조건을 걸어, "네이티브 스플래시는 HTML 레이어가 실제로 그려질 때까지만" 유지하는 방식을 검토해야 한다. 결정 1(무채색+아이콘 없음)은 실기기 확인상 문제없이 동작했다(회색 배경 자체는 자연스러움).

**2차 시도 및 최종 결론 (2026-07-16, JS→네이티브 신호 방식도 실패 — ADR-028 전체 폐기)**: 위 "다음 단계"를 그대로 구현했다 — `BootSplashPlugin`(Capacitor 커스텀 플러그인, `ready()` 메서드로 `AtomicBoolean` 플래그를 켬) + `index.html`의 인라인 스크립트(rAF 2회로 페인트 완료를 기다린 뒤 `BootSplash.ready()` 호출) + `MainActivity`의 `setKeepOnScreenCondition`이 그 플래그를 참조(상한 5초). logcat으로 신호 자체는 정상 동작함을 확인(`ready() called from JS`가 정확히 찍힘). 그런데도 실기기 화면 녹화(113프레임) 재검증 결과 **여전히 주황이 단 한 프레임도 나타나지 않았다** — 이전 시도와 거의 동일한 타임라인(무채색 회색 유지 → 앱 콘텐츠로 직접 크로스페이드).

**진짜 원인**: logcat 타임스탬프를 대조한 결과, 병목은 스플래시 유지/해제 로직이 아니라 **콜드스타트 자체**였다. `ready()` 신호는 스플래시 창이 뜨고 약 1.8초 뒤에야 발화했다(Capacitor 브릿지 초기화 + 8개 플러그인 등록 + WebView 로딩이 그만큼 걸림 — 이 앱 JS 코드가 실행되기도 전 구간). 신호 이후에도 실제 창이 그려지기까지 다시 ~1.2초가 더 걸렸다(`ActivityTaskManager: Displayed +3s127ms`). 즉 **HTML 레이어(`#boot-splash`)가 그려질 수 있는 시점 자체가 이미 콜드스타트 후반부라, 그 전까지는 무엇을 네이티브에 그려두든 사용자는 "아직 브랜드가 아닌 무언가"를 볼 수밖에 없다.** 네이티브 스플래시 해제 조건을 아무리 정교하게 바꿔도 이 전제(HTML 레이어가 뜨기 전 구간)를 앞당길 수 없다.

**결론**: ADR-028의 핵심 아이디어("브랜드를 네이티브에서 빼서 force-dark가 못 건드리는 JS 레이어로 옮긴다")는 구조적으로 성립하지 않는다 — 그 JS 레이어가 화면에 드러나는 시점 자체가 콜드스타트 후반부이므로, 결국 콜드스타트 내내 사용자가 보는 건 네이티브 레이어뿐이다. 따라서 **네이티브 스플래시에 브랜드(색+아이콘)를 그대로 두는 [[ADR-025]] 원래 구현이 더 낫다** — 다크모드에서 살짝 어두운 주황(`#D06100`)이 보이더라도, 콜드스타트 내내 브랜드가 전혀 안 보이는 것보다 낫다. ADR-028의 모든 변경(styles.xml 무채색화, `BootSplashPlugin`, `index.html` `#boot-splash`, `MainActivity` 신호 대기)은 되돌렸고 저장소는 [[ADR-025]] 상태로 복원됐다(빌드·706개 테스트·실기기 재설치 확인 완료). **이 방향은 더 이상 시도하지 않는다** — 색은 이미 실측 최댓값(`#D06100`), 노출 시간 단축은 콜드스타트 구조상 불가능함을 두 번의 실기기 검증으로 확인했다.

**추가 발견 (2026-07-16, "3초 무브랜드"는 테스트 아티팩트였음)**: 이 문서의 모든 실기기 측정은 `adb install -r` 직후 `am force-stop` 후 곧바로 재실행하는 방식이었다(ART가 전혀 컴파일 안 된 최악의 콜드스타트). 실사용 패턴(앱이 이미 실행된 적 있는 상태에서 OS가 백그라운드 프로세스를 회수 — `am kill`로 재현 — 후 재실행)으로 다시 화면 녹화해보니 **전혀 다른 결과**가 나왔다: 검정 전환(~1.3초) 이후 주황 네이티브 스플래시(`(206,97,0)` ≈ `#D06100`)가 약 1초 가까이 안정적으로 보이고, 이후 매끄럽게 앱 콘텐츠로 크로스페이드됐다. 즉 [[ADR-025]]의 원래 설계(1초 고정 유지)는 실사용 조건에서 노출 시간 자체는 문제없이 작동한다.

**다만 이 시점에 사용자가 정정**: "타이밍이 실사용에서 괜찮다"는 애초 문제(다크모드에서 색이 어두워 보인다는 것) 자체를 해소한 게 아니다 — `#D06100`은 여전히 `#FB8101`이 아니다. "손볼 게 없다"는 결론은 잘못된 결론이었고, [[ADR-029]]에서 실제 해결책을 찾았다.
