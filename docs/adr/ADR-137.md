### 원인 — «파일만 올려 두면 끝» 이 **매니페스트에는** 안 통한다

[[ADR-022]] 가 Cloudflare R2 를 버리고 GitHub Releases 를 고른 근거는 *"카드 등록 없이, `gh auth
login` 만으로"* 였다. 그 구성이 성립한 이유는 @capgo 의 매니페스트가 **우리가 형식을 정한 평범한
JSON 파일**이었기 때문이다. 정적 파일 하나면 됐다.

`expo-updates` 는 그렇지 않다. `expo-updates@57.0.13`(SDK 57 대응판) 소스를 직접 읽어 확인한 것 둘:

| | 사실 | 근거 |
|---|---|---|
| 응답이 `multipart/mixed` **여야 하는가** | **아니다.** 본문이 그냥 JSON 이면 통째로 매니페스트로 읽는다 | `FileDownloader.kt:471` — `contentType()?.type == "multipart"` 가 아니면 `response.body` 전체를 매니페스트 본문으로 |
| 응답 헤더 `expo-protocol-version` 이 **없어도 되는가** | **안 된다. 그 자리에서 던진다** | `UpdateFactory.kt:18` `null -> throw Exception("Legacy manifests are no longer supported")` · iOS 도 같은 가드(`Update.swift:155` `guard let protocolVersion … else { throw .legacyManifestInstantiationInvalid }`) |

즉 **막는 것은 본문 형식이 아니라 헤더 한 줄**이다. 그리고 GitHub Releases 자산 다운로드도 GitHub
Pages(`mapleroutine.store`)도 커스텀 응답 헤더를 못 붙인다. 우회로를 찾아봤지만 없다 — 설정으로 끄는
길도 없다(`UpdatesConfiguration.kt` 의 키 전수 확인. `enableExpoUpdatesProtocolV0CompatibilityMode`
는 Expo Go 전용이고 그것도 `protocolVersion` 이 **null 이 아님**을 전제한다).

**«자체 호스팅을 못 한다» 가 아니라 «정적 파일만으로는 못 한다» 이다.** `expo-updates` 는 오히려
자체 서버를 1급으로 설계했다 — 라이브러리 자신의 설계 문서가 그렇게 적어 두었다:

> expo-updates should be written for a **general server implementation** … It happens to work with
> EAS Update, but **other services should not be second class citizens.**
> — `expo-updates/guides/general.md`

### 1. 두 층으로 가른다 — **매니페스트는 우리 Worker, 번들·에셋은 GitHub Releases**

프로토콜이 요구하는 것은 **매니페스트 응답의 헤더**뿐이다. `launchAsset.url` 과 `assets[].url` 은
**아무 URL 이나 된다** — 클라이언트는 그 주소를 그냥 GET 한다.

```
  앱 ──(1) GET  updates.mapleroutine…  ──▶ Cloudflare Worker
                                             │  (2) GH Release 의 정적 JSON 을 읽어
                                             ◀──┘      expo-protocol-version 을 얹어 되돌려준다
  앱 ──(3) GET  github.com/…/releases/download/<태그>/<해시>  ──▶ GitHub  (Worker 를 안 거친다)
```

**대역폭이 Worker 를 안 지나간다는 것이 이 배치의 요점이다.** Worker 가 내보내는 것은 수 KB 짜리
JSON 한 장이고, 15 MB 짜리 번들·에셋은 지금과 똑같이 GitHub 이 받는다. 사용자가 늘어도 Worker 쪽에서
늘어나는 것은 요청 수뿐이고, 무료 한도 10만 req/일은 *"사용자 1만 명이 하루 10번 앱을 켠다"* 에
해당한다. **[[ADR-022]] 가 지킨 것(카드 없음 · 우리 저장소에 쌓임 · `gh release upload` 로 배포)이
그대로 유지된다.**

기각안:

- **EAS Update** — `eas update` 한 줄로 끝나고 인프라가 0이다. 그러나 매니페스트·에셋·채널·롤백이
  전부 남의 서비스 안으로 들어가고, [[ADR-022]] 가 *"자체 호스팅"* 을 고른 이유(무료 한도를 넘는
  순간의 과금 · 서비스 종료 위험 · 데이터 소유)가 3년 지나 그대로 유효하다. 여기서 얻는 것은
  «Worker 를 한 번 올리는 수고» 뿐인데 그 값이 너무 싸다.
- **집 서버 · 라즈베리파이** — 가장 «자체» 이지만, **OTA 엔드포인트가 집 전원과 공유기에 묶인다.**
  OTA 는 앱을 고치는 마지막 수단이라 그 의존은 방향이 거꾸로다 — 앱을 못 고치는 사태가 정전으로
  생긴다.
- **GitHub Pages 로 매니페스트 서빙** — 헤더를 못 붙인다(원인 절).
- **Cloudflare Pages 의 `_headers`** — 정적인 채로 헤더가 붙어 Worker 없이 될 것 같지만, 결정 3 의
  런타임별 분기(요청 헤더를 읽어 다른 매니페스트를 고르는 일)를 정적 파일이 못 한다. 어차피 코드가
  필요하면 Worker 가 더 단순하다.

### 2. Worker 는 **상태가 없다** — 배포는 여전히 `gh release upload` 하나다

Worker 는 요청 헤더(`Expo-Platform` · `Expo-Runtime-Version`)로 파일 이름을 만들어 GitHub Release 의
정적 JSON 을 그대로 가져와, 헤더를 얹어 되돌려준다. **매니페스트를 만들지 않는다.** 만드는 것은
배포 스크립트이고 저장하는 곳은 릴리스다.

```js
// 개념
const name = `manifest-${platform}-${runtimeVersion}.json`
const res = await fetch(`${RELEASE_BASE}/${name}`)
if (!res.ok) return new Response(null, { status: 204, headers: COMMON })  // 이 런타임엔 업데이트 없음
return new Response(res.body, { headers: { ...COMMON, 'expo-protocol-version': '1', … } })
```

이렇게 두는 이유는 **릴리스 경로에 실패 표면을 안 늘리려는** 것이다 — `publish-live-update.mjs` 머리가
이미 같은 판단을 적어 두었다(*"배포 스크립트가 릴리스 경로의 일부라 의존성이 늘수록 릴리스가 깨질
표면이 넓어진다"*). Worker 가 상태를 들면 배포가 «릴리스 업로드 + KV 쓰기» 두 갈래가 되고, 두 갈래가
갈리는 순간 어느 쪽이 사실인지 알 방법이 없다. **Worker 는 한 번 올리고 다시 안 건드린다.**

기각: **Worker 가 KV 에 매니페스트를 들고 배포 때 API 로 쓴다** — 위. · **Worker 가 `metadata.json`
을 읽어 매니페스트를 매 요청마다 조립한다** — 조립 규칙이 배포 스크립트와 Worker 두 곳에 생긴다.

### 3. `runtimeVersion` 이 `minNativeVersion` 을 대체한다 — 그리고 **정책은 `fingerprint`** 다

[[ADR-027]] 결정 7 의 `minNativeVersion` 은 *"이 번들을 적용하려면 이보다 새 네이티브가 필요하다"* 를
우리가 손으로 적던 필드였다. `expo-updates` 에서 같은 일은 **프로토콜이** 한다 — 클라이언트가
`Expo-Runtime-Version` 을 보내고(`FileDownloader.kt:createRequestForRemoteUpdate` 실측), 서버는 그
런타임에 맞는 번들만 준다.

> **정정 2 (2026-08-14) — 순서 규칙이 하나 생겼다.** `runtimeVersion` 이 fingerprint 면 그것은
> **네이티브 트리의 함수**다. 배포한 뒤 `expo prebuild` 를 돌리자 값이 바뀌었고
> (`2f68d187…` → `d1111d84…`), 매니페스트는 **아무도 묻지 않을 이름**으로 릴리스에 남았다. 앱은
> 204(업데이트 없음)를 받고, 역시 **아무 데서도 에러가 나지 않는다.**
> → **네이티브를 건드렸으면 `expo prebuild` 를 먼저 끝내고 배포하라.** 배포 스크립트에 왕복 확인
> 단계(`[6/6]`)를 두어, 방금 올린 매니페스트를 **클라이언트가 묻는 그대로** 물어보고 번들 해시까지
> 대조한다 — «올렸다» 가 아니라 «받아진다» 로 성공을 정의한다.

**정책은 `{ "policy": "fingerprint" }` 로 둔다.** 네이티브 의존성 그래프에서 값이 **계산된다** —
`minNativeVersion` 을 손으로 적던 시절의 사고(*"네이티브를 바꿨는데 그 숫자를 안 올렸다"*)가 원리적으로
불가능해진다. [[ADR-128]] 트레이드오프가 *"이 저장소에서 처음으로 «고칠 수 없는 릴리스» 가 생긴다"*
고 적은 그 위험의 반대편이 정확히 이것이다 — **네이티브가 안 맞는 번들이 나가면 앱이 죽고, 죽은 앱은
OTA 로 못 고친다.** 사람이 기억해서 막을 일이 아니다.

### 4. 「스토어 업데이트 필요」만 **우리 축에 남는다**

결정 3 을 그대로 두면 [[ADR-027]] 결정 7 의 분기가 조용히 사라진다. 런타임이 안 맞으면 클라이언트가
받는 것은 **204(업데이트 없음)** 이라, 사용자에게는 *"최신 버전입니다"* 로 보인다. **그것은 거짓이다** —
새 버전은 있고, 다만 스토어를 거쳐야 한다.

그래서 그 판정만 우리 축에 남긴다. Worker 에 작은 조회를 하나 더 두고, **`up-to-date` 로 떨어졌을
때만** 묻는다(업데이트가 있으면 물을 이유가 없다).

```
GET /latest?platform=ios  →  { "runtimeVersion": "…", "appVersion": "1.0.7" }
```

앱이 자기 `Updates.runtimeVersion` 과 비교해 다르면 `store-required` 로 간다 — [[ADR-027]] 결정 7 의
화면·문구·스토어 이동이 **글자 그대로 산다**. 프로토콜은 안 건드린다.

기각: **런타임이 안 맞아도 매니페스트를 준다** — `SelectionPolicy` 가 런타임으로 거르므로 받아만 두고
영영 안 띄운다(«받았는데 아무 일도 안 일어난다» 는 [[ADR-117]] 이 싫어한 형태다). · **204 응답 헤더에
표식을 싣는다** — 네이티브가 응답 헤더를 JS 로 안 넘긴다.

### 5. 우리 축의 값 넷은 매니페스트 `extra` 에 싣는다

스펙의 `extra: { [key: string]: any }` 가 그 자리다. **[[ADR-119]] 결정 1(원천 한 벌)· [[ADR-126]]
결정 2(핵심 목록 3~4줄)는 글자 하나 안 바뀐다** — 원천은 `core/src/data/release-notes.ts` 그대로이고,
배포 스크립트가 뽑아 싣는 자리만 `latest.json` 에서 `extra` 로 옮긴다. 노트·핵심 목록 없이는 배포가
중단되는 가드(`describeReleaseNoteGap`)도 그대로 산다([[ADR-119]] 결정 6 → [[ADR-126]] 결정 8).

| `extra` 필드 | 왜 프로토콜에 없나 |
|---|---|
| `highlights: string[]` | 우리가 만든 값([[ADR-126]] 결정 2) |
| `appVersion: "1.0.6"` | 프로토콜의 정체성은 UUID `id` 다. **사용자에게 보이는 버전은 우리 축**이고, 설정 화면·모달·개발 노트 「사용 중」 표식이 전부 이 값을 읽는다 |
| `sizeBytes` | 프로토콜에 용량 필드가 없다. [[ADR-027]] 이 모달의 재료를 «버전 + 용량» 으로 정했다 |
| `storeUrl` | [[ADR-027]] 결정 7 의 스토어 이동 대상 |

`extra` 는 **선택 필드로 읽는다** — [[ADR-119]] 가 `highlights` 를 필수 검사에 안 넣은 것과 **같은
이유**이고, 이번에는 그 이유가 더 세다: 매니페스트는 URL 고정·내용 가변인 데다 이제 **앱 버전과
매니페스트를 만든 스크립트 버전이 서로 다른 시점의 것**일 수 있다.

### 6. `LiveUpdatePort` 를 «프로토콜» 이 아니라 «행위» 로 다시 긋는다

지금 포트는 @capgo 의 모양을 그대로 드러낸다 — `httpGet`(매니페스트를 **호출부가 직접 판다**) ·
`download({ url, checksum })` · `applyBundle(id)`. 셋 다 `expo-updates` 에 짝이 없다(주소·체크섬·번들
id 를 런타임이 자기 안에서 다루고, 우리에게 안 보여준다).

그래서 경계를 **행위**로 다시 긋는다:

| | 지금 (@capgo 모양) | 다시 그은 뒤 |
|---|---|---|
| 확인 | `httpGet()` + core 가 파싱·버전비교 | `check(): Promise<LiveUpdateCheckResult>` |
| 받기 | `download({url, checksum}, onProgress)` | `download(onProgress): Promise<void>` |
| 적용 | `applyBundle(id)` | `apply(): Promise<void>` |

- **스토어가 그대로 갖는 것**: 상태 14개 · 셀룰러 확인 · 12초 타임아웃 · 완료 안내 판정. 즉
  [[ADR-027]]·[[ADR-061]]·[[ADR-065]]·[[ADR-117]]·[[ADR-126]] 이 정한 **UX 는 전부 그 자리에 남는다.**
- **어댑터가 갖는 것**: 프로토콜. `parseLiveUpdateManifest` · `isNewerVersion` · `checkForLiveUpdate`
  는 **capacitor 어댑터로 옮긴다** — 지우는 것이 아니라 **옮기는 것**이라 `app-capacitor` 는 계속
  돈다(전환 완료 전까지 스토어에 있는 것은 아직 그 앱이다).
- `LiveUpdateCheckResult` 는 **그대로 쓴다** — 다섯 갈래(`unsupported`·`error`·`up-to-date`·
  `store-required`·`update-available`)가 프로토콜과 무관한 «앱이 무엇을 할 수 있나» 의 분류다.

### 7. 채널을 하나로 줄인다 — 그리고 그것이 **`import.meta.env` 벽을 없앤다**

[[ADR-024]] 의 빌드 시점 채널 분리는 **사이드로딩 베타**(스토어 출시 전, APK 직접 배포)를 위한 것이었다.
2026-08-06 App Store 게시로 그 용도가 끝났고, 베타 채널은 1.0.0 리셋 이후 사실상 끊긴 채였다
(`features/live-update.md` 의 ⚠️ 항목). **사용자 판정으로 폐기한다.**

부수 효과가 하나 있는데 그것이 작지 않다. `core/src/features/live-update/store.ts` 는 **모듈 최상위**
에서 `import.meta.env.VITE_LIVE_UPDATE_CHANNEL` 을 읽고, RN 런타임에서 `import.meta.env` 는
`undefined` 라 **그 스토어를 값으로 import 하는 순간 죽는다**([[ADR-129]] 가 남긴 마지막 벽 ·
`core-shims.js` 가 *"OTA 를 이을 때 이 표가 그 자리를 맡을 가능성이 크다"* 고 예측해 둔 자리다).

**그 예측은 빗나간다 — 벽을 우회하는 것이 아니라 벽의 원인이 사라진다.** 채널이 없어지면 그 한 줄이
없어지고, 남는 빌드 시점 값(있다면)은 결정 6 에 따라 **어댑터의 것**이다. `core-shims.js` 의 표는
비어 있는 채로 남는다.

### 8. 에셋은 **내용 주소**로 올린다 — 두 번째 배포부터는 바뀐 것만 오른다

`expo export` 산출물을 실측했다(2026-08-14, `--platform ios --platform android`):

| | 개수 | 크기 |
|---|---|---|
| 에셋(`assets/<md5>`) | **293** | 6.0 MB |
| Hermes 번들(플랫폼당 1) | 2 | 4.8 MB × 2 |
| 합 | 295 + `metadata.json` | 15 MB |

에셋 파일 이름이 **이미 내용의 md5** 이고 **기본 이름 충돌이 0건**이다(전수 확인). GitHub Release 자산은
평평한 이름 공간이라 그대로 올라간다. 그래서 배포는 «릴리스에 이미 있는 이름은 건너뛴다» 하나로 끝난다:

- **첫 배포**: 295개 업로드
- **JS 만 고친 배포**: 에셋 해시가 그대로라 **번들 2 + 매니페스트만** 오른다(실측 확인 — 두 번째
  배포가 `자산 295개 중 2개 업로드`)

> **정정 1 (2026-08-14, 실기기 검증 중 발견) — 이 전제는 «번들» 에는 거짓이었다.**
>
> *"파일 이름이 이미 내용의 md5"* 는 `assets/<md5>` 에만 참이다(293/293 실측). 번들
> `_expo/static/js/<platform>/index-<hash>.hbc` 의 `<hash>` 는 **Hermes 이전** 단계의 것이라
> **같은 이름으로 다른 바이트**가 나온다. 두 번째 배포에서 번들이 «이미 있는 이름» 으로 걸러져
> 안 올라갔고, 매니페스트에는 새로 계산한 sha256 이 실렸다. 앱은 받아서 대조하다 버린다 —
> `AssetsFailedToLoad … SHA-256 did not match expected`.
>
> **배포도 성공하고 매니페스트도 정상이라 앱을 실제로 실행하기 전에는 어디에서도 안 드러난다.**
> 처방은 번들을 **자기 sha256 으로 이름 짓는 것**(`bundle-<platform>-<sha256>.hbc`) — 이름이
> 내용에서 파생되면 «같은 이름 = 같은 내용» 이 규칙이 아니라 **구조**가 된다. 그리고 배포 스크립트가
> 디렉터리를 훑는 대신 `metadata.json` 에서 올릴 것을 정한다(훑는 방식이 이 전제를 숨겼다).

받는 쪽도 같은 이유로 싸다 — `expo-updates` 는 파일 이름이 이미 있으면 안 받는다
(`FileDownloader.downloadAsset` → `path.exists()` → `ALREADY_EXISTS`). 네이티브에 내장돼 있던 에셋은
`EmbeddedLoader` 가 이미 같은 자리에 복사해 두므로, **그림을 안 바꾼 업데이트는 번들 4.8 MB 만
내려받는다**(@capgo 시절 zip 통짜 6.27 MB 와 같은 자릿수다).

### 9. 릴리스 태그와 버전

- **`live-update-latest` 는 손대지 않는다** — capacitor 앱(1.0.0~1.0.5)이 아직 스토어에 있고 그
  매니페스트를 본다. RN 이 그 자리를 대체하기 전에 지우면 **현역 앱의 OTA 를 끊는 것**이다.
- **`live-update-beta` 는 릴리스째 지운다**(사용자 판정). 담긴 것은 끊긴 채널의 1.0.46~1.0.48 이다.
- **새 태그에 1.0.6 부터 쌓는다.** 1.0.5(capacitor 의 마지막)를 이어받는 번호다.

---

**대가**

- **의존성이 하나 늘고, 그것이 우리 저장소 밖에서 돈다.** Worker 가 죽으면 «업데이트 확인 실패» 가
  된다([[ADR-065]] 결정 2 의 `check-error` — 모달을 안 띄우고 설정 화면 상태 행에만 남으므로 사용자
  흐름은 안 끊긴다). 옮기려면 `app.json` 의 URL 한 줄이고 코드는 우리 것이다.
- **`expo-updates` 는 네이티브 의존성이라 재빌드가 필요하다.** 이 결정을 담은 첫 릴리스 자체는 OTA 로
  못 나간다 — [[ADR-128]] 트레이드오프가 말한 «고칠 수 없는 릴리스» 가 **한 번 더** 있다는 뜻이다.
  그 다음부터 없어진다.
- **매니페스트 조회가 앱 부팅 경로에서 두 번**이 될 수 있다(결정 4 의 `/latest`). `up-to-date` 일
  때만이고 수백 바이트다.
- **`app-capacitor` 와 `app-rn` 이 서로 다른 OTA 프로토콜을 쓴다.** 전환이 끝날 때까지 배포 절차가
  두 벌이고, `foundation/release.md` 도 두 벌을 적어야 한다.

---

**열린 질문**

- **코드 서명을 켤 것인가**(`expo-updates codesigning:generate`/`configure`). 매니페스트를 우리
  엔드포인트가 내므로, 그 엔드포인트나 DNS 를 잡는 사람은 임의 JS 를 전 사용자에게 밀 수 있다.
  @capgo 시절과 **위험 수준이 같아서**(그때도 매니페스트 자체는 서명이 없었다) 이 결정의 전제
  조건은 아니지만, 자체 호스팅에서 Expo 가 1급으로 지원하는 유일한 방어선이다. 개인키 보관 부담과
  «키를 잃으면 그 앱들은 영영 업데이트를 못 받는다» 를 함께 재야 한다.
- **`enableBsdiffPatchSupport`** — 켜면 번들 전체(4.8 MB) 대신 차분을 받는다. 서버가 패치를 만들어야
  해서 결정 2 의 «Worker 는 상태가 없다» 와 부딪힌다. 배포 스크립트가 미리 만들어 올리는 길이 있는지는
  안 봤다.
- **새 릴리스 태그 이름** — 이 문서는 `live-update-rn` 을 가정하고 썼다. 전환이 끝나면 `rn` 이
  군더더기가 되므로 다른 이름이 나을 수 있다.
- **번들 하우스키핑을 안 정했다**(2026-08-14, **미루기로 사용자 판정**). 배포할 때마다 새 이름의
  번들 2개가 붙는데 옛 번들은 어느 매니페스트도 안 가리키는 **죽은 파일**이 된다(매니페스트는 같은
  이름으로 덮인다). 지우는 코드가 없어 릴리스당 ~9 MB 씩 쌓이고, 지금은 **손으로** 지운다(이 세션에
  fingerprint 가 세 번 바뀌며 8개를 그렇게 치웠다). capacitor 쪽 「최신 3개 유지」(2026-07-31 채택)에
  해당하는 정책이 RN 에는 아직 없다 — 정하면 `publish-rn-ota.mjs` 가 맡을 자리다. **에셋 293장은
  이 문제가 없다**(내용 주소라 같은 그림은 영원히 한 벌).
- **롤백**([[ADR-022]] 의 «크래시 시 자동 롤백»). `expo-updates` 에는 `RollBackToEmbedded` 디렉티브가
  있고 `notifyAppReady`/`appReadyTimeout` 의 짝도 있다([[ADR-117]] 결정 2 가 옮겨 갈 자리). 이 문서는
  거기까지 안 정했다.

---

**시뮬레이터에서 확인한 것** (iPhone 17 Pro / iOS 26.5 · **Release** 빌드 — `expo-updates` 는 debug 에서 꺼진다)

받기 전 모달부터 적용 후 재시작까지 한 바퀴를 실제로 돌렸다.

| 단계 | 확인된 것 |
|---|---|
| 부팅 확인 | `AppShell` 의 `checkOnBoot()` → Worker → 모달 **자동 표시** |
| 모달 내용 | `v1.0.6`(= `extra.appVersion`) · `4.6MB`(= `extra.sizeBytes` 4,844,546) · 「자세히 보기」(= `highlights` 가 있어서 그려진다, [[ADR-126]] 결정 6) |
| 받기 | `downloading` → `ready-to-apply`(「업데이트 준비 완료」) |
| 적용 | `reloadAsync()` → 재시작, 모달 없이 정상 부팅 |
| **증거** | 기기의 `.expo-internal/b4e8ab99….bundle` 이 매니페스트 `launchAsset` 의 **key·sha256 과 모두 일치** |

**「업데이트를 마쳤어요」([[ADR-126]] 결정 4)는 안 떴고 그것이 맞다** — 판정이 `isNewerVersion` 이라
내장 번들과 OTA 번들이 **같은 1.0.6** 이면 «올라간 것» 이 아니다. 다음 버전을 올릴 때 처음 뜬다.

**미검증**: 실기기 · **안드로이드**(매니페스트·번들은 올라가 있으나 앱을 안 돌렸다) · 롤백 ·
`store-required` 분기(런타임이 다른 빌드를 만들어야 한다) · 셀룰러 경고(어댑터가 `'unknown'` 고정).
