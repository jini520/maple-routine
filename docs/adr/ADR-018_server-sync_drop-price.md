# ADR-018 드롭 기록의 id 와 월드

> 🟢 유효
> 옛 번호: ADR-299 결정 4 · ADR-342 · ADR-343 · ADR-352
> 관련 소스: `storage/boss-drops.ts` · `storage/sqlite/uuid.ts`

## 배경

드롭 기록은 기기 간 동기화로 서버 `boss_drops` 에 올라가고, 서버는 가격을 적은 드롭을 받을 때 시세를 재는 판매가 줄을
적는다([[ADR-099]] 결정 26). 같은 드롭을 고쳐 다시 올리면 서버가 같은 줄을 덮어야 하고, 판매가 줄은 월드마다 시세를 갈라야
한다. 그런데 처음의 드롭 기록은 기록을 가리키는 값이 저장할 때마다 바뀌었고, 월드도 기록에 없었다. 이 문서는 드롭 기록의 id 와
월드를 정한다. 드롭을 올리는 방법은 [[ADR-099]] 결정 67 에 있다.

## 결정

### 결정 1. 드롭 기록의 기본키는 기기가 만든 uuid 하나다

`boss_drops` 의 기본키는 `id` 한 칸이고, 이 값이 서버 `boss_drops` 줄의 `id` 가 된다([[ADR-099]] 결정 8). 드롭은
`profit_entry_id` 로 수익 건을 가리키고, 캐릭터 · 보스 · 난이도 · 기간은 수익 건에서 읽는다([[ADR-078]] 결정 1). 이 값들로
드롭을 가리키지 않는 이유는 설계상 바뀌기 때문이다. 처치 난이도가 확정되면 드롭이 다른 수익 건으로 옮겨 간다. 묶음 안의 차례
번호(`dropIndex`)도 읽을 때 드롭 표의 차례로 매기는 값이라, 드롭 하나를 넣거나 빼면 뒤의 번호가 바뀐다. 이 값으로 서버의 줄을
가리키면 가격이 다른 아이템에 붙는다.

uuid 는 기기가 만든다. 서버가 만들어 응답으로 주면, 통신이 실패했을 때 사용자가 적은 가격이 기기에도 남지 않는다.
만드는 곳은 SQLite 다(`NEW_UUID_SQL`, `randomblob()` 으로 v4 형식을 만든다). Hermes 에는 `crypto` 가 없고, 네이티브
모듈을 새로 들이면 스토어 빌드를 기다려야 한다. SQLite 는 이미 들어 있어 OTA 로 나간다. 이 값은 비밀이 아니다. 남의
값을 알아내도 서버는 같은 id 의 줄이 남의 것이면 적지 않는다([[ADR-099]] 결정 8).

### 결정 2. 묶음을 다시 저장해도 같은 아이템은 같은 uuid 를 물려받는다

`replaceBossDropRecords` 는 그 수익 건의 드롭을 지우고 다시 넣는다. 그대로 두면 저장할 때마다 uuid 가 새로 생겨, 같은 드롭을
서버에서 지우고 새로 올리는 일이 저장마다 생긴다. 그래서 지우기 전에 기존 행의 uuid 를 읽어 두고, 아이템 줄(`item_id`)이 같은
드롭에 물려준다. 아이템 줄은 반지 레벨과 상자용 줄까지 가르고, 한 수익 건에 같은 아이템 줄은 하나라
(`UNIQUE (profit_entry_id, item_id)`) 한 uuid 가 두 행에 붙을 일이 없다. 드롭에 이미 uuid 가 있으면 그것을 먼저 쓴다. 난이도
확정으로 드롭을 다른 수익 건으로 옮길 때가 그렇다.

### 결정 3. 드롭의 월드는 수익 건의 `world_id` 다

수익 건(`boss_profit_entries`)의 `world_id` 가 기록 시점의 월드다. 월드마다 시세가 달라서, 서버는 판매가 줄의 월드를 수익 건에서
읽는다([[ADR-099]] 결정 26). 드롭과 처치는 같은 수익 건에 붙으므로 같은 월드를 쓴다. 결정석 가격을 모르는 보스도 드롭을 적으면
수익 건이 생기므로 월드를 적을 곳이 있다. 저장 함수가 읽을 때 월드 줄 id 로 월드 key 를 찾고, 이름은 `worldNameOf` 로 찾는다.

캐시에 월드가 없으면 `NULL` 이다. 0 이나 빈 문자열로 채우면 모른다는 사실이 값처럼 보인다. 이미 적힌 월드는 덮지
않는다. 그래서 묶음을 다시 저장해도 기록 시점의 월드가 바뀌지 않는다.
