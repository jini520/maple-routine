# ADR-018 드롭 가격 서버 전송

> 🟢 유효
> 옛 번호: ADR-299 결정 4 · ADR-342 · ADR-343 · ADR-352
> 관련 소스: `features/server-sync/` · `storage/server-sync-queue.ts` · `storage/boss-drops.ts` · `storage/sqlite/uuid.ts` · `server/drop-price.ts` · `types/drop-price.ts`

## 배경

사용자가 드롭 아이템을 판 가격을 서버에 모으면 아이템별 시세 추이를 볼 수 있다(이슈 #610). 그런데 기기의 드롭
기록은 이 일에 맞지 않았다. 기록을 가리키는 값이 저장할 때마다 바뀌었고, 월드도 기록에 없었다. 또
서버에 보내다 실패한 것을 어디에 두고 다시 보낼지도 정해야 했다. 이 문서는 드롭 기록이 서버로 가는 방법 전체를
정한다. 지금 서버로 보내는 기록은 드롭 가격 하나뿐이다.

## 결정

### 결정 1. 드롭 기록의 기본키는 기기가 만든 uuid 하나다

`boss_drop_records` 의 기본키는 `drop_record_id` 한 칸이다. 예전 기본키였던 `(ocid, boss_key, difficulty, period_key,
drop_index)` 는 평범한 칸으로 두고 인덱스만 건다. 이 다섯 칸 중 두 칸이 설계상 바뀌기 때문이다. `difficulty` 는 처치
난이도가 확정될 때 바뀌고, `drop_index` 는 그룹을 저장할 때마다 배열 위치로 다시 매겨진다. 그래서 목록에서 하나를
빼면 뒤의 번호가 당겨지고, 이 값으로 서버에 보내면 가격이 다른 아이템에 붙는다. 다섯 칸에 `UNIQUE` 도 걸지 않는다.
한 행씩 고치는 사이에 `drop_index` 가 잠깐 겹칠 수 있어서다. v1.0.13 에서 드롭 기록은 기간 행을 가리키는 새 테이블로
옮기고, 상태 칸을 서버와 같은 `record_status` 로 바꾼다([[ADR-078]] 결정 1 · 5, 미구현).

uuid 는 기기가 만든다. 서버가 만들어 응답으로 주면, 통신이 실패했을 때 사용자가 적은 가격이 기기에도 남지 않는다.
만드는 곳은 SQLite 다(`NEW_UUID_SQL`, `randomblob()` 으로 v4 형식을 만든다). Hermes 에는 `crypto` 가 없고, 네이티브
모듈을 새로 들이면 스토어 빌드를 기다려야 한다. SQLite 는 이미 들어 있어 OTA 로 나간다. 이 값은 비밀이 아니다. 남의
값을 알아내도 그 사람의 신원 없이는 쓸 수 없다(결정 7).

### 결정 2. 그룹을 다시 저장해도 같은 아이템은 같은 uuid 를 물려받는다

`replaceBossDropRecords` 는 그룹을 지우고 다시 넣는다. 그대로 두면 저장할 때마다 uuid 가 새로 생겨 서버에 같은 기록이
계속 쌓인다. 그래서 지우기 전에 기존 행의 uuid 를 읽어 두고, 아이템을 구별하는 값(아이템 key · 상자 출처 key · 반지 레벨)이
같은 드롭에 물려준다. 드롭에 이미 uuid 가 있으면 그것을 먼저 쓴다. 난이도 확정으로 드롭을 다른 그룹으로 옮길 때가
그렇다. 구별하는 값이 같은 드롭이 둘이면 첫 행만 물려받는다. 한 uuid 가 두 행에 붙으면 서버가 둘을 한 기록으로 보고 서로 덮는다.

저장이 끝나면 저장한 순서대로 uuid 를 돌려준다. 시트에서 방금 만든 드롭은 메모리에 uuid 가 없어서, 그 값을 받아
전송에 쓰고 메모리의 드롭에도 붙인다.

### 결정 3. 드롭 기록에 월드 칸을 따로 둔다

`world` · `world_key` 칸이 기록 시점의 월드다. 월드마다 시세가 달라서 서버로 보내야 한다. 같은 보스의 수익 행에서
물려받지 않는다. 결정석 가격을 모르는 보스는 수익 행이 없어서, 그 드롭은 물려받을 곳이 없다. 캐시에 월드가 없으면
`NULL` 이다. 0 이나 빈 문자열로 채우면 모른다는 사실이 값처럼 보인다. 그룹을 다시 저장할 때 기존 행의 월드를 그대로
물려받아, 기록 시점의 월드가 바뀌지 않는다.

### 결정 4. 저장하는 순간 한 건씩 보내고, 기기 저장이 먼저다

보낼 것을 찾으려고 기록 표를 훑지 않는다. 사용자가 저장하는 순간 그 기록 한 건을 보낸다. 기기에 쓴 다음에 보내고,
결과를 기다리지 않고, 실패해도 던지지 않는다. 사용자에게 보이는 것은 저장이고, 전송이 실패했다고 알려도 사용자가 할
수 있는 일이 없다.

보내는 곳은 셋이다.

| 곳 | 보내는 것 |
|---|---|
| 드롭 시트 저장(`setBossDrops`) | 저장한 드롭 전부 |
| 가격 화면 저장(`writePrice`) | 그 드롭 하나 |
| 난이도 확정 이관(`migrateDropsToConfirmedDifficulty`) | 새 난이도로 옮긴 드롭 전부. 안 보내면 서버 줄이 옛 난이도를 가리킨 채 남는다 |

`reportDropPrice` 는 uuid 만 받아 기록을 다시 읽어서 보낸다. 부르는 쪽이 가진 드롭 값에는 월드도 기간도 없어서,
손으로 조립하면 칸 하나가 빠져도 타입 검사를 통과하고 값만 사라진다.

기능이 나간 뒤 시작한 기간의 기록만 보낸다(`SERVER_PRICE_FROM`, 사용자 지정). 기준은 `period_key` 다. 바뀌지 않는
값이라서다(`recorded_at` 은 그룹을 다시 저장할 때 오늘로 덮인다). 기존 기록은 서버로 옮기지 않고, 기능이 나간 뒤에
지난 기간을 채운 기록도 보내지 않는다. 주간 기간 키 `YYYY-MM-DD` 와 월간 기간 키 `YYYY-MM` 이 둘 다 `YYYY-MM` 으로 시작해서
문자열 비교 하나로 가를 수 있다.

전송은 끌 수 없다. 설정에 토글이 없다(사용자 지정).

### 결정 5. 가격이 없는 기록도 상태를 달아 올린다

기록의 상태는 서버 줄의 `record_status` 칸에 적는다.

| 서버 상태 | 뜻 | 기기 쪽 |
|---|---|---|
| `pending` | 기록은 있고 가격이 아직 없다 | `price_state` 가 `NULL`. 또는 `'entered'` 인데 가격이 없거나 0 |
| `completed` | 가격이 있다 | `'entered'` 이고 가격이 1 이상 |
| `skipped` | 값을 매기지 않기로 했다 | `'excluded'`(기록 안함) |
| `deleted` | 기기에서 기록이 사라졌다 | 행이 없다. `DELETE` 로만 생긴다 |

`price_meso` 는 `completed` 일 때만 값이 있고 나머지는 `NULL` 이다. 서버의 `CHECK` 가 이것을 강제한다. 0 으로 적으면
0 메소에 팔았다는 뜻이 되어 미입력과 구분할 수 없다. 서버의 분포(최소 · 중앙값 · 최대)는 `completed` 만 센다.

미입력과 기록 안함도 올리는 이유는 둘이다. 판 것만 올리면 먹었는데 안 판 것이 얼마인지 서버가 모른다. 그리고 기록
안함을 지우기로 보내면 한 번도 올라간 적 없는 기록에 지우기 요청이 나간다.

### 결정 6. `DELETE` 는 기기에서 기록이 사라졌을 때만 보낸다

서버는 그 줄을 `deleted` 로 표시하고 `price_meso` 를 비운다. 줄은 지우지 않는다([[ADR-017]] 결정 6). 앱이 지우기를
보내는 곳은 셋이다.

- 드롭 시트 저장에서 빠진 드롭. 저장 전과 저장 뒤의 uuid 를 비교한다. 해제했다가 같은 세션에 다시 고른 드롭은
  결정 2 로 uuid 를 물려받아 빠진 것으로 세지 않는다.
- 획득 불가로 지워진 드롭. 확정 난이도에서 얻을 수 없는 드롭은 기기에서 지워진다. 난이도 확정 이관과, 기록을 불러올 때
  지우는 `loadDropsByRowKey` 두 곳이다.
- 대기 표의 원본이 사라졌을 때(결정 8).

기록이 이미 없어 다시 읽을 수 없으므로 `reportDropRemoved` 는 기간 키를 따로 받는다. 기준 기간 앞이면 보내지 않는다.

### 결정 7. 서버는 기록 하나에 줄 하나를 두고, 같은 사람 안에서만 덮는다

서버 `drop_prices` 는 자기 uuid 를 기본키로 두고, 기기가 만든 `drop_record_id` 는 칸으로 둔다. 서버에는 기기 행의
사본이 없으므로 이 칸은 다른 표를 가리키지 않는다. `UNIQUE (user_id, drop_record_id)` 이고 `POST` 는 그 쌍으로 덮어
쓴다. 응답만 사라져 기기가 같은 기록을 다시 보내도 줄이 늘지 않는다. 남의 uuid 로 보내면 내 줄이 하나 생길 뿐 남의
줄은 건드리지 않는다. 고친 이력은 남기지 않는다. 기록마다 마지막 값 하나다(사용자 지정).

한 건에 싣는 칸은 다음과 같다.

| 칸 | 뜻 |
|---|---|
| `dropRecordId` | 기기가 만든 uuid. 같은 기록을 고치면 같은 줄을 덮게 한다 |
| `itemKey` | 분포의 축. 서버가 `drop_items` 에서 찾아 `item_id` 로 적는다. 모르는 key 는 400 |
| `status` · `priceMeso` | 결정 5. `priceMeso` 는 판매 총액이고 내 몫이 아니다 |
| `periodKey` | 언제 먹었나. 바뀌지 않는 값이라 추이의 축이 된다 |
| `worldKey` | 결정 3. 서버가 `worlds` 에서 찾아 `world_id` 로 적는다. 없으면 `NULL`, 모르는 key 는 400 |
| `ringLevel` | 반지 레벨에 따라 시세가 다르다. 반지가 아니면 `null` |
| `boss` · `difficulty` | 어느 보스 · 난이도에서 얻었나. 서버가 `boss_difficulties` 에서 쌍을 찾고, 없으면 `NULL` 로 받는다 |

분배 인원 · 비율 · 수수료는 싣지 않는다. 내 몫을 계산하는 재료이고 시세와는 관계가 없다. 수량은 늘 1 이라 싣지 않는다.

아이템과 월드는 모르는 key 를 받으면 어느 아이템의 시세인지 모르는 줄이 되므로 거절한다. 앱은 서버 표를 받아 쓰므로
서버가 모르는 key 를 보낼 일이 없다. 보스 · 난이도는 없어도 시세 줄로는 쓸 수 있어서 `NULL` 로 받는다.

서버는 본문이 틀렸을 때만 4xx 를 낸다. 앱이 응답 받은 시도를 다섯 번까지 세고 버리기 때문에(결정 8), 서버가 멀쩡한
본문을 거절하면 그 기록이 사라진다. 옛 OTA 는 `status` 를 보내지 않으므로 서버는 `status` 가 없으면 `completed` 로 읽는다.

운영자는 관리 화면(`/admin/drop-prices`)에서 아이템 × 기간의 분포와 최근 줄을 본다. 읽기만 한다.

### 결정 8. 못 보낸 것은 대기 표 하나에 두고, 앱을 켤 때 다시 보낸다

```
server_sync_queue
  id          TEXT     PK. SQLite 가 만든 uuid
  kind        TEXT     어느 종류의 기록인가('drop-price')
  record_id   TEXT     UNIQUE. 그 기록의 uuid
  attempts    INTEGER  응답을 받은 시도 횟수
  last_error  TEXT
  created_at  TEXT
```

- 못 보낸 것만 줄로 남고 평소에는 비어 있다. 한 기록에 줄은 하나이고, 이미 있으면 그대로 둔다. 다시 저장했다고 시도
  횟수를 0 으로 돌리면, 서버가 계속 거절하는 건이 끝없이 다시 나간다.
- 값은 담지 않고 `record_id` 만 담는다. 보낼 때 원본에서 지금 값을 읽는다. 담아 두면 그 사이 또 고친 경우 중간 값이 간다.
- 올리기인지 지우기인지는 칸으로 적지 않는다. 원본이 있으면 올리기, 없으면 지우기다. 칸으로 적으면 지워진 기록에
  올리기가 남은 상태가 생길 수 있다.
- 기록 표에는 전송 시각이나 시도 횟수를 두지 않는다. 그것은 드롭 기록의 값이 아니다(사용자 지정).

앱을 켤 때(`AppShell` 이 준비된 뒤) `runServerSync` 가 백그라운드에서 한 번 훑는다. 첫 화면을 막지 않고, 실패해도 던지지 않는다.
순회 함수(`sweepServerSync`)는 기록의 종류를 모른다. 종류마다 함수 두 개(`read` · `send`)를 레지스트리(`registry.ts`)에서 찾는다.

| 결과 | 하는 일 |
|---|---|
| 보냈다 | 줄을 지운다 |
| 응답이 안 왔다(연결 실패 · 타임아웃) | 아무것도 안 한다. 다음 회차에 그대로 다시 보낸다 |
| 응답이 왔고 거절이다 | `attempts` 를 하나 올린다. 다섯 번째면 줄을 버린다 |
| 레지스트리에 없는 종류 | 줄을 버린다 |
| 밝힐 신원이 없다 | 그 회차를 통째로 건너뛴다. 횟수도 안 올린다 |

핵심은 응답이 왔는지로 구분하는 것이다. 네트워크가 없을 때도 횟수를 올리면, 비행기 모드로 앱을 다섯 번 켠 사용자가
그동안 쌓인 것을 모두 잃는다(사용자 지정). 그래서 `server/drop-price.ts` 는 다른 조회 어댑터와 달리 실패를
`no-response` 와 `rejected` 로 나눠 돌려준다. `attempts` 는 응답을 받은 뒤에 적는다. 미리 적고 성공하면 되돌리는
방식이면, 훑는 중에 앱이 꺼졌을 때 되돌리지 못해 켰다 끈 것이 시도로 남는다.

다섯 번 거절된 건을 버려도 되는 것은 서버가 모으는 목적이 통계라서다. 한두 건이 빠지는 것은 문제가 아니고,
기기의 기록은 그대로 남는다(사용자 지정).

종류를 레지스트리에 더하지 않으면 그 종류는 대기 표에 쌓이기만 하고 나가지 않는다. 순회 함수가 모르는 종류를 버리면
빠뜨린 것이 정상 동작처럼 보인다. 그래서 대기 표에 줄을 넣는 코드가 쓰는 이름이 모두 레지스트리에 있는지 테스트가 본다.

### 결정 9. 서버를 먼저 배포한다

새 앱은 `priceMeso: null` 과 `status` 를 보낸다. 옛 서버는 가격이 1 이상이어야 받으므로 새 앱의 미입력 · 기록 안함을
400 으로 거절하고, 앱은 다섯 번 뒤 그 건을 버린다. 서버를 먼저 올리면 옛 앱의 전송도 그대로 받는다. 이때 옛 앱이
기록 안함을 `DELETE` 로 보내 `skipped` 가 아니라 `deleted` 로 남는 것은 OTA 가 나갈 때까지의 일이라 받아들인다.
