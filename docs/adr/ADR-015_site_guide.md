# ADR-015 안내 사이트

> 🟢 유효
> 옛 번호: ADR-110 · ADR-229
> 관련 소스: `site/` · `PRIVACY.md` · `scripts/build-site.mjs` · `scripts/deploy-site.sh` · `app/auth/api-key-links.ts`

## 배경

`mapleroutine.store` 는 스토어와 AdMob 이 요구하는 문서를 올려 두는 정적 사이트다. 개인정보 처리방침
(`/privacy`)은 Play 와 App Store 모두에, 지원 URL(`/support`)은 App Store 에 등록되어 있다. `/app-ads.txt`
는 AdMob 이 이 도메인에서 읽어 간다. 이 셋이 열리지 않으면 스토어 등록정보나 광고 승인에 문제가 생긴다.

여기에 스토어가 요구하지 않는 페이지가 하나 더 있다. 넥슨 Open API 키 발급 가이드(`/api-key`)다. 이 앱을
쓰려면 사용자가 넥슨 Open API 사이트에서 키를 직접 받아 와야 하는데, 그 절차가 앱 밖에서 일곱 단계로
진행된다. 앱이 넥슨 사이트 링크만 주고 끝내면 사용자가 첫 화면에서 가장 많이 막힌다.

## 결정

### 결정 1. API 키 발급 가이드는 앱이 아니라 안내 사이트에 둔다

가이드는 `site/api-key.md` 이고 `mapleroutine.store/api-key` 로 열린다. 앱 안에 가이드 화면을 만들지 않은
이유는 셋이다.

- 스크린샷 일곱 장(약 1.2MB)을 앱 번들에 넣으면 모든 사용자가 받게 되는데, 실제로 보는 것은 처음 한 번뿐이다.
- 넥슨이 화면을 바꾸면 가이드도 고쳐야 한다. 사이트는 다시 올리면 바로 바뀌지만, 앱은 OTA 를 한 번 더 내야 한다.
- 사용자는 키를 받는 동안 어차피 브라우저에 있다.

### 결정 2. 앱의 키 입력 화면에는 가이드와 넥슨 사이트 링크를 둘 다 둔다

`API 키 발급 방법 보기` 는 가이드로, 입력 칸에 붙은 링크는 `openapi.nexon.com` 으로 연다. 처음 쓰는 사용자는
가이드를 따라가면 되고, 이미 키가 있는 사용자는 일곱 단계 안내를 거치지 않아도 된다. 개발 단계 키 안내
모달도 가이드를 연다.

두 주소는 `app/auth/api-key-links.ts` 에만 적고 폼과 모달이 함께 쓴다. 따로 적어 두면 사이트를 옮길 때 한쪽만
고쳐지고, 고쳐지지 않은 쪽은 키 때문에 막힌 사용자에게만 보이는 링크라 알아채기 어렵다.

설정 화면에는 가이드 링크를 두지 않는다. 설정에는 API 키를 다시 입력하는 화면이 없어서, 링크만 두면 따라가도
할 수 있는 일이 없다.

### 결정 3. 가이드는 서비스 단계 키를 받도록 안내한다

개발 단계 키는 초당 5건 · 하루 1,000건으로 제한된다. 이 앱은 여러 캐릭터를 한 번에 조회하므로 개발 단계
키로는 중간에 막힌다. 가이드의 단계 선택 항목에서 서비스 단계를 고르라고 적었다.

### 결정 4. 가이드 스크린샷은 저장소에 커밋한다

큰 원본 파일을 저장소에서 빼는 기준([[ADR-044]])은 크기가 아니라 다시 만들 수 있느냐였다. 이 일곱 장은
개인 넥슨 계정으로 들어가야 나오는 화면에 손으로 주석을 얹은 것이라 다시 만들 수 없다. 원본을 잃으면
가이드를 쓸 수 없게 되므로 `site/images/api-key/` 에 커밋한다.

### 결정 5. 사이트의 원본은 이 저장소에 둔다

`site/` 와 루트의 `PRIVACY.md` 가 원본이고, `scripts/build-site.mjs` 가 `dist-site/` 로 빌드한다. 서버 저장소로
옮기지 않는다. 정적 사이트는 서버 코드가 아니라 이 앱이 내놓는 문서이고, 서버는 그것을 내보내기만 한다.

개인정보 처리방침의 원본은 `PRIVACY.md` 하나다. 웹용 사본을 따로 두면 법적 문서가 두 개가 되어 내용이
어긋날 수 있으므로, 빌드할 때 이 파일을 렌더링한다. 페이지 제목과 설명은 프런트매터가 아니라 맨 위 HTML
주석에서 읽는다. `PRIVACY.md` 는 GitHub 에서도 그대로 읽히는 문서라, 렌더링되지 않는 `---` 블록이 맨 위에
보이면 안 되기 때문이다.

빌드 스크립트는 `site/` 에서 `.md` 와 `template.html` 만 빼고 나머지를 재귀로 복사한다. 그래서 `style.css`
· `app-ads.txt` · `images/` 같은 정적 파일은 스크립트를 고치지 않아도 함께 나간다.

### 결정 6. 정적 파일은 Oracle 의 nginx 가 디스크에서 바로 내보낸다

`/privacy` · `/support` · `/app-ads.txt` 는 앱 기능이 아니라 스토어 등록과 광고 승인에 필요한 주소다. 서버
앱이 멈추더라도 이 주소들은 열려야 하므로, 서버 앱을 거치지 않고 nginx 가 `/var/www/mapleroutine/` 의 파일을
바로 내보낸다.

### 결정 7. 배포는 사람이 손으로 한다

`npm run deploy:site`(`scripts/deploy-site.sh`)가 빌드하고, `rsync --delete` 로 Oracle 에 올린 뒤 다섯 경로의
응답 코드를 출력한다. `--delete` 를 쓰므로 지운 페이지가 서버에 남아 계속 열리는 일이 없다.

GitHub Actions 로 자동화하지 않는다. 자동화하려면 GitHub 에 Oracle 접속 키를 맡겨야 하는데, 그 키로는 정적
사이트뿐 아니라 서버 전체에 접속할 수 있다. 이 사이트는 처리방침을 고칠 때 정도만 바뀌어 1년에 몇 번이므로, 그
정도 빈도로는 키를 GitHub 에 계속 맡겨 둘 이유가 없다. 자주 바뀌게 되면 그때 CI 로 옮긴다.

빌드는 `CNAME` 과 `.nojekyll` 을 만들지 않는다. 둘 다 GitHub Pages 를 위한 파일이었고, 남겨 두면
`mapleroutine.store/CNAME` 처럼 아무 의미 없는 파일이 공개된다.

## 테스트

이 결정들을 확인하는 자동 테스트는 없다. 배포 스크립트가 끝에 다섯 경로(`/` · `/privacy` · `/support` ·
`/api-key` · `/app-ads.txt`)의 응답 코드를 출력하므로, 배포할 때마다 그 출력을 눈으로 확인한다.
