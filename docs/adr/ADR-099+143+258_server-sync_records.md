# ADR-099+143+258 사용자가 만든 기록은 서버에 두고 같은 사람의 기기끼리 맞춘다. 과거 드롭도 묶음으로 올린다

> ⚪ 미구현
> 관련 소스: `features/server-sync/*` · `storage/server-sync-sources.ts` · `storage/server-backfill.ts` · `server/write.ts` · 서버 `modules/users` · `modules/identity`

## 배경

> 사용자 지정(2026-09-19): 원본 데이터는 사용자 기기에 저장하지만, 변경되지 않는 총액과 2차 생산 목록 등은 서버에서
> 관리한다. 사용자 기기의 데이터를 완전히 옮기려는 게 아니다. 화면을 그리는 데이터는 남겨 둔다.

> 사용자 지정(2026-11-17): 모든 기기에서 동일한 데이터가 보일 것. 가계부에 방대한 강화 데이터는 결과 값만 정해진 데이터
> 스키마로 정제해서 새 기기에서도 이전 기간의 데이터를 굳이 다시 받지 않을 수 있도록 할 것. 사용자가 생산한 데이터는 모두
> 확인할 수 있도록 할 것. 서버의 제한된 리소스를 최소한으로 사용할 것.

서버로 올리는 이유는 둘이다. 여러 사용자의 기록으로 통계를 내는 것과, 같은 사람의 기기끼리 같은 기록을 보게 하는 것이다(#947).
드롭 가격의 전송 규칙은 [[ADR-018]] 에 있다.

지금까지 기록의 원본은 기기에만 있었다. 그래서 기기마다 기록이 따로 쌓였고, 기기를 잃으면 되살릴 수 없었다. 넥슨 스케줄러는 최근
13일만 주고, 강화 내역은 날마다 불러 18개월 치를 다시 받아야 한다.

보스 처치 · 가계부 기록 · 강화 합계는 한때 서버로 보냈다가 걷었다(#800). 서버가 기기가 만든 기록 id 로 줄을 가려, 같은 처치가 기기
수만큼 쌓였기 때문이다. 결정 8 이 넥슨이 준 값으로 줄을 가려 이 문제를 없앤 뒤 다시 보낸다([[ADR-101]] 결정 19 · 26).

지금 구현된 것은 결정 2 ~ 6 과, 결정 8 의 표 가운데 드롭 가격(`drop_prices`)을 올리는 것뿐이다. 결정 1 과 결정 7 ~ 17 은 구현 전이다.

## 결정

### 결정 1. 사용자가 만든 기록과 다시 받을 수 없는 기록은 서버에 두고, 같은 사람의 모든 기기가 같은 데이터를 본다 (사용자 지정 2026-11-10 · 11-17)

- 기기는 지금처럼 기기 저장소에 먼저 저장하고 화면도 기기 저장소에서 그린다. 저장한 뒤 서버로 올리고, 다른 기기는 서버에서 바뀐
  것만 받아 자기 저장소에 넣는다. 서버 저장이 끝나야 기록이 남는 방식으로 하면 오프라인에서 적을 수 없다.
- 넥슨에서 언제든 다시 받을 수 있는 값은 올리지 않는다. 쿼리 캐시 · 캐릭터 프로필 · 게임 데이터 사본이다.
- 넥슨에서 받았지만 시간이 지나면 다시 받을 수 없는 값은 올린다. 자동으로 적힌 보스 처치와 공유 컨텐츠 진행이다.
- 강화 합계도 올린다(사용자 지정 2026-11-17). 2026-11-10 에는 양이 많아 서버에 두지 않기로 했으나, 원본이 아니라 결과 값만 두는
  것으로 바꿨다(결정 11).
- 넥슨 로그인 사용자와 API 키 사용자 모두 올리고 받는다(사용자 지정 2026-11-10). 서버는 기록을 메이플 ID 와 ocid 로 묶어, 넥슨
  로그인으로 받든 API 키로 받든 같은 기록을 받는다.
- API 키 원문은 올리지 않는다(사용자 지정 2026-09-07). 부계정 키는 기기마다 새로 등록한다(사용자 지정 2026-11-17).
- 강화 합계에서 빠진 줄의 상황 알림([[ADR-102]])과 사용 로그([[ADR-158]])는 지금처럼 보낸다. 사용자에게 돌려주지 않는 운영 값이다.
- 동기화는 1.0.15 부터다. 1.0.15 를 배포하면 1.0.14 까지의 앱은 더 받지 않는다(결정 43).

### 결정 2. 드롭의 기준일을 걷고 과거 드롭도 올린다

처음에는 2026-10-15 이후 기간의 드롭만 보냈다(`SERVER_PRICE_FROM`). 이 기준을 걷고, 과거 드롭도 결정 3 의 묶음으로
올린다(사용자 선택). 드롭 시세 통계에 과거 판매가가 들어간다. 드롭 줄에는 어느 처치 기간의 드롭인지 기기 기간 행 id
(`periodRecordId`)를 싣는다. 서버 `drop_prices.period_record_id` 에는 외래키가 없어, 처치 기간을 서버로 보내지 않아도 받는다.

### 결정 3. 과거 드롭은 묶음 경로로 100 건씩 나눠 보낸다

업데이트 직후 사용자마다 천여 건이 한 건씩 나가면 서버 요청이 몰린다(사용자 선택 2026-10-26). 그래서 앱을 켤 때 보내지
않은 드롭을 `POST /v1/drop-prices/batch` 로 100 건씩 보낸다.

- 어디까지 보냈는지는 마지막으로 보낸 기록 id 를 Preferences `serverBackfill` 에 적는다. 앱이 중간에 꺼져도 다음 회차가 그
  뒤부터 잇는다. 100 건보다 적게 읽히면 끝으로 적고 다시 훑지 않는다.
- 한 묶음이 실패하면(응답 없음 · 거절) 그 회차를 멈추고 다음에 앱을 켤 때 같은 자리부터 다시 보낸다. 서버는 기록 id 로
  덮으므로 두 번 받아도 줄이 늘지 않는다.
- 서버는 건마다 결과를 돌려주고 받을 수 있는 건은 받는다. 통째로 거절하면 앱이 같은 묶음을 계속 다시 보내 그 사용자의 과거
  올리기가 멈추기 때문이다. 받지 못한 건만 평소 대기 표에 넣어 한 건씩 다섯 번 다시 보낸다(사용자 선택).
- 평소 저장은 지금처럼 한 건씩 보낸다([[ADR-018]] 결정 4). 과거를 보내는 동안 고친 드롭은 한 건 전송이 따로 덮는다.

### 결정 4. 대기 표 전송은 한 번에 한 회차만 돈다

전송을 깨우는 `kick.ts` 는 도는 중에 다시 깨우면 끝난 뒤 한 번 더 돈다. 두 회차가 겹치면 같은 줄을 두 번 보낸다.

### 결정 5. 서버는 사람과 넥슨 계정을 나눈다

다계정([[ADR-101]])을 위해 나눴다(사용자 선택 2026-10-26). 옛 `users` 는 한 줄에 `nexon_uid` 나 `api_key_hash` 하나를 둬서,
한 사람이 넥슨 계정을 여럿 가질 수 없었다.

- `users` 는 사람이다. `nexon_accounts` 의 한 줄이 넥슨 ID 하나이고, 칸은 `user_id` · 넥슨 로그인으로 확인한 `nexon_uid` ·
  기기가 만든 계정 id 다. API 키는 `nexon_account_keys`, 메이플 ID 는 `nexon_account_maple_ids` 가 든다([[ADR-101]] 결정 25).
- 로그인 방식과 상관없이 모든 계정의 기록을 보낸다(사용자 지정). 부계정의 기록을 어느 행에 붙이고 메인 계정과 어떻게 잇는지는
  [[ADR-101]] 결정 7 에 있다. 부계정 등록은 [[ADR-101]] 결정 14 대로 서버 전송 회차가 한다.

```
users                     id · deletion_requested_at · created_at
nexon_accounts            id · user_id · nexon_uid UNIQUE · referral_code UNIQUE · created_at · updated_at
nexon_account_keys        id · nexon_account_id · api_key_hash UNIQUE
nexon_account_maple_ids   id · nexon_account_id · maple_id UNIQUE
```

### 결정 6. 쓰기 요청에는 신원 헤더만 싣는다

기기가 만든 넥슨 계정 id 헤더(`x-nexon-account-id`)는 싣지 않는다. 기기마다 다른 값이라 서버가 [[ADR-101]] 결정 21 부터 읽지 않고,
기록은 실어 온 메이플 ID 로 넥슨 계정을 찾는다. 어느 계정의 신원으로 보내는지는 [[ADR-101]] 결정 7 에 있다.

### 결정 7. 동기화는 지금 서버에 받기 · 올리기 경로를 더해서 하고, 전용 동기화 서비스는 올리지 않는다 (사용자 선택 2026-11-17)

2026-11-17 운영 실측이다.

| 항목 | 값 |
|---|---|
| 앱 박스 | CPU 2 · RAM 952MB(쓸 수 있는 메모리 297MB, 스왑 526MB 사용 중) · 디스크 45G 중 14G 사용 |
| 서버 컨테이너 | 114MB |
| DB | 38MB · 연결 상한 20 · `shared_buffers` 32MB |
| DB 박스 | CPU 2 · RAM 954MB(쓸 수 있는 메모리 540MB, 스왑 2G 중 34MB 사용) · 디스크 45G 중 4.6G 사용 · 부하 평균 0.00 |
| 사람 | `users` 1,141줄(넥슨 로그인 770) · 7일 방문 979명 |

- 서버(NestJS · PostgreSQL)에 경로를 더하고, 기기는 지금 있는 대기 표(`server_sync_queue`)와 SQLite 를 그대로 쓴다. 새 서비스가 없어
  메모리가 거의 늘지 않는다.
- PowerSync 를 직접 운영하려면 복제 컨테이너 1GB 와 API 컨테이너 1GB, 묶음 저장용 DB 가 더 필요하다(공식 권장 사양). 앱 박스에 남은
  메모리로는 올릴 수 없다. ElectricSQL 은 동기화 서비스가 하나 늘고 PostgreSQL 논리 복제를 켜야 하며, 받기만 맡아 올리기는 직접
  만들어야 한다. PowerSync 클라우드는 사용자 기록이 외부 업체를 거친다. 그래서 셋 다 고르지 않았다.
- 실시간으로 밀어 주지 않는다. 기기가 정해진 때에 받아 간다(결정 9). 연결을 열어 두면 접속한 기기 수만큼 서버 메모리와 연결을 쥔다.
- 자원이 모자랄 것 같으면 결정을 폐기하지 않고 사용자와 상의한다(사용자 지정 2026-11-17). 상의할 기준은 결정 17 에 있다.

### 결정 8. 서버 표는 모두 칸이 정해진 표이고, 줄은 넥슨이 준 값으로 가린다 (사용자 선택 2026-11-17)

- 기록을 JSON 한 칸에 담지 않는다. 큰 기록과 작은 기록 모두 칸이 정해진 표로 둔다. 서버가 모든 값을 검사할 수 있고 통계에도 쓸 수 있다.
  대신 기기 표의 칸이 바뀌면 서버 이관과 배포가 함께 나간다.
- 줄의 유일 기준은 넥슨이 준 값(메이플 ID · ocid)과 기록 내용이다([[ADR-101]] 결정 19). 기기가 만든 id 만으로 가리지 않는다.
  식별자는 해시로 둔다(결정 12).
- 기기 줄에 id 가 있는 기록은 그 id 를 서버 줄의 `id` 로 그대로 쓴다(사용자 선택 2026-11-18). 서버가 따로 만든 id 와 기기 id
  (`period_record_id` · `drop_record_id` · `entry_record_id` · `total_record_id`)를 두 칸으로 두지 않는다. 같은 줄이 기기와 서버에서
  같은 id 를 갖고, 표끼리 가리킬 때도 그 값을 쓴다. 기기의 기록 id 는 모두 uuid 다. 아래에서 `기록 id` 는 이 `id` 를 말한다.
  - 남의 줄을 덮는 요청은 쓸 때 하는 주인 검사로 막는다. 같은 id 의 줄이 이미 있는데 그 줄의 주인이 요청한 사람이 아니면 적지
    않는다. 남의 id 로 보내면 자기 줄이 하나 생기던 방식([[ADR-018]])을 이것으로 바꾼다. 그 방식에서는 사람 줄이 바뀐 사람이
    같은 기록을 다시 올리면 줄이 하나 더 생겼다.
  - 기기 줄에 id 가 없는 기록(Preferences 의 설정과, 목록에서 풀어 낸 줄)과 `characters` 는 서버가 id 를 만든다. 기기는 그 줄을
    유일 기준의 값으로 가리킨다.
  - 드롭 판매가 표(`drop_sale_prices`, 지금의 `drop_prices`, 결정 26 · 29)도 합친다. 줄의 id 는 그 판매가가 나온 드롭의 id 다. 판매가 줄은
    서버가 드롭 기록을 받을 때 적는다(결정 26). 옛 DB 에서 옮겨 온 줄 가운데 같은 id 의 줄이 이미 있으면 셋으로 가른다. 줄의
    사람(`user_id`)이 요청한 사람이면 덮는다. 줄에 사람이 없으면(계정을 삭제해 비운 줄) 요청한 사람을 채운다. 기기가 만든 uuid 는
    그 기기만 알아서, 같은 id 를 든 요청은 같은 기록이다. 다른 사람의 줄이면 적지 않는다.
  - 2026-11-18 운영의 `drop_prices` 5,536줄 가운데 기기 id 가 같은 줄이 4쌍 있다. 모두 같은 드롭이 사람 줄 둘에 한 번씩 올라온
    것이다. 아이템 · 가격 · 기간이 같고, 뒤의 넷은 2026-11-08 하루에 올라왔다. 합치는 이관에서 쌍마다 나중에 올라온 줄을 남긴다.
  - 드롭 기록(`boss_drops`)은 수익 건을 참조로 가리킨다(결정 26). 드롭 판매가 표의 `period_record_id` 는 읽는 곳이 없어
    없앤다(결정 27).
- 기록마다 주인이 있다. 주인은 캐릭터(`characters` 표의 줄, 결정 20), 메이플 ID, 사람 가운데 하나다. 사람의 것은 그 사람의 메인 넥슨 계정
  줄(`nexon_accounts`)에 붙인다. 넥슨 계정 줄은 넥슨 ID 하나에 하나라서([[ADR-101]] 결정 25) 기기가 바뀌어도 같은 줄이다.
- 캐릭터 이름은 서버에 두지 않는다(사용자 지정 2026-11-10). 이름은 기기가 자기 캐릭터 목록에서 붙인다.
- 기록 표에 `identified_by` 칸을 두지 않는다(사용자 지정 2026-11-18). 올린 요청이 로그인이었는지 API 키였는지는 기록의 값이
  아니라 사람의 값이다. 넥슨 계정 줄의 `nexon_uid` 가 있으면 로그인한 사람이므로 거기서 읽는다. `boss_clears` · `drop_prices` ·
  `cashbook_entries` · `enhancement_totals` 에서 이 칸을 뺀다. 동기화와 상관없는 `usage_events` · `enhancement_anomalies` 에서도
  같은 이유로 뺀다(사용자 지정). 그러면 이 칸은 서버 어느 표에도 남지 않는다. 쓰는 칸이 없어진 enum `identity_source` 도 지운다.
- 이 칸을 읽는 곳은 둘이고 둘 다 넥슨 계정 줄에서 읽도록 고친다. 관리 화면의 드롭 가격 목록은 줄마다 로그인 · API 키를 보인다.
  계정을 삭제한 사람의 드롭 줄은 계정 줄이 없어 그 표시가 빈다. 사용 로그의 구성([[ADR-158]])은 지금 그 사람이 마지막으로 보낸
  사건의 값으로 나누는데, 그 사람에게 로그인한 넥슨 계정 줄이 있는지로 나누게 된다. 로그인한 적이 있는 사람이 키만 넣은 기기를
  쓰는 동안에도 로그인으로 센다.

기기 저장소와 서버 표의 짝이다. `고침` 은 지금 서버에 있는 표를 바꾸는 것이고, `새 표` 는 지금 서버에 없는 표다. 새 DB 에는 모든 표를

### 결정 9. 받기는 메이플 ID 마다 변경 번호를 기억해 그 뒤에 바뀐 줄만 받는다

- 결정 8 의 모든 서버 표에 변경 번호 칸(`change_seq`)을 둔다. 줄을 만들거나 고치거나 지울 때마다 서버 전체에서 하나인 순번의 다음
  값을 적는다.
- 기기는 주인(메이플 ID, 사람)마다 마지막으로 받은 변경 번호를 기억한다. 받을 때 그 번호들을 보내고, 서버는 주인마다 그보다 큰 번호의
  줄을 번호 차례로 돌려준다. 처음 받는 기기는 번호 0 을 보내 전부 받는다.
- 번호를 사람 하나가 아니라 주인마다 기억하는 이유는, 부계정을 새로 등록하면 그 메이플 ID 의 옛 줄이 한꺼번에 이 사람의 것이 되기
  때문이다. 사람 하나의 번호로 기억하면 그 옛 줄은 번호가 작아 영영 받지 못한다. 서버는 응답에 이 사람의 메이플 ID 해시 목록을 싣고,
  기기는 처음 보는 메이플 ID 를 0 부터 받는다.
- 서버는 한 주인의 쓰기를 한 번에 하나씩 처리한다(주인마다 advisory lock). 기록은 메이플 ID 가 주인이라, 로그인의 기기와 그
  계정의 키만 쓰는 기기가 같은 메이플 ID 에 쓰면 같은 잠금을 기다린다. 순번은 번호를 받은 차례와 커밋 차례가 다를 수 있어서, 잠그지
  않으면 받기가 지나간 뒤에 더 작은 번호의 줄이 나타나 그 줄을 놓친다.
- 지운 줄은 바로 지우지 않고 삭제 표식(`deleted_at`)을 적어 다른 기기가 받아 가게 한다. 표식이 선 줄은 180일 뒤 지운다(사용자 확인 2026-11-17). 180일 넘게
  받지 않은 기기는 서버가 알려 주는 가장 오래된 표식의 번호보다 자기 번호가 작으므로, 그 주인의 기록을 비우고 0 부터 다시 받는다.
- 받기는 스케줄 회차에 붙인다(사용자 지정 2026-11-17). 회차가 넥슨에서 실제로 받을 때마다 서버 기록도 함께 받는다. 회차가 도는
  때는 [[ADR-142]] 결정 5 의 넷이다. 앱을 켤 때, 백그라운드에서 돌아올 때, 신선한 시간이 지난 뒤 화면을 볼 때, 당겨서 새로고침할
  때다. 받는 때를 따로 두면 새로고침 한 번에 넥슨 데이터만 최신이 되고 다른 기기의 기록은 옛 것으로 남는다.
- 회차의 신선한 시간(`SYNC_TTL_MS`)을 10분에서 5분으로 줄인다(사용자 지정 2026-11-17). 켜 놓고 쓰는 두 기기가 어긋나 있는 시간이
  그만큼 줄어든다. [[ADR-142]] 결정 4 와 [[ADR-021]] 결정 6 의 10분은 값을 바꾸는 작업에서 함께 고친다.
- 올리기가 끝난 직후에도 받는다. 서버가 기록 id 를 바꿔 주거나 올린 줄을 거절할 수 있어서다(결정 10).
- 한 번에 받는 줄 수에 상한을 두고, 더 있으면 이어서 받는다. 응답은 gzip 으로 보낸다.
- 받은 줄을 기기 저장소에 넣은 뒤 그 표를 읽는 쿼리를 무효로 해 화면이 다시 그린다. 받은 줄은 대기 표에 넣지 않는다. 넣으면 받은 줄을
  다시 올린다.

### 결정 10. 올리기는 대기 표로 하고, 같은 기록을 고치면 나중에 도착한 쪽을 남기며, 함께 있을 수 없는 입력과 지운 기록의 수정은 거절한다 (사용자 선택 · 지정 2026-11-17)

- 기기는 저장한 기록의 id 를 대기 표에 넣고, 전송이 그 기록의 지금 값을 읽어 보낸다. 원본이 없으면 지우기를 보낸다. 드롭 가격이
  지금 쓰는 방식이고([[ADR-018]] 결정 4), 종류만 늘린다(`registry.ts`).
- 올리기는 종류를 섞어 한 요청에 묶는다. 기록마다 요청을 보내면 요청 수가 기록 수만큼 늘어 nginx 의 속도 제한(초당 10건)에 걸린다.
- 서버는 받은 값으로 줄을 덮는다. 고친 시각을 견주지 않는다. 기기 시계는 틀릴 수 있어서, 시각이 늦은 쪽을 남기면 시계가 앞선 기기의
  값이 계속 이긴다. 그래서 오프라인에서 고친 옛 값이 뒤늦게 올라오면 새 값을 덮는다. 2026-11-10 운영에서 두 기기를 같은 기간에 쓴
  사람은 넥슨 로그인 사용자 416명 가운데 1명이었다.
- 나중에 도착한 쪽을 남기는 것은 기록 id 가 같은 줄을 고칠 때다. 같은 기록을 두 기기가 고친 것이기 때문이다.
- 함께 있을 수 없는 기록이 들어오면 서버가 거절한다(사용자 지정 2026-11-17). 유일 기준(결정 8)이 같은 줄이 다른 기록 id 로 이미
  있는데 내용이 다른 경우다. 한 캐릭터가 같은 기간에 같은 보스를 다른 난이도로 적은 것, 같은 메이플 ID 가 한 주에 같은 에픽 던전을
  한 번 더 적은 것이 그렇다. 서버는 그 줄을 적지 않고 `duplicate_record` 로 답한다(결정 18). 먼저 도착한 줄이 남는다.
  - 기기는 먼저 저장하고 올리므로([[ADR-018]] 결정 4), 거절을 받으면 자기 줄을 지우고 받기를 해 서버의 줄을 넣는다. 그리고 입력이
    막혔다고 알린다. 알리는 문구는 구현 전에 사용자에게 받는다. 네트워크가 되면 입력 직후에 올리므로 거절도 곧바로 온다.
  - 유일 기준이 같고 내용도 같으면 거절하지 않는다. 서버는 먼저 있던 줄을 그대로 두고 받은 것으로 답한다. 넥슨이 준 처치를 두
    기기가 각자 동기화한 경우가 그렇다. 나중에 보낸 기기는 다음 받기에서 그 줄을 유일 기준으로 찾아 자기 기록 id 를 서버의 것으로
    바꾼다. 그 기록을 가리키는 줄(기간 행의 드롭)도 함께 바꾼다. 표마다 어느 칸을 내용으로 견주는지는 구현 때 결정 8 의 표에 적는다.
  - 유일 기준이 없는 기록(손으로 적은 가계부 · 파티 약속 · 계산기 기록)은 거절하지 않는다. 같은 내용이 두 번 있어도 맞는 기록이다(결정 13).
- 다른 기기가 지운 기록을 고쳐 올리면 서버가 거절한다(사용자 지정 2026-11-17). 삭제 표식이 선 줄에 수정이 오면 적지 않고
  `record_deleted` 로 답한다. 기기는 그 줄을 지우고, 수정할 수 없는 기록이라고 알린다. 문구는 구현 전에 사용자에게 받는다.
- 기록의 메이플 ID 가 보낸 신원의 것이 아니면 적지 않고 실패로 답한다([[ADR-101]] 결정 25).
- 못 보냈을 때의 규칙은 지금과 같다. 응답이 없으면 줄을 두고, 거절이면 횟수를 세어 다섯 번째에 버린다. `duplicate_record` 와
  `record_deleted` 는 다시 보내도 같은 답이라 처음 받았을 때 대기 표에서 뺀다.

### 결정 11. 강화는 날짜 · 캐릭터 · 분류 · 장비마다의 합계와 굳은 날만 서버에 두고, 새 기기는 굳은 날을 넥슨에서 다시 받지 않는다 (사용자 지정 2026-11-17)

- 강화 내역의 응답 원본은 기기에도 서버에도 두지 않는다. 기기의 `enhancement_totals` 한 줄이 날짜 · 캐릭터 · 분류 · 장비 하나의 합계이고
  ([[ADR-100]]), 서버 `enhancement_totals` 가 같은 유일 기준으로 그 줄을 든다. 장비는 넥슨이 준 이름으로 가린다(결정 37).
- 서버 표에 기기 표의 칸을 더한다. 받은 API 종류(`api_type`, 결정 32) · 월드 · 슈페리얼 비용 · 스타포스의 처음 성과 끝 성 · 이벤트 월드
  판정이다. 지금 서버 표는 이벤트 월드가 아닌 줄만 받는데, 기기끼리 맞추려면 모든 줄이 있어야 한다. 가계부 제외 표식([[ADR-160]])을
  구현할 때 그 칸도 이 표에 더한다. 빼면 다른 기기에서 뺀 강화 비용이 다시 지출로 잡힌다. [[ADR-160]] 의 `서버에는 보내지 않는다` 는
  이것으로 바뀐다(사용자 확인 2026-11-17).
- 금액은 올린 기기가 그때의 비용표로 매긴 값이다. 받은 기기는 다시 매기지 않는다. MVP 할인은 지금처럼 화면에 보일 때 붙인다.
- 어느 날을 다 받았는지도 서버에 둔다(`enhancement_settled_days`). 메이플 ID · 종류 · 날짜가 한 줄이다. 기기의
  `enhancement_history_checks` 에서 굳은 날(`settled`)만 올린다. 이것이 없으면 합계 줄이 없는 날이 강화를 안 한 날인지 아직 안 받은
  날인지 가릴 수 없어, 새 기기가 18개월 치를 다시 부른다.
  - 넥슨은 강화 내역을 넥슨 계정 단위로 준다. 그래서 굳은 날은 그 계정의 메이플 ID 마다 한 줄씩 적는다.
- 새 기기는 서버에서 받은 굳은 날을 자기 `enhancement_history_checks` 에 굳은 날로 적고, 그 날은 넥슨을 부르지 않는다. 굳지 않은
  날(오늘과 어제, 아무 기기도 받지 않은 날)만 넥슨에서 받는다.
- 다시 매기기([[ADR-100]])로 한 기기가 지난 날의 금액을 고치면 그 줄을 다시 올리고, 다른 기기는 받아서 덮는다. 다른 기기가 같은 요청을
  따로 돌려도 유일 기준이 같아 줄이 늘지 않는다.

### 결정 12. 식별자는 해시로 올리고, 받은 기기는 자기 캐릭터 목록을 해시해 원문으로 바꾼다

- ocid 와 메이플 ID 는 기기가 SHA-256 해시로 바꿔 보낸다. 서버에는 넥슨 식별자의 원문을 두지 않는다([[ADR-017]] 결정 11). 기록 안에서
  다른 캐릭터를 가리키는 칸(이전 기록의 받는 캐릭터, 조각을 가져온 캐릭터, 리프의 옛 ocid 와 새 ocid)도 해시로 보낸다.
- 받은 기기는 넥슨에서 받은 자기 캐릭터 목록의 ocid 와 메이플 ID 를 해시해 서버 기록과 짝을 맞추고, 원문으로 바꿔 저장한다.
- 짝이 없는 기록도 받는다(사용자 지정 2026-11-10). 지운 캐릭터, 이 기기에 키가 없는 부계정의 캐릭터가 그렇다. 금액에 넣고 캐릭터는
  알 수 없는 캐릭터로 보인다. 나중에 그 캐릭터가 목록에 나타나면(부계정 키를 등록하면) 원문으로 바꾼다.
- 같은 캐릭터의 ocid 는 기기나 키가 달라도 같다고 본다(사용자 판단 2026-11-10).

### 결정 13. 업데이트 전에 기기에 쌓인 기록은 처음 한 번 묶음으로 올리고, 겹치는 줄은 결정 8 의 유일 기준으로 합친다

- 1.0.15 로 올린 기기는 받기를 먼저 하고, 그 뒤 기기에만 있는 기록을 묶음으로 올린다. 과거 드롭을 올리는 방식(결정 3)을 다른 종류에도
  쓴다. 어디까지 올렸는지 종류마다 기기에 적어, 앱이 꺼져도 이어서 올린다.
- 받기를 먼저 하는 이유는 기록 id 다. 다른 기기가 먼저 올린 줄을 받아 유일 기준이 같은 자기 줄의 id 를 서버 것으로 바꾼 뒤에 올려야,
  드롭처럼 다른 줄을 가리키는 기록이 올바른 줄에 붙는다.
- 두 기기에 따로 쌓인 보스 처치 · 드롭 · 강화 합계 · 파티 설정은 유일 기준이 같아 한 줄로 합쳐진다. 내용이 다르면 먼저 올린 기기의
  줄이 남고, 나중에 올린 기기는 거절을 받아 자기 줄을 서버의 줄로 바꾼다(결정 10).
- 손으로 적은 가계부 기록은 합치지 않고 둘 다 남긴다(사용자 선택 2026-11-17). 같은 날 같은 물건을 두 번 산 기록도 맞는 기록이라
  내용으로 가릴 수 없다([[ADR-101]] 결정 19). 두 기기에 같은 지출을 각각 적은 사람은 두 줄을 보게 되고 직접 하나를 지운다.
- 파티 약속과 계산기 기록도 손으로 적는 기록이라 둘 다 남긴다.
- 메이플 ID 를 모르는 기록은 올리지 않는다. 주인을 모르는 옛 가계부 기록은 이미 대표 캐릭터에 붙였고([[ADR-101]] 결정 28), 캐릭터
  목록에서 본 적이 없는 캐릭터의 기록만 남는다. 그 캐릭터가 목록에 나타나면 올린다.

### 결정 14. 기기에는 지금 로그인한 사람의 기록만 둔다 (사용자 선택 2026-11-17)

- 같은 기기에서 다른 넥슨 ID 나 다른 API 키로 로그인하면, 앞 사람의 기록 가운데 아직 올리지 못한 것을 먼저 올린 뒤 기기에서 비운다.
  그 뒤 새로 로그인한 사람의 기록을 서버에서 받는다. 앞 사람으로 다시 로그인하면 서버에서 받아 그대로 보인다.
- 앞 사람의 기록을 남기면 그 기기만 다른 기기와 다른 데이터를 본다. 지금은 남아서 가계부 · 통계에 함께 잡힌다. [[ADR-101]] 결정 12 의
  그 문장을 이것으로 바꾼다.
- 올리지 못한 기록이 남아 있으면(오프라인, 서버 응답 없음) 사용자에게 묻는다(사용자 선택 2026-11-17). 그 기록을 `동기화하지 못한
  기록` 이라 부르고, 버리고 로그인할지 그만둘지 고르게 한다. 버리기를 고르면 비우고 로그인을 끝낸다. 묻는 모달의 문구는 구현 전에
  사용자에게 받는다.
- 로그아웃만 한 기기는 기록을 비우지 않는다. 같은 사람이 다시 로그인하는 일이 더 흔하고, 비우는 것은 다른 사람으로 로그인할 때로 충분하다.
- 같은 사람인지는 서버가 답한다. 로그인 뒤 첫 받기의 응답에 든 메이플 ID 해시 목록과 기기 기록의 메이플 ID 를 견준다.
- `today` 의 `넥슨 ID 연동하기` 는 같은 사람이 로그인을 붙이는 것이라 비우지 않는다([[ADR-101]] 결정 14).

### 결정 15. 설정은 앱 설정과 마지막 입력 기억을 빼고 모두 맞춘다 (사용자 지정 2026-11-17)

> 사용자 지정(2026-11-17): 글자 크기, 테마 같은 앱 설정, 마지막 기록을 제외한 나머지 항목을 모두 동기화. 단 부계정 키는 새로 등록해야됨

| 묶음 | Preferences 키 | 맞추나 |
|---|---|---|
| 추적 | `trackedCharacters` · `representativeCharacter` · `trackingMode` · `manualTrackedContent:{ocid}` | 맞춘다 |
| 이름 · 화면 구성 | `mapleIdNames` · `quickLinks` · `barOrder` · `figureMotions` · `statsCumulativeStart` | 맞춘다 |
| MVP 등급 확인 | `mvpWeeklyCheckOff` · `mvpLastCheckedWeek` · `mvpBulkApplyAsked` | 맞춘다 |
| 앱 설정 | `theme` · `textSize` · `dropEffect` · `overFrame` · `noticeSubscriptions` · `partyAlarmEnabled` · `scheduleAlertEnabled` · `keyboardHeight` | 맞추지 않는다 |
| 마지막 입력 기억 | `lastPointRate` · `lastHunts` · `hexaStorageChecks` · `lastBossIncomeTransfers` · `lastEpicDungeonRewards` · `lastSelectedCharacter` · `mesoUnits` · `partyScheduleView` · `todaySharedMapleId` | 맞추지 않는다 |
| 닫은 안내 | `dismissedNotices` · `dismissedSettlement` · `dismissedManualCompletion` | 맞추지 않는다 |
| 인증 | `authMethods` | 맞추지 않는다. 키와 세션은 기기에만 둔다 |

- `mesoUnits` · `partyScheduleView` · `todaySharedMapleId` 는 마지막에 고른 값을 기억하는 키라 마지막 입력 기억으로 넣었다. 닫은 안내는
  기기에서 본 사실이라 뺐다(사용자 확인 2026-11-17).
- 추적 캐릭터를 받은 기기에 그 캐릭터를 부를 키가 없으면(부계정 키를 등록하지 않은 기기) 그 캐릭터는 목록에 넣지 않고 서버 값은 그대로
  둔다. 키를 등록하면 목록에 나타난다. 빼고 올리면 다른 기기의 추적 목록에서도 사라진다.
- 로그인하면 추적 목록을 비우는 규칙([[ADR-101]] 결정 14)은 그대로다. 비운 뒤 서버에서 그 사람의 추적 목록을 받아 채운다. 서버에
  목록이 없을 때만 캐릭터 설정으로 간다.

### 결정 16. 지우기는 모든 기기에서 지워지고, 계정을 삭제하면 서버의 기록도 지운다

- 기록 하나를 지우면 서버 줄에 삭제 표식이 서고 다른 기기에서도 지워진다(결정 9).
- 데이터 삭제 화면에서 기록 묶음을 지우면 서버에서도 지운다. 기기에서만 지우면 다음 받기가 서버의 기록을 다시 넣는다. 지금은 서버
  사본을 지우지 않는다([[ADR-053]] 결정 6). 그 결정을 이것으로 바꾼다(사용자 확인 2026-11-17). 캐시처럼 서버에 올리지 않는 묶음은 지금처럼 기기에서만 지운다.
- 계정 삭제는 지금처럼 30일 유예 뒤 메이플 ID 줄과 함께 기록을 지운다([[ADR-017]] 결정 6). 새 표도 같다. 사람에 붙는 표는 넥슨 계정
  줄과 함께 지운다. 드롭 가격만 사람과의 연결을 끊고 남긴다.
- 개인정보 처리방침에 서버가 보관하는 항목이 늘어난 것을 적는다. 출시 전에 고친다.

### 결정 17. 서버 자원을 아끼는 규칙과 상의할 기준

- 받기와 올리기는 묶음이다. 앱을 한 번 켤 때 받기 한 번, 올릴 것이 있으면 올리기 한 번이 기본이다.
- 받기는 바뀐 것이 없으면 줄 없이 번호만 돌려준다. 서버는 주인 · 변경 번호 인덱스 하나로 답한다.
- 강화 합계가 가장 크다. 많이 쓰는 기기의 18개월 치가 약 950줄이었다(2026-11-10 실기기 이관). 모든 사람이 그만큼이면 100만 줄이고
  인덱스를 포함해 200~300MB 로 어림한다. 지금 DB 는 38MB 다.
- 처음 올리기(결정 13)는 출시 직후 모든 기기가 한꺼번에 한다. 묶음 크기와 묶음 사이 간격으로 서버 부하를 나눈다.
- 아래 가운데 하나라도 해당하면 구현을 멈추지 않고 사용자와 상의한다.
  - DB 박스의 디스크나 메모리가 위 어림을 감당하지 못한다. 2026-11-17 실측(결정 7)으로는 감당한다. 디스크는 40G 가 비어 있어
    300MB 가 1% 에 못 미친다. 강화 합계 표는 `shared_buffers` 32MB 보다 크지만, 받기는 주인 · 변경 번호 인덱스로 그 사람의 줄만
    읽고 나머지는 운영체제 캐시(쓸 수 있는 메모리 540MB)가 받는다. DB 박스의 쓸 수 있는 메모리가 200MB 아래로 내려가거나 스왑을
    500MB 넘게 쓰면 상의한다.
  - 앱 박스의 쓸 수 있는 메모리가 200MB 아래로 내려간다.
  - DB 연결 상한 20 에 닿는다.

### 결정 18. 서버의 거절은 정해진 코드로 답하고, 코드는 한곳에 모은다 (사용자 지정 2026-11-17)

- 서버가 요청을 받아들이지 않을 때는 HTTP 상태와 함께 `code` 를 준다. 앱은 문구가 아니라 `code` 로 가른다. 코드는 영어 소문자와
  밑줄로 쓰고, 서버 `src/common/error-codes.ts` 한 파일에 모은다. 앱은 `src/server/` 에 같은 목록을 둔다.
- 묶음 올리기는 기록마다 결과를 따로 답한다. 한 줄이 거절돼도 나머지는 적는다. 요청 전체가 거절되는 경우(신원 · 형식)만 HTTP
  상태로 답한다.

  | 코드 | HTTP | 뜻 |
  |---|---|---|
  | `login_required` | 403 | 넥슨 로그인 세션으로만 부를 수 있는 경로다 |
  | `account_deletion_pending` | 403 | 계정 삭제를 예약한 사람이다([[ADR-017]] 결정 6) |
  | `maple_id_not_registered` | 409 | 기록의 메이플 ID 가 보낸 신원의 것이 아니다([[ADR-101]] 결정 25) |
  | `same_account` | 409 | 자기 넥슨 ID 를 부계정으로 등록하려 했다([[ADR-101]] 결정 6) |
  | `registered_elsewhere` | 409 | 다른 넥슨 ID 에 등록된 부계정이다 |
  | `has_sub_accounts` · `login_is_sub_account` | 409 | 부계정을 가진 계정을 등록하거나, 부계정인 로그인이 등록하려 했다 |
  | `duplicate_record` | 기록마다 | 함께 있을 수 없는 기록이 이미 있다(결정 10) |
  | `record_deleted` | 기록마다 | 이미 지운 기록을 고치려 했다(결정 10) |

- 새 거절을 만들면 이 표와 코드 파일에 먼저 더한다. 코드를 문자열로 흩어 쓰면 앱과 서버가 다른 글자를 쓰게 된다.

### 결정 19. 보스와 난이도는 서버 표의 줄 id 로 가리키고, 기기 표도 1.0.15 에서 같은 id 로 바꾼다 (사용자 지정 2026-11-18)

- 기록은 보스의 난이도를 `boss_difficulties.id` 한 칸으로 가리킨다. 난이도와 상관없이 보스만 가리킬 때는 `bosses.id` 를 쓴다.
  `boss_key` 와 `difficulty` 글자 칸은 기록 표에 두지 않는다. 글자 두 칸이면 표마다 그 조합이 실제로 있는 난이도인지 따로 검사해야
  하는데, 줄 id 는 참조만 걸면 없는 조합이 들어올 수 없다.
- 주간 · 월간(`cycle`)은 보스가 아니라 난이도의 값으로 둔다(사용자 지정 2026-11-18). 같은 보스라도 난이도에 따라 주기가 다를 수
  있기 때문이다. `bosses.cycle` 을 `boss_difficulties.cycle` 로 옮기고 보스 표에서는 뺀다. 2026-11-18 운영의 보스는 모두 난이도마다
  주기가 같으므로, 이관은 보스의 값을 그 보스의 난이도 줄마다 그대로 적는다. 게임 데이터도 난이도마다 `cycle` 을 내고, 앱은 보스가
  아니라 난이도에서 주기를 읽는다.
- 같은 보스라도 주기가 다른 난이도는 한 캐릭터가 둘 다 잡을 수 있다(사용자 확인 2026-11-18). 기간 값(`period_code`, 결정 24)의
  첫 글자가 주기라서, 주기가 다른 처치는 기간 값이 달라 서로 겹치지 않는다. `boss_profit_entries`(지금의 `boss_clears`, 결정 23)의
  유일 기준은 둘이다.
  - 모든 줄은 캐릭터 · 난이도 · 기간으로 가린다. 기기 `boss_party_periods` 의 `UNIQUE (party_id, period_key)` 와 같다.
  - 처치한 줄(`clear_recorded_by` 가 찬 줄, 결정 27)은 캐릭터 · 보스 · 기간으로도 가린다. 같은 기간에 같은 보스를 난이도만 다르게 잡은
    처치가 올라오면 `duplicate_record` 로 거절한다(결정 10).
  - 둘째 기준을 처치한 줄에만 거는 것은 기기에 같은 보스의 처치 전 기간 행(기기의 지금 값은 `open`)이 다른 난이도로 함께 있을 수 있어서다. 하드로
    잡을 생각에 그 주만 파티 인원을 고쳐 두고 실제로는 노말을 잡으면, 하드의 처치 전 행과 노말의 처치 행이 둘 다 남는다. 모든
    줄에 걸면 둘 가운데 나중에 올린 줄이 거절된다.
- `boss_profit_entries` 의 `boss_id` 는 기기가 보내는 값이 아니다. 서버가 난이도 줄에서 채운다. 난이도 줄을 따라가면 알 수
  있는 값이지만, DB 의 유일 기준은 다른 표의 값을 볼 수 없어서 줄 안에 둔다(사용자 선택 2026-11-18). 코드로만 검사하면 메이플 ID
  잠금을 거치지 않는 쓰기가 하나라도 생겼을 때 같은 처치가 두 줄 들어간다. 난이도 줄과 어긋난 값이 들어가지 못하게
  `boss_difficulty_id` 와 `boss_id` 를 묶어 `boss_difficulties` 를 참조한다.
- 그 기간의 월드는 지금 있는 `world_id` 한 칸에 둔다. 글자 칸을 따로 더하지 않는다.
- 주기의 값은 `weekly` 와 `monthly` 둘이다. 지금 있는 값 `event_weekly` 는 주기가 아니라 시즌 보스라는 표시라서 주기에서 떼어
  `bosses.is_season_boss` 칸으로 옮긴다(사용자 선택 2026-11-18). 앱도 이 값으로 시즌 보스인지만 판정하고 주기는 주간으로
  다룬다(`lib/boss/bosses.ts`). 시즌 보스인지는 난이도가 아니라 보스의 성질이다. 이관은 `event_weekly` 인 보스의
  `is_season_boss` 를 켜고 그 난이도 줄의 주기를 `weekly` 로 적는다.
- 서버의 기록 표에서 이 칸은 비울 수 없고, 기록이 가리키는 보스 · 난이도 줄은 지울 수 없다. 지금 `boss_clears` 는 표에 없는 보스를
  받으면 칸을 비워 두는데, 그러면 다른 기기에 어느 보스였는지 돌려줄 수 없다. 표에 없는 보스 · 난이도로 온 기록은 거절한다.
  끝난 보스와 난이도는 지우지 않고 `until` 로 끝낸다.
- `bosses` 와 `boss_difficulties` 의 줄 id 는 다시 만들지 않는다. 이 id 가 모든 기기의 기록에 저장되므로, 표를 비우고 다시 채우면
  기기의 기록이 가리킬 줄이 없어진다. 운영 DB 를 옮길 때는 지금처럼 덤프로 옮긴다.
- 앱도 같은 id 로 저장한다(사용자 지정). 서버 게임 데이터가 보스와 난이도마다 `id` 를 함께 내고, 앱은 `GAME_DATA_CONTRACT` 를 올려
  새 사본을 받는다. `key` 는 보스의 값으로 남는다. 넥슨 응답의 보스 이름을 보스에 맞출 때와 그림 이름에 쓴다.
- 기기에 쌓인 기록은 1.0.15 로 올린 뒤 처음 켰을 때 한 번 바꾼다(사용자 지정). `GameDataLock` 이 화면을 가린 동안 앞에서 돌린다.
  줄 id 는 새 게임 데이터 사본에 있으므로 사본을 받은 뒤에 돌고, 한 트랜잭션으로 끝낸다. 도중에 앱이 꺼지면 다음에 켤 때 처음부터
  다시 돈다.
- 줄 id 를 찾지 못한 기록은 지운다(사용자 지정 2026-11-18). 기기에서는 변환 때 서버 표에 없는 보스 · 난이도를 든 줄을 지우고,
  서버의 기록 표는 운영에 줄이 없어 지울 줄이 없다. 드롭 판매가 표는 난이도 칸을 없애므로(결정 26) 난이도 줄 id 가 빈 줄을
  지우지 않는다.
- 보스를 든 기기 표의 칸과 변환 순서는 칸 설계를 확정한 뒤 [[ADR-078]] 에 적는다.

### 결정 20. 캐릭터는 서버의 `characters` 표에 한 줄로 두고, 캐릭터의 기록은 그 줄 id 로 가리킨다 (사용자 선택 2026-11-18)

- `characters` 는 캐릭터 하나가 한 줄이다. 줄 id, 그 캐릭터의 메이플 ID 해시(`maple_id`), ocid 해시(`ocid`)를 든다. `ocid` 는
  유일하다. 계정을 삭제하면 메이플 ID 를 따라 줄이 지워지고, 그 줄을 가리키는 기록도 함께 지워진다.
- 캐릭터가 주인인 기록 표는 `maple_id` 와 `ocid` 두 칸 대신 `character_id` 한 칸을 든다. 줄마다 두 칸을 따로 적으면 같은 캐릭터가
  표마다 다른 메이플 ID 아래에 적히는 것을 서버가 막을 수 없다. 캐릭터 표에서는 그 짝이 한 줄뿐이다. 결정 8 의 유일 기준에서
  ocid 는 `character_id` 로 건다. 캐릭터 줄이 ocid 하나에 하나라서 넥슨이 준 값으로 가리는 것과 같다.
- 약속의 보스 · 파티원, 계산기 기록의 캐릭터, 추적 캐릭터, 가계부의 받는 캐릭터와 조각을 가져온 캐릭터도 `character_id` 로 가리킨다.
- 기기 표와 앱 코드는 바꾸지 않는다. 기기는 지금처럼 메이플 ID 해시와 ocid 해시를 실어 올리고, 서버가 캐릭터 줄이 없으면 올리기를
  받는 자리에서 만든다. 내려줄 때는 서버가 `character_id` 를 ocid 해시로 풀어 준다. 캐릭터 줄 id 는 서버가 사용자마다 만드는
  값이라, 기기가 그것으로 저장하면 서버에 닿기 전에는 기록을 저장할 수 없게 된다.
- 드롭 판매가 표(`drop_sale_prices`, 지금의 `drop_prices`)는 캐릭터 줄에 묶지 않는다. `maple_id` 와 `ocid` 칸을 없애고, 판매가를
  올린 사람을 `user_id` 로 적는다(결정 26). 드롭 기록은 `boss_drops` 가
  수익 건을 따라 캐릭터 줄에 묶인다(결정 26). 판매가는 시세 계산에 쓰여 계정을 삭제해도 줄을 남기고, 2026-11-18 운영에
  1.0.13 앱이 올린 ocid 없는 줄이 5,413줄 있다. 캐릭터 줄에 묶으면 계정 삭제 때 함께 지워지거나 가리킬 줄이 없게 된다.
- 월드 리프로 ocid 가 바뀌면 캐릭터 줄의 `ocid` 를 새 값으로 고치고 옛 값을 `character_world_leaps` 에 적는다. 서버의 기록은
  캐릭터 줄을 가리키므로 고칠 것이 없다. 다른 기기는 그 줄을 받아 자기 기기의 옛 ocid 기록을 옮긴다. 부계정이 다른 넥슨 ID 로
  옮겨 가도 기록 표는 건드리지 않는다.
- ocid 는 캐릭터 이름을 알면 넥슨 API 로 누구나 구할 수 있다. 남의 캐릭터 ocid 를 자기 메이플 ID 로 먼저 올리는 요청을 막는
  방법은 구현 전에 정한다.

### 결정 21. 분배는 내 % 한 칸으로 두고 비율 합 칸을 없앤다 (사용자 지정 2026-11-18)

- 분배의 내 몫은 `split_share_millipercent` 한 칸에 둔다. 값은 내 % 에 1000 을 곱한 정수(0 ~ 100000)다. % 를 소수 셋째 자리까지 받으므로 이
  정수면 친 값을 오차 없이 담는다. `shares_total` 칸은 서버 표와 기기 표에서 모두 뺀다. 지금 이름 `my_share` 는 무엇의 몫인지와
  단위가 드러나지 않아 바꾼다. 이 값은 계산식에 바로 들어가므로 단위(1/1000 %)를 이름에 둔다.
- 입력이 내 % 하나로 바뀐 뒤로([[ADR-038]]) 새 기록의 비율 합은 언제나 100000 이다. 그 칸은 바뀌기 전에 적은 기록에만 뜻이 있다.
- 옛 기록은 1.0.15 의 기기 변환(결정 19)에서 `내 비율 ÷ 비율 합` 을 소수 셋째 자리 % 로 반올림해 옮긴다. % 로 떨어지지 않는
  비율(3 가운데 2 등)은 받는 금액이 조금 바뀐다. 10억 메소에서 3,300메소쯤이다. 화면의 % 는 이미 셋째 자리까지만 보여서 그대로다.
- 분배 칸은 보스 파티 설정 · 기간 행 · 드롭 · 가계부 품목 · 계산기 기록에 있다. 기기 표의 칸과 계산 코드는 구현할 때 그 기능의
  문서([[ADR-038]] · [[ADR-044]] · [[ADR-001]] · [[ADR-078]])와 함께 고친다.

### 결정 22. `제외` 는 분배 방식의 값으로 두고, 고르기 전의 분배는 남기지 않는다 (사용자 지정 2026-11-18)

- 분배 방식 칸 `split_type` 의 값은 `even` · `ratio` · `excluded` 셋이다. 칸과 enum 의 지금 이름은 `split_mode` 이고 결정 32 에서
  바꾼다. `crystal_excluded` 칸은 서버 표와 기기 표에서 모두 뺀다. `제외` 가 결정석을 팔지 않은 처치이고 결정석 내 몫을 0 메소로
  세는 것은 그대로다([[ADR-038]] 결정 12).
- `제외` 를 고르면 그 전의 인원 · 비율 · 분배 수수료를 지운다. 다시 `기본` 이나 `비율` 을 고르면 옛 값을 되살리지 않고 새로
  정하게 한다. [[ADR-038]] 결정 12 가운데 고르기 전 분배를 숨겨 두는 규칙(2026-11-14)을 이 결정이 바꾼다. 숨긴 값을 들고 있을
  일이 없으므로 칸을 따로 둘 이유도 없다.
- `split_type` 이 `excluded` 면 `party_size` 와 `split_share_millipercent` 는 비어 있다.
- 기기에서는 1.0.15 의 기기 변환(결정 19)에서 바꾼다. `crystal_excluded` 가 `1` 인 줄은 `split_type` 을 `excluded` 로 적고
  숨겨 둔 분배를 지운다. 이 칸의 `CHECK` 를 고치려면 표를 다시 만들어야 하는데, `boss_parties` 는 보스 줄 id 로
  바꾸느라 그때 다시 만든다.
- 드롭에는 `제외` 가 없다. 드롭은 드롭 기록의 분배 칸으로 나눈다.
- `제외` 인 보스는 인원이 없으므로 솔로로 다룬다(사용자 지정 2026-11-18). 드롭 가격을 적을 때 분배의 처음 값은 솔로이고,
  솔로 · 파티 필터에서는 솔로에 든다.
- 화면과 계산 코드, [[ADR-038]] 결정 12 의 본문은 구현할 때 함께 고친다.

### 결정 23. 표 이름은 그 표의 역할로 짓는다 (사용자 지정 2026-11-18)

- 서버와 기기의 표 이름은 그 표의 한 줄이 무엇인지를 말하게 짓는다. 이미 있는 이름이나 표끼리 매달린 관계에서 이름을 따오지
  않는다. 그렇게 지은 이름은 무엇을 담는 표인지 이름만으로 알 수 없다. 표를 하나씩 검토하면서 역할과 어긋난 이름을 바꾼다.
  아직 검토하지 않은 표는 이 문서에 옛 이름으로 적혀 있다.

  | 지금 이름 | 새 이름 | 한 줄의 역할 |
  |---|---|---|
  | 서버 `boss_clears` · 기기 `boss_party_periods` | `boss_profit_entries` | 한 캐릭터가 한 기간에 한 보스 · 난이도에서 얻는 수익 한 건. 처치 여부, 결정석 가격과 내 몫, 그 기간의 분배가 들어 있고 드롭이 이 줄에 매달린다 |
  | 서버 새 표 `boss_parties` · 기기 `boss_parties` | `boss_split_settings` | 한 캐릭터가 한 보스 · 난이도를 잡을 때 쓰는 기본 분배 설정 |

- `boss_clears` 는 처치하지 않은 기간 행도 담게 되어 이름이 틀린다. `boss_party_periods` 와 `boss_parties` 는 기기에서 줄이 서로
  매달린 관계에서 온 이름이다.
- 다른 표의 줄을 가리키는 칸은 그 표의 새 이름을 따른다. 드롭 기록이 수익 건을 가리키는 칸은 `boss_profit_entry_id` 다(결정 26).
  자기 표와 같은 말로 시작하는 표를 가리킬 때 칸 이름을 어떻게 줄이는지는 결정 36 에 있다.
- 칸 이름도 무엇의 값인지와 단위가 드러나게 짓는다(사용자 선택 2026-11-18). `boss_profit_entries` 의 칸이다. 기기 표의 같은 칸도
  함께 바꾸고, 분배 칸은 `boss_split_settings` 와 드롭 표에서도 같은 이름을 쓴다.

  | 지금 이름 | 새 이름 | 뜻 |
  |---|---|---|
  | `price_meso` | `crystal_price_meso` | 결정석 한 개의 가격. 나누기 전의 전체 금액이다 |
  | `payout_meso` | `crystal_received_meso` | 그 가격을 분배대로 나눈 뒤 내가 받는 메소. 앱 화면의 `받는 금액` 과 같은 값이다 |
  | `period_key` | `period_code` | 이 수익 건이 속한 기간(결정 24) |
  | `split_mode` | `split_type` | 분배 방식. 균등 · 비율 · 제외 가운데 하나다(결정 22). enum 이름도 같이 바꾼다(결정 32) |
  | `my_share` | `split_share_millipercent` | 비율로 나눌 때의 내 %(결정 21) |
  | `defeated_date` | `cleared_date` | 처치한 날짜. 같은 표에서 처치를 `clear` 한 말로 부른다. 서버에서는 형도 글자에서 날짜로 바꾼다 |
  | `source` | `clear_recorded_by` | 처치를 누가 적었는지. 동기화가 적었으면 `auto`, 사용자가 직접 적었으면 `manual` 이다 |
  | `split_fee_auto` | `split_fee_follows_mvp_grade` | 분배 수수료율이 MVP 등급을 따라가는지. 꺼져 있으면 사용자가 고른 값이다 |
  | `over_crystal_limit` | `over_crystal_sale_limit` | 주간 결정석 판매 한도를 넘긴 처치인지. 기기만 가진 칸이고 서버에는 두지 않는다(결정 27) |

- `clear_recorded_by` 의 값은 enum 으로 둔다(사용자 지정 2026-11-18). 지금 서버에 있는 enum `clear_source` 의 이름을 칸 이름에 맞춰
  `clear_recorded_by` 로 바꾼다. 값은 `auto` · `manual` 그대로다.
- 처치 상태 칸(`clear_status`)은 두지 않는다(결정 27).
- `party_size` 는 바꾸지 않는다. 분배에만 쓰는 값이 아니라 보스 카드의 인원 배지와 솔로 · 파티 필터도 읽는다.
- 두 금액은 결정석 가격 표와 같은 줄의 분배 칸에서 다시 구할 수 있지만, 기록할 때의 값으로 굳혀 서버에도 그대로 둔다. 패치로
  가격이 바뀌어도 지난 기록이 그때 값으로 남고, 앱 버전마다 계산식이 달라도 모든 기기가 같은 금액을 보인다.
- `boss_profit_entries` 에는 주기 칸을 두지 않는다. 기간 값의 첫 글자가 주기를 말한다(결정 24).
- 기기 표의 이름은 1.0.15 의 기기 변환(결정 19)에서 바꾼다. `boss_parties` · `boss_party_periods` · `boss_drops` 는 칸과 `CHECK`
  가 바뀌어 그때 다시 만드는 표다. 드롭이 수익 건을 가리키는 기기 칸 `period_id` 는 `boss_profit_entry_id` 가 된다.
- `boss_split_settings` 에는 분배를 정한 줄만 둔다(사용자 선택 2026-11-18). 서버에서 이 표의 `split_type` 은 비울 수 없다.
  기기에는 분배를 정한 적이 없어도 처치나 드롭이 생기면 만들어지는 빈 줄이 있다. 수익 건이 그 줄에 매달려 캐릭터와 보스를
  거기서 읽기 때문이다. 그 줄은 설정이 아니므로 올리지 않는다.
- 기기의 수익 건도 서버처럼 캐릭터(`ocid`)와 `boss_difficulty_id` 를 직접 든다(사용자 선택 2026-11-18). 설정 줄을 가리키던
  `party_id` 는 없앤다. 빈 설정 줄이 필요 없어지고 기기 표와 서버 표의 구조가 같아진다. 설정 줄을 지우면 수익 건과 드롭까지
  따라 지워지던 연결도 없어진다. 기기 저장 코드에서 두 표를 이어 읽는 곳은 24군데다.
- `bosses.alias` 는 `short_name` 으로 바꾼다. 좁은 곳에 쓰는 줄인 이름이다. 유효 기간 칸 `from` · `until` 은 `valid_from` ·
  `valid_until` 로 바꾼다(사용자 선택 2026-11-18). 무엇의 시작인지가 이름에 없고 둘 다 SQL 의 예약어다. 서버의 게임 데이터 표
  아홉 개(`bosses` · `boss_difficulties` · `boss_difficulty_rewards` · `boss_crystal_prices` · `world_periods` · `hunt_loot_items` ·
  `spend_items` · `symbol_level_costs` · `contents`)가 같은 이름을 써서 함께 바꾼다. 앱이 받는 게임 데이터도 새 이름으로
  낸다(결정 43).

### 결정 24. 기간은 주차와 월로 적는다 (사용자 지정 2026-11-18)

- 기록이 속한 기간은 `period_code` 칸에 적는다. 지금 이름은 `period_key` 다. `boss_profit_entries` 에 있고, 서버와
  기기가 같은 이름과 같은 값을 쓴다. 공유 컨텐츠의 진행(`shared_progress`)도 값이 속한 기간을 이 칸에 적는다(결정 33).

  | 주기 | 값 | 뜻 | 지금 값 |
  |---|---|---|---|
  | 주간 | `W202647` | 2026년 47주차 | `2026-11-19` |
  | 월간 | `M202611` | 2026년 11월 | `2026-11` |
  | 일간 | `D20261119` | 2026년 11월 19일 | `2026-11-19`. 일간 공유 컨텐츠의 진행에 쓴다 |

- 주차는 그 해의 첫 목요일에 시작하는 주를 1주차로 센다. 주간 초기화가 KST 목요일 0시이기 때문이다. 주는 시작한 목요일의 해에
  속한다. 2026-01-01 에 시작한 주가 `W202601`, 2026-12-31 에 시작한 주가 `W202653`, 2027-01-07 에 시작한 주가 `W202701` 이다.
  한 해는 52주이거나 53주다. 1월 1일이 목요일이 아니면 그 며칠은 전 해의 마지막 주차에 든다.
- 이 번호는 시작한 목요일의 ISO 주 번호와 같다. ISO 의 1주차가 그 해의 첫 목요일이 든 주이기 때문이다. 서버는 PostgreSQL 의 ISO
  주 함수로 날짜에서 값을 구한다.
- 지금 값은 주간이 그 주의 목요일 날짜이고 월간이 `YYYY-MM` 이라, 한 칸에 꼴이 둘이고 코드가 글자 길이로 주기를 가른다. 일간이
  생기면 주간과 같은 꼴이 된다. 날짜에 `-` 가 든 꼴 대신 몇 주차인지가 보이는 값으로 바꾼다.
- 값의 첫 글자가 주기를 말하므로 `boss_profit_entries` 에 주기 칸(`cycle`)을 두지 않고, 유일 기준에도 주기를 따로 넣지 않는다
  (결정 19). 주간 시작일과 월간 시작일이 같은 날(2026-10-01)에도 두 값은 `W202640` 과 `M202610` 으로 다르다. 서버는 쓸 때 값의 첫
  글자가 그 난이도의 주기와 맞는지 검사한다. 난이도의 주기가 `weekly` 면 `W`, `monthly` 면 `M` 이다(결정 19).
- 칸은 글자 형이고 꼴을 `CHECK` 로 검사한다. 주차는 01~53, 월은 01~12 만 받는다.
- 주를 가리키는 다른 칸도 같은 값으로 적는다. 설정의 마지막으로 등급을 확인한 주, 파티 약속의 시작 주 · 끝 주 · 주별 예외가
  그렇다. 칸 이름은 `_week_code` 로 끝낸다(결정 33).
- 기기에 쌓인 기록은 1.0.15 의 기기 변환(결정 19)에서 옮긴다. 값은 날짜만으로 계산되므로 서버 없이 옮길 수 있다. 화면은 값에서
  그 기간의 첫날을 구해 지금처럼 날짜로 그린다. 서버의 옛 줄은 DB 를 옮길 때 바꿔 적는다(결정 43).
- 게임 데이터의 유효 기간(`from` · `until`)은 기간 값이 아니라 날짜라서 지금 꼴 그대로 둔다.

### 결정 25. 분배 수수료율은 자동이거나 수동이고, 빈 값을 두지 않는다 (사용자 지정 2026-11-18)

- 분배 수수료율을 정하는 규칙은 둘이다([[ADR-038]] 결정 8 · [[ADR-050]] 결정 1). 자동이면 그 날짜의 그 메이플 ID MVP 등급 요율이고,
  수동이면 `0` · `3` · `5` 가운데 사용자가 고른 값이다. 등급을 고르지 않은 메이플 ID 는 일반이라 5% 다.
- 결정석의 수수료는 비율로 나눌 때만 쓴다. 처치한 수익 건(`boss_profit_entries`)에서 비율로 나눈 줄(`split_type` 이 `ratio`)은
  `split_fee_percent` 가 반드시 있다. 그 처치를 계산한 요율이기 때문이다. 서버는 빈 값을 받지 않는다.
- 분배 설정(`boss_split_settings`)과 처치 전 수익 건은 자동이면 `split_fee_percent` 를 비우고, 수동이면 반드시 채운다(사용자 선택
  2026-11-18). 자동인 설정은 처치를 적을 때 그 날짜의 등급 요율을 구하므로(`settingSplitFee`) 저장된 값이 쓰이지 않는다.
- 드롭(`boss_drops`)의 수수료는 다르다. 비어 있으면 수수료 없음이고, 3% 로 읽던 규칙이 없었다. 그래서 아래의 채우기는 드롭에
  하지 않는다. 드롭의 지난 금액은 받는 메소를 저장해 지킨다(결정 26).
- 코드가 빈 값을 3% 로 읽던 규칙을 없앤다. `lib/boss/party-shares.ts` 의 `DEFAULT_SPLIT_FEE_PERCENT` 와 `PartySizeModal` 의
  `?? 3` 두 군데다. 앱이 MVP 등급을 모르던 때에 넣은 값이고, 등급을 모르면 일반(5%)이라는 규칙과 어긋난다. [[ADR-038]] 결정 7 의
  "수수료율이 비었으면 3%다"를 이 결정이 바꾼다.
- 지금 화면에서는 비율을 고르면 수수료가 자동으로 시작해서 새 줄에는 빈 값이 생기지 않는다. 빈 값은 그 전에 비율로 적은 옛
  줄에만 있다. 옛 줄은 수동으로 고른 적이 없으므로 자동으로 본다. 1.0.15 의 기기 변환(결정 19)에서
  `split_fee_follows_mvp_grade` 를 켠다. 처치한 수익 건에는 그 기록 날짜의 등급 요율을 적고, 설정 줄과 처치 전 수익 건은 요율을
  비운다.
- 요율이 바뀌는 줄은 받는 메소(`crystal_received_meso`)를 다시 계산한다(사용자 확인 2026-11-18). 그 날짜에 실버 이상이던 메이플
  ID 의 줄은 3% 그대로라 바뀌지 않고, 일반 · 브론즈였거나 등급을 고르지 않은 메이플 ID 의 줄은 3% 에서 5% 로 바뀐다.

### 결정 26. 드롭 기록과 시세를 재는 판매가는 다른 표에 둔다 (사용자 선택 2026-11-18)

- 기기 간 동기화에 쓰는 드롭 기록은 새 표 `boss_drops` 에 두고, 시세 계산에 쓰는 판매가는 지금의 `drop_prices` 에 그대로 두며 이름을
  `drop_sale_prices` 로 바꾼다(결정 29). 앞에서는 `drop_prices` 에 칸을 더해 두 역할을 함께 맡기려 했다.
- 한 표에 두면 예외가 계속 생긴다. 옛 판매가 줄에는 종류 · 분배 · 수수료 값이 없어서 그 칸을 모두 비울 수 있게 해야 하고,
  그러면 서버가 드롭 기록의 값을 검사하지 못한다. 주인을 캐릭터 줄로 가리키지 못하고 수익 건과도 참조로 묶지 못한다. 지워지는
  때도 다르다. 계정을 삭제하면 드롭 기록은 지워야 하고, 판매가는 누구 것인지만 지우고 남겨야 한다([[ADR-101]] 결정 24).
- 2026-11-18 운영의 `drop_prices` 는 5,549줄이다. 5,455줄이 1.0.13 앱이 올린 줄이고 메이플 ID 도 ocid 도 없다. 메이플 ID 가 있는
  줄은 한 사람의 94줄이다. 시세 계산은 가격을 적은 4,810줄의 아이템 · 가격 · 적은 시각 · 월드 · 반지 레벨만 읽는다.

  | 표 | 한 줄의 역할 | 주인과 지워지는 때 |
  |---|---|---|
  | `boss_drops` | 한 수익 건에서 나온 드롭 한 개와 그 판매 기록. 가격을 적지 않은 드롭도 든다 | 수익 건에 매달린다. 캐릭터 · 보스 · 난이도 · 기간 · 월드는 수익 건에서 읽는다. 수익 건이나 계정이 지워지면 함께 지워진다 |
  | `drop_sale_prices` | 사용자가 적은 드롭 판매가 한 건. 시세를 재는 데 쓴다 | 주인이 없다. 계정을 삭제하면 사람 칸(`user_id`)만 비우고 줄은 남긴다 |

- `boss_drops` 의 칸이다. 기기 표도 같은 이름을 쓴다(결정 23).

  | 칸 | 뜻 | 기기의 지금 이름 |
  |---|---|---|
  | `id` | 기기가 만든 드롭 id(결정 8) | `id` |
  | `boss_profit_entry_id` | 이 드롭이 속한 수익 건 | `period_id` |
  | `item_id` | 얻은 아이템. 반지는 레벨까지 정해진 아이템 줄이다. 나온 상자는 적지 않는다(결정 28) | `item_key` · `box_origin_key` · `ring_level` |
  | `category` | 드롭 종류 | 같다 |
  | `price_status` | 가격을 적었는지. `pending` · `entered` · `skipped` | `record_status`, 값 `completed` |
  | `sale_price_meso` | 판매가. 나누기 전의 전체 금액 | `price_meso` |
  | `sale_received_meso` | 판매 수수료와 분배를 반영해 내가 받는 메소 | 없다. 읽을 때 계산한다 |
  | `priced_at` | 가격을 처음 적거나 바꾼 시각 | 같다 |
  | `sale_fee_percent` · `sale_fee_follows_mvp_grade` | 판매 수수료율과, 그것이 MVP 등급을 따라가는지 | `sale_fee_auto` |
  | 분배 칸 다섯 | 수익 건과 같은 이름이다. 드롭에는 `excluded` 가 없다 | 결정 21 · 23 |
  | `change_seq` · `deleted_at` · `created_at` · `updated_at` | 동기화 칸 | |

- `boss_drops` 의 유일 기준은 수익 건 · 아이템이다. 한 캐릭터는 한 기간에 한 보스에게서 같은 아이템을 둘 얻지
  못한다([[ADR-101]] 결정 24). 보스가 직접 떨군 것과 상자에서 나온 것을 함께 얻을 수 있는 아이템은 아이템 줄이 둘이라(결정 28) 두
  드롭이 겹치지 않는다. 지운 드롭은 다른 표처럼 `deleted_at` 으로 표시하고 가격 상태에 `deleted` 값을 두지 않는다.
- 기기의 드롭 기록도 품목을 `item_id` 한 칸으로 적는다(결정 28). 가계부 품목과 인벤토리의 아이템도 줄 id 로 적는다(결정 39 ·
  44).
- 받는 메소를 저장한다(사용자 선택 2026-11-18). 기기는 지금 읽을 때마다 계산하고, 지난 금액을 지키려고 빈 칸에 숨은 뜻을 둘
  두었다([[ADR-044]]). 수수료 두 칸이 다 빈 기록은 수수료 없이 나누는 옛 식으로 세고, 2026-10-19 전의 균등 기록은 내 비율 칸이
  차 있으면 비율 식으로 센다. 1.0.15 의 기기 변환에서 가격을 적은 드롭마다 지금 식으로 한 번 계산해 `sale_received_meso` 에
  적는다. 지금 식이 그 두 갈래를 그대로 타므로 지난 금액은 바뀌지 않는다. 변환 뒤에는 저장된 값을 읽고, 가격 · 분배 · 수수료를
  고칠 때만 다시 계산한다. 결정석의 `crystal_received_meso` 와 같은 방식이다.
- 판매가 줄은 서버가 적는다. 1.0.15 앱은 드롭 기록만 올린다. 서버는 가격을 적은(`entered`) 드롭을 받으면 같은 트랜잭션에서
  `drop_sale_prices` 에 그 드롭의 id 로 한 줄을 적는다. 아이템 · 판매가 · 적은 시각은 드롭에서, 월드는 수익 건에서
  읽고, 사람은 요청한 사람이다. 가격을 지우거나 드롭을 지우면 그 줄을 지운다(결정 29). 가격을 적은
  드롭은 두 표에 한 줄씩 있게 된다.
- 드롭 판매가 표의 칸은 여덟이다(사용자 선택 2026-11-19). 시세 계산이 읽는 것만 남긴다.

  | 칸 | 든 값 | 읽는 곳 |
  |---|---|---|
  | `id` | 그 판매가가 나온 드롭의 id(결정 8) | 줄을 가린다 |
  | `user_id` | 판매가를 올린 사람의 사람 줄. 계정을 삭제하면 비운다 | 시세가 사람마다 한 표로 셀 때([[ADR-071]] 결정 3) |
  | `item_id` | 판 아이템. 반지는 레벨 줄이다(결정 28) | 시세 |
  | `world_id` | 판 월드 | 시세의 범위(결정 41) |
  | `sale_price_meso` | 판매가 | 시세 |
  | `priced_at` | 가격을 적은 시각. 시세의 거래 시각이다 | 시세의 날짜 |
  | `created_at` · `updated_at` | 줄을 만들고 고친 시각 | 관리 화면의 정렬 |

- 사람은 `user_id` 하나로 적고 `maple_id` 를 없앤다. 2026-11-19 운영의 5,652줄 모두에 `user_id` 가 있고 `maple_id` 가 있는 줄은
  94줄이다. 지금 시세는 메이플 ID 에서 넥슨 계정을 찾아 사람으로 삼고 메이플 ID 가 없으면 `user_id` 를 쓴다. 사람 줄과 넥슨
  계정은 운영에서 1대1 이다. 한 칸으로 줄이면 해시 글자 대신 줄 id 로 적고(결정 39), 메이플 ID 에서 넥슨 계정을 찾아 올라갈
  필요가 없다.
- `ocid` 와 `boss_id` 를 없앤다(사용자 지정 2026-11-19). 같은 드롭인지는 동기화에 쓰는 `boss_drops` 가 판단한다. 이 표의 줄은 드롭
  한 개에 한 줄이고 드롭의 id 로 가린다. 지금 이 표에 `ocid · 보스 · 기간 · 아이템` 기준이 있는 것은 1.0.14 까지의 앱이
  `boss_drops` 를 거치지 않고 여기에 바로 올렸기 때문이다. 그 경로는 1.0.15 를 배포할 때 없앤다(결정 43). 그 뒤로 이 표에 줄을
  적는 것은 서버뿐이다.
  - `boss_drops` 에서 유일 기준이 같아 한 줄로 합쳐질 때(결정 10) 버려지는 드롭 id 의 판매가 줄은 지운다.
  - 계정을 삭제한 사람이 돌아와 같은 드롭을 손으로 다시 적으면 남아 있던 옛 판매가 줄과 새 줄이 시세에 함께 세인다. 계정을
    삭제하면 `boss_drops` 가 지워져 같은 드롭인지 판단할 근거가 없다. 드문 경우라 막지 않는다.
- `boss_difficulty_id` 와 `period_code` 를 없앤다(사용자 선택 2026-11-19). 시세는 읽지 않고, 관리 화면의 드롭 가격 목록만 보스 ·
  난이도 · 기간을 보여 주려고 읽는다. 다시 구할 수 있는 값이라(결정 27) 관리 화면은 `boss_drops` 에서 찾아 보여 준다. 옛 줄과
  계정을 삭제한 사람의 줄은 드롭 기록이 없어 그 칸이 비어 보인다.
- 그 밖에 `identified_by` · `period_record_id` · `ring_level` · `box_origin_item_id` · `record_status` 를 뺀다(결정 8 · 27 · 28 · 29).
- 1.0.15 로 올린 기기가 처음 드롭을 올릴 때 같은 id 의 옛 줄이 있으면 결정 8 의 규칙으로 그 줄을 덮는다. 그래서 같은 드롭이
  시세에 두 번 세이지 않는다.

### 결정 27. 없애도 되는 칸은 두지 않는다 (사용자 지정 2026-11-18)

- 다른 칸이나 참조표에서 다시 구할 수 있는 값, 다른 칸이 찼는지로 알 수 있는 상태, 읽는 곳이 없는 값, 기기마다 다시 계산하는 값은
  칸으로 두지 않는다. 기기 표에 있다는 이유만으로 서버 표에 옮기지 않는다. 칸이 많으면 서로 어긋날 수 있는 값이 늘고 동기화할
  것도 늘어난다. 표를 검토하다 그런 칸이 나오면 사용자에게 알리고, 빼는 것은 사용자가 정한다.
- 기록할 때의 값으로 굳혀야 하는 금액은 다시 구할 수 있어도 남긴다. `crystal_price_meso` · `crystal_received_meso` ·
  `sale_received_meso` 가 그렇다(결정 23 · 26).
- `boss_drops` 에 차례 칸(`sort_order`)을 두지 않는다. 기기 표의 같은 칸도 1.0.15 의 기기 변환에서 없앤다. 목록의 차례를 기억하던
  칸이고 사용자가 넣는 값이 아니다. 서버의 드롭 표(`boss_difficulty_rewards`)에 아이템마다 시트에서의 차례가 있으므로 그 차례로
  늘어놓으면 모든 기기에서 같은 순서가 된다. 상자에서 나온 드롭은 그 상자의 차례에 둔다.
- 번호로 차례를 적으면 동기화에서 어긋난다. 드롭 하나를 넣거나 빼면 뒤의 번호가 모두 바뀌어 그 묶음의 모든 줄이 바뀐 줄로
  올라가고, 두 기기가 같은 보스에 드롭을 하나씩 더하면 같은 번호가 겹친다.
- 기기 코드 몇 군데는 이 번호(`dropIndex`)로 묶음 안의 드롭을 찾아 고친다. 드롭 id 로 찾게 바꾼다. 시트의 드롭 순서는 넣은
  순서에서 드롭 표의 순서로 바뀐다.
- `boss_profit_entries` 에 처치 상태 칸(`clear_status`)을 두지 않는다(사용자 선택 2026-11-18). 처치했는지는 `clear_recorded_by` 가
  차 있는지로 안다. 처치한 줄은 `crystal_price_meso` · `crystal_received_meso` · `clear_recorded_by` 가 모두 차 있고 처치 전 줄은 셋
  다 비어 있다. 서버와 기기 모두 이것을 `CHECK` 로 지킨다. 기기 표는 지금도 상태와 이 칸들이 늘 같도록 검사하고 있어, 상태 칸은
  같은 사실을 한 번 더 적은 것이었다. 기기 표의 같은 칸도 1.0.15 의 기기 변환에서 없앤다. 새로 만들려던 enum `clear_status` 도
  만들지 않는다.
- 주간 결정석 판매 한도를 넘겼는지의 칸(`over_crystal_sale_limit`)은 서버에 두지 않는다(사용자 선택 2026-11-18). 그 주의 처치
  전체를 보고 받는 메소가 낮은 처치부터 고르는 계산값이다(`overCrystalLimitIds`). 기기마다 같은 기록으로 다시 계산하면 같은
  답이 나온다. 기기는 지금처럼 계산한 결과를 자기 표에 적어 두되 올리지 않고, 기록을 받은 뒤에 그 주를 다시 계산한다. 두
  기기가 각자 계산해 올리면 같은 줄을 서로 덮어쓰게 된다.
- 드롭 판매가 표의 `period_record_id` 를 없앤다(사용자 선택 2026-11-18). 서버 코드에 이 칸을 읽는 곳이 없다.
- 다시 구할 수 있지만 남기는 칸도 있다. `boss_drops.category` 는 드롭 표에서 보스 난이도와 아이템으로 구할 수 있지만, 운영자가
  드롭 표에서 그 줄을 지우면 지난 드롭의 종류를 알 수 없게 되고 상자에서 나온 드롭은 찾는 방법이 따로 필요하다. 서버 표의
  `created_at` · `updated_at` 은 동기화에는 쓰지 않지만 운영 데이터를 조사할 때 쓴다. 2026-11-18 에 난이도 줄 id 가 빈 줄과 기기
  id 가 겹친 줄의 원인을 이 두 칸으로 찾았다.

### 결정 28. 반지는 레벨마다 아이템 한 줄로 두고, 드롭 기록은 얻은 아이템 줄만 가리킨다 (사용자 지정 2026-11-18)

- 드롭 기록은 품목을 칸 셋(아이템 · 반지 레벨 · 나온 상자)으로 적어 왔다. 이것을 `items` 의 줄 하나를 가리키는 `item_id` 한 칸으로
  바꾼다. 반지 레벨은 아이템 줄로 옮기고, 나온 상자는 적지 않는다.
- `items` 에 반지를 레벨마다 한 줄씩 둔다. 반지 11개에 레벨 1 ~ 4 를 더해 44줄이 늘어난다. 레벨이 다른 반지는 시세도 다르고
  인벤토리에서도 따로 세는 다른 물건이기 때문이다. 이름은 `리스트레인트 링 lv.4` 꼴로 적는다(사용자 지정 2026-11-18). key 는 원래
  반지의 key 뒤에 레벨을 붙인다(`restraint_ring_lv4`). 앱 화면은 지금 `4레벨` 과 `Lv.4` 를 섞어 쓰는데, 아이템 이름을 그대로
  보이게 되면서 이 표기로 모인다. 원래 반지 11줄은 남긴다. 결과를 고르는 화면이 레벨 줄을 원래 반지로 묶어
  그린다. 생명의 연마석과 신념의 연마석은 레벨이 없어 그대로다.
- `items` 에는 칸을 더하지 않는다(사용자 지정 2026-11-18). 레벨 줄이 어느 반지의 몇 레벨인지는 새 표 `ring_level_items` 에 둔다.
  아이템 표의 칸으로 두면 레벨 줄이 아닌 650여 줄에서 그 칸이 비기 때문이다.

  | 칸 | 뜻 |
  |---|---|
  | `id` | 줄 id |
  | `item_id` | 레벨 줄인 아이템. 아이템 하나에 줄이 하나라 `UNIQUE` 다 |
  | `ring_item_id` | 원래 반지인 아이템 |
  | `ring_level` | 레벨. 1 ~ 4 |

  원래 반지와 레벨의 조합도 `UNIQUE` 다. 아이템 줄 하나에 하나씩만 딸린 표지만 자기 `id` 를 기본 키로 둔다(사용자 선택
  2026-11-18, [[ADR-016]] 결정 5). 가리키는 아이템 줄의 id 를 기본 키로 함께 쓰는 방식은 쓰지 않는다.
- 나온 상자는 기록에 적지 않는다(사용자 지정 2026-11-18). 같은 난이도의 같은 보스는 종류가 다른 반지 상자를 둘 주지
  않으므로(사용자 확인 2026-11-18), 보스 난이도와 아이템이 정해지면 상자가 하나로 정해진다. 상자는 읽을 때 지금의 드롭 표 셋에서
  찾는다.
  - 수익 건의 난이도가 주는 줄(`boss_difficulty_rewards`) 가운데 아이템이 상자인 줄(`drop_boxes`)을 고르고, 그 상자의
    내용물(`drop_box_contents`)에 드롭의 아이템이 든 상자를 고른다. 레벨 줄이면 `ring_level_items` 의 원래 반지와 상자의 레벨
    범위로 찾는다. 그런 상자가 없으면 보스가 직접 떨군 것이다.
  - 2026-11-18 운영의 드롭 표에서 상자를 주는 보스 난이도는 51개다. 36개는 상자를 하나 주고, 15개는 반지 상자 하나와 장신구 상자
    하나를 준다. 반지 상자를 둘 주는 난이도는 없고, 한 난이도의 두 상자에 함께 든 아이템도 없다.
  - `drop_boxes` 와 `drop_box_contents` 는 칸을 그대로 둔다. 상자의 레벨 범위(`level_min` · `level_max`)와, 결과를 고르는 화면에서
    칸이 놓이는 차례(`drop_box_contents.sort_order`)도 지금 칸을 쓴다. 상자의 내용물은 지금처럼 원래 반지 줄을 가리킨다.
- 같은 보스 난이도에서 직접도 떨어지고 상자에서도 나오는 아이템은 아이템 줄을 둘로 둔다(사용자 지정 2026-11-18). 상자를 적지
  않으면 두 드롭을 가를 것이 아이템 줄뿐이기 때문이다. 2026-11-18 운영에서 그런 아이템은 생명의 연마석 하나다. 감시자 칼로스
  카오스 · 익스트림과 최초의 대적자 하드 · 익스트림이 직접도 떨구고 생명의 보스 반지 상자로도 준다. 원래 줄은 보스가 직접 떨구는
  것으로 쓰고, 새로 더하는 줄은 상자의 내용물로 쓴다. 생명의 보스 반지 상자의 내용물 줄이 새 줄을 가리키게 바꾼다. 두 줄이
  같은 물건이라는 것은 `same_item_links` 에 적는다(결정 30). 새 줄의 key 는 사용자 확인을 받아 정한다.
- 그래서 기록에 얻은 경로를 따로 적지 않는다. 반지 레벨 줄은 상자에서만 나오고, 생명의 연마석은 경로마다 줄이 따로 있고, 그 밖의
  아이템은 보스가 직접 떨군다.
- `ring_level` 칸은 드롭 판매가 표와 시세 집계 표 둘(`market_days` · `maspi_basket`), 가계부 품목 · 인벤토리에서도 뺀다. 레벨 줄의
  `item_id` 하나로 가리킨다. 시세 집계 표의 유일 기준은 날짜 · 아이템 · 범위가 된다. 드롭 판매가 표의 상자
  칸(`box_origin_item_id`)도 뺀다. 시세 계산이 읽지 않는 칸이다(결정 27).
- 드롭 판매가 표는 같은 드롭인지를 스스로 가리지 않는다. 줄은 드롭의 id 로 가리고, 같은 드롭인지는 `boss_drops` 가
  판단한다(결정 26). 지금 있는 ocid · 보스 · 기간 · 아이템 · 획득처 기준([[ADR-101]] 결정 24)은 없앤다. 이관에서 레벨이 있는
  반지 줄은 레벨 줄로, 상자 칸이 찬 생명의 연마석 줄(1줄)은 새 줄로 옮긴다.
- 이렇게 나눠 두는 이유는 고칠 때의 범위다. 물건을 가르는 속성이 기록 표의 칸으로 있으면 새 속성이 생길 때마다 그것을 쓰는
  표와 코드를 모두 고쳐야 한다. 2026-11-11 에 드롭을 직접과 상자로 가르게 했을 때 서버의 표 · 유일 기준 · 올리기 코드와 기기
  표를 함께 고쳤다. 아이템 줄로 있으면 줄만 더하고, 기록 표와 기기 표는 그대로다. 반지에 새 레벨이 생기거나 등급이 있는 새
  아이템이 생길 때가 그렇다.
- 치르는 값이 둘 있다.
  - 기록이 가리키는 아이템이 그 보스에서 얻을 수 있는 것인지는 참조만으로 막지 못한다. 지금처럼 서버 코드가 검사한다.
  - 드롭 표가 두 가지를 지켜야 상자가 하나로 정해진다. 한 보스 난이도가 직접 떨구는 아이템 줄이 그 난이도 상자의 내용물에 들어
    있으면 안 되고, 한 보스 난이도의 두 상자에 같은 아이템 줄이 들어 있으면 안 된다. DB 의 유일 기준으로는 걸 수 없어 관리 화면이
    드롭 표를 저장할 때 검사한다. 직접도 떨어지고 상자에서도 나오는 아이템이 새로 생기면 아이템 줄과 `same_item_links` 줄을
    하나씩 더한다.
- 기록이 가리키는 `items` 줄은 지울 수 없다. 지난 드롭의 상자는 그 기간의 드롭 표로 찾으므로, 보스가 주는 상자가 바뀌면 드롭 표의
  줄을 지우지 않고 기간(`valid_from` · `valid_until`, 결정 23)으로 끝낸다. 상자의 내용물에서 아이템이 빠지는 일이 생기면 그때
  내용물 표에 기간 칸을 더한다. 지금은 두지 않는다(결정 27).
- 기기 표도 `item_key` · `box_origin_key` · `ring_level` 세 칸 대신 `item_id` 한 칸을 쓴다. 아이템 줄의 id 와 `ring_level_items` ·
  `same_item_links` 는 새 게임 데이터에 실려 오므로 1.0.15 의 기기 변환(결정 19)에서 함께 바꾼다. 레벨이 있는 반지 기록은 레벨
  줄로, 상자 칸이 찬 생명의 연마석 기록은 새 줄로 바꾼다. 맞는 줄을 찾지 못한 기록은 보스와 같은 규칙으로 지운다. 서버 아이템
  표에 없는 key 를 든 기록이 그렇다. 앱이 `기타` 반지에 쓰는 `other_ring` 은 2026-11-18 서버 아이템 표에 없다. 그 key 를 든 기기
  기록은 지우고, 아이템 표에 줄을 더해 살리지 않는다(사용자 확인 2026-11-18). 아이템 줄이 없으므로 결과를 고르는 화면에서도
  `기타` 는 고를 수 없게 된다([[ADR-044]] 결정 5).

### 결정 29. 시세를 재는 표는 `drop_sale_prices` 로 부르고, 판매가를 적은 줄만 둔다 (사용자 선택 2026-11-18)

- 지금의 `drop_prices` 를 `drop_sale_prices` 로 바꾼다. 한 줄은 사용자가 적은 드롭 판매가 한 건이고 시세를 재는 데 쓴다. 앱이
  가격을 넣는 화면에서 쓰는 말이 `판매가` 다. `drop_price_samples` 는 통계 용어를 붙인 이름이라, `market_sales` 는 `market` 이
  앱에 없는 말이라 쓰지 않는다(사용자 지적).
- 가격 칸 `price_meso` 는 `sale_price_meso` 로 바꿔 `boss_drops` 와 같은 이름을 쓴다.
- 판매가를 적은 줄만 둔다. 상태 칸(`record_status`)과 enum `drop_record_status` 를 없앤다(결정 27). 가격을 적지 않은 드롭은 이제
  `boss_drops` 가 담고, 시세 계산은 가격을 적은 줄만 읽어 왔다.
  - 가격을 적은 드롭이 오면 줄을 적는다. 가격을 지우거나 드롭을 지우면 줄을 지운다.
  - `sale_price_meso` 와 `priced_at` 은 모든 줄에 있다. 유일 기준에서 지운 줄을 빼던 조건은 필요 없다.
- 2026-11-18 운영 5,549줄 가운데 가격이 없는 739줄을 이관에서 지운다. 미입력 471줄, 기록 안 함 133줄, 지움 135줄이다. 시세에
  쓰이지 않던 줄이라 시세는 달라지지 않는다.
- 서버의 시세 표 넷(`market_days` · `market_judgements` · `market_runs` · `market_responses`)도 `market` 으로 시작한다. 동기화
  표가 아니어서 이 문서에서는 고치지 않고, 그 표들을 볼 때 이름을 다듬는다.

### 결정 30. 줄은 다르지만 같은 물건인 아이템은 `same_item_links` 로 잇는다 (사용자 지정 2026-11-18)

- 같은 물건인데 아이템 줄을 따로 둬야 할 때가 있다. 따로 둔 줄이 원래 어느 아이템인지를 새 표 `same_item_links` 에 적는다. 한 줄은
  따로 둔 아이템 줄 하나와 그 원래 아이템의 연결이다.

  | 칸 | 뜻 |
  |---|---|
  | `id` | 줄 id |
  | `item_id` | 따로 둔 아이템 줄. 아이템 하나에 줄이 하나라 `UNIQUE` 다 |
  | `original_item_id` | 원래 아이템 줄 |

- 2026-11-18 에 들어갈 줄은 하나다. 상자에서 나온 생명의 연마석 줄이 원래 생명의 연마석 줄을 가리킨다(결정 28).
- 드롭에만 쓰는 표가 아니다(사용자 지정 2026-11-18). 얻는 곳이 여러 곳이라 줄을 나눠야 하는 아이템이 생기거나, 드롭과 상관없는
  이유로 따로 둔 줄을 하나의 아이템으로 이어야 할 때도 이 표로 잇는다. 그런 표를 새로 만들지 않는다. 그래서 표 이름과 칸 이름에
  상자나 드롭을 넣지 않았다. 줄을 왜 나눴는지도 이 표에 적지 않는다. 그 줄을 쓰는 표가 안다. 상자에서 나온 줄이라는 것은 상자의
  내용물 표가 그 줄을 가리키는 것으로 안다.
- 원래 아이템 하나에 따로 둔 줄이 여럿 있을 수 있다. 원래 아이템 줄은 다른 줄의 따로 둔 줄이 될 수 없다. 연결이 두 번 이어지면
  원래 아이템을 찾을 때마다 끝까지 따라가야 하기 때문이다. 자기 자신을 가리키는 줄은 `CHECK` 로 막고, 두 번 이어지는 줄은 관리
  화면이 저장할 때 막는다.
- 읽는 규칙은 둘이다.
  - 기록은 따로 둔 줄을 그대로 가리킨다. 드롭 기록과 드롭 판매가가 그렇다. 원래 줄로 바꿔 적으면 직접 떨어진 것과 상자에서 나온
    것을 가를 수 없다.
  - 아이템마다 모으는 곳과 사용자가 아이템을 고르는 목록은 원래 아이템 줄만 쓴다. 시세 계산은 드롭 판매가를 읽을 때 따로 둔 줄을
    원래 아이템으로 바꿔 모은다. 그래야 생명의 연마석 시세가 둘로 갈리지 않는다. 앱에서 아이템마다 모아 보이는 화면도 같다.
- 따로 둔 줄의 이름 · 그림 · 분류는 원래 줄과 같은 값이다. 두 줄이 어긋나지 않게 하는 방법(관리 화면이 함께 고칠지, 읽을 때 원래
  줄에서 읽을지)은 구현 때 정한다.
- 서버 게임 데이터가 이 표를 함께 낸다.
- 표 이름은 역할에서 지었다(결정 23). 상자를 넣은 이름(`from_box_items`)은 반지 레벨 줄에도 들어맞고, 이 표가 하는 일은 상자를
  적는 것이 아니라 같은 물건을 잇는 것이어서 쓰지 않는다.

### 결정 31. 처치 난이도가 정해지면 그 난이도에서 얻을 수 있는 드롭은 남기고, 가리는 일은 서버가 한다 (사용자 지정 2026-11-18)

- 드롭을 처치 전에 적으면 실제 처치 난이도와 다른 난이도의 수익 건에 적힐 수 있다. 노말로 등록하고 드롭을 적었는데 카오스를
  잡은 경우다. 드롭 시트가 처치 전 줄에서 난이도를 바꿔 보여 줄 때도 저장은 그 줄의 난이도로 한다([[ADR-044]] 결정 2).
- 지금 앱은 처치 난이도가 정해지면 드롭을 그 난이도로 옮기고 그 난이도에서 못 얻는 드롭을 지운다([[ADR-040]] 결정 7,
  [[ADR-044]] 결정 8). 상자에서 나온 드롭은 상자로 가린다. 그래서 감시자 칼로스 노말의 백옥 상자에서 나온 리스트레인트 링 lv.4 는
  실제 처치가 카오스면 지워진다. 카오스는 백옥 상자를 주지 않기 때문이다. 그 반지는 카오스가 주는 생명 상자에서도 나온다.
- 1.0.15 부터는 아이템으로 가린다(사용자 지정 2026-11-18). 기록에 상자가 없으므로(결정 28) 보는 것은 하나다. 그 아이템을 처치한
  난이도에서 얻을 수 있는가다.

  | 경우 | 예 | 처리 |
  |---|---|---|
  | 처치한 난이도에서도 얻을 수 있다 | 위의 리스트레인트 링 lv.4 | 남긴다. 상자는 처치한 난이도로 찾으므로(결정 28) 고쳐 적을 값이 없다 |
  | 처치한 난이도에서 못 얻는다 | 같은 수익 건에 적은 얼티메이덤 링 lv.4. 생명 상자에 없는 반지다 | 지운다. 지금과 같다 |
  | 같은 물건을 다른 경로로만 얻을 수 있다 | 벨로나 노말에 직접 떨어진 생명의 연마석을 적었는데 하드를 잡았다. 하드에서는 생명 상자에서만 나온다 | 남기고, 아이템 줄을 같은 물건의 다른 줄로 바꾼다(결정 30) |

- 두 경로가 다 있는 난이도면 적힌 줄을 그대로 둔다. 감시자 칼로스 카오스는 생명의 연마석을 직접도 떨구고 상자로도 준다.
  2026-11-18 운영에서 생명의 연마석을 주는 방법이 난이도마다 갈리는 보스는 감시자 칼로스 · 벨로나 · 찬란한 흉성 · 최초의 대적자 ·
  카링이다.
- 옮기고 지우고 바꾸는 일은 서버가 한다(사용자 지정 2026-11-18). 처치한 수익 건을 받으면 같은 캐릭터 · 보스 · 기간의 다른 난이도
  수익 건에 달린 드롭을 처치한 수익 건으로 옮기고, 위 표대로 가린다. 기기는 그 결과를 받는다(결정 9). 지금은 기기가 옮기고 지운
  뒤 서버에 지우기를 보낸다. 기기가 여럿이면 각자 고쳐 올린 줄이 서로를 덮으므로 한곳에서 한다.
- 처치한 수익 건에 이미 있는 드롭은 그대로 두고 같은 드롭은 옮기지 않는다. 같은 드롭은 지금처럼 가린다([[ADR-040]] 결정 7).
  보스가 직접 떨군 것이면 아이템이 같은 것이고, 상자에서 나온 것이면 찾은 상자가 같은 것이다. 드롭 시트가 상자 하나에 결과를
  하나만 두기 때문이다.
- 서버의 결과를 받기 전에 기기 화면이 그 드롭을 어떻게 보일지는 구현 전에 정한다.

### 결정 32. 종류를 가르는 enum 과 칸은 `_type` 으로 끝내고, 서버의 모든 표를 함께 정리한다 (사용자 지정 2026-11-18)

- 종류를 가르는 enum 의 이름은 `_type` 으로 끝낸다. `_kind` 와 `_mode` 는 쓰지 않는다. 세 말이 같은 뜻으로 섞여 있었다. 2026-11-18
  서버의 enum 27개 가운데 `_type` 이 7개, `_kind` 가 3개, `_mode` 가 1개다.
- 칸 이름은 enum 이름에서 표 이름과 겹치는 말을 뺀 것이다(결정 36). 표 이름이 무엇의 종류인지를 이미 말하면 칸은 `type` 이다.
  `notices` 의 종류 칸은 `notice_type` 이 아니라 `type` 이다. `kind` 한 낱말로 된 칸은 `type` 으로 바꾼다.

  | 지금 이름 | 새 이름 | 값 | 쓰는 칸 |
  |---|---|---|---|
  | `notice_kind` | `notice_type` | `app` · `game` · `event` · `update` · `cashshop` | `notices.kind` 를 `type` 으로 |
  | `image_crop_kind` | `image_crop_type` | `boss_portrait` 등 넷 | `image_crops.kind` 를 `type` 으로 |
  | `hunt_loot_kind` | `hunt_loot_type` | `fragment` · `consumable` · `event` | `hunt_loot_items.kind` 를 `type` 으로 |
  | 새로 만들려던 `remembered_level_kind` | `remembered_level_type` | `symbol` · `hexa` | `remembered_levels.kind` 를 `type` 으로 |
  | 새로 만들려던 `manual_tracked_kind` | `manual_tracked_type` | `daily` · `weekly` · `boss` | `manual_tracked_items.kind` 를 `type` 으로 |
  | `enhancement_type` | `enhancement_api_type` | `cube` · `starforce` · `potential` · `soul_potential` | 강화 표의 `enhancement_type` 을 `api_type` 으로 |
  | `split_mode` | `split_type` | `even` · `ratio` · `excluded`(결정 22) | `boss_split_settings` · `boss_profit_entries` · `boss_drops` 의 `split_mode` 를 `split_type` 으로 |
  | 새로 만들려던 `tracking_mode` | `tracking_type` | `auto` · `manual` | `account_settings.tracking_mode` 를 `tracking_type` 으로 |

- `enhancement_type` 은 끝말이 아니라 앞말을 고친다. 넥슨에서 강화 내역을 받는 API 넷인데, 화면의 분류 다섯인
  `enhancement_category` 와 이름으로 구분되지 않는다. 무엇의 종류인지를 넣는다.
- `shared_progress` 의 칸 `kind` 는 그 칸이 쓰는 enum 이름과 같게 `content_type` 으로 바꾼다. enum 은 그대로다.
- 끝말이 `_category` · `_status` · `_source` · `_grade` · `_cycle` · `_scope` · `_section` 인 enum 은 그대로 둔다. 종류가 아니라 분류 ·
  상태 · 출처 · 등급 · 주기 · 범위 · 구역을 말하는 이름이다.
- `split_mode` 와 `tracking_mode` 도 `_type` 으로 바꾼다(사용자 지정 2026-11-18). 화면의 말이 `분배 방식` · `트래킹 모드` 라서
  `_mode` 로 두는 안이 있었다. 하지만 둘 다 정해진 값 가운데 하나를 고르는 칸이라 다른 enum 과 다르지 않다. 끝말이 둘이면 enum 을
  새로 지을 때마다 어느 쪽인지 따져야 한다. 화면의 말은 그대로 둔다.
- 형과 칸의 이름만 바뀌고 값은 그대로다. 앱이 받는 게임 데이터도 새 이름으로 낸다(결정 43).
- 기기 표의 칸도 1.0.15 의 기기 변환(결정 19)에서 같은 이름으로 바꾼다. `remembered_levels` 의 `kind` 와, `boss_parties` ·
  `boss_party_periods` · `boss_drops` 의 `split_mode` 다. 분배 칸이 있는 세 표는 그때 다시 만드는 표다(결정 23).
- 서버의 모든 표가 정리 대상이다(사용자 지정 2026-11-18). 이 문서가 처음 다룬 것은 기기끼리 맞추는 기록 표였지만, 이름과 칸을
  다듬는 일은 서버의 표 68개와 enum 27개 전체에 한다. 한 번의 서버 작업으로 고친다. 2026-11-18 에 검토를 마친 것은 보스와 아이템
  표이고, 나머지는 옛 이름으로 남아 있다. 표를 하나씩 검토하면서 결정 23 · 27 과 이 결정의 규칙으로 바꾼다.
- `contents.type` · `potential_reset_costs.type` · `usage_events.type` 은 그대로 둔다(사용자 지정 2026-11-19). 표 이름이 무엇의
  종류인지를 이미 말한다. `item_groups.kind` 는 enum 이 아니라 글자라서 그 표를 검토할 때 정한다.

### 결정 33. 이름만으로 뜻을 알 수 없는 enum · 표 · 칸은 이름을 고친다 (사용자 선택 2026-11-18)

  정하고, 정한 것만 여기에 적는다. 아직 정하지 않은 이름은 옛 이름 그대로다.

  |---|---|---|---|
  | enum `spend_form` | `spend_reward_type` | 에픽던전 추가 리워드를 경험치(`exp`)로 받는지 솔 에르다(`sol_erda`)로 받는지 | `form` 만으로는 무엇의 형태인지 알 수 없다 |

  모두 `spend` 로 시작해서 그 말은 칸 이름에 넣지 않는다(결정 36). 가계부 품목(`cashbook_entry_items`)의 `form_key` 는
  `spend_reward_type_id` 로 바꾸고 `spend_reward_types` 의 줄 id 를 적는다(결정 39). 가계부 표는 `spend` 로 시작하지 않아서 표

- 이 문서가 새로 만드는 표의 이름도 같은 기준으로 짓는다(사용자 선택 2026-11-18).

  | 표 | 한 줄의 역할 | 이름을 이렇게 지은 이유 |
  |---|---|---|
  | `boss_profit_calculator_records` · `boss_profit_calculator_record_characters` · `boss_profit_calculator_record_bosses` | 주간 보스 수익 계산기에서 저장한 기록 하나, 그 기록 안의 캐릭터, 그 캐릭터가 계산에 넣은 보스 | 무슨 계산기의 기록인지를 이름에 넣는다. 앱에는 사냥 계산기도 있다 |

### 결정 34. 컨텐츠의 완료 조건은 `contents` 표의 칸에 둔다 (사용자 지정 2026-11-18)

- 완료 조건이 지금은 서버 표에 없고 앱 코드에 있다. 넥슨이 주는 `type` 은 값이 둘(`contents` · `quest`)인데 완료를 가리는 방법은
  넷이다. 그래서 앱 코드가 컨텐츠 key 여섯 개와 카테고리 조건으로 가르고, 같은 조건을 카드와 완료 판정 함수가 따로 구현한다.
  둘이 어긋난 적이 있다(#1092).
- `contents` 표에 칸 `check_type` 을 더한다. 형은 새 enum `content_check_type` 이고 비울 수 없다. 넥슨 응답의 무엇을 확인해 판정하는지를
  가르는 값이다(사용자 지정 2026-11-18).

  | 값 | 넥슨이 주는 값 | 판정 | 2026-11-18 운영의 컨텐츠 41개 |
  |---|---|---|---|
  | `state_only` | 퀘스트 상태 0 · 1 · 2 | 퀘스트 상태만 본다. 2 면 완료, 1 이면 진행 중, 0 이면 시작 안함 | 24개. 일일 퀘스트 17, 주간 퀘스트 5, 유니온 드래곤 2 |
  | `count_only` | 횟수. 퀘스트 상태는 null 이다 | 횟수만 본다. 지금 횟수가 표에 적은 완료 횟수에 닿으면 완료 | 12개. 몬스터파크, 아케인리버 지역 컨텐츠 6, 에픽 던전 4, 길드 주간 미션 포인트 |
  | `both` | 퀘스트 상태와 횟수 | 퀘스트 상태를 먼저 본다. 2 면 횟수와 상관없이 완료, 0 이면 시작 안함이다. 1 이면 진행 중이고 횟수를 읽는다 | 2개. 성실한 조사에 대한 보답, 익스트림 몬스터파커 |
  | `score` | 점수. 퀘스트 상태는 null 이다 | 점수가 0 보다 크면 완료로 판정한다. 화면에는 완료 표시 대신 점수를 보인다(사용자 지정 2026-11-19) | 3개. 길드 지하 수로, 길드 플래그 레이스, 무릉도장 |

- 횟수로 완료를 세는 컨텐츠(`count_only`)는 완료로 세는 횟수를 `contents` 표의 칸에 적는다(사용자 지정 2026-11-18). 지금 횟수가 그 값에
  닿으면 완료다. 넥슨이 주는 최대 횟수에 기대지 않는다.
  - 이 칸은 `count_only` 인 줄에만 값이 있다. 다른 줄에 값이 들어가지 못하게 `CHECK` 로 막는다.
  - 에픽 던전은 지금 횟수가 5 면 완료다(사용자 확인 2026-11-18). 넥슨은 에픽 던전의 진행 중인 횟수를 주지 않고, 다 깨면 `5/0` 으로
    준다. 그래서 넥슨의 최대 횟수로는 완료를 가릴 수 없다.
  - `both` 인 컨텐츠에는 값을 두지 않는다(사용자 지정 2026-11-18). 완료를 퀘스트 상태로 가리고, 진행 중에 보일 최대 횟수는 넥슨이
    함께 준다.
  - 2026-11-18 운영의 `max_count` 에는 몬스터파크 14, 아케인리버 지역 컨텐츠 여섯에 각 1, 에픽 던전 넷에 각 5, 길드 주간 미션 포인트
    10 이 들어 있다.
- 조건을 표에 두는 것은 카드와 진행 링 · today 의 남은 스케줄 · 미완료 스케줄 알림이 같은 조건을 읽게 하려는 것이다.
- `contents` 표는 갈래마다의 표로 나누지 않는다(사용자 선택 2026-11-18). 완료 조건은 갈래가 아니라 컨텐츠마다 갈린다. 아케인리버 ·
  몬스터파크 · 길드는 한 갈래 안에 `check_type` 이 둘씩 있다. 그래서 표를 나눠도 표마다 같은 칸이 필요하다. 갈래 분류는 지금처럼
  `content_categories` 표가 맡는다.
- 넥슨이 실제로 준 값은 기기 백업의 스케줄 캐시에서 확인했다(2026-11-18, 백업 139벌).
  - 성실한 조사에 대한 보답은 시작 전 `0/0` · 상태 0, 조사 1회 `1/2` · 상태 1, 조사 2회 `2/2` · 상태 1, 퀘스트 완료 `0/0` · 상태 2 다.
  - 에픽 던전은 퀘스트 상태가 null 이고 횟수는 `0/0` 과 `5/0` 이 있었다.
  - 익스트림 몬스터파커는 횟수 `0/0` 에 상태 0 과 2 가 있었다. 진행 중인 값은 기록에 없다. 진행 중에는 `1/5` · 상태 1 처럼
    횟수와 상태가 함께 온다(사용자 확인 2026-11-18).
- 길드 플래그 레이스는 점수다. 하지 않으면 0 점이고 하면 1000 점이라 값이 둘 가운데 하나다(사용자 확인 2026-11-18). 1000 점이면
  완료로 판정하고 화면에는 점수를 보인다.
- 길드 주간 미션 포인트는 이름이 포인트지만 횟수로 둔다(사용자 지정 2026-11-18). 넥슨은 `n/10` 으로 준다.
- 지금 앱과 달라지는 것이 있다. 성실한 조사에 대한 보답은 조사 2회(`2/2` · 상태 1)가 진행 중이 된다. 지금 카드는 완료로 그린다.
  무릉도장은 층수가 0 보다 크면 완료로 센다. 지금은 완료를 세지 않고 진행 링의 분모에서 뺀다([[ADR-033]] 결정 5). 길드 지하 수로와
  길드 플래그 레이스는 지금처럼 값이 0 보다 크면 완료다. 횟수로 세는 컨텐츠(`count_only`)에서 횟수가 1 이상이면 완료로 세던 규칙은
  없앤다.
- 완료 횟수 칸의 이름과, 지금 있는 `max_count` · `max_count_override` 칸을 그 칸으로 대신할지는 `contents` 표를 검토할 때 정한다.
- 넥슨의 `type`(enum `content_type`)은 이름과 값을 그대로 둔다(결정 33). 완료 판정에는 쓰지 않는다.
- [[ADR-033]] 결정 5 의 본문과 앱 코드는 구현할 때 함께 고친다.

### 결정 35. 헥사 코어 표는 직업과 종류를 줄 id 로 가리키고, 직업은 표로 따로 둔다 (사용자 지정 2026-11-18 · 11-19)

- 지금 `hexa_job_cores` 는 직업 48개에 코어 14개씩 672줄이다. 직업 이름과 넥슨 타입을 줄마다 글자로 적는다. 솔 야누스와 솔
  헤카테는 모든 직업의 코어인데 직업마다 한 줄씩 48줄이다. 넥슨 타입으로는 종류를 가릴 수 없는 코어 50개는 이름 표
  `hexa_core_name_kinds` 에 따로 적는다.
- 표를 이렇게 둔다.

  | 표 | 지금 | 한 줄 | 줄 수 |
  |---|---|---|---|
  | `jobs` | 없다. 새 표다 | 직업 하나 | 49 |
  | `hexa_cores` | `hexa_job_cores` | 헥사 코어 하나 | 578 |
  | `hexa_core_types` | `hexa_core_kinds` | 헥사 코어 종류 하나 | 6 |

  | `jobs` 의 칸 | 형 | 뜻 |
  |---|---|---|
  | `id` | uuid | 줄 id |
  | `name` | text | 직업 이름. 직업 48개는 넥슨이 주는 이름이고 한 줄은 `전직업` 이다. 겹칠 수 없다 |
  | `is_all_jobs` | boolean | 모든 직업을 뜻하는 줄인지. 참인 줄은 `전직업` 하나뿐이다 |

  | `hexa_cores` 의 칸 | 형 | 뜻 |
  |---|---|---|
  | `id` | uuid | 줄 id |
  | `job_id` | uuid → `jobs` | 이 코어를 가진 직업. 비울 수 없다. 지금은 직업 이름 글자를 적는 칸 `job` 이다 |
  | `name` | text | 넥슨이 주는 코어 이름 |
  | `type_id` | uuid → `hexa_core_types` | 코어의 종류. 지금은 넥슨 타입 글자를 적는 칸 `api_type` 이다. 두 표가 모두 `hexa_core` 로 시작해서 그 말은 칸 이름에 넣지 않는다(결정 36) |
  | `icon_asset_id` | uuid → `assets` | 코어 그림 |
  | `sort_order` | integer | 같은 종류 안의 차례. 지금은 직업 안의 차례다 |

- `hexa_cores` 의 한 줄은 `job_id` 와 `name` 의 조합으로 가린다. `hexa_core_types` 의 칸은 지금 그대로다.
- 직업은 enum 이 아니라 표로 둔다(사용자 선택 2026-11-18). 새 직업이 나오면 줄만 더하면 된다. 다른 표가 직업을 적을 때도 이
  표를 가리킨다.
- 모든 직업이 함께 쓰는 코어(솔 야누스 · 솔 헤카테)는 직업 칸을 비우지 않고 `jobs` 의 `전직업` 줄을 가리킨다(사용자 지정
  2026-11-19). 서버는 그 줄을 `is_all_jobs` 로 찾는다. 이름 글자로 찾으면 글자를 고쳤을 때 공용 코어가 목록에서 빠진다.
- 한 직업의 코어 목록은 그 직업의 코어와 `전직업` 의 코어를 함께 읽어 만든다. 차례는 종류의 차례
  (`hexa_core_types.sort_order`)가 먼저이고, 같은 종류 안에서는 코어의 차례(`hexa_cores.sort_order`)다. 2026-11-18 운영의 직업
  48개는 모두 스킬 코어 둘, 3rd 스킬 코어, 마스터리 코어 넷, 강화 코어 넷, 솔 야누스, 솔 헤카테, 직업 공용 코어의 차례이고 종류
  표의 차례와 같다.
- 차례 칸은 두 표에 모두 둔다(사용자 확인 2026-11-19). 담는 값이 다르다. 종류의 차례는 종류 여섯의 차례이고, 코어의 차례는 한
  직업의 같은 종류 안에서의 차례다. 코어의 차례는 넥슨 hexamatrix 응답의 차례라서 이름순으로 대신할 수 없다. 2026-11-19 운영에서
  이름순과 다른 직업이 마스터리 코어는 48개 중 46개, 강화 코어는 47개다. 코어 줄에 직업 안의 전체 차례를 적고 종류의 차례를
  없애는 방법도 쓰지 않는다. `전직업` 의 코어는 한 줄이라 차례 값이 하나뿐이다. 그 값이 모든 직업에서 강화 코어와 직업 공용 코어
  사이에 맞으려면 직업마다 코어 수가 같아야 한다.
- 직업과 코어를 잇는 표는 두지 않는다(사용자 지정 2026-11-19). 여러 직업이 함께 가진 코어도 직업마다 한 줄씩 둔다. 화중군자
  VI(라라 · 렌 · 호영)와 콜 마스테마 VI(데몬슬레이어 · 데몬어벤져)는 그림 파일의 내용까지 같지만 직업마다 한 줄이다. 이 둘 때문에
  직업군을 분류해 한 줄로 합치지 않는다.
- 이름이 같아도 그림이 다르면 다른 코어다(사용자 지정 2026-11-18). `시그너스 팔랑크스 VI` 는 여섯 직업에 있고 그림이 여섯
  장이다. 이런 이름이 열 개다. 구분하려고 이름을 따로 짓지 않는다. 이름 칸에는 넥슨이 주는 이름을 그대로 두고, 줄 id 와 직업으로
  구분한다. 넥슨 응답과 맞출 때는 캐릭터의 직업이 가진 코어 안에서 이름으로 찾는다.
- 코어 줄이 종류 여섯 가운데 하나를 직접 가리킨다. 넥슨 타입 글자 칸 `api_type` 은 코어 줄에서 없앤다. 넥슨 타입은 종류 줄에
  있다. 이름 표 `hexa_core_name_kinds` 는 없앤다.
- 종류 표의 이름은 끝말 규칙대로 `hexa_core_types` 다(결정 32). 넥슨이 주는 값의 이름 `hexa_core_type` 과 말이 겹치지만, 종류 표가
  넥슨 타입을 칸 `api_type` 으로 따로 든다. 레벨별 비용 표 `hexa_core_level_costs` 의 칸 `kind_id` 는 `type_id` 가 된다(결정 36).

### 결정 36. 같은 말로 시작하는 표를 가리키는 칸은 겹치는 앞말을 빼고 쓴다 (사용자 지정 2026-11-19)

- 다른 표의 줄을 가리키는 칸의 이름은 가리키는 표의 이름에 `_id` 를 붙여 짓는다. 자기 표와 가리키는 표의 이름이 같은 말로
  시작하면 그 말은 칸 이름에서 뺀다. 표 이름에서 이미 읽은 말을 칸에서 다시 쓰지 않는다. `spend_item_options` 가 `spend_items` 를
  가리키는 칸은 `spend_item_id` 가 아니라 `item_id` 다.
- 앞말이 다른 표를 가리키는 칸은 가리키는 표의 이름을 그대로 쓴다. `item_id` 는 `spend` 로 시작하는 표에서는 `spend_items` 의
  줄이고, 그 밖의 표에서는 `items` 의 줄이다. 앞말이 다른 표에서 줄여 쓰면 어느 표의 줄인지 칸 이름으로 알 수 없다.
- 줄인 이름이 다른 표의 줄로 읽히면 구분되는 말을 남긴다. 계산기 기록의 보스 줄이 그 기록 안의 캐릭터 줄을 가리키는 칸은
  `record_character_id` 다. `character_id` 까지 줄이면 `characters` 표의 줄로 읽힌다.
- 2026-11-19 운영 스키마는 이미 이 방식에 가깝다. 다른 표의 줄을 가리키는 칸 71개 가운데 앞말을 뺀 칸이 17개다. 앞말이
  겹치는데 표 이름을 그대로 쓴 칸은 5개다(`boss_difficulty_id` 셋, `nexon_account_id` 둘).
- 이 규칙으로 이름을 정한 칸이다.

  | 표 | 칸 | 가리키는 표 | 지금 이름 |
  |---|---|---|---|
  | `spend_item_reward_types` | `reward_type_id` | `spend_reward_types` | `form_id` |
  | `hexa_cores` | `type_id` | `hexa_core_types` | 없다. 넥슨 타입 글자를 적는 칸 `api_type` 을 대신한다 |
  | `hexa_core_level_costs` | `type_id` | `hexa_core_types` | `kind_id` |
  | `boss_profit_calculator_record_characters` | `record_id` | `boss_profit_calculator_records` | 새 표다 |
  | `boss_profit_calculator_record_bosses` | `record_character_id` | `boss_profit_calculator_record_characters` | 새 표다 |

- 지금 앞말을 빼고 쓰는 칸은 그대로 둔다. `spend_item_options.item_id` · `spend_items.group_id` · `spend_items.tile_id` ·
  `drop_box_contents.box_id` 같은 칸이다. 가리키는 표의 이름이 바뀔 때만 따라 바꾼다(결정 23).
- `boss_difficulty_id` 는 줄이지 않는다. `boss` 로 시작하지 않는 표(`manual_tracked_items` ·
  `party_appointment_bosses`)도 `boss_difficulties` 를 가리킨다. `boss` 로 시작하는 표에서만 줄이면 같은 표를 가리키는 칸의 이름이
  둘이 된다.
- `boss_drops.boss_profit_entry_id` 도 그대로 둔다. 결정 23 · 26 에서 사용자가 정한 이름이고, 이 규칙을 정할 때 줄이는 칸에 넣지
  않았다.
- 가리키는 칸이 아니어도 같다(사용자 지정 2026-11-19). 칸 이름에 표 이름에서 이미 읽은 말을 다시 붙이지 않는다.
  `usage_events` 의 종류 칸은 `event_type` 이 아니라 `type` 이고, `notices` 의 넥슨 id 칸은 `nexon_notice_id` 가 아니라 `nexon_id` 다.
  enum 의 이름은 표 밖에서도 읽히는 이름이라 줄이지 않는다(`notice_type` · `usage_event_type`).

  | 표 | 앞말을 뺀 칸 | 뜻 |
  |---|---|---|
  | `notices` · `image_crops` · `hunt_loot_items` | `type` | 그 표의 줄의 종류(결정 32) |
  | `remembered_levels` | `type` | 심볼의 레벨인지 헥사 코어의 레벨인지(결정 38) |
  | `manual_tracked_items` | `type` | 일간 컨텐츠 · 주간 컨텐츠 · 보스 가운데 무엇인지 |
  | `party_appointment_members` | `type` | 글자로 적은 파티원인지 내 캐릭터인지 |
  | `enhancement_totals` · `enhancement_settled_days` | `api_type` | 넥슨에서 강화 내역을 받는 API 넷 가운데 무엇인지 |
  | `enhancement_totals` | `category` | 화면의 강화 분류 다섯 |
  | `party_appointments` · `party_appointment_exceptions` | `date` | 약속의 날짜(결정 33) |
  | `worlds` | `is_challengers` · `is_event` | 챌린저스 월드인지, 이벤트 월드인지(결정 40) |

  아직 검토하지 않은 표에도 같은 꼴이 있다. `cashbook_entries.entry_date`, `notices.notice_key`,
  `enhancement_anomalies.enhancement_type` · `anomaly_type` 이다. 그 표를 검토할 때 고친다.
- 아직 검토하지 않은 표의 칸은 그 표를 검토할 때 정한다. `nexon_account_keys` · `nexon_account_maple_ids` 의 `nexon_account_id` 는
  앞말이 겹치는데 표 이름을 그대로 쓴 칸이다. `spend_groups.category_id` 는 앞말이 다른 `cashbook_categories` 를 가리키는데 줄여 쓴
  칸이다.

### 결정 37. 강화 합계의 장비는 넥슨이 준 이름 하나로 가린다 (사용자 선택 2026-11-19)

- `enhancement_totals` 의 한 줄은 캐릭터 · 날짜 · 분류 · 장비 이름(`item_name`)으로 가린다. `item_group` 과 `item_key` 는 없앤다.
  서버 표와 기기 표 모두다.
- 지금 `item_group` 은 장비 표에 있는 장비면 `key:` 뒤에 장비 key 를, 없으면 `name:` 뒤에 공백을 지운 이름을 적는다. 서버 표의
  줄을 가리키는 값과 그냥 글자가 한 칸에 섞여 있다(사용자 지적 2026-11-19).
- 장비 key 는 이름에서 다시 구할 수 있는 값이다(결정 27). 넥슨 강화 내역은 장비를 이름으로만 준다. 앱이 그 이름으로 장비 표를
  찾아 key 를 얻는다(`equipmentItemKeyOfApiName`). 화면도 key 가 없으면 이름으로 장비 표를 찾는다
  (`features/cashbook/row-icon.ts`). 서버에는 `item_key` 를 읽는 코드가 없다.
- 장비 그림과 레벨은 읽을 때 이름으로 장비 표에서 찾는다. 장비 표에 나중에 더한 장비도 그 전에 적힌 줄에서 그림이 나온다.
- 이름은 넥슨이 준 글자 그대로 적고 그대로 견준다. 넥슨이 같은 장비의 이름을 띄어쓰기만 다르게 주면 두 줄로 갈린다.
  2026-11-19 로컬 기기 백업 하나의 합계 968줄, 장비 121종에는 한 장비의 이름 표기가 둘인 경우가 없었다.
- 한 줄이 가리는 것은 장비 한 개가 아니라 장비 이름이다. 넥슨 강화 내역에는 장비 하나하나를 구분하는 값이 없다. 이름이 같은
  장비 둘을 같은 날 강화하면 지금처럼 한 줄로 합쳐진다([[ADR-100]] 결정 8).
- 두 칸으로 나누는 안은 쓰지 않는다. 장비 표에 있는 장비는 `item_id` 에, 없는 장비는 `item_name` 에 적는 안이다. 한 줄의 기준이
  둘로 나뉘고, 장비 표에 장비를 더하면 그 전에 이름으로 적힌 줄과 그 뒤에 id 로 적힌 줄이 다른 장비로 남는다.
- 서버 표는 줄이 없어 칸을 바로 없앤다(결정 8). 기기 표는 1.0.15 의 기기 변환(결정 19)에서 두 칸을 없애고 유일 기준을
  `(ocid, history_date, category, item_name)` 으로 다시 만든다.

### 결정 38. 기억한 레벨의 대상은 종류와 줄 id 로 가리킨다 (사용자 지정 2026-11-19)

- `remembered_levels` 의 한 줄은 캐릭터 · `type` · `target_id` 로 가린다. `type` 이 심볼의 레벨인지 헥사 코어의 레벨인지를
  말하고, `target_id` 는 그 종류의 표에 있는 줄 id 다. `symbol` 이면 `symbols.id`, `hexa` 면 `hexa_cores.id` 다. 종류로 표를 고르고
  id 로 줄을 찾는다.
- 지금 기기 표의 칸 `item_key` 는 심볼이면 심볼 key 를, 헥사 코어면 코어 이름을 적는다. 아이템이 아닌데 이름이 `item_key` 이고,
  key 와 이름이라는 서로 다른 값이 한 칸에 있다. 둘 다 줄 id 로 바꾸면 한 칸에 든 값이 모두 줄 id 가 된다.
- 코어 이름은 여러 직업에 같은 이름으로 있을 수 있다. 2026-11-19 운영에 그런 이름이 12개다. 줄 id 는 직업까지 정해진 코어 한
  줄을 가리킨다(결정 35). 기기는 캐릭터의 직업이 가진 코어 안에서 이름으로 줄을 찾아 id 를 얻는다.
- `target_id` 한 칸이 두 표를 가리켜서 DB 의 참조는 걸 수 없다. 서버가 받을 때 `type` 이 말하는 표에 그 id 가 있는지
  확인한다.
- 칸을 둘(`symbol_id` · `hexa_core_id`)로 두고 한 줄에 하나만 채우는 안과 표를 둘로 나누는 안은 쓰지 않는다. 앞의 안은 줄마다 빈
  칸이 하나씩 생기고, 뒤의 안은 칸 구성이 같은 표가 둘이 된다.
- 앱이 받는 게임 데이터는 심볼과 헥사 코어마다 `id` 를 함께 낸다. 보스와 같은 방식이다(결정 19).
- 기기 표도 1.0.15 의 기기 변환(결정 19)에서 `kind` 를 `type` 으로(결정 32), `item_key` 를 `target_id` 로 바꾼다. 줄 id 를
  찾지 못한 줄은 지운다. 기억이 없는 대상은 지금처럼 넥슨이 준 레벨로 다시 채운다.

### 결정 39. 다른 표의 줄을 가리키는 값은 글자가 아니라 줄 id 로 적는다 (사용자 지정 2026-11-19)

- 서버의 표는 모두 줄 id(uuid)를 가진다. 다른 표의 줄을 가리키는 칸에는 그 줄의 id 를 적는다. key 나 이름 글자로 적지 않는다.
  줄을 id 로 바로 찾으려고 모든 데이터를 uuid 와 표로 두는데, id 로 적을 수 있는 값을 글자로 적으면 그렇게 두는 이유가 없어진다.
- 한 칸이 여러 표를 가리키면 종류 칸으로 표를 고르고 id 한 칸으로 줄을 찾는다(결정 38). 한 칸에 key 와 이름처럼 종류가 다른
  값을 섞지 않는다(결정 37).
- 이미 이렇게 정한 칸이다. 보스와 난이도(결정 19), 캐릭터(결정 20), 드롭의 아이템(결정 28), 헥사 코어의 직업과 종류(결정 35),
  기억한 레벨의 대상(결정 38), 가계부 품목의 대상(결정 44), 가계부 기록의 분류(결정 45), 아이템 종류(결정 46).
- `items.category` 는 `group_id` 로 바꾸고 `item_groups` 의 줄 id 를 적는다. 지금은 묶음 key 글자를 적는다. 두 표가 모두 `item` 으로
  시작해서 그 말은 칸 이름에 넣지 않는다(결정 36). 앱이 받는 게임 데이터도 묶음을 줄 id 로 낸다(결정 43).
- `cashbook_entry_items.form_key` 는 `spend_reward_type_id` 로 바꾸고 `spend_reward_types` 의 줄 id 를 적는다. 에픽던전 추가 리워드의
  종류다. 기기 표도 1.0.15 의 기기 변환(결정 19)에서 같이 바꾼다. 종류는 enum 값 둘(`exp` · `sol_erda`)뿐이고 표에 둘 다 줄이
  있으며 지우는 경로가 없어서, 변환에서 줄을 찾지 못하는 품목이 없다. 2026-11-19 에 기기 백업 127벌에 나온 값은 `exp` 하나다.
- `inventory_items.item_key` 는 `item_id` 로 바꾸고 `items` 의 줄 id 를 적는다. 레벨이 있는 반지는 레벨 줄의 id 를 적고
  `ring_level` 칸은 없앤다(결정 28). 기기 표도 1.0.15 의 기기 변환(결정 19)에서 같이 바꾼다. 인벤토리의 아이템은 아이템 표에서
  고른 것만 있고(기기 표의 `item_key` 는 비울 수 없는 칸이다), 서버에는 아이템 줄을 지우거나 key 를 바꾸는 경로가 없어서 변환에서
  줄을 찾지 못하는 일이 없다.
- 월드를 적는 칸 `world_key` 는 `world_id` 로 바꾸고 `worlds` 의 줄 id 를 적는다. `cashbook_entries` ·
  `cashbook_entry_fragment_uses` · `inventory_items` · `enhancement_totals` · `shared_progress` 다섯 표다. 수익 건은 이미 `world_id` 로
  적는다(결정 19). 기기에서 서버로 올리는 표의 `world_key` 도 1.0.15 의 기기 변환(결정 19)에서 같이 바꾼다. 캐릭터 목록처럼 올리지
  않는 기기 표는 이 문서가 다루지 않는다.
  - 월드를 모르는 줄은 지금처럼 빈 값이다. 앱은 넥슨이 준 월드 이름을 월드 표에서 찾아 key 를 얻고, 표에 없는 이름이면 비운다
    (`lib/world/worlds.ts` 의 `worldKeyOfApiName`).
  - 변환에서 줄을 찾지 못하는 값은 없다. 서버에는 월드 줄을 지우거나 key 를 바꾸는 경로가 없다. 2026-11-19 에 기기 백업 148벌의
    모든 표에 나온 월드 key 5개가 운영 표의 20줄 안에 있었다.
- 2026-11-19 에 지금 설계와 운영 스키마에서 이 결정과 다른 칸을 찾았다. 아직 고치지 않았고 표를 검토할 때 고친다.

  | 칸 | 지금 적는 값 | 가리킬 표 |
  |---|---|---|
  | `content_key`(`manual_tracked_items` · `shared_progress`) | 컨텐츠의 key | `contents` |
  | `mvp_grade_history.grade` | enum `mvp_grade` 의 값 | `mvp_grades` |
  | `market_days.scope` · `maspi_basket.scope` | 장비는 거래권 글자, 소비 아이템은 월드 key. 두 가지 값이 한 칸에 있다 | 월드는 `worlds`. 거래권은 표가 없다 |
  | `market_judgements.person` | 넥슨 계정 id · 메이플 ID · 사용자 id 가운데 줄에 있는 것. 세 가지 값이 한 칸에 있다 | `nexon_accounts` · `nexon_account_maple_ids` · `users` |

- 메이플 ID 해시 글자(`maple_id`)로 `nexon_account_maple_ids` 를 가리키는 칸도 줄 id 로 바꿀 수 있다. 지금 서버의 기록 표 넷과

  `maple_id_names`), `cashbook_entry_fragment_uses.source_maple_id` 가 그렇다. 기록을 메이플 ID 에 붙이는 결정(결정 5 · 8)에서
  해시 글자로 가리키기로 한 칸이라, 바꿀지는 따로 정한다. `drop_sale_prices.ocid` 는 없앤다(결정 26).

  표에 없는 장비가 있어 글자다. 사냥 계산기 입력의 `boosts` 는 켠 메소 획득 아이템 여럿을 쉼표로 이은 글자이고 목록이 앱 코드

### 결정 40. 참 · 거짓 칸은 `is_` · `has_` 나 동사로 시작한다 (사용자 선택 2026-11-19)

  낱말만 있는 이름(`valuable` · `event` · `rest`)은 참 · 거짓 칸인지 이름으로 알 수 없다. 이미 정한 `is_season_boss` ·
  `is_all_jobs` · `split_fee_follows_mvp_grade` 와 같은 방식이다.

  | `spend_groups.active` | `is_active` | 열린 묶음인지. 닫힌 묶음은 앱에서 고를 수 없다 |
  | `worlds.challengers` | `is_challengers` | 챌린저스 월드인지. 표 이름이 월드라 `world` 를 붙이지 않는다(결정 36) |

  | `shared_progress.active` | `is_registered` | 등록이 한 번이라도 확인된 컨텐츠인지([[ADR-032]] 결정 4) |

- `is_drop` · `is_equipment` · `is_default` · `is_representative` · `has_tariff` 는 그대로다.
- 수수료율이 등급을 따라가는지의 두 칸은 보스 표에서 정한 말(`follows_mvp_grade`, 결정 23 · 26)을 쓴다. 같은 것은 표가 달라도 같은

  `market_judgements.dummy` 는 시세 표를 검토할 때 정한다.
- 앱이 받는 게임 데이터도 새 이름으로 낸다(결정 43). 기기 표에 같은 칸이 있으면 1.0.15 의 기기 변환(결정 19)에서 같은 이름으로

### 결정 41. 시세를 재는 범위는 아이템의 묶음 종류로 가르고 `items.world_bound` 는 없앤다 (사용자 확인 2026-11-19)

  (`item_groups.kind`)로 안다. 같은 사실을 아이템 줄에 한 번 더 적는 `items.world_bound` 는 없앤다(결정 27).
- 2026-11-19 운영에서 `world_bound` 가 참인 아이템 14개는 모두 소비 묶음이다. 소비 묶음인데 거짓이라 거래권으로 재던 아이템
  가운데 판매가가 있는 것은 12개, 518줄이다. 선택 상자 둘, 에테르넬 방어구 상자 일곱, 교환권 셋이다. 이 12개도 월드마다
  잰다(사용자 확인). [[ADR-071]] 결정 1 의 `나머지 드롭 아이템은 장비로 둔다` 는 이것으로 바뀐다.
- 상자는 1.0.15 부터 드롭 기록이 얻은 아이템 줄을 가리킨다(결정 28). 그래서 새 판매가는 상자 줄에 쌓이지 않는다.
- 기타와 캐시 묶음의 아이템은 2026-11-19 에 판매가가 없어 범위를 정하지 않았다.

### 결정 42. 컨텐츠 표의 표시 칸 셋을 없앤다 (사용자 지정 2026-11-19)

- `contents` 의 `only_when_scheduled` · `trust_registration_flag` · `cumulative_score` 를 없앤다. 2026-11-19 운영의 컨텐츠 41개
  가운데 앞의 둘은 메이플 유니온의 주간 드래곤 퇴치와 PC방 주간 드래곤 퇴치에만, 뒤의 하나는 길드 지하 수로에만 켜져 있다.
- 드래곤 퇴치 둘은 오늘 화면의 공유 컨텐츠 위젯에 그리지 않는다. 스케줄러에 등록돼 있어도 그리지 않는다. 지금은 추적 캐릭터
  가운데 누군가 등록했을 때만 그린다([[ADR-058]] 결정 18).
- 위젯이 그릴 컨텐츠는 칸 없이 가른다. 공유 범위가 캐릭터가 아닌 컨텐츠 가운데 횟수를 확인하는 것(`check_type` 이 `count_only` 나
  `both`)만 그린다. 2026-11-19 운영에서 에픽 던전 넷 · 몬스터파크 · 익스트림 몬스터파커가 여기에 들고, 퀘스트 상태만 확인하는
  드래곤 퇴치 둘(`state_only`)이 빠진다.
- 최근에 활동한 캐릭터인지 판정할 때는 `check_type` 이 `score` 인 컨텐츠를 세지 않는다(`lib/scheduler/scheduler-activity.ts`).
  지하 수로의 점수는 주간 리셋 뒤에도 줄지 않아서, 세면 한 번이라도 한 캐릭터가 계속 활동한 것으로 잡힌다. 길드 플래그 레이스와
  무릉도장도 함께 빠진다. 완료 판정은 이것과 따로다. 점수가 있으면 완료다(결정 34).
- 드래곤 퇴치 둘의 등록은 지금처럼 이번 응답의 등록 값으로 정한다([[ADR-032]] 결정 5, 사용자 선택 2026-11-19).
  `trust_registration_flag` 가 가르던 동작이다. 대상은 칸 없이 가른다. 공유 범위가 캐릭터가 아니고 `check_type` 이 `state_only` 인
  컨텐츠다. 다른 공유 컨텐츠처럼 한 번 등록되면 계속 등록된 것으로 두면, 등록을 풀어도 같은 월드나 같은 메이플 ID 의 캐릭터
  카드에 계속 남는다.

### 결정 43. 서버 표는 1.0.15 를 배포할 때 한 번에 옮기고, 1.0.14 까지의 앱은 그때부터 받지 않는다 (사용자 지정 2026-11-19)

- 기기 간 동기화는 1.0.15 에 나간다. 그 전까지 운영 DB 와 표는 1.0.14 를 위해 지금 그대로 둔다. 서버 표 작업이 먼저 끝나도 새 DB
  와 표는 만들어 두기만 한다.
- 1.0.15 를 배포하면 1.0.14 까지 쓰던 DB 를 1.0.15 의 표에 맞춰 옮기고, 1.0.14 까지의 앱을 없앤다.
- 그래서 새 표는 1.0.14 까지의 앱을 받지 않는다. 그 앱에 지금 꼴의 게임 데이터를 따로 만들어 싣지 않고, 그 앱이 올리는 옛 꼴을
  받아 바꿔 적지도 않는다. 표와 칸은 1.0.15 앱만 보고 정한다.
- 옮기는 일은 한 번이다. 이 문서의 결정들이 적은 이관은 모두 그때 한다. 판매가 없는 줄을 지우고(결정 29), 드롭 판매가 표에서 칸을 빼고(결정 26), 기간 값을 주차 값으로 바꾸고(결정 24), 반지 줄을 레벨 줄로 옮기고(결정 28), 글자 key 를 줄 id 로 바꾼다(결정 39).
- 1.0.15 앱의 기기 변환(결정 19)은 이것과 따로다. 기기의 표는 1.0.15 로 올린 뒤 처음 켤 때 기기에서 바꾼다.
- 이 결정을 받기 전의 설계에는 옛 앱을 함께 받는다는 가정이 들어 있었다. 2026-11-19 에 문서와 지금 서버의 표 68개를 다시 보고
  그 가정으로 적은 문장을 걷었다. 서버 코드에서 옛 앱 때문에 있는 것은 셋이다. 게임 데이터에 함께 싣는 옛 그림 이름, 드롭 판매가
  표에 바로 올리는 경로, 1.0.13 앱의 줄을 사람(`user_id`)으로 찾는 경로다.
- 앱이 받는 게임 데이터는 표와 칸의 이름을 그대로 따른다(사용자 선택 2026-11-19). 지금 설계는 칸 이름을 바꿔도 응답의 이름을
  그대로 두었다. `short_name` 을 `alias` 로, `valid_from` 을 `from` 으로 냈다. 이유 둘 가운데 옛 앱이 영향을 받지 않게 한다는 쪽이
  없어졌고, 같은 값을 표와 앱이 다른 이름으로 부르면 서버가 그 사이에서 이름을 계속 바꿔 적어야 한다. 표기는 지금처럼 낙타
  표기다. `short_name` 은 `shortName` 으로 낸다. 앱은 `GAME_DATA_CONTRACT` 를 올려 새 사본을 받는다(결정 19).
- 옛 앱이 읽던 그림 이름을 없앤다(사용자 지정 2026-11-19). 게임 데이터에 그림 줄 id 와 함께 싣던 `iconFile` · `iconMap` ·
  `emblem` · `portraitSlug` · `backgroundMap` · `backgroundPortrait` 와 크롭의 `slug` 를 싣지 않는다. 그림은 그림 줄 id 로만
  가리킨다. 옛 글자 칸은 옛 앱이 남는 동안만 함께 내기로 한 것이다([[ADR-187]] 결정 4).
- `assets.path` 를 없앤다(사용자 지정 2026-11-19). 옛 앱이 그림을 찾던 경로다. 관리 화면도 그림을 줄 id 로 가린다. 지금 서버는
  디스크의 파일 이름(`<sha256>.<확장자>`)을 만들 때 확장자를 이 경로에서 읽는다. 그래서 확장자를 적는 칸 `extension` 을 더한다(사용자 선택
  2026-11-19). 값은 `png` · `webp` 같은 글자다.
- 새 DB 로 옮길 때 기준 표의 줄 id 를 그대로 옮긴다(사용자 선택 2026-11-19). 그림 · 아이템 · 보스 · 난이도 · 월드 줄이다.
  1.0.14 앱이 기기에 받아 둔 그림은 그림 줄 id 로 저장돼 있어서, id 를 새로 만들면 1.0.15 로 올린 기기가 그림을 모두 다시
  받는다. 옮겨 오는 판매가 줄도 아이템 · 보스 · 월드 줄을 id 로 가리킨다.
- 전환은 이 차례로 한다(사용자 지정 2026-11-19). 1.0.15 를 배포한다. 앱을 점검 중 상태로 잠근다. 옛 DB 를 옮긴다. 새 서버와 새
  DB 를 띄운다. 작업하는 동안 앱을 잠시 쓰지 못하게 한다. 그래서 옛 서버와 새 서버를 함께 띄워 두지 않고, 옮긴 뒤에 옛 DB 에
  적힌 줄을 다시 합치는 일도 없다.
- 지금 앱에는 서버의 점검으로 앱을 잠그는 화면이 없다. 넥슨이 점검 중일 때 머리글 아래에 서는 띠(`NexonMaintenanceBanner`)만
  있다. 점검 잠금은 1.0.14+1 로 먼저 낸다(사용자 지정 2026-11-19, #1093). 화면과 문구, 잠금을 켜고 끄는 방법은 그 이슈에서
  설계한다.
- 심사 기간에는 심사하는 1.0.15 빌드와 TestFlight 빌드가 붙을 서버를 DB 박스에 따로 띄운다(사용자 선택 2026-11-19). 새 서버는
  배포한 뒤에 띄우는데 심사하는 빌드는 새 표가 있어야 동작하고, 심사 중에 점검 화면만 보이면 반려될 수 있다.
  - 운영 중인 서버와 메모리를 나누지 않으려고 DB 박스를 쓴다. 2026-11-19 실측으로 앱 박스는 쓸 수 있는 메모리가 303MB 이고 스왑을
    544MB 쓰고 있다. DB 박스는 564MB 이고 부하가 없다. 지금 서버 컨테이너는 111MB 를 쓴다. 새 DB 도 DB 박스에 만들어 둔다.
  - 바깥에서 들어오는 요청은 지금처럼 앱 박스의 nginx 가 받고, 1.0.15 가 쓰는 주소만 DB 박스로 넘긴다.
  - 1.0.15 바이너리가 보는 서버 주소는 빌드할 때 굳는다. 심사 때와 출시 뒤의 주소가 같아야 하므로, 1.0.15 는 1.0.14 까지의 앱과
    다른 주소를 쓴다. 도메인을 나누면서 생기는 `api` 주소다(#1090). 전환할 때 그 주소가 가리키는 곳을 앱 박스의 새 서버로 바꾼다.
  - DB 박스에는 도커가 없어서 서버를 띄울 준비가 필요하다.
- 아직 정하지 않은 것이 있다.
  - 1.0.14+1 을 받지 않은 기기를 점검 중에 어떻게 막을지(#1093). 받는 지문 목록에서 빼는 방법([[ADR-011]] 결정 6)은 바이너리를
    가리고, 같은 바이너리 위의 옛 번들은 가리지 못한다.
  - 전환한 뒤에 루트 주소의 어느 경로를 남길지. 1.0.14 까지의 앱은 루트 주소(`mapleroutine.store/v1`)를 본다. 그 앱이 업데이트
    안내를 받으려면 루트 주소의 OTA 확인 경로(`/v1/ota/latest` · `/v1/ota/manifest`)가 계속 답해야 한다.

### 결정 44. 가계부 품목의 대상은 종류와 줄 id 로 가리킨다 (사용자 선택 2026-11-19)

- `cashbook_entry_items` 는 품목이 무엇인지를 `target_type` 과 `target_id` 두 칸으로 적는다. `target_type` 이 어느 표의 줄인지를
  말하고, `target_id` 는 그 표에 있는 줄 id 다. 종류로 표를 고르고 id 로 줄을 찾는다(결정 38 · 39).

  | `target_type` | `target_id` 가 가리키는 표 | 지금 `item_key` 에 적는 값 | 쓰는 분류 |
  |---|---|---|---|
  | `hunting_ground` | `hunting_grounds` | 사냥터 key | 사냥 |
  | `item` | `items` | 아이템 key | 사냥 전리품 판매 · 아이템 판매 · 아이템 구매 |
  | `spend_item` | `spend_items` | 지출 항목 key | 컨텐츠 · 이벤트·BM · 버프 · 주문서 |
  | `symbol` | `symbols` | 심볼 key | 심볼 강화 |
  | `hexa_core` | `hexa_cores` | 코어 이름 | 헥사 매트릭스의 스킬 |
  | `hexa_stat` | `hexa_stats` | 헥사 스탯 key | 헥사 매트릭스의 스탯 |

- 지금의 `item_key` 는 분류에 따라 여섯 표의 값을 글자로 적는다. 다섯은 key 이고 헥사 스킬만 코어 이름이다. key 와 이름이라는
  서로 다른 값이 한 칸에 있다(결정 37). 모두 줄 id 로 바꾸면 한 칸에 든 값이 모두 줄 id 가 된다.
- 헥사 매트릭스는 분류 하나에 표가 둘이다. 지금 앱은 스킬인지 스탯인지를 `hexa_activation` 이 비었는지로 가른다
  (`features/cashbook/records.ts` 의 `hexaParts`). `target_type` 이 `hexa_core` 와 `hexa_stat` 으로 갈라서 그 칸을 보지 않아도 된다.
- 종류 칸 없이 줄 id 한 칸만 두고 표를 기록의 분류로 고르는 안은 쓰지 않는다. 헥사 매트릭스를 지금처럼 다른 칸을 보고 갈라야
  하기 때문이다.
- 대상이 없는 품목은 두 칸을 비운다. 기타와 솔 에르다 조각, 직접 친 품목이다. 직접 친 품목의 이름은 지금처럼 `item_name` 에
  글자로 적는다. 한 줄에 `target_id` 와 `item_name` 을 함께 채우지 않는다.
- `target_id` 한 칸이 여섯 표를 가리켜서 DB 의 참조는 걸 수 없다. 서버가 받을 때 `target_type` 이 말하는 표에 그 id 가 있는지
  확인한다. 기억한 레벨과 같은 방식이다(결정 38).
- enum 의 이름은 `cashbook_item_target_type` 이다(결정 32). 사용자가 고른 것은 종류 칸을 두는 구조다. 칸 이름 `target_type` 과
  enum 의 이름 · 값은 Claude 가 붙인 후보다.
- 앱이 받는 게임 데이터는 사냥터 · 아이템 · 지출 항목 · 심볼 · 헥사 코어 · 헥사 스탯마다 `id` 를 함께 낸다. 보스와 같은 방식이다
  (결정 19).
- 기기 표도 1.0.15 의 기기 변환(결정 19)에서 `item_key` 를 `target_type` · `target_id` 로 바꾼다. 종류는 기록의 분류에서 정한다.
  헥사 매트릭스는 `hexa_activation` 이 비었으면 `hexa_core`, 값이 있으면 `hexa_stat` 이다. 코어는 기록이 붙은 캐릭터의 직업이
  가진 코어 안에서 이름으로 찾는다(결정 38).
- 사냥터 · 아이템 · 지출 항목 · 심볼 · 헥사 스탯은 변환에서 줄을 찾지 못하는 일이 없다. 서버의 관리 경로는 이 다섯 표에 줄을
  더하고 고치고 차례를 옮기기만 한다. 줄을 지우거나 key 를 바꾸는 경로가 없다. 앱은 이 표에서 고른 것만 기록에 적는다.
  2026-11-19 에 기기 백업 127벌의 가계부 품목에 나온 key 44개가 모두 운영 표에 있었다.
- 줄 id 를 찾지 못한 헥사 스킬 품목은 지우지 않는다. 코어 이름을 `item_name` 에 옮겨 적고 두 칸을 비운다(사용자 선택
  2026-11-19). 금액 · 레벨 · 조각 개수는 그대로다. 보스 기록과 기억한 레벨은 넥슨 응답으로 다시 채워져서 지우지만(결정 19 · 38),
  가계부는 사용자가 손으로 적은 값이라 다시 채울 곳이 없다. 지금 앱도 헥사 스킬 기록은 표를 찾지 않고 적힌 이름을 그대로 보여
  줘서(`lib/cashbook/hexa-matrix.ts` 의 `hexaTargetOf`) 화면이 달라지지 않는다.
  - 여섯 표 가운데 코어 표(`hexa_job_cores`)만 관리 화면에서 이름을 고치고 줄을 지울 수 있다. 2026-11-19 운영의 672줄은
    2026-10-30 에 처음 넣은 672줄과 직업 · 이름이 모두 같다. 고치거나 지운 적이 없어서 지금은 이런 품목이 없다.
  - 코어 줄을 지울 일은 없다(사용자 확인 2026-11-19). 남는 경우는 1.0.15 를 내기 전에 넥슨이 스킬 이름을 바꿔 표의 이름을 고칠
    때뿐이다.
  - 1.0.15 부터는 기록이 코어의 줄 id 를 들어서, 이름을 고쳐도 기록은 같은 줄을 가리킨다.

### 결정 45. 가계부 기록은 분류를 줄 id 로 가리키고 `entry_type` 칸을 두지 않는다 (사용자 선택 2026-11-19)

- `cashbook_entries.category_key` 를 `category_id` 로 바꾸고 `cashbook_categories` 의 줄 id 를 적는다(결정 39). 두 표가 모두
  `cashbook` 으로 시작해서 그 말은 칸 이름에 넣지 않는다(결정 36).
- 기록의 `entry_type` 칸은 서버 표와 기기 표에서 모두 없앤다. 분류 줄이 수입인지 지출인지(`cashbook_categories.entry_type`)를
  이미 갖고 있어서, 기록에도 두면 같은 값이 두 곳에 있게 된다(결정 27). 수입 · 지출은 분류 줄에서 읽는다.
  - 지금은 분류를 `entry_type` 과 `category_key` 두 칸으로 가린다. 기타(`etc`)가 수입과 지출 양쪽에 있기 때문이다. 줄 id 는 그
    둘을 한 칸으로 가린다.
  - enum `cashbook_entry_type` 은 분류 표가 계속 쓴다.
  - 서버에는 기록의 `entry_type` 을 조건으로 쓰는 조회가 없다. 인덱스 `cashbook_entries_category_date_idx` 는 `category_id` ·
    `entry_date` 로 바꾼다.
- 앱이 받는 게임 데이터는 분류마다 `id` 를 함께 낸다. 보스와 같은 방식이다(결정 19).
- 기기 표도 1.0.15 의 기기 변환(결정 19)에서 `entry_type` · `category_key` 두 칸을 `category_id` 한 칸으로 바꾼다.
  - 기기에는 분류를 담은 SQL 표가 없다. 분류는 서버에서 받은 게임 데이터에 있다. 그래서 기기의 조회는 분류의 줄 id 를 게임
    데이터에서 찾아 조건에 넣는다.
  - 2026-11-19 에 기기 저장 코드에서 `entry_type` 을 조건으로 쓰는 SQL 이 9곳이다(`storage/cashbook-entries.ts` ·
    `storage/income.ts` · `storage/spend.ts` · `storage/fragment-ledger.ts`). 4곳은 분류도 함께 걸러서 분류 id 하나로 된다. 수입
    전체나 지출 전체를 거르는 5곳은 그쪽 분류의 줄 id 목록으로 거른다.
- 변환에서 분류 줄을 찾지 못하는 기록은 없다. 서버에는 분류 줄을 지우는 경로가 없고, 줄의 `entry_type` 과 `key` 는 고칠 수 없다
  (`cashbook-categories.repository.ts`). 기기 표의 `category_key` 는 비울 수 없는 칸이다. 2026-11-19 에 기기 백업 127벌에 나온
  수입 · 지출과 분류의 조합 10개가 모두 운영 표의 15줄 안에 있었다.

### 결정 46. 아이템 종류 칸은 줄 id 로 바꾸고 가계부 품목과 인벤토리에 그대로 둔다 (사용자 선택 2026-11-19)

- 아이템 종류를 적는 칸은 `cashbook_item_types` 의 줄 id 를 적는다(결정 39). 가계부 품목의 `item_kind_key` 는 `item_type_id` 로
  바꾼다. 두 표가 모두 `cashbook` 으로 시작해서 그 말은 칸 이름에 넣지 않는다(결정 36). 인벤토리의 `item_kind_key` 는
  `cashbook_item_type_id` 로 바꾼다. 결정 33 에서 정한 이름 `cashbook_item_type_key` 는 이 이름들로 바뀐다.
- 가계부 품목의 종류 칸은 없애지 않는다. 아이템 줄에서 다시 구할 수 없는 값이다.
  - 직접 친 품목은 아이템 줄이 없어서 종류를 이 칸에서만 안다.
  - 아이템을 골라 적은 품목도 적힌 종류가 아이템 표의 종류와 다를 수 있다. 2026-11-19 에 기기 백업 127벌에서 아이템을 골라 적은
    조합 21개 가운데 1개가 달랐다. `boutique_ticket` 이 기록에는 캐시, 아이템 표에는 소비다.
  - 종류가 수량 단위와 관세 칸이 있는지를 정한다(`cashbook_item_types.unit` · `has_tariff`). 아이템 표에서 읽으면 그 기록을 다시
    열 때 폼이 달라진다.
  - 종류가 빈 품목은 빈 채로 둔다. 아이템 구매 · 판매가 아닌 품목과, 종류를 적기 전의 옛 아이템 구매 · 판매 기록이다.
- 인벤토리에도 종류 칸을 둔다(사용자 선택). 인벤토리는 장비가 아니면 메이플 ID · 월드 · 아이템마다 한 줄이고, 장비는 하나가 한
  줄이다. 이 기준을 DB 가 지키려면 줄 안에 종류가 있어야 한다. 기기 표도 지금 이 칸으로 그 기준을 건다(`storage/inventory.ts`).
  - 종류 칸을 없애고 아이템 줄의 묶음 종류에서 읽는 안은 쓰지 않는다. 기준을 저장하는 코드가 검사해야 하고, 묶음 종류 다섯을
    가계부 아이템 종류 넷으로 잇는 값(장신구는 장비)이 앱 코드(`features/inventory/catalog.ts`)에만 있으며, 관리 화면에서 아이템의
    묶음을 옮기면 이미 넣은 줄의 세는 방식이 함께 바뀐다.
  - 인벤토리 화면이 칸의 종류를 아이템 목록에서 먼저 읽는 것은 그대로다([[ADR-209]]). 저장된 종류는 한 줄의 기준과, 아이템
    목록에 없는 아이템의 종류에 쓴다.
  - 종류가 글자에서 줄 id 로 바뀌므로, 장비가 아닌 줄에만 거는 유일 조건은 장비 종류 줄의 id 로 가른다. 기준 표의 줄 id 는 새 DB 로
    그대로 옮긴다(결정 43). 조건에 id 를 적는 방법은 Claude 가 적은 후보이고 구현할 때 확정한다.
- 종류는 장비 · 소비 · 기타 · 캐시 넷이다. 서버에는 종류 줄을 지우거나 key 를 바꾸는 경로가 없다. 기기 백업에 나온 값은 이 넷과
  빈 값뿐이라 변환에서 줄을 찾지 못하는 일이 없다.

## 번호 기록

- ADR-099 (2026-10-26): 보스 처치 · 가계부 · 강화 합계를 서버로 보내는 결정을 처음 작성하고 구현했다(#507). 사람과 넥슨 계정
  나누기 · 계정 id 헤더 · 과거 기록 묶음 · 드롭 기준일 걷기 · 메모 칸 없애기를 함께 정했다
- ADR-143 (2026-10-30): 보스 처치 · 가계부 기록 · 강화 합계의 전송을 걷고 드롭 가격만 남겼다(결정 1, #800). 세 종류에만 걸리던
  결정을 지우고 남은 결정을 다시 번호 매겼다
- (2026-11-08) 결정 5 에서 키를 부계정으로 등록할 때 키 사용자를 메인 사람 밑으로 합치는 것을 걷었다. 부계정 기록은 부계정 행에 붙고 메인 계정과는 등록
  정보로 잇는다([[ADR-101]] 결정 7)
- (2026-11-10) 결정 5 의 계정 표를 [[ADR-101]] 결정 25 에 맞췄다. 넥슨 계정 줄은 넥슨 ID 하나에 하나이고, 키 해시와 메이플 ID 를 따로
  표로 둔다
- (2026-11-10) 결정 6 에 서버가 `x-nexon-account-id` 를 더 읽지 않는 것을 적었다([[ADR-101]] 결정 21)
- (2026-11-14) 결정 7(가계부 메모 칸 없애기)을 걷었다. 아이템 구매 · 판매에 메모를 적게 되어 칸을 다시 더했다([[ADR-048]] 결정 19, #1002)

  지정, #947 · #612). 강화도 합계와 굳은 날을 서버에 둔다(사용자 지정). 결정 7 ~ 17 을 더했다. 지금 서버에 경로를 더하는 방식 · 칸이 정해진
  표 · 나중에 도착한 쪽을 남기기 · 가계부는 둘 다 남기기 · 다른 사람으로 로그인하면 올린 뒤 비우기 · 설정 범위는 사용자 선택이다
