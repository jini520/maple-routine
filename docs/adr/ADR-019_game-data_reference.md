# ADR-019 게임 데이터의 규칙

> 🟢 유효
> 옛 번호: ADR-006 · ADR-151 결정 2 · 3 · ADR-261 · ADR-280 결정 1 · 2 · 3 · 4 · 7 · 9
> 관련 소스: `lib/game-data/` · `lib/boss/boss-profit-period.ts` 의 `isEffectiveIn` · `isEffectiveAnytimeIn` · `lib/boss/` · `lib/drop/` · `lib/cashbook/` · `lib/scheduler/` · `lib/world/` · `lib/equipment/` · `storage/sqlite/migrations.ts`

## 배경

보스 결정석 가격 · 드롭 표 · 컨텐츠 · 월드 같은 게임 수치는 게임 패치마다 바뀐다. 이 값이 틀리면 수익 계산과
기록이 조용히 틀린다. 그래서 값을 누가 정하는지, 기록이 이 값을 무엇으로 가리키는지, 값이 바뀐 뒤에도 지난
기록이 옛 값을 쓰게 하려면 어떻게 하는지를 정해야 했다. 이 문서는 그 세 가지 규칙을 정한다. 값을 서버에 두고
앱이 받아 오는 방법은 [[ADR-020]] 에 있다.

## 결정

### 결정 1. 게임 수치는 사용자가 확인한 값만 쓴다

결정석 가격 · 드롭 표 · 상자 내용물 · 파티 인원 상한 · 강화 비용 같은 게임 수치는 도메인을 아는 사용자가 확인한
값만 넣는다. AI 가 추정한 값을 넣지 않는다. 틀린 수치는 에러 없이 화면과 기록에 그대로 들어가서, 나중에 찾기 어렵다.

값을 바꾸는 곳은 서버 관리 화면이다([[ADR-020]]). 사용자가 목록에 주지 않은 기존 값은 바꾸지 않는다. 값은 서버
표에만 두고 코드에 박지 않는다. 예를 들어 기본 파티 인원 상한도 코드 상수가 아니라 보스 표의
`rules.defaultMaxPartySize` 다.

### 결정 2. 데이터와 기록은 이름이 아니라 key 로 서로를 가리킨다

key 는 영문 snake_case 이고(`black_mage` · `high_mountain`), 한글 이름을 영어로 옮겨 만든다. 로마자로 옮기면 길고
읽기 어렵다. key 는 화면에 나오지 않는 식별값이라 정확한 번역보다 한 번 정하면 바꾸지 않는 것이 중요하다. 다른 지역에
같은 이름이 있을 수 있는 사냥터는 지역 key 를 앞에 붙인다(`reverse_city_underground_track_1`). 새 key 를 정할 때는
사용자에게 이름과 key 의 짝을 보여 확인받는다.

묶음마다 마스터 표 하나에 key · 이름 · 그림 파일 이름을 적는다. 서버 게임 데이터의 칸으로 보스는 `bosses`, 드롭 아이템은
`dropItems`, 컨텐츠는 `contents`, 장비는 `equipmentItems`, 월드는 `worlds` 다. 드롭 표 · 상자 · 가격표 같은 다른
데이터는 key 로만 가리킨다. 이름을 바꿀 때 한 줄만 고치면 되고, 표끼리 이름이 어긋날 일이 없다.

보스 초상 slug(`portraitSlug`)나 컨텐츠 배경(`backgroundMap`) 같은 그림용 key 는 식별 key 와 따로 둔다. 그림 하나를
여러 식별 key 가 같이 쓸 수 있어서다.

### 결정 3. 기록은 key 와 그때의 이름을 함께 저장하고, 화면은 key 로 지금 이름을 찾는다

SQLite 기록과 Preferences 값은 key 칸을 두고, 이름 칸에는 적을 때의 이름을 그대로 둔다. 화면은 key 로 마스터 표를
찾아 지금 이름을 보이고, 표에 없는 key 면 저장된 이름을 보인다. 그래서 표에서 이름을 바꾸면 옛 기록에도 새 이름이
보이고, 이름을 바꿀 때마다 기록을 옮기는 SQL 을 쓸 필요가 없다.

key 를 얻지 못하면 key 는 `null` 로 두고 원래 이름을 그대로 둔다. 표에 없는 옛 기록, 넥슨 API 가 준 새 이름, 사용자가 직접
친 이름이 그렇다. 이때 화면에는 원래 이름이 나오고 그림은 없으며, key 가 필요한 판정(가격 · 드롭 후보 · 고가 판정)에서는
빠진다. key 를 못 찾았다고 기록을 지우지 않는다. 못 찾은 것이 못 먹은 것은 아니기 때문이다.

### 결정 4. 넥슨 API 이름은 NFC 로 맞추고 공백을 지운 뒤 완전히 같은지로 key 를 찾는다

보스 · 컨텐츠 · 월드 · 장비 · 심볼이 모두 같은 규칙이다. 넥슨 표기와 데이터 표기의 띄어쓰기가 보스마다 달라서
(`검은 마법사` 와 `검은마법사`) 공백을 지운다. 앞부분만 맞추는 비교는 쓰지 않는다. key 를 찾는 일은 응답을 앱
형식으로 바꾸는 곳에서 한 번 하고, 그 뒤로는 key 만 쓴다.

### 결정 5. 데이터 줄마다 유효 기간(`from` · `until`)을 적는다

값이 패치로 바뀌어도 지난 기간의 기록은 그때의 값을 써야 한다. 그래서 값을 덮어쓰지 않는다. 옛 줄에 `until` 을 적고
같은 시점의 `from` 을 적은 새 줄을 더한다. 새로 생긴 것은 `from` 만, 없어진 것은 `until` 만 적는다.

- `from`: 이 시점부터 유효하다. 없으면 처음부터다.
- `until`: 이 시점 전까지 유효하다. 없으면 끝이 없다.
- 값은 KST `YYYY-MM-DD` 이거나 `YYYY-MM-DDTHH:mm` 이다. 시각이 없으면 그 날 00:00 이다.

기간을 적는 데이터는 결정석 가격 · 드롭 표 줄 · 심볼 비용 줄 · 지출 항목 · 컨텐츠 줄 · 보스와 보스 난이도다. 같은
보스 · 난이도의 가격 줄에서 `until` 이 없는 줄이 지금 가격이다.

### 결정 6. 한 기간이 그 줄을 쓰는지는 기간의 첫날로 정하고, 경계가 첫날에 있고 시각까지 적혀 있을 때만 시계를 본다

판정은 `isEffectiveIn(row, periodKey, now)` 하나다. 주간 기간의 첫날은 리셋 목요일, 월간은 그 달 1일이다.
`from <= 첫날 < until` 이면 쓴다. 드롭 기록에는 처치 날짜가 없어 기간 중 어느 날에 먹었는지 구분할 수 없다. 그래서 첫날로 본다.
그 결과 적용일 전 날짜가 하루라도 들어 있는 기간은 옛 줄을 쓴다. 9월 기간의 검은 마법사가 9월 17일에 빠진 교환권을 계속 얻을
수 있는 것이 그 결과다. 반대로 하면 9월 초에 실제로 먹은 기록이 지워진다.

경계 날짜가 기간 첫날과 같고 시각까지 적혀 있을 때만 `now` 를 본다. 패치가 리셋과 다른 시각에 적용되는 경우다.
2026-09-17 패치는 오전 10시에 적용됐지만 주간 리셋은 그 날 00:00 이었다. 그 열 시간 동안 기간은 이미 새 주인데
게임은 패치 전이라, 이 시간에 확정되는 기록은 옛 값을 써야 한다. `now` 를 주지 않으면 시각은 무시하고 그 날 00:00 으로 본다.

### 결정 7. 가격과 드롭 후보는 그 기록의 기간으로 고른다

| 판정 | 함수 | 넘기는 기간 |
|---|---|---|
| 결정석 가격 | `findPriceEntry(boss, difficulty, periodKey, now)` | 기록할 기간 · 그 행의 기간 · 옮겨 갈 다음 주 |
| 드롭 시트의 후보와 고정 보상 | `getBossDropCandidates` · `getBossFixedDrops` | 시트가 연 행의 기간 |
| 컨텐츠 관리 목록 · today 공유 컨텐츠 · 수동 모드 카드 | `effectiveTemplateEntries` 등 | 지금 주간 기간 |
| 가계부 지출 타일 | `spendGroupsOf(category, dateKey)` | 적는 날짜가 든 주간 기간 |
| 보스 · 난이도가 그 기간에 있는지 | `isBossActiveIn` · `activeDifficultiesOf` | 지금 기간 또는 그 행의 기간 |

그래서 동기화가 언제 돌든 9월 10일 주의 처치는 옛 가격으로, 9월 17일 주의 처치는 새 가격으로 확정된다. 이미 기록된 행은
다시 쓰지 않는다. 파티 인원 상한(`getMaxPartySize`)과 보스의 난이도 목록(`getBossDifficulties`)은 기간을 보지 않는다.

기간으로 거르면 이미 있는 데이터를 잃는 곳은 거르지 않는다. 수동 모드에서 이미 추적 중인 컨텐츠는 목록에서 지우지 않고
그리기만 거른다. 옛 기록을 다시 여는 수정 시트와 옛 항목을 다시 분류하는 이관도 기간을 보지 않는다. 걸러 버리면 출시
전에 고른 항목이 저장소에서 사라지거나, 옛 기록의 선택을 되살리지 못한다.

### 결정 8. 기록을 지우는 판정은 기간 전체를 본다

확정 난이도에서 얻을 수 없는 드롭은 기기에서 지운다(`pruneUnobtainableDrops` · `isObtainableDrop`). 이 판정까지 시각으로
판정하면, 9월 17일 오전 9시에 적은 교환권을 10시에 앱이 지운다. 그래서 지우는 판정은 `isEffectiveAnytimeIn` 으로 그
기간 어느 때라도 유효했으면 남긴다. 드롭 후보를 보여 줄 때는 시각까지 보고, 지울 때는 너그럽게 본다. 시각이 없는 경계에서는
두 판정의 답이 같다.

### 결정 9. 이미 확정된 기록에 틀린 값이 들어갔으면 DB 이관으로 고친다

보스 수익 기록은 한 번 적히면 동기화가 다시 쓰지 않는다. 그래서 표를 고쳐도 이미 틀린 값으로 확정된 행은 그대로 남는다.
이럴 때는 DB 버전을 올려 이관으로 고친다. 지금까지 두 번 있었다.

- 버전 7: 2026-09-17 주에 오전 10시 전에 확정됐는데 새 가격이 들어간 행을 옛 가격과 그 분배액으로 되돌린다.
- 버전 8: 카링 노멀과 찬란한 흉성 노멀의 새 가격이 서로 바뀌어 있었다. 그 틀린 값으로 확정된 행만 골라 바로잡는다.
  틀린 값은 어느 가격 줄에도 없던 값이라 가격만 보고 골라낼 수 있다.

이관은 한 번만 돈다. 그 버전을 받지 못한 기기에는 틀린 값이 그대로 남는다.

### 결정 10. 보스의 메소 보상은 결정석 가격이고, 드롭 표에는 넣지 않는다

넥슨 원본의 고정 보상에는 강렬한 힘의 결정 · 메소 · 마일리지가 섞여 있다. 셋 다 드롭 표(서버 게임 데이터의 `bossDrops` 칸)에 넣지 않는다.

- 메소는 결정석을 팔면 들어오는 돈이라 결정석 가격(`crystalPrices` 칸의 `priceMeso`)으로 넣는다(사용자 확인).
  드롭 표에 또 적으면 같은 돈이 두 곳에서 세어져 수익 화면에 두 배로 잡힌다.
- 강렬한 힘의 결정은 바로 결정석 가격 표가 다루는 대상이라 드롭 표에 넣지 않는다.
- 마일리지는 어느 보스에도 적지 않는다. 적기 시작하면 모든 보스를 한 번에 채워야 보스끼리 어긋나지 않는다.

### 결정 11. 새 그림 파일 이름은 기존 이름 규칙을 따른다

새 보스나 아이템의 그림을 넣을 때 이름 규칙을 새로 만들지 않고 이미 있는 규칙에 맞춘다.

| 그림 | 이름 |
|---|---|
| 보스 초상(서버 그림 목록의 `bosses/`) | `portraitSlug` 와 같은 영문 camelCase(`bellona.webp`) |
| 보스 전용 고정 보상 조각 | `frag_eternel_<보스>` |
| 에테르넬 방어구 상자 | `box_eternel_<보스>` |
| 광휘 · 칠흑 보스 세트 | `bright_boss_<부위>` · `dark_boss_<부위>` |

사용자가 준 파일이 이미 webp 이면 다시 인코딩하지 않는다. 손실 압축을 한 번 더 하면 용량은 그대로이고 화질만 떨어진다.
