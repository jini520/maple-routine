# ADR-215: API 키 화면은 **로그인 화면**이다. `features/onboarding` 을 인증·진입·정렬 셋으로 가른다

> 🟢 유효 · 2026-09-04 · **구현 완료**

> 파일 56개가 움직였고 기존 테스트가 전수 통과했다(아래 「검증」). 남은 것은 실기기·시뮬레이터에서
> 세 흐름을 눈으로 보는 것뿐이다.

> 사용자 지정(2026-09-04): "API key를 입력하는 페이지는 사실 이 앱의 로그인 페이지야. 실제로 이
> 서비스가 넥슨의 프렌즈 서비스로 승급되면 oauth2 로그인으로 API key 입력 페이지를 대체할 거야.
> 그리고 관리 캐릭터 선택 페이지도 온보딩 보다는 이 서비스의 핵심이기 때문에 단순히 onboarding의
> 한 step으로 보기 어려워."

**관련**: [[ADR-110]](발급 가이드는 앱 밖) · [[ADR-143]]·[[ADR-144]](캐릭터 선택 화면) ·
[[ADR-211]](스케줄 관리 방법 단계 제거) · [[ADR-214]](개발 단계 키 차단) · [[ADR-116]](키 무효화 사슬)

## 맥락

### 한 이름이 세 가지 일을 덮고 있다

`features/onboarding/` 이 지금 드는 것은 셋이고, 그중 온보딩인 것은 없다.

| 파일 | 실제로 하는 일 |
|---|---|
| `state.ts` · `store.ts` · `format.ts` · `use-api-key-notice.ts` | **인증**. 키 검증·저장·무효화 감지·연결 해제 |
| `resume.ts` | **앱 진입 게이트**. 저장값에서 어느 화면을 열지 파생 |
| `representative-character.ts` | **캐릭터 정렬**. 순수 함수 둘이고 소비자가 다섯 |

### 코드가 이미 그 이름을 안 믿는다

**① 저장 레이어는 이것을 인증이라 부른다.** `storage/api-key.ts` 가 `getAuthConfig` ·
`clearAuthConfig` · `NexonAuthConfig` 다. 기능 레이어만 온보딩이라 부른다.

**② 온보딩 스토어를 밖에서 부르는 다섯 자리 중 넷이 인증 때문이다.**

| 부르는 곳 | 무엇을 | 실제로는 |
|---|---|---|
| `app/ApiKeyNoticeModal.tsx` | `apiKeyNotice` · `confirmApiKeyNotice` | 세션 만료 |
| `components/organisms/CharacterManage/CharacterManageBody.tsx` | `noticeApiKeyIssue('invalid')` | 401 처리 |
| `features/settings/store.ts` | `reset()` (연결 해제) | 로그아웃 |
| `app/AppShell.tsx` · `navigation/RootNavigator.tsx` | `status === 'completed'` | 진입 게이트 |

온보딩 **단계**를 묻는 외부 소비자는 하나도 없다.

**③ 파일이 이미 폴더를 탈출했다.** `ApiKeyNoticeModal.tsx` 는 `app/onboarding/` 이 아니라 `app/`
루트에 산다. 온보딩 밖 아무 화면 위에나 떠야 해서다. 인증이 온보딩보다 넓다는 것을 그 자리가 이미
인정하고 있다.

**④ 정렬 유틸의 소비자 다섯이 전부 온보딩 밖이다.** `compareByName` 을
`content-scheduler` · `boss-scheduler` · `boss-profit` · `schedule-sync` · `character-manage` 가
쓴다. 온보딩은 자기 파일을 자기가 안 쓴다.

### `OnboardingStatus` 여섯은 축 둘을 하나에 눌러 담은 것이다

```
인증 축     awaitingApiKey · verifyingApiKey · error
캐릭터 축   selectingContentCharacters · seedingTracking
completed = 둘 다 섰다
```

`deriveResumeTarget` 이 저장값 **둘**(`authConfig` · `trackedOcids`)을 읽어 이 **한** 축으로
누른다. 축이 둘인 것이 파생 함수에 이미 드러나 있다.

### 언젠가 OAuth2 가 온다

넥슨 프렌즈로 승급되면 키 입력 폼이 OAuth2 로그인으로 갈린다. 시점은 모른다. 지금 구조에서 그
교체는 `OnboardingStatus` · `OnboardingError` · `OnboardingEvent` 를 전부 건드리고, 캐릭터 선택
단계가 같은 열거형 안에 있어 그것까지 함께 흔들린다. 갈라 두면 바뀌는 것이 `features/auth` 하나다.

## 결정

### 결정 1. `features/onboarding` 을 셋으로 가른다

| 지금 | 옮겨갈 자리 | 왜 그 자리인가 |
|---|---|---|
| `features/onboarding/state.ts` · `store.ts` · `format.ts` · `use-api-key-notice.ts` | `features/auth/` | 로그인이다. OAuth2 가 오면 여기만 바뀐다 |
| `features/onboarding/resume.ts` | `features/app-entry/` | 앱을 열면 어느 화면이 서는가 |
| `features/onboarding/representative-character.ts` | `lib/character-order.ts` | 상태 없는 순수 함수 둘. 소비자가 다섯 기능에 걸쳐 있어 어느 기능의 것도 아니다. `lib/face-crop.ts` 옆자리 |
| `app/onboarding/ApiKeyForm.tsx` · `DevelopmentStageKeyModal.tsx` · `api-key-links.ts` | `app/auth/` | |
| `app/ApiKeyNoticeModal.tsx` | `app/auth/` | 루트로 나가 있던 것을 회수한다 |
| `app/onboarding/OnboardingScreen.tsx` 의 키 입력 갈래 | `app/auth/SignInScreen.tsx` | |
| `app/onboarding/ContentCharacterStep.tsx` | `app/character-setup/CharacterSetupScreen.tsx` | 단계가 아니라 화면이다 |
| `app/onboarding/OnboardingStep.tsx` | `components/templates/EntryScroll/` | 화면 둘이 서로 다른 `app/` 디렉터리에서 함께 쓴다. `ScreenScroll` 의 탭바 없는 형제 |

`features/onboarding/` 과 `app/onboarding/` 디렉터리가 사라진다.

### 결정 2. 상태를 두 축으로 가른다

```ts
// features/auth/state.ts
export type AuthStatus = 'signedOut' | 'verifying' | 'signedIn'
```
```ts
// features/app-entry/state.ts
export type EntryStage = 'signIn' | 'characterSetup' | 'ready'
```

`AuthStatus` 에 캐릭터라는 낱말이 없는 것이 요점이다. `OnboardingError` 는 `AuthError` 가 되고
`apiKeyNotice` · `developmentStageBlocked` · `accounts` 는 그대로 인증 쪽에 남는다.

**`'error'` 상태가 없어진다.** 지금 그 값이 그리는 화면은 `awaitingApiKey` 와 **같은 폼**이고
(`OnboardingScreen.tsx:66` 이 두 case 를 붙여 놓았다), 원인은 `error` 필드가 따로 들고 있다. 상태와
필드가 같은 것을 두 번 말하던 자리라 필드만 남긴다.

**방향은 한쪽이다.** `features/auth` 가 로그인 성공 뒤 `useAppEntryStore` 를 부른다. 그 반대는
없다. 인증은 진입 단계를 모르는 채로 서고, 그래서 OAuth2 가 와도 진입 쪽은 안 움직인다.
`features/settings/store.ts` 가 이미 같은 모양으로 스토어를 건너 부른다.

### 결정 3. 진입 화면 셋이 라우트 셋이 된다

`RootStackParamList` 의 `Onboarding` 하나가 `SignIn` · `CharacterSetup` 둘이 되고, `RouteTarget` 의
`kind: 'root'` 가 그 둘을 받는다. `RootNavigator` 가 `EntryStage` 로 어느 것을 그릴지 정한다.

`ROUTE_TABLE` 은 `/onboarding` 행을 `SignInScreen` 으로 두고(웹의 그 경로가 실제로 키 입력이었다)
`origin: 'rn'` 행 하나를 더한다. **웹 17행은 그대로**고 RN 이 5행에서 6행이 된다.

`OnboardingScreen.tsx` 의 status switch 가 통째로 사라진다. 무엇을 그릴지는 화면 파일이 아니라
내비게이터가 정한다.

### 결정 4. 시드는 스토어 상태가 아니라 화면의 대기 상태다

`seedingTracking` 이 스토어에 있는 것은 `OnboardingScreen` 이 단계 switch 로 화면을 갈아 끼웠기
때문이다. 화면이 라우트가 되면 그 화면이 자기 대기 상태를 든다.

이미 반쪽은 그러고 있다. `OnboardingScreen` 의 `isSubmittingContent` 가 저장이 끝나 전이하기 전
구간을 로컬 상태로 들고, 설정판(`SettingsCharactersScreen`)은 저장 진행률 전체를 로컬 상태 +
`ProgressModal` 로 든다. 시드 대기만 스토어에 있을 이유가 없다.

스피너와 문구(`체크리스트를 준비하고 있어요`)는 그대로 그린다.

### 결정 5. 캐릭터 선택 화면 둘은 그대로 둘이다

사용자 지정(2026-09-04)이다. CTA 와 게이트가 실제로 다르다. 첫 설정은 `계속하기` + 최소 1개,
설정은 `저장` + 변경 없음(`isDirty`)이다. 본문은 이미 `CharacterManageBody` + `useCharacterManage`
공용이라 중복이 82줄뿐이고, 하나로 합치면 모드 프롭이 CTA·게이트·헤더 유무 셋을 갈라야 해서 그
분기가 줄인 82줄보다 길어진다.

`SettingsCharactersScreen` 은 `app/settings/` 에 **그대로 둔다**. 라우트가 `/settings/characters`
이고 `use-settings-navigation` · `reload-tab-stores` 를 쓴다. 옮기면 설정 하위 페이지 묶음이 깨지고
얻는 것은 두 파일이 옆자리에 있다는 것뿐이다.

### 결정 6. 사용자가 보는 것은 한 픽셀도 안 바뀐다

이것이 성공 기준이다. 화면 순서·문구·버튼·전환이 전부 지금과 같고, 검증은 **기존 테스트가 전수
통과하는 것**이다. 옮기다 고칠 것이 보이면 여기서 고치지 않고 다음 ADR 로 미룬다. 리팩터 실패와
설계 실패가 한 커밋에 섞이면 어느 쪽이 원인인지 사라진다.

## 기각안

**A. 이름만 바꾸고 스토어는 하나로 둔다.** `useOnboardingStore` 를 `useAuthStore` 로 고치고
끝낸다. 가장 싸다. 그런데 `AuthStatus` 가 여전히 `selectingContentCharacters` 를 갖는다. OAuth2 가
오면 캐릭터 단계가 같은 열거형에서 함께 흔들리고, **그것이 이 문서가 고치려는 것 그 자체다.**

**B. 캐릭터 선택 화면 둘을 하나로 합친다.** 결정 5 를 볼 것.

**C. 진입 게이트를 `navigation/` 에 둔다.** `RootNavigator` 가 유일한 소비자라 그럴듯하다. 그러면
그 디렉터리에 저장소 읽기와 부팅 시점 상태가 들어간다. `navigation/` 은 지금 순수한 화면 표라
(`routes.ts` 머리글이 딥링크조차 안 두기로 못박았다) 그 성질을 깨뜨린다.

## 대가

- **한 커밋에 파일 49개가 움직인다.** 소스 27 · 테스트 22. import 경로가 전부 바뀌어 리뷰가
  어렵다. 그래서 결정 6 이 있다. diff 가 커도 읽는 사람이 물을 것은 하나다. 테스트가 그대로
  통과했는가.
- **스토어가 하나 늘어난다.** `useAppEntryStore` 는 필드 하나와 액션 셋뿐이지만 하이드레이션
  경로가 하나 더 생기고, 인증에서 진입으로 가는 호출 seam 이 하나 생긴다.
- **문서 72개가 온보딩을 말한다.** 전부 안 고친다. `docs/features/onboarding.md` 를
  `auth.md` 와 `app-entry.md` 로 가르고 `docs/README.md` 인덱스를 고치고, **파일 경로가 틀려지는
  자리만** 따라간다. 온보딩이라는 낱말은 「폐기된 정책」 절에 옛 이름으로 그대로 남는다.
- **ADR 여럿이 온보딩 단계를 근거로 적혀 있다**([[ADR-143]]·[[ADR-144]]·[[ADR-211]]·[[ADR-214]]).
  그 결정들은 하나도 안 뒤집힌다. 이름과 자리만 바뀌므로 각 ADR 에 정정을 달지 않고 이 문서가
  대응표를 든다.

## 결과

파일 56개. 커밋 셋으로 갈랐다.

| 커밋 | 무엇 |
|---|---|
| `refactor(lib)` | 정렬 유틸을 `lib/character-order.ts` 로. 소비자 여섯의 import 만 바뀐다 |
| `refactor(auth)` | 나머지 전부. 디렉터리 · 상태 두 축 · 라우트 · 테스트 |
| `docs` | 기능 문서를 둘로 가르고 들어오는 링크를 따라간다 |

**계획에서 벗어난 것 하나**를 적어 둔다. `page-header-title-row-policy` 가 `*Screen.tsx` 라는 파일
이름으로 「페이지 헤더를 갖는 화면인가」를 근사하고 있었는데, `CharacterSetupScreen` 이 이름만
`*Screen.tsx` 이고 헤더 줄은 없다. 화면을 고치는 것은 결정 6 이 막으므로 **그 정책의 경계를 명시적인
목록으로** 바꿨다(진입 화면 둘을 뺀다). 정책이 원래 말하던 경계 그대로다. 그 파일 머리글이 이미
「진입 화면에는 헤더 줄 자체가 없다」고 적고 있었다.

**세지 않은 이득 둘.**

- `OnboardingScreen` 의 status switch 가 통째로 없어졌다. 무엇을 그릴지는 이제 내비게이터가 정한다.
- `'error'` 상태와 `'seedingTracking'` 이 사라져 상태 여섯이 셋(`AuthStatus`) + 셋(`EntryStage`)이
  됐고, 그 둘은 서로를 모른다.
