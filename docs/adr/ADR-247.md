## 맥락

지금 앱이 받는 공지는 운영자가 직접 쓴 것 하나뿐이다. 사용자가 여기에 **게임 공지를 얹기로**
했다. 넥슨 Open API 에 공지 정보 조회가 있고, 서버가 그것을 주기 조회해 새 글을 알림으로
보낸다.

**이 문서를 쓰기 전에 여덟 엔드포인트를 실제로 호출했다**(2026-09-10, 사용자가 준 키). 그
결과가 설계를 세 군데서 바꿨으므로, 결정보다 실측을 먼저 적는다.

### 실측 (2026-09-10)

| 분류 | 목록 | 상세 | 응답 배열 키 | 목록 건수 | 상세 `contents` |
|---|---|---|---|---|---|
| 공지사항 | `/maplestory/v1/notice` | `/notice/detail` | `notice` | 20 | 17,596자 (텍스트 826자) |
| 업데이트 | `/maplestory/v1/notice-update` | `/notice-update/detail` | `update_notice` | 20 | **423,178자** (텍스트 35,384자) |
| 이벤트 | `/maplestory/v1/notice-event` | `/notice-event/detail` | `event_notice` | 19 | 283자 (텍스트 **0자**) |
| 캐시샵 | `/maplestory/v1/notice-cashshop` | `/notice-cashshop/detail` | `cashshop_notice` | 20 | 297자 (텍스트 **0자**) |

목록 항목은 `title` · `url` · `notice_id` · `date`, 상세는 `title` · `url` · `contents` · `date`
이고 이벤트는 `date_event_start`·`date_event_end`, 캐시샵은 `date_sale_start`·`date_sale_end`·
`ongoing_flag` 가 더 붙는다. `date` 는 `2026-09-09T16:24+09:00` 꼴이라 **초가 없고 KST 오프셋이
붙는다.**

여기서 나온 사실 다섯이 아래 결정들의 근거다.

1. **상세는 목록에 지금 떠 있는 것만 답한다.** 목록 밖 id 는 전부 400 `OPENAPI00004` 다
   (공지 149690 · 업데이트 700 · 캐시샵 628 · 지난 이벤트 1329·1330·1350·1355·1356·1368 확인).
   목록에서 빠지는 순간 그 글은 **영영 못 받는다.**
2. **`notice_id` 는 분류마다 번호 체계가 다르다.** 공지 149862 · 업데이트 811 · 이벤트 1374 ·
   캐시샵 642. 번호 하나로는 어느 글인지 못 가린다.
3. **상세 응답에 `notice_id` 가 없다.** 요청에 쓴 값을 우리가 붙여야 한다.
4. **이벤트와 캐시샵 본문은 이미지 한 장이다.** 텍스트가 0자다. 태그를 걷어 텍스트로 저장하는
   설계로 가면 이 두 분류는 본문이 빈칸이 된다.
5. **업데이트 한 건이 423KB다.** 목록 20건에 본문을 실으면 한 응답이 8MB가 된다.

### 이벤트 목록은 진행 중인 것만 든다

19건 전부가 종료일이 오늘 뒤였다. `notice-event` 는 게시판 최근 20건이 아니라 **지금 열려 있는
이벤트**를 준다. 그래서 항목이 목록에서 사라지는 것은 삭제가 아니라 종료이고, 우리 쪽에서
지우는 근거가 되면 안 된다.

썬데이 메이플은 일요일 하루짜리라 **그날의 목록에만 잠깐 뜬다.** 이 문서를 쓰는 목요일에는 네
목록 어디에도 없다.

## 결정

### 결정 1. 저장은 다섯 분류, 구독은 **네 토글**이다 (사용자 지정)

사용자가 정한 토글은 넷이다. 앱 공지사항 · 게임 공지사항 · 업데이트·이벤트 · 캐시샵.

| 분류(`kind`) | 어디서 오는가 | 어느 토글 |
|---|---|---|
| `app` | 운영자가 `/admin` 에서 쓴다 | 앱 공지사항 |
| `game` | `/maplestory/v1/notice` | 게임 공지사항 |
| `update` | `/maplestory/v1/notice-update` | 업데이트·이벤트 |
| `event` | `/maplestory/v1/notice-event` | 업데이트·이벤트 |
| `cashshop` | `/maplestory/v1/notice-cashshop` | 캐시샵 |

**분류를 넷으로 접지 않고 다섯으로 두는 이유는 원본이 다섯이기 때문이다.** 업데이트와 이벤트를
저장 단계에서 합치면 목록 화면이 둘을 가를 방법이 없어지고, 나중에 토글을 쪼갤 때 이미 쌓인
기록을 되살릴 수 없다. 구독은 사용자가 원한 묶음대로 넷이고, 그 묶음은 `kind` 에서 토픽으로
가는 **한 줄짜리 매핑**이다.

### 결정 2. 토픽 `notice` 는 **앱 공지 자리로 남는다**

이미 스토어에 나간 바이너리가 `notice` 토픽을 구독하고 있다([[ADR-146]] 결정 2 · `features/notice/store.ts`).
그 이름을 게임 공지로 돌리면 **업데이트를 안 받은 기기가 어느 날 갑자기 게임 공지를 받는다.**
사용자가 켠 적 없는 알림이다.

| 토글 | 토픽 |
|---|---|
| 앱 공지사항 | `notice` (그대로) |
| 게임 공지사항 | `notice-game` |
| 업데이트·이벤트 | `notice-update-event` |
| 캐시샵 | `notice-cashshop` |

**옛 토글이 새 토글 넷 중 첫째로 이어진다.** 저장된 값(`noticeSubscribed`)이 켜져 있으면 앱
공지가 켜진 상태로 올라오고 나머지 셋은 꺼진 상태다. 마이그레이션이 필요 없는 이유가 그것이다.

### 결정 3. `id` 는 `{분류}-{넥슨 notice_id}` 다

실측 2번 때문이다. 번호 체계가 분류마다 달라 `1374` 하나로는 이벤트인지 다른 무엇인지 모른다.
`game-149862` · `update-811` · `event-1374` · `cashshop-642` 로 짓는다.

앱 공지의 기존 `notice-YYYYMMDD-HHMMSS` 는 **그대로 둔다.** 이미 발송된 공지의 id 를 바꾸면
기기에 쌓인 것과 서버의 것이 갈라져 목록에 같은 글이 두 번 선다.

### 결정 4. 본문은 **블록 배열**로 저장한다. HTML 은 앱에 안 보낸다

실측 4번 때문에 «태그를 걷어 텍스트로» 는 못 쓴다. 이벤트·캐시샵이 빈칸이 된다.

```ts
type NoticeBlock =
  | { type: 'heading'; text: string }
  | { type: 'text'; text: string }
  | { type: 'image'; src: string }
  | { type: 'link'; text: string; href: string }
  | { type: 'table'; rows: string[][] }
```

파싱은 **서버가** 한다. 앱에 HTML 파서를 두면 그 파서가 OTA 를 타야 하고, 넥슨이 마크업을
바꿀 때마다 스토어 심사와 무관한 수정이 앱 배포 축에 실린다. 서버는 그날 고쳐 그날 나간다.

**`body` 는 남긴다.** 블록에서 뽑은 평문이고 쓰임이 셋이다. 푸시 `data` 에 싣는 미리보기 ·
목록의 두 줄 요약 · 블록이 없는 앱 공지의 본문. 상한을 둬서 4KB 페이로드에 들어가게 한다.

**결정 4가 왜 위험을 줄이는가.** 앱은 문자열과 배열만 그린다. 넥슨 본문에 무엇이 들어 있든
`<script>` 도 `<iframe>` 도 앱에 닿지 않는다. 파서가 아는 블록만 통과한다.

### 결정 5. 목록 응답에 **블록을 안 싣는다**

실측 5번이다. `GET /v1/notices` 는 `id`·`kind`·`title`·`body`·`publishedAt`·`link` 만 주고
`blocks` 는 `GET /v1/notices/{id}` 에서만 준다. 지금 앱의 목록 화면은 본문을 안 그리므로 잃는
것이 없다.

### 결정 6. 폴링은 **1분**이고, 발견한 자리에서 상세까지 받는다

실측 1번 때문이다. 목록에서 빠지면 상세를 못 받으므로 **나중에 받아 오는 길이 없다.** 새 항목을
본 그 회차에서 상세를 받아 저장한다.

부하는 문제가 아니다. 4종 × 1분 = 하루 5,760건이고 서비스 단계 키 한도(초당 500건 · 일 2,000만건)의
0.03%다. 넥슨 문서도 이 API 에 대해 **실시간 조회 또는 최소 일배치**를 권장한다고 적어 두었다.

**우리 DB 가 유일한 아카이브가 된다.** 넥슨은 지난 글을 안 준다. 그래서 이 표의 백업은 앱 공지
때와 등급이 다르다.

### 결정 7. 이벤트 알림은 **썬데이만** 보낸다 (사용자 지정)

이벤트는 전부 저장하고 목록에 보이되, **알림은 제목이 썬데이를 담은 것만** 나간다. 관측된 제목이
셋이다 — `썬데이 메이플` · `스페셜 썬데이 메이플` · `스페셜 썬데이`. 그래서 판정은 두 제목의
완전 일치가 아니라 **공백을 지운 제목이 `썬데이` 를 담는가**다. 넥슨이 접두어를 붙이거나 띄어쓰기를
바꿔도 살아남는다.

나머지 이벤트를 알림에서 빼는 이유는 **한 번에 몰려서**다. 8월 20일 패치 날 이벤트 5건과 캐시샵
4건이 같은 8시 14분에 올라왔다. 그 아홉을 다 쏘면 알림이 아홉 번 울린다.

### 결정 8. **첫 수집은 발송하지 않는다**

빈 DB로 처음 도는 회차는 79건 전부가 새 항목이다. 그대로 두면 첫 배포가 알림 79개를 쏜다.
**표가 비어 있는 분류의 첫 회차는 저장만 한다.** 그다음 회차부터 발송한다.

같은 이유로 **`sent_at` 이 NULL 인 것을 다시 쏘지 않는다.** 발송 실패는 다음 회차의 일이 아니라
그 회차에서 끝난다. 재시도를 넣으면 서버가 오래 죽었다 살아날 때 밀린 알림이 한꺼번에 터진다.

**구현하면서 이 규칙만으로는 부족한 것이 드러났다**(2026-09-10). 씨 뿌리는 회차를 실제로 돌려
보니 넥슨이 429 를 줘서 `game` 20건 중 4건만 저장하고 끊겼다. 그러면 **다음 회차의 `hasAny` 가
참이 되어** 남은 16건이 전부 알림으로 나간다. 씨 뿌리기는 «표가 비었는가» 라는 한 순간의 값으로
판정하는데, 그 회차가 중간에 죽으면 그 값이 거짓말을 한다.

그래서 규칙을 하나 더 둔다. **올라온 지 6시간 넘은 글은 저장만 하고 알림을 안 보낸다.** 폴링이
1분이라 정상 회차의 글은 언제나 몇 분 안쪽이고, 이 창을 넓게 잡아도 새 글은 다 잡힌다. 같은
규칙이 **서버가 하루 죽었다 살아나는 경우**도 함께 막는다. 둘 다 «오래된 글을 새 글로 읽는»
같은 실수다.

### 결정 9. 목록에서 사라진 항목을 **지우지 않는다**

이벤트 목록은 진행 중인 것만 든다. 사라짐은 종료이지 삭제가 아니고, 지우면 사용자가 어제 받은
알림을 눌렀을 때 상세가 없다. 종료된 이벤트는 목록에 남고 기간 필드가 지난 날짜를 말한다.

### 결정 10. 권한을 허용한 자리에서는 **넷 중 둘만 켠다**

[[ADR-228]] 결정 3 이 정한 «캐릭터를 고른 직후 한 번 묻는다» 는 그대로다. 바뀌는 것은 허용했을
때 무엇이 켜지는가다. 토글이 하나였을 때는 그것 하나였고 지금은 넷이다.

**앱 공지와 게임 공지를 켠다. 업데이트·이벤트와 캐시샵은 꺼진 채로 둔다.**

가르는 축은 «몰려 오는가» 다. 게임 공지는 13일에 10건이고 그중 핵심이 정기점검 안내라 늦게 알면
의미가 없는 종류다. 업데이트·이벤트와 캐시샵은 패치 날 한꺼번에 올라온다 — 실측으로 8월 20일
8시 14분에 이벤트 5건과 캐시샵 4건이 같은 분에 등록됐다. 묻지도 않고 켜면 그날 알림이 아홉 번
울리고, 그것이 알림을 통째로 끄게 만드는 종류의 경험이다.

**켜는 것만 부르고 끄는 것은 안 부른다.** 기본값이 꺼짐이라 이미 꺼져 있고, 해제를 또 부르면
FCM 왕복이 공짜로 늘면서 실패할 자리만 는다.

### 결정 11. 썬데이 메이플은 **기록으로 쌓는다** (사용자 지시)

사용자가 썬데이 메이플과 스페셜 썬데이 메이플을 **기록으로 남기려 한다.** 넥슨에는 그 기록이
없다 - 일요일이 지나면 진행 중 목록에서 빠지고, 빠지면 상세도 400 이다(맥락의 실측 1번).
**폴러가 그날 잡아 둔 것이 유일한 사본이 된다.**

새로 저장하는 것은 없다. 결정 6 이 이미 이벤트를 상세까지 받아 두고, 결정 9 가 목록에서
사라져도 안 지운다. 여기서 더하는 것은 **그것을 꺼내 보는 길**뿐이다.

```
GET /v1/sunday-maple?limit=20  → { items: SundayRecord[] }
```

**응답이 `Notice` 가 아니다.** 기록에서 가장 중요한 값이 «어느 일요일이었나» 인데 `publishedAt`
은 등록 시각이라 그것과 다를 수 있다. 그래서 이 경로만 `startsAt`·`endsAt` 을 싣고, 정렬 축도
등록일이 아니라 **이벤트 시작일**이다(없으면 등록일로 떨어진다).

**목록인데 `blocks` 를 싣는다.** 결정 5 의 예외다. 썬데이 본문은 이미지 한두 장이라 가볍고,
빼면 기록이 제목만 남아 볼 것이 없어진다.

**판정은 저장할 때가 아니라 조회할 때 돌린다.** 표식을 저장 시점에 박아 두면 빠르지만,
**우리는 이 API 가 주는 썬데이 제목을 아직 받아 본 적이 없다.** 웹 게시판에서 본 셋(`썬데이
메이플` · `스페셜 썬데이 메이플` · `스페셜 썬데이`)으로 세운 판정이라 곧 고칠 것이 거의
확실하고, 조회 때 돌리면 **판정을 고치는 것만으로 이미 쌓인 기록도 함께 바로잡힌다.**

**지난 회차는 못 가져온다.** 기록은 폴러가 처음 도는 일요일부터 쌓인다.

### 결정 12. 알림 **제목은 분류가 정하고 내용에 공지 제목을 싣는다** (사용자 지정)

| 분류 | 알림 제목 | 알림 내용 |
|---|---|---|
| `game` | 새 공지 사항이 올라왔어요. | 9/10(목) 넥슨 정기점검 안내 |
| `update` | 새 업데이트를 확인해보세요. | 클라이언트 1.2.418 업데이트 안내 |
| `event` | 새로운 이벤트가 시작돼요. | 스페셜 썬데이 메이플 |
| `cashshop` | 캐시 아이템이 업데이트 됐어요. | 마스터라벨 플러스 |

공지 제목을 알림 제목에 넣지 않는 이유는 **트레이가 한 줄로 자르기 때문**이다. 거기에
`클라이언트 1.2.418 업데이트 안내 (신규 HEXA 스킬 및…` 이 서면 무엇이 왔는지가 안 남는다.
제목이 «어느 갈래인가» 를 말하고 내용이 «무엇인가» 를 말한다.

**캐시샵만 제목을 손본다.** 원본이 `8월 20일 캐시아이템 업데이트 - 마스터라벨 플러스` 꼴이라
앞이 전부 같다(실측 20건 전부 그 꼴이었다). 그대로 두면 알림 스무 개가 같은 열두 글자로
시작하고 다른 것은 뒤쪽뿐이다. **접두어를 못 떼면 제목을 통째로 쓴다** - 넥슨이 꼴을 바꿨을 때
빈 알림을 보내는 것보다 낫다.

운영자 공지(`app`)는 이 규칙을 안 탄다. `/admin` 과 CLI 가 문구를 직접 받는다.

**이 결정이 [[ADR-146]] 결정 2 의 «문구는 서버가 만든다» 를 구체화한다.** 문구가 서버에 있는
것이 «OTA 로 고친다» 를 어기지 않는 이유는 서버가 심사를 안 받아 OTA 보다 빨리 고쳐지기
때문이고, 그 전제는 그대로다.

## 정정 1. 토글이 **다섯**이고 분류와 1:1이다 (2026-09-10, 사용자 지정)

결정 1 이 **다섯 분류를 네 토글로** 접었다. 업데이트와 이벤트가 `notice-update-event` 를 나눠
썼는데, 그 묶음이 뜻을 잃었다 - **이벤트로 나가는 것이 썬데이뿐**이라(결정 7) 그 한 줄이
«패치 노트와 썬데이» 두 가지를 말해야 했다. 이름을 붙일 수가 없는 줄이었다.

갈랐다. 이제 **분류 하나가 토글 하나이고 토픽 하나**다.

| 토글 (사용자 지정 문구) | 토픽 | `kind` | 권한 허용 시 |
|---|---|---|---|
| 앱 공지 사항 | `notice` | `app` | **켬** |
| 게임 공지 사항 | `notice-game` | `game` | **켬** |
| 썬데이 메이플 | `notice-event` | `event` | **켬** |
| 게임 업데이트 안내 | `notice-update` | `update` | 꺼짐 |
| 캐시 아이템 업데이트 | `notice-cashshop` | `cashshop` | 꺼짐 |

**결정 2 의 `notice` 유지는 그대로다.** 스토어 바이너리가 그 이름을 구독하고 있다.
`notice-update-event` 로는 이제 아무것도 안 보낸다 - 그것을 구독한 것은 개발 기기뿐이라
남은 구독은 조용히 놀고 끝난다.

**결정 10 의 기본 묶음이 둘에서 셋이 된다.** 썬데이가 들어간다. 늦게 알면 의미가 없는 종류라는
근거는 점검 안내와 같다. 업데이트와 캐시샵을 빼는 근거(패치 날 한꺼번에 올라온다)는 그대로다.

**타입이 하나 없어졌다.** `NoticeTopicKey`(넷)와 `NoticeKind`(다섯)를 잇던 `kinds` 배열이
사라지고 `NoticeSubscriptions = Record<NoticeKind, boolean>` 이 됐다.

## 대가

- **개인정보 신고 대상이 는다.** 넥슨 공지 본문을 우리가 저장한다. 공개 정보라 [[ADR-227]] 결정 4의
  판단이 그대로 서지만, Play 데이터 안전과 App Store 라벨은 `비밀인가` 가 아니라 `저장하는가` 로
  가른다.
- **넥슨 개발자 키로 서버가 주기 폴링하는 것이 약관상 되는지는 여전히 확인 전이다**([[ADR-227]]
  열린 질문 그대로). 이 문서가 그 답을 만들지 않는다.
- **파서가 넥슨 마크업에 묶인다.** 스마트에디터가 바뀌면 블록이 이상해진다. 그래서 파서는 아는
  태그만 통과시키고 모르는 것은 버린다. 빈 본문이 깨진 본문보다 낫다.
- **토픽이 넷이 되어 발송 실패가 갈린다.** 하나가 실패해도 나머지 셋은 나가야 한다.

## 구현 (2026-09-10)

두 저장소가 함께 움직인다. 계약은 `Notice` 이고 한쪽만 바꾸면 다른 쪽 타입 검사가 못 잡는다.

| 어디 | 무엇 |
|---|---|
| 서버 `src/html.ts` | HTML → 블록. 실측으로 423KB 가 블록 797개 · 57KB 가 된다 |
| 서버 `src/nexon.ts` | 여덟 엔드포인트를 한 모양으로. 목록 밖 400 을 `null` 로 접는다 |
| 서버 `src/poll.ts` | 회차 하나. 씨 뿌리기 · 6시간 창 · 썬데이 판정이 여기 산다 |
| 서버 `src/db.ts` | `kind`·`blocks`·`source_id`·기간 컬럼. 옛 행은 `kind` 기본값이 `app` |
| 앱 `types/notice.ts` | `NoticeKind` · `NoticeBlock` · 구독 넷 |
| 앱 `features/notice/topics.ts` | 토글 넷과 토픽 이름. 서버와 나눠 갖는 계약 |
| 앱 `app/settings/NoticeBlocks.tsx` | 블록을 그린다. 이미지는 `onLoad` 로 비율을 받는다 |

**실호출로 확인했다.** 씨 뿌리는 회차가 79건을 저장하고 발송 0건(24초), 정상 회차는 목록 4건에
1.1초다. 저장된 79건이 합계 827KB다.

## 열린 질문

- **앱 목록 화면이 다섯 분류를 어떻게 가르는가.** 탭인지 배지인지 정하지 않았다. 지금은 배지
  하나로 두고 건수가 쌓인 뒤에 다시 본다.
- **업데이트 본문 35,000자를 상세 화면이 어떻게 그리는가.** 블록 수백 개를 한 화면에 세우면
  스크롤이 무겁다. 접기나 목차가 필요할 수 있다.
- **`ongoing_flag` 와 판매 기간을 화면이 쓰는가.** 썬데이 기록이 기간을 쓰기 시작했다(결정 11).
  캐시샵의 `ongoing_flag` 는 아직 저장만 한다.
- **썬데이 메이플의 실제 응답을 못 봤다.** 제목·기간·본문이 어떻게 오는지 확인한 뒤 결정 11 의
  판정과 기록 화면을 손봐야 한다. 그전까지 앱에는 제품 화면이 없고 임시 점검 화면으로만 본다.
- **썬데이 이벤트 알림은 보류다**(2026-09-10, 사용자 지시 *"썬데이 이벤트 알림은 일단 보류.
  데이터가 어떻게 생겼는지 봐야돼"*). 결정 7 이 «이벤트는 썬데이만 보낸다» 로, 결정 12 가 그
  문구를 `새로운 이벤트가 시작돼요.` 로 정해 뒀지만 **실물을 보기 전까지는 그대로 두지 않는다.**
  코드는 안 바꿨다 - 아직 배포 전이라 지금은 어차피 아무것도 안 나간다. **배포하는 날 이것부터
  정할 것**: 그날 썬데이 알림을 내보낼 것인가, 문구는 이대로인가.
- **일요일 전에 서버가 떠 있어야 한다.** 그날 못 잡으면 그 회차는 영영 없다.
