# ADR-057+125 운영자 공지와 넥슨 공지

> 🟢 유효
> 옛 번호: ADR-228 결정 1 · 5 · 정정 3 · ADR-230 · ADR-247 결정 1 · 3 · 4 · 5 · 6 · 7 · 8 · 9 · 12 · ADR-266 결정 1 · ADR-277 · ADR-282 결정 1 ~ 9 · ADR-289 결정 2 · 3 · ADR-344 결정 1
> 관련 소스: `features/notice/` · `server/notices.ts` · `nexon/notice/` · `storage/notices.ts` · `storage/notice-banner.ts` · `types/notice.ts` · `app/settings/SettingsScreen.tsx` · `app/settings/SettingsNoticesScreen.tsx` · `app/settings/SettingsNoticeDetailScreen.tsx` · `app/today/NoticeBanner.tsx` · `navigation/AppNavigation.tsx`

## 배경

앱이 보여 주는 공지는 두 가지다. 운영자가 직접 쓰는 앱 공지와, 넥슨이 올리는 게임 공지다. 앱 공지는 점검이나
새 버전처럼 이 앱에 관한 소식이고, 게임 공지는 넥슨 게임에 관한 소식이다. 둘이 섞이면 한 줄만 보고 어느 쪽 이야기인지 알 수 없어서
나눠 보여 준다.

공지는 알림 탭 · today 배너 · 더보기 첫 화면 세 곳에서 사용자에게 보인다. 알림은 꺼 둘 수 있고 설정 하위 화면은
잘 열지 않으므로, 한 곳만으로는 공지를 못 보는 사용자가 남는다. 알림 구독과 권한은 [[ADR-056]] 에 있다.

## 결정

### 결정 1. 공지는 분류 다섯 가지로 나눈다

| 분류(`kind`) | 출처 | 앱이 받는 곳 |
|---|---|---|
| `app` | 운영자가 서버 관리 화면에서 쓴다 | 우리 서버 `GET /v1/notices?kind=app` |
| `game` | 넥슨 `/maplestory/v1/notice` | 넥슨 Open API |
| `update` | 넥슨 `/maplestory/v1/notice-update` | 넥슨 Open API |
| `event` | 넥슨 `/maplestory/v1/notice-event` | 넥슨 Open API |
| `cashshop` | 넥슨 `/maplestory/v1/notice-cashshop` | 넥슨 Open API |

넥슨 원본이 넷이므로 저장과 표시도 다섯으로 나눈다. 업데이트와 이벤트를 저장할 때 합쳐 버리면 목록에서 둘을
나눌 수 없다.

분류가 없는 공지는 `app` 으로 읽는다. 스위치가 하나였던 때 기기에 쌓인 공지와 그때 나간 푸시에는 분류가 없는데,
그때는 운영자 공지밖에 없었기 때문이다.

### 결정 2. 넥슨 공지 넷은 앱이 넥슨 Open API 에서 직접 받는다

넥슨 공지는 넥슨이 주는 목록을 그대로 보여 주면 충분하다. 그래서 앱이 저장된 자격(`currentCredential`)으로
넥슨 목록과 상세를 직접 부른다. 서버가 넥슨 목록을 받는 것은 알림을 보내기 위해서다(결정 11).

- 자격이 없으면 넥슨을 부르지 않고, 그 분류는 실패로 친다.
- 공지 조회는 API 키 오류 안내 모달을 띄우지 않는다. 더보기에 들어올 때마다 조회하므로, 키가 무효가 된 날 탭을 오갈
  때마다 모달이 뜨게 된다. 키 문제는 동기화가 같은 모달로 이미 알린다.
- 넥슨 목록은 지금 게시 중인 글만 준다(분류마다 최대 20건). 이벤트 목록에서 글이 사라지는 것은 삭제가 아니라
  이벤트가 끝났다는 뜻이다.
- 목록 응답의 배열 키가 분류마다 다르다(`notice` · `update_notice` · `event_notice` · `cashshop_notice`).
  `fetchNexonNoticeList` 가 이 차이를 흡수한다. 배열 키가 없는 응답은 빈 목록이 아니라 실패로 던진다. 빈 목록으로
  읽으면 기기의 사본이 지워진다.

### 결정 3. 넥슨 공지 id 는 `{분류}-{notice_id}` 다

`notice_id` 는 분류마다 번호 체계가 달라서(공지 149862 · 업데이트 811 · 이벤트 1374 · 캐시샵 642) 번호만으로는
어느 글인지 알 수 없다. 서버도 같은 형식(`event-1374`)으로 id 를 만들기 때문에, 알림의 `noticeId` 로 앱이 같은 상세를 연다.

- 넥슨 날짜 `2026-09-09T16:24+09:00`(초 없음 · KST)는 ISO UTC 로 바꿔 `publishedAt` 에 넣는다. 서버 공지와 정렬
  기준을 맞추기 위해서다.
- 목록에는 본문이 없으므로 `body` 는 빈 문자열이다.
- 이벤트 · 캐시샵 목록에서는 `thumbnail_url` 과 기간을 함께 읽는다. 기간은 이벤트가 `date_event_*`, 캐시샵이
  `date_sale_*` 다. 이 값들은 앱에서만 쓰고 서버 계약에는 없다.
- 상세 응답에는 `notice_id` 가 없어서, 요청할 때 쓴 번호로 id 를 만든다.

### 결정 4. 서버와의 계약에서 푸시 `data` 와 `Notice` 는 같은 형식이다

```
푸시 data   { noticeId, kind, title, body, publishedAt, link? }   값은 전부 문자열
GET /v1/notices?limit=20&kind=app   → { items: Notice[] }
GET /v1/notices/{id}                → Notice (blocks 포함)
Notice      { id, kind, title, body, publishedAt, link?, blocks? }
```

두 경로가 같은 형식이어야 상세 화면이 출처를 구분하지 않아도 된다. 계약이 두 저장소에 나뉘어 있어서 한쪽만 바꾸면
타입 검사로 잡을 수 없다. 필드를 더할 때는 `types/notice.ts` 와 서버 저장소를 함께 고친다.

- FCM 은 `data` 에 문자열만 받는다. 숫자나 불리언을 넣으면 발송이 거부된다.
- 목록 응답에는 `blocks` 를 넣지 않는다. 업데이트 한 건이 블록 797개 · JSON 57KB 라서, 20건에 넣으면 응답이
  MB 단위가 된다. 본문은 상세에서만 받는다.
- 앱은 아는 블록 종류만 통과시키고 모르는 `type` 은 버린다(`server/notices.ts` 의 `toBlocks`). 서버가 종류를 늘렸는데
  앱이 그것을 모르면, 그 조각만 빠지고 나머지 본문은 그대로 보인다.
- 서버 조회는 8초 안에 끝나지 않으면 실패로 본다. 화면이 이미 사본을 그리고 있어서, 늦게 실패하는 것보다 빨리
  실패하는 편이 낫다.

### 결정 5. 기기에는 분류마다 마지막 성공 응답의 사본만 둔다

공지의 원본은 서버와 넥슨에 있다. 기기에는 마지막으로 받은 응답의 사본만 둔다(Preferences `notices`).

| 조회 결과 | 사본 | 화면 |
|---|---|---|
| 성공 | 그 분류의 사본을 응답으로 통째로 바꾼다. 응답에 없는 id 는 사라진다 | 응답 |
| 성공인데 빈 목록 | 그 분류의 사본을 비운다 | 빈 문구 |
| 실패(오프라인 · 서버 장애 · 계약을 어긴 응답) | 건드리지 않는다 | 사본 |

- **푸시 내용은 기기에 저장하지 않는다.** 푸시로만 쌓인 공지는 서버가 지워도 기기에서 지울 신호가 없다. 실제로
  서버에서 지운 공지가 앱의 목록 · 상세 · 배너에 남은 적이 있다.
- **성공은 HTTP 200 이고 `items` 가 배열인 응답뿐이다.** 계약을 어긴 응답을 성공으로 읽으면 서버 버그 하나로 기기의
  공지가 모두 지워진다. 그래서 `fetchNotices` 는 실패를 `null`, 빈 응답을 `[]` 로 구분해 돌려준다.
- **사본은 분류마다 따로 바꾼다**(`replaceNotices`). 다른 분류는 그대로 두므로, 오프라인에서도 분류마다 마지막 목록이
  보이고 앱 공지가 넥슨 공지에 밀려나지 않는다. 사본은 최대 100건(다섯 × 20)이다.
- 저장 형식은 `notices` 한 칸에 `Notice[]` 이다. OTA 를 되돌려 옛 코드가 실행돼도 같은 칸을 배열로 읽고, 이미 쌓인 값을
  고쳐 쓰는 코드가 필요 없다.
- 같은 분류를 받는 중에 또 부르면 새로 부르지 않고 그 조회를 기다린다. 탭을 빠르게 오가도 호출이 겹치지 않는다.
- 사본은 데이터 삭제 대상이 아니다. 다시 받을 수 있는 조회 캐시라, 지워도 비는 공간이 곧 다시 차기 때문이다([[ADR-053]] 결정 2).

### 결정 6. 상세는 사본을 먼저 그리고, 받은 본문은 기기에 저장하지 않는다

상세 화면(`SettingsNoticeDetailScreen`)은 `noticeId` 하나만 받는다. 알림에서 왔든 목록에서 왔든 같은 것을 그리려면
id 하나로 찾는 방법뿐이다.

1. 사본에서 같은 id 를 찾아 먼저 그린다.
2. 사본에 없어도 조회한다. 20건 밖의 공지나 방금 온 알림은 사본에 없다.
3. id 가 넥슨 형식이면 넥슨 상세를, 아니면 서버 상세를 부른다(`fetchNoticeDetail`).

| 조회 결과 | 화면 | 사본 |
|---|---|---|
| 찾음 | 받은 공지(블록 포함) | 저장하지 않는다 |
| 없음(서버 404 · 넥슨 400 `OPENAPI00004`) | `공지를 찾을 수 없습니다` | 사본과 배너의 닫은 기록에서 뺀다 |
| 실패 | 사본의 공지 그대로 | 그대로 |

넥슨은 목록에 지금 떠 있는 글에만 상세를 주고, 목록에서 내린 글은 400 `OPENAPI00004` 로 답한다. 그래서 이 코드만
없다는 답으로 읽는다. 다른 400(키 무효 등)까지 없다는 뜻으로 읽으면 멀쩡한 공지가 사본에서 빠진다.

본문은 블록이 있으면 블록을, 없으면 사본의 `body` 를 그린다. 둘 다 없으면 조회 중에는 `본문을 받는 중이에요`, 조회가
끝났으면 `본문을 받지 못했어요` 를 적는다. 이벤트와 캐시샵은 본문이 그림 한 장이라 평문이 0자여서, 빈칸으로 두면
고장으로 보인다. `link` 가 있으면 `자세히 보기` 를 눌러 인앱 브라우저로 연다([[ADR-025]] 결정 8).

**헤더 제목은 그 공지의 제목이다.** 다섯 분류가 모두 `공지사항` 이면 무슨 글을 열었는지 본문을 읽어야 안다. 제목은 자르지 않고
줄을 바꾼다. 상세 화면은 제목 전체를 읽으러 오는 곳이기 때문이다. 뒤로 버튼은 제목 첫 줄 높이에 맞춘다. 제목이 헤더로 갔으므로
본문 쪽에는 제목을 다시 적지 않는다. 공지를 찾는 중이거나 찾지 못했으면 헤더에 `공지사항` 을 적는다.

| 분류 | 날짜 · 링크 줄 | 본문 |
|---|---|---|
| 앱 공지 · 게임 공지 · 업데이트 | 본문 카드 위 한 줄. 왼쪽에 발행일(`2026. 9. 10.`), 오른쪽에 `자세히 보기` 버튼(`tint` · `sm`) | 테두리 없는 카드(`Card`) 안 |
| 이벤트 · 캐시샵 | 그림 위 한 줄. 왼쪽에 달력 아이콘과 기간, 오른쪽에 `자세히 보기` 버튼(`tint` · `sm`) | 카드 없이 화면 폭 전체 |

- 이벤트 · 캐시샵의 본문은 그림 한 장이다. 카드 여백 안에 넣으면 그림만 좁아지므로 화면 양끝까지 그린다.
- 이벤트 · 캐시샵에는 발행일 대신 목록 카드와 같은 기간을 적는다(`noticePeriodLabel`). 사용자가 알고 싶은 것은 언제까지
  하는가이기 때문이다. 이벤트에 기간이 없으면 발행일을 적는다.
- 이벤트 · 캐시샵의 헤더 제목은 목록 카드와 같은 제목이다(`noticeDisplayTitle`). 캐시샵은 앞의 날짜 머리를 떼는데, 그 날짜는
  기간 줄이 말해 준다.
- 본문 그림과 배너 그림은 `expo-image` 로 그린다. 넥슨 본문 그림은 1.4~8MB 짜리 PNG 한 장이고(가장 큰 것 1752×13446),
  처음 받을 때 7~11초가 걸렸다(2026-10-29 실측). RN 기본 `Image` 는 받은 그림을 기기에 남기지 않아 열 때마다 다시 받는다.
  `expo-image` 는 기기 디스크에 남겨 두 번째부터는 바로 그리고, 화면 폭에 맞게 줄여 풀어 메모리를 덜 쓴다. 원본 크기로 풀면
  그림 한 장이 약 94MB 다.
- 본문 그림을 받는 동안 그 자리에 목록의 배너 그림(`thumbnailUrl`)을 깐다. 목록과 배너 넘기기에서 이미 받은 그림이라 바로
  그려진다. 상세 조회 응답에는 배너 그림이 없으므로 사본의 값을 이어 받는다. 알림으로 바로 열어 사본이 없으면 빈 자리다.
- `자세히 보기` 를 본문 위에 두는 것은 이벤트 그림이 세로로 길어서다. 본문 끝에 두면 그림을 끝까지 내려야 누를 수 있다. 글 공지도
  같은 자리에 두어 다섯 분류의 링크 자리를 하나로 맞춘다. `link` 가 없으면 버튼만 빠지고 날짜는 남는다.

### 결정 7. 넥슨 본문 HTML 은 앱이 블록으로 바꾸고, HTML 은 그리지 않는다

넥슨 상세의 `contents` 는 HTML 이다. `nexon/notice/contents.ts` 의 `parseContents` 가 이것을 블록 다섯 가지
(`heading` · `text` · `image` · `link` · `table`)로 바꾸고, 화면(`NoticeBlocks`)은 블록만 그린다. 본문에 무엇이 들어
있든 태그가 화면에 그려지지 않는다.

- 이벤트 · 캐시샵 본문은 `<img>` 한 장이라 이미지 블록 하나가 된다. 태그를 지워 평문으로 만들면 빈 본문이 된다.
- 화면에 안 보이는 요소는 안의 글자와 함께 버린다. `style` 이 `opacity: 0` · `display: none` · `visibility: hidden` 인 요소다.
  넥슨 이벤트 · 캐시샵 본문은 그림 속 글자를 검색되게 하려고 그림 위에 투명한 글자(`class="b_srch"`)를 겹쳐 둔다. 앱은 그
  글자를 그림 위에 겹치지 않으므로, 남겨 두면 그림 아래에 줄지어 선다. 이벤트 한 건에 12~64개, 캐시샵 한 건에 238개였다
  (2026-10-29 실측).
- 업데이트 맨 위의 스마트에디터 목차(`class="se-table-of-contents"`)도 버린다. 본문 안에 `목차` 목록이 따로 있어 같은 목록이
  두 번 서고, 목차의 링크는 문서 안 위치(`#toc_…`)라 앱에서 눌러도 갈 곳이 없다.
- 버릴 요소가 끝까지 닫히지 않으면 버리지 않는다. 그 뒤의 본문이 통째로 사라지는 것보다 글자가 몇 개 남는 쪽이 낫다.
- 문단 경계를 살리고, 한 문단 안의 span 조각은 공백 없이 붙인다. 스마트에디터가 글자를 span 수백 개로 쪼개기 때문이다.
- `script` · `style` 은 내용째, 주석은 통째로 버린다.
- `http` 주소는 `https` 로 올리고, 프로토콜 없는 주소는 `https` 로 채운다. 모르는 스킴(`javascript:` · `data:`)은 버린다.
  iOS 는 평문 http 이미지를 막는다.
- 블록은 최대 2,000개다. 업데이트 한 건이 문단 1,200개라 상한이 없으면 그 크기가 그대로 화면으로 간다.

넥슨 마크업이 바뀌면 이 파서를 OTA 로 고쳐야 한다.

### 결정 8. 공지 푸시가 앱에 도착하는 경우는 셋이고, 어느 경우도 기기에 쓰지 않는다

`use-notice-delivery.ts` 가 셋을 한 파일에서 다룬다. 하나라도 빠지면 특정 상황에서만 탭이 동작하지 않는데, 이것은 코드를
읽어서는 안 보이고 기기에서 그 상황을 겪어야 드러난다.

| 언제 | 받는 곳 | 하는 일 |
|---|---|---|
| 포그라운드에서 도착 | `onMessage` | today 배너의 `refresh()` 를 부른다. 보던 화면을 밀어내지 않는다 |
| 백그라운드에서 탭 | `onNotificationOpenedApp` | 상세 화면을 연다 |
| 꺼져 있다가 탭으로 열림 | `getInitialNotification` | 상세 화면을 연다. 마운트당 한 번만 읽는다 |

- 포그라운드에서는 FCM 이 `notification` 을 OS 에 넘기지 않아 알림이 뜨지 않는다. 아무것도 하지 않으면 화면에 아무 일도
  일어나지 않으므로 배너가 서버에서 다시 받아 온다. 그래서 공지 푸시 한 건이 서버 요청 한 건이 된다.
- 백그라운드에서 도착만 하고 탭하지 않은 공지는 JS 가 받지 못한다. OS 가 직접 알림을 그리고 JS 를 깨우지 않기 때문이다.
  이 공지는 다음 조회에서 들어온다.
- `parseNotice` 는 `noticeId` · `title` · `publishedAt` 이 있어야 공지로 읽는다. 본문은 필수가 아니다. 이벤트와 캐시샵은
  본문이 비어 있어서, 필수로 두면 그 알림을 탭해도 상세가 열리지 않는다. 공지가 아닌 푸시는 조용히 무시한다.
- 꺼진 앱을 알림으로 열면 상세 화면이 아직 스택에 없을 수 있다. 진입 게이트가 앱이 열린 뒤에만 상세 화면을 등록하는데,
  `getInitialNotification` 은 그보다 먼저 응답할 수 있기 때문이다. 그래서 `AppNavigation` 이 이동할 id 를 보관해 두었다가,
  스택에 등록된 화면 이름 목록에 `SettingsNoticeDetail` 이 생긴 뒤에 연다. 연 뒤에는 그 id 를 기억해, 다시 그려질 때
  같은 상세를 또 열지 않는다.

### 결정 9. today 배너는 가장 최근 앱 공지 하나만 보여 준다

today 머리 아래, 위젯 격자 위에 공지 하나를 보여 준다(`NoticeBanner`). 알림을 끈 사용자와 설정 화면을 열지 않는 사용자에게도
새 공지를 보여 주려는 것이다. 알림 구독과 상관없이 보인다.

- **후보는 사본에서 발행일이 가장 늦은 앱 공지 하나다**(`pickBannerNotice`). 넥슨 공지는 매일 들어와서, 분류를 가리지
  않으면 배너가 늘 넥슨 공지가 되고 운영자 공지가 첫 화면에 나오지 못한다. 발행일을 읽을 수 없는 공지는 맨 뒤로 보낸다.
  저장 순서에 기대지 않고 고를 때마다 발행일을 비교한다.
- **그 공지를 닫았으면 배너를 보여 주지 않는다.** 옛 공지를 대신 올리지 않는다. `다시 보지 않기` 는 이 배너를 없애 달라는
  뜻이지 다음 공지를 보여 달라는 뜻이 아니고, 누르자마자 다른 글이 뜨면 안 닫힌 것처럼 보인다. 지난 공지는 더보기에서 읽는다.
- 보여 줄 공지가 없으면 아무것도 그리지 않는다. 빈 상자를 두면 위젯 격자가 이유 없이 아래로 밀린다.
- **배너 스토어**(`banner-store.ts`)는 두 동작을 가진다. `load()` 는 기기만 읽고, today 에 들어올 때마다(포커스) 부른다.
  `refresh()` 는 서버에 `kind=app` 20건을 요청하고, 성공하면 사본을 바꾼 뒤 다시 고른다. 당겨서 새로고침과 포그라운드
  푸시 도착(결정 8)에서 부른다. 푸시 내용을 저장하지 않으므로 배너가 새 공지를 알려면 서버에 물어야 한다.
- **닫은 기록**(Preferences `dismissedNotices`)은 공지를 닫은 것이 아니라 배너를 닫은 기록이다. 목록과 상세에는 그대로 보인다. 최근
  50건까지 남기고, 앱 공지 조회가 성공하면 응답에 없는 id 를 뺀다(`saveNoticeResponse`). 다른 분류의 응답으로 정리하면
  그 응답에 앱 공지 id 가 없어 닫은 기록이 전부 빠지고, 닫은 배너가 되살아난다. 닫은 기록은 데이터 삭제 대상이 아니다.
  닫았다는 사실은 기기에만 있다.

배너의 생김새는 다음과 같다.

- 좌우 여백 없이 화면 끝까지 닿고 모서리는 둥글리지 않는다. 화면 가장자리에 닿는 상자에 둥근 모서리를 주면 잘린 것처럼
  보인다. 바탕은 `bg-surface` 이고 안쪽 여백은 네 면 모두 16 이다. 격자 좌우 여백과 같은 값이라 배지의 왼쪽 선이 아래
  타일들과 맞는다. 그래서 배너는 격자 래퍼 밖에 두고 여백을 직접 준다.
- 접힌 상태에는 확성기 아이콘 · `새 공지` 배지 · 발행일 · 제목 한 줄이 있다. 머리를 누르면 펼쳐지고, 다시 누르면 접힌다.
  펼치면 본문 두 줄과 `다시 보지 않기`(`text`) · `자세히 보기`(`primaryOutline`) 버튼이 나온다.
- 머리를 눌러도 상세로 가지 않는다. 바로 가면 `다시 보지 않기` 를 고를 수 없다.
- 버튼은 `sm`(32) 이고 위아래로만 `hitSlop` 6 을 줘서 누르는 영역을 44 로 맞춘다. 좌우로 넓히면 나란히 놓인 두 버튼의
  누르는 영역이 겹친다. 채운 버튼을 쓰지 않는 이유는 배너 안에서 버튼이 본문보다 먼저 눈에 띄기 때문이다.
- 펼친 상태는 공지 id 로 기억한다. 불리언으로 두면 펼친 채로 새 공지가 오면 새 공지도 펼쳐진 채로 보인다.

### 결정 10. 더보기 첫 화면에 소식 섹션 다섯을 보여 준다

더보기(`SettingsScreen`)에서 매일 바뀌는 것은 소식뿐이라 맨 위에 둔다. 섹션 순서와 이름은 사용자가 정했다.

| 섹션 이름 | 분류 | 보여 주는 것 |
|---|---|---|
| `NOTICE` | `app` | 최근 글 3줄 |
| `진행 중인 이벤트` | `event` | 배너 가로 넘기기 |
| `캐시샵 업데이트` | `cashshop` | 배너 가로 넘기기 |
| `공지 사항` | `game` | 최근 글 3줄 |
| `업데이트` | `update` | 최근 글 2줄 |

- 섹션 제목 줄의 `전체` 를 누르면 그 분류의 목록 화면(`SettingsNotices`)이 열리고, 섹션 이름이 그 화면의 제목이 된다.
- 글 줄은 제목 한 줄(넘치면 말줄임)과 날짜이고, 누르면 상세로 간다. 오른쪽에 chevron 은 없다.
- 더보기에 들어올 때마다(포커스) 사본을 먼저 그리고 다섯 분류를 다시 받는다. 넥슨 4번 · 서버 1번이다. 분류마다 따로
  끝나고, 성공한 분류만 화면을 바꾼다. 사본을 다 읽은 뒤에 조회한다. 순서가 바뀌면 늦게 끝난 사본 읽기가 방금 받은 목록을
  덮는다.
- 각 섹션의 상태는 아직 모름(`null`)과 받았는데 없음(`[]`)을 구분한다. 모르는 동안은 스켈레톤을, 없으면
  `아직 받은 {섹션 이름}이/가 없습니다` 를 그린다. 둘을 나누지 않으면 받아 보기도 전에 없다고 표시하게 된다. 조사는 이름의
  끝 글자 받침으로 고르고, 영문으로 끝나면 끝 글자가 모음일 때 `가` 다(`NOTICE가`).
- 글이 없는 섹션도 숨기지 않는다. 섹션이 사라지면 화면 순서가 바뀐다.
- 들어올 때의 조회는 실패해도 알리지 않는다. 당겨서 새로고침은 다섯이 모두 실패했을 때만 `소식을 불러오지 못했습니다` 토스트를
  띄운다. 키가 없으면 넥슨 넷이 늘 실패하므로, 일부 실패에도 알리면 앱 공지를 잘 받고도 매번 토스트가 뜬다.

**배너 넘기기**(`NoticeBannerRail`)는 이벤트와 캐시샵에 쓴다. 두 분류는 본문이 그림 한 장이라 제목만 보고는 무슨 이벤트인지
알기 어렵다.

- 칸은 화면 양끝까지 여백 · 테두리 · 둥근 모서리 없이 닿는다. 섹션 제목 줄은 여백 안에 놓인다.
- 칸 비율은 분류에 따라 정해진다. 이벤트 285:120, 캐시샵 443:130 이고(`noticeBannerRatio`), 그림은 `contain` 으로 넣는다. 그림을
  받은 뒤 비율을 계산하면 목록이 그림마다 흔들린다.
- 칸 왼쪽 위에 제목 캡슐을 얹는다. 한 줄이고 넘치면 말줄임이며, 바탕은 `rgba(20, 16, 12, 0.58)`, 글자는 흰색이다. 그림 위에서
  읽혀야 해서 테마 색을 쓰지 않는다. 그림을 가리는 넓이가 가장 작은 방식이라 골랐다.
- 그림을 못 받으면 같은 비율의 빈 칸과 캡슐만 남는다. 칸 높이가 비율로 정해지므로 한 칸만 높이가 달라지지 않는다.
- 한 칸씩 넘긴다(`pagingEnabled`). 칸 폭을 스크롤 상자 폭과 같게 두고 칸 사이 간격을 두지 않는다. 간격이 있으면 넘길
  때마다 그만큼 어긋난다.
- 마지막 배너에서 넘기면 첫 배너로, 첫 배너에서 거꾸로 넘기면 마지막 배너로 간다. 양끝에 사본 칸을 하나씩 두고, 넘기기가
  멈췄을 때 사본 칸에 있으면 같은 그림의 실제 칸으로 애니메이션 없이 옮긴다. 사본 칸은 스크린리더가 읽지 않는다.
  배너가 하나면 사본과 점을 두지 않는다.
- 넘길 때 새 배너가 이전 배너를 덮으며 들어온다. 이전 배너는 같은 방향으로 새 배너의 40% 속도로 밀리며 옅어지고
  (`0.3 + 0.7 × (1 − d)³`), 새 배너는 30% 에서 시작해 60% 넘겼을 때 완전히 진해진다. 옅게 할 때는 배너의 투명도가
  아니라 그 위에 덮은 `bg-surface` 막의 투명도를 바꾼다. 배너 자체를 투명하게 하면 두 배너가 겹친 부분만 진해진다. 이 두 칸 말고는
  숨겨, 이전 배너가 옅어질 때 아래 칸이 비치지 않게 한다. 값은 `notice-banner-motion.ts` 에 있다.
- 그림 안쪽 아래에 점을 얹는다. 점은 흰색 72%, 현재 표시는 주황이다. 넘기는 동안 표시가 다음 점 쪽으로 늘어났다가
  줄어든다(`wormBar`). 그림 밖에 두면 배너 아래에 빈 띠가 생긴다.
- 배너 칸 · 막 · 점 표시의 애니메이션 상자는 `Animated.createAnimatedComponent(View)` 다. NativeWind 가 감싼 `Animated.View`
  에 정적 스타일과 애니메이션 스타일을 배열로 넘기면 정적 쪽이 사라져 칸 폭이 빠진다.

**목록 화면**(`SettingsNoticesScreen`)은 받은 분류만 그린다. 열 때 한 번 받고, 당겨서 다시 받는다.

- 이벤트 · 캐시샵은 카드(`NoticeBannerCard`)를 세로로 쌓는다. 테두리 없는 `Card` 안에 그림, 제목(왼쪽 정렬, 최대 두 줄),
  달력 아이콘과 기간을 위에서부터 놓는다. 구분선은 두지 않는다. 카드끼리는 바탕색과 카드 색의 차이로 갈리고, 카드 안의 제목과
  기간은 글자 크기와 색으로 갈리기 때문이다. 기간은 한국 시간 날짜로 `2026.09.10 ~ 2026.09.16` 처럼 적는다. 넥슨이 끝을 `23:59+09:00` 으로 주므로 기기
  시간대로 적으면 한국 밖에서 끝 날짜가 하루 밀린다. 캐시샵에 기간이 없으면 `상시 판매` 를, 이벤트에 기간이 없으면 기간 줄을
  그리지 않는다.
- 캐시샵 제목은 앞의 `n월 n일 캐시아이템 업데이트 - ` 를 떼고 적는다(`noticeDisplayTitle`). 모든 캐시샵 제목이 이렇게 시작해서
  좁은 카드에서는 상품 이름이 뒤로 밀린다. 형식이 다르거나 떼고 나서 빈 문자열이면 원래 제목을 쓴다. 상세 화면의 헤더 제목도
  이 제목이다(결정 6).
- 앱 공지 · 게임 공지 · 업데이트는 더보기와 같은 글 줄이지만 제목을 자르지 않는다. 목록 화면은 제목 전체를 읽으러 오는 곳이다.

### 결정 11. 서버는 1분마다 넥슨 목록을 받아 새 글만 알린다

`maple-routine-server` 의 `src/modules/notices/notice-poller.ts` 가 1분마다 넥슨 공지 넷의 목록을 받는다. 넥슨은 목록에서
내린 글의 상세를 주지 않아서, 나중에 받을 수 없다. 그래서 새 글을 본 회차에 처리한다.

- 처음 보는 `{분류}-{notice_id}` 만 저장한다. 목록에서 사라진 글은 지우지 않는다.
- 아래 경우에는 저장만 하고 알리지 않는다.
  - 그 분류의 표가 비어 있는 첫 회차. 첫 배포 때 알림이 수십 개 나가지 않게 하려는 것이다.
  - 올라온 지 6시간이 넘은 글. 첫 회차가 넥슨의 429 로 중간에 끊기거나 서버가 오래 멈췄다가 다시 켜졌을 때, 밀린 글이 한꺼번에
    알림으로 나가지 않게 한다.
  - 썬데이 메이플이 아닌 이벤트. 이벤트는 패치 날 몰려 올라와서 다 보내면 알림이 여러 번 울린다. 썬데이 메이플은 공백을 지운
    제목에 `썬데이` 가 들어 있는지로 판단한다(`isSundayMaple`). 목록에는 모든 이벤트가 보인다.
- 발송이 실패해도 다음 회차에 다시 보내지 않는다. 다시 보내면 서버가 오래 멈췄다가 다시 켜질 때 밀린 알림이 한꺼번에 나간다.
- 상세는 썬데이 메이플만 받아 블록과 기간을 저장한다(`GET /v1/sunday-maple` 로 내준다). 나머지 넥슨 공지는 목록 값만 저장한다.
  앱이 넥슨 상세를 직접 받으므로 서버가 다른 본문을 저장할 이유가 없다.

알림 제목은 분류에 따라 정하고, 공지 제목은 알림 내용에 넣는다. 트레이는 제목을 한 줄로 자르므로, 공지 제목을 알림 제목에 넣으면 무엇이
왔는지 알 수 없다.

| 분류 | 알림 제목 | 알림 내용 |
|---|---|---|
| `game` | `새 공지 사항이 올라왔어요.` | 공지 제목 |
| `update` | `새 업데이트를 확인해보세요.` | 공지 제목 |
| `event` | `새로운 이벤트가 시작돼요.` | 공지 제목 |
| `cashshop` | `캐시 아이템이 업데이트 됐어요.` | 앞의 `n월 n일 캐시아이템 업데이트 - ` 를 뗀 제목. 못 떼면 원래 제목 |

운영자 공지는 이 규칙을 따르지 않고, 운영자가 쓴 알림 문구를 그대로 쓴다.

### 결정 12. 배너 넘기기는 보이지 않는 칸과 점을 다시 그리지 않게 만든다

더보기에는 배너 줄 둘에 칸이 스무 개 넘게 있다. 아무 조치 없이 두면 가만히 있거나 화면을 스크롤하기만 해도 기기가 계속 연산한다.

- **숨은 칸의 스타일에는 `transform` 을 넣지 않는다**(`bannerSlideStyle`). 숨은 칸은 `{ opacity: 0, zIndex: 0 }` 만 돌려준다.
  Reanimated 는 이전 스타일과 얕게 비교해 다를 때만 반영하는데, `transform` 은 부를 때마다 새 배열이라 값이 같아도 다르다고
  본다. 그러면 스크롤할 때마다 숨은 칸이 전부 다시 반영된다. 숨기 직전의 위치는 뷰에 남지만 투명하고 아래에 있어 보이지도
  눌리지도 않고, 다시 보일 때 새 위치를 넣는다.
- **점은 바탕을 불투명한 흰색(`#ffffff`)으로 두고 점 전체에 `opacity: 0.72` 를 준다.** 그림자는 `shadowOpacity: 0.35` 다. RN iOS 는
  바탕이 불투명할 때만 그림자 형태를 미리 계산하고, 반투명하면 점마다 그림자를 따로 그린다. 점이 마흔 개라 배너가 보이는 동안
  스크롤이 끊겼다. 바탕을 반투명하게 하던 때와 보이는 흰색(72%)과 그림자 진하기(0.35 × 0.72)는 같다. 안드로이드는 그림자를
  그리지 않는다.
