# ADR-137 헥사 강화 지출과 강화 레벨 기억

> 🟢 유효
> 관련 소스: `app/cashbook/spend/HexaMatrixForm.tsx` · `app/cashbook/spend/LevelRangeGrid.tsx` · `app/cashbook/spend/level-range.ts` · `app/cashbook/spend/SymbolForm.tsx` · `lib/cashbook/hexa-matrix.ts` · `features/cashbook/remembered-levels.ts` · `storage/remembered-levels.ts` · `nexon/hexamatrix/` · `features/server-sync/cashbook-entry-sync.ts`

## 배경

가계부 지출에 헥사 스킬 · 헥사 스탯 강화를 더한다(#631, 사용자 2026-10-09 · 2026-10-27). 헥사 강화는 메소 대신 솔 에르다와
솔 에르다 조각을 쓴다. 솔 에르다는 값을 매기기 애매해서 빼고, 조각만 지출로 잡는다. 지출은
`(필요 조각 − 교환 불가 조각) × 조각 개당 가격` 이다.

시안은 아티팩트 `헥사 코어 아이콘 변형` 과 `헥사 강화 지출 폼` 이다(2026-10-30). 폼은 수입 · 지출 시트의 새 디자인(#746) 위에 그렸다.

## 결정

### 결정 1. 코어 그림은 원본에 코어 묶음 라벨을 붙인 넷이다

- 원본은 게임의 HEXA 매트릭스 그림(68×71)이다. 192×192 로 키우고, 아래에 묶음 이름을 적은 알약 라벨을 붙인다(사용자 선택 2026-10-30, 시안 D).
- 그림은 넷이다. 코어 종류는 여섯이지만, 3rd 스킬 코어는 스킬 코어 그림을 같이 쓰고 직업 공용 코어는 공용 코어 그림을 같이 쓴다(사용자 지정 2026-10-30). 작은 그림에서 여섯을 가르면 서로 구별되지 않기 때문이다.
- 색은 게임 HEXA 매트릭스 창의 칸 색을 재서 맞췄다. 스킬은 원본 보라 그대로 둔다. 마스터리는 자홍(색상 314°), 강화는 하늘색(198°), 공용은 채도를 낮춘 회청색(231°)이다. 라벨 바탕도 같은 색 계열이다.
- 그림은 다른 게임 그림처럼 서버 그림 목록(`items/`)에 올린다. 앱은 파일명으로 찾는다.

### 결정 2. 레벨 범위는 격자에서 두 번 눌러 고르고, 심볼 강화도 같은 컴포넌트로 바꾼다

- 지금의 칸 막대 슬라이더(`LevelRangeSlider`)를 걷는다. 헥사는 레벨이 0 ~ 30 이라 칸이 31 개다. 막대에 숫자를 다 적으면 칸 폭이 9 쯤이라 숫자가 안 들어간다. 심볼 강화도 같은 컴포넌트로 바꾼다(사용자 지정 2026-10-30).
- 레벨 전부를 격자로 펼친다(사용자 선택 2026-10-30, 시안 C4-1). 헥사는 한 줄 8 칸, 아케인 심볼은 한 줄 10 칸이다.
- 격자 위에 탭 둘(`강화 전` · `강화 후`)이 서서 지금 어느 쪽을 고르는지 보인다. 칸을 누르면 그 쪽 값이 바뀐다. 강화 전을 고르면 탭이 강화 후로 넘어간다. 손이 한 번에 한 값만 고르게 해서 어느 쪽이 바뀌는지 헷갈리지 않게 하기 위해서다.
- 고른 범위는 끊김 없는 띠로 잇고 양 끝은 주색 원이다.
- 조각이 크게 드는 레벨(Lv.10 · 20 · 30)에 표시를 하지 않는다(사용자 지정 2026-10-30).

### 결정 3. 캐릭터의 강화 레벨을 기기에 기억하고, 강화 전 칸을 그 값으로 채운다

캐릭터마다 심볼과 헥사 코어의 강화 레벨을 기기에 저장해 둔다(사용자 지정 2026-10-30). 헥사는 코어 하나하나의 레벨을 따로 저장한다(결정 6).

1. **처음 값은 캐릭터 관리에서 추적을 시작하는 순간 넥슨 API 로 받아 채운다**(사용자 지정 2026-10-30). 심볼은 `character/symbol-equipment`, 헥사는 `character/hexamatrix` 다. 헥사 응답에 없는 코어는 활성화하지 않은 코어라 Lv.0 으로 본다.
2. 추적을 해제해도 기억은 지우지 않는다. 다시 추적을 시작할 때 그 캐릭터의 기억이 하나라도 있으면 받지 않고, 없을 때만 새로 받는다(사용자 지정 2026-10-30). 사용자가 쌓은 값을 넥슨 값으로 덮지 않기 위해서다.
3. 폼을 열면 강화 전 칸을 기억한 값으로 채운다. **폼에서는 넥슨 API 를 부르지 않는다**(사용자 선택 2026-10-30). 강화 후는 사용자가 고른다. 심볼 드롭다운의 만렙 묶음도 기억한 레벨로 가른다.
4. 예외는 기억이 비어 있을 때 하나다. 추적을 시작할 때 받기가 실패했거나, 이 기능이 생기기 전부터 추적하던 캐릭터가 그렇다. 그때는 폼을 열 때 한 번 받아 채운다(사용자 선택 2026-10-30).
5. 기록을 저장하면 강화 후 레벨이 기억한 값이 된다. 다음에 폼을 열면 그 값이 강화 전 칸에 선다.
6. 기억한 값이 실제 게임 레벨과 달라도 **사용자가 친 값을 믿는다**. 넥슨 레벨로 기억을 채우는 것은 위 1 · 4 처럼 비어 있을 때뿐이다.
7. 그 코어(심볼)의 가장 최근 기록을 고치면 기억한 값도 고친 강화 후 레벨로 바뀐다. 가장 최근 기록을 지우면 그 기록의 강화 전 레벨로 돌아간다(사용자 선택 2026-10-30). 더 옛 기록을 고치거나 지우면 기억은 그대로다. 그 뒤에 적은 기록이 이미 레벨을 옮겼기 때문이다.

### 결정 4. 헥사 코어 레벨은 `/maplestory/v1/character/hexamatrix` 에서 받는다

- 인자는 `ocid` 하나다. 코어마다 `hexa_core_name` · `hexa_core_level` · `hexa_core_type` · `linked_skill` 이 온다.
- 레벨은 `hexa_core_level` 만 쓰고 `hexa_core_event_level` 은 무시한다(사용자 선택 2026-10-30). 이벤트로 오른 레벨에는 조각이 들지 않았기 때문이다.
- 코어는 스킬 → 마스터리 → 강화 → 공용 차례로 온다.
- `hexa_core_type` 은 `스킬 코어` · `마스터리 코어` · `강화 코어` · `공용 코어` 넷뿐이다. 3rd 스킬 코어와 직업 공용 코어를 따로 가르지 않는다(2026-10-30 실측, 48 개 직업).
- **직업 공용 코어는 `공용 코어` 중 솔 야누스 · 솔 헤카테가 아닌 하나다**(사용자 지정 2026-10-30). 모든 직업이 공용 코어 셋을 갖고, 그중 둘이 솔 야누스 · 솔 헤카테다.
- **3rd 스킬 코어는 이름으로만 가를 수 있다.** 직업마다 `스킬 코어` 셋 중 어느 것이 3rd 인지 이름표가 필요하다. 이름표는 사용자가 확인한 값만 쓴다(결정 7). 이 값은 게임 데이터라 AI 가 추정해 넣지 않는다([[ADR-019]] 결정 1).
- 두 규칙은 결정 5 의 서버 표로 푼다. 앱 코드에 이름을 적지 않는다.
- 활성화하지 않은 코어는 응답에 없다. 레벨 0 으로 오지 않는다. 그래서 응답에 없는 코어는 Lv.0 으로 본다.
- 이름은 API 가 준 그대로 오지 않을 수 있다. 소울마스터의 `셀레스티얼 클리브` 는 이름 끝에 공백이 붙어 온다. 그래서 이름을 비교할 때는 앞뒤 공백을 걷는다.
- 코어 그림의 원본은 6차 스킬 조회 `/maplestory/v1/character/skill?character_skill_grade=6` 의 `skill_icon` 이다. 넥슨 정적 주소(`open.api.nexon.com/static/maplestory/skill/icon/<코드>`)이고 API 키 없이 열린다. 코어 이름(여럿을 묶은 코어는 `/` 앞)이나 `linked_skill` 이름으로 스킬을 찾는다.
- 앱은 넥슨 주소에서 그림을 불러오지 않는다. 32×32 PNG 를 무손실 webp 로 바꿔 서버 그림 목록의 새 디렉터리 `skills/` 에 `<코드>.webp` 로 올리고, 앱은 다른 게임 그림처럼 받아 기기에 둔다(사용자 지정 2026-10-30, [[ADR-020]]). 오프라인에서도 보이고 그림을 바꾸는 길이 하나로 남기 때문이다. 디렉터리는 서버 `ASSET_DIRS` 에 더한다. 앱은 서버 그림 목록의 경로로 찾으므로(`lib/assets/asset-lookup.ts`) 앱 쪽에 디렉터리 목록을 따로 두지 않는다.
- `linked_skill` 이름이 6차 스킬 이름과 다를 수 있다. 팔라딘의 강화 코어 `홀리 유니티` 는 `linked_skill` 이 `홀리 유니티` 인데 스킬 이름은 `홀리 유니티 강화` 다. 다른 강화 코어는 `linked_skill` 에 ` 강화` 가 붙어 온다.

### 결정 5. 코어 종류는 서버의 종류 표와 이름 표로 가른다

다음 코어가 또 다른 종류로 나올 수 있다(사용자 2026-10-30). 그래서 종류를 앱 코드에 적지 않고 서버 표 둘로 가른다(사용자 선택 2026-10-30).

- **종류 표**: 종류마다 key · 이름 · 그림 · 만렙 · 레벨별 비용(조각 · 솔 에르다) · 대응하는 API 타입(`hexa_core_type`) · 기본 종류 여부 · 차례를 둔다. 만렙을 칸으로 두는 것은 새 종류의 만렙이 30 이 아닐 수 있어서다. API 타입마다 기본 종류는 하나다.
- **이름 표**: 기본 종류가 아닌 코어만 코어 이름 → 종류로 적는다.
- 코어의 종류는 이렇게 정한다. 이름 표에 그 이름이 있으면 그 종류다. 없으면 그 API 타입의 기본 종류다.

| API 타입 | 기본 종류 | 이름 표에 적는 것 |
|---|---|---|
| 스킬 코어 | 스킬 코어 | 직업별 3rd 스킬 코어 48 개 → 3rd 스킬 코어 |
| 마스터리 코어 | 마스터리 코어 | 없음 |
| 강화 코어 | 강화 코어 | 없음 |
| 공용 코어 | 직업 공용 코어 | 솔 야누스 · 솔 헤카테 → 공용 코어 |

- 새 종류가 나오면 관리 화면에서 종류 한 줄과 이름 몇 줄을 더한다. 앱 업데이트가 필요 없다.
- API 가 종류 표에 없는 타입을 주면 그 코어는 비용을 낼 수 없어 고르지 못하게 막고, 서버 이상 로그로 알린다([[ADR-102]]).

### 결정 6. 폼에서는 종류가 아니라 실제 코어를 고른다

- 레벨을 기억하려면 코어 하나하나를 구별해야 한다. 종류만 고르면 같은 종류 코어가 여럿일 때(마스터리 코어는 넷) 강화 전 레벨을 정할 수 없다. 그래서 그 캐릭터의 코어 하나를 고른다(사용자 지정 2026-10-30). 이슈의 처음 결정(종류만 고른다)을 뒤집는다.
- 고르는 목록은 그 캐릭터 직업의 코어 전부다. 활성화하지 않은 코어는 API 에 안 나오므로, 직업마다 코어 목록을 서버 게임 데이터 표로 둔다(사용자 지정 2026-10-30). 칸은 직업 · 코어 이름 · API 타입 · 그림 · 차례다. 차례는 hexamatrix 의 차례다. 다른 게임 데이터처럼 관리 화면에서 고치고 앱은 받아 기기에 저장한다.
- 목록의 씨앗은 2026-10-30 에 직업 48 개의 상위 캐릭터(코어 14 개를 다 가진 쪽)를 hexamatrix 와 6차 스킬 조회로 받은 값이다. 직업마다 코어 14 개라 672 줄이고, 그림은 578 장(webp 합계 305KB)이다. 씨앗 초안과 그림은 맥의 `~/.maple-routine/hexa/` 에 있다(`hexa-cores.seed.json` · `skills/` · `core-icons/`).
- 코어 드롭다운은 종류별로 묶고, 줄마다 스킬 그림과 이름만 보인다. 레벨은 적지 않는다(사용자 지정 2026-10-30). 기억한 레벨과 게임 레벨이 다를 수 있어 어느 쪽을 적어도 헷갈리기 때문이다. 목록은 최대 높이 안에서 스크롤된다.
- 오리진 · 어센트는 가르지 않는다. 비용이 같은 종류(스킬 코어)이고 API 도 가르지 않기 때문이다.

### 결정 7. 직업별 3rd 스킬 코어와 직업 공용 코어 (사용자 확인 2026-10-30)

### 결정 8. 지출 갈래 `헥사 매트릭스` 하나 아래 헥사 스킬 · 헥사 스탯을 세그먼트로 오간다

- 지출 갈래 고르기에 카드 `헥사 매트릭스` 하나를 더한다(사용자 선택 2026-10-30). 게임 창 이름 그대로다. 하위 둘을 함께 덮는 이름이고, 하위 갈래 `헥사 스킬` 과 이름이 겹치지 않는다.
- 카드를 누르면 헥사 스킬 폼이 곧바로 서고, 첫 카드의 `강화 종류` 줄 오른쪽 세그먼트(`헥사 스킬 | 헥사 스탯`)로 오간다(사용자 선택 2026-10-30, 시안 A). 하위 갈래를 고르는 단계를 하나 더 두면 한 번 더 눌러야 하기 때문이다. 세그먼트를 폭 전체로 두면 칸 줄들 사이에서 혼자 모양이 달라 보여, 사냥 전리품 판매의 `분류` 줄처럼 라벨-값 한 줄로 둔다(사용자 지정 2026-10-30).
- 헥사 매트릭스 원본 그림은 큰 갈래 카드와 헥사 스탯에 쓴다(사용자 선택 2026-10-30). 결정 1 의 라벨 붙은 그림 넷은 코어 종류에 쓴다.

### 결정 9. 헥사 기록은 조각 칸 셋을 새로 더해 저장한다

- 기록 표(`cashbook_entry_items`)와 서버 기록 표에 칸 셋을 더한다. 필요 조각 개수 · 교환 불가 조각 개수 · 조각 개당 가격이다(사용자 선택 2026-10-30). 수정으로 다시 열면 이 값이 다시 서야 하고, 있는 칸(수량 · 단가)을 빌리면 칸의 뜻이 갈래마다 달라져 읽기 어렵기 때문이다.
- 헥사 스탯은 활성화 포함 여부도 저장한다. 필요 조각에서 활성화 몫을 다시 가를 수 있어야 수정 화면이 체크 상태로 열린다.
- 헥사 스킬 기록의 key 는 코어 이름이고 강화 전 · 강화 후는 있는 레벨 칸(`levelFrom` · `levelTo`)에 둔다. 헥사 스탯의 key 는 스탯 key 다.
- 금액은 저장할 때 `(필요 조각 − 교환 불가) × 개당 가격` 으로 계산해 굳힌다. 교환 불가가 필요 조각보다 많으면 0 이다.

### 결정 10. 이슈에서 먼저 정한 규칙 (사용자 2026-10-27)

- 서버 비용 표에는 조각과 함께 솔 에르다 개수도 넣는다. 지출 계산에는 안 쓰지만 나중에 쓸 데가 있다.
- 조각 개당 가격 칸은 빈 칸으로 연다. 마지막으로 친 값을 채우지 않는다.
- 금액이 0 인 헥사 기록은 서버로 보내지 않는다([[ADR-099]] 최종값 전송에서 뺀다).
- 헥사 강화는 사냥에서 보관한 조각을 빼지 않는다. 헥사를 올린 캐릭터와 조각을 모은 캐릭터가 달라서 누구의 보관에서 뺄지 정할 수 없기 때문이다. 직접 모은 조각도 강화에 쓰면 지출이고, 지출에서 빼는 것은 교환 불가 개수뿐이다.
- 캐릭터는 필수다. 헥사는 캐릭터마다 따로이기 때문이다.
- 헥사 스탯 Ⅳ ~ Ⅵ 처럼 활성화 비용을 모르는 스탯은 서버 표에 비용 없이 둘 수 있다. 그때 활성화 체크를 막는다.

### 결정 11. 서버를 먼저 배포한다

앱은 게임 데이터의 섹션이 하나라도 빠지면 받기를 실패한다(`features/game-data/sync.ts`). 그래서 `hexaMatrix` 섹션을 내는 서버를 먼저 배포하고 앱을 낸다. 지출 갈래 표의 `헥사 매트릭스` 줄과 `skills/` 그림도 앱보다 먼저 올린다.

### 결정 12. 하루 목록 · 통계 · 데이터 삭제

- 하루 목록 줄의 제목은 `헥사 매트릭스` 다. 내용은 헥사 스킬이면 코어의 첫 스킬 이름과 레벨(`매화검 본초 : 선참 VI 25 → 28`), 헥사 스탯이면 스탯 이름이다. 조각 개수는 적지 않는다(사용자 지정 2026-10-30).
- 줄 그림은 헥사 스킬이면 그 코어의 스킬 그림, 헥사 스탯이면 갈래 카드와 같은 헥사 매트릭스 원본 그림이다.
- 0 메소 헥사 기록도 하루 목록에 선다(사용자 선택 2026-10-30). 다른 지출은 0 이면 줄을 안 세우지만, 헥사 기록은 0 이어도 레벨을 옮겨서 고치거나 지울 길이 있어야 하기 때문이다.
- 통계에서 헥사 매트릭스 조각은 코어 · 스탯별로 나뉜다.
- 강화 레벨 기억은 데이터 삭제의 가계부 그룹이 기록과 함께 지운다. 기록만 지우고 기억을 남기면 다음 기록의 강화 전 칸이 지운 기록의 레벨로 서기 때문이다.

## 번호 기록

- ADR-137 (2026-10-30): 헥사 코어 그림 · 레벨 범위 격자 · 강화 레벨 기억 · hexamatrix 응답 해석을 처음 작성했다(#631). 같은 날 사용자가 확인한 직업 48 개의 3rd 스킬 코어 표, 서버 종류 표 · 이름 표로 종류를 가르는 결정, 실제 코어를 고르는 결정, 수정 · 삭제 때 기억값 규칙, 이벤트 레벨 무시, 6차 스킬 그림을 서버 그림 목록 `skills/` 에 webp 로 두는 결정, API 레벨이 낮을 때 채우지 않는 규칙, 직업별 코어 목록을 서버 게임 데이터로 두는 결정을 더했다. 지출 갈래 이름 · 하위 갈래 세그먼트 · 원본 그림을 쓰는 곳도 정했다. 기록 칸 셋 · 이슈의 먼저 정한 규칙 · 서버 먼저 배포를 더했다. 하루 목록 · 통계 · 데이터 삭제 규칙과 종류 표의 만렙 칸도 더했다. 처음 레벨을 추적 시작 때 받고 폼에서는 API 를 부르지 않도록 결정 3 을 다시 썼다
