# ADR-290: 사냥 기록의 조각 가격 칸을 비우면 그 조각이 캐릭터 보관에 든다. `조각 가격 나중에 입력` 체크박스는 걷는다

> 🟢 유효 · 2026-09-17 · **구현 완료**(2026-09-17) · 시뮬레이터 미검증 · 실기기 미검증 · 사용자 지정(2026-09-17)
>
> [[ADR-283]] 결정 1 · 2 를 뒤집는다. [[ADR-288]] 결정 2 가 기억하던 체크 셋에서 조각 체크가 빠진다.

**관련**: [[ADR-283]](조각 보관과 정산) · [[ADR-288]](사냥 시트가 마지막 체크 셋으로 열린다) ·
[[ADR-171]](수정 시트가 적을 때 쓴 입력을 되살린다)
**문서**: `features/cashbook.md` · `persistence/sqlite.md` · `persistence/preferences.md`

## 맥락

[[ADR-283]] 은 사냥 시트에 `조각 가격 나중에 입력` 체크박스를 두고, 켠 기록의 조각만 캐릭터 보관에 넣었다. 조각을 안 팔았으면
가격을 모르는데도 체크를 따로 켜야 했다. 사용자가 체크박스를 없애고, 가격을 입력하지 않으면 보관에 들게 해 달라고 했다(2026-09-17).

그런데 가격 칸은 0 과 빈 칸을 가르지 못했다. `mesoTextOf` 가 0 을 빈 칸으로 그리고 `mesoValueOf` 가 빈 칸을 0 으로 읽는다.
가격은 저장 조건에도 없었다. 2026-08-28 계산기가 들어온 뒤로 두 폼 모두 가격 없이 저장됐다. 그래서 DB 의 가격 0 은 사용자가
비워 둔 것인지 0 을 친 것인지 알 수 없다.

## 결정

### 결정 1. 체크박스를 걷고, 가격 칸이 비어 있으면 보관이다 (사용자 지정)

```
□ 획득 메소 직접 입력                       ← 수정으로 열면 이 줄이 없다
캐릭터 [선택 ▾]
[조각 그림] [ 80 ] 개 ··· [미입력 시 보관] 메소   ← 비워 두면 80개가 보관에 든다
                              12억 메소     ← 조각 값이 빠진 합계
```

- 계산기 · 수동 입력 두 폼에서 가격 칸이 비어 있으면 그 기록의 조각이 캐릭터 보관에 든다. 합계는 획득 메소뿐이다.
- **0 을 치면 보관이 아니다**(사용자 지정). 조각을 0 메소에 넘겼다는 기록이다.
- 자리표시자는 `미입력 시 보관` 이다(사용자 지정). 체크박스 이름이 하던 설명을 칸이 대신한다.
- 가격 칸은 꺼지지 않는다. 꺼질 이유였던 체크가 없다.
- 체크 줄에는 `획득 메소 직접 입력` 하나만 선다. 수정에서는 그것도 안 서므로 줄 자체를 그리지 않는다. 빈 줄을 두면
  위아래 간격만 한 칸 더 생긴다.

### 결정 2. 빈 가격은 `hunt_fragment_price` 의 `NULL` 이다

- **가격 칸은 0 과 빈 칸을 가른다.** 빈 칸은 `null` 이고 `0` 은 0 이다. 커서가 빠질 때 앞자리 0 은 걷지만 0 하나는 남긴다.
  글자와 값을 오가는 함수는 `optionalMesoValueOf` · `optionalMesoTextOf` 다. 다른 금액 칸은 전처럼 0 을 빈 칸으로 그린다.
- **수정으로 열면 저장된 값이 그대로 선다**([[ADR-171]] 결정 2). `null` 은 빈 칸, 0 은 `0` 이다. 둘을 같게 그리면 연 기록을
  저장만 해도 보관에 들고 나기 때문이다.
- 타입은 `HuntingCalculatorDetail` · `HuntingManualDetail` 의 `fragmentPrice: number | null` 이다. `fragmentsDeferred` 는
  없앤다. 같은 뜻을 두 칸이 들면 어긋날 수 있다.
- 합계 `huntTotalOf` 는 가격이 `null` 이면 조각 값을 안 더한다.
- 보관 조회 `getFragmentStorage` 는 `hunt_fragment_price IS NULL` 인 사냥 기록의 조각을 더한다.

### 결정 3. `hunt_fragments_deferred` 칸은 스키마에 남기고 읽지도 쓰지도 않는다

칸을 지우면 OTA 를 되돌렸을 때 옛 번들의 `INSERT` 가 없는 칸을 적다 실패해 수입이 하나도 안 적힌다. `db.ts` 의
`spend_records.form` 주석이 적은 결함과 같은 모양이다. 그래서 CREATE 본문과 `ensureColumn` 은 그대로 두고, `INSERT` ·
`UPDATE` 에서만 뺀다. 새 기록의 그 칸은 `NULL` 이다.

### 결정 4. 기존 기록은 DB 버전 9 가 한 번 옮긴다 (사용자 지정)

`category_key = 'hunting'` 이고 `hunt_fragment_price = 0` 인 행의 가격을 `NULL` 로 바꾼다.

- **이번 한 번만 0 도 입력 안 함으로 읽는다**(사용자 지정). 지금까지 칸이 0 과 빈 칸을 못 갈랐기 때문이다. 이관 뒤로는 0 이
  보관이 아니다.
- **체크 여부는 안 본다.** 체크를 켠 기록은 가격이 언제나 0 으로 저장돼 이 조건에 든다. 끈 채 가격을 비운 기록도 든다(사용자
  지정 `기존 입력건까지 모두`).
- 금액(`meso_amount`)은 안 바뀐다. 가격이 0 이든 `NULL` 이든 조각 값은 0 이다.
- 캐릭터 없이 저장된 옛 사냥 기록은 보관에 안 든다. 보관이 캐릭터별이라 셀 자리가 없다([[ADR-283]] 결정 5).
- 계산기 도입 전 행은 사냥 칸이 전부 `NULL` 이라 이관이 안 건드린다. 조각도 `NULL` 이라 보관에 더해지는 것이 없다.

### 결정 5. `lastHuntToggles` 는 켠 아이템만 기억한다

- 모양이 `{ boosts }` 가 된다. 옛 값에 남은 `fragmentsDeferred` 는 읽을 때 무시한다. 키를 지우지 않는 것은 켠 아이템이 그대로
  쓰이는 값이라서다.
- **계산기로 저장했을 때만 적는다.** 수동 폼에는 아이템 줄이 없어 기억할 것이 없다. 조각 체크를 기억하려고 수동 저장도 적던
  길(`nextHuntToggles`)이 할 일을 잃는다.

## 대가

- **옛 기록에서 정말 0 을 뜻한 가격도 보관이 된다.** 칸이 가르지 못해 알 길이 없다. 그 조각은 정산 폼의 보관 수에 더해지고,
  사용자가 그 기록을 열어 `0` 을 치고 저장하면 빠진다.
- **안 쓰는 칸이 스키마에 남는다.** 결정 3 의 이유다.
- **가격 칸만 0 을 다르게 그린다.** 다른 금액 칸은 0 이 빈 칸이고 이 칸은 `0` 이다.

## 기각

- **이관으로 `hunt_fragments_deferred` 를 채우고 계속 쓴다.** 가격 칸과 체크 칸이 같은 뜻을 들어 어긋날 수 있다. 결정 2.
- **이관 뒤에도 0 을 보관으로 읽는다.** 사용자가 앞으로는 비운 것만 보관이라고 정했다. 결정 4.
- **자리표시자 `비우면 나중에 정산`.** 사용자가 다른 문구를 골랐다. 결정 1.
- **칸을 지운다.** 결정 3.
