# ADR-194 — 문서는 비유 대신 평이한 개발 용어로 쓴다

> 🟢 **ACTIVE — 유효.** 2026-08-31 · 사용자 결정 · **적용 중**(문서부터 점진적으로).

## 맥락

문서가 읽히지 않는다는 지적이 나왔다. 원인을 두 가지로 나눠 재 봤다.

**번역투는 거의 없다.** `~에 대한` · `~을 위한` · `~에 의해` · 이중피동 · `~를 가진다` 같은
지표로 `docs/` 전체(2.4MB)를 훑으니 **275건**이었다. 1,000자당 0.1건이라 문제라고 할 수준이 아니다.

**문제는 비유로 압축한 문체다.** 뜻을 한 번 더 풀어야 읽히는 말이 `docs/` 와 `src/` 를 합쳐
**3,548건 · 578개 파일**에 퍼져 있다. 많이 쓰인 순서로 `갈래`(650) · `든다`(611) · `선다`(463) ·
`두 벌`(195) · `벽지`(168) · `한 칸`(162) · `한 벌`(139) 이다.

실제로 이런 문장이다.

| 지금 | 뜻 |
|---|---|
| 벽지는 가장 안쪽 불투명 화면이 **든다** | 테마 배경은 가장 안쪽 불투명 화면이 **그린다** |
| 시트는 **갈래마다 자기 폼**을 갖고, 칸의 상자는 **못 박는다** | 시트는 **입력 종류마다 다른 폼**을 쓰고, 입력칸 크기는 **고정한다** |
| 보스 수익의 날짜는 [[ADR-172]] 가 **캔다** | 보스 수익의 날짜는 [[ADR-172]] 에서 **처리한다** |
| 껍데기 탭 두 개는 **걷었다** | 빈 탭 두 개는 **삭제했다** |

쓸 때는 짧아서 좋지만, 읽는 사람은 매번 해독해야 한다. 문서를 읽는 사람이 사람 한 명과 AI
에이전트라는 점에서 둘 다 손해다 — 압축한 만큼 오독 확률이 올라간다.

## 결정

### 결정 1. 문서는 비유를 쓰지 않고 평이한 개발 용어로 쓴다

`docs/**/*.md` 가 대상이다. 판단 기준 하나 — **뜻을 풀어 다시 말해야 이해되는 문장이면 고친다.**
짧게 쓰는 것보다 한 번에 읽히는 것이 우선이다.

문서의 밀도 자체를 낮추라는 뜻은 아니다. 이 저장소의 문서는 «무엇을 왜 그렇게 정했나» 를
자세히 적는데, 그 습관은 그대로 둔다. 바꾸는 것은 **어휘**뿐이다.

### 결정 2. 바꾸는 말은 목록으로 고정한다

| 쓰지 않는다 | 대신 쓴다 |
|---|---|
| 든다 | 그린다 · 표시한다 · 담는다 |
| 갈래 | 종류 · 항목 · 분류 |
| 선다 · 섰다 | 놓인다 · 표시된다 · 만들었다 |
| 걷는다 · 걷었다 | 삭제한다 · 제거했다 |
| 못 박는다 · 못박는다 | 고정한다 · 명시한다 |
| 벽지 | 테마 배경 |
| 한 벌 · 두 벌 | 한 세트 · 두 벌(자료 구조면 «두 개») |
| 캔다 | 처리한다 · 채운다 · 찾아낸다 |
| 얹는다 | 추가한다 · 덧붙인다 |
| 물려받는다 | 상속한다 · 그대로 쓴다 |
| 죽었다 · 살아 있다 | 폐기됐다 · 유효하다 |

목록에 없어도 같은 부류면 고친다. 목록은 자주 나오는 것을 먼저 적어 둔 것이지 전부가 아니다.

**`죽은 결정` 만 예외다.** ADR 배지 체계가 이미 그 말을 쓰고 있어([[ADR-158]]) 지금 바꾸면
배너 · 인덱스 · 검사 테스트가 한꺼번에 흔들린다. 그 자리는 그대로 둔다.

### 결정 3. 소스 주석은 이번 범위가 아니다

`src/` 주석에도 같은 어휘가 3,000건 가까이 있지만 건드리지 않는다. 주석은 코드와 함께 읽히고
diff 가 코드 변경에 섞이면 리뷰가 어려워진다. **그 파일을 다른 이유로 열 때 함께 고친다.**

### 결정 4. 한 번에 하지 않고 문서 단위로 나눠 고친다

`docs/features/*` 와 `docs/foundation/*` 부터다 — 가장 자주 열리고, 현행 정책이 사는 곳이다.
ADR 본문은 **기록**이라 우선순위가 낮다. 다만 문서를 다른 이유로 다시 쓸 때는 함께 고친다.

수십만 자를 한 회차에 바꾸면 diff 를 검토할 수 없고, 뜻이 바뀐 곳을 찾지 못한다. 한 문서씩
끝내고 커밋한다.

## 이유

읽는 사람이 사람 하나와 AI 에이전트다. 압축된 비유는 **쓰는 순간에만** 이득이고, 읽을 때마다
비용이 든다. 문서를 읽는 횟수가 쓰는 횟수보다 훨씬 많으니 계산이 안 맞는다.

AI 에이전트 쪽은 더 나쁘다. `걷었다` 를 «삭제했다» 로 읽을지 «보류했다» 로 읽을지 문맥마다
갈리는데, 틀리게 읽어도 아무 신호가 없다. 그대로 코드에 반영된다.

## 트레이드오프

문서가 길어진다. `시트는 갈래마다 자기 폼을 갖는다`(19자)가 `시트는 입력 종류마다 다른 폼을
쓴다`(23자)가 된다. 그 정도는 감수한다.

문체의 개성이 줄어든다. 지금 문체는 읽는 맛이 있고, 짧은 문장에 판단까지 담는 장점이 있었다.
그것을 포기하는 대신 오독을 줄인다.

**기계로 치환할 수 없다.** `선다` 하나가 자리마다 «놓인다» · «표시된다» · «만들었다» 로 갈린다.
사람이 문맥을 보고 고쳐야 해서 진행이 느리다 — 그래서 결정 4 로 나눴다.
