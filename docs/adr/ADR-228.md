### ADR-228: **운영자 공지.** 계약을 먼저 못박고 앱과 서버를 나란히 짓는다 (2026-09-07, 사용자 지시)

> ⚪ **NOT IMPLEMENTED.** 계약만 있고 코드가 없다. 서버 저장소도 아직 없다. 착수 전에 이 문서와
> 아래 **열린 질문**을 다시 읽을 것.
>
> **정정 1 이 결정 2 의 스위치 자리를 옮겼다.** 인용 전에 문서 끝의 정정을 볼 것.

**배경**: [[ADR-227]] 이 서버를 들이기로 했고 그 첫 기능이 공지다. 파이프는 이미 섰다.
`PushPort`(구독·해제)와 FCM 런타임이 양 플랫폼 바이너리에 들어갔고, 발송기에서 안드로이드
에뮬레이터까지 **실제로 알림이 뜨는 것을 확인했다**(2026-09-07).

없는 것은 그 파이프를 쓰는 코드다. **지금 아무도 `subscribeToPushTopic` 을 안 부른다.**

사용자가 정한 것 넷(2026-09-07).

1. 구독은 **설정 토글**로. 켠 사람만 받는다.
2. 알림 권한은 **캐릭터를 고른 사람**에게, **한 번도 안 물었을 때**만 묻는다.
3. 알림을 탭하면 **공지 상세 화면**으로 간다(새 페이지).
4. 상세 내용은 **푸시로 받고 서버로 보강**한다.

그리고 순서로 **계약을 먼저 정하고 양쪽을 나란히** 짓기로 했다.

### 결정 1. **계약을 먼저 못박는다.** 페이로드와 API 를 이 문서가 소유한다

저장소가 둘로 갈리므로([[ADR-227]] 결정 3) 계약이 두 곳에 살게 된다. 한쪽만 바꾸면 타입 검사가
못 잡는다. 그래서 **말로 된 원본을 여기 둔다.**

**푸시 페이로드.** `notification` 은 OS 가 그리고 `data` 는 JS 가 읽는다.

```
notification: { title, body }          OS 가 그대로 그린다
data: {
  noticeId:    string                  중복 억제와 탭 이동의 열쇠
  title:       string
  body:        string                  요약이 아니라 상세 본문
  publishedAt: string                  ISO 8601
  link:        string | undefined      선택. 외부로 나가는 주소
}
```

**`data` 의 값은 전부 문자열이어야 한다.** FCM 이 그렇게 정해 뒀고, 숫자나 불리언을 넣으면 발송이
거부된다. 그리고 메시지 전체가 **4KB** 를 넘으면 안 된다. 본문이 길면 잘라서 보내고 나머지는
서버 조회로 채운다(결정 4).

**서버 API.** 공개 정보라 인증이 없다.

```
GET /v1/notices?limit=20&cursor=<불투명 문자열>
  → { items: Notice[], nextCursor: string | null }

GET /v1/notices/{id}
  → Notice

Notice = { id, title, body, publishedAt, link?: string }
```

`Notice` 가 푸시 `data` 와 **같은 모양**인 것이 의도다. 두 경로가 같은 타입을 만들어야 화면이
출처를 안 가린다.

### 결정 2. 구독은 **설정 토글**이 소유한다 (사용자 지정)

설정에 스위치를 하나 두고, 그 값이 곧 `notice` 토픽 구독 여부다. 켜면 `subscribe`, 끄면
`unsubscribe`.

**토픽 이름은 JS 에 있다.** 네이티브가 아니라 JS 라 OTA 로 바꿀 수 있고, 그것이 [[ADR-146]]
결정 2 의 *"토픽 이름은 서버 쪽 값이다"* 와 어긋나지 않는 이유다. 앱이 구독하려면 문자열을 알아야
하는데, 그 문자열이 심사를 안 타는 자리에 있으면 된다.

**저장은 어댑터를 거친다**([[ADR-003]] 의 살아 있는 절반). `STORAGE_KEYS` 에 키를 더하고
`storage/notice-settings.ts` 가 그 하나를 책임진다. 화면이 `preferences` 를 직접 안 부른다.

**UI 는 새 컴포넌트를 만들지 않는다.** `BossDropSheet` 의 `EffectToggle` 이 이미 스위치를 그린다
(`role="switch"` · `aria-checked` · 알약 안에서 손잡이를 옮기는 `translateX`). 같은 모양을 쓴다.
공용 컴포넌트로 뽑는 것은 세 번째 소비자가 생길 때 한다.

### 결정 3. 권한은 **캐릭터를 고른 직후** 한 번만 묻는다 (사용자 지정)

조건이 둘이고 **둘 다** 참일 때만 묻는다.

1. 캐릭터 관리에서 캐릭터를 골랐다(`setCharacterSelection` 이 성공했다)
2. 이 앱이 알림 권한을 **한 번도 물은 적 없다**

두 번째를 위해 키가 하나 필요하다. OS 에 물어봐서는 안 된다. 안드로이드의 `denied` 는 *"거부했다"*
와 *"아직 안 물었다"* 를 구분해 주지 않는 상태가 있고, 그것을 안 물었다로 읽으면 거부한 사용자에게
계속 팝업이 뜬다. **우리가 물었다는 사실은 우리가 기억한다.**

**허용하면 토글이 켜진다.** 그 순간이 사용자가 알림을 받겠다고 답한 자리이므로, 설정에 들어가
다시 켜라고 하지 않는다. 거부하면 토글은 꺼진 채로 남는다.

**이 결정이 [[ADR-146]] 결정 7 의 앞 절반을 뒤집는다.** 그 문서는 *"사용자가 알림을 켜는 순간이
유일한 요청 시점"* 이라고 정했고 근거가 **iOS 는 한 번 거부하면 다시 못 묻는다**였다. 그 사실은
지금도 참이다. 그래서 이 결정은 **대가를 알고 하는 교환**이다.

- **얻는 것**: 설정을 뒤지지 않는 사용자에게 닿는다. 캐릭터를 고르는 시점은 앱을 실제로 쓰기
  시작한 자리라, 첫 실행에 맥락 없이 묻는 것보다 훨씬 낫다.
- **잃는 것**: 그 자리에서 거부한 사람은 **영영 못 묻는다**. 나중에 토글을 켜도 알림이 안 뜬다.

그래서 **거부를 감지하면 말해 준다.** 토글을 켰는데 권한이 없으면 조용히 구독만 하지 않고, OS
설정으로 가는 길을 안내한다. 안 그러면 켜 놓고 안 오는 것이 고장으로 읽힌다.

[[ADR-146]] 결정 7 의 **뒷 절반은 그대로 지킨다**. 그 문서는 *"설정 > 알림은 첫 알림과 함께
온다"* 고 적었고, 지금이 그 첫 알림이다.

### 결정 4. 공지는 **기기에 쌓인다.** 서버는 보강이다 (사용자 선택)

푸시가 오면 `data` 를 그대로 기기에 저장한다. 그래서 **서버가 죽어도 받은 공지는 열린다.**
상세 화면이 여는 것은 로컬이지 네트워크가 아니다.

서버는 두 자리에서 보강한다.

- **목록**을 열 때. 구독 전이나 설치 전 공지는 기기에 없다. 그 구멍을 서버가 메운다.
- **상세**를 열었는데 로컬에 본문이 잘려 있을 때. 4KB 제한 때문에 긴 공지는 푸시에 다 못 싣는다.

**병합의 열쇠는 `noticeId` 다.** 같은 id 면 서버 것이 이긴다. 서버가 나중에 오타를 고칠 수 있고,
푸시는 발송 시점에 굳은 사본이기 때문이다.

**저장은 Preferences 다. SQLite 를 안 쓴다.** [[ADR-003]] 이 SQLite 로 가는 기준을
*"실제 쿼리(WHERE·날짜 범위·upsert)가 필요할 때"* 로 정해 뒀는데, 공지는 **최근 것부터 세로로
읽는 목록 하나**다. `eventWorldNames` 와 같은 모양이라 JSON 배열 한 칸으로 충분하다.
**최근 50건만 남기고 자른다** (오래된 공지를 다시 볼 일이 생기면 서버가 준다).

### 결정 5. 화면은 **둘**이다. 설정 아래에 산다

- **목록** `/settings/notices`. 설정에서 들어간다. 로컬에 쌓인 것과 서버에서 받은 것을 합쳐 최근순.
- **상세** `/settings/notices/:id`. 알림 탭이 곧장 여는 자리이고 목록에서도 들어간다.

둘 다 `routes.ts` 에 `kind: 'push'` 로 등록한다([[ADR-120]] 하위 페이지는 스택).

**알림 탭이 상세를 여는 길은 진입점 셋을 탄다.** 앱이 살아 있을 때 · 배경에 있을 때 · 죽어 있을 때
가 각각 다른 콜백이고, 마지막 것은 **앱이 뜨기 전에 도착한 알림**이라 내비게이터가 설 때까지
목적지를 들고 있어야 한다. 그 대기를 어디에 두는지는 구현 시점의 문제이고, 셋 중 하나라도
빠뜨리면 **어떤 경로에서만 탭이 안 먹는** 증상이 난다.

---

### 결정 6. 서버는 별도 저장소이고, **인바운드가 여기서 처음 생긴다**

지금까지 서버는 아웃바운드만 했다. FCM 으로 나가기만 했으므로 프록시가 필요 없었다. 결정 4 의
목록·상세 조회가 **앱에서 서버로 가는 첫 요청**이다.

그래서 [[ADR-227]] 결정 2 의 층이 여기서 실제로 필요해진다. **앱 → Oracle 무료 등급(nginx) →
집 미니 PC.** 두 구간을 잇는 방법은 그 문서의 열린 질문으로 남아 있다.

**서버가 죽어도 앱은 돈다**(결정 4). 목록이 로컬 것만 보이고 상세가 잘린 채로 열릴 뿐이다.
조회 실패를 화면 전체의 실패로 만들지 않는다.

## 대가

- **iOS 에서 한 번 거부한 사용자를 잃는다.** 결정 3. 앱 안에서 되돌릴 방법이 없다.
- **계약이 두 저장소에 갈라져 산다.** 결정 1 이 말로 못박지만 기계가 검사하지는 않는다.
- **푸시 본문과 서버 본문이 어긋날 수 있다.** 발송 뒤 서버에서 고치면 이미 받은 기기에는 옛 문구가
  남는다. 상세를 열 때 서버 것으로 덮지만, 알림 자체의 문구는 못 고친다.
- **4KB 를 넘기면 조용히 잘린다.** 발송기가 그것을 재서 막아야 한다.
- **인바운드가 열리면서 지켜야 할 것이 는다.** 속도 제한 · TLS · 프록시 가용성.

## 기각

- **권한을 부팅 때 묻는다.** [[ADR-146]] 결정 7 이 이미 기각했고 그 근거는 지금도 유효하다.
- **공지를 SQLite 에 넣는다.** 결정 4. 쿼리가 필요 없다.
- **토픽을 여러 개로 나눈다**(점검·이벤트·업데이트). 보낼 공지가 아직 한 종류도 없는데 축부터
  나누면 그 축이 맞는지 알 방법이 없다. 나눠야 할 이유가 생기면 그때 나눈다.
- **읽음 표시와 배지.** 이번 범위 밖이다. 열린 질문으로 남긴다.
- **스위치를 공용 컴포넌트로 뽑는다.** 결정 2. 소비자가 둘뿐이다.

## 열린 질문

- **토글의 기본값.** 이 문서는 권한을 허용하면 켜지는 것으로 적었다(결정 3). 그렇다면 권한을
  묻기 전의 기본값은 꺼짐이고, 그 상태가 사용자에게 어떻게 읽히는지는 화면을 그려 봐야 안다.
- **읽음 표시.** 안 읽은 공지에 배지를 다는가. 달면 읽음 상태를 어디에 두는가.
- **발송기가 4KB 를 어떻게 재는가.** UTF-8 바이트이고 키 이름도 센다.
- **서버 조회에 속도 제한을 어떻게 거는가.** 인증이 없어 누구나 부른다.
- **목록을 언제 갱신하는가.** 화면에 들어갈 때마다인지, 당겨서 새로고침인지.
- **공지를 지울 수 있는가.** 잘못 보낸 공지를 서버에서 지우면 이미 받은 기기의 로컬 사본은
  어떻게 되는가.

## 정정 1. 스위치는 **공지사항 페이지 안**에 산다 (2026-09-08, 사용자 지정)

결정 2 는 스위치를 설정 본화면의 행 하나로 두고, 화면을 따로 만들면 *"켤 것이 공지 하나뿐이라
그 화면이 거짓말을 한다"* 고 적었다. **그 근거가 안 선다.**

사용자가 만들려는 것은 `설정 > 알림` 이 아니라 **`설정 > 공지사항`** 이고, 그 페이지의 주된 내용은
스위치가 아니라 **공지 목록**이다. 알림은 그 기능의 일부이지 전부가 아니다. 목록이라는 진짜 내용이
있으므로 화면이 빈말을 하지 않는다.

그래서 구조가 이렇게 선다.

```
설정 본화면
  └ 공지사항                    행 하나 (chevron)
      └ /settings/notices       목록 + 구독 스위치
          └ /settings/notices/:id   상세
```

**얻는 것 둘.** 설정 본화면이 7행에서 안 늘어난다([[ADR-118]] 의 미검증 항목이 *"7행 + 고지 4줄이
스크롤 없이 들어가는가"* 이고, 행을 더하면 그 미검증이 커진다). 그리고 스위치가 **자기가 무엇을
켜는지 옆에 두고** 선다. 본화면의 행 하나였다면 사용자는 무엇이 오는지 모르고 켜야 했다.

결정 5 가 적은 화면 둘은 그대로다. **목록 화면이 구독 스위치를 함께 들게 되는 것**이 바뀐 전부다.

저장소·토글·권한·구독까지가 먼저이고(서버 없이 선다), 화면 둘과 서버 조회가 그다음이다.
