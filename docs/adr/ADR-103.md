## 맥락

이슈 #136("고가 아이템 드롭 연출 속도 개선")은 "속도"가 셋 중 어느 뜻인지를 사용자에게 물었다:

- (A) 연출이 **나타나기까지**가 느리다 → 로딩·디코드 문제
- (B) 연출 **재생**이 느릿하다 → fps 문제
- (C) 연출을 **끝내기**가 번거롭다 → loop 무한 + 탭 필수 구조 문제

**사용자 판정은 (B), 처방은 "fps 2배"**(2026-08-06). 이슈가 적어둔 "계측 먼저" 절차는 **이 결정에는 적용하지 않는다** — 그 절차는 (A)와 (B)를 구분하기 위한 것이었고, 구분은 화면을 보는 사람이 이미 내렸다. 재생 속도는 성능 수치가 아니라 **연출의 리듬**이고, 그 판정자는 도메인 전문가인 사용자다.

[[ADR-038]] 결정 8이 정한 값(실제 코드 값은 그 후 조정돼 screen 15 / pre 14 / loop 11.5 / end 12)은 와이어프레임에서 잠정 확정한 뒤 실기기 검증 없이 남아 있었다([[ADR-038]] "미확정 — 연출의 최종 fps는 실기기 검증 필요"). 이번이 그 검증이다.

## 결정

### 결정 1 — 네 단계 fps 를 모두 정확히 1.5배로 올린다

| 단계 | 프레임 | fps (전 → 후) | 길이 (전 → 후) | (반려된 2배) |
|---|---|---|---|---|
| screen | 16 | 15 → **22.5** | 1067ms → **711ms** | 30 / 533ms |
| pre | 8 | 14 → **21** | 571ms → **381ms** | 28 / 286ms |
| loop | 24 | 11.5 → **17.25** | 2087ms → **1391ms** / 1회 (∞ 반복) | 23 / 1043ms |
| end | 7 | 12 → **18** | 583ms → **389ms** | 24 / 292ms |

단계별 **고정 fps** 라는 방식([[ADR-038]] 결정 8)은 그대로다. 단계마다 값이 다른 것도 유지한다 — 버스트(screen)는 빠르게 터지고 기둥 loop 은 느리게 맥동해야 한다는 원래 의도가 배율에 무관하게 보존된다. **네 단계에 같은 배율을 걸고 배율 하나만 조정하는 방식**을 쓴 덕에 2배 → 1.5배 정정이 값 네 개(+ 팝인)의 재계산으로 끝났다 — 단계별로 따로 감을 잡았다면 되돌리기 어려웠다.

### 결정 2 — 중앙 아이템 팝인(CSS transition)도 같은 배율로 줄인다

`opacity .35s / transform .5s` → **`opacity .233s / transform .333s`**(÷1.5).

팝인은 fps 가 아니라 CSS transition 이라 fps 만 올리면 **혼자 옛 속도로 남는다.** 원래 타임라인은 팝인이 ScreenEff 종료와 거의 동시에 끝나도록 짜여 있었다(팝인 끝 1033ms · 버스트 끝 1067ms). fps 만 올리면 버스트가 먼저 사라지고 아이템만 남아 계속 커진다 — 연출이 끝난 뒤에도 등장 모션이 남는다.

| | fps만 1.5배 | 팝인도 1.5배 (채택) |
|---|---|---|
| 아이템 등장·팝인 시작 | 356ms | 356ms |
| 팝인 끝 | 856ms | **689ms** |
| ScreenEff 끝 | 711ms | 711ms |
| 결과 | 버스트가 사라진 뒤 145ms 동안 아이템만 커진다 | 함께 마무리된다 |

사용자 확인(2026-08-06)으로 채택. **fps 배율을 바꿀 때 반드시 같이 바꿔야 하는 값**이므로 코드 주석과 테스트가 이 연동을 고정한다.

### 결정 3 — `DROP_START_FRAME = 8` 은 그대로 둔다

아이템·기둥이 등장하는 시점은 **시간이 아니라 ScreenEff 프레임 인덱스**로 잡혀 있다. 8번 프레임은 버스트가 최대로 벌어지는 특정 그림이고, 트리거는 그 그림에 묶여야 한다. fps 를 올리면 등장 시점은 자동으로 따라온다(533ms → 356ms) — 상수를 만질 이유가 없다. 2배 → 1.5배 정정 때도 이 상수는 손대지 않았다.

### 결정 4 — 이슈 #136 의 (A) 가설은 이 ADR 이 다루지 않는다

이슈는 "가장 큰 `screen`(16프레임 1.0MB)만 프리로드 대상에서 빠져 있어 첫 프레임 디코드가 연출 시작을 밀 수 있다"는 가설을 적어뒀다(`DropEffectOverlay.tsx` 프리로드는 `pre`/`loop`/`end` 만 한다). 그건 **재생 속도가 아니라 시작 지연**이라 다른 축이고, 실기기 계측 전이라 손대지 않는다.

다만 방향이 서로 반대는 아니라는 점은 기록해 둔다 — fps 상향은 `screen` 프레임 교체 빈도도 같이 올리므로, (A)가 사실이라면 그 지연은 **완화되지 않고 그대로 남거나 더 눈에 띈다.** 실기기에서 시작 지연이 남으면 그때 (A)를 별도로 판다.

## 트레이드오프

| 얻는 것 | 잃는 것 |
|---|---|
| 연출 전체가 2/3 시간에 끝난다 — 기록 한 번에 붙는 대기가 줄어든다 | 프레임 수는 그대로라 각 프레임의 체류가 짧아진다. 프레임 간 이동이 큰 구간은 더 뚝뚝 끊겨 보일 수 있다(에셋 재제작 없이는 어쩔 수 없다) |
| loop 맥동이 1.5배 빨라져 "기다리는 느낌"이 준다 | 저사양 기기에서 JPEG 디코드·`src` 교체 빈도가 1.5배 — 특히 `screen`(평균 64KB/프레임, 미프리로드)이 부담이다. 실기기 확인 항목 |
| 2배에서 잃었던 "연출을 본다"는 느낌이 돌아온다 — 배율은 짧을수록 좋은 값이 아니다 | 22.5 · 21 · 17.25 · 18 은 60Hz 격자에 안 떨어져 프레임 체류가 2~3틱을 오간다 — 다만 이는 전과 같은 성질이고(15·14·11.5·12 도 마찬가지) 절대 오차는 오히려 작아진다 |

## 검증

테스트는 fps 상수가 아니라 **실제 타임라인**을 단언하고, 각 시점은 **1배(옛 값)와 2배(반려된 값) 양쪽에서 모두 깨지도록** 골랐다 — 배율을 어느 쪽으로 되돌려도 테스트가 잡는다.

| 항목 | 방법 |
|---|---|
| 아이템·기둥이 356ms 에 등장한다 | `DropEffectOverlay.test.tsx` — 300ms 에는 기둥 없음(2배면 있다), 400ms 에 `pre` 프레임(1배면 없다) |
| pre(381ms)를 지나 loop 로 넘어간다 | 같은 파일 — 700ms 에 `pre`, 800ms 에 `loop` |
| ScreenEff 가 711ms 에 끝난다 | 같은 파일 — 600ms 에 `opacity: 1`, 780ms 에 `0` |
| 탭 후 end(389ms)가 끝나면 닫힌다 | 같은 파일 — 340ms 에는 아직, 420ms 안에 `onClose` |
| 팝인이 같은 배율이다 | 같은 파일 — transition 값 단언 |
| 프레임·좌표 동기([[ADR-048]])는 그대로다 | 기존 테스트 유지(end 스텝 간격만 새 fps 로) |
