## 이 화면이 지키려는 한 문장

> **today 는 요약이지 목록이 아니다.**

위젯은 «지금 뭘 해야 하나» 에 한 눈에 답하고, 더 보려는 사람을 원래 화면으로 보낸다. 그래서
타일은 스크롤하지 않고, 넘치면 접고, 자기 자리를 벗어나 커지지 않는다. 이 문장이 아래 규칙 대부분의
근거다.

## 격자 ([[ADR-147]] 결정 1)

| 값 | 크기 |
|---|---|
| 열 수 | **4** (고정) |
| 표기 | **`가로x세로`(WxH)** — `2x4` 는 «폭 2 · 높이 4» 다 |
| 좌우 여백 | **16** (`px-4`, 앱 공통) |
| 타일 간격 | **12** (제안값) |
| 열 폭 | **유동** — `(창폭 − 32 − 12×3) / 4`. 360dp 에서 73 |
| 행 높이 | **고정 76** (제안값) |

- **치수는 `lib/widget-grid-metrics.ts` 의 `resolveWidgetGridMetrics(창폭)` 하나가 판다.** `onLayout`
  실측을 쓰지 않는다 — 첫 프레임에 0 이라 타일이 한 프레임 접혀 있다([[ADR-132]] 정정 30 과 같은 이유).
- **행 높이를 열 폭에서 파생하지 않는다.** 정사각 셀로 두면 격자가 화면 폭에 **비례해 길어져**
  폴더블 펼침(~700dp)에서 4x2 타일 하나가 화면 절반을 넘는다. 위젯은 폭이 늘면 **넓어지는** 물건이다.
- **좌우 16 은 앱 공통값이지 하단바의 14 가 아니다.** 바는 떠 있는 물건이라 다른 자를 써도 되고,
  여기서 14 를 쓰면 today 만 다른 좌우 선을 갖는다.
- 격자 블록 자체는 `ScreenScroll` 의 `gap-4` 흐름 안에 한 덩어리로 들어간다.
- **열 폭을 반올림하지 않는다** — 반올림하면 4칸 타일의 오른쪽이 화면 여백과 최대 3px 어긋난 채로
  조용히 살고, 그 어긋남이 폭마다 다르게 나타나 재현이 어렵다. 소수를 그대로 두면 `tileWidthPx(4)`
  가 언제나 `창폭 − 32` 다.

**계산된 타일 치수** — `tileWidthPx(w) = w×열폭 + (w−1)×12` · `tileHeightPx(h) = h×76 + (h−1)×12`:

| | w=1 | w=2 | w=3 | w=4 | | h=1 | h=2 | h=3 |
|---|---|---|---|---|---|---|---|---|
| 360dp (열 폭 73) | 73 | 158 | 243 | 328 | 높이 | 76 | 164 | 252 |
| 390dp (열 폭 80.5) | 80.5 | 173 | 265.5 | 358 | | | | |

아래 본문이 «158 폭» 이라 부르는 것(2x2 대표 카드의 직업 잘림 · 2x2 수익 타일의 top3 생략)이 이
표의 **360dp · w=2** 칸이다. **이 표는 계산값이고 실기기에서 재지 않았다** — 간격 12 · 행 높이 76 이
아직 제안값이라 그 둘이 바뀌면 표 전체가 함께 움직인다.

## 배치 ([[ADR-147]] 결정 2)

배치는 **명시적 좌표 배열**이다. 흐름 배치(자동 패킹)도, 행 단위(shelf) 배치도 아니다.

```ts
type WidgetHeight = number | 'auto'
interface WidgetPlacement { id: WidgetId; col: number; row: number; w: number; h: WidgetHeight }
function validateWidgetLayout(
  layout: readonly WidgetPlacement[],
  sizesById: Readonly<Record<string, readonly WidgetSize[]>>,
): LayoutViolation[]
```

**`sizesById` 를 인자로 받는다**(레지스트리를 import 하지 않는다) — 검증이 순수 함수로 남아 값
조합만으로 테스트가 서고, 위젯 레지스트리가 이 파일을 몰라도 된다.

검증 **다섯** — ① 겹치는 타일 없음 ② `col + w ≤ 4` ③ 통째로 빈 행 없음 ④ `(w,h)` 가 그 위젯이
선언한 `sizes` 안 ⑤ **`h === 'auto'` 이면 `w === 4`**(아래). 손으로 적는 값이므로 **테스트가 지킨다**.

기본 배치([[ADR-147]] 정정 13 · **정정 32**) — `row` 는 `auto` 타일의 nominal `h = 1` 기준이다.

```
(0,0)  4x1     대표 캐릭터
(0,1)  2x1     초기화 카운트다운      (2,1) 2x1  주간 결정석 판매 한도
(0,2)  4×auto  계정 및 메이플 ID 공유 컨텐츠
(0,3)  4×auto  캐릭터별 남은 스케줄
(0,4)  4x3     주간 보스 수익
(0,7)  2x1     이번 주 최고가 아이템  (2,7) 2x1  가격 미입력
(0,8)  4x1     아이템 드롭 가뭄
```

읽는 순서가 곧 이 배열의 근거다 — 정체(대표) → 마감·상한(초기화 · 결정석) → **한 번만 하면 되는
것**(공유) → 캐릭터별 할 일(남은 스케줄) → 결과(수익) → 결과의 디테일(최고가 · 미입력) → 정서(가뭄).
공유가 위인 이유는 **먼저 치우면 아래 목록이 줄어드는 관계**라서다(사용자 지정).

렌더는 격자 컨테이너 안 절대 배치이고, 컨테이너 높이 = `max(row + h) × (행높이 + 간격) − 간격`.
좌표 해석은 `resolveWidgetPositions(layout, metrics, autoHeightsById)` 하나가 맡는다 — auto 초과분을
누적해 아래 타일을 밀고, 컨테이너 높이를 «가장 아래 타일의 끝» 으로 돌려준다. **`row` 를 재계산해
다시 채우지 않는다**(자동 패킹 금지).

### 높이가 데이터에서 나오는 타일 — `4×auto` ([[ADR-147]] 정정 1)

「남은 스케줄」이 캐릭터를 **전부** 출력하므로 높이를 미리 알 수 없다. 그래서 «타일은 스스로 커지지
않는다» 에 조건 하나짜리 예외를 둔다:

```
h === 'auto'  →  w === 4
```

- **w=4 가 조건의 전부다.** 가로를 다 쓰면 **옆에 아무도 없으므로** 늘어난 만큼 아래 전부가 **같은
  값으로** 내려가고 겹침이 생길 수 없다. 좁은 타일에 auto 를 허용하면 옆 칸과 아래 칸이 서로 다른
  만큼 밀려 좌표가 무너진다.
- **`row` 는 그대로 손으로 적는다.** auto 타일의 `h` 는 **최소 높이**이고, 렌더러가 실측과의 차이만큼
  아래를 내린다 — `y = 적어 둔 y + Σ(위쪽 auto 타일들의 초과분)`.
- **타일 안 스크롤 금지는 그대로다.** 늘어나는 것과 스크롤하는 것은 다르다.

- **자동 패킹을 안 쓰는 이유는 «검증할 것이 없어서»** 다 — 알고리즘은 늘 어딘가에 넣으므로 배치
  실수가 실수로 드러나지 않는다.
- **shelf 를 안 쓰는 이유는 세로 타일**이다 — 한 행의 높이가 하나면 `1x2`·`2x2` 가 원리적으로
  표현되지 않는다.
- **v1 에서 이 배열은 코드 상수다.** 저장 스키마도 마이그레이션도 만들지 않는다(사용자 결정 —
  «고정 레이아웃 + 확장 가능한 설계»). 편집이 오면 배열만 저장소로 옮기고 검증 함수는 그대로 쓴다.

**기본 배치** (사용자 확정 2026-08-17, [[ADR-147]] 정정 13):

```
(0,0)  4x1     대표 캐릭터
(0,1)  2x1     초기화 카운트다운      (2,1) 2x1  주간 결정석 판매 한도
(0,2)  4×auto  캐릭터별 남은 스케줄   ← 아래 전부가 이 타일의 초과분만큼 내려간다
(0,3)  4x3     주간 보스 수익
(0,6)  2x1     이번 주 최고가 아이템  (2,6) 2x1  가격 미입력
(0,7)  4x1     아이템 드롭 가뭄
```

- **총 높이 852px**(캐릭터 4명 기준). 앞선 배치(1010)보다 158px 짧다 — 대표 카드가 4x2 → 4x1 로
  내려온 몫이 가장 크다. 검산: `max(row + h) = 8` 이므로 격자 자체가 `8×76 + 7×12 = 692` 로 **확정**이고,
  거기에 「남은 스케줄」의 초과분이 더해진다. **더해지는 값만 불확실하다** — 시안 실측을 쓰면
  `236 − 76 = 160` 이라 852, 그 실측을 요약한 식(`55 + 45n`)을 쓰면 `235 − 76 = 159` 라 851 이다
  (위 위젯 2 절의 1px 불일치). 아직 실기기에서 재지 않았다.
- **읽는 순서**: 정체(대표) → **마감·상한**(초기화 · 결정석) → 할 일(남은 스케줄) → 결과(수익) →
  결과의 디테일(최고가 · 미입력) → 정서(가뭄).
- `row` 는 「남은 스케줄」의 nominal `h = 1`(캐릭터 1명, 최소 높이) 기준으로 적는다. 그래서 좌표가
  `(0,3)` 에서 바로 이어지고, 렌더러가 실측 초과분만큼 아래를 민다.

## 위젯 규약 ([[ADR-147]] 결정 3)

```ts
// app/today/widgets/types.ts
interface WidgetDefinition {
  id: WidgetId
  sizes: readonly WidgetSize[]                 // 감당하는 크기(`{ w: number; h: WidgetHeight }`)
  target?: TabRouteName                        // 없으면 누를 수 없는 타일
  Component: React.ComponentType<WidgetProps>
}
interface WidgetProps { w: number; h: WidgetHeight; data: TodayViewModel }
```

- **`h` 는 선언한 값 그대로 내려간다 — `'auto'` 를 숫자로 접지 않는다.** 위젯이 갈라 그리는 기준이
  «내가 선언한 어느 크기인가» 라서, 선언에 없는 값(auto 타일의 nominal `1`)을 넘기면 그 분기가
  실제로는 존재하지 않는 크기를 가리킨다. 최소 높이는 배치를 푸는 쪽(`resolveWidgetPositions`)의
  사정이지 위젯이 알 일이 아니다.
- 표는 `widgets/registry.ts`(존재·크기·목적지) · 배치는 `widgets/layout.ts`(좌표) · 그리는 것은
  `WidgetGrid.tsx` 다. `validateWidgetLayout` 이 읽는 «선언된 크기» 표(`WIDGET_SIZES_BY_ID`)는
  레지스트리에서 **파생**시킨다 — 손으로 적으면 같은 목록이 두 벌이 된다.
- **좌우 여백(16)은 `WidgetGrid` 가 그리지 않는다.** 앱 공통 `px-4` 라 다른 화면과 같이 화면의
  래퍼가 준다 — 격자가 또 주면 두 겹이 되는데, 열 폭 계산은 `창폭 − 32` 를 전제로 서 있다.
- **`onLayout` 이 붙는 것은 `h: 'auto'` 타일뿐이다.** 나머지 치수는 계산으로 나오므로 재면 첫
  프레임에 0 이고 그 0 이 그대로 좌표가 된다([[ADR-132]] 정정 30 과 같은 이유). auto 타일만 재는
  이유는 그 높이가 **계산으로 나오지 않기** 때문이다(내용의 함수다).

- **위젯이 `w`·`h` 로 갈라 스스로 다르게 그린다.** 같은 데이터를 다른 밀도로 말하는 것이지, 큰 타일이
  작은 타일을 확대한 것이 아니다(iOS 위젯의 small/medium/large 와 같은 규약).
- **타일은 스스로 커지거나 줄지 않는다.** 크기는 배치가 준다.
- **넘치면 자르거나 접는다 — 타일 안에서 스크롤하지 않는다.** 타일 안 스크롤은 페이지 스크롤과
  제스처를 두고 싸우고, 위젯이 «작은 화면» 이 되는 순간 격자를 만든 이유가 사라진다.
- **탭 이동은 [[ADR-132]] 결정 9 의 광고 게이트를 탄다** — today 에서 어디로 가든 **그룹 이동**이다
  (today 자신이 그룹이다). 이 화면이 새로 여는 예외는 없다.

## 데이터 ([[ADR-147]] 결정 4)

**위젯은 스토어를 모른다.** `TodayScreen` 이 기존 스토어 넷과 캐시를 읽어 `TodayViewModel` 하나를
만들고 프롭으로 나눠 준다.

이유 셋 — ① 위젯이 화면보다 잘게 쪼개진 단위라 [[ADR-097]] 게이트의 «실행당 1회» 가 자동으로
따라오지 않는다(위젯 아홉이 각자 부르면 아홉 번 시도한다) ② 위젯이 순수 프리젠테이션이면 스냅샷
테스트가 스토어 목킹 없이 값 조합만으로 선다 ③ 같은 드롭 기록을 보는 위젯 셋이 각자 읽으면 각자의
시점에서 읽는다.

### 선행 조건 — `schedule-sync` 단일 비행 (**구현 완료**)

[[ADR-132]] 결정 8 이 기한을 *«today 에 내용이 붙는 시점»* 으로 못 박아 둔 구멍이고, **이 작업이 그
시점이었다.** 게이트 플래그는 성공이 아니라 **시도**를 기록하고(`sync-run-state.ts`) 신선도는 호출이
**끝나야** 갱신되므로, today 의 동기화가 날아가는 중에 스케줄 탭으로 들어가면 게이트가
`시도함 = true` · `신선함 = false` 를 보고 **같은 호출을 한 번 더** 낸다. today 가 첫 화면이라
실행당 첫 동기화를 대개 이 화면이 내므로 이것은 예외가 아니라 **지배 경로**였다.

- 처방은 순서가 아니라 **단일 비행**(진행 중인 호출이 있으면 그 프라미스를 함께 기다린다).
  자리는 `features/schedule-sync/schedule-sync.ts` 의 `inFlightRound` 모듈 변수다.
- **키는 «ocid 집합» 이 아니라 회차다** — 스케줄러 셋과 today 가 같은 추적 목록을 보므로 집합이
  같고, 집합을 키로 삼으면 목록이 다른 조합에서 여전히 두 번 나간다.
- **정산 즉시 슬롯을 비운다 — 실패도 캐시하지 않는다.** 단일 비행은 «평생 한 번» 이 아니라 «동시에
  하나만» 이다([[ADR-101]] 결정 4 와 같은 규칙). 실패를 들고 있으면 재시도가 죽은 결과를 받는다.
- **`prehydrate` 순차 루프는 안 건드렸다.** 그 루프가 순차인 근거([[ADR-101]] 결정 3 — 신선도는 앞
  회차가 끝나야 참이 된다)가 단일 비행으로 약해지지만, **고치는 것은 구멍이지 성능이 아니다.**
  `markSyncAttemptedThisRun` 시점도 그대로다.
- 프로덕션에서 부를 수 없는 `resetSyncSingleFlightForTests` 가 하나 늘었다 — 진행 중인 회차를
  잊어버리면 그 순간 단일 비행이 무너지므로 그 사실을 함수 이름과 주석이 함께 말한다.

### 화면이 거는 조회 — 진입 **하나**, 명시적 재조회 **셋 + 하나** (구현 확정)

| 경로 | 무엇을 부르나 | 근거 |
|---|---|---|
| 진입(마운트) | 컨텐츠 스토어 `loadTrackedOcids()` **하나** + `drop-history.load()` | [[ADR-132]] 결정 8 *«today 는 그 순차 밖의 **네 번째 트리거**»* — 예열이 탭 스토어 셋을 돌고 이 화면이 하나를 더 낸다. 다른 스케줄러 화면과 **같은 횟수**다 |
| 헤더 버튼 · 당김 | 탭 스토어 **셋의 `refresh()`** + `drop-history.load()` | 명시적 재조회는 TTL 을 무시하고([[ADR-097]] 결정 2) 사용자가 요구한 것은 «이 화면» 이다 — 하나만 읽으면 당겨도 보스·수익 위젯이 안 바뀐다. 셋이 동시에 나가도 단일 비행이 **한 회차**로 합친다 |

- **진입은 게이트가 있는 문(`loadTrackedOcids`)으로만 들어간다.** `refresh()` 는 게이트 밖이라
  진입에서 부르면 10분 TTL 이 통째로 사라지고, 그 손실은 화면에 아무 표시도 남기지 않는다. 그래서
  «어느 문을 쓰는가» 를 테스트가 회귀 가드로 잡는다(게이트 자체는 스토어 안의 계약이라 core 몫).
- **대가**: 이 화면에 머무는 동안 TTL 이 만료되면 컨텐츠 쪽만 다시 동기화되고 **보스·수익 위젯은 그
  탭에 들어갈 때까지 옛 스냅샷을 그린다.** 당김·헤더 버튼이 그 자리를 즉시 푼다.
- **동기화 시각 표기는 보스 수익 스토어의 `lastSyncedAt`** 이다 — 스케줄러 두 화면이 쓰는 «선택된
  캐릭터의 `syncedAt`» 은 이 화면에 선택이 없어 쓸 수 없고, 그 값이 이미 «페이지 전체 기준» 이며
  건너뛴 진입에서도 갱신된다([[ADR-111]]).

### 조립은 순수 함수다 — `app/today/view-model.ts`

```ts
function buildTodayViewModel(input: TodayViewModelInput): TodayViewModel
```

`TodayViewModelInput` 은 **스토어 «상태» 를 값으로** 받는다(스토어 인스턴스가 아니라). `now` 도
인자다 — 시계를 받아야 카운트다운·기간 판정이 테스트에서 고정되고, 그래서 이 파일은 `new Date()`
를 부르지 않는다. 위젯이 한 줄도 없는 단계에서 **로직 전부를 값 조합만으로 검증할 수 있는** 것이
이 형태의 값이다.

- **판정을 여기서 다시 쓰지 않는다** — 위 표 둘에 더해 수익 합산은 `groupTotalMeso`, 월드별 결정석은
  `summarizeWorldCrystals`(둘 다 `app/boss-profit/character-groups.ts`), 한도 분모는
  `WEEKLY_CRYSTAL_SALE_LIMIT`, 대표는 `resolveDisplayRepresentative` 가 판다. 두 벌이 되면 today 와
  원래 화면이 다른 수를 말한다.
- **초기화 시각도 조합이다** — 일간은 `getPeriodStartUtcMs(getCurrentKstDateKey(now)) + 24h`, 주간은
  `getMostRecentWeeklyResetKst(now) + 7일`, 월간은 다음 달 기간 키의 시작([[ADR-030]]). KST 오프셋
  상수를 여기서 다시 선언하지 않는다 — 리셋 시각의 진실이 둘이 된다.
- **`resets` 는 남은 시간과 «다음 초기화 시각(`atMs`, epoch ms)» 을 함께 준다** — 위젯이 스스로 시간을
  세게 되더라도 기준이 뷰모델 재생성에 흔들리지 않게 하려고 둔 값이다. **지금은 아무 위젯도 읽지
  않는다**(구현 확정) — 카운트다운에 초 단위 tick 이 없어 `remainingMs` 만으로 충분하고, 값이 다시
  계산되는 것은 `TodayScreen` 이 다시 렌더될 때뿐이다. 초를 그리기로 하면 그때 이 값이 tick 의 기준이
  된다.
- **`resets` 는 «주기 한 바퀴의 길이(`periodMs`)» 도 함께 준다**(구현 확정) — 위젯 6의 2x2 진행 바가
  «주기의 어디쯤인가» 를 그리는 분모다. 일간·주간은 상수지만 **월간은 달마다 다르고**(28~31일),
  위젯이 그것을 스스로 구하려면 KST 달 경계를 다시 계산해야 한다 — 리셋 시각의 진실이 둘이 되는
  자리라 경계를 이미 아는 이 파일이 뺄셈 한 번으로 함께 낸다.

#### 「이번 주」 의 범위 — 위젯 3·4·7 이 같은 자를 쓴다

셋 다 **현재 주간 기간 키 하나**로 자른다(보스 수익 화면의 주간 탭과 같은 범위). 스토어가 다른
탭·기간을 보고 있으면 그 행은 세지 않는다.

- 월간 키(`YYYY-MM`)로 저장되는 검은마법사 드롭은 여기 **안 든다** — 그쪽은 보스 수익 화면 월간 탭의
  몫이고, 위젯 3이 이미 주간 탭 기준이라 셋이 갈리면 같은 격자에서 서로 다른 기간을 말하게 된다.
- 셋이 같은 범위여야 위젯 7(가격 미입력)이 위젯 4(최고가)의 «없음» 을 설명한다([[ADR-147]] 결정 9).
- `unpricedCount` 는 `priceState === undefined` 만 센다 — `'excluded'`(기록 안함)는 «값을 매기지
  않기로 한» 사용자의 결정이라 기다리는 건이 아니다.
- **`unpricedPreview` 는 그중 앞 셋**이고 정렬하지 않는다(구현 확정) — 2x2 타일이 **이름**을 세우려면
  건수만으로는 부족한데, 미입력 건에는 비교할 값이 없어 «무엇 기준으로 앞 셋인가» 를 주장할 수 없다.
  그래서 스토어가 준 순서(`period_key DESC, ocid, boss, difficulty, drop_index`)를 그대로 쓴다.
- **금액 없는 드롭 타입이 금액 있는 쪽의 상위 타입**이다(`PricedDropView extends UnpricedDropView`) —
  미입력 건은 «아직 값이 없는» 것이지 «0원인» 것이 아니라([[ADR-147]] 결정 9), 그 사실이 타입에서도
  필드의 **부재**로 남는다.

#### 뷰모델이 정하는 나머지 둘

- **`scheduleTotal` 에 동기화 실패 캐릭터를 넣지 않는다** — 그 캐릭터의 남은 수는 «모르는» 값이고,
  화면에서도 수치 대신 「동기화 실패」가 선다. 합계가 화면에 보이는 숫자의 합과 일치한다.
- **대표 캐릭터 프로필이 캐시에 없으면 `null`** — 이름 없이 카드를 그릴 수 없고, ocid 는 사용자에게
  뜻이 없는 값이라 대신 넣지 않는다(`drop-history-store` 와 같은 규칙).
- **가뭄 기간의 라벨(`periodLabel`)도 여기서 만든다**(구현 확정) — `formatBossProfitPeriodLabel` 이
  «지금이 언제인가» 를 받아야 「이번 주」를 말할 수 있는데, 위젯이 시계를 읽으면 같은 화면의 두
  타일이 다른 시각을 말한다(위젯 6과 같은 규칙). 히스토리 화면과 **같은 라벨 함수**라 두 자리가 같은
  주를 다르게 부르지 않는다.

### 1. 대표 캐릭터 — 전투력은 보류, 경험치는 편승 ([[ADR-147]] 결정 7)

사용자 요청은 «닉네임 · 월드 · 레벨 · 길드 · 전투력 · 경험치 %» 였다.

- **전투력은 `character/basic` 에 없다.** 별도 엔드포인트의 스탯 배열이라 넣으면 **캐릭터당 호출이
  하나 더 느는 축**이 열리고, [[ADR-097]] 호출 예산을 다시 계산해야 한다. 이번에 하지 않는다
  (사용자 결정 — «경험치만 넣고 전투력은 보류»).
- **경험치는 같은 응답에 편승해 추가 호출이 0** 이고, 필드는 **확인됐다**(사용자 2026-08-17):
  `character_exp`(number, 누적 절대값) · `character_exp_rate`(**string**, `"80.300"`).
  - **`character_exp_rate` 가 문자열인 것이 함정이다** — `access_flag` 와 같은 모양이고, 문자열째
    비교하면 `"9.500" > "80.300"` 이 참이 되어(사전순) 진행률 바가 **조용히 뒤집힌다.** 정규화가
    `Number()` 로 풀어 `CharacterBasicProfile.expRate?: number` 로 싣는다.
  - **`character_exp`(누적 절대값)는 화면에 쓰지 않는다** — 레벨이 오를수록 커지는 값이라 «얼마나
    남았나» 를 말하지 못한다. 카드가 답할 것은 진행률이다.
- **타입은 옵셔널이되 «EXP 없음» 상태를 설계하지 않는다**([[ADR-147]] 정정 8, 사용자 판정). 옛 캐시
  엔트리에 그 필드가 없는 것은 사실이므로 값이 없으면 그 줄을 안 그리는 **방어적 기본값**만 남기고,
  그 상태를 화면 설계의 한 갈래로 두지는 않는다.

**카드는 월드 엠블럼 + 두 줄이다**([[ADR-147]] 정정 7 · **38**) — **4x2 · 4x1 · 2x2 셋 모두 같은 구조**.

```
[초상화] [엠블럼] 단풍루틴  백호단          EXP 80.300%
         Lv. 291  아크메이지(불,독)   ══════════════════
```

**길드는 닉네임 옆이다**(정정 38, 사용자 지시) — 셋째 줄에 혼자 서던 값인데 길드는 «누구인가» 의
일부지 별도 항목이 아니고, 4x1 은 내부 높이가 52 뿐이라 그 한 줄이 크다. 넘치면 **닉네임이 줄어든다**
(길드는 잘리면 다른 길드로 읽히지만 닉네임은 초상화가 이미 말한다).

- **월드는 텍스트 배지가 아니라 엠블럼 이미지**다 — `lib/world-emblem.ts` 의 `worldEmblemUrl(world)`
  (`world-emblems.json` 18종 + `assets/worlds/*.png`). 매핑에 없거나 파일이 없으면 `null` 이고 그때는
  **엠블럼만 생략**한다(그 함수가 이미 정한 폴백).
- **직업(`jobClass`)이 카드에 처음 선다.** [[ADR-144]] 결정 2의 «레벨 + 직업» 과 같은 조합이라 새
  규칙이 아니다. 그 값은 `character/basic` 이 아니라 `character/list` 에서 오므로 **옛 캐시에는 없고**,
  없으면 그 줄이 레벨만 그린다(타입이 이미 정한 규칙).
- **2x2 에서 직업이 잘린다** — 「아크메이지(불,독)」이 158폭의 한계다(열린 질문).
- **크기가 가르는 것은 밀도와 EXP 의 자리뿐이다**(구현 확정) — 4x1 은 EXP 가 **오른쪽 100px 열**(정정 38 — 70 에서 늘렸다. 바가 짧아 진행률이 눈에 안 들어왔고, 늘어난 30px 은 이름 줄에서 가져온다)
  (`EXP` + 퍼센트 + 얇은 바), 4x2·2x2 는 세 줄 **아래 전폭**. 초상화 44 / 72 / 56 · 이름 13 / 19 /
  14px 이고 2x2 만 가운데 정렬이다.
- **모르는 줄은 그리지 않는다** — `expRate` 가 없으면 EXP 블록째 없고(정정 8), 길드는 «미가입»
  (`null`)과 «모름»(`undefined`) 둘 다 줄을 비운다(이 카드는 그 둘을 가르는 자리가 아니다).
  **`expRate === 0` 은 아는 값이라 그린다** — 없는 것과 0 은 다르다.
- **진행률은 `toFixed(3)`** — API 가 준 소수 3자리 그대로다. 반올림하면 `99.999%` 가 `100%` 가 되어
  «다 찼다» 고 거짓을 말한다.

**«대표 없음» 상태는 존재하지 않는다**([[ADR-147]] 정정 2, 사용자 지시). [[ADR-143]] 결정 4가
*"미지정이면 목록의 첫 번째가 «임시 대표»"* 로 이미 답을 갖고 있고, **today 가 그 값을 읽는 첫
화면**이다.

- `resolveRepresentative`(`features/character-manage/derivations.ts`)는 지금 일부러 `null` 을 돌려주고
  주석이 그 이유를 *"그 값을 읽는 화면이 아직 하나도 없고"* 로 적어 두었다 — **그 문장이 낡는다.**
- **그 함수를 고치지 않고 옆에 하나 더 만든다** — `resolveDisplayRepresentative(orderedOcids, stored)`
  = `stored ?? orderedOcids[0] ?? null`. 둘은 **다른 질문**이다: 기존은 «사용자가 대표라고 말했는가»
  (캐릭터 관리의 채워진 별), 새것은 «지금 대표 자리에 설 캐릭터는 누구인가»(today 카드). 기존 함수를
  폴백시키면 [[ADR-144]] 결정 4(*대표를 안 고른 화면은 채워진 별이 하나도 없다*)가 깨진다.
- **«임시» 라는 표시는 하지 않는다** — [[ADR-143]] 결정 4의 *"그 규칙도 화면에 그리지 않는다"* 를 잇는다.

### 2. 남은 스케줄 — 이름·표기·정렬 ([[ADR-147]] 정정 3)

```
야간비행                    일퀘 4 · 주간퀘 1
                       주간 보스 1 · 검마 1
```

| 자리 | 값 |
|---|---|
| 분류 이름 | **일퀘 · 주간퀘 · 주간 보스 · 검마** |
| 수치 형태 | **텍스트**(알약 아님) · **두 줄** — ① 일퀘·주간퀘 ② 주간 보스·검마 |
| 수치 정렬 | **라벨 폭 고정 + `tabular-nums`** — 모든 행의 숫자가 같은 x 에 선다([[ADR-147]] 정정 12) |
| 강조 | **`font-weight` 400 → 800.** 라벨은 `text-muted`, 숫자는 닉네임과 같은 `text`(읽기 2 확정) · **테마 색 금지** |
| 실패 정렬 | **동기화 실패 캐릭터는 언제나 맨 아래** — 남은 개수를 모르므로 비교 대상이 아니다 |
| 배지 | **특수 케이스만** — `CLEAR` · 「동기화 실패」. 수치가 아니라 **상태**라 형태를 달리할 근거가 있다 |
| 완료 표기 | **`CLEAR`** (「다 했습니다」 같은 문장은 쓰지 않는다) |
| 자리 | 닉네임 **오른쪽**(상하 배치 금지) |
| 범위 | **선택된 캐릭터 전부** — 「외 N명」 접기 없음 |
| 전부 완료 | **전용 UI 없음** — 같은 목록이 전부 `CLEAR` 로 선다 |
| 정렬 | **남은 개수 많은 순 → 동수면 캐릭터 관리 순서** |

- **강조에 테마 색을 안 쓰는 이유**([[ADR-147]] 정정 9): 숫자를 `primary-ink` 로 칠하면 이 타일 하나에
  강조색이 **캐릭터 수만큼 반복**돼 격자에서 «여기가 제일 중요하다» 를 잘못 말한다.
- **정렬이 형태의 전부다**([[ADR-147]] 정정 12). 라벨 길이가 제각각(「일퀘」 2자 · 「주간 보스」 4자)이라
  그냥 나열하면 숫자가 행마다 다른 x 에서 끝나고 세로로 훑을 수가 없다. 라벨 폭을 고정하고
  `tabular-nums` 를 걸어 **2×2 격자**(col A = 일퀘/주간 보스, col B = 주간퀘/검마)로 세운다.
  `·` 구분자는 없애고, 행 사이에 헤어라인 · 헤더 아래에 `border-strong` 한 줄.
- **0 인 칸은 글자만 비우고 자리는 남긴다**(구현 확정) — 「일퀘 0」은 훑는 눈에 잡음이고, 칸을
  없애면 열이 어긋난다. `CLEAR`(전부 완료)·「동기화 실패」일 때만 격자 대신 배지 하나가 선다.
- **수치 줄 높이를 값으로 박는다**(`STAT_LINE_HEIGHT_PX = 14`, 구현 확정) — 빈 칸을 빈 글자로 두는
  것만으로는 부족하다. **빈 `Text` 의 높이가 플랫폼마다 다르므로**(글리프가 없으면 0으로 재는 경우가
  있다) 줄에 높이를 박지 않으면 보스 0인 캐릭터의 행만 접혀 아래 auto 계산이 성립하지 않는다.
- **높이 예상은 `55 + 45n` px 이고, 이 값을 믿지 마라.** [[ADR-147]] 정정 12 가 시안(HTML)에서 재
  «2명 145 · 4명 236 · 6명 326» 을 적고 그것을 `55 + 45n` 으로 요약했는데 **둘이 안 맞는다** —
  식은 145 / **235** / **325** 를 준다(4·6명에서 1px 차). 어느 쪽이 맞는지는 **RN 구현에서 다시 재지
  않아 모른다**: jest 는 레이아웃을 계산하지 않아 auto 높이를 스텁으로 흉내 내므로 자동 테스트로
  확인할 방법이 없다. **다행히 틀려도 화면은 안 깨진다** — 실제 높이는 `onLayout` 이 정하고 이 식은
  문서의 예상일 뿐이라, 어긋나는 것은 아래 「기본 배치」의 총 높이 계산뿐이다(실기기 확인 대상).
- **«맨 아래» 는 «0으로 취급» 이 아니다**(구현 확정) — 실패 여부가 **첫 번째 정렬 키**이고 남은 개수는
  그 다음이다. 0 으로 치환하면 실패 캐릭터가 `CLEAR`(남은 0) 캐릭터와 **동수로 묶여** 관리 순서에
  따라 그 위에 설 수 있다. 실패는 «모르는» 것이라 비교에 참여하지 않는 것이 맞다 — 위로 올리면
  «제일 밀린 캐릭터» 자리를 모르는 값이 차지한다(사용자 확정).
- **둘째 줄이 비어도 자리를 남긴다.** 보스가 0인 캐릭터는 둘째 줄이 비는데, 행을 줄이면 **행 높이가
  데이터마다 달라져** 목록이 들쭉날쭉해진다. **줄 수 자체는 목록 전체가 정한다**([[ADR-147]] 정정
  35) — 아무도 안 쓰는 줄은 모든 행에서 같이 빠지므로 행끼리는 여전히 같은 높이다. 그래서 실측
  `55 + 45n` 은 **두 줄이 다 설 때의 값**이고, 한 줄만 서면 그만큼 낮아진다(실기기에서 다시 잰다).

- **「검마」는 종류가 하나라서 종류 이름 대신 고유명이 선다.** `weekly-bosses.json` 의 `monthly` 가
  검은마법사 한 항목이라 «월간 보스 1» 과 «검마 1» 이 같은 말이고 더 짧다. **월간 보스가 둘이 되면 이
  이름이 거짓이 된다** — 참조 데이터에서 자동 파생하지 말고 그때 다시 정한다([[ADR-006]] 태도).
- **전부 완료에 축하 UI 를 두지 않는 근거는 위 «위젯은 사라지지 않는다» 와 같다** — 형태가 안 바뀌어야
  «어제와 같은 화면» 으로 읽힌다.

**행을 누르면 타일 안에서 펼친다**([[ADR-147]] 정정 25·26, 사용자 지시) — 화면을 옮기지 않는다.

| 자리 | 값 |
|---|---|
| 본문 | 카테고리 줄(일퀘 · 주간퀘 · **보스**) + 이름 알약. 보스는 주간·검마를 한 그룹으로 묶는다 |
| 보스 난이도 | **공용 `DifficultyBadge`** — 이 화면만의 표기를 새로 만들지 않는다 |
| 항목 이름 | **일일은 지역명까지**(`[일일 퀘스트] 소멸의 여로 조사` → `소멸의 여로`) · **주간은 접두어만**(`[주간 퀘스트] 타락한 세계수 정화에 대한 보답` 그대로, [[ADR-147]] 정정 41) · 그 밖은 원문 |
| 여닫기 | 행을 누르면 열리고 **같은 행을 다시 누르면 닫힌다** |
| 동시 펼침 | **하나** — 여섯이 다 열리면 1,000px 을 넘는데 타일 안 스크롤은 금지다(결정 3) |
| 상태 보존 | **안 한다**(저장소에 안 쓴다). 탭이라 앱을 켜 둔 동안은 남는다 |
| `target` | **없다** — 행이 각자 눌리면 타일 전체를 감싼 `Pressable` 이 설 수 없다(중첩) |

- **줄도 칸도 «그 행» 이 정한다**([[ADR-147]] 정정 35~37). **줄**(계열 — ① 일퀘·주간퀘 ② 주간
  보스·검마)은 그 행에 그 계열의 값이 하나라도 있을 때 서고, **칸**(수치)은 그 행에 그 값이 있을 때
  선다. 줄은 오른쪽 정렬이라 칸이 줄면 셰브런 옆에 붙는다. 아무도 보스가 안 남았으면 둘째 줄이
  여섯 행에서 다 같이 빠지는데, 그건 특수 규칙이 아니라 **이 규칙의 한 경우**다.
- **그 대가로 «모양이 다른 행 사이» 의 정렬과 «고른 행 높이» 를 잃는다**(정정 36·37). 빈 자리를
  남겨 두는 것이 곧 정렬이라 둘 다는 못 가지고, 사용자가 세 번에 걸쳐 간결함을 골랐다. 같은 모양의
  행끼리는 여전히 한 열이고(`tabular-nums` 와 칸 폭 상수는 남긴다), 목록이 남은 개수 순이라 그런
  행들이 대체로 붙어 선다.
- **주간만 접두어까지인 이유**([[ADR-147]] 정정 41, 사용자 지시) — 같은 지역에 **둘**(`타락한 세계수
  주간 임무` / `… 정화에 대한 보답`)이 있어 **그 뒷말이 곧 구분**이다. 지역명까지 줄이면 같은 칩이
  둘 서고, 실제로 그랬다. 일일은 지역당 하나뿐이라 뒷말이 정보를 안 더한다.
- **본문은 자르지 않는다.** 일퀘가 여덟이면 여덟을 다 적는다 — 「외 3개」로 접으면 펼친 이유가
  사라진다. 늘어난 높이는 `resolveWidgetPositions` 가 아래 타일을 밀어 흡수한다.
- **`CLEAR`·동기화 실패 행은 안 열린다** — 보여 줄 것이 없거나 **모른다**. 셰브런도 안 선다.
- **뷰모델은 개수 대신 이름을 든다**(정정 26) — 접힘의 수치는 그 배열의 `length` 라, 두 층이 같은
  배열 하나를 보고 «세는 것 = 보이는 것» 이 구조로 성립한다. **새 판정은 없다.**

### 3. 주간 보스 수익 — 증감 없음 · **0을 그린다** ([[ADR-147]] 정정 4)

- **증감 칩을 쓰지 않는다.** `rise`/`fall` 토큰과 `previousPeriodTotalMeso` 는 보스 수익 화면에
  그대로 살아 있고([[ADR-087]]), **이 위젯에서만** 안 쓴다.
- **기록이 없으면 `0 메소`** 로 그린다(사용자 지시). 위 «큰 0 을 그리지 않는다» 를 **이 위젯에서만**
  뒤집는 것이고, 그 규칙이 지키려던 것은 옆의 한 줄(*아직 이번 주 기록이 없습니다*)로 남긴다.
- **큰 금액 뒤에 `메소`.** 목록 행(top3)에는 안 붙인다 — 머리가 이미 단위를 말했다.
- **총 수익과 캐릭터별 수익은 결정석 + 아이템이다**([[ADR-124]]). 아이템 금액은 `lib/drop-price.ts`
  의 `sumDropPayout` 을 쓴다 — 합산을 두 벌로 만들면 이 위젯과 보스 수익 화면이 다른 규칙으로 더한다.

**네 크기가 무엇을 버리는지**(구현 확정):

| 크기 | 형태 |
|---|---|
| **4x3** | 기간 라벨 + 큰 금액(32px) + **결정석/아이템 스택 바 + 분해 금액** + 캐릭터 top3(**행마다 내역**) |
| 4x2 | 왼쪽 금액 + 스택 바, 오른쪽 top3(**내역 없이 이름 + 금액**) |
| 2x2 | 금액 + 스택 바 — **top3 없음**(158 폭에 «이름 + 금액» 행이 안 들어간다) |
| 2x1 | 기간 라벨 + 금액 — **스택 바·top3 없음**(기록이 없으면 여기에도 미기록 한 줄이 선다) |

- **스택 바가 이 타일에서 «두 번째 숫자» 의 자리다.** 증감 칩을 뺀 자리(정정 4)를 채우는 것은 시간축
  비교가 아니라 **구성 비교**다 — 이번 주 수익이 결정석에서 왔는지 아이템 판매에서 왔는지는 그 자체로
  이번 주의 사실이라 다른 기간을 조회하지 않는다. 색은 [[ADR-142]] 링과 같은 짝(`primary` = 결정석 ·
  `third` = 아이템)이고, 분해 금액이 같은 두 색 점을 달아 바를 읽는 법을 말한다.
- **그래서 뷰모델이 `crystalMeso`·`itemMeso` 를 함께 낸다**(위젯 단위·캐릭터 단위 둘 다). 위젯은
  스토어를 모르므로([[ADR-147]] 결정 4) 총액만 받으면 갈라 그릴 방법이 없다. 값은 새로 세지 않고
  기존 함수 둘을 그대로 쓴다 — 결정석 `sumPayout(bossRows)` · 아이템
  `sumDropPayout(collectGroupDrops(...))` 이고, 둘의 합이 `groupTotalMeso` 와 같다(이번 주 계산에는
  주차별 소계가 언제나 비어 있다).
- **금액은 `formatMesoShort` 로 접는다** — 두 벌로 만들면 이 타일과 보스 수익 화면이 다르게 접는다.
  그래서 **카운트업(`AnimatedMeso`)을 쓰지 않는다**: 그 컴포넌트는 `toLocaleString()` 의 자릿수 전체를
  굴리는 물건이라 접힌 표기와 애초에 짝이 맞지 않고, [[ADR-087]] 결정 6이 카운트업을 건 범위도
  보스 수익 화면이다.
- **기록이 없으면 스택 바·분해 금액 자리에 그 한 줄이 선다** — 0/0 인 바와 「결정석 0 · 아이템 0」은
  분해할 것이 없는데 분해한 척이다.

### 4·7·8. 「가장 비싼」은 시세가 아니라 **기록된 판매가** 순위다 ([[ADR-147]] 결정 9 · 정정 5)

앱은 아이템 시세표를 갖고 있지 않다. 아이템 금액의 유일한 출처는 사용자가 입력한 실제 판매가
(`RecordedDrop.priceMeso`)다. 그래서 위젯 4의 뜻은 정확히 **«이번 주에 기록된 판매가 중 가장 큰 것»**
이다.

- **가격 미입력 드롭은 순위에 넣지 않는다.** 값을 모르는 것을 가장 싼 것으로 단정하는 일이다.
  (`dropPayoutMeso` 가 합산에서 미입력·스킵을 0 으로 접는 것과는 **다른 문제**다 — 합산은 «더할 것이
  없다» 이지만 순위는 «비교했다» 를 주장한다.)
- **그래서 위젯 7(가격 미입력 N건)이 같은 격자에 있다.** 위젯 4가 «없음» 을 말하는 가장 흔한 이유가
  «안 팔았거나 안 적었다» 이므로, 그 답을 옆 타일이 들고 있어야 한다. **그리고 옆 타일이 들고 있으므로
  위젯 4 안에는 미입력 칩을 두지 않는다**([[ADR-147]] 정정 5 — 건수를 두 곳에서 말하지 않는다).
- 위젯 4의 표기 둘([[ADR-147]] 정정 5): 2x2 의 **아이템 이름은 한 줄**(두 줄로 접으면 행 높이가
  데이터에 따라 흔들린다) · 4x2 의 오른쪽은 **`top 5`**(2~5위) · 0건 문구는 **«가격이 입력된 아이템이
  없습니다»** 한 줄뿐.

> **⚠️ 지금 이 둘은 실기기에서 값을 못 받는다 — 원천이 가격을 안 싣는다.**
> `drop-history-store` 의 `toHistoryRecord` 가 저장 행을 `DropHistoryRecord` 로 옮기며 **가격 세 필드
> (`priceState`·`priceMeso`·`priceShare`)를 옮기지 않는다.** 저장소(`boss_drop_records`)에도 조회
> 함수(`getAllBossDropRecords`)에도 그 값이 있고 가격 기록 화면(`drop-price-store`)은 잘 읽는데,
> 히스토리 쪽 투영에서만 빠진다. 그래서 today 에서는 **위젯 4가 언제나 «가격이 입력된 아이템이
> 없습니다»** 이고 **위젯 7은 «기록 안 함»(`excluded`)까지 미입력으로 센다.**
> 뷰모델·위젯은 값이 오면 그대로 그린다(테스트가 값을 넣어 검증한다) — 고칠 자리는 그 한 함수다.
> **이 phase 의 범위 밖이라 손대지 않았다**(그 투영은 드롭 히스토리 화면도 함께 쓴다).

**위젯 4의 네 크기**(구현 확정):

| 크기 | 형태 |
|---|---|
| **2x1** | 「이번 주 최고가」 + 아이콘 36 + `12.0억 메소` — **아이템 이름 없음** |
| 4x2 | 제목 + 왼쪽 1위(아이콘 44 + 금액 + 이름 + 캐릭터·보스) · 오른쪽 2~5위 목록 |
| 2x2 | 제목 + 아이콘 40 + `12.0억 메소` **한 줄** + 아이템 이름 한 줄 + 캐릭터·보스 |
| 1x1 | 아이콘 + 금액 — **제목도 「메소」도 없다**([[ADR-147]] 정정 11, 물리적으로 안 들어간다) |

제목(「이번 주 최고가」)은 **1x1 만 버린다** — 위 세 크기는 다 그린다.

- **2x1 이 이름을 버리는 이유**는 이름이 잘려야 들어가기 때문이다. 「이번 주 최고가」 + 금액은 둘 다
  안 잘리고, 잘린 이름 한 조각보다 «얼마였나» 가 이 타일이 답하는 질문이다.
- **캐릭터 이름은 프로필 캐시에서 온다** — `PricedDropView.characterName` 이 옵셔널인 이유이고,
  캐시에 없으면 보스만 선다(ocid 를 대신 넣지 않는다 — 대표 카드와 같은 규칙).
- **아이콘 조회에 `slot` 을 함께 넘긴다**(`getItemIconUrl(name, slot)`) — 지금 데이터에는
  `iconFileBySlot` 이 없지만 다른 호출부 여섯이 전부 넘기고 있고, 안 넘겨서 나는 실패는 에러가 아니라
  **조용한 폴백 원**이다.
- **위젯 8(아이템 드롭 가뭄)은 가격 없이도 선다** — `isValuableDrop` 판정이 **이름 기반**이다. 두 위젯이
  겹쳐 보이지만 묻는 것이 다르다(얼마였나 / 언제 마지막이었나).

### 5. 주간 결정석 판매 한도 — 링은 **연속 호**, 한도는 **합치지 않는다** ([[ADR-054]])

**한도는 계정이 아니라 월드마다 각각이다**([[ADR-054]] 결정 1). 그래서 월드가 둘이면 분모도 둘이고,
이 타일은 그것을 **절대 합치지 않는다** — 보스 수익 화면이 좁은 헤드라인 한 줄에 `46 / 180` 으로
합치는 것([[ADR-054]] 정정 2)은 그 자리의 제약이지 이 격자의 규칙이 아니다. 합친 수는 어느 월드에서도
팔 수 있는 양이 아니다.

- **분모를 위젯이 정하지 않는다** — 뷰모델이 `WEEKLY_CRYSTAL_SALE_LIMIT` 을 `CrystalLimitView.limit`
  에 실어 준다. 위젯 소스에 **그 숫자가 한 번도 안 나오는 것**을 테스트가 검사한다([[ADR-006]]).
- **링은 «칸» 이 아니라 연속 호다**(구현 확정) — [[ADR-054]] 정정 1의 칸 링은 캐릭터당 주간 보스
  한도(12)를 쪼갠 것이라 칸을 셀 수 있었지만, 이 한도는 그 몇 배라 같은 방식이면 읽을 수 없는 톱니가
  된다. 비율을 말하는 링은 연속 호라는 [[ADR-142]] 결정 3의 갈래가 그대로 적용된다.
- **링 안의 분자·분모는 두 줄이지만 한 값**이다([[ADR-147]] 정정 15) — 줄 높이를 글자 크기의 0.92 로
  낮춰 붙인다. 벌어지면 «34» 와 «/90» 이 두 값으로 읽힌다.
- **글자는 링 크기에서 파생한다**(분자 0.27 · 분모 0.2) — 크기마다 따로 정하는 자리를 안 만든다.
- **잔량(`56개 남음`)이 글자가 되고 링은 소진량이 찬다** — 이 타일이 답하는 질문이 «더 팔 수 있나»
  라서다. 한도를 넘겨도(추적 밖 캐릭터, [[ADR-054]] 알려진 한계 1) «−n개» 라고 하지 않는다.

| 크기 | 형태 |
|---|---|
| **2x1** | 링 42 + 「결정석 판매」 + 월드명 + `56개 남음` — **첫 월드 하나** |
| 4x1 | 월드를 나란히 **최대 셋**(각각 링 38 + 월드명 + 남은 수) · 제목을 버리고 그 폭을 월드에 쓴다 |
| 2x2 | 제목 + 큰 링 56 + 주 월드 + 남은 수 + 나머지 한 줄(하나면 이름, 둘 이상이면 «외 N개 월드») |
| 1x1 | **링만** — 월드 이름이 사라진다 |

- **1x1 은 월드가 하나인 사용자에게만 정직하다**(주석에 명시) — 접근성 이름은 링이 계속 월드를 말한다.
- **집계할 것이 없으면 «집계할 기록이 없습니다» 한 줄**이다. 이유가 둘인데(이번 주 처치가 없다 /
  월드를 아는 행이 하나도 없다 — 구버전 캐시, [[ADR-054]] 결정 6) **어느 쪽도 단정하지 않는다**:
  「판매 0개」는 없는 사실을 단정하고, 「월드를 모릅니다」는 사용자가 할 수 있는 일이 없는 내부 사정이다.
  보스 수익 화면은 이 경우 줄을 통째로 지우지만([[ADR-054]] 구현 메모) **위젯은 사라질 수 없다.**

### 6. 초기화 카운트다운 — **KST 기준 · 일일만 1초 갱신** ([[ADR-147]] 정정 39)

- **목적지가 없는 유일한 타일**이다 — 초기화 시각은 이 타일이 다 말하고 더 볼 화면이 없다.
- **셋 다 KST 기준이다**(실측 확인 2026-08-18) — 일일은 `getPeriodStartUtcMs(getCurrentKstDateKey(now)) + 1일`,
  주간은 `getMostRecentWeeklyResetKst`(KST 목 00:00), 월간은 KST 월초. 세 함수 모두 `Date.UTC(...) − 9시간`
  으로 계산해 **기기 타임존과 무관**하고, 그 사실을 테스트가 타임존을 바꿔 가며 지킨다.
- **일일만 초까지 그리고 1초마다 다시 그린다** — `12시간 34분 56초`. 주간·월간은 분까지다(수십 시간
  남은 값에 초를 붙이면 글자만 길어진다). 일일에서 **«1분 미만» 은 사라진다** — `43초` 가 그 말을
  직접 한다. 숫자에 `tabular-nums`.
- **기준은 `atMs`** — 남은 시간을 틱 수로 세면 백그라운드에서 타이머가 눌려 조용히 뒤처진다. 절대
  시각에서 빼면 몇 번을 못 세도 다음 렌더가 맞는 값을 준다. 결정 4(«위젯은 시계를 안 읽는다»)를
  **이 위젯에서만** 뒤집는 것이고, 뷰모델 전체를 1초마다 다시 만들지 않기 위한 대가다.
- **임박을 색으로 말하지 않는다** — 1시간 미만에 `error` 를 빌리는 안이 시안에 있었으나 **색이 확정되지
  않았다**(실패가 아니라 임박인데 이 앱에 «경고» 축이 없다). 값이 무엇이든 글자 스타일이 같다는 것을
  테스트가 계약으로 잡는다.

| 크기 | 형태 |
|---|---|
| **2x1** | 「초기화까지」 + 일일 · 주간 두 줄 — **월간을 버린다**(대개 멀어 지금 급한 것이 아니다) |
| 2x2 | 셋 + 각각 **진행 바**(지난 몫이 찬다 · 분모는 뷰모델의 `periodMs`) |
| 4x1 | 셋을 가로로, 숫자를 16px 로 — 폭이 좁아 **초를 안 그린다** |
| 1x1 | 일일만 + 값이 **가장 큰 단위 하나**로 접힌다(초는 물리적으로 안 들어간다) |

### 7. 가격 미입력 드롭 — 옆 타일의 «없음» 을 이 타일이 설명한다

위젯 4가 「가격이 입력된 아이템이 없습니다」를 말하는 가장 흔한 이유가 «안 팔았거나 안 적었다» 이고,
**그 답을 이 타일이 든다**([[ADR-147]] 결정 9). 그래서 건수는 **여기서만** 말한다(정정 5).

**세 크기**(구현 확정):

| 크기 | 형태 |
|---|---|
| **2x1** | 건수 배지 36 + 「가격 미입력」 + `기록하기 ›` |
| 2x2 | 배지 28 + 제목 + **아이템 이름 셋까지** + `외 N건 · 기록하기 ›` |
| 1x1 | 건수 + 「가격 미입력」 — **행동 유도가 빠진다**(물리적으로 안 들어간다) |

- **2x2 만 이름을 보여 주는 이유**: 「값을 적어야지」보다 **「그 연마석 얼마에 팔았지」** 가 손을
  움직이는 문장이다. 건수만으로는 그 문장이 안 나온다.
- **이름 옆에 캐릭터·보스를 붙이지 않는다** — 붙이면 이름이 잘리는데, 이 타일이 답하는 질문은
  «무엇의 값을 적어야 하나» 라 이름이 먼저다. **반지 레벨은 이름의 일부로 센다**(같은 반지의 다른
  레벨은 다른 물건이다).
- **미리보기에 안 든 나머지는 «외 N건»** 으로 남는다 — 0이면 그 조각째 빠진다(«외 0건» 은 없는 것을
  세는 말이다). 타일은 목록이 아니라 요약이고 타일 안에서 스크롤하지 않는다([[ADR-147]] 결정 3).
- **배지 색은 `surface-2` 다** — 이 타일이 말하는 것은 «성과» 가 아니라 «밀린 일» 이고, 격자의 강조색은
  결과를 말하는 타일들이 이미 쓴다.
- **0건이어도 타일은 남고**([[ADR-147]] 결정 5) 「전부 기록했습니다」로 내용이 바뀐다. **그때는 행동
  유도도 함께 사라진다** — 기록할 것이 없는데 「기록하기」로 보내면 빈 화면에 도착한다. 「0건」이라
  쓰지 않는 이유는 숫자 0이 할 일처럼 읽히기 때문이다.

### 8. 아이템 드롭 가뭄 — 문구가 **단계마다 풀**이 된다 ([[ADR-147]] 정정 6)

문구·단계는 `lib/drop-history.ts` 가 이미 갖고 있다(`getValuableDroughtTier` ·
`formatValuableDroughtHeadline`). 지금은 0~3주가 **한 줄 고정**이고 마지막 단계만 풀인데, 전 단계를
풀로 바꾼다(사용자 지시 — *"최근 한국 인터넷 밈을 활용해서 좀 다양하게"*).

```ts
// headline: string  →  headlines: readonly string[]
formatValuableDroughtHeadline(weeksSince, lateIndex)  →  (weeksSince, index)
```

- **무작위 인덱스는 마운트당 한 번** 고른다 — 매 렌더마다 고르면 리렌더 때 문구가 깜빡인다(그 파일이
  적어 둔 규칙). 순수 함수를 유지하려고 `Math.random()` 을 그 파일에 두지 않는 규칙도 그대로다.
- **기존 다섯 줄은 지우지 않고 풀에 남긴다** — 그 파일 주석이 «앞 둘은 사용자 지정» 이라고 못 박아
  두었다. 더하는 것이지 갈아 치우는 것이 아니다.

**문자열은 확정됐다**([[ADR-147]] 정정 10, 사용자 선택 2026-08-17):

| 단계 | 기존(유지) | 채택(추가) |
|---|---|---|
| 0주 | 와따리! ㅇㄱㄱㄷ | **완전 럭키비키잖아** · **폼 미쳤다** |
| 1주 | 그래, 그럴 수 있지 | **다음 주엔 되겠지** |
| 2주 | 어?! 슬슬 쫌 그래!? | **슬슬 킹받는데** · **이게 맞나?** |
| 3주 | 선넘네?! | **이게 억까지 뭐야** |
| 4주+ | 다섯 줄 그대로 | — (채택 없음) |

**1주·3주는 풀이 둘뿐이라 «무작위» 가 얕다** — 두 문구가 번갈아 나오는 것처럼 보인다(열린 질문).

**세 크기**(구현 확정):

| 크기 | 형태 |
|---|---|
| **4x1** | 잎 26 + 헤드라인 + `마지막 · 7월 3주차 · 생명의 연마석 외 1개` + `3주째` 칩 |
| 2x2 | 잎 54(크게) + 헤드라인 + `3주째 아이템 드롭 없음` — **마지막 기간 줄을 버린다** |
| 2x1 | 잎 22 + 헤드라인 + `3주째` 칩 |

- **잎은 단계를 따라 늙는다** — 색·기울기·투명도·글로우를 `tier` 하나가 함께 고른다(값 하나가 두 축을
  같이 움직여야 "색은 슬픈데 문구는 신난" 어긋남이 안 생긴다). 그 표(`lib/drought-tier-styles.ts`)는
  **드롭 히스토리 화면과 한 벌**이다(구현 확정) — 5행짜리 값 표를 양쪽이 각자 들면 한쪽만 고쳐져
  같은 단계가 두 화면에서 다른 색으로 늙는다([[ADR-094]] 결정 1의 «호출부 2곳» 조건). 공유하는 것은
  **값뿐**이고 SVG 크기·testID·접근성 이름은 각 화면이 자기 사정대로 그린다.
- **0단계만 배경이 바뀐다**(`primary-tint`, 구현 확정) — 격자에서 유일하게 축하하는 타일이라 그 한
  자리에만 강조색을 쓴다. 나머지 단계는 배경을 아예 칠하지 않고, 슬픔은 잎이 진다.
- **0주는 「0주째」가 아니라 「이번 주」다**(구현 확정) — 셈은 맞지만 뜻이 없다(그 주에 먹었다는 것이
  0주의 정의다). 같은 이유로 4x1 의 아래 줄에서 **「마지막」이 빠지고**(진행 중인 주를 «마지막» 이라
  부르면 어색하다 — 히스토리 화면과 같은 규칙), 2x2 의 상태 줄은 «없음» 이 아니라 「이번 주에
  획득했습니다」가 된다.
- **요약이 `null` 이면 「아직 아이템 드롭 기록이 없습니다」** — 「0주째」로 위장하지 않는다. 0주는
  «이번 주에 먹었다» 는 **정반대**의 사실이고, 안 먹은 것과 안 적은 것은 다르다.
- **「물욕」이라는 말을 쓰지 않는다**([[ADR-147]] 정정 14) — 화면에 보이는 한국어는 「아이템 드롭」이고,
  영문 식별자(`valuable-drought` · `summarizeValuableDrought`)는 그대로 둔다. **렌더 결과에 그 문자열이
  없다는 것**을 두 위젯의 테스트가 검사한다.

### 9. 공유 컨텐츠 — **계열**로 묶고, 축을 주장하지 않는다 ([[ADR-147]] 정정 28~31)

몬스터파크·에픽 던전처럼 진행이 공유되는 일곱 항목을 위젯 2 에서 빼 이쪽으로 모은다. 캐릭터 넷이면
**하루 한 번 할 일이 넷으로 세어지던** 것이 이 분리의 이유다.

```
계정 및 메이플 ID 공유 컨텐츠            4개
─────────────────────────────────
에픽던전
  하이마운틴                      CLEAR
  앵글러컴퍼니                    CLEAR
  악몽선경
몬스터파크
  일간                             7/14
  익스트림 몬스터파커                1/2
메이플 유니온
  주간 드래곤 퇴치                CLEAR
  PC방 주간 드래곤 퇴치
```

**월드/계정이 아니라 계열이 축이다**(사용자 지정). Open API 는 월드 공유 항목을 **마지막 접속 월드
기준**으로 돌려주므로 월드로는 못 가른다([[ADR-030]] 결정 6, 사용자 확정 2026-07-21). 계열로 묶으면
**월드 라벨을 한 번도 안 쓰므로 틀린 말을 할 자리가 없다** — 한계가 사라진 것이 아니라 화면이 그
축을 주장하지 않게 된 것이다.

| 규칙 | 값 |
|---|---|
| 대상 판정 | `getShareScope(name) !== 'character'` — 분류를 새로 만들지 않는다 |
| 계열·짧은 이름 | `scheduler-content-catalog.json` 의 `group`·`shortName`(사람이 적는다, 정정 31) |
| 순서 | 계열은 `sharedGroupOrder`(손으로 적는다) · 계열 «안» 은 `worldShared` → `accountShared` 를 이어 읽은 순서 |
| 오른쪽 열 | **완료 → `CLEAR` · 미완료 + 카운트 → `n/max` · 미완료 + 카운트 없음 → 빈칸**(정정 33) |
| 완료 판정 | `weeklyContentCompletion`·`dailyContentCompletion`(위젯 2 와 같은 함수) |
| 머리의 수 | 완료가 아닌 **줄**의 수 |
| 머리의 `?` | 월드 한계 한 문장을 팝오버로(정정 34) |

- **미완료는 오른쪽을 비운다**(사용자 지정). 퀘스트형에 `0/1` 을 붙이려면 API 에 없는 분모를 앱이
  지어내야 한다.
- **완료는 언제나 `CLEAR` 다**(정정 33, 사용자 지시). 카운트형도 `14/14` 대신 `CLEAR` 다 —
  완료한 항목의 «몇 번 했나» 는 언제나 `max` 라 `CLEAR` 가 이미 그 말을 한다. 「익스트림만 예외」로
  적으면 정정 31 이 카탈로그로 밀어낸 «이름으로 유추하는 규칙» 이 코드로 되돌아온다.
- **몬스터파크 14 는 이미 데이터에 있었다** — 템플릿의 `max_count: 14`. 카탈로그 `note` 가
  *«월드당 14회(캐릭터당 최대 7회)… API 는 월드 총합을 now_count 로 반환»*(사용자 확인 2026-07-21)을
  적어 둔 그 값이다. 오버라이드 없이 `7/14` 가 나온다.
- **익스트림 몬스터파커만 `maxCountOverride: 2`**(사용자 확정 2026-08-18, 템플릿 값 5 와의 충돌을
  짚은 뒤). 컨텐츠 화면 카드는 이 항목을 `quest_state` 로 그리므로 그쪽에는 무해하다.

**유니온만 조건부다**(사용자 지정, 정정 30). 추적 중인 캐릭터 중 **아무의 스케줄러에도 유니온 항목이
없으면** 그 줄을 안 그린다 — 나머지 다섯은 등록 여부와 무관하게 항상 그린다. 판정은 뷰모델이 이미
부르는 `displayedWeeklyContents(...)` 의 결과이고, **카탈로그에서 거르면 안 된다**(거기서 빼면 컨텐츠
화면에서도 사라지고 나중에 유니온을 열어도 안 돌아온다). **계열이 아니라 항목 단위**라 둘 중 하나만
있으면 그 한 줄만 남는다.

**결정 5(«위젯은 사라지지 않는다»)의 예외가 아니다** — 사라지는 것은 줄이지 타일이 아니다. 일곱이 다
없어도 타일은 서고 다섯 줄이 빈칸으로 남는다.

**머리의 `?` 가 월드 한계를 말한다**(정정 34, 사용자 지시). 누르면 한 문장이 뜬다 —
*«계정 및 메이플 ID 공유 컨텐츠는 가장 마지막에 접속한 월드 기준으로 표시됩니다.»*
[[ADR-030]] 결정 6 이 «받아들이는 한계» 로 적어 둔 것을 **화면이 처음으로 사용자에게 말하는**
자리다(계열로 묶어 «안 그린 것» 과 «말한 것» 은 다르다). 말풍선은 **카드 안에 절대 배치**해
목록 위에 겹친다 — 인라인으로 펼치면 `h: 'auto'` 가 다시 재서 아래 타일이 전부 밀린다(정정 27).
공용 컴포넌트로 올리지 않는다(단일 사용).

## 빈 상태와 실패 ([[ADR-147]] 결정 5)

- **위젯은 사라지지 않는다.** 좌표 배치라 자리를 빼면 아래 타일이 올라오지 않고 **빈 사각형**이
  남는다 — 그 구멍은 «어제 있던 것이 오늘 없다» 로 읽힌다. 빈 상태는 **자기 타일 안에서** 말한다.
- **«없다» 와 «모른다» 를 가른다**([../foundation/error-resilience.md](../foundation/error-resilience.md)
  원칙 1). 동기화가 실패해 모르는 것을 «0 메소» 로 그리지 않는다. 이 화면은 숫자를 크게 그리므로
  그 구분이 특히 중요하다 — 큰 `0` 은 사실을 단정하는 그림이다.
  - **예외 하나 — 주간 보스 수익**([[ADR-147]] 정정 4, 사용자 지시). 기록이 없어도 `0 메소` 를
    그리고, 구분은 옆의 한 줄이 진다. 다른 위젯에는 번지지 않는다.
- 캐릭터 단위 실패 표식(`characterIssues`, [[ADR-068]] 결정 3)은 위젯 2·3 이 그대로 물려받는다.
- ~~예외는 대표 캐릭터 미지정 하나 — 그 타일만 CTA 로 내용을 바꾼다~~ → **그 상태가 존재하지 않는다**
  ([[ADR-147]] 정정 2 — 미지정이면 임시 대표가 선다).

**남은 것**:

- **`drop-history` 가 가격을 안 나른다**(위 «4·7·8» 의 경고 상자) — 위젯 4·7 이 실기기에서 값을
  못 받는다. `toHistoryRecord` 한 함수의 문제지만 드롭 히스토리 화면도 같은 투영을 쓰므로 고치는
  범위를 따로 정해야 한다.
- **1주·3주 문구 풀이 둘뿐**(위젯 8) — 무작위라기엔 얕다. 채울지 그대로 둘지.
- **2x1 결정석 타일이 첫 월드만 말한다**(위젯 5) — 기본 크기가 2x1 이라 월드가 여럿인 사용자는
  나머지를 못 본다. 지금의 답은 «4x1·2x2 로 키운다» 인데 v1 배치는 코드 상수라 사용자가 못 키운다.
  좁은 자리에 «외 N» 을 붙일지, 배치 편집이 올 때까지 둘지.
- **2x2 대표 카드의 직업 잘림**(위젯 1) — 「아크메이지(불,독)」이 158폭의 한계다.
- **전투력 도입 여부와 호출 예산** — 대표 한 명만 부르면 실행당 1회로 묶이지만, 위젯이 «캐릭터별»
  로 확장되면 추적 캐릭터 수만큼 는다.
- **타일 탭의 목적지** — 위 표는 제안값이다. 특히 결정석 한도·아이템 드롭 가뭄이 `Profit` 인지
  `/profit/drops`(전 기간 히스토리)인지는 실기기에서 눌러 보고 정한다.
- **온보딩 직후 착지** — [[ADR-132]] 열린 질문이 그대로다. 위젯 아홉이 **전부 빈 상태**인 첫 실행에서
  이 화면이 «시작하기» 를 겸할지, 그때만 다른 곳에 착지시킬지.
- **간격 12 · 행 높이 76** — 제안값. 실기기에서 확정한다. 바꾸면 위 「계산된 타일 치수」 표와
  총 높이 852 가 함께 움직인다.
- **「남은 스케줄」 auto 높이의 1px 불일치** — 시안 실측(145 / 236 / 326)과 그것을 요약한 식
  (`55 + 45n` → 145 / 235 / 325)이 4·6명에서 어긋난다. 실기기에서 재면 닫힌다.
- **`drop-history` 예열 여부** — 그 스토어는 전 기간 드롭을 SQLite 에서 통째로 읽는다([[ADR-071]]).
  today 가 첫 화면이라 그 비용이 콜드 스타트에 실린다. [[ADR-101]] 예열 목록에 더할지는 **실측 뒤에**
  정한다(지금 정하면 근거 없는 값이 된다).

- **다계정일 때 공유 컨텐츠 한 줄이 어느 계정 것인가**(위젯 9) — 에픽 던전 진행은
  `accountSharedProgress:{accountId}` 로 계정마다 따로인데([[ADR-143]] 결정 6) 위젯은 항목당 한 줄이다.
  계정이 하나면 지금도 맞고, 이 구멍은 다계정 사용자에게만 드러난다.
- **익스트림 몬스터파커의 `now_count` 가 진짜인가**(위젯 9) — `type: "quest"` 라 앱이 이 항목의
  카운트를 읽은 적이 없다. 늘 0이면 완료 전까지 `0/2` 로 보인다(완료 후에는 승격 규칙이 `2/2` 로
  만든다). 실기기에서 한 번 끝내 보면 닫힌다.
- **공유 컨텐츠 타일의 목적지** — 지금은 `target` 이 없다(위젯 2 와 같다).
