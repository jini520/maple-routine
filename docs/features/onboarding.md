## 단계 셋 ([[ADR-143]]·[[ADR-144]])

```
API 키 → 스케줄 관리 방법 → 캐릭터 선택
```

**메이플 ID 를 고르는 단계가 없다**([[ADR-143]] 결정 1). 캐릭터 선택 화면이 계정 드롭다운을 갖고,
**여러 계정의 캐릭터를 한 목록으로** 고른다([[ADR-144]]). 그래서 웹뷰 시절의 ‘계정 선택’·‘예열’·
‘계정 선택 프로브’ 세 단계가 통째로 사라졌고, 그 자리는 각각 이렇게 대체됐다:

| 웹뷰 시절의 자리 | 지금 |
|---|---|
| 계정 선택 단계(`AccountSelectionList`) | **없다**. 캐릭터 선택 화면의 드롭다운(`AccountSelect`) |
| 예열(🗑 ADR-016, 계정 전체 캐릭터 선행 조회) | **드롭다운으로 그 계정을 열 때** 그 계정 몫만 판정([[ADR-143]] 결정 5) |
| 계정 선택 프로브(`use-account-probes`) | 같은 이유로 없다. 판정은 로스터 조회가 한다 |
| 재개 표의 `selectedAccountId` 행 | **빠진다**(아래 ‘단계 재개’) |

`OnboardingScreen` 에는 `selectingAccount`·`prefetching` 두 case 가 **타입상으로만 남는다**(리듀서를
안 고쳤다. [[ADR-143]] 결정 8). 그 자리에는 빈 화면이 아니라 **키 입력 폼**이 선다: 저장소가 흔들려
`submitApiKey` 의 방어 분기가 그리로 떨어질 수 있고, 출구 없는 흰 화면은 [[ADR-116]] 이 없앤 잠금과
같은 얼굴이기 때문이다.

> **정리할 잔재 둘**(캐패시터가 사라진 지금 남은 것. [[ADR-143]] 결정 8·9 가 ‘캐패시터가 걷히면’
> 을 조건으로 걸어 둔 것들, [[ADR-155]] 로 그 조건이 충족됐다):
> - **`accountScope` 플래그**(`features/onboarding/flow.ts`). 기본값 `'single'` 에 `boot.ts` 가
>   `'all'` 을 주입하는 구조다. 이제 `'all'` 하나만 남기면 된다.
> - **`use-account-probes.ts`**. 제품 코드에 **소비자가 없다**(참조는 주석 한 줄뿐).

## 정책
- **키 입력**: 발급 절차는 **앱 밖 안내 사이트**(`mapleroutine.store/api-key`)가 담당하고 앱은 링크만 준다([[ADR-110]], 앱 내 단계별 위저드 아님: 스크린샷 7장이 번들에 들어가면 최초 1회 보는 화면 때문에 모든 사용자가 1.2MB를 받고, 넥슨이 화면을 바꿀 때마다 OTA 배포가 필요하다). 키는 `storage/` 보안 영역에 저장.
  - **`ApiKeyForm` 의 링크는 둘이다**(2026-08-08, 이슈 #61: 사용자 확정): 1차 경로가 **`API 키 발급 방법`(가이드)**, 다른 하나가 **`openapi.nexon.com` 바로 가기**(화면에서의 자리는 아래 ‘API 키 입력 화면: 갈림길 레이아웃’). 처음 쓰는 사용자를 넥슨 첫 화면에 떨궈 놓지 않는 것이 1차 경로를 가이드로 두는 이유고, 이미 발급받은 사용자에게 7단계 안내를 거쳐 가게 하지 않는 것이 바로 가기를 남기는 이유다. 가이드 1단계가 `openapi.nexon.com` 링크를 이미 품고 있어 **중복이 아니라 서로 다른 두 진입점**이다.
  - **외부 브라우저로 이탈해도 잃는 게 없다**. 두 링크 모두 시스템 브라우저로 나가지만(설정의 개인정보 처리방침 링크와 같은 패턴), 재개 지점이 저장된 값에서 파생되므로([[ADR-086]] 결정 1, 아래 "단계 재개") 키를 넣기 전에 나갔다 돌아오면 그대로 `awaitingApiKey` 다. 입력 중이던 값은 컴포넌트 로컬 상태라 앱이 메모리에서 내려가면 사라지지만, 이 시점에 사용자가 들고 있는 키는 아직 없다.
  - **설정 화면에는 진입점을 두지 않는다**(2026-08-08 사용자 확정). 설정에 API 키 재입력 경로 자체가 없어(계정 변경·연결 해제뿐) 가이드 링크만 놓으면 갈 곳 없는 안내가 된다. 키 교체 경로는 별도 과제로 분리한다.
- **계정 선택** (⛔ **지금은 이 단계가 없다**. [[ADR-143]] 결정 1. 아래는 ‘캐릭터가 0명인 메이플 ID’ 규칙의 출처로 남긴 기록이다): 키 제출 즉시 `character/list` 호출(별도 검증 엔드포인트 없이 이 호출 자체가 키 검증). **캐릭터가 0명인 메이플 ID 는 `normalizeCharacterList` 가 걸러내 목록에 오지 않는다**([[ADR-127]], 2026-08-12). `MapleAccount` 의 뜻이 *"응답에 있던 계정"* 이 아니라 **"고를 수 있는 계정"** 이고, 소비하는 네 자리가 전부 캐릭터가 있다는 전제로 쓴다. **계정 수와 무관하게 항상 "어느 메이플 ID를 쓸지" 선택 화면을 보여준다**(ADR-051). 계정이 1개여도 건너뛰지 않으며, 사용자가 "계속하기"로 확정해야 예열이 시작된다. 선택은 이후 설정에서 변경 가능. `storage/` 에는 `apiKey` 와 선택 `accountId` 만 저장(캐릭터 목록은 캐싱 안 함).
- **예열(🗑 ADR-016)** (⛔ **지금은 없다**. [[ADR-143]] 결정 5 의 ‘계정을 열 때의 자격 판정’이 대신한다. 아래는 기록): 계정 확정 즉시 온보딩을 끝내지 않고, 그 계정 **전체 캐릭터**(추적 대상 무관) 데이터를 진행률 바와 함께 미리 받는다. 이후 스케줄러·피커 첫 진입 시 로딩 없이 뜨게 하기 위함. `OnboardingStatus` 에 `'prefetching'` 추가, 각 캐릭터에 `character/basic` → `scheduler/character-state` 순서의 독립 파이프라인을 병렬 실행하고 하나 끝날 때마다 즉시 캐시 기록 + 진행률 갱신. 개별 실패는 그 캐릭터만 캐시 없이 넘어가고 전체를 막지 않는다. 전체 완료 시 `'completed'`. 캐릭터 많은 계정은 수 초 걸릴 수 있음(사용자 수용).
  - **예열은 "이번 실행의 동기화"로 친다**([[ADR-097]] 결정 3). 화면 진입 재조회 게이트는 앱 재시작 후 첫 동기화를 TTL 무시로 강제하는데, 예열이 그 표시를 남기지 않으면 온보딩 직후 첫 화면 진입이 **방금 받은 것을 그대로 다시 받는다**.
  - **`access_flag` 게이트를 걷어냈다**([[ADR-086]] 결정 3, 2026-08-03). 전에는 `access_flag: true` 인 캐릭터만 scheduler 를 예열했다. [[ADR-067]] 계측이 "false 여도 세 엔드포인트 모두 200"을 확인했으므로 그 게이트는 **받을 수 있는 데이터를 안 받는 것**이었다. 대신 예열이 후보 자격 판정(`resolveCharacterEligibility`)을 함께 수행한다. `access_flag: false` 이고 오늘 응답도 비었으면 과거 날짜를 거슬러 올라가며 활동 기록을 찾는다([content-scheduler.md](./content-scheduler.md) "후보 자격"). 휴면 캐릭터 1명당 최대 13회가 더 들지만 **캐릭터당 평생 한 번**이다(조회 원장이 재조회를 막는다).

## 단계 재개: 끝내지 않은 온보딩은 그 지점부터 ([[ADR-086]] 결정 1·2, 2026-08-03)
온보딩은 `API 키 → 계정 선택 → 예열 → 스케줄 관리 방법 → 관리 캐릭터 선택` 다섯 단계다. 어느 단계에서 앱을 종료하든 **다음 실행에서 그 단계부터 이어간다**. 전에는 `restoreFromStorage` 가 `selectedAccountId` 하나만 보고 곧바로 `completed` 로 전이해, 모드·캐릭터를 고르지 않은 채 빈 메인으로 떨어졌다.

재개 지점은 **저장된 값에서 파생한다. 진행 상태 전용 키를 두지 않는다.** 각 단계의 산출물이 이미 영속화돼 있어서, 진행 상태를 따로 쓰면 진실이 둘이 되고 한쪽만 써진 채 앱이 죽는 순간 어긋난다(고치려는 결함과 같은 종류의 결함이다).

**이 표는 두 경로에 함께 적용된다. 부팅(`restoreFromStorage`)과 키 재입력(`submitApiKey` 성공)** ([[ADR-115]] 결정 4, 2026-08-08). 파생 판정은 **함수 하나**이고 두 경로가 그것을 공유한다. 두 벌이 되면 재개 규칙의 진실이 둘이 되는데, 그것이 [[ADR-086]] 결정 1 이 진행 상태 전용 키를 거부한 바로 그 이유다.

| 저장 상태 | 재개 단계 |
|---|---|
| `apiKey` 없음 | `awaitingApiKey` |
| `selectedAccountId` 없음 | `selectingAccount`(저장된 키로 `character/list` 재조회). **RN 에는 이 행이 없다**([[ADR-143]] 결정 8) |
| `trackingMode` 미선택 | `selectingTrackingMode` |
| `trackedCharacters` 가 `null` 또는 `[]` | `selectingContentCharacters` |
| 그 외 | `completed` |

- **뒤 두 단계는 네트워크 없이 재개된다**. 모드 선택은 순수 UI, 캐릭터 선택은 `getCharacterPickerRoster` 가 자체 조회한다. **예열(ADR-016)을 다시 돌리지 않는다**(원장·캐시가 이미 부분적으로 따뜻하고, 조회 원장이 중복 호출을 막는다. [content-scheduler.md](./content-scheduler.md) "조회 원장").
- **`trackedCharacters === []` 는 완료가 아니다**. 최소 1명 규칙이 있으므로 빈 배열은 미완료와 동치다. 저장 레이어의 `null` vs `[]` 구분([[ADR-012]])은 그대로 두고, 온보딩 게이트에서만 둘을 같게 읽는다.
- **`trackingMode` 미선택을 `'auto'` 로 읽지 않는다.** `getTrackingMode()` 가 `TrackingMode | null` 을 반환하고 소비처가 `?? 'auto'` 로 흡수한다. **동작 기본값은 그대로 자동**([[ADR-035]] 결정 2)이고, 바뀌는 것은 "골랐는가"를 구분할 수 있게 된 것뿐이다. 고르지 않은 값을 화면이 "선택됨"으로 표시하는 것만 없앤다.
- **마이그레이션**: `trackingMode` 키가 없는데 `selectedAccountId` 와 비어 있지 않은 `trackedCharacters` 가 이미 있으면([[ADR-035]] 이전 설치본 완주자) `'auto'` 를 1회 기록한다. 안 하면 정상 사용자가 온보딩으로 되돌려진다.

### 키 재입력 경로: 키만 다시 받고 뒤 단계는 건너뛴다 ([[ADR-115]] 결정 4·5, 2026-08-08, 이슈 #157)
API 키가 무효화(401/403)되면 저장된 **`apiKey` 키 하나만** 지워지고 사용자는 이 화면으로 온다. 그래서 여기서 키를 다시 넣으면 `selectingAccount` 로 가지 않고 **위 표가 가리키는 단계(대개 `completed`)로 곧바로** 간다. 계정 선택·트래킹 모드·추적 캐릭터를 **다시 묻지 않는다**. 무효화된 것은 키 하나뿐이라 나머지 저장값은 여전히 사실이다.
- 전에는 `submitApiKey` 성공이 무조건 `selectingAccount` 로 가고 `selectedAccountId` 를 리셋해, 키 하나 때문에 계정 선택부터 캐릭터 선택까지 전부를 다시 시켰다(재개 파생이 부팅 경로에만 있었다).
- **예열(ADR-016)을 다시 돌리지 않는다**. 위 "뒤 두 단계는 네트워크 없이 재개된다"와 같은 근거다(캐시·조회 원장이 이미 따뜻하다).
- **계정 목록 대조 가드**([[ADR-115]] 결정 5): 새로 넣은 키가 **다른 넥슨 계정의 키**일 수 있다. 키 검증 때 이미 받는 `character/list` 응답에 저장된 `selectedAccountId` 가 들어 있는지 확인해, **없으면 재개하지 않고 기존대로 계정 선택부터** 간다. 가드가 없으면 남의 계정 키로 이전 계정 ocid 추적 목록을 그대로 쓰게 된다. **추가 호출은 없다**(이미 손에 있는 응답으로 판정한다).
  - **RN 은 같은 목적을 `trackedCharacters` 로 세운다**([[ADR-143]] 결정 9). 대조할 `selectedAccountId` 가 없으므로, 저장된 추적 ocid 가 새 응답에 **하나라도** 있으면 재개하고 **하나도 없으면** 캐릭터 선택 단계로 보낸다(`selectingAccount` 로 가던 자리). 일부만 없는 경우(캐릭터 삭제·이전)는 재개한다. 없는 ocid 는 피커와 동기화가 각자 이미 다룬다.
    - **가드는 ‘지킬 목록이 있을 때만’ 선다**. 저장된 목록이 `null`/`[]` 면 대조하지 않고 위 표 그대로 간다. 안 그러면 **처음 키를 넣는 신규 사용자**가 "목록이 비었으니 하나도 없다"로 걸려 스케줄 관리 방법 단계를 건너뛴다. 이 가드가 막는 것은 ‘남의 계정 키로 이전 목록을 그대로 쓰는 것’이라, 지킬 목록이 없으면 판정 대상 자체가 없다.
    - 대조는 응답의 **전 계정 캐릭터 ocid 집합**으로 한다(계정을 넘어 고르는 것이 본론이라 계정별로 나눠 볼 이유가 없다). **추가 네트워크 호출은 없고**, 추적 목록만 로컬에서 한 번 더 읽는다.
- **이 화면으로 보내는 알림은 이제 원인이 둘이다**. 키 무효화(400 `OPENAPI00005`·401/403)와 **호출 한도 초과(429)**([[ADR-116]] 결정 1, 2026-08-08). 둘은 **같은 사슬에 문구만 다르고**, 확인을 누르면 똑같이 `apiKey` 만 지워진 채 이 화면으로 온다. 그래서 재개 규칙(위 표)도 그대로 적용된다.
- **무효화·한도 초과 자체**(감지 지점·모달 문구·확인 후 이동·저장소에서 지우는 범위)는 여기가 아니라 [../foundation/error-resilience.md](../foundation/error-resilience.md) 의 401/403·429 항목이 원문을 갖는다. 이 절은 **키를 다시 받은 뒤**만 다룬다.

## UI

### API 키 입력 화면: 갈림길 레이아웃 (`ApiKeyForm`, 2026-08-08, 이슈 #61)
**이 화면에 오는 사람은 둘뿐이다. 키가 있는 사람과 없는 사람.** [[ADR-110]] 이 두 링크를 "중복이 아니라 서로 다른 두 진입점"이라고 적은 것을 **화면 구조로 옮긴다**. 전에는 둘 다 폼 **위** 한 문단 안에 인라인 밑줄 링크로 붙어 있어서, 1차 경로라고 선언한 가이드가 화면에서 가장 작고 흐린 요소(`text-sm text-text-muted` 문장 *안*)였다. 선언과 그림이 어긋나 있었다.

```
제목 블록(space-y-1)   h2 text-lg font-semibold text-text  "넥슨 API 키를 입력해주세요"
                       p  text-sm text-text-muted          "스케줄러 API를 사용하려면 개인 API 키가 필요해요"
                       p  text-xs text-text-muted          "입력한 키는 이 기기에만 저장되고 넥슨 외 어디로도 전송되지 않아요"
입력 블록(space-y-1)   label text-sm font-medium + input + 표시 토글
                       a text-xs  "openapi.nexon.com에서 확인" + ExternalLink h-3     ← 키가 있는 사람의 동선
확인 버튼              Button primary, w-full
구분선                 "아직 API 키가 없나요?"  (좌우 h-px bg-border, 가운데 text-xs text-text-muted)
가이드 블록(space-y-1) a.BUTTON_VARIANT_CLASS.outline  "API 키 발급 방법 보기" + ExternalLink h-3.5
                       p text-xs text-text-muted 중앙  "넥슨 오픈 API에서 키를 받는 7단계 안내"
```
- **제목을 되찾는다**. 온보딩 다섯 단계 중 이 화면에만 제목이 없었다(`TrackingModeStep`·`ContentCharacterStep` 은 모두 제목+보조문으로 시작한다). 같은 블록을 그대로 쓴다.
- **폼이 먼저다.** 넥슨 바로 가기가 인풋 바로 아래 붙어 "키를 이미 가진 사람"의 동선이 한 덩어리가 된다. 가이드는 확인 버튼 **아래** 구분선 뒤로 내려가되, 거기서 처음으로 **누를 수 있는 크기**(pill 버튼)가 된다.
- **가이드는 `<button>` 이 아니라 `<a>` 다**. 외부 URL로 나가는 이동이라 링크 시맨틱을 유지하고(스크린리더가 "링크"로 읽고 `target="_blank"`·`rel` 규칙이 그대로 적용된다), 겉모습만 `BUTTON_VARIANT_CLASS.outline` 을 입는다([design-system.md](../foundation/design-system.md) ‘기본 컴포넌트’).
- **7단계라는 사실을 나가기 전에 알린다**. 버튼 아래 한 줄. 무엇이 기다리는지 모른 채 앱을 떠나지 않게 한다.
- **주 CTA 바로 아래 같은 pill 이 하나 더 서는 위험**은 구분선과 그 문구가 막는다. 두 버튼은 색(채움 vs 테두리)·크기(16px vs `text-sm`)로도 갈린다.

**키 표시 토글**. 인풋 우측 `Eye`/`EyeOff`(lucide, 배경 없이 단독, `pr-11`). 기본은 가림(`type="password"`)이고 누르면 `text` 로 바뀐다. 키는 손으로 치는 값이 아니라 **붙여넣는 긴 문자열**이라 가려 두면 잘못 붙여넣었는지 확인할 방법이 없고, 실패해도 401 토스트만 뜬 채 원인을 못 본다. `text` 구간이 생기므로 `autoCapitalize="none" autoCorrect="off" spellCheck={false}` 를 함께 건다. 모바일 키보드가 첫 글자를 대문자로 바꾸면 **조용히 틀린 키**가 된다.

**안심 문구의 표현 (2026-08-08 사용자 요청 → 사실에 맞게 조정)**: 요청은 "수집하거나 저장하지 않는다"였으나 **"저장하지 않는다"는 사실이 아니다**. 키는 기기 Preferences(UserDefaults/SharedPreferences)에 저장된다(`storage/api-key`, [[ADR-007]]). 그래야 재실행 때 다시 넣지 않는다(위 "단계 재개"). 사실인 것은 **우리가 수집하지 않는다**이다: 백엔드가 없고([[ADR-003]]) 키는 `x-nxopen-api-key` 헤더로 넥슨에만 나간다(`nexon/http`). 그래서 문구는 **"이 기기에만 저장되고 넥슨 외 어디로도 전송되지 않아요"** 다. 지키지 못할 약속을 하지 않으면서 뜻(안심)은 그대로 전한다.

### API 키 검증 중: 폼 유지 + 버튼 스피너 (2026-07-16)
키 제출 시 화면을 이동시키지 않고 `ApiKeyForm` 을 그대로 유지한다(정상 경로 1초 미만이라 "확인 중" 문구가 깜빡이는 게 거슬림 → 문구 제거). `verifyingApiKey` 동안 `isSubmitting` 으로 유지, 입력값·위치 그대로, 제출 버튼 내용만 "확인"→스피너로 바꾸고 비활성화. 예열(prefetching)처럼 수 초 이상 걸리는 작업은 제외(진행률 바 표시).
```
버튼 스피너: h-5 w-5 rounded-full border-2 border-bg/30 border-t-bg animate-spin motion-reduce:animate-none
접근성: aria-busy, aria-label="확인 중", 스피너 aria-hidden
```

### 계정(메이플 ID) 선택 목록: ⛔ **없어진 화면의 기록** ([[ADR-143]] 결정 1)

> **이 화면은 지금 없다.** 계정을 고르는 자리는 캐릭터 선택 화면의 드롭다운(`AccountSelect`)이고, 거기서는 **대표 캐릭터 얼굴·이름을 쓰지 않는다**. 판정이 ‘계정을 열 때’로 미뤄져 열기 전에는 확인된 캐릭터가 없기 때문이다([[ADR-144]] 결정 2). 아래는 그 드롭다운이 무엇을 대체했는지 읽기 위한 기록이다.

각 계정 = [대표 캐릭터 얼굴 아바타 36px 원형] + 텍스트 2줄. 1줄 `[월드 엠블럼] {월드} · {이름} · Lv.{레벨}`, 2줄 `text-text-muted` `캐릭터 {N}개`. **직업 미표시**(이름이 길면 넘겨서 대신 월드를 첫 줄로). 월드 엠블럼 `src/assets/worlds/*`, `h-[18px] w-auto object-contain shrink-0`, 미매핑 월드는 텍스트만. 1줄 `truncate`, 텍스트 컬럼 `min-w-0`. 월드→엠블럼 매핑은 `world-emblems.json`(챌린저스1~4 모두 `challengers`). 컴포넌트는 온보딩 페이지형 레이아웃에 맞춰 자체 카드 없이 `w-full space-y-4`. 설정 계정 변경 모달이 이걸 카드로 감싸 재사용(모달 `card={false}`).
**계정이 1개면 그 항목을 초기 하이라이트로 지정한다**(ADR-051). 고를 것이 하나뿐이므로 항목 선택 탭은 생략하고 "계속하기" 확정 행위만 남긴다.

### 예열 진행률 바: ADR-016
진행률 바 프리미티브([../foundation/design-system.md](../foundation/design-system.md)) 재사용 + "캐릭터 정보를 준비하고 있어요 (18/45)" `text-sm text-text-muted`. **세로 중앙 배치**(2026-07-16): 예열은 온보딩 유일의 수 초 대기 화면이라 상단 붙임보다 중앙이 대기 화면다움. 컨테이너 `min-h-[calc(100dvh-var(--sa-top)-var(--sa-bottom))]` + `flex items-center justify-center`(온보딩엔 하단 탭바 없어 `--sa-bottom` 까지 빼야 정중앙). 설정의 재인증 예열(`AccountFlowStatus`, 모달 안)은 대상 아님.

시드 단계(`seedingTracking`)는 진행률 숫자가 없어 스피너만 쓴다. `MapleSweepSpinner size={32} text-primary` + "체크리스트를 준비하고 있어요". 화면 전체 대기라 셸 승계 카드는 씌우지 않는다([[ADR-061]] 결정 2).

### 스케줄 관리 방법(자동/수동) 선택 단계: `TrackingModeStep` ([[ADR-035]] 결정 13·22)
제목 "스케줄러를 어떻게 관리할까요?" + 보조문 "나중에 설정에서 언제든 바꿀 수 있어요." + 옵션 2개 + "계속하기". **기본 선택은 없고**(결정 17) 고르기 전까지 CTA가 비활성이다.

옵션 카드 안쪽 구조는 [settings.md](./settings.md) "스케줄 관리 방법 행/모달"에 한 번만 적는다. 설정 모달(`TrackingModeSelector`)과 **같은 카피(`features/tracking-mode/copy.ts`)·같은 카드 내부 구조**를 쓰기 때문이다(결정 22). 이 화면에만 해당하는 것:
- 바깥 카드 클래스는 `AccountSelectionList`·`ThemeSelector`와 공유하는 것을 그대로 쓴다(결정 22가 폐기한 것은 "신규 스타일 금지"이지 이 공유가 아니다). 바뀐 것은 카드 **안쪽**뿐이다.
- 온보딩 다른 단계와 달리 네트워크가 필요 없어 재개도 순수 UI다(위 "단계 재개" 표).

### 추적 캐릭터 선택 단계: 후보 목록 로딩 ([[ADR-053]], 구현 완료 2026-07-29)

> **RN 에서는 이 단계가 두 층이 된다**([[ADR-144]] 결정 2 · 구현 완료 2026-08-17). **위**는 계정을 넘는 ‘선택된 캐릭터’ 리스트(순서·대표가 여기 산다), **아래**는 계정 드롭다운 + 그 계정의 후보 목록이고, **두 층은 같은 행 카드**를 쓴다(갈리는 것은 좌우 슬롯뿐: 위는 끌기 핸들과 `★ ✕`, 아래는 `＋`). 아래 로딩·실패 정책은 **그 아래 층 자리에 그대로** 적용되고(계정을 바꾸면 아래만 다시 돈다. 위는 로컬 캐시로 그려 네트워크와 무관하다), 달라지는 것 셋: **후보 0건의 ‘계정 다시 선택’ 액션이 없어진다**(드롭다운을 되돌리는 것이 그 자리의 출구다. [[ADR-143]] 결정 10) · **고를 수 있는 계정이 하나도 없으면** 화면 전체가 빈 상태 + 키 재입력이다 · 같은 계정을 5분 안에 다시 열면 **조회 자체를 하지 않는다**([[ADR-144]] 결정 6 의 계정 전환 TTL).
>
> **‘계속하기’는 하단에 고정된다**([[ADR-144]] 정정 2, 2026-08-18 사용자 지정). 설정 하위 페이지의 ‘저장’과 **같은 액션 바**다(`bg-bg` + 위쪽 테두리 · 폭을 다 쓰는 버튼 · 안전영역은 바가 먹고, 잰 바 높이만큼 콘텐츠 아래를 비운다). 처음에는 이 단계만 ‘본문 끝에 서는 CTA’로 뒀는데, 본문이 설정과 같은 두 층이라 캐릭터가 많으면 유일한 전진 버튼이 화면 밖에 있게 된다. 그 바를 갖는 것은 화면이 아니라 **단계 셸**(`OnboardingStep`)이고, 그래서 `ContentCharacterStep` 이 그 셸을 직접 두르는 유일한 단계다(활성 조건이 `useCharacterManage` 안에 있어 스크롤과 바의 조상이 그 훅을 부르는 쪽이어야 한다).

**API 키 단계 실패 표시 ([[ADR-065]] 결정 1)**: 실패는 **토스트**로 알린다. 문구가 사라져도 이 자리엔 폼이 남으므로([[ADR-063]] 원칙 4) 인라인 문구를 두지 않는다. 세 경로 모두 `formatOnboardingError`(위치: `features/onboarding/format.ts`. 스토어가 쓰므로 `app/` 이 아니다) 로 **원인별 문구**를 띄운다.
- `submitApiKey` 실패: 전에는 원인과 무관하게 한 문구였다(바로 아래에서 원인을 계산해 state에 넣으면서도 토스트는 그 값을 안 썼다).
- `hydrate` 실패(저장된 키로 재실행했다가 조회 실패). 전에는 토스트가 아예 없어 아무 설명 없이 입력 화면으로 되돌아갔다.
- `setApiKey`(키 저장) 실패: 전에는 `try` 밖이라 미처리 rejection이었다. 이제 `storageWriteFailed` 로 알린다(그 문구가 처음으로 도달 가능해졌다).
- 액션은 두지 않는다. 온보딩 중에는 설정 화면이 없고 재시도는 폼에서 한다.

`ContentCharacterStep`([[ADR-035]] 결정 13)은 캐릭터 관리 피커와 같은 `getCharacterPickerRoster` 를 쓰므로 같은 정책을 따른다(원문은 [content-scheduler.md](./content-scheduler.md) "캐릭터 관리 피커: 후보 목록 로딩"): **활성(`access_flag: true`)이 확인된 캐릭터만** 표시, 표시할 캐시가 없으면 **스피너 → 조회 완료 후 한 번에** 목록(캐시가 있으면 기존 ADR-016 즉시 표시 + 개별 patch 유지), 조회가 끝났는데 목록이 비면 **"활성 캐릭터 없음"과 "조회 실패"를 구분**해 안내한다.
- 이 단계는 예열(ADR-016) 직후라 정상 경로에서는 캐시가 항상 따뜻하다. 콜드 스타트 분기는 예열이 통째로 실패했을 때만 밟는다. 그래서 여기서는 특히 **"조회 실패"를 빈 상태로 위장하지 않는 것**이 중요하다(선택할 캐릭터가 없으면 CTA가 비활성이라 온보딩이 진행 불가 상태로 멈춘다).
- 모달이 아니라 페이지라 판정 분기는 `ContentCharacterStep` 안의 `RosterBody` 가 직접 그린다(피커와 동일한 우선순위·마크업). 실패도 피커와 같은 공용 `ErrorState` 를 쓰고([[ADR-062]]), 스탈 배너 분기도 같다. **다른 것은 401 뿐**. 온보딩의 `invalidApiKey` 는 **다시 시도** + "API 키를 다시 확인해주세요"이고, 피커는 **액션 없음** + "키 입력 화면으로 이동합니다"다([[ADR-115]] 결정 7, 2026-08-08). 갈리는 근거는 "설정 화면이 있는가"가 **아니다**. 이 화면의 401 은 방금 넣은 키에 대한 **폼 자체의 실패**라 재시도가 실제 처방이고, 그래서 이 자리는 무효화 진입점에 **배선하지 않는다**([[ADR-115]] "구현하며 정정한 것" 5). 피커의 401 은 반대로 곧 화면을 키 입력으로 옮기므로 누를 것이 없다. **스탈 배너는 두 자리가 같다**(401 포함 전부). `formatStaleRosterError` 가 `place` 를 받지 않는 이유다.
  - **근거가 구조에서 배선으로 내려왔다**([[ADR-116]] 결정 2, 2026-08-08). 전에는 *"무효화 경로가 `completed` 일 때만 성립하므로 온보딩의 401 은 애초에 그 경로가 아니다"* 였는데, 가드가 **"키 입력 화면에 있지 않을 때"** 로 넓어져 구조가 더는 막아 주지 않는다. 이 자리의 401 을 폼 실패로 남기는 것은 이제 **미배선이라는 선택**이다. 새로 배선되는 것은 **429** 뿐이다(아래).
- **429 로 이 단계가 잠기던 것이 모달 경로로 풀린다**([[ADR-116]] 결정 1·2, 2026-08-08, 이슈 #176). 로스터 조회가 429 로 실패하면 출구 다섯 방향이 전부 막혀 있었다. `계속하기` 는 고를 캐릭터가 없어 영구 비활성 · `다시 시도` 는 같은 요청을 다시 쏴 또 429 · `계정 다시 선택`(`emptyAction`)은 **확정된 빈 상태 가지에만** 붙어 실패 화면에 도달하지 못함 · 단계는 라우트가 아니라 `status` switch 라 되돌릴 UI 없음 · 재시작하면 `deriveResumeTarget()` 이 **같은 단계로 되돌린다**. 온보딩 중에는 설정 화면도 없어 연결 해제조차 못 한다. 이제 그 위에 **닫을 수 없는 안내 모달**이 덮이고, 확인을 누르면 키 입력 화면으로 가서 **서비스 단계 키로 다시 넣을 수 있다**(문구·사슬의 원문은 [../foundation/error-resilience.md](../foundation/error-resilience.md) 429 항목).
  - **`계정 다시 선택` 을 실패 가지에 넘기는 것은 답이 아니었다**. 계정을 바꿔도 **같은 키라 429 는 그대로**다. 실제로 통하는 처방은 키를 바꾸는 것 하나뿐이다.
  - **429 발생 자체는 줄지 않는다**([[ADR-116]] 결정 5). 로스터·예열의 fan-out 동시성 캡은 이번 범위 밖이다(아래 "열린 질문").
- **후보가 0건이면 "계정 다시 선택"을 준다**([[ADR-086]] 결정 8, 2026-08-03). 결정 8이 조회 불가 계정을 잠갔어도 고른 뒤 전원이 조회 불가로 바뀌는 경로는 남는다. 온보딩에는 설정 화면이 없어 계정 선택 단계로 되돌아가는 것이 유일한 탈출구다. 피커의 빈 상태 문구("표시할 캐릭터가 없어요")를 그대로 쓰되 여기에만 이 액션이 붙는다.
- **최소 1명을 골라야 저장된다**([[ADR-086]] 결정 7). 0명은 화면을 빈 상태로 만들 뿐 어떤 의도도 표현하지 않는다. 피커도 같은 규칙이다([content-scheduler.md](./content-scheduler.md)).

## 계정 선택 프로브 ([[ADR-068]] 결정 4, 🟡 [[ADR-113]]): ⛔ **소비자가 없다**

> `use-account-probes.ts` 파일은 남아 있지만 제품 코드가 부르지 않는다. 아래는 그 판정 규칙이 어디로 갔는지(로스터 조회, [[ADR-143]] 결정 5) 읽기 위한 기록이다.

> RN 에는 이 프로브가 없다([[ADR-143]] 결정 5). 전 계정을 미리 훑는 대신 드롭다운으로 연 계정만 로스터 조회가 판정한다. 그래서 [[ADR-116]] 결정 3(‘판정 못 한 계정이 있으면 목록을 안 그린다’)이 RN 에서는 **계정 하나 단위**로 좁아진다.

계정 선택 화면은 각 계정의 **전체 캐릭터**에 `character/basic` 을 프로브한다(`features/onboarding/use-account-probes`). 전에는 대표 1명만 조회해 초상화만 채웠다.
- **전수 프로브가 settle 할 때까지 목록을 그리지 않는다**([[ADR-113]] 결정 3, 2026-08-08, 이슈 #163). 전에는 프로브 도착 전에도 계정을 고를 수 있었는데(모르는 것을 단정하지 않으려는 규칙이었다), 실제로는 **고를 수 없는 카드를 고를 수 있는 것처럼 먼저 보여주고 나서 뺏는** 결과가 됐다. 대표 캐릭터의 이름·레벨·초상화도 그 사이 한 번 바뀌었다. 원칙은 유효하고 이제 **"모르는 동안은 보여주지도 않는다"** 로 적용한다(피커 콜드 스타트가 추측 목록을 흘리지 않고 스피너를 보여주는 것과 같은 처방, [[ADR-053]] 결정 2).
  - **대기 표현은 `(완료/전체)` 한 줄 + 진행률 바뿐이고 설명 문장은 붙이지 않는다**([[ADR-113]] 결정 5). 시작 시점에 총량(전 계정 캐릭터 수의 합)을 알 수 있어 정확히 그릴 수 있다. **숫자는 남기고 문장만 뺀다**. 총량을 아는 것이 이 표현의 근거인데 그 총량을 화면에서 지우면 앞뒤가 맞지 않는다. 예열 진행률(`캐릭터 정보를 준비하고 있어요 (N/M)`)에서 앞 문장만 뗀 모양이고, 이 대기는 사용자가 **아무것도 고르기 전**의 관문이라 설명할 대상이 화면에 없다. 프리미티브는 [[ADR-061]] 결정 6 의 `h-1.5` 바(`components/atoms/ProgressBar`)를 그대로 쓴다. 이 자리는 [[ADR-061]] 결정 1("버튼 밖 24px 이상은 스윕 스피너")의 **두 번째 예외**다(첫 예외는 [[ADR-074]] PTR). 총량을 아는 대기에 불확정 스피너를 두는 것은 아는 것을 안 보여주는 것이다.
    - 직전 단계인 설정 `verifying` 과 **완전히 같지는 않다**. 그쪽은 `character/list` 가 한 번이라 총량이 없어 **숫자 없이 0% 바만** 세운다([settings.md](./settings.md)). 이어지는 것은 **프리미티브와 자리**이지 내용이 아니다.
  - **완료 판정은 "성공"이 아니라 settle 이다**([[ADR-113]] 결정 4). `getAuthConfig()` 가 `null` 이라 프로브가 시작조차 못 하는 조기 return, 계정이 0개인 경우, 개별 프로브 실패(네트워크·401·429) 전부 완료로 친다. 성공 기준이면 그 경로에서 화면이 영원히 로딩이 된다.
  - 설정의 계정 변경도 같은 `AccountSelectionList` 를 쓰므로 함께 적용된다([settings.md](./settings.md)).
- **대표는 "성공적으로 확인된 캐릭터 중 최고 레벨"**. `character/list` 의 최고 레벨이 조회 불가일 수 있어(실측) 계정 표기가 조회 불가 캐릭터의 이름·레벨이 되던 문제를 없앤다. **목록이 그려지는 시점에는 이미 프로브 결과가 있으므로 잠정 표시가 없다**([[ADR-113]] 결정 3). 후보 집합이 *"003 이 아닌 캐릭터"* 가 아니라 **"확인된 캐릭터"** 인 것이 요점이다([[ADR-116]] 결정 3 구현, 2026-08-08). 429 로 아무것도 못 본 캐릭터가 후보로 남으면 [[ADR-068]] 결정 4 가 없앤 그 문제가 429 경로로 되살아난다. 확인된 캐릭터가 0명이면 대표는 `null` 이다.
  - **`null` 이면 화면이 `pickRepresentativeCharacter(account.characters)` 로 폴백하는데, 그 인자가 빈 배열이면 던진다**. 그래서 **캐릭터가 0명인 계정은 여기까지 오지 않는다**([[ADR-127]], 2026-08-12). 정규화가 앞에서 걸러내므로 이 폴백의 인자는 항상 1명 이상이다(폴백 자체는 프로브가 시작조차 못 했을 때를 위해 남는다, [[ADR-113]] 결정 4). 이 불변식이 깨졌을 때 어떻게 되는지는 [../trouble/2026-08-12-onboarding-empty-account-crash.md](../trouble/2026-08-12-onboarding-empty-account-crash.md).
- **전원 조회 불가면 그 계정 카드에 경고**("이 계정의 캐릭터를 조회할 수 없습니다"). 전수 프로브라 "이 계정 전체"를 단정할 수 있다. 표본 1명으로는 못 한다(월드 리프는 캐릭터 1~2개 단위가 흔하다).
- **그 계정은 고를 수 없다**([[ADR-086]] 결정 8, 2026-08-03). 전에는 경고만 띄우고 선택은 허용했는데, 고르면 후보가 0명이라 "최소 1명" 규칙을 만족할 수 없어 온보딩이 진행 불가 상태로 멈춘다. 들어갈 수 없는 문은 잠근다. 목록이 프로브 뒤에 그려지므로 이 판정은 **처음부터 확정**이다.
- **조회 불가(`OPENAPI00003`)만 영구로 다룬다**. 그 외 실패(429·네트워크 등)는 **영구 판정이 아니라 "판정 불가"** 다("모르는 실패를 영구로 단정하지 않는다", [[ADR-113]] 결정 7 의 원칙). 판정은 계정 단위로 **세 갈래이고 겹치지 않는다**(`AccountProbeVerdict`. `queryable` / `allUnavailable` / `undetermined`, 판정 불가가 먼저다: 못 본 캐릭터가 남았으면 "전원 003"을 단정할 수 없다). 다만 **"영구로 단정하지 않는다"가 "확인된 것과 똑같이 다룬다"는 뜻은 아니다**. 확인하지 못한 캐릭터는 대표 후보에서 빠지고(위), 그런 캐릭터가 있는 계정은 목록에 서지 않는다(아래).
- **판정하지 못한 계정이 하나라도 있으면 목록을 그리지 않는다**([[ADR-116]] 결정 3, 2026-08-08, 이슈 #177). 전에는 003 이 아닌 실패를 `catch` 에서 **조용히 버려서**(`use-account-probes.ts:121-125`) 429 로 아무것도 못 본 캐릭터가 전부 "조회 가능"으로 분류됐다. `allUnavailable` 이 **항상 false**(위양성이 아니라 **위음성**)라 전원이 003 인 계정도 멀쩡해 보였고, 조회 불가 캐릭터가 대표로 설 수 있었다([[ADR-068]] 결정 4 가 전수 프로브로 없앴다고 적은 문제의 429 판). 화면에는 429 를 담을 필드조차 없었다.
  - 이것은 결정 3(*"모르는 동안은 보여주지도 않는다"*)을 **429 에도 적용**한 것이다. 지금까지 같은 ADR 의 **결정 3 과 결정 7 이 서로 반대 방향으로** 적용돼, 모르는 채로 확신에 찬 목록을 그리고 있었다.
  - **429 만이 아니라 003 이 아닌 모든 실패를 하나로 묶는다**(사용자 결정). 규칙이 하나로 단순해지고, 오프라인에서도 같은 화면이 뜨는 것은 **어느 쪽이든 그 계정에 대해 알아낸 것이 없다는 사실이 같기** 때문이다.
  - **그 자리의 출구는 안내 모달 하나**다. 429 를 만나면 [../foundation/error-resilience.md](../foundation/error-resilience.md) 429 항목의 사슬(닫을 수 없는 모달 → 확인 → 키 입력 화면)이 그대로 돈다.
  - **모달로 보내는 것은 429 뿐**이다. 그 원인만 처방이 "키 교체"라 이 화면에서 할 수 있는 것이 없고, 네트워크 등 나머지는 원인을 모르므로 키를 지울 근거가 없다. 그 자리에는 원인별 `ErrorState` + **다시 시도**(같은 계정 목록으로 프로브를 처음부터 다시 돈다)를 둔다. 원인이 섞이면 429 를 앞세운다(출구를 쥔 쪽이라 화면과 모달이 같은 이야기를 해야 한다). 어느 원인이든 그 자리에서 앞으로 갈 길이 하나는 있다([[ADR-116]] 결정 4).
  - **`isSettled` 의 의미는 그대로다**([[ADR-113]] 결정 4). 성공이 아니라 settle 기준인 것은 무한 스피너를 막는 장치이고, 바뀌는 것은 settle **이후의 표시**다.
- **자격(eligibility) 스윕은 이 대기에 넣지 않는다**([[ADR-113]] 결정 6). `basic` 은 어차피 전 계정을 부르고 있어 캐싱이 공짜지만 `scheduler/character-state` 는 선택 계정만 부른다. 당기면 안 고를 계정 몫이 순증한다. 003 판별에 스윕은 필요 없고, 자격 판정은 예열·피커의 몫으로 남는다([[ADR-086]] 결정 5).
- **결과를 각 계정의 `accountId` 로 `character-basic-cache` 에 쓴다**([[ADR-113]] 결정 2, 2026-08-08). 전에는 쓰지 않았는데(고르지 않은 계정 캐릭터가 피커의 stub 단계에 새어 나올까 봐: [[ADR-017]] 결정 6이 캐시 인덱스를 통째로 읽던 시절의 우려다), **[[ADR-086]] 결정 9가 인덱스를 계정별로 쪼개(`characterBasicCacheIndexKey(accountId)`, stub 은 `getAllCachedCharacterBasicOcids(accountId)`) 그 누출이 구조적으로 불가능해졌다.** 안 고른 계정 몫은 그 계정의 인덱스에만 들어가고, 나중에 그 계정으로 바꾸면 따뜻한 캐시로 재사용된다.

**계정 선택 실패 표시 ([[ADR-083]] 결정 4, 2026-08-02)**: 목록 상단 인라인 문구(`AccountSelectionList` 의 `errorMessage` prop)를 없애고 **토스트**로 통일했다. 계정 목록·"계속하기"가 그 자리에 남으므로([[ADR-063]] 원칙 4) 인라인일 이유가 없었다.
- 네 종류 중 `invalidApiKey`·`rateLimited`·`network` 는 **이미 스토어가 토스트를 띄우고 있어** 인라인은 중복이었다([[ADR-065]] 결정 1이 API 키 경로에 넣은 것).
- `storageWriteFailed`(계정 선택 저장 실패)만 토스트가 없어 인라인을 지우면 무음이 된다. `selectAccount` 의 `catch` 에 토스트를 추가했다. 액션은 두지 않는다(다시 계정을 누르면 되는 일이라 중복).
- 설정의 계정 변경 모달(`AccountFlowStatus`)은 이미 `errorMessage={null}` 을 넘기고 있어 표시가 바뀌지 않는다. 모달 본문 전체를 차지하는 그 컴포넌트 자신의 `error` 케이스는 여전히 인라인이다(그 자리의 내용).

### `character/basic` 5분 TTL 가드 ([[ADR-113]] 결정 1)
`character/basic` 호출을 **공유 경로 하나**(`features/schedule-sync/character-basic-fetch` 의 `fetchCharacterBasicCached(apiKey, accountId, ocid, now)`)로 모으고, "이 ocid 의 `basic` 이 5분 안에 캐시됐으면 네트워크를 건너뛰고 캐시 값을 돌려준다"를 그 자리에서 판정한다(캐시가 이미 들고 있던 `cachedAt` 을 여기서 처음 읽는다). TTL 값은 같은 모듈의 `CHARACTER_BASIC_TTL_MS`(`5 * 60 * 1000`) 하나뿐이다.
- **네 호출부가 전부 이 경로를 통과한다**. 계정 선택 프로브(`use-account-probes`) · 예열(`prefetch`) · 캐릭터 피커(`character-roster`) · 동기화 편승 갱신(`schedule-sync` 의 `refreshCharacterBasics`, [[ADR-097]] 결정 7). 넷은 **완전히 같은 요청**이고 소비하는 필드만 달라, 온보딩 한 바퀴에 같은 캐릭터로 세 번이 나가고 있었다. 원형 `fetchCharacterBasic`(`nexon/character`)과 캐시 쓰기(`setCachedCharacterBasic`)를 부르는 제품 코드는 이제 이 모듈뿐이라, 새 호출부가 원형을 직접 부르면 눈에 띈다.
- **`now` 는 호출부가 넘긴다**. 헬퍼가 시계를 스스로 읽지 않는다. 라운드 하나(프로브 1회·편승 갱신 1회)가 같은 기준 시각을 공유해야 같은 한 바퀴 안에서 판정이 흔들리지 않고, 오차는 항상 TTL 이 **짧아지는** 보수적인 방향으로만 난다. 파싱 불가·미래 `cachedAt` 은 만료로 취급하고(손상된 값·기기 시계 되감기가 캐시를 영구히 신선하게 만들면 안 된다) 경계는 배타적이다(정확히 5분이면 만료).
- **실패는 캐시로 폴백하지 않고 그대로 던진다**. 호출부들이 그 예외에 판정을 걸고 있다(400 `OPENAPI00003` → `characterUnavailable`, 401·429 → 전역 실패). 여기서 삼키면 그 판정이 통째로 죽는다.
- **호출부를 하나씩 고치지 않는 이유**: 그러면 호출자끼리 서로의 존재를 알아야 하고, 새 호출부가 생기면 조용히 중복이 되살아난다(실제로 [[ADR-097]] 결정 7이 넷째 호출부를 그렇게 추가했다). 공유 경로 하나면 **호출자끼리 서로를 몰라도 접힌다.**
- **5분인 이유**: ① 온보딩 한 바퀴(계정 선택 → 예열 → 모드 선택 → 피커)를 여유 있게 덮는다 ② **[[ADR-097]] 동기화 TTL 10분보다 짧아야 한다**. 같거나 길면 편승 갱신이 경계에서 거의 항상 건너뛰어져 사실상 죽는다. 대가는 5분 안에 피커를 다시 열면 개명·레벨업이 그만큼 늦게 반영되는 것이고, 그래서 [[ADR-097]] 결정 7의 "별도 TTL 은 두지 않는다"가 이 가드로 **정정**된다(그 결정의 호출 조건은 그대로 서고 가드가 하나 앞에 붙을 뿐이다).
- **절감의 값은 호출 수가 아니다**. 자격 스윕은 실패를 조회 원장에 기록하지 않으므로(의도된 설계, [[ADR-086]] 결정 4) 429 가 나면 다음 화면이 같은 13일을 처음부터 다시 훑고 그게 또 429 를 부른다. 중복을 접는 값은 **429 확률을 낮춰 원장이 채워질 확률을 올리는 것**이고, 원장이 한 번 차면 그 캐릭터는 그 뒤로 스윕이 없다(이슈 #158).
- **접은 것은 총 호출 수이지 한순간의 fan-out 폭이 아니다**. 프로브·예열·피커·편승 갱신 모두 `Promise.all` 로 대상 전체를 **동시에** 부르고 동시성 캡이 없다(프로브는 전 계정 × 전 캐릭터가 한 번에 나간다). single-flight 도 없어 같은 ocid 를 두 경로가 **동시에** 부르면 둘 다 나간다. TTL 은 이미 끝난 요청만 접는다(온보딩 한 바퀴는 순차라 지금 겹치는 경로가 없다). 429 가 남으면 다음 후보는 여기다.

## 열린 질문
- **다계정 동시 추적을 아무도 해 본 적이 없다**([[ADR-143]] 미검증, 2026-08-16 신설). 계정이 2개 이상인 `character/list` 응답은 [[ADR-007]] 시절 한 번 실측됐지만, 그 캐릭터들을 **함께** 추적한 적은 없다. 특히 계정 공유 진행도 원장(`accountSharedProgress:{accountId}`, [[ADR-030]])이 캐릭터마다 자기 계정으로 갈리는지는 실제 다계정 키로만 확인된다([[ADR-143]] 결정 6).
- **계정을 처음 열 때의 대기가 견딜 만한지**([[ADR-143]] 결정 5, 2026-08-16 신설). 예열을 ‘열 때’로 미룬 대가라, 캐릭터가 많은 계정을 드롭다운으로 처음 열면 그 계정 몫의 자격 판정을 기다린다. 두 번째부터는 조회 원장·5분 TTL 이 받는다. **눈으로만 판정된다.**
- ~~**고를 수 있는 계정이 하나도 없을 때의 화면**([[ADR-127]] 결정 3)~~ → **닫혔다**([[ADR-143]] 결정 10, 2026-08-16). 계정을 고르는 화면 자체가 없어지고, 드롭다운이 비면 캐릭터 선택 화면이 ‘빈 상태 + 키 재입력’을 직접 그린다.
- **넥슨이 `character_list: []` 를 내는 조건**([[ADR-127]] 대가, 2026-08-12 신설). 그런 응답을 직접 받아 본 적이 없다. 테스터 재현 조건에서 역산한 것이라, 방어는 하되 조건을 안다고 적지 않는다([../foundation/nexon-api.md](../foundation/nexon-api.md)). 테스터 키로 `character/list` 를 한 번 호출해 보면 닫힌다.
- **429 로 키를 지우고 온보딩으로 내보내는 것이 실사용에서 옳은지**([[ADR-116]] 대가, 2026-08-08 신설). 셋이 함께 미확인이다: ① **실제 429 를 한 번도 받아 본 적이 없다**(자동 테스트는 `rateLimited` 를 주입할 뿐 `nexon/http` → `toScheduleSyncError` → 진입점 → 모달이 **실제 429 응답에서** 이어지는지는 모른다. [[ADR-114]] 가 남긴 같은 항목이 그대로다) ② 모달에 닫기가 없고 429 응답에 일/초당 구분이 없어 **몇 초 뒤 풀렸을 실패에도** 키 입력 화면으로 간다 ③ 그렇게 지운 키가 **다음 날이면 다시 쓸 수 있는 키**일 수 있다(일 한도 소진은 무효가 아니라 오늘 소진된 것이다). 셋 다 눈으로만 판정된다.
- **무효 키 안내 모달을 실제로 만났을 때의 체감**([[ADR-115]] 결정 10, 2026-08-08 갱신: [[ADR-116]] 이후 **429 도 같은 모달**이라 이 질문은 두 원인 모두에 걸린다). 보스 목록을 보던 중에 무효 키가 감지되면 화면 위에 **닫을 수 없는 모달**이 덮이고 `확인` 외에는 누를 것이 없다. 결정 10 은 즉시 이동(옛 결정 1)이 *"이유를 읽기 전에 화면이 바뀐다"* 는 문제를 고친 것인데, **탭을 하나 더 요구하는 대가가 실사용에서 옳은지는 눈으로만 판정된다.** 함께 미확인인 것 둘: 여러 캐릭터에서 동시에 실패해도 모달이 하나만 뜨는지(결정 6) · 재입력 후 재개가 정말 예열 없이 즉시인지(결정 4·5). **무효 키 감지 → 모달 → 확인 → 키 입력 화면까지는 iOS 시뮬레이터에서 확인됐다**(2026-08-08, 넥슨에서 키를 실제로 삭제해 재현).
- 캐릭터 관리 피커 개선([[ADR-015]]) 잔여: Nexon `character/look` 이미지 얼굴 크롭 쿼리 공식 지원 여부(미지원 시 CSS 근사), 개선을 다른 캐릭터 선택 UI로 확장할지.
- **계정 선택 대기가 실제로 견딜 만한지**([[ADR-113]] 결정 3·5, 2026-08-08 신설). 캐릭터가 많은 계정에서 실사용해 보고 판단할 값이 셋이다: 5분 TTL · 동시성 캡을 둘지 · 문장 없이 숫자 한 줄로 충분한지. **어느 것도 실기기로 확인되지 않았다**(ADR-113 "실기기·실사용으로만 확인되는 것").
  - **동시성 캡은 [[ADR-116]] 범위에서 사용자가 명시적으로 기각했다**(2026-08-08). 질문이 닫힌 것이 아니라 **한 번 제기됐다 미뤄진 것**이다. 그래서 429 발생 건수는 그대로이고, 이 화면은 이제 429 를 만나면 **목록 자체를 안 그린다**([[ADR-116]] 결정 3). 429 가 잦은 계정은 계정 선택 단계에서 멈추고 출구가 안내 모달 하나다. **그 빈도가 실사용에서 얼마나 되는지도 함께 미확인이다.**
- **안 고른 계정의 캐시 엔트리를 정리할지**([[ADR-113]] 결정 2 의 대가, 2026-08-08 신설). 엔트리(`characterBasicCache:{ocid}`)는 전역 키이고 인덱스만 계정별이라 프로브가 훑은 모든 계정 몫이 저장소에 남는다. 지금은 **의도된 성질**로 둔다(그 계정으로 바꾸면 따뜻한 캐시로 재사용, [[ADR-086]] 결정 9). 계정이 많은 사용자에게 실제로 부담이 되는지 관측된 바 없으므로 관측 전에 정리 정책을 만들지 않는다.
