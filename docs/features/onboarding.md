## 단계 셋

[[ADR-143]]·[[ADR-144]] 다.

```
API 키 → 스케줄 관리 방법 → 캐릭터 선택
```

**메이플 ID를 고르는 단계가 없다**([[ADR-143]] 결정 1). 캐릭터 선택 화면이 계정 드롭다운을 갖고
**여러 계정의 캐릭터를 한 목록으로** 고른다([[ADR-144]]).

그래서 웹뷰 시절의 세 단계가 통째로 없어졌고, 그 자리는 이렇게 대체됐다.

| 웹뷰 시절의 단계 | 지금 |
|---|---|
| 계정 선택(`AccountSelectionList`) | **없다.** 캐릭터 선택 화면의 드롭다운이 대신한다 |
| 예열(⛔ ADR-016. 계정 전체 캐릭터 선행 조회) | **드롭다운으로 그 계정을 열 때** 그 계정 몫만 판정한다([[ADR-143]] 결정 5) |
| 계정 선택 프로브(`use-account-probes`) | 같은 이유로 없다. 판정은 로스터 조회가 한다 |

**코드에서도 전부 없앴다.** `OnboardingStatus` 는 `awaitingApiKey` · `verifyingApiKey` ·
`selectingTrackingMode` · `selectingContentCharacters` · `seedingTracking` · `completed` · `error`
일곱이고, `selectingAccount` 와 `prefetching` 은 남아 있지 않다. `use-account-probes.ts` 파일과
`accountScope` 플래그도 삭제됐다.

### 키 입력

발급 절차는 **앱 밖 안내 사이트**(`mapleroutine.store/api-key`)가 담당하고 앱은 링크만 준다
([[ADR-110]]). 앱 안 단계별 위저드가 아닌 이유는 둘이다. 스크린샷 7장이 번들에 들어가면 최초 1회 보는
화면 때문에 모든 사용자가 1.2MB 를 받고, 넥슨이 화면을 바꿀 때마다 OTA 배포가 필요하다.

키는 `storage/api-key.ts` 를 거쳐 기기에 저장한다.

- **링크는 둘이다**(2026-08-08, 이슈 #61, 사용자 확정). 1차 경로가 **‘API 키 발급 방법’(가이드)**,
  다른 하나가 **`openapi.nexon.com` 바로 가기**다. 처음 쓰는 사용자를 넥슨 첫 화면에 떨궈 놓지 않는
  것이 1차 경로를 가이드로 두는 이유고, 이미 발급받은 사용자에게 7단계 안내를 거치게 하지 않는 것이
  바로 가기를 남기는 이유다. 가이드 1단계가 `openapi.nexon.com` 링크를 이미 품고 있어 **중복이 아니라
  서로 다른 두 진입점**이다.
- **외부 브라우저로 나갔다 와도 잃는 것이 없다.** 두 링크 모두 시스템 브라우저로 나가지만, 재개
  지점이 저장된 값에서 파생되므로([[ADR-086]] 결정 1) 키를 넣기 전에 나갔다 돌아오면 그대로
  `awaitingApiKey` 다. 입력 중이던 값은 컴포넌트 로컬 상태라 앱이 메모리에서 내려가면 사라지지만, 이
  시점에 사용자가 가진 키는 아직 없다.
- **설정 화면에는 진입점을 두지 않는다**(2026-08-08 사용자 확정). 설정에 API 키 재입력 경로 자체가
  없어 가이드 링크만 놓으면 갈 곳 없는 안내가 된다.

### 캐릭터가 0명인 메이플 ID는 목록에 오지 않는다

[[ADR-127]](2026-08-12)이다. `normalizeCharacterList` 가 걸러낸다. `MapleAccount` 의 뜻이 *"응답에
있던 계정"* 이 아니라 **"고를 수 있는 계정"** 이고, 소비하는 자리가 전부 캐릭터가 있다는 전제로 쓴다.

이 불변식이 깨졌을 때 무슨 일이 나는지는
[../trouble/2026-08-12-onboarding-empty-account-crash.md](../trouble/2026-08-12-onboarding-empty-account-crash.md)
에 있다.

## 단계 재개

[[ADR-086]] 결정 1·2(2026-08-03)다. 어느 단계에서 앱을 껐든 **다음 실행에서 그 단계부터 이어간다.**
전에는 저장된 계정 id 하나만 보고 곧바로 완료로 전이해, 모드와 캐릭터를 고르지 않은 채 빈 메인으로
떨어졌다.

**재개 지점은 저장된 값에서 파생한다. 진행 상태 전용 키를 두지 않는다.** 각 단계의 산출물이 이미
영속화돼 있어서, 진행 상태를 따로 쓰면 진실이 둘이 되고 한쪽만 써진 채 앱이 죽는 순간 어긋난다.
고치려는 결함과 같은 종류의 결함이다.

| 저장 상태 | 재개 단계 |
|---|---|
| `apiKey` 없음 | `awaitingApiKey` |
| `trackingMode` 미선택 | `selectingTrackingMode` |
| `trackedCharacters` 가 `null` 또는 `[]` | `selectingContentCharacters` |
| 그 외 | `completed` |

**이 표는 두 경로에 함께 적용된다. 부팅과 키 재입력 성공이다**([[ADR-115]] 결정 4, 2026-08-08). 파생
판정은 **함수 하나**(`features/onboarding/resume.ts` 의 `deriveResumeTarget`)이고 두 경로가 그것을 공유한다. 두 벌이 되면 재개
규칙의 진실이 둘이 되는데, 그것이 [[ADR-086]] 결정 1이 진행 상태 전용 키를 거부한 바로 그 이유다.

- **뒤 두 단계는 네트워크 없이 재개된다.** 모드 선택은 순수 UI 이고, 캐릭터 선택은
  `getCharacterPickerRoster` 가 자체 조회한다.
- **`trackedCharacters === []` 는 완료가 아니다.** 최소 1명 규칙이 있으므로 빈 배열은 미완료와
  같다. 저장 레이어의 `null` 과 `[]` 구분([[ADR-012]])은 그대로 두고, 온보딩 게이트에서만 둘을 같게
  읽는다.
- **`trackingMode` 미선택을 `'auto'` 로 읽지 않는다.** `getTrackingMode()` 가 `TrackingMode | null` 을
  돌려주고 소비처가 `?? 'auto'` 로 흡수한다. **동작 기본값은 그대로 자동**([[ADR-035]] 결정 2)이고,
  바뀌는 것은 "골랐는가"를 구분할 수 있게 된 것뿐이다. 고르지 않은 값을 화면이 "선택됨"으로 표시하는
  것만 없앤다.
- **마이그레이션**: `trackingMode` 키가 없는데 비어 있지 않은 `trackedCharacters` 가 이미 있으면
  ([[ADR-035]] 이전 설치본 완주자) `'auto'` 를 1회 기록한다. 안 하면 정상 사용자가 온보딩으로
  되돌려진다.

## 키 재입력 경로

[[ADR-115]] 결정 4·5(2026-08-08, 이슈 #157)다. API 키가 무효화되면 저장된 **`apiKey` 하나만** 지워지고
사용자는 키 입력 화면으로 온다.

**그래서 여기서 키를 다시 넣으면 위 표가 가리키는 단계(대개 `completed`)로 곧바로 간다.** 트래킹
모드와 추적 캐릭터를 **다시 묻지 않는다.** 무효화된 것은 키 하나뿐이라 나머지 저장값은 여전히
사실이다.

전에는 키 검증 성공이 무조건 계정 선택으로 가고 저장된 계정 id를 리셋해, 키 하나 때문에 계정
선택부터 캐릭터 선택까지 전부를 다시 시켰다. 재개 파생이 부팅 경로에만 있었기 때문이다.

### 다른 계정의 키를 넣었을 때의 가드

새로 넣은 키가 **다른 넥슨 계정의 키**일 수 있다. 그러면 남의 계정 키로 이전 계정 ocid 추적 목록을
그대로 쓰게 된다.

**RN은 저장된 추적 ocid로 대조한다**([[ADR-143]] 결정 9). 키 검증 때 이미 받는 `character/list`
응답에 저장된 추적 ocid가 **하나라도** 있으면 재개하고, **하나도 없으면** 캐릭터 선택 단계로 보낸다.
일부만 없는 경우(캐릭터 삭제·이전)는 재개한다. 없는 ocid는 피커와 동기화가 각자 이미 다룬다.

- **가드는 지킬 목록이 있을 때만 동작한다.** 저장된 목록이 `null` 이나 `[]` 면 대조하지 않고 위 표
  그대로 간다. 안 그러면 **처음 키를 넣는 신규 사용자**가 "목록이 비었으니 하나도 없다"로 걸려 스케줄
  관리 방법 단계를 건너뛴다. 이 가드가 막는 것은 ‘남의 계정 키로 이전 목록을 그대로 쓰는 것’이라,
  지킬 목록이 없으면 판정 대상 자체가 없다.
- 대조는 응답의 **전 계정 캐릭터 ocid 집합**으로 한다. 계정을 넘어 고르는 것이 본론이라 계정별로
  나눠 볼 이유가 없다. **추가 네트워크 호출은 없고** 추적 목록만 로컬에서 한 번 더 읽는다.

### 이 화면으로 보내는 원인은 둘이다

키 무효화(400 `OPENAPI00005` · 401/403)와 **호출 한도 초과(429)**([[ADR-116]] 결정 1, 2026-08-08)다.
둘은 **같은 사슬에 문구만 다르고**, 확인을 누르면 똑같이 `apiKey` 만 지워진 채 이 화면으로 온다.
그래서 재개 규칙도 그대로 적용된다.

**무효화와 한도 초과 자체**(감지 지점 · 모달 문구 · 확인 후 이동 · 저장소에서 지우는 범위)는 여기가
아니라 [../foundation/error-resilience.md](../foundation/error-resilience.md) 의 401/403·429 항목이
원문을 갖는다. 이 절은 **키를 다시 받은 뒤**만 다룬다.

### 갈림길 레이아웃 (2026-08-08, 이슈 #61)

**이 화면에 오는 사람은 둘뿐이다. 키가 있는 사람과 없는 사람.** [[ADR-110]] 이 두 링크를 "중복이 아니라
서로 다른 두 진입점"이라고 적은 것을 **화면 구조로 옮긴다.**

전에는 둘 다 폼 **위** 한 문단 안에 인라인 밑줄 링크로 붙어 있어서, 1차 경로라고 선언한 가이드가
화면에서 가장 작고 흐린 요소(`text-sm text-text-muted` 문장 **안**)였다. 선언과 그림이 어긋나 있었다.

```
제목 블록   h2 text-lg font-semibold text-text  "넥슨 API 키를 입력해주세요"
            p  text-sm text-text-muted          "스케줄러 API를 사용하려면 개인 API 키가 필요해요"
            p  text-xs text-text-muted          "입력한 키는 이 기기에만 저장되고 넥슨 외 어디로도 전송되지 않아요"
입력 블록   label text-sm font-medium + input + 표시 토글
            "openapi.nexon.com에서 확인" + ExternalLink h-3     ← 키가 있는 사람의 동선
확인 버튼   Button primary, w-full
구분선      "아직 API 키가 없나요?"  (좌우 h-px bg-border, 가운데 text-xs text-text-muted)
가이드 블록 BUTTON_VARIANT_CLASS.outline  "API 키 발급 방법 보기" + ExternalLink h-3.5
            p text-xs text-text-muted 중앙  "넥슨 오픈 API에서 키를 받는 7단계 안내"
```

- **제목을 되찾는다.** 온보딩 단계 중 이 화면에만 제목이 없었다. `TrackingModeStep` 과
  `ContentCharacterStep` 은 모두 제목과 보조문으로 시작한다.
- **폼이 먼저다.** 넥슨 바로 가기가 인풋 바로 아래 붙어 "키를 이미 가진 사람"의 동선이 한 덩어리가
  된다. 가이드는 확인 버튼 **아래** 구분선 뒤로 내려가되, 거기서 처음으로 **누를 수 있는
  크기**(pill 버튼)가 된다.
- **가이드는 버튼이 아니라 링크다.** 외부 URL로 나가는 이동이라 링크 시맨틱을 유지하고(스크린리더가
  "링크"로 읽는다) 겉모습만 `BUTTON_VARIANT_CLASS.outline` 을 입는다.
- **7단계라는 사실을 나가기 전에 알린다.** 버튼 아래 한 줄이다. 무엇이 기다리는지 모른 채 앱을 떠나지
  않게 한다.
- **주 CTA 바로 아래 같은 pill이 하나 더 서는 위험**은 구분선과 그 문구가 막는다. 두 버튼은
  색(채움 대 테두리)과 크기로도 갈린다.

### 키 표시 토글

인풋 우측에 `Eye`·`EyeOff`(lucide, 배경 없이 단독, `pr-11`)를 둔다. 기본은 가림이고 누르면 보인다.

**키는 손으로 치는 값이 아니라 붙여넣는 긴 문자열이다.** 가려 두면 잘못 붙여넣었는지 확인할 방법이
없고, 실패해도 401 토스트만 뜬 채 원인을 못 본다.

보이는 구간이 생기므로 `autoCapitalize="none" autoCorrect="off" spellCheck={false}` 를 함께 건다.
**모바일 키보드가 첫 글자를 대문자로 바꾸면 조용히 틀린 키가 된다.**

### 안심 문구는 사실만 말한다

2026-08-08 사용자 요청은 "수집하거나 저장하지 않는다"였으나 **"저장하지 않는다"는 사실이 아니다.**
키는 기기
Preferences(iOS `UserDefaults` · 안드로이드 `SharedPreferences`)에 저장된다
(`storage/api-key`, [[ADR-007]]). 그래야 다시 켰을 때 안 넣는다.

사실인 것은 **우리가 수집하지 않는다**이다. 백엔드가 없고([[ADR-003]]) 키는 `x-nxopen-api-key` 헤더로
넥슨에만 나간다(`nexon/http`). 그래서 문구는 **"이 기기에만 저장되고 넥슨 외 어디로도 전송되지
않아요"** 다. 지키지 못할 약속을 하지 않으면서 뜻(안심)은 그대로 전한다.

### 검증 중에는 폼을 유지하고 버튼만 스피너로 (2026-07-16)

키를 제출해도 화면을 옮기지 않고 `ApiKeyForm` 을 그대로 둔다. 정상 경로가 1초 미만이라 "확인 중"
문구가 깜빡이는 것이 거슬렸다. `verifyingApiKey` 동안 `isSubmitting` 으로 두어 입력값과 위치는 그대로 두고 제출 버튼 내용만
스피너로 바꾸고 비활성화한다.

```
버튼 스피너: h-5 w-5 rounded-full border-2 border-bg/30 border-t-bg animate-spin motion-reduce:animate-none
접근성: aria-busy, aria-label="확인 중", 스피너 aria-hidden
```

### 실패는 토스트로 알린다

[[ADR-065]] 결정 1이다. 문구가 사라져도 이 자리엔 폼이 남으므로([[ADR-063]] 원칙 4) 인라인 문구를 두지
않는다. 세 경로 모두 `formatOnboardingError`(`features/onboarding/format.ts`. store가 쓰므로 `app/`
이 아니다)로 **원인별 문구**를 띄운다.

| 경로 | 전에는 |
|---|---|
| `submitApiKey` 실패 | 원인과 무관하게 한 문구였다. 바로 아래에서 원인을 계산해 state에 넣으면서도 토스트는 그 값을 안 썼다 |
| `hydrate` 실패(저장된 키로 재실행했다가 조회 실패) | 토스트가 아예 없어 아무 설명 없이 입력 화면으로 되돌아갔다 |
| `setApiKey`(키 저장) 실패 | `try` 밖이라 미처리 rejection 이었다. 이제 `storageWriteFailed` 로 알린다 |

**액션은 두지 않는다.** 온보딩 중에는 설정 화면이 없고 재시도는 폼에서 한다.

## 캐릭터 선택 단계

`ContentCharacterStep` 이다([[ADR-035]] 결정 13). **본문은 이 파일에 없다.** 설정 하위 화면
(`SettingsCharactersScreen`)과 **같은** `CharacterManageBody` 와 `useCharacterManage` 를 쓰고, 갈리는
것은 머리와 CTA 뿐이다([[ADR-144]] 결정 1). 이 파일에 있는 것은 제목 블록 · ‘계속하기’ · 최소 1개
게이트 셋이다.

### 두 층이다

[[ADR-144]] 결정 2(구현 완료 2026-08-17)다.

| 층 | 내용 | 좌우 슬롯 |
|---|---|---|
| 위 | 계정을 넘는 ‘선택된 캐릭터’ 목록. 순서와 대표가 여기 산다 | 끌기 핸들과 `★ ✕` |
| 아래 | 계정 드롭다운 + 그 계정의 후보 목록 | `＋` |

**두 층은 같은 행 카드를 쓴다.** 갈리는 것은 좌우 슬롯뿐이다.

아래 로딩·실패 규칙은 **아래 층에만** 적용된다. 계정을 바꾸면 아래만 다시 돌고, 위는 로컬 캐시로 그려
네트워크와 무관하다.

- **후보 0건일 때의 ‘계정 다시 선택’ 액션이 없다.** 드롭다운을 되돌리는 것이 그 자리의
  출구다([[ADR-143]] 결정 10).
- **고를 수 있는 계정이 하나도 없으면** 화면 전체가 빈 상태에 키 재입력이다.
- **같은 계정을 5분 안에 다시 열면 조회 자체를 하지 않는다**([[ADR-144]] 결정 6의 계정 전환 TTL).

### ‘계속하기’는 하단에 고정된다

[[ADR-144]] 정정 2(2026-08-18 사용자 지정)다. 설정 하위 화면의 ‘저장’과 **같은 액션 바**다(`bg-bg` +
위쪽 테두리 · 폭을 다 쓰는 버튼 · 안전영역은 바가 먹고, 잰 바 높이만큼 콘텐츠 아래를 비운다).

처음에는 이 단계만 ‘본문 끝에 서는 CTA’로 뒀는데, 본문이 설정과 같은 두 층이라 캐릭터가 많으면 유일한
전진 버튼이 화면 밖에 있게 된다.

그 바를 갖는 것은 화면이 아니라 **단계 셸**(`OnboardingStep`)이고, 그래서 `ContentCharacterStep` 이 그
셸을 직접 두르는 유일한 단계다. 활성 조건이 `useCharacterManage` 안에 있어 스크롤과 바의 조상이 그
훅을 부르는 쪽이어야 한다.

### 후보 목록 로딩

`getCharacterPickerRoster` 를 캐릭터 관리 피커와 공유하므로 같은 규칙을 따른다. 원문은
[content-scheduler.md](./content-scheduler.md) 의 "후보 캐릭터 자격"에 있다. 요약하면 캐시가 있으면
즉시 표시하고, 확인된 캐릭터부터 흘리고([[ADR-149]]), 조회가 끝났는데 목록이 비면 "활성 캐릭터 없음"과
"조회 실패"를 구분해 안내한다.

판정 분기는 `ContentCharacterStep` 안에서 직접 그린다(피커와 같은 우선순위와 마크업이다). 실패도
피커와 같은 공용 `ErrorState` 를 쓰고([[ADR-062]]) 스탈 배너 분기도 같다.

**다른 것은 401 뿐이다.** 온보딩의 `invalidApiKey` 는 **다시 시도** + "API 키를 다시
확인해주세요"이고, 피커는 **액션 없음** + "키 입력 화면으로 이동합니다"다([[ADR-115]] 결정 7,
2026-08-08).

갈리는 근거는 "설정 화면이 있는가"가 **아니다.** 이 화면의 401은 방금 넣은 키에 대한 **폼 자체의
실패**라 재시도가 실제 처방이고, 그래서 이 자리는 무효화 진입점에 **배선하지 않는다.** 피커의 401은
반대로 곧 화면을 키 입력으로 옮기므로 누를 것이 없다.

**스탈 배너는 두 자리가 같다**(401 포함 전부). `formatStaleRosterError` 가 `place` 를 받지 않는
이유다.

**근거가 구조에서 배선으로 내려왔다**([[ADR-116]] 결정 2, 2026-08-08). 전에는 *"무효화 경로가
`completed` 일 때만 성립하므로 온보딩의 401은 애초에 그 경로가 아니다"* 였는데, 가드가 **"키 입력
화면에 있지 않을 때"** 로 넓어져 구조가 더는 막아 주지 않는다. 이 자리의 401을 폼 실패로 남기는 것은
이제 **배선하지 않는다는 선택**이다.

### 429로 이 단계가 잠기던 것이 모달 경로로 풀린다

[[ADR-116]] 결정 1·2(2026-08-08, 이슈 #176)다. 로스터 조회가 429로 실패하면 출구 다섯 방향이 전부
막혀 있었다.

1. `계속하기` 는 고를 캐릭터가 없어 영구 비활성
2. `다시 시도` 는 같은 요청을 다시 쏴 또 429
3. `계정 다시 선택` 은 **확정된 빈 상태 가지에만** 붙어 실패 화면에 도달하지 못함
4. 단계는 라우트가 아니라 상태 switch 라 되돌릴 UI 없음
5. 재시작하면 재개 파생이 **같은 단계로 되돌린다**

온보딩 중에는 설정 화면도 없어 연결 해제조차 못 했다. 이제 그 위에 **닫을 수 없는 안내 모달**이 덮이고
확인을 누르면 키 입력 화면으로 가서 **서비스 단계 키로 다시 넣을 수 있다.**

- **‘계정 다시 선택’을 실패 가지에 넘기는 것은 답이 아니었다.** 계정을 바꿔도 **같은 키라 429는
  그대로**다. 실제로 통하는 처방은 키를 바꾸는 것 하나뿐이다.
- **429 발생 자체는 줄지 않는다**([[ADR-116]] 결정 5). 로스터와 예열의 fan-out 동시성 캡은 이번 범위
  밖이다(아래 [열린 질문](#열린-질문)).

### 최소 1명

[[ADR-086]] 결정 7이다. 0명은 화면을 빈 상태로 만들 뿐 어떤 의도도 표현하지 않는다. 피커도 같은
규칙이다.

## `character/basic` 5분 TTL

[[ADR-113]] 결정 1이다. `character/basic` 호출을 **공유 경로 하나**
(`features/schedule-sync/character-basic-fetch` 의
`fetchCharacterBasicCached(apiKey, accountId, ocid, now)`)로 모으고, "이 ocid의 `basic` 이 5분 안에
캐시됐으면 네트워크를 건너뛰고 캐시 값을 돌려준다"를 그 자리에서 판정한다. TTL 값은 같은 모듈의
`CHARACTER_BASIC_TTL_MS`(`5 * 60 * 1000`) 하나뿐이다.

- **호출부가 전부 이 경로를 통과한다.** 캐릭터 피커 · 동기화 편승 갱신([[ADR-097]] 결정 7) 등이다.
  전부 **완전히 같은 요청**이고 소비하는 필드만 달라, 온보딩 한 바퀴에 같은 캐릭터로 여러 번이
  나가고 있었다. 원형 `fetchCharacterBasic`(`nexon/character`)과 캐시 쓰기를 부르는 제품 코드는 이제
  이 모듈뿐이라, 새 호출부가 원형을 직접 부르면 눈에 띈다.
- **`now` 는 호출부가 넘긴다.** 헬퍼가 시계를 스스로 읽지 않는다. 라운드 하나가 같은 기준 시각을
  공유해야 같은 한 바퀴 안에서 판정이 흔들리지 않고, 오차는 항상 TTL이 **짧아지는** 보수적인
  방향으로만 난다. 파싱 불가와 미래 `cachedAt` 은 만료로 취급하고(손상된 값이나 기기 시계 되감기가
  캐시를 영구히 신선하게 만들면 안 된다) 경계는 배타적이다(정확히 5분이면 만료).
- **실패는 캐시로 폴백하지 않고 그대로 던진다.** 호출부들이 그 예외에 판정을 걸고 있다(400
  `OPENAPI00003` → `characterUnavailable`, 401·429 → 전역 실패). 여기서 삼키면 그 판정이 통째로
  죽는다.
- **호출부를 하나씩 고치지 않는 이유**: 그러면 호출자끼리 서로의 존재를 알아야 하고, 새 호출부가
  생기면 조용히 중복이 되살아난다(실제로 [[ADR-097]] 결정 7이 그렇게 추가됐다). 공유 경로 하나면
  **호출자끼리 서로를 몰라도 접힌다.**
- **5분인 이유**: ① 온보딩 한 바퀴를 여유 있게 덮는다 ② **[[ADR-097]] 동기화 TTL 10분보다 짧아야
  한다.** 같거나 길면 편승 갱신이 경계에서 거의 항상 건너뛰어져 사실상 죽는다. 대가는 5분 안에 피커를
  다시 열면 개명과 레벨업이 그만큼 늦게 반영되는 것이다.
- **절감의 값은 호출 수가 아니다.** 자격 스윕은 실패를 조회 원장에 기록하지 않으므로(의도된 설계,
  [[ADR-086]] 결정 4) 429가 나면 다음 화면이 같은 13일을 처음부터 다시 훑고 그게 또 429를 부른다.
  중복을 접는 값은 **429 확률을 낮춰 원장이 채워질 확률을 올리는 것**이고, 원장이 한 번 차면 그
  캐릭터는 그 뒤로 스윕이 없다(이슈 #158).
- **접은 것은 총 호출 수이지 한순간의 fan-out 폭이 아니다.** 대상 전체를 `Promise.all` 로 **동시에**
  부르고 동시성 캡이 없다. single-flight도 없어 같은 ocid를 두 경로가 **동시에** 부르면 둘 다
  나간다. TTL은 이미 끝난 요청만 접는다. 429가 남으면 다음 후보는 여기다.

## 열린 질문

- **다계정 동시 추적을 아무도 해 본 적이 없다**([[ADR-143]] 미검증, 2026-08-16 신설). 계정이 2개
  이상인 `character/list` 응답은 [[ADR-007]] 시절 한 번 실측됐지만, 그 캐릭터들을 **함께** 추적한 적은
  없다. 특히 계정 공유 진행도 원장(`accountSharedProgress:{accountId}`, [[ADR-030]])이 캐릭터마다 자기
  계정으로 갈리는지는 실제 다계정 키로만 확인된다([[ADR-143]] 결정 6).
- **계정을 처음 열 때의 대기가 견딜 만한지**([[ADR-143]] 결정 5, 2026-08-16 신설). 예열을 ‘열 때’로
  미룬 대가라, 캐릭터가 많은 계정을 드롭다운으로 처음 열면 그 계정 몫의 자격 판정을 기다린다. 두
  번째부터는 조회 원장과 5분 TTL이 받는다. **눈으로만 판정된다.**
- **넥슨이 `character_list: []` 를 내는 조건**([[ADR-127]] 대가, 2026-08-12 신설). 그런 응답을 직접
  받아 본 적이 없다. 테스터 재현 조건에서 역산한 것이라 방어는 하되 조건을 안다고 적지 않는다. 테스터
  키로 `character/list` 를 한 번 호출해 보면 닫힌다.
- **429로 키를 지우고 온보딩으로 내보내는 것이 실사용에서 옳은지**([[ADR-116]] 대가, 2026-08-08
  신설). 셋이 함께 미확인이다.
  1. **실제 429를 한 번도 받아 본 적이 없다.** 자동 테스트는 `rateLimited` 를 주입할 뿐, 실제 429
     응답에서 모달까지 이어지는지는 모른다([[ADR-114]] 가 남긴 같은 항목이 그대로다).
  2. 모달에 닫기가 없고 429 응답에 일·초당 구분이 없어 **몇 초 뒤 풀렸을 실패에도** 키 입력 화면으로
     간다.
  3. 그렇게 지운 키가 **다음 날이면 다시 쓸 수 있는 키**일 수 있다. 일 한도 소진은 무효가 아니라 오늘
     소진된 것이다.
- **무효 키 안내 모달을 실제로 만났을 때의 체감**([[ADR-115]] 결정 10, [[ADR-116]] 이후 **429도 같은
  모달**이라 두 원인 모두에 걸린다). 보스 목록을 보던 중에 무효 키가 감지되면 화면 위에 **닫을 수 없는
  모달**이 덮이고 `확인` 외에는 누를 것이 없다. **탭을 하나 더 요구하는 대가가 실사용에서 옳은지는
  눈으로만 판정된다.** 함께 미확인인 것 둘: 여러 캐릭터에서 동시에 실패해도 모달이 하나만 뜨는지 ·
  재입력 후 재개가 정말 예열 없이 즉시인지. **무효 키 감지부터 키 입력 화면까지는 iOS 시뮬레이터에서
  확인됐다**(2026-08-08. 넥슨에서 키를 실제로 삭제해 재현).
- **동시성 캡을 둘지.** [[ADR-116]] 범위에서 사용자가 명시적으로 기각했다(2026-08-08). 질문이 닫힌
  것이 아니라 **한 번 제기됐다 미뤄진 것**이다. 그래서 429 발생 건수는 그대로다.
- **안 고른 계정의 캐시 엔트리를 정리할지**([[ADR-113]] 결정 2의 대가, 2026-08-08 신설). 엔트리
  (`characterBasicCache:{ocid}`)는 전역 키이고 인덱스만 계정별이라 훑은 모든 계정 몫이 저장소에
  남는다. 지금은 **의도한 성질**로 둔다(그 계정으로 바꾸면 따뜻한 캐시로 재사용, [[ADR-086]] 결정 9).
  계정이 많은 사용자에게 실제로 부담이 되는지 관측된 바 없으므로 관측 전에 정리 정책을 만들지 않는다.
- 캐릭터 관리 피커 개선([[ADR-015]]) 잔여: Nexon `character/look` 이미지 얼굴 크롭 쿼리를 공식
  지원하는지(미지원이면 CSS 근사), 개선을 다른 캐릭터 선택 UI로 확장할지.
