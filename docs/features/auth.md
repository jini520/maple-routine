## 로그인 상태 셋

`AuthStatus` 는 `signedOut` · `verifying` · `signedIn` 이다([[ADR-215]] 결정 2).

**실패가 상태가 아니다.** 검증에 실패해도 서 있는 화면은 로그인 폼 그대로이므로, 실패를 상태로 두면
화면을 고르는 값과 원인을 담는 값이 같은 것을 두 번 말한다. 원인은 `error` 필드 하나가 든다.

**캐릭터라는 낱말이 없다.** 무엇을 고를지는 이 축이 모른다. 그래야 로그인 방식이 바뀔 때 캐릭터
설정이 함께 흔들리지 않는다.

## 키 입력

발급 절차는 **앱 밖 안내 사이트**(`mapleroutine.store/api-key`)가 담당하고 앱은 링크만 준다
([[ADR-110]]). 앱 안 단계별 위저드가 아닌 이유는 둘이다. 스크린샷 7장이 번들에 들어가면 최초 1회 보는
화면 때문에 모든 사용자가 1.2MB 를 받고, 넥슨이 화면을 바꿀 때마다 OTA 배포가 필요하다.

키는 `storage/api-key.ts` 를 거쳐 기기에 저장한다.

- **링크는 둘이다**(2026-08-08, 이슈 #61, 사용자 확정). 1차 경로가 **‘API 키 발급 방법’(가이드)**,
  다른 하나가 **`openapi.nexon.com` 바로 가기**다. 처음 쓰는 사용자를 넥슨 첫 화면에 떨궈 놓지 않는
  것이 1차 경로를 가이드로 두는 이유고, 이미 발급받은 사용자에게 7단계 안내를 거치게 하지 않는 것이
  바로 가기를 남기는 이유다. 가이드 1단계가 `openapi.nexon.com` 링크를 이미 품고 있어 **중복이 아니라
  서로 다른 두 진입점**이다.
- **외부 브라우저로 나갔다 와도 잃는 것이 없다.** 두 링크 모두 시스템 브라우저로 나가지만, 재개
  지점이 저장된 값에서 파생되므로([[ADR-086]] 결정 1) 키를 넣기 전에 나갔다 돌아오면 그대로
  `signedOut` 이다. 입력 중이던 값은 컴포넌트 로컬 상태라 앱이 메모리에서 내려가면 사라지지만, 이
  시점에 사용자가 가진 키는 아직 없다.
- **설정 화면에는 진입점을 두지 않는다**(2026-08-08 사용자 확정). 설정에 API 키 재입력 경로 자체가
  없어 가이드 링크만 놓으면 갈 곳 없는 안내가 된다.


## 개발 단계 키는 문을 못 넘는다

[[ADR-214]](2026-09-04)다. 키를 저장하기 **전에** 그 키가 개발 단계인지 잰다.

```
character/list ×1   검증. 401 · 400 OPENAPI00005 면 무효 키
      ↓ 성공
character/list ×10  프로브(`nexon/key-stage.ts`). 하나라도 429 면 개발 단계
      ↓ 통과
setApiKey
```

`character/list` 인 것은 선택이 아니다. **ocid 없이 API 키만으로 부를 수 있는 엔드포인트가 그것
하나**이고 이 시점에는 ocid 가 없다. 검증용 단건을 먼저 보내는 것은 키 오타처럼 흔한 실패가 10건을
태우지 않게 하기 위해서다.

**판정은 한쪽으로만 확실하다.** 개발 단계 한도가 초당 5건이라 429 를 보면 개발 단계인 것이
확실하지만, 못 봤다고 서비스 단계인 것은 아니다. 그래서 결과 타입에 `service` 가 없다
(`'developmentStage' | 'undetermined'`). 429 가 아닌 실패는 전부 `undetermined` 이고, **차단은
양성 증거를 요구한다.**

막힌 사용자가 보는 것은 **모달 하나**다(`app/auth/DevelopmentStageKeyModal.tsx`). 토스트도
띄우지 않는다. 토스트는 스스로 사라지면서 처방까지 데려가고, 폼과 같은 평면에 놓는 인라인은
지나칠 수 있다.

**닫을 수 있다.** 옆의 `ApiKeyNoticeModal` 이 안 닫히는 것은 뒤 화면이 이미 제 기능을 못 하기
때문인데, 여기는 뒤에 키 입력 폼이 멀쩡히 서 있어 닫는 것이 곧 다시 넣는 것이다. 확인이 저장소를
건드리지도 않는다(받지 않은 키라 지울 것이 없다).

**제목에 개발 단계 를 안 쓴다.** 이 사람은 그 낱말이 무엇인지 모르고 그것을 골랐으므로, 모르는
말을 돌려주면 무엇이 잘못됐는지가 전달되지 않는다. 제목은 `이 키로는 연결할 수 없습니다` 하나이고,
두 단계는 그 아래 **두 줄 표**에서 만난다.

```
넣으신 키                    개발 단계
──────────────────────────────────────
필요한 키                  서비스 단계   ← primary-tint
```

**두 줄이 붙어 있는 것이 요점이다.** 낱말을 모르는 사람에게 필요한 것은 뜻풀이가 아니라 **그
자리에 다른 값이 있었다**는 사실이고, 표는 그것을 한 눈에 준다. 떼어 놓으면 각각이 따로 선
사실이 되어 고를 수 있었던 것이라는 관계가 사라진다.

왜 못 쓰는지도, 한도가 몇 건인지도 안 적는다. 할 일은 다른 키를 받는 것 하나이고 그 사정이 그
일을 바꾸지 않는다.

머리(56px 열쇠 배지 · 제목)와 본문은 **가운데 정렬**이고 표만 좌우로 벌어진다.
`ApiKeyNoticeModal` 과 같은 골격이라 두 모달이 한 앱에서 온 것으로 읽힌다.

**그 골격은 이제 `components/organisms/NoticeModal` 이 갖는다**([[ADR-217]] 결정 3). 두 모달이 같은
틀을 부르므로 값이 갈릴 자리가 없다. 이 파일이 정하는 것은 넣을 것뿐이다. 열쇠 아이콘 · `primary`
톤 · 제목 · 두 줄 표(`content`) · 설명 · `다시 입력하기` · 발급 안내 링크.

배지는 `primary-tint` 바탕에 `primary-ink` 열쇠다. **붉은 원이 아닌 것이 결정이다.** 붉은 원은
실패를 뜻하는데 이 자리는 종류가 다른 것을 넣은 곳이고, 앱의 빨강은 조회 실패와 삭제가 이미 쓰고
있다. 원이 아니라 네모인 것은 아래 표와 모서리를 맞추기 위해서다.

**주 버튼은 `다시 입력하기` 다.** 이 모달은 길을 막고 서 있고 사용자가 바로 하는 일은 폼으로
돌아가는 것이라, 가장 큰 버튼이 앱 밖으로 내보내면 안 된다. 발급 안내는 그 아래 인라인 링크로
내려간다(폼의 `openapi.nexon.com에서 확인` 과 같은 모양). 잃는 것은 없다 — 모달을 닫으면 폼
아래에 같은 안내 버튼이 그대로 있다.

이름에 `자세히` 가 붙은 것은 **이 모달이 어디서 고르는지는 안 알려주기** 때문이다. 그 나머지가
저쪽에 있고 그 사이트는 이미 `단계: 서비스 단계 를 선택합니다` 를 적고 있다(`site/api-key.md`).
주소는 폼과 한 벌을 쓴다(`app/auth/api-key-links.ts`).

상태는 `error` 가 아니라 `developmentStageBlocked` 다. `AuthError` 는 곧 토스트 문구라
(`formatAuthError`) 거기 실으면 모달과 토스트가 같은 말을 두 번 한다.

이 문이 서기 전에는 [[ADR-116]] 의 사슬(429 를 만나는 자리마다 저장된 키를 지운다)이 혼자
`개발 단계 키는 로그인을 통과해 살아남을 수 없다` 를 떠받쳤다. 그 사슬은 **심층 방어로 남는다** —
판정이 안 서는 자리가 있어서다(안드로이드의 동시 5건 천장 · 느린 망 · 넥슨 리미터의 버스트 허용
여부. [[ADR-214]] 대가 1~3).


## API 키 입력 화면

`ApiKeyForm` 이다.

### 갈림길 레이아웃 (2026-08-08, 이슈 #61)

**이 화면에 오는 사람은 둘뿐이다. 키가 있는 사람과 없는 사람.** [[ADR-110]] 이 두 링크를 "중복이 아니라
서로 다른 두 진입점"이라고 적은 것을 **화면 구조로 옮긴다.**

전에는 둘 다 폼 **위** 한 문단 안에 인라인 밑줄 링크로 붙어 있어서, 1차 경로라고 선언한 가이드가
화면에서 가장 작고 흐린 요소(`text-sm text-text-muted` 문장 **안**)였다. 선언과 그림이 어긋나 있었다.

```
제목 블록   h2 text-lg font-semibold text-text  "넥슨 API 키를 입력해주세요"
            p  text-sm text-text-muted          "스케줄러 API를 사용하려면 개인 API 키가 필요해요"
            p  text-xs text-text-muted          "입력한 키는 이 기기에만 저장되고 넥슨 외 어디로도 전송되지 않아요"
입력 블록   label text-sm font-medium + input + 표시 토글
            "openapi.nexon.com에서 확인" + ExternalLink h-3     ← 키가 있는 사람의 동선
확인 버튼   Button primary, w-full
구분선      "아직 API 키가 없나요?"  (좌우 h-px bg-border, 가운데 text-xs text-text-muted)
가이드 블록 BUTTON_VARIANT_CLASS.outline  "API 키 발급 방법 보기" + ExternalLink h-3.5
            p text-xs text-text-muted 중앙  "넥슨 오픈 API에서 키를 받는 7단계 안내"
```

- **제목을 되찾는다.** 진입 화면 중 이 화면에만 제목이 없었다. `CharacterSetupScreen` 은
  제목과 보조문으로 시작한다.
- **폼이 먼저다.** 넥슨 바로 가기가 인풋 바로 아래 붙어 "키를 이미 가진 사람"의 동선이 한 덩어리가
  된다. 가이드는 확인 버튼 **아래** 구분선 뒤로 내려가되, 거기서 처음으로 **누를 수 있는
  크기**(pill 버튼)가 된다.
- **가이드는 버튼이 아니라 링크다.** 외부 URL로 나가는 이동이라 링크 시맨틱을 유지하고(스크린리더가
  "링크"로 읽는다) 겉모습만 `BUTTON_VARIANT_CLASS.outline` 을 입는다.
- **7단계라는 사실을 나가기 전에 알린다.** 버튼 아래 한 줄이다. 무엇이 기다리는지 모른 채 앱을 떠나지
  않게 한다.
- **주 CTA 바로 아래 같은 pill이 하나 더 서는 위험**은 구분선과 그 문구가 막는다. 두 버튼은
  색(채움 대 테두리)과 크기로도 갈린다.

### 키 표시 토글

인풋 우측에 `Eye`·`EyeOff`(lucide, 배경 없이 단독, `pr-11`)를 둔다. 기본은 가림이고 누르면 보인다.

**키는 손으로 치는 값이 아니라 붙여넣는 긴 문자열이다.** 가려 두면 잘못 붙여넣었는지 확인할 방법이
없고, 실패해도 401 토스트만 뜬 채 원인을 못 본다.

보이는 구간이 생기므로 `autoCapitalize="none" autoCorrect="off" spellCheck={false}` 를 함께 건다.
**모바일 키보드가 첫 글자를 대문자로 바꾸면 조용히 틀린 키가 된다.**

### 안심 문구는 사실만 말한다

2026-08-08 사용자 요청은 "수집하거나 저장하지 않는다"였으나 **"저장하지 않는다"는 사실이 아니다.**
키는 기기
Preferences(iOS `UserDefaults` · 안드로이드 `SharedPreferences`)에 저장된다
(`storage/api-key`, [[ADR-007]]). 그래야 다시 켰을 때 안 넣는다.

사실인 것은 **우리가 수집하지 않는다**이다. 백엔드가 없고([[ADR-003]]) 키는 `x-nxopen-api-key` 헤더로
넥슨에만 나간다(`nexon/http`). 그래서 문구는 **"이 기기에만 저장되고 넥슨 외 어디로도 전송되지
않아요"** 다. 지키지 못할 약속을 하지 않으면서 뜻(안심)은 그대로 전한다.

### 검증 중에는 폼을 유지하고 버튼만 스피너로 (2026-07-16)

키를 제출해도 화면을 옮기지 않고 `ApiKeyForm` 을 그대로 둔다. 정상 경로가 1초 미만이라 "확인 중"
문구가 깜빡이는 것이 거슬렸다. `verifying` 동안 `isSubmitting` 으로 두어 입력값과 위치는 그대로 두고 제출 버튼 내용만
스피너로 바꾸고 비활성화한다.

```
버튼 스피너: h-5 w-5 rounded-full border-2 border-bg/30 border-t-bg animate-spin motion-reduce:animate-none
접근성: aria-busy, aria-label="확인 중", 스피너 aria-hidden
```

### 실패는 토스트로 알린다

[[ADR-065]] 결정 1이다. 문구가 사라져도 이 자리엔 폼이 남으므로([[ADR-063]] 원칙 4) 인라인 문구를 두지
않는다. 세 경로 모두 `formatAuthError`(`features/auth/format.ts`. store가 쓰므로 `app/`
이 아니다)로 **원인별 문구**를 띄운다.

| 경로 | 전에는 |
|---|---|
| `signIn` 실패 | 원인과 무관하게 한 문구였다. 바로 아래에서 원인을 계산해 state에 넣으면서도 토스트는 그 값을 안 썼다 |
| `hydrate` 실패(저장된 키로 재실행했다가 조회 실패) | 토스트가 아예 없어 아무 설명 없이 입력 화면으로 되돌아갔다 |
| `setApiKey`(키 저장) 실패 | `try` 밖이라 미처리 rejection 이었다. 이제 `storageWriteFailed` 로 알린다 |

**액션은 두지 않는다.** 이 화면에서는 설정 화면으로 갈 길이 없고 재시도는 폼에서 한다.


## 키 재입력 경로

[[ADR-115]] 결정 4·5(2026-08-08, 이슈 #157)다. API 키가 무효화되면 저장된 **`apiKey` 하나만** 지워지고
사용자는 로그인 화면으로 온다.

**그래서 여기서 키를 다시 넣으면 [단계 파생 표](./app-entry.md#단계-파생)가 가리키는 자리(대개
`ready`)로 곧바로 간다.** 트래킹 모드와 추적 캐릭터를 **다시 묻지 않는다.** 무효화된 것은 키
하나뿐이라 나머지 저장값은 여전히 사실이다.

부팅과 이 경로가 같은 함수(`deriveEntryStage`) 하나를 공유한다. 그 판정은 인증이 아니라
[app-entry.md](./app-entry.md) 가 소유하고, 로그인은 검증 응답을 넘겨 주기만 한다
([[ADR-215]] 결정 2 의 「방향은 한쪽이다」).

전에는 키 검증 성공이 무조건 계정 선택으로 가고 저장된 계정 id를 리셋해, 키 하나 때문에 계정
선택부터 캐릭터 선택까지 전부를 다시 시켰다. 재개 파생이 부팅 경로에만 있었기 때문이다.

### 다른 계정의 키를 넣었을 때의 가드

새로 넣은 키가 **다른 넥슨 계정의 키**일 수 있다. 그러면 남의 계정 키로 이전 계정 ocid 추적 목록을
그대로 쓰게 된다.

**RN은 저장된 추적 ocid로 대조한다**([[ADR-143]] 결정 9). 키 검증 때 이미 받는 `character/list`
응답에 저장된 추적 ocid가 **하나라도** 있으면 재개하고, **하나도 없으면** 캐릭터 설정 화면으로 보낸다.
대조하는 코드는 `features/app-entry/store.ts` 의 `resolveAfterSignIn` 이다.
일부만 없는 경우(캐릭터 삭제·이전)는 재개한다. 없는 ocid는 피커와 동기화가 각자 이미 다룬다.

- **가드는 지킬 목록이 있을 때만 동작한다.** 저장된 목록이 `null` 이나 `[]` 면 대조하지 않고 파생 표
  그대로 간다. 안 그러면 **처음 키를 넣는 신규 사용자**가 "목록이 비었으니 하나도 없다"로 걸려 스케줄
  관리 방법 단계를 건너뛴다. 이 가드가 막는 것은 ‘남의 계정 키로 이전 목록을 그대로 쓰는 것’이라,
  지킬 목록이 없으면 판정 대상 자체가 없다.
- 대조는 응답의 **전 계정 캐릭터 ocid 집합**으로 한다. 계정을 넘어 고르는 것이 본론이라 계정별로
  나눠 볼 이유가 없다. **추가 네트워크 호출은 없고** 추적 목록만 로컬에서 한 번 더 읽는다.

### 이 화면으로 보내는 원인은 둘이다

키 무효화(400 `OPENAPI00005` · 401/403)와 **호출 한도 초과(429)**([[ADR-116]] 결정 1, 2026-08-08)다.
둘은 **같은 사슬에 문구만 다르고**, 확인을 누르면 똑같이 `apiKey` 만 지워진 채 이 화면으로 온다.
그래서 재개 규칙도 그대로 적용된다.

**무효화와 한도 초과 자체**(감지 지점 · 모달 문구 · 확인 후 이동 · 저장소에서 지우는 범위)는 여기가
아니라 [../foundation/error-resilience.md](../foundation/error-resilience.md) 의 401/403·429 항목이
원문을 갖는다. 이 절은 **키를 다시 받은 뒤**만 다룬다.


## 열린 질문

- **429로 키를 지우고 로그인 화면으로 내보내는 것이 실사용에서 옳은지**([[ADR-116]] 대가, 2026-08-08
  신설). 셋이 함께 미확인이다.
  1. **실제 429를 한 번도 받아 본 적이 없다.** 자동 테스트는 `rateLimited` 를 주입할 뿐, 실제 429
     응답에서 모달까지 이어지는지는 모른다([[ADR-114]] 가 남긴 같은 항목이 그대로다).
  2. 모달에 닫기가 없고 429 응답에 일·초당 구분이 없어 **몇 초 뒤 풀렸을 실패에도** 키 입력 화면으로
     간다.
  3. 그렇게 지운 키가 **다음 날이면 다시 쓸 수 있는 키**일 수 있다. 일 한도 소진은 무효가 아니라 오늘
     소진된 것이다.
- **무효 키 안내 모달을 실제로 만났을 때의 체감**([[ADR-115]] 결정 10, [[ADR-116]] 이후 **429도 같은
  모달**이라 두 원인 모두에 걸린다). 보스 목록을 보던 중에 무효 키가 감지되면 화면 위에 **닫을 수 없는
  모달**이 덮이고 `확인` 외에는 누를 것이 없다. **탭을 하나 더 요구하는 대가가 실사용에서 옳은지는
  눈으로만 판정된다.** 함께 미확인인 것 둘: 여러 캐릭터에서 동시에 실패해도 모달이 하나만 뜨는지 ·
  재입력 후 재개가 정말 예열 없이 즉시인지. **무효 키 감지부터 키 입력 화면까지는 iOS 시뮬레이터에서
  확인됐다**(2026-08-08. 넥슨에서 키를 실제로 삭제해 재현).
- **동시성 캡을 둘지.** [[ADR-116]] 범위에서 사용자가 명시적으로 기각했다(2026-08-08). 질문이 닫힌
  것이 아니라 **한 번 제기됐다 미뤄진 것**이다. 그래서 429 발생 건수는 그대로다.
