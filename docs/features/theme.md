# 테마 시스템 (Theme)

> **범위**: 캐릭터 대표 컬러 기반 다중 테마의 시맨틱 토큰 스키마·토큰 파생 규칙·테마별 컬러 값·배경 이미지·런타임 전환·시스템 다크 모드 연동. 기본 팔레트·시맨틱 색 체계는 [../foundation/design-system.md](../foundation/design-system.md).
> **관련 소스**: `features/theme/`(Zustand store) · `storage/theme.ts` · `src/theme/`(`ThemeProvider` · `theme-vars.ts`(NativeWind `vars()`) · `context.ts` · `MediaScope.tsx` · `screen-backdrop-policy.ts`) · `global.css` + `tailwind.config.js` · `src/data/job-themes.json` · `lib/theme-derive.ts` · `lib/theme-backgrounds.ts` · `components/templates/ThemeBackdrop/` · `src/assets/themes/` · `AppShell`(`restoreFromStorage`).
> **관련 ADR**: [[ADR-009]] [[ADR-064]] [[ADR-088]] [[ADR-089]] [[ADR-105]] ADR-106 [[ADR-108]] [[ADR-109]] [[ADR-006]] [[ADR-104]] ADR-122. **관련 문서**: [../foundation/design-system.md](../foundation/design-system.md), [settings.md](./settings.md).

## 정책
테마마다 **34개 시맨틱 토큰**을 값으로 갖는다([[ADR-064]], 17토큰에서 확장). 현재 등록: **"머쉬맘"(라이트, 기본)·"혼테일"(다크, 시스템 다크 기본)·"레테"(다크)·"렌"(라이트)·"엔젤릭버스터"(라이트)·"검은마법사"(다크)**. 목표는 캐릭터 대표 컬러로 **수십 개**까지 늘리는 것이고, 스키마·파생·등록 방식이 모두 그 전제로 설계돼 있다.

- **토큰은 `theme-vars.ts` 가 «이름 → 값» 맵으로 내고 NativeWind `vars()` 가 렌더 트리에 내린다.** `className`(`bg-primary`·`text-text-muted` …)이 `var(--color-*)` 로 그것을 읽으므로, 컴포넌트 코드는 그대로 두고 **`ThemeProvider` 가 내리는 맵만 바꾸면** 전환된다(웹은 같은 값을 `<style>` 문자열로 굳혀 `:root[data-theme]` 에 붙였다 — 값이 객체로 이미 있어 RN 은 문자열이 될 필요가 없다).
- 선택 테마는 Zustand(`features/theme/store.ts`) + `storage/theme.ts`(Preferences 어댑터) 영속화, `AppShell` `restoreFromStorage` 흐름에서 앱 시작 시 hydration.
- **시스템 다크 모드 연동**: `restoreFromStorage()` 가 저장된 테마가 없을 때 OS 설정을 확인해 라이트="머쉬맘"/다크="혼테일"을 기본값으로 씀(앱 실행 시 1회 판정, 실행 중 OS 변경은 재시작 전까지 미반영). 사용자가 설정에서 한 번이라도 명시 선택하면 그 값이 저장돼 이후 시스템과 무관. **"OS가 지금 무엇인가"는 `ColorSchemePort` 가 답한다**([[ADR-128]]) — 묻는 법이 플랫폼마다 달라서다(웹뷰=위 미디어 쿼리 / RN=`Appearance.getColorScheme()`). 어느 쪽이든 **판정을 못 하면 라이트로 폴백한다**(웹뷰는 `matchMedia` 부재, RN 은 `null` 반환) — 모르는 것을 다크로 읽으면 저장된 테마가 없는 첫 실행이 통째로 다크로 열린다. 구독 API 는 두지 않는다(실행 중 변경 미반영이 정책이라 부를 곳이 없다).
- **같은 토큰이 모드에 따라 반대 역할을 하는 자리**(스크림 위 패널 테두리)는 **파생 토큰으로 푼다** — RN 에는 선택자가 없어 `--color-panel-border` 를 `mode` 에서 파생시킨다. 웹은 같은 자리를 `data-mode` CSS 속성으로 풀었다(🗑 ADR-123·⛔ ADR-122). 어느 쪽이든 **분기 재료는 `mode` 이고 테마 이름이 아니다** — 이름으로 분기하면 [[ADR-064]] 결정 8이 폐기한 `DARK_THEMES` 수동 목록이 되살아난다.
- **OS 색 구성표를 묻는 일은 `ColorSchemePort` 가 맡는다**([[ADR-128]] 결정 4) — 상태 바 같은 시스템 표면을 칠하는 것도 포트 뒤다(`ThemeAppearancePort`). 미디어 스코프는 `theme/MediaScope.tsx` 컴포넌트 하나이고(상속·재선언 성질이 CSS 변수와 같다), 배경 이미지는 URL 이 아니라 `<Image>` 로 그린다(아래 「배경 이미지」).
- 설정 화면에선 등록된 테마 중 하나를 고른다 — 목록은 카테고리 섹션 + 프리뷰 타일이고 위에 라이트·다크 필터가 붙는다(아래 「카테고리와 선택 목록」, UI 상세는 [settings.md](./settings.md)). 직업 기반 자동 매핑은 미정이라 범위 밖.
- 값 소스: `src/data/job-themes.json`([[ADR-006]] — AI가 임의로 채우지 않고 사용자 확인 후 반영).

## 이름 규칙
| 접두/접미 | 뜻 | 예 |
|---|---|---|
| `X` | 채움 배경 | `bg-primary` 버튼 |
| `on-X` | **X 채움 위**의 전경(텍스트·아이콘) | `bg-primary text-on-primary` |
| `X-tint` | X 계열 **옅은 배경** | `bg-primary-tint` 배지 |
| `X-ink` | X 계열 **텍스트/아이콘** | `text-primary-ink` 링크 |

`on-X` 와 `X-ink` 를 헷갈리지 말 것 — 채움 위에 얹는 전경이면 `on-X`, 표면/틴트 위에 놓이는 X색 글자면 `X-ink` 다.

## 38토큰

**Accent** — X ∈ `primary`·`secondary`·`third`·`error` 각각 `X` / `on-X` / `X-tint` / `X-ink`, 추가로 `primary-hover`.

**시맨틱 색은 브랜드 시드와 무관하게 휴가 고정된다** — `error`(휴 27)·`info`(휴 235)에 이어 [[ADR-087]]이 `rise`(휴 26, 값 상승)·`fall`(휴 262, 값 하락) 2쌍을 더했다. 시드에서 파생하면 테마마다 뜻이 달라지므로 **명도·채도만 `mode` 램프로 가르고 휴는 고정**하며, 틴트는 그 색을 `surface` 에 15% 섞는다. `rise`/`fall` 은 accent 가 아니라 `info` 와 같은 **틴트+잉크 2토큰 쌍**이다(채움·`on-X` 가 없다 — 배경으로 깔 일이 없다).

**고정이라서 시드 쪽에 제약이 걸린다 — 새 테마의 `primary` 는 휴 26~27 을 피한다**([[ADR-089]] 결정 1). 그 자리에 두면 브랜드 채움과 실패 토스트·상승 칩이 같은 색이 된다. 검은마법사가 정확히 이 문제였고(레퍼런스의 진홍이 휴 23.8), 고정 휴를 옮기는 대신 **시드를 옮겼다**(맵의 카민 휴 10.6 → 16° 확보). 고정을 옮기는 것은 그 고정의 존재 이유를 지우는 것이라 답이 아니다. 붉은 계열 캐릭터를 담을 땐 인접 휴(카민·마젠타 쪽)에서 잡는다.

## 값 파생
**사람이 정하는 값은 4개**다 — `primary`·`secondary`·`third`(캐릭터 일러스트에서 추출) + `mode`. 나머지 30개는 생성 도구가 파생한다([[ADR-064]] 결정 9). 34개를 손으로 채우면 테마를 수십 개로 늘릴 수 없다.

- **중립(`bg`·`surface`·`surface-2`·`border`·`border-strong`·`text`·`text-muted`·`text-disabled`)**:
  명도·채도는 `mode` 별 램프 고정값이고 **색상(H)은 `primary` 를 따라간다** — 무채색 대신 테마 고유
  톤을 갖게 하려는 것이다.

  **붉은 시드(휴 0~30) 테마는 중립이 갈색이 된다.** 규칙의 정상 출력이지 값 실수가 아니다 — 그 휴를
  채도 0.02~0.03 까지 낮추면 나오는 색이 정확히 갈색·토프다. 검은마법사가 그랬고(카민 휴 10.6 →
  `#654F51`·`#826F71`·`#B69DA0`), **그 테마만 중립 휴를 340(자두)으로 덮어** 풀었다([[ADR-105]]
  결정 1). 채도를 죽이는 쪽(×0.35)은 갈색은 없애지만 램프가 색조를 주는 존재 이유까지 없앤다.

  **덮을 땐 램프의 명도·채도를 그대로 쓰고 휴만 바꾼다** — 톤 계단이 다른 테마와 같은 자리에 남는다.
  같은 램프를 쓰는 `media-*` 4개·`scrim`·`shadow-color` 도 함께 덮어야 한 테마가 두 색조로 갈리지
  않는다. 틴트·`track` 은 표면에서 파생되므로 따라 움직인다(손대지 않는다). 생성 도구에 중립 휴
  인자를 뚫지 않은 것은 지금 필요한 게 **한 테마의 override** 뿐이기 때문이다 — 같은 요구가 또 나오면
  그때 시드에 `neutralHue` 를 붙인다.
- **`on-X`**: X의 **색상(H)을 물려받은** 아이보리 또는 짙은 색. 순수 흑/백은 쓰지 않는다 — 배경색마다 어울리는 전경색이 따로 있다. 색 있는 채움 위에는 **아이보리가 기본**이고(주황 위 `#FFEEE2`, 파스텔 핑크 위 `#FFECF6`), 짙은 전경으로 넘어가는 것은 **아이보리가 글자로서 사라질 때뿐**이다. 판정은 잉크와 **같은 가시성 하한(2:1)** 으로 한다 — "이 색이 보이는가"라는 같은 질문이라 같은 선을 쓴다. 채도는 원 색상보다 크게 낮춘다(전경은 글자라 색이 튀면 읽기를 방해한다).

  | 채움 | 아이보리 대비 | 결과 |
  |---|---|---|
  | 엔젤릭 파스텔 핑크 `#FF80CC` | 2.02 | 아이보리 |
  | 머쉬맘 주황 `#F58B0F` | 2.16 | 아이보리 |
  | 레테 베이지 `#D1C093` | 1.61 | 짙은 전경 |
  | 머쉬맘 노랑 `#F7D00D` | 1.34 | 짙은 전경 |
  | 렌 창백한 하늘 `#C9EEF2` | 1.11 | 짙은 전경 |

  밝기(`L`)로 경계를 잡던 방식은 폐기했다 — 채움 밝기는 아이보리가 읽히는지의 **대리 지표**일 뿐이라 같은 밝기라도 색상에 따라 갈리는 걸 못 본다. 실제로 엔젤릭 파스텔 핑크(`L 0.766`)가 경계 `0.75` 를 아슬하게 넘겨 짙은 전경이 됐고 그 그림이 어울리지 않았다(2026-07-30).

  이 토큰은 **색감이 정하고 대비는 참고만 한다**(아래 판단 순서). 경계를 대비 수치가 아니라 밝기로 잡는 것이 요점이다 — 대비선으로 잡으면 어느 선을 아슬하게 넘느냐로 그림이 튄다. 대비를 맞추려고 명도를 더 밀지도 않는다. 밝은 쪽에서 끝까지 밀어봐야 대비는 거의 안 오르고(2.38→2.45) 색조만 씻겨 흰색이 된다.
- **`X-tint`**: `color-mix(in oklab, var(--color-X) 15%, var(--color-surface))`. 테마당 손튜닝 값이 늘지 않는다. 다른 농도가 필요한 테마만 명시값으로 덮는다.

  **덮어야 하는 경우 — 시드와 표면의 색상이 멀 때.** 15% 규칙은 시드 색이 표면 색조와 가깝다는
  조건에서 잘 듣는다. 혼테일의 갈색 표면(`#241110`)에 얼음 `#6BB4E8` 을 15% 섞으면 두 채도가
  서로 상쇄돼 **`#31272B`** — 바꾸기 전 회색 틴트와 구분되지 않는 무채색이 나온다. 농도만 올리면
  (25%·35%) 회보라를 거쳐 그냥 밝아질 뿐이라, 이 테마의 `secondaryTint` 만 **차가운 베이스에
  얼음을 20% 섞은 `#203343`** 으로 덮었다([[ADR-088]] 결정 2). 규칙 자체는 그대로다.

  검은마법사가 **같은 자리에서 같은 처방**을 받았고([[ADR-089]] 결정 2), `secondary` 를 골드로
  바꾼 뒤에도 **색만 바뀌어 같은 실패가 재발했다**([[ADR-105]] 결정 2) — 자주 표면(`#1C1319`,
  휴 339)에 골드(`#E7B758`, 휴 82)를 15% 섞으면 `#362824` 로 휴가 **46° 끌려간** 흙색이 된다.
  골드 휴에서 직접 잡은 `#3B2B07`(휴 이탈 1°)로 덮는다. **시드가 바뀌면 덮개 값도 다시 잡아야
  한다** — 덮개는 그 시드와 그 표면의 함수다.

  **진단은 대비가 아니라 색조로 한다.** 두 실패 모두 대비비로는 걸리지 않는다 — `#30252F` 와
  `surface2` 의 대비는 1.04:1 이라 "구분된다"고 읽히지만 실제로는 안 보인다. 같은 명도대에 같은
  색조라서인데, 대비비는 명도 차이만 재므로 이 실패를 원리적으로 못 잡는다. **틴트가 accent 의
  휴를 실제로 띠는지**(이탈 각도)를 보라. 다만 이걸 전역 임계로 세우지는 않았다 — 같은 척도로
  레테 `secondary` 가 115°, 엔젤릭버스터가 45° 이고, 둘 다 시드 채도가 낮아(C 0.06) 남는 채도가
  0.008 수준이라 휴 자체가 잡음인 경우다. 덮는 자리는 테마별 값 결정으로 남는다.
- **`X-ink`**: **accent 원색을 그대로 쓴다.** AA 를 겨냥하지 않는다 — 그렇게 했더니 머쉬맘 브랜드 주황(`#F58B0F`)이 짙은 갈색(`#A15800`)으로 눌려 탭·배지·링크 53곳이 통째로 바뀌었다. 색상(H)을 유지한 채 명도만 조정하는 보정은 **아예 안 보이는 색**(가시성 하한 2:1 미만)에만 걸린다. 이 토큰을 만든 이유였던 렌의 창백한 하늘색(`#C9EEF2`, 1.24:1)이 딱 그 경우다.
- **`track`**: `surface-2` 를 그대로 쓴다. 대비를 맞추려고 명도를 벌리지 않는다 — 특정 테마에서 진행률이 안 읽히면 그 테마만 `track` 을 덮는다.
- **`scrim`·`shadow-color`**: `mode` 와 `bg` 색조에서 파생.
- **`media-*`**: 테마 색조를 띤 어두운 배색으로 파생(일러스트 페이드·text-shadow가 어두운 배경 전제).

### 미디어 스코프
일러스트 카드 안은 배경이 `surface` 가 아니라 `media-surface` 라서 **accent 토큰의 기준이 바뀐다**. `X-tint`·`X-ink` 를 그대로 쓰면 대비가 어긋난다 — [[ADR-021]] 정정에 기록된 미해결 AA 미달(카드 안 점수 배지 `bg-third/20 text-third`, 레테 **3.88:1**)이 정확히 이 문제다.

카드 루트에 `.media-scope` 를 두고 그 안에서 기준 토큰을 다시 묶는다.

```css
.media-scope {
  --color-surface: var(--color-media-surface);
  --color-surface-2: /* 카드 안 한 단계 위 표면 — 진행 pill·파티 배지 */;
  --color-track: /* 카드 안 진행률 트랙 = surface-2 */;
  --color-border:  var(--color-media-border);
  --color-text:    var(--color-media-ink);
  --color-text-muted: var(--color-media-ink-muted);
}
```

**카드 위에 직접 놓이는 것만 다시 묶는다.** accent 틴트·잉크(`*-tint`·`*-ink`)는 건드리지 않는다 — **틴트 칩은 자기 배경을 갖고 있어서** 뒤의 카드 색과 무관하고, 카드 기준으로 다시 계산하면 옅은 칩이 어두운 칩으로 바뀌어 카드에 묻힌다(머쉬맘 완료 배지가 `#FCF6DD` 옅은 크림에서 `#382C14` 어두운 올리브가 됐던 문제, 2026-07-30). 어두운 카드 위의 옅은 칩은 오히려 잘 보인다.

**예외 하나 — 완료 배지(`secondary-tint`·`secondary-ink`)는 모드별로 값을 준다.** 카드 안에서 이 두 토큰을 쓰는 곳이 완료 배지뿐이라(토스트 성공 톤은 스코프 밖) 스코프에서 갈라도 다른 자리를 건드리지 않는다.

| 모드 | 완료 배지 | 이유 |
|---|---|---|
| 라이트 | 페이지 틴트 그대로 (`#FCF6DD`) | 어두운 카드 위 옅은 칩이 잘 보인다 |
| 다크 | 진한 채움 (`secondary` + `on-secondary`) | 옅은 틴트가 카드 안 "시작 안함" 배지(`surface-2`)와 구분이 안 된다 |

**카드 안에서 쓰는 토큰을 하나라도 빠뜨리면 페이지 값이 그대로 내려온다.** 실제로 `surface-2`·`track` 을 빠뜨려 어두운 카드 위에 페이지의 밝은 크림색 pill 이 얹혔다("시작 안함" 배지, 2026-07-30). 회귀 테스트가 스코프 재선언 누락과 밝기 이탈을 함께 잡는다.

커스텀 프로퍼티는 **선언된 요소에서** `var()` 가 해석되므로 스코프 안에서 다시 선언해야 새 기준이 반영된다(`:root` 선언을 상속만 받으면 `surface` 기준 값이 그대로 내려온다). 생성 도구가 테마마다 accent 값을 **두 벌**(일반 / 미디어) 계산하므로 사람이 채우는 값은 늘지 않는다.

이 스코프 덕에 카드 안 컴포넌트는 앱 전역과 **똑같은 레시피**(`bg-primary-tint text-primary-ink`)를 쓰면서 자동으로 어두운 기준을 따른다.

**런타임이 아니라 생성 도구로 한다** — 색 값은 도메인 데이터라 [[ADR-006]] 상 사용자 확인이 필요한데, 런타임 계산은 그 확인 절차를 없앤다. 시드를 넣으면 38토큰 + 대비 계측 리포트가 나오고, 사람이 확인해 `job-themes.json` 에 커밋한다.

> ⚠️ **`npm run theme:gen` 은 없어졌다**([[ADR-157]]) — 그 CLI 는 `vite-node` 위에 서 있었고,
> vitest 를 걷으면서 vite 계열 의존을 통째로 지웠다. **파생 규칙 자체는 그대로 `src/lib/theme-derive.ts`
> 에 있고 테스트가 지킨다** — 없어진 것은 그것을 부르던 껍데기뿐이다. 값을 새로 뽑는 방법은
> 다시 정한다(사용자 결정, 2026-08-21).

터미널에 색 견본·대비 계측·붙여넣을 JSON 블록·미디어 스코프 파생값이 함께 나온다. 대비 때문에 실패로 끝나지 않는다. 파생 규칙 본체는 `lib/theme-derive.ts`(색 공간·대비 프리미티브는 `lib/color.ts`)에 있고 스크립트는 껍데기다 — 회귀 테스트가 같은 함수를 재사용하므로 도구와 테스트가 갈라지지 않는다.

## 판단 순서 — 색감이 먼저, 대비는 참고
**전체 색감과 캐릭터의 컬러 컨셉이 최우선이고, 대비비는 그다음에 참고한다**([[ADR-064]] 판단 순서, 2026-07-30 사용자 결정).

- **파생은 색 관계로 정한다** — 색상(H) 물려받기, 밝기 구간, 표면 톤 따르기. 대비 수치가 색을 정하지 않는다.
- **대비는 재서 보여준다** — `measureThemeContrast` 가 수치와 기준선 아래 목록을 낸다. 통과/실패를 매기지 않고, 생성 도구도 대비 때문에 실패로 끝나지 않는다. 받아들일지는 수치와 실제 그림을 함께 보고 사람이 정한다.
- **다만 명도를 맞춰 만드는 토큰은 예외다** — `text`·`text-muted`·`*-ink` 는 여전히 AA를 겨냥해 만든다. 그 토큰들의 존재 이유가 "이 색을 글자로 쓸 수 있게 만든 값"이기 때문이다. 색상(H)은 그대로 두고 명도만 최소한으로 움직이므로 컬러 컨셉도 상하지 않는다. 반면 `on-*`·`track` 은 색감이 정하고 대비는 참고만 한다.

**특정 테마의 값을 바꾸고 싶으면 `overrides` 로 그 토큰을 덮는다.** 면제(waiver) 같은 별도 장치는 없다 — 통과/실패가 없으므로 면제할 것도 없다. 미달값이 조용히 묻히지 않게 하는 것은 **리포트가 항상 수치를 낸다**는 사실이 맡는다([[ADR-021]] 의 3.88:1 이 코드 어디에도 표시 없이 방치됐던 전례를 반복하지 않는다).

## 배경 이미지 (선택)
테마는 색 38토큰 외에 **배경 이미지**를 가질 수 있다([[ADR-088]]).

**지금 값을 가진 테마는 혼테일·검은마법사 둘이다**([[ADR-108]]·[[ADR-109]], 2026-08-07). ADR-106
으로 뗐던 둘이 새 그림으로 다시 채워졌고, "새 그림은 JSON 블록 하나로 다시 붙는다"는 그 전제가 두 번
확인됐다(제품 코드·타입·CSS 변경 0). 배경 없는 나머지 네 테마는 CSS 자체가 나가지 않아 그림이 한
픽셀도 안 바뀐다.

**둘 다 `size: cover` 다 — 늘리지 않는다.** 그림의 구성 종류는 `size` 를 가르지 않고, **크롭이
얼마나 아픈지**와 `position` 을 어떻게 고르는지를 가른다([[ADR-109]] 결정 1·2).

| 구성 | 예 | 폰에서 가로 노출 | 잘려 나가는 것 |
|---|---|---|---|
| 하단 앵커 **장면** | 검은마법사(종횡비 2.475) | 19% | 양쪽 사슬·블레이드 |
| **프레임/비네트** | 혼테일(1.782, 고드름이 네 변을 두름) | 26% | **좌우 고드름 기둥** |

**프레임 쪽 크롭이 더 아프다** — 장면은 중심부가 남으면 인상이 얼마간 살지만, 프레임은 양 끝이
정의상 서로 반대편이라 좁은 슬라이스 안에 둘 다 담을 방법이 **원리적으로** 없다.

`auto 100%` 와 `cover` 는 세로로 긴 화면에서 결과가 같지만 **뜻이 다르다**: 화면이 그림보다 가로로
길어지면 `cover` 는 가로를 채우려 더 확대하고, `auto 100%` 는 세로만 채운 채 좌우에 `bg` 를 남긴다.
지금은 `cover` 로 통일했고, 태블릿 가로처럼 넓은 화면에서 프레임을 남기고 싶어지면 그때 갈린다.

`dim` 은 그림마다 다시 잡는다(옛 혼테일 0.82 · 옛 검은마법사 0.78 → 지금 **혼테일 0.80 · 검은마법사
0.55**). 옛 값과 비슷해 보여도 **물려받은 값이 아니라 새로 잡은 값**이다 — 그림이 다르면 `dim` 도
`position` 도 다시 재야 한다.

혼테일이 더 높은 이유는 **상단 고드름이 헤더 텍스트와 겹치기 때문**이다(제목·"캐릭터 관리"가 놓이는
자리에 밝은 파란 얼음이 온다). 검은마법사는 내용이 아래쪽에 모여 헤더와 안 겹친다. 둘 다 알파를 크게
써서(투명 50% / 36%) `dim` 이 실제로 누르는 면적은 옛 불투명 그림보다 작다.

> **RN 에서는 `dim` 의 뜻 자체가 다르다**([[ADR-133]]).
>
> 웹은 헤더가 자기 자리에 그림 조각을 따로 그리지만([[ADR-088]] 결정 5-1), RN 은 **벽지 한 장만**
> 그리고 헤더는 아무것도 안 칠한다 — [[ADR-131]] 로 고정 영역이 사라져 조각이 서 있던 전제가
> 없어졌기 때문이다. 그래서 제목·필터가 그림 위에 그대로 앉는다.
>
> 더 중요한 차이는 **바탕**이다. RN 은 그림 **뒤에 테마 `bg` 를 깔고**, 덮는 색도 검정이 아니라
> **같은 `bg` 를 알파로** 쓴다. 그림이 알파를 크게 쓰는데(투명 50% / 36%) 그 뒤가 비어 있으면
> «어둡게» 를 `dim` 혼자 지게 되고, 검정으로 덮으면 어느 테마든 같은 회색으로 수렴한다. 바탕이
> 있으면 `dim` 은 «검게 덮는 양» 이 아니라 **«그림을 바탕색 쪽으로 당기는 양»** 이다 — 올려도
> 그 테마의 색조가 남는다.
>
> 그래서 RN 값은 웹에서 물려받을 수 없다. 화면에서 다시 골랐고(**혼테일 0.80 · 검은마법사 0.55**),
> 혼테일은 숫자가 같지만 뜻이 다른 값이다.

```jsonc
"background": {
  "image": "blackmage-background",  // src/assets/themes/<slug>.webp — 슬러그만 적는다
  "size": "cover",                  // background-size
  "position": "25% bottom",         // background-position
  "dim": 0.65,                      // 이미지 위에 덮는 검정 불투명도 (0~1)
  "fadeTop": "0px"                  // 위쪽에서 --color-bg 로 페이드되는 높이 (웹은 헤더가 그림을 이어 그려서, RN 은 벽지 한 장이라 이음매 자체가 없어서 0)
}
```

- **그림을 고치는 게 아니라 값을 고친다.** "더 어둡게"는 `dim`, "아래쪽 수정이 보이게"는
  `position`, "확대"는 `size` 다. 코드를 건드릴 일이 없어야 다른 테마에도 값 한 블록으로 붙는다.
- **하늘(윗부분)은 알파로 비워 둘 것**([[ADR-108]] 결정 2). 불투명한 그림을 화면 일부에만 깔면
  그림 윗변과 `bg` 사이에 **가로 띠**가 생기는데, `fadeTop` 은 이걸 못 고친다 — 그 값은 **뷰포트
  상단**을 페이드하는 것이지 그림의 윗변을 다루지 않는다. 하늘이 투명이면 `bg` 가 그대로 비쳐
  이음매가 구조적으로 없다. **webp 변환에서 알파를 지킬 것** — `convert('RGB')` 하면 하늘이 검게
  채워져 이음매가 되살아난다.
- **원본 `.png` 를 `src/assets/themes/` 에 남기지 말 것**([[ADR-108]] 결정 3). glob 이
  `*.{webp,jpg,png}` 라 같은 이름의 `.png` 와 `.webp` 가 **같은 슬러그로 충돌**해 한쪽이 조용히
  다른 쪽을 덮고, 안 쓰는 원본까지 번들에 실린다.
- **`cover` 는 가로가 긴 그림에서 대부분을 잘라낸다.** 세로로 긴 폰 뷰포트(종횡비 약 0.46)에
  종횡비 2.475 짜리 그림을 `cover` 로 깔면 **가로가 19%만 보인다**([[ADR-108]] 결정 4 실측) —
  `position` 으로 고를 수 있는 건 "어느 19%를 볼지"뿐이다. 그림 전체를 보이려면 `100% auto` 로
  하단 띠를 만들거나, **캔버스를 폰 비율로 다시 뽑는 것**(종횡비 ≤ 0.46)이 답이다.
- **`position` 이 항상 `center` 인 것은 아니다 — 그림의 대칭축이 그림 한가운데가 아닐 수 있다.**
  새 그림을 붙일 때마다 확인할 것. 검은마법사 맵이 그랬다([[ADR-105]] 결정 3, 그림째 폐기됐지만
  **방법은 남는다**) — 왕좌·눈의 대칭축이 x=413/800(**51.6%**)이라 `center` 로 두면 화면에서
  오른쪽으로 치우쳐 보였다. `cover` 가 세로로 긴 뷰포트에서 그림을 2.6배로 확대해 가운데 150px 만
  보여주므로 원본 13px 어긋남이 화면에서는 **35px(390 폭의 9%)** 가 됐다 — **세로 뷰포트에서는 이
  오차가 배율만큼 증폭된다**는 것이 요점이다. 재는 법은 그림을 좌우 반전해 겹쳐 보고(미러 상관) 오차가
  최소가 되는 x 를 찾는 것이고, 그 x 를 퍼센트로 옮기면 된다(확대 배율이 커서 결과 퍼센트는 뷰포트
  비율에 거의 안 흔들린다 — 검은마법사는 폭 360~430 에서 ±2px 였다). **그림을 다시 자르지 않는다** —
  헤더 조각이 같은 에셋을 같은 기하로 그리므로 에셋을 바꾸면 양쪽을 함께 맞춰야 한다.
- **값은 눈으로 맞춘다** — 수치로 고를 수 없다(어느 크롭에서 수정·달이 보이는지는 뷰포트 비율까지
  걸린다). 확정 값은 `job-themes.json` 의 `background` 블록에 사람이 넣는다([[ADR-006]] — 확인은
  사람이 한다). 이 조정에 쓰던 `/debug/theme-background` 화면은 **삭제됐다**(디버그 도구는 만들고 쓰고 지운다) —
  값을 다시 만질 일이 생기면 도구 복원이 선행돼야 한다(옛 구현은 `git log` 참고).
- **에셋 해석**: `lib/theme-backgrounds.ts` 가 **커밋된 목록**(`src/assets/generated/themes.ts`)에서
  슬러그→에셋을 찾는다([[ADR-129]] — 일일 퀘스트 지역 배경 `lib/daily-quest-backgrounds.ts` 와 같은
  방식이고, 확장자 혼재와 macOS NFD 파일명도 같은 이유로 같은 처리를 한다). JSON 은 번들 경로를
  모른다. 그림을 넣거나 지우면 **`npm run assets:gen` 을 돌려야** 목록이 따라오고, 안 돌리면
  `src/assets/generated/__tests__/asset-manifest.test.ts` 가 빨개진다. **목록에 든 파일은 어느 테마도
  안 써도 번들에 실리므로** 쓰지 않게 된 그림은 파일째 지워야 실제로 빠진다(ADR-106 결정 2).
- **테스트는 "배경 있는 테마"를 데이터에서 고르지 않는다**(ADR-106 결정 3·4). 선언이 0건이어도
  기계장치(`--theme-bg-*` 방출 · 슬러그 미해석 폴백 · 백드롭 렌더 분기)는 계속 검사돼야 하므로,
  있음 쪽 사례는 **테스트가 픽스처로 만들고**(`theme-registry.test.ts`) 컴포넌트 쪽은
  `getThemeDefinition` 을 부분 모킹해 주입한다(`App`·`PageHeader`·`ThemeBackdrop` 테스트).
  없음 쪽은 진짜 테마 여섯으로 계속 실물 검사한다. 선언이 0건이면 뜻이 없어지는 전수 검사는 통과가
  아니라 **`it.skipIf` 로 skip** 이다 — "검사했고 괜찮다"와 "검사할 것이 없다"를 리포트에서 가른다.
- **깔리는 방식**: `components/templates/ThemeBackdrop` 이 **한 장**을 셸의 **첫 자식**으로 깐다
  ([[ADR-088]] 결정 4). RN 은 형제 순서가 곧 그리는 순서라 음수 z-index 가 필요 없고, 웹이 그것을
  쓰느라 겪던 함정(*"루트의 `bg-bg` 를 빼야 이미지가 보인다"*)도 함께 사라졌다.
- **`cover` 와 위치는 좌표로 계산한다**(`theme-backdrop-layout.ts`) — CSS `background-size/position`
  이 없기 때문이고, 그 계산을 여러 자리가 **공유하는 것**이 이음매를 없애는 조건이다. `dim` 은 그림
  위에 덮는 검정 한 겹이고 값·자리는 웹과 같다.
- **헤더 자리에 따로 칠하지 않는다**([[ADR-133]] — [[ADR-088]] 결정 5-1 폐기). 배경은 **벽지 한 장**
  뿐이고, 헤더도 그 위를 함께 스크롤한다([[ADR-131]] — 고정 영역이 없다). 웹 시절 `ThemeHeaderBackdrop`
  이 헤더 몫의 배경 조각을 따로 그리던 구조는 사라졌다.
- **화면이 자기 벽지를 들고 다니는 경우가 있다**([[ADR-134]] 정정 5, `theme/screen-backdrop-policy.ts`)
  — 한 장으로 깔려면 그 위 내비게이션 화면들이 **투명**해야 하는데, 안드로이드에서는 전환 중 두 화면이
  겹치는 동안 **위 화면 너머로 아래 화면 글자가 비친다**(실기기 확인). iOS 에는 그 증상이 없어
  **양쪽 모습을 함께 바꾸지 않는다** — 안드로이드에서만 화면을 불투명하게 하고 벽지를 화면마다 들려
  보낸다.
- **카드는 불투명을 유지한다.** 반투명 카드는 카드 안 텍스트 대비가 배경 그림 위치마다 달라져
  이 문서의 대비 계측이 뜻을 잃는다([[ADR-088]] 결정 6).

## 카테고리와 선택 목록 ([[ADR-104]], 2026-08-06)

테마는 **카테고리 하나**에 속한다. 값은 `job-themes.json` 의 `category` 필드(문자열 한 개)이고, 소속은 게임 도메인이라 **사용자 확인으로 정한다**([[ADR-006]]).

| 카테고리 | 테마 | 뜻 |
|---|---|---|
| `기본` | 머쉬맘 · 혼테일 | 앱이 기본값으로 쓰는 라이트/다크 두 종 |
| `직업` | 렌 · 엔젤릭버스터 · 레테 | 캐릭터 대표 컬러에서 온 테마. 앞으로 수십 종이 여기로 들어온다 |
| `보스` | 검은마법사 | 보스에서 온 테마 |

- **겹침은 없다.** 머쉬맘·혼테일은 보스이기도 하지만 "앱의 기본 라이트/다크"라는 역할이 우선이라 `기본` 에만 둔다. 겹침을 허용하면 `category` 가 배열이 되고 같은 테마가 목록에 두 번 나온다 — 지금 필요한 최소는 문자열 한 개다.
- **표시 순서 = 카테고리 순서(`기본` → `직업` → `보스`) → 그 안에서 JSON 키 순서.** 카테고리 순서는 색 데이터에서 유도할 수 없는 **프로덕트 결정**이라 JSON 이 아니라 `theme-registry.ts` 에 상수로 둔다(`DEFAULT_THEME` 과 같은 자리). JSON 에 순서 번호를 넣으면 테마를 추가할 때마다 번호를 다시 매기게 된다.
- **선택 목록은 2열 프리뷰 타일**이다. 타일이 그 테마의 `bg` 위에 `surface`·`surface2`·`primary` 로 미니 화면을 그리고 이름을 그 테마의 `text` 색으로 얹는다 — 이름이 아니라 **화면을 보고** 고르게 하는 것이 목적이다. 이름 옆 ☀/☾ 가 `mode`.
- **라이트·다크는 섹션이 아니라 필터다.** 카테고리와 모드는 직교하는 축이라 둘 다 제목이 될 수 없다. 목록 위 칩 **전체 · 라이트 · 다크**(기본 전체), 상태는 **저장하지 않고**(모달을 닫으면 전체로 복귀), 거른 결과가 **0인 카테고리 섹션은 헤더째 감춘다**. 현재 선택된 테마가 필터에서 빠지는 것은 정상이다.
- **목록에 배경 이미지는 쓰지 않는다.** 앱의 `dim`(0.82/0.78)은 전체 화면 기준이라 92px 타일에 그대로 덮으면 검은 띠고, 노출하려면 썸네일용 `dim` 을 새로 관리해야 한다. 배경은 테마를 적용한 뒤 화면 전체로 보는 것이 자리다.

## 테마 추가 방법
`src/data/job-themes.json` 에 블록 하나를 추가하면 끝난다([[ADR-064]] 결정 10). `ThemeName` 은 JSON 키에서 추론되고, 타입 가드·`THEME_OPTIONS`·라이트/다크 판정·CSS 변수 주입이 모두 이 파일을 따라간다. 개별 파일을 손으로 동기화하지 않는다. 블록에는 **`category` 한 줄이 함께** 들어간다([[ADR-104]]) — 값은 사용자에게 확인하고 넣는다.

회귀 테스트는 값을 나열하지 않고 **스키마(34필드 + `mode` + `category`) + 파생 규칙**을 검사한다([[ADR-064]] 결정 11) — 테마가 늘어도 테스트가 늘지 않는다. **겨냥함**으로 표시한 항목만 대비를 확인하고, 나머지는 계측해 보여주기만 한다.

## 테마 토큰을 쓰지 않는 영역 (의도적)
아래는 테마를 따라가지 **않는** 것이 맞다. 정규화 대상으로 오해하지 말 것([[ADR-064]] 적용 범위 밖).

- **`components/DifficultyBadge`** — 5난이도 하드코딩 팔레트. 게임 고유 난이도 색이라 테마를 따라가면 의미가 깨진다([[ADR-006]] 도메인 데이터).
- **고가 드롭 골드 연출** — `app/boss-profit/valuable-card-glow.ts`·`valuable-row-glow.ts`(`#f7d00d` 계열). 전 테마 공통 네온 골드.
- **네이티브 브랜드색** — 스플래시 배경 `#F58B0F` 하나(`app.json` 의 `expo-splash-screen` 블록 → Android `values/colors.xml`·iOS colorset, [splash.md](./splash.md)). 앱 실행 전이라 선택 테마를 모르는 시점이다. 선택 테마를 스플래시에 반영할지는 별도 결정.

## 열린 질문
- **직업 테마의 단위** — 직업 대분류인가 5차 전직 세부인가. 테마 이름과 실제 직업(전직) 매핑도 함께 미정이다. 카테고리 분류([[ADR-104]])는 이 답에 의존하지 않는다(어느 쪽이든 `category: "직업"`).
- 선택 테마를 네이티브 스플래시·부트 커버에 반영할지.
