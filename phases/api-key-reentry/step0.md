## 배경 — 실측으로 확인된 사실 (이 결정의 근거이니 그대로 문서에 옮겨라)

**이슈 #157 이 "선행 확인 항목"으로 남긴 질문**: 저장소에 키만 없고 `selectedAccountId`·트래킹 모드·
추적 목록은 남은 상태에서 재개가 어느 단계로 떨어지는가?

실측 결과 **두 구간으로 갈린다**:

| 구간 | 실제 동작 |
|---|---|
| 부팅 시 | `getAuthConfig()` 가 apiKey 없으면 **나머지를 읽지도 않고** null 반환(`storage/api-key.ts:6-17`) → `restoreFromStorage` 조기 반환 → `awaitingApiKey` → App 가드가 `/onboarding` 으로 보냄 ✅ |
| **키 재입력 후** | `submitApiKey` → `API_KEY_VERIFIED` → 리듀서가 **무조건** `selectingAccount` 로 가고 `selectedAccountId` 를 null 로 리셋(`state.ts:97-106`) → 계정 선택 → 전체 예열([[ADR-016]]) → 모드 → 캐릭터를 **전부 다시 묻는다** ❌ |

즉 이슈가 전제한 "키 입력만 하고 나머지는 건너뛴다"는 **지금 성립하지 않는다.** 재개 파생([[ADR-086]]
결정 1)이 **부팅 경로에만** 있고 키 입력 성공 경로에는 없기 때문이다. 저장소에는 값이 그대로 남아
있는데도 다시 묻는다.

**부수 발견**: `App.tsx:295-344` 가드가 이미 `status !== 'completed'` 면 모든 라우트를 라우터로
`/onboarding` 에 보낸다. 그래서 **온보딩 상태를 뒤집는 것만으로 이동이 일어난다** — 스토어가
라우터를 알 필요가 없고 `window.location` 도 필요 없다([[ADR-050]] 자동 충족). "훅에서 토스트를
띄우는 이유는 액션이 라우터를 필요로 해서"라는 `use-sync-error-toast.ts:15-17` 의 전제도 사라진다.

## 작업

### 1. `/docs/adr/ADR-115.md` 신설

기존 ADR 파일(예: `/docs/adr/ADR-114.md`)의 형식을 그대로 따르라 — 제목 줄, **배경**, **결정 N**,
**이유**, **트레이드오프**, 상태 표기. 제목 상태는 **`(설계 확정 · 구현 전, 2026-08-08)`** 으로 적고
step 6 이 '구현 완료'로 바꾼다.

제목: `ADR-115: API 키 무효화(401/403) → 토스트 + 키 입력 화면 자동 이동, 뒤 단계는 저장된 값으로 재개`

담아야 할 결정 (**사용자와 확정된 것이다 — 임의로 바꾸지 마라**):

**결정 1 — 401/403 을 만나면 토스트 한 줄을 띄우고 곧바로 키 입력 화면으로 보낸다.**
- 사용자가 액션을 누를 때까지 기다리지 않는다. **토스트에 액션 버튼을 두지 않는다** — 이동이 이미
  일어났으므로 누를 것이 없다(`error-resilience.md` 원칙 3 "원인을 실제로 푸는 행동만 액션으로 준다"와
  일치). 지금의 `설정 열기` 액션(`use-sync-error-toast.ts:49-56`)은 제거된다.
- 문구는 **`API 키가 더 이상 유효하지 않습니다`** 다. 이슈 초안의 `"키가 더 이상..."` 에 **`API `** 를
  붙여 앱 카피 규약에 맞춘다 — 다른 자리가 전부 `API 키` 로 쓴다(`schedule-sync/format.ts:13`,
  `app/settings/error-message.ts:6`, `features/onboarding/format.ts`).
- **대가를 인지하고 고른 것이다**: 작업 중이던 화면을 빼앗는다. 다만 무효 키 상태에서는 어느 화면도
  제 기능을 못 하므로 남겨 둘 화면이 없다.

**결정 2 — 이동은 "온보딩 상태를 뒤집는 것"으로 일어난다. 스토어는 라우터를 모른다.**
- `App.tsx:295-344` 의 `isCompleted` 가드가 이미 라우터로 `/onboarding` 에 보낸다(위 "부수 발견").
- `window.location` 을 쓰면 문서가 리로드돼 네이티브 SQLite 커넥션이 stale 하게 남는다([[ADR-050]]).
  이 결정은 그 함정을 **피하는 것이 아니라 애초에 만나지 않는다**.
- 복귀 화면은 기존 온보딩 완료 규칙 그대로 **`/content`** 다. 이탈 라우트를 기억했다 되돌리지 않는다 —
  그 상태를 새로 만들어야 하고 기존 완료 규칙과 충돌한다.

**결정 3 — 무효 키는 저장소에서 지운다. 단 `apiKey` 키 하나만.**
- `selectedAccountId`·`trackingMode`·`trackedCharacters` 는 **남긴다** — 무효화된 것은 키 하나뿐이므로
  나머지를 지울 이유가 없고, 결정 4 의 재개가 그 값들을 쓴다.
- 기존 `clearAuthConfig()` 는 `selectedAccountId` 까지 지우므로 **쓰면 안 된다**(그것은 연결 해제용이다).
- 지우는 이유: 안 지우면 앱을 재시작했을 때 무효 키로 다시 `completed` 로 복귀하고, 첫 동기화에서 또
  401 을 맞아 다시 튕긴다. 사용자에게는 "재시작하면 되는 것처럼 보이다가 안 되는" 상태가 된다.
- **알려진 열화**: 저장소 삭제 자체가 실패하면(디스크 등) 화면은 키 입력으로 가지만 재시작 시 옛
  무효 키가 되살아난다. 그때는 다시 이 경로를 탈 뿐이라 막다른 길이 아니므로 별도 처리를 두지 않는다.

**결정 4 — 키를 다시 넣으면 뒤 단계는 저장된 값으로 재개한다.**
- 계정 선택·트래킹 모드·추적 캐릭터를 **다시 묻지 않는다.**
- 구현은 [[ADR-086]] 결정 1 의 재개 파생표를 **`submitApiKey` 성공 경로에도 적용**하는 것이다. 파생
  판정은 **함수 하나**로 두고 부팅(`restoreFromStorage`)과 공유한다 — 두 벌이 되면 재개 규칙의 진실이
  둘이 된다(그것이 [[ADR-086]] 결정 1 이 진행 상태 전용 키를 거부한 바로 그 이유다).
- **예열([[ADR-016]])을 다시 돌리지 않는다** — 캐시가 이미 따뜻하다([[ADR-086]] 결정 1 과 같은 근거).

**결정 5 — 재개에는 계정 목록 대조 가드가 붙는다.**
- 새로 넣은 키가 **다른 넥슨 계정의 키**일 수 있다. 검증 때 이미 받는 `character/list` 응답에 저장된
  `selectedAccountId` 가 들어 있는지 확인해, **없으면 재개하지 않고 기존대로 계정 선택부터** 간다.
- 가드가 없으면 남의 계정 키로 이전 계정 ocid 추적 목록을 그대로 쓰게 된다(계정 불일치 상태).
- 추가 호출은 없다 — 이미 손에 있는 응답으로 판정한다.

**결정 6 — 멱등성은 "`completed` 일 때만 무효화가 성립한다"로 얻는다.**
- 여러 화면·여러 캐릭터에서 401 이 동시에 터져도 **토스트 1회 · 이동 1회**다. 첫 호출이 상태를
  `awaitingApiKey` 로 뒤집으면 뒤따르는 호출은 가드에 걸려 아무 일도 하지 않는다.
- **키 입력 화면에서 다시 401 이 나는 경우는 이 경로가 아니다** — 그때 상태는 `completed` 가 아니므로
  같은 가드가 막는다. 재이동 루프가 구조적으로 불가능하고, 그 실패는 폼 자체의 에러 처리로 남는다
  ([[ADR-065]] 결정 1 의 토스트).

**결정 7 — 401 감지 지점 전부가 이 진입점 하나를 부른다.**
- 대상: 스케줄러 3화면 동기화 토스트(`use-sync-error-toast`) · 캐릭터 피커 로스터 조회
  (`ErrorState`·스탈 배너) · 설정 계정 변경 모달(`refreshAccounts` — 저장된 키로 재조회하다 맞는 401 도
  키 무효화다).
- 그 자리들의 **`설정 열기` 액션은 전부 제거된다.** 그래서 [[ADR-062]] 결정 3 의 *"401 은 설정으로
  보낸다"* 는 **폐기**되고 *"401 은 키 입력 화면으로 보낸다(자동)"* 로 대체된다. 목적지가 바뀐 이유는
  단순하다 — **설정에는 키를 바꿀 자리가 없다**(2026-07-25 제거, `settings.md` 폐기 이력).
- [[ADR-008]] 의 *"401/403 → 설정에서 다시 입력해주세요 배너"*(미구현 보류)도 **배너 없이 자동 이동**
  으로 대체된다. 배너를 새로 만들지 않는다.

**결정 8 — 설정의 "API 키 변경" 행은 이번에 부활시키지 않는다.**
- 무효화가 아닌데 키를 바꾸고 싶은 경우는 이슈 #157 의 미정 3 이고 **#135(설정 구조 개선)와 함께
  본다.** `useSettingsStore.changeApiKey`(로직·테스트가 살아 있다)는 **배선하지 않고 그대로 둔다** —
  그 경로의 401 은 "사용자가 방금 나쁜 키를 입력한 것"이라 무효화 경로와 성질이 다르다.

**이유**·**트레이드오프** 절도 채워라. 트레이드오프에는 최소한 이 셋을 담아라: ① 작업 중이던 화면을
빼앗는다 ② 저장소 삭제 실패 시의 열화(결정 3) ③ 401 판정이 잘못되면 유효한 키를 지운다(`NexonAuthError`
는 401/403 에서만 만들어지므로 감수한다).

### 3. `/docs/features/onboarding.md` — "단계 재개" 절 갱신

현행 재개 파생표(22~28행 부근)는 **부팅 경로만** 설명한다. 아래를 반영하라:

- 표는 그대로 두되, 그 표가 **부팅과 키 재입력 두 경로에 함께 적용된다**는 것을 명시하라([[ADR-115]]
  결정 4). "재개 지점은 저장된 값에서 파생한다"는 원문 문장이 이제 두 경로를 덮는다.
- **키 재입력 경로**를 소절로 추가하라: 401/403 으로 키가 지워진 뒤 사용자가 키를 다시 넣으면
  `selectingAccount` 로 가지 않고 저장된 값이 가리키는 단계(대개 `completed`)로 곧바로 간다. 예열은
  다시 돌지 않는다.
- **계정 목록 대조 가드**(결정 5)를 적어라 — 새 키의 `character/list` 에 저장된 `selectedAccountId` 가
  없으면 재개하지 않고 계정 선택부터.
- 무효화 자체(토스트·자동 이동)는 온보딩 기능 문서가 아니라 `error-resilience.md` 가 원문을 갖고, 여기
  서는 재개 쪽만 다루고 링크로 넘겨라(문서 중복 금지).

### 5. `/docs/foundation/error-resilience.md` — 401 정책 갱신

- **실패 모드 표의 401/403 행(40행)**: 현행은 *"캐시 유지, 전역 `apiKeyInvalid: true` → 설정 진입 유도
  배너. 무효 키 자동 재시도 금지"* 다. **캐시 유지와 자동 재시도 금지는 그대로**이고, 처방을 *"토스트
  1회 + 키 입력 화면 자동 이동, 저장된 `apiKey` 만 삭제"* 로 바꿔라([[ADR-115]] 결정 1·3).
- **원칙 3(12행)** 의 *"401 에 '다시 시도'를 주는 것은 … 금지 — 설정으로 보낸다"* 에서 **목적지를
  고쳐라**. 원칙("그 원인을 실제로 푸는 행동만 액션으로 준다")은 그대로이고, 401 은 이제 **액션조차
  주지 않는다**(이동이 이미 일어났으므로 누를 것이 없다).
- 45행(`character/list` 조회 실패)·46행(전역 실패)이 401 처리로 귀결된다고 적은 부분이 새 처방과
  어긋나지 않는지 확인하고, 어긋나면 맞춰라.
- 이 문서 하단 **"폐기된 정책 (history)"** 절에 [[ADR-062]] 결정 3 의 목적지 변경을 한 줄로 남겨라
  (절이 없으면 `docs/README.md` 규약대로 만들어라).
