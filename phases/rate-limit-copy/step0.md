## 배경 — 무엇을 문서화하는가 (이슈 #158)

### 증상

테스터 일부에게 **캐릭터 관리 피커에 캐릭터가 거의 뜨지 않는다.** 추적 중인 대표 캐릭터 1명만
남고 그 위에 **"목록이 최신이 아닙니다"** 배너가 뜬다. 원인은 **개발 단계 API 키의 호출 한도
초과(429)** 로 확인됐다(2026-08-07).

### 전제가 틀렸다

`docs/foundation/nexon-api.md:10` 은 이렇게 적혀 있다:

> 개발 단계 초당 5건/일 1,000건, 서비스 단계 초당 500건/일 2,000만 건. **이 앱은 사용자가 이미
> 승인받은 서비스 단계 키를 쓰므로** 개발 단계 상한 검증은 불필요.

이 문장은 **개발자 본인 키에만** 맞다. 테스터·사용자는 각자 `openapi.nexon.com` 에서 발급받은
**개발 단계 키**(초당 5건 / 일 1,000건)를 넣는다. 이 전제 위에 [[ADR-008]] 의 "병렬 호출이 한도와
충돌하지 않는다"가 서 있었다.

### 이 이슈가 고치는 것은 "문구"다

429 가 세 자리에서 서로 다르게 뭉개진다.

**(a) 스탈 배너가 원인을 무시한다** — `StaleBanner.tsx:12-15` 은 `message: string` 과
`onRetry: () => void` 를 받고 `loadError.kind` 를 보지 않는다. 호출부 2곳
(`CharacterTrackingPicker.tsx:59` · `ContentCharacterStep.tsx:46`)이 `"목록이 최신이 아닙니다"` 를
하드코딩한다. **401·429·네트워크·조회 불가가 전부 같은 한 줄로 보이고**, 배너는 무조건 "다시 시도"
버튼을 붙인다 — `error-resilience.md` 원칙 3("401에 다시 시도 금지 · 429에는 액션을 주지 않는다")과
어긋난다.

**(b) 429 문구가 잘못된 처방을 준다** — 현재 4곳이 전부 "잠시 후 다시 시도해주세요" 계열이다.
개발 단계 키에는 **틀린 안내**다: 일 1,000건을 넘긴 것이면 다음 날까지 안 풀리고, 초당 5건이면
앱이 버스트를 쏘는 한 재시도해도 또 429다. 실제 해결책은 **넥슨 개발자 센터에서 서비스 단계
신청**인데 아무도 그 말을 하지 않는다.

### 열린 결정은 이미 닫혔다 — A안(판정하지 않는다)

넥슨 API 는 키의 단계를 알려주지 않아 429 만으로 개발/서비스 단계를 구분할 수 없다. 세 안 중
**A(판정하지 않는다)** 를 사용자가 채택했다(2026-08-08). 429 문구를 단계 무관하게 고쳐 "입력하신
API 키가 서비스 단계 키인지 확인해주세요"의 뜻을 담는다. 추가 호출 0회·오탐 없음, 대신 서비스
단계 사용자에게도 같은 문구가 보인다.

기각된 두 안: **B(온보딩에서 프로브)** — 일부러 429 를 내는 설계이고 온보딩에 호출·시간이 붙는다.
**C(429 발생 관측 누적)** — 추가 호출은 없으나 상태와 판정 규칙이 새로 생긴다. 둘 다 **감지 자체가
목적이 아니라 사용자가 다음 행동을 아는 것이 목적**이라는 점에서 값이 비용을 못 넘는다.

### 사용자가 확정한 문구 (2026-08-08)

수치(초당 5건·일 1,000건)는 **넣지 않는다** — 서비스 단계 사용자가 봐도 어색하지 않고, 좁은
자리에도 같은 문구를 쓸 수 있다.

| 자리 | 429 문구 | 액션 |
|---|---|---|
| `ErrorState`(피커·온보딩, 목록이 아예 없을 때) | 제목 **호출 한도를 초과했습니다** / 설명 **입력하신 API 키가 서비스 단계 키인지 확인해주세요** | 없음 |
| `StaleBanner`(목록이 있을 때) | **호출 한도를 초과했습니다 — 서비스 단계 키인지 확인해주세요** | 없음 |
| 설정 계정 카드(인라인) | **호출 한도를 초과했습니다. 입력하신 API 키가 서비스 단계 키인지 확인해주세요** | 없음 |
| 토스트(스케줄러 3화면·온보딩) | **호출 한도를 초과했습니다** | 없음(현행) |

**토스트만 짧은 이유**: `Toast.tsx:88` 의 본문이 `truncate` 라 한 줄을 넘기면 잘린다. 처방은 목록
자리(배너·`ErrorState`)와 설정 카드가 준다 — 토스트는 원인만 말한다.

### 스탈 배너 분기 규칙 (사용자 확정)

배너는 **재시도가 실제로 통하는 실패에만** 액션을 준다. `ErrorState` 와 갈리는 근거는 자리다 —
배너는 목록이 남아 있어 액션이 없어도 막다른 길이 아니다.

| 원인 | 배너 문구 | 피커 | 온보딩 |
|---|---|---|---|
| `invalidApiKey` | API 키가 유효하지 않아 목록을 갱신하지 못했습니다 | 설정 열기 | 없음 |
| `rateLimited` | 호출 한도를 초과했습니다 — 서비스 단계 키인지 확인해주세요 | 없음 | 없음 |
| `characterUnavailable` | 이 계정의 캐릭터를 조회할 수 없습니다 | 없음 | 없음 |
| `network`·`periodOutOfRange`·`notCollected` | 목록이 최신이 아닙니다 *(현행 유지)* | 다시 시도 | 다시 시도 |

### 범위 밖 (이슈가 명시적으로 분리한 것)

- **(c) 자격 스윕이 429 를 삼켜 캐릭터가 조용히 사라지는 문제**(`character-eligibility.ts:90-102`) —
  문구가 아니라 목록이 비는 원인이다. 별도 버그.
- **로스터·예열 경로의 프리플라이트·동시성 캡 부재** — 429 를 애초에 덜 나게 하는 쪽.
  [[ADR-008]] 전제 재검토와 함께 별도.
- `character/basic` 3라운드 중복 제거는 **이미 끝났다**([[ADR-113]], 이슈 #163).

## 작업

### 1. `/docs/adr/ADR-114.md` 신설

기존 ADR 파일(`ADR-112.md`·`ADR-113.md`)의 서식을 따라라 — 제목 행, `**날짜**`·`**상태**`·`**관련**`
메타 3줄, `## 맥락`, `## 결정`, `## 기각안`, `## 대가/트레이드오프`, `## 검증` 구조.

- **날짜**: 2026-08-08
- **상태**: **설계 확정 · 구현 전**, 2026-08-08, 이슈 #158 (step 6 이 '구현 완료'로 마감한다)
- **관련**: [[ADR-062]] 결정 3·4 · [[ADR-063]] · [[ADR-008]] · [[ADR-067]] 결정 1 · [[ADR-083]] 결정 2 ·
  이슈 #158

**적어야 할 결정 5개** (표현은 재량이나 내용은 그대로):

1. **429 는 키의 단계를 판정하지 않고 문구로만 안내한다**(A안). 넥슨 API 가 단계를 알려주지 않고
   429 만으로는 구분이 불가능하다. **감지가 목적이 아니라 사용자가 다음 행동을 아는 것이 목적**이라
   문구 한 벌로 끝낸다. 확정 문구는 위 표 그대로 적어라.
2. **429 에는 액션을 주지 않는다** — [[ADR-062]] 결정 3 의 "429의 재시도 버튼은 비활성화하지
   않는다(사용자 결정 2026-07-30)"를 **폐기**한다. 그 결정은 "초당 한도라면 잠시 뒤 재시도가
   통한다"를 전제했는데, 일 1,000건 소진이면 다음 날까지 안 풀리고 새 문구의 처방은 재시도가
   아니라 **키 단계 확인**이다 — 버튼이 문구와 어긋난다. `error-resilience.md` 원칙 3 과도 일치한다.
3. **스탈 배너가 원인별로 갈린다.** `StaleBanner` 는 계층(molecule)을 지키기 위해
   `ScheduleSyncError` 를 받지 않고, **호출부가 `features/schedule-sync/format.ts` 의 새 함수
   `formatStaleRosterError(error, place)` 로 문구·액션을 뽑아 넘긴다.** 배너의 액션 규칙은 위 표
   그대로이고, 그 근거는 **"배너는 목록이 남아 있어 액션이 없어도 막다른 길이 아니다"** 이다.
   같은 401 이 `ErrorState`(온보딩)에서는 재시도를 유지하는 이유도 같은 근거의 뒷면이다 — 그쪽은
   목록이 없어 액션을 빼면 화면에 아무 길도 없다.
4. **토스트는 원인만, 인라인은 처방까지.** `Toast.tsx:88` 본문이 `truncate` 라 한 줄이 상한이다.
   `truncate` 를 풀어 전 토스트의 레이아웃 규칙을 바꾸는 대신, **자리마다 담을 수 있는 만큼**
   담는다([[ADR-063]] 의 "자리가 문구를 정한다"와 같은 계열).
5. **`nexon-api.md` 의 "서비스 단계 키 전제"를 정정한다.** 사용자는 각자 발급받은 **개발 단계**
   키를 쓴다. [[ADR-008]] 의 "병렬 호출이 한도와 충돌하지 않는다"가 이 전제 위에 서 있었다는 것도
   함께 적어라 — **다만 프리플라이트·동시성 캡 도입은 이 ADR 의 범위가 아니다**(별건).

**기각안** (이유와 함께):

- **B. 온보딩 키 검증 때 단계를 프로브한다** — 짧은 간격 연속 호출로 추정. 확실하지만 온보딩에
  호출·시간이 붙고, **일부러 429 를 내는 설계**다.
- **C. 429 발생 횟수·간격을 누적해 "개발 단계로 보인다" 플래그를 세운다** — 추가 호출은 없으나
  상태와 판정 규칙이 새로 생기고, 판정이 서기 전 첫 429 에는 여전히 틀린 문구가 나간다.
- **`Toast` 본문의 `truncate` 를 `line-clamp-2` 로 바꿔 전 자리에 같은 문구를 쓰기** — 429 하나
  때문에 모든 토스트의 레이아웃 규칙이 바뀐다.
- **문구에 수치(초당 5건·일 1,000건)를 넣기** — 서비스 단계 키 사용자에게는 관계없는 숫자이고,
  배너 한 줄에 들어가지 않는다.
- **`StaleBanner` 가 `ScheduleSyncError` 를 직접 받기** — molecule 이 feature 어휘를 알게 된다.
  포맷은 호출부가 하고 배너는 문구·액션만 받는다([[ADR-094]] 결정 2 의 계층 방향).

**대가/트레이드오프**:

- **서비스 단계 키 사용자도 "서비스 단계 키인지 확인해주세요"를 본다.** A안을 고른 값이 이것이다 —
  오탐 대신 **무해한 잉여 안내**를 택했다.
- **429 에서 사용자가 앱 안에서 할 수 있는 일이 없어진다**(버튼이 사라진다). 실제로 할 수 있는 일이
  없었던 것을 화면이 인정하는 것이라 후퇴가 아니다.
- **토스트와 인라인의 429 문구가 다르다.** 같은 원인에 두 문구가 생기는 것은 비용이지만, 잘린
  문구보다는 낫다.
- **일 한도 소진과 초당 한도를 구분하지 않는다.** 429 응답에 그 구분이 없다.

**검증** 절에는 "무엇을 자동 테스트가 담보하고 무엇이 실기기·실사용으로만 확인되는가"를 나눠 적어라
(실제 수치는 step 6 이 채운다). **개발 단계 키로 실제 429 를 재현해 배너를 확인하는 것은
실기기·실사용 몫**이라는 것을 명시하라.

### 4. `/docs/foundation/error-resilience.md` 갱신

- **원칙 3**(12행)에 429 의 처방이 "잠시 후 재시도"가 아니라 **키 단계 확인**이라는 것과, 그래서
  429·401 에는 배너에도 재시도를 붙이지 않는다는 것을 한 줄 덧붙여라([[ADR-114]] 결정 2·3).
  **스탈 배너도 원인별로 갈린다**는 사실을 명시하라 — 지금 이 원칙의 마지막 문장("보여줄 항목이
  있으면 그 위에 스탈 배너를 얹는다")은 배너가 원인을 무시해도 되는 것처럼 읽힌다.
- **429 행**(39행)의 **"평소 초당 5건 큐잉으로 애초에 거의 안 만남"** 은 사실과 다르다(로스터·예열
  경로에는 큐잉·프리플라이트가 없다). 실제로 만나는 실패임을 반영해 고치고, 옛 문장은 history 절로
  옮겨라. 처리 칸에는 새 문구 정책을 가리켜라.
- **엣지 케이스** 절에 "개발 단계 키의 일 한도 소진은 다음 날까지 풀리지 않는다 — 재시도로 풀리는
  실패가 아니다" 한 줄을 넣어라.

### 5. `/docs/foundation/design-system.md` 갱신

- **185행 "429의 재시도 버튼은 비활성화하지 않는다(사용자 결정)."** → **액션 자체를 주지 않는다**로
  고쳐라([[ADR-114]] 결정 2). 옛 문장은 history 절로.
- **"스탈 배너" 절**에 배너가 원인별 문구·액션을 받는다는 것과, **액션이 없을 수 있다**는 것을
  적어라(지금은 "다시 시도"가 고정인 것처럼 적혀 있다).

### 6. `/docs/features/content-scheduler.md` 갱신

- **34행**의 스탈 배너 설명("목록이 최신이 아닙니다" + 다시 시도)을 원인별 표로 고쳐라 — 위
  "스탈 배너 분기 규칙" 표를 그대로 옮기면 된다. `network` 계열만 옛 문구를 유지한다는 것을 명확히.
- 로스터 실패 절(36행 부근)의 **"`rateLimited`·`network` 는 다시 시도"** 를 **`network` 만
  다시 시도**로 고쳐라.
- 옛 표현은 이 문서 하단 history 절로 옮겨라.

### 7. `/docs/features/settings.md` 확인

설정 계정 플로우의 `error` 카드(`AccountFlowStatus.tsx:99-115`)가 원인과 무관하게 "다시 시도"를
단다. **429 일 때만 그 버튼을 빼는 것**이 step 5 에 포함되므로, 이 문서에 그 정책을 한 줄 적어라
(절이 없으면 계정 변경 절 안에). 문구도 함께 적어라("호출 한도를 초과했습니다. 입력하신 API 키가
서비스 단계 키인지 확인해주세요").

### 8. `/docs/features/onboarding.md` 확인

429 문구를 언급하는 자리가 있으면 갱신하라. **없으면 손대지 마라** — 억지로 넣지 말고, 안 넣었다면
그 판단을 summary 에 적어라. "열린 질문" 절도 읽고 이번 결정으로 닫히는 항목이 있으면 제거하라.

## 금지사항

- **`src/` 아래 어떤 파일도 수정하지 마라.** 이유: 이 프로젝트는 docs-first 이고, 코드 변경은
  step 1~5 가 각자의 좁은 범위로 한다. 여기서 코드를 건드리면 어느 결정이 어느 변경을 낳았는지
  추적이 끊긴다.
- **옛 정책 문장을 삭제하지 마라.** 이유: `CLAUDE.md` 규칙 — 정책을 바꿀 땐 각 문서 하단
  "폐기된 정책 (history)" 로 **이동**한다.
- **자격 스윕(`character-eligibility.ts`)·프리플라이트·동시성 캡을 이 ADR 의 결정으로 적지 마라.**
  이유: 이슈 #158 이 명시적으로 별건으로 분리했다. 맥락으로 언급하는 것은 되지만 **결정 항목으로
  올리면** 다음 step 이 범위를 넘겨 구현한다.
- **ADR 전문을 여러 개 컨텍스트에 올리지 마라.** 이유: `CLAUDE.md` 규칙. 위에 지정한 4개만 열어라.
- **`docs/adr/` 의 다른 ADR 파일을 수정하지 마라.** 이유: 폐기·정정 사실은 새 ADR 과 인덱스 행,
  그리고 기능 문서의 history 절이 기록한다.
- **새 ADR 번호를 114 이외로 쓰지 마라.** 이유: `docs/adr/` 의 최신은 ADR-113 이다.
